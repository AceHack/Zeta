# Git over SSH to GitLab, on the LAN (port 2222)

> `git clone git@<gitlab>:group/project.git` needs a route to GitLab's own sshd (the `gitlab-shell` pods). Port **22** on the node and on every
> LoadBalancer address is **the node's own sshd** (key-only, user `zeta`), never GitLab. GitLab's `gitlab-gitlab-shell` Service is ClusterIP-only. So
> GitLab's SSH is exposed on **2222**, over every LB address, by the same `externalIPs` mechanism the node relays already use, and GitLab is told to
> advertise 2222 in the clone URLs it shows.

## What is in git

| Piece | Where | What it does |
|---|---|---|
| Service `gitlab-shell-lan` (ns `gitlab`) | written by the `discover` container of `full-ai-cluster/k8s/applications/cluster-hygiene/node-lan-hosts.yaml` ("FIFTH JOB") | `type: ClusterIP`, selector `app: gitlab-shell, release: gitlab` (the chart's own), port `2222 -> 2222`, `externalIPs` = **every LoadBalancer address in the cluster that does not already serve :2222**, recomputed every 30 s. Cilium (kube-proxy replacement) turns each `<ip>:2222` into a frontend for the pods. |
| Role + RoleBinding `node-lan-hosts-gitlab-shell-lan` (ns `gitlab`) | `gitlab-runner.extraObjects` in `full-ai-cluster/k8s/applications/gitlab/Application.yaml` | Lets `discover`'s ServiceAccount (`node-lan-hosts`, ns `zeta-node-hosts`) create that one Service and get/patch/update it by name. Declared **here**, not in cluster-hygiene: cluster-hygiene syncs at wave 20, before namespace `gitlab` exists. |
| `global.shell.port: 2222` | same Application, `valuesObject.global.shell` | The advertised SSH port (`ssh_port` in `gitlab.yml`, so the clone URLs in the UI). Chart 10.4.1 has no other coordinate (`gitlab-shell.service.externalPort` does not exist). |

**No address is in git.** The addresses belong to one home network; `discover` reads them from the cluster (the same way it does for `https-relay`,
`ssh-relay` and `http-relay`), so a rebuilt cluster, or another LAN, gets the right set with no edit. A failed listing keeps the last set (unknown is
not "remove"). Until namespace `gitlab` exists the apply fails quietly and is retried every 30 s.

### What changes on a running cluster when this merges

Measured with `helm template` of chart 10.4.1 against the Application's `valuesObject`, before and after: only `ssh_port: 22 -> 2222` in the
webservice, sidekiq and toolbox ConfigMaps (those three pods roll once, on the existing `maxSurge: 0` strategy: a short web/Sidekiq blip), the
ClusterIP Service `gitlab-gitlab-shell` port `22 -> 2222` (its `targetPort` was and stays 2222), one inert nginx tcp-services ConfigMap key, and
the new Role/RoleBinding. The `gitlab-shell` Deployment itself is **not** restarted. If the Service was first applied by hand (as it was on the
owner's node), `discover` adopts it on its next tick (`--server-side --force-conflicts`, same name, same fields): no gap.

## Using it

LAN clients, `~/.ssh/config`:

```
Host gitlab.flowdent.net
    HostName 192.168.1.250     # any LB address of the cluster works; use the one `kubectl -n gitlab get gateway gitlab-lan` shows
    Port 2222
    User git
    IdentityFile ~/.ssh/id_ed25519
```

then `git clone git@gitlab.flowdent.net:<group>/<project>.git`. Without the config, the URL form is `ssh://git@192.168.1.250:2222/<group>/<project>.git`
(that is what GitLab's UI shows once `global.shell.port` is applied, with the Gateway address as the host). Add your **public** key under
*Preferences -> SSH keys* in GitLab. Check the route: `ssh -p 2222 -T git@192.168.1.250` answers `Welcome to GitLab, @<user>!`.

## Limits (read these)

- **LAN only.** The router does not forward `:2222`, and nothing here opens it. `ssh.flowdent.net:22` from the internet (`docs/ops/SSH-FROM-OUTSIDE.md`)
  reaches the **node's** sshd, not GitLab. To use GitLab SSH from outside the LAN the owner must add a router forward of an external port to the
  node's `:2222` (the same MAC-keyed-router reasoning applies: the node answers `:2222` on every one of its addresses, so any binding works).
  Note that GitLab's sshd then faces the internet and has no per-source rate limit (the `nixos-fw` limit in `node-lan-hosts` covers `:22` only).
- **Port 22 is not GitLab.** Never point a git remote at `:22` of the node or an LB address; it will ask for the `zeta` OS user's key.
- **Host key.** gitlab-shell's host keys live in Secret `gitlab-gitlab-shell-host-keys` (`gitlab` namespace, generated by the chart's
  shared-secrets job only when missing). They survive pod restarts and upgrades; a **rebuilt cluster** generates new ones, so clients see
  `REMOTE HOST IDENTIFICATION HAS CHANGED` once. That is expected after a rebuild, and a surprise any other time: investigate before running
  `ssh-keygen -R`. The node's own sshd has a different key, so a `known_hosts` entry for `[192.168.1.250]:2222` and one for `192.168.1.250` do not conflict.
- **A DNS name is optional.** `gitlab.flowdent.net` in the config above is only a local alias; the `HostName` is what routes. GitLab itself serves
  by address on the LAN (`docs/ops/INSTALL-TIME-CONFIG.md` row 6).
- **Cannot prove from git:** that Cilium honours `externalIPs` on a real node and that a LAN client reaches it. Only the live node did (a clone
  worked from the LAN). The tests below render and execute the manifests; they do not open a socket.

## Falsifiers

- `src/Core.TypeScript/cluster/node-lan-hosts-relay.test.ts` runs the `discover` script against a stub `kubectl`: the Service's namespace, selector,
  port, label and `externalIPs` (every LB address, none from this network when the fixture is another one; an address already serving :2222 is skipped;
  a failed listing applies nothing).
- `src/Core.TypeScript/cluster/gitlab-exposure.test.ts` (j) renders the Application with `helm template`: `ssh_port` is 2222 everywhere, the chart's
  own Service selector and the shell pods' `containerPort` match what `gitlab-shell-lan` targets, the Role is least-privilege, and no `externalIPs`
  is rendered by the release.

## Other live-only settings, findable from here

Two cluster settings and one Deployment exist **live** and are not (all) in this repo; they are recorded so a rebuild does not silently lose them.

- **KubeVirt `vmStateStorageClass: longhorn`** and **CDI `scratchSpaceStorageClass: zeta-block-replicated`**: applied by hand, with the re-apply
  commands, the reason, and the warning that `argocd app sync cdi` reverts the CDI value, in `docs/ops/WINDOWS-11-VMS.md` (the settings block
  before step 1, and "Known issues" 2 and 4). Not repeated here.
- **The flowdent.net website Deployment** is applied from the **fd-webclient** repository's `k8s/flowdent-web/deployment.yaml`, not from this repository (nothing here
  creates it). A rebuilt cluster needs that manifest applied again from fd-webclient.
