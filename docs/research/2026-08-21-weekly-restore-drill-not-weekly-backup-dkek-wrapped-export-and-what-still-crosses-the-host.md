# A weekly restore drill, not a weekly backup — DKEK wrapped export, and what still crosses the host

**Design, 2026-08-21. No device touched, no token contacted, no DKEK, share, PIN or password
handled, nothing applied to a cluster.** Third in the thread with
[`2026-08-21-hands-off-metal-*`](2026-08-21-hands-off-metal-what-a-node-can-provision-for-itself-and-the-three-classes-that-need-a-human.md)

[`2026-08-21-two-hsms-per-node-*`](2026-08-21-two-hsms-per-node-and-n-of-m-across-nodes-what-the-seal-layer-will-actually-accept.md).
Aaron, verbatim:

> *"we need to come up with like a once a week key backup process if possible but we never want to
> let keys be exported to non secure surface like cpu traces, i'm the master of side channel
> attacks we need like a dual hsm usb process for no side channel key leaks, lets start a design on
> this since most hsms just have exportable or not"*

**Human anchor for the threat model** (`.claude/rules/anchor-to-human-prior-art.md`): the
requirement is Aaron's, from building Itron's mesh hardware, firmware, PKI and secure boot — this is
his domain, not a generic security preference. The standard treatments the requirement stands on are
**Kocher, *Timing Attacks on Implementations of Diffie-Hellman, RSA, DSS, and Other Systems*
(CRYPTO '96)** and **Kocher, Jaffe & Jun, *Differential Power Analysis* (CRYPTO '99)** — cited
because §4 needs them to say precisely which side channels this design does and does not close.

## 0. Three answers

1. **"Exportable or not" is a false binary, and the third state is real and measured.** The
   SmartCard-HSM's **DKEK** is a 256-bit AES Device Key Encryption Key, *generated by the device's
   own RNG*, which the device never reveals. A key leaves as `wrap-key.bin` — ciphertext under the
   DKEK — and can be unwrapped only by another device that holds the same DKEK. Plaintext key
   material exists only inside secure elements; the host carries ciphertext.
2. **That property is true of KEY material and false as an unqualified sentence.** §3 attacks it and
   finds **two** secrets that do cross the host: the **DKEK share password** and the **User PIN**.
   Neither is a key; both are sufficient, in combination with something else, to matter. The design
   is built around defending exactly those two, and the claim is restated precisely at the end of §3.
3. **The reframe, offered for rejection:** a weekly *backup* of a long-lived key re-copies bytes that
   did not change. What decays is **confidence that a restore works**. So the weekly artifact should
   be a **restore drill** — restore onto a spare token, verify the restored key produces the same
   public key, destroy the test artifact. *A backup that has never been restored is a hope, and
   custody failures are overwhelmingly discovered at restore time.* Weekly literal backup is cheap
   and can be kept too; the drill is the part that carries a guarantee.

## 1. The mechanism, measured

From `sc-hsm-tool(1)` and the OpenSC SmartCardHSM documentation:

| step | command | what crosses the host |
|---|---|---|
| establish DKEK | `sc-hsm-tool --initialize --so-pin … --pin … --dkek-shares N` | SO-PIN, PIN |
| export a share | `sc-hsm-tool --create-dkek-share aaron.pbe` | a **password**; the file is PBE-encrypted |
| load a share | `sc-hsm-tool --import-dkek-share aaron.pbe` | the same password |
| back up a key | `sc-hsm-tool --wrap-key backup.bin --key-reference 1` | **ciphertext only** |
| restore a key | `sc-hsm-tool --unwrap-key backup.bin --key-reference 1 [--force]` | **ciphertext only** |

- *"The DKEK will be generated using the random number generator in the SmartCard-HSM and is then
  encrypted using Password-based-Encryption."* The DKEK itself has no plaintext representation
  outside the device — **only a key check value (KCV) is disclosed**, which is exactly enough to
  prove two devices hold the same DKEK without revealing it. That KCV is the drill's verifier (§5).
- The wrap file carries *"key description, the optional certificate and the key value encrypted
  under the DKEK."*
- `--dkek-shares 0` requests a device-random DKEK — i.e. a device that can wrap but whose DKEK can
  never be reproduced elsewhere. That is "backup that cannot be restored", so it is not this design.

### 1.1 The one-way door — and it is the highest-value sentence in this document

> **`--initialize`** — *"Initialize token, removing all existing keys, certificates and files."*
>
> And: *"After using `--initialize` with one or more DKEK shares, the SmartCard-HSM will remain in
> the initialized state until all DKEK shares have been imported. **During this phase no new keys
> can be generated or imported.**"*

**A DKEK cannot be added to a token that already holds the key you want to protect.** Establishing
one erases the device. So the backup design is not something to adopt later — it is decided
*before the first key is generated*, or it is not available for that key at all, ever.

That is the same shape as the seal-custody decision in the previous doc (an in-TPM key cannot become
an imported one after the fact), arriving from the token side. **Two independent one-way doors, both
open today, both closing the moment something real is stored.** The second quoted sentence is the
consolation: a half-imported DKEK is a *visible, safe* state — the device refuses to hold keys until
the share set is complete, so an interrupted ceremony cannot leave a key sitting under a partial DKEK.

### 1.2 DKEK shares are n-of-n; the threshold knob is one layer down

`--dkek-shares N` sets how many shares **recreate** the DKEK, and the device reports *"DKEK import
pending, 2 share(s) still missing"* until **all** are in. There is no t-of-n at the DKEK layer.

The threshold exists on the **share password**: `--pwd-shares-threshold` / `--pwd-shares-total` split
a share's password (t, n). So the resilience design is:

- **DKEK shares (n-of-n)** decide *who must participate* — with two shares, Aaron **and** Max.
- **Each share's password (t-of-n)** decides *what happens when a holder is unavailable*.

That directly answers the single-holder-unavailable case, and it answers it in a way that is easy to
get backwards: **duplicating the share FILE is safe** (it is PBE-encrypted and useless alone), while
the *password* is the thing to split. A design that guards the file and single-copies the password
has protected the wrong artifact.

## 2. The vendor split, on Aaron's own criterion — measured

This is where the dual-vendor question from the previous doc meets the side-channel requirement, and
the two vendors are **not equivalent on the property Aaron named.**

| | SmartCard-HSM (CardContact) | YubiHSM 2 (Yubico) |
|---|---|---|
| symmetric backup key | **DKEK, generated by the device RNG** | wrap key, AES-CCM |
| does that key ever exist in plaintext on the host? | **No.** It leaves only as PBE-encrypted shares; only the KCV is public | **Yes, in the documented flow.** `get-pseudo-random` writes the wrap key to a file — Yubico's own words: the file *"should therefore be considered sensitive"* since it contains **the key in cleartext** — then `put-wrap-key` imports it into each device |
| per-object opt-in | keys are wrappable under the DKEK established at init | explicit `exportable-under-wrap` capability per object |
| backup format | `sc-hsm-tool` wrap file | `.yhw` |

**Why this is structural rather than sloppiness on Yubico's part:** backup requires **two devices to
share one symmetric key**. `generate-wrap-key` does exist and generates on-device — but a key
generated inside device A cannot appear inside device B without crossing something. CardContact
solved that with a share protocol (device generates, exports only password-encrypted shares).
Yubico's documented answer is to generate the key outside and import it into both, which puts it in
host RAM, in a file, and through whatever wrote it.

**So on Aaron's stated criterion the $79.26 device wins**, and it wins on the exact axis he named.
That is worth stating plainly because it inverts the usual price intuition.

**And the cross-vendor limit, stated so nobody designs against it:** the two wrap formats are not
interoperable. **You cannot wrap on a SmartCard-HSM and unwrap into a YubiHSM.** Dual-vendor
therefore means *two independent custody chains*, never one chain with two device types in it —
which is consistent with the previous doc's §4.3(ii) recommendation to give the two vendors
**different functions** rather than the same one.

## 3. Attacking the central claim: every place plaintext can touch the host

The claim is *"plaintext key material exists only inside secure elements; the host is a dumb pipe
carrying ciphertext."* Attacking it in order:

| # | surface | verdict |
|---|---|---|
| 1 | **the wrap blob** | ciphertext under a 256-bit AES DKEK. Safe on any medium — **but see §4.3**: it is exactly as strong as the share set, so blob and shares must never be stored together |
| 2 | **DKEK share files** | PBE-encrypted. Safe to duplicate |
| 3 | **the share PASSWORD** | **PLAINTEXT ON THE HOST.** Typed into a terminal, held in the tool's memory. This is the real exposure |
| 4 | `--password` **in argv** | argv is world-visible in `ps` for the life of the process, and lands in shell history. `--password env:VAR` avoids argv and puts it in the environment, readable via `/proc/PID/environ` by the same user and by root. **Neither is safe; the interactive prompt is** |
| 5 | **generated passwords and (t,n) share strings printed to stdout** | `--create-dkek-share` *prints* them. Any `tee`, `script(1)`, CI log, or terminal scrollback captures the ceremony |
| 6 | **a remote session** | the fleet has GL.iNet Comet KVMs and uses them. **A KVM-over-IP or SSH ceremony puts the share password on a network.** This is the likely mistake here, not a theoretical one |
| 7 | **swap / hibernation** | the password sits in RAM for seconds; unencrypted swap can persist it for months. *(Measured, and it is currently in our favour: `full-ai-cluster/nixos/hosts/control-plane/hardware-configuration.nix` sets `swapDevices = lib.mkDefault [ ]`. That is a placeholder file, so it is a fact about today's declaration, not about a provisioned node.)* |
| 8 | **core dumps** | a crash while holding the password writes process memory to the coredump path. `systemd-coredump` is on by default on NixOS |
| 9 | **shell history** | a mistyped password lands on the wrong line and is written to disk |
| 10 | **the USB bus** | wrap blobs are ciphertext, fine. **But the User PIN crosses the bus in the APDU**, and the SmartCard-HSM has no secure messaging by default. A malicious hub, a bus analyser, or a compromised host sees the PIN — **not the key** |
| 11 | `--unwrap-key --force` | overwrites whatever it is pointed at. Two tokens connected at once is how a drill destroys the production key |

**So the claim, restated so it can be defended:**

> **No key material — neither the protected key nor the DKEK — is ever present in plaintext outside
> a secure element, on any host, at any point in the backup or restore path.** Two *non-key* secrets
> do cross the host: the **DKEK share password** (during establishment and restore) and the **User
> PIN** (on every authenticated operation). Host CPU-trace and memory-scraping attacks therefore
> have no key to observe — and they do have those two, so the ceremony's host hygiene is a
> first-class control rather than an afterthought.

That restatement is what `tools/setup/hsm/dkek-ceremony-preflight.sh` (§7) enforces: rows 4–9 and 11
of the table above, fail-closed, before a human types anything.

## 4. Honest limits, because the claim is strong

### 4.1 Side channels *on the token* are a different class and are NOT addressed

Wrapped export defeats an attacker watching **the host**. It says nothing about an attacker with the
token in hand and an oscilloscope. **Timing** (Kocher 1996) and **differential power analysis**
(Kocher, Jaffe & Jun 1999) attack the device's own execution, and no protocol built on top of the
device can close them — resistance there is a property of the silicon and its countermeasures.

The in-domain proof that this is not hypothetical is already on file: **EUCLEAK / YSA-2024-03** was
an EM side-channel key extraction against an Infineon cryptographic library, affecting YubiKey 5 and
YubiHSM 2 simultaneously, and it survived roughly 14 years and ~80 Common Criteria evaluations.

> **So "no side-channel key leaks" must never stand unqualified. It is true of the HOST and unproven
> of the DEVICE.** The SmartCard-HSM's own certification level remains **unchecked** here — it was
> logged as unchecked in the procurement work and this document does not close it.

### 4.2 USB is a shared bus

Ciphertext on it is fine. The PIN on it is not (§3 row 10). The mitigation is physical and boring:
a dedicated ceremony host, no hubs, nothing else plugged in, and the knowledge that the PIN alone
buys an attacker nothing without the token.

### 4.3 The DKEK share set **is** the security boundary — not the token count

Any device holding the DKEK can unwrap the backup. Adding a third token does not add security if
that token holds the DKEK; it adds another place the key can be reconstituted. So:

- the number that matters is **how many share-sets exist and who holds them**, not how many HSMs
  are in the drawer;
- the wrap blob and the shares are **one secret split in two**, and storing them together silently
  recombines it.

## 5. The reframe: a weekly RESTORE DRILL

**Why not a weekly backup.** The keys under discussion are long-lived by construction — a seal key,
a CA key. Re-wrapping an unchanged key weekly produces N copies of the same ciphertext and adds N
opportunities for one of them to be stored badly. The thing that genuinely degrades over a year is
**confidence that the restore path still works**: tool versions drift, a share password is
misremembered, a `.pbe` file silently corrupts, a custodian changes laptops.

**The drill, weekly:**

1. Preflight the host (§7). Refuse on any failure.
2. Connect **the spare token only**. The production token stays in its envelope — **the drill never
   touches it**, which is why a weekly cadence carries no risk to the live key.
3. Import the DKEK shares into the spare; **check the KCV matches** the recorded one.
4. `--unwrap-key backup.bin --key-reference 1` onto the spare.
5. **Verify**: read the restored key's public key and compare its fingerprint against the one
   recorded in the repo at wrap time. Optionally sign a fixed test vector and check the signature
   verifies against that public key.
6. **Destroy the test artifact**: `--initialize` the spare, which erases it (§1.1) and leaves nothing
   restored anywhere.
7. Append a receipt: date, KCV, public-key fingerprint, spare token serial, tool version, verdict.
   **No secrets** — every field is a public value or a hash.

**Can the drill avoid an authenticated session that could handle key material?** Partly, and the
split is worth being exact about:

- **The verification half needs no session at all.** A public key is a public object; comparing a
  fingerprint against a committed value is arithmetic. It can be done off-token entirely.
- **The restore half necessarily needs the User PIN on the spare** — unwrapping is a key-handling
  operation and no protocol makes it otherwise.
- **What it does avoid is any session on the PRODUCTION token.** That is the property worth having,
  and it is stronger than the session-capability distinction: the live key is not merely protected
  by a capability set during the drill, it is *not electrically present*.

**A failed drill is a finding, not a chore.** Its failure modes each mean something specific:
KCV mismatch ⇒ wrong or corrupted share set; PBE decrypt failure ⇒ a forgotten or wrong password
(the most common real custody failure); unwrap error ⇒ blob corruption or a tool-version
incompatibility; fingerprint mismatch ⇒ **the backup is of a different key than you think**, which
is the one that would otherwise be discovered on the worst day of the year.

## 6. The ceremony, concretely

**Roster** (two SmartCard-HSMs ordered, one YubiHSM 2 on hand):

| device | role | why |
|---|---|---|
| SC-HSM **A** | production key, in service | |
| SC-HSM **B** | **drill / restore target only** | same vendor is *required* here — the wrap format is not interoperable (§2) |
| YubiHSM 2 | **a different function**, never a backup target of A | previous doc §4.3(ii): vendor diversity buys most when the two vendors hold different functions |

**Custody:** 2 DKEK shares — Aaron and Max, n-of-n (§1.2), so a restore needs both. Each share's
password split (t, n) so a single unavailable holder is survivable. Share **files** duplicated
freely; share **passwords** split. Wrap blob stored apart from both (§4.3).

**Phase 0 — decide, before any key exists.** §1.1 is a one-way door. Share count, holders, password
threshold, and which keys will be wrappable are settled here or not at all.

**Phase 1 — DKEK establishment. The sensitive moment.** The shares are most exposed when they are
first created and imported, because that is the only time their passwords exist. Preconditions, all
enforced by the preflight: physical console (**no SSH, no KVM**), stdout is a terminal (nothing
recording), core dumps off, swap off, no `--password` in argv, history off, exactly one token
connected.

**Phase 2 — key generation on A**, after the DKEK, never before.

**Phase 3 — wrap.** `--wrap-key` on A; record the KCV and the public-key fingerprint in the repo
(both public); store the blob apart from the shares.

**Phase 4 — the weekly drill on B** (§5). A and B are **never connected simultaneously** — that rule
does two jobs at once: it makes a wrong-target `--force` impossible, and it means no single host
ever has both halves of the custody set in reach.

**Phase 5 — rotation of the drill token.** After a drill, B is erased. If B is ever kept as a warm
standby instead, it stops being a drill token and becomes a **second production custodian**, with
all of §4.3's consequences. That is a different decision and should be made deliberately.

**What a human must do that they do not do today** — the governance-visible diff, since this
proposes new human work rather than removing it:

| | today | proposed |
|---|---|---|
| DKEK establishment | — (no HSM in service) | **once**, both custodians present, at a physical console |
| key generation | — | on A, after the DKEK |
| wrap | — | once per key |
| **weekly** | — | **~10 minutes: preflight, drill on B, append receipt** |
| restore, for real | undefined | the drill, minus the erase step |

**Not landed, not decided.** Every row is a proposal, and the ceremony is a gated class: fresh human
authorization plus the biometric gate, with a witness.

## 7. What shipped with this document

`tools/setup/hsm/dkek-ceremony-preflight.sh` — **host hygiene, fail-closed.** It touches no device,
runs no `sc-hsm-tool`, reads no key, PIN, share or password, and creates nothing. It answers one
question — *is this host a safe place to hold a share password for the next few seconds* — and
answers REFUSE by default. Seven conditions, one per row 4–9 and 11 of §3.

Why a preflight rather than a ceremony script: the ceremony is a human act behind a gated class and
automating it is neither asked for nor permitted. What *is* automatable is the part a human reliably
gets wrong at 11pm — that this terminal is an SSH session, that core dumps are on, that swap is
live, that stdout is being teed into a file that ends up in a git repo.

**Its falsifier is `src/Core.TypeScript/installer/dkek-ceremony-preflight.test.ts` — 20 properties:**

- every condition refuses **on its own**, naming itself (so no guard is unreachable behind another);
- every condition set to `unknown` refuses — *a check that did not run must never read as one that
  passed*;
- a **missing** record refuses exactly like `unknown`: silence is not consent;
- an **empty** fact record refuses on **all seven** conditions rather than falling through to PASS;
- multiple failures are all reported at once, not one per re-run;
- the script **executes no ceremony command** — asserted over code lines with comments *and quoted
  strings* stripped, because the refusal messages deliberately name the tools they protect the
  operator from, and a message is not an invocation.

Mutation-checked rather than asserted: making the preflight actually invoke `sc-hsm-tool` goes red,
and making one `unknown` fall through to PASS goes red. `shellcheck -S warning` clean.

The reader half (`dkek_preflight_read_facts`) is outside the marked block and outside the test's
claim — a fixture cannot stand in for `/proc/swaps`, and pretending otherwise is the exact failure
this repo keeps finding.

## 10. Gated / never-run

No device touched, no token contacted, no DKEK established, no share created or imported, no key
wrapped or unwrapped, no PIN or password handled, `op` not invoked, no cluster contacted. DKEK
establishment, key generation, wrapping and restoring remain a **gated class**: fresh human
authorization plus the biometric gate, with a witness. Designed here; run by a human, never by an
agent.
