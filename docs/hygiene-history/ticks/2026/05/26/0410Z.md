## Root cause — BACKLOG.md serialization

All 10 PRs touch `docs/BACKLOG.md` (the auto-generated index per `tools/backlog/generate-index.ts`) AND add a single backlog row file. The conflict pattern:

1. Each PR's branch was forked from main at time T₀, with BACKLOG.md generated at the row-set-on-main-at-T₀
2. As main accepts subsequent backlog rows (`d04d78728`, `3eace3aeb`, `230efca0f`, `230efca0f`, etc.) the BACKLOG.md index regenerates with each merge
3. PRs opened in quick succession at time T₀ never regenerate BACKLOG.md after each subsequent merge — they hold the T₀ version
4. By the time the Nth PR comes up for merge, N-1 BACKLOG.md regenerations have stacked on main; cumulative merge conflict on BACKLOG.md becomes unresolvable in auto-merge

This is the **N-PR-batch-touching-BACKLOG.md-serializes-conflict pattern**. Operational mitigation candidates (research-only this tick; substrate-engineering for future backlog row):

- **Batch authorship**: open at most 1-2 BACKLOG.md-touching PRs simultaneously; let each merge fully before opening the next
- **Index-merge-driver**: configure git custom merge driver for `docs/BACKLOG.md` that runs `BACKLOG_WRITE_FORCE=1 bun tools/backlog/generate-index.ts` post-merge instead of textual 3-way merge
- **Index out-of-tree**: move BACKLOG.md to a build artifact published via CI rather than committed; eliminates the file from the conflict surface entirely
- **Index re-gen on PR-open hook**: GitHub Actions workflow that auto-regens BACKLOG.md on PR-update events and pushes the regen back to the branch

None of these are landed; this audit names the pattern + the candidates for the next bounded substrate-engineering round.
