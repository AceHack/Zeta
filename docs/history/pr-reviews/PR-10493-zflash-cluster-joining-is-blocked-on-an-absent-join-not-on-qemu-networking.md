## Description

## The finding

`cluster-joining` was recorded everywhere as `blocked-on-multi-vm-orchestration` — which reads as *fix the QEMU network and the scenario is done*. Measured, that is the **second** blocker.

**The first blocker is that there is no join to observe.** The success contract is `B0891_CLUSTER_JOIN_SERIAL_MARKERS`, and a scan of the guest tree finds **zero emitters across 45 files**. The only producer of those strings in the repository is a mock serial log inside `multi-vm.test.ts`. `k3s-server.nix` still carries `MULTI-NODE TODO: workers`, and `zeta-install.sh` has no join plumbing at all.

### Why the ordering is load-bearing

Fix only the networking and concurrency, and the joining node boots, emits nothing, and times out — an honest `skipped` becomes a `failed`. That is strictly worse: it points a future reader at a network bug that is not there, and the tempting fix for a mysterious timeout is to relax the marker set. That is how a false green gets manufactured.

## What this PR does

- **`join-implementation-probe.ts`** — reports the neutral fact (`absent` / `emitted`) through an injected reader, so it carries no ambient I/O.
- **`join-implementation-probe.test.ts`** — fixture-driven falsifiers plus a **promotion tripwire** that fails the day the guest starts emitting the markers, with a message saying to promote the scenario and reminding the reader the second blocker is still open. **A failure there is good news.** The tripwire is itself guarded against vacuity: it asserts it actually read guest files, so a moved tree cannot make absence trivially true.
- **`scenarios.ts` / `run.ts` / `scenarios.test.ts`** — the corrected verdict and skip message, naming both blockers in order.

`cluster-joining` stays **`skipped`**. Nothing was dispatched, no green was manufactured.

## Two corrections worth stating plainly

1. **`ubuntu-24.04` GitHub runners DO expose `/dev/kvm`**, and this repo already boots QEMU on them (`build-ai-cluster-iso.yml`). So the own-hardware argument for this test class is **wall-clock and cost, not capability** — the existing single-VM steps already carry 90-minute timeouts, and hosted jobs cap at 6 hours. Stating it as a capability gap would have been wrong and would have weakened the case.

2. **A Docker Compose join test would be vacuous today.** The only join that exists is k3s's own agent-to-server join — upstream software. A two-container test would verify Rancher's code, not Zeta's, and would go green on a machine where Zeta provisioning is entirely broken. The container path becomes genuinely valuable the moment Zeta owns a join step of its own; until then it is scaffolding around an empty room.

Also corrects the premise that several scenarios carry `scaffolded` — measured, **exactly one does**, so no siblings are waiting behind this fix.
