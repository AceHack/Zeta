## Description

# Summary

`test (TS suite)` has been red across many PRs since roughly 17:54 UTC today. It is **not
flaky** — measured, not inferred, it is a sequence of *deterministic* failures from
different causes, and the current one on `main` is a real loosening of the USB credential
binding.

`selectCliBindingMaterial` (added in #11016, merged 18:57 UTC) `.trim()`-ed the value it
handed to the KDF. So `--usb-uuid "<A> "` and `--usb-uuid "<A>"` derived the **same** key,
and a blob bound to one restored on the other. `key-refusal-falsifier.test.ts` caught it on
its "identity A with trailing whitespace" case — that test exists precisely to forbid a
near-miss identity being silently accepted, and its own comment predicted this failure mode
verbatim: *"a well-meaning 'be lenient about operator input' normalisation is exactly how
binding gets loosened by accident."*

The fix separates two questions that were conflated:

- **"Was a factor supplied?"** — an operator-input question. A whitespace-only value answers
  *no*, and trimming to decide that is correct. Kept.
- **"What bytes go into the KDF?"** — a cryptographic question. The answer is the operator's
  bytes, **verbatim**. The trim is removed here.

Nothing needed the trim: the sysfs probe already normalises at the source (`trimOrNull` in
`usb-iserial-probe.ts`, where the trailing newline is an artefact of reading a sysfs
attribute), and the keyfile path never went through a string. Normalise where the artefact is
introduced, never where the key is derived.

# Spec alignment

`docs/security/USB-IDENTITY-THREAT-MODEL.md` §4. Observable behaviour is restored to what the
threat model and the falsifier test already claimed; no spec text needed changing, because the
trim was never the documented behaviour.

"trim is banned here".

Every row is a *derived artefact or content assertion that went stale on merge*, red for a

notice. The DRIFT GATE row is the clearest instance: it was reproducibly red on clean
`origin/main` (e5fd8f8f) with this change stashed, and by tip 73db9367
`bun src/Core.TypeScript/ace/build-graph.ts derive --write` reports "already current" and the
file is green again. That row healed on its own; this row did not, because the stale thing was
the *code*, not a manifest.

Not bundled here on purpose: bundling would hide that one red X has been at least three
different bugs.

**The varying failure set is timeout-boundary contention, not order-dependence.** Six local
whole-suite runs on a loaded workstation failed a *varying subset* of one file's tests
(`audit_retractibility.test.ts`) at 30001 / 30002 / 30003 / 30004 / 32369 / 47716 / 52020 ms
against its declared 30 000 ms cap. Same file every time, different members. Which ones trip
depends on machine load; the file does a repo-wide reference scan. Deliberately **not** "fixed"
by raising the cap — that would be papering over it, and it is green in CI.

Not touched, and flagged for a separate decision:

- **`bun test` crashed with a segfault** in one of five runs (Bun v1.3.14, macOS arm64, during
  `observe/grammar-16.test.ts` after the WebSocket-heavy realtime tests). Upstream bug, not
  ours, but it is a real source of "the failure set varies" on developer machines.
- **`audit_clause_drift.test.ts > default base ref > returns 0 with no args`** is a function of
  the working clone's git refs, not of the code. Proven: `--base 5a610039^ --head HEAD` exits 1
  in a clean clone, because #10869 changed an ALIGNMENT.md clause body — so any checkout whose
  local `main` lags that commit fails the test deterministically. It passes in CI and in a fresh
  clone. Making it hermetic means injecting the base ref rather than resolving it from ambient
  git state; that is someone's intentional guard and worth a deliberate decision, not a
  drive-by.
