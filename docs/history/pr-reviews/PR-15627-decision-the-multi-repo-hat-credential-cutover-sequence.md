## The multi-repo + hat-credential cutover — an ordered sequence, not another round

Aaron, 2026-08-26: *"lets route pushing this forward — we've been doing this for a while but i'd like to cut over, and also cut over to multi repo design."*

The split has been through four design rounds. **This adds no fifth.** It takes the decided destination and produces the thing the rounds never produced: an ordered sequence, each step with a reversal and a falsifier, with an explicit irreversible line below which nothing proceeds without Aaron.

**Nothing was executed.** No repository created, no code moved, no secret or GitHub App created or modified.

### The sequence

Reversible: **S1** first hat (one workflow file) → **S2** per-leg install subset → **S3** remaining hats + the two required audits that hardcode the old secret names → **S4** the two missing falsifiers → **S5** cross-repo glue rehearsed in-tree against a self-pin.

Then the irreversible line: **S6** create `zeta-formal` → **S7** move content → **S8** re-measure → **S9** revoke the retired PATs.

### The credential half is a PREREQUISITE, not a parallel track

The brief's reading was *at least accompany*; mine is **precede**, on three grounds. The third is decisive and it is not new architecture — it connects two existing measured findings:

`2026-08-26-three-verdict-loss-mechanisms-*` §9 item 3 already asks Aaron *"change the merge actor from `github-actions[bot]` to the PAT? This widens what that credential does."* **That dilemma exists only because the credential is a role.** Widening a PAT changes what it *is*, permanently. Minting a merge-scoped App token for one act is a hat and widens nothing. The credential model is not a cost the split imposes — it is the resolution of a question already blocking 40% of `main`'s commits from getting a gate run.

The PAT≡role / App-token≡hat mapping is **checked property-by-property** against `2026-08-09-*-hats-grant-claims-bounded-duration-*` §C (bounded duration by default · expiry needs no coordination · revocation is a −1), not asserted.

### Two things measured here, at `d3396ab838`

- **`build-graph.json` is COMPLETE over the CI domain** — `audit-build-graph-completeness.ts` rc=0, 119 targets / 37 jobs / 4 leg-bearing workflows, 3 targets declared UNCOVERED and forcing FULL. Round 3's acceptance condition for wiring job selection is **already met**, which is what makes S2 a one-PR artifact rather than a project.
- **The credential census is 81 workflows · 8 long-lived GitHub PATs · 0 App tokens.** The role table is more than twice the size the brief assumed, and `ZETA_SOCIETY_DISPATCH_TOKEN` — one of its three named entries — is referenced by **no workflow at all**, while the credential actually dispatching is a Cursor Secret the table does not mention. The role model is already drifting at N=1.

### First step, first repo

**First step is S1:** execute the GitHub App bootstrap already written and never run in `docs/operations/RULESET-RECONCILIATION.md` §8 (*"Nothing below has been done."*). One workflow file, one App, one commit to revert, the PAT left in place. It retires the highest-privilege PAT in the tree (`Administration: write`) and **touches no required check** — which is exactly why it is smaller than starting with the flush lane, whose conversion must move two gate-required audits in the same PR.

**First repo is `zeta-formal`, not `Forge`/`ace`** — cleanest closure (2 live units, 2 toolchains, **0 external packages**, 2,977 MB single-owner), lowest churn (48 commits/90d so the pin mechanism is exercised without pin churn), dedicated workflows already exist. And the counterintuitive reason: its cache cost is **0.02 GiB**, so **nothing about cache pressure can confound the measurement of whether the split mechanism works.** A first cut should be an experiment, not a payoff. `Forge` at 383 commits/90d is the worst possible first experiment; `ace` cannot be first by rule.

### What it does NOT solve — stated up front

**`Zeta-core` does not get under the ceiling.** 11.17 GiB charged at peak. S2 attacks the union half (59% of the logical set) and is the largest lever available, but two terms survive it: the **2.6× ref multiplier**, which travels with the repo because it inherits 96% of build-touching commits; and the **untouched OS×arch axis**, where `dotnet-macOS-ARM64` alone is 1,858 MB = 20% of the entire ceiling. **After the prerequisite lands, `Zeta-core` may still be over, and nobody has specified the further cut.** Round 3 §9 names two candidates and this plan picks neither — it sequences S8 to produce the measurement that would let Aaron pick.

Also unsolved: multi-repo hat scoping is unprovable until a second repo exists (S6); three S3 acceptance checks are `consistent with`, not `metered`; the interactive `gh pr merge --auto` identity is in no role table.

### What Aaron must decide

Seven items in §7, only one of which blocks this week: **create the `zeta-ruleset-reconciler` App and store its key** (org secret, or the YubiHSM lane?). The rest: reorder ADR Stage 1 · create `zeta-formal` (irreversible) · revoke the PATs (irreversible, and fine-grained PATs cannot be re-minted headlessly) · is the merge-actor change acceptable as a bounded hat · the second `Zeta-core` cut · the budget projection the ADR's own gate already owes (21 snapshots exist, no projection computed).
