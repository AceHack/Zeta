## Description

## The occasion — a constraint that was resident, correct, and still did not run

`CLAUDE.md` carries this in **every** agent's context at every wake:

> `references/prior-art/` — explicit-target searches ONLY; a naive `grep -r .` is a 2-hour runaway.

Hours later an agent opened its investigation with an unconstrained `grep -rn ... .` from the repo root. Two background jobs ran **over an hour** and burned host I/O.

The rule was written, it was correct, it was loaded — and it still failed, because nothing enforced it. That is the vacuity class applied to guidance rather than to tests. Aaron's read:

> *"this is one of the main reasons we want to dogfood our own clis and not ever rely on bash or random clis from others, they don't have our constraints built in to avoid things like this"*

## What the prior-art search found — and why it reframed the PR

**A dogfooded search tool already existed.** `src/Core.TypeScript/search/grep.ts`, written 2026-05-31, for this exact reason, with `references/prior-art` already in its exclusion list. It did not prevent the incident, and *why not* is the whole design input:

1. **It was unadvertised and unused.** Nothing in the repo imports it except its own test. `CLAUDE.md` names the constraint but never names the tool. A tool nobody is pointed at is not a mechanism — it is a second document.
2. **It is itself a runaway.** Measured here: `bun grep.ts <needle>` over this tree printed **nothing** and had **not finished at 300s** — 0.66s user, 0% CPU, blocked in synchronous per-file reads. No time bound, no file bound, no output until completion, so you cannot tell "working" from "no matches". An agent that tried the in-repo tool first and hit that would reach for bash next — which is what happened. **A guard that makes the safe path slower than the unsafe one has selected for the unsafe one.**

So this PR fixes the existing tool's category of failure rather than adding a third one.

## Two things the prose got wrong — measured, not inferred

**1. The named directory is not the heavy one.**

`references/prior-art` is **8.0K** on this machine: a `.gitignore` and a `README.md`, nothing mirrored in. The 24G shared checkout is:

| tree | size |
|---|---|
| `src/Core.Lean4/.lake` | **6.9G** |
| `.git` | 4.1G |
| `src/Core.Rust.*/target` (all crates) | ~700M |
| `node_modules` | 222M |
| `references/prior-art` | **8.0K — empty** |

An exclusion set naming only `prior-art` **would have prevented nothing today.** So `exclusions.ts` carries a dated measurement beside every entry, and a test fails if one is missing. Folklore is what put a now-empty directory at the centre of the rule.

**2. The cost is per-file-OPEN — not per-byte, not per-directory.**

| operation | result |
|---|---|
| `rg --files` (walk, no opens) | 40,984 files in **0.33s** |
| `rg -c <pattern>` (opens + reads) | **did not finish in 180s** — 0.53s user, **3% CPU** |
| `bun grep.ts <needle>` (whole tree) | **did not finish in 300s**, zero output |
| **`bun search.ts <pattern>` (whole tree)** | **refused in 2.36s**, naming what to do next |

`ps` during those runs: Microsoft Defender's on-access scanner at **464% CPU**, load average **36.6**. Every file open is being AV-scanned. That is why the walk is ~1000x cheaper than the reads — and it is what makes the guard affordable: **count what you would open, before you open it.**

## Layer 1 — `/.ignore` (free, and honestly partial)

Generated from `exclusions.ts`. ripgrep, `fd` and `rga` honour it, so a **bare `rg`** is safe here with no flag to remember and no rule to have read.

**Stated in the file itself:** `grep -r` honours **none** of this. POSIX grep has no ignore-file concept, so the exact tool that caused the incident is untouched by layer 1. You can make *some* external tools carry a constraint; you can never make all of them. That asymmetry is the argument for layer 2, not against it.

## Layer 2 — `search.ts`, fail-closed on scope

**What it refuses**

- **An over-budget scope** (default 4000 files opened). The refusal names the count, the top directories responsible, and `--max-files N`. Whole-tree search here is 41,673 files → refused in 2.36s.
- **A target inside an excluded tree**, e.g. `search.ts foo references/prior-art`. It does **not** silently return zero. The refusal names the tree, its measured size, and the exact `--allow` invocation.
- Usage errors up front — non-positive `--max-files`, invalid regex — rather than mid-walk.

**What it allows**

- Any narrowed search: `search.ts foo src/Core.TypeScript`, `--ext ts,md`.
- **The deliberate prior-art search**, which `CLAUDE.md` *encourages*: `search.ts foo references/prior-art --allow references/prior-art`. `--allow` is scoped to the tree named and unlocks nothing else.
- `-i`, `--files`, `--ext`, `--root`.

**What it never does: narrow silently.** Every pruned tree is reported on stderr with the rule that pruned it. Exit `3` (refused) is deliberately distinct from `1` (no matches) — a refusal sharing an exit code with "no matches" is invisible to its caller.

> A confident empty result is worse than a runaway. The runaway is loud and you kill it; the empty result is believed.

## CodeQL caught me shipping the same bug I was fixing — fixed, not suppressed

The first push introduced `js/regex-injection` at **high** severity, twice. The finding is correct and the irony is the point: a `RegExp` built from a command-line argument can backtrack catastrophically, and **JavaScript has no regex timeout** — so one careless pattern hangs the process with no budget able to stop it. That is an *unbounded search*, the exact failure this tool exists to refuse, shipped inside the guard.

`grep.ts` had already reasoned its way to literal-only matching in 2026-05-31, explicitly citing "no ReDoS / regex-injection surface". This PR regressed that. **Corrected by removing the capability — no alert dismissal, no inline suppression.**

`-e`/`--regex` is now **refused with a pointer**, never silently ignored: silently dropping the flag would search the pattern literally and return confidently wrong results, the same believed-empty-answer failure the excluded-target refusal exists to prevent. A test asserts a regex metacharacter matches *literally*, so reintroducing regex fails the suite.

The division of labour is honest: **literal here**, where the scope budget is; **regex in ripgrep**, whose engine is linear-time and cannot backtrack (Cox 2007, *Regular Expression Matching Can Be Simple And Fast*) — and which the `.ignore` in this PR already keeps off the heavy trees.

## Falsifiers — 29 tests, 7/7 verified mutants killed

Mutation harness byte-`cmp`s the file before and after patching, so a mutant that did not land is reported as `HARNESS-FAIL` rather than counted as a survivor, and byte-`cmp`s again after restore.

| mutant | result |
|---|---|

| M2 budget boundary `>` → `>=` | **survived → fixed**, now killed |
| M3 excluded-target refusal removed | killed |
| M4 heavy-tree pruning removed from walk | killed |
| M5 skipped-tree reporting suppressed | killed |
| M6 `.ignore` renderer drifts from `HEAVY_TREES` | killed |

**M2 was a real gap found by the harness, not a formality**: the budget boundary was asserted nowhere, so `>` or `>=` would both have shipped. Pinned by an added test, then re-run and killed.

The drift falsifier is the third one asked for: `.ignore` is **generated** from `exclusions.ts` and a test asserts the on-disk file is byte-identical to the renderer's output — the two cannot disagree silently.

## Honouring `clone-at-tag-stays-sufficient`

Zero new dependencies — `node:fs` and `node:path` only. Nothing in `tools/setup/`, the workflows, or the build props requires it. `lint-clone-at-tag-is-sufficient.ts` passes. **It is an oracle, not a hub: the good path, never the only path.**

## Scope held

Built the tool and the ignore file. **Did not** migrate the ~8 existing call sites that hand-roll `prior-art` handling — `grep.ts` now re-exports from `exclusions.ts` (what centralisation cleanly required) and nothing else was touched. Sized in the work-item: ~1 focused PR, half a day, and it needs reading rather than a blind sed because some of those sites may intend a different set.

## What this still does NOT prevent — honestly

1. **Nothing stops an agent typing `grep -r` anyway.** This is the big one and it is unfixed by design: the tool is opt-in, and the incident was caused by a tool we do not control. Only the harness/permission layer could refuse that, and refusing it repo-wide would break legitimate uses.
2. **`grep -r` still ignores `.ignore`.** Layer 1 covers ripgrep-family tools only.
3. **The budget bounds files opened, not bytes or time.** 4000 files that are each 2MB is still slow. There is no wall-clock kill switch.
4. **`--max-files 999999` is one flag away.** That is deliberate — a guard with no override gets switched off wholesale — but it means the guard is a speed bump for anyone determined.
5. **The measurements are host-specific.** They are dated and attributed to this machine; the 464%-CPU AV scanner is not universal, and the numbers should be re-measured, not trusted, elsewhere.
6. **No regex.** A real capability gap, mitigated but not closed by pointing at `rg`. An agent needing regex leaves this tool, and `rg` has no scope budget — only `.ignore`.
7. **The heavy-tree list is still hand-maintained.** It now demands a measurement per entry, but nothing *discovers* a newly-heavy directory. A `du`-based auditor would close that; not built here.
8. **`grep.ts` still exists and is still reachable.** Two search tools is a fork in the guidance until one is retired.
9. **`CLAUDE.md` still does not name the tool** — and "unadvertised" is the *measured* reason the previous tool failed. This is the single highest-leverage remaining change and it is a one-line diff. **It is not in this PR because `CLAUDE.md` is configuration and an agent's own say-so is not authorization to edit it.** It needs a human:

   > `bun src/Core.TypeScript/search/search.ts <pattern>` — repo search, refuses an unbounded scope. `.ignore` makes bare `rg` safe too; `grep -r` is still unguarded.
