## Description

## Three of the four were ArgoCD semantics, not workloads

PR #13326's dev `longhorn` alias made eleven Applications reachable. Six went
straight to Synced+Healthy; four bound their volumes, ran their pods, and then
failed for reasons that had nothing to do with storage. **Three of those four
were not workload problems at all** — they were ArgoCD's own reconciliation
semantics. Each is fixed and asserted under the **full auto-sync contract**;
none is asserted less than before. `hindsight` stays deferred with a much better
recorded reason.

**Asserted roster: 28 → 31** of 46 discovered Applications.

### `cockroachdb` — a PostSync hook deadlocked against the health it produces

Not a dev-lane artefact: **no 3-replica CockroachDB under this chart has ever
come up healthy under ArgoCD on any substrate, metal included.**

The chart already ships the fix — `templates/job.init.yaml` renders
`cockroachdb-init` when `conf.join` is empty and `single-node` is false, both
true for us — and annotates it `helm.sh/hook: post-install,post-upgrade`. ArgoCD
maps that to PostSync, and PostSync runs only after the Sync phase is Synced
**and Healthy**. So: StatefulSet healthy ⟸ pods Ready ⟸ `cockroach init` ⟸
PostSync ⟸ StatefulSet healthy. Circular. Measured symptom: 3/3 Running,
readiness 503 for 38m, no init Job in the namespace.

Read from source rather than docs: gitops-engine `pkg/sync/sync_context.go`
keeps a running non-hook task pending until `health.GetResourceHealth` says
Healthy, and `setRunningPhase` prints the literal `waiting for healthy state of`.

**Fix:** `init.jobAnnotations: {argocd.argoproj.io/hook: Sync}`. gitops-engine
`pkg/sync/hook/hook.go` `Types()` says it in its own comment — *"we ignore Helm
hooks if we have Argo hook"* — so this **replaces** the PostSync mapping rather
than fighting it, and no YAML key is duplicated.

**Idempotent by construction**, as required for a hook that re-runs every sync:
the chart's loop breaks on *either* `Cluster successfully initialized` *or*
`cluster has already been initialized`, so a second run against a live store
exits 0 without touching data. `DeletePolicies()` unions Argo and Helm delete
annotations, so the policy stays `BeforeHookCreation`.

**Offline evidence:** rendering from the Application's own valuesObject before
and after gives a **one-line diff**, on the init Job. The rendered document
strict-parses with duplicate-key detection on.

### `kube-prometheus-stack` — a Secret the chart is configured never to create

Grafana was `CreateContainerConfigError`, `secret "grafana-admin-credentials"
not found`. `grafana.admin.existingSecret` is deliberate, so that no credential
is committed here — and nothing in the dev lane ever created one.

**Where the fix does NOT go:** weakening `existingSecret` would change what the
**metal** cluster deploys in order to make a CI lane green. Instead
`applyDevBootstrapSecrets` mints the Secret at bring-up, beside the StorageClass
aliases and before the app-of-apps root, from `full-ai-cluster/dev-cluster/` — a
directory ArgoCD never reads, so the blast radius is structural, not
conventional.

The value is **drawn per cluster** (`randomBytes(24)`), never committed and never
logged; a well-known constant would have worked, but a drawn one cannot be
promoted by anyone copying it. Idempotent by asking first (`resourceExists`), so
re-running a bring-up does not silently rotate Grafana's password.
`assertDevGrafanaAdminSecretPresent` refuses an included run whose cluster lacks
it — in seconds, naming the Secret, rather than burning 2400s and reporting a
Progressing Deployment.

### `weaviate` — the DESIRED state was moving, not the live state

Render weaviate 17.6.0 from the Application's own valuesObject **twice** and
diff. Exactly two lines differ:

```text
<   username: "eVJ6bFJwREhiZnBMR1RvbmZ4cmdOUmFhZUNZT2R4bHA="
<   password: "VFR3ZlZPcUxWaU95UWVSUVFIZlZ5WW9US252eFhIRE4="
---
>   username: "WFdDcEg5cHFFcjBoY1ZRR253cGVCWjd5b1dsVVpXQkU="
>   password: "S0twbUFyeVlpRkozZTlGOVBUdVQ1QlhMZlMwc08xQXQ="
```

Both in `Secret/weaviate-cluster-api-basic-auth`. Everything else in ~1000
rendered lines is byte-identical, so that is the **whole** drift — which is the
fact that makes an ignore rule honest here rather than a cover. Nothing in the
cluster was mutating anything; git was holding noise. `_helpers.tpl` tries to be
idempotent via `lookup`, but ArgoCD's repo-server renders with `helm template`
and no cluster, so only the `randAlphaNum 32` fallback ever runs.

**Fix:** `ignoreDifferences` scoped to one named Secret and two named keys —
the mechanism argo-cd's own `docs/user-guide/diffing.md` names for exactly this
cause (*"a Helm chart is using a template function such as `randAlphaNum`…"*) —
plus `RespectIgnoreDifferences=true`.

**The SSA hazard was checked, not assumed.** Under server-side apply a manager
that stops sending a field it owns has that field *removed*, so "strip the
ignored fields from the desired state" would read as "delete the credential on
the second sync". It is not what happens: argo-cd `controller/sync.go` says at
that branch that it *"applies the live values in the configured ignore
differences fields"*.

**What it costs, stated:** ArgoCD stops comparing those two keys. There is no
desired value to compare against, so nothing is lost — and
`argocd-health-test.test.ts` refuses a widening (`/data` wholesale, a nameless
rule, a jq expression, a managed-fields manager).

### `hindsight` — left deferred, and here is what was learned

Not fixed, which is the honest outcome. Three independent blockers now, any one
sufficient:

1. **Capacity, measured.** `Insufficient cpu` on the 1-node runner: chart
   defaults 500m + 250m + 250m against an applied-set total of 4131m on 4 vCPU
   with ~950m already reserved by kind's system pods.
2. **The `dev` resource rung CANNOT reach this lane** — the part that looked
   like the fix and is not. `--resource-profile dev --apply` rewrites the
   **working tree**; ArgoCD syncs the **committed** tree at `--git-ref`; CI runs
   only `--budget`, a report. There is no dev-only resource override, so
   lowering these numbers lowers them for metal too, where an under-request buys
   an evictable pod rather than a refused one. That trade is a maintainer call,
   not a CI convenience.
3. **The `valuesObject` is largely inert against chart 0.3.0** — a defect in its
   own right. It sets `postgresql.primary.persistence.*`, `api.llm.*` and a
   top-level `service`; the chart reads `postgresql.persistence.*`,
   `api.env`/`api.secrets`/top-level `existingSecret`, and
   `api.service`/`controlPlane.service`. (Its Postgres is an in-chart StatefulSet
   on `ankane/pgvector`, not a Bitnami subchart — that is where `primary.` came
   from.) Rendered proof: the PVC comes out with **no `storageClassName`** at
   **8Gi**, not longhorn at 10Gi, and no `HINDSIGHT_API_LLM_API_KEY` reaches the
   api container.

Row 3 matters beyond this lane: the storage-profile ladder governs
`postgresql.primary.persistence.size` for `hindsight`, so **that governed number
has never had an effect on anything.**
