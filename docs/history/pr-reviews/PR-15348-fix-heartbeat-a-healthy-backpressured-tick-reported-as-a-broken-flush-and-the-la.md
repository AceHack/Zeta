## Description

The heartbeat flush lane has been red on every tick for every agent holding
work. Measured across 12 consecutive runs: the "Arm heartbeat PR auto-merge"
step concluded `failure` for every lane with a delta and `skipped` for every
lane without. Never once `success`.

Its error text is `$AGENT snapshot produced no PR number`, which names the
FLUSH step, so the red reads as a broken flush. Three separate agents
diagnosed it as a token-scope fault on the auto-merge call. That call was
never reached on any of those runs — the step fails at its `[ -z "$PR" ]`
guard, before any `gh` invocation.

THREE DISTINCT FAULTS, all fixed here.

1. A SUCCESS PATH THAT DECLARED NOTHING.
   The flush step's backpressure branch — an intentional, healthy no-op, "the
   lane keeps the delta and the next flush carries it" — returns `exit 0`
   before reaching `merge-heartbeats-to-main.ts`, which is what writes
   `pr_number`. It never wrote `skip` either, so the arming step's
   `steps.flush.outputs.skip != 'true'` guard read an empty string, passed,
   and hard-failed on a blank PR number. Now declares `skip=true`.

2. THE SAME DEFECT ON A SECOND PATH.
   The `RC == 4` "already on main" no-op does the same thing. This one was
   NOT found by hand — the audit added below found it after fix (1) was
   already written, and it would have kept producing the identical
   misleading red on every already-on-main tick.

3. BACKPRESSURE WITH NO ESCAPE IS A DEADLOCK.
   Waiting on the open flush PR is correct only while that PR can still
   merge. A CONFLICTED one never can, and the retirement pass that would
   clear it sits BELOW the early return, so it is never reached. The lane
   then waits on an event that cannot occur while the tick still reports
   healthy. Measured: soraya blocked behind DIRTY #15319 since 07:50, alexa
   behind #15326. A DIRTY blocker is now closed so the lane can re-cut —
   which loses nothing, because `heartbeat/$AGENT` holds the unlanded work,
   not the ref, and re-cutting over current main is also what resolves the
   conflict.

   Scoped deliberately to DIRTY. A gate-FAILING PR is not retired: re-cutting
   every tick would relaunch the same failing checks forever and turn a real,
   visible failure into an invisible retry loop. That case gets a loud
   warning past 90 minutes instead — a stuck lane a human can see beats a
   stuck lane that hides itself.

THE FALSIFIER: audit-workflow-step-output-has-writer.ts (AH003)

The vacuity class, inverted. The familiar direction is a check that cannot
fail reading as a check that passed; this is a step that cannot pass,
reporting a defect in the subject it is pointed at rather than in itself.
Both are decided by the wiring rather than by the thing under test, and both
are invisible in a red-vs-green summary.

CONTROL (mandatory, and it is what makes this more than an assertion): run
against UNFIXED main it exits 1 and names both instances —

  agent-heartbeat.yml [flush-to-main] step 'flush'
      returns success at run-block line 103 having written none of 'skip'
      returns success at run-block line 191 having written none of 'skip'

Against the fixed tree it exits 0 over 77 workflows and 53 references.

Two false results were caught during development and both are pinned by
regression tests, because each is more instructive than the fix:

  * FALSE POSITIVE. The first draft flagged passkey-proposal-gated-commit.yml,
    whose runner does write `branch` and `proposal_id` — from inside
    TypeScript, behind a helper. Blocking CI on a working workflow is the
    expensive direction. The audit now follows script invocations, and
    reports OPAQUE (counted and printed, never silently dropped) when a
    delegated script computes output names it cannot resolve.

  * FALSE NEGATIVE, and the worse one. The first implementation used a single
    "has anything been written above?" latch. A guard that writes and
    immediately exits set that latch and silently exempted every later early
    return — which is exactly how it missed fault (2) above. Replaced with
    real shell scope tracking: an `exit 0` is satisfied only by an
    unconditional write, or by its own guard writing before returning.

The audit is also hardened against its own vacuity. While this file was being
written a bad edit deleted a helper, every workflow threw, the `catch`
swallowed it, and it printed "OK — every reference has a writer" over 77
unchecked files. Unreadable workflows are now collected and named in the
output, and a scan that finds zero references across a non-empty workflow
directory exits 2 as a configuration error rather than passing.

Tests: 27 pass, 0 fail. Under mutation (writesOutput forced true,
successPathsWithoutWrite forced empty) 10 of 27 go red; the 17 survivors are
the negative and control cases, which is the correct split.
