## ONE VOCABULARY, NOT A FOURTH DIALECT

`src/Core.TypeScript/ace/setup-realizers/unhashed-pin.ts` takes the `from-url` spelling verbatim
and adds the second case Aaron named ("we don't need a pin at all"), because a vendor endpoint
with no version cannot pin a tag it does not have:

| declaration | when | the URL |
|---|---|---|
| `sha256=<64-hex>` | the normal case | anything |
| `sha256=tag-only  tagonly=<reason>` | pin the tag instead of the SHA | MUST carry a version-shaped tag |
| `sha256=unpinned  unpinned=<reason>` | no pin at all | must NOT carry one |

The third is **refused when a version-shaped tag exists** — the weakest declaration may not be
chosen where a stronger one is available. That is the shrink direction enforced at the point of
declaration.

**Not the default, mechanically.** A digest costs 64 characters somebody measured. A reason has a
floor — 20 characters, three hyphen-separated words, and a small list of non-reasons (`todo`,
`tbd`, `unknown`, `see-comment`) refused by name. An exception cheaper than the rule spreads on
its own. **Opt-in per row; no global switch, and the module says none may be added.**

**Visible.** `unhashedInstallNotice` prints `UNPINNED INSTALL: <subject> ← <url> — no digest was
verified. Declared reason: ...` as a WARNING, so it survives a quiet run.

## MECHANISMS WIRED

| mechanism | before | after |

| `from-elan` | `"manifest row must include URL and sha256="` | routes through `resolvePin` |
| `from-autotools-tarball` | `"sha256= pin required"` | routes through `resolvePin` |
| `from-installer` | **no digest slot at all** | pin mandatory; digest rows refuse to exec on mismatch |

`from-installer` is the one that mattered most and was not on the original list. It fetched six
vendor shell scripts over HTTPS and **executed** them, with HTTPS as the only trust anchor and
nothing in the tree recording that fact. That is the worst version of an unhashed dependency —
not one somebody accepted, one nobody had to. The six are unverified still (vendors publish no
stable artifact); the exposure is now declared, counted, and printed.

## A DEFECT FIXED IN PASSING

`from-elan` validated only `sha256 === undefined`, so **any** non-empty string passed. Its own
test carried `sha256=abc`, which reached `verifySha256File` and could only fail at install time
on a real machine. Refused at parse time now; the test was updated and two refusals pinned.

## A DEFECT IN PR #17244, reported not fixed here

`requireSha256` reads the URL as `attrs.url`. In every manifest format here the URL is a
**positional token**, never an attribute — so `attrs.url` is `undefined` for every real row and
the tag-only path would throw *"requires a version-shaped tag in the URL, and "" has none"* at
install time. The 7 unit tests pass because they supply `url` as an attr, which the production
caller never does: green everywhere except in production.

`resolvePin` takes `url` as an explicit parameter for exactly this reason, and this PR adds the
falsifier that class needs — a test that runs `resolvePin` over the **committed manifest text**,
exactly as the realizer calls it, for every wired manifest.

## THE INVENTORY — the "handled separately" half

`docs/UNHASHED-DEPENDENCIES.md`. **Derived, never hand-kept** (`--write` regenerates it):

- **6 declared** unhashed, each with its own stated reason
- **172 undeclared** across 15 mechanism rows, each with the specific obstacle named
- **1923 digest-covered**, printed so the numbers are a ratio rather than a scare

The undeclared half is the honest part. Five mechanisms each quietly permitting one unhashed
dependency is not five small decisions, it is one large one nobody made — and until this page
existed nobody could count them.

## THE AUDIT FAILS BOTH WAYS — proven by running it, not by reading it

`audit-unhashed-dependencies.ts` (AH011), on the `cross-verify` floor. Each direction was
reproduced against the real tree, with a clean rc=0 baseline before and after:

```
BASELINE                                                        rc=0
DIRECTION 1  append a declared row, do not regenerate the page   rc=1
             "ENTERED WITHOUT LANDING IN THE INVENTORY: from-installer newtool"
DIRECTION 2  give a declared row a 64-hex digest                 rc=1
             "NO LONGER UNHASHED, STILL ON THE ROSTER: from-installer forge"
             "THE ROSTER SHRINKS."
DIRECTION 3  create an undescribed manifest                      rc=1
             "UNDESCRIBED MECHANISM: tools/setup/manifests/from-newthing"
RESTORED                                                        rc=0
```

Direction 2 is the property worth having and the one a one-way check lacks: an exception that is
no longer needed cannot sit there looking justified. Direction 3 keeps the other two honest — an
undescribed mechanism contributes to neither, so a new one would arrive invisible to a page whose
whole job is being the complete list.

**A caught vacuity, recorded because it is the class this repo names as its worst.** The first
version compared the digest-covered denominator table as roster too, so every run reported all
~1900 covered dependencies as stale. A check that fails always is as useless as one that cannot
fail. Fixed, and pinned by a test.
