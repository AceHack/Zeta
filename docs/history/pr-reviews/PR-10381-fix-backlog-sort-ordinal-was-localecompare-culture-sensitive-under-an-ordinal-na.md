## Description

Surfaced by the build-graph work. `lint-frontmatter.ts:90` read:

```ts
const SORT_ORDINAL = (a, b) => a.localeCompare(b);
```

A direct contradiction of its own name and of `.claude/rules/culture-invariant-by-default.md`. `localeCompare` is culture-**sensitive** — the result depends on runtime locale and ICU build, so the same input can sort differently on two machines.

## Why it is not cosmetic

Both call sites (`:316` `sortedMissing`, `:352` `sortedRedundant`) order **ZetaId row-ids whose sorted output is compared across runs**. A locale-dependent order is a determinism bug waiting for a machine with a different ICU build — the exact four-oracle byte-lock failure mode the rule exists to prevent, and the same class as the `GCounter` / `ZSet.ofSeq` incident it cites.

Fixed to `a < b ? -1 : a > b ? 1 : 0` — UTF-16 code-unit order, ordinal, identical everywhere. Still a named comparator, so `sonarjs/no-alphabetical-sort` (which forced a comparator in the first place) stays satisfied.

## Scope, stated honestly

This is **one** site, not the ~20 estimated. `localeCompare` appears **112 times across 64 files** — but a blanket replacement would be **wrong**: display sorting is legitimately culture-aware, and the rule says so.

Only two hits mention "ordinal", and the other is a test comment *correctly* documenting the discipline. This fixes the one comparator that lies about itself; auditing the remaining 111 is a per-site judgement call, not a sweep.
