## Description

fix(metal): the breaker never saw a success, and zflash's auto-pull could not pass its own gate

Two defects found by rehearsing the metal-bringup runbook. Both are the same
shape: a refusal that looked like it was working because the thing it was
supposed to measure never reached it.

DEFECT A -- the R9 circuit breaker counted installs, not failures.

zeta-install.sh had exactly ONE ledger write site and it only ever wrote
`started`. zeta_pf_validate_ledger counts `started` as a failure and resets on
`ok`, but nothing in the tree wrote an `ok`, so the consecutive-failure count
never reset. Rehearsed against the real extracted shell: three SUCCESSFUL
installs from one stick leave `trusted 3`, and the fourth boot comes up OPEN --
stranding an operator who did nothing wrong.

A completed install now records its success. Both writes go through one
`zeta_ledger_append` helper so they cannot disagree about numbering, and the
`ok` write is the LAST statement in the script -- under `set -e`, "we got here"
is the whole evidence it asserts. It is deliberately not in a trap: a trap
fires on failure paths too, which would make the success record unconditional.
Append-only, so power loss mid-install still leaves a bare `started` and is
still counted.

Every existing fail-closed property is kept: an unparseable or non-contiguous
ledger still opens the breaker, and an unwritable ESP still reports `blind` and
forces the full cancel window.

DEFECT A' -- a fail-OPEN hole found while verifying A, not previously reported.

The installer reads the ledger through `$(sudo cat ...)`, and command
substitution strips trailing newlines, so the final record always arrives
unterminated. `while IFS= read -r line` sets $line and then returns non-zero on
such a line, dropping it. Measured on main: a ledger whose last line was
garbage validated as `trusted 1` on the installer's own read path while
validating as `untrusted` everywhere else. The shell-parity test could not see
it because the test appended a newline the real caller never has.

DEFECT B -- zflash's auto-pull could not satisfy zflash's own integrity gate.

`autoDownloadFreshIsoIfNeeded` copied only the `.iso` and deleted the temp dir,
so the bare `zflash` form both runbooks recommend refused at its own gate.
Measured against the real artifacts of run 32461224707:

  as shipped ......................... manifest-missing
  sidecar copied verbatim ............ iso-not-in-manifest
  sidecar filename field rewritten ... verified

The middle line is why the rewrite is load-bearing rather than cosmetic: CI
publishes `nixos-minimal-<version>-<arch>-linux.iso`, the auto-pull renames it
to a run-stamped local name, and the gate looks the file up by EXACT basename.
`gh run download` also puts each artifact in its own directory, so the sidecar
is a SIBLING of the ISO and the download scan had to stop filtering to `.iso`
before it could be found at all.

The digest is TRANSCRIBED from the publisher's manifest and never recomputed
from the bytes just downloaded. Hashing the download and writing that as its
own manifest would produce a gate that passes unconditionally -- worse than no
gate, because it reads as one that ran. Only the filename field is edited, and
only after CI's manifest is confirmed to name the artifact actually taken. When
no manifest can be found the ISO stays unverifiable and the gate still stops
the write; nothing is downgraded to make the path work.

DEFECT B' -- the auto-pull was unreachable for the operator who needed it.

`autoDiscoverIso` bailed with exit 2 on a machine with no pre-existing
`zeta-installer-*.iso`, and it ran BEFORE the auto-pull -- so bare `zflash`
could not bootstrap itself. Discovery now returns `found` / `none` / `refused`
and lives in iso-discovery.ts, testable because cli.ts calls main() at module
scope and cannot be imported. `none` reaches the pull; `refused` (every
candidate positively names a different arch) still refuses, because a download
that papers over a real arch mismatch produces a board that will not boot.
