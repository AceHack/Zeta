## Description

## The short version

Three unclean reboots in 11 hours. I was asked to build a capture harness
*because the evidence was gone*. **Both reasons it was believed gone are false**,
and checking them took ten minutes and produced the root cause.

> **The three reboots are kernel panics, the panic reports were on disk the
> whole time, and all three are the kernel's physical page map disagreeing with
> its own reference accounting. All three panicked inside a `Cursor` process.
> Not one of `bun`, `node`, `dotnet`, `git`, `claude` or `forge` appears in any
> of them.**

```
05:46:58  panic(cpu 17): pmap_remove_range_options: ... wired count underflow @pmap.c:5072      task: Cursor
07:41:09  panic(cpu 8):  pmap_recycle_page: page 0x109bba68000 is referenced @pmap_data.c:2334  task: Cursor Helper (Renderer)
08:17:54  panic(cpu 4):  pmap_recycle_page: page 0x10758888000 is referenced @pmap_data.c:2334  task: Cursor Helper (Renderer)
```

The two `pmap_recycle_page` panics share **25 of 26 de-slid kernel frames**.
Random memory decay does not land on the same instruction twice in 37 minutes.

### The two falsified premises

| premise | reality |
|---|---|
| "No `.panic` files in `/Library/Logs/DiagnosticReports/`" | There were three, in **`Retired/`**. macOS ages reports into that subdirectory within hours; on a machine crashing several times a day it is where the evidence *is*. |
| "The unified log store is EMPTY for the pre-reboot windows" | It had **rolled**, not emptied. `log show --start "2026-08-23 21:30:00"` returned **10,289,058 lines, unprivileged**, including every crash window's tail. |

The first one is `signal-death.ts`'s rule moved from a process to a directory:
**an empty result and a result you failed to obtain are different values.** A
non-recursive search found nothing and it was reported as "there were no panics"
rather than "I did not look there." `findPanicReports()` now searches all four
directories and reports `unsearchable` separately from `found none`.

Also, since it reframes the whole thing: **9 of the last 10 boots were unclean.**
The last clean shutdown was 2026-08-13. This is a long-running pattern that
accelerated, not a bad morning. And there is a **fourth** crash today that
`last reboot` does not show (`panic-base+socd` at 05:46:58) — which is why panic
reports, not `last`, are ground truth.

## What I capture, and why each piece exists

The design is decided by one measurement. `logd` buffers in memory and flushes
periodically; whatever is unflushed when the machine dies **never reached a
disk**:

```
last persisted log line   2026-08-24 08:16:36
panic (NVRAM panicmedic)  2026-08-24 08:16:59.664
next boot (kern.boottime) 2026-08-24 08:17:16.285
                          ---------------------------------
BLACKOUT                  23.6 s alive, unlogged, UNRECOVERABLE
DOWN                      16.6 s
```

**The machine spent longer dying than rebooting and none of it is in any log.**

On the claim I was asked to verify rather than assume — *does a boot-time
capture preserve the previous boot's tail?* — **verified true, with a measured
hole.** `log collect` at boot recovers the previous boot up to the last flush,
needs **no `sudo`**, and is worth doing. It cannot recover the final ~20–30
seconds because those bytes were never written. That is the entire justification
for a heartbeat that `fsync`s.

Second clock: `Persist/` is a fixed **509 MB ring** filling at ~130 MB/hour under
agent load — **under 4 hours of history**. The window shrinks exactly when the
machine is in the state you want to study.

| command | what it preserves | cost |
|---|---|---|
| `vitals` | 1 Hz NDJSON, **`fsync` per sample** — the only thing that survives the blackout | 34.5 MB/day |
| `error-ring` | live `log stream` Error+Fault into a two-file byte-capped ring | **fixed 64 MB** |
| `snapshot` | nvram/panicmedic, kmutil, systemextensionsctl, pmset, ps, iostat, df, mount, thermal + **copies of every `.panic`** | 48 MB/day @ 96/day |
| `archive` | `log collect` + APFS-clone dedup of the symbol catalog | 124 MB real/archive |
| `boot` | classifies the boot; **archives the previous boot's tail immediately if unclean** | one archive |
| `triage` | the runbook, executed | text |
| `prune` / `cost` | bounds it, and prints the bill from artifacts on disk | — |

`vitals` records load, total and per-harness process counts, free/compressed
pages, swap, and `kern.num_files` against `kern.maxfiles` — the latter because
it is one of the few resources here with a **hard ceiling** (65536, ~13.4k at
idle). Not claimed as a panic mechanism; its trajectory into a crash is worth
having.

## Disk cost, measured rather than estimated

`log collect --last 2m` writes **524 MB**, of which **449 MB is a static symbol
catalog** (`dsc` 303 MB + 243 two-hex-digit dirs, 146 MB). Copying that into
every capture is the entire cost. APFS `cp -c` clones share blocks — **303 MB
cloned for 4 KB of real disk** — so the catalog is kept once and cloned in, and
**every clone is verified with `log show --archive` before the original is
discarded**. A dedup that silently produced an unreadable archive would be the
vacuity class aimed straight at forensics; a failed verification reverts and
refreshes the canonical.

Two consecutive captures, with a `df` delta as the independent witness:

```
1st archive (seeds the shared catalog):  594 MB real
2nd archive:                              97 MB real  for 540 MB of apparent content
tool's own "REAL disk cost" figure:       96.7 MB     <- agrees with df to 3%
```

**~580 MB/day growing; ~4 GB steady state at the default 7-day / 6-archive
retention, plus a one-time ~447 MB catalog.** On 1.8 TB free. `cost` reads the
sizes off disk rather than reciting these numbers.

## Does the existing signal-death research already predict this?

**The class, yes. The mechanism, no — and the update is worth having.**

`docs/research/2026-08-15-139-and-134-are-signal-deaths-*.md` found 147 crashes
across unrelated vendors, 38 inside garbage collectors, plus two
`SIGKILL (Code Signature Invalid)`, and concluded *"a memory-integrity fault
beneath every runtime."* Its §2c ranked **memory hardware fault** first.

Today's panic strings say **accounting**, not decay: a wired counter decremented
below zero, and a page handed to the recycler while still referenced. That gives
a single mechanism producing both datasets — a physical page still mapped by A
gets recycled into B; A's GC follows a pointer that changed underneath it and
segfaults; a signed page stops matching its signature. Every runtime affected,
because the fault is below all of them. On macOS 26 with SPTM (present in these
reports) the kernel **panics** on the inconsistency instead of silently
completing the recycle — a plausible reason panics started now while the
userspace pattern predates them.

**Filed as a hypothesis, not a result.** "Explains everything" is itself a
warning (`numerology-vs-number-theory.md`), and one day of panic data cannot
carry it. What it earns is a cheap discriminating experiment (below). It does
**not** disturb the standing warning that locally-produced byte-locks on this
machine are suspect and CI is the trustworthy oracle — today's panics strengthen
that.

```
  *** 3 panics share an IDENTICAL kernel backtrace (tasks: Cursor Helper (Renderer)).
      That is a REPRODUCIBLE kernel bug, not 3 independent memory faults. ***
```

### 2. Retargeted from cause to conditions

The cause is settled by Apple's own report — an XNU physical-map bug, with
`roots installed: 0` (no third-party kernel code) and `0% compressor / 0
swapfiles` (no memory pressure) ruling out the alternatives from inside the
report itself. So the harness now records **what conditions trigger it**:

- **`vm-churn.ts`** — `Translation faults/s` and `copy-on-write/s`, the two
  counters that measure pmap entries being created and destroyed, which is the
  lifecycle `pmap_recycle_page` sits at the end of. Measured ~30k/s idle,
  **648,837/s** under a deliberately injected 10-process mapping load.
- **Per-application processes / threads / resident MB** — the measurement that,
  over several panics, separates *Cursor is the trigger* from *Cursor is the
  likeliest bystander*. The first census already leans against the bystander
  reading: `chrome:48p/1400t/17052M` vs `cursor:16p/420t/7569M`, yet Cursor is
  the panicking task **4 of 4**. Recorded with its limits stated — one sample,
  and resident bytes are not a mapping rate.
- **`feedback-report`** — generates the Apple Feedback Assistant filing from the
  panic files on disk. **It does not submit.** That runs under Aaron's Apple ID
  and is his call. It also *declares* a missing load profile rather than
  omitting it, because a filing without reproduction conditions gets closed as
  "cannot reproduce".

### Retracted, and my reasoning was wrong

I treated `panicmedic-auxkc-present: true` as evidence the Paragon kexts were
implicated. **That flag records only that an auxiliary collection exists**, not
that it was loaded into the panicking kernel. `roots installed: 0` with secure
boot on closes it. Defender is excluded structurally — an EndpointSecurity
extension is userspace and has no path to `pmap_data.c`. Neither should be
chased further.

### Three parse bugs the live run caught that my fixtures did not

All three from writing fixtures out of field *names* instead of real bytes:

| bug | effect |
|---|---|
| `vm_stat` prints exactly one counter **quoted** (`"Translation faults":`) | the single most important counter here rendered as `?` |
| `ps -AM -o pid=` **silently ignores `-o`** and prints default columns | every process fell back to a thread count of 1 |
| `kern.num_threads` is a **limit** (81920), not a count (~5,700) | a constant printed in a column labelled as a measurement — a flat thread graph across every panic |

All three now have verbatim-bytes fixtures, and the thread count is
cross-checked against an independent source (17 `ps -AM` lines = 16 threads per
`top`).
