from here.** `081M00VN9P1087G0R000FYTTVS` stays open with a named hardware dependency.

  Node:   (none)

## What was wrong

`probeTpm2` was `exists("/dev/tpmrm0") || exists("/dev/tpm0") || readdir("/sys/class/tpm")`.

1. **`existsSync` returns `false` for every error.** Permission denial, unreadable `/sys`,
   and genuine no-TPM all produced `{ available: false }` — a check that could not run
   reporting as a check that ran and said no. The old code's own comment read *"report
   absent rather than guess"*; reporting absent **is** the guess. Same shape #11509
   measured, where an empty `grep RANDOM_TRUST` would have read as "off" while the truth
   was "on".
2. **A device node is not a family.** `/dev/tpm0` is also a **TPM 1.2** node. The probe
   returned `{ available: true, path: "/dev/tpm0" }` on a 1.2-only machine and offered the
   `hardware-tpm2` tier there — a tier that cannot work on a chip with no `TPM2_Create`,
   no `tpm2_unseal`, no SHA-256 PCR bank. Same inference as *library on disk ⇒ token
   attached* (#10644), one layer down.

Also: it claimed `/dev/${entries[0]}` from a `/sys/class/tpm` listing of unspecified
order, on a host that registers both `tpm0` and `tpmrm0` — so it could name a device path
it had never checked existed.

## The four-way distinction (five states)

| state | means | what it is NOT |
|---|---|---|
| `present` | a usable node AND a confirmed family 2.0 | — |
| `absent` | `/sys/class/tpm` **enumerated** and registers no chip | not "we could not look" |
| `unreadable` | a source exists and denied us (EACCES/EPERM) | not "no TPM" — a privileged caller gets a different answer |
| `unavailable` | no tpm class, no tools, or not Linux | not "no TPM" — the driver may simply not be loaded |
| `indeterminate` | a node is there and nothing confirmed the family | not `present` — never round an unconfirmed device up to a capability |

`absent` has **exactly one producer**: a listing that succeeded and came back empty. A
missing tool, a denied read and an errored read are recorded as evidence and never
counted as a negative — so a check that did not run can never look like one that passed.

The sharpest pair is `unavailable` vs `absent`. `/sys/class/tpm` **existing and empty** is
a real enumeration returning a real negative (the fTPM-disabled-in-BIOS case the item
names). `/sys/class/tpm` **not existing** means the subsystem is not exposed, where "no
TPM installed" and "driver not loaded" are indistinguishable — reporting that as `absent`
would be flatly wrong on an x86 node whose fTPM is enabled.

Tests that pin it: `four causes, four states — collapsing any pair is the defect` (each
cause → its state, plus `no two of the four share a state` and four distinct operator
actions in the reasons); `a missing tool and a denied read can NEVER produce ABSENT`
(8 non-answers); `a device node is not a family — the TPM 1.2 trap`; and at the caller,
`the four not-present states reach the caller intact, and only one is a hardware finding`.

## Structure

`tpm2-linux-probe.ts` splits **capture** (all IO, through an error-preserving seam that
keeps ENOENT / EACCES / not-installed / not-attempted apart) from **classify** (a pure
function of a serialisable record). So the parsing is fully testable with no TPM, and a
capture taken on real silicon can be committed as text and replayed forever.

`tpm2-linux-captures.json` holds the fixtures. Every entry carries `provenanceKind`:
**one** is `observed` (the macOS one, i.e. the entry that proves only that the probe
declines to answer where it cannot ask); the rest are `hand-constructed` and each says
`NO TPM WAS CONTACTED` in its provenance string, which a test asserts.

## How the hardware dependency gets discharged

```bash
bun tools/setup/persona-keys/tpm2-linux-probe.ts --capture-json
```

Emits the whole reading as JSON. Append it with `provenanceKind: "observed"` and an
`expectedState` **written from what the operator sees** (BIOS setting, `tpm2_getcap`
output) rather than copied from the classifier — the fixture must be able to disagree
with the code. A guard test asserts that no `observed` capture reports `present`; it goes
red the moment real silicon lands, which is the signal to close the item. The gap cannot
close silently, and cannot stay closed by accident.

## UNVERIFIED

- That a real TPM 2.0 produces the reading the `present` fixture describes. Hand-built
  from `drivers/char/tpm/tpm-sysfs.c` (exports `tpm_version_major` since kernel 4.19) and
  the tpm2-tools 5.x `properties-fixed` YAML shape. **Nobody here has seen either from a
  device.**
- That `tpm2_getcap properties-fixed` emits exactly this YAML on the version a node ships.
  The parser fails *closed* (`undefined` → not a negative → at worst `indeterminate`), but
  it has never met the real tool.
- The exact stderr of a TCTI permission failure. Recorded as evidence only, never counted
  toward a state.
- Whether fTPM is in fact commonly disabled in BIOS on nodes we would buy. That is the
  item's premise and it remains hearsay.

**Nothing here observes hardware. No device is claimed attested, sealed, or present.**
