## Description

## What broke

`www.gnupg.org:443` stopped answering on 2026-08-26. Both Windows legs of `main` failed the toolchain step on every commit (`c3addd47`, `4ca7cc9b`), identically on x64 and ARM:

```
Installing 'gnupg' (2.5.21) [64bit] from 'main' bucket
A connection attempt failed because the connected party did not properly respond
  ... [::ffff:5.9.17.227]:443 (www.gnupg.org:443)
URL https://www.gnupg.org/ftp/gcrypt/binary/gnupg-w32-2.5.21_20260702.exe is not valid
  | scoop install gnupg failed (exit 1)
```

The outage is upstream. **What is ours is that it was survivable and we could not survive it.**

`manifests/windows` line 73 carries `choco=gnupg`. The same job printed `choco: 2.7.3` seventy seconds before it died. The third resolver was installed, named in the label on every line of install output, and never asked.

## Defect 1 — a fallback that could not fire

The manifest loop picked the **first available** source with an `if/elseif` and ran only that one. scoop is bootstrapped forty lines above, so `Have scoop` is always true and the winget and choco branches were unreachable for every input on every platform. "scoop -> winget -> choco" — in the step label, in step 1b's *"the THIRD resolver source"* comment, and in the manifest's own column layout — described a fallback that could not execute.

Now the loop builds the whole candidate chain and falls through on a non-zero **exit**, not merely on a missing CLI. Success short-circuits, so a healthy scoop still costs exactly one attempt. A required tool failing on every source still throws, and the message names every attempt rather than only the first. Simulated against the measured failure: scoop fails, winget fails, choco installs, job continues.

## Defect 2 — the failure reporter could not run

`Name the crashed/hung test (on failure)` was gated on bare `failure()` and runs `bun .../print-blame-sequences.ts`. When the failing step is the one whose job is to install bun, the reporter dies with `The term 'bun' is not recognized`. **That is why both annotations on the check-run read `Process completed with exit code 1` and neither named a step.**

A reporter that depends on the artifact whose installation just failed goes silent in exactly the case it exists for.

- The blame printer is now gated on `steps.test.outcome == 'failure'` — the only state where a blame `Sequence_*.xml` can exist. It is exit-0-always by contract, so a non-zero exit there now means what it should.
- A new **toolchain-free** reporter runs on `failure()` using nothing but `echo` — a builtin in bash and an alias in pwsh, so it needs no `shell:` key and no installed program — and emits an `::error` annotation naming which of install / guard / build / test actually failed.

## Falsifiers

Nine assertions in `src/Core.TypeScript/ci/toolchain-install-stall.test.ts` (guards 6-7). Every one fails against the pre-fix tree and passes after — verified by reverting each file and re-running.

The last one is the general form, stated once so the class cannot return under a new name:

> every `failure()`-gated step in `build-and-test` either needs no toolchain, or names the step it reports on.

## What this does NOT fix

gnupg still has exactly one origin on the scoop path, so the next outage costs one extra minute per Windows job before choco rescues it. Pinning a mirror is a separate decision, not made here.

## Correction worth carrying

The first read of this failure was *"it reproduces on two consecutive commits, therefore it is deterministic, therefore it is our defect."* That inference is wrong: **an upstream outage reproduces identically** — it is stable while its cause is stable. Reproducibility does not separate an internal defect from an external one. Only the error text does.
