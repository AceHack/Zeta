## Description

## The defect

The `timeout-minutes: 5` on `path-filter` was not *bounding* the job — it was **killing** it.

Measured over **287 `Checkout` steps** (REST jobs API across 390 recent gate runs): **12 were cancelled at exactly 298–300s** — at the cap, not near it.

Because `path-filter` gates **both** `build-and-test` and `full-verify`, each kill skipped 2 of 8 floor jobs and red-lined the whole run as `gate scope=reduced: 6/8 floor jobs ran`. The rate was climbing while I measured: ~21% of concluded gate runs an hour before this PR, ~32% at re-sample.

## The distribution, and where 15 min comes from

Successful checkouts only (n=273):

| p50 | p75 | p90 | p95 | p99 | max |
|-----|-----|-----|-----|-----|-----|
| 22s | 23s | 36s | 70s | 201s | 262s |

Histogram: 236 of 273 land in 15–29s, then a genuinely heavy tail — 105s, 120s, 155s, 201s, 232s, 262s — and then 12 observations pinned at the cap.

That shape is the finding: the tail is **continuous up to 262s**, so a 5-minute cap sat *inside* the distribution and truncated it. This is right-censored data — the 12 kills have no measured duration, only a lower bound.

**15 minutes** = ~3.4× the slowest observed success, ~41× the median. Far enough out that it fires only on a true hang, which is what a timeout is for. The asymmetry justifies erring high: a high cap is paid for only by an already-stuck job, while the low cap was being paid for by every slow-but-healthy run.

## This is a stopgap, and the comment says so

The comment in the file states the basis, the date, and the expiry, so the next reader finds a dated decision rather than a magic constant. The repo adds ~170 commits/day and the fetch this cap covers grows with the **ref count** (81 heads + 359 tags today) — so 15 min will be outgrown too.

**The real fix is to stop over-fetching.** `fetch-depth: 0` makes checkout fetch every branch and every tag at full depth:

```
git fetch --no-tags --prune origin +refs/heads/*:refs/remotes/origin/* +refs/tags/*:refs/tags/* +<sha>:refs/remotes/pull/N/merge
```

Measured: **297 MB** for that, vs **162 MB** for the two commits the diff actually needs. Every other job in this workflow uses a shallow checkout (~162 MB) and completes in ~9s with essentially zero hangs across hundreds of samples; `path-filter` is the only `fetch-depth: 0` job and the only one that hangs. That fix follows in a **separate PR** so it gets its own scrutiny — it has a behavioural surface this one does not.
