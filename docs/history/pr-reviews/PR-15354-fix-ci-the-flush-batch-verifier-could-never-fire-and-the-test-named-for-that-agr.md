## Description

`verify-flush-batch` in `agent-reviewer.yml` gated on
`contains(github.head_ref, '-flush-')`. That was right while every snapshot
ref was `heartbeat/<agent>-flush-<40 hex>`. #15309 moved the fleet to a
REUSED ref, `heartbeat/<agent>-flush` — no trailing `-`. The parser in
`verify-flush-batch.ts` was updated to accept both forms; the trigger was
not.

Measured: `skipped` on all twelve most recent runs. A check that never ran,
reading as a check that passed. This is the second time this specific trigger
has been wrong, which the file's own comment records.

THE PART WORTH READING — the test that was supposed to prevent exactly this:

    test("its trigger matches the branch form the fleet actually produces", () => {
      const wf = executableBody();
      expect(wf).toContain("-flush-");

It was NAMED for the agreement it did not check. It asserted a magic
substring, so it passed BECAUSE the trigger was stale, and it would have
refused this fix. Its own comment said the two must agree "or the two drift
the way the trigger already did" — it knew about drift, was written after a
previous instance, and still could not see this one. A string assertion
cannot notice its string going wrong.

Replaced with a test that EVALUATES the real `if:` expression against the
real parser. It extracts the expression from the workflow, interprets the
exact GitHub Actions surface the trigger uses (`startsWith`/`endsWith`/
`contains` over `github.head_ref`, with `&&`, `||`, `!`, parentheses), and
asserts that whatever fires is whatever `deriveProducer` can name — in both
directions. It THROWS on syntax it does not model rather than guessing,
because a silently-mis-evaluated expression puts us back at a green test over
an unchecked trigger.

CONTROL, which is what makes this more than an assertion:

  new test vs UNFIXED workflow  -> 29 pass, 1 fail (EVALUATES case)
  new test vs FIXED workflow    -> 30 pass, 0 fail

The old test passed both, which is the whole defect.

Two further cases are pinned as controls: the evaluator must return false for
the stale expression on `heartbeat/otto-flush` while still returning true on
the legacy form (that asymmetry is exactly why the break looked fine), and it
must throw on unmodelled syntax.

`-buffer` is excluded from the new trigger deliberately:
`heartbeat/<agent>-flush-buffer` satisfies `contains('-flush-')` but parses
to a null producer, which is a `severity: fail` finding — firing on it would
manufacture a red from a healthy ref.

Found by the ruleset-as-code agent while auditing something unrelated, not by
the guard that existed for it.
