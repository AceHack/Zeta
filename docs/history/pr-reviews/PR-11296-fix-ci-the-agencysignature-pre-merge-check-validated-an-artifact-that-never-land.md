## Description

fix(ci): the AgencySignature pre-merge check validated an artifact that never lands

The check rested on a stated premise that is FALSE for this repository. Its header read:
"GitHub squash-merge takes the PR BODY as the commit message, so the body is where the trailer
block has to be for it to survive the merge at all." Measured:

    gh api repos/Lucent-Financial-Group/Zeta -> squash_merge_commit_message = COMMIT_MESSAGES

GitHub builds the squash from the PR's COMMIT MESSAGES, concatenated with `---------`
separators. The PR body never reaches it. So a PR could carry a perfect block in its body, go
green on `agencysignature (PR body)`, and land a squash commit with no block at all -- which
`audit-main-tip` then correctly reddens on main, where it cannot be fixed without rewriting
history.

That is not hypothetical. PR #11267 had the block in its body, PASSED this job, and landed
48d3f4ed0aaf with zero occurrences of `Agency-Signature-Version`. main is red on it right now.
A green check that structurally cannot protect the invariant it appears to protect -- and one I
personally trusted when I merged that PR.

FIX: add a second step validating the SQUASH PREIMAGE -- the PR's commit messages, from
`pulls/<n>/commits` -- through the SAME validator. The two jobs now judge one artifact: the
commit, which is also where audit-main-tip reads.

WHY NOT JUST FLIP THE SETTING TO PR_BODY. That would make the old sentence true with one
setting change and it is the wrong call. GitHub does NOT re-run checks when a PR body is
edited, so pass-green -> edit-body -> merge would produce a blockless squash behind a green
check, on text this workflow already labels ATTACKER-CONTROLLED. Commit messages cannot change
without a push, and a push re-triggers checks. Binding the signature to the commit is both what
actually lands and the only tamper-evident option.

Implementation notes, both deliberate:
  - The commit list comes from the API, not `git log`: actions/checkout is shallow by default
    so BASE..HEAD would not resolve, and fetch-depth: 0 is an expensive way to buy a list
    GitHub hands over directly.
  - Reconstruction is CONSERVATIVE, not byte-exact. The validator needs ten contiguous keys
    somewhere in the text; concatenation cannot manufacture that block if no commit carries it.
    Eliminating the false GREEN is the point. A red here means a commit really is missing its
    block.
  - `pull-requests: read` added, least privilege, for this step only.

TWO-SIDED FALSIFIER, run against real PRs rather than fixtures:
  - #11267 (the PR that produced the bad commit) -> exit 1
  - #11272 (a PR whose block is in its commits)  -> exit 0
So it catches the actual failure and does not redden everything. actionlint clean.

NOT DONE, and deliberately: the existing red on 48d3f4ed0aaf stays. The auditor's own header
says the fail-closed change "adds no retroactive red to main -- and removes none of the red
already there", and that commit is a TRUE POSITIVE. Silencing it with a roster entry would be
exactly the silent exemption the fail-closed inversion was built to end. It is fixed forward or
it stays visible; the roster is not a mute button.
