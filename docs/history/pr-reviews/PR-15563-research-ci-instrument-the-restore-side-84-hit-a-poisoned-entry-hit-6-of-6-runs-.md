## Description

Adds **§9** to the sawtooth measurement that landed in #15538. Purely additive against current `main` — the only lines it removes are the two it renumbers/extends.

low-memory.yml jobs across 7, none skipped for missing logs.

- gate.yml hit rate 84.0% (420/500 restores), 75.1% excluding apt-archives and
  setup-bun's own cache -- the two families this repo does not key itself.

- The poisoned 172 KB dotnet-Linux-X64 entry §6.3 reported from two samples is
  restored on 6 of 6 gate runs, every time on build-and-test (ubuntu-24.04). The
  same hash on other arches holds 429,688,927 B and 1,948,464,753 B. Every hit
  also logs "not saving cache", so the entry is self-preserving: ~/.dotnet is
  re-installed by install.sh on every ubuntu-24.04 gate run while the cache
  reports a hit. Job ids recorded in §9.3. The WRITER is still not identified.

- install-v2 is a cold-key STAMPEDE, not a thrash loop. This REFINES §4.4 rather
  than contradicting it: §4.4 was right that the save fires on a genuine miss.
  What it could not see is that 12 jobs miss TOGETHER against a fixed key hash,
  all 12 upload the same ~1.19 GB blob, and 31 lost the reservation race across
  3 runs. So one cold key costs 12 full installs and ~11 wasted uploads, and the
  lever is how often the key goes cold (§6.1), not the save logic.

- nuget and elan were split across TWO key namespaces -- arch-qualified in
  gate.yml/lean-proof.yml, arch-less in low-memory.yml/codeql.yml. 28.6% hit rate
  against gate's 78.8% for the same content, with the same
  Directory.Packages.props digest charged twice in the live cache (357 MB +
  358 MB). Churn is excluded as the cause: the digest was constant at c922cac0
  for the whole window. This IS a save whose restore key never matches, and it is
  the case §4.4's argument does not reach -- §4.4 asked about split restore/save
  steps within a job, and the divergence is BETWEEN WORKFLOWS. Fixed in #15560,
  which also ships the falsifier that goes red on the main this measured.

§9.5 confirms §7 item 2 on a new axis. Twelve job definitions inside one workflow
independently raced to write the same install-v2 tar -- not twelve jobs reading a
shared cache, twelve that each missed and each began uploading every toolchain.
Under round 3 §7's candidates those twelve would not all live in one repository,
so the union blob is a single physical artifact 23 job definitions genuinely
share. A repo boundary RELOCATES it. The per-leg install subset is a
PREREQUISITE for the split's cache goal, not a follow-up.

WHAT §9 DOES NOT CLAIM, stated because each was close enough to round up to:

- It does not close §8's open bullet. That bullet asks whether a job FAILED
  because of a cache miss. §9 collects the per-job cache-hit outputs §8 named as
  the missing ingredient and stops there; knowing a restore missed does not
  establish a job failed because it missed. The bullet stays open.
- It does not re-derive §5's Zeta-core 11.17 GiB or the 59% union share. §9.5
  confirms the union-blob MECHANISM; those figures stay at bounded, not
  predicted.
- It does not reverse §4.4. Both of §4.4's falsifications stand as written.

Three items are marked not established in §9.7: the writer of the poisoned entry,
the cause of the cold window (branch-scoped visibility -- timing-consistent only,
scope not confirmed), and Windows steady state (n=1). Two smaller findings in
§9.6 are named and deliberately not acted on: an apt-archives key that does not
determine its content (three payload sizes under one key), and Linux-nuget-*,
written by GitHub's managed dependency-submission workflow which is not in this
repo.
