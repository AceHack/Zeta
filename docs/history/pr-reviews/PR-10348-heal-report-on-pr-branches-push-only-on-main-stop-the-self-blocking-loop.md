## Description

`lint-autofix-apply` pushed its heal commit to whatever branch triggered it, including PR branches. That starts a loop which **blocks the PR it was trying to help**:

1. PR opens → `lint-autofix` computes a heal
2. `lint-autofix-apply` → **pushes the heal to the PR branch**
3. that push is a `synchronize` event → re-triggers the PR workflows
4. `triggering_actor = github-actions[bot]` → GitHub parks the run as **`action_required`**
5. with a required status check, that run never reports → **PR blocked** until a human approves a workflow by hand

Observed on **PR #10346**: gate passed at 16:08, the heal pushed at 16:13, and the PR has been stuck behind an unapproved run since. Every markdown-touching PR would do the same, so approvals accumulate and someone clears them by hand forever.

## Rejected alternative, recorded because it's the tempting one

A cron job calling `POST /actions/runs/{id}/approve` to drain pending runs.

That gate is a **security control** — it's what stops bot- and fork-triggered workflows executing untrusted code with repo credentials. Blanket auto-approval removes the control while leaving its appearance, which is the same shape as a bare `|| true` and as the ignore list nobody consulted.

## The fix addresses the cause

- On **`main`**: the heal lands as before — there's no author to surprise.
- On **any other branch**: it's **reported**. The job summary carries the exact diff and the one-liner to apply it locally, plus a `::notice`.

Not silence — the finding still surfaces, it just doesn't seize someone else's branch.

That second property matters independently of the loop: **the healer was rewriting contributors' commits under their PR without being asked.**

Both paths simulated (`main` → PUSH, other → REPORT), the only `git push` now sits inside the `main` guard, YAML parses.
