## What landed

- `docs/BACKLOG.md` — new section with three rows:
  1. **Zeta hot-path checked-vs-unchecked audit** — per-site bound analysis across ~30 `Checked.(+)`/`Checked.(*)` call sites. Six-class classification matrix. FsCheck bound proofs + BenchmarkDotNet deltas required per demotion. Owners: Naledi / Soraya / Kenji / Kira. L effort.
  2. **Craft production-tier ladder** — first module: checked-vs-unchecked arithmetic. New directory tier at `docs/craft/subjects/production-{lang}/{topic}/` (proposed in PR #208, still open). M effort.
  3. **Top-level `docs/craft/README.md`** — currently absent; S-effort hygiene follow-up.
- `docs/hygiene-history/loop-tick-history.md` — Otto-47 row + schema clarification that `auto-loop-N` is a per-session counter (UTC timestamp is the canonical ordering key; compaction resets the counter).

## Why now

Zeta currently uses `Checked.(+)`/`Checked.(*)` pervasively with canonical rationale at `src/Core/ZSet.fs:227-230` (unbounded stream-weight sum sign-flip). Rationale applies unevenly — counter increments, SIMD-lane partial sums, bounded-domain products are demotion candidates. Aaron's *"unchecked is much faster when its safe"* names the operative principle.

## Companion PRs

- PR #208 — production-tier Craft module (open; teaches the decision framework)
- PR #209 — BenchmarkDotNet harness (MERGED as `3e1b97f`; proves the framework's ≥5% gate claim)

## What this is NOT

- Not a mandate to demote every `Checked.` site (canonical stream-weight-sum case stays Checked).
- Not a license to skip property tests (demotion requires bound proof).
- Not onboarding material (production-tier ladder is a distinct audience).
