## Description

## What was actually wrong

The aarch64 boot proof has been reporting a green check while failing. Two defects; fixing only the timeout would have kept the second.

**The image was never broken.** I downloaded the ISO artifact from run 31953781386 and booted it locally on an M2 Ultra (QEMU 11.0.1). It reaches `zeta-installer login: nixos (automatic login)` in **24s under HVF** and **52s under pure TCG**. The CI job's serial log ends at `EFI stub: Exiting boot services` after exactly 1800s — the guest was still inside the kernel handoff when the budget expired. Confirmed from the job log directly: `timeout: 1800s`, `-cpu max`, and the harness's own `aarch64 without same-arch KVM; using TCG` warning. The `ubuntu-24.04-arm` runners do not expose `/dev/kvm`, so this lane is pure TCG on QEMU **8.2.2**.

A hypothesis I held, tested, and **refuted** — recorded so nobody re-runs it. The CPU model is not the lever:

| TCG `-cpu` (same host, same ISO) | to login |
|---|---|
| `max` (what CI uses) | 58s |
| `max,pauth-impdef=on` | 62s |
| `cortex-a72` | 60s |
| `neoverse-n1` | 63s |

All within noise, so `-cpu max` is left alone.

## Defect 1 — TIMEOUT and BOOT-FAILED were indistinguishable

This is the one that matters, because it is why a real boot break would read as "TCG was slow again".

A genuinely non-bootable image **does not exit QEMU**. Reproduced with a 4MB `/dev/urandom` "ISO": EDK2 finds no boot option, drops to the UEFI Shell, and sits there — still alive at 180s. So the old code burned the full budget and printed `Timeout (1800s) waiting for ...`, the same sentence and same exit code a slow-but-healthy boot produced. Separately, the `abandoned` predicate required `qemuExitCode !== 0`, so a guest that powered itself off cleanly was also waited out and mislabelled a timeout.

The discriminator that works is serial **content**, not process exit: a boot-stage ladder (`none → firmware → bootloader → efi-stub → userspace → login`) plus positive failure markers. Verified against three real captured logs:

| serial log | stage reached | outcome |
|---|---|---|
| healthy boot (local HVF) | `login` | BOOTED |
| **the actual failing CI run** | `efi-stub` | **TIMEOUT** |
| non-bootable image | `firmware` | **BOOT-FAILED** |

Exit codes are now `0` BOOTED / `1` BOOT-FAILED / `2` usage / `3` TIMEOUT, and the ladder prints live with elapsed seconds so the next CI log *shows* where the time goes instead of leaving us to guess. Locally that profile is `firmware t=1s → bootloader t=16s → efi-stub t=17s → login t=52s`, i.e. 35 of 52s sit in exactly the segment where CI dies.

## Defect 2 — the step could not fail

`continue-on-error: true` is removed; it made the boot proof vacuous. It is **not** simply flipped to blocking, which would trade a silent lane for a flaky red one. The step branches on the exit code instead — **BOOT-FAILED fails the job, TIMEOUT warns only**. The proof becomes load-bearing; the budget stays advisory.

**Honest limit, stated rather than papered over:** a break that manifests as a silent *hang* past the bootloader still lands in the advisory bucket. This gate catches images that fail to boot, not images that hang. Tightening that needs the CI boot to first land reliably under budget.

## Budget

1800 → 4200s. The implied CI slowdown is **>31x** versus the local TCG measurement, which is more than a config tweak closes — so the budget is raised *with instrumentation* rather than guessed at precisely. The job's own `timeout-minutes: 120` bounds the blast radius (~6 min is checkout/nix/apt/build). This PR touches `qemu-boot-test.ts`, which is in the workflow's path filter, so **this PR's own run produces the real number** via the stage ladder.

## Falsifier

`qemu-boot-test.ts` previously had **no test at all**, which is a large part of why this survived. 34 tests added, built on the three real logs. They are falsifiers, not assertions — four reverts were mutation-tested and every one is caught:

| reverted to old behavior | tests failing |
|---|---|
| drop the failure-marker check | 1 |
| restore the non-zero-exit-only predicate | 1 |
| collapse TIMEOUT into exit 1 | 3 |
| revert the budget to 1800 | 2 |

Demonstrated end-to-end rather than asserted, same harness and flags:

```
non-bootable image   -> BOOT-FAILED, exit 1, in 6s   (not 1800s)
real CI ISO          -> BOOTED,      exit 0, in 52s
real CI ISO, 25s cap -> TIMEOUT,     exit 3, stage=efi-stub
```

The third case reproduces the CI signature exactly, and it is **exit 3** where the non-bootable image is **exit 1**. The workflow dispatch was tested for all four codes: `0` pass, `3` pass+warning, `1` fail, `2` fail.
