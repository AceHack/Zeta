## Description

## Summary
Minimal F# ASP.NET Core Web API serving CRM seed data as JSON. Any frontend choice consumes the same 9 endpoints. Build green, 0 warnings. `dotnet run` + curl confirmed all endpoints working.

### Verified output
```
GET /api/pipeline/funnel      → [{"count":10,"stage":"Lead","totalCents":5400000}, ...5 stages]
GET /api/pipeline/duplicates  → 2 collisions ([1,13] share alice@acme; [5,19] share bob@trades)
GET /api/customers/1          → {"id":1,"name":"Alice Plumbing LLC",...}
```

### Endpoints
- `/api/customers` + `/api/customers/{id}` + `/api/customers/{id}/activities`
- `/api/opportunities` + `/api/opportunities/{id}`
- `/api/activities`
- `/api/pipeline/funnel` (count + total-cents per stage)
- `/api/pipeline/duplicates` (customers sharing an email)

### Why stack-independent
Aaron has not picked Blazor vs React vs other for the frontend. This API ships a JSON contract any of them can consume. Frontend-stack decision stays open.

### Why this move
Third EXT commit of the session on priority #1. Live-lock audit fired earlier; inaugural lesson said "ship external-priority increments when smell fires." Three landed, all priority #1.

### What this does NOT do
- No Postgres wiring — in-memory v0; Npgsql is a follow-up PR
- No Zeta / DBSP / retraction-native language exposed to frontend
- No writes (read-only v0), no auth, no docker-compose yet
