## Description

## The question

Aaron 2026-08-14: *"our zetaids might need new categories that don't have timestamps — we want to be able to represent anything as a **universal pointer**. we might need a **v3 zeta id** or some **zetaid/content address relation mapping**."*

## The short answer: do not add v3 — it already exists at v1, under Category

**CHECKED** by reading `Codec.fs` / `zeta-id.ts` rather than the docs:

- `packGeneric` gives **categories ≥ 9 a 119-bit payload and no Timestamp field**. Two layouts already share the envelope at v1, discriminated by **Category** (bits 65–68, same offset in both layouts), not Version.
- `Category.ContentAddress = 9` is registered in `registry/categories.yaml` and all seven oracles; `ZetaIdPayload` is already the `Observation | ContentAddress | Generic` union.
- **Two production sites already mint derived, clock-free ids**: `pr-manifest-shards.ts` (PR number written into the id — pure, injective, invertible, `timestamp: 0` = unspecified; 6,498 on disk) and `tick-shards.ts` (content digest; 586 on disk).

So the blocker on `gen(gen) == gen` was never the *existence* of Timestamp/Randomness. It was that `pack` draws randomness from an **ambient** `SimulationEnvironment`. Point that env at the subject and the id regenerates forever. **The fix is a noninterference (§13) discipline about where identity bits come from, not a new envelope.**

Two corrections to the brief's framing, both CHECKED: there is **no 80-bit hole** (Timestamp @75 and Randomness @0 are not contiguous — 48 bits of other fields sit between them), and **no v2 exists** (`registry/id-versions.yaml` registers V1 only; 100% of 9,918 scanned ids are v1).

## The guard, re-scoped

Aaron's mid-task correction is right: a fixed-offset 128-bit id is sortable by whichever field you mask to the top, so "refuse unknown versions at every sort site" is **over-broad**, and I am reporting it as such. Surveyed **all 13 ZetaId sort sites** and classified each by ordering *intent* — **exactly one orders by time-from-the-id, and it is `ls workitems/`, not code.** Every code site orders by an ISO timestamp carried in the record, or wants any stable total order at all.

`src/Core.TypeScript/zeta-id/sort-key.ts` makes the site declare its field instead:

| | |
|---|---|
| `timeSortKey` | ms from the Timestamp field. **Refuses** unknown versions **and** any category ≥ 9 |
| `identitySortKey` | the whole 128 bits — total, version-agnostic, carries no time claim |
| `compareByField(offset,width)` | the general masked sort; time order is its special case |
| `isTimeSortableSet` | *checks* the `ls workitems/` claim instead of asserting it |

### It catches a defect that exists TODAY

The two live `inventory/items/` ids (`Category.InventoryAsset` = 10) read out of bits [75,123) as ms epoch **228_227_880_623_423 — the year 9200** — and sort after every observation id that will ever be minted, with nothing saying so. The tests name those two real ids.

> **CORRECTION (see the retraction comment below).** An earlier version of this paragraph blamed `new-item.ts` for "an offset that does not line up." **That was wrong and is retracted.** The mint writes exactly where it intends: the ms round-trips exactly, lands at id bits [82,123) above the constant Category field, and `ls inventory/items/` genuinely is chronological within the category — the two live ids decode on their own layout's terms to `2026-07-02T22:11:57.370Z` and `.419Z`, in lexical order. The year-9200 figure is what you get decoding a **Generic** id against the **Observation** layout: a **misread, not a miswrite**. What survives is narrower and is what this PR actually fixes — **cross-layout comparison is meaningless and nothing said so**. `new-item.ts` is byte-unchanged here, and three new tests plus a mutant pin the mint as correct so nobody "fixes" a correct offset later.

## Did Aaron's 80/20 hold? No — inverted; the shape held exactly

| Denominator | id-time-dependent |
|---|---|
| stored ids (9,918 scanned) | **~4%** (392 in `workitems/`) |
| mint sites (11 non-test) | **~27%** (3, plus a 4th that intends to and doesn't) |
| sort sites (13) | **1**, and it is `ls`, not code |

Every reader that needed real time order independently reached for an ISO string in the record instead of the id. The corpus has already voted against id-as-clock. But the *shape* of the intuition held: the non-time cases are the two most interesting algorithms in the store — upsert-by-construction, zero ambient entropy, replayable.

## Birthday bound

`p ≈ 1 − exp(−N²/2^(b+1))`:

| Width | 50% at N | N=10⁶ | N=10⁹ | N=10¹² |
|---|---:|---:|---:|---:|
| 119 bits (`packGeneric`, exists) | 9.6 × 10¹⁷ | ~0 | ~0 | 4.2 × 10⁻¹³ |
| 80 bits (the hypothetical) | 1.29 × 10¹² | 4.1 × 10⁻¹³ | 4.1 × 10⁻⁷ | 0.339 |
| 32 bits (`tick-shards` today) | 7.7 × 10⁴ | ≈1 | 1 | 1 |

**80 bits is acceptable** — 1 in 2.4 million at a billion objects, ~10 orders of magnitude under undetected-media-error probability — and it **breaks near 10¹²**. But it is the wrong number to design to, because 119 is already on offer and pushes the 50% point to 10¹⁸. Strongest option is neither: where a natural key fits, write it in and the map is injective — collision-free by *construction*, which is what `pr-manifest-shards.ts` does.

## Envelope vs sibling, and the git comparison

**One envelope; it is already built.** Git's own split cuts the other way from how it's usually told: commit/tree/blob SHAs share **one** 160-bit object-name space with an in-object *type header*; refs are a separate namespace because a ref is not an object. Mapped over: **Category is the type header**, and `workitems/<zetaid>-<slug>.md` **is** the ref layer (mutable name, immutable id — the slug can be reworded and the id doesn't move). The ZetaId↔ContentAddress mapping Aaron floated is the right structure and it's already present as filenames + frontmatter. A second 128-bit identifier *type* would be the type error: it forks the Crockford convention, seven cross-verified oracles, and every `isCanonical` check to buy a distinction Category already draws.

No coinage: this is a **versioned identifier union with a type-tagged discriminator** (RFC 4122 variant/version; multiformats `multihash`).

## Hardware intrinsics — named, with the honest caveat

**BMI2 `PEXT`/`PDEP`** (Intel Haswell, 2013) do scattered-field extract/deposit under a mask in one instruction. Caveat that changes the answer on *this* fleet: they are microcode-emulated and ~2 orders of magnitude slower on AMD before Zen 3, and **AArch64 has no single-instruction equivalent** — and `inventory/items/` records a Mac Studio M2 Ultra. Nothing in `BitLayout` needs `PEXT` today: every declared field is contiguous, so masked sort is one shift + one AND everywhere.
