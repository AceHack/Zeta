## Description

## My previous fix (#10913) did not work. Owning it and replacing it.

#10913 kept #10850's PAT on `agent-heartbeat`'s checkout and added an in-step fallback: on a 403,
unset `http.https://github.com/.extraheader`, re-point `origin` at
`https://x-access-token:$GITHUB_TOKEN@github.com/…`, retry. I verified it against a **stubbed
`git`** in three modes and shipped it.

It failed on the first real tick after merge — run
[`31954669720`](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/31954669720),
2026-08-16T15:08Z:

```
remote: Permission to Lucent-Financial-Group/Zeta.git denied to AceHack.   <- primary (PAT)
##[warning][heartbeat] ZETA_TELEMETRY_FLUSH_TOKEN cannot push ... falling back to GITHUB_TOKEN
remote: Permission to Lucent-Financial-Group/Zeta.git denied to AceHack.   <- fallback, SAME identity
##[error]Process completed with exit code 128.
```

**Why the verification did not catch it:** the stub modelled the *control flow*, not the
*credential resolution*. It proved the fallback branch was taken and said nothing about which token
git actually authenticated with. That is the same defect class the fleet is clearing today — a
check that cannot fail on the thing it exists for — and it was mine.

Two things established afterwards by **local experiment**, not reasoning:

- `git config --unset-all "http.https://github.com/.extraheader"` **does** remove the key (exit 0,
  key gone) — so "the unset silently failed" is not established either.
- `git -c http.<url>.extraheader=…` **appends**, it does not override (`--get-all` returns both
  values) — so the obvious repair is also wrong.

The reason the retry kept AceHack's identity is **not established**. So the mechanism is removed
rather than iterated on.

## What this ships instead

Use the mechanism already **proven in this repo** rather than a new one: drop the `token:` override
from **both** checkouts, so the persisted credential is the default GITHUB_TOKEN.

- `society-heartbeat.yml` and `tick-metrics.yml` check out exactly this way, and
  `heartbeat/society` + `heartbeat/tick-metrics` kept updating right through the outage
  (14:08Z and 14:24Z today, while the agent lanes were frozen at 2026-08-15T22:55Z).
- workflow-level `permissions:` already grants `contents: write`.
- The PAT stays where it belongs: as `GH_TOKEN` on the flush step, which is what `gh` reads for PR
  creation. That is the same split the two working workflows use.

**It also removes a latent second break.** #10850 put the PAT on the **flush** job's checkout too,
and that credential authenticates `flush-via-staging.ts`'s
`git push --force-with-lease origin HEAD:refs/heads/<lane>`. It had not surfaced yet only because
the tick job was producing no events to flush.

## What this does NOT claim

- **081M010H4KE is not fixed** — `gate (required)` still will not start on `heartbeat/*` PRs. It is
  also not made worse: #10709/#10710/#10711 have had no `gate` in their rollups since 2026-08-14
  either way. A degraded lane beats a dead one.
- `required-check-started.ts` in the flush job is **untouched**, so the workflow still fails while
  `gate` never starts. This does not get to look green by being worked around.
- Re-apply #10850's approach once the PAT carries `contents: write`
  (`081M05G8D36087G0R0034D3QPA`, operator-only).
