## Description

## What

Aaron 2026-07-03: *"this is basically our Shiva Garbage Collector"* — his Eureka, seeded in `MixIr` slice 3. This builds the collector the seed promised.

The mix-as-data slices made the mix's rules **data** (`mixDef`, `evalDef`, specs, load descriptors), which is what makes collection possible: **you cannot GC baked code, but you can GC values.** `ShivaGc` is mark-sweep over a content-addressed heap of those reified values.

The Trimurti duality made concrete: the generator (**Brahma**) emits reified tables; **Shiva** (the destroyer) reclaims the ones nothing references. Collection is a **Z-set retraction (−1)**: what `gen` posted (+1), Shiva retracts when it leaves the reachable set — the emit/retract duality applied to the reified self.

Heap = `{ id, value, refs:[id] }` objects (all `DynamicValue`, byte-lockable). `mark` = transitive closure over `refs` (cycle-safe, unlike refcount); `collect` = retain reachable, retract the rest, returning survivors + the collected ids.

## Tests (6, build 0/0)

1. **live-survive + garbage-collected** — collected set = `heap − survivors` (the −1)
2. **cycle-safe** — a reachable cycle survives; an **unreferenced** cycle is collected (refcount would leak it)
3. **idempotent** — `collect ∘ collect = collect` (discipline #6)
4. **deterministic** (DST)
5. **collects a stale reified `mixDef`** — the GC runs on the actual mix-as-data tables (the seed made real): an active reification survives, a stale one is reclaimed
6. the heap is **byte-lockable**

## Honest scope
Mark-sweep over an explicit content-addressed heap; ids stand for content hashes. Weak-reference/ephemeron integration + incremental/generational collection are the follow-ons.
