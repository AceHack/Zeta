## Description

workitem: hardware inventory lives on three surfaces that do not know about each other

Found while checking whether the fleet composition behind the confidential-computing tier
split was recorded anywhere checkable. It is - three times, in three places, none of which
references the others:

  docs/inventory/hardware-2026-05-27-addison-draft.md  Addison's audit: 15 mini-PC /
                                                       workstation line items, 24 GPUs
  inventory/items/                                     the ZetaId register, git-as-database,
                                                       with minting + generation tooling, a
                                                       live Pages site and an independent
                                                       Phase-7 security audit -- 2 ITEMS
  docs/HARDWARE-CAPABILITY-MATRIX.md                   separate again

So the audited register holds 2 of ~40 assets while the data sits in a draft the register
does not know about. The draft's own header says it promotes to canonical after Addison and
the operator reconcile miner counts; that never happened, so the audited data never reached
the audited register.

The item explicitly says DO NOT bulk-import the May draft. Aaron 2026-08-14: Addison is
redoing the inventory to make it more accurate. Importing ~40 ZetaId-keyed files from a
document she is superseding would hand her 40 rows to re-verify against her own fresh audit,
and every correction becomes a diff against data that was never right. The draft already
flags its own unreliability - "the counts on the bitcoin miners are messed up there are more
but it's close", plus one RTX 3090 marked uncertain provenance. Her audit is the source; the
register is the target; this item is about making that path work.

Four concrete asks instead: prove the import path end-to-end on a few items so a bulk import
is known-good rather than a first attempt at scale; decide what a "unit" is before rows exist
(GMKtec NucBox K11 x 2 is two assets or one row with a quantity, and one-file-per-asset
argues for two); retire or cross-link the other two surfaces so it cannot re-fork; and check
amazon-orders-extract.ts, since Aaron notes this started from Amazon history and order data
is better provenance than a hand-typed list.

Why it matters beyond tidiness: "we have an audited asset register" is a claim with 2 rows
behind it, which is the kind of thing diligence finds. And which nodes can EVER offer
hardware-enforced isolation is a per-CPU fact - TDX is Xeon, SEV-SNP is EPYC, and Addison's
list shows Ryzen 9 7940HS / 9955HX / N100 / N150 / J4125, i.e. all consumer. That conclusion
currently rests on a draft, and the register is where it should be checkable.
