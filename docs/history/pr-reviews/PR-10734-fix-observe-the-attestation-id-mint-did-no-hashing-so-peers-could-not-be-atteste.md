## Description

## What this is

Filename hygiene in `docs/observe-events/` — which turned out to be a symptom, not the condition.

A ZetaId scan (#10690) reported three ids as `v15 cat10`, an impossible version/category. The names decode to `{"attestor":"ale`, `{"attestor":"ott`, `{"attestor":"sor` — the event's own JSON, hex-encoded.

**Correction to the framing I was given:** these are not "a different naming scheme wearing the same clothes." The `id` field *inside* each file is the same string. It is one broken producer, and the filename ambiguity is downstream of it.

## The two defects, both silent

`observe/emit-attestation.ts`, line 96–98 before this change:

```ts
// Mint ID from content hash (deterministic — same attestation = same ID = idempotent)
const content = JSON.stringify({ attestor, attested: peer, window: data.latest });
const id = Buffer.from(content).toString("hex").slice(0, 32).padEnd(32, "0");
```

**1. There is no hash.** 32 hex chars is 16 bytes; the first 16 bytes of that JSON are `{"attestor":"xyz`. The id was a function of **the attestor's first three characters** and nothing else — `attested` and `window` never reached it. The write used `flag: "wx"`, so every attestation after the first per attestor hit `EEXIST` and was logged *"already attested (idempotent)"* and discarded. Total loss reported as G-set dedup working. Hence exactly three files, one per attestor prefix, all attesting `society`, unchanged 2026-08-09 → 2026-08-14. `otto`/`otto-cli` and `sora`/`soraya` collide outright.

**2. The mixed naming broke peer attestation entirely.** Recency was `readdirSync().sort().slice(-50)` — lexical filename order as a proxy for time order. The folder holds three schemes, and every `society-*` name sorts after every 32-hex name regardless of when it was written. On the live corpus **the last 50 filenames were 100% `society` events**, so no agent heartbeat was ever a candidate and the only peer anyone could attest was `society` itself. The subsystem could not attest a peer, and had not since it was added.

That second one is the real cost of the ambiguity, and it is what makes this worth fixing rather than documenting.

## Changes

- **`deriveAttestationId`** — a DERIVED ZetaId mint: SHA-256 over the length-prefixed subject in the randomness field, window end in the timestamp field. 80 bits of discrimination, which §7 of the 2026-08-14 ZetaId research doc puts at p < 10⁻¹⁶ at this corpus size. Follows the derived-vs-minted discipline (§6a) and the worked pattern in `forge-host/github/pr-manifest-shards.ts`. Uses `node:crypto` rather than the repo's BLAKE3 module, which needs an npm package.
- **`selectRecentEvents`** — recency decided on the parsed `at`, never on the filename.
- **`hygiene/audit-observe-event-filenames.ts`** — decodes the version field instead of trusting `/^[0-9a-f]{32}$/`, which is exactly what let these through. Scan floor of 500. Wired into `gate.yml`.
- **`docs/observe-events/README.md`** — the schemes, the frozen names, and why.

## The three legacy files are preserved, not renamed

They are real recorded attestation facts (§5 Memory Preservation), nothing in the repo references them by id, and a rename would rewrite recorded history for no gain. They sit in a **closed, dated** allowlist of three named files, and the audit **fails if one goes missing** — so the allowlist cannot quietly become a licence for new ones.
