## Description

## What

Second pass on the TPM/HSM comparison landed in
[#12200](https://github.com/Lucent-Financial-Group/Zeta/pull/12200), answering Aaron's follow-up.

> *"does the TPM resource manager virtualise contexts, or merely multiplex them? if we multiplex them we
> can come up with protection via obfuscation — I don't like this security model but it stops 80% of
> attackers."*

Checked against **`drivers/char/tpm/tpm2-space.c`** and **`include/linux/tpm.h`** in mainline rather
than against summaries, as asked. Documentation and source reading only — no TPM session opened, no key
created or used, no ownership taken, no device written to. **Max's machine was not accessed.**

## The split is real, and the source moves the boundary

```c
struct tpm_space { u32 context_tbl[3]; u8 *context_buf;
                   u32 session_tbl[3]; u8 *session_buf; u32 buf_size; };
```

The isolation unit is **three transient slots and three session slots per open file descriptor** — a
hard compile-time limit, matching the TPM 2.0 spec's guaranteed minimum of three transient objects,
which is the scarcity the resource manager exists to hide.

**But the enumeration boundary is narrower than "transients and sessions."** `tpm2_map_response_body`
special-cases exactly one handle type — `TPM2_HT_TRANSIENT` is mapped and *dropped* when not yours;
everything else hits `default:` and is copied through verbatim. So transients and sessions are isolated
for **execution** (both are context-saved per space), while for **enumeration** only transients are
filtered. Persistent handles, NV indices, PCRs and hierarchies are one global namespace visible to every
container on the node.

**And the starvation finding does transfer — as a performance finding.** Virtualisation is implemented
by swapping against one serialised device: up to six context load/save operations per command. Bounded
per command by the array sizes, **unbounded in rate**. A shared TPM is a shared queue, and this is a
soft degrading DoS with no error code — harder to detect than the HSM's hard `YHR_DEVICE_SESSIONS_FULL`,
not easier.

## The obfuscation idea — the honest read

**On this surface it is closer to 0% than 80%, and the source shows why.** Obfuscation would have to
apply to the non-virtualised half, and the kernel does not filter it:

```
tpm2_getcap handles-persistent     # TPM2_GetCapability(TPM_CAP_HANDLES, TPM_HT_PERSISTENT)
tpm2_getcap handles-nv-index
```

**`TPM2_GetCapability` takes no authorization session** — which is exactly why `tpm2_getcap` works on a
fresh machine before anything is provisioned. `TPM2_NV_ReadPublic` is likewise unauthenticated, so
hiding a handle does not hide its shape, and the namespace is a flat 24-bit space that is walkable
anyway. The attackers it stops are the ones who were not going to look, and looking is one command with
no credential.

**The converse is recorded, because the general instinct is right.** Obfuscation as a defence-in-depth
*layer* is legitimate; the rule is only that it must never be the thing being counted. An obfuscation
layer is `unmetered` (`toy-is-free-metered-must-be-earned.md`), and asserting it as a control is the
vacuity class — a control that cannot fail is not a control. The test, stated so it can be applied:
**name the attacker it stops, and name the observation that would show it did not.** Real controls that
belong there instead: per-container NV indices with distinct auth values, policy sessions binding
indices to container identity, or a vTPM/separate device — the only route that makes the *namespace*
per-tenant rather than making entries in a shared one harder to guess.

## Repair boundaries (new §7a) — this may matter most for Max's node

On the Xbox precedent: **every parser below the update boundary is a permanent liability, and what
matters is how big the replaced unit is.**

The YubiHSM's firmware is not field-upgradable, so the boundary is exactly the USB port. That
**reframes #12178's central finding as good news** — nearly every SDK CVE there was a client-side parser
bug, which is the *right place* for a parser bug to be, and all were fixed by a package upgrade. EUCLEAK
is the exception, below the boundary, replace-only. dTPM firmware *is* updatable but adds a third repair
class: ROCA (CVE-2017-15361) needed a firmware update **and** regeneration of every key made before it.
faulTPM attacks PSP silicon — below any update boundary, no firmware fix.

| | replace-unit |
|---|---|
| YubiHSM 2 | **one USB device, hot-swappable** |
| discrete TPM | a soldered chip / the board |
| AMD fTPM | **the CPU — in practice the machine** |

**And this lands on the threshold roster directly.** n−k prices device replacement assuming replace-units
are *independent and cheap*. An fTPM's replace-unit is the node, so replacing it takes down every
co-resident tick source at once. A k-of-n threshold defends against independent loss, not correlated
loss — several tick sources rooted in one machine's fTPM are **n shares wearing one costume**.

That is a procurement argument for a USB HSM on Max's node that survives even if every isolation
objection in the document were fixed tomorrow, which is what makes it the stronger one.
