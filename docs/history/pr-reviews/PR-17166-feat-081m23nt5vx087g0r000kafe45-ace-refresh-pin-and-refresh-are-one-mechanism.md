## Description

Two maintainer decisions, 2026-09-09: *"we want to keep quantum circuit ... also lets come up with a refresh mechanism and put it in our ace package manager that's what it's for for the pinned dependencies."*

## The sentence the whole change exists for

**A pin nobody can refresh is how a security posture rots. A refresh that does not re-pin is how supply-chain integrity is lost.** A previous agent declined to blind-pin digests for exactly the first reason — freezing a base image can *worsen* posture — and that is the design brief, not an obstacle. One mechanism, one registry, both halves.

MEASURED 2026-09-09, Scorecard `PinnedDependenciesID`: **18 open alerts** — 8 `containerImage`, 3 `nugetCommand`, 3 `downloadThenRun`, 2 `npmCommand`, 2 `pipCommand`. This closes the 8 container ones and says precisely why it does not touch the other 10.

## How it stands against `clone-at-tag-stays-sufficient`

`ace` may be the good path and may never be the only one — **exit, not degree**. So:

- **The pin lives at the POINT OF USE.** `FROM image:tag@sha256:...` in the Dockerfile, which `docker build` reads with **no package manager present**.
- **`tools/setup/manifests/pinned-refs` is a MIRROR, never a source.** Nothing in any build path reads it. Delete this tool, delete all of `ace`, and every pinned dependency still resolves — you lose only the convenience of refreshing them.
- **`--verify` is the falsifier for that claim**, not a paragraph: it refuses whenever a row's digest differs from the digest actually written at its point of use, so a registry that quietly became the source of truth would go red. It runs in `gate` **directly beside `lint-clone-at-tag-is-sufficient.ts`** — same invariant, one layer down.
- `refresh` is deliberately **not** added to that lint's resolver verb list. Refreshing rewrites a committed pin so a human can read the diff; it never resolves anything at build time. Measured after the change: **`lint-clone-at-tag-is-sufficient.ts` exits 0 over 7 surfaces.**

## The four required properties

| property | mechanism |
|---|---|
| pin + refresh are one verb | one registry; `--report` / `--refresh` read the rows `--verify` polices |
| refresh is a reviewable diff | `--refresh` edits the point of use in the working tree and stops — never commits, never pushes |
| **re-verify on refresh** | `remeasure=` is **mandatory** (a row without it is a *parse error*, not a default). A failed re-measure **restores the file** and keeps the old digest |
| staleness is observable | `--report` → fresh / moved / past-horizon / **unknown**, non-zero on a finding |

**UNKNOWN IS NOT FRESH.** It is decided *before* the horizon, because calling an unresolvable row `past-horizon` would imply we know the pin is behind — and we do not.

## What "checked" means per kind — they differ

| kind | pin | checked | resolver |
|---|---|---|---|
| `container` | registry manifest digest | the Dockerfile still **builds** on the new base | **implemented** (Registry API v2) |
| `npm-advisory` | latest version still excluding the patched major | upstream publishes no release admitting the fix | **implemented** (npm registry) |
| `nuget` | `packages.lock.json` contentHash | `dotnet restore --locked-mode` | none → **unknown** |
| `npm-lock` | `package-lock.json` integrity | `npm ci` | none → **unknown** |
| `pip` | PyPI artifact hash | `pip install --require-hashes` | none → **unknown** |
| `downloadThenRun` | — | — | **no kind at all** |

The three unresolvable kinds are **named, not stubbed** — a stub returning `fresh` would be a check that cannot fail. `downloadThenRun` gets no kind because a fetched file already belongs to `from-url` + `repin-rolling.ts` (**081M23ESC5B087G0R002HJ39DG**, in flight); a second mechanism for one subject is the duplication a registry exists to prevent.

**Digests cross-checked, never single-sourced.** All six distinct refs were resolved by `--resolve` against each registry's HTTP API v2 **and** compared against Scorecard's independently computed remediation digests. Byte-identical on all six.

## Decision 1 — `quantum-circuit` stays, and the first premise offered was FALSE

It was proposed that "nothing imports it". **Four files do** — it is a live `role=second-oracle` cross-verify oracle. A `not_used` dismissal on that premise would have been refuted by its own first check.

The premise that is actually true, measured 2026-09-09:

1. GHSA-x2fc-mxcx-w4mf is reached via `deepExtend` **upon a configuration update**, and `quantum-circuit`'s published main (446437 bytes) has **zero** call sites for `math.config` / `math.create` / `deepExtend`.
2. **No file in this tree imports `mathjs`** at all.
3. It is a devDependency of a `private: true` package — it never reaches a consumer.
4. **There is no version fix, ever.** Across all **240** published releases the declared `mathjs` range is one of `^3.8.0` / `^3.20.2` / `^6.0.3` / `^6.6.5`, so the highest major ever admitted is **6**, against a first-patched of **7.5.1**.

Alert #15 dismissed `not_used` on that basis — **and only that one alert.**

**What enforces the premise:** `src/Core.TypeScript/hygiene/lint-mathjs-dismissal-premise.ts` in `gate` checks parts 2/3/4 offline every PR, and reports part 1 as **UNKNOWN — never a pass** when `node_modules` is absent. The upstream expiry is the `npm:quantum-circuit!mathjs@7` row, which `--report` re-resolves: the day a release admits `mathjs` 7.x it goes `moved` and the dismissal is revisited instead of aging into a silence.

## Falsifiers

Each mutant killed exactly its intended falsifier, so the two declared **CONTROLS survive** — a green happy-path test proves nothing on its own. Mutation logs with killer names are in each test header.

**M4 is the original bug, found by the tool on its own first run:** `--verify` called a correctly pinned Dockerfile *unpinned*, because that file's header comment names its base image. A guard that matches its own documentation is reading the wrong text; both new files strip comments and both prove it with a test.

## Honest limits

- The 60-day horizon is a **policy number, not a measurement**.
- `docker build` is a **weak** re-measure: it proves the image still builds, not that it behaves. Named as weak rather than sold as strong.
- **A hand-written receipt passes** — stated in the ledger header, same admission `from-url-rolling-receipts` makes.
- The Windows row can only be refreshed on a Windows docker host; elsewhere the refresh **refuses**. Fail-closed, and rarely refreshed.
- `--report` needs the network, so only the offline `--verify` runs in `gate`.
