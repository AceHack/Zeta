## Description

`metal` was the one rung in this ladder with no measured machine behind it. Two comparators close that; the maintainer's trade is **costed, not taken**.

## 1. `compute-provenance` — the CPU/memory twin of `capacity-provenance`

`findCapacityProvenance` compares the **storage** ladder against `spec.hardware.storage`. There was no CPU equivalent, so the only machine either CPU rung was ever compared against was a **4000m runner** — while the checked-in registrations measure **16** and **22** logical CPUs. ~4x between the substrate the numbers were validated against and the substrate they are for.

The new check compares the **active resource rung** over the **metal cohort** against measured node capacity, on the same three commitments as the storage one:

- **REFUSES** when no registration carries both `hardware.cores` and `hardware.memory` — an absent comparator is an absent check, and it is not acknowledgeable. The runner envelope is explicitly named in the refusal as *not* a substitute.
- **Convicts, never acquits.** The bound is the node's whole measured capacity, nothing held back for the kubelet, control plane, kube-system or OS; and 30 of 46 Applications render BestEffort pods no arithmetic here ever sees. The message says so.
- **A floor per dimension.** `verifiedNodeCompute` returns the smallest-CPU node *and* the smallest-RAM node separately, because nothing forces them to be the same box.

Green today, printed on **every** auditor run rather than only when it fails:

```
* metal  metal cohort (46 apps):  8106m /  19752Mi   dev lane (37 apps):  4231m /  11427Mi
  measured floor: node-ad1efd 16000m (cores=16 x 1 node(s), nproc = LOGICAL CPUs)
                  node-ad1efd 62942Mi (memory="66G" read as DECIMAL — free -h --si)
```

**The cohort is read, not assumed.** `metalAppliedDirs` parses the bootstrap root's own exclude glob. It returns all 46 today; hardcoding 46 would have been correct today and silently wrong the first time somebody narrowed that root. Pricing the metal box against the **dev lane** instead would under-count by gitlab, ollama, vllm and longhorn — four of the largest reservations in the catalogue.

### Two unit traps, both found at the capture command

| field | captured by | means | trap |
|---|---|---|---|
| `hardware.storage` | `lsblk -ndo NAME,SIZE` | **BINARY** — `931.5G` is 931.5 GiB | already handled by `lsblkSizeToGib` |
| `hardware.memory` | `free -h --si` | **DECIMAL** — `66G` is **62942Mi**, not 67584Mi | reading it as binary inflates the bound 4642Mi/node — the **acquitting** direction |
| `hardware.cores` | `$(nproc)` | **LOGICAL CPUs** — `cores: 22` on a 16-core/22-thread Ultra 9 185H | the thread count is the *right* number (it is what the kubelet reports as `capacity.cpu`); the field **name** is what is wrong |

One node, two hardware fields, two unit systems, one line apart in the same shell function. Both readings are documented at their parser. Independent confirmation that decimal is right: 66 GiB is 70.9 GB, more RAM than a 64 GiB machine physically has — a binary reading of `66G` describes a machine that does not exist.

## 2. `rung-coverage` — the green budget gate was about a rung the tree does not carry

Re-measured, exit codes read directly and never through a pipe:

| rung | `--check` | `--budget` |
|---|---|---|
| `dev` | **1** (54 drifts) | **0** ← what CI runs |
| `metal` | **0** ← what the tree carries | **1** |

One rung checked-but-not-budgeted, the other budgeted-but-not-checked, each green on the half it was measured against, and nothing comparing the two. The workflow comment already said so **in prose**. Prose is not a check.

- **`ledger.activeResourceProfile` is now REQUIRED.** This is the key that did not exist. `activeStorageProfile` has always said which disk rung the tree carries; the CPU ladder had no such declaration at all. `readLedger` refuses a ledger without it, for the reason it refuses a missing `activeStorageProfile`.
- **`findResourceProfileDrift`** checks the tree actually carries the rung the ledger names — otherwise the new key is a label nobody checks.
- **`ciBudgetedProfile` derives the budgeted rung from the workflow's own `run:` line.** A constant saying "CI budgets dev" would be a second source of truth that can disagree with the command. Zero matches or two different rungs → **refuse**; two answers is not an answer.
- A disagreement blocks unless carried as `acknowledgedRungBudgetGap` with **all four numbers pinned**. It is carried today: `metal@dev-lane=4231m/11427Mi>>2500m/9216Mi`. Move any of the four and it re-reddens.

## 3. The decision underneath — costed, not taken

`docs/research/2026-08-22-one-tree-two-substrates-the-resource-rung-override-trade.md`. Header says it: **not a recommendation.**

| cohort | at `metal` | at `dev` |
|---|---|---|
| dev lane (37 apps) | **4231m / 11427Mi** — over the 2500m budget by 1731m | 1906m / 6207Mi — fits, 594m spare |
| metal cohort (46 apps) | 8106m / 19752Mi — fits 16000m, 7894m spare | 5016m / 13348Mi — fits, 10984m spare |

Two facts that decide nothing but shape the choice: **`dev` on metal is unused reservation, not a capacity failure** (the box holds either rung), and **no app-local fix closes the CI gap** (hindsight removed *entirely* still leaves 3231m; mimir at 1610m is the larger single reservation).

- **Option A — apply `dev` to the committed tree.** Machinery cost: **none**, the verb exists. It costs metal its floors on 27 of 30 governed rows. The honest counterweight, measured: **21 of the 30 governed rows are `metalSource: chart-default`**, covering six of the nine governed directories — what is given up is the upstream chart author's guess, not our measurement. That does not make the cut free; it makes both sides reservations, and only one of them is ours. Fully reversible.
- **Option B — a per-substrate override point.** Four shapes priced: a second committed rendering (`applications-dev/`, ~150–250 lines plus a regenerate-and-diff check, but the tree exists twice); Helm parameter overrides (needs an ApplicationSet rewrite — the App-of-Apps pattern, `app-of-apps-discovery.ts` and the depth-1 cohort assumption all go); a Kustomize overlay (smaller, but `verifyResourceProfileApplied` reads dotted paths in the Application's own `valuesObject`, so the *check* is what pays); or make the substrates match — the lane needs **5.731 vCPU**, so an 8-vCPU runner absorbs it for money-per-minute forever, and note it makes the *dev lane* fit, not `metal`.

Both options delete the acknowledgement. Neither is picked here.
