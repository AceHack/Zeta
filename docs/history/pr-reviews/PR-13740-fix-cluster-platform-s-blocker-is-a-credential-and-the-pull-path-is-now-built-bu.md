## Description

## The question

Aaron asked of `platform`: *"two ghcr.io images no registry serves — is this a real chart?"*

**It is, and they are.** #13472 established that; this PR acts on it. Re-measured today: anonymous manifest GET returns **401**, both GHCR packages are **`visibility: private`** with **36 versions** each, and until this PR **no pod spec anywhere in `full-ai-cluster` declared `imagePullSecrets`** — the only occurrences of that key were field definitions inside CRD schemas.

So the kubelet pulled anonymously and took the 401 **on every substrate**. This is why the metal platform control plane has never started either.

## What this builds — and what it deliberately does not

**Builds the pull path:**

- both pod specs declare `imagePullSecrets: [ghcr-pull]` (a `LocalObjectReference`, so it resolves in `zeta-platform` and nowhere else)
- `applyDevRegistryPullSecret` mints that Secret at dev/CI bring-up from a token in the environment — wired into both bring-ups **and** the third door, `apply-root-app.ts`
- the health-test job grants `packages: read` and maps `github.token` into `ZETA_GHCR_PULL_TOKEN` (GitHub does not put the token in a step's env on its own; without the mapping the mint silently skips)
- `assertDevRegistryPullSecretPresent` refuses an included run whose cluster lacks the Secret

**Does not lift the deferral.** The gap between "wired" and "measured" is the point — see below.

## Why the refusal exists at all

`ImagePullBackOff` is reported by ArgoCD as **`Progressing`**, never `Degraded`. Un-defer without a working credential and the run burns its full 2400s and then reports the *symptom* rather than the cause. The refusal names the missing Secret in seconds instead.

## The state this refuses to create

An `imagePullSecret` naming a Secret nothing creates does not fail loudly — it fails as another `ImagePullBackOff`, indistinguishable from having no credential at all. Worse still is a Secret built around an **empty or whitespace** token: in-cluster it is indistinguishable from a real credential lacking permission, with an object sitting in the namespace making the credential half *look* done.

So `resolveRegistryToken` treats whitespace-only as **absent**, and the mint **skips rather than mints**. A workflow interpolating a repository secret that was never created yields exactly the empty string, which is why that case is tested by name.

Both guards are **mutation-checked**: dropping the `imagePullSecrets` reference from `portal.yaml`, or accepting whitespace as a token, each turns the suite red.

## Why it is a separate class from `DEV_BOOTSTRAP_SECRETS`

The admin credentials there are **DRAWN** — entropy enters at the mint, so it cannot fail and a skip would be a bug. This one is **SOURCED**, so a bring-up with no token in scope legitimately mints nothing.

Putting it on that roster would also have **falsified that roster's own asserted invariants**: *"two fresh clusters get different passwords"* is false of a sourced token (two clusters correctly get the same one), and `mints.length === DEV_BOOTSTRAP_SECRETS.length` is false the moment a mint may skip.

Relatedly, the bring-up `env` is now a **declared parameter** rather than read from `process.env` inside the mint. It decides whether the mint runs at all, so left ambient the same commit would pass on a laptop and fail in CI (which exports `GITHUB_TOKEN`) — §13 noninterference, and a concrete flake avoided.

## Why the deferral stays

The linkage that governs whether a repo-scoped `GITHUB_TOKEN` may read these packages **is measured and it is favourable**: both report `repository.full_name = Lucent-Financial-Group/Zeta`.

But **no job has yet presented that token to GHCR and been served a layer**, and an API field reporting a grant is not the registry honouring it. Lifting on the strength of the wiring would assert a pull nobody performed — the same round-up #13472 existed to remove.

Two details in how the deferral is written:

- the gate derives from `DEFAULT_ROOT_DEV_CATALOG.excludeGlob`, so the check **arms itself on the same edit that lifts the entry** rather than needing a second one (a check wired to fire only once somebody remembers to enable it is the half-wiring this file exists to catch)
- the `LIFTS WHEN` says **`Healthy`, not `Synced+Healthy`** — the lane accepts `sync=Unknown health=Healthy`, and a `LIFTS WHEN` stricter than its own gate is how a deferral outlives its cause. That has already cost a cycle once.

## The metal finding

CI can mint this because a workflow already holds a token. **Metal cannot.**

A registry pull token is **secret material** under the constitutional rail in `INJECTION-POINTS.md`, so its only sanctioned transit is **operator-typed at the cluster console at install time**. There is no path by which an unattended node obtains it.

> While these packages are private, **unattended metal bring-up of `platform` is not achievable** — not for want of automation, but because the node cannot hold a credential nobody gave it.

That is recorded against the standing goal that hardware comes up with no manual step, rather than left in a values file.

## The decision that is not mine

The exit that **removes** the requirement rather than satisfying it is making the two packages **public**, after which `imagePullSecrets` becomes inert and metal needs no credential at all.

That is a **disclosure decision and it is Aaron's alone**. It is recorded in `INJECTION-POINTS.md` as the alternative, with its trade stated honestly against the operator-typed path — and it is **not advocated here**.
