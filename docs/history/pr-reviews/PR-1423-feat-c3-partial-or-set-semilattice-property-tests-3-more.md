## Summary

Three FsCheck properties for `OrSet`, mirroring the G-Counter / PN-Counter pattern:
- OR-set merge value is commutative
- OR-set merge value is idempotent
- OR-set merge value is associative

Compares on the **observable element-set** (`Set.ofSeq orset.Value`), not on internal entry weights — OrSet.Merge is `ZSet.add`, so weights can vary by merge order but the externally-visible CRDT set must be invariant under semilattice laws.

  <pre>
  P1: `buildOrSet` constructs states by repeatedly calling `OrSet.Add`, which internally uses `Guid.NewGuid()` and does a `ZSet.add` against a singleton each step. This makes the FsCheck properties non-replayable (the same shrinking trace re-runs with different tags) and also turns building a size-N set into O(N^2) work due to repeated linear merges. Consider building an `OrSet` directly from a single `ZSet.ofSeq` over `(elem, deterministicTag)` pairs (e.g., tags derived from the list index) so the generator is deterministic and O(N log N) / O(N) consolidation work instead of repeated merges.
  </pre>
