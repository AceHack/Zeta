## Description

## What

A `build-ai-cluster-iso` run has carried **two** ISOs since the aarch64 job landed. `zflash`
resolved that by taking the first `.iso` in `readdirSync` order — directory-hash order on APFS —
so which architecture the operator flashed was a coin flip nothing in the tool could see. The
cached copy was named without an arch token, so a wrong pick then became the newest file in
`~/Downloads` and won every later auto-discovery. Sticky, and invisible in the filename.

The only symptom is `no bootable device` on the target board — the same message a Secure Boot or
boot-order problem gives — after a full flash-and-walk-to-the-box cycle has been spent.

This was already on file as known-unknown #2 of `docs/runbooks/2026-08-16-first-metal-bringup-preflight.md`,
with the mitigation "pass the ISO path by hand". That is the operator carrying a defect the tool
should carry, on the single most-walked path in the cluster workstream.

## How

Selection moved into `lib.ts` as pure, tested functions:

- `selectIsoForArch` — for a download tree. Collects **every** `.iso`, sorts so the verdict does not
  depend on `readdirSync` order, reads the arch from the **whole path** (the artifact DIRECTORY as
  well as the name, because `configuration.nix` `mkForce`s an `isoName` carrying no arch token, and
  if a future nixpkgs honours that on both arches the directory is the only signal left). It
  **refuses rather than guesses** — only-wrong-arch and ambiguous trees are errors that name the
  failure.
- `selectDownloadedIsoForArch` — for `~/Downloads`. Deliberately **more lenient**, and the asymmetry
  is the point: a CI run is a closed set we understand, but the Downloads folder is an open-ended
  human history (the preflight records two eight-week-old arch-less ISOs in it right now), so
  refusing on ambiguity there would break a path that works today. It refuses only when *every*
  candidate positively names a different arch.
- `stampedCiIsoFileName` — the cached copy now carries `-<arch>`, which is what stops a wrong pull
  from outranking correct older ISOs on mtime forever.

Default is **x86_64**, not the host arch: the cluster nodes are x86_64 (`full-ai-cluster/flake.nix`
gates the NixOS checks to `x86_64-linux` for exactly that reason) and the operator flashes from an
arm64 Mac, so deriving it from the host would pick aarch64 every time. `--iso-arch
x86_64|aarch64|host` overrides.

## Falsifier

Mutate `selectIsoForArch` back to "return the first ISO" and **7 tests go red**. Run before the
lint refactor and again after, so the tests pin behaviour rather than shape. 90 pass in
`lib.test.ts`, 464 across `zflash/`, 345 across `installer/`, `audit-installer-substrate` PASS,
`tsc --noEmit` clean. eslint on the three touched files: 97 errors vs a 99-error baseline on the
same files — net reduction, no new ones.

## Dogfooding, same path

- `execFileSync("cp", ...)` -> `copyFileSync`. `zflash` has a Windows path
  (`flash-usb-windows.ts`) where no `cp` binary exists, and shelling out for a copy the runtime
  already provides is a needless dependency.
- `docs/runbooks/zflash-end-to-end.md` CP-1 instructed a hand-download-and-rename that the tool now
  performs. Corrected in place rather than left as a parallel manual procedure — a doc describing a
  manual process a tool already automates is a dogfooding gap in doc form.
