## Description

bug(shivagc): the byte-identity falsifier compares `run recipe` to itself

`audit-check-arity` R2 went red on `main` after #14831. Adjudicated by reading
the normalizer and then the test, rather than by trusting the rule name --
`record()` substitutes let-bindings before comparing, which is what surfaces
this.

THE DEFECT. `ShivaGcRegen.Tests.fs` §4 builds the heap as
`ShivaGc.object' "derived" (run recipe) []`, so `droppedBytes` traces to
`bytes (run recipe)`; two lines later `regeneratedBytes = bytes (run recipe)`.
Both sides share one producer. The test establishes that `run` is
DETERMINISTIC -- real, non-trivial, DST depends on it -- but not the claim in
its own name, that regeneration reproduces what was dropped. It cannot: what
was dropped was defined as the regeneration.

Its comment is where the slip is visible: "Note what is NOT read here: the
dropped object. These bytes are produced, not copied." True -- and the dropped
object's bytes were also produced by `run recipe`. Not copying is not the same
as not sharing a producer.

Worth more than an ordinary redundancy because it is THE SAME DEFECT the author
agent had just identified in the test it replaced (`ShivaGc.Tests.fs:116`
"measures retention and reads as regeneration evidence"). Catching the pattern
did not confer immunity to it, which is why the mechanical check exists.

Filed as 081M0T9V2EV087G0R0000YYPDK with the fix direction: pin the expected
value as a committed hex-in-JSON golden vector and assert BOTH sides against
that literal, so neither is defined in terms of the other. Explicitly NOT
raising `registry/check-arity-census.json` -- registering it would record a
near-vacuous assertion as legitimate, the vacuity class acquiring a permanent
home.

ALSO IN THIS COMMIT, an unrelated near-vacuity two lines up:
`Assert.Equal(List.length (ids h), List.length all)` is strictly implied by the
list equality above it (equal lists have equal lengths), and its "no
duplication" comment is already discharged there. Deleted rather than
registered.

BLAST RADIUS, verified rather than inferred from a red X:
`lint-bash-retirement-inventory` is NOT in `gate (required)`'s needs list
(`build-and-test`, `lint`, `lint-typescript`, `cross-verify`, `full-verify`),
and the CI Gate ruleset requires only `gate (required)`. It blocks nothing. An
earlier claim in this session that it "blocks every PR in the fleet" was wrong
and is retracted in the work-item. R2 stays red deliberately until the golden
vector lands -- the honest state, since the correct fix is a test redesign and
not a census bump.
