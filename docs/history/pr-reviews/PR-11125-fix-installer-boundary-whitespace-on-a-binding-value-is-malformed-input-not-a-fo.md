## Description

# Summary

`main` is red on `key-refusal-falsifier.test.ts`, and this lands it green with the reasoning
recorded rather than by picking a side.

**The framing "trim or don't trim" has no good answer, because both silently decide something
about key material.** This line has now been set three ways in one day:

| | behaviour | what it costs |
|---|---|---|
| #11016 | `material: input.usbUuid.trim()` | silently **rewrites** KDF input — `<A> ` and `<A>` derived the *same* key, so a blob bound to one opened on the other |
| #11111 | `material: input.usbUuid` | silently **accepts** — key material is honest, but `<A> ` becomes a real, different, unrecoverable binding. Persist with a stray space, restore without it, locked out at restore time with no diagnosis. **My change, my footgun.** |
| **this PR** | `return { error: … }` | **fails closed and says why** |

Rejecting pays neither cost. No key material is rewritten behind the operator's back, and the
typo surfaces immediately — while the input is still in front of them — instead of on a
machine they may no longer have.

# Answering the review directly

**1. Do the check path and the derive path see the same canonical value?**

There is no split, and there never was one to create. `selectCliBindingMaterial` is the
*single* producer; `zeta-creds-persist.ts` and `zeta-creds-restore.ts` are its only consumers;
both hand `binding.material` straight to the KDF. **The AEAD tag is the check** — there is no
second path that could disagree. The presence test (`trim().length > 0`) and the material are
sequential — a gate, then a value — not two canonicalizations of one input.

**2. Was whitespace-normalization "intended and documented"?**

Checked, and no. The comment cited as evidence of original intent
(*"Whitespace is different: the CLI selector canonicalizes…"*) was written by **#11112, which
merged at 21:51:32 — 2 minutes 38 seconds after #11111 at 21:48:54.** Its diff *deletes* the
comment that predicted the defect and replaces it with one asserting the opposite. Its own
message says it "reconciles the end-to-end falsifier with the source-owned binding selector
landed on main" — but the selector it was written against was the pre-#11111 one. It raced the
fix and recorded the defect's behaviour as the contract. That is a review-visible fact, not a
criticism of Vera: two agents editing one contract 158 seconds apart is a coordination
failure, not a judgement failure.

**3. The usability stake — the strongest part of the review, and it is why this PR is not just
a revert.**

Taken seriously and answered on evidence: **no probe can emit a value with boundary
whitespace**, so the footgun requires a hand-typed value in both directions.

- `parseUuidFromDiskutilInfo` (`zflash/lib.ts`) trims diskutil's column padding **and then
  requires** `/^[0-9a-fA-F]{4}-[0-9a-fA-F]{4}$/` — a total regex that cannot match a spaced
  string. Whitespace is not merely stripped there, it is *unrepresentable* downstream.
- `trimOrNull` (`usb-iserial-probe.ts`) strips the sysfs trailing newline at the read.
- The keyfile path is bytes, never a string.

So canonicalization already happens **exactly once per source, where the artefact is born**.
The CLI trim was a second one stacked on the first — which is why removing it broke nothing
real, and why re-adding it would buy nothing real either. But bare acceptance still left the
hand-typed case failing silently and late, which the review was right to flag. An error fixes
that better than a trim does: the operator is told, rather than quietly bound to something
they did not type.

# Notes

**#11112's verdict-column table is kept.** Splitting the table into verdict classes is a real
improvement — it makes each refusal's *reason* legible instead of asserting one blanket
outcome — so only the whitespace row's verdict changed, from `normalized` to `malformed`. The
two verdicts are deliberately not one rule: `refused` means the AEAD tag rejected a foreign
identity, `malformed` means the CLI would not accept the value at all. Both write nothing,
which is what the file asserts.

The full three-step history is in the comment at the table, because this row has now been
wrong in *opposite* directions and the next reader deserves the sequence rather than only the
current answer.

**Owned:** my #11111 comment claimed `<A> ` was "a near-miss identity being silently
accepted." That was overstated — `<A> ` is not a near-miss *identity*, it is the same identity
carrying a formatting artefact, and no attacker who cannot already produce `<A>` gains anything
from it. The trim's defect was that it rewrites key material, not that it opened an oracle. The
review was right to push on that, and the corrected reasoning is what this PR is built on.
