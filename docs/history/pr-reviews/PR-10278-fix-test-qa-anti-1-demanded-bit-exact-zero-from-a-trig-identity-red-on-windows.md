## Description

`main` went red on the **gate** job: 4786/4791 passed on `windows-2025`, with `QA-ANTI-1` the single failure. It passes on macOS, which is why it landed green.

## Diagnosis, measured not inferred

The test builds `a` with `|a| = 1` via `ofPolar 1.0 theta`, so `magSq a` is `cos²θ + sin²θ`, and `blaschkeDerivMagSq` computes `(1 - aMagSq)²`. **That trig identity is not bit-exact in floating point** — it's `1.0 ± 1ulp` depending on the platform's `Math.Cos`/`Math.Sin` and whether the multiply-add is fused. So the numerator is ~`1e-32`, not exactly `0`, and `Assert.Equal(0.0, derivSq)` fails.

**This isn't a Windows quirk to work around.** Measured on macOS:

```
theta samples where cos²+sin² ≠ 1.0 exactly:  2308 / 10001
worst |1 - (cos²+sin²)|:                      2.22e-16
```

**23% fail exactness on this very machine.** The test's particular θ landed in the passing 77% here and the failing 23% on Windows, for identical input. It was fragile by construction; the platform only decided which side it fell on.

## The fix follows the file's own convention

Every **positive** golden vector in this file already asserts with `Assert.InRange(x - 1e-12, x + 1e-12)`. This negative control was the sole outlier demanding exact equality.

It's also **strengthened as a negative control**: asserting only "near zero" would still pass if `blaschkeDerivMagSq` were changed to always return `0`, so it now additionally asserts the result differs from the canonical QA-5 vector — which is what a negative control exists to rule out.

Not my code (`21902c89d`), but `main` was red and the diagnosis reproduced.
