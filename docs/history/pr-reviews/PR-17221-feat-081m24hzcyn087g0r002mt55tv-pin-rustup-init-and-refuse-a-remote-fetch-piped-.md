## Description

## What

`tools/setup/common/install-rust-wasm32.sh:32` piped `https://sh.rustup.rs` straight into `sh` — the **last live `downloadThenRun` on the install path**, on a script consumed three ways (dev laptops, CI runners, devcontainer images; GOVERNANCE.md §24). It carried an open OpenSSF `PinnedDependenciesID` alert.

It now uses the mechanism PR #17200 adopted for Ollama, **extended rather than duplicated**.

| piece | file |
|---|---|
| the pin | `tools/setup/rustup-pin.json` — rustup **1.29.1**, four platforms |
| the mechanism | `src/Core.TypeScript/ace/{pinned-artifact,install-pinned-artifact}.ts` |
| the refresher | `src/Core.TypeScript/ace/refresh-rustup-pin.ts` (`--check` is the drift falsifier) |
| the proof | `.github/workflows/verify-rustup-pin.yml`, on a real `ubuntu-24.04` runner |

## The verification is BEFORE execution, and that ordering is the point

`installPinnedArtifact` fetches → compares SHA-256 → *only then* marks the file executable and runs it. A pipe executes the bytes as its **first** act, so no check it could perform afterwards would be a check at all. Falsified rather than asserted: wrong bytes leave `madeExecutable` and `ran` **empty**.

Two capabilities the Ollama pin never needed, both added as refusals:

- **`artifacts` is a LIST.** One digest cannot describe four platform builds, so inheriting `entry.contentAddress` is offered only to a single-artifact pin; a multi-platform pin sharing one digest is refused.
- **`kind: "run-installer"`** executes the verified bytes. `runArgs` on an `archive` is refused rather than ignored, and `--run-arg` handed to an archive is refused before the fetch.

## Fail-closed, and no rolling exception needed

Fails closed, which is **not** an increase in blast radius: the call site already ran under `set -euo pipefail`, so the old `curl | sh` aborted `install.sh` on a network failure too. What is refused is a *fallback* to the unpinned installer.

No `from-url-rolling-exceptions` row (PR #17183) is required: `static.rust-lang.org/rustup/archive/<version>/…` is version-addressed, so a new rustup release leaves the pin **stale, not broken**. `sh.rustup.rs` is the rolling alias — exactly why it is not what we pin.

**Honest limit, weaker than the Ollama pin's:** rustup has ONE distribution channel. The `.sha256` sidecar is served from the same origin as the binary, so agreeing with it detects a corrupted transfer and would **not** detect a compromised origin; `rust-lang/rustup`'s GitHub releases carry no `rustup-init` assets to cross-check against (measured 2026-09-10: the API has no release for tag `1.29.1` at all). Recorded in the pin's `_doc` and in `refresh-rustup-pin.ts` rather than glossed.

The Rust toolchain version stays declared once, in `.mise.toml`, and reaches the mechanism as `--run-arg=--default-toolchain --run-arg=$RUST_VERSION`.

## Added on the coordinator's ask: the kubeconform attestation 503

`github:yannh/kubeconform@0.7.0` fails `mise install` when GitHub's `trust-metadata-api` returns 503, taking down **both** ARM lanes (gate `build-and-test (windows-11-arm)` and `live kind ArgoCD health (ubuntu-24.04-arm)`, run 34427150482) while their x86 siblings pass. Same defect class as the rustup pipe: a third party's *availability* on the critical path of `install.sh`.

### Verdict on moving it to `from-url`: it does NOT fit — four measured reasons

1. **`from-url` structurally cannot host it.** A row is `<dest> <url> sha256=` — one URL for all hosts, no platform axis, no extraction, no PATH placement. kubeconform ships **eight** platform archives (`.tar.gz` on Unix, `.zip` on Windows), each containing a binary.
2. **The mechanism that could is POSIX-only, and the failing gate lane is Windows.** `install-pinned-artifact.ts` now has the platform axis and archive extraction, but its rim uses `resolveElevatorPathOrThrow("sudo")`, splits `PATH` on `:`, and hardcodes `tar --zstd`. `windows-11-arm` is the **required-gate** lane. A Unix-only migration leaves the blocking failure standing and fragments the tool graph.
3. **It would be the third pin of one tool.** `.mise.full.toml` says `0.7.0`; `gate.yml:1055` independently runs `go install github.com/yannh/kubeconform/cmd/kubeconform@v0.7.0`.
4. **It fixes one exposure of at least four.** The same failing log shows `golangci-lint`, `uv` and `actionlint` making the same attestation call.

### The roster is the finding, and it is bigger than kubeconform

Measured: `github_attestations = true` is a **global default** and `aqua.github_attestations = true` as well, so every `aqua:`-resolved tool is exposed (`k3d`, `kind`, `kubectl`, `helm`, `shellcheck`, `actionlint`, `golangci-lint`, `uv`, `1password-cli`) — and the set **grows with no diff in this repo** the day any upstream starts publishing attestations. (`python.github_attestations` is already `false`, disabled in `mise.sh` after this exact class of incident.)

Two more facts from the log: the `[2/3] checksum` step **already passed** before the attestation call, and **there is no `mise.lock` in the tree with `locked = false`** — so that checksum is verified against one *fetched from upstream at install time*, and **no mise-managed tool has a committed digest at all**.

**The fix is `mise.lock`**, verified by running it: it emits committed per-platform `sha256` + URL in TOML — the same shape and the same property as a `from-url` row — and `windows-arm64` is supported explicitly. Only once that lands does turning the attestation call off stop being a bypass and become a *relocation* of the check. **Nothing was disabled here**, and no retry budget was extended. Filed with the full measurement as **081M24MADR2087G0R001FCD8K6** (P1), because it is a fleet-wide `[settings]` + three-way-parity change, not a drive-by in a pin PR.

### What IS fixed here: the misleading second failure

Six `if: always()` teardown steps in `k8s-argocd-health-test.yml` ran `bun …-down.ts` with no toolchain installed and died `bun: command not found`, exit 127 — so the job showed two reds and the **last** one, the one a reader sees first, was a missing runtime rather than the 503 five steps earlier. A genuine teardown failure — bun present, the down script non-zero — still goes red.
