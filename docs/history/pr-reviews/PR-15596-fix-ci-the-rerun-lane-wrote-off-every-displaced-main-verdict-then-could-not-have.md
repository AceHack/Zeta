## Description

fix(ci): the rerun lane wrote off every displaced `main` verdict, then could not have recovered one anyway

Two defects, and shipping either alone leaves a fix-shaped no-op.

1. `isSuperseded` matched `head_branch` and ignored `head_sha`. On a PR branch that is
   right — a newer run IS a newer commit and replaces the old one. On `main` every commit
   shares one branch name, so the next push run carries a verdict for a DIFFERENT commit
   and replaces nothing. Every displaced `main` run was skipped as
   `superseded — concurrency working as designed`, a reassuring sentence asserting the
   opposite of what happened. Measured effect: 66 second attempts on `pull_request`
   against exactly 1 on `push` over 600 runs.

2. The rerun POST was `rerun-failed-jobs` unconditionally. A displaced run has ZERO jobs,
   so there is nothing "failed" to re-run. Measured against run 32952848390 (a displaced
   `push` run on `main`, `total_count: 0`):

       POST .../rerun-failed-jobs -> 403 "This workflow run cannot be retried"
       POST .../rerun             -> 201, run_attempt 2, 35 jobs created

   That 403 carries the exact sentence `classifyRerunRefusal` recognises as ordinary and
   unactionable. Fixing (1) without (2) would have selected all 22 displaced runs, logged
   22 cheerful `refused-not-retriable` skips, and recovered nothing — a check that runs,
   classifies correctly, and does nothing. This resolves §8.4 of the research doc, which
   listed the question as unverified.

Measured before/after on the 2026-08-14 fixture (100 real runs, 37 cancelled):

  | | before | after |
  |---|---|---|
  | classified `superseded` | 27 (22 of them on `main`) | 5, all on PR branches |
  | selected for rerun | 10 | 32 |
  | selected on `main` | 0 | 22 |
  | selected off `main` | 10 | 10 — byte-identical |

The whole delta is on `main`. The PR lane, where guard 3 does 100% of its useful work, is
unchanged, which is why the carve-out is scoped to the default branch rather than requiring
sha equality everywhere.

Scope and cost. `Human-Review`/what blocks a merge: nothing changes. No workflow, ruleset,
or repository setting is touched — `gate.yml`'s `concurrency:` block belongs to #15566 and
is not edited here. Guard 2 still caps this at one automatic attempt per run id and guard 4
at 180 minutes, so the worst case is one gate run (~94 runner-min) per displaced commit
inside the staleness window. Honest bound on the ongoing benefit: #15566 landed per-SHA
push concurrency at 09:55Z and the 6 push runs since carry zero cancellations, so the
displaced population this recovers should now be ~0. What this buys standing is that if a
`main` run is cancelled for ANY reason — timeout, infra, a revert of #15566 — its verdict
is recovered instead of written off with a sentence that reads like everything is fine.

Falsifiers. Four mutants, each killed:
  - delete the `head_sha` predicate           -> 6 tests fail
  - `chooseRerunEndpoint` always failed-jobs  -> 4 tests fail
  - CLI hardcodes the default branch          -> 1 test fails (this one SURVIVED the first
    round and the test that kills it was added because of that — no sibling was supplied
    anywhere, so guard 3 could not fire and the plumbing was never exercised)
  - CLI hardcodes the job count               -> 2 tests fail

The fixture gains a real `head_sha` per run, back-filled from the same API. Six archived
`action_required` PR runs now answer 404; their SHA is recorded as an ABSENT FIELD rather
than invented, and the policy treats an unknown SHA on the default branch as "cannot
establish supersession" (re-run) rather than as a match.

Registers: the 403/201 endpoint result, the 27->5 / 10->32 fixture deltas, and the 66-vs-1
retry ledger are `metered`. "The displaced population is now ~0" is `consistent with` 6
post-#15566 runs, not established.
