## Description

## The defect

`hygiene/audit-workflow-cli-flags.ts` enrols a tool in the lint when its parser
"demonstrably rejects unknown flags" — detected by regexing for an `unknown arg`
diagnostic. It regexed the **raw** source. Its sibling `extractAcceptedFlags`
strips comments first. **The inconsistency was the bug:** a tool that merely
*discusses* unknown arguments in prose reads as having a closed parser, and the
audit then polices workflow invocations against a parser that does not exist.

PR #10853 caught it the sharpest possible way. That agent removed a guard from
`setup-dual-background-agents.ts` to mutation-prove it, and its suite stayed
fully green — because the comment above the guard, explaining why the phrase
`unknown arg` matters, still contained the phrase. **The explanation of the
guard satisfied the guard-detector.**

The fix is one line of behaviour: `hasClosedFlagSet` now reads
`stripComments(source)` — the same text `extractAcceptedFlags` reads, through
the **same** stripper. A second comment-stripper would be the same divergence
one level down.

## The same inconsistency, other direction — the workflow side

While reading for the pattern in that file I found it repeats, mirrored. The
**tool** side was read with comments stripped; the **workflow** side never was.
So a commented-out invocation was scanned as if it ran. Measured on this repo:

```text
7 of 121 scanned invocations came from `#` comment lines
  scaffold-stage1-create-repos.yml   3   header documents `--repo X --dry-run` examples
  agent-heartbeat.yml                1   names merge-heartbeats-to-main.ts in prose
  context-cost-trend-cadence.yml     1
  manifesto-citation-snapshot-cadence.yml 1
  memory-index-drift.yml             1
```

None produces a violation today, so it is latent in exactly the same way: the day
a documented example drifts from its tool's real flag set, CI fails on a line
that never executes. `stripWorkflowComments` blanks whole-line `#` comments
(comments in both YAML and shell, no ambiguity) **before** continuations are
joined — joining first would weld a live remainder onto a comment.

Effect, isolated: `invocationsScanned` 121 → 114. `toolsChecked`,
`toolsSkippedOpenParser` and `violations` **byte-identical**.

Deliberately whole-line only. A trailing `#` in a `run:` block is a shell
comment, but `#` also lives inside quoted arguments and URLs, and guessing where
a shell comment starts without a shell parser is how a stripper starts eating
live code — which this file already has a scar from.

```text
MUTANT C    stripWorkflowComments becomes the identity      EXIT=1   21 pass 3 fail
              stripWorkflowComments > blanks whole-line # comments and preserves the line count

```

The two tool fixtures are generated from one template and differ **only** by
whether the guard line is present; the comment mentioning `unknown arg` is in
both. Three assertions pin that, so a fixture that silently lost the phrase
cannot green the suite while proving nothing:

```ts
expect(/unknown arg/i.test(GUARD_IN_PROSE_ONLY)).toBe(true);                 // phrase IS there
expect(/unknown arg/i.test(stripComments(GUARD_IN_PROSE_ONLY))).toBe(false); // only in prose
expect(/unknown arg/i.test(stripComments(GUARD_IN_CODE))).toBe(true);        // control
```

The end-to-end pair is the payoff: same workflow passing `--batch 3`, same tool.
Guard in prose → skipped, zero violations. Guard in code → `--batch` caught.

## The reflexive check — and a residual limit I am not hiding

#10853's agent wrote the defect into its own harness, so I ran the detector
against the two files I touched. Both match `unknown arg`/`unknown flag` **after**
stripping, and both legitimately: the test file's fixtures are string literals in
code, and this auditor's own `main` prints

```ts
`${result.toolsSkippedOpenParser.length} skipped (parser tolerates unknown flags)\n`
```

Read that carefully. **The auditor's own report line — which says a tool
*tolerates* unknown flags, the exact opposite of having a closed parser — makes
the auditor read as having a closed flag set.** Comment-stripping cannot fix
that, because this matches a **phrase**, not a **behaviour**.

So the fix is an improvement, not a soundness proof, and the docstring now says
so. What it buys is real: it removes the largest and most tempting source of the
error — prose written to *explain* a guard, which is precisely what a careful
author adds, and precisely what fooled #10853. Neither file is invoked by any
workflow, so nothing is policed on this basis today.

The mitigation that makes the residue tolerable is unchanged and is the header's
own asymmetry: a false enrolment can only cause a violation to be **reported**
against a flag the source never mentions — loud, not silent.

## Findings recorded, not fixed

**1. `stripComments` over-strips: a `/*` inside a STRING literal opens a phantom
block comment.** This is a live defect and I found it while checking why
`zflash/cli.ts` lost its in-code diagnostic. That file contains

```ts
process.stderr.write(`--- mounted USB volumes (/Volumes/*) ---\n`);
```

The `/*` in `/Volumes/*` opens a comment that runs to the next `*/`, eating
**35,339 of 56,526 bytes — 63% of the file**, including the real
`unknown flag(s):` diagnostic at index 41,171 and every flag literal in the
eaten region.

This is the same *class* as the scar already documented in `stripComments`
(a `/*` inside a **line comment**, fixed by stripping line comments first); the
existing fix does not reach a `/*` inside a **string**.

**Blast radius, measured against a string-aware reference scanner: 81 of 2,453
files lose more than 200 bytes.** Worst: `ace/build-graph.test.ts` 20,904 bytes
(63%), `zflash/cli.ts` 17,708 (31%), `hygiene/validate-agencysignature-pr-body.ts`
8,049 (18%), `hygiene/fix-markdown-md032-md026.ts` 5,327 (27%),
`invariant-substrates/tally.ts` 3,287 (33%).

**It falsifies a claim in the code.** `extractAcceptedFlags`'s docstring says the
accepted set "can only ever OVER-accept, never under-accept, which means the
lint's failures are trustworthy." Over-stripping makes it under-accept, so a
false *positive* is reachable: a workflow passing a flag the tool genuinely
accepts, reported as guaranteed-fatal, because the literal was inside the eaten
region.

**Not fixed here, and the reason is not scope.** A correct stripper needs to
track string, template and **regex-literal** context — this very file contains
``/["'`](--[A-Za-z0-9]...)/g``, whose character class holds all three quote
characters, so a naive string-aware scanner is *worse*: it enters a bogus string
mode, stops stripping, and re-opens the exact defect this PR closes. Doing it
right is a small lexer; doing it approximately is a regression wearing a fix's
costume. It deserves its own change and its own reading.

**2. `hygiene/audit-push-without-rebase.ts` reads workflow YAML raw, same class
as fix B, and has live instances.** It counts a commit-back lane via
`PUSH_TO_MAIN.test(src) && COMMITS.test(src)` over the raw file, and two
workflows carry `git push origin HEAD:main` **only inside a `#` comment**
(`budget-snapshot-cadence.yml:58`, `manifesto-citation-snapshot-cadence.yml:35`).
Not fixed: different lint, and its output is a counter rather than a hard
violation, so whether a documented lane should count is a judgement call.

**3. The sweep for this pattern across the hygiene lints came back nearly
empty, which is the useful result.** Of 88 lint files that `readFileSync` and
regex source, only two strip comments at all. `lint/runner-version-freshness.ts`
strips once into `uncommented` and every probe reads it — internally consistent,
no divergence. `audit-workflow-cli-flags.ts` was the sole file where two probes
disagreed about what they read, and it disagreed in both directions.

Worth noting: `runner-version-freshness.ts` already had exactly the whole-line
`#` YAML stripper `extractInvocations` was missing (`/^[\t ]*#/`). The discipline
existed in the repo; this lint just did not apply it.

**4. My own measurement tool was invalidated by my own fix, and I only caught it
because the number was too clean.** The first sweep imported `hasClosedFlagSet`
as its "raw" probe — which, after the fix, strips comments, so `raw` and
`stripped` became the same computation and the sweep reported **zero** files
enrolled by comment alone. It was rerun with the regex written out inline, which
is how the five in the table above were found. Recorded because the failure mode
is exactly this PR's: *a probe that measures the thing it is made of.*
