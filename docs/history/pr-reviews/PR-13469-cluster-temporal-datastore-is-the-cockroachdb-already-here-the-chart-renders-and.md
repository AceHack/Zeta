## Description

`temporal` was in the cluster application set with no datastore wired, and PR #13429 recorded it **UNRENDERABLE**: `temporal@0.59.0` refuses to `helm template` without a store it was never given. Declared, unschedulable, unverified. Its intended datastore existed only as a commented-out block.

Aaron authorised either Cassandra or CockroachDB. The reasoning below is the deliverable as much as the manifest is.

## Why CockroachDB — and the deciding fact is not "Postgres-wire is nice"

**Cassandra cannot be the whole answer at this pin.** Temporal server 1.27.2 (this chart's `appVersion`) ships [`schema/cassandra/`](https://github.com/temporalio/temporal/tree/v1.27.2/schema/cassandra) with exactly one subtree — `temporal/`, the default store. There is no `schema/cassandra/visibility/`, while [`schema/postgresql/v12/`](https://github.com/temporalio/temporal/tree/v1.27.2/schema/postgresql/v12) carries **both** `temporal/` and `visibility/`. Checked at the tag, not read off a blog.

So choosing Cassandra costs:

* a **new 3-node stateful service** — and the chart's bundled subchart is `cassandra` 0.14.3 from the **archived** `helm/incubator` repo, image `cassandra:3.11.5`, with `persistence.enabled: false` by default (emptyDir — a durable-execution engine on a store that loses its data on restart, unless we also add 3 × 10Gi of longhorn);
* **and still** a second store for visibility, SQL or Elasticsearch.

Two new stateful services, not one. That is the opposite of the question actually being asked, which was which choice makes the cluster simpler when every stateful service has to come up unattended on metal.

**CockroachDB is already here**: pinned at 14.0.5, wave 0, 3 Raft members. Reusing it adds no operator, no chart pin, no backup story, and — measured — **no PVC**.

**What the chart supports at 0.59.0**, read from the chart: `_helpers.tpl`'s `temporal.persistence.sql.driver` passes `server.config.persistence.<store>.sql.driver` straight through and `server-job.yaml` branches on `postgres12`; the chart's own `values/values.postgresql.yaml` even carries a CockroachDB note in its TLS comments. Temporal's docs are plain about the register: PostgreSQL, MySQL, Cassandra, SQLite are tested, and *"We do not run tests with vendors like Vitess and CockroachDB."* **Untested, not unsupported** — and the untested half is named below with an exit condition rather than left for metal to discover.

## 3. What happens when CockroachDB is unavailable

Temporal keeps **no local durable state** — no PVC, no StatefulSet. Every workflow, task queue and timer is in CockroachDB.

* Frontend/history/matching/worker stay up, persistence calls fail, the frontend returns `UNAVAILABLE` and the server retries on a backoff. Nothing is lost: in-flight workflows **stall** and resume from the task queues.
* On a **cold** start with the store down, the schema Job's `create-default-store` init container fails and retries to `backoffLimit: 100`. Loud and named.
* Losing **one** of three Raft members is not this case; quorum survives and Temporal does not notice.

**The sync wave already expresses the bring-up half, and it was already declared.** `sync-wave-dependency-graph.yaml` carries `temporal dependsOn: [cockroachdb]`; `ace`'s `resolveGraph` derives the height and `derive-sync-waves.ts` compares it against the annotations — cockroachdb wave 0, temporal wave 10, **no disagreement on this edge** (still 8 disagreements overall, 0 new). What changed is the *citation*: it used to say the wiring was commented out and the edge recorded a declared intent. It now names the two live host lines. **What no sync wave can express** is the runtime dependency — ArgoCD does not restart temporal when CockroachDB goes away later, and should not; the retry loop covers that, not the wave.

## The two things this does NOT do, named with exits

Neither blocks the render. Both block a working deployment, so neither is left for metal.

**BLOCKED — the visibility store's schema does not apply to CockroachDB.** [`schema/postgresql/v12/visibility/versioned/v1.2/advanced_visibility.sql`](https://github.com/temporalio/temporal/blob/v1.27.2/schema/postgresql/v12/visibility/versioned/v1.2/advanced_visibility.sql) opens with `CREATE EXTENSION IF NOT EXISTS btree_gin;` and a plpgsql `CREATE FUNCTION convert_ts(...)` that is then used inside `GENERATED ALWAYS AS (...) STORED` columns. CockroachDB implements neither: `btree_gin` is unimplemented ([cockroachdb/cockroach#51992](https://github.com/cockroachdb/cockroach/issues/51992), open) and computed columns may not reference user-defined functions (CockroachDB known limitations, #122945). **The default store is unaffected** — `schema/postgresql/v12/temporal/schema.sql` has no extension, no UDF, no generated column — which is why this is a split and not "Temporal does not work on CockroachDB".
*How it fails:* the `update-visibility-store` init container of `temporal-schema-1` errors; the Job retries and fails, by name.
**LIFTS WHEN:** a CRDB-compatible visibility schema is handed to `temporal-sql-tool --schema-dir`, **or** visibility is pointed at a real PostgreSQL/Elasticsearch, **or** CockroachDB grows `btree_gin`.

**BLOCKED — no TLS material, and this CockroachDB is TLS-only.** `applications/cockroachdb/Application.yaml` sets `tls.enabled: true` with the selfSigner. The chart *can* express this (`_admintools-env.yaml` emits `SQL_TLS*`; `server-configmap.yaml` passes the whole `tls:` block through), but the CA is a Secret in the `cockroachdb` namespace, this app runs in `temporal`, and no `temporal` SQL user exists. Declaring `sql.tls` today would point a values block at a Secret nothing creates — **a declaration governing a path that does not exist, which is exactly the defect `rendered-storage-claims.ts` was built to catch**. So it is not declared; it is named.
**LIFTS WHEN:** the CRDB CA is distributed into the `temporal` namespace (the cluster already runs `trust-manager` for this) and a `temporal` user + sealed password Secret exist; then `sql.tls` and `existingSecret` go live and the render is re-measured.

## A defect this change found in the checker that merged as #13429

`adjudicate` computes staleness over `baseline.findings` **only** — never over `baseline.unrenderable`. So an acknowledgement for a chart that **started rendering** stayed matching nothing, forever, green. The baseline file's own `$comment` says *"STALE ENTRIES FAIL … refused exactly like a catalogue row matching no claim"*; that sentence was true of one of its two lists.

It bit exactly here: this PR's central act is **retiring** `full-ai-cluster/temporal@0.59.0` from that list, and **re-adding the retired entry as a mutation was not refused**. Nothing would ever have forced anyone to delete it.

Fixed: `staleUnrenderableKeys`, wired into both audit paths, keyed `<appId>@<targetRevision>` so a pin bump invalidates rather than inherits. Three falsifiers added, and all three go red against a neutered build (M6).
