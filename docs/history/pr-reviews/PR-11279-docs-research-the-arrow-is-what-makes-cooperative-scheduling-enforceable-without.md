## Description

docs(research): the arrow is what makes cooperative scheduling enforceable without interrupts

Aaron: "this is exactly it, we should save this somewhere, this was a hard middle ground to
come to in my mind."

It arrived buried in the 80/20 note, which is the wrong shelf -- that note is about Ismael and
incompleteness, and this is a standing design result that holds with or without her. Extracted.

The dilemma: preemptive scheduling costs INTERRUPTS (hidden coordination -- a control transfer
in no call graph, at a point nobody wrote down, which also makes replay non-deterministic
because WHERE you were interrupted is not a function of the program). Cooperative/green-thread
scheduling costs TRUST (one task that never yields starves the rest, and the scheduler has no
recourse because it cannot see inside the task).

The usual conclusion is pick your poison: determinism or liveness. Aaron's formulation is that
the choice is an artefact of an OPAQUE TASK REPRESENTATION and disappears once the task is an
Arrow: because the structure is legible BEFORE it runs, the scheduler can ENFORCE yield points
instead of trusting them. Preemptive safety, cooperative determinism, no interrupt.

The mechanism is not scheduling cleverness -- it is what Arrow/Applicative representation makes
available. "Will this task yield, and where?" becomes answerable statically, by looking, rather
than dynamically, by waiting and being disappointed. A yield point locatable before execution
can be REQUIRED before execution. Trust was only ever needed because the task was a black box.
Restated: an interrupt is the substrate admitting a control transfer it did not declare, and
the Arrow is the declaration.

The limit is real and is the 80/20 boundary. Enforceable in the Applicative/Arrow fragment;
in the Kleisli fragment the next step does not exist to be inspected until the previous one has
run, so there is nothing to enforce against. ArrowApply === Monad is why that is a theorem and
not a preference. Enforceable scheduling is not a separate design win -- it is what being in
the reducible region BUYS, and leaving it is a tariff, not a bug.

Register row kept deliberately: "our scheduler currently enforces this way" is NOT CLAIMED.
The note states what the representation makes POSSIBLE, not what PredictionScheduler.fs does
today. The argument is clean enough to feel like a description of the system and it is not one
yet -- checking means reading the code, not reasoning about it.
