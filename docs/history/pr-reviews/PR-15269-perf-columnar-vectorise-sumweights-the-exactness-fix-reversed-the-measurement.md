## Description

Third and final follow-up to #15246 / #15260. The full BenchmarkDotNet sweep over the **committed** harness — run post-fix on a quiet machine — contradicts a decision I made from pre-fix numbers and wrote into the type's header.

## The reversal

`SumWeights` dispatched to scalar because the vector path measured **0.67x** out of cache. Making overflow exact (#15260) changed the balance: detecting a real wrap costs the **scalar** loop an extra test per element, while the vector loop amortises the same work across lanes and pays it once per 4 096-element chunk.

| n | scalar | vector | ratio |
|---|---|---|---|
| 4 096 | 2 129 ns | 1 561 ns | **1.36x** |
| 65 536 | 34 001 ns | 25 088 ns | **1.36x** |
| 1 048 576 | 563 µs | 396 µs | **1.42x** |

Faster at **every** size, so there is no cache-size threshold to invent. `SumWeights` now dispatches to the vector path. Both paths are exactly equivalent (verified in #15260), so this is purely a speed change.

## Three of my own claims, corrected against the measurement

The header table is replaced wholesale with numbers from the committed harness rather than my scratch prototype.

1. **"Layout alone bought nothing" was too strong.** AoS → SoA on the *sorted* scan is 538 µs → 421 µs (**1.28x**) purely from touching 8 bytes per element instead of 16. On the *shuffled* scan it is worth nothing, because branch misprediction dominates and locality cannot help. Abadi et al. 2013's claim holds where the loop is branch-bound; the bandwidth win is real where it is not. The nuance is now in the header instead of the flat claim.

2. **The ranged weight sum on a sorted key column is 1.00x — no win at all** (582 µs scalar vs 584 µs vector). Previously this was implied to inherit the count kernel's speedup. Stated outright now, including that a `ColumnZSet` key column is exactly the case where it buys nothing.

3. **`ZSet.weightedCount` (351 µs) beats this type's scalar sum (563 µs)**, and that is not a columnar regression — it is doing a *weaker* job, since its overflow behaviour depends on element position while these kernels are exact. Recorded as the honest cost of exactness rather than left looking like a loss.

## Benchmark fixes

- **Removed the `VectorWidth()` benchmark.** Timing a method that returns a constant measures nothing, and BenchmarkDotNet escalated it to ~5×10⁸ ops trying to resolve a sub-nanosecond call — it took longer than every real case combined. Lane count is read from `ColumnKernel.VectorWidth` instead.
- **Added `AosRangeCountShuffled`**, completing the 2×2 of layout × predictability, so the layout effect can be read off in both regimes rather than inferred from the sorted case alone.

The exact-overflow contract and the 1.5x vectorisation gate both hold at **two different lane widths**. That is the property the per-lane version violated.
