## Description

## The near miss

`#10577` fixed the heartbeat's archive backfill so it would finally run. It would then
have made the hole **worse than it found it**.

`archive-pr-reviews.ts` writes to **two** places:

| path | what it is |
|---|---|
| `docs/github/prs/shards/<NNN>/<zetaid>.json` | the **index** entry — a pointer, with an `archive_path` field |
| `docs/history/pr-reviews/PR-<N>-<slug>.md` | the **body** — the rendered review threads, the actual substrate |

The step ran `git add docs/github/prs/`. It staged the pointer and dropped the target.

Nothing else rescued it. The commit guard used `git diff --quiet`, which is **blind to
untracked files**, and a fresh archive body is always untracked. The later codegen step's
`git add -A` is gated on the same blind check, so on a tick where the archive was the only
producer that block never ran at all.

**It is self-sealing.** `selectBatch` skips any PR that already *has* a shard. So each tick
would mark 3 PRs archived, commit no body, and never re-select them via `--all-merged`
again. At 3/tick it would have converted "1,345 merged PRs missing from the mirror" into
"1,345 shards naming a file that is not in the tree" — recoverable only by explicit
per-number re-runs.

## Measured on `origin/main` @ `d55305bb45`, not inferred

- **0 of 6,469** shards were dangling. The damage had **not landed yet** — the step had not
  flushed a tick since `#10577` merged ~70 minutes earlier. This is a catch before the first
  flush, not a post-mortem.
- **0** archive bodies have *ever* been added by a heartbeat commit. All 6,471 on main came
  from `pr-archive-on-merge.yml` (`archive(pr-reviews)`, `ci(pr-archive)`) or a bulk backfill
  PR (`data(pr-reviews)`, `docs(archive)`).
- `git diff --quiet`'s blindness to untracked files reproduced directly in a scratch repo.

All counts parsed with `python3`, never `echo`/`grep` on structured text.

## Fix

- The step stages `docs/history/pr-reviews/` too, and the guard's `git ls-files -o` half
  names it — so the `git add` is reached on exactly the tick that has new bodies.
- `archive-pr-reviews.ts` exports `WRITE_TARGETS` (its full write set). The test derives the
  required pathspecs **from that constant** rather than restating them, so a new output
  directory added to the tool fails the guard until the step stages it too. **The class is
  closed, not the instance.**

### Non-vacuity, mutation-proven

Replanting the historical `git add docs/github/prs/` and its single-pathspec guard fails
**exactly 3** of the new tests — the `WRITE_TARGETS` loop, the body-directory pin, and the
untracked-guard check — and all 3 pass when restored.

## Drain rate: `--limit 3` → `--limit 25`

Measured, not estimated. Cost splits into fixed and marginal:

| | cost |
|---|---|
| **fixed** — `gh pr list --state merged --limit 3000` | **30 GraphQL points**, ~10s |
| **marginal** — per PR archived | **3 GraphQL + ~2 REST + ~4.4s** |

The 3 GraphQL points per PR is a *measurement*. The node-count formula predicts ~150/PR for
the `reviewThreads` query; GitHub actually charged **1 point for each** of the three calls.
Per Aaron's standing constraint, the REST half (`/pulls/N/comments`, `/commits/{sha}`) costs
**zero** GraphQL — only `gh pr view` ×2 and the `reviewThreads` query touch it.

So at `--limit 3` the step spent **39 points to archive 3 PRs — 77% of its budget on the
listing**. At 25 it spends 105 for 25 (71% useful), ~2 min wall.

Bounded at 25 rather than 50 by `timeout-minutes: 10`, which is the ceiling that would
actually hurt — blowing it kills the whole tick. Recent soraya ticks: **136 / 293 / 188s of
600s**. +102s leaves ~34% headroom; +230s would not.

Drain goes from **~9 days to ~27 hours**.

## Why this PR does not bulk-drain the 1,345

Deliberate, argued with the numbers:

- **~4,035 GraphQL points and ~100 minutes** against a **5,000/hour ceiling shared with the
  fleet** (observed fleet draw ~600/hour). Affordable in isolation, no headroom for 1.5h.
- **~2,690 files / ~7.2 MB in one commit.** GitHub's diff UI cannot render it and no
  reviewer can read it. A 2,690-file PR nobody can review is not better than the background
  drain it replaces — it is the same bytes with the review signal deleted.
- **The drain is resumable, and that was proved by observation, not assumed:** a first
  `--limit 5` run archived 8726/9027/9028/9029/9038; a second run with no state carried over
  started at **9048** and continued. The selector reads the shard store, so a tick that dies
  mid-sweep costs at most `--limit` PRs of rework.

Bounded resumable ticks are worth more than one heroic run — and they are now *correct*,
which they were not before this PR.

## `manifest.jsonl` — the conflict class stays retired

Checked, and untouched. `docs/github/prs/manifest.jsonl` is a **derived** index; this step is
its **single serialised writer** (`derive-pr-manifest.ts --write`, soraya-only, under the
`agent-heartbeat` concurrency group). `pr-archive-on-merge.yml` deliberately `git restore`s
it so N concurrent archive PRs never append to one shared file — the pairwise-conflict class
`081KZYP7MNV087G0R002FWR9B2` retired. **Nothing here re-stages it from a second writer**, and
the 10 sample archives produced while measuring were dropped from the branch rather than
committed, precisely so this PR does not carry a 1,345-line manifest rewrite.

## Retracted

Two readings I made and then killed with better measurements, recorded because both looked
like findings:

1. *"17 REST list requests cost 0 core"* — an artifact of the hourly window resetting
   mid-measurement. Response headers are monotonic: REST costs **1 core each**.
2. *"the cron is `*/15`, so the drain is ~4.7 days"* — the cron string says 15 minutes;
   **observed** scheduled runs land ~every 30 minutes. 2 ticks/hour, so the ~9 days in the
   brief was right and my figure was wrong. Every rate in this PR uses the observed cadence.
