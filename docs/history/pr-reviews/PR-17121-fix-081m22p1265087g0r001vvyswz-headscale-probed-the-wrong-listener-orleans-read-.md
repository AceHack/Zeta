## Description

fix(081M22P1265087G0R001VVYSWZ): headscale probed the wrong listener; orleans read redis-auth from a namespace nothing minted it into

Two unrelated causes behind one red lane, both named by the crash-loop log
collector rather than guessed. Run 34323056405.

HEADSCALE -- a 404 is an answer, so the server was healthy and killed anyway.

  "Liveness probe failed: HTTP probe failed with statuscode: 404"
  "Container headscale failed liveness probe, will be restarted"  -> BackOff

The probes hit /health on port `metrics` (9090). Headscale serves /health on
the MAIN listener; the metrics listener serves /metrics and /debug/* and
nothing else. Measured against the pinned tag v0.29.3, both directions, so the
fix is not a guess that moves the 404 somewhere else:

  hscontrol/app.go   registers GET /health on the primary router
  hscontrol/debug.go registers /metrics and /debug/*; no /health

Probe moved to port `http` (8080). Nothing else about headscale changed.

ORLEANS -- a Secret reference is namespace-local, and `optional: true` made the
miss silent.

  RedisConnectionException: NOAUTH Returned - connection has not yet authenticated
    at RedisClusteringOptions.DefaultCreateMultiplexer
    at RedisMembershipTable.InitializeMembershipTable

`redis-auth` was minted only into namespace `redis`, where the Valkey chart
reads it as auth.usersExistingSecret. Correct while Valkey was its only
consumer. Then orleans/statefulset.yaml began projecting the same NAME via
`secretKeyRef: { name: redis-auth, key: password, optional: true }` -- and a
secretKeyRef resolves in the POD's namespace, which is `orleans`. Nothing ever
minted it there, `optional: true` left the env var unset, the silo connected
with no password, and Valkey refused. One absence (Secret not in this
namespace) wearing another absence's meaning (Redis has no auth).

The mechanism for this already existed and this credential was on the wrong
list. DEV_BOOTSTRAP_SECRETS draws per spec because each of those has exactly
one consumer; DEV_SHARED_SECRETS draws ONCE across namespaces, and its own
docstring names this failure: "drawing per namespace would mint different
values and leave services authenticating with a key the store does not know."
redis-auth acquired a second consumer and stayed on the single-consumer list.
Moved, with namespaces ["redis", "orleans"].

AND THE ASSERTION THAT EXISTS TO CATCH THIS REPORTED GREEN FOR IT.

`assertDevBootstrapSecretsPresent` walked only DEV_BOOTSTRAP_SECRETS, so it
checked the Secret in the one namespace it knew about, found it, and passed --
while the namespace that actually needed it had nothing. A check that cannot
see the failure it is named for. It now walks DEV_SHARED_SECRETS x namespaces
too, which is the only form that can observe a per-namespace miss. That walk is
new; its absence is what let this run for days.

Falsifiers: the arity expectations follow the move (5 -> 4 bootstrap), a new
test pins that every namespace reading redis-auth is on the spec, and the
existing behavioural test "included scope REFUSES when the dev redis ACL
credential is absent" is what kills the mutant that deletes the new walk -- a
real refusal, not a source grep. Two mutants, both killed: reverting namespaces
to ["redis"] (the original defect) and dropping the shared-secret walk.

`optional: true` is deliberately LEFT in place. Making it required turns a
missing Secret into CreateContainerConfigError, which ArgoCD reports as
Progressing rather than Degraded, so the lane would burn its full 2400s and
report a symptom. A loud NOAUTH at connect is the better failure, and now it
only fires when the credential is genuinely wrong rather than merely elsewhere.
