## 2. Declared vs scheduled at bring-up — the split holds, the conclusion does not

**500 GiB of the 1599 provisions nothing on a fresh sync.** Verified, with citations:

- **ollama (200 GiB)** — `applications/ollama/Application.yaml` carries `zeta.io/sync-policy: manual` and no `spec.syncPolicy.automated`. Classified `manual` by `manual-sync-policy.ts` (the same predicate the health harness uses), so ArgoCD never applies it.
- **vllm (200 GiB)** — same annotation on `applications/vllm/Application.yaml`. Note its PVC is a **standalone `PersistentVolumeClaim` object** inside `deployment.yaml`, matched by `directory.include: '{namespace,deployment,service}.yaml'` — so `replicas: 0` is *not* what makes it free.
- **arc-runner-set model-cache (100 GiB)** — **applied by nothing.** `bootstrap/root-application.yaml` includes only `'{*/Application.yaml,Application.yaml}'`, and `arc-runner-set/Application.yaml` sources a *remote Helm chart* (`repoURL: ghcr.io/actions/actions-runner-controller-charts`, `chart: gha-runner-scale-set`) rather than that git path, so it cannot apply its own sibling. The file's header claim *"Reconciled by the arc-runner-set Application"* is **false**. Unreachable under either reading of ArgoCD's include matching (base name or relative path). **This is a live bug beyond storage**: `minRunners: 1` mounts `claimName: arc-model-cache`, so the warm runner stays Pending on a PVC that does not exist.

**But the conclusion "so it fits" is false.** Bring-up is **1099 GiB** against a measured **1047 GiB** — still over by 52 GiB on a bound that counts the USB stick and reserves nothing for the OS. The mimir correction is exactly what closed that gap.

**And the split must not become a discount.** Longhorn's StorageClass is `volumeBindingMode: Immediate` — hardcoded at `longhorn-1.7.2/templates/storageclass.yaml:18`, not configurable — so an applied PVC provisions its replica with **zero consuming pods**. What keeps 500 GiB off the disk is the Application never being applied, and that is one `argocd app sync` away. So the gate **convicts on declared** and **reports bring-up**. A gate that convicted on the bring-up subset would pass today and fail the first time someone acted on it.

## 3. The `minimal` profile — 200 GiB, and what each cut costs

Every consequence is written per claim in `storage-profiles.json`. The ones that are not just "smaller":

| claim | large → minimal | what it costs |
|---|---|---|
| **cockroachdb** | 100Gi x3 → **32Gi x1** | **HA DROPPED, said out loud.** One Raft member: no quorum, no replication, no survivable node failure. It is also the only honest setting on one box — `full-ai-cluster/cockroachdb` is *already* in `acknowledgedFalseRedundancy` because the chart's soft `podAntiAffinity` co-schedules all three today. What is removed is nominal redundancy. Use `standard` at nodeCount ≥ 3. |
| **nats** | 20Gi x3 → **4Gi x1** | **HA DROPPED.** No R3 streams, no quorum; a stream with `replicas > 1` refuses to create. Same already-acknowledged single-node situation. Stream retention limits must shrink or publishes are rejected. |
| **redis replica** | 10Gi x2 → **4Gi x1** | **HA DROPPED, smallest of the three** — replication is async so there is no quorum to lose; what goes is read fan-out and one warm standby. |
| **prometheus** | 100Gi → **16Gi** | **RETENTION CUT, and it is not automatic.** The Application sets `retention: 15d`; 16Gi will not hold it and Prometheus fills the disk and wedges its WAL. Selecting `minimal` **also requires** cutting `prometheus.prometheusSpec.retention` to ~3d. That field is deliberately *not* rewritten by `--apply` (it is not a capacity quantity), so the catalogue calls it out and the auditor prints it. |
| **mimir** ingester/SG/compactor | 50Gi → **8Gi** each | Head-block headroom, index-header cache, compaction scratch. History lives in MinIO and is untouched; the costs are write-backpressure on a backlog, slower long-range queries, and stalled compaction. |
| **weaviate** | 100Gi → **12Gi** | Vector index ~1/8. Weaviate does not evict: full means **ingest fails**. |
| **hindsight postgres** | 20Gi → **8Gi** | Caps retained agent memory; writes fail when full. **First cut to give back** if a minimal box has room. |
| **agent-memory** | 10Gi → **4Gi** | Manifesto §5 surface — this is agent memory, so filling it is a memory-loss risk, not a perf one. |
| **arc model-cache** | 100Gi → **8Gi** | Below the ~16GB the cache exists to avoid re-pulling per tick, so on `minimal` the cache does not do its job. Works as designed at `standard` (32Gi). |
| **platform portal** | 5Gi → **4Gi** | Riskiest small cut: single writer of the Room log, and the manifest says the volume *is* the source of truth. Pod count stays 1 in every rung. |
| ollama / vllm | 200Gi → **10Gi** each | One small quantised model, not a library. Deferred phase anyway. |

## 4. The mechanism — a catalogue plus a checker, no new templating layer

The repo deploys with ArgoCD Applications carrying **inline `valuesObject`**; there is no `valueFiles`, no kustomize, no overlay anywhere in the tree (checked). So an overlay would have been a new layer, and an ApplicationSet rewrite of 45 Applications a much larger one.

The smallest thing that works with *this* repo:

- **`full-ai-cluster/k8s/storage-profiles.json`** — the ladder as data. One row per claim: manifest coordinate, size and pod count per rung, `podsSource` (`manifest` / `chart-default` / `singleton`) with **required evidence** for the last two, `scheduledAtBringUp` with its reason, and the consequence prose.
- **`storage-profiles.ts --profile <rung> --apply`** — writes the sizes and pod counts through the YAML **document** API, so every comment survives (tested; the files carry their reasons in comments).
- **`activeStorageProfile`** in `single-node-budget.json` — the per-deployment choice, beside `nodeCount`. `readLedger` **refuses** a ledger without it; a default rung would let the check agree with a profile nobody selected.

`large` is byte-for-byte today's manifests, so **this PR changes no manifest** and a test pins that.

## 6. What is NOT faked

**(c) cannot be done safely without dynamic resizing, and this PR says so instead of pretending.** Kubernetes can *grow* a PVC (with `allowVolumeExpansion` and a filesystem grow) and **cannot shrink one at all** — the only way down is destroy-and-restore. "Size for the big box and shrink later" is a one-way door: a volume provisioned at 200Gi can never move onto a 300 GiB node. So (c) is served by a **ladder chosen once at bring-up**, stated in the module header.

**The 200-300 GiB band, honestly.** Longhorn keeps `storageMinimalAvailablePercentage` = 25 by chart default (our `longhorn/Application.yaml` leaves it unset), so schedulable ≈ 0.75 x (disk − OS root):

```
  minimal    200 GiB declared  ->  ~267 GiB Longhorn disk  ->  a ~300 GiB box
```

`minimal` fits a **300 GiB** box. It does **not** fit a 200 GiB *disk*, which has only ~127 GiB schedulable. That limit is written into the catalogue rather than glossed, and nobody has to trust it — the auditor does the sum against measured hardware per node.
