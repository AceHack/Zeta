### Job 2 — the direction

`docs/research/2026-09-09-learning-geometry-from-pictures-is-a-second-track-and-efficiency-is-its-entry-fee.md`

Written to the **relaxed** constraint. Aaron mid-task: *"this is not load bearing but
preferred, a 2nd track would be okay if we can see the efficiency gains."* So the document
does not argue fitting-vs-deriving; it prices the second track.

**The connections, tested rather than asserted:**

- **The Bayesian fit is real but narrower than the framing.** "Nonlinear inverse problem" is a
  count, not an identification — it licenses Levenberg–Marquardt, bundle adjustment, VI, MCMC
  and gradient descent equally. The UT is distinguished only where a **Gaussian/EP-family
  belief over geometry parameters** needs the moments of a nonlinear function of it. Under a
  gradient-descent re-rendering loss — what 3DGS actually does — the UT plays no role at all.
  Also corrected: `FactorGraph.runToFixpoint` says in its own docstring that DBSP wiring is
  *"the next integration (slice 4b)"*. "Our EP already runs on DBSP" would be citing an intent.
- **DBSP for LOD needs one condition, and there is a counterexample.** `O(Δ)` is bought only if
  refinement is **local**. Progressive Dynamics is not local across levels *by design* — its
  coarse proxy energies restrict fine-level gradients — and that coupling is **why** the levels
  agree. A single "LOD is a Δ so use DBSP" claim would be wrong on the simulation half. An
  unrun falsifier is stated (Z-set keyed by `(face-id, level)`; measure entries touched per
  LOD step) and it can return a negative.
- **Progressive Dynamics is the strongest match in the link set, and its transferable idea is
  ours.** Strip the overstatement and the mechanism is that **the coarse level is derived from
  the fine one** — derived-not-authored applied to LOD, published, by an outside group, for a
  purely practical reason.

**The entry fee**, reusing the roadmap's existing oracle rule rather than inventing a parallel
evaluation. A learned track earns its place when it reports all four of: payload in bytes
against **27,621**; ns/sample against the measured **1.81 / 3.03 / 45.5** table; the fraction
of pixels moved against the exact build (calibrated: SBVH **0%**, subdivision **2.9%** for
7.4x, one-ulp **2.40%**); and what it can represent that the derived track cannot.

**And the uncomfortable part is said rather than reframed:** on three of those four axes the
derived track is expected to win, and the second track's real case is **coverage, not
efficiency**. If it is adopted citing efficiency, the stated condition and the actual
justification will have come apart. Two honest resolutions are offered; the one the document
argues against is adopting it for coverage while citing efficiency.

**The single most useful finding:** Aaron's sentence contains **two projects**, and only one
gives up the preference — *LOD-by-restriction* (cheap levels derived downward from exact
geometry; keeps a root index by construction) versus *reconstruction from photographs* (the
genuine second track, and the one that owes the four numbers).
