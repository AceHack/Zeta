## Description

## What this closes

**`~/.config/zeta/secrets-env.sh` put an 852-byte 1Password service-account token
into the environment of every interactive shell on this machine**, and every
process descended from one. `op-token-setup.sh:83` wrote the
fetch-and-export; `shellenv.sh:111` wrote the line that sourced it from the user
profile.

It outranks the rest of the custody stack because **an environment variable
crosses `exec` regardless of the child's code identity.** A code signature, a
keychain ACL, an IMA appraisal and a TPM seal each bind a secret to a *caller*;
an inherited variable has already escaped the question of who the caller is. So
it is the one exposure no signing work can reach — and the cheapest to fix,
because the fix is deletion rather than compilation. §13 noninterference
(Goguen & Meseguer 1982) stated for credentials.

**Blast radius, measured before removing it:**

| | |
|---|---|
| affected | every interactive shell + every agent session descended from one |
| **not** affected | `launchd`-started cells — their plists set explicit `EnvironmentVariables` with no `OP_*` key |
| observe | nothing; that is what let it survive |
| **in-repo consumers of `OP_SERVICE_ACCOUNT_TOKEN`** | **zero** — `rg` finds the name only in the two files that create the hoist and the note documenting it. The only consumer is the `op` CLI reading its own env, ad hoc |
| action | re-run `op-token-setup.sh`, open a new shell |
| SLA | repo side: this PR. Operator side: one command, below |

## The replacement — point of use, never exported

`src/Core.TypeScript/secrets/credential.ts`

- `withCredential(service, fn)` — fetch, hand to one callback, drop. Never
  touches `process.env`.
- `spawnWithCredential(service, envVar, argv)` — **the one site where a
  credential legitimately reaches an environment, named rather than hidden.**
  `op` takes its token from `OP_SERVICE_ACCOUNT_TOKEN` in its own environment;
  that is `op`'s interface, we do not control it, and there is no stdin or fd
  form. So a credential must enter *some* environment for `op` to run at all.

  |  | hoist | `spawnWithCredential` |
  |---|---|---|
  | who exports | the parent shell | nobody — parent `process.env` untouched |
  | who inherits | every descendant, for the session | one child, one `exec` |
  | lifetime | until the shell exits | until the child exits |
  | legibility | ambient | `grep` finds every crossing |

- `buildChildEnv` is split out as a **pure function** so "the parent is not
  mutated" is testable in CI with no credential present.

## Two corrections to the survey that filed this (#10698)

**1. Exit 44 is `errSecItemNotFound`, not `errSecInteractionNotAllowed`.**
`security(1)` truncates the OSStatus to its low byte:

```
errSecItemNotFound           -25300  -> exit byte 44
errSecInteractionNotAllowed  -25308  -> exit byte 36
errSecAuthFailed             -25293  -> exit byte 51
```

Reproduced — a service name that simply does not exist also exits 44. The
survey's §3.1b probe was not *denied*; its item was **not found**, consistent
with living in a keychain that was not on the search list. The conclusion was
right; the evidence was not. That arithmetic is now a test.

**2. The correct evidence, and it is stronger.** Same `bun` process, same item,
two callers:

```
security(1) subprocess          zeta-op-service-account -> OK, len=852
in-process SecItemCopyMatching  zeta-op-service-account -> -25293 errSecAuthFailed
in-process SecItemCopyMatching  <absent service name>   -> -25300 errSecItemNotFound
```

Identical for `zeta-op-aaron`, `zeta-op-ca`, `zeta-manus-api-key`. The
absent-name control is what makes the middle line an **authorization** result
rather than a broken query: the identical query shape reaches the item and is
refused.

**No dialog was raised at any point.**
`SecKeychainSetUserInteractionAllowed(false)` runs before the first lookup, so an
ACL miss returns an OSStatus instead of a GUI prompt. A denial is a result to
record, not an obstacle to route around.

## Why five are deferred, and it is not timidity

**Finding 2 above inverts the port order.** Every existing `zeta-*` item was
stored by `security add-generic-password` with **no `-T`**, so its ACL names only
`/usr/bin/security`. Porting the readers first converts working reads into
`errSecAuthFailed`. The ACL-authoring side must move first — and that is a
biometric-gated **operator** re-store, not an agent action
(`081M01028VF087G0R001W0VD0B`).

And there is nothing worth naming in a `-T` yet:
`security find-identity -v -p codesigning` returns **`0 valid identities found`**
on this machine, so an ACL could only name `bun`'s mise-managed path — volatile
across upgrades and shared with every bun program on the box. That is a pinned
path pretending to be custody.

So: `manus-smoke-test.ts` ported first because it is a smoke test — if the
in-process path regresses a human sees it immediately and nothing in production
breaks. The helper reports which path served every read (`via: "in-process" |
"deputy"`) so the fallback is loud and cannot quietly become permanent.

**Stated plainly: until the re-store ceremony, code-bound key access on macOS
buys nothing.** The mechanism is present and the call path defeats it.

## Operator step — biometric-gated, the agent did not run it

```bash
bash tools/setup/op-token-setup.sh            # secure dialog; re-stores the token, deletes the hoist file
```

## Constraints held

- **No key material read, printed or logged.** Every measurement is a length or
  an OSStatus. The 852 figure is the one already in the record.
- **No interactive dialog.** `SecKeychainSetUserInteractionAllowed(false)` before
  the first lookup makes a prompt structurally impossible in this path.
- **Nothing mutated on the maintainer's machine** — no writes to
  `~/.config/zeta/`, no keychain changes, no `launchctl`. Sandbox `HOME` was used
  for both differential runs.
- **No signing key** generated, proposed, or held.
- **code identity ≠ custody ≠ attestation.** In-process Security.framework calls
  let the *caller's* identity reach the keychain — a precondition for custody,
  not custody. Nothing here is attestation; that needs a vendor root and a remote
  verifier, neither of which exists on this machine.
