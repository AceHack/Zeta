## Description

`lint-k3s-join-intent-preflight.test.ts` has failed twice on the SAME assertion --
`nixos-rebuild switch --impure` -- once in CI on 2026-09-10 and once on `main` itself on
2026-09-08 (PR-17008 review record). Both times the failure text pointed at the SCRIPT's
output. PR #17008's fix closed the spawn env, and the failure came back.

The reason it came back is that the failure was never about the script.

`run()` called `spawnSync` and then concatenated `r.stdout` and `r.stderr` WITHOUT EVER
LOOKING AT `r.error`. `spawnSync` reports ENOBUFS (maxBuffer exceeded, output TRUNCATED),
ENOENT, and signal termination through `r.error`, and it still returns whatever partial
output it managed to capture. So every one of those became a downstream assertion failure
saying "the remediation line is missing" -- naming a defect in the SCRIPT for a defect in
the HARNESS. A diagnosis cannot be reached from a message that describes the wrong subject,
which is why two people looked at this and neither found it.

WHAT THIS DOES NOT DO, stated plainly: it does not fix the flake. My first hypothesis was
truncation, and I MEASURED IT AND IT IS REFUSED -- the refusal path prints 1,999 bytes
against a 65,536 buffer, 32x headroom. So maxBuffer is not the ordinary cause and raising it
would fix nothing. What was missing was the CHECK, not the room. The next occurrence will
name its own cause instead of blaming the script, and that is the whole claim.

Also handled: `null` stdout/stderr template into the literal string "null", which then fails
a `toMatch` for the same misleading reason. Absent output is now absent, not "null".

FALSIFIER, and it caught a defect in the fix itself. Forcing the bound below the measured
1,999 bytes makes the guard fire and name truncation. On the first run it reported

  output exceeded maxBuffer (65536 bytes)

while the limit that actually fired was 512 -- because the message hardcoded the literal
instead of reading the bound. A DIAGNOSTIC LYING ABOUT ITS OWN CAUSE, inside the fix for a
diagnostic that lied about its cause. Caught by the falsifier, not by review. There is now
one `SPAWN_MAX_BUFFER` constant used by both the spawn and the message, so the two cannot
disagree; re-running the same experiment now reports `(512 bytes)`.
