## Description

## What this is

Aaron asked for our key rotation to be genuinely tested. The rotation path was already
well tested for what it **does**; this adds the other half — does it **refuse** when it
should, and does the safety property it advertises survive being applied twice?

**No live material was touched.** Nothing here rotates, revokes, deletes or re-issues any
real key, cert, token or credential. Every test runs entirely inside `mktemp` dirs with a
throwaway CA, fake biometric doors, and a fake `git add`. No secret value is read, printed
or asserted on — every key is compared by SHA256 fingerprint only, and `RR-9` checks by
inspecting the import block that no real door (`realBiometric`, `macTouchIdAuth`,
`realSudoGateEffects`, `analyzeSudoAuthChain`) is even reachable from this file.

## The rotation path, as it actually is

Three layers, all already in tree, all separately mature:

| layer | file | what rotates |
|---|---|---|
| planning | `src/Core.TypeScript/federated-identity/rotation.ts` | the four-band SVID renewal planner |
| the gate | `src/Core.TypeScript/federated-identity/ceremony-gate.ts` | which ops are unattended vs biometric-ceremony |
| on-disk | `tools/setup/persona-keys/rotate.ts` | machine key · device cert · **CA key**, overlap-window dual-key |
| revocation | `tools/setup/persona-keys/key-epoch-ledger.ts`, `federated-identity/revocation.ts` | G-set, old quorum signs the new key, `foldChain` reports `forked` and never a winner |
| math | `tools/setup/persona-keys/frost-delta-rotation.ts` | `A' = A + [delta]B` — the revoked share is asked for nothing |

The revocation half is a **G-set**, not a Z-set: it is grow-only by design, so a
"retraction" here is *adding* a signed transition, never removing an element. `KL-5`/`KL-6`
already pin merge idempotence/commutativity/associativity and order-independence of the
fold, and `admit` is a pure function of the element precisely so merge stays commutative.
I found nothing to add there — it is the best-tested part of this surface.

The gap was in the **on-disk overlap-window rotate**, and it is not a small one.

## Three defects

### P0 — the CA overlap window collapses on the second rotation

`rotateCaKey` writes the trust set as literally `[currentActive, new]` and never unions
with the self-CA lines already in `trusted-user-ca-keys.pub`.

- rotation #1 → `[CA1, CA2]` — the overlap, correct
- rotation #2 → `[CA2, CA3]` — **CA1 silently evicted**, while device certs it signed are
  still well inside their `-V` window

A cert verifies iff its signing CA is in `TrustedUserCAKeys`, so every machine that has not
re-signed since rotation #1 stops verifying. The module's own stated reason it is safe to
run — *"because >=2 keys are valid across the swap, NOTHING the rotated key protects
breaks"* — is false from the second use onward. Its comment says the old line "is removed
only AFTER the window (a later teardown / a follow-up `rotate --finalize`)"; this is that
removal firing immediately as a side effect of an unrelated rotation.

Reachable from the shipped CLI with no typo and no unusual flags: run
`rotate-cli.ts --ports ca-key --confirm` twice. `rotate.test.ts` rotates **once**, so the
property is pinned exactly where it holds.

### P1 — the operator readout asserts the guarantee unconditionally

`formatRotate` prints `∅-blast-radius: … nothing protected breaks.` on every approved run,
byte-identically, including the run that falsifies it. An assertion that cannot be false is
not an assertion — and this one is in the surface a human reads before deciding the
rotation went fine.

### P1 — `rotate` overwrites the previously retired private key

`retiredCaKeyPath` / `retiredMachineKeyPath` are fixed single slots and `movePrivate`
renames onto them, so rotation #2 destroys rotation #1's retired private key: irreversible,
unattended, no ceremony. `ceremony-gate.ts` classifies `export-or-destroy-key` as
`biometric-ceremony` because irreversibility is a gated class here, and MANIFESTO §5 says
an identity transition must never silently destroy memory. This destruction rides in
unannounced on an operation classified `rotate-leaf-signing-key` / `rotate-node-root-key`.

### P1 — the port dispatch has an open default

`planPort` and `rotatePort` are both if-chains whose fallthrough is `device-cert`. So
`rotate(fx, { ports: ["ca_key"] })` — a hyphen/underscore typo, or any future union member —
is **not refused**: it rotates the device cert, reports `action: "rotated"`, stages a repo
write, and leaves the CA the caller asked for Active. The single biometric prompt names the
port **requested** (`ca_key`), not the one **performed** — under the standing "the biometric
IS the authorization" position, that is an approval for an act that did not happen.

Calibrating honestly: this is **not** reachable from either shipped CLI — `rotate-cli.ts`
and `rotate-cluster-cli.ts` each filter against `ROTATE_PORTS` and exit 2. It is latent, for
programmatic callers and for the next member added to the union, which is **not a type
error**. `ceremony-gate.ts` earns exactly this property by construction with a `switch` that
has no `default`; its sibling module does not.

## What remains untestable without live material

Stated loudly in three places — the test file header, `RR-9`'s stdout on every run, and here —
because a limitation only in a comment is a limitation nobody reads:

1. **A real biometric.** Every door here is a fake; what is proven is that the *caller*
   honours the door's verdict, never that a finger touched a sensor. `biometric.ts`
   `claimsBiometric()` already states the deeper limit: on a stock macOS sudo stack a
   fingerprint, a smart-card PIN and a password are indistinguishable, so even a **live** run
   reports `factor: unattributed`, not `biometric`.
   **Manual procedure:** run the rotate CLI with `--confirm` on a host whose `/etc/pam.d/sudo`
   has `pam_tid.so` as the *only* satisfier, and confirm the readout says
   `factor established: biometric`. Nothing automated substitutes for that.
2. **A real HSM / PIV token.** `open-authenticated-hsm-session` and
   `provision-or-reconfigure-hardware-token` are `biometric-ceremony` in `ceremony-gate.ts`
   and need the physical device.
3. **A real sshd handshake.** Cert acceptance is asserted by the rule sshd applies — signing-CA
   fingerprint present in `TrustedUserCAKeys` — which is the same oracle `rotate.ts`'s own
   header uses. It is not a live `ssh` connection.
4. **The live estate.** Rotating the real CA is a ceremony, not an agent action. `rotate-cli.ts`
   defaults to a dry run and the operator procedure is `ONBOARDING-RUNBOOK.md`.

## Cost of the fixes, named

The P0 fix is not just "union the sets". Retaining every prior CA forever turns each retired
CA into a permanent trust root — the opposite defect, and a worse one. The fix needs a
**closing** bound too: a CA line may leave only once no unexpired cert names it as signer, or
by an explicit `--finalize`. That is real work, and it is why the entry says both halves are
required rather than pretending the one-line version is the fix.
