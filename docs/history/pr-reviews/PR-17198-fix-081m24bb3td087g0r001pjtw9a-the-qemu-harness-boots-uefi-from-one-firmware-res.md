## Description

## What was wrong

Scenarios 3 and 4 booted **legacy BIOS**. The installer refused — correctly — and the harness waited out a 30-minute timeout for a marker that could never arrive:

```
ERROR: not booted in UEFI mode (/sys/firmware/efi absent). This ISO is hybrid, so it will
boot in legacy/CSM and then fail at bootloader install AFTER the disk has been wiped.
```

Measured on dispatch run **34410308790**, via the serial tail added by #17130.

## The cause was a MISSING arg, not a wrong one — which is why nothing caught it

Two QEMU launchers, two answers:

| launcher | firmware | used by |
| --- | --- | --- |
| `ci/qemu-full-install-test.ts` | resolves OVMF, passes `-drive if=pflash` | scenario 2 — **passed** |
| `qemu-state.ts` `buildQemuSystemBootArgs` | `-machine q35`, **no pflash at all** → QEMU's built-in SeaBIOS | scenarios 3, 4, and every other non-`boot-cluster-up` scenario |

## One resolver, two importers

`src/Core.TypeScript/ci/ovmf-firmware.ts` now holds the candidate roster, resolution, the writable-VARS copy, and the pflash arg pair. Copying the resolver into `qemu-state.ts` would have fixed this instance and **rebuilt the exact condition that produced it** — two implementations free to drift apart silently.

## Firmware is a required, explicit input

`uefiFirmware` has no default, and the legacy variant is spelled `legacy-bios-no-uefi` with a **mandatory `reason`**. The defect was that legacy BIOS was reachable by *saying nothing*; it is now reachable only in writing. Making it required rather than optional is the whole argument — the type checker then found all **nine** call sites that had never stated their firmware.

## Per-VM writable NVRAM — the real design decision

OVMF needs a **writable** NVRAM image; the distro ships a read-only template. `multi-vm.ts` boots more than one guest, so one shared `OVMF_VARS.fd` would put two firmwares on one file and let boot entries written by one guest appear in another — an undeclared cross-VM channel. So `MultiVMRuntimeInput` carries `existingUefiFirmware` **and** `joiningUefiFirmware`, mirroring `existingDiskPath` / `joiningDiskPath`, which makes separateness structural rather than a convention a caller has to remember.

## Resolution at execute time, not plan time

My first cut threw from the planner. That broke `run.ts --dry-run` and the fail-closed planning tests on any host without OVMF — it would have **reddened a lane that runs on every PR (`zflash-harness-lint`) in order to fix one that runs on dispatch**. Corrected: `ovmfForPlanning` names the canonical paths and copies nothing; `requireOvmfForGuest` throws and is called only on the path that actually spawns QEMU.

Verified: `--dry-run` → rc=0; retention without `EXECUTE=1` → rc=1, still `"fails closed"`.

## Fail-fast on the terminal marker

The refusal string joins `RETENTION_ABSENT_TERMINAL_MARKERS`, reusing the existing terminal-marker machinery rather than adding a parallel path. ~**60 runner-minutes per dispatch** were being spent serving out timeouts on a determined failure.

**This narrows nothing.** A run that trips it still exits non-zero — it just says so in seconds instead of thirty minutes.

## Falsifiers

13 new tests asserting arg **presence and order** (a missing arg is invisible to any assertion about the args that *are* present). Mutation-tested:

| --- | --- |

What is verified is the firmware the harness now hands QEMU, the fail-fast, and that no PR-time lane regressed.
