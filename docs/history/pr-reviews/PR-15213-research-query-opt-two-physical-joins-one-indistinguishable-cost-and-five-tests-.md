## The premise correction that motivates the work

We have **neither** code anchors nor human anchors. `references/prior-art/` is **8 KB, two files**; the 103 mirrors named in `reference-sources.json` — postgres, mysql, foundationdb, voltdb, duckdb, clickhouse, arrow — are catalogued and **not materialized** on this machine. And `docs/PRIOR-ART-LIST.md` carried no cost-based-optimisation lineage at all. The human half is the half that survives an empty `references/` directory, so it is the half this PR supplies.

## Three findings, verified directly at `6cec0e272`

**1. Zeta has two physical join algorithms and a cost model provably incapable of choosing between them.** `ZSet.join` is a **hash join** (`Dictionary` + `nextIdx` chaining, probe side `a`). `IndexedZSet.join` is a **sort-merge join** (ordinal-sorted runs, single merge walk). `Plan.fs` gives `"join"` and `"indexedJoin"` the *identical* formula `(a * b) / max 1L (max a b)`, and `EstimatedCpuNanos` is `max 40L rows * 40L` — rows alone, no per-operator term. So `cost(join) ≡ cost(indexedJoin)` for every input. Access-path selection is exactly what Selinger 1979 exists to do; we have the two access paths that motivated it. And `IndexedZSet` is sorted **by construction** — a materialised *interesting order*, free information, never priced.

**2. The `Plan` cost tests are named after formulas they do not assert.** `Plan join estimates product-over-max` (`Plan.Branches.Tests.fs:146`) asserts, in full:

```fsharp
plan.Count |> should be (greaterThan 0)
```

`EstimatedRows` is never read. Four sibling tests are the same shape. This is *why* the stage-two mutation run (every join heuristic → `999999L`) leaves 34/34 green. It is worse than an absent test: a test named `Plan join estimates product-over-max` reads, to anyone scanning the suite, as the cost model's falsifier. It cannot fail for any value.

**3. `SimdMerge.fs` contains no vector instructions.** Its header promises AVX2/NEON/AVX-512 loads, branchless compare + conditional select, masked stores. `Vector<int64>.Count` is used **only as a loop chunk size**; the merge front is two scalar `while` loops. Its cited correctness evidence — a fuzz test named *"fuzz: SIMD merge matches scalar"* — **does not exist**.

Also: `Catalog.fs` holds **no statistics** (Selinger's architecture is a cost formula *over catalog statistics*); **no columnar layout exists anywhere**; `ArrowSerializer` is genuine `Apache.Arrow` 23.0.0 but has **zero production callers**; and the Arrow golden vectors' cross-check is vacuous *by its own header's admission* — both sides call the same .NET library, which is agreement between correlated implementations.

## The uncomfortable consequence, stated

Finding 1 is a cost-model defect, and the best evidence says cost models are the **least** important of the three components. Leis et al.'s 2025 retrospective (PVLDB 18(12), read directly): *"the impact of the cost model is dwarfed by errors in cardinality estimation."* So fixing the access-path cost is worth doing because it is nearly free and unblocks physical-operator choice — **not** because it will make queries fast. Cardinality estimation is what would, and that is the stage-two statistics doc's territory.

## Four first steps

| ask | state | smallest first step |
|---|---|---|
| vectorised | `Simd.fs` real but dead; `SimdMerge.fs` SIMD in name only | **repair or strike the false header first**, then benchmark scalar-vs-SIMD, then vectorise `MergeKernel.fs` (the kernel `ZSet.(+)` actually calls) |
| row store | this is what we have — `ImmutableArray<ZEntry<'K>>`, sorted AoS | none; **name it** as the row variant |
| column store | absent | SoA `ZSet` (parallel `keys` / `weights`), judged on one measurement |
| Arrow | built, thin, unused | check in hex-in-JSON vectors from an **independent** impl (pyarrow/arrow-rs) |

The column-store and vectorisation first steps are **the same step**: `ZSet.weightedCount` documents wanting `MemoryMarshal.Cast` + `TensorPrimitives.Sum`, then concedes *"we can't safely use MemoryMarshal.Cast"* because of the AoS layout — and does a 4-way unrolled scalar loop. SoA makes the weight column a contiguous span and that operation safe. Which is Abadi et al. 2013's central claim reproduced in miniature: column storage without column execution buys little.

Highest value-per-line in the whole document: give the two joins different costs and write the test that fails when they are equal. A handful of lines in a 97-line file, no statistics required — the distinguishing terms are structural, not data-dependent.

§3 flags honestly which were read in full (the 2025 retrospective; Kersten's abstract) and which rest on bibliographic verification plus standard summaries.

**Three corrections to the brief that commissioned this**, each the anchoring rule working as designed:
- The `Peter Selinger — Potrace` entry is a **correct citation for a different person**, not a misattribution. Repair applied is disambiguation in place **plus** the missing Patricia G. Selinger entry — deleting a correct citation to fix a lookup failure would have been the worse error.
- MonetDB/X100's third author is **Nes**, not Manegold.
- Cost-based optimisation over incremental view maintenance is **not** an unwritten area — **Tempura** (PVLDB 14(1), Alibaba) is a Cascades-style incremental optimizer over Calcite. What is genuinely open is narrower: **no published cost model over DBSP circuits**, where the unit is a delta and `integrate`/`differentiate` make retained state a first-class cost term, and where the bilinear rewrite triples the join sites with no published account of which term dominates.

Two entailment checks that changed a citation's use: **Velox** *"does not contain a language front end, nor a global query optimizer"* — so it anchors composable **execution**, never plan search. And **learned optimisers** are constrained here by rule, not taste: ambient runtime feedback violates §13 noninterference and breaks §7 DST replay unless the feedback is a declared, replayable circuit input.
