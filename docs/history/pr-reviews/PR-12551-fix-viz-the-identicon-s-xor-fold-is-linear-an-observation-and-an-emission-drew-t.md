## Description

Follows #12533, which landed 27 minutes before this review and fixed the truncation correctly. **Its repair is the finding.**

## Defect 1 — the truncation (#12533's, independently confirmed here)

`glyphOf` read bits 0..31 of a 128-bit ZetaId, which are **exactly the `Randomness` field**. Measured against compiled `Zeta.Core`: 1000 ids differing only by timestamp drew **1** glyph; 42 ids spanning Category × Persona × Location drew **1** glyph. Confirmed, and already fixed upstream.

**The quoted threshold is wrong by ~20%** — in the original report, in #12533's docstring, and in its test comment. "Birthday at roughly 65 536" is `√N`, not the expected-first-collision statistic. Expected first collision is `√(πN/2) ≈ 82 137`; the 50% point is `≈ 77 163`. Measured on the truncating implementation: first collisions at **77 994** and **78 231** over two independent draws, and **zero** at n = 65 536 (P(≥1) there is 39.3%, not ~1).

## Defect 2 — the repair XOR-ed four lanes, and XOR is linear

`lane 0 ^^^ lane 32 ^^^ lane 64 ^^^ lane 96` removes the *truncation* and keeps a *structure*. XOR over GF(2) is linear: two ids collide iff `fold(a XOR b) = 0`, a 96-dimensional subspace of deltas. Every ZetaId field is a **contiguous bit-range**, so that subspace lands on the field boundaries — any two bit positions exactly 32 apart cancel exactly.

Measured on the landed fold via `ZetaIdCodec.pack` with a fixed nonce:

| construction | result |
|---|---|
| two ids identical in **every** field but timestamp, `1 + 2^32` ms apart (49.7 days + 1 ms) | **byte-identical glyph** |
| all 16 deltas of the form `2^f \| 2^(f+32)`, f = 0..15 | **16 of 16 collided** |
| **Observation** vs **Emission** (different `Category`), delta cancelled by one timestamp bit (global 97, inside Timestamp) | **byte-identical glyph** |

Constructible from the layout, field-aligned, reachable by ordinary minting. No birthday argument covers these; they are not the declared residual. `Category`'s entire job is "WHAT KIND of thing this is", and two kinds drew one picture.

**The stated reason for choosing XOR is false on the facts.** *"a hash would need a fourth byte-lock"* — `hash.fmix64` is already a registered generator with an IR row in `GeneratorIrRegistry` and an existing cross-oracle byte-lock at `tests/cross-verification/fmix64`. There was no fourth lock to build. `fmix64` stays O(1) and allocation-free: five shifts, two multiplies, no array.

**And the test named for the bound pinned the bug.** `the 32-bit bound is exact — a collision can be constructed on demand` asserts `glyphOf a = glyphOf (a XOR (k<<<32) XOR (k<<<64))`. That is not the pigeonhole — it is the linear cancellation, asserted as a *requirement*. It would have blocked this repair. Replaced with a search-based exhibition of the real bound (first collision at n = **91 570** on a fixed SplitMix64 stream; zero by 65 536).

## The fix

`foldTo32` folds both 64-bit halves through MurmurHash3's `fmix64` (Appleby, public domain, already byte-locked). `GlyphSpaceBits = 32` and the mirror-symmetric face are untouched — 32 bits is a **ceiling**, not a fix target: 8 free nibbles, right half is the bit-reverse of the left, and beating it means dropping the mirror.

`GeneratorRegistry` bumps `zetaid.glyph` 1 → 2. #12533 changed the pixels and left the version at 1, contradicting the registry's own contract (*"bumping a version = a new id, so a change is never silent"*) — for one commit a registered generator's content-address claimed output it no longer produced. `zetaid.glyph@2` joins the `generator-registry-id` cross-verify vectors; TS and F# independently agree on `f42314cf4d9df1441cf5025a4509f484`.

## The 2026-08-14 survey erred — and the taxonomy has a missing bin

It cleared this twice (`:126`, `:196`) as `ZetaIdViz.fs:45 | bijective, harmless`. Line 45 is the **inner** nibble→byte bit-reversal and the survey is right about it. Line 45 is not the encoder — line 41 was, a 2^96-to-1 projection running *before* the bijection. `bijective(g)` does not give `injective(g ∘ f)` for lossy `f`.

**Class: inner-map injectivity verified, composition injectivity asserted.**

Second-order, and the reason the correction is longer than the row it fixes: the survey's three-class taxonomy (index / total-categorical / non-injective-magnitude) **has no bin for linear encoders**. A lane-XOR is total, branch-free, and every input bit reaches the output — it passes every test that taxonomy offers and still collides on a field-aligned subspace. A fourth class belongs there: **structure-preserving compressors**, where the failure is not that information is thrown away but that the *algebra of the input survives into the output*. Both corrections appended to the doc in place.
