## Description

Closes the P1 I deliberately left live when I fixed the CA trust-set P0 (#14554), and recorded in `docs/BUGS.md` so it would not read as an oversight.

## The defect (verified against `origin/main` @ `c8b23f023`)

`planPort` and `rotatePort` in `tools/setup/persona-keys/rotate.ts` were if-chains whose fallthrough was `device-cert`. So `rotate(fx, { ports: ["ca_key"] })` rotated the **cert**, reported `action: "rotated"`, staged it for a PR, and raised one biometric prompt naming `ca_key` — the port that did **not** move.

Mateo's original calibration is preserved: this is **not reachable from either shipped CLI** (`rotate-cli.ts` and `rotate-cluster-cli.ts` each filter against `ROTATE_PORTS` and exit 2). It is latent for programmatic callers and for the next member added to the union — **which was not a type error, and that is the actual defect.** The typo was its most visible symptom, not the bug.

## The fix — two guards that are complements, not substitutes

**TYPE.** Both functions are now `default`-less switches, the shape `ceremony-gate.ts` `ceremonyRequirementFor` already earns in this codebase and its sibling did not. `PortPlan` becomes a per-port **discriminated union**; each handler accepts only its own member and returns `RotationOf<its own port>`.

**VALUE.** A roster check inside `rotate()` — in the mechanism, not two copies in two CLIs — refuses a value cast into the union. A total switch cannot do this: `"ca_key" as RotatePort` matches no case and falls out as `undefined`. The **whole run** is refused, before the plan and before the gate, because a run that silently dropped one requested port would prompt for one act and perform a smaller one — the same mismatch this exists to prevent.

## Is the prompt/performed-port guarantee structural, or merely unreachable today?

The question worth asking, and the honest answer is **structural for the derivation, unreachable-by-construction for the dispatch** — the two halves have different strengths and I am not going to call them one thing.

The old code had **two independent derivations of "which port"**: `opts.ports` rendered the prompt, and an if-chain fallthrough chose the act. Two derivations can disagree, and they did. There is now **one**: `planPort` classifies, writes its `port` as a **literal at the classification site** (not echoed from the parameter), and both the prompt and the dispatcher read that same object. The handlers also take their paths from the plan rather than recomputing them, so the act operates on the object the human approved.

So the prompt cannot name a port other than the one classified — that is structural, not a reachability argument. What is *type-enforced* rather than *derivational* is the step from classification to handler, and that is what proof B1 covers.

One consent bug that was **not** in the original report, found while fixing this and fixed here: the old prompt named the **requested** ports including ones that were **absent**. `--ports machine-key,ca-key` on a host with no CA set up prompted for a CA swap that never happened. `performing` now filters on `plan.present`. RR-7b arm A is exactly this case.
