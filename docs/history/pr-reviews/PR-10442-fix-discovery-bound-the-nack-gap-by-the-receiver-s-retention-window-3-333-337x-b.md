  seq=64       in=74B  out=2483B       amp=33.6x       elapsed=0.1ms
  seq=65       in=74B  out=2518B       amp=34.0x       elapsed=0.0ms
  seq=5000000  in=74B  out=246666953B  amp=3333337.2x  elapsed=537.2ms

`header.seq` is `readUInt32BE` of an unauthenticated packet (`envelope.zid` is echo
suppression, not identity), and the resulting NACK is BROADCAST -- so this is a
mesh-wide amplification vector, and the u32 field permits 859x the probed value.

## The decision: desync, NOT a truncated NACK

The filed proposal was to CAP the list. Not taken. A truncated NACK asserts "these 64
are what is missing" while meaning "here are 64 of an unknown number" -- a partial
signal presented as a complete one, which is this repo's recurring defect class.

Chosen instead: a gap wider than the bound is not loss the receiver can speak to.
Beyond its retention window it cannot distinguish "the sender emitted these and they
were lost" from "the sender was quiet", from "another peer's stream interleaved" (one
global `expectedSeq` counts every peer), from "this packet is lying". So it reports a
local `DesyncEvent` and sends NOTHING. Gaps within the bound behave exactly as before:
full enumeration, no truncation anywhere in the wire format.

The desync is surfaced LOCALLY (`onDesync`), never sent. Every byte emitted in response
to an unauthenticated packet is an amplification factor, and a reflector that answers
"you are desynchronised" is still a reflector.

## The bound is derived, not chosen

MAX_NACK_GAP = RECV_BLOCK_WINDOW * BLOCK_TOTAL = 8 * 8 = 64 -- the receiver's own
retention window. The `8` was a bare literal in the block-eviction path and is now a
named constant, because a derivation pointing at a literal is two magic numbers
agreeing by luck. Beyond that window the blocks are evicted: nothing is recoverable and
no state backs a claim. LOSS_WINDOW = 64 reaches the same number independently -- a
single gap wider than the AIMD window yields lossRate > 1, which is not a rate.

## Named costs, not silently accepted

- The in-window reply is still a 33.6x reflector. Bounded, not eliminated. Unicasting
  to the peer that revealed the gap would fix the mesh fan-out, but this transport
  interface exposes `broadcast` only -- an interface change, not a security patch.
- A burst losing >64 CONSECUTIVE packets now produces no congestion signal at all. Real
  regression in the heavy-loss case, and not fixable here: with one `expectedSeq` shared
  across all peers, the wide-gap case is not measurable in the first place.

Both are written into the module's "Honest boundary" section, not just this message.
