## Description

## What was wrong

Gatekeeper generates a constraint CRD only after the Rego compiles. Two of the seven hat policies never compiled, so their CRDs never appeared, the `wait-gatekeeper-hat-constraint-crds` Sync hook exhausted `backoffLimit: 2`, the hat-system sync failed ("retried 10 times") — and **all seven** wave-3 Constraints stayed `OutOfSync`, including the five whose Rego is fine. The policy engine was running with zero policies installed.

## The discriminator, not a plausible story

Runs `34323056405` (red) and `34338106811` (**green**) both name exactly two missing CRDs in the init container:

```
NotFound: customresourcedefinitions "hatconflict.constraints.gatekeeper.sh"
NotFound: customresourcedefinitions "hatnocycle.constraints.gatekeeper.sh"
```

Compiling all seven modules extracted from `policies/*.yaml` with `opa check --v0-compatible` (the mode Gatekeeper uses for `spec.targets[].rego`, gatekeeper chart 3.23.1) fails for exactly those two and passes for the other five:

```
hatconflict:11  rego_compile_error:   var conflict_name declared above
hatnocycle:18   rego_parse_error:     unexpected identifier token ("or")
hatnocycle:7    rego_compile_error:   var next declared above
hatnocycle:12   rego_compile_error:   var next declared above
hatnocycle:30   rego_compile_error:   var sup declared above
hatnocycle:9    rego_recursion_error: rule reachable is recursive
```

Five defects, two classes. `some X` immediately followed by `X := ...` is a redeclaration. `reachable` calling itself is recursion, which Rego forbids outright — so `hatnocycle` could not have compiled however the syntax was spelled, and transitive reachability has to be `graph.reachable`. `or` is not a Rego operator; the CREATE/UPDATE disjunction it reached for never applied to UPDATE at all.

## Why nothing caught it, and what now can

Constraints and ConstraintTemplates carry **no ArgoCD health assessment**, so hat-system reported `health=Healthy` while holding zero installed policies — and `isApplicationSynced` accepts `OutOfSync + Healthy`. The lane named "included Synced+Healthy proof" passed over it in the green run as well as the red one.

So this adds the falsifier at the layer that can judge it: a step asking **Gatekeeper itself** whether every ConstraintTemplate compiled (`status.created`, `status.byPod[].errors`). Zero templates is a **failure**, not a skip — a loop over an empty list is the check that cannot fail. The jq selector was checked both ways against sample statuses: a compiled template is not selected, an errored one and a status-less one are.

## Cost

One `kubectl get` + `jq` in an existing job. No new job, no new matrix axis, no new action, no new secret. Public repo, GitHub-hosted standard runner — `billable.UBUNTU.total_ms = 0`.

## Still open (recorded in the workitem, not silently dropped)

The new step is a live-lane falsifier, ~25 minutes from change to verdict. A unit-level `opa check` over every ConstraintTemplate would catch the same class in seconds, but needs `opa` added to the pinned toolchain — a three-way-parity/toolchain decision rather than a bug fix, so it is named rather than taken here.
