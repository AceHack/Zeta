## Description

Found while diagnosing why **#12175 has been blocked for three days**. Its kind run showed this alongside the storage-class failures:

```
pods "wait-gatekeeper-hat-constraint-crds-snlbr" is forbidden:
violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false,
unrestricted capabilities, runAsNonRoot != true, seccompProfile
```

All four at once — because the pod template carried **no `securityContext` at all**, while `hat-system/namespace.yaml` sets `pod-security.kubernetes.io/enforce: restricted`. Enforcement has no warning phase: the pod is rejected at **admission** and never runs.

## Why this is its own change, not a footnote

This Job is an ArgoCD **Sync hook** whose entire purpose is making cold-start sync work — its own header says that without it, sync fails with `could not find constraints.gatekeeper.sh/HatWarmup`.

So the guard was **present, wired into wave 2, and unable to run** — which means the failure it exists to prevent came back. A guard that cannot execute is the vacuity class in its most literal form.

## A risk I introduced and then closed

`readOnlyRootFilesystem` is **not** one of the four things `restricted` requires — I carried it over from the sibling `deployment.yaml` as defence in depth. But it costs `kubectl` its writable discovery cache under `$HOME`, so left alone it would have **traded an admission failure for a runtime one**. The cache now points at an emptyDir, and the mount is asserted to resolve to a declared volume.

## The falsifier

A manifest defect with no test is how this one survived, so one lands with it. `restricted-namespace-workloads.test.ts` **derives** the namespace set from the manifests that actually carry the enforce label — not a hand-written list — and checks every authored pod template in them. Its own first assertion is that the derived set is non-empty, so **the suite cannot pass vacuously** the day that label is renamed or moved.

Scope is stated rather than implied: it checks only the four fields admission requires, and it cannot see Helm-rendered workloads, which arrive from a chart rather than this tree.

## Checked, not assumed

Both mutations were **asserted to apply** before their result was read — a mutation that silently patches nothing is indistinguishable from a test that cannot fail, an error made twice in this repo today.

| mutation | result |
|---|---|
| M1 — container `securityContext` removed | 4 → **3 pass / 1 fail** |
| M2 — pod `securityContext` removed | 4 → **3 pass / 1 fail** |

Restored: 4 pass / 0 fail. `tsc --noEmit` exit 0 — read as an **exit code**, since that tool colourises its output and grepping it for `error TS` matches nothing.

**Honest limit:** this is a manifest change verified by parsing, not by admitting a pod. No cluster ran it. The kind lane on a PR touching these paths is what would prove it — and #12175 is that PR.
