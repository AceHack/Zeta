## Description

Five Dependabot alerts with a published patched version, all closed by a
version change the installed tree actually carries. Zero dismissals.

  70        smol-toml  package-lock.json                     <=1.7.0 -> 1.7.1
  27 / 28   qs         src/Renderers/website/pnpm-lock.yaml  <6.16.0 -> 6.16.0
  21 / 22   qs         demo/identity-dla-site/pnpm-lock.yaml <6.16.0 -> 6.16.0

The four qs alerts were deferred by PR #17124 as "a different ecosystem and a
separate change". This is that change: a flat pnpm.overrides entry per site,
which is the mechanism already in use there (tailwindcss>nanoid), plus a
regenerated lockfile so --frozen-lockfile still installs.

WHAT THE smol-toml ALERT DID NOT NAME. It reads as "a dependency is out of
date". What was actually wrong is that our OWN override was holding it there,
and holding it BELOW what its consumer asked for. markdownlint-cli2 0.23.2
declares an exact smol-toml 1.7.0; the root overrides block has said 1.6.1
since 2026-04-21 (8f61566942) with no recorded reason anywhere in the tree.
For four and a half months it silently DOWNGRADED the tool the markdown gate
runs on -- the exact wrong turn PR #17124 identified and rejected, already
committed and standing. And 1.6.1 is on the wrong side of CVE-2026-85730.

MEASURED, WITH A CONTROL. The CVE is an infinite loop, so the falsifier is a
timeout and the control is the version we were shipping:

  smol-toml 1.6.1  parse("a=[1 #")  -> rc=124, never returned, core pinned
  smol-toml 1.7.1  parse("a=[1 #")  -> throws TomlError, sub-second
                   parse("a = [1, 2] # trailing") -> {"a":[1,2]}

Both site fixes were checked on DISK rather than in the lockfile: after
pnpm install --frozen-lockfile, node_modules/.pnpm holds qs 6.16.0 in both
sites. website: pnpm run check and vite build pass. demo: the deploy own
entry, identity-dla-pages-build.ts, passes.

THE FALSIFIER. src/Core.TypeScript/hygiene/lint-overrides-take-effect.ts,
wired into the build-graph-completeness gate job beside the other premise
checks. An overrides entry is a security control written as a version string,
and nothing checked that it took effect. It refuses three measured shapes:
lockfile drift (including a split resolution hidden behind an alias key), a
NESTED key (bun ignores nested overrides, so npm would show a fix bun never
installs -- PR #17124 hit this live), and a range rather than a pin. A missing
lockfile exits 2 and says which: UNKNOWN is not a pass.

Mutation-checked end to end, not only in unit tests: reverting the override to
1.6.1 gives rc=1 against both lockfiles; rewriting bun.lock alone to 1.6.1
gives rc=1 naming only bun.lock; the unmutated tree gives rc=0.

Verification: bun test lint-overrides-take-effect.test.ts 19/19;
agencysignature-block.test.ts 82/82; bunx tsc --noEmit -p tsconfig.json rc=0;
