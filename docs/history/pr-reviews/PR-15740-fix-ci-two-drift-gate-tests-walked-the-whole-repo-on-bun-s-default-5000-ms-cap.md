## Description

## The audit's real error

`cross-verify (ace-suite)` went red on `main` at `af0f1d478c` (job `98378495016`).
The annotation said only `Process completed with exit code 1`. From the job log:

```
(fail) the checked-in repo graph > DRIFT GATE: regenerating from the repo's
       manifests reproduces the checked-in graph [5174.08ms]
  ^ this test timed out after 5000ms.
(fail) the checked-in repo graph — quorum > DRIFT GATE: a hand-invented
       reviewer class fails derive [5200.08ms]
  ^ this test timed out after 5000ms.
```

**Nothing had drifted.** `build-graph.json` was correct. Both tests *timed out*.
The audit reported a defect that did not exist, on a leg inside `gate (required)`.

## Does it gate?

**Yes, by construction.** `gate (required)` is the only required context in the
`CI Gate` ruleset; `cross-verify` is named in `gate-required.needs`; and GitHub
collapses the whole 31-leg matrix into one `needs.cross-verify.result` that is
`success` only when every leg succeeded. Checked rather than assumed.

## The cause — not the commit it landed on

`af0f1d478c` is a periodic heartbeat batch merge touching only `data/` and
`docs/github/prs/shards/015/`. That reads exactly like a manifest↔shard invariant
break. **It is not one:** the two commits *after* it — `22f7268d89`, `6c21c701bf`
— are **green** with those same files present, and a broken invariant would have
stayed broken. Isolation to one commit discriminated *timing*, not *causation*.

What actually happened is a threshold crossing. Five call sites perform a
repo-wide derivation over `git ls-files` (**52,819** entries, only growing).
Measured across four consecutive `main` legs:

| test | 3 legs back | 2 back | 1 back | `af0f1d478c` |
|---|---|---|---|---|
| regenerating from the repo's manifests | 3669 ms | 4121 ms | 4452 ms | **5174 ms** ❌ |
| a hand-invented reviewer class | 3597 ms | 4075 ms | 4423 ms | **5200 ms** ❌ |

Against Bun's default **5000 ms** per-test cap. Which commit was standing at the
crossing was arbitrary.

## Instance or coupling? — **Coupling.**

Three of the five sites already carried an explicit `30_000` from
`081KZZ3JHP1087G0R00027ARRR`, added a week earlier because they measured *"too
close to survive a loaded runner"*. The other two were left on Bun's **default** —
a budget nobody chose, over a cost nobody bounded. Both of those are the two that
failed. Raising two numbers would not be inherited by the next site added, so this
ships the guard too.

## What changed

1. **The two sites declare `30_000`**, matching their three siblings.
2. **A new check refuses the class.** It parses this test file and fails on any
   test performing a repo-wide derivation without an explicit timeout — with two
   non-vacuity controls (the block parser must find >50 tests; the predicate must
   match the two real sites), so it cannot pass over an empty set.
3. **The leg now annotates.** A non-zero audit emits
   `::error title=cross-verify (<id>)::<title> FAILED (exit N). Command: …`, so a
   reader learns *which* of 31 legs failed and whether it was a check that failed
   (1) or one that never ran (2), without downloading the log. Deliberately a
   `console.log` of a workflow command inside the Bun process already running: no
   shell, no `shell:` key, no installed program — a reporter that needs a
   toolchain cannot report a toolchain failure.

## Nothing is weakened — proven by mutation, not asserted

A timeout is a wall-clock bound, not a skip, not `continue-on-error`, not a
baseline. The assertions are untouched:

| mutant | result |
|---|---|
| drop a derived target from `build-graph.json` | both drift gates **FAIL**, with `::error::… has drifted. Run: …derive --write` |
| strip either new `30_000` | the coupling check **FAILS**, naming the test |
| delete the new annotation | its reporter test **FAILS** |

A false alarm on the blocking floor is not a lesser fault than a miss — it costs
the same thing, the verdict stops carrying information, and it is what gets a gate
switched off.
