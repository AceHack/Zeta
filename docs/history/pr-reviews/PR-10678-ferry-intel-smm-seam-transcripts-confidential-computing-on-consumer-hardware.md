## Description

ferry: Intel SMM/SEAM transcripts + confidential computing on consumer hardware

Ferries two Aaron-forwarded transcripts on Intel's hidden CPU operating modes, with an
analysis that RETRACTS a suggestion I made an hour earlier.

Verbatim in ip-questionable/ per the notice-and-takedown policy; analysis restates every
claim so a takedown costs nothing.

The peel (Mirror -> Beacon), because the source is partly wrong and the corrections matter:
SMM is SYSTEM Management Mode, not "Service"; SEAM is the publicly documented foundation of
Intel TDX, not an undocumented backdoor; and - the load-bearing fact the transcript never
states - you CANNOT put your code in SEAM root, because it runs an Intel-signed module. That
kills the "hide our OS in there" idea outright.

The retraction: I suggested TDX/SEV-SNP as a route to a signer whose key the host cannot
read, on hardware we own rather than rent. It is NOT available on the fleet Aaron actually
has. TDX is Xeon-only, SEV-SNP is EPYC-only, SGX was removed from consumer desktop, and
consumer Ryzen has SME (memory encryption) but not per-VM isolation or attestation. Addison's
inventory confirms it: Ryzen 9 7940HS, 9955HX, N100, N150, J4125 - all consumer/mobile. Right
about the mechanism, wrong about the fleet.

Which makes Aaron's position correct rather than a compromise: "consumer swarms in the gpu
are not guaranteed independent like server swarms can be with real hardware isolation, that's
an acceptable split and even investors will understand that." The doc records that as a tier
table. It is legible to a technical investor precisely BECAUSE it declines to claim the
stronger property on cheaper hardware. And it does not weaken the custody design at all -
geographic distribution is what makes shares independent, and that is a property of where the
boxes are, not of what the CPU supports.

One tension nobody had named: unified-memory AI CPUs make key isolation WORSE, not better. A
discrete GPU has its own VRAM behind an IOMMU; on a unified architecture the iGPU addresses
the same physical memory as the CPU, so the boundary depends entirely on IOMMU/driver
enforcement rather than physical separation. The property that makes those parts good for BNN
inference makes them bad for the thing we want next. Recorded before hardware is chosen at
scale rather than discovered after.

GPU sandboxing: VFIO full-device passthrough works on consumer cards and is real containment
for the one dependency we cannot rewrite, verify or sign. SR-IOV is gated to licensed
datacenter cards. Community firmware work can unlock partitioning, but that changes the
resource-sharing story and NOT the trust story - partitioning obtained by patched firmware is
not attested isolation and must not be presented as such.

Docs only.
