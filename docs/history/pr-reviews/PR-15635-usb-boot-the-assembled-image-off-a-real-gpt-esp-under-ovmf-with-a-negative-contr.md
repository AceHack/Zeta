## Description

Aaron's ordering, which is the whole shape of this PR:

> *"not yet — only my usb after exhaustive ci/github workflow/action tests."*

So this is not one step moved; it is an attempt to exhaust what CI can cover, plus a classification that says precisely what is left and why, because every hardware-only row converts into physical work with one stick and one machine.

## What moved

`multiboot-qemu-uefi-smoke.yml` boots a **synthesised directory** through vvfat. That proves `BOOTX64.EFI` and `grub.cfg` are the right files; there is no partition table anywhere in its path. Its own comment says so. It verified an artifact was **built**, not that it **boots**.

The new lane wraps the assembled FAT image in a real GPT (protective MBR, primary + backup headers, 128-entry array, ESP at LBA 2048) and boots it under OVMF as `-device usb-storage`.

```
[gpt-esp-usb-boot-smoke] observed ZETA-GPT-ESP-USB-BOOT from a GPT ESP
(type c12a7328-f81f-11d2-ba4b-00a0c93ec93b, LBA 2048) on -device usb-storage;
1 stick enumerated as [hd0], 2 sticks as [hd0 hd1];
negative control (loader removed) correctly did NOT boot
```

**67 seconds, three boots.** Non-vacuity is structural:

| phase | configuration | required outcome |
|---|---|---|
| A | one stick, loader present | reaches the marker |
| B | one stick, loader **removed** | must **NOT** reach it — checked *first* |
| C | two sticks, distinct iSerials | firmware enumerates **two** disks |

Phase C is `MAN-USB-02`'s premise — *do two attached sticks actually produce two candidates* — observed for the first time, paired against A's one-stick control so "saw two" cannot mean "counted one twice".

## The falsifier, demonstrated — and what it cost us

| run | mutation | result |
|---|---|---|
| `32977525049` | `none` | **green** 67 s |
| `32977813494` | `esp-type-guid` | **red** — *"the boot STILL reached the marker; the mutant is not falsifying"* |
| `32977847861` | `zero-gpt` | **red** — boot never reached the marker |
| `32978777533` | `remove-loader` | **red** — boot never reached the marker |
| `32979381604` | `esp-type-guid` after fix | **red** — caught by the static cross-check |
| `32979570729` | `none` (restore) | **green** |

The second row is the point. **OVMF boots a FAT partition regardless of its type GUID** — its FAT driver never consults it. So the boot *cannot* falsify `c12a7328-…`, and the `sfdisk --json` cross-check (which had been gated on `mutation === "none"`) was the only thing enforcing it. It now runs unconditionally; skipping it under mutation would have left that mutant caught by nothing — the vacuity class reintroduced by the falsifier itself.

Without the knob, this lane would have shipped claiming coverage it does not have.

## Three independent GPT readers, none of them ours

`sfdisk --json` (util-linux) in the lane; macOS `diskutil` locally (`GUID_partition_scheme`, Partition Type **EFI**, offset 2048 blocks, FAT32 mounts); OVMF's own partition driver. CRC-32 tests use published check values; the mixed-endian GUID byte sequence is written by hand, not generated by the encoder under test.

## The register's stale claim, retired

`MAN-USB-05` said *"Nothing in this repository can observe a UEFI boot."* That is now false, and a stale claim inside the register of things-CI-cannot-check asks a human for time CI already spent. Both `MAN-USB-05` and `MAN-USB-02` now state which layer is covered and which is not, with the narrowing marked rather than silently rewritten.

## The classification

`docs/research/2026-08-26-usb-boot-verification-in-qemu-*.md`, three buckets kept deliberately apart so *"I did not get to it"* can never read as *"QEMU cannot do this"*:

- **COVERED** — in CI today with a falsifier.
- **COSTED** — QEMU/CI can do it; recipe and runtime given; **not built**. Linux-guest USB enumeration (~4 min; covers the hub and card-reader collapse cases `MAN-USB-02` calls untestable — **both are emulable**); Secure Boot **policy** under OVMF secboot (~1 day, ~3 min runtime; would leave only real-hardware key enrolment and attestation); attestation-verifier logic (out of bounds here — `persona-keys` is another agent's lane, #15564).
- **HARDWARE-ONLY** — with a disputable per-item reason.

Two splits came from measurement, not argument:

- **`MAN-USB-01` (macOS):** a raw disk image via `hdiutil` reports `BusProtocol: "Disk Image"`, **and** is excluded from `diskutil list external physical` entirely. So the parse half is cheap on a hosted macOS runner and the bus-protocol string is genuinely irreducible.
- **`MAN-USB-04`:** `hdiutil` *does* create `/dev/rdiskN`, a real raw character device. Three of four sub-claims are cheaply coverable; the residue is *"does **this** controller short-read"*. Its **handling**, though, is a software question we are currently paying hardware to answer.

The doc ends with an ordered physical session — what to bring, what to record first, and why (`MAN-USB-01`'s literal `BusProtocol` string is the highest-value observation of the session and cannot be obtained any other way).
