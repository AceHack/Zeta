## 1. Are the loss numbers accurate? No — the channel is uncalibrated

`burstParams` hardcodes `lossInGood = 0, lossInBad = 1`, and **every call site in the test file
goes through it**. That is the **Gilbert** (1960) channel with a total outage in the bad state,
not the **Elliott** (1963) generalisation with `k` and `h` free. The two remaining parameters come
from round numbers — `[0.005 … 0.3]` loss, `[1, 2, 4, 8]` burst — with no fit, no trace, and no
citation to a fit anywhere in the harness, tests, or research doc.

**This bounds #10417; it does not diminish it.** Still parameter-independent and sound: **56/56 vs
0/56** (pure algebra), **XOR-7/8 goodput dominance** (measured on an identical drop trace),
`UCH-2`, `UCH-8`. Bounded to "under this synthetic channel": every **cliff** number.

**Real 802.11 anchor found — CHECKED.** da Silva & Pedroso, *Sensors* 22 (2022), 410 hours of
indoor 802.11 UDP traces:

| quantity | measured | harness |
|---|---|---|
| `p` / `r` | **0.0393 / 0.1862** (mean burst **5.37**) | derived from round targets |
| loss in **bad** state | **0.6097** | **1.0** hardcoded |
| loss in **good** state | **0.0055** | **0.0** hardcoded |
| burst distribution | **Pareto Type II**, max **8,853** | geometric |
| adequacy | 2-state GE "cannot capture the behavior of the real system" (they use 4-state HMM) | 2-state GE |

The `lossInBad = 1` choice is not merely pessimistic, it is **mis-shaped in the direction that
matters most**: a 61%-loss bad state leaves ~3 of 8 gone per block — sitting exactly on the
[8,4,4] correction boundary, where shipped-vs-ML is maximally consequential.

**LoRa and satellite: searched, NOT FOUND.** Recorded as UNRESOLVED with the leads, rather than
filled in from memory. The one on-point LEO paper (Wang et al., IEEE ToC 2026) is paywalled.

## 2. Corruption is an absent fault class — and nothing could detect it

`applyFaults` drops, duplicates, reorders; it **never mutates a payload byte**. [8,4,4] corrects
**3 erasures but 1 error**, and the shipped decoder corrects **1 and 0**. `grep` for
checksum/CRC/HMAC/MAC over the transport returns one doc comment and nothing else.

**MEASURED** — erase data packet 0, flip one bit in parity packet 5:

```
erased d0 truth : [ 1, 2, 3, 4 ]
recovered       : [ 254, 2, 3, 4 ]
returned null?  : false
silently wrong? : true
```

Recovery **moves corruption out of redundancy the application never sees and into payload it
does**. Weakest capability, largest blast radius, and the one class not modelled. The cheap fix is
an integrity tag that **degrades corruption to erasure** — cost named in the item (4 bytes of
CRC32 on an 8-byte payload is 50% header growth on LoRa; a CRC stops accidents, not a forger).

## 3. The erasure-vs-congestion framing HOLDS — and the class already has a name

**RFC 4653** (CHECKED) is titled *Improving the Robustness of TCP to **Non-Congestion Events***
and states the identity directly:

> "suppose segment 3 was not dropped by the network, but rather delayed … The above scenario will
> play out in **precisely the same manner**."

So `UCH-16`'s ~500x reordering collapse is **not a separate bug from the AIMD design** — both are
non-congestion evidence entering a congestion controller. The consequence is that the fix is
**"separate the loss signals," not "tune the thresholds"**: no value of `HIGH_LOSS_THRESHOLD`
separates 5% corruption loss from 5% congestion loss when the estimator does not carry the
distinction. A reorder hold-down is still correct — it is RFC 4653's own mechanism — but it
patches one door and leaves corruption-loss, the larger source on these links, still driving
multiplicative decrease.

Anchors: Balakrishnan et al. ToN 1997 (**CHECKED**), BBR / Cardwell et al. 2016, Chiu & Jain 1989,
Gettys & Nichols 2011. Note `LossCause` already has the right type and infers it **from the loss
rate itself** — circular.

## 4. Two defects found by reading, both measured

**P0-security — unbounded NACK from an attacker-controlled `seq`, then broadcast.** Bounded probe
at `seq = 5e6`:

| | |
|---|---|
| inbound packet | **70 bytes** |
| outbound broadcast | **236,666,951 bytes** |
| amplification | **3,380,956x** |
| blocking, single-threaded | **929 ms** |

The field is a `u32`, so 859x that is reachable. It is **broadcast**, making it a mesh-wide
amplification vector — the "broadcast storm on WiFi mesh" the module's gossip debounce exists to
prevent, reached without gossip. `expectedSeq` also latches via `Math.max`. Filed to
`docs/BUGS.md` P0. **A `fast-check` property over the header fields finds this on its first run.**

**`decodePacket` returns a pooled-buffer view, not a copy**; `blockPos` is a `u8` never
range-checked (harmless today by accident — `undefined !== null` classifies it as a duplicate).
Recorded, not separately filed; covered by the fuzzing item.

## Where we stand against the field

**Ahead:** seeded counter-based faults, disjoint streams, DoP-invariance, and **analytic
falsifiers on the loss process** — netem/Pumba/Toxiproxy inject faults but do not verify they
injected the intended distribution. The differential ML oracle is the strongest idea in #10417.

**Behind:** uncalibrated channel; no corruption; **no time axis at all** (the controller's entire
output is a millisecond gap, never evaluated against latency or a real queue); and a
solved-in-1997 loss-signal conflation still in the design.

**Honest summary: #10417 built a good instrument and pointed it at a channel we made up. The
instrument is worth keeping; the channel needs a citation.**
