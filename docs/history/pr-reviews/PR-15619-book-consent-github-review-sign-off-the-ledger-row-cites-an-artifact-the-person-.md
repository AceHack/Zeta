## Description

## What this adds

A GitHub-native way for the ~20 people named in *You, Born at the Hinge* to record consent with a credential they already control, plus the verifier that refuses to publish when the record stops being true.

**The property enforced:**

> They produced the artifact with a credential they control, and verification does not route through Aaron.

`CONSENT-LEDGER.md` stays the source of truth for scope and reasoning. This is its machine-checkable half.

## The mechanism

A pull request whose diff **is** the passage about them, with the person as reviewer. GitHub already has three authenticated, timestamped, attributed decision verbs: **Approve** = consent, **Request changes** = decline with their reason attached, **Comment** = discuss. No custom vocabulary, no form, and the diff is the ask — they read the exact text, not a summary that can drift from it.

A `grant` event cites the review id. The audit re-fetches it and requires it to exist, be `APPROVED`, and be authored by the declared account — matched on the **numeric user id** as well as the login, because GitHub frees a deleted login for re-registration and the id is never reused.

## Consent is given to text, not to a name

The grant also carries the sha256 of the passage between `consent:begin` / `consent:end` markers. A one-character edit goes **STALE** and refuses publication. GitHub's `dismiss_stale_reviews` covers only the PR's own lifetime, not an edit months after merge — which is the case that actually matters during revision.

A person may instead grant over their whole **footprint** (`spanId: "*"`), so re-consent is a delta that names which member span moved rather than a fresh read of everything.

## Two tiers, matching the maintainer's own gradient

Repo drafts are public, disclosed and disputable; the distributable book is the hard demarcation.

| tier | check |
|---|---|
| `gate.yml` (repo) | **false claims** — review missing / not APPROVED / wrong author, a de-identified passage that still carries the name, a subject not on the roster |
| `pages-deploy.yml --publish` | additionally **insufficient consent** — STALE text, an unclaimed named passage, a revoked passage still present |

`mode=deidentified` is first-class: no consent event needed, but it fails in **both** tiers if the name is still in the text. That is the maintainer's live practice (a subject carried role-only pending her reply) turned into something a machine can refuse.

## Revocation is a fold, and it is asymmetric on purpose

`grant(+1)` / `revoke(-1)`, folded per `(person, scope, spanId)`. Both events are kept — raw vault, a single version of the facts. Ordered by the artifact's own timestamp, never a local clock; on an exact tie the revoke wins.

A **grant may not be "relayed"** and is refused at parse time. A **revoke may arrive on any channel**, including Aaron relaying a phone call. Privacy is hard money: one-way to more privacy is free, less privacy needs the owner. A hard-to-use revocation means somebody stays in a book they wanted out of.

## Proven failing — live, against a real GitHub review

Positive control is a real `APPROVED` review (`cli/cli#14262`, review `5024289867`, `babakks`, id `36728931`), fetched over the network:

| mutation | result |
|---|---|
| change one word in the passage | `STALE`, exit 1 |
| point at review id `9999999999` | `REVIEW_MISSING`, exit 1 (live 404) |
| claim `acehack` authored it | `REVIEW_WRONG_AUTHOR`, exit 1 |
| same login, different account id | `REVIEW_WRONG_AUTHOR`, exit 1 |
| relayed revoke after the grant | `REVOKED_PASSAGE_PRESENT`, exit 1 |
| no review source | `UNCHECKED`, **exit 3 — never 0** |
| relayed *grant* | exit 2, refused at parse |

42 tests, each negative paired with the positive control it mutates from so a failure cannot come from an earlier guard firing on a broken fixture. The shipped `consent-events.json` is opened and parsed by a test, so it is not an expectation nothing reads.

## What it does not give you

Stated in §11 so nobody mistakes a green verifier for a signed release. It proves an account bearing that login and id submitted an `APPROVED` review at that timestamp and the published text still hashes to what was in front of it. It does **not** prove who holds the account, that they read it, or that consent was informed and uncoerced. **E-signature (DocuSign / Dropbox Sign class) is the legal instrument; a DKIM-signed email reply is the vendor-independent archival channel. This is the machine-checkable layer and a substitute for neither.**

What it adds that a signed PDF cannot: an e-signature proves consent *was given*; this proves the **text still is what they consented to**.

## Corrected premise, checked not assumed

This work was briefed on the assumption that Zeta is private and would need a separate public repo so signers would not become collaborators. `gh repo view` returns `"visibility":"PUBLIC"`. So the constraint does not exist, the PRs live in Zeta, **zero collaborators are added**, and there is no copy of the passage to drift. `artifact.repo` is a field, so moving later is a data change, not a code change.

Also verified and stated: approvals from users without write access do **not** count toward branch protection's required reviews. The design deliberately does not depend on that — we need the review as an attributable artifact, not a merge gate. A design that needed it would push straight back toward granting twenty people write access.
