## Description

**`main` is RED** on the offline chart-targetRevision audit, with two findings that are the same event seen from both sides:

```
[acknowledgement-stale]   the register records sealed-secrets 2.16.2 as unpublished,
                          but this run produced no finding for it
[roster-entry-orphaned]   the snapshot still carries the bitnami-labs coordinate
                          no Application references any more
```

Both are the predicted consequence of **#13333 and #13339 landing together**. That coupling was flagged in #13339's body at the time: the register is drift-checked **both ways**, so fixing a pin makes its acknowledgement stale, and whichever PR merged second owed the one-line removal. Both merged, and neither paid it.

This is the register working exactly as designed — and the audit says so in its own refusal text:

> *An acknowledgement that outlives its defect is an allowlist, which is the thing the register exists instead of.*

## Two changes, one cause

- the `sealed-secrets` entry is **deleted** from `ACKNOWLEDGED_UNPUBLISHED`;
- `--refresh` re-derived the snapshot, swapping the dead `bitnami-labs.github.io` coordinate for `bitnami.github.io`.

The 165-line snapshot diff is one coordinate replacing another and its version list — checked rather than assumed: the only `repoURL` lines that move are `- bitnami-labs…` / `+ bitnami…`.

## `forgejo` is deliberately unchanged

Its refresh reported **`unreachable`** (`index.yaml` → 404), which the tool keeps distinct from **`unpublished`** on purpose, so a registry outage can never harden into a false "this version does not exist" verdict offline. Choosing between 9.0.0, 10.x and 11.x moves the values schema under a hand-written `valuesObject` — a maintainer decision.
