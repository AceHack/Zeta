## Description

## Why

The platform manifests pin `:latest` images (`ghcr.io/lucent-financial-group/{zeta-portal,zeta-platform-controller}`) but **no CI ever built them** — so a fresh cluster had nothing to pull and the portal could never run against the live API. This is the gap between "K8sOps merged" and "portal engages a real cluster."

## What

- **`build-platform-images.yml`** — on push to `main` (+ `workflow_dispatch`): build both Dockerfiles, push `:latest` + immutable `:sha-<commit>` to GHCR, cosign-sign by digest (keyless OIDC, same model/caveats as `build-ai-cluster-iso.yml`). PR builds validate the Dockerfiles without pushing (no registry write from forks). Minimal third-party actions — only `actions/checkout` + `cosign-installer`, both already SHA-pinned in-repo; GHCR auth/build/push use the runner's Docker via bare commands. Matrix over the two images. `ubuntu-24.04`, `contents: read` workflow-level, `packages`/`id-token` job-scoped, concurrency group.
- **`portal.yaml` / `controller.yaml`** — `imagePullPolicy: IfNotPresent → Always`, so a `rollout restart` actually re-pulls the rebuilt `:latest` (with `IfNotPresent` the kubelet keeps the stale cached image).
- **`portal/DEPLOY.md`** — the runbook: how the portal detects the cluster (in-cluster ServiceAccount — no config, no registration step), the `push → image → ArgoCD → pod` chain, Tier-1 demo + Tier-2 real (k3d side-load or the NixOS k3s cluster), per-tab verification, and the digest-pin follow-up.

## The chain this completes

```
push to main → build-platform-images.yml → ghcr.io/.../zeta-{portal,controller}:latest
            → ArgoCD zeta-root → platform/Application.yaml → pods (Always) pull fresh
```

No code changes to the portal/controller themselves; this is the deploy substrate around the K8sOps work in #7397.
