## What this is

**The design lock Aaron asked for**: one canonical definition of a valid AgencySignature block, in one module, called by both instruments — so they *cannot* disagree in future rather than merely agreeing today.

Recovery of the old malformed records **is** built, but it is the bonus, not the deliverable.

## The problem, measured on `main` (not theorised)

The convention had **two hand-maintained implementations** — `validate-agencysignature-pr-body.ts` (pre-merge) and `audit-agencysignature-main-tip.ts` (post-merge) — and they disagreed in **two independent ways**. Over the 6990 commits after the v1 ship anchor:

| finding | count | what it means |
|---|---|---|
| `CORRECT` (strict git-trailer parse) | **296** | the substrate can actually parse it |
| complete 10-key block git **cannot** parse | **716** | 551 are the identical blank-line-before-`Co-authored-by:` shape |
| version key present, **no complete block** | **976** | reported `CORRECT` with reason *"AgencySignature block present"* — false for all 976 |
| blocks with values the **pre-merge gate rejects** | **420** | the auditor never checked values at all |

So **1692 of the 1988 signed commits (85%)** were passing on the lenient path while the summary claimed the strict one. Spread across ~20 agent identities plus workflows, from the v1 ship date onward — not one actor's habit.

The second divergence is Otto's: `Human-Review: not-implied-by-credential` + `Human-Review-Evidence: chat` is **rejected at PR time and accepted on main**. Live instances on `main` include `Action-Mode: autonomous` (29), `agent-chosen` (29), `Human-Review: pending` (27).

Both are the same defect: **a governance convention whose meaning depends on which parser reads it.**

## What changed

**New `src/Core.TypeScript/hygiene/agencysignature-block.ts`** — THE rule, once: `REQUIRED_KEYS`, `ENUMS`, the `Human-Review` ⇄ `Human-Review-Evidence` cross-field constraint, Task shape, v2 `Cell`, plus `findSignatureBlock` (lenient recovery scan) and `validateBlock` (pure; returns violations, prints nothing, decides no exit code).

Both instruments import it. Their local copies are **deleted, not duplicated** — the validator now has no key list, no enum table and no cross-field rule of its own.

**Outcome taxonomy split.** The auditor *always* had a lenient message scan; it just reported the result as `CORRECT`. Now four distinguishable outcomes, separately counted:

- `CORRECT` — strict parse
- `RECOVERED-MALFORMED` — complete block, git parses none of it
- `RECOVERED-PARTIAL` — version key only, no block
- `INVALID-VALUES` — parses, breaks a value rule

**Recovery recovers the DATA, never silences the DEFECT.** A recovered block is still held to the same value rules (otherwise "put a blank line in it" becomes the way to skip enum checking), and never prints as a clean `PASS`.

## Enforcement — I picked, I did not file it back

Aaron said *"however the reconcile"*, so this does not come back as a question:

- **Pre-merge: blocking.** The PR body is still open; one edit fixes it, and it stops the next malformed block reaching `main`. That is the design lock working going forward.
- **Post-merge: non-blocking by default.** Turning it on today would red-X the next commit from any lane still using the old template, and no lane is fixed here. One-line flip (`RECOVERED_STATUSES_ARE_REGRESSIONS` / `INVALID_VALUES_ARE_REGRESSIONS`) or `--fail-on-recovered`.

I chose the **stricter-but-defensible** reading — the pre-merge gate's — because it is the one with the cross-field constraint the spec actually states (§5.3), so reconciling toward the auditor would have meant deleting a real rule.
