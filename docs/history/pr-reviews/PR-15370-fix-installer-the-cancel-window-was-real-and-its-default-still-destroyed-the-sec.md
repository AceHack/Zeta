## Description

## The one that matters

`zeta-first-boot.sh` runs `zeta-install` with `ZETA_AUTO_CONFIRM=WIPE` and `BOOT_DISK=auto`, and every fixed non-USB disk that is not the boot disk becomes a DATA disk and is wiped.

**I re-verified the "zero-width Ctrl-C window" finding and it is CLOSED.** Step 2.9 is a real wall-clock countdown, any keypress aborts, and a cancel exits 10 instead of 0. That fix landed 2026-08-21 and it holds.

**What it did not fix is its default.** `decideWipeScope` returned `"proceed"` for every disposition unless the circuit breaker was open. The path it runs on is *defined* by nobody being at the keyboard. So on a node with a second disk holding data, the outcome was unchanged by the window — destruction, 60 seconds later.

The classifier already computed the distinction; the decision now uses it:

| disposition | default | why |
|---|---|---|
| `blank` | PROCEED | nothing to consent to losing |
| `prior-zeta-install` | PROCEED | ours; re-paving is the declared intent of a re-flash |
| `foreign-data` | **ABORT** | data nobody put there for us |
| `indeterminate` | **ABORT** | a disk we could not read; an uncertain enumeration refuses |

One-way — it turns PROCEED into ABORT, never the reverse. The disk stays *in scope*; a keypress still destroys it. What changed is that the choice has to be **made** rather than **defaulted**.

**Cost, stated:** a headless install onto a box with a pre-existing foreign partition now stops and waits for a human. That is the intent, not a regression. It is the only case where proceeding is both unrecoverable and unwitnessed. The zero-typing property survives exactly where it was designed for.

## Also in here

- **The gate reprints the roster at the countdown itself** — path, size, transport, model, disposition. "The disks listed above" names nothing on a console that has already scrolled past the probe. A device the kernel reports no size for prints `SIZE UNREADABLE` and **forces ABORT**.
- **The restore claim now names its transport.** `fw_cfg` does not exist on metal; on hardware the unit falls back to `systemd-ask-password` on tty1. The mechanism is untouched and this is still not a metal proof — but the unit now logs `transport=qemu-fw_cfg metal-capable=no` on the success line and the QEMU harness **refuses a restore that does not declare one**, so a green CI restore cannot be quoted as metal evidence.

## One fail-open found and deliberately NOT closed

Step 1 enumerates with `awk '$2=="disk" && $3==0 && $4==0 && $5!="usb"'`. That predicate is *"not known to be USB"*, not *"known to be internal"*. Measured against a fixture:

```text
/dev/nvme0n1   NF=5   $5=[nvme]     admitted
/dev/vda       NF=4   $5=[]         admitted   <- transport unknown
```

`/dev/vda` reports no transport and **every QEMU install depends on it being admitted**, so tightening this would red the whole emulation lane for no gain on metal. Documented in the runbook (item 6) with the honest mitigation — unplug external drives before first boot — rather than silently narrowed or silently left.

## The runbook had gone stale in the dangerous direction

Corrected in place with the evidence attached and the originals kept — a 2am operator who half-remembers the page needs to know which half.
