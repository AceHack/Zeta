### 1. No far shore


Every TypeScript module named `*scheduler*`, and what it consumes:

- `ferry-throttler/drain-scheduler.ts` — `LaneSnapshot { hasWork, queueDepth, bytesQueued, drainCount }` → which **lane** to drain
- `ferry-throttler/heat-aware-scheduler.ts` — the same, with AIMD weight decay under heat
- `zetadb/scheduled-node.ts` — runs one tick when invoked; decides nothing

Not one carries a prior, a likelihood, a cost, or more than one candidate future. `drain-scheduler` selects among lanes that **already have queued work** — a fairness discipline over an existing multiset, which is not even cost-bound pruning. Handing it a posterior would require inventing a meaning for one.

### 3. The near shore destroys its own alternatives

`categorical-bayesian-planner.ts` is what the item points at as *"an actual candidate search"*, and it is one. Its signature ends the discussion:

```
BayesianHierarchicalSearch(...) -> { totalStatesExplored, plan: readonly string[] | null, jointLogLikelihood, finalUncertaintyEntropy }
```

Both levels keep a running best (`bestCoarsePath` / `bestSubPlan`) and drop every rival. By the time it returns, **the possibility space it searched no longer exists** — a consumer receives a decision, not a distribution. It is not a generator waiting for a consumer; it is a **complete pruner that already chose**, using entropy only to size its own budget (`maxStatesPerBlock = floor(500 * (1 + H))`). The cost-bound half again, in another language.

Two more structural facts for anyone tempted to compose the directory with itself: `CategoricalFactorTensor` appears in exactly two files (its own module, its own test), and `shiva`'s `FactorGenerator = (stateKey: string) => number` has **no adapter** to the planner's `CategoricalFactorTensor`. The two factor-graph modules in one directory have never composed with each other.

## Why nothing was built

- **`interfaces-free-classes-earned-under-rules.md`** — an implementation is a privilege earned under a rule; a `CandidateEstimator` with no TypeScript caller has nothing to earn it.
- **`only-the-irreducible-is-primitive-generate-the-rest.md`** — the generator already exists at the irreducible end, in F#. A second one in a language with no consumer is a duplicate frozen special case.
- **`toy-is-free-metered-must-be-earned.md`** — wiring an unmetered model into live action selection would make agent behaviour depend on a model nothing can refute, which is **worse** than the constants it replaced because it would *look* principled.

PR #10844, asked to reprice a composition operator, answered *"do not build it — an operator with no caller is speculative API design."* Same answer from the other end of the same razor: **a bridge with no far bank is speculative infrastructure, and a work item naming it does not conjure the far bank into existence.**

**What would change this answer**, stated so the refusal is falsifiable rather than permanent: a TypeScript consumer that takes **more than one** candidate and **defers** some under a budget. The moment one exists, the crossing has a destination and this document is obsolete.

## The one real adjacent surface — recorded, not built

There *is* a live TypeScript decision surface with a declared pluggable scorer and a production caller:

```
service/loop-tick.ts:346   await choose(world, { composer: defaultComposer })
observe/chooser.ts:44      interface ComposerBackend { score(menu, world): Promise<readonly number[]> }
observe/composer.ts:66     heuristicComposer -- five hand-set weights, no falsifier
```

`chooser.ts`'s own comments call the L2 tier *"Bayesian/heuristic scoring"* and offer *"(Bayesian scorer / local LLM)"*. Real port, called on every autonomous tick, one implementation made of `readiness 0.3 / priority 0.2 / modeCoherence 0.25 / forgeBoost 0.15 / operatorBoost 0.1`.

**It is a different work item, and building it today would be a regression**, which is why it is recorded rather than taken:

- It is a **chooser, not a scheduler** — picks one action, escalates on low confidence, no cost model, no budget, no defer. It performs neither of the two prunings the parent item distinguishes.
- Its **menu is supplied, not generated** (`buildMenu(world)`). A scorer re-weights what is already there; the possibility space is untouched by construction, so Rodney's Razor is not reachable from that seam.
- The TypeScript BNN's posterior is **over the wrong thing**: `error-bnn-bridge.ts` keeps a Student-t posterior per **error dimension** (`schema`, `type`, `range`, `constraint`, `auth`, `transport`, …) — *"how badly calibrated is my teaching on dimension d"*, not a posterior over actions. Using it as a candidate estimator means **hand-writing the prior and likelihood per menu action** — exactly the *"hand-supplied at every call site"* defect the parent item exists to remove, relocated to another language and called progress.
- `confidence` there is a score gap, `(max − secondMax) / max`. Renaming it "posterior" would be the silent-promotion failure in one line.
