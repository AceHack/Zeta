## Description

## What this is

Aaron asked for the Kubernetes cluster path to be **dogfooded** — actually stood up and exercised, not
specified. It was. A real K3S v1.31.4+k3s1 control-plane was booted twice with exactly the manifest set
`services.k3s.manifests` declares, and the documented first boot **does not work**. This fixes it and
leaves behind a check that fails if it is reverted.

## Inventory — register per surface

`unmetered` is the honest default (`.claude/rules/toy-is-free-metered-must-be-earned.md`): implemented,
used, never falsified. Nothing here was called "real" for being unlabelled.

| Surface | Register (before) | Witnessed by |
|---|---|---|
| `full-ai-cluster/k8s/**` | **metered** | daily live-kind lane + `k8s-manifests.test.ts` |
| `infra/k8s/applications/**` | **metered** | `validate-applications.ts` + 12-case mutation suite (`helm-validate.yml`) |
| `src/Core.TypeScript/cluster/**` (k3d/kind harness) | **metered** | `argocd-health-test.ts` + unit tests |
| **`infra/k8s/bootstrap/**`** | **unmetered** | **nothing** — the lane triggered on it and could not see it |
| `infra/nixos/**` (host configs, k3s modules) | **unmetered** | nothing evaluates them |
| root `flake.nix` `nixosConfigurations` | **unmetered** | no CI job; **no `flake.lock` exists at all** |
| K3S token distribution | **planned** | documented manual step, `sops-nix`/`agenix` TBD |
| MetalLB / ingress / Cilium under `infra/` | **absent** | `--disable=servicelb,traefik` with no replacement declared |

The interesting row is the fourth. `helm-validate.yml` **triggers** on `infra/k8s/**`, so a bootstrap
change ran a lane — but that lane's validator only ever scanned `infra/k8s/applications`. A check that
runs and cannot fail on the file that changed reports green. That is how the bug below survived.

## The first real gap

Boot a control-plane today via the documented `nixos-install --flake /mnt/etc/zeta#control-plane` and
**ArgoCD never installs.** Measured, not inferred:

```
Addon kube-system/argocd-install     CHECKSUM <empty>
Addon kube-system/root-application   CHECKSUM <empty>
Warning ApplyManifestFailed  Applying manifest at ".../argocd-install.yaml" failed:
                             the server could not find the requested resource
$ kubectl -n argocd get pods   -> No resources found
$ kubectl get crd | grep argo  -> (nothing)
```

retried every ~15 s forever. `infra/k8s/bootstrap/argocd-install.yaml` was a
`kustomize.config.k8s.io/v1beta1` **Kustomization** — a build-time kustomize input, not a Kubernetes API
object. K3S does support kustomize, but only for a *directory* containing `kustomization.yaml`, and
NixOS's `services.k3s.manifests` cannot emit that shape: each attribute becomes one flat file under
`/var/lib/rancher/k3s/server/manifests/`. `root-application.yaml` then failed too, because its
`argoproj.io` CRD ships *with* ArgoCD — so **nothing under `infra/k8s/applications/` ever deployed.**
Steps 3–9 of the bootstrap order in `infra/README.md` did not happen.

## The fix

Convert it to the `helm.cattle.io/v1` **HelmChart** CR K3S's own Helm Controller understands — the shape
`full-ai-cluster/k8s/bootstrap/` already uses, whose header records the same conclusion reached on real
hardware first: *"the plain-resources format that `services.k3s.manifests` actually understands."*

argo-cd chart **7.7.10 → appVersion v2.13.2**, the exact ArgoCD version the Kustomization pinned —
checked against `https://argoproj.github.io/argo-helm/index.yaml`, not assumed, and the same pin the
daily live-kind lane already exercises.

Re-measured on a fresh K3S with the fix:

```
Addon argocd-install     CHECKSUM 74f5ece3...   Addon root-application  CHECKSUM 89c4faea...
argocd-application-controller-0  1/1 Running    applications.argoproj.io     registered
argocd-server-...                1/1 Running    applicationsets.argoproj.io  registered
argocd-repo-server-...           1/1 Running    appprojects.argoproj.io      registered

NAME                     SYNC STATUS   HEALTH STATUS
zeta-root                Synced        Healthy      <- App-of-Apps
argo-rollouts            Synced        Healthy
argo-workflows           Synced        Healthy
local-path-provisioner   Synced        Healthy
cockroachdb/gitlab/longhorn/orleans  (deploying — heavy charts on a laptop VM)
```

`root-application` still fails its *first* attempt — its CRD arrives with ArgoCD — and K3S's addon
controller retries it into place. That was measured too and is now written down in the README rather
than left as a surprise.

## The falsifier

`infra/k8s/tests/validate-bootstrap.ts` + `validate-bootstrap.test.ts`, both wired into
`helm-validate.yml`. Ten mutation cases, each asserting exit 1 **and** the specific reason, plus an
unmutated control asserting exit 0 so an unconditionally-failing validator would not satisfy it.

The load-bearing case restores the retired Kustomization verbatim. Run against `main`'s actual file it
reports `20 passed, 1 failed` — **the guard goes red on the bug it was written for.** It also covers
both directions of the `services.k3s.manifests` roster (a declared source that does not exist; a
bootstrap file nothing declares), strict YAML with duplicate-key detection, and unpinned HelmCharts.
`infra/nixos/**` is added to the lane's triggers because the roster lives there.

## What I deliberately did NOT do — scoping is Aaron's call, not mine

1. **No root `flake.lock`.** The root flake's header says *"The flake.lock pins the entire universe."*
   There is no root `flake.lock` and there never has been. `nix flake metadata` resolves every input
   fresh — and pulls `nixos-hardware` against a **nixpkgs-unstable 26.05pre**, so two installs of the
   same commit on different days are not the same cluster. Committing one pins nixpkgs for every cluster
   node at once; that is a decision with a blast radius, not a drive-by. **Stated in the README instead.**
2. **No CI evaluation of `nixosConfigurations`.** I evaluated all three host configs locally — they *do*
   evaluate (`control-plane`, `worker-gpu-01`, `worker-gpu-02` all produce a `.drv`) — but nothing in CI
   does, so the `hardware-configuration.nix` stubs whose comments say they exist "so `nix flake check`
   succeeds in CI" are serving a check that does not exist. A `nix`-enabled eval job is a real lane with
   real runner cost and belongs in its own PR.
3. **Did not touch the K3S token paths.** `k3s-server.nix` sets `tokenFile` to
   `/var/lib/rancher/k3s/server/token` and `k3s-agent.nix` to `.../agent/token`; K3S *writes* the server
   one itself. Whether those defaults are right is entangled with the unshipped `sops-nix`/`agenix`
   decision, and I will not guess at a credential path. **No secret was read, printed, or handled in this
   work; `op` was never run.**
4. **Did not touch the missing ingress/LB.** `--disable=servicelb --disable=traefik` with no replacement
   declared means `LoadBalancer` Services stay Pending. Already documented in `k3s-server.nix`; the chart
   values here pin `server.service.type: ClusterIP` so ArgoCD does not become the first victim of it.
5. **Did not converge the two installer substrates.** `infra/` and `full-ai-cluster/` are still parallel
   bootstrap trees. `full-ai-cluster/` is the one with a live CI lane; `infra/` is the one the root flake
   and `infra/README.md` point at. That is a real fork and out of scope here.
6. **Did not touch `worker-gpu-*` join.** Bringing a worker up needs a live control-plane and a shared
   token — steps 8–9. Untested, and honestly labelled `unmetered` in the README rather than implied to work.

## Cost

Zero. The k3s probe ran locally in the already-running podman machine; the only network was public image
and helm-index pulls. Nothing external was provisioned, and the two added CI steps are ~2.2 s inside a job
that already exists.
