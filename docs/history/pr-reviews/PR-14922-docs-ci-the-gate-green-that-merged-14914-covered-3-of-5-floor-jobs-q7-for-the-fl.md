## Description

docs(ci): a second false-green, caught live on this PR's own gate run

`path filter` was CANCELLED at 5m4s on run 32767938815 — the gate run for this very
PR. `build-and-test` and `full-verify` both declare `needs: path-filter`, so both
went `skipped`, and the `gate (required)` verdict step treats `skipped` as
acceptable. It published SUCCESS with two of five floor jobs never having run, on a
code-touching PR. `gh pr checks 14914 --required` -> rc=0.

The verdict step's own comment says "Skipped is acceptable (path-filter gated)" —
which assumes `skipped` means path-filter DECIDED docs-only. It does not distinguish
that from path-filter DIED.

The `Emit scope` mitigation worked and is not sufficient: it published
`##[notice]gate scope=reduced: 3/5 floor jobs ran. Skipped: build-and-test,
full-verify.` so this green does carry its scope — but armed auto-merge reads the
verdict, not the annotation.

The cap is NOT the cause and raising it is NOT proposed. Measured over the last 40
completed pull_request gate runs: `path filter` ran 39 times, succeeded 39 times,
n=39 min=27s p50=33s p90=36s max=57s. Five minutes is ~9x p90. The 5m4s is a hang,
which is the class rerun-cancelled-gate.yml exists for.

The remedy is floor semantics and it costs ZERO additional runner minutes —
path-filter already runs on every PR — so `- path-filter` in `gate-required.needs`
adds no job and no minutes and turns this silent green red. That is a floor change,
so it is Q7 for the maintainer rather than a line I edit, and the cost in the other
direction is stated: PRs would then block on a rare infrastructure hang.
