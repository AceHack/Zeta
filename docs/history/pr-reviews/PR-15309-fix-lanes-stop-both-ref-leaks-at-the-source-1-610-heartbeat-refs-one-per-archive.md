## Description

## Summary

Two lanes minted a permanent git ref per flush. 3,098 remote branches; ~2,900 were these. This is the **source** fix — no branches are deleted here.

**Neither leak was what it was reported as**, so the corrected diagnosis is recorded alongside each fix.

## LEAK 1 — heartbeat flush refs (1,610 of 1,631 `heartbeat/*` refs)

`agent-heartbeat.yml` pushed `heartbeat/<agent>-flush-<SOURCE_SHA>` — a new ref every flush (alexa 564, otto 532, soraya 514).

Reported as *the supersede path leaking when a superseded PR is closed unmerged*. **It is not.** Ruleset **"Heartbeat Branch Protection" (16934633)** covers `refs/heads/heartbeat/*` with a `deletion` rule, `bypass_actors: []`, `current_user_can_bypass: "never"`. So no agent, admin or workflow can delete one — **and `delete_branch_on_merge` cannot fire on them either.**

Checked, not assumed:

| evidence | result |
|---|---|
| merged flush PRs #15267 / #15255 | heads **still on the remote** |
| `automation/*` archive branch of merged PR #15283 | **deleted on merge** (same repo, same setting, no deletion ruleset) |

So **every flush leaked its ref, merged or not**, and "delete the branch when its PR reaches a terminal state" was never an available fix. Under the ruleset as written the only remedy is to stop minting names.

**Fix:** the ref is now `heartbeat/<lane>-flush`, one per lane, force-updated in place. This needs **no ruleset change and adds no bypass actor** — the protection stays exactly as strict. It is not a new invention: it is the shape `flush-via-staging.ts` has run on tick-metrics / society / drift-sweep for months, and those lanes leak nothing.

**Safety against "the superseded flush carried observations the newer one did not":** the head is never moved while a PR is open on it — the job checks first and backpressures — so there is never more than one open flush PR per lane and nothing is ever superseded. Unlanded work is held by the **lane** (rebuilt every tick carrying any prior unflushed delta over main), not by the ref.

## LEAK 2 — one `automation/pr-archive-*` ref per archived PR

The root cause is the **tolerance**, not the reasons it fired. On a PR-creation policy denial the workflow classified the error, wrote a step-summary note, and `exit 0` **with the branch already pushed**. Seventeen changes to that workflow each removed one *reason* `gh pr create` could fail; **none removed the `exit 0`**, so each time it failed for the next reason the run still went green with a ref stranded.

Per the maintainer's decision, archives now route through **`flush-via-staging.ts`** — one shared staging lane, no per-record branch. Reused as-is, not reimplemented; **delivery is a single call**.

**Concurrency** is handled with an optimistic-concurrency retry rather than a lane-wide `concurrency:` group. GitHub keeps only *one* pending run per group and cancels earlier pending ones, so serialising would **silently drop archive runs** under exactly the load that matters (merges land ~25 s apart). The retry is safe because `prepare` rebases on the winner, the archiver short-circuits on identical bytes, and the shard path is a function of the PR number.

**No path pushes a ref and exits 0 any more.**

### Latency tradeoff (stated, not discovered later)

A record used to get its own PR immediately; it now rides the lane's next flush, and parks on the buffer if the lane's PR is under test. **"PR merged" and "archive on main" are no longer simultaneous.** Nothing reads these docs on the merge path — the readers (backfill sweep, `derive-pr-manifest.ts`, the audits) are cadence jobs keyed on *is the record present*, never on arrival within N seconds.

### The PR step is transitional

`flush-via-staging` delivers via a PR, and the PR is the part being deprecated. The **durable half of this change is the batching**, which is right whether delivery is a PR today or a direct push tomorrow; delivery is deliberately one swappable call. See #12058.

## The falsifier — AH003, `gate.yml` floor job, **fatal**

`src/Core.TypeScript/hygiene/audit-orphaned-archive-refs.ts` asks the question none of the seventeen fixes did: **is the record ON MAIN?** Its sibling `audit-archive-pr-lane.ts` takes `gh pr list` as input and is structurally blind to a ref that never had a PR — which is what all of these were.

It runs on the pre-merge floor and is fatal, not as the non-fatal warning its sibling gets: *a lane that leaked because one failure was tolerated does not get its falsifier installed as another tolerated failure.*

### Running it corrected the diagnosis a third time

The backlog was reported as "1,284 stranded records". It is:

```
1298 archive ref(s); 1279 landed (safe to delete),
19 not on main (16 in flight, 3 settled, 0 unreadable age)
```

| count | meaning |
|---|---|
| **1,279** | records that **are** on main — the backfill lane landed them by another route and nothing reaped the ref. **Ref litter, safe to delete.** |
| **16** | pushed within the grace window, still landing. Normal operation. |
| **3** | genuinely stranded: **PRs #14346, #14882, #15186**. The only real loss. |

Had the audit reported a single "orphan count" of 1,298, the obvious next act — *delete the orphans* — would have **destroyed 3 irreplaceable records to tidy up 1,279 dead ones.** That is why the verdicts are not collapsed.

The grace window is part of the invariant, not a loophole: the first version had none and went 11 → 18 in half an hour on healthy operation. An unreadable age counts **against** the ratchet, never as clean. The gate is a high-water mark that may only be lowered — deleting a stranded ref does not make it pass, because the record is still absent from main.

## What I did NOT do

- **No branches deleted.** The separate cleanup agent owns that. This PR tells it which are safe: **1,279 `landed` refs are safe to delete; the 3 `settled` ones must be landed first.**
- **The 3 stranded records are not landed here.** That is a small, bounded backfill (`archive-pr-reviews.ts` for 3 PR numbers), not the 1,284-record batching exercise it was scoped as. Sizing it correctly was itself a result of this PR.
- **`is-pr-create-policy-denial.ts` is left in place**, now referenced only by its own test. Removing it is scope creep; flagging it because it encodes the tolerance and invites rewiring.
