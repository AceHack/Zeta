## The one he meant: difference lists

The talk **names them exactly**:

> "data structures with 'holes' in them" · "logic variables: explicitly modeling partial information" · **"retroactive immutability!"** · "still immutable … just unstuck in time" · "constant-time append to an immutable list" · "more fundamental than lazy evaluation or lazy streams (a bit closer to futures/promises)" · "…apply to more than just lists — difference trees? difference dictionaries?"

A difference list's tail is an **unbound logic variable** — a hole with a known shape and position. Appending is *binding the hole*: O(1), no copy, and every existing holder sees it at once.

**This is a better model of the template than the Bε-tree buffer I reached for earlier today:**

| | buffer | **hole** |
|---|---|---|
| what occupies the slot | pending operations awaiting flush | **nothing** — an unbound variable |
| cost | real storage, must be drained | **free**; an absence with a name |
| who fills it | the owner, on flush | **anyone holding the reference**, by unification |
| effect on holders | none until flush arrives | **immediate and shared** |
| Gordon Bell test | the buffer *is* there | **it isn't there** — the point |

So a template isn't a placeholder holding content; it's an **unbound variable with a declared shape**, and instantiation is *unification*, not a write. That makes "a template should be data, not machinery" precise rather than stylistic.

## Content-based addressing

Rolling hash ("Fast, Cheap, and Able to Roll"; *drop 1, take 1, new hash*) → rsync → content-defined chunking, citing **Tridgell's thesis p.64**.

The load-bearing detail for `zetafs`: fixed-size blocks **fail** because *"inserts/deletes shift each block"* — a one-byte insertion re-aligns everything after it. Cutting on a property of the **content** localises the damage. Plus the two-stage discipline: **cheap rolling filter, then sha1 confirm** — the rolling hash is a candidate generator, never a security primitive.
