## Description

docs(research): capacity is what the hardware cluster unlocks — storage and CNI already are not

Aaron asked for hardware readiness and for outside-the-box thinking on the CI
exclusions. Looking properly found that THREE OF THE FOUR BARRIERS I REPORTED AN
HOUR EARLIER WERE WRONG, and the one that is real is not the one the plan
targets. Correcting it in the tree because hardware decisions are being made on
it.

  I SAID: cilium is untested, only hardware closes it.
  MEASURED: false. `live kind Cilium CNI` is its own job with
  networking.disableDefaultCNI and a dedicated profile. It is excluded from the
  INCLUDED-APPS lane because it is tested in a DEDICATED one.

  I SAID: Longhorn needs real disks and more than one node.
  MEASURED: already solved, by exactly the move Aaron proposed.
  dev-cluster/manifests/longhorn.yaml binds a StorageClass NAMED `longhorn` to
  rancher.io/local-path. Run 32519516070: 11 Applications stopped being
  storage-excluded, 6 reach Synced+Healthy. The workloads never needed Longhorn,
  they needed the NAME — a StorageClass is a name bound to a provisioner, so the
  same unmodified manifests bind on a kind node.

  I SAID: the remaining exclusions are hardware.
  MEASURED: mostly credentials and convergence bugs.

WHAT IS ACTUALLY RED: the live-kind lane has failed on main since 2026-09-05
16:56 — 21 of the last 29 completed runs. 34/37 healthy; the laggard is
`hindsight`, and its own deferral record says in capitals "CAPACITY -- AND
HINDSIGHT IS THE SYMPTOM, NOT THE CAUSE ... FailedScheduling 0/1 nodes are
available: 1 Insufficient cpu". The blocker is CPU on a 4-vCPU runner.

THE LOAD-BEARING CORRECTION TO THE TWO-NODE PLAN: adding kind nodes does not add
CPU. kind nodes are containers on one host sharing one CPU allocation, so a
3-node kind cluster on a 4-vCPU runner has 4 vCPU arranged differently. The
two-node change is right for other reasons — replication, anti-affinity, PDBs,
topology spread and nodeSelector paths all pass VACUOUSLY on one node, including
the exact GPU selector wiring whose absence hid the device-plugin defect — but
it does not fix the failure that is red today, and would slightly worsen it.

GPU WITHOUT A GPU: the ollama/vllm exclusion conflates two claims. "Syncs,
schedules onto the labelled node, pulls, probes pass" needs no silicon — advertise
nvidia.com/gpu as an extended resource and run the workload CPU-only, which both
support. "The model infers on the accelerator" needs hardware. Splitting it turns
two hard exclusions into two assertions at a named depth plus one honest
deferral, and it should be vendor-parameterised from the start since the module
already takes a vendors list and Aaron will have non-NVIDIA GPUs.

THE PATTERN, which is already the repo's: cilium has its own lane, kubevirt+cdi
has its own lane. New capabilities get FOCUSED lanes; the broad included lane
should not grow them — it is the one already CPU-starved.

Register: measured — failure history, final states, the hindsight capacity
finding quoted from its own record, the Longhorn alias outcome quoted from run
32519516070, the Cilium lane's existence, both kind profiles being single-node.
Argued but NOT measured — that a larger runner fixes it; the size needed is
unknown and the honest next step is measuring peak requested CPU against the
runner's 4 rather than guessing a tier.
