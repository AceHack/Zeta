## Description

Closes #14558 — that PR moved `global.json` alone, which is the half-fix the
`dotnet-sdk` entry in `.github/dependabot.yml` says will be produced and refused.
The bot supplies the notification and the exact version; this PR supplies the
coupled edits.

## A feature band, not a patch

`.mise.toml` has said in prose for months that a `10.0.3xx -> 10.0.4xx` move is
the one that moves the bundled Roslyn and must carry the CodeAnalysis pins with
it in one commit. This is the commit that prose was written for, and the
prediction held.

| value | before | after |
|---|---|---|
| `.mise.toml` `dotnet` (single declared source) | 10.0.303 | **10.0.400** |
| `global.json` `sdk.version` (restatement) | 10.0.303 | **10.0.400** |
| `Microsoft.CodeAnalysis.CSharp` | 5.6.0 | **5.9.0** |
| `Microsoft.CodeAnalysis.Analyzers` | 5.6.0 | **5.9.0** |
| `FSharp.Core` | 10.1.400 | 10.1.400 — unchanged, and that is a *measurement* |

## Measured, not inferred

Roslyn was read by executing each SDK's own `Roslyn/bincore/csc.dll -version`
(the method `audit-codeanalysis-sdk-match.ts` uses). The two values already on
file were reproduced **first, as a control**, before the new SDK was read:

```
10.0.302 -> 5.6.0-2.26329.109   control, matched the recorded value
10.0.303 -> 5.6.0-2.26377.103   control, matched the recorded value
10.0.400 -> 5.9.0-1.26379.115   the minor moved, 5.6 -> 5.9
```

`5.9.0` is exactly what Dependabot proposed on #13590 and the guard refused when
the SDK was still on 5.6.0. The bot had the **right version at the wrong time**:
it could see the package feed and could not see the SDK.

## The `ignore:` entry stays, with a corrected rationale

Its LIFTS-WHEN condition is now met once, so leaving the old comment would leave
a stale justification. But "lifts when the SDK's Roslyn >= the pin you want" was
never a one-shot condition to discharge and delete — it recurs at **every feature
band**, and the next Roslyn minor will reach the feed before the SDK that can load
it reaches this repo. Deleting the entry would remove the refusal and keep only
the notification. The comment now records the completed lifecycle instead.

## FSharp.Core did not move, on purpose

Each SDK declares its implicit FSharp.Core as `<FSCorePackageVersion>`:
`10.0.303 -> 10.1.303`, `10.0.400 -> 10.1.400`. The repo already pinned
`10.1.400`, i.e. **ahead of the SDK it ran on**. This roll does not bump it; it
makes the existing pin correct for the first time.

## One instruction in the brief was not followed

I was asked to repoint `.mise.toml` and `global.json` from
`audit-dotnet-pin-parity.ts` to `mise-pin-parity.ts`, on the grounds that the
former does not exist. **It does exist** — on `origin/main` and in this tree —
and it is exactly the check those comments describe; I ran it.
`mise-pin-parity.ts` is a *different* check that holds mise's own `min_version`
across the NixOS installer flakes. Making the edit would have replaced a correct
pointer with a wrong one, so the comments are unchanged.

## A trap paid for twice, now recorded

An XML comment may not contain a double hyphen. I put one in
`Directory.Packages.props`; the file stopped parsing, MSBuild silently stopped
applying `ManagePackageVersionsCentrally`, and every F# project failed restore
with `NU1504 duplicate FSharp.Core`. That reads exactly like an SDK regression
and I nearly filed it as one — **a control build on the OLD SDK reproduced it and
cleared 10.0.400.** The note is now in the file, and a `--` in the note itself
caught the same mistake a second time.

The macOS vnode trap documented 2026-08-23 also fired and is **confirmed**:
`mise install` reports failure for an install that succeeded
(`Installation finished successfully` is in the same output), because the
replaced host binary is SIGKILLed on the stale code-signature cache entry
(exit 137, empty output). The comment now says not to revert the pin on this
signature.
