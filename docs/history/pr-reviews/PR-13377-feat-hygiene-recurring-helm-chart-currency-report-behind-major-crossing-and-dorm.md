## Description

## The ask

> "it would be good if there was some kind of reoccuring check on out of date helm charts." — Aaron

## Why this is not the check that already exists

`src/Core.TypeScript/hygiene/audit-chart-target-revisions.ts` (#13333) answers **"does this pin RESOLVE?"** and gates every PR. **Currency** is a different question, and a pin can resolve perfectly and be twenty-three majors behind — which is the actual state of `kube-prometheus-stack` (`65.5.0` against upstream `88.5.3`). The one-off survey that measured it (#13325) is a snapshot that started rotting the day it landed. This is the recurring version.

## How the existing refresh is reused — no second network lane

A Helm `index.yaml` carries `version` and `created` **side by side**, so the publish dates come out of the fetch `--refresh` was already making: **zero additional requests, zero additional schedule**. One pass of `audit-chart-target-revisions.ts --refresh` now writes both snapshots, and the report renders offline from them.

| file | question | who writes it |
|---|---|---|
| `published-chart-versions.json` | what upstream publishes | `--refresh` (unchanged) |
| `published-chart-dates.json` | **when** it published each | `--refresh`, same pass, same fetch |
| `docs/CHART-CURRENCY.md` | the report | `report-chart-currency.ts --write`, no sockets at all |

The two snapshots are written **independently**. Folding them into one "something changed" flag made a dates-only change rewrite the roster whose only difference would then be `fetchedAt` — the timestamp-only weekly diff that file's own comment refuses to produce. Caught during this work by inspecting the first `--refresh` diff.

## The report's shape

One row per remote chart coordinate, worst first: `verdict · app · chart · pinned · pin published · newest stable · published · behind · bump · upstream`.

**`bump` is its own column**, exactly as asked: `**MAJOR**` / `minor` / `minor (0.x)` / `patch`. A patch bump and a major bump are not the same decision and a release count cannot tell them apart. `minor (0.x)` is separate because below `1.0.0` semver permits anything to change in a minor, and nine pins here are on a 0.x line.

Current headline: **32 of 35 behind · 13 crossing a major · 9 on a 0.x minor · 1 `DORMANT` · 1 `UNREACHABLE` · 1 pin never published · 3 with no dates available.**

## Behind vs unmaintained — the inversion this handles

A pure versions-behind metric reports **the most dangerous dependency in the tree as the healthiest one**. `minio` is the only pin that is not behind, and only because upstream archived the repository: `5.4.0`, published `2025-01-02`, silent **595 days**. So the gap and upstream's publishing record are **two columns**, and that row reads `DORMANT`, not `CURRENT`.

The recurring version immediately found a second case the one-off survey did not name: **`headscale`** — 31 minors behind *and* upstream silent 548 days. That is the argument for a recurring report in one row.

## A check that did not run never looks like one that passed

- `forgejo`'s repository is unreachable → `UNREACHABLE`, carrying the HTTP 404 verbatim. Never "up to date".
- The three **OCI** coordinates have no publish dates *available* — `/v2/<repo>/tags/list` carries no `created`, and reading one would cost a manifest fetch per tag. They render `unknown`, never `active`, and say why by name.
- No roster entry, or an empty version list → `UNREACHABLE`, `behind: null` (never `0`, which would read as current).

## This is NOT a blocking check

Being behind is a **standing condition, not a regression**. A gate would be red from birth (32 of 35) and learned-to-ignore within a week. Nothing here ever exits non-zero because a chart is out of date. `--check` fails for exactly one reason — the generated file no longer matches what the committed data renders — and it runs **only** in the existing weekly `chart-version-refresh.yml`, `continue-on-error`, in a job that is not in the required set. The whole report is also written to `$GITHUB_STEP_SUMMARY` there.

**Byte-identical on re-run:** no clock is read in the renderer. Ages are measured against the snapshot instant (`fetchedAt`), which is both deterministic and the more honest statement — *"as of the last refresh, upstream had published nothing for 595 days"*. `docs/CHART-CURRENCY.md` is added to `.prettierignore` so `format:write` cannot put the formatter and the generator in a permanent fight over the same bytes (same rationale as `docs/github/prs/shards/`).

## Mutation check

34 tests. **10 mutations applied, each proven applied by `cmp` against a saved pristine copy** (not `git HEAD`, which was dirty with the edits), **10 caught**:

| mutation | result |
|---|---|
| dormant branch deleted (0-behind archived chart reads `CURRENT`) | CAUGHT |
| unreachable repository reports as up to date | CAUGHT |
| unknown activity collapses to `active` | CAUGHT |
| major crossing reported as minor | CAUGHT |
| missing date becomes 0 days ("published today") | CAUGHT |
| behind counts the pin itself (`gt` → `gte`) | CAUGHT |
| pre-releases counted as published | CAUGHT |
| unparseable pin silently counts as 0 behind | CAUGHT |
| renderer reads the clock | **SURVIVED**, then CAUGHT |
| dates snapshot rewritten when identical | CAUGHT |

The survivor is worth stating: the determinism falsifier matched `\d{4}-\d{2}-\d{2}T[\d:]+Z`, and the injected `new Date().toISOString()` carries **milliseconds**, so the pattern written to catch that defect could not see it — and the "renders identically twice" test passes trivially when both calls land in the same millisecond. Fixed by widening the class and adding a direct source-level check (`renderReport.toString()` contains no `new Date` / `Date.now`); the mutation is now caught.
