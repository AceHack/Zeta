## Defects found — all six fixed

**1. `kubectl apply -f deploy/k8s/` applied the example secret.** kubectl selects by **extension**, never by filename, so `31-work-provider-secret.example.yaml` was a live manifest in the apply set. It carries `WORK_PROVIDER: "github"` plus `GITHUB_TOKEN: "REPLACE_WITH_A_REAL_TOKEN"`, `GITHUB_OWNER`, `GITHUB_REPO` — a **complete** provider config, so the resolver's throw-on-partial fail-fast does not fire. The documented bring-up therefore turned the external work port live against `your-org/your-repo` with a placeholder token, **silently destroying the internal-only safe default `30-worker.yaml` promises**. Moved to `deploy/k8s-templates/`, which also keeps it inside the yamllint/kubeconform globs (both recurse `agentic-organization/deploy`).

**2. cockroach and nats were BestEffort.** Neither declared `resources.requests`, so the kubelet evicts them **first** under node memory pressure — on a single node, the database and the message bus die first. Requests added (→ Burstable). No limits added: a ceiling guessed without a measured working set OOMKills where no ceiling does, so that stays **reported, not gated**.

**3. `20-nats.yaml` documented a Job that does not exist.** Its header said the stream and durable consumer "are provisioned by the nats-provision Job". There is no such Job anywhere in the tree — provisioning is `deploy/provision-nats.ts`, a **host-run script needing a port-forward**. The worker *binds* an existing durable (`consumers.get`) and never creates one, and the throw escapes to an unguarded `void runMain().then(...)` — an unhandled rejection, not the graceful degraded path. Header corrected to say what is actually true.

## Would these come up on a single USB-booted node?

**No — not from `kubectl apply -f deploy/k8s/` alone**, and that was true before this PR. Two undocumented manual steps stand between the manifests and a running org, now recorded in a **stale-guarded exception register** rather than papered over:

- `agentic-org-worker:keepalive` is built and `kind load`ed **by hand** (only recorded procedure: `HANDOFF_GOAL_ORCHESTRATION_MOAT.md:267`) and exists in no registry → ImagePullBackOff on any fresh node, because `IfNotPresent` still *pulls* when the image is absent.
- the JetStream stream/consumer must be provisioned by the port-forwarded script → without it the worker crash-loops.

Resource fit is *not* the problem: totals are **950m CPU / 3584Mi requests**, which schedules on a modest node. Limits sum to 7000m / 10496Mi, which is oversubscription, not a scheduling failure.

Both register entries carry a reason and a `LIFTS WHEN:` condition, and an entry matching no image in the tree **fails the audit** — a corrected reference cannot leave a false excuse standing.

## `--dry-run` — evaluated and deliberately not added

Measured on kubectl 1.36 with no cluster: `apply --dry-run=client` errors **identically** on a valid tree, a bad `kind`, and an unknown field (`failed to download openapi … connection refused`). Even `--validate=false` needs the API server for RESTMapping (`unable to recognize`); the only thing it catches cluster-less is a missing `kind`, which kubeconform already catches. It **cannot discriminate**, so adding it would be a check that cannot fail — either always red, or `|| true` and vacuous. `--dry-run=server` needs a live cluster and is out of scope for this job.
