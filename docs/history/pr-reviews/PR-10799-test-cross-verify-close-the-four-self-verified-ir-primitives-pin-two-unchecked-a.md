## Finding 1 — the four self-verified primitives: resolved

`lcg32_glibc`, `lcg32_numerical_recipes`, `lcg64_mmix`, `murmur3_32_tail` each had exactly one lane, generated from the IR, with `vectors.yaml` derived from that same lane. `nway-diff` passed them at `minOracles = 1`: the IR checked against itself.

Each now carries an independently written `_gen/gen.py`, typed from the published recurrence or reference source, **never** from the IR — no `*.ir.json` read, no import of the generated lane, closed-form arithmetic. `NO_INDEPENDENT_ORACLE` in `ir-vs-handwritten.ts` is now **empty**, and the paired test asserts it equals the scan in both directions, so a future bare primitive cannot land silently.

## Finding 2 — both anchor claims verified against primary sources, both confirmed, with two corrections

### `rng.lcg32_glibc` — confirmed, and stronger than briefed

Computes `(1103515245*x + 12345) mod 2^32`. glibc `stdlib/random_r.c`, `__random_r`, TYPE_0, fetched from the GNU C Library source:

```c
int32_t val = ((read_state(state, 0) * 1103515245U) + 12345U)
               & 0x7fffffff;
write_state (state, 0, val);
*result = val;
```

The mask is mod 2^31 **and the masked value is written back into the state**, so the recurrence itself is mod 2^31 — not a full-width state with a truncated output, which is the reading that would have let the two agree. Computed both forms over the committed vectors:

| id | committed (mod 2^32) | glibc TYPE_0 (mod 2^31) |
|---|---|---|
| x-2 | 2207042835 | 59559187 |
| x-3 | 3310558080 | 1163074432 |
| x-6 | 2326136519 | 178652871 |
| x-7 | 3429651764 | 1282168116 |

Exactly the four named in the brief; the other six agree because their products stay under 2^31 and the mask is a no-op. Six-of-ten agreement is how a wrong anchor survives a spot check.

**Correction 1 to the brief (strengthens it).** glibc's default `rand()` is not this generator at all. `rand()` calls `__random()`, whose `unsafe_state` is initialised `.rand_type = TYPE_3` (`stdlib/random.c`) — the degree-31 additive-feedback trinomial, not an LCG. TYPE_0 is reachable only via `initstate()` with a state buffer under 8 words. So the name is wrong about the algorithm *and* about which glibc code path it would even be.

**Correction 2 to the brief (weakens one clause).** "The mod-2^32 form matches the ANSI C *example* `rand()` from K&R/C89" is right about the constants and about the state update on an ILP32 target, and wrong if read as reproducing that function. The C89 example is `next = next * 1103515245 + 12345; return (unsigned int)(next/65536) % 32768;` — its state is an `unsigned long` (mod 2^64 on LP64) and its return is bits 30..16. This generator reproduces neither its output nor, on a 64-bit target, its state. The honest description is *a full-word 32-bit LCG carrying the ANSI/glibc-TYPE_0 constant pair*, and `numerology-vs-number-theory.md` lands in the same place: the constant pair appears in several distinct generators, so the constants never identified which one this is — the **modulus** does, and it says none of them.

### `hash.murmur3_32_tail` — confirmed

Appleby's `smhasher/src/MurmurHash3.cpp`, `MurmurHash3_x86_32`, under the reference's own `// body` marker:

```c
for(int i = -nblocks; i; i++)
{
  uint32_t k1 = getblock32(blocks,i);
  k1 *= c1;  k1 = ROTL32(k1,15);  k1 *= c2;
  h1 ^= k1;
  h1 = ROTL32(h1,13);
  h1 = h1*5+0xe6546b64;
}
```

The IR's three ops are the last two lines — the per-block accumulator combine. The section labelled `// tail` handles the leftover 1..3 bytes with `c1 / ROTL32(_,15) / c2` and an XOR, and contains no rotl-13, no multiply-by-5, no `0xe6546b64`. Arithmetic correct; name wrong.

### Third finding, not in the brief — `rng.lcg64_mmix`'s increment is contested

The multiplier `6364136223846793005` is uncontested and Knuth's. The **increment** is not: the committed `1442695040888963407` is the pairing overwhelmingly cited as "Knuth MMIX" (and is the leading digits of log2(e) = 1.442695040888963…, Knuth's habit), but Wikipedia's LCG parameter table currently gives the MMIX row as `c = 9754186451795953191`, sourced to `rsixfour.c`. **I did not resolve this** against a primary Knuth source, and the test records both facts rather than implying agreement by silence — a matching multiplier does not identify a generator.

## Why the rename is filed, not landed

Priced precisely rather than estimated. `idOf name version` is a pure function of the name, so a rename moves the generator's ZetaId, the `generator` field **inside** the content-addressed IR document, and every golden byte derived from either: **13 files for glibc, 11 for murmur3**, plus a directory rename each — including `_golden/zeta-ir-v4.golden.json`, where the name is both the key and embedded in the canonical-JSON value.

Two things decided it, and the second is dispositive:

* `generator-registry-id/vectors.yaml` does **not** byte-lock either name (checked — neither has a row), so the id-treaty lane is untouched. The cost is real but bounded.
* **The rename cannot be split from `src/Core/ZetaIrV4.fs`**, which is owned by a sibling agent in flight on the canonical IR evaluator. Reporting the overlap rather than resolving across the boundary.

So the deliverable is the accurate docstring plus the filed work-item that the brief named as the correct outcome when cost is high — **081M02YCNMA087G0R003TK7AEW**, carrying the full file table, both candidate names, and the explicit fork the owner must choose for glibc: rename to a name that does not claim glibc (vectors unchanged), or re-derive as real glibc TYPE_0 (4 vectors change). Those are different decisions and the ticket refuses to blur them.

What is *not* deferred: both findings move from a prose comment on `ir-vs-handwritten.ts` — the register that let them sit unnoticed in the first place — into `anchor-entailment.test.ts`, 13 executable rows that pin the anchors that hold, the anchors that do not, the four divergent glibc values, and the unresolved MMIX increment. A finding nothing can contradict is the same vacuity class as a check that cannot fail.
