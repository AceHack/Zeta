## Description

## Summary

Makes load-bearing the docstring promise on `ISinkOperator` that *"the scheduler enforces terminal placement"* — until this PR, that promise was vapor. After topological sort in `Circuit.Build()`, scans every operator's `Inputs` for sinks and rejects with a diagnostic.

**PR 2 of 8** in the algebra-capability campaign. Stacked on **#4558** (PR 1).

## Mechanism

```fsharp
// After topo-sort succeeds, before built <- true:
for op in ops do
    for dep in op.Inputs do
        if dep.IsSink then
            invalidOp $"Sink-terminality violation: operator '{op.Name}' (id={op.Id}) reads from sink '{dep.Name}' (id={dep.Id}). ..."
```

- O(N + E) per Build; zero per-tick cost.
- Runs AFTER topo-sort so IDs are stable and cycle detection (the more structural problem) fires first when both are present.
- Error message names both endpoints, their IDs, the algebraic reason (\"retraction-lossy\"), and a pointer to the contract.

## Why this matters

Sinks are retraction-lossy by design — `BayesianRateOp` aggregates `BetaBernoulli` state that doesn't un-accumulate when a -1 weight arrives. Letting a downstream operator read from a sink would break the Z-set relational composition laws. The type-checker catches some cases (output-type mismatch); generic-typed sinks like `ISinkOperator<ZSet<int>, ZSet<int>>` slip through without this runtime check.

## Tests (9 new, all pass)

**Positive** (sinks at terminus build normally):

- Single sink at terminus
- Sink consuming Map output (sink itself terminal)
- Multiple independent sinks
- Non-sink plugin feeding Map (rejection is sink-specific, not blanket)

**Negative** (sink-feeding-op rejected):

- Map ← sink
- Filter ← sink
- Plus ← sink (multi-input op case)

**Error message contract**:

- Names both operators + IDs
- Cites `PluginApi.fs:ISinkOperator`
- Explains \"retraction-lossy\" reason

**Ordering**: cycle detection fires before sink-terminality.
