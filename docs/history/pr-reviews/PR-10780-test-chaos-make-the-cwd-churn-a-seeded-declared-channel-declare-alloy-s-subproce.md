## Description

## The defect

On PR #10757 (a wasm byte-lock change) `build-and-test (ubuntu-24.04)` failed with one test:

```
Failed Zeta.Tests.Formal.AlloyRunnerTests.Alloy spec Spine structural invariants hold
  Alloy Spine failed with exit 1. Output:
  Error occurred during initialization of VM
  java.lang.Error: Properties init: Could not determine current working directory.
      at jdk.internal.util.SystemProps$Raw.platformProperties(java.base@26.0.2/Native Method)
```

The JVM died before `main` because its working directory did not exist. Nothing to do with #10757's diff.

## Mechanism — measured, not argued

Four links, each checked separately before anything was changed:

| # | link | how it was checked |
|---|---|---|
| 1 | `Environment.CurrentDirectory` is process-global; the durability churn test assigns it in a loop | source |
| 2 | `Process.Start` with `WorkingDirectory` unset hands the child that CWD at fork time | measured with a probe script |
| 3 | the churn test's `finally` deletes the tree those directories live in | source |
| 4 | a JVM whose cwd is an unlinked inode dies at exactly that frame | **reproduced 10/10**, message byte-identical on JDK 26 |

Then end-to-end under the real xunit scheduler, on **unmodified `origin/main`**: **1 failure in 80 runs** — same test name, same JVM message. Post-fix: **0 in 80**.

Honest reading of those two numbers: 1-vs-0 at n=80 is weak evidence on its own, and it is not what this PR rests on. The load-bearing evidence is deterministic and is now shipped as tests (below).

## Corrections to the framing I was given

* **"TLC is protected because it sets `DisableParallelization`; Alloy didn't get that."** Not the reason. `Tlc.Runner.Tests.fs` is immune because it sets `psi.WorkingDirectory <- specsPath`. Its `DisableParallelization` is for counterexample-trace files in the specs directory — a different hazard entirely. Alloy left the working directory unset, so Alloy was the one in the blast radius.
* **This churner has bitten Alloy before.** `Alloy.Runner.Tests.fs` already documents a prior race between these exact two tests, fixed at a different site (`AppContext.BaseDirectory` instead of process CWD). The channel was known and was being patched one victim at a time.

## The fix

Aaron's reframing (2026-08-15) is the target: *"this is our deterministic simulation testing, any ambient channel should be replayable under test with chaos testing like behaviors too at least metered and understood and not hidden."* The churn is **kept** — it is deliberate fault injection and it is what proves `WitnessDurableBackingStore` canonicalises a relative path exactly once. What was wrong was its shape.

**`tests/Tests.FSharp/_Support/CwdChaos.fs`** — the churn becomes a declared channel:

* **Seeded** — `CwdChaos.schedule` is a pure function of `(seed, steps, targetCount)`; same seed, same flip sequence, every machine. SplitMix64 with the same constants as `src/Core/ChaosEnv.fs`, so the two chaos surfaces draw from the same arithmetic.
* **Metered** — `CwdChurnReport` carries flips applied, failures caught, and the first failure message. The old `with _ -> ()` made a churner that had stopped churning indistinguishable from one that was working.
* **Declared** — the process-global blast radius is named in a box at the top of the file, and membership is opt-in via a non-parallel `cwd-chaos` xunit collection rather than by scheduling luck.
* **Honest limit, stated in the file** — the seed fixes *which* directories are visited and *in what order*. It does **not** fix the interleaving with the system under test; no seed reproduces that. `schedule` is replayable; the race is not. Calling the whole thing deterministic would be the vacuity failure this repo names elsewhere.

**`Subprocess.startInfo`** makes a child's working directory a **required argument**, closing the ambient channel at the crossing (discipline #7 noninterference). Alloy's three spawn sites use it.

Both halves are deliberate: the collection makes the overlap not happen; the declared cwd makes it harmless if it does anyway.

## Why these are falsifiers and not passing assertions

* `subprocess spawned under seeded CWD churn survives its targets being deleted` — spawns JVMs under churn, then unlinks every churn target mid-startup. **Mutation check run by hand: deleting `psi.WorkingDirectory <- workingDirectory` makes this test fail; restoring it makes it pass.**
* `a subprocess inheriting an unlinked ambient CWD fails to start` — an EXPECT-VIOLATION witness, the shape `Tlc.Runner.Tests.fs` already uses. It asserts the hazard is **real**. If a future runtime stops failing here it goes red on purpose, rather than the guard quietly becoming decoration.

## Coverage: gained, not lost

Nothing was removed from the durability test — same 50 constructions, same relative paths, same invariant. Three changes, all additive:

* it now asserts `report.Flips > 0`. **The old test could pass with zero churn**: if the churner thread never got scheduled, or every assignment threw into `with _ -> ()`, `mismatches = 0` passed having tested nothing under churn.
* three churn targets instead of two. `schedule` never repeats a target back-to-back (a repeat is a no-op `chdir` that would have quietly halved the churn rate); with only two targets that rule fully determines the order and the seed would be inert. That degenerate case is asserted out loud in `CWD churn over two targets is forced alternation, seed or no seed` rather than left as a surprise.
* the once-a-week JVM crash is now an on-demand test.

## Known remaining gap, stated rather than hidden

Seven other test modules spawn `z3` / `/usr/bin/env` with `WorkingDirectory` unset (`Formal/Z3.Laws`, `Merkle.Laws`, `Crdt.Laws`, `Clock.Laws`, `ByteCost.Laws`, `Metric.Bounds`, `NftCommitDomainSep.Z3`). They are out of the blast radius now that the churn collection is serialised, and `z3` does not appear to resolve its cwd at startup the way a JVM does — but they were not converted to `Subprocess.startInfo` and I did not verify the `z3` claim. Deliberately out of scope; a fourth subprocess-spawning test added later should use the helper.
