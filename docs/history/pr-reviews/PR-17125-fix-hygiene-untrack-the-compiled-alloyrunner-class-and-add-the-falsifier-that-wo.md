## Description

fix(hygiene): untrack the compiled AlloyRunner.class and add the falsifier that would have caught it

Scorecard reports 9 BinaryArtifactsID alerts. Six are the adjudicated
artifact-under-test exception. Three are not, and one of those three is a real
defect the repo already had an opinion about.

The adjudication, re-measured rather than assumed:

- The six src/wasm-dla/bytelock/dla-canonical-*.wasm alerts (580-584, 711)
  correspond exactly to the six substrate modules named in
  .claude/rules/no-binary-in-proof-lineage.md. audit-proof-lineage-binaries.ts
  passes: "6 roster substrate(s), 9 build recipe(s), 7 committed binary
  file(s), 4 golden vector(s)". The exception holds and the enforcer that
  keeps it honest still runs.
- Three alerts name binaries the exception does NOT cover: alloy.jar (243),
  AlloyRunner.class (244), tla2tools.jar (245).

The defect (alert 244). src/Core.Alloy/classes/AlloyRunner.class is compiled
output of src/Core.Alloy/AlloyRunner.java, which is committed beside it.
.gitignore has ignored that scratch directory since 2026-04 and describes it
in its own words as "Regenerated; not source" -- but it names
tools/alloy/classes/, and the tree moved to src/Core.Alloy/. The rule moved;
the ignore did not; the intermediate got committed.

It is not merely untidy. tests/Tests.FSharp/Formal/Alloy.Runner.Tests.fs
"skips compilation if the .class file is newer than the .java source", so a
committed .class silently outranks the source it claims to come from -- a
checked-in binary deciding what the formal-methods harness actually executes.
That is the exact failure the rule exists to prevent, and it survived because
no in-repo check looked outside src/wasm-dla/bytelock/.

Fixed: untracked the .class (git rm --cached; the harness rebuilds it with
javac on first run) and repaired .gitignore to name both paths, with the
reason written down so the next move does not repeat it.

The falsifier, because a per-site fix leaves the class open.
src/Core.TypeScript/hygiene/lint-no-committed-build-intermediates.ts fails on
any tracked path ending in .class .o .obj .a .bc .pyc .pdb, repo-wide, with
no allowlist -- a hand-maintained exception list is the drift the rule warns
about. Wired into gate.yml beside the decide-by-grep guard and registered as
hygiene:no-committed-build-intermediates, so it runs rather than merely
existing. audit-linter-coverage-vs-invocation.ts now reports 36 scripts and
agrees with the ledger.

The check is shown to be capable of failing. Six falsifiers in
lint-no-committed-build-intermediates.test.ts, including the six byte-lock
.wasm paths as a NEGATIVE case (the linter must not argue with an adjudicated
exception) and AlloyRunner.java as a near-miss (it ends in "a" and must not
read as the ".a" archive). Mutation-checked: deleting ".class" from the
watched set turns 2 of the 6 red. Restored, 6/6 green.

Not fixed, and not dismissed: alerts 243 and 245, alloy.jar (21 MB) and
tla2tools.jar (4.3 MB). These are third-party tools with no committed source,
which the rule does not cover -- but removing them collides with
.claude/rules/clone-at-tag-stays-sufficient.md, which requires the tree to
stay buildable and checkable from a clone at a tag with no package manager
present. Vendoring may be what that rule REQUIRES here. Two rules point
opposite ways and picking between them is not a drive-by call; filed as
081M22RYY4W087G0R0020H2528 for the architect. The alerts stay open, because
an unresolved tension is not a dismissal reason.

Verification: bun test on the new falsifiers 6/6; bunx tsc --noEmit exits 0;

gate.yml; audit-proof-lineage-binaries.ts, lint-workflow-job-timeouts and
audit-linter-coverage-vs-invocation all pass.
