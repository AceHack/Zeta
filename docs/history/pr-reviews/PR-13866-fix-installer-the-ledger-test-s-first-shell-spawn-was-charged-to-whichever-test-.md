## Description

`installer-unit-tests` went red on main at 792635694 (#13852) with a TIMEOUT, not
an assertion failure: "THE REGRESSION: four installs from one stick" exceeded
bun's 5000ms default. It has now done this twice in two days (4572e07a4, 792635694)
and passed on every commit between.

MEASURED, from the red job's own log (job 97073835706):

```
four installs   ( 6 appends)   5005.65ms  -- TIMED OUT
one install     ( 2 appends)   1912.43ms
ten installs    (20 appends)    210.26ms
```

The cost FALLS as the work RISES. That is a warm-up curve, not a property of the
code under test: twenty appends run in 210ms once bash/cat/grep/date/tee/sync are
in the page cache, so per-append is ~10ms and ~4.8s of that first test was
one-time. This workflow runs `tools/setup/install.sh` immediately before
`bun test`, which is the disk churn that leaves the cache cold.

RULED OUT, both by measurement:

* NOT a regression from #13852. It edits zeta-install.sh, but both blocks this
  test extracts are byte-identical across it — ZETA-LEDGER-APPEND
  011a3f5b7a0ac239ad213338caeb2f95, ZETA-PREFLIGHT-PARITY
  d85e96cb9aa0e168f16b5d9baba0d7fc, before and after. The subject did not change.
* NOT the global `sync(1)` per record, which was my first suspect and was wrong.
  Stubbing sync out entirely moved the same script 1223ms -> 1263ms over five runs
  each. Inside the noise. Recording the wrong guess because the next reader will
  have it too.

THE FIX IS NOT A RAISED TIMEOUT. Raising it would widen a bound on a test that
asserts nothing about time, and would leave the cost to land on whatever test
happens to be declared first next. Instead the ambient cost is moved OUT of the
measured region: one throwaway `runLedgerShell` at module scope, before any test
exists to be charged for it. No assertion and no bound is touched, and every test
gets STRICTER — each now measures only its own work against the same 5000ms.

HONEST LIMIT: not reproducible on a warm developer machine (first spawn is ~1.5x
the median here, not 25x), so the evidence is the CI timing curve, not a local
repro. If the timeout recurs with this in place, the warm-up is a ruled-out cause
rather than an untested suspicion — which is the whole reason to pay it explicitly
rather than raise the bound.
