## Description

Aaron, 2026-08-15: *"we've had a lot of these 139 and 134 we should like dispatch someone to investigate and see if they can reproduce and/or fix, it might be some non-determinism slipping in somewhere."*

**139 = 128+11 SIGSEGV. 134 = 128+6 SIGABRT.** I found the nondeterminism. It is not in our code, it is not in CI, and it is not in one toolchain.

## The answer

**`AceHacks-Mac-Studio` recorded 147 process crash reports between 2026-08-08 and 2026-08-15.**

```
77  SIGSEGV        47  SIGABRT       19  SIGTRAP
 2  SIGBUS          2  SIGKILL (Code Signature Invalid)
```

Across `dotnet` 49 · `node` 16 · `bun` 14 · `git` 5 · `lean` 5 · `csc` 4 · `Tests.FSharp` 4 · `java` · `rustc` · `cargo` · `gpg` · `golangci-lint` · `llama-server` — **and** Chrome, Claude, Manus and ExpressVPN helpers, `xpcproxy`, `mediaanalysisd`, and three of Apple's own `XProtectRemediator*` binaries, which run none of our code.

**38 of the 147 fault inside a garbage collector walking the heap** — CoreCLR `gc_heap::mark_object_simple1` / `plan_phase` / `relocate_survivor_helper`, and V8 `MarkingVisitorBase` / `ConcurrentMarking::RunMajor` / `Scavenger::Process`. A heap-walker chases every pointer in the heap, so one corrupted word surfaces there first — and it surfaced in two GCs that share no code. The two code-signature kills are not crashes at all: the kernel found pages that **did not read back the bytes they were signed with**.

Unrelated memory managers from unrelated vendors do not all start faulting in their heap-walkers in the same week. **This is strong evidence of a memory-integrity fault beneath every runtime on that machine.**

**Not proven to be RAM**, and I refuse to round that up. `.claude/rules/numerology-vs-number-theory.md` says too many correlations is a warning; I asked the independence question and it survives (separate address spaces, separate allocators, separate vendors, plus a non-crash integrity signal), but three causes still fit:

| hypothesis | fits? | how to discriminate |
|---|---|---|
| **Memory hardware fault** | fits all four lines of evidence | **Apple Diagnostics** — hold `D` at boot |
| **OS / system-extension defect** (ExpressVPN installs one, and is among the crashers) | fits most; explains the signature kills less well | remove the network extension, re-measure |
| **Sustained extreme load** — load average **29** across 24 cores | fits the rising rate (7/day → 58/day) | drop fleet concurrency, re-measure |
| **Our code** | **excluded** — Apple's XProtect binaries do not run our code | — |

**The next step needs a human at the machine.** Two of the three remedies are free.

**What it costs us meanwhile:** locally-produced byte-lock treaties and golden vectors from 08-08 onward are suspect, and "I ran the gates locally and they were green" is weakened in both directions. **CI is the trustworthy oracle right now** — see below.

## The sharp end — what a crash was being believed as

`lean-proof.yml` decided **20 proof-regression gates** as

```bash
if lake env lean FILE 2>&1 | grep -q 'sorryAx'; then echo "::error::..."; exit 1; fi
```

A pipeline's exit status is the **last** command's, so `lean`'s status was discarded. The gate passes iff `sorryAx` is **absent**, and a prover that dies prints nothing.

**Measured, not argued.** That step extracted verbatim from main's tip and replayed with a `lake` that does nothing but `kill -SEGV $$`:

```
MAIN step exit=0
Lean research-proof axiom audit clean (no sorryAx).
```

Twenty machine-checked-proof gates reporting green with no prover output at all. The same step after this PR, same fake `lake`:

```
step exit=2
::error::toymodel axiom audit: the check DID NOT RUN — KILLED BY SIGSEGV (shell code 139) — no verdict was produced
::error::A process that did not finish produces the same empty output as a clean pass.
         This is reported as 'no measurement', never as 'no findings'.
*** it emitted nothing at all, which is exactly the trap ***
```

and with a healthy silent `lake`: **exit 0, 39 checkmarks**. Kill it and it is caught; restore it and it passes.

The irony worth recording: that file **already** carried an anti-vacuity guard whose comment reads *"A check that cannot fail is not a check."* It caught the name-resolution vacuity class and could not catch the process-death class — because the guard itself was written as `... | grep -q 'Unknown constant'`. **The guard had the defect it was guarding against.** And `lean` is in the crash population, 5 reports.

And live in this PR's own first build: `error MSB6006: "dotnet" exited with code 134` on `src/Core/Core.fsproj`, then three clean re-runs. The crash report gives the mechanism — `FailFastIfCorruptingStateException` → `EEPolicy::HandleFatalError` → `PROCAbort` → `abort()`, reached from `HandleHardwareException`. **The CLR reporting a hardware memory fault.** So 134 is not a different family from 139; it is a runtime's report of one. Note MSBuild renders it as `MSB6006 ... code 134` and never as `SIGABRT`, so grepping build logs for the signal name finds nothing.

**Second, independent trap:** bun-hosted `tsc` emits SGR colour even to a file, so `grep -c 'error TS'` returns **0 on output that does contain a TS error**. Different mechanism, same false clean — the brief's instance #1 has two sufficient explanations at once.

## What ships

- **`hygiene/signal-death.ts`** — classify the exit **disposition** before anyone reads the output: completed / exited-nonzero / **killed** / **never-started**. Killed means output is truncated at an arbitrary point and means *nothing*.
- **`hygiene/run-checked.ts`** — run as a child (no pipeline), assert completion, *then* apply `--deny`/`--require`. Exit codes deliberately distinct: `0` ran and held · `1` ran and found something · **`2` did not run**. The absence of a measurement is not the absence of findings. `--strip-ansi` for the colour trap.
- **`hygiene/lint-no-decide-by-grep.ts`** — refuses the shape in any workflow. **Polarity is the whole rule:** `if CMD | grep -q P` is fail-**open** under a crash (the defect); `if ! CMD | grep -q P` is fail-**closed** and is deliberately **not** flagged — the two live `ollama list | awk | grep -qx "$MODEL"` sites are correct as written and stay. Fires on all 20 sites on main, clean here, floor of 40 workflows so a scope regression cannot report success.
- **`lean-proof.yml`** — all 20 gates rewritten. **`gate.yml`** — the lint wired in next to the credential-hoist guard.
- **`lint-typescript.ts`** — the pre-existing retry-on-signal stays (a bounded retry against a genuinely nondeterministic *environment* is defensible) but can no longer be **silent**: the success path now says the first attempt died and on what signal. **A retry bounds duration, not correctness.** Given 147 crashes, a crash nobody records is a point missing from the series that would have found the machine sooner.

## It happened to this PR, twice, while writing it

**1. My first PR body lost its own AgencySignature block.** It quoted `run-checked.ts`'s output, which contained a line beginning `---`. That is a **patch boundary** to `git interpret-trailers`, which stopped parsing there and found **no trailers at all**. Caught by running `git interpret-trailers --parse` against the *posted* body rather than assuming it was fine. `run-checked.ts` now uses `***`; reverting fails three tests.

**2. Fixing that exposed a vacuous test of my own.** Bun colourises console output **even when stderr is a pipe**, so every diagnostic line arrived prefixed with an SGR sequence. Two consequences:

- `line.startsWith("---")` **could never fail** — a vacuous test, inside the change whose subject is vacuous checks, caused by the very ANSI trap the change documents.
- **GitHub Actions would not have rendered the `::error::` annotations at all**, because Actions only recognises a workflow command when the line *begins* with `::error::`. A guard whose alarm does not render is most of the way back to no guard.

`run-checked.ts` now writes to `process.stderr` directly; reverting to `console.error` fails the annotation test. Both mutants were run and both restore clean (29 pass).

**3. One more live crash, on the final typecheck before committing:**

```
Args: "bun" "node_modules/typescript/bin/tsc" "--noEmit" "-p" "tsconfig.json"
RSS: 2.73GB | Peak: 2.73GB
panic: Segmentation fault at address 0x8801174532B8
oh no: Bun has crashed. This indicates a bug in Bun, not your code.
```

exit **133**, zero `error TS` lines; three immediate re-runs exit 0 / 0 bytes. A **wild pointer**, not a null deref. Bun says it is a bug in Bun — on the strength of the 147, I do not believe it. A wild pointer in bun, in CoreCLR's GC, in V8's GC and in `XProtectRemediatorGenieo` in one week is one cause, not four.
