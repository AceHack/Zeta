## Description

## The finding this closes

From the seal-tier PR (#10513): *use-without-extract is not met by any tier and cannot
be behind this port -- `loadShare` returns the share scalar.* Every adapter therefore
carried `usesWithoutExtract` typed as the literal `false`. **This is the port change.**

## The port

`tools/setup/persona-keys/frost-partial-signer.ts`

```
commit(x)                    -> public nonce commitments + an opaque single-use handle
signPartial(handle, package) -> a partial z_i
```

No method returns a share scalar. Alongside it the storage port is split:
`FrostShareAdapter` is store-only; `loadShare` moved to the explicitly-named
`ExtractingFrostShareAdapter` (`extractsScalar: true`, `usesWithoutExtract: false`,
both literal); and the bulk extractor `loadFrostKeyShares` is **deleted** -- it had
zero production callers, so removing it costs nothing and is the strongest statement
available.

## What is achieved vs what is claimed

`createSoftwarePartialSigner` takes an `ExtractingFrostShareAdapter`. **The constructor
signature is the honesty claim:** it can read the scalar, so the scalar is in this
process. What changed is the window size, not its existence.

| path | where the scalar can appear |
|---|---|
| `loadShare` | the caller process, for as long as the caller keeps it |
| software `signPartial` | one function frame in this module |
| hardware `signPartial` | never outside the chip -- **not achieved by anything here** |

Typed, not documented: `usesWithoutExtract: true` is reachable **only** in the union
branch that also declares `exposureBoundary: "hardware-boundary"`. No factory reaches
it (`createNonExtractingPartialSignerStub` throws); **FPS-14 walks every export and
proves it**, so the claim is unmade in fact.

## One round does not suffice (CHECKED)

The binding factor `rho_i` hashes the full commitment list and the challenge covers
`R = SUM_j (D_j + [rho_j]E_j)` -- a participant knows neither when generating its own
nonce. Nonces are born inside `commit()` and never leave; the handle is single-use and
is **burned before any arithmetic**, so a failed `signPartial` cannot leave a reusable
nonce (FPS-7). Two partials over one nonce give `z1 - z2 = lambda*(c1 - c2)*s_i`.

## PKCS#11 cannot compose a partial -- CHECKED against the spec, not inherited

My prior L2 note said consumer HSMs do not do FROST in firmware. That was carried
forward unverified, so it was checked against **PKCS#11 v3.1**:

- No mechanism performs modular scalar arithmetic on a sensitive key and returns the number.
- `CKM_ECDSA` / `CKM_EDDSA` generate the nonce internally and compute the challenge over
  **their own R**, so neither can be bound to the group R.
- Derive mechanisms emit **non-extractable key objects**; `CKM_ECDH1_DERIVE` is a point
  multiply, not `Z_L` arithmetic. `CKM_BIP32_CHILD_DERIVE` (the only additive-tweak shape)
  is a **Thales vendor extension**, secp256k1-only, still a key object.

And the absence is **structural**, which is a better reason than the one inherited: a
partial is an extractable affine function of the secret, so a generic primitive emitting
one becomes a key-extraction oracle on the second challenge against one nonce. Safe
emission requires the token to enforce nonce freshness and challenge binding itself --
which *is* FROST in firmware.

**Consequence for the ladder:** buying HSMs does not buy L2. A YubiHSM 2 at $650/guard
still lands at at-rest sealing, i.e. L1 with better hardware. L2 needs FROST-aware
firmware (programmable applet, extensible open firmware, or a purpose-built device such
as Frostsnap) or the L3 confidential-compute route. Ladder doc updated; I also corrected
its L1 line, which said at-rest sealing "realizes invariant 2" -- it does not.

**No hardware was exercised.** Apple Silicon has a Secure Enclave, not a TPM 2.0, so
`hardware-tpm2` cannot work there at all, and the P-256-only Enclave cannot do Ed25519
partials either.

## The fake stays unmistakable

A partial must verify against the group key or it is not a signature, so a fake `z`
**cannot** be made cryptographically distinguishable -- and pretending otherwise would
be the worse outcome the brief warns about. So the guard is placed earlier: the session
declares `requiredSealTier`, and `signPartial` **refuses to produce a partial at all**
for a tier that is not its own (FPS-17). `combineFrostPartials` refuses a mismatched
partial in both directions (FPS-18). FPS-17b proves the refusal is not vacuous by
showing the fake *can* sign a fake-declared session. The `sealTier` label on a partial
is documented as a misconfiguration guard, not a cryptographic one.

## P0 found in passing, fixed here

`randScalar` (`frost.ts`, `frost-dkg.ts`) and `randCoeff` (`shamir.ts`) defaulted to
`Math.random`, and **every production call site reached that default** --
`frost-ca-custody.ts` passes no `random` to `frostKeygen`, `frostDkgKeygen`, or
`frostThresholdSign`. So the **CA group signing scalar**, the **Shamir coefficients**,
and **every FROST nonce** came from V8 xorshift128+, whose state is recoverable from its
own output. Defaults now use the OS CSPRNG (rejection sampling for GF(257)); the injected
door is untouched so DST replay is unaffected. `frost-csprng-default.test.ts` counts
`Math.random` calls, so a regression fails rather than passing a diff review.

**Residual, filed in `docs/BUGS.md` as P1:** material generated before this commit is
weak and code cannot retroactively fix it. Rotation is a ceremony and needs the human
maintainer; I document it, I do not fire it.
