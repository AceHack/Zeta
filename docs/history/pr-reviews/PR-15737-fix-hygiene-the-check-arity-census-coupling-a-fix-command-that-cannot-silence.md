## Description

## The defect is the coupling

Both check-arity audits ratchet a **hand-maintained** JSON census. A change that adds an assertion must remember to hand-edit a registry file, or `main` goes red. Measured on 2026-08-26, three episodes across **both** audits:

| window | rule | onset | cure |
|---|---|---|---|
| 08-26 14:51:19Z → 20:18:33Z (**5h27m**, 8 failing runs, 0 greens between) | R5 | `880690e6` | `f208f60a`, a one-file **+1/−0** census row — five hours later |
| 08-25 21:48:12Z → 22:02:50Z | R2 | `85b93663` | `d65a8f85` (#15446), by **fixing the test** |
| 08-27 00:37:16Z → open | R2 | `ed28cf9e` (#15718) | still red |

## Is the census derivable? Mechanically yes — and deriving it would be wrong

`--emit-census` already reproduces the file exactly; there is **no human judgement stored in it**, only `path → count`. But the census's *function* is to force an adjudication when the population changes, and that adjudication is nowhere recorded. A CI step that re-derived and accepted would make R2/R5 **a check that cannot fail** — this class's own subject.

So this cuts the coupling at the **judgement seam** instead: everything mechanical becomes one command; the judgement stays deliberate.

## Two live defects, both the coupling rather than the rule

1. **A duplicated key nothing could see.** `frost-hsm-secrets.test.ts` appeared **twice** in the non-equality census — `f208f60a` (#15662) and `0054459b33` (#15646) each added the identical row by hand, hours apart, neither able to see the other's edit. `JSON.parse` keeps the last duplicate and discards the rest **silently**, so every run reported OK while the checked-in artefact was not the artefact the audit describes. Fixed here.
2. **The equality census was missing a row**, so `hygiene:check-arity` was red on `main` — found by *running* the audit, not by reading the check name.

## What lands

- **`check-arity-census.ts`** — one shared substrate for both audits.
- **Canonical form is checked.** The census must round-trip (`parse → serialize → bytes`). Duplicate keys, rows inserted out of ordinal order, and formatting drift all fail here, where before they were invisible. Form only — it never touches the ratchet.
- **The fix command is named verbatim** and drives the **same code path** as the check, so the two cannot disagree — the property `build-graph.ts derive --write` already has and this ratchet lacked.
- **It cannot silence a finding.** `--write` canonicalises, **lowers** and **removes** rows (none of which carries a judgement) and **refuses every raise**, leaving the old value so the ratchet still fires. Accepting a raise is a separate command, `--write --accept-raises`, which prints each site under an explicit banner.
- **The failure names the sites** — `path:line`, the test name, both sides — plus `::error file=,line=,title=` annotations.
- **A toolchain-free step-namer** for the job (21 steps, previously **zero** ids), using only `echo`. The #15692 pattern, one job over.
- **Self-scoping `--drift-check`**, wired into `preflight.ts` for both audits.

### Why `--write` may not raise a count — measured, not assumed

A census row means either **ACCEPT** (adjudicated correct) or **SILENCE** (a true finding made to stop being reported), and the artefact cannot tell them apart. After the two seeding sweeps (`d7a5d2eb`, 109 rows; `049f64b4`, 56 rows) this census saw **ten edits: ten raises, zero lowerings.** A ledger you can only add to is a suppression list, whatever anyone intended. (The other remedy leaves no trace here, which is why that count understates it — #15446 fixed the test, so `FreeTimeAllocation.Tests.fs` appears in no census at all.)

**So the remedy tally, as asked:** of the two clearances I can classify, **one accepted by census row** (#15662) and **one strengthened the test** (#15446); across the whole post-seeding history, **10 accepts, 0 lowerings, ≥1 strengthen**.

## One fact worth recording: does this leg block?

Three readings were attempted from outside and two were wrong, so here is the **structural** answer from the file. `gate-required.needs` names job **IDs**: `matrix-setup, path-filter, build-and-test, lint, lint-typescript, cross-verify, full-verify, test-typescript-hermetic`. The `lint` entry is job id **`lint`**, whose display name is **`lint (semgrep)`** (gate.yml:733/748). The arity checks run in job id **`lint-bash-retirement-inventory`**, display name **`lint (bash retirement inventory + hygiene unit tests)`** — **not in `needs`**, and it has no matrix, so no roll-up rule applies to it either.

The confusion is a **display-name prefix collision**: two different jobs whose names both begin `lint (`. The open-PR census confirms the structural read — `gate=success, arity=failure` occurs twice, and `gate=failure, arity=success` three times. #15661's red gate is explained by **`path filter` = cancelled**, which *is* in `needs` (verified via the check-runs API), not by the arity leg.

**Blast radius, which is the fact that matters:** the arity leg is failing on **15 of 17 open PRs** — `main`'s condition propagating to everything branched from it. Not a per-PR defect; the coupling.
