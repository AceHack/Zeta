## 1. A defect in #15668, with a measured before/after

`k3s-server.nix` and `k3s-agent.nix` both **set** `zeta.k3sDatastorePreflight.enable`, and `k3s-server.nix` additionally **reads** `config.zeta.cluster.{podCidr,serviceCidr}`. Neither imported the module defining either option — `k3s-datastore-preflight.nix` and `cluster-network.nix` are imported only by `common.nix`.

That makes each role module evaluable **only** inside the host aggregate. "Everywhere else" is not hypothetical: every NixOS VM test imports the role module directly and by design, which is exactly why `nixosTest` is not vacuous here — it exercises the shipped file rather than a transcription of it.

`nix eval .#checks.x86_64-linux.<check>.drvPath`:

| tree | `k3s-control-plane-cluster-init` | `k3s-agent-join` |

| `main` (`da6f3ccc02`) | `.drv` | `.drv` |

The regression is confined to evaluation; no shipped behaviour changes, because `common.nix` already imported both modules on real hosts. The fix follows the precedent `k3s-agent.nix` already set for `k3s-join-observer.nix`: the file that owns an option's value owns its import.

## 2. Why the existing two-node test does not cover this

`k3s-agent-join.nix` boots a server and an **agent**. An agent has no datastore, no etcd and no CA — it presents a token and becomes a kubelet. The defect `injected-server-join.nix` was written for is a **control plane** told to join that founded instead, and `--server` on a `role=server` node joins an **etcd** cluster. Different code path, and it had no boot-time coverage.

### `k3s-server-join` — two `role=server` nodes, hermetic

The load-bearing assertion is **not node count**. Two nodes that each founded are also both "up" — that is precisely the state of the two machines on the LAN whose CA founding epochs are twelve days apart. It asserts both nodes hold the **same cluster CA** (sha256 of `server-ca.crt`), the check that told those two apart, plus that the joiner carries the control-plane role label rather than merely appearing in `get nodes`.

It also pins **JoinBlocker 1 from the running system**: preflight `ExecMainExitTimestampMonotonic` < k3s `ExecMainStartTimestampMonotonic`, with both asserted non-zero *first* — a unit that never ran reports `0`, and `0 < anything` would pass while proving nothing.

### `k3s-datastore-preflight-fail-closed` — one node, dirty disk

k3s **ignores** `--cluster-init`/`--server`/`--token-file` when an etcd datastore exists on disk, so a declarative join onto a dirty disk is a silent no-op with `systemctl status k3s` green throughout — the one failure mode here with no symptom at all.

`lint-k3s-datastore-preflight.test.ts` already executes the refusal *script* over fixtures. What no test could reach is whether **systemd honours `before` + `requiredBy` on a boot**. Rewire that unit `wantedBy` and k3s starts anyway, the script still exits 1, and every existing assertion still passes — the vacuity class in unit-file form. The assertion that refutes it is that **`k3s.service` never started**, not that the preflight failed. A canary file inside the seeded datastore turns "IT DELETES NOTHING" from prose into a check.

## 5. THE VM TEST FOUND A DEFECT ON ITS FIRST RUN — and it is the one this PR was written to look for

`k3s-server-join` went red on run `33020639794`, and not for a harness reason:

```
AssertionError: the join endpoint resolves to '127.0.0.1', not to the
founder ('192.168.1.1').
```

`k3s-server.nix` set `networking.hosts."127.0.0.1" = [ "control-plane" ]`
**unconditionally**. On a node `injected-server-join.nix` has pointed at another
cluster, that entry and the real endpoint mapping both land in `/etc/hosts`, the
addresses are emitted in attribute order, `"127.0.0.1"` sorts ahead of any
10./172./192. address, and glibc answers with the first match. So the joining
control plane dialled **its own supervisor** — which joins nothing and founds a
second cluster. That is the defect `injected-server-join.nix` exists to prevent,
reintroduced one layer below it in name resolution, and no eval-level test could
have seen it: the option values were all correct.

**The fix is to stop asserting something false, not to out-order it:**

```nix
networking.hosts = lib.mkIf (config.services.k3s.serverAddr == "") {
  "127.0.0.1" = [ "control-plane" ];
};
```

`control-plane -> 127.0.0.1` is true exactly when the API server that name refers
to **is this node** — i.e. when this node founds. `serverAddr == ""` is nixpkgs'
default, pinned as such by the founding scenario in
`k3s-server-join-eval-test.nix`, and on a `role=server` node it is written by
`injected-server-join.nix` and by nothing else. Relying on entry order instead
would be a guess about glibc *and* about attrset iteration.

**Not VM-only.** `injected-cluster-address.nix` already supplies
`control-plane -> <founder-ip>` on hardware for every node whose segment address
differs from the founder's — which includes a joining control plane — and its own
comment says `k3s-server.nix` "maps control-plane -> 127.0.0.1 **on the
founder**". That sentence was aspirational when written; it is now true, and the
two modules stop contradicting each other.

**Sovereign-by-default is untouched.** `clusterInit = mkDefault true` still
stands, a node flashed with no endpoint still founds, and its `/etc/hosts` is
byte-identical to before. Only the joining branch changes — from silently
founding a rival cluster to failing loudly against an unreachable name if nobody
supplied resolution.

Measured locally (`nix eval`, aarch64-darwin — no `/dev/kvm` here, so the boot is
still CI's to report):

| node | `networking.hosts` |
|---|---|
| founder | `{"127.0.0.1":["control-plane"],"127.0.0.2":["founder"]}` |
| joiner | `{"127.0.0.2":["joiner"],"192.168.1.1":["control-plane"]}` |

All **20** `checks.x86_64-linux` evaluate; `nix flake check --no-build` is green
on the darwin set. The assertion stays exactly where it is and keeps its
falsifier role — make the alias unconditional again and it goes red again.

## 6. `live kind Cilium CNI` — red on `main`, and not for a network reason

Named rather than assumed, because "it also fails on main" does not by itself say
whose it is. The two failures are different and both are in this lineage:

| tree | failure |
|---|---|
| this PR's old head | `0/2 from the pool` against a hardcoded `10.42.0.0/16`, while the derived pod CIDR is `10.143.0.0/17` |
| `main` since `5e196ea244` (#15668) | `error: not a dotted-quad CIDR: "10.143.0.62 /32"` — a **crash**, no verdict at all |

The jsonpath is `{.metadata.name}={.status.podIP}{' '}{.spec.hostNetwork}`, so the
tail after `=` is **two** fields and the second is empty on any pod that does not
set `hostNetwork` — the ordinary case for CoreDNS. `row.split("=")[1]` therefore
returns `"10.143.0.62 "`, and `${ip}/32` on that is not an address.

It was invisible until #15668 because the predicate used to be
`startsWith("10.42.")` — total on any string, so it could not notice that the
string was not an address. Making the containment exact (correct, and required
once the pod CIDR became a derived `/17`) is what exposed the sloppy split. Both
halves are fixed here: `podIpField` takes the token between `=` and the first
whitespace; `podIpInPool` shape-checks the **observed** address and returns false
rather than throwing, because an empty `podIP` is a normal transient and a lane
that dies on one reports nothing — while counting it as not-from-the-pool still
**fails** the check. The **declared** pod CIDR is still validated and still
throws, since a malformed one means the values file is wrong.

**Falsifier, because a five-minute kind bring-up is not one.** Both functions are
exported and pinned by `cilium-kind-up.test.ts` (9 tests, 17 assertions), and the
mutations were **run**, not asserted:

| mutation | result |
|---|---|
| restore `row.split("=")[1]` | **4 fail** |
| drop the dotted-quad shape check | **1 fail** (it throws again) |
| as committed | 9 pass |
