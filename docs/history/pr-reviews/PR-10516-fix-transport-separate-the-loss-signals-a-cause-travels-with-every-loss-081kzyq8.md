## Description

Closes `081KZYQ8KNB087G0R000G8QPRE` (P1) — **step one of three**, and the other two are untouched
on purpose.

## The defect

`lossRate : float` could not carry **what kind** of loss it was, so channel corruption and queue
overflow produced the same number and the same multiplicative decrease. Measured by the BDP link
harness with congestion **structurally zero** (asserted, not assumed): **7.1× throughput lost at
2% corruption, 90× at 10%**.

No threshold repairs that — 5% corruption and 5% congestion are the same quotient. RFC 4653 states
the identity outright: a delayed segment and a dropped segment *"play out in precisely the same
manner."*

## The fix

The scalar is **removed**, not annotated beside a replacement. `nackCount` and
`lossRate(state): number` are gone. A loss arrives as a typed `LossSignal`
(`congestion | corruption | reorder | unknown`, each carrying its sequence numbers); the estimator
counts **by cause**; only `congestionSuspectRate` steers the gap. Same rung-1 move as
`BoundJustification` (#10461) — *a bare scalar is where distinctions go to die.*

## The finding, which is not the fix — read this table first

**The two causes are separable in the MODEL and not at the RECEIVER.** New experiment 7
(`attributionPoint`, `UBL-15`, demo table `UBL-I`):

| scenario | reported missing | attributed | unknown | attributable |
| --- | --- | --- | --- | --- |
| corruption 10% | 946 | 0 | 945 | **0.0%** |
| congestion, 2× offered | 9901 | 0 | 9881 | **0.0%** |
| jitter 5ms → reorder | 4018 | 4008 | 0 | **99.8%** |

A queue drop and a corrupted frame reach the receiver as *the same event*. There is no integrity
check (`081KZYP1X3B087G0R001EZ37PQ`) and no queue/delay signal — so rather than document that, the
`congestion` and `corruption` cases require evidence values branded with **unexported** `unique
symbol`s and are **unconstructible**. `ULT-31` fails the moment somebody adds a minting function,
which is the intended trigger. A four-case taxonomy whose empty cases can be filled in by assertion
is worse than a two-case one, because it *looks* like the distinction was made.

**This promotes `081KZYP1X3B` from filed to on the critical path.** The 7.1×/90× is not recoverable
by any control-law change; it is gated on making corruption perceivable.

## Results, split by door

**Reorder door — closed substantially.** A reported-missing sequence number that then *arrives* is
retracted, and the decrease it caused is **recomputed** without it, reversed only if it no longer
holds (`ULT-28` is the negative control: retracting 1 of 4 losses leaves a still-valid backoff
standing).

| paced throughput, 5ms jitter, zero loss | before | after |
| --- | --- | --- |
| throughput | 20.9 pkt/s | **466.2 pkt/s** |
| collapse factor | 47.7× | **2.14×** |

**Corruption door — unmoved.** `UBL-10` still reports 0.139 at 2% and 0.010 at 10%. Every one of
those erasures is `unknown`, and unattributed loss keeps the classical backoff — deliberately.
Refusing it would be *assuming corruption*: the same error with the sign flipped, whose failure mode
is congestion collapse (Jacobson 1988) rather than lost throughput. Every anchor here *adds a
signal* (ELN, BBR's rate model, RFC 4653's dupthresh); none simply stops responding to loss.

**Control preserved.** `UBL-8`: under loss that genuinely *is* congestion, Jain **0.976** at **79%**
utilisation. The controller is still a congestion controller.

## Costs, named rather than absorbed

- **NACK volume doubles under reordering**, 4.7% → 9.4% (`UCH-16`) — the retraction is a second
  broadcast, so the amplification bound this module guards (the 3,333,337× incident) is now 2
  messages per in-window gap. No new peer-controlled lever: a retraction is only emitted for a
  sequence number this receiver itself reported.
- **A peer can claim `reorder` to suppress a sender's backoff.** The data path is unauthenticated
  and could already fabricate NACKs to *cause* backoff. Same hole, opposite sign, not closed here.

## Ordering held

`gapMs` is still unwired (`UBL-14` asserts the send path never mentions it) and the estimator still
evaluates against a partial window (`081KZYN37T`, re-pinned in `ULT-10b`). The residual 2.14× is
*because* of the second one — a retraction takes one propagation delay, and a partial-window
evaluation can fire before it lands. That is the ordering argument as a number.
