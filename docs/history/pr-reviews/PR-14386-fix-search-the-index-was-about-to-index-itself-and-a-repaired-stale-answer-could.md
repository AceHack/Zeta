## Description

## Two defects in #14359, both found by reading the output rather than the code

The first post-merge query on `main` returned `db/search-index/inverted/files.txt` as a hit for `landauer`. Not *wrong* — the file does contain the string — but not an answer anyone wants, and pulling on it found two separate faults.

### 1. The index was about to index itself

Seven of the artifact's own files sit **under** the 512 KiB blob cap:

| file | bytes |
|---|---|
| `terms-q.jsonl` | 339,264 |
| `terms-j.jsonl` | 307,416 |
| `terms-z.jsonl` | 261,913 |
| `terms-y.jsonl` | 205,857 |
| `terms-x.jsonl` | 173,144 |
| `high-df.jsonl` | 57,366 |
| `manifest.json` | 10,165 |

So the next scheduled rebuild would have indexed the previous one: **every term in the index becoming a term _in_ the index, every path in `files.txt` a hit for itself**, and the artifact growing each cycle for no retrieval value. The large shards were excluded only by the size cap — **luck, not design**: `isIndexablePath` returned `true` for all 40 of them.

`db/search-index/` is now an excluded tree, with that measurement recorded beside it as `EXCLUDED_TREES` requires.

### 2. A repaired stale answer could disagree with a fresh one — the worse one

`isIndexablePath` answers from the **path** alone. The builder also applies a **blob-size cap**, which needs the size at the rev. So the changed set admitted files the index would never contain, the verifier `git grep`ped them, and **a stale query returned a hit that a fresh query does not** — the same question with two answers, decided by how stale the index happened to be.

That is precisely the class of defect this tool exists to eliminate, and I built it in. It is also how `files.txt` surfaced above: it changed in the merge, passed the path predicate, and got grepped — while the builder had skipped it for size.

The fix splits one set into the two it always was:

| set | role |
|---|---|
| `changed` | what to **withdraw**. Wider on purpose — a file deleted, or grown past the cap, must lose its hit, because a fresh index would not list it either. |
| `verifiable` | what to **read**. Matches the builder's corpus exactly, size included. |

## Falsifiers — 28 pass, three new, each proven to discriminate

| mutation | result |
|---|---|
| self-exclusion removed | **red** |
| verify set collapsed back onto the retraction set | **red** (2 tests) |

The new tests: the self-exclusion; a **repaired-vs-fresh agreement** test over a corpus that gained both an oversize and a small file, asserting the two answers are *equal*; and a test that a file which grew past the cap appears in `changed`, not in `verifiable`, and loses its hit.

## Why this is a PR and not a quiet amend

Both faults were *shipped*. Recording them where they happened is the point — the README now carries all four defects this index has had, and every one was found the same way: **by checking the output against ground truth instead of trusting that the code said what I meant.**
