## Description

`pnpm@10.15.1` sat in **root** `devDependencies` while the repo's `packageManager` is `bun@1.3.13`. Every `bun install` call site therefore fetched and extracted the pnpm tarball — and `error: Fail extracting tarball for "pnpm"` flaked **four times in one day** across unrelated jobs (PR #10353 `test`, `Deploy to GitHub Pages`, `drift-sweep`, PR #10365 `test`).

Exactly **one** consumer needed it. Now exactly one pays for it.

## What changed — 4 files, zero workflow YAML

- **`package.json`** — dropped `"pnpm": "10.15.1"`.
- **`bun.lock`** — regenerated. Diff is exactly 3 lines, no collateral churn.
- **`identity-dla-pages-build.ts`** — the dangling-resolution failure mode, fixed in the same commit. It no longer resolves `repoRoot/node_modules/.bin/pnpm`. It reads the **site's own `packageManager` field** as the single source of truth and provisions that exact pnpm via `bun x`, spawned from `process.execPath` — the bun binary already running the script. Nothing is required on `PATH`, so one code path serves laptop, devcontainer and runner (§24). `ZETA_PNPM_BIN` is an escape hatch; `PATH` is deliberately **not** probed, because accepting an ambient pnpm would reintroduce the version drift this removes.
- **`tools/setup/manifests/apt`** — corrected a stale comment claiming `asc` arrives via `pnpm add -g` and that pnpm is "already in mise". Neither was ever true.

**Correctness side effect:** the Pages build now runs **pnpm 10.4.1** — the version the site declares and locked against — instead of the root's drifted 10.15.1.

## Path filtering was rejected, and checking was the right call

Three independent reasons **not** to filter:

1. `paths:` applies only to `push`/`pull_request`. `pages-deploy.yml` also fires on `schedule: */15` and `workflow_dispatch`, where GitHub ignores `paths:` entirely — and the scheduled runs are the bulk of the residual exposure. Near-zero benefit.
2. The workflow deploys the **whole** site — book in 10 languages, eBooks, llmtv, PWA, identity-dla. Filtering the push trigger to `demo/identity-dla-site/**` would stop deploying book and llmtv changes. That is exactly the "worse than the flake" outcome.
3. Conditionally skipping just the identity-dla *step* is also unsafe: `actions/deploy-pages` republishes `./dist` wholesale, so a run that skipped the build would upload a `dist` missing that subtree and 404 it — and per the workflow's own comment, **the schedule exists precisely to restore a complete artifact after the book 404'd**. Conditional skip would break the thing the schedule was added to fix.

## Exposure — my count was wrong, corrected upward

I estimated 19 call sites (16 frozen + 3 bare). There is a **17th** frozen call inside a multi-line script block at `lockfile-healer.yml:117`, so the denominator is **20**.

All 20 fetched pnpm before. **Now 20 of 20 stop**, with a single on-demand fetch remaining on the Pages path only.

Run-weighted — the number that actually matters — sampling the last 200 workflow runs: pnpm-fetching jobs totalled ~90 (gate at 17 runs × 3 sites dominates), of which Pages was 6. **~93% fewer fetch events.**

## Verified vs not verified

**Verified locally** (network available): `bun run pages:build` green end to end, artifact present at `dist/demo/identity-dla-site`; build log confirms `Done in 14.9s using pnpm v10.4.1`, `pnpm check` (tsc) and vite build pass; `bun install` reported `1 package removed` and root `node_modules/.bin/pnpm` is now absent — so the old code path would genuinely fail, confirming the dependency was load-bearing. `tsc --noEmit`, `eslint`, `prettier --check` clean. The typecheck gate caught a real `noUncheckedIndexedAccess` bug in the first draft.

**Not verified, stated plainly:** behaviour on `ubuntu-latest` (tested on darwin with bun 1.3.14; CI pins 1.3.13 — `bun x` exists in both, but the CI path is untested); the devcontainer leg; Windows (the old `pnpm.cmd` branch was removed since `bun x` picks the platform binary itself — likely more portable, untested).

**And the honest limit: the residual flake is contained, not eliminated.** `bun x` uses the same bun tarball-extraction code path that produced the failure. The Pages path can still hit it.
