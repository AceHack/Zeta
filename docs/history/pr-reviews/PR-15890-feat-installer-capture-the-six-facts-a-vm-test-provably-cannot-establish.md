## Description

The hardware-remainder doc §5 names six things as HARDWARE-ONLY, each with a
reason, under the house sentence "X is a measured fact, not a declared one."
Today all six live in PROSE. Nothing captures them — so when a machine is
flashed, the answers exist only in whatever a person happened to look at, and are
gone by the next boot. With two GPU boxes waiting to be flashed, that is the gap
worth closing first: the artifact has to exist before the hardware does, or the
first boot teaches us nothing we can keep.

FIVE ARE PROBE-ABLE. ONE IS NOT, AND SAYING SO IS THE POINT.

    §5.1 real NIC / link        PARTIAL  carrier + negotiated speed readable;
                                         switch behaviour under load is not
    §5.2 serial console         YES      a UART is present or it is not
    §5.3 power-loss durability  NO       needs power physically cut mid-write
    §5.4 internal vs USB disk   YES      sysfs `removable`
    §5.5 secure boot enrolment  YES      EFI SecureBoot / SetupMode
    §5.6 TPM presence           YES      device node + tpm_version_major

§5.3 goes to `unmeasured` WITH ITS REASON and stays there, on a fully-probed host
too — there is a test that fails if it ever disappears. A meter whose product is
the measured/unmeasured partition has to be willing to leave a row empty; the
alternative is a plausible number nobody can defend, which is worse than a gap
everybody can see.

ABSENT AND FALSE ARE DIFFERENT ANSWERS, and that is the property the module lives
on. A probe reporting `no` when it could not look turns "we never checked whether
this box has a TPM" into "this box has no TPM", and the second is a claim someone
will act on. Hence `Tri = yes|no|unknown` everywhere, and a test that a host with
no sysfs answers `unknown` on every row while NAMING each absence in `unmeasured`.
The distinction is real, not pedantic: `/sys/class/tpm` present-but-empty is a
genuine `no`, and it is tested separately from `/sys/class/tpm` absent.

TWO PLACES A PLAUSIBLE WRONG ANSWER WAS AVAILABLE:

  * EFI variables carry a 4-BYTE ATTRIBUTE PREFIX, so the byte answering "is
    Secure Boot on" is the FIFTH. Reading byte 0 returns the attributes — usually
    6 — and looks like a perfectly good answer. That is why it is a named
    function with its own test rather than an index inside a conditional.
  * sysfs reports speed `-1` for "no link". Coercing that to 0 would publish a
    measured speed of zero. It is `null`.

EVERY READ IS INJECTED through `HardwareProbe`, so the module is a pure function
of its inputs, the tests drive fixture trees rather than the machine they run on,
and it degrades honestly on a laptop (§13 noninterference, §7 DST). No timestamp,
so two emissions on one unchanged host are byte-identical (#6 idempotency) — which
is what lets a later boot prove nothing about the hardware changed.

It DECIDES nothing. Nothing gates on it, exactly like `host-capability-vector.ts`
whose `unmeasured` discipline this follows. A fact that gates before it is trusted
is a fact nobody got to check.

Written with raw control bytes in the EFI fixtures the first time — 19 NULs in
the source, the third instance of that class today and the one my own memory entry
warns about. Here a control character genuinely IS required, so the rule applies
in its other form: write the escape, then verify the bytes. `audit-no-raw-nul-in-source`
clean.
