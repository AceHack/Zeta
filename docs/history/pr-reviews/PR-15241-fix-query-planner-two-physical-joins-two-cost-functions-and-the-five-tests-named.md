## Description

fix(query-planner): two physical joins, two cost functions -- and the five tests named after formulas they never asserted

`ZSet.join` is a HASH join (Dictionary over `b`, probe with `a`). `IndexedZSet.join`
is a SORT-MERGE join (one walk over two key-sorted runs). `Plan.fs` gave them the
IDENTICAL formula and `EstimatedCpuNanos` was a function of row counts alone, so
`cost(join) == cost(indexedJoin)` for EVERY possible input. A planner consulting that
model could never prefer one -- which is precisely the choice Selinger et al. 1979
exists to make.

DEFECT 1 -- the two joins now have genuinely different cost functions:

  hash        = build * 60 + probe * 30 + out * 40
  sort-merge  = sort(left) + sort(right) + (left + right) * 10 + out * 40
  sort(n)     = if already ordered then 0 else n * ceil(log2 n) * 12

The hash cost is asymmetric in its two inputs (build side charged more than probe --
a random-write insert vs a lookup), which is the property that lets a planner advise
a side swap. The merge cost is symmetric (a merge walk has no build side) and is
dominated by whether the order already exists.

`IndexedZSet` is sorted BY CONSTRUCTION -- a materialised interesting order in
Selinger's sense. `sortNanos` prices it at exactly zero. The order is NOT free
overall: `indexWith` is now charged the sort that establishes it, once, so the model
says what is true -- an index pays off on REUSE, and indexing both sides for a single
join is more expensive than just hash-joining them.

DEFECT 2 -- `Plan join estimates product-over-max` asserted, in full,
`plan.Count |> should be (greaterThan 0)`. Four siblings were identical. That is why
a mutation run setting join estimates to `999999L` left 34/34 green. It is worse than
an absent test: the NAME reads as the cost model's falsifier. Eighteen tests in
`Plan.Branches.Tests.fs` now assert the formula their name claims, against the actual
input estimate rather than a hardcoded constant, plus a new
`Plan.CostModel.Tests.fs` carrying 16 falsifiers for the access-path choice. Each
names the mutant it kills in its comment.

DEFECT 3 -- `Catalog.fs` held no statistics, so the cost model was a formula over
nothing. New `CatalogStatistics.fs` carries `NCARD` (row count) and per-column
`ICARD` (distinct values), each paired with a `StatSource` provenance. Absent
statistics degrade to NAMED fallbacks (`Plan.DefaultSourceRows`, "assume every key is
unique") labelled `DefaultNoStatistic`, and provenance folds weakest-wins through the
plan -- a formula over a default IS a default, and `Explain` prints `stats=default`
so a human can see it. Statistics persist on the catalog metadata table under
`stat:rows:` / `stat:ndv:` / `stat:src:` prefixes; `ensure` does not retract them
(schema is the hub, statistics the satellite -- DV2.0 #5).

The shipped HLL sketch is deliberately NOT wired in. HLL merges by `max` with no
decrement, so on a retracting DBSP stream it counts keys-ever-seen; distinct-values
sits in the join formula's DENOMINATOR, so that deflates estimates monotonically --
a planner that gets quietly more wrong the longer the stream runs. The refusal and
its reason are written into `CatalogStatistics.fs`.

Register: everything stays `unmetered`, stated in the code. The nanosecond weights
have never been calibrated; what is earned is their ORDERING, not their magnitudes.
And per Leis et al. 2015 and their 2025 retrospective, cost-model error is dwarfed by
cardinality-estimation error -- this buys operator CHOICE, not speed.

Anchors (Beacon): Selinger, Astrahan, Chamberlin, Lorie & Price, SIGMOD 1979 (access
paths over catalog statistics; interesting orders) - Shapiro, TODS 11(3), 1986
(hash vs sort-merge in main memory) - Graefe, ACM Computing Surveys 25(2), 1993 §4 -
Leis, Gubichev, Mirchev, Boncz, Kemper & Neumann, PVLDB 9(3), 2015 + PVLDB 18(12),
2025. Design doc: PR #15213.
