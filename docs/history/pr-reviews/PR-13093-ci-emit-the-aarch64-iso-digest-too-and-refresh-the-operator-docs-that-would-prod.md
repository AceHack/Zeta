## Description

**R25** from the USB design ledger. The x86_64 job writes a per-ISO `<iso>.sha256` sidecar; **the
aarch64 job emitted neither digest nor signature**, so the verify gate could never be satisfied for an
arm64 image — **the Pi rung had no integrity story at all.**

Per-ISO sidecar rather than a bare `SHA256SUMS`, and the reason is measured: an unrelated
`~/Downloads/SHA256SUMS` **belonging to Bitcoin Knots** was found and parsed by the gate on the
maintainer's machine, which then refused while printing 28 bitcoin filenames. **A per-ISO sidecar
cannot be hijacked that way.**

One deliberate divergence, not drift: the aarch64 **artifact name is fixed** rather than derived,
because both jobs emit an identically-named ISO and **two artifacts in one run may not share a name.**

## Confirmed before landing: this does not regress the ISO build

This agent found the **read-only-Nix-store bug independently** and wrote the sidecar to `RUNNER_TEMP` —
so the file already carries the same fix #13063 landed. **Two agents, one measured CI failure, the same
one-word conclusion.** `actionlint` clean.

## Cosign on aarch64 — reported, not done, and the argument against is the point

It needs `id-token: write` at job scope — a permissions elevation wanting human sign-off. **But the
recommendation is to not do it yet even if approved:** `cosign verify-blob` **appears nowhere in
executable code**, only in comments and step summaries.

> **Signing a second architecture that nothing verifies buys provenance theatre and one more
> OIDC-capable job. Build the verifier first, then elevate both.**

## The runbooks were actively dangerous, not merely stale

`zflash-end-to-end.md` had **zero** occurrences of `sha256` — and worse, its documented CP-1 correction
has the operator **rename** the artifact, while the integrity check matches on **exact basename**. **So
following the runbook converted `manifest-missing` into `iso-not-in-manifest`.** And the preflight's
failure-signature list **did not include the refusal an operator hits first.**

The rename was **adjudicated rather than deleted**, against my own initial framing: **the rename is
load-bearing**, because the stamped filename carries the **arch** and discovery picks newest-by-mtime —
**removing it trades a refusal for a wrong-arch write.** The lookup gives instead, narrowly.

## Deliberately held back

The zflash **source** half — shared supply path, Linux and Windows integrity gates, `MIN_ISO_BYTES`
de-duplication, entry-point parity audit — **touches files in flight in #13085** and would conflict. It
lands as its own change once that merges. **Recorded here so the split is visible rather than looking
like the parity work was dropped.**
