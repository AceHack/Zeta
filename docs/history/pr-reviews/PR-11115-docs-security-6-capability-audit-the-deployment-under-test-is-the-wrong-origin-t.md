# Notes

**The credential finding (§6.6), plainly.** There is **no GitHub credential in browser storage and no PAT in the PWA** — verified by reading source. The PWA's only GitHub calls are unauthenticated public reads; `localStorage` holds a public credential ID and the signed delegation, neither of which is a GitHub credential. But §6.6 asks what the credential *is*, and there are **three legs with three answers**:

| leg | credential | class |
|---|---|---|
| commit + push | workflow `GITHUB_TOKEN` (`contents: write`) | **passes** — Actions App installation token, repo-scoped, job-lifetime |
| open the PR | `ZETA_PR_ARCHIVE_TOKEN` | **UNKNOWN** — secret values are unreadable by design; the "Pull requests: write" phrasing does not discriminate PAT vs App |
| create the issue | local `gh` credential store | **fails in spirit** — `gh auth login` yields a broad user-scoped CLI OAuth token, not a scoped App installation token |

The `gh` leg is bounded and I say so: the only action is `gh issue create`, the relay is loopback-bound and origin-checked, and **nothing the issue says is trusted** — the workflow re-verifies assertion, device signature, registry, freshness and path policy first (DDP-3 is exactly that attack, refused). Low severity, but an honest §6.6 answer is "a user-scoped CLI token on the operator's laptop," not "a fine-grained App installation token."

**Gaps worth acting on.**
1. **§6.5 breaks at `→ descriptor`.** The receipt records credential, device and patch digest but not `delegationDigest` — which is already computed and verified, and would pin the whole descriptor in 32 bytes. One field, schema bump to v4, and §6.5 becomes checkable rather than aspirational. Cheapest real improvement here.
2. **Zero receipts exist on `main`** (contents API → 404), so the whole path is **unexercised end-to-end**. Every end-to-end claim is `DOCUMENTED-UNVERIFIED` regardless of what any unit suite reports.
3. **§6.1 `maxPatchBytes` has no test** — a check with no failing mutant. **T-1** closes it, needs no capability and no biometric, and could be written today.
4. **Bumping the registry `sequence` does NOT revoke a device delegation** (`<=` on the delegation path vs `===` on the v2 proposal path). Intended, but an operator reaching for a sequence bump as an emergency revoke would believe they had revoked and be wrong.

**Credit where due:** the capability half is substantially better built than the checklist's warning anticipates. Scope is a *type* enforced at the executor (not the UI), the device key is non-exportable P-256 so this is proof-of-possession rather than a bearer token, the capability's only action is `stage-review-branch` (merge authority stays with required checks), and it cannot rewrite its own authority — `.github/`, `docs/security/`, the verifier and the PWA are all protected paths.

**Six staged tests (§4 of the doc)** cover §6.2 TTL, §6.3 revocation immediacy, §6.4 cross-client replay, both §6.6 credential identifications and the §6.5 descriptor gap — each with the request, the expected refusal, and the mutation that proves it is not vacuous. They are blocked on Aaron's biometric, not on effort.

**Unrelated but noted:** a `manus-connector` App is installed org-wide (`repository_selection: all`) with `contents: write`, `administration: write` and `organization_personal_access_token_requests: write`. Nothing in this flow uses it; flagged for a separate look outside this §6 scope.
