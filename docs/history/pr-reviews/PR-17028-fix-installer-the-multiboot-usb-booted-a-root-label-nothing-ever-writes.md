## Description

## B6 — the multiboot stick cannot find its own root

The committed GRUB menu boots:

```
linux (loop)/@KERNEL@ findiso="$isofile" root=LABEL=ZETA_MULTIBOOT
```

The assembler formats the stick with:

```
mformat -F -v ZETA_MB ...
```

**A FAT volume label holds at most 11 characters. `ZETA_MULTIBOOT` is 14.** So it is
not merely the wrong label — it is a label that **cannot be written by anything**, and
stage-1 was told to find its root on a device that can never appear.

The whole image is a single FAT32 filesystem with the ISOs under `/boot/iso`, so the
label GRUB needs is exactly the one the assembler writes.

## Why it survived review

The two constants lived in **different trees** — a `.cfg` under `full-ai-cluster/` and
a `.ts` under `src/` — and nothing compared them.

## Fix

`grub.cfg` boots `root=LABEL=ZETA_MB`, and the label is now **exported** from
`assemble.ts` as `MULTIBOOT_FAT_LABEL` so it has one home.

## Falsifiers — both mutation-checked

| test | what it pins |
|---|---|
| the label GRUB boots is the label the assembler writes | reads the committed `grub.cfg`, compares every `root=LABEL=` against the exported constant — they cannot drift apart again |
| the label is writable as a FAT volume label at all | the ≤ 11 character property, which is what made the old value *impossible* rather than merely wrong |

Restoring `ZETA_MULTIBOOT` fails these two and **only** these two (**15 pass / 2 fail**);
with the fix, **17 pass / 0 fail**. `tsc --noEmit`: 0 errors.

## Scope, stated honestly

- Repairs the **multiboot** path only.
- The **single-ISO** path was never affected — it uses the ISO9660 `volumeID`
  `ZETA_INSTALL` (12 chars, legal there; 32-char limit), which also drives the
  installer's refuse-to-wipe-myself guard.
- **Unverified:** no multiboot stick has been built and booted from this change. The
  guard proves the two constants agree, not that the stick boots.
