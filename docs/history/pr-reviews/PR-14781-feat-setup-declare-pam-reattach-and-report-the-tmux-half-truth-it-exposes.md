## Description

Follow-on to #14753. Two halves: a one-line stopgap that unblocks Aaron today, and the design finding it is a specimen of.

## The defect

Touch ID sudo is **inert inside tmux** on the maintainer's host right now, and #14753's verifier said `DURABLE` anyway. `pam_tid` is configured; `pam_reattach` is absent from both Homebrew prefixes. Without it the prompt cannot appear inside a multiplexer — the shell agent work actually runs in — and sudo silently falls back to the password. Certifying the config as durable while the factor does nothing there is telling half the truth, which is the same shape as everything else this week.

## Half 1 — the stopgap, and it is labelled one

One line in `tools/setup/manifests/brew`, which `tools/setup/macos.sh` already walks (step 3). So `install.sh` installs it and **nobody types `brew install`** — which was the actual ask. No new surface, no `declarative/` directory, no Brewfile, no `from-brew.ts`.

Checked rather than assumed:

- **The formula**, against the Homebrew API: `pam-reattach` 1.3, `homebrew/core`, MIT, zero dependencies, bottled arm64 back to big_sur.
- **The parser**, using `macos.sh`'s own awk: the row emits exactly `pam-reattach`, and the manifest now yields 26 formulae.
- **Bare, not `tier=`-tagged.** brew's parser reads `tier=` (`zeta_tier_of_line`); apt's passes the whole line to `apt-get`. `PR-10083` is the row that broke the ubuntu install test by tagging one. Untagged = slim = every host, which is right for a 50 KB module with no deps.
- **Not mirrored into `apt`/`windows`.** A PAM-module-for-Aqua has no Linux or Windows meaning, and a row that silently no-ops on another OS is a declaration that constrains nothing.

## Half 2 — the verifier now reads the manifest

The declaration is **checked, not hoped for**:

- declared **and** missing → `error`, RED. That is install drift.
- **un**declared and missing → observation only. Nothing promised it.
- a test asserts the real `manifests/brew` still declares it, so deleting the row fails a test rather than silently downgrading the check to an observation.
- it parses the manifest the same way `macos.sh` does — two parsers for one fact can disagree.

New output line, and `DURABLE (RED)` is now a reachable, correct state:

```
Touch ID for sudo: DURABLE (RED)
  Touch ID works in tmux    : NO
  [x] pam_reattach is DECLARED in tools/setup/manifests/brew and is NOT installed...
      Fix by re-running the declarative setup: tools/setup/install.sh
```

**Proofs** (fixture tree, never his `/etc`): idempotency `cmp` rc=0 with `already correct`; revert-deleted RED; **new** — reattach removed → `DURABLE (RED)`, restored → GREEN. 35 tests pass, `tsc` 0, `eslint` 0.

## The design finding

`docs/research/2026-08-24-granular-tool-dependencies-*.md`. `pam-reattach` is a good specimen: **exactly one consumer** (`touchid-sudo.ts`), and the only place to declare it is a list every macOS setup installs in full — 26 formulae, so a job that only typechecks TypeScript installs `agda`, `emscripten`, `llvm` and now a PAM module. That is the monorepo union-of-everything arriving in the dependency graph.

Measured, not assumed:

- **ace has the per-unit graph and it is pointed at the other half.** `deps.ts` has `DependencyNode` / `dependsOn` / `resolveGraph` / temporal versions — and one data file in the whole tree (`examples/helm-dependency-graph/`). The tool side has 20 flat manifests and no graph. **The app side got the graph; the setup side did not.**
- **It cannot carry tool deps as-is.** `DependencyNode.chart` is *required* and `outputs.consumes.target` is a Helm values path. `dependsOn` + the reachability walk *do* generalize and should be lifted to an interface rather than copied.
- **`capability-manifest.ts` is not the carrier.** It models what a package may **do**, not what it **needs**. Conflating them yields a system where declaring a dependency grants an authority.

**The unit is derived, not declared** (Aaron): imports, includes and invoked command names *are* the declaration — a manifest can drift from the code, an import cannot. Imports are cheap per language; **invoked command names are the hard case**, hidden in string literals. Which is why the port matters: a foreign command behind a named effects object is *legible to a graph* in a way a bare `spawnSync` is not. Testability is why `SudoGateEffects` / `realSudoGateEffects()` got built; **declarability is what it turns out to buy.** And **#14727 (merged `7fcae2f28`) is the first instance, not a neighbour** — `resolveElevator("sudo")` turns an undeclared dependency on ambient `PATH` into a declared one on a committed registry. Security and supply chain, same operation.

## A finding about the precedent I was told to copy

Aaron settled storage: commit the derivation. That dissolves `clone-at-tag-stays-sufficient` rather than negotiating with it. The named precedent is `build-graph.json` (87 KB, gated by `build-graph-completeness`). **I read the guard before copying it, and it does not do what the pattern needs:**

- `audit-build-graph-completeness.ts:361` — `JSON.parse(readFileSync(GRAPH))`. It **reads** the committed file and checks three internal-consistency directions against `.github/workflows/`. **It never re-derives from the tree and never diffs.**
- So it enforces **completeness**, not **currency**. A tree that grows a source directory nobody added stays internally consistent and passes.
- `gate.yml` runs the audit; nothing re-derives. A `build-graph:derive` verb and `derivationInputsTouched()` **both exist** and CI calls neither.

Not a contradiction of doctrine — `build-graph.json` is *DEFINED, not CALCULATED* by an explicit 2026-06-07 decision, so hand-authored rows are legitimate there. But **the drift guard the derived-dependency design depends on does not exist yet, while looking like it does.** `bun install --frozen-lockfile` is the model to copy instead: re-derive-and-compare, already caught real drift (#14303), and it is the command developers already run with one flag.

**Negative result, recorded because Aaron asked whether we "regressed to advance":** `git log --all --diff-filter=D` over `*zeta-deps*`, `*deps.yaml`, `*.deps` found **nothing deleted**. On that evidence granular tool deps were never built and lost. The search matches filenames, not mechanisms, so it is weak evidence of absence and I have said so in the doc.
