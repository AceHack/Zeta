## Description

Work item: `081KVNYZXQ608QG0R002G35565` — crypto-agile PQ keychain. This is the **first slice**; the item stays open.

## The load-bearing property

A keychain that silently degrades a PQ request to a classical key would let a caller believe it holds post-quantum protection it does not hold. `derivePqKey(mnemonic, typeId)` therefore has **no fallback path of any kind** — unknown type, declared-but-unimplemented type, and experimental type each throw. There is no branch that returns a classical key, a substitute algorithm, or `undefined`.

Two supporting guards:

- Registry `status` is **computed** from whether a `keygen` is present (`statusOf`), so a hand-edited status string cannot claim an implementation that is not there.
- A **post-condition** checks produced key lengths against the registry's verified lengths, so a mis-wired row (e.g. an `ml-dsa-65` row pointing at `ml_dsa44`) is caught rather than silently serving a different algorithm under the requested name.

## What is implemented vs scaffolding

**Implemented** — deterministic keygen via `@noble/post-quantum@0.6.1`, which is **already a pinned root dependency** and already used by `src/Core.TypeScript/crypto/better-git-crypt/crypto.ts`. **No new dependency. No hand-rolled primitive. No lattice code in Zeta.**

| type | standard | path |
|---|---|---|
| `ml-dsa-65` | NIST FIPS 204 | `m/44'/1120'/0'/0'` |
| `ml-kem-768` | NIST FIPS 203 | `m/44'/1121'/0'/0'` |

**Declared and REFUSED** — each blocked on a decision, not on effort:

| type | why deferred |
|---|---|
| `x-wing` | hybrid-by-default is an unresolved **maintainer** policy decision |
| `slh-dsa` | FIPS 205 defines **twelve** parameter sets (SHA2/SHAKE x 128/192/256 x s/f), trading signature size against speed by >2x |
| `adinkra-experimental` | `neverSoleProtection` — refused even if a keygen is later attached |

## What this is NOT

Stated plainly because this is the area where an overstated claim does the most damage:

- **Nothing signs or encapsulates with these keys yet.** This slice produces key *material* and a type registry. It is not a protocol, not a rotation, and not itself a post-quantum security property.
- Deriving an ML-DSA-65 keypair **does not make anything quantum-safe**.
- The word "hybrid" appears only as a **declared, unimplemented** type. There is no hybrid key in this PR.
- Every key still descends from ONE 256-bit BIP-39 seed. HKDF expansion does not create entropy and is not claimed to; that is the standard BIP-32/SLIP-0010 tradeoff the classical keyring already makes, stated explicitly rather than left implicit.

## Open maintainer decisions (surfaced, not decided)

1. **Hybrid-by-default?** Scope item 3. Protocol decision with interop consequences.
2. **Which SLH-DSA parameter set?** Picking one silently would be the wrong kind of default.
3. **Coin index assignment** (1120–1124). Unused by anything today, so changing them is currently **free**; once a key at one of these paths is published or trusted it re-keys and is no longer free.

## Test vectors — which kind

- Length assertions use the **published** FIPS 203/204 parameter sizes (ML-DSA-65 pk 1952 / sk 4032 / sig 3309; ML-KEM-768 ek 1184 / dk 2400 / ct 1088).
- The two byte-lock digests are **SELF-GENERATED and labelled as such** in the test file. They prove determinism and guard our derivation choices (path, HKDF label `zeta/pq/<id>/v1`, expansion length). They are **not NIST KATs** and prove nothing about ML-DSA/ML-KEM correctness — that is `@noble/post-quantum`'s upstream ACVP conformance and is not re-litigated here.
- Seed is the published BIP-39 all-zero-entropy 24-word test mnemonic — a test seed by construction, never a live key.
