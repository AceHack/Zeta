## Description

`drift-sweep` has failed on **every scheduled run since 2026-08-12T16:55Z** — 30+ consecutive reds, roughly every 30 minutes for a day. Last green: 16:25Z. This is the source of the red jobs.

## The failure

From the retraction-actuator step:

```
actuator: BD001 open 0 consecutive tick(s) at tick 239
error: Command failed: git rev-list e9fcfbece..c93b0c52
fatal: Invalid revision range e9fcfbece..c93b0c52
```

`retraction-actuator.ts:163` walks `git rev-list ${iso.greenHead}..${iso.redHead}` to find candidate commits between the last known-green head and the red one. **`actions/checkout` defaults to a depth-1 clone**, in which neither SHA exists, so the range is unresolvable.

## Why it passed before and then didn't

While the actuator was idle with `greenHead == redHead`, the range was trivial and a shallow clone could answer it. The moment main advanced far enough that `greenHead` fell outside the single-commit window, every subsequent run failed identically — which is why it went from 100% green to 100% red at one instant rather than degrading.

## The `git fetch origin main` below cannot rescue it

Fetching a branch into a shallow repository **does not deepen history** — it only moves the tip. The step reads as though it re-syncs everything, and that reading is what let the shallow default go unnoticed.

## Proven, not inferred

Both SHAs are valid commits, and the identical range resolves to **4 commits** in a full clone. The SHAs are fine; the clone was not.

## Fix

`fetch-depth: 0` — which **six other workflows in this repo already set** for exactly this reason (`agent-reviewer`, `pr-archive-on-merge`, `context-cost-trend-cadence`, `manifesto-citation-snapshot-cadence`, `build-ai-cluster-iso` ×2). `drift-sweep` was the exception, and it's the one workflow that runs the actuator.
