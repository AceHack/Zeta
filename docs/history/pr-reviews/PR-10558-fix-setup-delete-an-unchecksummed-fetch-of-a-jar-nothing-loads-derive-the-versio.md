## Description

## What

Closes `081M001E114087G0R001AZF4KD`. **An installer fetched a jar nothing loads, unchecksummed, from a URL whose bytes move -- and the docs named a version nothing runs.** Both defects were surfaced by #10548 while pinning the TLC invocation; both are the same shape, an artefact that reads as authoritative and is not.

## Does anything read the downloaded jar? No

`tools/setup/manifests/from-url` wrote `tools/tla/tla2tools.jar` and `tools/alloy/alloy.jar`. Every runner opens the **committed** jars instead:

| consumer | jar it loads |
|---|---|
| `src/Core.TypeScript/formal-verification/run-tlc.ts:160` | `src/Core.TLA/tla2tools.jar` |
| `tests/Tests.FSharp/Formal/Tlc.Runner.Tests.fs:63` | `src/Core.TLA/tla2tools.jar` |
| `src/Core.TypeScript/formal-verification/run-alloy.ts:90` | `src/Core.Alloy/alloy.jar` |
| `tests/Tests.FSharp/Formal/Alloy.Runner.Tests.fs:44` | `src/Core.Alloy/alloy.jar` |

`rg` over workflows, `.devcontainer`, install scripts and TS: **zero** live readers of `tools/tla/` or `tools/alloy/`. The single consumer was `doctor.sh`, verifying that the installer's own download had happened -- a loop nothing else entered. Three-way parity checked on all three legs, not just CI.

## Delete or checksum? Delete -- a checksum would have been the wrong fix

The destination was unread, which alone settles it. But the URL is also a **mutable pointer**, which is why adding `sha256=` to that row would have been actively wrong. `tlaplus` tags `v1.8.0` as a rolling **prerelease** ("The Clarke release", created 2026-07-15) and re-uploads its assets in place -- `tla2tools.jar` asset `updated_at` is **2026-08-11**. Measured today:

| | sha256 | bytes | banner |
|---|---|---|---|
| committed `src/Core.TLA/tla2tools.jar` | `71546dff...` | 4,357,353 | `TLC2 Version 2026.05.18.174321 (rev: 8ba1027)` |
| the same URL, fetched 2026-08-14 | `ab323b79...` | 4,486,193 | `TLC2 Version 2026.08.11.125311 (rev: 0894c34)` |

Same URL, different bytes, three months apart. A digest pinned to that row goes red on **upstream's** re-upload schedule, not on any change of ours -- a mutable `@v4` tag one layer below the actions.

Alloy is the control case: its v6.2.0 release is genuinely immutable (published 2025-01-09, assets never re-rolled) and `org.alloytools.alloy.dist.jar` hashes `6b8c1cb5...`, **byte-identical to the committed jar**. Its version claim was true. Its destination was still unread, so the row went too.

## What replaces the rows: the rule, not the rows

`from-url` now **refuses** a row with no `sha256=`. This is the established pattern, not a new one -- `from-elan` and `from-autotools-tarball` both already required a pin, and `verifySha256File` already existed in `curl-fetch.ts`. `from-url` was the only fetcher in the repo that never called it.

- verifies **before** the rename, so a mismatch cannot leave bytes at the destination where the next run's existence check would adopt them;
- **re-verifies a destination that already exists** -- present is not the same as correct, and a bare `existsSync` is exactly what waves a poisoned or half-written file through.

The manifest keeps its header stating both questions a future row must answer: what reads this path, and what digest pins these bytes.

## Can the doc version be derived? Yes -- without a JVM

The jar carries its own provenance as plain text in `META-INF/MANIFEST.MF`:

```
Build-TimeStamp: 2026-05-18T17:43:21.13Z
X-Git-ShortRevision: 8ba1027
```

TLC composes its banner from exactly those two fields, so `lint-verifier-jar-provenance.ts` reads them and reproduces `2026.05.18.174321 (rev: 8ba1027)` -- **byte-identical to what `java -cp src/Core.TLA/tla2tools.jar tlc2.TLC` prints**, with no java on the box. It also hashes the bytes. The docs now carry the derived version and sha256, and the lint fails if they disagree. Swap a jar, the docs go red until updated.

That is a different assertion from #10548's, not a duplicate: theirs checks the **runtime banner** of the jar the gate loaded (java, gate time); this checks that **the documentation** matches the committed bytes (no java, hygiene time), and it covers Alloy, which #10548 does not touch.

## Found on the way: the TLA skill taught `-deadlock` backwards

Fixing the stale jar path in `.claude/skills/formal-methods/blueprints/tla-expert.md` surfaced this line:

The committed jar disagrees. `tlc2.TLC -help`:

> **-deadlock** if specified DO NOT CHECK FOR DEADLOCK. Setting the flag is the same as setting CHECK_DEADLOCK to FALSE in config file. When -deadlock is specified, config entry is ignored

So the agent-facing skill was teaching precisely the inversion that produced the divergence #10548 fixed -- a hand-run passing `-deadlock` and reading green is running a **weaker** check than CI. Corrected, along with its jar / spec-dir / runner paths (the specs moved to `src/Core.TLA/` in 2026 and the skill still pointed at `tools/tla/`). Flag *authority* stays with #10548; this only removes a false statement about what the flag means.

## Why this is NOT a second solver-floor registry

`registry/smt2-solver-floor.json` exists because z3 and cvc5 come from the runner's `apt`: ambient version, silent degradation, and a floor is the only lever. The jars are the **opposite** situation -- committed to git, byte-pinned by the diff -- so the question is never "how new is it" but "which bytes are these". Committed binary => derive its identity and check the docs against it. Ambient binary => declare a floor. Recording the distinction here so the two do not get conflated later.

Nothing in this PR touches `registry/tlc-models.json` or `src/Core.TLA/**` (#10548's), which remain the authority on which jar and which flags the gate runs.
