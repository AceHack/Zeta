## Description

## The outage this unblocks

Every open PR is red at **`Install toolchain via three-way-parity script (Unix; GOVERNANCE §24)`** — `install.sh` failing closed on the `tla2tools` digest, which fails every job that installs the toolchain. MEASURED across nine PRs from three authors, 5 to 22 failing checks each; **none of the diffs is the cause.**

Upstream republishes that asset from its own CI. **Four distinct builds measured 2026-09-09** — and two of them **shared a git rev**: same source, different bytes. So a rebuild is often not a new checker, and the digest cannot tell the difference.

## What this ships

**The exception is DATA, per-ref, recorded** — Aaron, 2026-09-09: *"we can just save the exceptions somewhere and let it not break install.sh."*

`tools/setup/manifests/from-url-rolling-exceptions` — one row per ref: `accept=auto` (a closed set of one), `verify=`, `declared=`, `expires=`, `exitcheck=`, `tradeoff=`. One row exists, for `src/Core.TLA/tla2tools.jar`.

**There is no global switch, by construction.** `activeExceptionFor` compares dests with `===` — a row reading `*  accept=auto` matches the literal dest `*` and nothing else. No prefix match, no glob, no env var, nothing for a later agent to find and flip.

### Still fails closed

| situation | disposition |
|---|---|
| rolling row, **no** exception | fails closed (unchanged) |
| rolling row, **expired** exception | fails closed, **and the gate is red** |
| rolling row, exception, `verify` **fails** | fails closed, and the failure is recorded |
| **non-rolling** row, bytes changed | fails closed — a supply-chain event, never a rebuild |
| fetch/transport failure · malformed digest | fails closed (unchanged) |

Two independent refusals guard the non-rolling case: the lint refuses such a row, and the realizer will not look one up unless the manifest row carries `rolling=`.

### The record is the price of the concession

An auto-accept with no record turns a **loud** failure into a **silent** one, which is strictly worse. So every acceptance prints a banner and appends to `.zeta/from-url-rolling-accepts` (untracked, append-only, idempotent):

```
src/Core.TLA/tla2tools.jar  from=bb82311b…  to=8836549e…  when=2026-09-09T22:20:51.771Z  verify=deferred  verdict=not-run  outcome=accepted  expires=2026-12-08
```

`verdict=not-run` is a first-class value and is **never spelled `pass`**. The refusal path records too, which is what keeps `verdict=fail` reachable rather than decorative. It is **not** `from-url-rolling-receipts` — accepting is not measuring, and only `repin-rolling.ts` after a passing re-measure can move a pin.

### The pin does not move — so nothing is laundered

`from-url` still pins the old digest, and `registry/tlc-models.json`, `docs/INSTALLED.md` and `docs/dependency-status.md` still name it and still disagree with the accepted bytes. **Provisioning is unblocked; the verifier claim is not.** `lint-verifier-jar-provenance.ts` is deliberately left unchanged and still reports the divergence.

**So the unblock is PARTIAL and the residue is named:** once install completes, the TLC runs judge the loaded jar against the committed `versionBanner`, so on a rolled build the **TLA+ lane will report a banner mismatch**. That is a true statement and it stays. What changes is blast radius — an install failure fails *every job that installs the toolchain*; a banner mismatch fails *only the TLA+ lane*. Before/after numbers for that are not in hand and are not asserted.

### Expiry is mechanical, not a comment

- `expires=` ≤ 90 days after `declared=`; **past ⇒ inert at install time AND a red gate** (`lint-rolling-exceptions.ts`).
- The row's **premise** has its own falsifier, **run** in the gate: `lint-tla2tools-rolling-premise.ts` goes red when no gate-tier model expects the named-temporal diagnostic (`Temporal property <Name> was violated`) that only the rolling build provides — i.e. when the reason for tolerating a rolling upstream has evaporated.

### Auto-re-measure: tried, measured, declined — with the number

`run-tlc.ts --all` is **52 models in 5m53s** (all 52 passing on the newest build). Six minutes on every `install.sh` is not affordable — and it could not run in the accept path anyway, because it judges the jar against a **committed pin surface the accept path may not move**. So `verify=deferred`, honestly recorded; the `verify=` argv mechanism is built and tested for the next row that has an affordable check.

## Also: a real defect fixed in `repin-rolling.ts`

It **could not re-pin from a tree without the previously-pinned bytes** — every cold CI cache, every fresh clone. The old identity came back `null`, the `versionBanner` restatement was silently never rewritten, and the re-measure then failed on a banner mismatch that says nothing about any model: **MEASURED, 52/52 models "failed" that way, after six minutes.** `identityFromSurfaces` reads the previous identity from the pin surfaces (where it is already written), fails closed on ambiguity, and refuses with **exit 2 before** the re-measure rather than exit 1 after it. Re-run: `rewrote 2 value(s)` per surface where it had rewritten 1.

## THE SECURITY TRADEOFF

Stated plainly, because it is real and the maintainer made this call knowingly.

**While the exception is live, whoever can choose the bytes behind that URL chooses the model checker this repo runs** — anyone who can publish to the tlaplus v1.8.0 release tag, plus anyone who can forge the TLS-terminated response. **An attacker in that position could ship a TLC that reports every model as valid**, and the digest would no longer refuse it. Bounded by the expiry date and by there being exactly one row. What they do *not* get is a green verifier claim: the pin has not moved, so they would additionally need a 52-model sweep to pass and a receipt to be earned.

## What is NOT in this diff, on purpose

Aaron has since given the mechanism its governing idea — **an unpinned dependency is an exception NOBODY GRANTED** — and authorised the full design. The design doc (§2c) carries it, with the **22 ungranted sites measured and named** (12 container base images on mutable tags, 7 package-manager commands, 3 `curl | sh` sites) and the target of **one** register composing with `pinned-refs` (#17166) rather than a third. It is not built here because the repository is red for three authors and the unblock ships first.

**One retraction carried in the doc:** a first draft asserted the re-pin remedy's half-life is shorter than the merge latency. Three digests in three hours is *measured*; that inferred *rate* is not, and the peer who produced it withdrew it after re-measuring. A re-pin may well hold.

## Update: the pin was moved, and what each outcome of the TLA+ lane means

The exception unblocked `install.sh` fleet-wide, then the 52 TLC models correctly
refused the rolled jar with `TOOLCHAIN DRIFT`. **That red was the mechanism
working** — the difference between an install outage that *hides* a verifier
change and one lane that *names* it. It has since been resolved the sanctioned
way: `repin-rolling.ts` moved the digest **and** the banner to
`8836549e` / `TLC2 Version 2026.09.09.213036 (rev: ede5b88)` only after a real
**52/52** sweep, with an earned receipt and evidence file.

This PR also merges `origin/main`, where **a sibling agent hit the same
`repin-rolling` defect in the same hour and landed first**. Their fix is taken
wholesale and mine discarded — two implementations of one mechanism is the
duplication this agenda exists to prevent. The append-only receipts ledger keeps
both lineage rows (`f629a67c` and `8836549e`).

**Either way the x64 leg lands, the read is already fixed:**

- **Green** → the loop closes. This merges and unblocks the PRs that are red
  purely at the install step.
- **Red** → the honest read is that **a re-pin cannot keep pace with upstream**,
  and Aaron's full-rolling design (design doc §2b-bis) becomes **urgent rather
  than a follow-up** — it is the only path that does not put a human in the loop
  on every upstream rebuild. It is specified there already: advance digest *and*
  identity together, gated on the sweep, never on trust.

**One hazard found on the way, kept on the record because it has no symptom**
(design doc §8b): a pattern matching wider than `deriveIdentity` emits silently
**truncates** the pinned banner. `judgeToolchainBanner` asks
`stdout.includes(pinned)`, so the truncated pin stays satisfied — **52/52 passes
while the check permanently stops checking part of what it checked.** Caught by
reading the diff, not by a test; and three of my own tests had *codified* it,
because a falsifier written alongside the thing it checks inherits its blind
spot. `main`'s surviving pattern does not have this bug; what it lacks is an
*enforced* guard against reintroducing it, which is routed as a follow-up and
matters far more once identity substitution runs automatically on every roll.
