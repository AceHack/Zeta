## Description

## What happened

Run `34369317553` (main, `de612352`) aborted the included proof at **T+123 s of a 2400 s budget** on `openziti-controller=Synced/Degraded`. The cluster own events, captured seconds later **in the same job**:

```
49s  Updated health status: Progressing -> Degraded
32s  Updated health status: Degraded -> Progressing
```

It had already left `Degraded` when the abort was printed. The run reported a failure the cluster had recovered from, and **2277 seconds of budget went unspent**.

## The same Application did this before

`degradedHealthTerminalFailure` docstring already records run `33830308187`: the wait aborted on `openziti-controller=OutOfSync/Degraded` while the pod was still `Init:0/1`, and *"events after the abort went Degraded -> Progressing -> Synced"*. The remedy then was to narrow the rule from any `Degraded` to `Synced/Degraded`.

That narrowing was right and **was not enough** — because the defect was never *which sync status* accompanies the Degraded. It was **trusting one sample**.

## The change

The abort now needs the same Application degraded on **two consecutive polls**.

This is not a weakening. A genuinely dead workload is still abandoned after roughly one poll interval (15 s in CI) rather than 2400 s — which is the entire purpose of the terminal class. What is removed is the single-sample false positive. Consecutive **polls** rather than elapsed seconds, deliberately, so the guarantee does not silently change when `--poll-sec` moves.

The single-poll predicate is untouched and still refuses `OutOfSync/Degraded` as rollout; a test pins that, so this cannot quietly re-widen the narrowing it builds on.

## Mutation-tested

| mutant | tests failed |
|---|---|
| confirmation removed (back to one sample) | 2 |
| any app degrading confirms any earlier one | 1 |

The source-grepping guard asserting the wait loop **calls** the abort was updated to match the new call rather than the old identifier — a guard still matching `degradedHealthTerminalFailure(lastVerdicts)` would have passed over exactly the regression it exists to catch.

## Not diagnosed here

**Why** `openziti-controller` flaps Progressing → Degraded → Progressing during bring-up. Under the old behaviour the lane could not stay up long enough to find out; now it can.

## Cost

One extra local variable in an existing loop. No new job, no new step, no new tool.
