## Defect 1 — the macOS flasher could not be tested, so it was not

`flash-usb-linux.ts` and `flash-usb-windows.ts` each export their decision logic and
carry a test file (565 and 554 lines). `flash-usb.ts` — the macOS arm, **the one the
maintainer's own laptop runs** — exported nothing and had no test file.

MEASURED before this change:

```
$ bun test --coverage src/Core.TypeScript/zflash/ | grep -c "zflash/flash-usb.ts"
0
```

Zero occurrences: it was not a low coverage number, it was **absent from the report**,
because no test ever imported it.

It could not have had one. The module called `main()` at file scope with no
`import.meta.main` guard — the guard both sibling arms already had. Discrimination proof,
same command against `origin/main` and against the fix:

```
=== IMPORTING origin/main flash-usb.ts (no argv, stdin closed) ===
Usage: bun src/Core.TypeScript/zflash/flash-usb.ts [flags] <path-to-iso>
  ...
rc=2  <-- ORIGINAL: import terminated the importing process
=== restored; re-running same import against the FIX ===
REACHED LINE AFTER IMPORT; exports: 21
rc=0  <-- FIXED: import is inert
```

`REACHED LINE AFTER IMPORT` never printed on the original. The safety rails of a
destructive tool were untestable because reaching them fired the destructive path they
exist to gate.

**Fix:** add the guard, then extract the rails from the 660-line `main()` into an exported
pure surface. These are **extractions, not a second copy** — `main()` calls each one. A
mirrored rail that drifts from the rail actually enforced is worse than no test, because it
reports green about code that no longer runs.

## Defect 2 — the token hardware lane was unreachable by its own documented command

`frost-share-adapter.hardware.test.ts` argues its non-vacuity from *"opting in without
hardware FAILS rather than skips."* That is true — and true only in a configuration its
documented command did not reach. The file is in `bunfig.toml` `pathIgnorePatterns`
(correctly — no runner has the silicon), and **bun applies `pathIgnorePatterns` even to an
explicit path filter.**

MEASURED 2026-08-23, darwin-arm64:

```
$ ZETA_FROST_HARDWARE_LANE=pkcs11 bun test ./tools/.../frost-share-adapter.hardware.test.ts
The following filters did not match any test files
rc=1
```

`rc=1` is **also** what the lane returns when it runs correctly and finds no token. So:

| situation | exit | did the lane run? |
|---|---|---|
| opted in, no token | 1 | yes — HW-1/HW-2 fail correctly |
| opted in, **token attached** | 1 | **no — nothing was checked** |

The operator's only signal could not tell them apart, and the reading that looks like
diligence is the one where nothing ran. RE-MEASURED with the escape hatch added:

```
$ ZETA_FROST_HARDWARE_LANE=pkcs11 bun --config=bunfig.hardware-lane.toml test ./tools/...
✗ HW-1: the declared token is actually present
✗ HW-2: a share round-trips through the token; the wrapping key never leaves it
 1 pass  2 fail   Ran 13 tests
```

Note also `bun test --config=X` parses without complaint and **ignores X**; only
`bun --config=X test` honours it. Both halves of that trap are now documented in the file
and pinned by `MLANE-14`.

Registry entry corrected — its `MEASURED 2026-08-13` line was no longer reproducible.

## The automated / manual split

**Automated now (no hardware), 60 tests, weighted on the refusals:**

flag allowlist including misspelled near-misses (`--shrot`) · value flags with no value ·
`diskutil` plist parse including malformed input · USB/USB-C bus filter **and its
`Internal` conjunct** · zero/one/**many** selection where many is a refusal and not a
picker · both size bounds at the exact boundary · boot-disk parse (`/System/Volumes/Data`
must not read as `/`) · `disk3` vs `disk30` · partition paths and injected newlines · nonce
freshness · exact acceptance matching with no `.trim()`.

**Genuinely needs hardware — 10 checks, registered and printed loudly:**

`MAN-USB-01..05` (bus strings from a real controller, two-stick ambiguity, **Touch ID
actually firing at the sudo gate**, read-back on real media, UEFI boot) and
`MAN-TOK-01..05` (token identity, cross-token share refusal, touch presence, attestation
chain to vendor root, on-device key origin).

`usb-hardware-manual-lane.ts` holds them as data — it shells out to nothing, asserted by
`MLANE-9`. The banner prints on **every** run of the suite, unconditionally, not from
inside a `skipIf`, and ends:

```
A green run of this suite says NOTHING about the lines above.
```

Long form with expected outputs and a stated action on mismatch in
`docs/security/USB-HARDWARE-SETUP-TEST-PROCEDURE.md`. `MLANE-10/11` fail if the doc drifts
from the register **in either direction**.

`MAN-USB-03` is the one that carries the standing constraint: the agent executes the setup,
the human approves the gate, **the biometric is the authorization** — and its on-mismatch
line says that a password prompt instead of the Touch ID sheet means the run was authorised
by a shared secret an agent could hold, so record the factor honestly rather than claim a
biometric that did not fire.
