## Description

Follow-up to #15246, which **auto-merged at 05:53 before these fixes were pushed**. The version now on `main` has two real defects and a false claim in its own header. Both defects were found after that PR went green — the first by an adversarial review, the second by re-reading my own fix for the first.

## 1. The overflow behaviour was host-ISA-dependent

The kernels checked overflow **per lane**. But the scalar twin unrolls into 4 accumulators and the vector path partitions into `Vector<int64>.Count` lanes — 2 on NEON, 4 on AVX2, 8 on AVX-512. Those are *different partitions*, so the pair disagreed in **both** directions, and which way depended on the machine:

```
[MaxValue; MaxValue; -MaxValue; -MaxValue]   NEON: throws     AVX2: returns 0
[MaxValue; -MaxValue; MaxValue; -MaxValue]   NEON: returns 0   AVX2: throws
```

Same bytes, same code, different behaviour per host. That is a **DST replay violation (§7)** and a **four-oracle byte-lock violation**, in a public API.

Worse, in the terms this repo cares about: the type's header claimed the scalar/vector pair "agree on every input" and called that pairing "the correctness falsifier". **The advertised falsifier did not exist.** That is the vacuity class, and I shipped it.

**The fix is not documentation.** New contract: compute the **exact mathematical sum**, raise `OverflowException` **iff the true sum does not fit `int64`**. Accumulation stays in `int64` at full speed and folds into an `Int128` running total only at the points it would actually have wrapped (detected branchlessly with `((a XOR s) AND (b XOR s)) < 0`, which is exact for two's-complement addition including `Int64.MinValue`). No partial-sum artefact, no lane-width dependence, no silent wraparound.

This is strictly better-defined than `ZSet.weightedCount`, which remains position-dependent — so `ColumnZSet.weightedCount` now succeeds on a few inputs where `ZSet.weightedCount` raises. Both still refuse to wrap silently.

## 2. The wrapping-lane fallback then narrowed per *chunk*

The fix above processes in 4 096-element chunks. The fallback for a wrapping lane called the **public** scalar kernel, which narrows to `int64` — so two chunks exceeding `int64` in opposite directions raised, even though the true sum was `0` and the scalar twin over the whole span returned `0`.

Found by re-reading the fix, not by a test — because the differential test I had written capped `n` at 40, **one chunk**, and could not reach the class at all. Fixed by keeping the fallback wide.

## Verification

- Every named witness now agrees; genuine overflow (`[MaxValue; 1]`, `[MinValue; -1]`, 64 × `MaxValue/4`) still raises on **both** paths.
- 5 000 extreme-magnitude differential trials — weights drawn from {near `MaxValue`, near `MinValue`, tiny, `MaxValue/k`} so partial sums wrap constantly — **zero disagreements**. Every 50th trial draws `n ∈ [4000, 9000)` so the chunk boundary is crossed.
- **Both fixes are mutation-checked**: reverting either one fails exactly the test written for it, and no other.

## Silent-failure fixes in the Arrow bridge

- `OfRecordBatch` ignored `NullCount`. A null slot reads back as `0L` from `.Values`, so a null weight became a **zero-weight Z-set entry** — illegal, with no error anywhere. Now refused, along with wrong column count and short columns.
- Neither `OfRecordBatch` nor `ReadIpc` validated any Z-set invariant, while the `ColumnZSet` ctor documents that *the caller* owns "keys strictly ascending". Crafted IPC therefore produced an unsorted column whose binary search silently lies. Now checked at the boundary where untrusted bytes cross.
- `ReadIpc` returned `Empty` for truncated or garbage bytes, making a **corrupt checkpoint indistinguishable from an empty one**. Now raises `InvalidDataException`; a zero-length span stays the one benign case.
- The write path had a big-endian guard and the read path did not.
- The `ColumnZSet` ctor did not check that its two columns are parallel.
- `i + width` loop guards can wrap `int` near `Int32.MaxValue`; now `i <= len - width`.

## Two false claims of mine, corrected

- The Arrow header said the conversion is **"a buffer handoff, not a transform"**. It is not: `MemoryMarshal.AsBytes(column).ToArray()` copies once per column. Corrected to "bulk reinterpret-and-copy", with the genuinely zero-copy route (`ImmutableCollectionsMarshal.AsMemory`) named, and marked **not done** with the ownership question that blocks it.
- The measured table conflated two data regimes into one headline. A scalar predicate scan costs whatever its **branch predictor** costs, so the same kernel measures ~6x apart depending only on key order, while the vectorised kernel costs the same either way:

| range count, n = 1 000 000 | scalar | vector | ratio |
|---|---|---|---|
| **shuffled** column | 3 387 µs | 341 µs | **9.9x** |
| **sorted** column | 594 µs | 341 µs | **1.75x** |

A `ColumnZSet` **key** column is sorted by construction, so the honest expectation there is ~1.75x — and on a sorted column you would binary-search the two boundaries rather than scan at all. The vectorised scan earns its keep on columns that are **not** the sort key. `ColumnZSetBench` now measures both regimes instead of only the flattering one, and its setup uses distinct keys so `ZSet.ofSeq` cannot dedup the column and make every `n =` label wrong.
