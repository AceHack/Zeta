## Description

## The defect

`gate (required)` is the **sole required status check** — the one thing branch protection
consults, and what armed auto-merge waits on. Its verdict step was one grep:

```bash
if echo "$results" | grep -qE '"(failure|cancelled)"'; then exit 1; fi
```

so **`skipped` counted as success**. That is *correct* for the path filter — a docs-only
PR legitimately skips `full-verify`, and most runs on this repo are exactly that. It is
*wrong* for the other producer of the same word: **GitHub marks a job `skipped` when a
job it `needs:` did not succeed.**

So a dead `path-filter` skips **both** `build-and-test` and `full-verify`, the roll-up
sees two `skipped` values, and the gate reports **SUCCESS with its two heaviest subjects
never run**. A check that did not run looked exactly like a check that passed, at the most
expensive place in the repo for that to be true.

Surfaced and deliberately left open by #15504.

### It is not hypothetical — it fired yesterday

**Gate run [32881149945](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/32881149945)**,
2026-08-25 17:59Z, `pull_request` on `claude/tender-hawking-xmcs6m`:

```
cancelled  path filter
skipped    build-and-test (${{ matrix.os }})
skipped    full-verify (7-lang oracle + cost + proofs)
success    gate (required)      <-- the sole required status check
```

The path filter was cancelled, both of its dependants were therefore skipped, the roll-up's
grep saw two `skipped` and no `failure`, and **the one check branch protection consults
reported SUCCESS**. What that green covered: *not one* .NET build or test leg, and *not*
the seven-language byte-lock.

The trigger is **`cancelled`, not `failure`** — worse than the case I first reasoned about,
because cancellation is an **everyday event here** (`cancel-in-progress` fires on every PR
push). That run's job list is committed as a fixture and replayed in the tests. It is not
alone: see *Honest incidence* below for the second instance, a **Dependabot dependency bump**
that went green the same way six hours earlier.

## Why not simply fail on `skipped`

It would redden **every docs-only PR**, and a gate that blocks correct work is worse than
the hole it closes. `skipped` is genuinely two-valued; the fix **separates the values**
rather than collapsing them onto the pessimistic one.

## How the two values are separated — without a roster

A skip is legitimate **iff**:

1. `gate.yml` gives the job a **job-level `if:`** — a declared licence to skip
   (`full-verify`'s `if: needs.path-filter.outputs.code == 'true'`), **and**
2. **every job it `needs:` reported `success`.**

Both halves are read out of `gate.yml` itself, reusing #15504's parser. Give a job an `if:`
and it becomes skippable here **with no edit to the checker**; delete one and it stops
being. A hand-written list of "jobs allowed to skip" would drift silently in the
**permissive** direction, which is the failure class this repo keeps rediscovering.

`build-and-test` declares **no** job-level `if:` — its docs-only handling is at *step*
level — so its skip has exactly one explanation and is refused. `full-verify` declares one,
so its skip is judged on its prerequisite. Both readings come out of the file.

**The one-level upstream check is sufficient because a test says so**:
`gate-skip-verdict.test.ts` asserts every prerequisite of every floor job is itself in the
floor. Add a floor job with an unseen prerequisite and that test goes red on every run — the
runtime rule would also fail closed, but only on runs where that job skips, which is too
late to be the guard.

## Fail closed, and what that costs — stated, not hidden

Every unclassifiable state blocks: unreadable `gate.yml`, unparseable `gate.yml`, empty
`needs` context, a result string GitHub does not document, a prerequisite the roll-up cannot
see. **So this step can now redden a gate because a *parse* failed, where before it could
only do so because a *job* failed.** That is a real new failure mode and the main thing to
weigh in review.

Two things bound it: `gate.yml` is read from the roll-up's **own sparse checkout in the same
job** (if that is broken the job already fails today, before this step), and the parse is
pinned against the real `gate.yml` by tests that run in `test (TS hermetic)` — itself a
floor job. A gate that fails *open* is the thing this entire change is about.

## Honest incidence

Scanned the **last 400 completed `gate` runs**. **23** had a non-success `path filter`
(all of them `cancelled` — `cancel-in-progress`, not a job defect). **21 reddened the gate
anyway**, because the same cancellation also caught some *other* floor job and `cancelled`
was already a blocking value. **Two did not**, and both are from 2026-08-25:

| run | branch | what the green covered |
|---|---|---|
| [32881149945](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/32881149945) | `claude/tender-hawking-xmcs6m` | no .NET build/test leg, no 7-language byte-lock |
| [32861098038](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/32861098038) | `dependabot/uv/src/Core.Python/uv-minor-patch-…` | same — **on a dependency bump** |

The second one is worth pausing on: **a Dependabot dependency bump whose required check went
green having run no build and no test, with a red `lint (Python)` beside it.** That is the
exact shape the floor exists to prevent — an unreviewed third-party version change admitted
on a green that covered none of the things that would have caught it.

Both runs are committed as fixtures and the regression block runs over both, so neither is an
anecdote that got a paragraph and no falsifier.

So the absorbing condition is **narrow** — it needs the prerequisite dead *and* every other
floor job clean — and it is **~9% of the runs that hit it**, recent, and reached by an
entirely ordinary event. My first commit said the scan had found nothing; extending it found
these, and the correction is recorded in the second commit rather than folded back into the
first.
