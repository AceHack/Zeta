## Description

## Aaron's ask

> *"why do i have to do work on the hardware? is not not possible to ship where it will be fully operational without human intervenion on hardware? I'm trying to avoid any manual step, if they are absoutly needed, could the nix installer setup anything that's needed?"*

**Scoping first, per the ask.** The doc is the deliverable; the code shipped with it is inert and decides nothing.

## The answer, short

**Yes to the fallback** — the nix installer can pre-stage the whole seal userspace, and it is one word of config. **No to the whole ask** — three classes remain:

1. **Firmware.** No OS can enable its own fTPM. `secure-boot.nix` already names this class ("no software can put its own firmware into UEFI Setup Mode"). A KVM-over-IP — which the fleet already has — makes it *remote*, never *automatic*.
2. **The physical acts.** Power, cabling, the stick.
3. **One custody decision**, and it is the one that matters.

Everything else — install, TPM userspace, token, `operator init`, **and unseal on every boot** — is automatable. The last one is the step Aaron is actually paying for today.

## The tradeoff, not buried

A key generated inside a TPM cannot be exported, so **the board becomes the only thing that can ever unseal that vault.** OpenBao says it:

> *"If the seal mechanism or its keys are permanently deleted, then the OpenBao cluster cannot be recovered, even from backups."*

Recovery keys do not save you — *"purely an authorization mechanism"*. The repo already models the same fact, tested, in `credential-binding-model.ts`: `tpmSeal × machine_swap → decrypts: false`. Three candidate recovery stories are priced in §3 and **none is decided here.**

One timing note: TOPOLOGY.md §2 measured that Vault holds nothing today, so "accept the loss" is **free right now** and gets monotonically more expensive from the first secret stored.

## The hardware premise is UNMEASURED — that is a finding

`tpm2-linux-captures.json` carries twelve captures and **exactly one is `observed`**: the Mac Studio, state `unavailable` ("we could not ask"). The four `node.yaml` self-registrations have **no TPM field at all**. So *"we can count on it"* is a **declaration** with an empty probe surface behind it. One command closes it (`081M00VN9P1087G0R000FYTTVS`), and every claim in the doc is conditional on it.

## Measured at the fleet's own pinned nixpkgs rev

- `pkgs.openbao.tags = [ "hsm" "ui" ]` — **PKCS#11 is already compiled in on Linux by default.** The earlier *"own a build or a plugin pin"* price does not apply to the nix path.
- `tpm2-pkcs11` **1.9.2** — the version we would install, not the 1.10.1 the prior doc read: `CKM_RSA_PKCS_OAEP` present, `CKM_AES_GCM` absent. The mechanism pin is re-checked at **our** version.
- `security.tpm2.*` read from module source — including that **without `applyUdevRules` a non-root seal process reads exactly like "no TPM"**.
- `maintainers/aaron/gpg-pubkey.asc` is ed25519 + cv25519, and OpenBao imports `ProtonMail/go-crypto` (ECDH-capable). So `-recovery-pgp-keys` can address a recipient **that already ships in the clone**.

That last one is the spine: an unattended `operator init` emits ciphertext addressed to a key the node does not hold, so TOPOLOGY.md §5's refusal (*"automation would have to hold unseal shares somewhere a process can read them"*) **does not apply — there is nothing readable to hold.** What it does *not* buy is stated in the same section.

## Also found

`detectBiometricPlatform` returns `unsupported` on Linux, fail-closed. **The nodes are Linux**, so a biometric gate *on a node* is not implementable today. This locates the standing rule rather than weakening it: the approval happens on the Mac, and the cheapest shape is Touch ID gating the one decryption of the root-token blob — no new mechanism.

## Governance

**`TOPOLOGY.md` §5 is not rewritten.** §5 of the doc is a **proposal** against it with the human-facing diff spelled out, for Aaron to accept or refuse.

## What ships here (inert)

- `tpm2-seal-model.nix` — three modes, `derivePlan`, and `assess` over the probe's **five states**. `absent` is the only state that produces `drift`; the other three produce `check-did-not-run`.
- `tpm2-seal-prereqs.nix` — default `off` sets **no option** (verified against a real `nixosConfigurations.control-plane` eval: all-false/null plan). `provision` **fails evaluation**, naming C1–C5.
- `tpm2-seal-prereqs-eval-test.nix` + a `checks` entry — **25 properties green**, forced by `nix flake check --no-build`. **Mutation-checked, not asserted**: loosening the gate goes red by name; flipping the `withHsm` pin to `false` goes red by name.

**`zeta.tpm2Seal.mode = "prereqs"` is deliberately NOT flipped.** Flipping it changes every node's closure and loosens `/dev/tpmrm0` to the `tss` group — small, defensible, and Aaron's to decide.
