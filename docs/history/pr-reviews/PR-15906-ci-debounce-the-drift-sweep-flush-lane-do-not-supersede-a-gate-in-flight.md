## Description

## The measured problem

`drift-sweep.yml` fires on **every push to main**.

| quantity | measured |
|---|---|
| merges to `main` | 68 in ~6h — one per **5.3 min** |
| `gate` on `heartbeat/drift-sweep` | **~16 min** (median, n=13 successes) |
| ρ (arrival ÷ service) | **≈ 3** |
| outcome on that branch | **39 cancelled** vs 40 success |

Every cancellation had an inter-push gap of **6–11 min**; every success had **≥13**. Each tick
pushed the lane branch, restarting gate on the open flush PR and cancelling the run in flight.

That's queueing saturation, not flakiness. Past ρ ≥ 1 a queue doesn't get slower — **it stops
draining.** The flush PR couldn't land while main stayed busy, and it grew while it waited.

The `on: push` trigger was added 2026-08-10 to make the tick faster. It made *measurement* faster
and *landing* unboundedly slower. Both are true; only the first was intended.

## The guard

It asks the direct question — **is the previous tick still in gate?** — rather than "was the last
push < N minutes ago". A time window needs N calibrated to gate's duration and rots the moment gate
gets faster or slower. This self-tunes and targets the actual mechanism.

**Nothing is lost by skipping.** Tick numbering is `max existing + 1` from the ledger and the lane's
`prepare` step already unions the unlanded payload — a tick that never lands never existed. The cron
heartbeat (`7,37`) guarantees liveness even if every event-driven tick in a busy hour is skipped.

**It fails open.** Unreadable run, missing or unparseable start time, or a run past a 45-minute
stuck-cutoff all proceed. A wrongly-skipped tick costs a delayed measurement; a wrongly-starved lane
costs *silence that looks like health*, and that's the worse failure here.

## The decision is a tested module, not shell in YAML

`gate.yml` states the rule this follows: *logic in a `run:` block is logic no test can reach.* The
workflow step pipes bytes; `flush-lane-debounce.ts` is a pure function with **15 falsifiers**,
weighted toward the skip-too-much direction because that's the silent failure. Two worth noting:

- the **control** that a completed run proceeds — without it, an always-skip implementation passes
  every skip assertion and starves the lane permanently;
- **clock skew** — a run that started "after" now is not evidence it finished, so it still skips.

## Scoped by evidence to one lane

| lane | cancelled/100 | guarded? |
|---|---:|---|
| `heartbeat/drift-sweep` | **39** | yes |
| `heartbeat/tick-metrics` | 4 | no — its problem is 55 *failures*, unrelated |
| `lockfile-healer`, `metrics`, `zetadb-scheduled-node` | no gate runs | no |

Adding the guard where nothing saturates would slow those lanes for no benefit. The module is
reusable when another lane earns it.
