## Description

fix(heartbeat): the flush pre-merged main into main, so every lane reported a green no-op and nothing landed

`docs/github/prs/manifest.jsonl` has been repaired by hand twice (#15471, #15511)
because the automated repair stopped landing. The derive step is fine; the writer
commits; it is the FLUSH that has not put anything on `main` since
2026-08-25T16:08:11Z — four minutes before #15372 shipped a local pre-merge into
the flush job.

WHAT THE PRE-MERGE ACTUALLY DID. The flush job checks out `main` (`ref: main`) and
never leaves it, and the block ran:

    git merge --no-edit origin/main
    git push --force-with-lease=... origin "HEAD:refs/heads/$SNAPSHOT_REF"

so it merged main into main — a fast-forward — and then wrote **main itself** over
`heartbeat/<lane>-flush`, deleting the parked lane payload from the ref the PR is
cut from. `merge-heartbeats-to-main.ts` compared main to a copy of main, returned
rc=4 "already contains", and the rc=4 branch — written for a genuine no-op —
exited 0. The step created the condition that made its own success branch true.

MEASURED, NOT INFERRED (2026-08-26T07:50Z):
  - `heartbeat/soraya-flush` and `heartbeat/alexa-flush` both pointed at exactly
    `origin/main`;
  - run 32942319401 logged "4 heartbeat commits to flush", then
    "+ e0daddeaf...dc15f463d (forced update)" where dc15f463d is an ordinary
    SINGLE-PARENT main commit — a real pre-merge cannot produce a commit that does
    not have the lane as a parent;
  - every flush job in the last 16 h: step green, "Arm auto-merge" SKIPPED, no open
    flush PR for any of the three lanes;
  - manifest.jsonl landing gaps on main over 14 days / 303 landings:
    p50 27.4 min, p90 81.6, p95 158.5, max 2799.5; 14/302 gaps over 180 min. The
    file's claimed "~1 hour" bound was the flush gate's PERIOD, not a measured lag.

Neither of the two failures blocking sibling lanes tonight is involved: no
`pre-push[floor]` refusal and no stale `--force-with-lease` — this step exits 0.

THE FIX. The pre-merge moves to `premerge-flush-ref.ts`, whose first act is
`checkout --detach <laneSha>`, and which then asserts the result contains BOTH the
lane tip and the base before returning. It refuses to push; the workflow still owns
the credential. It registers no custom merge driver: `merge=theirs` in this
direction means `main`, which would resolve the lane's fresh shards and archive
bodies to main's older copies.

THE FALSIFIERS.
  - `premerge-flush-ref.test.ts` runs against a real scratch repo from a tree
    checked out on `main` — the exact condition the job supplies — and asserts the
    result still contains the lane. The old behaviour is reproduced as an explicit
    CONTROL so the assertion is provably discriminating. Mutation-checked: deleting
    the checkout kills 3 of 9 tests.
  - The rc=4 branch now checks its own claim. A no-op is only honest if `main`
    really contains the tip this tick parked (`$LANE_SHA`, captured before the
    pre-merge can move `$SOURCE_SHA`). If it does not, the flush is reporting
    success over unlanded work and the job goes red. That is the detector the
    manifest watchdog could never be: `pr-manifest-integrity.yml` sees the
    staleness three hours later and cannot say why.
  - A pre-merge failure that is not a content conflict is now fatal instead of a
    warning, so "produced the wrong commit" stops looking like "produced none".

The `|| echo` on the derive step stays, and the file now says why: that step also
archives PRs, reconciles review threads, audits the lane, runs the healers and the
mutation probe, and carries the codegen output, and the index is regenerated from
the shards next tick. It was never the liveness check, and the two ways the repair
silently stops now both have one.

No events were lost at any point: the lane still holds every unflushed tick and the
flush is idempotent (G-Set union).
