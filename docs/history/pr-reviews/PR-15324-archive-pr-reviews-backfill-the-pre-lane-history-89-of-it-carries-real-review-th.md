## Description

## Summary

Backfill of the PR-review archive backlog. Companion to #15316, which fixes the ongoing failure; this recovers the history.

**Worklist: 2436 eligible merged PRs with no archive record.** Produced by `backfill-pr-archive.ts` (landed in #15316), paced and resumable.

## What this recovers, and why it is the valuable half

The largest population here is the **1,506 PRs merged before `pr-archive-on-merge.yml` existed** (it landed 2026-05-06). That is not a lane failure — there was no lane. It is also, measured, the **richest review data in the repo**:

> **345 of the first 389 backfilled docs (89%) carry at least one review thread**, one with 22.

Compare the present day: only **2.8%** of recent merged PRs ever acquire a review thread (measured in `agent-heartbeat.yml`'s own reconcile comment). April–May 2026 was the human-heavy review period, so the pre-lane era is exactly the substrate the archive exists to own — *"you can't train on a rate limit github api."*

## How it was produced

- **Idempotent** (§12) — the per-PR work is `buildArchive` / `writeArchive` / `writeShard`, imported from the existing archiver rather than reimplemented. `writeArchive` short-circuits on identical bytes; `writeShard` no-ops modulo the two wall-clock-noise fields. Re-running changes nothing.
- **Paced** — 500-request reserve so it cannot starve the agents sharing the token, `Retry-After` honoured verbatim, exponential backoff with jitter, minimum inter-PR delay. Observed cost: GraphQL stayed above 4,200/5,000 throughout. **Zero throttles, zero failures.**
- **Resumable, and the resume was exercised for real** — the run was stopped mid-drain to re-pace it and resumed cleanly at cursor 158. The checkpoint is rewritten after every PR, so a crash loses one record.
- **Concurrency-safe with the cadence sweep** — the shard store is re-checked per PR, so records the sweep landed meanwhile are skipped rather than re-fetched.
- **Batched delivery, not one PR per record.** Opening a PR per record is the accumulation that produced 1,298 orphaned branches.

The branch sat DIRTY, so its gate could never run and main's `every open PR has gate (required)` audit went red on every tick.

### The conflict set was not what it looked like

| count | what | kind |

The six source-file conflicts were the surprise: **`main` had independently landed this branch's own tooling via #15316**, so the same files exist on both sides with no common ancestor.

### The 187 shard conflicts are noise-only — measured, not assumed

Shards are one-file-per-PR keyed by an **injective** `ZetaId(pr_number)`, so the shard set is a G-Set whose merge is union and a same-path conflict can only ever be *the same PR archived twice*. `writeShard` documents itself as a no-op modulo `fetched_at` and `commit_sha`.

Comparing **every** conflicted shard's two merge stages with those two fields stripped:

```
noise_only (fetched_at + commit_sha ONLY) = 187
SUBSTANTIVE differences                   =   0
```

No record content was at stake, so **nothing was re-fetched from the API**.

The resolution — main's record on overlap, the branch's records in the gaps — is not a hand-merge. It is exactly the tool's own fixed point: `--resume` re-checks the shard store per PR and **skips** one already present, so running the backfill against current `main` would have produced this tree and spent hours of API budget doing it.

### The code conflicts: `main` already contains all of it

`archive-pr-reviews.ts` was the only true content conflict, and `main` carries every one of the branch's edits (both new `export`s, the `isArchiveEligible` sweep filter, the widened `--json` field list). main's `backfill-pr-archive.ts` is the branch's file **plus** prettier formatting, a `loadCheckpoint` TOCTOU fix and a TS7022 inference fix; its coverage audit adds a backtested threshold. Nothing branch-side is lost, so `main` is taken for all six.

### The workflow conflict, resolved deliberately

Both sides appended **the same step** to `pr-manifest-integrity.yml`. Verified mechanically rather than by eye — comment-stripped, both sides are **126 lines and byte-identical**. The only difference is that main's carries an extra comment block recording the measured **108s runtime against `timeout-minutes: 10`**.

So this was not a choice between two behaviours. Taking the branch's side would have **deleted that measurement from main** while changing nothing that executes. main's side is kept: strict superset, identical behaviour.

### One reversal from the original plan, stated rather than buried

This PR originally said the manifest was **deliberately not staged**. That is no longer true and the paragraph has been removed. The merge itself auto-merged `manifest.jsonl`, and a line-interleaved auto-merge of a derived JSONL index is precisely what `derive-pr-manifest.ts` says must never stand — *"the derived file carries no information the shards do not, so regenerate is always the correct resolution."* So it was regenerated from the 12,388 shards and verified in sync.

The original reasoning still has force: a staged manifest is a shared-path surface, so this PR can be re-dirtied by any archive writer that lands on `main` before it merges. That is a **re-dirty risk, not a correctness risk** — the repair is one mechanical `--write`. It is called out here rather than left for the next agent to rediscover.

Incidentally, regenerating also repaired a pre-existing **28-shard lag in main's own manifest** (10,721 shards indexed by 10,693 lines).
