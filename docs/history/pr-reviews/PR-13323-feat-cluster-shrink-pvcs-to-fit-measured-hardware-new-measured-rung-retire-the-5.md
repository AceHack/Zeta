## Description

## What

Shrinks the shipped `longhorn` PVC declarations to fit the box we actually measured, and **retires `acknowledgedCapacityShortfall`** — by arithmetic, not by exemption. Nothing about `single-node-readiness` was relaxed; it makes the same comparison against the same measured evidence and now comes back clean.

`activeStorageProfile: large` → **`measured`**, a new rung defined by a **rule** rather than a hand-typed table:

> every claim with `scheduledAtBringUp: true` takes `standard`'s value; every claim with `false` keeps `large`'s.

That rule is re-derived in a test, so an edit that breaks it cannot pass as a rung.

| | declared | at bring-up |
|---|---|---|
| before (`large`) | 1599 GiB | 1099 GiB |
| after (`measured`) | **967 GiB** | **467 GiB** |

## Against SCHEDULABLE capacity, not raw

**Finding: the gate compares against RAW disk.** `findCapacityProvenance` sums every block device on the smallest measured node and reserves nothing — for Longhorn, the OS root, swap or the ESP. That is deliberate (it convicts, never acquits) but it is not the number a cluster has to fit inside.

The real reserve, read off the **deployed** manifest rather than remembered: `full-ai-cluster/k8s/applications/longhorn/Application.yaml` sets neither `storageOverProvisioningPercentage` nor `storageMinimalAvailablePercentage`, so longhorn-1.7.2 chart defaults apply — **100** (`values.yaml:214`) and **25** (`:216`) — giving **75%** placeable. (`infra/`'s copy sets 200/15 → 85%; only one app-of-apps root can own the cluster, so the auditor takes the **tighter** of the two rather than guessing.)

```
raw, every block device on node-ad1efd        1047 GiB   <- what the gate compares
schedulable, 75% of (1047 - 30 GiB OS root)    763 GiB   <- what Longhorn will place
schedulable if only /dev/nvme0n1 is a
  Longhorn disk (defaultDataPath is on root)   676 GiB

measured, bring-up                             467 GiB   fits both, by 296 / 209 GiB
measured, declared                             967 GiB   under raw; OVER schedulable
```

The auditor now **prints** this beside the raw bound. It stays a **report, not the gate**, and the reason is in the code: the estimate assumes *which* devices Longhorn manages (`defaultDataPath: /var/lib/longhorn` puts the default disk on the root filesystem, so `/dev/sda` is not a Longhorn disk until somebody adds it), assumes a 30 GiB OS root, and ignores `storageReservedPercentageForDefaultDisk` whose default the chart does not state. A bound built on three assumptions can be wrong in the **acquitting** direction, and the raw sum cannot.

Also worth stating: **`large` could never have stood up on this box.** Even its bring-up subset needs ~1495 GiB of device. That is what the raw-only comparison was hiding.

## The 500 GiB standing decision

`ollama` (200Gi), `vllm` (200Gi) and `arc-runner-set/model-cache` (100Gi) are **untouched**. They are the whole gap between declared and schedulable. None provisions on a fresh sync — two are `zeta.io/sync-policy: manual`, arc's PVC is applied by nothing (081M0JM6SSG087G0R0029X3F6Z) — so the cluster comes up well inside the schedulable bound.

They are left alone deliberately: shrinking a ceiling nobody decided to lower buys headroom the bring-up total never spends, and deletes a stated capacity intent instead of costing it. **The consequence is printed on every auditor run** rather than absorbed as a passed check: syncing those Applications at these ceilings would ask Longhorn for storage it will refuse to place. Running `standard` instead takes declared to 595 GiB and clears the schedulable bound outright, at the price of those ceilings (200→48, 200→48, 100→32). That is Aaron's call and it now has its number attached.

## Governors — a number without its governor is not a size

New `governors` field on a catalogue row: non-capacity scalars, per profile, **written and verified in the same `--apply` pass as the size they bound**, with required `governorEvidence`.

Its first user is **prometheus, which had no size-based retention at all**. kube-prometheus-stack 65.5.0 ships `retentionSize: ""` (`values.yaml:3732`), so `retention: 15d` was a *time* bound that cannot see the disk and Prometheus grew until the volume filled and the WAL wedged. The row previously said the retention cut "is NOT rewritten by `--apply`" and asked whoever selected a rung to remember. An instruction to remember is the vacuity class. `retentionSize` is now `24GiB` at this rung and moves with the volume.

**75% of the volume is a BUDGET CHOICE, not a derived minimum**, and the catalogue says so: size-based retention deletes the oldest block only after the limit is crossed, so the volume needs room for the head block and the WAL on top, and nobody here has measured this cluster's ingest rate.

**Empty `governors` is a real answer**, and each row says which case it is: *moves by itself* (nats — chart emits `max_file_store: {{ pvc.size }}`, `files/config/jetstream.yaml:17`); *no history to govern* (mimir — working space, blocks in object storage); *no mechanism exists* (weaviate, cockroachdb, hindsight, agent-memory — they refuse writes); *does not move and is left* (**tempo** — chart default `tempo.retention: 24h`, `values.yaml:57` → `block_retention`, is a time window that cannot see the disk; cutting it needs a measured span rate nobody has, and inventing one and calling it a requirement is what this ladder exists to stop, so the residual risk is named in the manifest instead).

## Caveats

- **Kubernetes can GROW a PVC but cannot SHRINK one.** These numbers are free to move down only while the volumes do not exist. On a cluster where they are already bound, the migration is destroy-and-restore per volume from backup — Longhorn's StorageClass here is `reclaimPolicy: Retain`, so the old volume survives the PVC, but nothing resizes it downward.
- `--apply` round-trips YAML through the document API, which reflows a few inline-collection spacings (`[ "a" ]`, `limits:   {` → `limits: {`). Values are unchanged; this is pre-existing applier behaviour.
