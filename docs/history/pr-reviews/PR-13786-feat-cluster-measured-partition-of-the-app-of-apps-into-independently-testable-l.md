## Description

## Aaron's observation, and the honest answer to it

> *"if we have independent helm chart groups we can test those independently. we could have different groups of applications that depend on each other and test each group of apps independently if they don't have dependency overlaps. i think ace package manager should hopefully be able to tell us if there are independent helm app groups we can test independently."*

**The shape is right. The literal reading does not work, and that is measured, not asserted.**

Connected components of the undirected dependency graph — the zero-duplication partition, the exact reading of *"if they don't have dependency overlaps"* — gives **15 components, one of which holds 32 of the 47 Applications**:

```
[32] agent-memory alloy arc-controller arc-runner-set cert-manager cilium cilium-lb-ipam
     cockroachdb deepseek-coder external-secrets gmod headscale hindsight kube-prometheus-stack
     loki longhorn mimir minio nats ollama openziti-controller platform qwen-coder redis spire
     spire-crds tempo temporal trust-manager vault vllm weaviate
[2]  hat-system open-policy-agent
[1]  argocd · sealed-secrets · node-feature-discovery · kubevirt · cdi · seaweedfs · headlamp
     · argo-rollouts · argo-workflows · dapr · forgejo · gitlab · orleans
```

Every storage consumer hangs off `longhorn`, the networked ones off `cilium`, and `platform` (cert-manager + cilium + cilium-lb-ipam + longhorn) staples the bootstrap chain to the storage chain. That one component contains **both** 23-GiB images. `connectedComponents()` is kept in the module for exactly this reason — to keep saying so.

## What does work: dependency closures, because the hubs are cheap

The giant component is glued by hubs that cost almost nothing to duplicate — `longhorn` 0.69 GiB of images, `cilium` 0.94, `cert-manager` 1.11. So the unit is not the component but the **closure** (an app plus its transitive dependencies), and lanes may **share** hubs by each paying for them.

A closure lane is **dependency-complete by construction**, which is the property bring-up actually needs. Disjointness never was.

## Disk, not CPU — this is not a parallelism optimisation

All 47 together: **5016m / 13348Mi / 74.5 GiB** against **2500m / 9216Mi / 10 GiB** unreserved. CPU over by **2.0×**, disk over by **7.5×**. No CPU ladder shrinks an image, so sharding is the only route by which "test every chart" is reachable on hosted runners at all.

## Derived, never hand-listed

The matrix is computed on every run and **nothing in the workflow names an Application**. A hand-written shard list drifts from the dependency data the moment someone adds a chart — the shape this repo has already been bitten by (a glob deferring nine directories while a registry reasoned about five, both green). `buildModel` refuses every mismatch across the four sources, including the join hazard that `oz/Application.yaml` is `metadata.name: openziti-controller` while the catalogue keys it `oz`.

## Intent vs observed edges — built, and measured to change nothing today

`spec.intentAdjudication` added to the graph. An edge is `observed` or `intent`; the partitioner enumerates candidates from the citations that mention declared intent and **refuses any it does not answer**.

Not a grep, and the file shows why: `temporal -> cockroachdb`'s citation reads *"was a DECLARED INTENT until 2026-08-22 … and is now a live connection"*. A substring match convicts it **backwards**.

**Measured consequence:** `--drop-intent-edges` returns the same two lanes with identical footprints and the same 38/47 coverage. The only number that moves is `hindsight`'s closure, **24.06 → 23.19 GiB** — still 2.7× a lane budget. (23.19 is measured; the first draft of that comment guessed 22.5 and was corrected.) The mechanism is built because intent edges accumulate, not because these two cost a lane today.

## The x2.67 ratio is an estimate, and each lane job convicts it

Disk figures are compressed registry bytes × 2.67, an aggregate measured over four images. Every lane job pulls **exactly its own lane's images** and reads the real `df` delta, failing if the measured cost exceeds the budget. That is what converts the whole exercise off a ratio. The lane job also checks the runner's own `/proc` against `runnerEnvelope`, whose capacity half is GitHub's published spec and not something we measured.

**What it does not yet do, said plainly:** it does not bring the lane *up*. `--root-exclude` emits the ArgoCD `directory.exclude` glob that scopes a root Application to one lane, and `app-of-apps-discovery.ts` already reads that field — so the wiring is one step, not a redesign. It is not taken here because a bring-up that has never run is not something to assert in a workflow comment.

## Honest limits

1. **x2.67 is uniform** and per-image error is real — the four samples span ×2.49–×3.39. The lane jobs are what fix this.
2. **FFD is a heuristic**; 2 lanes is an *upper* bound on the optimum, not the optimum. Chosen for determinism and legibility.
3. **`measure-lane-footprints.ts --check` must not become a gate** — it depends on 129 third-party registries being up. The offline join refusal in `lane-partition.ts` is the gate.
4. **`ace`'s own `loadDependencyGraphFromFile` cannot parse this graph** (`YAML parse failed: UnsupportedConstruct`); `derive-sync-waves.ts` already uses the `yaml` package instead, and so does this. Noted, not fixed here.
5. Lane composition is **`dev`-rung specific**; `--rung metal` and `--margin` re-derive it.
