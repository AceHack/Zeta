## Description

`gate (required)` has been absent from every `heartbeat/*` flush PR since 2026-08-14.

## The recorded cause was wrong, and the correction matters

The standing explanation was *"GitHub does not trigger workflow runs from `GITHUB_TOKEN` pushes."* That is not what the API shows. Measured on `heartbeat/alexa` **before** touching anything:

```
pull_request      gate  completed/action_required  actor=github-actions[bot]
workflow_dispatch gate  completed/success          actor=AceHack   (SAME head sha)
```

The run **is** created. It is created and immediately parked in `action_required`, so it never executes and never contributes a check to the PR rollup. The cure is the same either way — a push actor that is a human account — but a wrong mechanism in the record is how the wrong fix gets copied forward.

## Why it is safe to try this again

#10850 did exactly this and killed all three lanes for **16.75 hours**, because the PAT had no `contents: write`. The operator granted that on 2026-08-16. **This PR does not take the grant on faith.**

## What is new vs #10850 and #10913

A **preflight that dry-run pushes to the real remote on every tick**, before the tick does any work.

#10913 verified a credential fix against a **stubbed git** and it died on its first real tick — a stub models control flow and says nothing about which token git authenticates with. `git push --dry-run` is not a stub: GitHub authorizes at the `git-receive-pack` advertisement, before any ref is considered, so it returns the true 403/200 and updates nothing.

On a credential denial — and *only* a credential denial; a network blip must not silently re-point the credential — it swaps to `GITHUB_TOKEN`, **re-probes**, and reports which credential is live. The re-probe is what #10913 lacked: a repair that is applied and never checked looks identical to one that worked.

Failure mode is bounded: mis-scoped or revoked PAT ⇒ **degraded lane** (telemetry lands, gate does not start), loudly, via `::error::` + step summary. Never a dead lane.

## Which checkout gets the PAT, and why for each

| checkout | PAT? | why |
|---|---|---|
| **tick job** | **yes** | its credential performs `git push heartbeat/$AGENT`, and that push's actor is the entire question |
| **flush job** | **no** | #10850 put it here too — its second, latent break. Checked, not assumed: the only `git push` in this workflow is the tick job's; every git call in the flush job is read-only (`fetch`/`rev-list`/`log`/`config`). A credential that pushes nothing gets no push rights. |

#10926 reverted the flush-job PAT for a **stale reason** (it cited `flush-via-staging.ts`, which belongs to `society-heartbeat.yml`/`tick-metrics.yml`; this job runs the API-only `merge-heartbeats-to-main.ts`). Right conclusion, wrong reason — corrected in place.

Not "did the push succeed" — the push already succeeds today. The falsifier is **does `gate (required)` start on a `heartbeat/*` PR.** Verified by dispatching this branch's workflow (run `31962679616`), a real tick with real secrets:

**Before** — PR #10710, head `383883e0`: 6 checks, **zero gate**.

**After my tick's push (17:49:31Z):**
```
pull_request gate            in_progress  actor=AceHack   <- executes, not parked
pull_request CodeQL          success      actor=AceHack
```

## Honest limits

- The **fallback** path was not exercised in production (the PAT works, so nothing forced it). Its credential-swap mechanism was checked against real git + the real remote locally, not on a runner.
- Local experiment resolved what #10926 left open: **both** repair mechanisms (`--unset-all` + inline-URL creds, and `--replace-all` of the extraheader) work under real git. So the bench does **not** reproduce #10913's production failure and cannot predict it — which is precisely why the preflight re-probes rather than trusting its own repair.
