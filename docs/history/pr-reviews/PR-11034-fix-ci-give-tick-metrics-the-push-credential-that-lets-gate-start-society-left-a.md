## Description

# Summary

`gate (required)` never starts on the `heartbeat/tick-metrics` flush PR, for the same reason
#10986 fixed on `agent-heartbeat.yml`: **a `pull_request` run whose triggering actor is
`github-actions[bot]` is created and then parked — status `completed`, conclusion
`action_required` — so it never executes and never contributes a check.** The push that
creates the flush PR's head is the one whose actor decides this, and on this lane that push
is `flush-via-staging.ts`'s `git push --force-with-lease origin HEAD:refs/heads/heartbeat/tick-metrics`,
authenticated with whatever the checkout persisted — which was the default `GITHUB_TOKEN`.

This extends the proven cure to **one** lane and deliberately leaves the other as an
untouched control.

# The defect, re-measured on these lanes (not inherited from #10986)

Both candidate lanes were verified against the live API before anything was changed:

| lane | flush PR | head | `pull_request` runs | gate row in rollup | verdict |
|---|---|---|---|---|---|
| `heartbeat/tick-metrics` | #10588, open since 2026-08-14 | `c79a60c8` | 34, **all** `completed/action_required`, `actor=github-actions[bot]` | **none** (6 check-runs total) | defect present |
| `heartbeat/society` | #10708, open since 2026-08-14 | `e0f031ae` | 34, **all** `completed/action_required`, `actor=github-actions[bot]` | **none** (6 check-runs total) | defect present |
| `heartbeat/alexa` (positive control, post-#10986) | #11021 | `85f101a1` | `gate \| pull_request \| in_progress \| actor=AceHack` | gate run executing, 72 check-runs | cured |

So the defect is real on **both** lanes; neither is exempt and neither was fixed by accident.

# What changed

`.github/workflows/tick-metrics.yml` only:

1. **PAT on the checkout whose credential performs the push, and only that one.** Checked
   per-lane rather than assumed: this workflow has a single job and a single checkout, and
   the push it authenticates is inside `flush-via-staging.ts flush`. The `GH_TOKEN` already
   on the Flush step is a different credential doing a different job (`gh` PR creation) and
   was never the missing half. Two-rung ladder (`ZETA_TELEMETRY_FLUSH_TOKEN || GITHUB_TOKEN`),
   not the Flush step's three-rung one — `ZETA_PR_ARCHIVE_TOKEN` is scoped for PR creation
   and its contents-write standing is unestablished, so it is not a credential this push
   should silently land on.
2. **A preflight step** doing a real `git push --dry-run` to the real remote, probing a
   `credprobe/` ref rather than the live lane branch (HEAD is main and the lane has diverged,
   so a permission answer would otherwise be indistinguishable from an ancestry answer).
3. **Swap only on a credential answer** (`denied to` / `Authentication failed` /
   `Invalid username or token` / `error: 403`); anything else is annotated inconclusive and
   the credential is left alone, so a network blip cannot silently re-point it.
4. **Re-probe after the swap.** #10913's fallback ran, logged that it ran, and was denied
   under the same identity — a repair applied and never re-checked is indistinguishable from
   one that worked.

# The control, declared rather than forgotten

**`society-heartbeat.yml` is left byte-identical.** #10850 changed three lanes at once and
cost ~16.75h; one lane treated against one lane untouched is what makes the next real-tick
reading attributable rather than merely hoped-for. The control is asserted in the test
(`CONTROL` in `flush-via-staging.test.ts`), with instructions to move its entry into `TREATED`
in the same commit as the yaml change — so treating it later is a deliberate act, and leaving
it is never mistaken for an oversight.

Also **not** carried over, deliberately: agent-heartbeat's `gh workflow run gate.yml` dispatch
belt. Shipping two independent gate-starting mechanisms at once would make the real-tick
reading unattributable — if gate appears, which one did it? The credential is the mechanism
the measurement points at; the dispatch belt can be added later, on evidence.

# Notes

**The real-tick falsifier is NOT yet observed and this PR does not claim it is.** The lane
runs from `main`, so the first run under this change happens after merge. What must be read
on the next `heartbeat/tick-metrics` flush, and recorded as a PR comment:

```
gh api "repos/{owner}/{repo}/actions/runs?head_sha=<new head>" \
  --jq '.workflow_runs[]|select(.name=="gate")|"\(.event) \(.status)/\(.conclusion) actor=\(.triggering_actor.login)"'
```

Expected, by analogy with the alexa control: `pull_request <running> actor=AceHack` instead of
`pull_request completed/action_required actor=github-actions[bot]`. If it still reads
`github-actions[bot]`, the credential is not the whole story on this lane and that is a finding
to state, not to explain away.

**Blast radius if the PAT is wrong.** The preflight falls back and re-probes, so the worst case
is a *degraded* lane — telemetry still parks on `heartbeat/tick-metrics`, `gate` still does not
start, and the run says so loudly in an `::error::` and a step summary. That is exactly today's
behaviour, made visible. The #10850 shape (dead lane) requires a *silent* absent-token, which the
`||` ladder covers.

Not chased here: `lint (TS)` / `test (TS suite)` are red on `main` already and are not in the
`gate (required)` floor (`build-and-test`, `lint`, `cross-verify`, `full-verify`).
