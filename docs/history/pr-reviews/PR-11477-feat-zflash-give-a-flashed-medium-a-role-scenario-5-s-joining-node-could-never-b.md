## Description

## The premise, verified before building on it

The brief said zflash writes no firstboot config to the ESP. Checked rather than
assumed, and it holds:

- `planFileBackedZflashImage` (`lib.ts`) could emit exactly **four** ESP
  destinations — `/zeta-authorized-keys.pub`, `/zeta-hostname.txt`,
  `/zeta-creds.enc`, `/zeta-wifi-credentials.json`. None carries a role.
- `zeta-first-boot.sh` sources `/etc/zeta-firstboot.conf`, a file baked into the
  ISO's read-only Nix store by `usb-nixos-installer/nixos/installer/configuration.nix`
  shipping `HOST=control-plane`, then execs `zeta-install "$HOST"`. Under
  automation the tty1 role prompt takes that timed default.
- That configuration.nix comment defers a per-flash `--role` to "v2" scope.

So the role was an **ISO-build-time** decision the flash could not move, and a
second node installed a second control plane, ran no k3s agent, and therefore ran
no join observer.

### On `create-joining-disk` — the brief's third blocker

It is **not** the intended vehicle, and it is not related to role provisioning.
It is a member of the `MultiVMExecutionStep` union in `multi-vm.ts:273` and
nothing emits it — it named a step (create a blank qcow2 for the joining node)
that `executeMultiVMRuntimePlan` never performs. Dead union member, left as-is
here rather than folded into an unrelated change.

## What this adds

**Pure core** — `src/Core.TypeScript/zflash/firstboot-role.ts`. No I/O, no QEMU,
no filesystem. `resolveFirstbootConfig` applies defaults and returns typed
refusals; `composeFirstbootConfFileContent` renders a bash-sourceable file with a
key order fixed by the function rather than by object iteration, so equal inputs
produce byte-identical output. `HOST` is the emitted variable name because that
is what `zeta-first-boot.sh` already reads — renaming it would produce a file the
guest sources and ignores.

**The injection surface is guarded twice.** The file is `.`-sourced by bash on a
node about to partition a disk, so every value (a) must pass a conservative
allowlist — no `$`, backtick, quote, `;`, `&`, whitespace or newline — and (b) is
emitted single-quoted.

**Wiring.** `lib.ts` gains `/zeta-firstboot.conf` and `/zeta-join-token`
destinations, and **refuses** a token the config does not name — a write nothing
reads looks like provisioning and provisions nothing. `file-backed.ts` and
`prepare-boot-image.ts` gain `--role` / `--flake-host` / `--join-server-url` /
`--join-token`. `multi-vm.ts` carries each scenario-5 VM's required role as a
value a test can assert.

**Guest side**, so the ESP file is not a golden vector nobody opens:
`zeta-first-boot.sh` sources the ESP conf in preference to the ISO's (strictly
additive — no ESP conf, byte-identical prior behaviour); `zeta-install.sh`
installs the token at `/mnt/var/lib/rancher/k3s/agent/token`, which is exactly
where `k3s-agent.nix` points `services.k3s.tokenFile`, and stages the join URL;
`injected-join-server.nix` overrides `serverAddr` for **agents only**, mirroring
`injected-hostname.nix` including its `mkOverride 50` priority.

## What is NOT claimed

**Nothing here has been booted.** I cannot run QEMU in this environment. The end
-to-end path is **UNVERIFIED**. Verified: the pure TypeScript (372 unit tests),
`tsc` + prettier + style, `bash -n` on both scripts, `shellcheck -S error` clean,
`nix-instantiate --parse` on the new module. Unexercised: the ESP mount/probe
loop in `zeta-first-boot.sh`, the sed extraction and token install in
`zeta-install.sh`, and any evaluation of `injected-join-server.nix`.

So `joining-node-role-provisioning` **stays** in `JoinBlocker` — the same standard
`shared-l2-segment` is already held to. A provisioning chain that has never
provisioned anything is a claim, not a capability.

**A new blocker is named rather than left to be discovered at dispatch:**
`joining-node-address-assignment`. The shared segment is a bare QEMU socket with
no DHCP, no DNS and no router. Avahi/nss-mdns is the only name service on the
guests and answers for `.local` names only, so `k3s-agent.nix`'s default
`https://control-plane:6443` — a bare single label — cannot resolve there.
`SCENARIO5_JOIN_SERVER_URL` therefore uses `control-plane.local`, and the existing
node must be flashed `--host control-plane` (without it `zeta-install.sh`
generates a random `node-<6hex>`). Whether mDNS completes over IPv4 link-local on
that segment is **UNMEASURED**.

**Security, stated not smuggled:** `/zeta-join-token` is secret material stored
**plaintext** on a FAT ESP, which is a weaker bar than the constitutional rail
sets. It is never written implicitly, is intended for the QEMU harness, and the
correct home is the existing encrypted cred-blob path (081KSKBP80008QG0R003AX2A69).
Recorded as a gap in `INJECTION-POINTS.md` §6 rather than argued away.
