## Description

Three defects in the R7 cancel window **I landed in #13107**, found by *rehearsing* it rather than reading it. Each is the same shape as the bug that window was built to fix: a guard that reads as a guarantee and is not one.

## 1. Enter did not cancel

`read -n 1` consumes Return as its **delimiter** and yields an **empty variable** while still returning success. The loop tested `[ -n "$ZETA_CANCEL_KEY" ]` — so Return, the key a worried operator actually mashes, fell straight through.

Proven at the mechanism level, no tty required:

```
printf '\n' | read -r -n 1 -s -t 1 K   ->  rc=0  key=[]   len=0
printf 'x'  | read -r -n 1 -s -t 1 K   ->  rc=0  key=[x]  len=1
```

The old test cancels on `x` and **not** on Return. A successful read *is* a keypress; that is what is tested now.

## 2. Keypresses burned the countdown

Remaining time decremented once per **iteration**, but `read` returns immediately when a key arrives instead of spending its 1s timeout. A burst of keystrokes spun the window to zero in milliseconds.

Combined with (1): **mashing Enter consumed the entire window and failed to cancel** — the guard failing precisely when someone panics. The deadline is now wall-clock, so an early return cannot spend time it did not wait.

Local wall-clock is correct here and is *not* a shared-fold leak — it steers a local action (a UI timeout) and never enters a shared conclusion.

## 3. A successful cancel exited 0

`zeta-first-boot.sh` reads 0 as success, so deliberately aborting printed **"Install complete. Rebooting in 10s"** — and then rebooted. The abort was announced to the operator as a finished install.

Cancel now exits **10**, and the caller gives it its own branch. Collapsing it into "Install failed" would have been the milder version of the same lie; the cancel branch does not reboot.

The header comment claiming *"any keypress aborts to a shell"* was mine, and was false for the most likely key. It is now true.

## Checked, not assumed — including a rehearsal I threw away

My first harness drove both loop shapes through `script -q /dev/null` with piped stdin, which delivers **EOF rather than keystrokes**. Both arms reported `cancelled=YES` and the comparison was worthless. The mechanism test above replaced it, and needs no tty because the delimiter behaviour is what the bug turns on.

`bash -n` clean on both scripts.

**Still unproven, and unchanged by this PR:** `read -n 1` behaviour under systemd on tty1, and whether a serial-only operator can answer the window at all — output mirrors to `ttyS0` while stdin is `tty1`. Both are hardware questions.
