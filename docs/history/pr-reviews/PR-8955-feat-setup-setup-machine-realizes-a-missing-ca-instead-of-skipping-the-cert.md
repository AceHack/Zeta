## Description

## The ONE change

In `setup-machine.ts`, when the cert step finds **no local CA** (`~/.config/zeta/ca/` absent), instead of skipping the cert it now **realizes a CA** (`ca.ts` `ensureCa`) under the **same** `sessionBiometric` approval already in scope — **no second prompt** — then proceeds to sign. So a fresh host ends with **CA + machine key + cert under ONE fingerprint** (the solo / first-node / CA-holder case). Previously the cert was a clean skip.

## One approval covers it (proof)

The up-front `requireBiometric(session.door, …)` fires the human door once; the session gate caches that one decision and **replays** it to machine-keygen, `ensureCa`, and cert-sign — the underlying human door fires **at most once**. The added test asserts `prompts().length === 1` while the CA is realized **and** the cert is signed.

## Idempotent + fail-closed

- **Idempotent:** an existing CA is a no-op — `ensureCa` returns `exists`, no prompt, the CA is **never re-created** (test: CA-present run, `caGenCalls() === 0`).
- **Fail-closed:** a declined approval poisons the session → **nothing** realized (no CA), generated, or signed; the human is still prompted only once (test: declined run, all counters 0, `caRealized.action === "aborted-biometric"`).
- **`--dry-run`** stays end-to-end inert; the plan shows `would realize a new local CA` (verified via `--dry-run`).

## Deferred (kept tight, not built)
