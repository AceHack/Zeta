## Description

fix(heartbeat): the PR manifest is append-only too — a fourth path, not a regression

soraya's tick failed at 02:43Z (run 31988867656) on the same step the 2026-08-16 carry fix
addressed. It is not a regression, and the log says so in two adjacent lines:

    Auto-merging db/mutation-findings/soraya.jsonl          <- declared path, merged clean
    CONFLICT (content): Merge conflict in docs/github/prs/manifest.jsonl   <- undeclared

The three declared paths behaved exactly as designed; a FOURTH append-only file conflicted, and
the preparer failed the tick because an undeclared conflicting path is supposed to fail it. Typed
backpressure working, and a new member of the class surfacing behind it. Expect more of these as
merge volume rises -- roughly 15 PRs landed tonight, which is what put enough rows in this file
for a lane to diverge on it.

THE JUSTIFICATION IS DIFFERENT FROM THE FIRST THREE AND THE DIFFERENCE MATTERS. Those were safe
because single-writer. This one is NOT: `pr-archive-on-merge.yml` and `agent-heartbeat.yml` both
append, plus the derive/migrate tools. It is safe for a stronger reason -- append-only under a
globally unique key, with that uniqueness ENFORCED rather than assumed:
`pr-manifest-integrity.yml` fails on a "duplicate-keyed shard". If union ever duplicated a row, an
existing check goes red. Measured on this tip: 6776 lines, 6776 distinct pr_number.

Not covered, stated: union is wrong for an EDIT to an existing row. Nothing edits rows today
(archival appends once per PR on merge), and the integrity check would catch it if that changed.

MY FIRST TEST FOR THIS WAS VACUOUS AND I CAUGHT IT BY MUTATION. It called
prepareHeartbeatBranch("soraya") against a fixture that only pushes a heartbeat/alexa lane, so
remoteFound was false, NO MERGE RAN, and it passed with the .gitattributes line deleted -- a test
that passes for the wrong reason, in a test written to prove non-vacuity. Now pinned to the lane
the fixture actually pushes, with a comment recording the trap so the next person does not reset
it. Verified both directions: 10 pass clean, 1 fail with the attribute removed.
