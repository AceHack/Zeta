## Description

## The hypothesis, and why 75% was not the finding

A merge-conflict measurement on #11551 turned up one archived review doc reporting
`| Total threads | 0 |` for a PR that actually has a thread. `main` holds 8,075 archived
review docs; **6,097 (75.5%) report zero**.

That number proves nothing on its own and is not treated as evidence here. Most PRs in this
repo are agent-generated and auto-merged, so genuinely having no review threads is the
*expected* case. What made it worth a test is the **shape**: in the artifact, a zero meaning
*"we did not capture"* is indistinguishable from a zero meaning *"there were none."* Vacuity
class — a check that did not run looking like one that passed.

## Sample size, chosen before the run

Rule of three (Hanley & Lippman-Hand 1983, *JAMA*): zero events in n draws gives a 95% upper
bound of ≈3/n. I wanted the **null** outcome — "the archive is honest" — to license a bound
under 3%, i.e. ≤183 of 6,097 docs, at which the 75.5% headline moves less than one point.
3/n ≤ 0.03 ⇒ **n = 100**. Seed **4** (the repo's common seed), mulberry32 + partial
Fisher–Yates, printed so the draw replays. Cost counterweight: 100 GraphQL calls ≈ 2% of the
5,000 point/hour budget.

A second arm was added *because the mechanism predicted it*: if this is a truncating race
rather than a zero-specific bug, **non-zero** docs must under-report too. n=40 there — a
directional check, not a rate I extrapolate (its rule-of-three ceiling would have been 7.5%).

## Result

| population | n | seed | AGREE | UNDER-REPORT | OVER-REPORT | FETCH-FAILED |
|---|---|---|---|---|---|---|
| recorded `Total threads = 0` (6,097 docs) | 100 | 4 | 79 | **21** | 0 | 0 |
| recorded `Total threads > 0` (1,978 docs) | 40 | 4 | 32 | **8** | 0 | 0 |

GitHub's API was healthy for both runs — **0 fetch failures out of 140**, so no partial-sample
caveat is needed.

- 21/100 → Wilson 95% CI **14.2%–30.0%** ⇒ **864–1,828** of the 6,097 zero-docs misreport.
- The non-zero arm (8/40 = 20%, CI 10.5%–34.8%) is statistically indistinguishable from it.
- The archive **never over-reports**: 0 of 140.

**So the framing in the brief was itself too narrow, and that is the main finding.** This is
not "the zeros are fake" — it is a uniform early-snapshot truncation across the whole archive.
The zero class is simply where truncation is *total*, and therefore invisible. Both directions
the brief asked for are answered: the archive under-reports, and it does so beyond the zeros.

## Mechanism: a race — measured, not assumed

The brief guessed a race from the PR-9181 evidence and told me not to assume it. Checked all
four candidates:

| candidate | verdict |
|---|---|
| **race** (archive fetches before threads land) | **confirmed** |
| pagination cap | excluded — counts are 1–15; page size is 50 (threads) / 100 (comments) |
| API permission | excluded — the same credential fetches the missing threads now |
| parsing bug | excluded — 1,978 docs carry non-zero counts; the parser works |

The confirming measurement: for all 22 discrepant PRs examined,
`first_thread_comment_at − merged_at` is **positive** — min **+22 s**, median **+109 s**, max
+78 min, **zero negatives**. Not one thread that existed *before* the close event was dropped.

The clock it races: `pr-archive-on-merge.yml` triggers on `pull_request: closed`, and recent
runs complete ~40 s after the event. The thread authors are exclusively
`copilot-pull-request-reviewer` and `chatgpt-codex-connector` — automated reviewers that post
*after* merge. The archiver wins, records what it saw, and nothing revisits.

**Second-order finding.** The orphan drains (#11472) ship archive content **verbatim from the
original merge-time run** — they re-derive *set membership*, not API content. PR-9181's doc
landed on `main` today (2026-08-17) and still carries a July-2 zero. Draining does not heal
this; only a re-fetch would.

## Deliberately NOT fixed

No archived document is modified in this PR. Rewriting ~6,000 historical documents is a large,
hard-to-reverse action on the repo's own memory (§5 Memory Preservation), and the mechanism
being known does not make the scope decision mine. Measured, reported, stopped —
`081M08MVPR9087G0R000NCF8PV` carries three unranked candidate remedies for @AceHack to rule on.

Worth noting the cheapest one, because it does not touch history at all: record `fetched_at`
against `merged_at` **in the doc**, so a reader can see a zero was taken 12 s after close and
distrust it on sight. That converts the vacuity into a legible uncertainty for free.

## Mutation test (discipline #1)

Run on scratch copies in `/private/tmp/...`; the repo's archived docs were never touched
(`git status docs/history/pr-reviews/` clean throughout).

```
baseline           -> 9181 UNDER-REPORT, 10000 AGREE                  exit 1
A: 10000 0 -> 5    -> 10000 OVER-REPORT flagged                       exit 1
B: 9181  0 -> 1    -> both AGREE, the flag CLEARS on corrected data   exit 0
C: PR 9999999      -> FETCH-FAILED, excluded from the rate            (not agreement)
restored           -> baseline reproduces exactly                     exit 1
```

Mutation B is the one that matters: the flag tracks the data, not a constant. Mutation C is
the anti-vacuity guard — **a failed fetch is never agreement**, or the checker would reproduce
inside itself the exact defect it exists to find.

   one-off: ~1 in 5 archived docs.
