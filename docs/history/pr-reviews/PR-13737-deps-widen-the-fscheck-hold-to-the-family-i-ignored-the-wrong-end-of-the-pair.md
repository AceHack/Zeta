## Description

deps: widen the FsCheck hold to the family — I ignored the wrong end of the pair

#13676 held FsCheck.Xunit.v3 on major/minor. It did not work, and the timing is
unambiguous: that PR merged at 11:52:06Z and Dependabot opened #13696 at
12:13:18Z -- 21 minutes later, with the ignore live -- still carrying
FsCheck.Xunit.v3 3.4.0.

The ignore was on the wrong end of the coupling. From the published nuspec,
FsCheck.Xunit.v3 3.4.0 requires FsCheck [3.4.0] EXACTLY, so the two move as a
locked pair. #13696 bumps FsCheck 3.3.4 -> 3.4.0 -- which nothing ignored -- and
FsCheck.Xunit.v3 cannot stay at 3.3.4 against it. Ignoring the follower cannot
stop the leader from dragging it along.

Widened to the FsCheck* family, which is the unit that actually moves.

The underlying reason is unchanged and still measured: FsCheck.Xunit.v3 3.4.0
requires xunit.v3.extensibility.core [4.0.0, 5.0.0) while the tree pins xunit.v3
at 3.2.2, so the whole family is gated behind a xunit v3 -> v4 migration.
NU1608 under Warning-As-Error is what that looks like from CI.

LIFTS WHEN: xunit.v3 moves deliberately to the 4.x line, in the same change as
the FsCheck bump, so the exact pin can never be half satisfied.

A process note I am recording because it nearly produced a false report. While
diagnosing this I read my local clone and concluded the #13676 ignore had been
LOST in a merge -- git log showed one commit for the file, the entry was absent,
and merge-base said the merge commit was not an ancestor of main. All three were
artifacts of a clone 30+ commits stale behind a fetch that had not advanced. The
API showed the entry present on main the whole time. Verify the tree, not just
the command: a stale tree answers every question confidently and wrongly.
