## What

Aaron 2026-07-03: *"this sounds great lets continue."* Slice 1 made the mix's **parameters** data (loadImm descriptor, `MixCall` value). Slice 2 makes the mix **algorithm** data.

`specializeMem`'s per-effect decision procedure — `setreg` folds into the register state, `setmem` into memory, `halt` drops — was hard-coded F# match arms. It's now a **`mixDef` rule table** read by a fixed abstract-action engine (`IsaSpec.specializeReified`):

```
mixDef = { rules: [ {e, action, target} ] }   // action ∈ {fold, drop}, target ∈ {reg, mem}
```

The algorithm's **shape** is a value. And crucially the **same `defaultMixDef` drives every ISA** — it's over the effect vocabulary, not opcodes — so the partial-evaluation algorithm is one data object that specializes CHIP-8 and the 6502 alike.

## Tests (3 new, 7 MixIr total green — build 0/0)

1. **faithful** — the reified algorithm reproduces native `specializeMem` byte-for-byte (CHIP-8 + 6502)
2. **one algorithm, every ISA** — the identical `defaultMixDef` value drives both ISAs
3. the algorithm is **byte-lockable** data

## Honest scope

This reifies the mix's **decision procedure** (which effect folds into which state, which drops). The engine's **control** — the iteration loop and the abstract-value evaluation — is still native. Reifying those too (the whole PE as an IR program `mix` can run on itself) is the final slice.

Progression: **slice 1** = mix parameters as data + `gen(gen)==gen`; **slice 2** = mix algorithm as data, one object for all ISAs.
