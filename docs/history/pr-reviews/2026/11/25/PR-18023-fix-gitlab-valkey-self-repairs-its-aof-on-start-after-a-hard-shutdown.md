## Description

Why: a power cut left gitlab-valkey crash-looping on an AOF whose incremental file ended in 682 NUL bytes after a complete command. Valkey's default aof-load-truncated forgives only a cut-off final command, so the server refused to start and nothing in the pod repaired it. GitLab web stayed down.

What: an idempotent `aof-repair` init container (check; only on error back up to a timestamped dir, keep 3, then valkey-check-aof --fix; unrepairable: keep backup, move AOF aside, start empty), pinned durability flags, 60 s grace period. See commit 89765f0 and docs/ops/GITLAB-VALKEY-HARD-SHUTDOWN.md.

Falsifier: src/Core.TypeScript/cluster/gitlab-valkey-aof-self-heal.test.ts (13 tests, 0 pass / 13 fail before, 13 pass after, incl. a real Valkey 7.2.14 container). 18 neighbouring cluster tests: 631 pass. Node proof on a scratch pod over a copy of the live AOF: healthy is a no-op, NUL tail self-heals with backup kept, second run is a no-op.

Follow-up: the shared redis Application has the same exposure and no repair.
