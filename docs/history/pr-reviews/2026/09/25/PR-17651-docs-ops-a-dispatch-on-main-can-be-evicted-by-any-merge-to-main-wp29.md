## A dispatch on `main` can be evicted by any merge to `main`

Two lost CI runs tonight — WP25's and mine — to a rule that is not guessable from the workflow file.

The concurrency group is `${{ github.workflow }}-${{ github.ref }}`, and `github.ref` is `refs/heads/main` for a **dispatch on main** *and* for **every push to main**, so they share one group. `cancel-in-progress: false` correctly protects a *running* run — but GitHub keeps only the **newest pending run per group**. A dispatch queued behind a push is therefore evicted by the next merge.

**Measured:** run 36090644178 (`workflow_dispatch` on `main`, 03:30:38Z) sat `pending` behind a push from 03:27 and was cancelled at 03:46:53Z when the next merge landed. Three hours of QEMU, never started. It reports `completed/cancelled`, which reads like somebody cancelled it on purpose.

**The workaround** — what turns two lost runs into a technique:

```bash
git push origin origin/main:refs/heads/<you>/<purpose> -f
gh workflow run build-ai-cluster-iso.yml --ref <you>/<purpose>
```

A different `github.ref` is a different concurrency group, and the tree is byte-identical to main's tip.

## `--paginate` is not optional here, and the failure is silent

A PR on this repo can carry 110+ check runs. `per_page=100` without `--paginate` returns one page, so a query filtered to a check that lands on page 2 comes back **empty** — which reads exactly like "not reported yet". WP30 waited eighteen minutes on a check that was already green. Recorded next to the "confirm the dispatch took" recipe, which is where someone will be running exactly these queries.
