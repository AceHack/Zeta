## Root cause

An isohybrid ISO's MBR partition 1 starts at **LBA 0** and spans the whole image, so `/dev/sda` and `/dev/sda1` expose the **same iso9660 filesystem with the same `ZETA_INSTALL` label**. `/dev/disk/by-label/ZETA_INSTALL` resolves to whichever udev processed last. When it lands on the whole disk, the boot medium is mounted from `/dev/sda`, that mount holds the device `O_EXCL`, and `mount` on any partition of it returns `-EBUSY` — util-linux's `fsconfig system call failed: /dev/sda2: Can't open blockdev`.

**Measured**, run 36073981145, five lanes that print the ESP scan, same ISO, minutes apart:

| lane | `/dev/sda1` | `/dev/sda2` |
|---|---|---|
| restore / wifi / keyfile / retention | openable (iso9660, not FAT) | **mounted** |
| **picker** | **Can't open blockdev** | **Can't open blockdev** |

`/dev/sda1` is byte-identical in all five. A filesystem property cannot vary like that; a claim on the device can — and the failing lane's own `lsblk` names it: `sda 8:0 0 1.6G 1 disk /iso`, the whole disk mounted.

**Reproduced locally, end to end**, on the real installer ISO over a loop device: `mount -t vfat` on the ESP partition succeeds with the whole disk unclaimed, and all three existing rungs are refused (`already mounted or mount point busy`) the moment `mount <wholedisk>` is held — including on `p1`, which is not FAT at all. Control and treatment on the same bytes, seconds apart.

## This is not a CI defect

A USB stick is the same image with the same LBA-0 partition 1, the same duplicate label and the same race. On the losing side of the coin an operator gets **no injected SSH pubkeys**, a random `node-<6hex>` instead of the hostname they chose, **no wifi credentials** and no firstboot conf — with nothing said about any of it. Run 36044770870's guest did exactly that and came up as `node-24cfc8`. The severity reframe is now at the top of the work item, above the CI framing it was filed under.

## Rung 4

`mcopy -s -n -o -i /dev/sda@@<offset> ::/ <tmpfs>` — reads the ESP through the **whole disk**, so it never opens the partition and the claim does not block it.

- **Chosen over `losetup -r`** because it is the smaller answer: no loop device to allocate and release, no kernel FAT driver, and it is the exact inverse of how the ESP was **written** (`mcopy -i img@@offset` on the host). `mtools` ships in this ISO's `systemPackages` beside `util-linux` — checked, not assumed.
- **The offset is DERIVED, never constant.** `lsblk -bno START` reads sysfs, so it needs no open of the partition — which is the whole point. Unreadable, non-numeric or zero **refuses**. This work item began with a fallback constant that was wrong and could not disagree with itself; a second constant would be that mistake twice.
- **Read-only by construction**: a copy onto a fresh tmpfs at the caller's mountpoint, so every consumer keeps working on a path and the caller's own `umount` still cleans up. The `rw` ledger mount is untouched.
- **Announces itself** as `via=mtools-copy:/dev/sda@@137216`. A run the fix carried must not read as a healthy one.
- **Verified against the shipped function with the claim actually held**, not in a clean environment.

## Evidence capture — closing the gap rather than arguing it

I said the healthy side of the comparison was *inferred*, because `lsblk` prints only from a diagnostics block that runs only on failure. The scan now records `boot-medium=` (`findmnt -n -o SOURCE /iso`) and resolves by-label symlinks inline as `part->target`, **on the healthy path too**. The next occurrence proves itself.

And the squeeze strips util-linux's `mount: <mountpoint>: ` prefix before truncating — measured, the 64-char cap spent 36 characters on the mountpoint and cut the answer at `Can_t_o`.

## Falsifiers

Seven new cases driving the **shipped** shell functions: rung 4 carries an unopenable partition with the right derived offset and tmpfs; refuses an unreadable start, a start of 0 (the whole-disk alias), and an unresolvable parent; unmounts its own tmpfs on a failed copy-out; is **not** reached when an earlier rung works; and the squeeze keeps the kernel's half of the message.

The harness's `mount` stub now **refuses** past the end of its scripted list rather than aborting on an unbound array element — that abort would have killed the harness mid-run and parsed every field to empty, which is the defect class this file exists to refuse, and it bit this file once already.
