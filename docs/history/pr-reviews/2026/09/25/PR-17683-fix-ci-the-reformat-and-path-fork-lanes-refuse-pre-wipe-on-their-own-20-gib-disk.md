## Description

fix(ci): the reformat and path-fork lanes refuse pre-wipe on their own 20 GiB disk — it was never the 1400 GiB one (WP35)

081M3CAJD7J087G0R0021H6WRS.

THE SUSPECT IS ELIMINATED BY MEASUREMENT, AND THAT IS THE MORE USEFUL HALF.
`scenario 3 — reformat with retention` and `scenario 4 — path-fork migrate vs
fresh` were failing on a 30-minute wall-clock timeout, and the obvious suspect was
#17631 raising the QEMU virtual disks from 40 GiB to 1400 GiB: both scenarios are
reformat-heavy, so perhaps `mkfs.ext4` on a ~1279 GiB longhorn1 partition had
stopped being free. It had not, and they never ran on that disk.

The retention/path-fork harness has its OWN disk constant —
`DEFAULT_DISK_SIZE_GB = 20` in `zflash/test-harness/qemu-state.ts`, unchanged
since the harness was first committed (6c8dd6a876, #6220) — and nothing in the
tree passes `diskSizeGB`. `QEMU_DISK_SIZE_GB = 1400` lives in
`ci/qemu-full-install-test.ts` and is reached only by the plain-install lanes,
which is exactly why those pass and these two do not. There is nothing to time:
`mkfs` is never reached, because nothing is ever wiped.

WHAT THE SERIAL LOGS ACTUALLY SAY. Run 36097366591, artifacts
`b0891-retention-serial-logs` and `b0891-path-fork-serial-logs` — both ~2.7 KB,
where a full install produces ~76 KB:

  Internal storage devices (fixed; USB and hot-plug bays excluded):
    /dev/vda              HDD        20G    serial=

  ERROR: BOOT disk /dev/vda is 20 GiB, which cannot hold ESP 1 GiB + root floor
  120 GiB + a 1 GiB minimum longhorn1 tail (need >= 122 GiB). ... Nothing has
  been wiped. ... (3) install anyway on a MINIMUM 1 GiB tail with
  ZETA_ALLOW_LONGHORN_UNDERSIZED=1 ...

  [zeta-first-boot] Install failed (rc=1). See output above.
  [zeta-first-boot] Dropping to interactive shell.

Scenario 4's bootstrap log carries the byte-identical refusal.

THE ACTUAL REGRESSION is #17616's pre-wipe root-floor refusal. The plain-install
lanes were unblocked TWICE — first by staging the override on the flashed image's
ESP (#17618), then by #17631 giving them a disk the roster genuinely fits on. The
retention and path-fork lanes were unblocked NEITHER time. `allowLonghornUndersized`
has been threaded lib.ts -> file-backed.ts -> prepare-boot-image.ts since #17618,
and nothing ever set it. The 20 GiB disk was correct before #17616 and became a
refusal after it, silently, because nothing tied the two facts together.

FIX 1 — THE OVERRIDE IS DERIVED, NOT PINNED. `harnessDiskNeedsLonghornOverride()`
compares the harness disk against the installer's own floor
(`ZETA_ESP_GIB + ZETA_ROOT_FLOOR_GIB + ZETA_LONGHORN_MIN_TAIL_GIB`). These two
lanes test partitioning, retention and the migrate-versus-fresh fork — install
MECHANICS, never a claim about capacity — so the named override is the honest way
for them to run below the floor, and the installer's own refusal text says so. The
plain-install lanes take the opposite answer and must: their claim IS capacity, so
#17631 gave them a disk that fits precisely to stop them exercising the override.
Deriving it rather than writing `true` means raising the harness disk past the
floor disarms the override by itself, instead of leaving a stale concession that
quietly keeps testing the wrong path.

FIX 2 — THE 30 MINUTES WAS DEAD WAIT, SO IT IS NOT A TIMEOUT PROBLEM. The refusal
lands ~2.5 minutes in (30 s DHCP + 90 s ethernet + 30 s discovery probe); the
harness then serves out the remaining ~27 minutes of its 1,800,000 ms budget —
about 55 runner-minutes per dispatch across the two scenarios. `nixos@zeta-installer:~`
is ALREADY a terminal marker and IS present, but the wait loop suppresses that one
marker while `serialFirstBootInProgress` holds, and it holds forever once
"[3/3] Running zeta-install" has printed. The suppression is right — the login
banner appears long before an install finishes — and its cost is that a first boot
which reached the shell BECAUSE IT FAILED looked identical to one still working.
`[zeta-first-boot] Install failed (rc=` closes that door: emitted only in the
branch where zeta-install returned neither 0 nor 10, and that branch does nothing
but drop to a shell. Same failure class as 081M24BB3TD087G0R001PJTW9A, through a
different door.

NOT DONE, DELIBERATELY. The timeout is not raised — it was never the constraint.
The disk is not resized — 20 GiB is right for what these lanes test, and resizing
would make them slower proxies for lanes that already exist.

FALSIFIERS: `zflash/test-harness/longhorn-floor.test.ts`, ten tests. The floor is
PARSED out of `zeta-install.sh` rather than restated, so the two copies cannot
drift; the boundary is pinned at the floor and one below it; the marker is checked
against the emitter's own format string; and one test REPLAYS the measured serial
output, asserting both that first-boot-in-progress suppression was what hid it and
that the new marker is not suppressed. Reverting either fix turns four of the ten
red — measured, not assumed.

WHY IT MATTERS BEYOND CI. These two scenarios are the only coverage of an operator
reflashing over an existing install and of the migrate-versus-fresh decision — a
second install on the same machine, or an upgrade. Both are ordinary things a
person does with a USB stick and both have been unverified since #17616.

OUT OF SCOPE, FOUND IN THE SAME LOG AND REPORTED RATHER THAN FIXED:
`zeta-cluster-discover: discovery could not run (browser-error: avahi-browse
exited 1: avahi-browse: unrecognized option '--no-db-lookup')`. Bootstrap-or-join
discovery has never run in these lanes; it falls back to the ISO default role every
time. The harness says so honestly — "This is a check that did not run, NOT a check
that passed" — but the flag is wrong against the shipped avahi.
