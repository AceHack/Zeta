The previous fix worked: no wait_for_unit anywhere near a poll loop, and all
three assertions on the observable effect passed.

WHAT FAILED, AND IT IS THE FIXTURE, NOT THE CLAIM. TARGET 2 hand-wrote a fake
token, 'K10deadbeef::server:0000...'. k3s never reached the datastore
comparison with it -- 25 times it died earlier, at token NORMALISATION:

  level=fatal msg="Error: preparing server: failed to bootstrap cluster data:
  failed to reconcile with local datastore: failed to normalize server token;
  must be in format K10<CA hash>::<username>:<password>"

A malformed token tests k3s's PARSER. This test is about its datastore
RECONCILE. So the bad token is now derived FROM THE REAL ONE with sed,
replacing only the password field after the final colon: the K10<real CA
hash> and the username survive, normalisation passes, and the mismatch lands
where it is supposed to.

AND TARGET 2 IS NOW OBSERVED, NOT REQUIRED -- the same disposition, for the
same kind of reason, as target 3 in k3s-agent-tls-self-heal.nix. Whether a
wrong token reaches the STILLBORN fatal specifically is a fact about k3s
internals on this substrate (single-node, embedded etcd, --cluster-init), and
this run measured how easily you get a different fatal instead. A bounded poll
decides which happened and BOTH BRANCHES PRINT, so a green run's own log says
which one it took -- an observation that was skipped must never look identical
to one that passed, which is the defect class this entire work item is about.

WHAT STAYS UNCONDITIONAL, on both branches: the datastore, its files, and the
sentinel are all still present after whatever k3s was failing with. That is
what the module actually promises, it does not depend on which fatal was
reproduced, and it is asserted on every run. TARGET 1 likewise stays required.
The refusal path's own logic remains pinned over fixtures in
k3s-datastore-bootstrap-recovery.test.ts, which runs on the bun path.
