## Description

Thirty-nine PRs landed on this trajectory in one session. This is the handoff document: what is **measured**, what is **not**, and the operational traps that cost real time.

## Why it is shaped this way

The maintainer's question was whether the helm applications start correctly on a real USB install. The honest answer has two halves, and a summary that gives only one of them is worse than none — so the doc splits them:

- **On an adequately-resourced node nothing crash-loops.** 25/49 Applications converged, 4 correctly excluded, and a grep for `Evicted|OOMKill|MemoryPressure|DeadlineExceeded|Liveness probe failed` returns **0** on run `36117868219`. The 20 unfinished are unfinished, not failing.
- **On a memory-constrained node applications DO crash-loop**, and the mechanism is measured rather than inferred: 61 kubelet liveness-kill events over 28 containers, six exits of 137 with `Reason: Error`, zero `OOMKilled`, zero `Evicted`. The probes kill the containers before the OOM killer reaches them. `coredns` and `metrics-server` are among the 28 and are the node's own floor — which is why the follow-up orders the work floor-first, re-measure, then the remainder.

## What it carries

- Per-verdict state of the installed-disk lane, including verdict 7 reading **false** and why that is the honest reading.
- Which of the five lanes answers which question, and the measured reason the unconstrained Docker replica is **systematically optimistic about CPU** (`buildDockerRunArgs` sets no `--cpus`/`--memory`/`--cpuset-cpus`).
- Nine defects fixed, each with its before/after figure rather than a description.
- An **Open** table that includes the one thing nobody could measure — whether the roster converges on 16–22 core / 66 G hardware. The CI guest is 4 vCPU / 12 GiB and the runner is itself 4 vCPU, so that is a hard ceiling, not an oversight.
- Operational traps: `per_page=100` silently truncating past 100 check-runs, `-F` vs `-f` for boolean dispatch inputs, dispatch-on-main eviction, `git push origin <name>` pushing the named ref rather than HEAD, and Windows `rm -rf` following a directory junction into the shared `node_modules`.
- The defect class that found most of the rest: thirteen instances in one session of a check whose **failure and absence are indistinguishable**, three of them inside machinery written to catch it — with the tell that caught it twice, *a result that was too clean*.
