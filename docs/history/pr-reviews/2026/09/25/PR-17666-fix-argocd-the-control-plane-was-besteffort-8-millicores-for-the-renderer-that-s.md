## The finding

Dispatch **36097310492** (WP11, real installed disk, 90 min) watched the ArgoCD roster peak at **25/35** Synced+Healthy at t=1214s and fall to **13/35** by t=3007s, flat across the last four samples 723s apart.

**Every ArgoCD container was BestEffort.** `helm template` at the pinned argo-cd 10.8.0, against both pin sites' own values, renders nine containers with `requests` absent — the chart ships `resources: {}` for every component, and neither `k8s/bootstrap/argocd-install.yaml` nor the self-management Application set a single one.

In cgroup terms that is `cpu.weight` **1 of 507** at the metal rung: **~8 millicores** of a 4-vCPU guest, shared across seven pods. A repo-server rendering 49 Applications' Helm charts on 8 millicores is the `DeadlineExceeded ... failed to generate manifest` reported by 19 of the 100 unconverged rows. **The deadline was never the binding constraint.**

**The finding was not missing — it was unacted.** `missing-resource-requests.ts` has printed `full-ai-cluster/argocd` as ACTIONABLE row #1 since 2026-09-04, and its own header names argocd in the BestEffort set. A check nobody acts on is one step past a check nobody reads.

## Eviction was my first answer, and it is refuted

Commits 4 and 5 are a retraction and its resolution, kept as **separate commits** so the correction is auditable rather than buried in a rewrite.

I wrote "what goes backwards is what gets EVICTED" into five files. That was an inference from two measured facts, presented as a finding. The same dispatch's artifact refutes it:

```
evicted / OOMKilled / MemoryPressure / oom_reaper / "Out of memory"   = 0
kernel-side "Out of memory: Killed" / "Memory cgroup out of memory"   = 0
```

And the crosstab puts the regression on the **sync axis, not the health axis**:

```
 22  sync=Unknown    health=Healthy    <- comparison failed, WORKLOAD FINE
 25  sync=OutOfSync  health=Healthy
 21  sync=Synced     health=Progressing
  0  sync=Synced     health=Missing    <- the eviction signature, ABSENT
  1  sync=Synced     health=Degraded
```

47 of 102 rows sat at `health=Healthy`; six of the final twelve read "Failed to load TARGET state" while LIVE state read fine. **The pods were up. ArgoCD could not render what they should be.**

**The branch survives the retraction unchanged, and that is the point rather than a rescue.** Eviction is repaired by moving off BestEffort; a slow renderer is repaired by a repo-server with CPU. Same root cause — a control plane with no reserved capacity. Not one number moved; only the claims around them. **The falsifier asserts on the REQUEST, not on the mechanism**, which is why none of its 22 cases needed rewriting. That was the load-bearing design decision: a check pinned to a mechanism documents a belief, not a defect.

## The prediction this makes — stated before the next run

The roster over-commits the guest's memory at both rungs (**1.47x** dev, **2.09x** metal) and that did **not** bite, because only 35 of 49 Applications were ever created — `zeta-root` never completed a comparison, so the roster never reached full memory demand.

> **The CPU starvation prevented the memory over-commit from ever manifesting.**

So the failure mode should **MOVE, not vanish**. More Applications deploy; memory becomes the next wall. If the next dispatch shows pressure or eviction where this one showed none, **that is this change working and the 1.47x arriving on schedule** — not a new defect.

## What lands

**1 — requests on the ArgoCD control plane, both pin sites.** 750m/1408Mi at metal, 275m/768Mi at dev, across repo-server, application-controller, server, redis, applicationSet. **Requests only, no limits**: a CPU limit throttles the renderer, a memory limit OOM-kills the controller that has to recover. Five governed `resourceClaims` rows; the `ungovernedRequests` argocd row retires.

**2 — `k3s-server.nix` / `k3s-agent.nix` reservations.** `Allocatable == Capacity`: nothing was held back for the k3s server process, which on k3s hosts the apiserver, scheduler, controller-manager and kine **inside a systemd unit, outside every pod cgroup**. `single-node-readiness.ts` has printed that sentence on every run for weeks. **Pod-level requests cannot reach it** — which is why this half stays even though the PR is long, and leader-election lease renewal is exactly the observable that would tell you whether it worked.

One absolute number is defensible on both hardware profiles because **the k3s server's load tracks the CLUSTER, not the NODE**: same 49 Applications either way. Cost: 18.8% CPU / 16.6% RAM on the 4-vCPU guest, 4.7% / 3.2% on a 16-core node. Agent reserves less (250m/512Mi) because it runs no apiserver.

*A hazard in my own change, caught:* `--eviction-hard` **replaces** the default map rather than merging, so passing `memory.available` alone would have silently deleted `imagefs.available<15%` and `nodefs.inodesFree<5%` — a disk-exhaustion regression shipped as a memory fix, on a node that pulls ~135 images. All four signals written out; only `memory.available` changes.

**Honest limit, in the file:** without `--kube-reserved-cgroup` these are **accounting, not enforcement**. The enforcement form is declined deliberately — a misconfigured one makes the kubelet refuse to start, which on a first-boot installer is an unrecoverable node.

**3 — the falsifier.** Adoption values parity + no-BestEffort, in `audit-argocd-pin-parity.ts`. Proven red by mutating the **real** files, not only fixtures.

## Two defects found while fixing the first

**The mirror that was not a mirror.** `Application.yaml` has claimed in prose since it was written that "adopting this Application is a no-op transition." Rendering both value sets: bootstrap **6** workloads, Application **7**. Four keys absent here, so adoption at **sync-wave -90** — the earliest wave, while ~135 images pull — turned dex back on and added a Deployment. Repaired; the two sets are now render-equivalent, verified.

**`applicationSet.enabled` is INERT at 10.8.0.** No such chart key, and the ApplicationSet Deployment is ungated — it renders unconditionally. Real at 7.7.10; the 7.7.10 to 10.6.0 bump orphaned it. Removal verified render-neutral.

Filed separately as **081M3BTKNNB087G0R000EPCNJ1**, because *why nothing caught it* is bigger than the key: `inert-valuesobject-keys.ts` scans **Applications**, and this lived in a **bootstrap** manifest. The whole `k8s/bootstrap/` tree — the manifests K3S applies at first boot, before ArgoCD exists to correct anything — has **no inert-key coverage at all**. It surfaced only because the parity repair copied the key into an Application for the first time.

## Capacity, checked both directions

`compute-provenance` goes **12215m to 12965m** against an unchanged **16000m** floor: green, 3035m spare. Memory 27147Mi of 62942Mi.

**The dev lane does not fit, and is carried as pinned debt** (`dev memory 9868>9216`) rather than absorbed by shrinking requests. The honest reading: it never fit. It declared 9100Mi of a 9216Mi budget while **26 of 49 Applications declared nothing at all** — an undercount with 116Mi of decoration on top, and the first honest pricing of any of those 26 was always going to end it. 18 ACTIONABLE Applications remain; pricing them moves this number further the "wrong" way, which is the measurement improving rather than the tree getting heavier.

## Replica fidelity, measured

`buildDockerRunArgs` sets **no `--cpus`, no `--memory`, no `--cpuset-cpus`** — the container gets the whole runner host with no hypervisor tax, while the installed-disk lane runs `-m 12288 -smp 4` inside a 4-vCPU runner that is also running QEMU. **The replica is systematically optimistic about CPU**, the one axis that matters for this organ, which is why it reached 35 Healthy of 42 where the installed disk fell to 13 of 35. With eviction refuted, CPU headroom is the remaining explanation.

A green replica run is evidence the roster is **internally consistent**, never that it converges on constrained hardware. Recorded in the harness; **not fixed here** — `--cpus=4 --memory=12g` would invalidate every baseline in that file and deserves its own change.

## Rejected, on the record

- **repo-server replicas** — a second replica of a starved process halves each share and doubles resident memory on a node already over-committed.
- **timeout relaxation** — more wall clock made it worse; a longer deadline cannot outrun a renderer with 0.2% of the box.
- **`reposerver.parallelism.limit`** — correct, but **second**: bounding concurrency helps only once the renderer has CPU to bound.
