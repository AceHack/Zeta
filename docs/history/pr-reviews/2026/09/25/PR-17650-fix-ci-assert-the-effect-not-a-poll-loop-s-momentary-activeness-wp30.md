081M39CR74D087G0R002BEG2G4. The VM test added by this PR went red on its own
first wired run (36089766331) -- in the HARNESS, not in the module. Recording
what it measured, because the run is evidence either way.

WHAT THE RUN PROVED GREEN, on a real k3s, on the serial console, in order:

  t=34s  VERDICT unbootstrapped-watching: datastore ... has not served yet
         and k3s has restarted 0 time(s) (threshold 2) -- watching
  t=35s  [sentinel] this datastore has now served (readyz succeeded); wrote
         /var/lib/rancher/k3s/server/db/.zeta-datastore-has-served
  t=44s  VERDICT served: marker present ... will never be auto-discarded

The middle line is TARGET 1 and it is the whole reason this test exists. The
sentinel writer's DEFAULT readyz command really does succeed against a real
k3s from inside its real systemd unit. Had it not, no sentinel would ever be
written on any node, every healthy datastore would read as stillborn, and the
module would cause the data loss it exists to prevent -- silently, with the
recovery path firing exactly as designed. That is now measured, not assumed.
The first and third lines also confirm the verdict machinery on real hardware
shape: two different states of one boot, arriving as two different lines.

WHAT WENT RED, AND WHY IT IS THE HARNESS: wait_for_unit on
zeta-k3s-datastore-bootstrap-recovery.service, timing out after 121.02s on a
node where that unit was working correctly. Both units are Type=simple with
Restart=always / RestartSec=10s -- they run for ~80ms, exit 0 ("Deactivated
successfully", all over that run's journal), and start again 10s later. They
are INACTIVE for ~99% of wall-clock, and wait_for_unit waits for ACTIVE. It is
a coin flip against a poll loop.

THE WORSE HALF IS THAT IT WON THE OTHER FLIP. The same predicate PASSED on the
sentinel unit moments earlier, by luck. A green from it would have meant
nothing at all -- a check that can pass without its subject being healthy, in
the test written to prove a guard is not a check that cannot fail.

So both calls are gone. The test now asserts the observable EFFECT -- the file
that got written, and the verdict lines by name -- which is what the module
promises. wait_for_unit survives only on k3s.service, which is genuinely
long-running.

Also records the step's MEASURED cost in the workflow comment rather than
leaving the next person to discover it: 4m 00s on that run, 121s of which was
the timeout a correct predicate does not pay; its same-shape sibling measured
3m 01s on the same run.

## Second commit: gate the two orphaned NixOS lanes on `only_wp11` too

A WP11-scoped dispatch is a deliberately NARROWED probe. Three of this workflow's ten NixOS test steps never carried the guard that implements that narrowing. One was mine (fixed before #17646 merged); the other two were orphaned — WP25 is stopped, and the HA step belongs to a filed work item nobody has started — and are fixed here with authorization. **Trigger condition only; no step's assertions change.**

Measured on run 36089766331: served-datastore step 4m 00s (121s of it the timeout this PR's first commit removes), self-heal step 3m 01s — both billed to any narrowed probe.

They needed *different* fixes:

1. **`zero-length k3s credentials self-heal on boot`** — a step in `build` beside eight guarded siblings. Gets the identical step-level condition.
2. **`3-node HA cluster survives losing a replica-holding node`** — gated at the **job** level instead. A step-level guard would be half a fix: `cluster-ha` is a 120-minute three-guest lane whose Checkout / Free runner disk / Install Nix / memory-sampler steps are its own setup, and a skipped final step still pays for all of it. Its condition `github.event_name == 'workflow_dispatch'` admitted every dispatch including `only_wp11=true`, so a probe narrowed to one installed-disk boot was also standing up a 3-node HA cluster with replicated Longhorn. `only_cluster_ha` is unaffected (`&&` short-circuits, orthogonal input); PR/push never reached the job.

**Ten of ten now**, by two mechanisms, with comments saying which and why. **No step was found that should legitimately run on a scoped dispatch** — if one is ever added it needs a comment saying so, because an intentional omission and a forgotten one are the same absence.


### The `cluster-ha` guard is not a way of silencing a red

That job has been failing intermittently and it is filed as its own work item (etcd quorum symptoms after the node kill, possibly nested-VM disk latency rather than a product defect). Gating it out of `only_wp11` dispatches does not hide it: **it still runs on every unscoped dispatch, which is the only trigger it has ever had.** No trigger that ran it before this change stops running it, except the narrowed probe that should never have been running it.

One correction to the record while checking this — it is **intermittent, not uniformly red**. Measured across the three most recent dispatch runs:

| run | cluster-ha | duration |
|---|---|---|
| 36073981145 (09-24 23:45) | failure | 14m 29s |
| 36044770870 (09-24 18:56) | **success** | 42m 36s |
| 36020388280 (09-24 15:28) | failure | 49m 57s |

So the work item is a flake investigation, not a permanent breakage, and the 42m green is the measurement that makes it one. Recorded here rather than left as "it has been failing every time it runs".

### Count, corrected

Eleven Nix/NixOS steps carry the narrowing, not ten — `Nix eval checks — cluster CIDR derivation + server-join model` is the eleventh and was already guarded. Nine of eleven before this commit, **eleven of eleven after**. The `cluster-ha` job's condition is spelled `!inputs.only_wp11`, symmetric with the `build` job's existing `!inputs.only_cluster_ha`, rather than the step-level `!(github.event_name == 'workflow_dispatch' && inputs.only_wp11)` spelling — the job clause already requires `workflow_dispatch`, so the longer form would be redundant there.
