## Description

**Verdict 7 ran for the first time (dispatch `36097310492`) and emitted nothing.** Verdicts 1–6 passed on the installed disk at t=152s. Three defects, all in the **check**, not the cluster. The cluster's own finding is filed separately as `081M3BPJNRS087G0R0008WFXBZ`.

## 1. A bound that outlives its reader is not a bound — the verdict never exists

I sized the bound at 4200s and claimed the harness's `K3S_VERIFY_TIMEOUT_SECONDS` (4500s) left ~300s of slack. **It does not.** The harness counts from the **phase-3 login**; the unit counts from its own **ExecStart**.

**MEASURED: the two clocks are ~770s apart.** The harness stopped reading serial while the unit was still polling at its own `t=3730s`. No JSON block was written; verdict 7 was **ABSENT**.

One thing worked exactly as designed: `summarizeK3sFirstBootVerifyVerdict` treats an absent verdict 7 as a **FAILURE**, never a pass. **That guard earned its keep on the first run** — without it this would have been a silent green.

**Bound → 3000s**, sized from the measured offset plus a reporting budget. **This is not relaxing a bound to make a run pass — it is the opposite**, and the data says it costs nothing:

| t (unit clock) | Synced+Healthy |
|---|---|
| **1214s** | **25 / 35 — the peak** |
| 3007s | 13 / 35 |
| 3579s | 13 / 35 |
| 3652s | 13 / 35 |
| 3730s | 13 / 35 |

Convergence went **backwards**. The extra wall clock was producing silence, not convergence.

## 2. A failed probe was read as a negative result

`collect_roster_facts` piped `kubectl get applications -o json` into jq under `|| true`. A kubectl that could not reach the API server produced an **empty facts file**, which classified as a perfectly clean `0/0` roster.

**MEASURED: 17 of 59 samples** read `0/0 … zeta-root sync=-` on a cluster whose peak was 25/35. Had the *final* sample been one of those 17, the verdict would have reported `appCount=0` about a cluster it simply failed to ask.

This is **the exact defect class this verdict was built to catch, reproduced one layer down inside the verdict's own collection** — the same shape as `api-unavailable) : ;` in the transport rule.

Now: the probe's exit status is checked, and `jq -e 'has("items")'` catches the empty/truncated body that arrives with exit code 0 (verified against real jq — an empty Application **list** passes, an empty or garbage **body** fails). A failed sample is `unknown`: previous counts **stand** rather than being zeroed, it is loud on serial, and `probeFailures` rides into the verdict JSON so a reader can tell a quiet cluster from an unreachable one. Nodes and pods stay non-fatal — they only ever make the exclusion buckets *smaller*, the conservative direction.

## 3. `undecidable` fired on ordinary, perfectly schedulable workloads

The rule was "Pending **and** carries required `nodeAffinity`". Far too broad: almost every chart's DaemonSet carries a `kubernetes.io/os: linux` nodeAffinity, and **every** pod is Pending for a moment while its image pulls.

**MEASURED: it fired on `longhorn` and `node-feature-discovery`.** Since `undecidable` *fails* the verdict, that would have made the lane **permanently red for a reason about the check rather than about the cluster** — and a permanently-red lane stops being read.

Both conjuncts are now required: required nodeAffinity **and** the **scheduler itself** refusing to place the pod (`PodScheduled=False`). A pod Pending while pulling an image is not a scheduling question at all. Two new falsifiers pin each half — nodeAffinity-without-refusal and refusal-without-nodeAffinity both stay `unconverged`.

A verdict whose scope is misread is worse than one that is narrow, and this one's *name* promised more than its substrate can deliver.

### The regression now leads the cluster item

25/35 at t=1214s → 13/35 by t=3007s → **flat across the last four samples, 723s apart.** Twelve Applications that *were* Synced+Healthy stopped being so. "It just needs longer" predicts a monotonically rising count; a rise, a fall and a stall refutes it. That is what makes this a **capacity** problem, not a patience problem.

**Leading hypothesis, registered as hypothesis with a named falsifier:** `timeout.reconciliation` defaults to 180s, so all 49 Applications re-render every three minutes forever; with `repoServer.replicas: 1`, no resource requests, and a fraction of one contended vCPU, a sweep plausibly cannot finish inside one period — sweeps overlap, renders time out, Synced apps flip to `Unknown`. That predicts exactly the measured shape. **Falsifier:** raise it to ~900s, everything else unchanged. Peak retained ⇒ holds; still falls to ~13/35 ⇒ the hypothesis is wrong.

### It is a product finding, not a CI artifact

An operator installing on a modest box gets exactly what was measured — a root Application that never completes a comparison and a roster stalled at a third. Four candidate directions are in `081M3BPJNRS087G0R0008WFXBZ`, ordered by what the measured shape points at, with the note that a too-short render timeout gives a low **plateau** rather than a fall from a higher peak, so it does not explain the regression on its own.
