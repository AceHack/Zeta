## Description

## What this lane is for

**It is the fastest instrument in this repo for the question the maintainer
actually asked** — does the roster come up on a modest box without applications
crash-looping or failing to start. **Sixty minutes, no ISO build**, controlled
against an unconstrained twin on the **same commit**, and it reproduces the
crash-loop cascade that previously needed a ~90-minute installed-disk run to see
at all.

## The gap this closes

Two lanes boot the same roster and disagree, and until now the cheaper one could
not be asked the expensive one's question.

| lane | run | result |
|---|---|---|
| Docker replica (`cluster/first-boot-replica.ts`) | 36108486753, 65 min | 42 Applications: **35 Healthy / 5 DIVERGENCE / 2 FAIL**; stages 1-5, 7, 8 PASS, including a hard `docker kill -s KILL` recovery |
| installed disk (`ci/qemu-full-install-test.ts`) | 36097310492, ~90 min | peak **25 of 35** Synced+Healthy, regressed to **13 of 35**; ArgoCD repo-server timing out on manifest generation |

WP32 measured why and wrote it into `buildDockerRunArgs`' own docstring: that
argv sets **no `--cpus`, no `--memory`, no `--cpuset-cpus`**. The container gets
the whole runner with no hypervisor tax; the installed-disk guest gets
`-m 12288 -smp 4` inside a 4-vCPU runner that is *also* running QEMU. So a green
replica run is evidence the roster is **internally consistent** and is **not**
evidence that it converges on constrained hardware — and asking the constrained
question costs a ~90-minute ISO build every time.

## A second mode, not a replacement

WP32 deliberately left that argv alone because `--cpus=4 --memory=12g` would
invalidate every baseline recorded beside it. So `--constrained` is additive:
omit it and the argv is **byte-identical** to the pre-WP33 one, which a test now
pins by constructing both and differencing them. The default lane still answers
*"is the roster internally consistent"*; the new one answers *"does it converge
when the control plane has to compete"*. Both are worth having.

## The swap denial is the sharper half — and it is derived, not chosen

Docker's default `--memory-swap` is **2x `--memory`**. A plain `--memory=12288m`
would therefore have handed the container **12 GiB of the runner's swapfile that
the real node does not have** — `hosts/control-plane/hardware-configuration.nix`
declares `swapDevices = [ ]`.

Memory pressure would then have surfaced as **thrash instead of the OOM kill the
guest actually takes**, and the lane would have looked like it survived a
condition it had quietly been excused from. That is a fidelity defect that is
invisible by construction and would have been permanent — a constrained lane
reporting green while being silently exempt from the pressure it exists to apply.

`--memory-swap` is set equal to `--memory` **derived from that host config**
rather than written as a literal, so the denial stays correct — and stops being
applied — if someone gives the node swap later.

## What it binds, and why that is the lane's purpose rather than its limitation

Both lanes run on `ubuntu-24.04` (4 vCPU / ~15.9 GiB), so **`--cpus=4` is at or
above what the host would give anyway and does not bind**. The CPU tax the
installed-disk lane really pays is QEMU's own overhead, which no `--cpus` number
expresses; inventing a tax fraction ("QEMU costs ~40%, so `--cpus=2.5`") would be
a fabricated constant wearing a measurement's clothes. So the mode **binds
memory, denies swap, and leaves CPU unbound — and says so on every run:**

```
mode=constrained cpus=4 memory=12288m host-cpus=4 host-memory=15989m cpu-limit-binds=no memory-limit-binds=yes
```

That is not decoration. Printing `mode=constrained cpus=4` and stopping would let
a green read as *"converges under the installed-disk CPU budget"* when CPU was
never restricted — a check indistinguishable from its own absence, which is the
class this effort has already found ten instances of. An unreadable host is
`unknown`, never assumed to bind.

**And it makes the lane purpose-built for the standing prediction.** After the
control-plane capacity fix (#17666) the claim on record is that the failure mode
should **move to memory rather than vanish**: the roster over-commits the guest's
memory (1.47x at the dev rung), and that never bit only because CPU starvation
stopped 14 of 49 Applications from ever being created. A lane that constrains
memory while leaving CPU alone tests that claim **in isolation**.

## Derived, never hardcoded

`K3S_VERIFY_CPU_COUNT` / `K3S_VERIFY_MEMORY_MB` are exported from
`ci/qemu-full-install-test.ts` and imported. `resolveConstrainedLimits`
**REFUSES** — exit 2, at `--dry-run` time, before anything expensive starts —
rather than substituting a guess if either stops being a usable number, and the
refusal names which constant it could not read.

A falsifier pins that no second copy exists: re-type the literal in the replica,
drift the source, and the test goes red in milliseconds instead of in a lane that
silently measured the wrong envelope. Verified by mutation (hardcode `4`, move
the source to `8` → 1 fail).

## Where it runs, argued from a measurement

Schedule + `workflow_dispatch` only; **not** `pull_request`. The five most recent
completed runs of the unconstrained job took **64-70 minutes** each
(36108486753: `07:36:19Z -> 08:41:16Z` = 65 min). The constrained job runs the
same eight stages with strictly less memory and no swap, so it cannot be cheaper.
Neither job is in the required gate, so a per-PR constrained run would buy **no
blocking signal** for ~65 extra runner-minutes on every roster PR.

On schedule and dispatch **both jobs run in parallel on the same commit**, and
that is the load-bearing half of the placement rather than a convenience.

| | unconstrained | constrained |
|---|---|---|
| envelope | `cpus=unlimited memory=unlimited host-cpus=4 host-memory=15989m cpu-limit-binds=no memory-limit-binds=no` | `cpus=4 memory=12288m host-cpus=4 host-memory=15989m cpu-limit-binds=no memory-limit-binds=yes` |

| stages 1-5, 7 | PASS | PASS |
| wall clock | 65m51s | **59m44s** |

**Memory was the only limit that bound**, and constraining it cost **13 Healthy
Applications** and produced **15 more FAILs**. Note the constrained run finished
*faster* while converging far worse — stage 6 gives up and moves on, so wall
clock is not a convergence proxy.

### The mechanism it reproduces: a liveness crash-loop cascade

> memory pressure → containers slow → **liveness probes time out** → the kubelet
> SIGKILLs them → restart → more pressure

**The kill's origin is measured, not inferred.** The cluster emitted **61 kubelet
`Normal Killing … Container <name> failed liveness probe, will be restarted`
events over 28 distinct containers**, alongside six containers exiting **137 with
`Reason: Error`** and **zero `OOMKilled`, zero `Evicted`, no `MemoryPressure`
node condition**.

That combination is not a puzzle, it is the answer: **the liveness probes kill
these containers before the OOM killer ever reaches them.** `OOMKilled` is what a
pod's own memory cgroup produces; a kubelet probe kill produces `Error`. And the
probe failures are `context deadline exceeded` rather than `connection refused`
almost throughout — the endpoint is there and cannot answer in time, which is
starvation, not a crash.

#### Two of the 28 are not workloads — `coredns` and `metrics-server`

They are the **node's own floor**, and that changes how the rest of the list
should be read. DNS being liveness-killed under this envelope means an unknown
share of the other 26 are **downstream victims** rather than independent
findings: a pod that cannot resolve a Service name fails its own probe for a
reason that has nothing to do with its own resource budget.

So the 26 are symptoms of **at least two causes**, and the floor is the one to
fix first. Widening a budget on `db` or `tempo` while DNS is being killed
underneath them is treating a symptom of a cause still running — and the list may
shorten on its own once the floor holds. The follow-up is ordered accordingly:
floor first, **re-measure**, then whatever survives.

### Stage 8: the power-cut does not recover under constraint

Unconstrained, a hard `docker kill -s KILL` recovers cleanly — `RECOVERED`, every
previously-Healthy Application back, every seeded Secret intact, no PVC rebind.
Constrained, the same power cut ends `NOT_RECOVERED`:
`CONTAINER_CRASHLOOP(spire/spire-server-0[spire-controller-manager])`.

That is the power-cut scenario on a modest box — the target hardware this
installer exists for — and it is a distinct result from the stage-6 count, not a
row in the same table.

### Register on the prediction: consistent with, NOT confirmed in the form stated

The failure **did** move, and it moved when memory was the only thing
constrained. But it arrives as a **liveness cascade**, not as the OOM kill or
eviction that "the failure mode moves to memory" predicted. Memory pressure is
the plausible upstream cause; this harness has not measured that it is the *only*
one. What it **has** measured is the kill mechanism, and that is now closed.

### The lever already exists — and is deliberately not pulled here

`src/Core.TypeScript/cluster/liveness-kill-budget.ts` computes
`initialDelaySeconds + (failureThreshold - 1) * periodSeconds`, and keda's
Application carries the worked precedent: `failureThreshold` widened 3 → 20 after
keda-operator was measured restarting in 4 of 5 CI runs, because that chart ships
no `startupProbe`. This lane is the instrument that says which *other* charts
need the same treatment — and unlike the run that motivated keda's fix, it is
controlled.

**No budget is widened in this PR.** A fix landed in the same change as the
measurement would make the measurement unreviewable. Filed as its own follow-up
with the 28 components as starting evidence.

### And this is the lane doing the job it was built for

The installed-disk lane's symptom class now reproduces in **60 minutes**, on a
substrate that could never produce it before, with no ISO build at all.

## Nothing is relaxed to get a green

Same stage budgets, same soak, same power-cycle. Three outcomes, all findings:

- converges **as well as** unconstrained → the installed-disk regression has a
  cause other than the resource envelope, and that is worth knowing;
- fails **with memory pressure** → the prediction above confirmed from a third
  substrate, in minutes rather than 90;
- fails **some other way** → still a named per-Application verdict.
