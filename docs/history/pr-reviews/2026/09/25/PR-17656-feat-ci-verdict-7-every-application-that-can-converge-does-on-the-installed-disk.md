## Description

## The gap

WP11 now passes all six verdicts on a real installed disk, cluster up in ~150s. But look at what they assert:

| # | verdict | what it actually covers |
|---|---|---|
| 4 | `helmJobs` | **SEVEN** bootstrap charts only — cilium, cert-manager, spire-crds, spire, trust-manager, external-secrets, argocd |
| 5 | `rootLanded` | the app-of-apps **Application object** exists |

Nothing asserts that the other ~48 Applications ever reach Synced and Healthy. `rootLanded` means the root landed, not that its children converged. So the maintainer's actual question — *will the applications on the helm chart start up correctly when I plug the USB in* — was answered only by the Docker replica and the kind lanes, and **never once on a real installed disk**.

## Verdict 7 — `rosterConverged`

> Every Application that **CAN** converge on this node reaches Synced+Healthy within a bound; every one that **cannot** is NAMED with its reason and excluded.

A naive "all Applications Healthy" verdict is **unpassable**, and an unpassable verdict trains a reader to ignore a red. `cdi`, `kubevirt`, `ollama` and `vllm` omit `spec.syncPolicy.automated` on purpose and nothing on this boot runs `argocd app sync`; a workload whose `nodeSelector` demands `zeta.io/gpu: nvidia` on a box with an Intel Arc stays Pending forever by design.

### Derived, never a hardcoded list

- **manual-sync** is `manual-sync-policy.ts`'s convention, read off the **live Application object** — ArgoCD applies those annotations verbatim, so the declaration travels with the object and needs no repo checkout on the installed disk. Its three refusals carry over exactly: annotation without a reason, annotation **with** an `automated:` block, and an omitted block nobody claimed are all **MALFORMED** and earn the FULL Synced+Healthy contract. A malformed declaration must never be cheaper to satisfy than a correct one.
- **an excluded manual-sync app is still asserted**, by that module's own weaker contract: ArgoCD must have COMPLETED a comparison (sync ∈ {Synced, OutOfSync}, never `Unknown` — that is a ComparisonError) and health must be `Missing` or `Healthy`. An exclusion that asserts nothing is a decoration.
- **schedulability** is decided the way Kubernetes decides it: a Pending pod's `spec.nodeSelector` against the union of every Node's labels. In cluster this is **exact** — which is the half `schedulable-demand.ts` (WP28, #17620) could only call `undecidable` from a checked-in `ClusterNode` registration, where `lspci … | head -1` cannot prove a second card is *absent*.

### Three outcomes, and the third is said out loud

`undecidable` is WP28's disposition carried over. This check evaluates `spec.nodeSelector` and **not** `affinity.nodeAffinity` — writing a second evaluator for that match-expression language is exactly the duplicate reasoning reusing WP28 is meant to avoid. A Pending pod carrying required nodeAffinity makes its Application `undecidable`: named, counted separately, and **failing** the verdict, because "I could not tell" is not "it worked".

### The empty-roster false green is closed

"0 unconverged out of 0 Applications" is the exact shape this effort has now found **nine** instances of. Three guards:

1. the verdict carries `k3sActive` and `appCount` into its own JSON, the way verdict 6 already does for `podCount`;
2. it requires **`zeta-root` itself** to report `sync=Synced` — that is what establishes the roster is *complete*, since an Application the root never created is invisible to a loop over live Applications;
3. a provably-unschedulable Pending pod that cannot be attributed to exactly one Application is reported as `unattributed-pod` and fails, rather than being dropped.

In the TypeScript summarizer, an **absent** verdict 7 reads as a **failure**, never as a pass.

### The bound came from a measurement

`k3s-first-boot-roster.nix`'s own header budgets **45–70 min** for k3s plus ~2–3 GB of Helm image pulls converging on a comparable VM. The app-of-apps roster is a strict **superset** of that bring-up, so the bound is that range's **upper** end — 70 min = 4200s — never a mid value and never a number chosen to make one run pass. It is clamped by the unit's existing `DEADLINE_SECONDS` (also 4200s), which is what actually bites: verdicts 1–6 resolve at ~150s, leaving ~4050s. That clamp keeps the unit emitting inside the harness's `K3S_VERIFY_TIMEOUT_SECONDS` (4500s) and the step's `timeout-minutes: 100` — **MEASURED run 36073981145: the entire step took 19m48s**, so ~80 min of that budget was unused. **No workflow or harness timeout changes in this PR.**

### It can fail — proven

`src/Core.TypeScript/ci/wp11-roster-shell-parity.test.ts` extracts the two pure decision functions **verbatim** from the `.nix` (the `ZETA-WP11-ROSTER-BEGIN/END` markers) and runs them under a real bash+awk — same harness and same reason as `wp11-nobadpods-shell-parity.test.ts`. **24 tests, organised around what must still go RED:**

- an Application stuck `Progressing` past the bound → `unconverged`
- a declared manual-sync app whose comparison never completed (`Unknown`) → `unconverged`
- a declared manual-sync app that is `Degraded` → `unconverged`
- every malformed declaration (annotation+automated, no reason, `Manual` not case-folded) → full contract
- a **satisfiable** `nodeSelector` buys no exclusion
- a provably unschedulable pod nobody owns → `unattributed-pod`
- an empty roster counts **zero Applications**, not zero failures

Mutating one line of the classifier (`sync=="Synced" && health=="Healthy"` → always true) turns **12 of the 24 red**.

### It reports while it waits

Sixty-seven minutes of silence on a serial log is indistinguishable from a hang. Every poll (30s) prints a counts line — `N Synced+Healthy, M progressing, K excluded, U undecidable`, plus `zeta-root sync=…` — and every fifth poll names what is still outstanding. Every classified row, **including each exclusion and its reason**, is printed on serial on every boot; up to ten unconverged Applications also get ArgoCD's own conditions dumped.

## Cross-check against the Docker replica's measured roster

The replica lane's stage 6 measured the same roster four hours before this PR: **42 Applications — 35 Healthy, 5 DIVERGENCE, 2 FAIL.** Verdict 7 derives its exclusions independently, so the two lists are a real cross-check rather than a restatement. They agree on four of seven and **differ on three, all in the same direction — verdict 7 excludes LESS.**

| app | replica, measured | verdict 7, derived | agree? |
|---|---|---|---|
| `cdi` | DIVERGENCE — declared manual-sync | `excluded-manual-sync` | ✅ |
| `kubevirt` | DIVERGENCE — declared manual-sync | `excluded-manual-sync` | ✅ |
| `cilium` | **FAIL** — Synced+Progressing, `ExcludedResourceWarning: … EndpointSlice cilium-ingress is excluded in the settings` | `unconverged` | ✅ both red |
| `weaviate` | **FAIL** — Synced+Progressing | `unconverged` | ✅ both red |
| `spire` | DIVERGENCE — confirmed **non-metal** nested-container DNS crash loop | `unconverged` | ❌ **and verdict 7 is right to differ** |
| `openbao` | DIVERGENCE — sealed by design on a fresh cluster | `unconverged` | ❌ real gap, named below |
| `hindsight` | DIVERGENCE — needs an external API key | `unconverged` | ❌ real gap, named below |

**`spire` is the one where disagreeing is the correct behaviour.** The replica's own classification says the crash loop is *confirmed non-metal* — an artifact of nested-container DNS that an installed disk does not have. So `spire` must converge here, and importing that exclusion would carry a Docker artifact into a metal verdict. If verdict 7 reports `spire` unconverged on the installed disk, that is a **finding**: it would mean the non-metal classification is wrong.

**`openbao` and `hindsight` are a real gap, and it is deliberately left open.** Both are genuinely-defensible non-convergences that also hold on metal, and neither carries a machine-readable declaration verdict 7 could read off the live object. The right repair is to give them one — `zeta.io/sync-policy: manual` is the wrong annotation, because neither is manual-*sync*; both are *converges-only-after-an-operator-action*, which the convention has no word for yet. `full-ai-cluster/INJECTION-POINTS.md`'s `**EXTERNAL**` table is the maintained source for `hindsight`'s half and `first-boot-replica.ts` already parses it, but that table lives in the repo and verdict 7 runs on an installed disk with no checkout; baking a snapshot in at Nix eval time would create a second, separately-drifting copy of a roster.

**Widening the bucket to make these green is the one thing this verdict must not do.** An exclusion that swallows a real failure is how a verdict stops meaning anything — so they stay `unconverged`, named on serial with their last Sync+Health state, and the gap is reported rather than absorbed.

## What this hands back to WP28

`081M397QHX8087G0R003DQSY0B` left GPU schedulability `undecidable` because a checked-in `ClusterNode` registration is built from `lspci -nn | grep -iE 'vga|3d|display' | head -1` — **one** device — and "the first display adapter is Intel" cannot establish "there is no NVIDIA card". That is structurally unprovable from the registration, and `schedulable-demand.ts` is right to refuse.

**In-cluster the same question is exact, and this PR is where the answer now lives.** Kubernetes schedules on Node *labels*, not on installed hardware, so comparing a Pending pod's `spec.nodeSelector` against the union of every live Node's labels decides it outright — no `undecidable`, no guess, and no acquitting inference. The follow-up item can point here for the in-cluster half while leaving the registration-derived half honestly undecidable.
