## Run 2 retracts the baseline this item was built on

Run `36114004943` ran on the **same commit** as run 1, with **no capacity fix**, and the repo-server starvation symptom **did not reproduce** — 19 `sync=Unknown` + `DeadlineExceeded` rows in run 1, **zero** in run 2.

1. **Run 1 is not a reliable baseline.** Anything measured as "before the fix" using its 19 rows compares against a sample that does not reproduce on its own commit.
2. **The BestEffort measurement stands; the causal link is weaker.** WP32 measured *by rendering* that nine ArgoCD containers carry no requests and the control plane sits at `cpu.weight` 1 of 507 — true independent of any run, and wrong regardless of whether it was the proximate cause on any given day, so **the fix remains correct**. What is weaker is that it *is* what produced run 1's symptom. Keep the measurement, downgrade the causal claim — the register WP32 used retracting its own eviction inference.
3. **The dominant run-2 state is the more important finding anyway:** `sync=Synced health=Progressing` x60, 148 pods, 4 vCPU / 12 GiB, best 16 of 43. **The roster synced.** Not a control-plane defect, not an application defect — a box too small for the roster.


Applications **fell** while running pods went **up** — the opposite of what eviction predicts. "We watched pods hold while Applications fell" is a finding; "we found no evictions" is not.

## API reachability is the signal — and this one has a mechanism

Unlike the retracted `DeadlineExceeded` symptom, this is not bare correlation:

> The **k3s server process lives outside every pod cgroup.** Pod-level `resources.requests` cannot reach it. Only a **node-level** reservation (`kube-reserved` / `system-reserved`) could have protected it from the roster's own pods — exactly the half of #17666 this measures, and the half intermittency cannot explain away.

## What the 20 remaining non-convergences are

`grep -cE 'Evicted|OOMKill|MemoryPressure|DeadlineExceeded|Liveness probe failed'` returns **0**. Nothing is crash-looping, nothing is being killed, nothing is timing out. They are `Progressing`, or `Degraded` for reasons already classified (`hindsight`'s external credential, `openbao` sealed by design).

> **The roster does not converge on this hardware, and it is not converging slowly because something is broken. There is just not enough machine.**
