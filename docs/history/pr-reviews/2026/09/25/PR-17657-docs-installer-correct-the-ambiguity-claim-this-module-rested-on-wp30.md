## Description


081M39CR74D087G0R002BEG2G4. A claim asserted in five file headers, three
merged commit messages and the work item is FALSE. It is corrected in place,
with the measurement next to it, rather than quietly replaced -- the reason it
spread to five files is that nobody could tell it had never been measured, and
a bare replacement assertion would inherit exactly that defect.

WHAT WAS CLAIMED: that k3s's message is "ambiguous by construction" -- that
because it says "check server token value AND verify datastore integrity", the
identical text appears when a GOOD, already-served datastore meets a WRONG
token, so deleting on that signature would destroy a healthy cluster.

WHAT WAS MEASURED, run 36095623765: a real, already-served datastore given a
well-formed wrong token (derived from the real one, so normalisation passes)
does NOT print the stillborn message. Across 151s of polling, every restart
printed:

  level=fatal msg="Error: preparing server: failed to bootstrap cluster data:
  failed to reconcile with local datastore: bootstrap data already found and
  encrypted with different token"

k3s DISTINGUISHES the two cases:

  stillborn datastore          -> "no bootstrap data found in datastore ..."
  good datastore, wrong token  -> "bootstrap data already found and encrypted
                                   with different token"

A hint string was read as a disambiguator.

THE GUARD IS STILL RIGHT; ITS REASON IS NARROWER AND MORE DURABLE. The
signature is not ambiguous, but it is A SINGLE STRING IN AN UPSTREAM LOG LINE,
and pinning data destruction to a log grep is fragile in a way a has-served
marker is not. k3s can merge, reword or reorder those messages in any release;
the sentinel does not care.

AND THE MEASUREMENT BOUGHT A STRONGER PROPERTY THAN THE ONE DESIGNED FOR, so
it is now stated as a property rather than left as a happy accident:
FATAL_SIGNATURE matches ONLY the stillborn message, so the wrong-token case
never reaches the recovery path at all -- it is filtered one step BEFORE the
sentinel is consulted. TWO INDEPENDENT CONDITIONS must both hold before
anything is deleted, and either alone is sufficient to refuse. The sentinel is
belt-and-braces, not the primary guard.

THE OPERATOR-FACING REFUSAL TEXT CHANGED TOO, and that one mattered most: it
told whoever was reading the serial console that "k3s's own message cannot
tell the two apart", which is false and is advice. It now says the combination
is UNEXPECTED, names the message a wrong token actually produces, and still
refuses to touch anything.

WHY WE LEARNED THIS AT ALL: TARGET 2 in the VM test is OBSERVED, NOT REQUIRED,
and on run 36095623765 it printed "NOT REPRODUCED within 150s on this
substrate" -- loudly, on a GREEN run. A required assertion would have gone red
and been read as a test bug, which is precisely what happened the first time
round (36093540290, where a malformed token died at normalisation instead). An
observation that announces its own absence is the opposite of the defect class
this module was written inside of, and it is the only reason the false claim
surfaced instead of surviving.

Its EXERCISED branch is now the loud one: if a wrong token ever DOES produce
the stillborn fatal, that contradicts this measurement and says k3s's
behaviour or wording changed -- so the message says so rather than quietly
confirming the old story.

ALSO, unrelated to the correction but in the same file: every test in
k3s-datastore-bootstrap-recovery.test.ts now carries an explicit 30s timeout.
Each spawns a real `bash <script>`, and under load a single spawn was measured
past bun's 5s default (suite: 15.8s idle, 49.9s loaded; one single-spawn test
timed out at 5.96s). A test that goes red because the machine was busy is a
check that can fail without its subject being wrong -- the same defect class,
mirrored, as one that can pass without its subject being right.

Three merged commit messages (#17646, #17650, #17653) still carry the old
claim. They are immutable history and are not rewritten; this commit is the
correction of record, and every surviving mention of the claim in the tree is
now marked as the superseded one.
