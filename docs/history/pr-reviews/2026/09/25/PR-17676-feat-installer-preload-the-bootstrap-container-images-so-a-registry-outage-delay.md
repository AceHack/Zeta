## THE FINDING THIS ANSWERS

The first-boot external-dependency inventory (#17670, 081M3BWJ96T087G0R0028WT3S3)
produced a measurement nobody had made: the 134 first-boot container images span
**EIGHT registries**, and the pull-through cache covers **ONE**.

```
docker.io           48   mirrored via mirror.gcr.io
quay.io             34   UNMIRRORED
ghcr.io             31   UNMIRRORED
registry.gitlab.com 14   UNMIRRORED
registry.k8s.io      4   UNMIRRORED
others               3   UNMIRRORED
```

36% covered. Every unmirrored registry enforces its own per-source-IP rate limit,
so an operator behind an office NAT, a CGNAT ISP or a campus network shares that
budget with strangers. When it is spent the install does not stop and say so — it
half-provisions, and the only explanation the operator gets is a stack location.

## WHAT SHIPS, AND WHAT IT COSTS

The **bootstrap slice only**: the 25 images behind the seven charts
`services.k3s.manifests` installs — cilium, cert-manager, spire, trust-manager,
external-secrets, argocd, plus the local-path provisioner.

**MEASURED: 1,019,156,480 bytes.** ISO +1.0 GB; installed disk +~2.7 GB at the
x2.67 unpacked ratio `storage-profiles.json` established. Those numbers were
measured and reported BEFORE any code was written, and approved on that basis.

21 of the 25 sit on registries the mirror does not cover, which is what makes
this a principled slice rather than an arbitrary gigabyte:

```
quay.io               12 images   718.4 MB  UNMIRRORED
ghcr.io                5 images   184.7 MB  UNMIRRORED
registry-1.docker.io   4 images    40.8 MB  mirrored
ecr-public.aws.com     1 image     34.5 MB  UNMIRRORED
registry.k8s.io        2 images    29.6 MB  UNMIRRORED
cgr.dev                1 image     14.4 MB  UNMIRRORED
```

## WHAT IT DOES NOT DO — STATED IN EVERY HEADER

**It makes the cluster COME UP without a registry. It does NOT make the roster
CONVERGE offline.** The remaining ~109 catalog images still pull from eight
registries. The operator gets a running cluster with ArgoCD visibly reconciling
and visibly behind, instead of a partially provisioned node with no explanation.
Overclaiming that would be worse than not building it.

k3s's own built-ins (`rancher/mirrored-pause`, `mirrored-coredns-coredns`,
`mirrored-metrics-server`, `klipper-*`) are deliberately absent: they ship inside
the k3s release image and are in containerd before the agent starts — confirmed
by `ctr images ls` on a container booted with every registry blackholed.

## THREE DEFECTS FOUND WHILE BUILDING IT, EACH INVISIBLE FROM THE ARTIFACT

**1. The ConfigMap blindness.** `local-storage.nix` embeds the local-path
provisioner's `helperPod.yaml` as a STRING inside a ConfigMap, carrying
`image: busybox`. A structural `image:` walk cannot see it. The first derivation
shipped `rancher/local-path-provisioner` with `busybox` missing — a provisioner
that cannot provision, on exactly the storage wave this preload protects. Fixed
by `imagesInEmbeddedManifests`.

**2. `skopeo` breaks digest-pinned references, silently.** An OCI-layout
destination forces OCI media types, so skopeo rewrites a docker manifest LIST
into an OCI index: new bytes, new digest. The kubelet normalises
`repo:tag@sha256:X` to `repo@sha256:X` and asks containerd for digest X — the
INDEX digest — while the archive holds the rewritten index (or, with
`--override-arch amd64`, only the amd64 child). `--preserve-digests` does not
rescue it; skopeo refuses the conversion rather than performing it.

Measured with quay.io blackholed: plain tag gave *"already present on machine"*;
digest-pinned gave `ImagePullBackOff`, `dial tcp 127.0.0.1:443`. That is **5 of
25 images — every cilium one, 389 MB, 38% of the payload and the chart without
which nothing else schedules.** A preload built the obvious way would have
shipped, looked right, imported cleanly, and left the CNI pulling from a registry
on every first boot. Fixed by assembling the OCI layout byte-for-byte from the
registry, which preserves the index digest by construction and drops the skopeo
dependency entirely. Re-measured against the same blackhole: `Succeeded`.

**3. One untagged name costs the whole archive.** k3s retags every entry as it
imports, and a bare `busybox` is not a `NamedTagged`:

```
failed to import .../zeta-bootstrap-images.tar: failed to retag images:
failed to parse tag for image busybox: can't cast reference.repository to NamedTagged
```

One bad name, twenty-five images lost. Fixed by `containerdImageName`, which
normalises ONLY the untagged case to the canonical form CRI would resolve to
anyway, and leaves everything else verbatim.

## DERIVED, NEVER LISTED

Nothing here is a second copy of a roster — a defect class this tree has paid for
repeatedly. `buildRoster` (`first-boot-replica.ts`) parses
`services.k3s.manifests` out of **both** `k3s-server.nix` and
`local-storage.nix`'s inline `pkgs.writeText` entry; `parseHelmChartCrs` finds
the HelmChart CRs; `imagesInDocuments` and `measureImage` (`image-footprint.ts`)
do the scanning and the sizing. **One sizer, not a second.** The
`infra/k8s/bootstrap/` tree is excluded automatically and correctly, because
nothing in the NixOS roster references it.

## VERIFY EARLIER, NOT LESS

The committed snapshot (`full-ai-cluster/k8s/bootstrap-preload-images.json` —
TEXT, per `no-binary-in-proof-lineage`) pins each image to the digest its
linux/amd64 manifest resolved to. The ISO lane re-resolves **every pin before
anything is fetched**, then fetches BY DIGEST and checks every blob against the
digest that asked for it. An image that moved under its tag fails in CI — with
credentials, no meaningful rate limit, and a human reading a red build — rather
than on an operator's first boot.

## THE FALSIFIER, AND ITS MANDATORY NEGATIVE CONTROL

`bootstrap-preload-blackhole.ts` boots the real roster in k3s with **every**
registry in the snapshot pointed at 127.0.0.1, and probes each image with a Pod
that names it verbatim and runs a command that cannot exist — so the probe always
fails to START and the only thing under test is whether it had to PULL.

`--both` runs it twice and **refuses to report success unless the negative
control goes red**:

- positive (archive mounted) gives `CARRIED`
- negative (EMPTY images directory) gives `BLOCKED`

A negative control that passes does not weaken the result, it **voids** it
(`BLACKHOLE_INEFFECTIVE`) — because a blackhole test that passes on an empty
images directory is the same defect in a new costume. The blackhole host list is
**derived from the snapshot**, not typed, so an image that moves to a new
registry is covered with no code change.

The harness caught two defects in itself, both recorded in-place:
- it probed before k3s finished importing a 1 GB archive (21 of 25 falsely
  `BLOCKED` with a perfectly good archive);
- it left docker.io reachable, making four images **unjudgeable** — a probe that
  succeeds by pulling is indistinguishable from one that succeeds by preloading.

## ABSENCE IS NEVER SILENT

`zeta-bootstrap-image-preload-status.service` runs **before** k3s, writes a named
`PRESENT <bytes>` / `ABSENT` verdict to `/run`, and in the ABSENT case explains
exactly what the operator will now see. It is deliberately **non-fatal**: a node
with a working network boots fine without this, and refusing to start k3s over a
missing optimisation would convert a reliability improvement into a new way to
brick an install. The eval test pins both halves — loud AND non-fatal — plus the
ordering and the fact that `common.nix` imports it for every node, not just
control planes.

## THE PROOF — RUN, AND ITS NEGATIVE CONTROL IS RED

Measured 2026-09-25, k3s v1.35.7+k3s1 in Docker, all eight registry hostnames in
the snapshot pointed at 127.0.0.1 inside the container:

```
=== POSITIVE: bootstrap roster, registries blackholed, archive mounted ===
  positive: CARRIED — all 26 probed image(s) resolved locally — no pull was attempted

=== NEGATIVE CONTROL: same boot, EMPTY images directory ===
  negative: BLOCKED — 1 image(s) had to be pulled and could not be
      BLOCKED    docker.io/rancher/mirrored-pause:3.10.2

=== PROVEN ===
```

The negative control blocking on the **sandbox image** is the sharpest form of
the point: without the preload the node cannot create a pod sandbox at all, so
nothing runs and not one of the other twenty-five images gets as far as being
tried. Every other probe in that run is honestly `UNDECIDED`, because it never
got the chance to fail.

Register: **metered**. The falsifier is nameable, it was run, and its negative
control went red.

## THE `build-iso` FAILURE, AND WHICH OF THREE OPTIONS I TOOK

Run 36129391858 failed my own step with `Cannot find package 'yaml'`. The job
installs Bun but never ran `bun install`, because every other `bun` step in it is
node-builtins-only. The preload module is not — it reads YAML to derive the
roster. Worth being precise about where it failed: this is a plain `run:` step
that executes *before* `nix build`, not something inside the nix build.

**Taken: option 1 — do the work outside nix and pass the result in.** The verify
and archive steps are ordinary CI steps that run before `nix build`, produce a
file, and the nix build consumes that file. `bun install` there gives them the
dependency they need and touches nothing nix sees, and it leaves the derivation
in TypeScript where its falsifiers live.

**Rejected: hand-parsing the HelmChart CRs to drop `yaml`.** A second YAML parser
in this tree is its own defect class, and this module exists precisely to avoid a
second copy of a roster.

**Rejected outright: making `node_modules` reachable from inside the nix build.**
That breaks nix's isolation and would make the ISO build depend on a `bun install`
having happened — the property `clone-at-tag-stays-sufficient.md` protects. Worth
stating that option 1 does NOT have that effect: `isoImage.contents` falls back to
a loud `lib.warn` and an ISO with no preload, so a clone at a tag with no bun on
PATH still builds a working ISO. It just builds one that pulls at first boot, and
says so.

## THE CodeQL ALERTS WERE REAL, AND THIS REPO ALREADY KNEW THE FIX

Six new first-party alerts. None dismissed. `.github/codeql/codeql-config.yml`
records the negative result from the round that tried to ship custom barrier
models — a data extension is ignored by the shipped query, a local pack cannot
ride in on `packs:` or `queries:` — and states the conclusion followed here:

> What DOES close a first-party alert is a guard in the code that CodeQL's
> DEFAULT taint barriers already recognise — an allowlist membership test, a
> regular-expression test. That is a real refusal at runtime as well as a barrier
> at analysis time, so the finding is FIXED rather than explained.

There are even fixtures for this exact query pair, with `guarded.ts` pinned silent
and `unguarded.ts` pinned reported.

- `js/incomplete-sanitization` — `importCompleted` built a RegExp from the archive
  name and escaped only `.`. Every other metacharacter was live, which is worse
  than no escaping because it reads as safe. Replaced with a line scan. **Cleared.**
- `js/http-to-file-access` (3) and `js/file-access-to-http` (2) — guards added on
  the content address, the registry host and the repository path. **The first
  attempt put them behind named helpers and the alerts stayed open**; the
  fixture tests the value *at the site that uses it*, so the guards are now
  inline at each URL-building and path-building site. The named helpers remain as
  the readable definition of the shapes, with a test that reads this module's own
  source and asserts the inline copies and the named ones are the same literal —
  because a duplicated constant with no drift check is the defect this module is
  otherwise entirely about.
