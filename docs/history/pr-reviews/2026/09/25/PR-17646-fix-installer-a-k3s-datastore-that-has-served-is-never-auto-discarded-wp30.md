## Description


081M39CR74D087G0R002BEG2G4. k3s creates /var/lib/rancher/k3s/server/db and gets
roughly 20 seconds to write bootstrap data into it. Stop the machine inside that
window on its FIRST boot -- impatience, a power cut, a tripped breaker -- and the
datastore exists with nothing in it. A non-empty datastore is the one thing k3s
will not initialise into, so it refuses forever:

  level=fatal msg="Error: preparing server: failed to bootstrap cluster data:
  failed to reconcile with local datastore: no bootstrap data found in datastore
  - check server token value and verify datastore integrity"

No reboot recovers it. MEASURED on a real installed disk, run 35968222668:
k3sServiceActive=false, NRestarts=58, that fatal 76 times in the journal.

THE NAIVE FIX IS CATASTROPHIC AND IS NOT WHAT THIS DOES. Deleting the datastore
whenever k3s reports that fatal is confiscation of the one thing on the machine
that cannot be regenerated (manifesto SS5) -- exactly what k3s-datastore-preflight.nix
already refuses to do for the dirty-disk case. k3s's message is ambiguous BY
CONSTRUCTION ("check server token value AND verify datastore integrity"): the
identical text appears when a GOOD datastore meets a WRONG TOKEN, and deleting
there destroys a healthy cluster.

THE GUARD IS A HAS-EVER-BOOTSTRAPPED SENTINEL. One unit writes
db/.zeta-datastore-has-served exactly once, only after k3s's OWN /readyz has
genuinely succeeded -- not "the process is active", which is precisely the gap
that produces this defect class. A second unit READS it, and acts only when it
is ABSENT and k3s has crash-looped past a threshold reporting that exact fatal.
When it is PRESENT nothing is touched, whatever the restart count.

So the recovery window opens at first boot and closes FOREVER the first time the
cluster works. That is now a property of the script's SHAPE, not of a condition
a reader has to verify by getting to the end: the sentinel branch returns before
the recovery code is reachable at all.

EVERY OUTCOME SPEAKS, AND THEY ARE DISTINGUISHABLE. This effort found six
separate instances of a check whose failure and whose absence looked identical;
the first revision of this module printed only on the paths where it ACTED,
which would have made it the seventh. Every terminal path now ends in a verdict,
once per boot per distinct outcome (latched on /run, so a boot's whole story
arrives in one line each, in order, and a 10s poll loop never floods):

  stillborn-recovered  no marker, the datastore had never served, discarded
  served / served-refused   marker present -- never touched, whatever k3s says
  datastore-absent     no datastore directory at all; nothing to recover
  unbootstrapped-watching / other-crash-loop / stillborn-recovery-exhausted

The sentinel writer says it too: if its readyz command ever stopped working, no
sentinel would ever be written and every healthy datastore would look stillborn
forever -- the guard inverted into the data loss it exists to prevent. That
branch now prints VERDICT waiting-for-readyz once per boot rather than nothing.

TWO FALSIFIERS, FOR TWO DIFFERENT THINGS.

k3s-datastore-bootstrap-recovery.test.ts (21 tests) EXECUTES both shipped .sh
files over fixture directories with every external dependency injected -- same
discipline as k3s-agent-tls-self-heal.test.ts. Its has-served suite is the
falsifier for the one property this pair exists to guarantee, including that the
guard is not a disguised restart threshold (100000 restarts, still untouched).

nixos/tests/k3s-datastore-bootstrap-sentinel.nix boots a REAL k3s and proves the
two halves no fixture can reach, both of them the dangerous ones: that the unit's
DEFAULT readyz command actually succeeds from inside its real systemd unit, and
that a real already-served datastore handed a WRONG TOKEN reproduces the same
ambiguous fatal -- the claim this whole module rests on, asserted in prose
everywhere and measured only here -- and SURVIVES it, then serves again once the
token is restored. Wired as a named step in build-ai-cluster-iso.yml beside its
siblings, because a flake check no workflow runs is a check nothing executes.
