## Description

Work item only, no code change. Found while trying to verify that WP11 verdict 7 now emits — **run `36110246885` never got that far.** It failed at **13m37s in phase 1**, so the installed disk was never booted.

> `first-boot provisioning contract failed — tools/setup/install.sh failed on first boot after exhausting its retries`

Cause, **6 occurrences** on serial, and the **only** tool that failed (`grep -oE "Failed to install [a-zA-Z0-9:@./-]+" | sort | uniq -c` returns exactly one line):

```
Failed to install github:yannh/kubeconform@0.7.0:
  GitHub artifact attestations verification error:
  GitHub API returned 403 Forbidden: {"message":"API rate limit exceeded...
  Location: src/toolset/toolset_install.rs:244
```

## The policy is not the bug

`.mise.toml` documents at length why artifact attestations are enforced — including the real `fastq@1.20.2` regression the policy caught. Verifying provenance before installing a binary is right. **The item explicitly says not to respond by disabling it.**

## The verification path is the bug

It calls GitHub's API, and **unauthenticated that limit is 60/hour per source IP**. A first boot has no `GITHUB_TOKEN`. So the install fails **closed** — correctly, in that it refuses to install what it could not verify — and takes the whole provisioning contract with it.

**An operator hits this exactly as CI did.** Plug the USB in behind a busy office NAT, a CGNAT ISP or a campus network, and the shared public IP has very likely already spent its 60. The node comes up **partially provisioned**, with nothing saying that a *rate limit* — rather than anything about the machine — is why. That is squarely the "will it work when I plug the USB in" question.

## Candidate directions (cheapest first)

1. **Give the verification path a token where one exists** — lifts CI to 5000/hour. Does nothing for a real operator.
2. **Make the failure NAME the rate limit.** Today the operator gets `install.sh FAILED rc=1` and a stack location in `toolset_install.rs`. Worth doing **regardless of the others**.
3. **Retry with backoff on a 403 rate-limit specifically** — the current 3 attempts are seconds apart; a rate limit needs minutes, and the response carries the reset time.
4. **Pre-stage the verified binary in the ISO** — it is already a pinned version. Verify at image-build time where a token exists. Biggest change, best operator outcome.

## Second site, same tool, same hour — not conflated

`chart pins + helm template + kubeconform` went red on #17662 at 07:32 (`Valid: 15, Invalid: 0, Errors: 5`) and passed on a re-run with no code change. That is a **different site** — kubeconform *running* and failing to fetch schemas, not failing to *install*. What they share is being network-dependent failures of the same tool in the same hour, which is worth knowing when triaging either.
