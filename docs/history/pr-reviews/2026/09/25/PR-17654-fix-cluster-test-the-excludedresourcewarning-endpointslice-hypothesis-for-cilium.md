## Description

## WHY

ArgoCD's own condition has been in the replica lane's output every run:
`ExcludedResourceWarning: Resource discovery.k8s.io/EndpointSlice
cilium-ingress is excluded in the settings`. Confirmed the exclusion is
NOT this repo's config — it's the pinned argo-cd chart's (10.8.0)
compiled-in default, whose own stated assumption ("never child objects of
managed resources that need to be presented in the resource tree") does
not hold for `cilium-ingress`'s EndpointSlice.

**Checked weaviate against the same mechanism first** (do not assume a
matching symptom shares a cause): weaviate's `status.conditions` is
**empty** (full report JSON, run 36002885823). `hasExcludedWarning=True`
occurs exactly once across all 42 Applications — only cilium, despite 41
others also owning Services. Confirmed different, still-unexplained cause
for weaviate; no change attempted there.

## The fix

`resource.exclusions` set explicitly in both
`full-ai-cluster/k8s/applications/argocd/Application.yaml` and the
bootstrap twin `full-ai-cluster/k8s/bootstrap/argocd-install.yaml` (kept
in lockstep), reproducing every chart-default rule verbatim except
dropping `discovery.k8s.io/EndpointSlice` from the exclusion. The chart's
own `ignoreResourceUpdates` default for that kind keeps diff noise
suppressed once it's tracked.

## CONFIRMED — two live runs, the mystery has not recurred

Triggered twice (36097120172, 36102477428). **Both** show `cilium`'s
`status.conditions` as `[]` — the `ExcludedResourceWarning` is reliably
gone — **and** the exact symptom this PR exists to fix (`Progressing`,
empty conditions, no pod issue to attribute it to) **did not recur in
either run**, after appearing in every one of 10+ prior runs this session
without exception.

Both runs still FAILed cilium, but for a *different, already-diagnosed,
unrelated* reason (confirmed via `describe pod`): `cilium-operator` lost
its leader-election lease against the k3s API server under CI load
(`context deadline exceeded`) — the same transient infra-timing pattern
diagnosed earlier this session, unrelated to resource tracking. Two
occurrences in a row masked a clean Healthy read both times; not chased
here, out of scope. 2-for-2 on the mystery not recurring, against 10+/10+
recurring pre-fix, is strong enough evidence to treat the correlation as
causal.

**Honest register kept**: this started as a well-evidenced hypothesis, not
a proven mechanism (excluded resources are removed from ArgoCD's
`targetObjs` before health aggregation per `controller/state.go`, in
tension with a direct causal path I could not fully confirm at the source
level). The live evidence above is what settles it. Does NOT touch
`first-boot-replica.ts`'s classification logic — a genuinely-Progressing
app still FAILs exactly as before.
