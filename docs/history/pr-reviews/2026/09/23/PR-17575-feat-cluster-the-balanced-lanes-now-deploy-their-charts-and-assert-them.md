## Description

The lane partition has always stopped short of a cluster. Its own workflow
header said so: "It does not yet BRING UP the lane ... the wiring is one step,
not a redesign." This takes that step, on the lanes designed 2026-09-18 (subject
charts priced at the HA rung, dependencies at dev, the metal first-boot set in
every lane, six lanes balanced for headroom, from the same dependency graph ace
parses).

Each lane job now creates a k3d cluster -- k3s + Cilium, metal's own pair -- and
runs the ArgoCD health harness with `--lane-dirs`. That one list drives BOTH what
the root catalogue applies (the lane-scoped exclude glob) and what the harness
asserts (the expected set). They have to be one list: when they drift a lane
either hangs on a chart nobody deployed (the k3d bring-up already documents that
failure) or goes green without looking at one it did. `application-dirs.ts` is
the shared module, and `application-dirs.test.ts` pins that the applied set
equals the expected set for every real lane on both kind and k3d -- including a
test that drives the real `gitOpsAppCatalog` with a recording control plane,
because a test computing the glob itself would stay green if the applicator
ignored the lane.

Every CLI answer comes from one partition under `--balanced` -- matrix,
per-lane images, budget, dirs -- because a lane id only means something relative
to the partition that minted it. The matrix carries directory names, not roster
names: `openziti-controller` lives in `oz` and `gmod` in `game-hosting/gmod`, and
joining on the wrong key silently drops the Application.

Found on the way: the partition roster held 49 Applications and the harness
asserted against 48. Discovery walked depth 1; ArgoCD's include glob is not
path-segment bounded and applies `game-hosting/gmod`. gmod was already excluded
from dev by a written reason, so nothing was deployed-and-failing -- but the
harness could not see it at all. Discovery now walks depth 2 via the shared
module. Two tests pinned the old gap and are updated to the new truth rather than
flipped: gmod is now visible and held out by its reason, and the audit's red case
moves to a DEPTH-3 Application, which ArgoCD still applies and discovery still
cannot reach.

Witnessed: 13 new tests; four mutations each caught -- applicator ignores the
lane (1 red), discovery back to depth 1 (4 red), discovery ignores the lane (2
red), lane glob drops base deferrals (2 red). Existing suites green: harness 179,
partition 57, discovery 28, census 20, footprint 22, use-cases 59, manual-sync 22.
tsc 0, actionlint clean.

WHAT A GREEN LANE DOES NOT YET PROVE, stated on the workflow step too:
- HA. The tree is served at `dev`, so subjects run at dev replicas. Serving
  subjects at `metal` while dependencies stay at `dev` is the next step.
- Some lanes are mostly dependencies. lane-1's only subject is `temporal` and
  lane-2's are `gmod` + `redis`; temporal and gmod are excluded from the dev
  proof by written reasons. The partition does not yet know which subjects the
  proof can test, so it can spend a runner re-asserting shared dependencies.
- Nothing has run live. The first CI run of this workflow is the first bring-up.

FIRST LIVE RUN, and what it changed (35919883647). Every lane came up, scoped
correctly, and stalled on the SAME three shared base charts while its own charts
went Healthy -- lane-4 18/21, lane-5 16/19, lane-3 8/11: cilium, openbao and
spire, Progressing for 20 minutes. Two of the three came from a flag I left out:
both passing `included` jobs run `--ephemeral-vault-init`; without it OpenBao
stays sealed and spire waits on it. Added, with their 2400s timeout (job timeout
75). A single-node anti-affinity hypothesis was checked and REFUTED first -- the
passing kind cluster is also one node, and the operators are already 1 replica.
cilium is NOT explained: no `included` run has ever proven the ArgoCD cilium
Application Healthy (kind excludes it). The failure step now prints per-resource
health for every non-Healthy Application and the cilium rollout, so a repeat
stall names its resource.
