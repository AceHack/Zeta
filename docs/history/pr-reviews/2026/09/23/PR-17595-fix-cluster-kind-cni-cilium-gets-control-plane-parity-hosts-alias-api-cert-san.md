## Description

The brief asks for Cilium coverage to COUNT rather than be excluded. The lane
that would count it -- `PROBE kind+Cilium included proof`, dispatch-only -- was
dispatched on this work's branch (run 35929570637) and FAILED the same way it has
since 2026-09-09. Read, not guessed:

- 14 minutes into the run `cilium-*` was Init:CrashLoopBackOff and
  cilium-operator CrashLoopBackOff; 30 Applications went Degraded/Progressing
  behind them, starting with cert-manager's webhook becoming unreachable.
- The sequence: the bring-up helm-installs Cilium with `k8sServiceHost`
  rewritten to the kind node's Docker DNS name (cilium-kind-lane.ts says so in
  its own log line). The included lane then LIFTS the `cilium` Application
  (`ciliumOwnsCniSlot`), ArgoCD adopts the release and selfHeals it back to the
  metal value `control-plane` -- which the kind node cannot resolve, and which
  the kind API server's certificate does not name.
- k3d hit the identical defect and already carries the fix
  (`applyK3dControlPlaneHostsAlias`: `127.0.0.1 control-plane` in the server
  node's /etc/hosts); metal gets the pair from k3s-server.nix (/etc/hosts +
  `--tls-san=control-plane`). kind had neither half.

THE FIX, both halves:
- `applyKindControlPlaneHostsAlias` writes the same idempotent line into
  `<cluster>-control-plane` right after the API is up and before the catalogue
  can lift the Application (the agent is hostNetwork, so the node's /etc/hosts is
  what it reads). The line is now one shared constant for k3d and kind.
- ci.cilium.kind-config.yaml adds `control-plane` to the API server's
  `certSANs` (kubeadm ClusterConfiguration patch), so TLS verification accepts
  the name once it resolves.

FALSIFIERS (use-cases.test.ts +2): the kind cilium bring-up writes the alias
into `<cluster>-control-plane` before the catalogue, kindnetd never does; the
profile carries the SAN. MUTATION-CHECKED 3/3 (alias call dropped, alias written
into the wrong container, SAN removed).

NOT CLAIMED: that the probe now passes. The lane is 90 minutes and
dispatch-only; it is re-dispatched on this branch and its verdict is what
decides whether the probe can be promoted to run on push. If another blocker is
behind this one, it will be named from that run's log, not inferred.
