## Summary

081M35K4PV6087G0R001Z3E0P8 (WP24). PR #17540's audit named `gitlab-initial-root-password` a "known, separately-tracked gap — never minted at all." The real defect was mechanical, not a missing decision: `gitlab/Application.yaml` sets `global.initialRootPassword: { secret: gitlab-initial-root-password, key: password }`, and that reference had **zero occurrences** in `audit-existing-secret-is-minted.ts`'s own output — the chart spells the field `secret` (a bare leaf), not `existingSecret`/`secretName`/`secretKeyRef.name`, so the audit's detection regex could never see it.

- **Mint it**: `internal-secret-seeding.yaml` gains a `seed-gitlab-root` ServiceAccount/Role(create-only)/RoleBinding/Job in namespace `gitlab`, same draw-entropy + tmpfs + `kubectl create secret generic` shape as every sibling credential in that file. `dev-cluster/lib.ts` gains `DEV_GITLAB_ROOT_SECRET` for dev/CI, cross-checked against the metal manifest by `internal-secret-seeding.test.ts`.
- **Password rule, checked not guessed**: docs.gitlab.com/user/profile/user_passwords/ (chart appVersion v17.7.0) — min 8, max 128, no breach-list match, no name/username/email/predictable-word substring, **no character-class requirement** (unlike OpenSearch). A plain 64-hex-char CSPRNG draw satisfies this by construction.
- **Why we don't rely on the chart's own generator**: GitLab's `shared-secrets` pre-install hook would mint this Secret too, but its RBAC grants `get`/`list`/`create`/`patch` and GETs-then-PATCHes — broader than the create-only posture `internal-secret-seeding.yaml`'s own header established for every sibling credential (WP14/WP16). Seeding it ourselves keeps GitLab on the same posture.
- **The other GitLab reference**: `appConfig.object_store.connection.secret` / `registry.storage.secret` both point at `zeta-blob-store`, already minted (namespace added in the #17486/#17505 lineage) — confirmed covered, not a second gap.

## Sweep — the durable fix
