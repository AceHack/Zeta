## Description

## What

Follow-up to #17569 (merged). The new 3-node HA cluster test has run twice on hosted runners. Both runs got through cluster formation and then timed out waiting for the PVC to bind. This PR changes only the test harness. It touches no product module and grants the product no reachability or configuration it does not ship.

### What the two runs measured

| run | setup | reached | failed at | host RAM peak |
|---|---|---|---|---|
| 35920509908 | 3 × 4096 MiB, all state on the root images | 2 joins as etcd members, one CA, source-scoped etcd rules, 3 nodes Ready, Longhorn on 3 nodes with each disk registered, `numberOfReplicas=3` (1476 s) | PVC bind (900 s). etcd `slow fdatasync` over 1 s, applies up to 5.7 s, k3s restarting on every server | 14572 / 15989 MiB |
| 35926193063 | 3 × 3584 MiB, `/var/lib/rancher` on its own `cache=unsafe` disk | 3 nodes Ready at 336 s, Longhorn up at 1155 s | PVC bind again. 26847 slow-fdatasync warnings; CSI sidecars only created 2 min before the timeout | 13213 / 15989 MiB |

### Changes

- **`/var/lib/rancher`** (etcd and containerd state) moves to its own emulated disk. Both extra disks use `cache=unsafe`.
- **etcd's `db` directory** moves to tmpfs (1 GiB cap).
  - The host has almost no free memory left for page cache, so writes stall whatever the qemu cache mode is.
  - Only server3 crashes, and quorum survives on the other two, so nothing the test proves depends on etcd surviving a guest crash.
  - `db/etcd` is not pre-created, so `k3s-datastore-preflight` still sees a from-scratch node.
- **Joiners' k3s is actually held back now.** Longhorn's disk annotator declares `wants = k3s.service`, so it started the joiners' k3s at boot (measured at ~49 s, before the founder existed). The annotator is now held back as well, and the script asserts k3s is inactive before starting it.
- **Every long wait dumps diagnostics** on timeout: nodes, pods, PVC/PV/VolumeAttachments, events, Longhorn CRs, and csi-provisioner logs. Run 1 died without any of this.
- **The `cluster-ha` job is now `workflow_dispatch` only** until it has a green hosted run. Both measurements are in its comment. On push it would currently be a standing red on every `full-ai-cluster` change. The wider trigger set comes back in the change that records the first green run.

## Verification

- **Needs CI:** only a dispatched `only_cluster_ha` run on this branch can prove whether it passes.
