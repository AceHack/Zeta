## Description

The maintainer, 2026-09-23: "where possible like PVC we should try to have an
abstraction so no chart is requesting a specific PVC provider, it references
some class of PVC that's more abstract."

Before: 20 class lines across 16 Applications wrote `longhorn` and seven wrote
`zeta-local-path`. Dev could only run them by faking the provider -- a
StorageClass literally NAMED `longhorn` bound to rancher.io/local-path.

THE CAPABILITIES (src/Core.TypeScript/cluster/storage-capabilities.ts)
  zeta-block-replicated  durable RWO; metal -> driver.longhorn.io (1 replica on
                         one box, as the chart's defaultReplicaCount); dev -> local-path
  zeta-block-local       node-local RWO, THE DEFAULT; metal + dev -> local-path
  zeta-shared            RWX; metal -> Longhorn share-manager (nfs-utils already in
                         longhorn-prereqs.nix); dev -> deliberately UNBOUND
Each cluster binds the names in ONE file: metal in nixos/modules/local-storage.nix
(k3s auto-manifest, present before ArgoCD), dev in dev-cluster/manifests/
(zeta-block-{local,replicated}.yaml, replacing longhorn.yaml + zeta-local-path.yaml).

TWO DESIGN CALLS, BOTH ARGUED FROM THE TREE
- The default is zeta-block-LOCAL, not zeta-block-replicated (the brief proposed
  replicated). Measured: the class-less claims in the render (dapr 48, gitlab 66,
  loki 20, mimir 6 GiB) total ~140 GiB; defaulting them onto the budgeted
  Longhorn pool takes it from 943 GiB to ~1083 GiB against 1047 GiB usable on the
  smallest registered node -- over the box. And the default must provision at
  first boot, before Longhorn's wave -15 (vault/TOPOLOGY.md fact #6). Moving it
  is a disk-budget decision left to the maintainer, stated in the module.
- WaitForFirstConsumer on BOTH clusters. local-path needs the scheduler's node
  (Immediate would pick one first -- wrong on multi-node); for Longhorn it is the
  topology-aware mode. Metal's replicated class moves from the chart's Immediate;
  dev was already WFFC. Cost stated: a PVC with no consumer never binds.
- Dev now has ONE default like metal: bring-up clears the default mark on kind's
  `standard` / k3s's `local-path` when present.

MIGRATION
- Every Application/bootstrap manifest: longhorn -> zeta-block-replicated,
  zeta-local-path -> zeta-block-local, arc-runner-set's RWX model cache -> zeta-shared.
  Blueprint default (platform-controller) -> zeta-block-replicated.
- rendered-storage-claims snapshot REGENERATED ONLINE (helm, network): only the
  class names moved -- same 37 claims, same sizes, unrenderable still [].
- Harness: `devLonghornStorageClassAliasDeclared` -> `devBoundStorageCapabilities`
  (a SET, fail-closed per file); the storage rule is now "requests a class dev
  does not bind"; the live assert checks every bound class's provisioner.
- Disk ladder: governs the metal LONGHORN POOL, whose member classes are DERIVED
  from the metal bindings (`metalPoolCapabilities`) -- crossCheckClaims takes a
  set; budgetedStorageClasses = [zeta-block-replicated]; ledger prose figures
  re-keyed (the ledger-figures check caught 879 -> 779 + 100 zeta-shared).
- A real hazard caught on the way: audit-vault-topology-coherence read "declared
  in the k3s manifest" as "provisionable at boot". With the Longhorn-backed
  capabilities now declared there, that would have cleared a wave -60 claim on
  zeta-block-replicated. Availability now follows the PROVISIONER.
- first-boot-replica rebinds the one metal zeta-block-replicated document to the
  dev binding (a StorageClass provisioner is immutable, so a second object of the
  same name could not apply), and THROWS if there is nothing to rebind.
- reason-truth caught four stale citations (the deleted alias path; pvc-class
  `longhorn` for ollama/vllm/hindsight) and they are re-anchored. The `longhorn`
  exclusion reason now says what it is: the chart needs block devices, covered by
  nixos/tests/longhorn-volume-binds.nix; it holds no other Application out.

THE FALSIFIER: storage-capabilities.ts, run in the plan job. An ALLOWLIST over
every Application + bootstrap manifest AND the committed render -- a provider
name nobody listed is refused too -- plus per-cluster bindings held to one
default + WFFC + what each promises. 14 tests.

MUTATION-CHECKED: 17 mutations, 17 caught (allowlist, render scan, default
count, dev-binds-RWX, Immediate, pool derivation, dev binding provisioner/name,
storage rule off / any-bound-suffices, vault boot-vs-provisioner, replica
rebind no-op / wrong document, stock-default clearing both directions, dropped
binding apply, crossCheck set).

MIGRATION NOTE FOR A LIVE METAL CLUSTER: a StatefulSet's volumeClaimTemplates
are immutable, so an already-running StatefulSet whose class name changed will
need `kubectl delete sts --cascade=orphan` before ArgoCD can re-sync it. Bound
PVCs keep their data and their old class; only new claims use the new names.

Dry-run: 48 charts, 35 asserted on kind/kindnetd -- unchanged, as intended for a
rename (the lane-sizing PRs are what move that number).

WFFC CONSEQUENCE, NAMED CONCRETELY: on metal, `ollama` (replicaCount 0) and `vllm`
(replicas 0) are manual-sync and scaled to zero; their 200Gi claims have no consumer, so
under WaitForFirstConsumer a hand-triggered sync leaves those PVCs Pending (Progressing)
until a replica runs. That is the truthful state -- nothing is using the volume -- and the
manual-sync contract accepts Missing. The orphaned arc-runner-set model-cache PVC is the
same case and is already registered as declared-never-rendered.
