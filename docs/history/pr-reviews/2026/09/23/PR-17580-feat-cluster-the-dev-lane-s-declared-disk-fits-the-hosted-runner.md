## Description

The maintainer, 2026-09-23: make dev capacity actually fit. Measured first: the
dev lane (40 applied Applications) declared ~582 GiB of PVC on a runner with
70 GiB free, ~32 GiB of which its images take. local-path is thin (a directory,
no quota), so none of that was bytes on the runner -- ollama's own manifest says
so -- but a declared capacity the substrate cannot honour is a claim the lane
does not keep. After this change: 31.8 GiB declared against a 34.2 GiB budget
(70 free - 4 reserved - 31.8 images). FITS. Metal keeps every committed size.

THREE PIECES, each reusing a mechanism that already existed

1. `ci` STORAGE RUNG at the bottom of the existing ladder (storage-profiles.json),
   the brief's "reuse the size profiles if right" -- it was. Sizes are one idle
   smoke-test replica's worth; pods EQUAL `measured` on every row (asserted), so
   dev changes DISK and never the replica topology it asserts (cockroachdb stays
   3, nats 3, redis 3). `storageProfileForResourceRung: {dev: ci}` joins the two
   ladders; `--serve-tree dev` now applies resource rung -> storage profile ->
   rung overrides to the STAGED copy (`applyServeTreeRung`, one exported function
   the tests drive offline). The tree's activeStorageProfile stays `measured`.
2. DEV RESIZE OVERRIDES for the claims the ladder does not govern -- every one on
   `zeta-block-local` or a class-less chart default: dapr scheduler (48 GiB ->
   3), forgejo, loki backend+write, mimir kafka+alertmanager, openbao data+audit,
   opensearch, seaweedfs, spire. One override per Application, each with its own
   substrate reason and exit. The loader gained an optional `resizes:` list naming
   the RENDERED claim each override shrinks, and REFUSES a resize whose size no
   `set` value writes.
3. `rung-override-audit.ts`, run in the plan job:
   - every override path under `valuesObject` is classified against the pinned
     chart's schema snapshot (inert-valuesobject-keys' own machinery). A typo'd
     key edits the staged tree, passes the no-op refusal, and changes nothing the
     chart renders -- this is what catches it. 0 findings on the live roster.
   - prices every rendered claim of every applied Application at the size the
     dev lane SERVES (ladder row at `ci`, counted once per row; else a declared
     resize; else the committed size -- an unpriced claim COSTS, it is never
     free) against free - reserved - the applied cohort's images. A resize naming
     a claim the render lacks is refused as stale.

The k3d job's comment said "PVC sizes stay at the metal storage profile ... Do not
invent a fourth budget". This prices against the SAME runner envelope, not a new
one, and the comment is updated to say what changed and at whose request.

HONEST LIMIT: the audit reads the committed render snapshot, not a render of the
staged tree (that needs helm + network). Check (3a) is what makes that sound: an
override resizing through a path the chart reads renders at the size it declares.

FALSIFIERS: rung-override-audit.test.ts (17), including an offline end-to-end:
stage the tree, apply the dev rung, read cockroachdb at 1Gi staged / 48Gi
committed with replicas unchanged, forgejo 1Gi / 20Gi, dapr 1Gi.
MUTATION-CHECKED: 9 mutations, 9 caught (resize-vs-set check, unpriced-costs-nothing, stale resize, inert path accepted, fit forced true, images not subtracted -- which SURVIVED the first pass and got its own test --, serve tree skipping the storage profile, rung-mapping validation, per-claim instead of per-row ladder pricing).
