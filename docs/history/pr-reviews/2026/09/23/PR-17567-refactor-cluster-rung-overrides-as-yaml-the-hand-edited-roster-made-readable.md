## Description

The per-rung field-override roster is hand-edited and its reasons are long
prose. As JSON every reason was one unbroken line and the header was an array
of strings. The maintainer wants hand-edited config human-readable, so it is
YAML now: folded `>-` scalars for reason/liftsWhen, comments for the header.
Generated snapshots (lane-footprints.json, rendered-*.snapshot.json) stay JSON.

Content is unchanged -- checked by deep-equality of the parsed `overrides`
array against the JSON it replaces before the JSON was deleted.

- The file carries `apiVersion: cluster.zeta.io/v1` / `kind: RungOverrides`,
  the same move sync-wave-dependency-graph.yaml makes: it sits under a manifest
  root kubeconform walks, where a kind-less document is an error and an unknown
  kind is skipped (measured: Skipped 2, Errors 0). The loader REFUSES any other
  pair, so a stray manifest at this path cannot be read as an override roster.
  New falsifier; mutation-checked (dropping the kind check turns it red, 1/1).
- rung-overrides.test.ts was named by no workflow step and no path filter, so
  editing an override triggered none of the lanes it shapes. It now runs beside
  lane-tree-source.test.ts, and the .ts/.test.ts/.yaml are in both path lists.
- opensearch/Application.yaml's header cited an override that no longer exists
  (the extraEnvs block moved into the manifest for both rungs); corrected.

Local: rung-overrides 12/12; tsc 0. lane-tree-source's live-bundle tests fail
8/27 on this macOS host identically on unmodified main (git clone --bare into
/var/folders), so they are left to CI's Linux runner.
