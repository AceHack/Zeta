## Description

`argocd-health-test.ts` wrote its own limit down, and it was a large one: the RWX guard scans the **checked-in** tree, but most Applications are `spec.source.chart` against an external `repoURL` — the repo holds a `valuesObject` and the PVC's access mode lives upstream. So for exactly the Applications it existed to protect, it scanned files that cannot contain the answer. A chart bump introducing RWX passed it, with a **hang** as the symptom (RWX never binds on local-path → pod `Pending` → ArgoCD reports *Progressing*, not *Degraded*).

`rendered-storage-claims.ts` already renders every chart and records `storageClassName`, `size` and `count`. It did not record `accessModes`. That is the whole missing wire.

## The two detectors turned out to be complementary

I went in to *replace* the checked-in scan. The measurement said not to:

- the render covers **23 Applications / 38 claims**;
- **`arc-runner-set` is not among them**, and declares `accessModes: [ ReadWriteMany ]` in its own committed `model-cache-pvc.yaml`.

Each sees a case the other structurally cannot — the scan sees in-repo manifests, the render sees upstream charts — so the guard now asks **both** rather than trading one blind spot for another.

## Measured, and it closes an open question

**Of 38 rendered claims, all 38 declare access modes and ZERO request `ReadWriteMany`.**

So no chart needs RWX for HA, and dev does **not** need an RWX-capable provisioner pulled in to serve one. The only RWX claim in the tree is a model **cache**, not an HA requirement.

## Silence is not clearance

`appsTheRenderIsSilentAbout` reports Applications neither detector covers instead of letting them read as safe. They are **not** excluded on that basis — excluding an Application for being *unmeasured* would quietly shrink the roster the proof covers.

The snapshot read fails **open**, deliberately and only there: a missing or corrupt file must not make every Application look RWX-free, and equally must not make them all look RWX and empty the proof roster. It yields `[]`, the checked-in scan still applies, and the absence surfaces as a reporting gap.

**Fixed on the way:** the snapshot cache ignored its `repoRoot` parameter, so the first caller's tree would have become every later caller's answer.
