## Description

fix(cluster): the nvidia device plugin is declared on a node that cannot apply it

Aaron 2026-09-07, on the host roles: "control-plane and worker-gpu are
distinctions, almost placeholders ... I'm not sure these are built right, we
built them a long ago and then did a bunch of design work and never updated."

Following that instinct found a live defect, measured by EVALUATING THE FLAKE
rather than by reading it:

  nixosConfigurations.worker-gpu.config.services.k3s.role      => "agent"
  nixosConfigurations.worker-gpu.config.services.k3s.manifests => [ local-path-provisioner,
                                                                    nvidia-device-plugin ]
  nixosConfigurations.control-plane.config.services.k3s.role      => "server"
  nixosConfigurations.control-plane.config.services.k3s.manifests => 12 entries,
                                                                     nvidia-device-plugin ABSENT

`services.k3s.manifests` writes each entry into
/var/lib/rancher/k3s/server/manifests, and the k3s DEPLOY CONTROLLER submits
them — on a SERVER. On an agent the files are written and nothing reads them: no
error, no warning, no applied resource.

So the NVIDIA device-plugin DaemonSet is declared exactly once, on the one node
that cannot apply it. `gpu-device-plugin.nix` says in its own comment that this
is the only route ("a future k8s/applications/gpu-device-plugin/ Application
could take over ... but it doesn't exist yet") and no such Application exists —
checked. CONSEQUENCE: GPUs are never advertised to the scheduler, so a GPU pod
stays Pending forever, and every check in the tree passes because nothing was
wired to notice.

`local-path-provisioner` is declared on the agent too, but ALSO on the
control-plane — dead weight rather than a gap. The distinction is in the roster.

THIS COMMIT DOES NOT FIX IT, on purpose. The fix turns on whether the device
plugin becomes a server-declared cluster concern or an ArgoCD Application, and
that choice belongs with the role-composability redesign Aaron opened in the
same message — GPU is ORTHOGONAL to the k3s role (measured: gpu modules touch
only `manifests` via mkMerge and `extraFlags` via mkAfter, while server/agent
both assign `role` outright), so "control plane AND gpu" is expressible today
and simply has no host expressing it. Choosing the fix before that design would
be choosing it twice.

WHAT THIS COMMIT DOES is make the defect impossible to lose again:
`audit-k3s-manifests-reach-a-server.ts` fails when a host imports a
manifest-setting module without importing a server-role module. It went RED on
the live tree at both worker-gpu and worker-template — the cookie-cutter, which
means fixing worker-gpu alone would reintroduce the bug on the next node
provisioned.

The two are ACKNOWLEDGED with the consequence and a LIFTS condition, so the debt
is visible rather than blocking. The roster may only SHRINK: a host that stops
being broken while still listed fails the audit, and a test asserts every
acknowledged host still has the defect. An acknowledgement that outlives its
defect is a stale claim about the tree.

Honest limit, in the file: the audit reads IMPORT LISTS, not evaluated config.
The eval above is ground truth and the audit prints the commands to re-run it.
