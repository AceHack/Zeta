## Description

fix(zetafs): Windows rewrote a virtual store path, so a bindings store read as new

Aaron: "i think we are having windows issues." Measured: both Windows legs fail
6/6 on recent main gate runs — `build-and-test (windows-2025)` and
`(windows-11-arm)` — and it is ONE test out of 6545:

  ZetaFsFreezeTests."new freeze volume writes ns=bindings and git-trees deltaLog
  still refuses" — Assert.Throws() Failure: No exception was thrown.

ROOT CAUSE, and it is a single line. `ZetaFsDeltaLog.fs:36` did
`Path.GetFullPath dir`. A ZetaFs store path is a VIRTUAL, POSIX-rooted path —
every other path operation in that type goes through `ZetaFsPath`, separator
'/', whose `join` already carries a `rooted` concept. That `GetFullPath` was
the ONLY OS-dependent path call in the subsystem, which is precisely why it
produced a single-platform failure.

On Linux and macOS `Path.GetFullPath "/store"` is the identity. On Windows it
returns `D:\store` — drive-qualified, backslashed. The `FileSystem` still holds
the store at `/store`, so the FORMAT probe missed, an `ns=bindings` store was
read as a NEW store, and the refusal the test asserts never fired.

THE HEALER HAD ALREADY FOUND IT AND CORRECTLY DECLINED TO FIX IT:

  [zetafs-virtual-path] src/Core/ZetaFsDeltaLog.fs: line 36: Path.GetFullPath
  resolves against the process CWD — ambient state. NOT auto-healed: removing it
  changes behaviour for real-path callers. Needs a human.

It was right on both counts — the line is ambient state, and deleting it would
have broken relative real-path callers. What it could not do is draw the
distinction, which is the entire fix:

  already POSIX-rooted -> a VIRTUAL path. Leave it alone; OS resolution corrupts it.
  anything else        -> a real relative/OS path. Resolve against CWD, exactly as before.

So real-path behaviour is unchanged to the byte, and virtual paths stop being
rewritten into a filesystem that does not hold them. A warning that sat waiting
for a human was the whole of the Windows breakage.

Added a test pinning the rule, with its limit stated in the test itself: on a
POSIX runner the assertion is trivially true and would NOT have gone red before
the fix. It cannot be made to — the divergence exists only where the OS path
rules differ. Its job is to put the rule somewhere a reader will find it rather
than inside a constructor comment.

Verified: `dotnet build src/Core` 0 warnings 0 errors, and 89/89 ZetaFsFreeze
tests pass locally on macOS. The claim that matters — the Windows legs — is
CI's to make, and I am not claiming it here.
