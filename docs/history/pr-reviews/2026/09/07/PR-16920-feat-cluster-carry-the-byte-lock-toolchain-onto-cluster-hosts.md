## Description

feat(cluster): carry the byte-lock toolchain onto cluster hosts

Aaron 2026-09-07, choosing against the alternative I had recorded: "we DO want to
be able to run the whole toolchain on the real hardware and cluster, so we don't
need to exclude."

The alternative was to record that cluster hosts do not need it, and the evidence
for that was real — measured 2026-09-06, `bytelock.yml` runs only on
ubuntu-24.04 / macOS / Windows GitHub runners and installs wabt via apt, brew and
choco, so nothing depends on the NixOS declaration TODAY. Rejected on purpose:
what CI happens to do now is not the bound on what the cluster should be able to
do.

Carried from `infra/nixos/modules/common.nix`, which was the ONLY NixOS
declaration of these nine and is scheduled for deletion
(081M00QCHWA087G0R000GKKRXD). Without this the deletion would have silently
removed the toolchain from every NixOS host — a capability lost to a cleanup,
which is exactly what rostering `src/wasm-dla/README.md` as `blocking` was for.

Packages: wabt, binaryen, emscripten, nodejs, zig, llvm, rustup, go, lua5 — the
nine substrates the byte-lock compares. Verified none was already present in
full-ai-cluster's `systemPackages` (checked per package, not assumed), so there
are no duplicate entries.

README repointed to the surviving module, and it now says the coverage is a
DECISION rather than an accident of where a package list happened to live.

Roster: `src/wasm-dla/README.md` drops — it no longer names the stale tree, and
it was one of the three remaining `blocking` entries. The new module is `prose`:
its only mention is the paragraph recording the provenance and the rejected
alternative. blocking 3 -> 2.

Verified: `nix-instantiate --parse` on the edited module exits 0, and the
cluster-tree-consumers audit is green.
