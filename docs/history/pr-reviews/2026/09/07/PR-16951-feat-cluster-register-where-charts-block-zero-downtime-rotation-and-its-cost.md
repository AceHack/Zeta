## Description

> Aaron 2026-09-07: *"we should record where charts limit us and how much downtime it costs to rotate. This might mean pushing upstream changes to the chart or holding our own fork."*

## The doctrine already exists — the gap is conformance

`docs/DECISIONS/2026-06-15-zero-downtime-id-rotation-pattern-overlap-window-dual-key.md` is **Active** and applies the overlap-window dual-key pattern to *every* derived key and the CA, with TLA+-verifiable safety (the identifier always resolves). Aaron's *"3 versions per access level"* is that pattern at N=3 rather than N=2, and his note that credentials travel on Z-sets over DBSP puts rotation **inside** the zero-downtime schema-evolution work rather than beside it.

So the ADR is a decision about **our** keys. A third-party Helm chart whose values take one secret name and one key **cannot express an overlap window no matter what we mint.** This registers each case with a named exit.

## Five minted credentials, and the answers are not uniform

| exit | credential | why |
|---|---|---|
| **NOT_NEEDED** | `redis/redis-auth` | Valkey defines **users**, not one password — the ACL model *already* expresses concurrent credentials. Overlap is available without touching the chart; we just mint one user instead of N. **First candidate for N=3; nothing external blocks it.** |
| **UPSTREAM** | `openziti/ziti-admin-credentials` | The ziti controller is an identity authority for the mesh, so its own admin credential is where an overlap window is worth most. UPSTREAM not FORK — the change is small and generic, every operator benefits, and forking an identity component to rotate its own key is the worst of both. |
| **ACCEPT** | `grafana`, `forgejo` | One name; operator logins seeded at first boot. A restart-length gap costs a human a retry, not cluster availability. |
| **ACCEPT** | `opensearch` | `SINGLE_BY_DESIGN`, and read as such: the variable is the **INITIAL** admin password, seeding the security index on first boot. Live rotation goes through the security API, so the chart field is the wrong lever — neither UPSTREAM nor FORK helps. |

That non-uniformity is the argument for a register rather than a blanket rule.

## Two honesty rules, enforced rather than stated

1. **Downtime is `UNMEASURED`, never estimated.** Nobody has measured a rotation here. An estimate in that column would be indistinguishable from a reading the next time someone quoted it. Every `UNMEASURED` row must carry a `measurementRoute` naming what would produce a real number, and the audit **refuses a row that lacks one** — a cost nobody can ever measure decays into a permanent excuse.
2. **`upstreamCapability` defaults to `UNVERIFIED`, and FORK on an UNVERIFIED chart is refused.** Whether a chart *could* accept a set is a claim about their contract, not ours; asserting it from our own values file reads our configuration as if it were their schema. Forking a chart nobody has opened is deciding to maintain it sight-unseen.

Drift is caught both ways (a minted Secret with no row; a row naming a Secret nothing mints), and a row whose Application no longer names its Secret is caught by reading the tree.

**Mutation-checked, not assumed:** deleting the redis row turns the suite red (8 pass / 1 fail); restoring it green (9 pass / 0 fail). Negative-path detectors run against a nonexistent root so the detector does the work, not the fixture.
