## Description

fix(security): enforce the premise under Scorecard alert #24 (SAST coverage of main)

Alert #24, open since 2026-04-27 and re-reported by today's Scorecard run: "SAST
tool detected but not run on all commits: 12 commits out of 29 are checked".

THE ALERT IS TRUE. CodeQL runs per PUSH, not per COMMIT, so an intermediate commit
inside a multi-commit PR is never scanned. Measured 2026-09-13:

    PR #17394    2 commits    2 scanned
    PR #5323     3 commits    2 scanned
    PR #17341   10 commits    4 scanned

Scorecard's wording is "12 COMMITS out of 29", and that is exactly the population.

IT IS NOT A HOLE IN `main`. This repo squash-merges: an intermediate commit on a PR
branch is discarded at merge and never enters `main`'s history. The property that
matters -- every commit that actually LANDS is scanned -- holds:

    last 30 commits on main       30 / 30 carry a successful `Analyze (*)` run
    last 29 merged PR heads       29 / 29 carry one

That reasoning is worth nothing while nothing checks it, which is the vacuity class
pointed at a dismissal. `audit-sast-covers-main.ts` is the check. It goes red the day
a commit lands on `main` without a successful Analyze run -- the day the dismissal
stops being justified. Live against main today: 12/12 scanned, 1 degraded.

FOUR HYPOTHESES, THREE REFUTED, AND ONE OF MY OWN INSTRUMENTS WAS THE BUG:

  1. main commits unscanned                 REFUTED -- 30/30 scanned
  2. merged PR heads unscanned              REFUTED -- 29/29 scanned
  3. Scorecard counts `github-code-scanning` app runs and we have none
                                            REFUTED as an explanation: we do have
                                            none (all 106 check runs on main come
                                            from `github-actions`), but the model
                                            predicted ~12 present and measured 0
  4. intermediate commits in multi-commit PRs unscanned        CONFIRMED

The first pass at #4 reported `scanned=0` for EVERY multi-commit PR -- a crisp
all-or-nothing rule that was an artifact: a nested `gh api` inside a piped
`while read` had its stdin consumed, so every commit read as unscanned. The true
numbers are above and are messier. A measurement that produces a tidier story than
the truth is the one to re-run.

THE FORCING CASE THE CHECK IS BUILT AROUND. A cancelled Analyze run still CREATES a
check run, so counting run EXISTENCE reports coverage over a commit nothing scanned.
That error was made during this very investigation: counting commits that "have
Analyze check-runs" gave 30/30 while 36 of 99 CodeQL runs on main were being
cancelled. `judge()` counts successful runs only; a commit with 3 cancelled Analyze
runs and 0 successes is UNSCANNED, and there is a test pinning exactly that.

FALSIFIER, NOT DECORATION. 7 tests, control 7 pass / 0 fail; three mutants killed:
  count run existence instead of outcome   -> 6 pass / 1 fail
  empty sample passes vacuously            -> 6 pass / 1 fail
  never report unscanned                   -> 4 pass / 3 fail

Drift tier on purpose: it reads the forge over the network, so it cannot sit in the
required floor and a network failure must not read as a coverage failure.
