fix(security): the bun version is declared once -- 54 of 55 restatements disagreed

MEASURED 2026-09-13. `mise.lock` resolves bun to 1.3.14. Of the 55 `bun-version:`
keys under `.github/`, exactly ONE matched it:

    32  bun-version: latest      no pin at all
    12  bun-version: "1.3.13"    one patch BEHIND the lock
     9  bun-version: 1.3         a range, resolved per-run by setup-bun
     1  bun-version: 1.3.13      same value, unquoted
     1  bun-version: 1.3.14      the only site agreeing with mise.lock

CI ran at least three different bun versions depending on which workflow you landed
in, and the one site matching the declared lock was outnumbered 54 to 1. Nothing
checked it: `audit-dotnet-pin-parity.ts` settled exactly this question for .NET and
had no bun counterpart.

`latest` is the sharp one, and "unpinned" undersells it. It is an UNDECLARED ENTROPY
CHANNEL (manifesto §13): the toolchain moves with no commit, so a run cannot be
replayed and a green result cannot be attributed to the source it claims to test.
`gate.yml` itself carried one, on the job that classifies the PR's domain.

THE RESOLUTION, the same shape audit-dotnet-pin-parity settled for .NET:

    `mise.lock`'s resolved bun version is the SINGLE DECLARED SOURCE.
    Every `bun-version:` under `.github/` is a checked RESTATEMENT of it.

The LOCK rather than `.mise.toml`, because `.mise.toml` says `bun = "1.3"` -- a
range, which the dotnet audit refuses as canonical for the reason that applies here
too: mise resolves it per-machine, so a restatement has nothing single to check
against. The range is not demoted; the check requires the lock to satisfy it.

All 55 keys now read "1.3.14": 55 insertions / 55 deletions across 39 workflow
files, every added line a bun-version line, all 39 still parsing.

A SECOND RESTATEMENT, FOUND BY THIS PR GOING RED. `gate-narrow-js-jobs.test.ts`
asserted the literal `bun-version: "1.3.13"`. Updating that literal would have
relocated the drift, not removed it -- a test that hardcodes the value it checks
cannot notice the value moved. It now reads the version from `mise.lock`. Its intent
("these narrow jobs pin bun rather than reaching for install.sh") never depended on
which version was pinned. Checked that the derived assertion still discriminates:
with `mise.lock` mutated to 1.3.99 and gate.yml unchanged, 3 of its 4 tests fail;
restored, 4 pass and the lock is byte-unchanged.

AN UNTESTED EXPORT, FOUND BY REVIEW. The code-quality bot reported an unused import
of `parseMiseBunRange`, and `lint (TS)` was red for the same symbol -- one defect
from two directions. The tempting fix is to delete the import, which silences the
reviewer and keeps the gap: an unused import in a TEST file is the visible edge of
an untested export, and this one reads the `.mise.toml` pin the whole parity claim
is checked against. Four tests added instead, including the two an unanchored regex
would fail: a commented-out `# bun = "9.9.9"` must not win, and a tool named
`sunbun` must not match.

FALSIFIER, NOT DECORATION. 24 tests, control 24 pass / 0 fail. Four mutants, all
killed (measured at 20 tests, before the four above were added):
  segment compare -> string startsWith    -> 19 pass / 1 fail
  tolerate `latest`                       -> 18 pass / 2 fail
  unanchored lock regex (picks dotnet's)  -> 10 pass / 10 fail
  missing lock -> pass                    -> 19 pass / 1 fail

The first mutant SURVIVED at first, and that is the useful part.
`satisfies("1.3.1", "1.3.14")` was written as the forcing case for segment-vs-
character matching and proves nothing: the length guard returns false before the
comparison runs, so the test passed because an EARLIER guard fired. The real case
needs the pin shorter than the version -- `satisfies("1.3", "1.35.0")`, where
`"1.35.0".startsWith("1.3")` is true and minor 35 is not minor 3.

Wired as cross-verify leg `bun-pin-parity` through the roster; the roster's own
parity test refused the entry until `--derive --write` regenerated gate.yml's matrix
and docs/ci/CROSS-VERIFY-CHECK-NAMES.md.

Not changed, and named so it is not mistaken for an oversight:
`nci-witness-capability.test.ts` notes that Bun 1.3.13 crashes in a VM callback. The
workaround there refuses dynamic-import syntax before execution; it holds regardless
of bun version, and the bump neither breaks nor obsoletes it.
