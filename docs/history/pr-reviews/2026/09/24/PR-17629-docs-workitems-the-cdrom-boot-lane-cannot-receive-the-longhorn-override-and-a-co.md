## Description

Files `081M39QY9N8087G0R000E08D2B`, and corrects a claim I made in #17625.

## The gap

`081KSNY2Z0008QG0R0008PN7RQ scenario 2 — boot + install substrate` boots the installer from `-cdrom`. **A cdrom exposes no vfat partition**, so there is nowhere to stage `/zeta-firstboot.conf` and no way to deliver `ZETA_ALLOW_LONGHORN_UNDERSIZED`. It bails before the wipe on the #17611/#17614 pre-wipe refusal and cannot be unblocked by the mechanism that unblocks every other lane.

## The WP27 scan instrumentation named it in one line, on its first real use

Run 35996447262, `qemu-full-install-serial.log`:

```
[081M392JR97087G0R003QAFH0Y-esp-conf] esp-conf=none tried=/dev/disk/by-label/ZETA_INSTALL(no-vfat)
ERROR: BOOT disk /dev/vda is 40 GiB, which cannot hold ESP 1 GiB + root floor 120 GiB
+ a 1 GiB minimum longhorn1 tail (need >= 122 GiB).
```

One candidate — the ISO9660 label — and `(no-vfat)` says it would not mount. Before #17625 this path produced **no output at all** and the failure was indistinguishable from a lane that staged nothing.

## A regression from the gate, not from the harness

| run | time | scenario 2 |
|---|---|---|
| 35968222668 | 07:10, **before** #17611/#17614 | **success** |
| 35985197702 | 10:05, after | failure |
| 35996447262 | 12:01, after | failure |

The gate is correct on its own terms: a 40 GiB disk genuinely cannot hold the 943 GiB roster.

## The claim of mine this refutes

#17625's body says *"all five `qemu-full-install-test.ts` invocations in `build-ai-cluster-iso.yml` set a flag that reaches the USB-image branch, so no lane needs the override and misses it."*

**That is wrong.** Scenario 2 reaches the harness through `src/Core.TypeScript/zflash/test-harness/run.ts --scenario boot-cluster-up`, so a grep for `qemu-full-install-test.ts` in the workflow does not find it, and it sets only `QEMU_FIRST_SESSION_PHASE3=1` — which does not force the USB-image branch. I checked the wrong set and stated the result as exhaustive.

## Four options, none taken here

Named strongest-first in the work item: a non-boot FAT stick beside the cdrom (existing machinery, but it perturbs the disk enumeration this lane partly exists to test); a fw_cfg-delivered conf (a security-surface decision, and `fw_cfg` does not exist on metal so it can never be the general answer); raising the disk past 122 GiB (clears the first gate only — the capacity verdict still refuses); or flashing the lane (which deletes the cdrom coverage).

Routing, not guessing.

## Not blocking WP11

WP11 boots a flashed image and reads its ESP conf correctly — `esp-conf=esp:/dev/disk/by-label/EFIBOOT` in the same run.
