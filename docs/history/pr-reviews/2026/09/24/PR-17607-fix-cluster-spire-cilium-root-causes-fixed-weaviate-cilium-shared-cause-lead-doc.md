### cilium + weaviate — a strong shared lead, not yet a fix

Once cilium's resync loop stopped, its remaining symptom became
byte-identical to weaviate's: `Synced`, fully converged workload, zero
events, no health message, and an application-controller log that never
syncs anything yet never reports Healthy. `grep -rl RespectIgnoreDifferences
full-ai-cluster/k8s/applications/*/Application.yaml` returns **exactly
these two files** (now three, with seaweedfs — see below) and no others in
the 42-app roster — the only apps using that sync option are the only apps
showing this symptom. Documented with a concrete reproduction plan in
workitem `081M38GCTFX087G0R003MMTXJE`; seaweedfs was fixed anyway (per
explicit direction) as a deliberate, watched bet, recorded as such in its
own Application.yaml comment — six CI rounds (~7h) were spent gathering this
evidence and further live rounds did not sharpen it further.

## Also fixed (found while gathering evidence)

- **Stage 6 roster-stabilization race** (`rosterHasStabilized`): the very
  first triggered run on this branch (35943167812) settled at `apps=2`
  (only `argocd`+`zeta-root`, both trivially Healthy) *before* ArgoCD's
  app-of-apps recursion had created the other ~40 Applications —
  `allApplicationsSettled` is vacuously true over a list that hasn't
  finished growing. The run went GREEN in 35 minutes having assessed almost
  nothing. Now requires settled-AND-stable roster size across two
  consecutive polls.
- **`collectAppFailureDiagnostics`**: stage-6 FAILs never threw, so the
  existing `collectFailureDiagnostics` never fired for them — a FAIL
  carried only a one-line summary and no record of why. Now captures
  `describe pod` + `logs --previous` + namespace events + generation/
  revision fields + the Application's `.status.health` + matching
  application-controller log lines, automatically, for any future FAIL.
