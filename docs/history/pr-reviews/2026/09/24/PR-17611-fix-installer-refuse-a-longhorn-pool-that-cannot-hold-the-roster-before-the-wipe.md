## The headline is not the missing check — it is the existing one reading green

On a real single-disk USB control-plane install, **Longhorn is given a 1 GiB disk and the committed roster claims 943 GiB from it.** Fifteen Applications' PVCs pend forever on a cluster that otherwise comes up.

`single-node-readiness.ts`'s `capacity-provenance` compares the roster against the **sum of every block device** on the smallest registered node — 1047 GiB for `node-ad1efd` — prints a 763 GiB schedulable estimate, and exits 0 with `no blockers.` Its own header already carried the admission:

> counts the USB stick, and it ignores the ESP, the root filesystem, swap, and Longhorn's own reserve

The missing term is **partitioning**. Physical disks are not schedulable capacity, and on a single-disk box the whole question is `LONGHORN1_TAIL` regardless of how big the disk is. That is the expensive class this repo names most often: a check that did not measure the thing, looking exactly like one that passed.

## What lands

**1. `longhorn-geometry` — a fourth comparator, red before it is green.** Beside `capacity-provenance` and `compute-provenance`, same REFUSE-without-a-comparator shape.

- **Demand** is per-class `max(rendered, derived)` over the classes `metalPoolCapabilities()` reports as bound to `driver.longhorn.io` — read out of `local-storage.nix`, never a hardcoded pair. `max` because the two readings are blind in **opposite** directions and the tree exercises both: the YAML extractor cannot see upstream chart pod counts (779 vs rendered 843), and the render snapshot misses claims outside the trees it covered (0 vs derived 100). Taking either alone acquits on the class the other one sees.
- **Capacity** is the *installer's* geometry — `LONGHORN1_TAIL` read out of `zeta-install.sh`, plus each non-boot disk whole — with the boot disk assumed to be the **smallest** device. That is the most generous reading, which keeps the verdict convicting and never acquitting.
- The arithmetic prints on **every** run, green or not.

**2. A pre-wipe refusal in `zeta-install.sh`**, beside `assert_boot_disk_large_enough` — before the cancel window and ~130 lines before `wipefs -af`. Pure decision functions live in a marked `ZETA-LONGHORN-CAPACITY` block and are compared against a TypeScript oracle over every input class, the same discipline as `repo-pin` and `disk-preflight` (the ISO ships no bun and the repo is not cloned until after the wipe, so a module the shell "called" would be a golden vector nothing reads). The bail prints the arithmetic and three remedies cheapest-first, **leading with a second internal disk**, because the installer already formats every non-boot disk whole.

**3. The 75% usable fraction is derived, not chosen** — `min(over-provisioning, 100 - minimal-available)` over the chart defaults the deployed Application leaves in place, pinned by test to `mostConservativeUsableFraction`. What it still does not model (ext4 overhead, `storageReservedPercentageForDefaultDisk`) pushes real capacity **down**, so it stays an over-estimate and the refusal stays one-way.

## The constant cannot go stale quietly

943 is a literal in shell-reachable TypeScript only because nothing on the pre-wipe path can compute it. `longhorn-geometry` recomputes the demand from the snapshot on every run and **refuses, unacknowledgeably**, when the two disagree — and the readiness workflow now watches `longhorn-capacity-preflight.ts` and `zeta-install.sh` so that check actually re-runs.

## Parity found a real divergence while being written

The shell clamp is a digits-only parser; JavaScript's coercion is not. `" 931"` read as 931 and `"1e3"` as 1000 on the TS side, 0 on the shell side. Closed by making the oracle a parser too (`clampGibFromText`) — **not** by narrowing the fixtures.

## What this does NOT fix, stated plainly

Both registered nodes carry `115.5G` + `931.5G`. Read as generously as the registration permits that is **699 GiB schedulable against 943 of demand — short by 244.** Growing the `longhorn1` tail **cannot** close that on this hardware; it buys back only what ESP and root do not need. So the geometry change is deliberately **not** in this PR: the remedy is a maintainer call between a smaller storage rung, more disk, and a larger tail. The two shortfalls are recorded in the ledger as **debt**, with both numbers in the key, so a roster that grows, a tail that shrinks, or a node re-registered with different disks all re-redden rather than inheriting clearance.
