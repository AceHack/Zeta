## Description

## WHY

Run 35996447262 (main, first-ever WP11 green attempt): `noBadPods=FALSE` at
elapsed=141s, one second after `rootLanded` at 140s — the earliest possible
instant any pod could show transient startup-ordering churn. `spire-agent`
(a DaemonSet with no readiness dependency on spire-server's StatefulSet)
showed CrashLoopBackOff restarts=1. Verdict 6/6 was the ONLY one of six
verdicts in `zeta-first-boot-k3s-verify.nix` with no poll — a bare
`kubectl get pods` grep fired the instant verdict 5 resolved.

Judgement (081M39T5661087G0R001FTJ78W): ordinary startup-ordering churn,
not the confirmed-non-metal DNS/hostNetwork race (proven absent from VMs;
WP11 boots a real VM) and not a genuine defect — restartCount=1 is weaker
evidence than this repo's own already-measured clean-VM baseline of 3
restarts settling over 180s (081M343EM0R087G0R003C8ZHJ7, run 35706939767).

**This lane went green on `main` BEFORE this fix landed** (run 36014672753,
`main`@6fe58743d4: all six verdicts pass, `noBadPods=true` at 145s). That
does not make the fix unnecessary — it makes it more important. The old
code still on `main` at that point is exactly what was diagnosed: one
ungated `kubectl get pods | grep` snapshot, no loop, no retry. spire-agent
simply did not happen to be mid-restart at second 145 on that run. **A
verdict that goes green by luck goes red by luck** — the next person to see
this lane red would have been told "it passed last time," which is how a
flaky gate teaches people to re-run instead of read. This fix is the
difference between a lane that **IS** green and a lane that **HAPPENS** to
be green: it changes nothing about the passing run's own two-and-a-half
minutes (real convergence is still real convergence), it changes whether
the check is measuring convergence or measuring an instant.

## The fix

1. Give verdict 6 the same poll-to-a-bound shape its five siblings already
   have — `SOAK_SECONDS=180`, cited at the constant to the measured
   baseline above, not tuned to pass any specific run.
2. A pod counts as settled only once TWO CONSECUTIVE samples agree it is
   neither bad nor still accumulating restarts — never a single all-clear
   snapshot (a crash-looping container can read "Running" between crashes).
3. **A genuine crash-loop still fails — proven, not asserted.** The two
   pure decision functions are extracted VERBATIM from the `.nix` module
   and run under a real bash+awk in the new
   `wp11-nobadpods-shell-parity.test.ts` (same discipline as
   `longhorn-capacity-preflight-shell-parity.test.ts`). 8 tests, including
   "NEVER SETTLES": a restart count climbing across 5 simulated samples
   stays unsettled at every one, including the last.
4. One line, both outcomes distinguishable on serial:
   `noBadPods=true after 62s (N sample(s), M pod(s) total, all settled)` vs
   `noBadPods=false after 180s (N sample(s), M pod(s) total, deadline
   reached): ns/name restartCount=K still unsettled`.
5. **`k3s never became active` is now its own outcome, not a silent
   `true`.** MEASURED (coordinator, reading `main` directly): when
   `K3S_ACTIVE` is false the old code's pod-collection block never runs,
   `BAD_PODS_JSON` stays `"[]"`, and `NO_BAD_PODS` defaults `true` — a
   sixth verdict reading green as confirmation nothing was wrong while
   measuring nothing. `$K3S_ACTIVE` is now carried directly onto verdict 6
   (a distinct log sentence + a `k3sActive` JSON field), so this is never
   inferred from `podCount=0` — which a genuinely-empty-but-active cluster
   could also produce.
6. `podCount` + `samples` added to the JSON (optional fields, older
   verdict JSON still parses) — distinguishes "no bad pods among N" from
   "no pods at all", reportable-only.
7. Diagnostics gap closed in the same PR (it was small): `bad_pod_diag`
   mirrors the existing `k3s_diag` function's shape — `describe pod` +
   `logs --previous` for every still-unsettled pod at the deadline.
   Confirmed missing by grepping the full serial-log artifact for run
   35996447262: zero pod diagnostics beyond the bare verdict line.
