Same trigger, same preceding steps, same invocation, opposite outcome. So neither the trigger type nor "eleven QEMU-heavy steps ran first" is the discriminator — the loss is **intermittent**. The schedule/dispatch pairing in the work item is a confound: those two runs also differed in ref and ISO.

## Falsified: disk pressure truncating the image

Measured at each bake, on the bake's own filesystem (`df -B1 --output=avail`, which the harness already prints): both runs end their restore phase 1 at `runner free: 49.9` / `49.6 GiB`, reclaim 25.80 / 26.10 GiB about a second later, and bake a 1.63 GiB image into ~75.7 GiB free. Indistinguishable. (The `runner free: 72.9 GiB` quoted in the work item is measured *after* the failing phase 1 died early, so it describes nothing.)

Separately, truncation does not produce this symptom at all: the real failing ISO was baked locally through this exact path and truncated to 1 MB and 2 MB, and the ESP **loop-mounts fine** both times.

## What the symptom actually is

```
36014672753  esp-conf=none tried=EFIBOOT(no-conf),ZETA_INSTALL(no-vfat),/dev/sda1(no-vfat),/dev/sda2(no-conf)
36044770870  esp-conf=none tried=EFIBOOT(no-vfat),ZETA_INSTALL(no-vfat),/dev/sda1(no-vfat),/dev/sda2(no-vfat)
```

In the failing run **every** candidate refused `mount -t vfat` — including `/dev/disk/by-label/EFIBOOT`, a symlink that exists *only* because blkid had already parsed that boot sector. It stayed refused for the whole install (iter-4.2 missed the pubkey, iter-5.2 missed the hostname, WP11 missed its marker), so it is not an enumeration race that settles. blkid could read the FAT and the kernel would not mount it: a narrow class the kernel names on stderr every time, and both guest probes were sending it to `/dev/null`.

## What lands

1. **The guest keeps the mount error.** `(no-vfat)` becomes `(no-vfat:<reason>)`, squeezed space-free so `espConfScanOutcome`'s `tried=(\S*)` still parses; `zeta-install.sh` collects one `partition: reason` line per refusal and prints them in the iter-4.2 diagnostics block. Neither changes control flow. **This is the change that ends the investigation** — on the next occurrence rather than by another sampling run.

2. **The post-bake read-back stops reading only the part that is still readable.** `mdir ::` lists the FAT12 root directory, which lives at byte 5_632 of the ESP. MEASURED on the real failing ISO: that listing exits 0 on an image truncated to 1 MB *and* to 2 MB. It is now `mdir -/ ::` (recursive — walks every directory cluster through the FAT, including the ISO's own `EFI/BOOT/`) plus an `mtype` byte-exact round-trip per inline write, which is the only part that proves the data is *retrievable* rather than merely *indexed*. Content is never echoed — three ESP destinations carry plaintext secrets, and the mismatch test asserts the whole message by equality rather than by absence checks.

3. **`detectIsohybridEspOffset` now says whether the offset was confirmed.** The old function ended `if (guard) return fallback; return fallback;` — two branches, one value, so its own FAT-BPB check could not change the answer, sitting on the single number that every ESP write *and* the entire read-back address. When that number is wrong, writer and verifier are wrong **together** and the bake confirms itself. `prepareBootImage` now refuses `fallback-unconfirmed` before writing. The head buffer also grew from 141_824 bytes — exactly enough to check the fallback and nothing else, so an ESP past LBA 276 was structurally undetectable — to 8 MiB, read with a bounded `read()` instead of pulling the whole 1.67 GiB ISO into memory.

4. **The `only_wp11` step condition.** `UEFI keyfile restore decrypt` carried `if: github.event_name == 'workflow_dispatch'` with the `&& !inputs.only_wp11` half **missing**, while its own upload-serial-log sibling three lines below had it. Measured on 36044770870: every other dispatch-only step reported `skipped`, that one ran for **15m 48s**, and then its log upload skipped — so a scoped probe paid a quarter of an hour for a lane it had not asked for *and* the failure it produced could not be read. 36014672753 did the same four hours earlier. Both halves now agree, and `docs/ops/WP11-SCOPED-DISPATCH.md` carries the invocation (`-F`, not `-f`, for a typed boolean) plus how to confirm it took.

## Honest limits

- **The local replay used the ISO artifact, not the image that failed.** The baked USB image is not uploaded, so what was shown is that the bake's *inputs* are deterministic-good — not that the bytes QEMU booted were. Different claims.
- **Every read-back command addresses `<image>@@<espOffsetBytes>`**, so a bake that wrote at the wrong offset verifies at the wrong offset and passes. That class is refused by (3), before the write; nothing downstream of a write can catch it. Recorded in the code as a limit, not papered over.

Measured ISO geometry for whoever picks up the root cause: ESP at **LBA 268** (offset 137_216), 6144 sectors = 3 MiB, FAT12, `mkfs.fat`, label `EFIBOOT`. The `ISOHYBRID_ESP_OFFSET_FALLBACK_BYTES` constant (141_312, LBA 276) is **4_096 bytes inside that ESP**.
