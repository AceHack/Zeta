## Description

Docs-only, on `081M39CJP96087G0R001T4J2R3`. The code is already on `main` in #17638, #17640 and #17641; this records two things that belong in the work item rather than only in commit messages.

## 1. The autodetect correction, recorded as a correction

The mount ladder's attempt 2 was proposed as *"try `mount` with no `-t`, let the kernel autodetect"*. As written, that would have been **a worse bug than the one being mitigated**.

Both ESP probes walk **iso9660** partitions — `/dev/sda1` is in the failing runs' own `tried=` list — so an autodetect attempt can succeed on a filesystem that is not FAT, and the probe would then have sourced `/zeta-firstboot.conf` off it. Silently.

What makes attempt 2 safe to have at all is the `findmnt` confirmation of `vfat`/`msdos` and the unmount-and-refuse on anything unconfirmable. That is a **correction to the design**, not a guard someone happened to add, and the work item now says so in those terms.

## 2. A test harness that cannot report its own breakage is not a test harness

Worth writing down because it happened **inside the machinery built to catch this class**, which makes it the most instructive instance in the whole work item.

The bash harness for the ladder's falsifiers first read `run.ok ? run.value.stdout : ""`. An unspawnable shell would have parsed every field to the empty string and failed the assertions with the wrong story — a check whose failure is indistinguishable from its absence, reproduced in the tool written to refuse exactly that. Both halves are loud now: the spawn **throws** on failure, and the shell-function extractor **throws** rather than returning `""`, so the suite cannot pass against an empty function.

## 3. Three PRs, none claiming to close it

Stated plainly in the work item. The mitigation holding is not the cause being found, and the section on the ladder says `via=vfat` is the healthy shape while anything else is the mitigation firing — the difference between a mitigation and a fix quietly becoming permanent.
