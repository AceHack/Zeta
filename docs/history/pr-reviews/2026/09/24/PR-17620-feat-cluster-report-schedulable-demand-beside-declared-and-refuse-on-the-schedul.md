## The measurement

**DECLARED** demand is what the roster asks for. **SCHEDULABLE** demand is what the *currently registered fleet* could ever be asked for. They differ by **400 GiB — 47% of the pool the installer refuses against**:

| app | claim | why it cannot run here |
|---|---|---|
| `ollama` | 200 GiB | `nodeSelector: zeta.io/gpu: nvidia`, manual-sync only |
| `vllm` | 200 GiB | `nodeSelector: zeta.io/gpu: nvidia`, manual-sync only |

Every checked-in `ClusterNode` records an Intel display adapter, and `local-storage.nix` binds every capability class `WaitForFirstConsumer` — so a PVC with no schedulable consumer provisions nothing and reserves nothing.

**Why this is not tidying.** A guard that refuses an install over demand nobody can generate will eventually refuse a legitimate one, and then the operator sets the override reflexively. That is how a fail-closed check becomes a formality — and the check is only worth having while its number means something.

## Three verdicts, not two, and the third is the honest one today

`satisfied`/`unsatisfiable` would be wrong here, and wrong in the **acquitting** direction: an exclusion makes the demand smaller and the guard weaker, so it has to be **proven**, not inferred.

It cannot be proven from today's registrations. The capture was:

```sh
lspci -nn | grep -iE 'vga|3d|display' | head -1
```

**One device.** A box with integrated Intel graphics *and* a discrete NVIDIA card records the Intel one (00:02.0 sorts first) and the NVIDIA card is simply absent. So *"the registration says Intel"* is not *"this node has no NVIDIA GPU"* — it is *"the first display device is Intel"*, a different and much weaker claim.

```
declared                         943 GiB   <- keeps the exit code
proven unschedulable               0 GiB
UNDECIDABLE from registrations   400 GiB
schedulable                  543–943 GiB   (a RANGE)
```

Every excluded row is printed with the app **named** and the reason spelled out. A smaller number appearing unexplained is how a gate quietly stops meaning what its readers think it means.

## Derived on both sides, never a typed list

The vendor→PCI-ID table **and** the label key are read out of `nixos/modules/gpu-node-label-checks.nix`, for the reason that file states about itself: *"a label advertised from one place and checked from another drifts, and a drifted check passes."*

A vendor is identified by its **PCI vendor ID**, never by marketing text — a name containing "Intel" is not an identification, and a test pins that with an Intel-branded NVIDIA board.

## The capture is fixed, so the range can collapse

`spec.hardware.gpus` now enumerates **every** display device. `spec.hardware.gpu` is kept unchanged so old readers and old registrations still work, and the **presence** of `gpus` is what marks a record as a complete enumeration. Nothing backfills it — absence is meaningful. One node re-registering makes the exclusion provable and the split exact at 543 GiB.

## The installer refuses on the schedulable figure and prints declared beside it

The two constants are **equal today, and that is the point rather than an oversight**: nothing is proven, so schedulable == declared. When it drops, `longhorn-geometry` **refuses** while the constants disagree — the drop is a red gate, not a quiet one.

## Two heuristics, both leaning the safe way

The nearest-enclosing-`nodeSelector` walk inherits `replicasGoverning`'s limitation and can attribute a neighbouring workload's selector. The manifest-wide fallback — needed because a PVC is often its own document, which is exactly vllm's shape — is used **only when every selector in the manifest agrees**.

Either error would move a claim *out* of the schedulable total, the acquitting direction, so neither is trusted on its own: capacity leaves the total only once `classifySelector` proves it. `affinity.nodeAffinity` is deliberately **not parsed at all** — a half-understood parse of `In`/`NotIn` over required-vs-preferred tiers produces confident wrong answers.

## A property of the fleet, not of the roster

A node joining tomorrow with an NVIDIA card makes those 400 GiB schedulable with **no manifest edit at all**. Stated where it is computed and in the printed report.
