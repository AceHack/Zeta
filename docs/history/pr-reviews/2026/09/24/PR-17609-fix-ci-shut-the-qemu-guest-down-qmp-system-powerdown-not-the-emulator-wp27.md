## Description

## The finding (measured, not hypothesised)

`src/Core.TypeScript/ci/qemu-full-install-test.ts` `runQemuUntil()` tore every phase down like this:

```ts
qemu.kill("SIGTERM");
await Bun.sleep(2000);
if (!qemuExited) qemu.kill("SIGKILL");
```

**SIGTERM to `qemu-system-x86_64` kills the EMULATOR.** The guest OS inside it is never told anything: its page cache is discarded and every dirty block that had not reached the virtual disk is lost. On ext4 with delayed allocation that produces files whose inode exists and whose data blocks never landed — **zero-length files**.

Measured on run 35954415942's `qemu-k3s-first-boot-verify-serial-log`: on the phase-3 boot, every file under `/var/lib/rancher/k3s/agent` is 0 bytes with timestamps from the **previous** boot, plus `/etc/rancher/node/password` at 0 bytes. k3s's `LoadOrGenerateKeyFile` refuses to regenerate a file that exists, so it retries forever and `k3s.service` never reaches active — which is why the "WP11 — installed-disk first-boot k3s verify" step has **never** produced a green verdict.

## The gap that matters

Phase 2 was **always** crashed before phase 3 booted. So WP11 has only ever measured the **post-crash** path. The path a real user gets — plug the USB in, install, the machine reboots cleanly, k3s comes up — has never been measured by this lane at all. That is the gap this closes.

## What changed

**New module `src/Core.TypeScript/ci/qemu-guest-teardown.ts`.**

- A QMP client over a per-phase unix socket: greeting → `qmp_capabilities` → `system_powerdown` (the ACPI power button; a NixOS guest runs a real `systemd-shutdown`, which syncs).
- A fallback ladder that **reports which rung stopped the process** — `already-exited` / `graceful` / `sigterm` / `sigkill` — with elapsed time, on stdout, so a later run can be *read* rather than guessed at.
- `graceful` is reported **only** when QMP accepted the command **and** the process was then observed to exit. An accepted command that produced no exit is *not* graceful, and there is a test that says so. A teardown that always reported "graceful" without checking would be the vacuity class this repo refuses.
- An unreachable QMP socket is **named out loud** (`WARNING … page cache WILL be discarded`) and falls back. Never silent.
- Budget: 180s for the guest shutdown (the brief's floor was 120s; a NixOS shutdown with k3s running has to stop every containerd shim and unmount kubelet's volumes first), then 15s after SIGTERM, then SIGKILL.

**Wiring.** Each phase gets its own `-qmp unix:<tmp>/qmp-phase<N>.sock,server=on,wait=off`. The argv is byte-identical when no socket path is passed, so every existing arg-builder test is untouched.

**Deliberate mid-work kills stay kills.** When `wait()` already returned a failure the guest has *not* finished what it was doing and nothing downstream opens that disk (phase 1's failure exits the run; phase 2's failure skips phase 3), so the graceful rung is skipped — spending up to 180s syncing a filesystem nobody reads would buy nothing. The reason is logged either way, so a reader never has to infer which of the two cases a run was in.

## The falsifier

Making the teardown graceful is a *claim about the guest filesystem*. A green WP11 verdict would not prove it: k3s could come up because WP25's self-heal **deleted** the truncated credentials and k3s regenerated them — which is exactly what the lane measured before, and exactly what it must stop measuring.

So the assertion is on the self-heal's own output. `assertNothingToHealAfterGracefulShutdown(phase3Serial, phase2.teardown?.path)`:

| status | when | verdict |
|---|---|---|
| `inert` | no `[zeta-k3s-agent-tls-self-heal]` line at all — WP25 is not in this ISO | reported loudly, **not** a pass and **not** a failure |
| `precondition-absent` | phase 2 did **not** take the `graceful` rung | nothing asserted — a crashed disk is expected there |
| `clean` | graceful, and both self-heal targets reported clear | **pass** |
| `healed` | graceful, yet files were still removed | **red** — the graceful path did not deliver what it promises |
| `indeterminate` | the unit ran, removed nothing, and said nothing conclusive | **red** — silence is not a pass |

**It does not block on #17608 and edits none of its files.** The marker literals are duplicated from `full-ai-cluster/nixos/modules/k3s-agent-tls-self-heal.sh` deliberately; `status: "inert"` is what makes that duplication self-announcing rather than quietly vacuous, and a coherence test against the producer activates by itself once that file lands.

## The self-heal is NOT weakened

A power cut during first boot on real hardware produces exactly this state, so the self-heal stays. What changes is that **CI stops manufacturing the crash on every run** and starts measuring the ordinary path.
