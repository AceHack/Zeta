## Description

Follow-up to #17638, same work item `081M39CJP96087G0R001T4J2R3`. It records the measurement that **falsifies the last standing hypothesis**, and closes the other half of the discipline #17638 opened.

## The hypothesis, and it was a good one

The LBA-276 fallback constant (141 312) sits **4 096 bytes inside** the real ESP (137 216). A bake that fell back would write over the FAT tables while leaving the boot sector — and therefore the `EFIBOOT` label udev reads — intact. Label readable, filesystem unmountable, permanently, from first boot. That is both halves of the symptom, and it explained the intermittency too, since the two runs booted different ISOs.

## Measured: both ISOs, pulled from their run artifacts

**Three independent legs, all against the hypothesis:**

1. **The geometry does not vary between builds.** Both ISOs put the ESP at LBA 268. The ISO is not the hidden variable.
2. **The fallback was never reached in either run.** The old algorithm resolves through the MBR branch on both heads.
3. **And if it had been reached it would have been loud, not silent.** There is no FAT boot sector at 141 312, and mtools refuses one. Measured on the real failing ISO:

```
mcopy -o -i fb.img@@141312 payload ::/zeta-authorized-keys.pub
  exit=1   init :: non DOS media / Cannot initialize '::'
mdir  -i fb.img@@141312 ::
  exit=1   (same)
real ESP at 137216 afterwards:                       MOUNTS OK
bytes differing inside the 3 MiB ESP vs clean convert: 0
```

A fallback bake fails at `mcopy`, so `runFileBackedZflashCli` returns command-failed, `prepareBootImage` errors and the harness exits 2 in about two seconds. It never produces a booting guest, and it writes nothing.

**Consequence for what #17638 shipped, stated plainly:** `prepareBootImage`'s `fallback-unconfirmed` refusal is a **guard, not the fix.** It turns a cryptic `init :: non DOS media` into a named refusal one step earlier — worth having — but it is not what lost these injections, and the work item does not close on it.

## What this PR adds: the good case, said out loud

#17638 fixed a function whose two branches returned the same value. Making only its *failure* loud would have left the same gap one layer out — so:

- `PrepareBootImageResult` now carries `espOffsetBytes` + `espOffsetSource`, and `qemu-full-install-test.ts` prints `ESP offset 137216 bytes (LBA 268) source=mbr — an MBR 0xEF entry and a FAT boot sector at that offset agree` **on every bake**. The two runs compared above printed *identical* bake lines, so answering "did this bake resolve the offset or guess it?" cost an ISO download and a hand-written MBR parse. It now costs one line of the job log.
- The post-bake read-back prints its own one-line result for the same reason: a bake that verified everything and one that verified nothing were indistinguishable in a log. **Counts, not names** — `/zeta-join-token` and friends are plaintext secrets. It goes to **stderr** deliberately: `main()` writes `ZFLASH_QEMU_RETENTION_BOOT_IMAGE=` to stdout and callers parse that, so a new stdout line would be a wire-format change wearing a log's clothes.
- Falsifiers for both, including one asserting the success line is **absent** when verification is off — otherwise the log could claim a check that never ran, which is the vacuity class one layer up.
- `describeEspOffset` is tested on the case that matters: the two fallback outcomes carry the *same number* and must not render identically. That collision is the defect this whole work item started from.

## Still open

Why the kernel refused `mount -t vfat` on a partition whose FAT label blkid had just read, for a whole install, on one run and not the next, from an image whose ESP geometry is identical and whose bake path is deterministic. The mount-error capture from #17638 is what answers that, on the next occurrence rather than by another sampling run.
