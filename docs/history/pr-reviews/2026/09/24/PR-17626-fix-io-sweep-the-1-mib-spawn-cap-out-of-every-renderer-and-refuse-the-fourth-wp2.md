## Description

#17622 fixed **one** helm runner. There were **four**, and a lint now refuses the fifth.

## The sites

All `node:child_process.spawnSync` with no `maxBuffer`, all therefore capped at Node's 1 MiB default, all killing the child with `ENOBUFS` and returning **truncated stdout**:

| file | status |
|---|---|
| `cluster/rendered-storage-claims.ts` | fixed in #17622 |
| `cluster/inert-valuesobject-keys.ts` | a **byte-identical clone** of it |
| `hygiene/audit-local-helm-charts.ts` | `run()`, used for helm **and** kubeconform |
| `installer/zeta-creds-to-k8s.ts` | **found by the new lint** — nobody had listed it |

**The clone is why this recurred, so it is deleted rather than fixed.** `inert-valuesobject-keys.ts` carried a copy of `defaultRunHelm` identical to the byte; #17622 fixed the original and the copy kept the defect. That file now imports the one runner, which is exported for the purpose.

## Measured, not assumed — and it corrects my own earlier report

I reported "no new inert key surfaced from the six" as a zero delta. That was measured through a **still-broken runner**. Re-measured now, and the delta *is* zero — but for a better reason than either of us had: **that file's only helm invocation is `helm pull --untar`**, which writes to disk and emits a status line. It never runs `helm template`, so the missing cap there was latent and could not have truncated anything. The output confirms it: `49 discovered, 49 checked against a chart schema, 0 NOT COVERED`.

## The validator is the one that mattered

`audit-local-helm-charts.ts` pipes `helm template` into `kubeconform`. A truncated render means the validator checks a **shorter document set and passes** — a schema validator reporting success over material it never saw, in the check whose entire job is schema validation.

Also latent today, and only because the two in-tree charts have no `templates/` directory at all and render to one byte. (That file's own summary reads `Schema-validated manifests: 0` — its own question, for someone else.)

## Where the real lesson is

`Bun.spawnSync` is deliberately **not** swept — it carries no such ceiling, and `image-resolvability.ts` uses it on purpose.

And that file is where this gets uncomfortable. Its comment **already contained a correct, complete diagnosis** of this defect — the same six charts, the same ENOBUFS, the same empty stderr — and fixed it *privately*, by handing that one caller a different runner, explicitly leaving the shared renderer alone *"which several other validators use unmodified"*.

Three of those validators kept the defect. **A local workaround for a shared defect leaves the shared defect.** That comment now says so, and says not to add `maxBuffer` to a Bun call that has no such option.

## The falsifier

A new `uncapped-renderer-spawn` rule in `lint-hand-rolled-io.ts`, which **found the fourth site within a minute of existing**.

It matches a Node `spawnSync` whose call text names a renderer or validator (`helm`/`kubeconform`/`kubectl`/`kustomize`, including the `helmBin` and `k3sBin` *bindings* every real site actually uses — a literal-only rule would have matched none of the four) and which declares no `maxBuffer`.

Call text is read by **counting parens**, not by a fixed window: too small a window misses a `maxBuffer` on a later line (a false refusal), too large reads the *next* call's options as this one's (a false clearance, which is worse). Both directions have a test. `Bun.spawnSync` is excluded by a negative lookbehind, with a test pinning that.

**One bound, imported:** every site now takes `DEFAULT_MAX_BYTES` from `io/safe-io.ts` rather than spelling out 64 MiB. Raised, never removed — an unbounded child can hang the process.
