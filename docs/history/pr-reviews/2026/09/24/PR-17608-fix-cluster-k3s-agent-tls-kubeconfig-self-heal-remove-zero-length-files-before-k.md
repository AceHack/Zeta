## Root cause, measured -- a THREE-LAYER CHAIN, all found on real CI runs of this fix

On the real USB-installed disk, k3s never finishes starting, so Kubernetes never comes up and no app ever starts.

**The before-control, on current `main` today (not an old branch).** Run **35960376641** (`schedule`, branch `main`, commit `e7a39dca`, 2026-09-24T05:32Z): the ISO lane's *only* failing step across the whole run is "WP11 — installed-disk first-boot k3s verify" — `build-iso-aarch64 + qemu-boot` is green and nothing else failed. The six verdicts from that run's `qemu-k3s-first-boot-verify-serial-log`:

```
verdict 1/6 bootedMultiUser=true   elapsed=0s
verdict 2/6 k3sServiceActive=false elapsed=4202s
verdict 3/6 nodeReady=false        elapsed=4203s
verdict 4/6 helmJobs               elapsed=4203s
verdict 5/6 rootLanded=false crdSeen=false verdict=inconclusive-crd-absent elapsed=4203s
verdict 6/6 noBadPods=true         elapsed=4203s
```

`grep -c 'error loading key from'` on that same log returns **119** — the dynamiclistener `<nil>` wedge this PR fixes, reproducing on `main` today, 119 times in one 70-minute boot window. (One honest caveat on verdict 6/6: `noBadPods=true` here is true because there are **no pods at all** — k3s never started. A verdict that reads green while carrying no information is the vacuity class; not this PR's bug to fix, and not a reason to widen scope, but worth saying so a future reader scanning six verdicts doesn't count it as five-of-six passing.)

- `k3s.service` is `activating` forever. k3s logs, every ~8s for 70+ minutes: `Waiting to retrieve agent configuration; server is not ready: /var/lib/rancher/k3s/agent/serving-kubelet.crt: failed to create certificate request ... error loading key from /var/lib/rancher/k3s/agent/serving-kubelet.key: <nil>`.
- `ls -l /var/lib/rancher/k3s/agent` showed **every** agent file at 0 bytes.

**Why this reproduces on every CI run, exactly:** `qemu-full-install-test.ts`'s `runQemuUntil()` tears the guest down with `qemu.kill("SIGTERM")` then `SIGKILL` after 2s — that kills the *emulator*, not the guest; the guest OS never shuts down, its page cache is discarded, and ext4 delayed allocation leaves inodes with no data blocks. CI manufactures the exact crash this module heals, on every phase transition — which is also exactly what a real power cut during first boot on metal produces. (WP27, spawned separately, has landed the phase-2 teardown as a real ACPI `system_powerdown` over QMP so CI can also measure the clean path — merged to `main` as #17609, not touched by this PR.)

**Bug 1, cited.** k3s's agent certs load through rancher/dynamiclistener's `cert.LoadOrGenerateKeyFile` (`cert/io.go`): a file that **exists** with 0 bytes reads with `err == nil`, so `os.IsNotExist(err)` is `false`, and the function takes the "real read error" branch instead of regenerating — formatting the nil `err` with `%v` as the literal string `<nil>`, the exact text measured. Deleting the zero-length file turns the next read into a genuine `IsNotExist`, which the same function already handles by regenerating.

**Bug 2, measured on this branch's own first CI run of the bug-1-only fix (run 35943840554, `-f only_wp11=true`):** the `<nil>` text was gone, and k3s failed differently: `Sending HTTP/1.1 400 response ...: node password not set`. Cited (k3s community precedent — [discussion #8121](https://github.com/k3s-io/k3s/discussions/8121), [codybunch.com "Kubernetes Fix: Node Password Rejected"](https://blog.codybunch.com/2020/10/13/Kubernetes-Fix-Node-Password-Rejected/)): the agent presents a per-node secret from `/etc/rancher/node/password` on every bootstrap request; the server keeps a table of already-established passwords at `/var/lib/rancher/k3s/server/cred/node-passwd`. **Fixed and proven** on run 35954415942: both bugs cleared, k3s progressed well past both retry loops (a much larger, image-pull-heavy serial log, no `<nil>` and no "node password not set" anywhere in it).

**Bug 3, a real regression caught before merge, on that same run.** With target 1 swept as "every zero-length file under `/var/lib/rancher/k3s/agent`, minus one excluded containerd subtree," the self-heal's own log showed `removed 3243 zero-length file(s)` in one boot. The overwhelming majority were under `.../agent/containerd/io.containerd.<component>.<version>.<name>/...` — containerd's own plugin-namespaced working data (overlayfs snapshot content for extracted images, the content-addressed blob store, the metadata bolt db). Every one of those was genuinely zero bytes and genuinely **not** a truncated k3s credential: OCI runtimes create empty `snapshots/*/fs/etc/{hosts,resolv.conf,hostname}` files *on purpose* as bind-mount targets, and container images legitimately ship zero-length marker/lock files (`py.typed`, empty `__init__.py`, `.rpm.lock`, `dpkg/lock`, …). Deleting them corrupts already-extracted image content, which k3s does not regenerate the way it regenerates its own bootstrap credentials — strictly worse than the hang this module exists to fix.

## Fix — three targets, an ALLOWLIST for target 1, one `ExecStartPre`

`full-ai-cluster/nixos/modules/k3s-agent-tls-self-heal.nix` + `.sh`: an `ExecStartPre` on `systemd.services.k3s` (same shape as WP20's `k3s-wait-for-address.nix`), imported by both `k3s-server.nix` and `k3s-agent.nix`. Before k3s starts, it removes only:

1. **An explicit allowlist of two places, not a swept tree:**
   - `$AGENT_DIR` itself, **one level deep only** (`-maxdepth 1`) — the certs/keys/kubeconfigs this target exists for.
   - `$AGENT_DIR/etc`, **recursively** — containerd's own process *config* (`config.toml`, `crictl.yaml`, `certs.d/*/hosts.toml`), a different directory from `$AGENT_DIR/containerd` (the runtime's working data — **never named by either clause, and therefore never a candidate**, by construction rather than by exclusion).
2. **`/etc/rancher/node/password`** (named) — the agent's own per-node registration secret.
3. **`/var/lib/rancher/k3s/server/cred/node-passwd`** (named, server role only) — the server's per-node password lookup table.

Every path removed is logged; the script never fails the unit. **Why an allowlist and not a blacklist:** a single excluded subtree only defends against the one unsafe location a given run happens to reach — an allowlist defends by construction, because the measured-safe set is exactly the two clauses above, and the healthy first self-heal invocation on run 35954415942 already proved they're sufficient. The only thing the allowlist gives up versus the old sweep is `agent/containerd/containerd.log`, whose zero-length state is normal and was never load-bearing.

**Scope decision, stated rather than assumed.** `server/tls` (CA material), `server/cred/encryption-config.json` + `ipsec.psk` (an encryption key and a shared secret, not a lookup table), and now **the whole `$AGENT_DIR/containerd` directory** (containerd's own runtime data — legitimately zero-length image content and mount-point placeholders k3s does not own and cannot regenerate) are **deliberately left alone**. **Residual risk, named:** a power cut truncating any of those is *not* self-healed here and still needs manual recovery. The datastore (`server/db`) is outside this module's scope entirely.

**Can a stale server-side entry block regeneration on a node that keeps its name?** Yes. Targets 2 and 3 are the two ends of one handshake, and the measured failure truncated *both* together — clearing both and letting each regenerate independently works because an empty table has no stale entry to contradict a fresh password. If only target 2 were truncated while target 3 survived with a real entry for this node name, k3s would report a *different* string ("node password rejected", [k3s-io/k3s#746](https://github.com/k3s-io/k3s/issues/746)) and this module does not resolve it — curing that means deleting one node's entry inside a store whose on-disk shape is not fixed across k3s datastore backends, which this module does not attempt. Named explicitly in the module header, not silently assumed away.
