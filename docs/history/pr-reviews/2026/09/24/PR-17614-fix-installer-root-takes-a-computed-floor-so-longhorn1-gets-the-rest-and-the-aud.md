## The headline, and the split that makes it one

`#17611` proved the defect and stopped it reaching a disk. This fixes it — and the number that matters is not the one either of us led with first.

The `measured` rung declares **943 GiB** but provisions **443 GiB at bring-up** — the subset a fresh sync actually applies. The geometry fix gives a single 1 TiB disk **607 GiB** schedulable.

> **607 > 443: the geometry change alone makes "plug the USB in and the applications come up" true on the default single-disk path.**

607 < 943, so the steady state the cluster grows into still does not fit. That stays recorded as debt rather than papered over. **Necessary, not sufficient**, and the difference between "the installer is broken" and "the roster outgrows one disk" is the difference between what blocks a user tonight and what does not.

## Commit 1 — the auditor printed a FALSE binding mode on every run

This one is first because it is the one that had already done damage.

`single-node-readiness.ts` printed this on every run, and two other committed surfaces asserted it:

> Longhorn's StorageClass is volumeBindingMode Immediate, so any PVC that gets applied provisions with zero pods

**It is false of every class this roster claims on, and always was.** `local-storage.nix` binds all three capability classes `volumeBindingMode: WaitForFirstConsumer` — `zeta-block-local` (66), `zeta-block-replicated` (77), `zeta-shared` (92). `git log -L 71,80:...local-storage.nix` shows `zeta-block-replicated` was **created** that way by #17576 ("charts name a storage capability, never a provider").

**Where it came from**, because it was not invented: it is true of the Longhorn *chart's* own `longhorn` StorageClass. But `applications/longhorn/Application.yaml` sets `persistence.defaultClass: false`, and every claim in the tree names a capability class instead. The sentence described a class nothing claims on, written before the rename and carried across it unchecked.

**Why that is worse than a stale comment.** It was *printed*, by the auditor whose whole job is refusing unchecked assertions, to every reader on every run — and it measurably misled one. A design argument for re-binding the `ollama`/`vllm` caches rested on *"Longhorn prices ceilings; local-path prices use"*, which is false under `WaitForFirstConsumer`: an unconsumed PVC reserves nothing either way. That proposal is now on hold because its strongest premise was this line.

**The fix is not a better sentence.** A sentence can rot again; a value read from the authoritative file cannot. `printedBringUpNote` derives the mode from `metalStorageBindings()` — which already parses `local-storage.nix` for `storage-capabilities.ts`, so one import and no new parser — and names the file it read so a reader can check rather than trust. An unreadable bindings file prints `could not be read`, never a default: naming a mode nobody read is the exact defect being replaced.

**The conclusion survives the correction**, which is the test of whether it was ever real. Bring-up is still a REPORT and never a discount — a manual-sync app is one `argocd app sync` *and one schedulable pod* away from being counted. A test asserts that, so a later "simplification" cannot quietly turn the report into a discount.

Also corrected, as prose that now defers to the parser: the DECLARED-vs-SCHEDULED header in `storage-profiles.ts`, and the `ollama` `bringUpNote` in `storage-profiles.json`.

## Commit 2 — root takes a computed floor, `longhorn1` takes the rest

`LONGHORN1_TAIL` defaulted to `1G` and root filled the disk. Now it defaults to `auto`: root gets a computed floor and `longhorn1` gets the **rest**. An explicit size still overrides with its existing `>=1G` / `<=1T` bounds.

```
931 GiB disk − 1 GiB ESP − 120 GiB root floor = 810 GiB tail
810 × 75% Longhorn will place                 = 607 GiB schedulable
```

**The floor is derived, and every term is GiB:**

| term | GiB | source |
|---|---|---|
| unpacked container images, **whole** roster | 73 | `image-footprint.measured.json` `all` cohort: 77.69 GB × 10⁹ / 1024³ = 72.35, rounded up |
| OS, swap, `/nix/store` generations, logs | 30 | `OS_ROOT_ALLOWANCE_GIB` — a budget choice, reused rather than re-guessed |
| × 1.15 safety factor | | stated, so the rounding is a decision |
| **= 118.45 → 120** | | |

The source measurement is published in **GB** (decimal) and every constant here is **GiB** (binary), with the conversion shown at each one. Mixing them in a capacity floor is the Mars Climate Orbiter class this repo cites by name.

**Which way the error leans**, stated at the constant: the ×2.67 unpack ratio is a *measured over-estimate* for the two images that dominate (a CI pull found ×1.77 and ×2.35). On the **root** side that is the safe direction — root gets more than it needs and Longhorn gets less than it could, costing capacity and causing no failure. **The same ratio on the demand side of a capacity check would be the acquitting direction, and is not used there.**

**The local-path term is reported, not reserved.** 220 GiB of `zeta-block-local` + cluster-default ceilings also land on root (gitlab 66, dapr 48, forgejo 20, loki 20, opensearch 20, seaweedfs 20, openbao 15, mimir 6, spire 5 — pinned to the render snapshot by test). It is deliberately *not* in the floor: local-path's provisioner is `mkdir -m 0777 -p "$VOL_DIR"`, a directory with no quota, so a PVC there costs the bytes **written**. Reserving the ceiling would starve the pool for bytes nobody has written. Both the installer and the auditor print it, so no later change can move the cliff from one partition to the other unseen.

**A disk too small refuses, it does not clamp.** `autoLonghornTailGib` returns 0 when the disk cannot hold ESP + floor + a 1 GiB minimum, and 0 means bail with the numbers printed. Clamping to 1 would be the original defect wearing a computation.

**One correction to the comparator, caught by running it.** `installerGeometryFor` assumed the **smallest** device was the boot disk — right under a fixed tail, and inverted under `auto`, where a bigger boot disk yields a bigger tail. On `node-ad1efd` the smallest device is 115.5 GiB and cannot hold the 120 GiB floor at all, so the "generous" reading was picking a layout the installer would refuse. It now enumerates every boot-disk choice, drops the ones the installer would refuse, and takes the maximum — generous under both tail modes, no separate case. The registered nodes move 699 → 694 GiB schedulable and the acknowledgement keys move with them, which is the keys doing their job.

## Filed, not built: `081M397QHX8087G0R003DQSY0B`

Measured while investigating commit 1, and it changes every capacity conversation from here:

**`ollama` and `vllm` declare 400 GiB — 47% of the pool — and cannot schedule on any registered node.** Both carry `nodeSelector: zeta.io/gpu: nvidia`; every checked-in `ClusterNode` records an **Intel Arc Pro 140T**. Both are manual-sync only. Under `WaitForFirstConsumer` those PVCs provision nothing and reserve nothing.

The honest fix is not to move or delete them — it is to report **schedulable** demand beside **declared**, excluding claims whose workload carries a selector no registration satisfies, derived from the manifests and the registrations rather than a typed list. Declared keeps the exit code: a GPU arriving tomorrow makes the demand real, so schedulable must not become a discount. That needs its own selector/label parsing on both sides and its own falsifiers, so it is filed with the measurements in it rather than bolted on here.

The proposed `ollama`/`vllm` re-binding to `zeta-block-local` is **held** pending that measurement — partly because commit 1 falsified its strongest premise, and partly because moving 400 GiB of advisory claims onto a root filesystem with a 120 GiB floor is exactly the cliff-moving this PR prints a line to prevent. If the schedulable total turns out to be 543 GiB, the question may not need answering at all.
