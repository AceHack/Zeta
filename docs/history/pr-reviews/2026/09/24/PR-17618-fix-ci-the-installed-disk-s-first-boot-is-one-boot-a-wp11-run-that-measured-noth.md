## Description

## 0. First, the measurement #17609 bought

Run **35968222668** (`-f only_wp11=true`), the first run with a graceful teardown:

| | control 35960376641 (`main`) | 35968222668 (graceful) |
|---|---|---|

The zero-length TLS truncation was **CI-manufactured** and is gone. `reboot: Power down` is the evidence that matters: QMP *accepting* `system_powerdown` would not have proved it landed in the guest.

Underneath it was a different failure, and the rest of this PR is about it.

## 1. The installed disk's FIRST boot is ONE boot

Phase 2 boots the installed disk with **no network**, waits for a login banner, and stops ~26 s in. `k3s.service` starts anyway, creates `/var/lib/rancher/k3s/server/db`, and gets about 20 seconds — not enough to write bootstrap data. Now that the guest shuts down **cleanly**, that half-initialised datastore is **durably** on disk, and k3s will not initialise into a non-empty one:

```
level=fatal msg="Error: preparing server: failed to bootstrap cluster data:
failed to reconcile with local datastore: no bootstrap data found in datastore
- check server token value and verify datastore integrity"
```

58 restarts, 76 fatals, `k3sServiceActive=false` at 4202s, no recovery path on that disk.

**The artefact is the split itself.** On metal, phase 2 and phase 3 are the *same boot*: a machine installs, reboots **once**, and k3s comes up. The harness split that boot in two purely to check a login banner, and the artificial second boot is what manufactures the stillborn datastore.

So the WP11 lane no longer reboots. `waitForInstalledLoginThenK3sVerdict` makes the login assertion from the same serial, earlier, and the boot continues into the verdict. `phase3` **is** `phase2` there, by name, so every consumer reads the boot that actually produced the verdict. The lane now measures one first boot — what it always claimed to measure and never has.

**Deliberately not "wipe the datastore before phase 3."** That would hide a defect that also exists on metal: a machine powered off in the first ~20 seconds of its first boot — impatient operator, power cut, tripped breaker — gets a permanently wedged cluster that no reboot recovers. Product-side fix, routed separately; referenced here, not built here.

One consequence stated out loud because getting it wrong would be silent: the self-heal precondition now reads **phase 1's** teardown path, not phase 2's. The boot that *wrote* the disk this one reads is the install, because phase 2 *is* this boot.

## 2. A run that measured NOTHING must not report as a timeout

Measured on run 35965945581. Two minutes into phase 1 the guest said:

```
[k3s-first-boot-verify] no zeta-qemu-k3s-first-boot-verify on boot USB ESP
```

so `/mnt/etc/zeta/qemu-k3s-first-boot-verify` was never written, the verdict unit was never enabled, and `wp11-k3s-verify` appears **zero** times in a 445 KB serial log. The harness then sat for **100 minutes** printing "waiting for k3s first-boot verdict" and failed on *timeout* — which reads as *k3s was slow* and was in fact *k3s was never measured*.

- `wp11PreconditionFailure` is checked **inside the phase-1 poll**, so the run aborts at the guest's own sentence rather than after ~100 minutes. A 50× improvement in how fast this lane tells the truth.
- `assertWp11VerdictUnitEnabled` additionally requires the **positive** `wrote /mnt/etc/zeta/qemu-k3s-first-boot-verify` line. A serial carrying **neither** line — truncated, or a reworded producer — is reported, not passed. Absence of bad news is not good news.
- **Second observable, same condition:** it also convicts on `[iter-5.2]   no zeta-hostname.txt on USB ESP` while the marker survived. This harness always bakes a hostname for a USB-image lane, so a guest that generated a random `node-<6hex>` installed a node whose identity nobody chose — and the phase-2 login contract downstream would assert against that random name and **pass**.
- The message names the right producer: *"the whole ESP probe came back empty"* (look at the bake and the guest's ESP mount) versus *"only this marker is missing"* (look at the marker bake and `zeta-install.sh`'s WP11 block).

**Filed, not fixed — `081M39CJP96087G0R001T4J2R3`.** A full `workflow_dispatch` silently loses *every* boot-USB ESP injection: operator pubkey, injected hostname, USB UUID capture, and the WP11 marker. A `schedule` keeps all of them. The work item carries both run ids, the per-symptom table, and what has been ruled out — not a shared image (`mkdtempSync` per invocation, so no two steps can touch the same one), and not visible in the bake's ~2 s of byte-identical output.

## 3. The Longhorn pre-wipe refusal was about to bail every install lane

#17611/#17614 added a pre-wipe refusal when the provisioned Longhorn pool cannot hold the committed roster. `zeta_auto_longhorn1_tail_gib` computes `disk − 1 GiB ESP − 120 GiB root floor`, so on this harness's single virtual disk of 40 GiB (64 for WP11) the tail is negative, clamps to 0, and refuses. **Correctly** — on real hardware that disk genuinely cannot hold the 943 GiB roster.

`ZETA_ALLOW_LONGHORN_UNDERSIZED='1'` is now staged on the **flashed image's** ESP `/zeta-firstboot.conf`, which `zeta-first-boot.sh` already sources. Threaded `lib.ts` → `file-backed.ts` → `prepare-boot-image.ts` → the harness. Pairs with #17616, which exports the name so it reaches the `zeta-install.sh` child.

- **Appends** to a role-written conf rather than pushing a second write at the same ESP destination — `zeta_source_esp_firstboot_conf` takes the first conf it finds, so two would be a coin toss. Appended **last**, so a role key further down the same sourced file cannot clobber it.
- **Not** baked into the ISO's own `/etc/zeta-firstboot.conf`. That file ships on every USB cut from the ISO, so a value there would clear the guard for real operator installs — the guard deleting itself.
- Unconditional in the USB-image branch, **checked rather than assumed**: all five `qemu-full-install-test.ts` invocations in `build-ai-cluster-iso.yml` set a flag that reaches that branch, so no lane needs the override and misses it, and none gets it without needing it. The plain-ISO cdrom path (no ESP to write to) is never exercised by that workflow.
