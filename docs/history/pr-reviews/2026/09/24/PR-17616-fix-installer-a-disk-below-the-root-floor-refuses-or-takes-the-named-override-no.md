## Description

**Urgent.** #17614's root floor (merged) breaks **every QEMU install-to-disk lane**, including the WP11 installed-disk first-boot verify. Nothing has gone red yet only because `scenario 2 — boot + install substrate` is skipped on the PR path, so the next scheduled WP11 run on `main` is the first one that would hit it.

## The arithmetic on the CI substrate

`qemu-full-install-test.ts` creates **one** virtual disk: `DISK_SIZE_GB = 40`, or `K3S_VERIFY_DISK_SIZE_GB = 64` for the WP11 phase. Both are **below** the 120 GiB root floor:

```
40 − 1 ESP − 120 floor  →  zeta_auto_longhorn1_tail_gib returns 0
```

and 0 means REFUSE. The resolver bailed **unconditionally, before the pool check** — so `ZETA_ALLOW_LONGHORN_UNDERSIZED=1` would not have helped either, because it gates the pool refusal further down. Two gates, one of which nothing could clear.

## One override now covers both

That is the design point, not a convenience. The two refusals are the same claim measured at two places — *"this disk cannot hold the committed roster"* — so an operator who has said `ZETA_ALLOW_LONGHORN_UNDERSIZED=1` has answered both. A second variable would make them name one fact twice, and the second one would be the one nobody sets.

Under the override the fallback is `ZETA_LONGHORN_MIN_TAIL_GIB` (1 GiB) with root taking the rest — the pre-WP28 layout. As a **default** that is exactly the defect this work package closes; as an **explicitly named fallback** on a 40 GiB virtual disk it is the only layout that installs at all. The arithmetic still prints, and the message still says *"debt you named, not a cleared check"*.

## No test-mode branch, and a falsifier for it

The installer never sniffs `$CI`, `GITHUB_ACTIONS`, `/sys/class/dmi`, `systemd-detect-virt` or a hypervisor flag. A check that disables itself when it notices it is being tested is the vacuity class built into the guard that exists to refuse it.

The test **strips comments before scanning**, because the bail text legitimately explains why the QEMU lanes set the override — a scan that failed on the word rather than on the *branch* would be measuring prose. It also asserts the only condition the fallback branches on is the named override.

## The override now reaches the installer

`zeta-first-boot.sh` exports it, for the same reason it already exports `ZETA_ISO_COMMIT` and `ZETA_ALLOW_REPO_DRIFT`: the ESP `/zeta-firstboot.conf` is **sourced**, so a value set there reaches that script's shell and *not* the child `zeta-install` process. Without the export the override could be set correctly and still do nothing — a knob that turns and is not connected.

It is a pass-through and sets no policy: unset stays unset, and a test asserts the line is `${VAR:-}` and never `=1`. Deliberately **not** baked into the ISO's own `/etc/zeta-firstboot.conf`, which ships on every USB — a value there would clear the guard for every operator install too, which is the guard deleting itself.

## Tested at 40 and 64 explicitly

Read out of the harness rather than restated, so a lane that resizes its disk re-checks this arithmetic instead of leaving it stale. Plus the boundary at ESP + floor + 1 and one GiB either side.

The property asserted is that the tail is **0 and never negative**: a negative would reach `sgdisk -n "2:0:-<n>G"` as an end code computed from a negative remainder, which is how a partitioner gets asked to do something nobody meant.

## ⚠️ Still outstanding — one line, and it is not in a file I own

**Nothing sets the override in CI.** `git grep ZETA_ALLOW_LONGHORN_UNDERSIZED` finds it only inside this check and its oracle. **This PR makes the lane fixable; it does not by itself fix it.**

The lane needs `ZETA_ALLOW_LONGHORN_UNDERSIZED=1` written where the guest can read it. The ESP `/zeta-firstboot.conf` is the declared channel and `zeta-first-boot.sh` now carries it the rest of the way, so the remaining change is staging that line — which happens in `src/Core.TypeScript/ci/qemu-full-install-test.ts`, **WP27's surface**. Reported rather than edited, with a comment saying the QEMU disk is 40/64 GiB by design because the lane tests install *mechanics*, not capacity.
