## Description

The brief: GPU charts must support AMD as well as NVIDIA. nodeSelector cannot
express OR, and `nvidia.com/gpu` / `amd.com/gpu` are different extended
resources, so one committed tree cannot ask for "either". Make the vendor a
per-cluster dimension of the rung-overrides mechanism rather than forking
Applications; keep metal's NVIDIA default.

THE DIMENSION (rung-overrides.yaml `dimensions:`)
  gpuVendor: { committed: nvidia, values: [nvidia, amd] }
An override may carry `when: {gpuVendor: amd}` and fires only for a tree built
with that selection (`applyServeTreeRung(rung, staged, {gpuVendor: "amd"})`).
Refused at load: an undeclared dimension, an unknown value, a single-value
dimension, and a `when` on the COMMITTED value (the tree already is that).
`validateSelection` refuses a typo'd selection, so `amdd` cannot build the
NVIDIA tree under the AMD label. With no selection every existing caller builds
byte-for-byte the tree it built before (asserted: 0 vendor edits on metal).

THE AMD FORMS (rung metal, when gpuVendor amd)
- ollama: `ollama.gpu.type: amd` -- the pinned otwld chart then pulls
  `ollama/ollama:0.33.2-rocm` (the pinned form of `ollama/ollama:rocm`) and adds
  `amd.com/gpu` to limits. MEASURED with `helm template` against the staged AMD
  valuesObject: rocm image, amd.com/gpu in requests and limits, selector
  zeta.io/gpu=amd, ZERO occurrences of nvidia. The requests/limits maps are
  replaced because the chart merges ours over its own and ours named
  nvidia.com/gpu.
- vllm: image `rocm/vllm:latest` (AMD's ROCm build; the committed CUDA image is
  vllm/vllm-openai:latest, equally unpinned), selector + both resource maps.
The node side already speaks both: nixos gpu-device-plugin.nix runs the ROCm
plugin on `zeta.io/gpu: amd` nodes. HONEST LIMIT: metal clusters sync the
committed tree, so an AMD metal cluster needs the served-tree path
(first-boot-replica already serves trees); that wiring is the follow-up.

EXCLUSION REASONS, RE-MEASURED -- and the finding that governs every lift. At
`dev` the included lane fits CPU with ~785m spare but MEMORY with 116Mi
(9100 / 9216Mi). CPU is compressible and was floored; memory is not. So gitlab
(5605Mi), temporal (1184Mi), platform (160Mi) and ollama's dev form (512Mi)
cannot join THIS lane whatever else is fixed -- they need the lane-partition
work. A new reason-truth citation kind, `lane-memory`, makes that claim checked
rather than prose (total AND verdict, polarity-paired like `lane-cpu`); five
reasons cite it. vllm's reason now names disk (~23 GiB CUDA image beside ~32 GiB
of lane images) as the constraint that binds before the GPU. The ollama reason
names its stale ungoverned budget row (0m/0Mi) as a defect.

FALSIFIERS: rung-overrides.test.ts +6 (dimension refusals, fire-only-when-
selected, selection validation, LIVE AMD tree has no NVIDIA key in ollama or
vllm while the committed tree keeps it, LIVE default build fires no vendor
override); reason-truth.test.ts +1 (lane-memory).
