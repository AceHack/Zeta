## Description

## Summary

`first-boot-replica.ts` stage 6 blamed the wrong things. `computeAppVerdict`
attributed pods with `pod.namespace === app.name`, which is **false** for every
Application whose `spec.destination.namespace` diverges from its directory
name — `cilium` (kube-system), `kube-prometheus-stack` (monitoring),
`openziti-controller` (openziti), `seaweedfs` (object-store), and others — so
a real problem in a shared namespace was invisible and the app FAILed with
the vacuous `"no classified pod issue"` message. Several other verdicts were
also flat-out wrong: `cdi`/`kubevirt` are MANUAL-SYNC by design and should
never FAIL on `Missing`; `hindsight`/`ghcr-pull` need operator-supplied
EXTERNAL secrets no first-boot lane can mint; `openbao` boots sealed by
design and stays `Progressing` forever on a fresh cluster.

### What changed

1. **Attribution** (`attributePodToApp`, `computeNamespaceOwnership`,
   `podBelongsToResource`) — three mechanisms, tried in order and each
   documented at the call site:
   - namespace-exclusive fast path (one Application claims the namespace via
     `spec.destination.namespace` or `status.resources[]`)
   - owner-reference match against the app's declared `status.resources`
     (with the one-hop ReplicaSet/Job prefix match a Deployment/CronJob's pod
     actually needs, since `status.resources` never lists the intermediate
     controller)
   - ArgoCD's own `app.kubernetes.io/instance` tracking label as a fallback
   Never infers the namespace from the app name.

2. **Expected-divergence classification**, each citing its source of truth:
   - manual-sync apps via `manual-sync-policy.ts`'s new `manualSyncDeclarations`
     (reads the same annotation convention that file already governs — not a
     hand list)
   - external-secret gaps via a new parser over
     `full-ai-cluster/INJECTION-POINTS.md`'s `**EXTERNAL**`-marked rows
     (`parseExternalSecretCatalog`)
   - openbao's sealed-by-design first-boot state (`isKnownSealedByDesign`,
     sourced from its own `TOPOLOGY.md` §5)

3. **Item 3 — no more vacuity.** A Progressing/Missing app with no classified
   pod issue now reports its unhealthy `status.resources` entries and
   `status.conditions` in the verdict reason, instead of the bare
   `"no classified pod issue"` message.

4. **161 new/updated unit tests** across both test files (`first-boot-replica.test.ts`,
   `manual-sync-policy.test.ts`), each written to fail if its rule is
   inverted — attribution, ownership, owner-ref matching, the external-secret
   parser (including against the REAL `INJECTION-POINTS.md`), and end-to-end
   `computeAppVerdict` classification scenarios for every named case above.

Full backward compatibility: every new field on `AppConvergenceSnapshot` is
optional, `PodVerdict.appName` is optional (falls back to the old
`namespace === app.name` check when absent), and `computeAppVerdict`/
`computeAppVerdicts` take an optional context that defaults to empty (old
behaviour) — all 139 pre-existing tests in `first-boot-replica.test.ts` and
22 in `manual-sync-policy.test.ts` pass unchanged.

## Before / after (per the WP23 problem statement)

| App | Before | After |
| --- | --- | --- |
| `cilium` | FAIL: `health=Progressing with no classified pod issue in namespace "cilium"` (wrong namespace) | Attributed via `kube-system` ownership + owner-ref match; real verdict (Healthy, or a genuine FAIL/DIVERGENCE with the actual pod evidence) |
| `kube-prometheus-stack` | Same class of false FAIL (`monitoring` namespace) | Attributed correctly |
| `openziti-controller` | Same class (`openziti` namespace) | Attributed correctly |
| `seaweedfs` | Same class (`object-store` namespace) | Attributed correctly |
| `cdi` / `kubevirt` | FAIL on `Missing` (manual-sync apps asserted the full contract) | DIVERGENCE, citing `manual-sync-policy.ts`'s declared reason |
| `hindsight` (`hindsight-llm-api-key`) | FAIL: `SECRET(CreateContainerConfigError)` | DIVERGENCE, citing the EXTERNAL row in `INJECTION-POINTS.md` |
| `openbao` | FAIL: `no classified pod issue` | DIVERGENCE: sealed-by-design (TOPOLOGY.md §5) |
| `weaviate` | FAIL: `Progressing with no classified pod issue` | Still FAIL if genuinely unexplained, but now reports the unhealthy `status.resources`/`conditions` instead of nothing |

A remaining FAIL after this change means a real pod-level problem (IMAGE,
SECRET not in the external catalog, CRASHLOOP, UNKNOWN) correctly attributed
to the right app, or an app-level condition/resource this harness genuinely
cannot explain — exactly what a real metal first boot would also suffer.
