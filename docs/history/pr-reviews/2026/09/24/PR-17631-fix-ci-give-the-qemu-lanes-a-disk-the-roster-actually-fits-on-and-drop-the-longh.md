## Description

Takes the fifth option over the four I named in `081M39QY9N8087G0R000E08D2B`. It is better than all of them, and it removes the problem instead of routing around it.

## Why the override had to go, not just be delivered better

Staging `ZETA_ALLOW_LONGHORN_UNDERSIZED` on the flashed image's ESP **worked** — run 35996447262's guest read `esp-conf=esp:/dev/disk/by-label/EFIBOOT` and the lane produced **five of six passing verdicts for the first time ever**. It is still the wrong answer:

- **Every QEMU install was exercising the override path** — the one path a real USB install should never take. The computed root floor, the tail arithmetic and the real `sgdisk` geometry were short-circuited on every run, so the lanes measured a thing nobody ships.
- **The cdrom lane could not be unblocked at all.** `scenario 2 — boot + install substrate` has no vfat partition to stage anything on. The WP27 scan instrumentation named that in one line on its first real use: `esp-conf=none tried=/dev/disk/by-label/ZETA_INSTALL(no-vfat)`.

## The arithmetic, derived from `zeta-install.sh`'s own constants

```
tail        = disk − ZETA_ESP_GIB(1) − ZETA_ROOT_FLOOR_GIB(120)
schedulable = tail × ZETA_LONGHORN_USABLE_PERCENT(75) / 100     [integer]
verdict ok  needs schedulable ≥ ZETA_LONGHORN_DEMAND_GIB(943)
```

so `tail ≥ ceil(943×100/75) = 1258` and `disk ≥ 1379`. **`QEMU_DISK_SIZE_GB = 1400`** is that with slack (tail 1279, schedulable 959). An exact fit would turn any future +1 GiB of roster demand into a red lane with no margin.

One constant now — the WP11 lane's 64 GiB special case is gone, because k3s plus a few GB of chart images is noise against a disk sized for the roster.

**A test re-derives that floor** by parsing the four constants out of `zeta-install.sh`, so a roster that grows or a root floor that moves goes red in 0.2 s instead of in a 90-minute lane. It asserts the *truncated integer* schedulable, not the ideal one.

## The sparseness claim is measured, because it is the thing that could bite

qcow2 allocates what the guest **writes** (~17–20 GiB), not the declared virtual size — that is the whole reason 1400 GiB is nearly free. The failure mode that would break it is `mkfs.ext4` eagerly writing inode tables across a ~1.3 TiB partition. Modern `mke2fs` defaults to `lazy_itable_init=1` so it should not, but *"should not" is not a measurement*, and this lane has already spent a night on assumptions that read like facts.

`reportQcowAllocation` now prints, after phase 1:

```
after phase 1 (install): qcow2 virtual=1400.0 GiB allocated=18.0 GiB (1.29% of virtual); runner free: 60.0 GiB
```

and warns — never fails — when the allocation exceeds what the runner has left. A run in the sparse world and a run in the eager world now look **different in the log** instead of identical until one of them hits ENOSPC. Free space that could not be read is reported as `unknown` rather than omitted: *"no headroom line"* and *"headroom is fine"* must not look the same.

If the measurement comes back large, the number is in the log and the fallback is a one-line revert to the override for the cdrom lane specifically. I do not expect it to.

## One contract goes DORMANT, and says so

`assertEspFirstbootConfWasRead` was added when every USB bake staged a conf. No lane stages one now, so asserting would convict every lane — and keeping it alive by staging a no-op value to give it something to find would be the vacuity class wearing a test. It is gated on `stagedEspFirstbootConf` and prints `DORMANT` with the guest's actual `esp-conf=` value and the words **"This is not a pass."**

**ESP arrival is still covered**, by an observable every USB lane really does stage: `wp11PreconditionFailure` convicts on `[iter-5.2]   no zeta-hostname.txt on USB ESP`, and the guest reports its scan outcome on every boot regardless. The join is not uncovered — it is covered by the thing the lane actually stages.
