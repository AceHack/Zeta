## Description

Follow-up to #17618. **The stated root cause is not what happened, and I can show it in one command** — so this PR fixes the thing that made the run un-diagnosable instead.

## What run 35985197702 showed

It bailed before the wipe on exactly the refusal the Longhorn override exists to spare this lane:

```
ERROR: BOOT disk /dev/vda is 64 GiB, which cannot hold ESP 1 GiB + root floor 120 GiB
+ a 1 GiB minimum longhorn1 tail (need >= 122 GiB)
```

and the guest's first line said `source=iso:/etc/zeta-firstboot.conf`.

## What it did NOT show

The proposed cause was *"zflash only writes the ESP conf when `--role` is passed, so there was nothing for the append to append to."* That is an **argv-level** constraint in the CLI help text; `prepareBootImage` does not go through argv. With the WP11 lane's exact inputs and **no role**, `planFileBackedZflashImage` returns:

```
/zeta-authorized-keys.pub
/zeta-hostname.txt
/zeta-qemu-k3s-first-boot-verify
/zeta-firstboot.conf :: "ZETA_ALLOW_LONGHORN_UNDERSIZED='1'\n"
```

`planFileBackedZflashImageExecution` emits the matching `mcopy … ::/zeta-firstboot.conf`, and `file-backed.ts`'s post-bake `mdir` verification (081KZHJPJCF) **fails the bake** when a planned file does not land. That bake passed.

**So the conf was written and the guest did not read it — and nothing in the run could say why.** That silence is the defect this PR fixes. I have not guessed at the mount; I have made the next run answer it.

## 1. The scan was silent, so three different failures looked identical

`zeta_source_esp_firstboot_conf` printed nothing on any path. A run that found no conf, a run whose mount failed on every candidate, and a run where the glob matched no block device produced **byte-identical** output: none. The only downstream signal was `source=iso:`, which is *also* what a correct run prints when nothing was staged.

It now reports unconditionally, on every boot:

```
[081M392JR97087G0R003QAFH0Y-esp-conf] esp-conf=<outcome> tried=<candidates>
```

with a per-candidate reason — `(no-vfat)` for a candidate that would not mount, `(no-conf)` for one that mounted without the file — and `no-block-devices-matched` when the loop considered nothing. One more run distinguishes all three, and that run bails in ~4.5 minutes rather than 90.

## 2. A role-less ESP conf must not claim the role was DECLARED

This one would have bitten quietly, and it is why I did not simply widen the writer.

`ZETA_ROLE_SOURCE=esp:` is read a few lines later as *"a human chose this role"* (`ZETA_ROLE_DECLARED=yes`), and a declared role **skips bootstrap-or-join discovery outright**. Sound while an ESP conf could only exist because someone passed `--role`. It no longer can be — the QEMU lanes stage `ZETA_ALLOW_LONGHORN_UNDERSIZED` on that same file.

Left alone, writing a role-less conf would have promoted every such node from DEFAULTED to DECLARED and turned discovery off via an unrelated knob. The role source now moves **only when the conf actually declares a role**, checked against the file rather than the resulting variable (`ZETA_ROLE` is already set from the ISO conf by then, so "is it set?" cannot tell the two apart). The conf's **arrival** and the role's **provenance** are now two separately reported facts.

This is also why the falsifier asserts on the new `esp-conf=` line rather than on `source=esp:` as suggested: for a conf that declares no role, `source=iso:` is the **correct** output, and asserting `esp:` there would have demanded the very conflation this section removes.

## 3. The test that was supposed to cover this could not fail

```ts
expect(sh).toContain("ZETA_ALLOW_LONGHORN_UNDERSIZED");
```

A statement about a file in this repo, not about a value reaching a guest — and green throughout the failing run. Same shape as a `${VAR:-}` that is never exported: a knob that turns and is not connected.

Replaced by `assertEspFirstbootConfWasRead`, which reads what the **guest** reported and runs on every USB-image lane. Its failure text points at the guest and says outright that the host side is not the suspect, because sending the next reader at the bake costs another run. An ISO with no instrumentation is reported as **its own case**, never folded into "not found" — a rebuild need and a regression are different findings.

What survives as a static check is honest about its limits: it now also requires `zeta-first-boot.sh` to **export** the name (not merely set it) and to carry the scan prefix at all, with a comment saying that presence in three files is still not arrival in a guest.

## Filed, not fixed — `081M39K8ND1087G0R000G4EN4N`

**Cluster discovery has never run.** `cluster-discovery/probe.ts:83` passes `--no-db-lookup`, which this image's `avahi-browse` rejects, so every browse pass exits 1 and bootstrap-or-join has only ever taken the fallback.

The module's own reporting is exactly right — `probe-failed` is not `no-peers-found`, and it says *"a check that did not run, NOT a check that passed"* — which is why this is a finding rather than a disaster: nothing downstream was told an empty network was observed. The work item names the flag **and** the missing falsifier, because dropping the flag without one leaves the same silence that let this go unnoticed.

## Tests

126 in `qemu-full-install-test.test.ts`, 239 across the four affected files; `tsc --noEmit` clean, `bash -n` clean on the installer script.

The new tests include the exact shape run 35985197702 produced (`esp-conf=none` with a `(no-conf)` candidate) as a **failing** case, an ISO-without-instrumentation as a distinct case, and a check that `zeta-first-boot.sh` gates the role-source move on the conf declaring a role.

## Still open

Why the guest did not read a conf that was demonstrably on the ESP. The instrumentation above is what answers it, in one fast run, instead of another hour of inference.
