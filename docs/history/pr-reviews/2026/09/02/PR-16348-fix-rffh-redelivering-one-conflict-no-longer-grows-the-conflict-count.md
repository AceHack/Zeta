## Description

## What

Found by an adversarial math review of the RFFH PRs, **verified in the code before acting on it**.

On `ConflictDetected` the receipt was appended unconditionally and `state.Evidence`
was never updated — so the *same* conflicting message delivered N times appended N
identical receipts and `tryConsensusStatus` returned `EvidenceConflicted(N, _)`.

In the one module whose stated invariant is that **replaying the same evidence
identity must not change the conclusion**, the conflict count was an unbounded
channel through which at-least-once delivery changed it. `RFFH-10` pinned the
single-delivery case only, so nothing caught it.

Fix: whole-receipt dedupe. The same conflict, reported again, is one conflict.

## What I got wrong on the way, and why the test stays

My first fix keyed on `(EvidenceId, RetainedFingerprint, ChangedFingerprint)` and
**merged emitter labels** into the matched receipt, on the theory that a new
emitter reporting a known conflict is new information.

**That branch is unreachable.** The content fingerprint already covers the emitter
column, so two emitters asserting byte-identical content produce *different*
fingerprints and are, by this module's own definition, two conflicts. I had written
code for a case that cannot occur, under a comment asserting behaviour that could
never fire — the exact vacuity class this repo audits for, produced while fixing a
different instance of it.

The merge is gone rather than left in looking load-bearing, and **`RFFH-10c` now
pins the property that made it unreachable** — so anyone who later narrows the
fingerprint has to decide deliberately whether two columns disagreeing identically
is one conflict or two.

than a one-line correctness fix:
