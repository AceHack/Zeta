## Description

First full local gate run on **Windows 11** — bun 1.4.0, .NET SDK **10.0.400** (the pinned version).

| gate dimension | result |

| `dotnet test Zeta.sln -c Release` | 7,083 tests — **2 failed** |
| `bun test src/Core.TypeScript/agent-heartbeats/` | 237 tests — **19 failed** |

**None of those 21 failures is a defect in the code under test.** Each is a test asserting something
about the machine rather than about its subject — and each cost real time to tell apart from a real
failure, which is what this PR fixes.

## 1. bun's 5000 ms default cap — 17 of the 19

`prepare-heartbeat-branch` and `premerge-flush-ref` build real git repositories and drive them with
real `git` subprocesses. Alone they are green (39/39, 9/9). In the same `bun test` invocation as
their siblings, git contention pushes several past 5000 ms and they fail with an **empty stderr** —
`git fetch origin failed:` and nothing after the colon. A timeout wearing the costume of a git error.

**Causal proof:** the identical three files with `--timeout 60000` produced **zero** of those
failures, leaving only §2.

It is load-dependent, which is why it reads as flake: 19 failures with a `dotnet` build running
alongside, 4 on a quieter run, 0 on an idle machine. Linux CI is fast enough never to see it — so it
fires only on a contributor's machine, where it reads as `main` being broken.

`bunfig.toml` already states the rule and the remedy:

> bun 1.3.14 does not implement `[test] timeout` … THE EFFECTIVE PER-TEST CAP IS 5000 ms … a global
> raise hides slow tests … **A test that is slow BY NATURE carries its own explicit timeout.**

One test in `prepare-heartbeat-branch.test.ts` already carried a hand-written `30_000`. This is that
precedent applied to all 48 siblings, behind one named constant so there is a single value to change.

## 2. A POSIX path assertion — 2 of the 19

`heartbeatPath` returns a **local filesystem** path (it is handed to `mkdirSync`/`writeFileSync`), so
native separators are the correct output; asserting the literal `/repo/docs/...` asserts the host OS
rather than the function. Composed with `join` instead — the real assertion (the `YYYY/MM/DD`
segments, the zero-padding, the hex filename) survives, the accidental one goes.

The sibling `heartbeatRepoRelPath` builds the repo-relative **git** path, must stay forward-slashed
on every OS, and already has a test asserting exactly that. That is why they are two functions, and
why only one of them may use `join`.

## 3. git `core.symlinks=false` — 1 of the 2 .NET failures

`ProvisionalExperienceReplayMatchesGoldenVectors` hashes a fixture tree holding two git symlinks
(mode `120000`). Git materialises those as real symlinks only when `core.symlinks` is true — on
Windows that needs Developer Mode or an elevated clone, and git sets it `false` otherwise. With it
false they arrive as **ordinary files whose content is the target path** (`../file1.txt`, `..`), so
`HashDirectory` classifies them `file` instead of `symlink` and hashes a different tree:

```text
Expected: "081478c5744a061d3eb3e9800a78517b8f6dc060759a2ce2a0"···
Actual:   "ec74217287ef7d611fbbbc2153159e3bd399f353cb9cab3bab"···
```

**The golden vector is not wrong and is not touched** — it is the four-oracle treaty. What is wrong
is presenting an input this checkout *cannot represent* as a byte-lock failure. Now detected and
skipped with the reason named, using the `Assert.Skip` idiom already in `Infra/CwdChaos.Tests.fs`;
xunit reports skipped-with-cause, never a pass.
