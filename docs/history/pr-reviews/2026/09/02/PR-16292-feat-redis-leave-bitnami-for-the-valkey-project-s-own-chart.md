You delegated the choice: *most supported, or best fit for our workflows.* This is that decision and what it rests on.

## Measured, not assumed (Docker Hub API, 2026-09-01)

| repository | state |

| `bitnami/valkey` | **the same** — `latest` only, and its chart defaults to `tag: latest` |
| `valkey/valkey` | **9.1.x, real versioned tags, published that day** |

**The finding that settled it:** switching flavours *inside* Bitnami escapes nothing. Bumping the Bitnami chart trades a frozen archive for an **unpinned rolling tag** — worse, since a frozen tag at least does not change under you.

## Chosen: `valkey-io/valkey-helm` 0.11.0

The Valkey project's own chart. Pins `valkey/valkey` with `tag: ""` → appVersion, not `latest`. Renders **`docker.io/valkey/valkey:9.1.1`**, an immutable tag.

**Not chosen — keep a Bitnami chart and override the image.** That is what the old pin did, and it worked *only* because `bitnamilegacy` is still a Bitnami image with Bitnami's filesystem layout. Pointed at `valkey/valkey` it would break on `/opt/bitnami` paths — and `allowInsecureImages` silences the assertion that would have said so.

## Workflow fit

Orleans reads cluster membership from here over StackExchange.Redis. Valkey is wire-compatible, so the client is unchanged. The **Service name is not**: `redis-valkey`, not `redis-master` — read off an actual render rather than guessed. `orleans/configmap.yaml` moves with it in this commit.

**Resources are declared, because this chart declares none.** `resources: {}` is its default and renders **BestEffort** pods — the first evicted under node pressure. An evicted cache here is a cluster that loses its *membership store*. 100m/128Mi per pod carries the old bitnami `resourcesPreset: nano` figure forward rather than inventing one.

## Two of my own values were inert, and the guard caught both

- `replica.username` — the key is **`replicationUser`**. The chart *defaults* it to `"default"`, so the wrong spelling renders cleanly and silently replicates as the **full-privilege default user** instead of the minimal one.
- top-level `persistence` — this chart has no such key; only `replica.persistence`, which is what actually produced the longhorn PVC.

## Why this is a draft

The storage/resource ledger addresses redis through **bitnami value paths** (`master.persistence.storageClass`, `replica.replicaCount`) and models it as *master + replicas*. The Valkey chart renders **one** StatefulSet, two pods, **one shared volumeClaimTemplate** — so the two-row split no longer describes reality, and re-pointing the paths would preserve a shape that is now wrong.

That is a restructure of the ledger governing cluster capacity planning. Filed as **081M1F8ZE90087G0R003X3PYN9** rather than rushed.
