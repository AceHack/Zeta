## Description

Three defects in the tick loop's own safety surfaces, all found by **running** it on a fresh clone
rather than by reading it. Two are fixed here; the third is reported below, unfixed.

## 1. Two Claude Code hooks spawn paths that moved in #8048

| hook | spawned | actually lives at |
|---|---|---|
| `verify-branch-pretooluse.ts` | `tools/orchestrator-checks/verify-branch.ts` | `src/Core.TypeScript/orchestrator-checks/` |
| `check-md032-pretooluse.ts` | `tools/hygiene/check-md032-blanks-around-lists.ts` | `src/Core.TypeScript/hygiene/` |

PR #8048 relocated both directories; neither literal followed.

**Why it stayed invisible.** The branch hook still returned a well-formed
`permissionDecision: "deny"` — so it still *read* as a working gate, and only its reason string
(`error: Module not found "...verify-branch.ts"`) said otherwise. And it is opt-in: with
`ZETA_EXPECTED_BRANCH` unset it exits 0 before it would ever discover its target was gone. A gate
nobody armed cannot report its own absence.

Verified by piping the hook contract to the script directly:

|  | before | after |
|---|---|---|
| expected `feature/x`, on `main` | deny — `Module not found` | deny — `ERROR: Pre-commit branch mismatch. Expected: feature/x Current: main` |
| expected `main`, on `main` | deny — `Module not found` | exit 0, no output |
| Bash call that is not `git commit` | exit 0 | exit 0 |

**The guard matters more than the fix.** `tsc` cannot see a path inside a string and the hooks have
no tests, so nothing asserted these literals name files. `audit-hook-script-paths.ts` checks both
ends of the wiring — every `$CLAUDE_PROJECT_DIR`-rooted command in `.claude/settings.json` and
every `${projectDir}`-rooted path the hook scripts spawn — and is wired into `preflight`
(milliseconds, pure path existence).

It earned its place immediately: **the md032 reference above was found by this audit, not by a
reader.** Mutation-checked — reverting either path fix turns `THIS repo has no dangling hook
references` red.

## 2. `--dry-run` never reached the tick body, so a dry run still pushed `origin/main`

`tools/tick-source/README.md` promised `--dry-run` "only declines to move the remote ref". It did
not. `runTick`'s dryRun branch sits at **STEP 4** (the lane push); the body it spawns at STEP 2 is
`run-loop-real.ts`, built with no `--dry-run`, whose event sink is folder-direct-to-main — it
pushes `origin/main` itself, long before STEP 4 declines to.

Measured on a fresh clone, 2026-09-02:

```text
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Required status check "gate (required)" is expected.
 ! [remote rejected]     HEAD -> main (push declined due to repository rule violations)
[execute] FAILED: append-failed — push failed after 3 rebase-retry attempts; local commit undone
```

Nothing landed and the local commit was correctly undone — but **what stopped it was a server-side
setting the flag knows nothing about.** On a fork, a mirror, or any clone whose default branch is
unprotected, that push succeeds. A dry run whose safety depends on a ruleset elsewhere is not a dry
run.

Fixed by forwarding the flag. Note where the defect actually was: **`toConfig`, not
`defaultTickCommand`** — a test exercising `defaultTickCommand` alone would have stayed green
through the whole bug, so the regression test asserts on `toConfig(...).tickCommand`.
Mutation-checked: reverting the one-line `toConfig` change reddens exactly that test and leaves the
other 24 green. The Actions lane never passes `dryRun`, so the "same body as the Actions lane"
invariant is unchanged.
