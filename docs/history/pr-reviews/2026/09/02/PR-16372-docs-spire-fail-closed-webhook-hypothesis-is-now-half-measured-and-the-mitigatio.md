## Description

## The pin does not move. What changes is what is known about why.

### Measured now

Rendering 0.24.2 and 0.30.1 with this Application's own `valuesObject` at
`--kube-version 1.35.6`: **both** ValidatingWebhookConfiguration webhooks —
`vclusterspiffeid.kb.io` and `vclusterfederatedtrustdomain.kb.io` — move
`failurePolicy: Ignore → Fail`.

The WATCH note on this pin predicted exactly that shape. It is no longer a
prediction.

### Still not measured

That this is **what turned the live lane red**. A fail-closed webhook whose
backing service isn't ready *would* block admission; nothing has observed it doing
so here. Only the isolation run closes that — which is why the pin has not moved.

The two halves are kept apart deliberately: collapsing them is how a guess becomes
a citation.

## The `spire-bundle` caveat is answered — and it was not a loss

0.30.1 stops **templating** that ConfigMap; the spire-server writes it at runtime.
The chart still renders the `spire-bundle` Role with `resourceNames: [spire-bundle]`
(*"Role to be able to push certificate bundles to a configmap"*), and the server
config still carries `BundlePublisher` with `configmap_name: spire-bundle`.
Nothing in this tree consumes it by name, so there's no dangling reference either
way.

## The mitigation exists in the chart

`controllerManager.validatingWebhookConfiguration.failurePolicy`
(spire-server subchart, `templates/controller-manager-webhook.yaml:19`).

Setting it to `Ignore` takes 0.30.1 **while keeping 0.24.2's admission behaviour**
— making the bump and the policy change two decisions instead of one bundled
together.

Worth knowing when reading that template: it emits a hardcoded
`failurePolicy: Ignore # Actual value to be set by post install/upgrade hooks` on
one branch and the values-driven value on the other, so **the live object can
differ from the rendered one**. A render is evidence about the manifest, never
about the cluster — the same reason this pin is held rather than reasoned about.

## Also here: my own guard caught a stale entry the moment it became true

Riven's **#16362** merged and now mints `redis-auth` on the dev roster, so the
`redis|redis-auth` acknowledgement in `existing-secret-is-minted.baseline.json`
stopped matching anything and **failed as STALE** — exactly what its `liftsWhen`
said it would. Deleted. The entry was written to be short-lived, and it was.
