## Description

## What

Files `081M1HH1ERN087G0R00309EG9D`. Aaron corrected the currency report:

> i read headscale is still supported not unsupport fyi

He is right, and the `DORMANT` label is measuring something else.

## What is actually true, measured 2026-09-02

| | chart | appVersion |
|---|---|---|
| what we pin (`charts.gabe565.com`) | `0.16.0` | **v0.25.0** |
| the maintained chart (`headscale/headscale`) | `1.0.19` | **0.29.3** |
| the project's latest release | — | **v0.29.3** (2026-07-29) |

The chart **moved home**. `charts.gabe565.com` is a third-party personal repo —
still alive, it publishes `adguard-home` actively — that stopped updating its
headscale chart 559 days ago. We are **four server releases behind** and nothing
in the tree says so. Same shape as the `tempo` / `cert-manager` relocations.

## The general defect, which is worth more than the instance

**Chart currency is not app currency, and the report only measures the first.**

For a chart that pins an application image, a dormant chart freezes the product
at whatever `appVersion` it last shipped — and the report renders that as
`DORMANT` / zero behind, i.e. *nothing to do here*. That is exactly the failure
the report's own headline already names for `minio`:

> a pure versions-behind metric reports the most dangerous dependency in this
> tree as the healthiest one

…one level down. `minio` was chart-current because upstream archived; `headscale`
is chart-current because its packager moved on. Both read healthy.

## Filed, not fixed

Relocating packagers is a **migration**, not a bump — different values schema — so
it needs the treatment redis→valkey got. And "stay on gabe565 deliberately" is a
legitimate answer that should be written into the Application either way. Neither
should be chosen as a side effect of a currency sweep.
