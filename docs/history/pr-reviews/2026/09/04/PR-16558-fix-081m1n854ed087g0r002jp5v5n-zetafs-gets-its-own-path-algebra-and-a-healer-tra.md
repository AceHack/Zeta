## Description

The filed finding from #16557, fixed — plus the autohealer track for the class.

## The defect

A ZetaFS module hands every path it builds to `FileSystem.Current`, which is an **abstraction**: it may be the host filesystem, it may be `InMemoryFileSystem`, and the module cannot tell. All five were building those paths with `System.IO.Path.Combine` — a function of the **host** (`\` on Windows, `/` elsewhere).

So the namespace of a filesystem meant to be the substrate's own took its shape from whichever machine ran the code. That's ambient state in a namespace (§13), and it breaks the DST property that identical inputs give identical outputs regardless of host: **a key written on Windows and one written on Linux were literally different strings for the same file.**

**Measured:** 27 `Path.Combine` + 4 `Path.GetDirectoryName` across `ZetaFsFreeze`, `ZetaFsMutbuf`, `ZetaFsCli`, `ZetaFsFormat`, `ZetaFsDeltaLog`. All 31 now go through `ZetaFsPath`.

### Why a `/`-join is also correct for real host paths

This is what makes it a strict improvement rather than a trade. Win32 accepts **both** separators — `Path.AltDirectorySeparatorChar` is `/` on Windows precisely because the API treats it as one — so `C:\store/objects` opens the same file as `C:\store\objects`. **There is no case where `Path.Combine` is right and this is wrong.**

`directoryName` is here rather than `Path.GetDirectoryName` not because that function is known to be wrong, but because its behaviour on a `/`-shaped path under Windows is something this codebase would have to *assume*. A pure substring split needs no assumption and is testable identically on every platform.

## The healer track

`healers/zetafs-virtual-path.ts` carries a `Detector` and a `Healer` and passes `certify()` for **idempotence, closure and convergence**.

**Where the judgement went** — `lockfile-healer.yml` is explicit that a "no intelligence" healer must have none, and `Path.Combine` is *correct* on a genuine host path, so a repo-wide rewrite would be a judgement at every site. The judgement is removed by **scope, not cleverness**: inside a module that routes every path through `FileSystem.Current` and never touches `System.IO.File`/`Directory` directly, there is no host path, so the rewrite is mechanical. `inScope` **derives** that set from the files themselves rather than from a roster — a new ZetaFS module is covered the moment it exists, and a module that starts touching the host filesystem leaves scope on its own.

### What ships today is the detector, writing nothing

`run-tier0.ts` reads `.ts/.tsx/.js/.md/.yml` and would have to be widened to `.fs` to register the healer — which changes the blast radius of **five** healers over a language none of them was written against. Each would very likely no-op on F#, and *"very likely no-op"* is an assumption about five things that **write to the repository**. That runner's own header records what that class of assumption cost once: a sibling tool probed with `--help` started a ~1,700-file rewrite.

So registration is **filed** (`081M1N97ECS087G0R003GCPEDZ`) with its own re-certification step, rather than slipped in beside a fix.

### The detector's own guards

- **Zero ZetaFs files found is an alarm, not a pass** — a renamed directory would otherwise report "no drift" over nothing.
- **`Path.GetFullPath` is a warning, never rewritten.** It's a *different* defect — ambient CWD, not ambient separator — and removing it changes behaviour for real-path callers. Failing on it would keep the check permanently red for a decision it isn't allowed to make. Filed as `081M1N97EDM087G0R000W35B5M` with the three options and which one matches how this repo usually resolves an ambient input (refuse it rather than resolve it).
