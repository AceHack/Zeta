## `081M1N0VTN8087G0R0008VE34B` (P1) — resource requests everywhere

The budget step has printed this every run and nobody acted on it: **29 of 47 Applications render pods that request nothing at all.**

| bucket | count |
| --- | --- |
| governed (a rung row exists) | 12 |
| renders requests, no rung row | 6 |
| **renders nothing — BestEffort** | **29** |

The membership is the argument: **`cockroachdb`** (the largest declared storage consumer), **`vault`**, **`longhorn`**, **`nats`**, **`spire`** and **`argocd`** are all BestEffort. The control plane, the storage layer, the secret store and the GitOps engine that would have to recover from an eviction are all first in line to be evicted.

**Requests are the floor with no exceptions. Limits are case-by-case**, and your constraint is written down as the asymmetry it rests on:

| | CPU limit | memory limit |
| --- | --- | --- |
| effect when hit | **throttled** — slower, still correct | **OOMKilled** — the pod dies |
| safe to set blind? | mostly, and still hurts latency-sensitive work | **no** |

A memory limit on anything whose working set scales with load is a crash waiting for a busy day; a CPU limit on a component holding a leader-election lease can produce a throttle-induced lease loss that looks like a partition.

Includes a **ratchet** requirement — without one this is a cleanup that regrows, so `ungovernedRequests`'s current membership becomes the high-water mark and a new Application arrives governed or red.

## `081M1N0VTP0087G0R0034E7Y0G` (P1) — HA and backups

The backup half has a one-word answer. Searched the whole cluster tree for `backupTarget`, `velero`, `barmanObjectStore`, `backup:`, `RecurringJob`, `VolumeSnapshot`:

> **Zero hits. There is no backup machinery anywhere in `full-ai-cluster/`.**

Longhorn has no `backupTarget`. CockroachDB — 3 members, 48Gi each — has no `BACKUP` schedule. Vault has no snapshot schedule, so a lost Raft volume is a lost unseal state.

**And the distinction the item exists to hold: replication is not backup.** Three Raft members survive a node dying. They do not survive a bad write, a `DELETE`, a schema migration, an operator bug, or `prune: true` — all of which replicate faithfully and instantly to every replica. So *"not already replicated somewhere"* is the right test for the HA half and is **not** sufficient for the backup half.

The HA half starts from `acknowledgedFalseRedundancy`, which already carries six apps declaring multi-replica topologies on `nodeCount: 1` (cockroachdb, vault, nats, redis, platform, kubevirt). Three copies in one failure domain is not HA — it's three times the disk for the same availability. The work is deciding, per workload, whether it's genuine-once-a-second-node-exists, false redundancy to scale down now, or a case that needs a backup because no replica count addresses the failure that threatens it.

**Backups before HA:** backups protect against what replication cannot and work on one node today, while HA on `nodeCount: 1` mostly cannot be honest yet.
