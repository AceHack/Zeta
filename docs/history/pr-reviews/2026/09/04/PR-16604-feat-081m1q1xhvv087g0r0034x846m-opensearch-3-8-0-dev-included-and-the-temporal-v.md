## Description

Aaron 2026-09-04: *"lets pull in open search, i've been discussing with google"* — and on the first draft of this, *"what does dev excluded mean, we want to try to test on dev for all of these."*

## The version, read live

**3.8.0** (chart and appVersion both) from `opensearch-project.github.io/helm-charts`, read off the live repo index with `helm search repo opensearch --versions` rather than from recall — Aaron asked for exactly that, *"so we don't have to migrate/update later"*. **Not** `bitnami/opensearch` (chart 2.0.10 / app 3.2.0 on the same index): this tree is moving off bitnami, and the upstream project publishes its own.

## What it's for — and the half that's blocked

The tree has no general text index; `weaviate` is a **vector** store with a BM25 mode, which isn't the same thing. That gap closes today.

The other job — Temporal's visibility store — is **blocked on a version floor**. Temporal currently runs *both* default and visibility persistence on CockroachDB, which its own guidance says is wrong at volume. Temporal's self-hosted visibility docs state the floor verbatim:

> "OpenSearch 2+ with Temporal Server v1.30.1 and later"

We pin temporal chart 0.59.0, appVersion **1.27.2** — below it. Clearing it needs the 0.59.0 → 1.6.0 migration (`sql.driver` → `sql.pluginName`, five bundled subcharts removed upstream, versioned schema migrations against CockroachDB). **That migration is now on the critical path for this feature.**

## Dev-included — a correction made mid-change

The first draft excluded it from dev believing the lane had no memory left. That was wrong twice: a dev-**excluded** Application is never *applied* in CI at all (twelve are in that state), and the belief was stale — the 25m `cpuMillis.dev` floor from 2026-08-23 had freed the lane.

## And the cost is larger than I first said

I told Aaron it "fits" on the strength of `lane-partition`'s 1482Mi of spare. **That's a different denominator** — lane-partition packs Applications into runner-sized lanes; the budget that matters is the dev lane's own applied set. Measured properly: **9356Mi → 10380Mi against 9216Mi, over by 1164Mi** — an eightfold widening of what was a 140Mi overage an hour earlier.

The budget is **not** widened to hide it. It's carried in `acknowledgedLaneBudgetShortfall` with the denominator mistake named, spent out of the ~4300Mi the envelope leaves unreserved for BestEffort pods.

## Sizing

One node (chart default is 3 × 1000m against a 2500m lane). Heap pinned at 512M at both rungs — the chart's own default is a 512M heap against a *100Mi request*, five times over, which makes the pod a first-choice eviction target. **Not HA**, said out loud: no shard replication. Acceptable for a derived, re-indexable index; not for a store of record.

Storage is 20Gi on `zeta-local-path`. A ladder row was written and **backed out on the tooling's own conviction** — `budgetedStorageClasses` is exactly `["longhorn"]`, and `single-node-readiness` refused it ("its capacity is being counted against a PVC that is not there"). It's a baseline acknowledgement instead.
