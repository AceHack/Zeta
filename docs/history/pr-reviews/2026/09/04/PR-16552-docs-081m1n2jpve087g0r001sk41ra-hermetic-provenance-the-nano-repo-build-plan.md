## Description

Two things, both from the hermetic-tier conversation.

## 1. The provenance, in `bunfig.hermetic.toml`

The word is **borrowed, and the borrowing was never written down anywhere in this repo** — exactly the anchoring debt `anchor-to-human-prior-art` names. Now recorded:

- **In software it's Google's term of art**, from Blaze then Bazel, now standard across that family (Buck, Pants; Nix uses it roughly interchangeably with "pure"). Bazel's definition: a build is hermetic when it is **insensitive to the state of the machine**. The point was never speed — it was that a failure should *mean* something. If a build can go red because of your laptop, a red build has stopped being information. Which is the argument this file's own measurement already makes, arrived at independently and now given its proper name.
- **The older sense is the metaphor the software one keeps.** A *hermetic seal* is an airtight one, named for Hermes Trismegistus — the Greek Hermes fused with Egyptian Thoth, patron figure of alchemy — because alchemists were credited with fusing a glass vessel shut so nothing could get in or out.

### And the caveat, because the name promises more than the file delivers

| | Bazel | ours |
| --- | --- | --- |
| inputs pinned | yes | yes — `install.sh` + frozen lockfile, pinned Bun and SMT binaries |
| per-action sandbox | yes | **no** |
| network cut per action | can | **no** |

Sealed against the host's **configuration**, not against everything. Written down so the next reader doesn't trust this tier with properties it doesn't have.

## 2. The nano-repo build plan, written up as research

> *"either ace our package manger or maybe we need a full one build system like bazel but we want to support monorepos split over nano/microrepo … super isolated incremental builds and impacted test runs only … gated by a good multi repo workflows / discriminated unions"*

The doc's job is to make this an **increment, not a greenfield**. It starts from what's checked in: `ace/build-graph.ts` already holds the graph, the `affected` query, edges *derived* from `.fsproj`/Cargo/lakefile rather than invented, and the safety property that **unknown escalates to FULL**. The missing piece isn't a build graph — it's that today's graph has exactly one repo root.

Four things it settles or names honestly:

**Why not just adopt Bazel.** It would breach `clone-at-tag-stays-sufficient`: a tree that needs `bazel` on PATH is a tree with an appointed hub, and the discriminator is exit, not degree. So Bazel is an **oracle we consult, not a hub we route through** — the graph and the carve stay ours and stay plain data, and a faster executor over them is an optimisation anyone may decline.

**The relative-path instinct is the overlay workspace**, and it has a tradition worth naming: Android `repo`, Cargo workspaces, pnpm/Rush/Nx, bzlmod `local_path_override`, Nix flakes `follows`, git subtree. The property they all buy is the one being asked for — *a reference means the same thing whether the producer is a sibling checkout or a pinned artifact; only the resolution differs, and the graph does not change shape between those cases.*

**Its failure mode, recorded now rather than discovered.** An overlay makes the build depend on which repos happen to be present — ambient state, precisely what hermeticity forbids. So the union must be **declared in a manifest**, never inferred from what's lying around on disk. A build that silently changes meaning because a sibling directory exists is the §13 noninterference violation wearing a convenience.

**Why DUs gate it.** A cross-repo reference is a sum type — `SameRepo` / `SiblingRepo` / `PinnedRelease` / `Generated` / `Unknown`. As a *string* it collapses two different silences ("matches no target" and "belongs to a repo you haven't checked out") into one, and the second isn't an unknown at all: it has a correct answer, use the pin. `DuExpand.fs` is where that thread already lives, and its *"independent local actions commute into a global effect"* is exactly what a multi-repo affected-set needs — the union of per-repo carves must not depend on visit order. The same invariant as the in-flight commutativity work, one layer up.
