## Description

The backend-store and "what would make these fully tested" pass Aaron asked for. Doc only — no manifest changes.

## Three findings

**1. Ten upstream chart tests exist and none has ever run.** Pulled all 32 charts at our exact pins: thirteen ship test templates, ten are real runtime `helm test` hooks — nats does a request/reply round-trip, cockroachdb a client connect, vault a server probe, valkey the auth path. ArgoCD renders with `helm template` and maps only a subset of Helm hooks onto its phases; `helm.sh/hook: test` is not in that map.

The repo already knew this sentence — PR-13373's review and the forgejo work item both note that such a Pod is one "ArgoCD never applies on sync". Both times it was cited to explain why the Pod contributes **0** to a resource budget. Nobody followed it to the other consequence.

**So the tests Aaron proposed writing are mostly already written, upstream.** The missing piece is a carrier.

**2. The carrier — including a correction to my own first draft.** I initially wrote "don't use PostSync", citing cockroachdb's deadlock note. Reading that note properly, it doesn't apply here:

> A PostSync hook that **produces** the health it waits on deadlocks.
> A PostSync hook that merely **observes** health does not.

`cockroach init` produces health (measured: 38 minutes of 503s). A test observes it. The real obstacle is *ownership* — the Pods are rendered upstream and `helm.valuesObject` can't annotate an arbitrary rendered resource — which is what makes the Argo-tool route cleaner. We already run argo-workflows 2.0.3 and argo-rollouts 2.43.0.

**3. `zeta-backups` is a bucket with no writer.** seaweedfs creates five buckets; four are consumed. Longhorn's `backupTarget` and `backupTargetCredentialSecret` are both unset. 24 Applications hold **1,168 GiB** of PVCs, none backed up.

The one-line fix is unsound three ways and is **not** taken here: 20Gi target against 1,168 GiB (58×), on unreplicated `zeta-local-path` so backups would be *less* durable than their sources, in the same failure domain. Filed with a `LIFTS WHEN` instead.

## A correction kept visible

An earlier pass listed argocd and spire as S3 consumers. That came from a loose `grep -E 'seaweedfs|s3:'` that matched a **comment** in spire's file about mimir's S3 auth, and matched nothing real in argocd's. Both are PVC-only, correctly so. Left in the doc rather than silently fixed — a grep answers "does this string appear", never "is this wired".
