## Description

## What

Ownership under `~zeta` and `/etc/zeta` is right by construction after a USB install. Found on a real bare-metal reinstall (node-5b2dfa).

## Root causes (measured on the live node, read-only)

1. **UID/GID resolution could never succeed.** `sudo chroot /mnt id -u zeta` resolves `id` through the live ISO's PATH, and every entry on it is under `/run`. `/run` is a tmpfs that does not exist inside `/mnt` until the installed system boots. Every install printed `WARN: could not resolve zeta UID/GID ... falling back to 1000:100`. The guess happened to be right (`id zeta` on the node gives `uid=1000 gid=100`), so nobody noticed the resolution was broken.
2. **`~/.kube` was `root:root 0750`.** It was created at 23:20:10 on first boot, which is exactly when `zeta-creds-to-k8s.service` ran (journal). That unit runs as root with `HOME=/home/zeta`, and `k3s kubectl` writes its discovery cache to `$HOME/.kube/cache`. The installer never touches `~/.kube`.
3. **`git -C /etc/zeta …` as zeta failed with "detected dubious ownership".** `/etc/zeta` is root-owned, and the system gitconfig had no `safe.directory` entry for it.

Everything else under `~zeta` was `zeta:users` on the live node. `.kube` was the only root-owned path.

## Fix

- `zeta_resolve_home_ids` reads `/mnt/etc/passwd`, which nixos-install's activation has already written. If that fails it uses the owner of `/mnt/home/zeta` as a second witness, and it never accepts a root-owned home as that witness. If neither works it refuses rather than guessing. The function is a marked block, tested in real bash.
- One `chown -R $ZETA_UID:$ZETA_GID $ZETA_HOME` sweep runs after the last installer write under the home, so a step that forgets its own chown can no longer leave a root-owned path. File modes are untouched.
- `zeta-creds-to-k8s.nix`: `HOME` is now the unit's own `StateDirectory`. The operator's home is still passed explicitly with `--home`, and `MISE_DATA_DIR` keeps the bun shim fallback working. tmpfiles `d` + `Z` rules re-own an existing `~/.kube` on nodes that were already installed.
- `common.nix`: `/etc/zeta` **stays root-owned**, for three reasons. Root evaluates and activates it, it holds root-only files (`initial-hashedpassword`), and a flake the unprivileged user could write is a way for that user to become root. It is declared as a system-wide git `safe.directory`. git's check protects you from a *less* privileged owner, and trusting root costs nothing.

## Red → green

`src/Core.TypeScript/installer/home-ownership-shell-parity.test.ts`: 11 tests. All 11 fail on `origin/main` and all 11 pass with this change. They cover resolution from passwd fixtures (exact-name match, malformed entry, home-dir witness, refusal), the removal of the chroot call, the sweep being the last write under the home and sitting inside the home-exists gate, the creds-to-k8s `HOME`, the tmpfiles repair, and the `safe.directory` declaration.

## Not verified

- No nix evaluation was run locally (there is no nix on this host). `programs.git.config.safe.directory` and the tmpfiles `Z` rule are checked only as text.
- No install on real hardware or in QEMU. The live node has not been rebuilt, so its `~/.kube` repair has not been observed.
- `zeta-creds-restore.service` also runs as root with `HOME=/home/zeta`. On this node it exited early (no ESP blob), so it wrote nothing. I have not proven that it never writes anything under `$HOME` as root.
