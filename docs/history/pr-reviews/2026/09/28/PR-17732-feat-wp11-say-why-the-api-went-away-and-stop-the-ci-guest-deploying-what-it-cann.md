## Description

## Why

WP11 run 36364782876 lost its API server at about 157 pods. 14 of 62 roster probes failed, and by the end `127.0.0.1:6443` was refusing connections while `k3s.service` still showed active. The serial log had **no journal or kernel lines**, so four possible causes looked identical: a k3s restart loop, an etcd stall, an OOM kill, and reclaim thrash.

## 1. Diagnosability (`zeta-first-boot-k3s-verify.nix`)

The unit now captures evidence at two points: the **first** failed roster probe or `pods -/-` listing, and again **at the end**. It captures:

- k3s `NRestarts` and state
- `free -m`
- PSI for cpu, memory and io
- kernel OOM lines
- live cgroup protection: cpu.weight and memory.low/min/current for system.slice, k3s.service and kubepods.slice. This lets the next run show whether #17728 reached the kernel.
- the last 200 lines of the k3s journal

Each capture ends in one of three states, `captured`, `failed` (the section is named with its exit status), or `did-not-run`. An unreadable kernel log counts as `failed`, never as "no OOM found". Both captures go to serial and into the verdict JSON as `pressureDiagnostics`.

## 2. CI envelope (`zeta-wp11-ci-envelope.nix` + `k8s/wp11-ci-envelope.json`)

**Decision: exclude from the CI guest, not enlarge it.**

- The hosted runner has 16 GiB and the guest already uses 12 GiB.
- Nothing has measured whether QEMU plus the runner fit if the guest grows.

**What is excluded, and why:** `gitlab`, `temporal` (including its CNPG Postgres), and `game-hosting/gmod`.

- These three landed the day the lane collapsed (#17711, #17718, #17708).
- At the metal rung they request **10533 MiB / 4875m / 24 pods**. That is more than the guest's entire allocatable (9228 MiB / 3250m).
- The dev/CI kind lanes already exclude the same three for the same substrate reason (`DEFAULT_ROOT_DEV_CATALOG`).

**How it works:**

- It only acts on a guest that has the WP11 marker, and only before k3s first starts.
- It writes a copy of the root Application with `directory.exclude` added, plus a k3s `.skip` file for the original. The `.skip` mechanism is documented in k3s's "Auto-Deploying Manifests".

**Safety:**

- **A real install has no marker, so it deploys everything unchanged.** Without the marker, the unit removes only files that carry its own tag.
- If it cannot anchor on the root manifest's shape, the unit **fails and writes nothing**, and the full roster deploys.

**Visibility:** Verdict 7 prints the exclusion, and the JSON carries it as `ciEnvelope`.
