## Description

## Defect

Live on node-5b2dfa (2026-09-27): `game-hosting/gmod-0` sits at 1/2 in CrashLoopBackOff. The game container is fine after #17708. The `sftp` sidecar (atmoz/sftp) exits 1 on every restart:

```
cat: can't open '/home/gmod/.ssh/keys/*': No such file or directory
/usr/local/bin/create-sftp-user: Error on line 90: cat "$publickey" >> "$userKeysAllowedFileTmp"
```

**Root cause:** the keys volume is the ConfigMap `gmod-sftp-keys` with `optional: true`. A fresh install has no such ConfigMap (checked read-only: `game-hosting` holds only `kube-root-ca.crt` and `ziti-controller-ctrl-plane-cas`), so the mount is an empty directory. atmoz's `create-sftp-user` requires at least one key there. A sidecar that crashes keeps the pod, and so the StatefulSet, unready.

## Fix: SFTP is opt-in

The sidecar now runs a small `sh -c` gate:

- **No key file** under `/home/gmod/.ssh/keys`: it logs `SFTP disabled ...` and polls every 30 s. The pod goes 2/2 Ready and nothing listens on :22. Dotfiles are ignored because the glob `*` skips ConfigMap bookkeeping entries like `..data`.
- **A key file appears**: it runs `exec /entrypoint gmod::1000:1000`. This is the same key-only user spec as before.

**Operator step to enable SFTP** (also written in the manifest comment):

```
kubectl -n game-hosting create configmap gmod-sftp-keys --from-file=operator.pub=$HOME/.ssh/id_ed25519.pub
```

The kubelet copies the new ConfigMap into the running pod within its sync period. `kubectl -n game-hosting delete pod gmod-0` makes it happen immediately. The ConfigMap is not in the Application's `directory.include`, and `prune: false`, so ArgoCD will not remove it.

The #17708 securityContext and the #17709 decision to leave out ServerSideApply are unchanged.
