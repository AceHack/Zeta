## Description

## What

The operator's dev toolchain now installs **after first boot**, in the background and under a time bound. It no longer holds the USB install before the reboot.

## Root cause (measured on the 2026-09-27 bare-metal reinstall, node-5b2dfa)

`zeta-install.sh` ran `ZETA_HOST_TIER=full tools/setup/install.sh` before rebooting. At tier `full` that is ~18 mise toolchains and several GB. It had up to 3 attempts with no time bound, and its output was hidden behind `| tee log | tail -40`. On that reinstall the console sat silent for about 30 minutes. k3s, ArgoCD and the roster need none of it.

## Change

- **`zeta-dev-toolchain.service`** (`nixos/modules/zeta-dev-toolchain.{nix,sh}`, imported by `common.nix`):
  - A **timer** starts it (`OnBootSec=2min`). A oneshot wanted by `multi-user.target` would hold back reaching that target.
  - Ordered after `network-online.target`. Runs `install.sh` as the operator via `runuser`.
  - `Nice=19`, `CPUSchedulingPolicy=idle`, `IOSchedulingClass=idle`, so it cannot compete with k3s's first boot.
  - Bounded twice. Each attempt has its own timeout (3600s; a hang ends as a named `rc 124`). The whole unit has `TimeoutStartSec`, and if systemd kills it, `ExecStopPost` reports the kill by name.
  - Keeps what the installer had: the same idempotent retry (3 attempts), the durable `~/.zeta/install-sh-firstboot.log`, the `PARTIAL-PROVISION` marker, and the `ZETA-INSTALL-FAILURE-CAUSE` classifier, moved verbatim.
  - Runs once: `ConditionPathExists=!~/.zeta/dev-toolchain.ok`. A failed run leaves no stamp, so the next boot retries it.
- **`zeta-install.sh`** keeps one bounded pre-reboot step: `mise install bun` (600s). The installer's own TypeScript helpers (wifi→NM converter, iSerial probe, keyfile writer, credential picker, bao/seal) and the first-boot credential units resolve the repo-pinned bun. The completion banner now says the toolchain continues in the background, and gives `journalctl -u zeta-dev-toolchain -f`.
- **QEMU harness, moved assertion:**
  - The phase-1 contract now requires positive evidence that the installer deferred the toolchain. It fails if `install.sh` ran before the reboot, and fails if the bun bootstrap failed.
  - The installed-disk serial carries `zeta-dev-toolchain: START / SUCCEEDED / FAILED`. `classifyDevToolchain` maps it to `succeeded | failed | did-not-run | running`.
  - On the **WP11** lane (the only first boot with a network), the harness waits up to 1200s after the k3s verdict and requires `succeeded`. That step's timeout goes from 100 to 120 minutes.
  - Lanes whose installed disk boots offline log the state as DORMANT, which is not a pass.
- Registered the new `.sh` in the bash-retirement inventory as a host-service wrapper. The unit that installs bun cannot itself run on bun.

## Red → green

- `src/Core.TypeScript/installer/dev-toolchain-post-boot.test.ts` (17 tests): no executable installer line invokes `install.sh`; the bun bootstrap is `timeout`-bounded and installs only bun; the unit is declared with `TimeoutStartSec`, `ExecStopPost`, Nice/idle scheduling, after network-online, timer-started, and imported by `common.nix`. The runner is **executed** in real bash with a stub `runuser` and a fake `install.sh`, covering: succeeded, failed after retries, recovered on retry, named cause, named per-attempt timeout, and stop-post naming a systemd timeout while staying silent after an ordinary failure. On `origin/main` the file fails because none of this exists.
- `qemu-full-install-test.test.ts`: tests for the new contracts, plus marker-to-producer coupling for both scripts.

## Not verified

- **No real boot.** The unit has not run on metal or in the WP11 QEMU lane, which only runs on dispatch or schedule. The ~1200s wait and the 120-minute step budget are estimates.
- Assumptions I have not observed:
  - `mise install bun` creates `~/.local/share/mise/shims/bun`, which `zeta-creds-restore` checks as a precondition.
  - The agent services (otto, vera, lior) tolerate a delay before their CLIs exist.
- Nix evaluation was not run locally; `build-iso`'s `nix flake check` covers it in CI.
