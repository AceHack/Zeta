## Description

## Why

WP11 run 36364782876 (4 vCPU / 12 GiB guest, ~157 pods) lost its apiserver partway through. Pod probes timed out, all 44 ArgoCD apps reported `failed to get server version`, and by the end `127.0.0.1:6443` was refusing connections while `k3s.service` still showed active. That serial log has no journal or kernel lines, so **which mechanism fired is not known**. The WP11 diagnostics change (work item 081M3K1K1XV087G0R002A6YFRS) will capture that on the next run.

This PR closes three mechanisms. Each was measured open on the live metal node (node-5b2dfa: 22 cores, 62 GiB, freshly reinstalled; read-only):

| measured | value |
|---|---|
| `kubepods.slice` cpu.weight vs `system.slice` | **830 vs 100** (pods outweigh every system service, k3s included, 8.3:1 under contention) |
| memory.min / memory.low on `k3s.service` and `system.slice` | **0 / 0** |
| containerd `oom_score_adj` (k3s-server: -999) | **0** |
| k3s-server RSS vs `kube-reserved` memory | **3.1 GiB vs 1Gi** |

On k3s, the apiserver, embedded etcd (`--cluster-init`), kubelet and containerd all run in `k3s.service`, outside `kubepods.slice`. #17666's reservations only affect accounting, as its own comment says.

## What

New `k3s-process-protection.nix`, imported by `k3s-server.nix` and `k3s-agent.nix`:

- **MemoryLow on `k3s.service` and `system.slice`.** The host's cgroup2 mount has no `memory_recursiveprot`, so the parent slice has to carry the protection too. The value equals the role's `kube-reserved` memory (server 2G, agent 512M). It is soft protection, not `MemoryMin`. etcd's bbolt is a file-backed mmap, which is exactly what reclaim takes first.
- **CPUWeight 1000 on `k3s.service` and `system.slice`.** This only takes effect when the CPU is saturated. It beats the kubelet-computed kubepods weight on both the 22-core node and the WP11 guest.
- **OOMScoreAdjust -999.** This is the kubelet's own value, and it now also reaches containerd.
- **kubelet `registry-qps=20` and `registry-burst=50`** (defaults 5/10, which caused `pull QPS exceeded` on first boot). Pulls stay **serialized**: kubelet 1.35 has no `--max-parallel-image-pulls` flag (checked in `cmd/kubelet/app/options/options.go`), and k3s documents no kubelet config drop-in. Unbounded parallel unpacking inside `k3s.service` on 4 vCPU is the contention this PR is meant to prevent.
- **`eviction-soft` `memory.available<1Gi` for 1m, with max pod grace 60s**, ahead of the hard 500Mi.
- Server **kube-reserved memory 1Gi → 2Gi**.
- **Not set: IOWeight.** The disks run the `none` scheduler, where `io.weight` does nothing. Setting it would add a knob with no effect.

## Red → green

`k3s-process-protection.test.ts` first checks the kubelet's shares→weight formula against the **measured** 830. Then it asserts the invariants.

- **RED:** with main's role files, 5 of 13 checks fail. Neither role imports the protection or sizes MemoryLow to kube-reserved, and server kube-reserved is 1Gi. On main the module itself does not exist.
- **GREEN:** 13 of 13 pass.

## Not verified

- A boot. Whether this is enough to keep the WP11 guest's API up is for the follow-up WP11 dispatch to measure.
