## Description

## Why

#17711 set `upgradeCheck.enabled: false` on the gitlab Application because the chart's `pre-upgrade` hook deadlocks ArgoCD's first sync. That also removed the guard against chart bumps that skip a GitLab required upgrade stop. Under GitOps an upgrade only ever happens through a PR that moves the chart pin, so this PR puts the check on the PR.

## How the verdict is computed

`src/Core.TypeScript/cluster/gitlab-upgrade-path-guard.ts`:

1. Reads the gitlab Application at the PR base and at HEAD (`git show <rev>:<path>`).
2. If the pin (repoURL, chart, targetRevision, `global.gitlabVersion`) is unchanged, or the Application is missing on either side: **NOT APPLICABLE**, and helm is never called.
3. If the pin changed: `helm template --show-only` renders the **old** pin's `chart-info` ConfigMap (what the cluster holds after the last sync) and the **new** pin's upgrade-check ConfigMap and Job (with `upgradeCheck.enabled` forced on). The Application's own values are used both times. It then runs the new chart's `runcheck` offline with `sh`, with a synthetic `/chart-info` that holds the old `gitlabVersion`/`gitlabChartVersion` and the Job's env (`GITLAB_VERSION`, `CHART_VERSION`). **The script's exit status is the verdict, and its stdout is the failure message.** GitLab's upgrade-stop table is not reimplemented.
4. **Downgrades fail.** I measured that the chart's script allows them (8.6.0's runcheck only requires that the old release be >= 17.5), so this is the one comparison the guard makes itself: plain version order.

The CLI prints PASSED, FAILED or NOT APPLICABLE. It exits 1 only on FAILED, and exits 2 when it could not run. Chart archives are cached in `.helm-render-cache/`, the same convention `rendered-storage-claims.ts` uses.

It runs in `helm-validate.yml` → `charts` job (helm is confirmed on PATH there) on `pull_request` only, against `pull_request.base.sha`, which is fetched shallowly. The test suite runs in the same job.

## Not verified or out of scope

- The guard is only as strong as the chart's own script. Each chart release encodes one minimum previous version, so the guard is exactly as strong as the in-cluster hook it replaces, and no stronger.
- Per-component image-tag overrides are not read. Only `global.gitlabVersion` or the chart appVersion is used, and that is also all the hook reads.
- The PostgreSQL-secrets branch of the script is not exercised (the secrets dir is pointed at a path that does not exist).
- The chart-script tests need network on the first pull. They skip loudly when helm is not on PATH.
- The CI step has not been observed on a PR that actually changes the pin. This PR only edits a comment, so the step will report NOT APPLICABLE here.
