## Description

## Why

On the live USB install (node-5b2dfa), temporal was stuck at Synced/Degraded while it pointed at CockroachDB. PR #17707 seeded a password, but that could not fix it, for three reasons:

1. CockroachDB had no `temporal` SQL user that carried that password.
2. CockroachDB only accepts TLS, and its CA was in another namespace.
3. temporal v1.27.2's SQL visibility schema runs `CREATE EXTENSION btree_gin` and uses a plpgsql UDF inside `GENERATED ... STORED` columns. CockroachDB supports neither (cockroach#51992, #122945).

Temporal tests PostgreSQL for both stores, and the CloudNativePG operator is already Synced/Healthy on metal.

## Design

- **`applications/temporal/postgres/`**: a new directory-source Application `temporal-postgres`, sync wave **5**.
  - A CNPG `Cluster` `temporal-postgres`:
    - PG 17 image `ghcr.io/cloudnative-pg/postgresql:17.11-minimal-trixie`
    - `bootstrap.initdb` creates database `temporal`, owned by role `temporal`
    - `max_connections` is 200
    - requests 250m/512Mi
    - 10Gi on `zeta-block-local`
  - A CNPG `Database` `temporal_visibility`, same owner, `btree_gin` ensured present. The `Database` CRD exists on the installed CNPG 1.30; I checked this read-only on the node, where no Cluster exists yet.
  - The directory sits under `temporal/`, so the dev `temporal/**` exclude defers the database together with its only consumer.
- **Credentials have one source.** Both stores use `existingSecret: temporal-postgres-app`. CNPG generates that Secret and sets the same password on the role; the chart reads key `password`. The #17707 `seed-temporal-store` Job and its namespace are removed, so there is no second password that could drift.
- **TLS:** `tls.enabled: true, enableHostVerification: false` gives `sslmode=require`, confirmed in temporal v1.27.2 `session.go`. The connection is encrypted but the server certificate is not verified. The reason: `temporal-postgres-ca` also holds `ca.key`, and mounting that Secret into every temporal pod would expose the key. The exit condition is written in the header.
- **Schema:** `schema.createDatabase.enabled: false`, because CNPG creates both databases. The chart's setup and update init containers use the `postgres12` schema dirs and retry (backoffLimit 100) until the primary accepts connections.
- **Storage is node-local on purpose.** CNPG replicates at the PostgreSQL level and recommends local volumes, and a single node has nothing to replicate to. This keeps the volume out of the Longhorn pool and the installer's refusal constants. The one constant that moved is the local-path advisory, 220 → 230 GiB (TS and `zeta-install.sh`).
- **Sync order:** cloudnativepg (-70) < temporal-postgres (5) < temporal (10). The graph now declares `temporal -> temporal-postgres -> cloudnativepg`; the `temporal -> cockroachdb` edge and its adjudication are removed. CockroachDB itself stays.

## Checker changes this needed

- `metal-secret-production.ts` has a new **operator-generated** producer class, `collectCnpgClusters`. It derives `<cluster>-app`, its namespace, owner, databases and `-rw` hosts from committed CRs that some Application actually applies.
- `secret-reference-audit.ts` knows the same thing at name level.
- `rendered-storage-claims.ts` and `rendered-resource-requests.ts` now read a CNPG Cluster's `spec.storage` / `spec.resources` as the PVC and pod its operator creates. Without this, the instance counted as 0 GiB and 0m.
- Snapshots, the resource ladder row and the budget prose were re-measured.
- A harness defect showed up (`applied-vs-asserted-agreement`): a nested Application under an excluded dir was still asserted, even though ArgoCD's `<dir>/**` drops it. Fixed in `isExcludedFromIncludedProof`, `auditAppliedButUnasserted` and `devLaneAppliedDirs`. Also, `applicationDirs()` skipped the children of a directory that has its own Application.

## Red → green

`src/Core.TypeScript/cluster/temporal-datastore.test.ts` fails all 3 tests on origin/main and passes here:

- **(a)** both stores use a Postgres plugin and point at a CNPG `-rw` host that some Application creates, and the database is owned by the login user.
- **(b)** the Secret temporal reads is operator-generated on metal, with the key the chart reads, owned by the same role. Nothing else seeds a second copy.
- **(c)** sync waves order cloudnativepg < the Cluster's Application < temporal.

Across `src/Core.TypeScript/cluster`, the only failures left are the ones that also fail on origin/main on Windows. `local-checks.ts` fails only the listed pre-existing Windows classes (tempo chart-currency, graphql lint, mathjs, twitch-ai build, light-time, 7-lang toolchains, a gh-api drift probe).

## Not verified

- Nothing was synced on metal, so convergence on a live cluster is unproven: the Cluster becoming Ready, the schema Job succeeding, and temporal going Healthy.
- `btree_gin` being present in the `minimal` image is reasoned (Debian's contrib is part of `postgresql-17`), not measured.
- The postgres image is not in the image audits. `image-footprint` and `image-source-provenance` read `image:` keys, and CNPG spells it `imageName`. This is noted in `cluster.yaml`.
- Server certificate verification is off (see TLS).
