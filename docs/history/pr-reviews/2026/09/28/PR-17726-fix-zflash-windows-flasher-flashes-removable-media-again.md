## Description

## Defect

`src/Core.TypeScript/zflash/flash-usb-windows.ts` ran `Set-Disk -Number N -IsOffline $true` before the raw write. Windows refuses that for removable media (`Set-Disk : Not Supported ... Removable media cannot be set to offline`, reproduced 2026-09-27 on a PNY USB 3.2.1 FD, disk 3), so the flasher aborted on every USB stick. #6981 (db4f8f274e) had a removable-media path; the #8076 refactor dropped it. Work item: `081M3K29CQM087G0R000B5ZV3N`.

## Design

For every target, after the existing rails (USB-only selection, boot/system refusal, size bounds, `establishIsoIntegrity` manifest gate, confirm phrase):

1. **Stage a verified copy.** Copy the ISO into a fresh `mkdtemp` directory, hashing as it copies. The hash must equal the sha256 the integrity gate established, so the bytes baked and written are the bytes that were verified. The copy is removed on every exit path.
2. **Bake the ESP payloads into the copy.** The new `esp-fat-writer.ts` is pure TypeScript with no mtools and no mount. The ESP is the MBR `0xEF` partition with start > 0; there is no guessed fallback offset. It handles FAT12 and FAT16, and generates 8.3 aliases with numeric tails plus VFAT LFN entries. Multi-cluster chains are written into every FAT copy. Timestamps are the FAT epoch, so bakes are deterministic. An existing name is refused, never overwritten. Every file is read back through every FAT copy and compared. The payload list comes from the shared planner (`planFileBackedZflashImage`), so Windows bakes the same files as the other arms: pubkey, `--host`, `--role`/`--flake-host`/`--join-server-url`/`--join-token`, `--acme-email`/`--public-domain`, and `--repo-pin`. Flag validation uses the device CLI's validators.
3. **Prepare the disk.** Run `Set-Disk -IsReadOnly $false`, then `Clear-Disk -RemoveData -RemoveOEM -Confirm:$false`. There is **no offline** and **no `mountvol /N`**.
4. **Raw-write.** Write everything past the first 1 MiB first, and write the first 1 MiB (the partition table) **last**. Then fsync.
5. **Read back.** Read exactly the written range back from the device and compare its sha256 with the baked image. A mismatch exits 1.

The stale fork `full-ai-cluster/tools/flash-usb-windows.ts` is **deleted**. Its divergence test failed as designed once the canonical copy changed ("the delete/dedupe question has to be reopened"), and the fork still carried the offline defect. Its README moves to `src/Core.TypeScript/zflash/README-flash-usb-windows.md` and documents the new flow. If the fork should stay, reverting that one deletion re-arms its tests.

## Red → green

- New `flash-usb-windows-removable.test.ts` covers:
  - disk prep issues read-only-clear then Clear-Disk, with no `IsOffline` and no `mountvol`, against a fake runner that refuses offline the way Windows does;
  - partition table last, checked on a fake device file at the moment of the head write;
  - read-back: a flipped byte, dirty padding, or a short device each fail;
  - a staged copy whose hash does not match is refused;
  - the ESP writes equal the shared planner's for the same flags;
  - end-to-end on temp files.
- New `esp-fat-writer.test.ts` builds a fixture shaped like the real ISO ESP (LBA 276, 6144 sectors, FAT12 `EFIBOOT`, spc 4). It checks the result with an **independent** FAT parser (`test-harness/isohybrid-esp-fixture.ts`) covering directory entries, checksum-verified LFN, and the cluster chain in both FATs. It also covers multi-cluster files, alias collisions, FAT16, and refusals (existing name, no 0xEF, FAT32, ESP full).
- Both files are red on `origin/main` (the new module and exports do not exist there) and green on this branch: 71 tests across the two Windows test files, plus 15 FAT tests. `bun run typecheck` is clean, and `audit-flash-entrypoint-parity` is OK.
- One-off hand cross-check: I baked the key into the real `zeta-installer-26.05-x86_64-linux.iso` with `esp-fat-writer.ts`. The resulting ESP was byte-identical to what mtools produced for the same key, except for the directory timestamps.

## Not verified

- No real flash was done. Nothing here opened `\\.\PhysicalDriveN` or ran the real `Clear-Disk`.
- Nothing shows whether Windows touches the disk between the tail write and the head write.
- Nobody has booted a stick flashed this way.
- Fixed (non-removable) USB disks now take the same Clear-Disk path, with no offline. This is untested on hardware.
- `injectPubkeyIntoEsp` (the post-write mount ladder) and `flash-and-inject.ts` (which still uses `mountvol /N`) remain in the tree unused by this arm and could be removed in a follow-up.
