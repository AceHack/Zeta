## Description

## What

PR #17722 found that the three `atmoz/sftp:alpine` sidecars in `full-ai-cluster/k8s/applications/platform/blueprints.yaml` (`gmod`, `unturned`, `arma-reforger`) are rendered by `platform-controller/src/blueprint.ts` with no args, meaning no user spec, and no keys mount. atmoz's `create-sftp-user` needs a user spec. For a key-only user it runs `cat /home/<user>/.ssh/keys/*` under `set -Eeo pipefail`, which fails when the directory holds no key. So the sidecar crash-loops and every game-server pod stays unready.

This PR applies #17722's opt-in pattern to the rendered sidecars.

- **Engine (`blueprint.ts`):** a new generic `sidecar.configMaps` field: `{ name, mountPath, optional }[]`.
  - Each entry is mounted read-only.
  - `name` is templated with `${VAR}`.
  - The mounts are rendered on both StatefulSet and Deployment pods. The old `data-extra-cm` placeholder and `stripPlaceholder` are gone. A StatefulSet still gets its data volume only from `volumeClaimTemplates`.
- **Library (`blueprints.yaml`):** each sftp sidecar now:
  - mounts the **optional** per-server ConfigMap `${RESOURCE_NAME}-sftp-keys` at `/home/zeta/.ssh/keys`;
  - runs a `sh -c` gate that logs `SFTP disabled … waiting` and idles while that directory holds no key file. ConfigMap `..data` is a dotfile, so `*` does not match it;
  - runs `exec /entrypoint zeta::<uid>:<gid>` once a key appears.
- **Users:**
  - **99:100** for gmod and unturned. This is the data owner: the ich777 `start.sh` runs `chown -R ${UID}:${GID} ${DATA_DIR}`, and the image config defaults are UID=99, GID=100.
  - **1000:1000** (the pod fsGroup) for arma-reforger. The acemod image has no `User`, so it runs as root and its files are owned 0:0, and SFTP should not be served as root. Read access works through the group. **Write access to files the game created is not guaranteed.**
- atmoz `create-sftp-user` (master) accepts a non-unique uid and creates a missing gid group, so `99:100` is a valid spec on alpine.

To enable SFTP on a server:
`kubectl -n <ns> create configmap <name>-sftp-keys --from-file=operator.pub=$HOME/.ssh/id_ed25519.pub`

## Red, then green

New describe block in `blueprint.test.ts`. Like `gmod-sftp-keys.test.ts`, it **runs** the rendered sidecar script under `sh`. atmoz's `/entrypoint` is replaced by a stub that fails the way atmoz does (no user, or an empty keys directory), and `sleep` is replaced by a marker that ends the run, so the test uses no timers. For each blueprint it asserts:
- the keys come from an optional ConfigMap mounted read-only;
- the data is still served at `/home/zeta/data`;
- with an empty keys directory the sidecar idles and never reaches atmoz;
- a directory holding only `..data` still idles;
- once a key is present, atmoz starts with `zeta::<owner>`.

- Base branch (after #17729): **12 fail**.
- After the fix: platform-controller, k8s-manifests and portal blueprint-agent tests are 135/135.
- `bun test src/Core.TypeScript/cluster/` shows no failures that mention blueprints or sftp. Its failures are the known Windows-environment ones.
- local-checks: 9 failures, all on the pre-existing Windows list.

## Not verified

- No live pod was run.
- It is unchecked that sshd accepts a kubelet-created `/home/zeta/.ssh` holding the read-only keys mount. The gmod StatefulSet uses the same layout.
- It is unchecked that atmoz's chroot is happy with the data mount's ownership.
- arma-reforger SFTP write access is unchecked, as described above.
