## Description

`drift (loud)` on #17414 reported `drought`: last verdict 2026-09-05, 678 unverified
commits, ZERO gate runs since, "TRIGGER MAY BE BROKEN". Every part of that was false. Nine
minutes later the identical query returned a completed verdict from 2026-09-14T18:18, and
`gate.yml` on main was 37 success / 3 failure across its last 40 runs, all `event=push`. CI
had received a `?branch=main&event=push` page whose newest entry was ~10 days old, and the
fold turned it into a confident, specific, wrong claim.

WHY THE GUARD FOR THIS COULD NOT FIRE. `detectStaleWindow` exists for exactly this case and
its reasoning is correct -- absence only proves staleness if the caller SHOULD appear in the
listing. But it is gated on `selfIsInsideWindow`, which requires the caller to be a
push-on-main run of `gate.yml`, and `drift (loud)` runs on `pull_request`. So the guard is
structurally inert on the event the detector most often runs under, which is precisely when
a stale page becomes a false drought. The gap was never in that guard; it was the absence of
a witness for every OTHER event.

THE WITNESS HAS TO BE A DIFFERENT QUERY SHAPE. Reading the same listing twice was tried and
refuted: `per_page=1` and `per_page=60` returned the same newest run, because two reads of
one index can be stale together. Looking a run up BY HEAD SHA is a different index, so it is
a real second opinion:

  a gate run exists for main's newest commit and the window did not list it
    -> the WINDOW is stale. Register `unknown`, never `drought`.
  no gate run exists for that commit
    -> the trigger really did not fire, and `drought` is the honest answer.

`witnessRunForNewestMainCommit` returns `undefined` when the lookup itself fails, and the
caller then reports NOT MEASURED rather than treating "I could not ask" as "nothing is
there" -- the distinction this file already insists on everywhere else.

Mutation-verified in three directions, because a guard that cannot fail is the thing this
detector exists to catch:
  discriminator always false (the original bug)     73 pass  2 fail
  witness ignored, everything called stale          58 pass 17 fail
  stale window still registers drought              74 pass  1 fail
  control                                           75 pass  0 fail

Live against the forge after the change: register `ok`, last verdict run 34877216727
(2026-09-14T18:18), 2 commits and 2 gate runs since. `tsc --noEmit` rc=0 on an empty log.

WHY THIS ONE MATTERED MORE THAN ITS SEVERITY SUGGESTS. `drift (loud)` is not in the
`gate (required)` floor, so nothing was blocked -- but the gate WORKFLOW's conclusion is red
whenever any job in it fails, so one false alarm turned the whole workflow red on a PR whose
floor had passed. A reader who checks that once and finds it false learns to skim it, and
this is the detector whose entire job is telling real silence from apparent silence.

NOT made `continue-on-error`. The file already refuses that for the right reason: the defect
was a wrong ANSWER, not an inconvenient one.

Fixes the false alarm seen on #17414.
