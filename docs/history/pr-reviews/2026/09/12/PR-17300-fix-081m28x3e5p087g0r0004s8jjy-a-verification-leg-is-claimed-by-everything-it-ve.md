## Description

Closes `081M28X3E5P087G0R0004S8JJY` — the one thing #17293 left open, done the long-term way rather than patched.

## The rule

> **A verification leg cannot be derived from "which targets produce this artifact". It must be claimed by everything it VERIFIES.**

A verifier exists to catch changes that *do not declare themselves*, so deriving its trigger from declarations is circular: the change that most needs the verifier is exactly the one that won't turn it on.

## What was wrong

`gate/full-verify` was claimed by **4 of 121** targets — `rust:Core.Rust.Observe`, `ts:cross-verification`, `unit:go`, `unit:python` — while the job installs and smoke-checks **seven** toolchains (`bun, python3, go, rustc, cargo, dotnet, java`) and runs the 7-language IR byte-lock over `src/`. All 59 dotnet targets, 35 of 36 Rust crates and the Q# oracle claimed nothing.

An F#-only change that **broke** the byte-lock would not have turned the leg on.

## The fix is in the graph, not in `gate.yml`

`attachTreeWideVerifiers` is a post-pass over the merged target list. **4 → 106 of 121**, and `full-verify` now gates on its leg instead of the `code` path regex — strictly more precise, and derived rather than hand-written.

A post-pass rather than edits across five derivation functions, because that scattered shape is *why* the graph has already been wrong three separate ways (2026-08-19: `lint-fsharp`/`lint-csharp` claimed by no target, 35 Rust crates invisible, a Lean leg naming a job that doesn't exist).

The 15 exclusions are two **measured** classes:

| excluded | why |
|---|---|
| the 10 synthetic `leg:` rows | tree/file-type properties, not builds. Attaching a verifier to `leg:markdown` would run the seven-toolchain build on every docs change — the cost this mechanism exists to avoid |
| `agda`, `alloy`, `tla`, `lean` | full-verify's nineteen steps neither build nor run them; each has its own workflow or none |

## Two defects the mechanism caught in this change's own implementation

**1. Over-claiming against measured evidence is not caution.** The first draft attached the verifier to Agda/Alloy/Lean because the job installs `java` and nobody had measured otherwise. `audit-build-graph-completeness.ts` refused it — those rows are *rostered* as uncovered with reasons on file. Over-claim-when-uncertain governs **uncertainty**, not contradicting a finding, and it would have pinned the selector in full mode for changes that provably need nothing.

**2. A deriver may not disagree with itself.** The first pass was add-only. `deriveGraph` preserves declared rows verbatim, so a leg written once became an input the next time and could not be taken back: after narrowing the scope, `derive` reported *"already current"* while the completeness audit still refused three rows. The pass is now authoritative in **both** directions — strip every tree-wide verifier, re-add where it belongs — so it's a total function of its sources and idempotent against its own output.

## `cross-verify` stays ungated — but the reason changed

Not "its leg under-claims". **No leg can express its scope.** It's 45 audits under one check name covering source, `.github/workflows/**`, dependency manifests, `workitems/**`, commit metadata and the archive tree. Several of those are **declared inert**, and an inert path produces no target — so there's nothing for a leg to attach to. Widening the graph can't fix that; splitting the matrix can.

**LIFTS WHEN** the matrix is selected per-audit rather than per-job. Each of the 45 has its own scope, and `ci/cross-verify-roster.ts` is where those would live.
