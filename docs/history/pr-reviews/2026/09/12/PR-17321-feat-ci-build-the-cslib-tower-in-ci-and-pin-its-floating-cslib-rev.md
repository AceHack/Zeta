## Description

## What

`src/Core.Lean4.Cslib` had **zero CI**. It was rostered UNCOVERED in
`audit-build-graph-completeness.ts` and carried `legs: []` in `ace/build-graph.json`, so
nothing selected it and nothing built it. Its lakefile pointed at "the opt-in workflow",
which did not exist.

> "we need this cslib — **all AI labs are contributing for AI research**." — Aaron

This gives it a real lane, a real leg, a pinned dependency, and two guards that fail when
the build produces nothing.

## 1. The pin — `rev = "main"` was live, not merely misleading

`src/Core.Lean4.Cslib/lakefile.toml` required cslib at `rev = "main"`.

| | |
|---|---|
| what `lake-manifest.json` had resolved | `e0573fbc08dbad14cd492736d5fe83fde0d83cf2` (2026-06-19, *"chore: bump toolchain to v4.32.0-rc1"* — matching this tower's `lean-toolchain`) |
| what upstream `main` points at today | `b777e0891698a7764e1387300eb0f9053b417b42` |

So the manifest was holding the tree still while the lakefile floated. Any `lake update`,
or any resolve with no manifest present, would have jumped ~3 months and a toolchain — the
failure `.claude/rules/clone-at-tag-stays-sufficient.md` and manifesto §7 (DST) exist to
prevent. **Pinned to `e0573fbc…` in both `lakefile.toml` and the manifest's `inputRev`.**
`lake update` against the pin produces no other manifest change, which is the check that
the pin is self-consistent rather than merely written down.

## 2. The measurement that made the roster's reason wrong

The roster said *"the lake cache is multi-GB"*. Measured locally (M-series, home link):

| | |
|---|---|
| **TRUE COLD** — no `.lake`, empty XDG cache, nothing but a checkout | |
| &nbsp;&nbsp;`lake exe cache get` (dep clone + 8564 archives + decompress) | **102 s** |
| &nbsp;&nbsp;`lake build` (cslib compiled from source, 2737 jobs) | **56 s** |
| &nbsp;&nbsp;**total** | **158 s** |
| **WARM** (`.lake` intact) — `lake build` | **2 s** |
| mathlib warm, cslib rebuilt from source | 74 s |
| `.lake` materialised | **7.4 GB** (6.3 GB mathlib oleans · 500 MB mathlib `.git` · 186 MB cslib's own build) |
| `~/.cache/mathlib` for this pinned rev | **430 MB** |

The size claim was **true and was being used to decide about time**. From absolutely
nothing the whole tower is 2m38s, because `lake exe cache get` downloads pre-built oleans
instead of compiling Mathlib.

The 7.4 GB is still load-bearing, in the opposite direction: it is **why this workflow does
not cache `.lake`**. A 7.4 GB entry is ~74% of GitHub's 10 GB per-repo cache ceiling and
would evict every other cache in the repo. What is cached is `~/.cache/mathlib` (430 MB),
the compressed archive the 6.3 GB is decompressed out of — and stated honestly, that cache
buys **availability, not many minutes**: the cold path is already 158 s, so the win is not
depending on the Azure blob store on every PR.

## 3. Its own lane, not the gate

`timeout-minutes: 45`, `actionlint` clean, **not** on `gate (required)`.

Its own workflow rather than a second job in `lean-proof.yml` because the two towers are on

third-party action.**

## 4. A job that builds nothing is worse than no job

Both guards were **mutation-tested locally**, not just written:

**Artifacts.** `CslibTower.olean` non-empty · cslib's own
`Cslib/Computability/Distributed/FLP/Consensus.olean` non-empty (the *dependency* built, not
just our five-line file) · ≥ 100 cslib oleans emitted (156 measured). Catches a `lake build`
that exits 0 having compiled nothing.

**A POSITIVE axiom audit**, through `run-checked.ts` and never a pipeline:

```
--require 'Cslib.FLP.Consensus.fault_mono'
--require 'Cslib.FLP.ZeroFaultAlg.consensus_zero'
--deny 'sorryAx'  --deny 'Unknown constant'
```

Those two are the declarations the **G1 Byzantine-fault lift** extends. An absence-only
audit passes when the subject fails to resolve — which is exactly how `lean-proof.yml` once
graded 13 `FinDataProcessing` names that resolved to nothing — so this one requires the
axiom lines to actually appear. Mutants checked:

| mutant | result |
|---|---|
| rename a declaration (simulates pin drift) | fails, naming the unknown constant |
| drop `import Cslib` (simulates a no-op build) | fails on the missing required pattern |

**And `CslibTower.lean` was itself the vacuity class.** Its entire content was
`theorem cslib_tower_smoke : True := trivial`, which compiles just as happily with
`import Cslib` deleted — so the file's own comment claiming it "proves the tower stands"
was false. It now `#check`s the same two FLP names, so **`lake build` fails on a dropped
import** (mutation-tested) for anyone building by hand, not only in CI. `#check` rather
than a term because both declarations are universe-polymorphic and a term-level reference
leaves universe metavariables; an unresolved name in `#check` is still an elaboration
error. It proves a name *resolves* and says nothing about its *proof*, which is why the
axiom audit stays.

**Two gate jobs went red, both legitimately, both fixed in the second commit:**

**`lint (structural hygiene)` — the unbounded-growth register.** `build-graph.json` crossed
its pinned ceiling of 49 at 50 commits, because this branch adds one `legs` line to it. The
row anticipated exactly this — *"the first crossing is the signal, and re-pinning costs one
line plus a re-measured rate"* — so it is re-pinned to 50 **with** the re-measurement:
1.7 versions/day over 29 days against 1.8/day at 49, i.e. **flat**; on-disk 38.1 KB across
48 blobs (0.8 KB/version, 105× smaller than raw). Nothing in the model changed, so the pin
moves by exactly one and stays tight.

**`lint (bash retirement …)` — the apt budget.** The new job runs `install.sh`, so it is a
*governed* job needing a row in `apt-job-timings.measured.json`. Added to `unmeasured` (the
sanctioned hand-edit surface, 14 precedents) because a p90 over one run is a p90 in name
only — and the entry **names the fallback as wrong** rather than leaning on it: the pre-apt
reserve is 120 s and this job's real non-apt work is ~303 s. `420 + 10 + 303 = 733 s`
against 2700 s, ~1970 s of margin. It passes on the 120 s fallback too, so the verdict does
not depend on which number is used — but what actually carries it is the timeout, and that
is now written down.

**Follow-up this exposes:** `install.sh` at `ZETA_HOST_TIER: full` is 103 s — a quarter of
the job — for a lane that needs elan and bun. The tier was declared `full` only because
`lean-proof.yml` declares it. Trimming it is a real measurement nobody has taken; recorded
in the workflow and in the timings row rather than guessed at here.

**And `local-checks.ts` caught neither**, which is worth knowing: the register step needs
`fetch-depth: 0` history, and the apt-budget assertion lives in the hygiene unit-test suite
that local-checks reports as *"1 not attempted (slow)"*. Its summary line is a floor, not a
gate preview — and it says so honestly.
