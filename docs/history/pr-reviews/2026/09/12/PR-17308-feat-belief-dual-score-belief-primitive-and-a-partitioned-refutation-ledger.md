## Description

## What

A **dual-score belief primitive** and its first consumer, a **refutation ledger**.

Aaron 2026-09-11, quoted in the module header because the wording is the spec:

> "refutations should also have a numerical score not just true false as well, probablities over true false is really an extension of keep uncertainy open, we should also track **true chance and false chance sepratly**, there is a lot of good data there **when they don't add up to 1, that is signal itself**, around false positives and negatives similar to our **dual bloom filter design**, we should let them **float independly of each other**."
>
> "this is the same for **any** true/false belief even our numeric claims."

That last line is why this lives in `src/Core.TypeScript/belief/` rather than inside the ledger. One primitive, many callers.

## The primitive - `src/Core.TypeScript/belief/dual-score.ts`

| | |
|---|---|
| `dualScore(trueChance, falseChance)` | the only constructor. **Refuses** non-finite and out-of-`[0,1]` legs; never clamps, never derives one leg from the other, and never constrains the **sum** |

### The bloom / anti-bloom echo is deliberate and cited

`docs/research/bloom-filter-frontier.md`, Assess row "Bloom vs anti-bloom (2026-09-05)" (`081M1T9SMM9087G0R002FS29S4`): two grow-only filters, three-valued `{present, absent, unknown}`, unknown region `fp(I) x fp(D)`, resurrection-in-both = UNKNOWN. The header carries the mapping table and states what does **not** transfer: a Bloom filter's FPR is analytic in `(m, k, n)` and its union is defined on bit sets; here the two chances are supplied by callers and there is no defined union.

### No combination rule ships, and that is the point

The algebra is **under review by the math team (Lumen)** against Dempster-Shafer, Jøsang subjective logic, Belnap's FOUR, Walley imprecise probability, and quasi-probability / Wigner negativity. **Dempster's rule is known-pathological under high conflict** - Zadeh's counterexample returns the diagnosis both experts thought nearly impossible - which is exactly the regime this type exists to preserve. Picking a rule now would be guessing.

So the module exports nothing named `merge` / `combine` / `and` / `or` / `fuse` / `normalise` / `consensus` / `join`, **and a test reads the module's own export list to keep it that way**. The one joining operation the ledger's briefing needs is `toyJoin` (componentwise max), and a test asserts its **limitation** - two weak independent witnesses stay weak under max, where a real fusion rule would strengthen them - so it cannot be quietly promoted.

The header states the open question plainly rather than answering it:

> `src/Core/WSet.fs` is already ring-generic - `'W = Z` (Distinct), `'W = C` (Born), `'W = R>=0` (EP projection), each with its boundary nonlinearity applied at the outer edge.
>
> 1. Is `(trueChance, falseChance)` a **fourth `'W`** for that calculus?
> 2. Is "regularize it to a belief" precisely that ring's **missing boundary nonlinearity**?

If (1) has an answer, the combination rule follows from the ring rather than from somebody's preference.

### Register discipline

No calibration study backs this file, so nothing asserts a calibrated threshold. `toyClassify` has **arity 2** and a test pins it - a default parameter would make it 1, and an uncalibrated default inherited by callers is the silent promotion `.claude/rules/toy-is-free-metered-must-be-earned.md` exists to prevent.

## The ledger - `db/refutations/YYYY/MM/DD/<32-hex ZetaId>.json`

Hypotheses **tried and disproven**, so a fresh context is told what not to propose. Three rows seeded from today:

1. `process.stdin.resume()` cannot keep a child alive under `stdio: "ignore"` - stdin is `/dev/null`, the read hits EOF immediately, and the ref is released in the same tick. `{trueChance 0, falseChance 0.97}`
2. Reading through a file handle does **not** close the `js/file-system-race` window on the lock's contended path - the alert is about the check-then-use pair, not the read API. `{0.05, 0.9}`
3. `fromJSON(...).leg != false` **skips** instead of running - GitHub casts both `null` and `false` to 0, so an absent leg reads as a disabled one. `{0, 1}`

**Never a single file.** One append-only row per file in date folders - the shape `workitems/events/` already uses. Nothing is ever rewritten, so the history cost is the row itself rather than a fresh copy of the ledger per append (the `data/tick-latest.json` failure mode, avoided by construction).

Two Category-9 **content addresses** per row, which is where idempotency comes from:

- `claim` = BLAKE3 over `surface` + `hypothesis`, **length-prefixed** so a boundary shift cannot collide. The DV2.0 **hub** key: two witnesses of one hypothesis share it and can disagree without anyone picking a winner.
- `id` = BLAKE3 over the canonical body. The **satellite** key. Re-writing an identical row is a no-op; a different body under the same address is **refused**, never overwritten.

`byClaim` groups and keeps every row (raw vault - a single version of the facts, never of the truth); `renderBriefing` prints both legs separately, names the shape, prints each contributing row, and applies no threshold on the reader's behalf.
