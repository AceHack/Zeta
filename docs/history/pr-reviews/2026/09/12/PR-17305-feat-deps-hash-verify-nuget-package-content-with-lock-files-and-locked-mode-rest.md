## Description

Enables NuGet lock files repo-wide and `--locked-mode` at the three restore sites the open Scorecard alerts name, so package **content** is hash-verified rather than only version-pinned.

Aaron 2026-09-11, authorizing it: *"yes you can route the lock files, it is in the direction we want to go for nation state security."*

## Why a version pin was not enough

`Directory.Packages.props` already pins every version, transitively (`ManagePackageVersionsCentrally` + `CentralPackageTransitivePinningEnabled`). A version is a **label**, and a label is not a **byte** — a package republished under an unchanged version number passes a version pin without complaint. `packages.lock.json` records a **sha512 contentHash per resolved package**, direct and transitive; `--locked-mode` refuses the restore when the resolved graph does not match it.

Closes three OpenSSF Scorecard `nugetCommand not pinned by hash` alerts:

| alert | site |
|---|---|
| #264 | `.github/workflows/low-memory.yml:253` |
| #890 | `full-ai-cluster/orleans-silo/Dockerfile:11` |
| #285 | `genesis/_src/auth-backend/Dockerfile:5` |

## What landed

- `RestorePackagesWithLockFile` in the root `Directory.Build.props` — once, not 64 times.
- The same property **restated** in `full-ai-cluster/orleans-silo/Directory.Build.props` and `genesis/_src/auth-backend/Directory.Build.props`. Both files exist to *stop* inheritance from the root, so without restating it those two would have been the only .NET builds in the repo with unverified package bytes.
- **63 committed `packages.lock.json`** — 54 in `Zeta.sln`, the 2 container projects, and the 7 projects outside the solution (so building one of those does not leave an untracked file behind).
- `--locked-mode` at the three sites above. Both Dockerfiles now `COPY` the lock file before restoring.
- `docs/NUGET-LOCK-FILES.md` + two `CONTRIBUTING.md` hooks — the bump workflow, because a gate that fails with no stated remedy is a trap.

## The check was proven to fail before it was claimed

Measured on this branch, not assumed:

- Blake3 moved `3.0.2 -> 3.0.1` with the lock left alone → `dotnet restore --locked-mode` refused with **NU1004**.
- Reverted; a **plain** `dotnet restore` regenerated the lock unaided. That is why the documented remedy is a plain restore, not `--force-evaluate`.

## Boundary, stated rather than discovered later

`dotnet build` restores **implicitly and unlocked**, so the solution-wide gate job (`dotnet build Zeta.sln -c Release`) would regenerate a stale lock rather than fail on it. Only the three sites above verify; the `low-memory` lane covers `tests/Core.CSharp.Tests`' transitive closure, not the whole solution.

Left deliberately: gate runs on ubuntu, windows and macos, and a lock that legitimately differs per-OS would turn a supply-chain check into a cross-platform flake. Widening locked mode wants a measurement of cross-OS lock stability first, on a lane that can fail loudly without blocking `main`. `docs/NUGET-LOCK-FILES.md` carries this in the same words.

Docker images were **not** built — no daemon on this host. Each container project's restore was run directly in its own directory instead (`dotnet restore <proj> --locked-mode`, both exit 0).
