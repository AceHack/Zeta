## Windows, stated explicitly per tool

**FriCAS does NOT need WSL.** The brief assumed it would, as it historically did. Upstream now publishes self-contained Windows builds — `fricas-1.3.13-windows-x86-64.zip` and, since 1.3.13, `fricas-1.3.13-windows-arm64.zip`. Both are landed as `manifests/from-zip` rows with sha256 pins cross-checked against upstream's own `sha256sum-1.3.13.txt`, the GitHub release-API `assets[].digest`, the ScoopInstaller/Extras manifest where one exists, **and the bytes as downloaded here**. `from-zip` rather than a scoop row because `fricas` is in the Extras bucket while `install.ps1` bootstraps Main alone — and because a vendor asset pinned by digest lands in the digest-covered denominator where a scoop package id would not.

**SageMath has no native Windows story at all**, verified three ways: conda-forge `--platform win-64` fails to solve outright, there is no Homebrew formula (404 for both `sage` and `sagemath`), and upstream dropped native Windows after 9.3. So Windows Sage is WSL — but that does **not** reduce to the lane we already have. `sagemath` is in Ubuntu **jammy** at 9.5 and **absent from noble, plucky and questing** (Launchpad), so `manifests/apt` cannot acquire it on the runner OS this repo uses. `wsl-install-sh-test.yml` runs `install.sh` inside WSL2 Ubuntu-24.04 and works — it just has no Sage to install. The WSL leg is the easy half; the conda-forge mechanism is the part that needs a decision.

## The finding: Ubuntu arm64 FriCAS installs and cannot start

Reproduced twice on clean `ubuntu:24.04` arm64:

```
INTERNAL-SIMPLE-FILE-ERROR: File error on
".../aarch64-unknown-linux-gnu/algebra/compress.daase": Cannot open
```

`fricas-databases` is a hard `Depends`, is `Architecture: all`, and ships its payload under `/usr/lib/fricas/target/x86_64-pc-linux-gnu/` while the arm64 wrapper sets `FRICAS=.../aarch64-unknown-linux-gnu`. Upstream packaging defect, documented in the row rather than worked around. Nothing in the tree invokes FriCAS yet, so this is wasted bytes on an arm64 runner and not a red lane — the first lane that *does* invoke it must be pinned to amd64 or macOS.

(A separate container artifact, recorded so it is not confused with the above: Ubuntu builds FriCAS with GCL, GCL calls `personality(ADDR_NO_RANDOMIZE)`, and the default seccomp profile blocks it — `personality failure 38`. Not applicable to a GitHub Actions VM runner; applicable to a container lane that *runs* FriCAS.)

## What was NOT measured

- **Nothing ran on Windows** — no Windows host. The rows are correct by construction (digest verified before extraction; `bin=` paths read out of the actual archives with `unzip -Z1`), but *that FriCAS starts on Windows* is a claim no run here supports. Closing it costs one `windows-2025` job.
- **No Windows arm64 runner exists** on GitHub, so that row's runtime is unobservable in CI today.
- **No Intel Mac**, and there is no x86-64 macOS bottle, so that path source-builds.
- **FriCAS source build on arm64** — podman reused the cached `linux/amd64` image and said so; the 455 s figure is amd64 run twice, not an arm64 datapoint.
- **SageMath inside WSL end to end** — nothing to run until a mechanism exists.
