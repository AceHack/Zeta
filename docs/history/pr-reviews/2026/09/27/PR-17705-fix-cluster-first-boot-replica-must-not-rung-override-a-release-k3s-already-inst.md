## Description

## What broke

First-boot replica, constrained lane (dispatch 36333824468; also the 2026-09-27 scheduled run):

> spire: OutOfSync/Progressing -- ... StatefulSet.apps "spire-server" is invalid: spec: Forbidden: updates to statefulset spec for fields other than ... are forbidden (retried 5 times)

## Root cause (measured)

This is **not** drift between the committed twins. `helm template` of spire 0.24.2 at kube 1.35.6, rendered with `k8s/bootstrap/spire-install.yaml`'s values and again with `k8s/applications/spire`'s values, produces a **byte-identical** StatefulSet.

The replica serves ArgoCD a **dev-rung** tree. In that tree, `rung-overrides.yaml` entry `spire/disk-dev` sets `spire-server.persistence.size: 512Mi`. k3s, meanwhile, installs the committed bootstrap HelmChart at **5Gi**. So `spec.volumeClaimTemplates[spire-data].spec.resources.requests.storage` is 5Gi live and 512Mi desired. That field is immutable, and ArgoCD's patch is refused forever.

**Scope:** only lanes that run the k3s bootstrap roster *and* a rung-overlaid Application tree, which today means the first-boot replica. The committed (metal) tree renders all 7 adoption pairs identically, and the new check verifies that too.

## Fix

- The replica skips rung overrides on Applications that adopt a bootstrap HelmChart (`overridesOnAdoptedApplications`, which today matches exactly `spire/disk-dev`). The kind/k3d lanes install no bootstrap charts, so they keep the override.
- `src/Core.TypeScript/cluster/adoption-immutable-fields.ts` renders every bootstrap↔Application pair (argocd, cert-manager, cilium, external-secrets, spire, spire-crds, trust-manager). Each pair is rendered against both the committed tree and the dev tree the replica serves. It compares the fields the API server refuses to update: StatefulSet selector, serviceName, podManagementPolicy and volumeClaimTemplates; workload selectors; Service clusterIP; the template of a non-hook Job; PVC fields. It is wired into `helm-validate.yml`.
  - Negative control: `--apply-all-overrides` fails on exactly `StatefulSet/spire/spire-server spec.volumeClaimTemplates[spire-data]` (5Gi vs 512Mi). Without that flag, all 7 pairs × 2 trees pass.
  - Hermetic tests in `adoption-immutable-fields.test.ts` cover the comparison and the served-tree skip. A mutation that removes the skip filter turns the served-tree test red.

## Node container died (same run)

The constrained container stopped during stage 6: the API refused connections from 17:12:33, and stage 8 found the container `not running`. The soak and stage 7 then **passed vacuously** over a dead API. The cause was not recorded anywhere and is still unknown.

The harness now:
- reads `docker inspect .State` (ExitCode, OOMKilled, Error, timestamps) and the last 40 lines of the container log whenever the node is not running;
- fails stage 6 on a confirmed-dead node;
- marks stage 7 INCONCLUSIVE when no samples were collected;
- attaches the report to a failed stage-8 `docker kill`.

If the next run reports OOMKilled, that means the whole node ran out of memory at the 12 GiB cap, which is the same memory-pressure question metal faces.
