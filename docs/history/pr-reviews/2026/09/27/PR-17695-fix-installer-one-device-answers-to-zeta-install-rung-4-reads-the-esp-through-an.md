## The defect
An isohybrid ISO's MBR partition 1 starts at LBA 0 and spans the image, so `/dev/sda` and `/dev/sda1` expose the same iso9660 with the same `ZETA_INSTALL` label; `by-label` picked between them by udev event order. When `/iso` was mounted from the whole disk it held it `O_EXCL`, and the ESP (SSH key, hostname, wifi, firstboot conf, repo pin) was unopenable for the whole install.

## Changes
- **Source-side pin**: `nixos/modules/install-label-single-device.nix` sets udev `link_priority=-100` on the *whole disk* when it carries the ISO volume label. It applies in the initrd (`boot.initrd.services.udev.rules`, which decides the stage-1 `/iso` mount) and in stage 2 (`services.udev.extraRules`, used by the first-boot scan). The partition always owns `by-label/ZETA_INSTALL`. Optical media still work: `sr0` has no partitions, so it is the only candidate. The image layout (xorriso flags) is **unchanged**. Changing it would affect BIOS boot, UEFI boot, dd-to-USB and every QEMU lane, and would mean replacing nixpkgs' ISO builder to pass one flag.
- **Falsifier**: `bootMediumShape` in `qemu-full-install-test.ts` fails a USB lane whose guest reports `boot-medium=` a whole disk. It passes on a partition, and reports **did-not-run** (not a pass) when the line is absent or unparseable.
- **Reader hardening (rung 4, both scripts)**: when a candidate is the LBA-0 alias or a whole disk, the rung now resolves the parent disk and reads the ESP at the ESP partition's own start. It finds that partition by type (`0xef` or the GPT ESP GUID) using `lsblk` data from sysfs/udev, and never guesses a start. Before this change it refused with `start-lba-0-not-a-partition`. A test now checks that the two copies of the rung are identical apart from the variable prefix and `sudo`.
- **`(no-conf)` becomes `(no-conf:saw=...)`**: the scan line now lists what a readable ESP actually held (`nothing` = empty FAT, `unlistable` = the listing failed). This makes "read, but no conf staged" distinguishable from the `(no-vfat:...)` unopenable case.

## What the nightly evidence actually showed (run 36297481926, job 108558899207)
That `esp-conf` line came from the **initial-format** `qemu-boot-test` lane. Its bake stages authorized-keys, hostname and creds, with **no `/zeta-firstboot.conf`**. `boot-medium=/dev/sda1` was the healthy shape, and `/dev/sda2(no-conf)` means the ESP **mounted fine** and simply had no conf. So the ESP was not unopenable on that run. The `sda1` "Can't open blockdev" is `sda1` already being mounted at `/iso`. The job's actual failure is the `ZETA_ISO_COMMIT='unknown'` repo-pin refusal. Another agent owns that, and this PR does not touch it.
