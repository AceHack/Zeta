## Description

## What broke
Since WP34 (#17676), the ISO workflow runs `git add -f` on the preload image archive, which leaves the tree dirty. So the flake has no `self.rev`, and `configuration.nix` baked `ZETA_ISO_COMMIT=unknown`. `zeta-install.sh` rejects `unknown` as `invalid-format` and **fails closed**. The result: **every CI-built ISO aborts its operator install.** The test lanes hid this because they write an ESP `/zeta-repo-pin` over the baked value. Nightly [36297481926](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/36297481926) was the first run where that ESP pin was lost:

```
[repo-pin] ZETA_ISO_COMMIT='unknown' is not a 40-hex git commit; refusing to treat it as a pin.
[zeta-first-boot] Install failed (rc=1).
```

## Fix
- **Workflow:** after staging the archive, assert that it is the **only** tracked difference from HEAD. Only then stage `preload/iso-commit` containing HEAD. If anything else is dirty, refuse to stamp a commit.
- **`configuration.nix`:** pin = `self.rev`, else the staged `iso-commit`, else `""`. The validator already treats `""` as no-pin, which is the honest outcome for a dirty hand build. It never uses `dirtyRev`, because that would pin to a commit missing the local changes. The comment that claimed `unknown` meant no pin is corrected.
- **Falsifier:** a new step reads the **realized** provenance file from the ISO's closure and fails unless it equals HEAD.

## Not verified here
There is no Nix on the authoring machine. The `build-iso` job on this PR is the first real evaluation, including `lib.trim` and the new step.
