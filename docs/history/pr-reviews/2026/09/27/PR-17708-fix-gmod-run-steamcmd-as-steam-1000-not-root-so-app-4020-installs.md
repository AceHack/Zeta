## Description

## Defect (live)

Fresh bare-metal install, node-5b2dfa, 2026-09-27: ArgoCD app `gmod` OutOfSync/Progressing; `game-hosting/gmod-0` init container `install` in CrashLoopBackOff (exit 8, 8 restarts):

```
Waiting for user info...OK
ERROR! Failed to install app '4020' (Missing file permissions)
```

## Root cause

It is **not** the "non-root pod with no fsGroup" shape. The pod already sets `fsGroup: 1000`. Live `initContainerStatuses[].user.linux` showed the container ran as **uid 0 / gid 0** (supplemental 0, 1000): `cm2network/steamcmd:root` defaults to root, and no `runAsUser` was set. SteamCMD's tree (`/home/steam/steamcmd`) belongs to the image's `steam` user (1000:1000), and SteamCMD run as root fails this install with `Missing file permissions`. The PV is Longhorn ext4 (`fsType: ext4`), so the 32-bit/64-bit-inode explanation does not apply here.

## Fix

- `install` and `gmod` containers: `securityContext: { runAsUser: 1000, runAsGroup: 1000 }`, which is the image's own `steam` identity.
- Pod `fsGroup: 1000` is unchanged. A comment now says the default `fsGroupChangePolicy: Always` is load-bearing: it re-groups files a previous root run left on the existing PVC. The sftp sidecar is untouched because `atmoz/sftp` needs root for its chroot.

## Guard (red-TDD)

`src/Core.TypeScript/cluster/pvc-write-identity.ts` + test:
- `steamcmd-as-root`: a SteamCMD-image container without an explicit non-zero `runAsUser`.
- `non-root-no-fsgroup` / `fsgroup-mismatch`: a non-root container that writes a PVC-backed mount while the pod has no `fsGroup`, or has an `fsGroup` that is neither its `runAsGroup` nor in `supplementalGroups`.
- The tree-wide scan of plain-YAML workloads under `full-ai-cluster/k8s/applications` found only gmod.

Red on `origin/main` (2 findings, `install` + `gmod`, `steamcmd-as-root`); green after.
