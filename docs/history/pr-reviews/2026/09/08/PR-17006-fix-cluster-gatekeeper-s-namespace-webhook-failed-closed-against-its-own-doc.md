## Description

The Application carries a ten-line rationale citing the node-09485d incident — *"41 k3s restarts in 10 min, API permanently 503, cluster bricked"* — and concludes a policy engine must never be able to take down the API server, **"so it fails OPEN"**. It then set two failure policies to `Ignore`.

**Those two keys don't reach the webhook that gates namespaces.** `check-ignore-label.gatekeeper.sh` reads its own value, `validatingWebhookCheckIgnoreFailurePolicy`, which the chart defaults to `Fail` and which nothing in this tree overrode.

## Why it matters on a cold boot specifically

Gatekeeper is sync-wave **−25**. Once its `ValidatingWebhookConfiguration` lands but before its pods are Ready, a `Fail` policy makes the API server reject **every namespace CREATE cluster-wide** — and `CreateNamespace=true` is on the root sync options plus ~40 Applications, with explicit Namespace documents at waves ≥ −25.

`controllerManager.exemptNamespaces` doesn't help: those become `--exempt-namespace` **process flags**, not webhook selectors, so they cannot admit anything while the process is down.

**Honest bound, stated in the file:** this is a *window*, and ArgoCD retries, so a cold cluster may converge through it. What is not in doubt is that the property the file states in prose was not the property it configured — in the exact direction the cited incident exists to prevent. Setting it costs nothing while gatekeeper is up: every Constraint in this tree scopes to `society.zeta.io` Hat/HatBinding, so this webhook polices nothing else.
