## Description

docs(research): geo-distributed sites — federate, and the RTT that decides it

Aaron 2026-09-08 flagged this explicitly as an assumption: "i think clusters are
okay for local connections but we likely need federation for geo distributed,
this is an assumption on k8s design prinicples ... if we can do geo distriubted
clusters without peanlity then me and max can join the same cluster."

The assumption is correct, and the reason is mechanical rather than a matter of
principle. The cluster runs k3s with EMBEDDED ETCD (--cluster-init;
k3s-server.nix:331 notes the 127.0.0.1 bind), so it replicates by Raft:

  * every write needs a QUORUM and an fsync, so control-plane write latency has
    a floor of the RTT to the median member;
  * leader election is timing-based, and etcd's defaults -- 100 ms heartbeat,
    1000 ms election timeout -- are documented as suiting a LOCAL network. On a
    WAN link where RTT approaches the heartbeat, followers call elections for
    heartbeats that were merely slow, and the cluster churns leaders under no
    fault at all;
  * tuning trades one cost for another: raising the heartbeat toward the RTT
    buys stability by making failover SLOWER.

Measured in-tree: NOTHING tunes any of it. No heartbeat-interval, no
election-timeout, no etcd-arg anywhere under full-ai-cluster/. A stretched
cluster built today would run a WAN link at LAN defaults, which is the
configuration most likely to produce spurious elections.

Two things the document is careful about. The penalty lands on the CONTROL
PLANE, not on workload traffic -- pods talking to pods pay network latency and
nothing more. And "without penalty" is answered NO while "impossible" is also
wrong: stretched clusters are buildable, they just trade write latency and
failover time for one API surface.

THE ZETA-SPECIFIC ARGUMENT IS STRONGER THAN THE KUBERNETES ONE, and it is
labelled as mine and argued rather than measured. Zeta's substrate is built to
AVOID global consensus -- Z-set retraction, CRDT merge, the commutative belief
fold, reintegration-is-not-reconvergence, and local-time-never-enters-the-shared-
fold. A geo-stretched etcd inverts the stack: it makes the strongest consistency
requirement in the system the foundation for a design whose point is not needing
one. It also collides with manifesto section 1 (scale-free: no central
coordination point) and section 2 (lock/wait-free: a shared quorum blocks
progress on another party's availability).

Rather than issue a doctrine, the document gives the MEASUREMENT that settles
it, since Aaron's framing was a conditional: median RTT under ~10 ms is
same-metro and a shared cluster is unremarkable; ~10-50 ms is workable with
tuning that does not exist here yet; over ~50 ms, federate. That threshold table
is the falsifier for the recommendation -- if they measure single-digit RTT, the
recommendation is wrong for their case and a shared cluster is fine.

Recommendation: one cluster per site, federate across. Honest status of the
federation half is recorded rather than implied -- federated-identity/ exists,
but federation-loop.ts states its own limits ("No network listener of any kind
... No real SPIRE ... No hardware ... Ephemeral keys only"), so federation is
MODELLED, NOT DEPLOYED. The cross-site plane today is GitHub, and that is
already a federation rather than a stopgap: git is append-only,
partition-tolerant, and needs no quorum to accept a write.

Aaron's own identity design already points this way: join authorised by repo +
contributor GitHub login, with a fork able to run different clusters over time,
anchors identity OUTSIDE any cluster. A cluster-CA-anchored join would make the
cluster the root of trust and a fork second-class; repo-anchored join makes each
site's cluster an implementation detail.

Also records what this implies for the dev stick: join material is PER-SITE, so
"for dev we want the cluster join materials" is consistent with federating and
does not commit to a stretched cluster.
