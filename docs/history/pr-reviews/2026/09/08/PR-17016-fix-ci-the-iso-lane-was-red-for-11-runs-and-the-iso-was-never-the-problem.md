## Description

`build-ai-cluster-iso` has had **11 failures and 4 cancellations** since its last green run, and a USB stick is about to be flashed. **The x86_64 ISO builds successfully in every one of those runs** — step 17 is green throughout. Three separate defects downstream of it, none in the image.

## 1. The current failure is a false positive

`FAILURE_MARKERS` are substring-scanned over the whole serial log, and one was the bare word `"panic"`. nixpkgs 26.05 ships a stock systemd unit whose derivation is `unit-panic-on-fail.service.drv` — printed by `nixos-install` inside its *"these 346 derivations will be built"* list. So every run after the 25.11 → 26.05 bump killed the installer at 8 minutes, mid-install, having done nothing wrong.

**The bump didn't break the image. It broke this marker.**

The sibling harness already had the discipline — `qemu-boot-test.ts` matches `"Kernel panic"` and carries a comment explaining why `"Boot failed:"` was deliberately *not* used, because healthy boots print it.

Verified both directions:

| string | matches |
|---|---|
| `…unit-panic-on-fail.service.drv` | **none** |
| `Kernel panic - not syncing: VFS…` | `Kernel panic` |

## 2. The first failure, which predates the bump, was ENOSPC

`uv tool install` died with *"No space left on device"* while provisioning, after nine toolchains (wabt, binaryen, emscripten, nodejs, zig, llvm, rustup, go, lua5) were added to the cluster hosts. The last run to reach that stage reclaimed **17.28 GiB of a 20 GB image**. Raised to 40.

**Stated as a prediction, not a measurement** — no 26.05 run has survived past the marker kill, so nothing has re-reached that stage. The package list is unchanged and headroom was under 3 GiB.

**And it's a real-metal finding, not only CI:** the same nine toolchains install onto a real host, so any target disk near 20 GB fails the same way.

## 3. The alternating failure is a race

k3s applies the control-plane label **asynchronously** after registration, and the assertion sampled once. In the failing logs the joiner reports *"Annotations and labels have been set successfully"* **twelve lines below** the assertion that just failed. The same file already uses `wait_until_succeeds` at three other k3s assertions — this was the one that didn't.

## Left alone deliberately, and reported instead

The marker `"bail"`. The installer's `bail()` emits `ERROR: $*` and never the literal word, so it **cannot catch the thing it's named for** — false-positive surface with no true-positive behind it. Narrowing it changes detection semantics and wants its own evidence, so it's written into the file as a finding rather than guessed at.

## Why 11 red runs went unnoticed

The lane is **not** in `gate (required)` — by explicit design; the workflow says so itself. Worse, `scenario 2` is gated on `push || workflow_dispatch`, so **the nixpkgs bump's own PR reported success with the install proof skipped.** The proof never ran on the change that broke it.
