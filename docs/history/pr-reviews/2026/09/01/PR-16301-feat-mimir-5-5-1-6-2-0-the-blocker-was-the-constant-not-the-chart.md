## Description

Held earlier today, now released — because the reason for the hold turned out not to be about mimir at all.

Chart 6.x declares `kubeVersion: ^1.32.0-0`. The bump was reverted when `audit-observability-chain` refused to render it — against a `KUBE_VERSION` literal of **1.31.0 that nothing derived and nobody had checked**. The cluster ships k3s **1.35.6**. #16296 replaced that literal with a declaration derived from this repo's own flake lock, and the constraint simply does not apply to us.

**Measured on this branch**, not carried over: mimir 6.2.0 renders cleanly at 1.35.6 with this Application's own `valuesObject`, PVCs carrying `storageClassName: longhorn`. Re-run here rather than trusting the earlier reading, because that reading was taken against a different tree.

The rest of the earlier analysis is unchanged: this loses the four `mimir-nginx` resources (6.x drops the bundled nginx gateway for `gateway.*`; we never configured nginx and nothing references it), and **`minio.enabled: false` is still load-bearing** — the chart defaults it `true`.

## The three storage acknowledgements return with it

They are a **false positive of the schema derivation, not inert keys**: 6.2.0 ships those keys *commented out* in its `values.yaml`, and a commented line is in neither the chart values nor a template's `.Values` reference — so the tool cannot see a key that demonstrably works. Carried **with the render that disproves the finding**, never as a bare silencing.

The baseline-empty control moves 11 → 14 to match, because that assertion only proves the acknowledged findings are real if its count tracks the baseline.
