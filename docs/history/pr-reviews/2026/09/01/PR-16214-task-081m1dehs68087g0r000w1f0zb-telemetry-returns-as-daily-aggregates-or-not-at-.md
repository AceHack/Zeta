## Description

Aaron 2026-09-01 gave the redesign a **target** instead of "less":

> *"we could just reduce telemetry to a few counts per day per metric with a few dimensions attached and get everyting we need, 100mb a day is just insane for our current state of the project"*

## Why this is a SHAPE change, not a sampling-rate change

Measured on this repo, 2026-08-30/31:

```
101.7 MiB growth in one 24h window        98.5% telemetry
172.8 MiB / 48h  REWRITTEN single files
  0.9 MiB / 48h  write-once shards     -> 99.5% of bulk was accumulators
```

The cost was **never the number of metrics.** It was rewriting a whole file per tick, so every tick paid for the entire history again. Halving the tick rate halves a quadratic; **a daily aggregate removes it.**

~50 metrics × ~5 dimensions × a few counts/day ≈ tens of KB/day. Against 100 MB/day that's ~1000× — reachable by changing *what a write is*, not how often it happens.

## The acceptance criterion that matters

A falsifier that **fails when a telemetry surface is rewritten rather than appended.**

Without it, "redesigned" and "re-enabled" are indistinguishable at review time — and the second reproduces the number that disabled all fifteen lanes.

## The review tell

Trigger shape sorts these without reading a byte count:

- `pr-archive-on-merge` → `pull_request: [closed]`, merge-only, **no cron** — writes only when something happened
- every disabled telemetry lane → **cron-driven** — writes whether or not anything happened

A returning lane that is still cron-driven had better be writing an aggregate, or it's the same lane with a new name.

## Explicitly not the priority

Training data outranks telemetry at this stage (`081M1DDQ4G0087G0R002SCRFHA`). Telemetry stays off until it costs what a daily aggregate costs.
