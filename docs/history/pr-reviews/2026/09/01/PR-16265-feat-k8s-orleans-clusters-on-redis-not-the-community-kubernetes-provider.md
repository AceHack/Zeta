## Description

"We can start with redis" — this records that decision where the silo will read it.

## Why not `provider: kubernetes`, which is what the file said

That maps to `OrleansContrib/Orleans.Clustering.Kubernetes` — a **community** package storing membership in CRDs.

Microsoft's own `Microsoft.Orleans.Hosting.Kubernetes` is **not** a clustering provider. It *complements* one by watching pod lifecycle so a deleted pod marks its silo dead promptly — which is exactly what the `POD_NAME` / `POD_NAMESPACE` / `POD_IP` downward-API env in `statefulset.yaml` already supplies. Both belong in the silo; only one of them is membership, and the file was naming the wrong one.

## Why Redis

`Microsoft.Orleans.Clustering.Redis` is **first-party and stable as of Orleans 10.0**, and `redis/` already runs here and reports Healthy in the included proof. It also keeps us off the AdoNet path, since Orleans' PostgreSQL clustering functions read affected rows with `GET DIAGNOSTICS ROW_COUNT` — which CockroachDB documents as **not supported**.

**The locking question is settled the other way**, recorded so it isn't re-litigated: the hypothesis was that Cockroach might diverge on locking granularity. It doesn't matter — that SQL takes **no locks at all** (no `LOCK TABLE`, no advisory locks, no `SELECT FOR UPDATE`), only a single-row compare-and-swap on a version row, which is precisely what CockroachDB is built for. The blocker is PL/pgSQL coverage, not concurrency semantics.

## Two values verified rather than assumed — one was wrong first pass

- The secret key was written `redis-password`; `redis/Application.yaml` declares **`existingSecretPasswordKey: password`**. Corrected by reading the Application.
- **`redis-master` confirmed by rendering** bitnami redis 20.5.0 with `architecture=replication` — it emits `redis-master`, `redis-replica(s)`, `redis-headless`. Not taken from memory of bitnami conventions.

Carries Orleans' own caveat: **Redis persistence must be explicitly enabled** — a volatile Redis loses membership, and losing membership takes the cluster with it.

## This configures nothing yet

Stated in the file so nobody reads it as deployed: `statefulset.yaml` is `replicas: 0` behind a placeholder image, and **no `Microsoft.Orleans.*` package is referenced anywhere in this repo** — `OrleansCronAdapter.fs` says of itself it's *"a lightweight in-memory adapter… in a real deployment, this would be backed by Orleans IGrain timers."*

The first real step is a silo image carrying grain code. This is the clustering decision that image will read.
