## Description

## Why this one first

Everything in the tree depends on ArgoCD. It was pinned at chart `7.7.10` — **ArgoCD v2.13.2**, published 2024-12-12, **200 chart versions behind**.

## Both pins move together — that is the whole risk

ArgoCD is **self-managed**: the Application *adopts* the installation the K3S bootstrap manifest creates. The file has warned since it was written that version drift between them makes ArgoCD try to change its own version on first reconcile, in the **earliest sync wave** (`-90`). So this commit moves both, and only both:

| file | 7.7.10 → 10.6.0 |
|---|---|
| `k8s/bootstrap/argocd-install.yaml` (K3S `HelmChart` CR) | ✅ |
| `k8s/applications/argocd/Application.yaml` (self-management) | ✅ |

## Measured before bumping, not assumed

`helm template` with the Application's **exact** `valuesObject` at both versions:

- Both render clean. **45 → 50 resources.**
- The five new ones are all `NetworkPolicy` (application-controller, dex-server, redis, repo-server, server) — **additions; nothing removed.**
- **Every value we set still takes effect at 10.6.0**, checked key by key:
  - `global.domain` → appears in the render
  - `server.service.type` → `argocd-server` Service is `ClusterIP`
  - `configs.params.server.insecure` → reaches `argocd-cmd-params-cm`
  - `notifications.enabled: false` → **zero** notifications resources rendered

That last group is the half a major chart bump usually breaks: a values key that silently stops being read renders fine and configures nothing. It was checked individually rather than inferred from "it templated".

## Why the risk is smaller than "200 behind" suggests

**There is no live cluster.** The only kubeconfig contexts are ephemeral CI kind clusters and none is reachable. So this is *not* an in-place v2.13 → v3.x migration with its CRD and RBAC hazards — it is changing which version a cluster that does not exist yet gets installed at. The k8s lanes are what actually clear it.

## The guard caught me first

`audit-chart-target-revisions` **refused** the pin on the first run — its snapshot predated `10.6.0` and it correctly reported that ArgoCD could never resolve it. That is the mechanism working, and it is why the version snapshot and `docs/CHART-CURRENCY.md` are regenerated here. `inert-valuesobject-keys` is keyed by `chart@version`, so its schema snapshot is re-measured too.

## `.gitignore` gains `.helm-schema-cache/`

`--write-snapshot` writes **3533 files / 39 MB** of vendored upstream chart values there. It was never tracked and never ignored, so `git add -A` swept the whole of it into a commit. This branch is a rebranch of the one that happened on (no PR existed). The cache is fine — it is re-derivable by re-running the tool — it just must not be committed.


## What the render could NOT measure — the v3.0 runtime changes, checked separately

`helm template` proves the **values** survive. It cannot see RBAC semantics or resource-tracking behaviour, so the three v3.0 changes that actually bite were checked against our config directly:

| v3.0 change | our exposure | why |
|---|---|---|
| ApplicationSet CRD can exceed the client-side-apply size limit (3.2→3.3), with a **self-management-specific** procedure — and this Application *is* Argo CD's self-management config | **already mitigated** | `syncOptions` has carried `ServerSideApply=true` since it was written |
| resource tracking flips **label → annotation** by default, with a documented orphan-resource edge case | **not applicable** | we never set `application.resourceTrackingMethod`, so we take the new default *from the start* — the orphan case is about migrating resources already tracked by label, and there are none |
| **logs RBAC enforced by default** — the UI logs tab disappears without an explicit `logs, get` grant | **low, and named** | we define no RBAC policy, so chart defaults apply; admin is unaffected, and any non-admin user added later needs the grant |

Every one of those resolves favourably **because there is no live cluster** — which is the same fact the risk argument above rests on, so it is stated once and used twice rather than being an independent piece of luck.

Two further v3.x items worth recording even though they do not block: Helm bumped to 3.17.1 inside Argo CD at 3.0 (a `null`-in-values behaviour change), and to **v4.2.0** at 3.4→3.5 — a second, unrelated Helm-engine bump. Neither touches the four values we set.
