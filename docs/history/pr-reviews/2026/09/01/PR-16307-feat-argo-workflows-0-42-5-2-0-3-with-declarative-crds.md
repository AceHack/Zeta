## Description

The last chart held for an unexplained reason — and the reason was a **wrong conclusion from a right observation**.

I refused this bump earlier today because 2.0.3 renders **zero** CustomResourceDefinitions where 0.42.5 renders eight, which would leave a cluster unable to hold a Workflow at all. The observation was correct and reproducible, including with `--include-crds`. The *conclusion* was wrong: chart 2.x ships full CRDs through a **pre-install hook Job that server-side-applies them**, so they are never part of a plain template render. `crds.install: true` was the default the whole time.

## Taking the declarative path instead

`crds.full: false` templates the CRDs as ordinary manifests. The hook path would work, but it trades declarative manifests for a **privileged Job doing server-side apply at PreSync** — and a Job that fails leaves an Application that can never sync.

## Measured, both versions, same values, at the declared Kubernetes version

| | resources | CRDs | hook Jobs |
|---|---|---|---|
| 0.42.5 | 29 | 8 | 0 |
| 2.0.3 | 29 | 8 | 0 |

**Resource-name diff: nothing added, nothing removed.** An identical resource set across a major chart bump — the strongest like-for-like evidence available without a live cluster.

## The cost, stated rather than omitted

Minified CRDs carry `x-kubernetes-preserve-unknown-fields`, so Workflow specs get **less schema validation** from the API server than full CRDs would. That is a real trade: weaker field validation in exchange for CRDs our tooling can **see**. The lane partitioner, the storage ledger and kubeconform all read the render, and a CRD delivered by a hook Job is invisible to every one of them — which is also why the original observation looked like a catastrophe rather than a delivery-mechanism change.
