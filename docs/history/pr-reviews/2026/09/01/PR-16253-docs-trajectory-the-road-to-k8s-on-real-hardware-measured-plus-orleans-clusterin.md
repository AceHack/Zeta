## Orleans clustering — the locking question, answered

The hypothesis was that CockroachDB might diverge from PostgreSQL on locking granularity. **That half is favourable; the risk is elsewhere.**

Orleans' PostgreSQL clustering SQL takes **no locks at all** — no `LOCK TABLE`, no advisory locks, no `SELECT FOR UPDATE`, no explicit serializable txn. It's a single-row CAS on a version row, exactly what CockroachDB is built for.

**The actual blocker is PL/pgSQL coverage.** Those functions read affected rows with `GET DIAGNOSTICS ROW_COUNT`, which CockroachDB documents as **not supported** (alongside `PERFORM`, `EXECUTE`, `CASE`, `FOUND`), and its exception blocks cannot catch transaction retry errors. AdoNet clustering will not install on Cockroach as shipped. A dialect can be authored — Orleans keeps its SQL as *data* in `OrleansQuery` — but that's a maintained fork.

**Recommends Redis**: stable as of Orleans 10.0, first-class rather than the OrleansContrib package, with the docs' own caveat that persistence must be explicitly enabled.

**On scale-out** — the question mostly dissolves: membership is one row per silo and needs *availability*, not sharding. The thing that scales out in Orleans is the silos.
