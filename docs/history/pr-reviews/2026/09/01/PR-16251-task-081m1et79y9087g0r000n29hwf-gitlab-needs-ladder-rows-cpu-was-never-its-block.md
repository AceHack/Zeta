## Description

Attempted the request directly, measured it end to end, and am filing the **specification** rather than the change. Both halves are deliberate.

## CPU was never gitlab's blocker

`lane-partition` names gitlab as the one oversize quarantine (`cpu 2525m > 2125m`), which reads as *"shrink CPU and it fits."* It isn't. The recorded deferral reason gives the real one:

> **76 GiB of PersistentVolumeClaims** across four workloads — gitaly 50Gi, minio 10Gi, postgresql 8Gi, redis 8Gi

Against a runner with ~70 GiB free. **Fixing CPU alone unlocks nothing.**

## Measured, by rendering

| | default | achievable dev |
|---|---|---|
| cpu | **2525m** | 1350m |
| memory | **5733Mi** | 4191Mi |
| PVC | **76.00 GiB** | 5.00 GiB |

The default render **reproduced** the ledger's stored `2525m / 5733Mi` and the reason's `76 GiB` (to 1Mi of rounding) *before* producing the new numbers — which is why the second column is trustworthy rather than merely computed.

## Why the obvious change is the wrong mechanism

Writing those values into `valuesObject` **does work** — `lane-partition` then reports `TOO BIG FOR ONE HOSTED RUNNER: 0`, `covered by a lane: 45/47`. It's still wrong twice:

1. **A rung is expressed through `resourceClaims`, not base values.** With no claims, `valuesObject` renders at *both* rungs — `storage-profiles.test.ts` caught it instantly (metal `9256m → 8081m`). A dev-sized reservation would ship to metal.
2. **Storage has its own ladder** (`minimal`/`standard`/`measured`/`large`). A flat `persistence.size` applies at `large` too — a real GitLab would get **2 GiB of git storage**.

`--profile NAME --apply` *writes* the ladder's values into the Applications. The ladder is the mechanism; base values are its output, not its input.

So it was reverted rather than shipped. The row carries the 14 exact knobs (verified against the pinned subchart `values.yaml`), the claim schema, and the `excludeGlob` retirement that must follow — **or gitlab stays untested even once it fits.**
