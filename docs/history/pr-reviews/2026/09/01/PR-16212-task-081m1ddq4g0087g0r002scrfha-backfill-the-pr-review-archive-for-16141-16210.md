## Description

`pr-archive-on-merge` was disabled 2026-08-31 while stopping telemetry growth. **It is not telemetry** — it fires on `pull_request: [closed]`, only for merges, and carries no `schedule:`. It got swept up with the cadence lanes and nothing noticed for a day.

The review archive stops at **#16140**. Roughly **#16141–#16210** have no entry, including fourteen PRs merged 2026-08-31. The workflow is close-triggered, so it will **never** retroactively fire for them.

**Re-enabled 2026-09-01** after checking Aaron's condition — PR-triggered only, no cron — so the ongoing loss has stopped. This item is only the gap.

## The growth question, measured

Standing constraint: *"avoid unbounded growth until we split into multi repo."* A proposal that doesn't price itself against that is asking for a decision without the number.

| surface | files | size |
|---|---|---|
| `docs/github/prs` (shards) | 13,592 | 60 MB |
| `docs/history/pr-reviews` | 13,593 | 87 MB |
| | | **~11 KB per PR** |

**Backfilling ~70 PRs ≈ 770 KB.** Against 147 MB of existing archive — and against a repo measured growing **101.7 MiB in one 24h window, 98.5% of it telemetry** — that is roughly **0.5% of a single day's telemetry**.

**The PR archive was never the growth driver.** Treating it as one is precisely what got it disabled. Ongoing cost is bounded by merge rate, not a cron: ~154 KB on a 14-merge day.

## Filed, not done — and one explicit hold

The repo split is the standing plan for where bulk archives live. If it lands first, the backfill belongs **in the archive repo**. The numbers say cost is small either way, so this is a **placement** decision — and placing it wrong is harder to undo than doing it late.
