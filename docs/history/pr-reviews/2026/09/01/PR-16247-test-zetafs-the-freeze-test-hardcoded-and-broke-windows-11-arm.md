## Description

`ZetaFsFreezeTests.sealed log does not leave freeze-intent ASCII in the clear` fails on **windows-11-arm** with:

```
System.IO.FileNotFoundException : /freeze-enc/log/freeze
  at Zeta.Core.InMemoryFileSystem.ReadAllBytes
```

An **in-memory** filesystem cannot miss a file for disk reasons — that's the tell.

Production composes the path portably:

```fsharp
let private logPath (v: Volume) = Path.Combine(logDir v, "freeze")
```

So on Windows it writes `/freeze-enc\log\freeze`, while the test read the literal `/freeze-enc/log/freeze`. `InMemoryFileSystem` keys on the exact string, so the two never met. **The test was asserting about one platform while claiming to assert about the code.**

## Measured, not inferred

`windows-11-arm` was `success` on the **seven** gate runs before `7c6eae0e` and `failure` on it. The break arrived with that merge.

## Why it got in — the part worth keeping

`build-and-test` is `continue-on-error` for `windows-*` and `macos-*`, so the failure was **advisory and blocked nothing**. That's a defensible setting — cross-platform runners do flake — but it means a genuine platform-specific defect merges silently, and the only thing between that and a regression is somebody reading a job that is *allowed* to be red.

## Verified where I can, and the limit stated

The freeze suite passes **5/5 on this host** after the change, so the fix doesn't regress the platform I can run. I **cannot** verify Windows locally — the claim that it repairs `windows-11-arm` rests on the mechanism (`Path.Combine` vs a literal separator) and is confirmed or refuted by CI, not by me.
