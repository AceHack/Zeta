## Description

Main went red on `f83701a62` (`arity-equality`, R2): **two unadjudicated self-comparisons**, both sides normalising to a single expression.

```fsharp
let bytes = Array.init 90_000 (fun i -> byte (i % 199))
let a = ZetaFsJumprope.buildV1 bytes
let b = ZetaFsJumprope.buildV1 bytes      // the SAME array
Assert.Equal(a.Content.ToHex(), b.Content.ToHex())
```

The test's **name is the claim** — *identical **files** share chunk ids* — and that's the content-addressing property the whole dedup design rests on.

What the code asserted was `f(x) = f(x)` over **one array object**, which is strictly weaker. It could only ever have caught nondeterminism inside `buildV1` (an ambient seed or clock), and it would have passed unchanged against an implementation that keyed on **array identity** or memoised per object — exactly the bug that breaks dedup between two genuinely distinct files with equal bytes.

## Strengthened, not adjudicated

`audit-check-arity --write --accept-raises` was the one-command exit, and it would have been a **false record**: it asserts *"the two executions really do differ"*, and they did not — both sides read one array.

Silencing the audit here would have preserved a test that cannot fail, which is the defect the audit exists to find.

`Array.copy` closes the gap: a separate allocation with equal contents, so the assertion now tests the claim its name makes. The two inputs are additionally asserted to be **distinct objects with equal bytes**, so the strengthening can't decay back into one-file-twice if someone later "simplifies" the copy away.

## Verification — stated honestly

- ✅ `audit-check-arity` passes — rc=0 measured directly: 790 files, 0 problems
- ✅ the test **compiles** — it reaches `buildV1`
- ⚠️ **I could not execute it here.** `ContentHash256.ofBytes hook is not initialized` on this host.

The **control** shows that isn't mine: an untouched sibling test *and* the original test on stock main fail identically — 9 of 11 in the class. `build-and-test (ubuntu-24.04-arm)` is green on `f83701a62`, so the suite runs fine in CI and this is a local Blake3 hook gap.

**So the runtime verdict comes from CI.** If content-addressing does *not* survive a copied array, this test now fails — and that failure would be a **real finding about dedup**, not a defect in the test.
