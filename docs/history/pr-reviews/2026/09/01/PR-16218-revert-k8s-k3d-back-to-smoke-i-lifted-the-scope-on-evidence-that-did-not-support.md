## Description

## What I did wrong

#16203 lifted the k3d lane from `--scope smoke` to `included` on the stated condition *"one green smoke run exists."* Two did.

But **`included` does not assert what smoke asserts.** It asserts 33 Applications reaching Synced/Healthy on this substrate, and two green smoke runs are not evidence for that. The PR said the budget was *"matched to `live-kind-included`"* — that was about the **timeout**, and I let a sizing match read as a viability match.

## Measured

k3d has **never** passed at `included`. It failed on the lift's own branch, then on `main`, then on every run of the follow-up branch. Same Applications each time:

```
openziti-controller   Unknown   Degraded
trust-manager         Synced    Degraded
spire                 Synced    Progressing
vault                 Unknown   Progressing

cilium                Unknown   HEALTHY      ← the provider-aware lift works
```

So **main's k8s lane has been red on a change I made**, and the provider-aware cilium work is *not* what's red — that part does exactly what it claimed.

## This PR

Restores `smoke` (1200s / poll 10 / 45 min — the values sized for it) and records the episode **in place** rather than deleting the lift note.

The new `LIFTS WHEN` is **"those four are understood"**, not *"another smoke run goes green"* — the latter is precisely the inference that produced this revert.

## The four are filed, not waved through

`081M1DFQ2MZ087G0R000CMNHQX`. **k3s + Cilium is what metal runs**, and until this lane existed nothing in the repo had ever reconciled an App-of-Apps on a Cilium cluster — `live-kind-cilium` runs Cilium without ArgoCD; `live-kind-included` runs ArgoCD on kindnetd. These are plausibly real metal findings surfaced early.

The item states the honest alternative too — they could be k3d artifacts, as the CoreDNS `127.0.0.11` finding turned out to be — and gives the test that distinguishes them.
