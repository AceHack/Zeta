## Description

Attempt 3 (run `33481362793`) got further than either predecessor: the **Cilium bring-up succeeded** and the proof ran to its preflight, which then refused:

```
{"kind":"DevStorageClassMissing","message":"... declares a dev StorageClass named
 \"longhorn\" over rancher.io/local-path, and the included proof asserts Applications
 that request it, but in cluster zeta-ci-cilium-included it is not present. Those PVCs
 would stay Pending, which ArgoCD reports as PROGRESSING rather than Degraded ..."}
```

## That refusal saved the experiment from a false positive

**`Progressing` is the exact symptom the four Applications show on k3d.**

Without this guard, the job would have reported apps Progressing on kind+Cilium, and the obvious reading — *"Cilium causes it"* — would have been **wrong**, caused instead by a StorageClass that `--existing` skipped. I would have had a clean-looking verdict table, a plausible conclusion, and no way to know it was an artifact of my own harness invocation.

That's the third harness refusal to catch this experiment mid-error (empty git ref → vault ceremony → this), and all three share one root cause: **`--existing` skips the harness's own cluster preparation, and the `included` proof depends on it.**

## Design note

`bringUpKindCiCluster` applies this manifest during *its* cluster creation; `cilium-kind-up.ts` builds the cluster a different way and does not.

Applied in the job rather than inside `cilium-kind-up.ts` deliberately — that module also serves the `live kind Cilium CNI` lane, which tests the CNI alone and has no business growing a StorageClass it doesn't need.

The step **asserts** the provisioner is non-empty after applying, rather than trusting `kubectl apply` to have produced something. A silent apply would send this back into the same refusal one 30-minute run later.

## Known remaining coupling — named, not discovered

The harness has a second preparation refusal: `DevRegistryPullSecretMissing` (`applyDevRegistryPullSecret` mints `ghcr-pull`). It did **not** fire on attempt 3 and should not, because `platform/**` is still in `DEFAULT_ROOT_DEV_CATALOG.excludeGlob`. If it does fire, that's the next known step rather than a surprise.
