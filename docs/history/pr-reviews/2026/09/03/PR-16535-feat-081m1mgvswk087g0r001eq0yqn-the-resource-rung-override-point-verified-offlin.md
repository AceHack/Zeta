## The blocker, as the harness already stated it

`argocd-health-test.ts` carries this in its hindsight blocker note, and it is exactly right:

> **THE `dev` RESOURCE RUNG CANNOT REACH THIS LANE**, which is the part that looked like the fix and is not. `storage-profiles.ts --resource-profile dev --apply` rewrites the WORKING TREE; ArgoCD syncs the COMMITTED tree at `--git-ref` ... **One committed tree, two substrates, no override point.**

MEASURED 2026-09-03, `storage-profiles.ts --resource-profile <rung> --budget`:

| rung | dev lane (39 apps) | budget | |
| --- | --- | --- | --- |
| `dev` | 1165m / 9164Mi | 2500m / 9216Mi | fits |
| `metal` | **6390m** / 14352Mi | 2500m / 9216Mi | does not |

The committed rung is `metal`, so CI applies 6390m of requests to one 4000m node. On run 33790413535 that is four pods the scheduler can never place, each `0/1 nodes are available: 1 Insufficient cpu`:

| pod | metal | dev |

| `hindsight-api` | 500m | 25m |
| `hindsight-control-plane` | 250m | 25m |
| `hindsight-postgresql` | 250m | 25m |

**It is not fixable by trimming numbers.** The gap is 2.5×, and the metal rung is correct for the substrate it names — 6390m on a 16-core box is unremarkable. Both rungs are right; what is missing is a way for one deployment to get one of them.

## The mechanism

`ports.ts` builds the root Application from `gitRepoUrl` + `gitRef` + `path`, and `gitRepoUrl` is **already** an injected parameter (`ZETA_ARGOCD_GIT_REPO_URL`). The override point is not a concept to invent — it is a repository to point at.

`lane-tree-source.ts` builds it: a staged copy of `full-ai-cluster/k8s` with the rung applied through the **same** `applyResourceProfile` the `--verify` path checks (it already takes a `repoRoot`, so no working tree is mutated), self-referencing `repoURL`s pointed at an in-cluster server, committed to a bare repository, repacked, and packed into a ConfigMap served over git's dumb-HTTP transport by a `busybox httpd` pod.

**419,840 bytes packed against a 716,800-byte budget (58.6%)**, 134 files, 12 repoURL rewrites.

### Why in-cluster, not a pushed ref

| | |
| --- | --- |
| repository growth | a per-run ref grows the repo forever — the standing concern |
| credentials | a pushed ref needs write access, so it cannot work for a fork PR |
| **races** | a *shared* ref force-pushed by two concurrent runs makes one lane sync the other's tree — a correctness fault, not churn |

Serving in-cluster has none: nothing is pushed, nothing leaves the runner, and two concurrent runs cannot see each other because each cluster holds its own copy.

### Why dumb HTTP over a static server

The bare repo is built locally, including `git update-server-info` — the whole of what that transport needs. The server therefore needs no git binary, no smart-HTTP CGI and no credentials. Every capability it does not have is one that cannot break in a lane whose failures cost forty minutes each. `git://` was rejected because the daemon protocol is disabled by default in some hardened git builds.

## Two size findings, both from the refusal firing rather than from a plan

1. **`clone --bare` leaves loose objects** — one zlib stream per blob, which throws away all cross-file redundancy. 1,382,400 bytes against 219,231 for a plain `tar cz` of the same files: the repository was **six times larger than the directory it holds**. The build now repacks into one delta-compressed pack *before* `update-server-info` — in that order, because a pack list written before a repack names a pack that no longer exists.
2. **Serving `full-ai-cluster` whole was 1,136,640 bytes.** Nothing outside `full-ai-cluster/k8s` is referenced by any Application, so only that is served.

Both were found because `MAX_TREE_BYTES` refused, which is what that refusal is for.

## The falsifier is end-to-end despite being offline

The test **clones the bare repository it just built** and reads mimir's kafka request out of the clone, asserting `25m` (dev) rather than `1000m` (the value that could not be scheduled).

**Mutation-verified 2026-09-03:** applying the rung *after* the commit — a plausible ordering bug — turns exactly that assertion red.

Four refusals, each with a test:

| refusal | why it matters |
| --- | --- |
| zero-file staging copy | a served empty tree makes every Application vanish, which ArgoCD reports as a clean prune rather than a fault |
| rung apply produced 0 edits | a lane that believes it runs `dev` while serving `metal` — the false-green this exists to remove |
| no self-referencing repoURL rewritten | a **partial** override: the Applications get `dev`, everything they point at stays `metal` |
| packed tree over budget | named here, not discovered as an etcd rejection inside a lane |

The rewrite is **targeted, not global** — a test pins that third-party chart repoURLs (`grafana.github.io/helm-charts`) are left alone, since rewriting those would trade a scheduling failure for a render failure.

## Not done here, and why it's split

The harness wiring — a `--serve-tree <rung>` flag that applies these manifests, waits for the server, and points the root Application at it — is a separate change.

Deliberate: each live-lane verification costs about forty minutes, and landing an unverified big-bang change into the critical path of the one proof that gates the k8s lane is worse than landing the verified mechanism first. Everything in this PR is checked offline and mutation-tested; the next PR is the part only CI can judge.
