## Description

Found by **running the loop end to end** against a local Ollama model (`qwen2.5:0.5b`), not by reading it:

```
bun src/Core.TypeScript/observe/run-loop-real.ts --dry-run --participant local-llm:qwen2.5:0.5b
[forge] PR state read FAILED: [object Object] — continuing WITHOUT PR state (NOT treating as zero PRs)
```

## What was actually in hand

`ForgeError` is a rich value — `{ kind, message, retryable, raw }`. The real error was:

```
auth-failure: no GitHub token in ~/.config/zeta/auth/github.json or GH_TOKEN/GITHUB_TOKEN
              — run `harny login github` (gh CLI is not a fallback)
```

Two steps destroyed all of it:

1. `readPRStateAsync` declared its failure `error: unknown` — **widening away a type it held**.
2. The loop then did `String(error)`, which on a plain object is `"[object Object]"`.

## Why this is more than a log line

`forge-host/result.ts` **already** classifies every kind (`rate-limited` / `network` retryable; `auth-failure` / `permission-denied` / `not-supported` / `not-found` / `parse-failure` / `internal` not) and every adapter sets `retryable`. **Nothing in `observe/` ever read it** — a field that exists to be acted on, read by nobody.

So an expired token and a transient network blip produced identical output, and the loop retried the expired token on every tick forever while the operator was never told to fix anything.

After:

```
[forge] PR state read FAILED — auth-failure: no GitHub token in ~/.config/zeta/auth/github.json
        or GH_TOKEN/GITHUB_TOKEN — run `harny login github` (gh CLI is not a fallback)
        (not retryable — waiting will not fix this, an operator must act) — continuing WITHOUT PR state
[forge] this will not clear on its own (auth-failure) — the loop will keep running without PR state
        until an operator fixes it
```

`forgeFailureDisposition` deliberately **does not re-classify** — it reads `retryable`, because a second classifier would be a competing opinion that diverges from `forge-host/result.ts` the first time either is edited. A test pins that by handing it a `ForgeError` whose `retryable` contradicts its kind.

## And one in my own test

The first version of *"no kind can ever render as `[object Object]`"* built its fixture message as `` `something went wrong (${kind})` ``, so `expect(described).toContain(kind)` passed **on the message alone**. A mutant that dropped `error.kind` from the output **SURVIVED**. Fixed by using a message that does not contain the kind — the matrix found a vacuous assertion I wrote.

## Scope, stated honestly

48 sites in `observe/` + `enforcement/` + `forge-host/` use the `e instanceof Error ? e.message : String(e)` idiom. That idiom is *correct* for an `Error` and for a string; it only degrades for a plain object. This changes the **four in the loop's own path**, not all 48.
