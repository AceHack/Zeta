## Description

`MERGE_OBSERVE_QUERY` spread a union type condition **directly inside a connection**:

```graphql
statusCheckRollup {
  contexts {
    ... on CheckRun { name status conclusion }
    ... on StatusContext { context state }
  }
}
```

`contexts` is a `StatusCheckRollupContextConnection`, not a list of nodes. GitHub refuses the whole query, every time, for every PR:

```
Fragment on CheckRun can't be spread inside StatusCheckRollupContextConnection
```

So **`ForgeHost.getPrGateState(n)` returned `internal` for every call it has ever made** — which is also why it had **zero callers**: nobody could have used it successfully. Found by pointing the new merge-receipt gate (#16439) at two real PRs.

## Why no test caught it

Both doubles built the **same wrong shape the query believed in**:

```ts
commits: { nodes: [{ commit: { statusCheckRollup: { contexts: [] } } }] }
```

A double written from the implementation reproduces the implementation's own idea of the shape, so the suite agreed with the bug instead of catching it. That is the sharpest available example of a test that cannot fail.

## The fix

```graphql
statusCheckRollup {
  contexts(first: 100) {
    nodes {
      __typename
      ... on CheckRun { name status conclusion }
      ... on StatusContext { context state }
    }
  }
}
```

The type condition is applied to the **node**, the connection is traversed explicitly and bounded, and `__typename` is requested so a union node stays distinguishable after parsing. Parser and types follow (`contexts.nodes`); both doubles are corrected to the real shape.

## The falsifier that does not depend on a double

Three assertions on the **query text**, which is the part the server actually judges:

- the `... on CheckRun` spread must appear **after** `nodes {`, never directly inside the connection;
- the connection is paginated (`contexts(first:`) rather than unbounded;
- `__typename` is requested.
