## Description

PROVEN FLAKY, not inferred. The same commit 356f7348d, no tree change, produced two
verdicts on macos-26:

  attempt 1  02:37:01Z  FAILURE  TlcRunnerTests:946, 661 ms
  attempt 2  03:00:57Z  SUCCESS  whole attempt, 0 failures

The assertion:

  Assert.Equal(pid.ToString(...), (readTextSharedWithWriter stdout).Trim())
  Expected: "36522"   Actual: ""

The grandchild still holds `stdout` OPEN FOR WRITING at that point, so its bytes become
visible on the WRITER's schedule and not on ours. Read once and the line asserts a RACE
rather than the cancel-and-drain behaviour it is named for.

Corroborating timing, from this repo's own archived runs of this test
(docs/research/tlc-attempt-retention-validation/2026-09-07/): 184 ms and 68 ms. The failing
instance took 661 ms -- 3.6x to 10x normal. The fixture was under real time pressure and an
assertion with no tolerance cannot survive it.

Every other bound in this test already has one: :930 waits 30 s for readiness, :933 waits
10 s for launcher exit, :941 waits 10 s for the drain. Line 946 had none at all.

PRIOR ART SETTLES THE CLASS. PR #17071 -- "four windows failures, one diagnosis: bounds with
no tolerance" -- raised the readiness bound in THIS SAME TEST from 10 s to 30 s. That fix
reached the readiness bound and left this line untouched, so #17071's own diagnosis applies
to a line it never edited.

Fix: spin until the expected PID is visible, bounded at 10 s, then assert.

TOLERATES THE DELAY, NEVER THE ABSENCE -- the property that makes this a fix rather than a
suppression, and it is measured rather than asserted. Mutating `expectedPid` to a value that
can never appear makes the test FAIL at the new line after the bounded wait:

  Failed: 1, Passed: 69, Total: 70, Duration: 10 s

So a PID that never arrives still fails, it fails within a bounded time, and it fails
through Assert.Equal so the message carries the value actually observed instead of a bare
timeout.

Unmutated: 70 passed, 0 failed. Build 0 warnings / 0 errors (TreatWarningsAsErrors).

Honest limit, stated because it matters: this cannot be proven to fix the flake locally. The
defect only manifests under time pressure that a healthy machine does not reproduce, so what
is demonstrated here is the absence property and the build, not the disappearance of the
race. The falsifier is the failure not recurring on macos-26.
