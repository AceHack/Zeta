## Description

CodeQL alert #798, `actions/untrusted-checkout/medium`, `gate.yml:270`.

The `path-filter` job checked out the default ref for a `pull_request` trigger -- the PR's
merge ref, i.e. contributor-controlled code. It then never looked at it. The `detect` step
below fetches BOTH SHAs explicitly and runs a TWO-DOT `git diff A B`, which compares two
fetched OBJECTS and never consults the working tree. The checkout existed only to provide a
git directory.

Fix: check out the base commit, which is already trusted.

  ref: ${{ github.event.pull_request.base.sha }}

The diff is byte-identical -- both endpoints are still fetched by SHA in `detect` -- and the
fail-closed property is unchanged: a missing object still aborts on `fatal: bad object`
rather than yielding a wrong changed-file set and silently skipping jobs that should have run.

WHY THIS IS A FIX AND NOT A SUPPRESSION, since the alert is arguably a false positive today:

  - workflow permissions are `contents: read`
  - the trigger is `pull_request`, NOT `pull_request_target`
  - this job's only two `run:` blocks are inline shell and execute nothing from the tree

All three are true, and all three are properties of the CURRENT job held by nothing but
review. A future step that reads one file from the working tree would silently make the
untrusted checkout load-bearing, and nothing would flag it -- the alert would already have
been argued away. Not putting the untrusted code on disk removes the class rather than
adjudicating the instance, and it cost one line.

This is also why it is not dismissed. The repo has taken zero dismissals since 2026-09-07,
and an alert that can be closed by a real change should be, not explained.
