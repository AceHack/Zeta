## Description

Two OpenSSF Scorecard alerts, `PinnedDependenciesID` score 9, both in the `lint (yaml/k8s)`
job of gate.yml:

  #457  .venv-yamllint/bin/python -m pip install --upgrade pip   <- unpinned, every run
  #458  .venv-yamllint/bin/pip install yamllint==1.38.0          <- version-pinned, not hash-pinned

#457 IS DELETED, NOT PINNED. It bought nothing: the venv's own pip installs a hash-pinned
requirements file perfectly well -- verified end-to-end below on a stock venv with no
upgrade. Upgrading it first meant the tool that enforces our pins was itself the one
unpinned network install in the step.

#458 becomes `--require-hashes -r tools/setup/manifests/yamllint-requirements.txt`.

A version pin says WHICH RELEASE. A hash pin says WHICH BYTES. PyPI versions are immutable
by policy, not by construction, and the gap between those two is the whole reason the check
exists.

SDIST HASHES, NOT WHEEL HASHES, deliberately. Wheels are per-platform -- measured locally,
`pip download` produced `pyyaml-6.0.3-cp314-cp314-macosx_11_0_arm64.whl`, while the runner
is manylinux x86_64. A hash set measured on one machine silently fails on the other. A
source distribution has one hash everywhere. Tradeoff stated: PyYAML compiles a C extension
from sdist (and falls back to pure Python without libyaml headers); the runner has a
compiler and the cost is seconds.

`--require-hashes` IS THE PROPERTY, NOT THE DIGESTS. With it, pip refuses ANY requirement in
the file that lacks a hash, so a future addition cannot be slipped in unpinned. Transitive
deps are listed explicitly because that mode requires it -- pip will not resolve an unhashed
dependency of a hashed one.

PROVEN TO WORK AND PROVEN TO REFUSE, both measured rather than asserted:

  stock venv, no pip upgrade   -> Successfully installed PyYAML-6.0.3 pathspec-1.1.1
                                  yamllint-1.38.0; `yamllint --version` -> 1.38.0
  one digit changed in a hash  -> ERROR: THESE PACKAGES DO NOT MATCH THE HASHES FROM THE
                                  REQUIREMENTS FILE
  a requirement with no hash   -> ERROR: Hashes are required in --require-hashes mode

A pin only ever shown to install is the vacuity class; the second and third lines are what
make this a check.

NOT TOUCHED, and named so the gap is visible rather than assumed closed: `go install
github.com/yannh/kubeconform/cmd/kubeconform@v0.7.0` on the next line is a THIRD pin of
kubeconform (the others are `.mise.full.toml` and the mise install path), and consolidating
those is its own change. `dotnet restore` in low-memory.yml (#264, `nugetCommand`) wants a
`packages.lock.json`, which is a repo-wide decision, not a workflow edit.
