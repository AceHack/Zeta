## Description

## What

CodeQL reports fifteen `js/file-system-race` alerts. **Ten are the same defect written ten times.** Five are legitimate flows that must not be "fixed" — this change annotates those in the code and explains them below. **No alert is dismissed.**

## The defect

Nine sites carried some spelling of:

```ts
const current = existsSync(p) ? readFileSync(p, "utf8") : "";
if (current !== next) writeFileSync(p, next, "utf8");
```

Three separate resolutions of one name, so *did it exist*, *what was in it* and *what did we overwrite* can each describe a different inode. It is not merely a scanner finding: **the write is conditional on the check**, so a replacement between them silently inverts the decision. It also swallowed an error it should have raised — `existsSync` returns false for `EACCES`, so a present-but-unreadable file read as an absent one and was then overwritten.

## The primitive

`writeTextIfChanged(path, text, { mode, maxBytes })` in `src/Core.TypeScript/io/safe-io.ts`, composed from the two primitives that already exist: one `readFileBounded` descriptor answers both the existence and the content question, and `writeFileOwned` runs with no check in front of it. `not-found` is the **only** error read as "absent"; an unreadable or over-cap file is a refusal, not a silent overwrite. The mtime-preserving no-op every caller relies on is kept exactly — identical bytes open nothing for writing.

Six falsifiers, **mutation-checked**: swallow read errors / never no-op / ignore `maxBytes` / always report `created: false`. Each mutant kills exactly one test (`78 pass` → `77 pass 1 fail`, four times).

**`memory-encrypt-loop.ts` is the one that most deserved it.** `if (existsSync(out) && !force) skip;` then `writeFileSync(out, ...)` is the check-then-create race in its textbook form, and the payload is an **age envelope** — `--force`-less mode exists precisely so a re-run cannot destroy one. It is now `exclusive: opts.force !== true`, which asks the kernel, the only participant that can see both halves at once; the loser gets `already-exists`, which is exactly the "output exists" the check meant.

**`flash-and-inject.ts` opened the ISO three times** — `"r"` to fstat its size, `"r+"` to inject the key, `"r"` again to stream it at the device. The file that was measured, the file that was keyed and the file that was written to the stick were three name resolutions. It now holds one `"r+"` descriptor for the whole run, with an explicit `fsyncSync` replacing the flush the old close provided.

## Not migrated — three sites where the second open IS the point

| alert | site | why |
|---|---|---|
| #259 | `flash-and-inject.ts` device read-back | the re-open is the assertion |
| #256 | `esp-inject.test.ts` persistence check | the re-open is the assertion |
| #811 | `bus/claim.ts` lock recovery after EEXIST | no fix exists |

The first two re-open deliberately, to read back what actually landed on the device / in the file. Reusing the write handle would assert only that the bytes this process wrote are the bytes this process wrote — **a check that cannot fail, which is worse than no check.**

The third has no fix available. An `EEXIST` from `openSync(lp, "wx")` **is** the discovery that a lock exists, and no syscall both fails on collision and hands back the colliding object, so every correct lock-recovery path opens twice. The race that mattered there was already closed in an earlier change (the holder PID and the mtime now come from one descriptor); what remains is the shape, not a defect.

Each of the three carries a comment saying so, so the next reader does not "fix" it into vacuity.

## Modes

Every migrated repository write passes `mode: 0o644` — the mode `writeFileSync` produced under the repo umask, kept exactly, because `writeFileOwned` defaults to `0o600` and a repository file only its writer can read is a change nobody asked for. The **one** exception is the age envelope, which takes `0o600` deliberately and says why in the code.
