## Description

Ferries a third-party video transcript on the "abstraction agent" preprint, plus its comment thread, and writes up what the loop is and where it plugs into what we already have.

## The three claims worth the files

**1. It is elicitation, not distillation — and the difference is the property we already protect.** Distillation moves weights into a small opaque model. This moves the *names and definitions of the axes* into text a human can disagree with per-axis, before any data. Our own good-meter test — *anyone can inspect it and agree to the rules* — fails a distilled network however accurate, and passes an elicited state space. That is why the thing Aaron said he was trying to avoid keeps coming back: what he was avoiding was distillation, and this is the other one.

**2. Every pruning step in the loop restates a rule already carved here.** Drop constant variables **is** the vacuity class (an axis nothing varies on cannot discriminate). Drop highly-correlated variables **is** *"too many correlations is a warning, not a confirmation signal."* Validate only through the solver **is** toy-until-falsified, with the solver as the falsifier. And the rover example — two rovers both averaging 6, a generalist and a volcanic specialist — is the raw-vault sentence stated as geometry: collapsing them to one number is a merge that produced one surviving value.

**3. The result the talk does not state: an LLM proposer's value is bounded by the falsifier's LATENCY, not by the proposer's quality.** Worked instance from today on #17249 — two confident, fluent, wrong hypotheses about a CodeQL alert, each refuted in ~4s by the local CLI, before the surviving variable (*which binding the barrier applies to*) was found. Against CI-only feedback the same three-hypothesis search costs three gate runs. Registered `toy`, argued from one instance, and falsifiable by holding the proposer fixed and varying only latency. It lands on the audit-vs-time-to-commit thread: shortening the gate is not only a cost saving, it raises the value of every proposal the fleet makes.

## Aaron's position, held separately (§4a)

He replied in the thread that changing model design is irrelevant because the problem is **turn-based**; what is needed is context-window compression that keeps long-running context and ontologies, and we should look for **ontology reduction over either model or harness upgrades**.

That reframes the paper: the elicited state space is not primarily a solver input, it is an *ontology reduction* — and the solver is what keeps the compression honest, which is the part every other compression scheme lacks. His claim and mine reach the same negative (the binding constraint is not the model) by different routes and give different positives, so the doc holds both rather than merging them: **latency sets how cheaply an axis is found; retention sets whether it must be found again.** Together they are the ratchet, with an elicited retained axis as the artifact.

And it is testable here, because the repo has been running it for months — the carved-sentence rule, the `MEMORY.md` hub (210KB → ~1.5KB), the `CURRENT-*` fast path, the DV2.0 hub/satellite split *are* ontology reduction aimed at exactly that boundary. Still `toy`: nobody has run the before/after, and the model-version confound is real.
