## Description

Four js/file-system-race alerts (high), which are two alerts twice: 557/558 on
src/Renderers/website/vite.config.ts and 576/577 on
demo/identity-dla-site/vite.config.ts, at readFileSync (line 33) and
writeFileSync (line 46). The two files were BYTE-IDENTICAL, so this is one
defect with two copies -- and nothing keeps them in sync, which makes "fixed in
one, not the other" the natural failure. Both are patched; diff between them is
still empty afterwards.

THE EXPLOIT, DEMONSTRATED RATHER THAN ASSERTED. trimLogFile resolved logPath
FOUR times -- existsSync, statSync, readFileSync, writeFileSync -- and decided
on the first two whether the last would truncate. Same fixture both times: a
5890-byte file and a browserConsole.log symlink pointing at it.

  CONTROL (old code):  victim 5890 -> 588   truncated someone elses file: true
  SUBJECT (new code):  ELOOP               victim 5890 -> 5890, untouched

THE FIX. openSync(logPath, O_RDWR | O_NOFOLLOW) resolves the path exactly once;
neither O_CREAT (this function must never bring a log into existence) nor
O_TRUNC (it must never empty one before reading it). fstatSync(fd) instead of
statSync(path), so the size deciding the trim belongs to the file the descriptor
already holds. readSync / ftruncateSync / writeSync all name the descriptor, so
no window remains to swap the name. ensureLogDir drops its existsSync guard --
mkdirSync({ recursive: true }) already succeeds when the directory exists, so
the guard bought a second path lookup and no safety.

TWO DEFECTS THE ALERT DID NOT NAME.

1. catch { /* ignore trim errors */ } is a handler that cannot fail. A log that
   had stopped trimming for any reason grew without limit and said nothing. The
   new handler separates the one expected case (ENOENT -- no log yet, which is
   the do-then-interpret answer to "does it exist") from everything else, which
   now warns with its errno.
2. readSync may return short. Decoding the whole buffer regardless would append
   the untouched tail of the allocation into the log it is trimming, so the
   decode is bounded by bytesRead.

CHECKED CASE BY CASE:

  1. missing file       -> ENOENT, quiet return, and does NOT create the file
  2. file under maxSize -> untouched
  3. file over maxSize  -> 4890 bytes -> 590; keeps line-499, drops line-0
  4. symlinked path     -> ELOOP, target untouched (control above truncates it)

Both sites still build: pnpm run check + vite build rc=0 for the website;
identity-dla-pages-build.ts -- the entry the deploy itself runs -- rc=0 for the
demo.

SCOPE, HONESTLY: this is dev-server-only code (the plugin runs under
configureServer, so a production vite build never reaches it). That lowers the
severity and does not change the disposition -- the attack needs local write
access to the project directory, which is what a developer machine running a dev
server hands out.
