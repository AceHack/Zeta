## Description

The comment landed two commits ago predicted "a large reduction in the cancellation RATE"
after scoping `cancel-in-progress` to pull requests. That prediction was WRONG, and acting on
it would have caused the fix to be reverted.

Measured on `main`, 2026-09-10, the first six completed runs after the change:

  cancellation rate                       69% before  ->  67% after   (barely moved)
  cancelled runs that had STARTED a job   4 of 4 before (2-6 jobs each)
                                          0 of 4 after  (0 jobs, 0 started)

The RATE is the wrong metric. The NATURE is the right one.

Before the change, cancellation killed analyses that were ALREADY RUNNING -- real work
destroyed, and the alert baseline left stale, which is the entire defect. After the change it
only drops QUEUED duplicates that had done no work. That is the pending-supersede case
already documented here, and it is harmless: nothing was computed, so nothing was lost.

Under a fast push cadence the queue-supersede case dominates the count, so the headline rate
stays high while the harm goes to zero. A reader checking only the rate sees 67% and concludes
the fix did nothing.

Corrected falsifier -- count cancelled runs whose jobs actually STARTED:

  gh api ".../actions/runs/<id>/jobs" --jq '[.jobs[]|select(.started_at!=null)]|length'

Zero is the fix working. Non-zero is the fix not applying, and is the ONLY reading that
justifies revisiting the setting.

This is the same failure this whole thread is about, pointed at my own check: a measurement
that cannot distinguish the thing it is supposed to detect. The rate could not tell a
destroyed analysis from a superseded queue entry, so it would have reported a working fix as
a failed one -- and the remedy for a "failed" fix is reverting to the configuration that
destroyed 64 of 93 analyses.
