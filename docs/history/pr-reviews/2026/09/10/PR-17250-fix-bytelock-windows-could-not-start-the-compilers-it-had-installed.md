## The symptom

Run 34501385444, both Windows legs: WAT, Zig, AssemblyScript and Emscripten all failed with `exited with status null` — **while every one of those tools was installed and reported present**. `status: null` is not a compiler rejecting the source; it is a process that never started. The whole class was invisible because that message reads like a compiler error.

## Two causes, both Windows-specific and both mine

**1. `$GITHUB_PATH` carried bash paths.** Every step here runs under Git Bash, so `/tmp/zigdir/zig-windows-x86_64-0.13.0` is a perfectly good path *to bash* — and meaningless to the Windows Node process that actually spawns the compilers. The wabt step even printed `/tmp/wabt/wabt-1.0.41/bin/wat2wasm`, proving the install worked, and the build could not resolve the directory. `cygpath -w` is Git Bash's own translator; it is applied through one helper the steps source rather than in four copies, so an untranslated path is a *missing call* instead of a typo in one of four.

**2. `spawnSync` does not search PATHEXT.** `spawnSync("zig", …)` cannot find `zig.exe` — that is the shell's job, not Node's. And `.cmd`/`.bat` are a second, different problem: since the CVE-2024-27980 mitigation Node **refuses** to spawn them without `shell: true`, which is exactly what `asc` ships as. `resolveExecutable` walks PATH against PATHEXT and takes the shell route **only** for `.cmd`/`.bat`, so `cmd.exe` is never handed the emscripten argument strings full of `[`, `'` and `,` to re-parse.

`run()` also stops reporting these two things identically: a process that could not start now says so, and names what it resolved to.

## What worked, and is worth keeping

The failure policy from #17247 behaved exactly as designed. All six substrates were attempted rather than the leg dying on the first one, the four that failed were **named** in the log, and the byte-lock's own liveness floor delivered the honest verdict — *"only 4 substrate(s) actually executed (minimum 8)"*. The diagnosis above is readable **because** of that change; under the previous fail-closed step the log stopped at WAT.

Linux and macOS are unaffected by both fixes and were green throughout.
