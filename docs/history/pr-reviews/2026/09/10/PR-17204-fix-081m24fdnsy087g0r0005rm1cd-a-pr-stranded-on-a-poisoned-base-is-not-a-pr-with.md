## Description

## The measurement

Eight open PRs each showed 19-24 failing checks. Read one at a time that is eight broken branches. Measured together it was **one event**:

| PR | base | behind | every failure at |
|---|---|---|---|
| 17173, 17175, 17176, 17177, 17178, 17179, 17180, 17186 | `cf6de5aa` | 15 | `Install toolchain via three-way-parity script` |

A rolling dependency pin went bad and was re-pinned **on main, after their base**. The branches were never broken — they were **stranded**, and the fix is a base refresh, not a code change.

## Why a module and not a shell pipeline

The diagnosis had been reached ad hoc more than once here, and gotten wrong more than once. This is the decision core made reproducible.

## What it refuses to do

- **No check has reached a conclusion ⇒ `unknown` with a reason, never `current`.** An empty failure list on a head whose checks are queued or cancelled establishes nothing. This refusal is the reason the module exists.
- **`cancelled` and `skipped` are the absence of a verdict** — not a pass, not a fail. Measured here: 88% of gate runs on `main` were cancelled by concurrency, and `gh pr checks` renders cancelled as failure, which sent a rerun filter past exactly the runs that needed rerunning.
- **Behind is necessary but NOT sufficient.** A PR 15 commits behind and failing its own unit test returns `own-failure`, and the description says refreshing the base would **HIDE** it. Auto-refreshing on behindness alone buries real defects.
- **Only the latest attempt per check name is judged.** Taking any matching run quoted a stale 08:29 failure as current when the 08:46 attempt had succeeded.
