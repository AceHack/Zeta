## The serial tail did its job, and it refutes the hypothesis on file

```
timeout (1800000ms) waiting for serial markers: ZETA CLUSTER NODE INSTALL COMPLETE.
last 40 serial line(s):
  ...
  [R7] No keypress; proceeding (headless default preserved).
  [R9-breaker] ledger not writable; this attempt is NOT counted (breaker stays blind next boot)
  ERROR: not booted in UEFI mode (/sys/firmware/efi absent). This ISO is hybrid, so it
  will boot in legacy/CSM and then fail at bootloader install AFTER the disk has been
  wiped. Reboot and choose the 'UEFI:' entry for this USB device.
```

**"The guest never started" is refuted.** The guest booted, ran `zeta-first-boot`, ran discovery, probed the disks, and ran the 60-second wipe countdown. It then hit a **fail-closed refusal from the installer, which is behaving exactly correctly** — it even warns that proceeding would wipe the disk and *then* fail.

## The cause, read from the code rather than inferred

There are **two QEMU launchers in this harness, with different firmware**:

| scenario | launcher | firmware |
| --- | --- | --- |
| 2 (`boot-cluster-up`) | delegates to `ci/qemu-full-install-test.ts` (`run.ts:20`, `:243`) | resolves `OVMF_FIRMWARE_CANDIDATES`, passes `if=pflash` — **UEFI** |
| 3, 4 and every other scenario (`run.ts:381`) | `buildQemuSystemBootArgs` (`qemu-state.ts:497`) | `-machine q35`, **no pflash at all** → QEMU defaults to **SeaBIOS** (legacy/CSM) |

That is why scenario 2 clears the UEFI check and 3/4 structurally cannot. The defect is in the **harness's QEMU configuration** — not the installer, not zflash.

## Cost this burns today

Each of scenarios 3 and 4 waits the full `1800000ms` for a marker that **cannot arrive** — the installer already printed a fatal `ERROR:` line. That is **~60 runner-minutes per dispatch spent proving a determined failure**, because the harness has no fail-fast on a known-fatal serial marker. Worth fixing on its own merits.

## Why this is filed rather than fixed

Verifying a fix needs a `workflow_dispatch` measuring ~2.5 h, and **per-VM writable `OVMF_VARS`** in the multi-VM harness is a real design decision (`multi-vm.ts` boots more than one guest; one shared VARS file means two guests writing the same NVRAM). Landing an unverified CI behaviour change is the thing this audit is about. The proposed shape, including the falsifier and its mutation control, is written out in the work item.
