AgencySignature v1 stamps `Agent-Model` and `Agent-Runtime` on every commit. Coverage is
perfect -- 425 blocks across the last 300 commits, every field filled. The data was still
unusable for the one question it was collected to answer, because both fields were FREE TEXT
and the values fragmented. Measured over 3000 commits:

  claude-opus-5 / Claude Opus 5 / claude-opus-5[1m] / Claude    1538 commits, ONE model
  claude-code / Claude Code / claude-code-cli / (remote)        1489 commits, ONE harness
  bun + git + gh CLI                                            1324 commits, NOT A MODEL

A corpus that cannot be GROUPED cannot be correlated. "Does this defect class cluster by
model?" is exactly the question the shared-prior thesis needs answered, and `Agent-Model` was
the only column that could answer it.

ALIASES ARE RECORDED, NOT REWRITTEN. History is immutable, and editing 3000 commit messages
to tidy a label is the laundering this repo refuses everywhere else. `registry/agent-identity-
roster.json` records what each identity has historically been written as; normalisation happens
at READ time. The roster is data, so adding a model is a reviewed diff, not a code change.

`none-automation` IS A VALUE, NOT A GAP. A workflow with no model in the loop needs somewhere
honest to say so. Left free, those lanes wrote their toolchain into the model field and became
a phantom sixth model family in every grouping. Naming the absence is what stops absence from
looking like presence.

AN UNKNOWN VALUE IS VISIBLE. `canonicalize` returns null rather than falling back to the raw
string, and `groupByModel` collects nulls under `null` instead of dropping the rows. Falling
back to raw is precisely HOW the fragmentation happened: every new spelling silently became its
own category.

FOUR AXES, EACH WITH ITS OWN AGENDA -- Aaron 2026-09-10: "very similar to human+company as
model+harness ... each one of the 4 all have their same agenda i use in a soft way, it's
inferred agenda, not implied." MODEL carries a training prior; HARNESS carries affordances, and
what a tool makes easy is what gets done; HUMAN is `Credential-Identity`, already on every
block; COMPANY is the vendor added here -- which is the layer `rho-is-a-layer-stack` already
names as a nesting layer of rho. They are not interchangeable: a defect clustering by VENDOR is
a training claim, one clustering by HARNESS is a tooling-affordance claim, and conflating them
attributes a tool's shape to a model's prior.

THE REGISTER RULE, pinned in the file because it governs how this may ever be extended.
Aaron: "in our system only self claimed agendas are implied" and "all other agendas are
inferred based on chosen oracles."

  IMPLIED  = SELF-CLAIMED. First-person authority, taken as given.
  INFERRED = read off behaviour BY A CHOSEN ORACLE. A reading, never authoritative.

So THIS FILE CONTAINS NO AGENDA FIELD, and a test enforces that. Every value here is an
IDENTITY -- which model, which harness, whose vendor -- a checkable third-party-observable
fact. An agenda is an inner state, and `engagement-profiles` holds those are asked about and
believed, never inferred. And because inference is oracle-relative, any schema that ever does
store one must store a TRIPLE -- the reading, the oracle that produced it, the evidence it was
read from. Dropping either of the last two converts a chosen reading into an asserted fact
about a person or a model, which is the smuggling `dual-use-detection-is-neutral-oracle-decides`
forbids. Grouping evidence by author is a METER; attributing purpose to that group is an ORACLE.
