## Description

Continues #17271 (merged). After a merge request opens, the organization now follows it up by itself, checks every change it makes and every answer it gives, and does what the organization has configured.

## What changes

1. **The organization watches its own merge requests.**
   - **Run profiles** (`org run-profile set|list`) store how each run starts: run-org's arguments, non-secret environment, the poll interval and a maximum run time. An environment key that names a secret is refused.
   - **A watcher** (`bun watch-org.ts --org <id>`) looks at each profile on its interval. It starts a run only when something is new:
     - feedback that was polled or filed by a webhook;
     - an answer that is still owed;
     - an item that was never decided;
     - an after-open step that has not run yet.

     It will not restart for the same reasons more than once every 6 intervals, and it stops an overrunning run by PID.
   - **One run per store:** run-org takes `<store>/run.lock` before touching anything. That covers runs a person starts by hand, too.
2. **What follows an opened MR is configuration** (`changeRequests.afterOpen`, for example `comment=aireview`).
   - It runs once per request.
   - A comment already on the request (for example one a person posted by hand) counts as done.
   - The org's own comment is never raised as feedback.
   - It is required where asked: `org configure` raises it, and run-org refuses to start while it is unstated.
3. **A follow-up's code is reviewed like the original work, before it is pushed.**
   - The item's `implementation_review` and `qa_uat` gates review every commit since the last one people saw, each by a gate owner other than the hat that made the change.
   - The reviewer must show that each fix's test fails without the fix.
   - A rejection pushes nothing and leaves the items open with the reviewer's reason.
4. **Every answer to a reviewer is checked before it is posted.**
   - A read-only session confirms each claim against the checkout and the request's current description.
   - An answer that fails the check is withheld and its item reopened.
   - If the check cannot run, nothing is posted.
5. **A rewritten description carries what reviewers were told.**

    <pre>
    Checked this one rather than waving it through, and it is a **real race that is deliberately handled** — not a defect, and not one that reading through a handle would close.

    The flagged pair is `openSync(path, "wx")` throwing `EEXIST` (the check) and `readFileSync(path)` on the next line (the use). Between them the holder can release, or release and be replaced. Every one of those outcomes lands somewhere correct:

    | what happens in the window | what the code does |
    |---|---|
    | holder releases, file gone | `readFileSync` throws → `held = undefined` → `rmSync` is a no-op → loop retries the `wx` open and **acquires** |
    | holder releases, a new holder acquires | reads the **new** owner, `isRunning(new pid)` → returns `heldBy` the new holder |
    | file present, owner alive | returns `heldBy` — the intended path |
    | file present, owner dead | stale → removed → taken over, once (`attempt === 1`) |

    The `EEXIST` **is** the atomic discovery — `O_CREAT|O_EXCL` is the thing doing the mutual exclusion, and it is not the part CodeQL is pointing at. The read that follows only answers *who* holds it, which is advisory, and its failure is already routed to the stale-takeover path.

    **Why the usual remedy does not apply here.** `FileSystemRace.ql` stops flagging when the use takes a **handle** rather than a path. That would silence this alert without changing anything: the window is between the `wx` open and the *next* open either way, and on the contended path there is no fd to reuse — the `wx` open failed, so no handle exists. Rewriting it to `openSync(path, "r")` + read-from-fd would move which call the query sees and close nothing. That is gaming the detector, which this repo refuses, so I have not done it.

    One thing genuinely worth knowing, and it is a *choice* rather than a slip: an **unparseable** lock file is treated as stale and removed, so a corrupt lock belonging to a live process would be taken over. That is the deliberate reading of "unreadable ⇒ take over", and `release()` guards the other direction by re-reading and comparing pid before removing, so a run that outlived a takeover never deletes its successor's lock.

    Resolving — the finding is accurate about the shape and the handling is correct. Not dismissed in the security tab; the alert stays open and visible.
    </pre>
