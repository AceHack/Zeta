## Description

## What this is for

An epic gets a feature branch **unless** it is a catch-all bucket — `AIAGENT-796` and its kind — in which case its stories and bugs branch from the trunk and merge back individually. Configurable, as part of the SDLC surface rather than beside it.

## The first attempt was the thing not to build

It added a `branchBuckets` field to the org record, three `org bucket` commands, and its own path into the runtime: a **fourth parallel configuration system**, bolted next to the SDLC layer built for exactly this, and the next deterministic knob would have needed a fifth. Reverted whole.

## What replaces it

A third member of the surface that already exists:

| | read by | says |
|---|---|---|
| practice | an agent | which skills to reach for, and the process in words |
| directive | an agent | what holds regardless of what is being done |
| **setting** | **the runtime** | **what the process DOES at a mechanical decision** |

Same scoping, same required reason, one place to look — `org practice list` shows all three.

```bash
org setting bind --setting integration_branch --value direct \
  --for AIAGENT-796 --why "..."
```

`integration_branch` has three states and the third is the usual one:

- `direct` — no branch here, and nothing under it gets one either
- `collect` — a branch, even where the shape rule would not give one
- unset — the shape decides (two or more code-producing items)

Scoped by **work id or ticket key**, matched against both, because the two vocabularies belong to different readers: an operator writes `AIAGENT-796` and the cascade calls the same node `proj-009`.

## Why this cannot be derived

Measured against the real project rather than argued:

```
AIAGENT-796  "Dev Portal: Stabilization"   148 children, years of unrelated work
AIAGENT-1519 "Agentic TPM Overhaul"         12 children, one coherent feature
```

Both collect. Only one is a feature. A single branch holding 148 unrelated fixes is a second trunk that never merges, and every fix on it waits for every other. What separates them is **coherence**, which no property of the cascade exposes — a judgement made once per epic, which is what configuration is for.

A child-count threshold was the obvious alternative and is worse than nothing: it would call a twenty-story feature a bucket, silently, in a place nobody would look.

## The defect the mutation matrix found

An **organization-wide** `integration_branch` was accepted, stored, listed as configuration — and filtered out of the decision, because the lookup read only scoped rows. "We do not use feature branches" is a real thing to say and the command claimed to have stored it.

The fix needed **two lookups**, because two different questions were being conflated:

- *"was THIS item singled out?"* → scoped rows only
- *"does this collection carry a branch?"* → scoped, then organization-wide

Reading org-wide in the first made a blanket `direct` short-circuit at the **leaf**, so an epic explicitly set to `collect` never got its branch. It also needed one more true rule — **a leaf is never a collection** — without which a blanket `collect` made every story "take" the branch and therefore get none.

## Verified

Against the live registry with `AIAGENT-796` set to `direct`:

```
AIAGENT-796   collects=2   base=main                   (straight to trunk)
AIAGENT-1519  collects=2   base=feature/AIAGENT-1519    (feature branch)
```

Identical shape, opposite outcome, configuration alone.

## Evidence and its limits

Mutation matrix **16/17**, and the runner verifies its own restore — hash before, restore, re-hash, refuse to continue on a mismatch. That is a direct response to an earlier pass whose matrix left a function body empty and reached a commit.

The one survivor is the `settings` pass-through on the collection-**landing** call. It is unreachable from the runtime harness: landing needs a Done collection and a real-fidelity change port, and a seeded fully-Done cascade did not reach it either. The rule itself is covered in `branch-topology.test.ts` with and without a `direct` setting, so what is unproven is narrowly that the runtime hands its settings to that one line. It is stated in place in the test file rather than left silent; the honest place to close it is an end-to-end run over real git where a feature branch actually lands.
