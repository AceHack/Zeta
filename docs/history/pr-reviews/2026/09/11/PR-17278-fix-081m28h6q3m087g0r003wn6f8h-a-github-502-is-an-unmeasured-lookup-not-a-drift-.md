## Description

`drift (loud)` went red on **two merged PRs** — #17275 and #17276 — with nothing drifted:

```
error: GitHub API 502 for .../actions/runs/34508975922/jobs?per_page=100
  at ghJson (drift-loud.ts:921) → fetchRun → main
```

A single transient 502 threw out of `fetchRun` and rendered as a failing check. That's the conflation this repo already carved, in the agencysignature workflow's own words: a failing lookup *"would surface as the pipeline's status and be read as 'the claim is refuted', when it is in fact 'the lookup did not happen'."*

And this file **already had the vocabulary** — its liveness path prints *"UNVERIFIABLE on this attempt … not verified, not broken"*. It just never applied it to the API calls it's built out of.

## The split

| | |
|---|---|
| **transient** — 429, 500, 502, 503, 504, transport | retry, then **UNKNOWN** |
| **answer** — 400, 401, 403, 404, 409, 422 | loud and **unretried** |

Retrying a refusal only spends the budget to be told no again, more slowly. A truncated body or bad JSON stays fatal exactly as before. Backoff is bounded and jittered (400/1200/3000ms) so a fleet of lanes hitting one degraded edge doesn't resonate.

At the entry point a `GhLookupUnavailable` exits **0, loudly** — an `::warning` plus a sentence saying drift was **not measured**: *"not clean, not dirty, UNKNOWN. Re-run the lane to get an actual reading."* Exit 0 matches the liveness precedent directly above it; what must not happen is the absence of a reading passing as a clean bill of health. Every other error still throws.

## Why fix a non-blocking lane

It doesn't gate merges — which is exactly the danger. **A drift lane that reds on upstream weather teaches its readers to ignore it**, and an ignored detector is worth less than no detector: it costs the CI minutes *and* supplies the belief that something is watching.

    Checked, and this one is a false positive — the guard is the next line.

    The loop runs `GH_RETRY_DELAYS_MS.length + 1` times on purpose: one initial attempt plus one retry per configured delay. On the final iteration `GH_RETRY_DELAYS_MS[attempt]` is indeed a read past the end — and in JavaScript that is `undefined`, not an out-of-bounds fault, which is exactly what line 968 tests:

    ```ts
    const delay = GH_RETRY_DELAYS_MS[attempt];
    if (delay === undefined) break;
    ```

    This is not incidental. `tsconfig.json` has `noUncheckedIndexedAccess` on, so the read is typed `number | undefined` and the compiler *requires* the check before `delay` can be used as a number. The code cannot reach `setTimeout` with an out-of-range index, and a test that removed the guard would not compile.

    So all `length` delays are used, there are `length + 1` attempts, and the fall-through raises `GhLookupUnavailable` — which is the whole point of this PR: a 502 is an unmeasured lookup, not a drift finding.

    Resolving. If the same rule fires here again I will restructure the loop to index `[attempt - 1]` under an `attempt &gt; 0` guard so the read is in-bounds by construction rather than by an adjacent check.
