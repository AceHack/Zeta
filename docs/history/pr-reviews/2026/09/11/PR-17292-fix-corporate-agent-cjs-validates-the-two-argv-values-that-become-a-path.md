## Description

## What this does

Two real defects in `tools/agent.cjs`, the model-client added in #17249. **Neither
was reported by CodeQL** — they are defects the sweep found while reading the file
that CodeQL *did* flag, and they are the only things in the current open-alert set
that a code change can honestly repair.

### 1. Path injection on the two argv values that become a filesystem path

`main` built `mkdirSync(join(OUT_DIR, workId))` and
`join(OUT_DIR, workId, gate + ".md")` from unvalidated argv. `workId` is not this
process's own invention: it travels from a ticket key that `serve-work.ts` accepts
off an inbox, which is exactly why *that* file has validated the same shape since
CodeQL found the pattern there. A `workId` of `../..` wrote the organization's
document outside `ORG_DOCS_DIR`.

Both values are now tested against the shared predicate in
`src/Core.TypeScript/corporate/safe-path-segment.ts` — the module whose own
docstring predicted a third site, after `serve-work.ts` and `uat-three-criteria.ts`.
**Test and refuse, never mangle**: a malformed value exits 2 and says which one it
was. `agent.cjs` is CommonJS run by `node` and cannot import a `.ts` module, so the
pattern is restated there and then **pinned** to the original by a test that reads
both files, requires exactly one `/^…$/u` literal in each, and fails if they drift.

### 2. Check-then-use file races (CWE-367), three sites

Every read in the file was gated by `existsSync(p)` first. That is the shape
`src/Core.TypeScript/hygiene/lint-check-then-use-file-races.ts` refuses — and
could not see here, because it scans TypeScript and this file is `.cjs`. Reads now
happen once and interpret their own `ENOENT`; `readdirSync` carries
`{ withFileTypes: true }` so an entry's kind arrives with the listing rather than
from a second `statSync`; and a context document that will not open is **said on
stderr** instead of dropped in silence (the old comment claimed the absence "says
so by omission", but the only surface carrying it was a `relied on <ref>` line
that never appears — indistinguishable from a step handed nothing).

A now-dead `.filter((t) => t !== "")` was removed rather than left: it guarded
against a read that no longer happens there, so it had become a check that cannot
fail.

## Alerts deliberately NOT fixed, and why

Read at CodeQL CLI **2.27.0**, against the query sources, not from memory.

### `tools/agent.cjs` — #951 `js/file-access-to-http`, #950 `js/http-to-file-access`

These are the tool's purpose. It reads `.claude/skills/*/SKILL.md` and sends them
to a model (#951: file data reaches an outbound request), and it writes the
model's document to disk (#950: file content comes from a response).

`FileAccessToHttpCustomizations.qll` defines exactly two sanitizers — a `.length`
property read, and a generated-code expression. `HttpToFileAccessCustomizations.qll`
declares an abstract `Sanitizer` with no concrete member reachable here. There is
no barrier any correct version of this program could pass through: closing these
means deleting the feature. #950 is the exact twin of **#805**, already closed as
`won't fix` on `f4-question-bias-run.ts` with the same reasoning.

What *was* fixable behind them — the unvalidated path and the racy reads — is
fixed above.

### `js/file-system-race` — #811 `bus/claim.ts:80`, #259 `zflash/flash-and-inject.ts:134`, #256 `zflash/esp-inject.test.ts:89`

All three are `openSync(p, …)` followed by a second `openSync(p, …)` on the same
path variable, and all three already carry an in-code account of why the second
open is the point:

- **#256 / #259** — *the re-open IS the assertion*. Reusing the write handle would
  prove only that the bytes this process wrote are the bytes this process wrote: a
  check that cannot fail, which is worse than no check.
- **#811** — the `EEXIST` from `openSync(lp, "wx")` *is* the discovery that a lock
  exists; learning who holds it requires opening the file it named. No syscall both
  fails on collision and hands back the colliding object.

`FileSystemRace.ql` excludes a use whose path argument is a file *handle*
(`not getAFileHandle(…).flowsTo(use.getPathArgument())`) and pairs check-to-use
through `AccessPath::getAnAliasedSourceNode`. So the only ways to silence these are
to reuse the handle (destroys the assertion) or to recompute the path into a
differently-rooted variable (pure detector-gaming). Both are refused.

### #798 `actions/untrusted-checkout/medium` — `.github/workflows/gate.yml:327`

The flagged region is the `detect` step's `run:` block (327–480), not the checkout.
The checkout above it was already moved to `ref: github.event.pull_request.base.sha`,
so **no untrusted code is on disk**; `detect` fetches the head *object* to run a
two-dot `git diff`, and the classifier it then runs (`bun path-domains.ts`) comes
from the base tree.

Removing the residual finding means not fetching the head SHA at all — replacing a
provably fail-closed local diff with a paginated REST call — which changes the
failure semantics of a job that gates the whole `gate` check. That is a maintainer
decision about a critical path, not a sweep's call.
