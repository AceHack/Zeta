## Summary

The USB installer targets home hardware, which loses power. Every existing `first-boot-replica.ts` lane tests only the FIRST boot converging — nothing tests that a *converged* cluster survives an unclean stop (stale leases/locks, stuck PVC attachments, an unclean k3s datastore stop, Cilium not reattaching BPF programs, Argo CD re-sync storms, non-idempotent seeding Jobs re-running).

This adds an **optional stage 8** (`--power-cycle`, armed in CI) that runs after stage 7:

1. **Baseline** after stage 6/7 settle: per-app sync/health, per-container `restartCount`, seeded internal Secret data hashes + resourceVersions (derived from `dev-cluster/lib.ts`'s `DEV_BOOTSTRAP_SECRETS`/`DEV_SHARED_SECRETS` — never a third hand-written copy of the six credentials `internal-secret-seeding.yaml` mints), and Bound PVC bindings.
2. **Hard power-cut**: `docker kill -s KILL` (not a graceful stop), keeping the named k3s data volume, then `docker start`. Downtime recorded.
3. **Wait** (bounded ~15min budget) for API up, node Ready, Cilium Ready, every previously-Healthy Application Healthy again. Then **soak** ~300s.
4. Four pure, independently-tested rules compose into `RECOVERED` / `NOT_RECOVERED(app, reason)`:
   - `appsFailedToRecover` — every previously-Healthy Application must be Healthy again
   - `containerCrashLoopsAfterRecovery` — **reuses** stage 6's own `restartCountRegressions` + `classifySoakRegressions` (including its spire-agent known-non-metal allowlist) rather than duplicating them. A single restart caused by the power cut itself is expected and does not fail: the soak window opens only once recovery is confirmed, so that restart is already baked into both sides of the before/after comparison.
   - `secretDataChangedAfterRecovery` — idempotency; compared by SHA-256 hash only, raw values never read into a log line
   - `pvcsReboundAfterRecovery` — a PVC bound to a different volume is data loss
5. Per-issue table rendered into the JSON report and `$GITHUB_STEP_SUMMARY` via `renderPowerCycleVerdictMarkdown`.

`internal-secret-seeding.yaml`'s Jobs were confirmed already create-only (`kubectl create`, never `apply`/`replace`) — the gap this closes is the *absence of a check*, not a defect in the seeding mechanism.

Workflow `timeout-minutes` raised 150→180 for the added ~20min recovery+soak budget.
