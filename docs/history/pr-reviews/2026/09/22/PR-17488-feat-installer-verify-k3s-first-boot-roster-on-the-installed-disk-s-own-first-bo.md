## Summary

Closes the literal "plug in the USB and run it" gap named in WP11: nothing
before this booted the **installed disk itself** with network, past a login
prompt, and watched k3s + the first-boot roster converge. The ISO lane's QEMU
scenarios stop at a serial marker on the installer side (`ZETA CLUSTER NODE
INSTALL COMPLETE`), and phase 2 deliberately reboots the installed disk with
no network (`scenarios.ts` says Kubernetes/ArgoCD health is out of scope).
`nixos/tests/k3s-first-boot-roster.nix` proves the k3s modules converge but
boots them directly in a nixosTest sandbox — never through disko
partitioning, `zeta-install.sh`'s host selection, or the installed
`configuration.nix`'s real import graph.

- `full-ai-cluster/nixos/modules/zeta-first-boot-k3s-verify.nix` — a oneshot
  systemd unit on the installed disk, **gated OFF by default** via
  `ConditionPathExists` on `/etc/zeta/qemu-k3s-first-boot-verify` (same
  mechanism `zeta-first-session.nix`'s QEMU-only demo already uses). On its
  first multi-user boot it prints one JSON verdict to serial with six named
  checks + timings: `bootedMultiUser`, `k3sServiceActive`, `nodeReady`
  (Cilium up), `helmJobs` (per rostered `HelmChart`, complete + failed
  attempts), `rootLanded`/ROOT_LANDED (the same deploy-controller-retry
  question `k3s-first-boot-roster.nix` asks), `noBadPods`
  (ErrImagePull/ImagePullBackOff/CrashLoopBackOff, with restart counts).
- `qemu-full-install-test.ts` phase 3 (`QEMU_K3S_FIRST_BOOT_PHASE=1`) —
  reboots the SAME installed disk a second time with a user-mode NIC (explicit
  `bootindex` on both disk and NIC, to avoid the UEFI PXE boot-order stall
  `buildQemuDiskBootArgsPure`'s own comment already names), waits for the
  verdict, fails the run on any of the six checks, and appends a
  human-readable summary + the raw JSON to `$GITHUB_STEP_SUMMARY`.
- A tenth ESP marker, `/zeta-qemu-k3s-first-boot-verify`, threaded through
  `zflash`'s `lib.ts`/`file-backed.ts`/`injection-rail.ts` (classified
  `public-identifier`, `satisfies`-checked exhaustive) /
  `prepare-boot-image.ts`, plus a `zeta-install.sh` probe that stages it onto
  `/mnt/etc/zeta` at install time. Catalogued in
  `full-ai-cluster/INJECTION-POINTS.md`.
- A new workflow step in `build-ai-cluster-iso.yml`, **`workflow_dispatch` +
  daily `schedule` (05:23 UTC) only — not on the PR path.** The bring-up this
  checks is budgeted 45-70 min by the nixosTest lane that already asks the
  same question (that lane's own header); putting it on every PR touching
  the installer/k3s paths would slow the already-heaviest ISO lane for no
  benefit to the merge-gating question PRs actually need answered.
