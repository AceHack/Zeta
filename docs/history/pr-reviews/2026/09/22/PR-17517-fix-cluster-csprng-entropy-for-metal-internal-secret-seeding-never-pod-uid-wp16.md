## Description

## Threat

`full-ai-cluster/k8s/bootstrap/internal-secret-seeding.yaml` (WP14, merged in #17505/#17509)
mints the six INTERNAL first-boot Secrets (`grafana-admin-credentials`, `ziti-admin-credentials`,
`opensearch-admin-credentials`, `forgejo-initial-admin`, `zeta-blob-store`, `redis-auth`) by
drawing randomness from each seeding Job's own pod UID via the Kubernetes Downward API. That is
weak on two counts:

- A pod UID is readable by anyone with `get`/`list` on Pods in the namespace, and it also shows up
  in Kubernetes events, audit logs, controller logs and `kubectl describe` — Job pods persist until
  their TTL, so the "secret" was derivable by anyone who could see the completed pod.
- A UUIDv4 carries ~122 bits of entropy sourced from the apiserver's ID generator, which is not a
  CSPRNG designated for secret material.

## Fix

Replaces the Downward API draw with a `/dev/urandom` read that happens **inside** each pod and
never appears in any API object:

- A new `draw-entropy` initContainer (`busybox`, pinned by **tag AND digest** — the one container
  in this manifest with a shell) runs first, reads 32 bytes from `/dev/urandom`, hex-encodes them
  (256 bits — over double a UUIDv4's entropy) and writes the result — plus, for the two SHARED
  credentials (`zeta-blob-store`, `redis-auth`), every templated config fragment that embeds it —
  to an **in-memory** (`emptyDir: {medium: Memory}`, tmpfs, never disk) volume shared with the
  rest of that pod.
- The `kubectl` containers (still the already-pinned, shell-less `registry.k8s.io/kubectl:v1.32.3`)
  read the value off that file with `--from-file`, never as an argv token or env var — so the
  drawn value never appears in a Pod spec, event, annotation, log line, or `kubectl describe`
  output.
- `ttlSecondsAfterFinished` tightened 86400 → 300 (defense in depth; a completed Job's pod has no
  further use once `kubectl create` exits).
- `image-source-provenance.json` updated (via its own `--refresh`) to add the pinned
  `busybox:1.36@sha256:...` reference. (See note below on how this refresh was run.)

## A side-finding while updating the ledger

Running `image-source-provenance.ts --refresh` with a `gh` token that has `rate_limit` access but
lacks the `read:packages` OAuth scope silently downgrades every previously-measured `ghcr.io` row
from `public`/`found` to `unknown`/`absent` — the packages API returns 403, which the code
(intentionally) cannot distinguish from "package genuinely absent", and `ghUsable()` only checks
`rate_limit`, so the existing protective fallback never engages. Reproduced locally; ran the
refresh with the packages-API half explicitly disabled instead (the code's own documented
fallback path) so only the new `busybox` row and stale-tag pruning changed. Filed as a follow-up
finding for `ghUsable()` to actually detect the missing scope rather than trusting `rate_limit`
alone.
