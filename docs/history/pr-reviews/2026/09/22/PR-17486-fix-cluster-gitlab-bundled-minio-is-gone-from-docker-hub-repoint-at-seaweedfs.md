## Description

## Summary

`full-ai-cluster/k8s/applications/gitlab/Application.yaml` (chart gitlab 8.7.0, automated sync, wave 30) defaults `global.minio.enabled: true`, pulling `minio/minio:RELEASE.2017-12-28T01-21-00Z` and `minio/mc:RELEASE.2018-07-13T00-53-22Z`. Both repositories return 401 for every tag on Docker Hub (measured directly against `registry-1.docker.io` with a valid anonymous pull token; control test against `library/alpine:latest` succeeded) -- the same MinIO community-edition Docker Hub withdrawal (~2026-09-11) that `object-store/BLOB-STORE-CONTRACT.md` already documents for the cluster's own former standalone `minio/` Application. A first-boot sync with the bundled subchart enabled ImagePullBackOffs on both, and the `minio-create-buckets` Job GitLab's object storage depends on never completes.

**forgejo** (the either/or alternative) is unaffected -- its published default values carry no `minio` reference at all. **tempo** uses a `local` trace backend, not minio. **loki** and **mimir** already disable their own bundled minio and point at the cluster's SeaweedFS instance.

## Options considered

1. **Repoint at in-cluster SeaweedFS** (chosen) -- the pattern loki/mimir already use.
2. **A still-maintained minio image mirror** -- checked and rejected. GitLab's own image mirror (`registry.gitlab.com/gitlab-org/cloud-native/mirror/...`) carries no minio project at all (searched via the GitLab API, empty result across the whole `gitlab-org` group tree). `quay.io/minio/{minio,mc}` still resolve (both linux/amd64 + linux/arm64), but their newest tags are `RELEASE.2025-09-07` / `RELEASE.2025-08-13` -- no release since, consistent with the same archival `BLOB-STORE-CONTRACT.md` already records (Feb 2026, no further development, no security patches). Repointing at it would re-import the unpatched-object-store posture the cluster already paid down once for its shared store.
3. Document + file a workitem -- not needed since (1) was feasible.

## Change

- `global.minio.enabled: false`; GitLab's consolidated object storage (`global.appConfig.object_store.connection`) and the container registry's own storage driver (`registry.storage`) both point at the in-cluster SeaweedFS instance, sharing the `zeta-blob-store` credential loki and mimir already use.
- `seaweedfs/Application.yaml` gains the five buckets GitLab needs: `git-lfs`, `gitlab-artifacts`, `gitlab-uploads`, `gitlab-packages`, `gitlab-registry` (names match the gitlab chart's own defaults where one exists).
- `dev-cluster/lib.ts`'s `DEV_BLOB_STORE_SECRET` gains `gitlab` as a fourth namespace and two new key shapes (`connection` for the Rails consolidated form, `config` for the registry's storage driver), so `audit-existing-secret-is-minted` stays green without inventing a new credential.
- Re-rendered (helm 4.2.0, chart pulled to a scratch dir per `.mise.full.toml`) and reconciled every downstream measurement the removed `Deployment/gitlab-minio`, `Job/gitlab-minio-create-buckets` and its 10Gi PVC touch: `rendered-storage-claims` snapshot+baseline (-10Gi zeta-local-path), `rendered-resource-requests` snapshot (-150m/-128Mi, both rungs), `storage-profiles.json`'s `ungovernedRequests` row and prose, `single-node-budget.json`'s two prose ledgers, `argocd-health-test.ts`'s cited gitlab PVC total (76 -> 66 GiB), and forgejo's either/or budget comment. Every touched figure is machine-checked (`findLedgerFigureDrift`, `reason-truth.ts`, the storage-claims/resource-requests test suites).
- `infra/gitlab` (the separate, out-of-scope sibling Application) and its entry in `lane-footprints.json`'s image list are untouched -- not in this task's scope.

PR #17475 (image-resolvability) and PR #17479 (registry-mirror-coverage) -- both open, not yet merged as of this PR -- independently measured this same 401 and are cited as corroborating prior evidence. Neither ships a checked-in `image-resolvability.json` snapshot on `main` yet, so there is none to refresh here; if #17475 merges first, that snapshot's gitlab-minio `unknown` rows should be re-run to confirm they disappear.
