## Summary

Two first-boot defects measured on a real NixOS VM boot of the USB first-boot roster (GitHub Actions run [35687536936](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/35687536936), workflow `k3s-first-boot-roster-vm.yml`, branch `claude/first-boot-roster-vm`, PR #17472):

1. **SPIRE's `kubectl` hook image doesn't exist.** The `spire` chart's post-install/post-upgrade/pre-delete hooks derive their `kubectl` image TAG from `.Capabilities.KubeVersion.Version` (chart 0.24.2, `spire-lib.kubectl-image`) whenever `tools.kubectl.image.tag` is unset. k3s reports `v1.35.7+k3s1`, the chart derives `docker.io/rancher/kubectl:v1.35.7`, and rancher has never published that tag (Docker Hub 404) — `helm-install-spire`'s post-install Job `ErrImagePull`/`NotFound`-looped forever on the real VM. Fixed by pinning `spire-server.tools.kubectl.image.tag: v1.35.6` (verified published, multi-arch) in both `full-ai-cluster/k8s/bootstrap/spire-install.yaml` and its ArgoCD twin `full-ai-cluster/k8s/applications/spire/Application.yaml`.

2. **`kubernetes-version.json` was stale.** It declared `1.35.6` while the VM (built from the current `flake.lock`) ran k3s `1.35.7`. Confirmed via nixpkgs at the locked rev (`c25784012c9982bca5b3e0de87e90bbdac8927d3`): `pkgs.k3s = k3s_1_35`, and that package's `versions.nix` declares `k3sVersion = "1.35.7+k3s1"`. Updated the declaration and fixed the gap that let it go unnoticed: `lint-kubernetes-version-agrees.ts` only checks in-repo consumers *against* this file, never this file against the flake lock itself (its own header says so). Added that missing half as a new `nix eval` step in `first-boot-manifest-check.yml`.

## What else changed

- **Class-catcher**: new `full-ai-cluster/k8s/tests/render-kube-version-image-drift.ts` renders every first-boot and catalog chart TWICE (declared Kubernetes version and declared+1 patch) and fails if a chart's rendered image set differs between the two — the one thing that happens when an image depends on the cluster version. Verified to go RED on the pre-fix `spire-install.yaml` and GREEN once the pin landed. Wired into `helm-validate.yml`'s `charts` job for both the bootstrap and catalog scopes, with an offline mutation-proof test alongside it.
- **Catalog search**: checked all 31 external Helm charts + 2 OCI charts in the catalog (every `Application.yaml` and bootstrap `HelmChart` CR) for the same class. One more instance exists — `kube-prometheus-stack`'s `charts/crds/templates/upgrade/job.yaml` — but `upgradeJob.enabled` defaults `false` and nothing here overrides it, so it never renders today; noted in the new checker's comments rather than pinned.
- **`render-first-boot-charts.ts`'s own default was stale too**: it hardcoded `--kube-version 1.33.0` (unrelated to the declaration, and invisible to `lint-kubernetes-version-agrees.ts`'s patterns) instead of reading `kubernetes-version.json` — so the CI render lane for the first-boot roster had been validating against a Kubernetes surface the cluster does not have on every PR. Fixed to default from the declaration, same as `validate-applications.ts` already does.
- **k3d dev/CI lanes aligned to metal**: `dev-cluster/k3d-config.yaml` and `dev-cluster/profiles/ci.k3d-config.yaml` were pinned to `rancher/k3s:v1.36.1-k3s1`, a full minor ahead of the declared metal version; both files' own headers say they exist to mirror the metal substrate, so moved both to `v1.35.7-k3s1` (verified published, multi-arch). `kind`'s node image is **not** pinned in-repo, and `kindest/node` publishes no `v1.35.6` or `v1.35.7` tag at all (only `.0`/`.1`/`.5`/`.8`) — noted rather than forced into an inexact pin.
