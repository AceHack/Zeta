## Description

## Summary

Investigation of why `cilium`, `spire`, `openbao` and `longhorn` sit
`Synced`/`Progressing` forever on the real first-boot roster
(`first-boot-replica.ts` run 35696323545 on main), which matters because a
pending change (#17477/#17497) gates later sync waves on child-Application
health — any provider stuck Progressing stalls the whole catalog on metal.

## Findings table

| App | Resource | Root cause | Classification | Fix |
|---|---|---|---|---|
| **cilium** | `GatewayClass/cilium` | `status.conditions[Accepted]` stuck at the chart's static placeholder (`Unknown/Pending: Waiting for controller`) — cilium-operator 1.20.1 refuses to start its Gateway API controller because the vendored Gateway API CRD bundle (v1.2.1 STANDARD) is missing `TLSRoute`/`BackendTLSPolicy` entirely and ships `ReferenceGrant` at `v1beta1` only, while Cilium's `RequiredGVKs` wants all seven Gateway API kinds at `v1` | **METAL DEFECT** — the bootstrap manifest is applied identically on real NixOS metal; nothing depends on Docker | Bumped `full-ai-cluster/k8s/bootstrap/gateway-api-crds.yaml` to the official Gateway API v1.6.1 STANDARD channel install (verbatim release asset). **Live-verified**: applied the new CRDs to the running replica, restarted `cilium-operator`, `GatewayClass/cilium` went `Accepted=True` within seconds, and a forced ArgoCD refresh moved the Application to `Healthy`. |
| **spire** | `spire-agent` DaemonSet pods | CrashLoopBackOff: `could not open attestation stream to SPIRE server: ... dial udp <clusterIP>:53: i/o timeout`. A control probe (identical hostNetwork+`ClusterFirstWithHostNet` busybox pod) could not reach kube-dns's ClusterIP at all inside the Docker replica, while a pod-network probe reached it fine | **REPLICA ARTIFACT — CONFIRMED on a real NixOS VM, not inferred** | Added two subtests directly to `full-ai-cluster/nixos/tests/k3s-first-boot-roster.nix` (the metal oracle — no container nesting) and ran them on an actual GitHub-hosted KVM VM: hostNetwork DNS resolution to a ClusterIP **PASSED**, and spire-agent's restart count held flat (`[3,3,3,...]`, settled during ordinary startup churn) over a 180s window — **PASSED**. Recorded as a named DIVERGENCE in `first-boot-replica.ts` so the harness reports this as expected rather than an unexplained FAIL. No metal-side change needed. |
| **openbao** | `openbao-0` server container | Comes up sealed: `security barrier not initialized` — no PKCS#11/TPM seal is wired yet and no unseal-shares Secret exists | **EXPECTED, by design, on both the replica and metal today** — the Application.yaml's own header already documents this | None needed; confirmed the ONLY cause is the absent seal material. |
| **longhorn** | `longhorn-manager` DaemonSet | CrashLoopBackOff — no block devices are attached to the Docker replica container | **REPLICA ARTIFACT** — already named in `first-boot-replica.ts`'s `DIVERGENCES` (`no-longhorn-disks`) before this investigation | None needed; confirmed correct and unchanged. |
