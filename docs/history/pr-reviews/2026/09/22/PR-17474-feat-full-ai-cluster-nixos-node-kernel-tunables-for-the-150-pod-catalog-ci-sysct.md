## Description

## Summary

grep found **no kernel tunables** anywhere in `full-ai-cluster/nixos/modules/` — no
`fs.inotify.*`, `vm.max_map_count`, or nofile overrides — on a single-node k3s
control plane running ~150 pods from the Argo CD catalog. This closes that gap and
closes the matching CI blind spot (the Docker kind/k3d lanes run on a stock GitHub
runner kernel, not NixOS, so they could never have caught it).

### The table

| setting | NixOS effective default (measured, not assumed) | required | set to |
|---|---|---|---|
| `vm.max_map_count` | **65530** — kernel compile-time constant `DEFAULT_MAX_MAP_COUNT` (`include/linux/mm.h`, `USHRT_MAX - MAPCOUNT_ELF_CORE_MARGIN`). Not raised by systemd's `sysctl.d/50-default.conf`, nixpkgs' `kernel.nix`, or nixpkgs' k3s module at this repo's pinned nixpkgs rev. | `>= 262144` — [OpenSearch docs](https://opensearch.org/docs/latest/install-and-configure/install-opensearch/index/); our `opensearch/Application.yaml` runs the chart's own `sysctlInit.enabled: false` default, so nothing else can raise this | **262144** |
| `fs.inotify.max_user_instances` | **128** — flat kernel default (`inotify_user.c`, `init_user_ns.ucount_max[UCOUNT_INOTIFY_INSTANCES] = 128`), host-wide per user (no user-namespace isolation here) | ~150 pods' worth of kubelet + config-reloader sidecars + log-tailing agents each open their own instance; kind's own [known-issues doc](https://kind.sigs.k8s.io/docs/user/known-issues/#pod-errors-due-to-too-many-open-files) hits the identical default and recommends 512 | **512** |
| `fs.inotify.max_user_watches` | **dynamic, 8192..1048576** — 1% of non-highmem RAM pages, clamped (`inotify_user.c`) | pinned explicitly so behaviour doesn't depend on which box gets flashed; same kind citation recommends 524288 | **524288** |
| `LimitNOFILE` (k3s systemd unit) | **already 1048576** — nixpkgs' own k3s module (`mkRancherModule`) sets this, matching upstream k3s's `install.sh`; containerd + every pod process fork from that tree and inherit it | met already | *(no change — investigated, found correct)* |

Measured against this repo's pinned `flake.lock` (`nixpkgs` rev
`c25784012c9982bca5b3e0de87e90bbdac8927d3`, `linux_default` = 6.18.108, `systemd`
260.2) by fetching the actual pinned sources from GitHub rather than guessing — a
prior assumption that "recent NixOS raises `vm.max_map_count` by default" does **not**
hold at this pin.

### What shipped

- `full-ai-cluster/k8s/node-tunables.json` — single source of truth (values +
  measured host defaults + citations), read by both consumers below.
- `full-ai-cluster/nixos/modules/k8s-node-tunables.nix` — applies the JSON via
  `boot.kernel.sysctl`; imported from `common.nix` so control-plane, worker-gpu, and
  worker-template all inherit it uniformly.
- `full-ai-cluster/nixos/tests/k8s-node-tunables-eval-test.nix` — eval-only test
  against the **real** `nixosConfigurations.control-plane` / `.worker-gpu`, proving
  both hosts ship every declared value exactly. Registered in `flake.nix` as
  `checks.<system>.k8s-node-tunables-model`, and named in
  `build-ai-cluster-iso.yml`'s "checks this lane is the only evaluator of" list (nine
  eval-only checks becomes ten).
- `src/Core.TypeScript/cluster/node-tunables.ts` (+ `.test.ts`) — the TypeScript twin.
  Nix cannot import TypeScript and vice versa, so the JSON is the coupling. `--apply`
  runs `sudo sysctl -w` for every declared entry; default prints the commands.
- `.github/actions/apply-node-tunables/` — composite action wired into all six
  `live-*` jobs in `k8s-argocd-health-test.yml` (kind, k3d, kind-cilium,
  kind-cilium-included, kind-included, kind-virt), right after `bun install`, before
  cluster creation — so CI now runs under the same limits production ships, and if
  those limits are ever too low for CI's own workload, that becomes visible instead
  of silently absent.

`first-boot-replica.ts` (flagged as a possible concurrent landing under
`src/Core.TypeScript/cluster/`) was not present on `origin/main` as of this branch's
merge — nothing to wire in; noted here for whoever ships it next.
