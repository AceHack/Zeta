## HelmChart retries (ordering evidence)

Real retry counts, read from the one k3s helm-install pod's own
`containerStatuses[].restartCount` (see "bugs found" below — `job.status.failed`
undercounts this to zero): `cert-manager` and `trust-manager` retried while
waiting on Cilium's CNI / cert-manager's webhook respectively, matching the
roster comment's documented intent exactly. `trust-manager`'s install
literally failed with `no endpoints available for service
"cert-manager-webhook"` until cert-manager's webhook was ready — a
service-*readiness* race the file-order comment does not claim to solve,
distinct from the submission-order property it does claim.

## Dual-owner churn (argocd, cilium, cert-manager, spire/spire-crds,
trust-manager, external-secrets)

Two independent signals sampled repeatedly: the k3s-side Helm release
Secret's `resourceVersion` and the matching ArgoCD Application's
`sync.status`. **Local runs (Docker Desktop, 20 vCPU): no churn, either
signal, either run.** **CI run (4 vCPU): `cilium`'s ArgoCD Application
oscillated Synced → OutOfSync ×4 → Synced while its Helm secret's
resourceVersion stayed constant** — read honestly, this is NOT two
reconcilers overwriting each other (the release was never re-installed); it
is ArgoCD noticing transient drift, plausibly Cilium's own agent/envoy pods
restarting during their noisy startup window, and self-healing on its own. A
**calibration gap in the harness**, not a cluster defect, is recorded in the
workitem: the `>=2 status changes` heuristic cannot distinguish one clean
dip-and-recover from genuine repeated fighting, because any single recovery
from an initial `Synced` sample necessarily produces exactly 2 changes.
On the CI run's second measurement, the identical check reported **clean, no
churn** — consistent with a one-off dip, not a persistent property.

## Crash-looping pods

`spire-agent` restarted repeatedly (5-6x, every one of 3 runs) with `could
not open attestation stream to SPIRE server: ... dial udp 10.99.x.x:53: i/o
timeout` — a CoreDNS-under-load symptom from syncing the **full, unfiltered**
`k8s/applications` catalog (45-50 Applications) on a single node with no
capacity planning, not an ordering defect in the bootstrap roster.

## Fidelity finding: the replica's k3s version tracks `kubernetes-version.json` — including its staleness

`docker.io/rancher/kubectl` / `ErrImagePull` was **not** observed on any of
this harness's runs. That is not a disagreement with the real NixOS VM boot
(runs 35687536936, 35688935223), which DID measure it — it is an
**explained, and favourable, consequence of the harness's design**.

`first-boot-replica.ts` derives its k3s image tag from
`full-ai-cluster/k8s/kubernetes-version.json` — deliberately, so the replica
never hand-copies a second version literal to drift from the real one. That
file currently declares `1.35.6+k3s1` (measured 2026-09-01) and is itself
**stale**: the NixOS flake lock the metal image actually builds from resolves
to k3s `1.35.7`. `rancher/kubectl:v1.35.6` exists on Docker Hub;
`rancher/kubectl:v1.35.7` does not — which is exactly the image the real VM
boot failed to pull for the SPIRE post-install hook. The replica ran the
older, available tag and never hit the broken pull; not because the defect
isn't real, but because it was reading a stale-but-internally-consistent
version pin.

PR #17478 (`claude/pin-kube-version-derived-images`) fixes
`kubernetes-version.json` to `1.35.7` and pins the derived kubectl image.
**Once it merges, this replica will automatically pick up the corrected
version on its next run** — no change needed here — and should then either
reproduce the same `ErrImagePull` (if #17478 doesn't fully close it) or
confirm it's fixed. That the replica's fidelity to metal is gated entirely by
one committed file, with no second place to update, is the design working as
intended.

## Divergences from metal (named in the harness's own output)

- Container, not a NixOS VM — no systemd, no k3s preflight units
- `root-application.yaml`'s `targetRevision` patched to this branch (the one
  permitted modification)
- No Longhorn disks, no GPU
- Mount propagation forced shared **post-start**, inside the replica's own
  mount namespace (`mount --make-rshared /`) — NixOS metal's systemd gives
  Cilium a shared root for free; Docker Desktop and the GitHub-hosted runner
  do not, and a container-create-time `--mount ... bind-propagation=rshared`
  of the host's own `/sys/fs/bpf` is refused outright on both

## Bugs found and fixed (six in this harness, none in the manifests)

1. Read-only manifests mount made k3s fail hard at boot (`ccm.yaml` write
   failure) — dropped `:ro`.
2. Cilium needs `/sys/fs/bpf` **and** `/run/cilium/cgroupv2` shared for its
   sibling envoy container — fixed with a post-start `mount --make-rshared /`.
3. k3s's `helm-install-*` Jobs use `restartPolicy: OnFailure` with **one**
   pod, so `job.status.failed` never increments across retries — stage 3 now
   reads the pod's `containerStatuses[].restartCount` instead.
4. Stage 6 silently reported "0 Applications" on a swallowed `catch {}` — now
   logs *why* (kubectl exit code / parse failure).
5. Stage 7's dual-owner check queried `kube-system` for every chart's Helm
   release Secret; the Secret lives in `spec.targetNamespace`, and five of
   the six dual-owned charts target a *different* namespace — the check
   found evidence for `cilium` alone and silently reported "no churn" for
   the rest without ever having looked.
6. A read-then-exists-check TOCTOU (CWE-367) in `buildRoster` and the
   `--with-longhorn-alias` path, caught by this repo's own
   `cross-verify (check-then-use-races)` gate.
