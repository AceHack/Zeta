## Summary

- `k3s-first-boot-roster.nix` boots the REAL first-boot k3s manifest roster (cilium, cert-manager, argocd, spire, trust-manager, external-secrets HelmCharts + root-application) and answers k3s-server.nix comment block #5's open question: does `root-application` land as `Application/zeta-root`, or does it stick behind a kind the API server had never heard of at submission time? It has existed as a flake check since it was written and **nothing ever built it** — `first-boot-manifest-check.yml` only runs `nix flake check --no-build` (evaluates, never realises), and `build-ai-cluster-iso.yml` has no step naming it at all despite a comment claiming the ISO lane runs it.
- Adds `.github/workflows/k3s-first-boot-roster-vm.yml`: daily cron + `workflow_dispatch` + PRs scoped to the roster's own inputs. Mirrors `build-ai-cluster-iso.yml`'s online-VM steps (pinned checkout + nix-installer-action, `--option sandbox false`, ubuntu-24.04). Uploads the VM test log as an artifact and prints named verdicts (self-heals / inconclusive / stuck) into `$GITHUB_STEP_SUMMARY`.
- Fixes the false "RUN only by the ISO lane" claim in `first-boot-manifest-check.yml`.
- `k3s-first-boot-roster.nix`: adds `helm-install-<chart>` Job-completion assertions for spire-crds, spire, trust-manager, external-secrets — stronger than "the HelmChart CR exists" (a CR is created regardless of whether `helm install` ever succeeds).
