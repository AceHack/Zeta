## Summary

Follow-up to #17488 (WP11: installed-disk first-boot k3s verify). The
`workflow_dispatch` run I triggered from that PR (run
[35697298781](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/35697298781))
came back failed with a real bring-up defect: `zeta-k3s-first-boot-verify.nix`'s
unit never ran at all.

**Evidence** (from the run's `qemu-k3s-first-boot-verify-serial-log`
artifact): the installed disk booted cleanly through phase 3's own banner,
and two sibling units sharing the identical `/dev/ttyS0` serial-mirroring
pattern — `zeta-first-session-ci` and `zeta-creds-restore` — both printed
their expected lines on that exact same boot, proving `multi-user.target`
was reached and the serial channel works. Not one line from
`zeta-k3s-first-boot-verify` appeared anywhere, not even its own
unconditional first log call — which only happens when `ExecStart` is never
invoked.

**Root cause**: the unit carried `after = [ "multi-user.target"
"network-online.target" ]; wants = [ "network-online.target" ];`. systemd
defers `ExecStart` until every `After=` target has settled, and on this
image's first boot (QEMU user-mode NIC + NetworkManager) `network-online.target`
apparently never settles within the observed 75+ minute window. The unit was
simply never invoked — indistinguishable from a hang on serial because
nothing ran to report it.

**Fix**: order on `local-fs.target` only (matching the two sibling units
that worked). The unit already polls internally, with its own bounded
deadline, for everything that actually needs the network (`k3s.service`,
`kubectl`, Helm charts) — the same pattern `k3s-join-observer.nix` already
uses. Also adds `StandardOutput/StandardError = "journal+console"` as
defense-in-depth.
