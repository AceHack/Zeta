## Description

## Summary

Root-cause work for the USB install defect measured in run 35717757526: `nixos-install --flake .../full-ai-cluster#control-plane` installed a real disk, booted it with network, and `k3s.service` **never** reached `active` in 4201s.

- Adds `nixos/tests/control-plane-host-boots-k3s.nix`: boots the WHOLE `nixosConfigurations.control-plane` host (imports `hosts/control-plane/configuration.nix` verbatim — the same one-element module list `flake.nix`'s `mkSystem` uses, so there's no second module list to drift), through the real UEFI/OVMF/systemd-boot chain (`virtualisation.useBootLoader`/`useEFIBoot`), not nixosTest's fast default path. Three subtests: no systemd ordering cycle, `k3s.service` reaches `active`, node reaches `Ready`. Wired as a flake check plus `.github/workflows/control-plane-host-boots-k3s-vm.yml`.
- Applies a fix in `k3s-server.nix`/`k3s-agent.nix` via a new shared module `nixos/modules/k3s-wait-for-address.nix`: drops `systemd.services.k3s`'s `after`/`wants` on `network-online.target` (nixpkgs' rancher/k3s module, pinned `nixos-26.05` commit `1e8bc658`, orders k3s on it) and adds a bounded `ExecStartPre` that polls up to 120s for a global-scope IPv4 address before proceeding regardless — addressing the node-ip risk the architect flagged (k3s passes no `--node-ip`/`--advertise-address`, so it self-resolves its address at startup; k3s's own `Restart=always`/`RestartSec=5s` remains the backstop for a still-later address).

## IMPORTANT — honest evidence about validation (architect-requested negative control)

Per review, I built a throwaway negative-control branch (`claude/control-plane-host-vm-boot-repro`, closed PR #17532) carrying the same test **without** the fix, to check whether the VM test actually reproduces the defect before trusting a green run on this branch.

**It did not reproduce the defect** — twice:

1. Run 35742067241 (nixosTest's default fast boot, `-kernel`/`-initrd`, skipping UEFI/systemd-boot entirely): `k3s.service` reached `active` in **0.30s**. No ordering-cycle evidence.
2. After fixing that fidelity gap (`useBootLoader`/`useEFIBoot`, matching `qemu-full-install-test.ts`'s real OVMF/systemd-boot boot chain that WP11 actually exercises) — run 35743154251: `k3s.service` *still* reached `active` in well under 30s (`Starting k3s service...` at 14.1s uptime → `Started k3s service.` at 29.6s), with `systemctl show k3s.service` confirming `After=...network-online.target` **was present** (matching unfixed upstream) and settled promptly anyway. No ordering cycle.

**Conclusion: this VM harness cannot reproduce run 35717757526's finding, with or without the fix, even after closing two real fidelity gaps.** So this PR's green CI run is *not* proof the fix addresses the real defect — only that it doesn't regress anything the VM test can see. The fix here is justified instead by:
- The identical `After=network-online.target` shape, already root-caused and fixed on a sibling unit in this repo (`zeta-first-boot-k3s-verify.nix`, 081M33XMWME087G0R000825CCB, run 35697298781 — that unit printed *nothing* across 75+ minutes with the same ordering, while sibling units ordered only on `local-fs.target` printed fine on the same boot).
- The dependency being `wants`, not `requires` (checked against pinned nixpkgs source), so dropping the ordering is low-risk.
- The added bounded wait + k3s's own `Restart=always` as defense-in-depth against the node-ip risk, independent of whether network-online is the true root cause.

**This should be cross-checked against PR #17530** (branch `claude/wp11-k3s-diagnostics`), which re-runs the real installed-disk ISO test with richer diagnostics (ordering-cycle journal grep, `systemctl show k3s`, `NetworkManager-wait-online` status) directly on the harness that actually found the bug. That is the real oracle for this question; this PR's VM test — while a genuinely new, previously-absent regression-test capability (no test had ever booted the full host config before) — is not.
