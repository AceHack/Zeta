## Description

**Filed against my own bug report.** `081M1TFG81G087G0R001XPQGQZ` records orleans
reporting `Synced/Progressing` on the live lane, and the best that report could do was
say the pod was *"most likely Pending"* on a *"leading hypothesis"* about its CPU
request. That vagueness was not caution — it was a missing surface, and the bug's own
closing line says so: *"a Pending pod is currently diagnosed by guesswork, which is a
gap in the lane rather than in orleans."*

## The gap

All nine commands in `REPO_BACKED_CHILD_WAIT_DIAGNOSTIC_COMMANDS` are ArgoCD-side or
`kube-system`. **Nothing looked at the workload pods.** So the bundle could observe
*that* ArgoCD was unhappy and never *why* — and a bundle that cannot distinguish
`Pending` from `CrashLoopBackOff` is not a diagnosis, it is a prompt to speculate.

## The two commands

| label | command |
|---|---|
| `not-running-pods` | `get pods -A -o wide --field-selector status.phase!=Running,status.phase!=Succeeded` |
| `warning-events` | `get events -A --field-selector type=Warning --sort-by=.lastTimestamp` |

**Both field-selectors are load-bearing rather than tidy.** Without
`status.phase!=Succeeded`, every completed Job pod in the cluster lands in the dump and
buries the one pod that matters. Without `type=Warning`, the events drown in Normal
`Pulled`/`Created`/`Started` spam. In both cases the diagnostic still runs and still
produces output — which is the failure mode worth naming: **noise nobody reads looks
exactly like coverage.**

Warning events are what carry the *why*: `FailedScheduling` names the exact
insufficient resource, `ImagePullBackOff` names the image, `FailedMount` names the
volume. That is what turns *"most likely Pending"* into a reading.

## The falsifier

Asserts **shape, not labels** — a label with the wrong field-selector would pass a name
check and dump the wrong thing. Mutation-checked both ways:

- drop `status.phase!=Succeeded` → **red**
- drop `type=Warning` → **red**
- restore → **96/96 green**
