## Non-blocking, but not rotting

Aaron: *"windows and mac can always stay non blocking but we dont want to let it rot."* Those two halves need different mechanisms:

- **A leg's own health is advisory** on macOS/Windows (`continue-on-error`). Those platforms carry a rate this repo does not keep green — the drift reporter puts `build-and-test (windows-2025)` at **30/59 executions failed, 50.8%** — so blocking would import that flakiness into this gate.
- **A cross-processor disagreement stays blocking** for every leg including these. `cross-processor` has no `continue-on-error` and is not conditional.

> A missing toolchain is **environmental** and must not block. A substrate computing **different bytes on two machines** is the fault class this workflow exists to catch, and it blocks wherever it appears.

**Anti-rot, because non-blocking is exactly how a leg rots.** The comparison needs only *two* legs, so three healthy Linux legs would hold this green forever while macOS and Windows quietly stopped reporting. Three mechanisms, none of them blocking:

1. **Measured floors** — Windows raised 1 → **8** with its eight-name required list. A degraded leg goes red and is *visible* rather than passing at a floor of 1. **A floor left at 1 is rot.**
2. The comparator **names every leg it could not read**.
3. **`--expect-legs`** — a leg that *vanishes* emits a GitHub warning annotation plus expected-vs-reported counts. An unreadable leg counts as **present** there on purpose: it is already named once, and reporting it twice would suggest two problems where there is one.
