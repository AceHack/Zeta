## Description

Second failure on the included proof (check-run 101435639577), beside the orleans one this
session already tracks. **Filed rather than diagnosed, deliberately.**

## It is a different symptom from the one fixed earlier today

headscale went `Missing` → `Progressing` → green after `base_domain` moved from
`zeta.local` to `tailnet.zeta.local`. **`OutOfSync` says the live objects differ from the
manifests and the sync did not converge** — which the `base_domain` defect never produced.
Not assumed to be a regression of it.

## Two things eliminated statically, because they are cheap and they are facts

| candidate | verdict |
|---|---|
| a sync-policy gap | **not it** — the Application carries `prune`+`selfHeal` and both `syncOptions` |
| a `storageClassName` the lane does not provide | **not it** — the StatefulSet asks for `longhorn`, and the lane applies a `longhorn` alias over `rancher.io/local-path` at bring-up |

## What is not eliminated is not guessed at

The image is `ghcr.io/juanfont/headscale:0.29.3`, and the bring-up prints every run that it
mints no ghcr.io pull Secret and that *"Applications whose images live in ghcr.io will not
start in this cluster."* But that surfaces as `ImagePullBackOff`/Degraded rather than
`OutOfSync/Progressing`, and **no pod state was captured on this run**. Writing it down as
the cause would be the same move this lane keeps punishing — so the work-item says what it
does not know instead.

## The blocker is named, with its PR

**#16758.** The pod-level diagnostics were wired only to the repo-backed child-wait timeout,
and a health-verdict failure does not take that path. Once it lands, the next proof carries
one `FailedScheduling` / `ImagePullBackOff` / `FailedMount` line for this app — and this
becomes **one read instead of one experiment**.

## Done when

from a captured event rather than inferred from the manifests. A green that arrives without
