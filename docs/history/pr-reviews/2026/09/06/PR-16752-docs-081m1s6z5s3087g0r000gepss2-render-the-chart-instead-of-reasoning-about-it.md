## Description

Docs only, against `081M1S6Z5S3087G0R000GEPSS2` (the blob-store S3 credential that is a
plaintext literal in five committed files). **The literal is still in the tree** —
removing it is the work-item, not this PR. This records what rendering the chart
actually shows, before anyone attempts the fix.

## Confirmed

`seaweedfs/Application.yaml` sets `s3.enabled: false` with `allInOne.enabled: true`,
which makes the `s3.credentials` block **look inert**. It is not. `helm template
seaweedfs 4.45.0` against this Application's own `valuesObject` renders the committed
literal into a Secret **twice** — as `admin_secret_access_key`, and again inside the
`seaweedfs_s3_config` identities JSON.

## Corrected — my own first read, written down because the next reader will make it too

That same render carries `read_access_key_id` / `read_secret_access_key` for an
`anvReadOnly` identity, and they read exactly like a **second committed credential
pair**. They are not. Rendering twice gives two different values
(`TfyV3sgj7l7wdsMzP3Mf`, then `97iPWEs9okjBlwK8XdRT`), so the chart mints them with
`randAlphaNum` per render and nothing in this tree declares them.

## What that surfaces instead — an undeclared dependency on hook semantics

A Secret whose content is non-deterministic per render *should* churn on every ArgoCD
sync. It does not, and the reason is two annotations the chart puts on the object:
`helm.sh/resource-policy: keep` and `helm.sh/hook: "pre-install,pre-upgrade"`. So it is
created once and never updated.

**If either annotation changed upstream, every sync would rotate a credential nobody is
watching.** Noted for a falsifier when the work-item is picked up — the fix replaces
this Secret anyway.

## The remaining unmeasured half, named so it is not rediscovered

`applyDevBootstrapSecrets` draws a fresh `randomBytes(24)` **per spec**, so three
namespaces needing **one shared value** (`object-store`, `loki`, `mimir`) cannot be
expressed by adding three entries to `DEV_BOOTSTRAP_SECRETS`. The mint API needs a shape
it does not have — which is the concrete reason this credential is harder than the
OpenSearch and forgejo ones that preceded it.
