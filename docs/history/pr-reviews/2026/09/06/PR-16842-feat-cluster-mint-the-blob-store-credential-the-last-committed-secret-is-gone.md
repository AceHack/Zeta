## The blocker was the mint shape, not the manifests

`applyDevBootstrapSecrets` draws entropy **per spec** — correct for a credential with one
consumer, **wrong** for one a producer and three consumers must agree on. Three bootstrap
entries would have minted three different values and left two services authenticating with a
key the store does not know.

So `DevSharedSecretSpec` is a second, narrow shape rather than a widened first one:
`namespaces` is a list, the value is drawn **once**, and `keys` is a **function** of that
value — because the consumers don't agree on the spelling either. seaweedfs wants an inline
JSON identities document under `seaweedfs_s3_config`; loki and mimir want a plain env var.

**All-or-nothing on re-run** is the subtle half: if *any* namespace already holds the Secret
the whole spec is skipped, because filling in the missing two with a fresh draw would leave
the third holding the old value — a mismatch that surfaces as an S3 auth error days later
rather than as a refusal now.

The consumer side is each chart's **own documented mechanism**, not a trick — loki's values
name `-config.expand-env=true` and say *"such environment variables can be then stored in a
separate Secret and injected via the global.extraEnvFrom value"*; mimir says the same.

## Five tests went red and every one was right

- **`audit-existing-secret-is-minted` refused `zeta-blob-store`** — it only knew the bootstrap
  roster. Taught it both.
- **Chasing that refusal found a real blind spot in that auditor:** its pattern matched
  `existingSecret` but not `existingConfigSecret` — the word is existing-**Config**-Secret, so
  the substring is absent. **seaweedfs's reference was invisible to the credential audit**, and
  a chart naming an unminted Secret in that field would have passed silently. Widened to
  `existing<Anything>Secret`, still bounded at both ends.
- **"every minted Secret is referenced" compared arrays** and broke on the first credential
  referenced by three Applications. Re-stated as a set comparison — which is the property.
- **The mint-count and three idempotency tests assumed one roster.** Asserting the spec count
  would pass over a shared secret that reached only one of its three namespaces.
- **The entropy test paired manifests to specs by index** and read past the end. Replaced with
  a by-name lookup, and the exception is now stated where the rule is: shared secrets are
  *deliberately* not distinct across namespaces.

## And my own anti-vacuity guard failed, correctly

`expect(secrets.length).toBeGreaterThan(0)` guarded the leak check against being vacuous — and
it was keyed to **a defect existing**, so minting the credential away broke it. Re-keyed to
the **mechanism**: a planted control proves the encoded-leak detector fires on a haystack
containing only the base64 form, where a raw string search would find nothing.

## What is not proven here

**No cluster has run this.** `helm template` cannot show that loki and mimir successfully
expand the env var, only that the values are well-formed. The live included proof closes that
— and it is why the env var and the `-config.expand-env=true` flag are in the **same commit**:
landing either alone would authenticate with the literal characters
`${BLOB_STORE_SECRET_KEY}`, a **silent** auth failure rather than a crash.
