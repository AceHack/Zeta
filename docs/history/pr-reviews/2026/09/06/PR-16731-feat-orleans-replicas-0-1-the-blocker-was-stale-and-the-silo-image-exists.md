## Description

## The blocker was stale

`orleans/configmap.yaml` said *"THIS CONFIGURES NOTHING YET … because no Microsoft.Orleans package is referenced anywhere in this repo"*, and `statefulset.yaml` sat at `replicas: 0` **citing that comment as its reason**. Every piece it named as missing now exists:

| | |
|---|---|
| `Zeta.Orleans.Silo.csproj` | `Microsoft.Orleans.Server` + `Clustering.Redis` **10.3.1** (verified latest stable on NuGet) |
| `orleans-silo/` | `Dockerfile`, `Program.cs`, `Grains/`, `ClusterConfig.cs` |
| `build-platform-images.yml` | builds and pushes it |
| GHCR `:latest` | published **2026-09-05** |

So `replicas: 0` stopped being honest. It was correct while the image was a placeholder; afterwards it was **an app that could not fail because it never ran**. Bumped to 1 in the same change that corrects the comment. **Zero-pod Applications drop 4 → 3.**

Safe to raise: if Redis clustering fails, `host.RunAsync` throws and the container exits — it **crash-loops rather than reporting a false Ready** through the `tcpSocket` probe. Wave ordering was already correct (redis 0, orleans 10).

## Four things the bump surfaced

1. **Flow-style YAML made the rung ladder unfalsifiable.** `requests: { cpu: …, memory: … }` — the overlay writer cannot rewrite inside a flow mapping, so the auditor reported `unoverlayable-row`: *"a rung the render never sees would agree with every rung equally."* Converted to block style.
2. **A cross-tree namesake was reported as a defect.** `discoverApplications` walks **both** `full-ai-cluster` and `infra/k8s/applications`; four directory names exist in both; claims are keyed by `dir` alone. **Orleans is the first dual-tree directory to carry a resourceClaim**, so nothing had exercised that path. Fixed with `claimPathTargetsAnotherApplication` — a claim inside a *different* application is skipped because another Application answers for it, while a claim inside *no* application still fails. **The check is not weakened.**
3. **`:bootstrap` never existed.** `infra/k8s/bootstrap/initial-orleans.yaml` pinned it; the provenance refresh measured that tag at **404** while `:latest` is 200. The build publishes `latest` and `sha-<commit>`, never `bootstrap` — so that manifest named an image that could never resolve and would have `ImagePullBackOff`'d the moment anyone raised its replicas.
4. **An acknowledgement predicted its own retirement and was retired on schedule.** The `ours-unpublished` entry said: *"LIFTS WHEN: a build+push workflow publishes the package, `--refresh` records `artifact: public`, and this entry then goes STALE and fails."* All three happened. Retired with the history recorded rather than deleted — an acknowledgement that named the conditions of its own end and then met them is the mechanism working, and the next reader should see that it did.

Public is intended (Aaron: *"publically avialable is just fine"*), so world-readable is a decision, not a leak.

## Scope note

`infra/orleans` **stays at `replicas: 0`, deliberately** — it is the legacy tree's copy under a separate root app-of-apps, and raising it would put **two silos on one Redis clustering identity**. Retiring that tree is a separate question, being looked at separately.
