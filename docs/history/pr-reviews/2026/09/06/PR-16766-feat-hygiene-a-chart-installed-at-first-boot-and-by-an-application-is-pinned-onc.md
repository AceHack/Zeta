## Description

Requested: *"continue with our k8s/helm testing that closely matches metal in CI."* This is
that testing, and what it found on its first run.

## No CI lane applies `*/k8s/bootstrap/` at all

The kind and k3d lanes bring ArgoCD up from `dev-cluster/use-cases.ts`. So **NixOS first
boot is the least-exercised surface in the tree** — and a defect there is invisible to every
live lane. This audit is text-only and offline, which is exactly what lets it cover a path no
CI cluster takes.

## Four divergences, three of them CRD-bearing

| chart | first boot | Application | gap |
|---|---|---|---|
| `cert-manager` | v1.16.2 | v1.21.1 | 5 minor, **CRD-bearing** |
| `external-secrets` | 0.10.7 | 2.10.0 | **major**, 0.x → 2.x |
| `spire-crds` | 0.5.0 | 0.6.1 | **pure CRD chart** |
| `trust-manager` | v0.15.0 | v0.24.0 | **CRD-bearing** |

The other four agree (`argo-cd` ×2, `cilium`, `spire`). Each divergent pair means K3S
installs one version on real hardware at first boot and the Application upgrades **the same
Helm release** in an early sync wave — the mid-run self-upgrade `argocd-install.yaml`'s own
header calls *"exactly the failure that cached the seaweedfs manifest error"* (run
33736439359: cached manifest error, seaweedfs `health=Healthy` **vacuously**, zero applied
resources).

`trust-manager-install.yaml` states the same coupling for a **value** — the two *"share a
Helm release"*, so a mismatch is *"two reconcilers flipping the flag against each other"* —
and never extended it to the version. The file guards the smaller half of its own hazard.

`validate-bootstrap.ts` already checks each HelmChart pins an **exact** version. It never
asks whether that version agrees with anything else, which is how an exact-and-wrong pin
passed.

## The pins are not bumped

Each bootstrap CR carries its own `valuesContent`, so a bump is a real cluster change per
chart that needs those values re-rendered first. **Four blind bumps to charts that install
on real hardware at first boot is the guessing this repo refuses elsewhere.** All four are
acknowledged with a reason and a lift condition; the work-item carries a suggested order
(`spire-crds` first — no values to re-render; `trust-manager` after `cert-manager` because
it consumes its CRDs; `external-secrets` last, as a migration rather than a bump).

**The key carries both versions**, which stops the roster becoming a permanent excuse: move
either side and the entry goes **stale** and the audit fails on it. A half-paid debt reports
both halves.

## Ten falsifiers

Weighted toward how a check over an unexercised path goes quietly useless: multi-document
parsing (`spire-install.yaml` really carries two HelmCharts — a first-doc-only parser would
silently check one and still print a confident count), the stale-key and half-paid cases, a
bootstrap-only chart **not** being a divergence, and one case that reads the **real** tree so
a rename cannot leave the nine fixture-driven ones green over an audit reading nothing. The
audit also **refuses** on an empty scan rather than reporting zero divergences.

## Two of this repo's own lints caught me writing it, and both were right

`localeCompare` in the sort (culture-sensitive — and this output is compared against a
committed baseline, so the roster's meaning would depend on the machine that ran it) and two
`existsSync`-then-read pairs (check-then-use). **Both fixed, neither baselined.**

## And one thing worth writing down

`audit-cluster-tree-consumers.ts` uses `git grep`, which sees only **tracked** files. Run
before `git add`, it reported **rc=0 and "roster matches the tree"** over a new file it could
not see. Staged, it went red immediately and correctly. A check that cannot see the change
under test is the vacuity class with an unusually short fuse.

The new audit is rostered `blocking`, with a note that its tree-deletion failure mode is
**soft**: guarded reads mean it would keep passing while silently covering one tree fewer,
which is worse than breaking.
