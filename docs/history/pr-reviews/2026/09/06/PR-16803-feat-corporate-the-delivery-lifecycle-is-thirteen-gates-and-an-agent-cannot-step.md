## Description

## The lifecycle the maintainer described, and the port list that was stale

Two tasks: port three modules recorded as unported, then audit the delivery lifecycle against a description of what it should be.

**The port list was stale, and checking it was most of that work.** `observe-for-hat` was fully ported already (`scopeOf`/`batchesInScope` are the same functions under corporate's names); `hat-lifecycle` was ported bar one predicate; `schedule-optimizer` had everything except **pace**. A name-matched diff claimed 0 of 15 schedule exports present, which was wrong in the direction that produces fifteen duplicate functions — the same class as pass 14's stale stated-limits.

## The chain was too short for the process it claimed to run

Seven gates → thirteen. Added `business_context_grooming`, `peer_review`, `architecture_design`, **`adversarial_review`**, `qa_uat`, `final_architecture_review`.

The adversarial gate sits **after** the design and **before** the build, because the interesting failures are between the documents and changing them is still cheap there. It is owned by three departments so the pass can come from outside the line that produced the plan. `final_architecture_review` exists because `architecture_approval` judged a *drawing* six gates earlier — approving the drawing is not approving the building.

All six are staffed in `org-seed.ts`; the runtime refuses to start when any gate has no owning hat, so an unstaffed phase could not merge as a silent no-op.

## Determinism, with falsifiers instead of a comment

`lifecycle.test.ts` — 24 tests, 564 assertions — drives the chain adversarially. ORDERED / OWNED / UNFORGEABLE, each asserted in **both** directions so none is satisfied by a chain that simply never works.

**A defect of mine the tests caught:** thirteen `GateKind` values declared, twelve wired into `ORDERED_GATES`. And **a test I damaged while fixing others**: an automated rewrite handed "OUT OF ORDER is refused" the priors it was supposed to lack, leaving it green and asserting nothing.

## A gate approval now says what it consulted

`GateEvaluation.evidenceRefs` carries what the decider looked at, threaded from the `Review` port. **I reversed my first design and the reversal is the point** — it *refused* evidence-free approvals, which looked like enforcement and was none: `autoApproveReview` ("reads no evidence and consults nobody") returns `auto-approved:<gate>:<workId>` and sailed through. A control the null adapter satisfies is the vacuity class.

The shipped claim is the narrower true one: an attested approval is **distinguishable** from a bare one, and the null reviewer **names itself**. Making a fabricated reference impossible is not something this mechanism can do, and that is written down.

## Also in here

- `mission-trajectory.ts` — PACE, distinct from schedule pressure's LOAD. It landed **unwired for one commit** (the "library the loop does not consult" failure this survey began from); an audit for modules nothing imports caught it.
- `EscalationTrigger.UnknownEncountered` — raised by the worker itself, the only honest response to a genuine unknown. Legal actions deliberately exclude `AcceptRisk`.
- `isInCooldown` extracted from its only caller so the staffing rule can be falsified on its own.
