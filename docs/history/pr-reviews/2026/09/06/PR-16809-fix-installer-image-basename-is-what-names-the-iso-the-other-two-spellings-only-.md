## Measured, before and after — on the artifact, not the option

```
before   image.fileName             = zeta-installer-25.11.iso
         system.build.isoImage.name = nixos-minimal-25.11.20260522.b77b3de-x86_64-linux.iso

after    image.baseName             = zeta-installer-25.11-x86_64-linux
         system.build.isoImage.name = zeta-installer-25.11-x86_64-linux.iso
         (aarch64)                  = zeta-installer-25.11-aarch64-linux.iso
```

## The near-miss is the point

I started this as **`image.fileName`** — the option the rename warning names — and **it
evaluates to our value.** So does `isoImage.isoName`, because nixpkgs *aliases* the old
spelling. **Only `image.baseName` reaches the derivation.**

A fix validated by reading the option back would have shipped green, silenced the warning,
and changed nothing: the artifact would still be `nixos-minimal-*`. That alias is why this
survived three months, and it is why the check added here asserts the **artifact**.

## The arch stays in the name

The nixpkgs default carried it, and dropping it trades one legibility defect for another:
both jobs would emit `zeta-installer-<release>.iso`, a downloaded file could not say which
machine it is for, and the two ISO artifacts would **collide on name inside one run** — which
the aarch64 upload step already works around, for exactly that reason. Found by reading that
step's comment, not by CI failing on it.

## The fix-forward is reverted with it

All **12** `find` sites dropped the `-o -name 'nixos-minimal-*.iso'` arm. That fallback is
what kept the lane green over the wrong name — the finder had learned to accept the wrong
answer instead of anyone asking why the right one wasn't applied — and leaving it would leave
the mechanism that hid this.

## And it has a falsifier, which the original ask did not include

`assert-iso-name.ts` runs after each ISO build and refuses a name the tree did not choose.
Its message distinguishes *"the option went inert again"* from *"somebody renamed the
prefix"*, because those want different fixes. Six cases — including that an **empty directory
is a failure, not a pass**, so the check does not join the family of defect it was written
for.

## I also filed a duplicate of this bug earlier today

`081M1VP8G1M087G0R001GYHWMA` (#16805), in which I wrote *"the warning has been printed on
every run and read by nobody."* **Someone read it, diagnosed it more accurately than I did,
and filed it in May.** That's the second time today I've called something undiscovered that
was already on file. The duplicate is kept and annotated rather than deleted, as the record
of the near-miss.
