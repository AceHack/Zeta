## Description

One of the four divergences `bootstrap-application-pin-parity` found (#16766), and the one
its own suggested order put first.

K3S installed `spire-crds` **0.5.0** at first boot; the Application adopted the same Helm
release at **0.6.1**. So the cluster upgraded its own CRDs in an early sync wave, underneath
a `spire` chart (0.24.2 on both sides, correct) coming up against them.

## Measured before touching the pin

`helm template` at both versions:

| | 0.5.0 | 0.6.1 |
|---|---|---|
| CRDs rendered | `clusterspiffeids`, `clusterfederatedtrustdomains`, `clusterstaticentries` | **same three** |
| served API version | `v1alpha1` in all three | **same** |
| `openAPIV3Schema` property diff | — | **0 removed, 0 added**, in all three |

**The API surface a running controller sees is unchanged.** That is what made this the cheap
one: the CR carries no `valuesContent`, so there was nothing to re-render and nothing to
migrate.

## The baseline entry is deleted, not edited

That distinction is the mechanism working. The key carries **both** versions, so an edited
entry would be a fresh acknowledgement of a divergence that no longer exists — the audit
reports a key matching nothing as **stale** precisely so a paid debt cannot be quietly
re-acknowledged.

**Three remain:** `cert-manager` (5 minor, CRD-bearing), `external-secrets` (major, 0.x → 2.x),
`trust-manager` (CRD-bearing, and should follow cert-manager since it consumes its CRDs).
