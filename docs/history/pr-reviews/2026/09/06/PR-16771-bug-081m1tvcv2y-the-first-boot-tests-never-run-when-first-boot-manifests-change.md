## Description

Found while continuing the metal-parity work. **Filed with the fix priced rather than
applied** — every option costs CI minutes in a repo that is actively being slimmed, and that
trade is yours.

## The measurement

`k3s-first-boot-apply-order-eval-test.nix` **reads the bootstrap manifests.** Its own section
header says so — *"Reading the manifests themselves"* — it filters `services.k3s.manifests`
by `hasPathSource` and opens the path-sourced ones, naming `spire-install.yaml`,
`trust-manager-install.yaml`, `root-application.yaml`. `k3s-first-boot-roster.nix` asserts
all 11 rostered manifests are staged and applied.

`build-ai-cluster-iso.yml` is the only lane that runs them. Its `paths:` filter covers
`full-ai-cluster/nixos/**`, the flake, the installer and a list of `src/` scripts — **and not
`full-ai-cluster/k8s/bootstrap/**` or `infra/k8s/bootstrap/**`.**

## Confirmed on this session's own work

PR #16755 moved the ArgoCD pin K3S installs on **metal first boot** from 7.7.10 → 10.8.0 in
`infra/k8s/bootstrap/argocd-install.yaml`. `build-ai-cluster-iso` has **no run for that
branch** — its latest at the time of writing was 2026-09-06T01:48 on `main`, before the
change existed.

**I edited a first-boot manifest and the first-boot tests did not run.** Not hypothetical.

## The irony worth preserving

The apply-order test is scrupulous about exactly this failure, in its own words:

> *"Naming what was not opened is the point: a check that silently skips an input is the
> vacuity class."*

The test names every input it cannot open. The **workflow** silently skips the whole test
when its inputs change. Same defect, one layer out.

## Three options, priced

Measured from the last run: `build-iso` **32 min**, `build-iso-aarch64 + qemu-boot` **26
min**, in parallel.

| | cost | closes |
|---|---|---|
| **A.** add the two globs to `build-ai-cluster-iso.yml` | **~32 min per bootstrap edit** | everything, including the VM tests |
| **B.** a small lane running only the **pure-eval** checks on `k8s/bootstrap/**` | **seconds** — apply-order is an `import` plus a trivial `runCommand`, no VM | the apply-order/roster *properties*, not the boot |
| **C.** leave it, record the gap | free | nothing |

**B is the honest recommendation**, and the split is real: `k3s-first-boot-apply-order` is
pure evaluation, while `k3s-first-boot-roster` is a full `nixosTest` whose own header says it
*"REQUIRES INTERNET (five Helm charts and roughly 2-3 GB of images)"*. The cheap half carries
most of the value for a manifest edit — order, roster completeness, the
before-its-kind-exists property — and costs seconds.

**But B adds a workflow**, which cuts against *"zeta is trying to stay small."* A lane is a
check rather than accreted data, so it is a different **kind** of growth than the PR archive
— but it is still growth. That is the whole reason this is filed and not done.

## Done when

A change to either bootstrap tree runs at least `k3s-first-boot-apply-order`, **and the
choice between A, B and C is recorded** — so a future reader can tell a deliberate cheap half
from a forgotten expensive one.
