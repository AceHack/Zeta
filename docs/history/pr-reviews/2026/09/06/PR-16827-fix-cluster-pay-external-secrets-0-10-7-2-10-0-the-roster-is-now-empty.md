## The major-version risk is real, and a rendered-object diff does not show it

It is in the **served API versions**:

```
0.10.7   externalsecrets / secretstores / clustersecretstores:  v1alpha1 + v1beta1 served
2.10.0   v1 served+storage, and v1beta1 served: FALSE
```

Nothing in this tree creates such an object, so nothing breaks — the only
`external-secrets.io/v1beta1` in the whole repo is **inside a comment**.

**But that comment is instructions.** It is an example `ClusterSecretStore` for Vault that
*"lands as a separate manifest after vault + ESO are both healthy"*. Following it would have
produced an object the API server refuses, at the moment someone finally did the Vault wiring
— and the Application has been pinned at 2.10.0 since 2026-09-01, so **the trap was already
armed.**

Corrected to `v1` in the same change, after checking every field it uses exists in the v1
schema: `server`, `path`, `version`, `auth.kubernetes.mountPath`, `auth.kubernetes.role`.
