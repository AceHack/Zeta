## Description

Neither is reproducible here, and neither needs to be. Both are instrumentation: the next
occurrence arrives already legible instead of costing a reconstruction.

1. k3s PREFLIGHT TRANSCRIPT COMPLETENESS (081M2FC9TFX087G0R0003FK5J0)

   The harness already refuses a spawn that FAILED. It had nothing to say about a spawn that
   SUCCEEDED and returned a PARTIAL transcript -- which is the failure this test keeps having:
   2026-09-08 on main, 2026-09-10 in CI, 2026-09-14 on #17406, every time on the
   `nixos-rebuild switch --impure` assertion, every time reported as though the SCRIPT had
   omitted a line.

   Measured on the 2026-09-14 occurrence: ~450 bytes against a 1,999-byte refusal, stopping
   mid-stream on a bare prefix line, with `r.error` undefined so the existing guard stayed
   silent. Three explanations were then refuted one at a time -- maxBuffer (32x headroom
   unused), spawn failure (guard did not fire), the ZETA_SERIAL_DEVICE second sink (pointed at
   a nonexistent path by this very function). The reconstruction cost more than the defect.

   EVERY EXIT PATH OF THE SCRIPT ENDS ON A KNOWN LINE, so completeness is checkable rather
   than guessed. A transcript that does not end on one now fails AT THE HARNESS with the byte
   count, line count, status, signal and tail, and says explicitly that this is an environment
   fact rather than a defect in the script.

   Verified by simulating the observed failure -- cutting the refusal short at the same place:
     INCOMPLETE -- bytes: 579 (a complete refusal is ~1999), lines: 6, status: 1,
     signal: null, last line: "[zeta-k3s-join-intent]"
   which is the shape of the real occurrence. Restored: 23 pass / 0 fail.

2. IO_SharingViolation NAMES THE TRIPLE IT ASKED FOR (081M2K8XT63087G0R000GSXC0P)

   `IO_SharingViolation_File` reports WHICH path lost and never under what mode the loser
   asked -- and the mismatch IS the defect. Measured 2026-09-15 on `build-and-test (macos-26)`:
   1 failure in 6898, DiskDeltaLog live replay, message carrying the path alone. Learning what
   was even being requested meant reading the call chain by hand.

   `PhysicalFileSystem.OpenFile` now rethrows an IOException carrying
   `[asked: mode=... access=... share=... path=...]`, inner exception preserved. Same type,
   same failure, strictly more said. Intermittent and platform-specific means the next
   occurrence may be the only sample anyone gets.

   Verified against a real sharing violation rather than assumed:
     MESSAGE: ... because it is being used by another process.
              [asked: mode=Open access=Read share=Read path=/var/.../x.bin]
     carries triple: true   inner preserved: true

NEITHER IS A RETRY AND NEITHER SUPPRESSES ANYTHING. Both work items say so explicitly: a retry
converts a true intermittent alarm into silence. These make the alarm legible, nothing more.

Verified: `dotnet build src/Core` 0 warnings 0 errors; DiskDeltaLog suite 35 pass / 0 fail;
k3s preflight 23 pass / 0 fail; the completeness guard fires on a simulated truncation and is
silent on a whole transcript.
