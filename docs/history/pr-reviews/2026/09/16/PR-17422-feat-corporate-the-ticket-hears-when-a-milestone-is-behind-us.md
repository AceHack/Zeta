## Description

## The gap

Measured on the Agentic Team, 2026-09-11..14: the organization decided an architecture, wrote an implementation, reproduced a defect, ran QA and opened a merge request on AIAGENT-1658 — and **the Jira ticket said nothing the whole time**. Every trace lived in the organization's own store and in GitLab. To the people who asked for the work, watching the tracker, it was indistinguishable from work nobody had started.

## What lands

When a gate the organization calls a **milestone** passes, its ticket gets one short comment:

```
**implementation review — done**

What was done
- Archive now targets the session the menu was opened on, not the most recent one …
- Added SessionSwitcher.archiveTarget.test.ts: 5 cases, all red before the change.
- Ran the client unit suite: no new failures against master.

What happens next
- QA replays the reported flow in a browser before this is called done.

Status: fix written and reviewed; waiting on QA

Merge request: https://…/merge_requests/1222 (`defect-AIAGENT-1658`)
```

Milestones are the operator's (`org ticket-reports set --milestone architecture_approval --milestone implementation_review --milestone qa_uat`), checked against the real gate roster at load and at set — a typo like `architecture-approval` looks configured and would report nothing forever, so it is refused with the list of real gates.

## What it deliberately is not

A log of every verdict. Measured on the FlowDent store: **349 verdicts, 290 of them rejections (83%)**, one gate rejecting a single item **81 times**. A comment per verdict would bury the ticket in the organization's own deliberation, which is what the review loop is *for* — it iterates until the work comes back clean, and only the clean result is news outside. A milestone reports when it **passes**, once per work item; a turn-back stays inside the loop.

## Generic over trackers

Intake mints `requestRef` as `<source>|<externalId>`, so a Jira item reports to Jira and a Linear item to Linear **with nothing configured**; `--tracker-kind` overrides that for an organization that reads in one place and reports to another. `tools/ticket-comment.cjs` implements both as a table — Jira Cloud (one POST, the text built into ADF so bullets are bullets and `**bold**` is bold) and Linear (the human identifier resolved to an issue id, then `commentCreate`; its comments are markdown already) — so a third tracker is a table entry, not a rewrite. A tracker nobody implemented is a **refusal**, never a no-op: an update nobody receives must not read as an update delivered.

## Shape

- **Two halves, separate.** An agent writes the update (`claude-agent.cjs ticket-update`, told to write for somebody outside who cannot see the organization's ids, and to say plainly when something was *not* established); a command posts it. A tracker outage cannot make the organization re-think, and a bad update cannot be blamed on the network. The merge-request link is appended by the organization, never by the agent — a link it invents is a link that does not exist.
- **Said once.** `ticket_reported` is a fact keyed by (work item, gate); `foldTicketReports` is what the next run reads. A post that fails records nothing and is retried next run.
- **Credentials.** A PATH read at call time, never on argv. The endpoint override is loopback-only, so no env var can redirect a token off the machine — the credentials file's own checked URL stays the destination.
- **Asked, not assumed.** `configure-plan` gains a `tell_the_ticket` step, required of any organization whose work comes from a tracker; `run-org` refuses to start when milestones are stated with nothing configured to write or post them.
