## Description

The repo had 6 open code-scanning alerts. All 6 are now dismissed and 5 of them
carry a mechanical premise checker, because a dismissal whose premise nothing
checks is the vacuity class -- it looks like a disposition and constrains
nothing, and the day the premise stops being true, nothing says so.

Two of the six had no checker. This adds them.

lint-no-privileged-untrusted-checkout.ts (CodeQL #798)
------------------------------------------------------
The severe case is the PAIR, not either half. A head checkout under plain
`pull_request` is safe -- a forked PR gets a read-only token and no secrets, so
running the author's code grants them nothing new, and resume-diff.yml does this
deliberately. The vulnerability is a PRIVILEGED trigger (pull_request_target /
workflow_run / issue_comment, which carry base-repo secrets and a write token)
combined with a checkout the PR author controls. Refusing the pair is what lets
the safe single halves keep working.

Measured by parsing every `on:` block as YAML, not by grepping: this repo's
`pull_request_target` mentions are ALL prose saying "never pull_request_target",
so a grep for the identifier matches the comment that forbids it. Zero workflows
use a privileged trigger with an untrusted checkout.

The checker's own first bug is recorded in it: it treated a bare checkout as
untrusted everywhere and fired on rerun-cancelled-gate.yml, whose bare checkout
IS its documented guard. Under workflow_run the default ref is the DEFAULT
BRANCH (trusted); only under pull_request* is it the merge ref. A checker that
flags the safest available pattern is worse than none -- it trains readers to
dismiss it, and the real finding then arrives pre-ignored.

lint-nuget-force-evaluate-is-confined.ts (Scorecard #963/#964)
--------------------------------------------------------------
Scorecard is RIGHT that those two restores are unpinned: they pass
--force-evaluate. It is accepted because that workflow's SUBJECT is the
re-resolution -- asking whether a lock resolves identically across operating
systems cannot be done under --locked-mode, so pinning it would delete the
experiment rather than secure it. Same shape as the binary-under-test exception
in no-binary-in-proof-lineage.md: the artifact being MEASURED is not the
artifact being TRUSTED.

An exception with no scope is a licence, so this checker is its scope. It goes
red if any other workflow adopts the flag, or if the experiment stops using it
(which would make the alerts stale rather than dismissed-with-premise).

Both are mutation-verified, not merely green
---------------------------------------------
  privileged trigger + head checkout added to the tree   -> rc=1
  gate.yml base.sha -> head.sha                          -> rc=1
  --force-evaluate added to low-memory.yml               -> rc=1
  control, tree restored                                 -> rc=0

24 unit falsifiers besides, including the false-positive case above, so it
cannot come back.

HONEST GAP: five of the six dismissals have a checker. #965 (js/file-system-race
in esp-inject.test.ts) does not. Its mitigations are real -- a mkdtempSync 0700
directory with an unpredictable name, plus an fstat dev+ino equality against the
write descriptor so a swapped object fails rather than silently passing -- but
they are verified by inspection, not by a check. A grep-for-the-pattern checker
would be satisfied by a comment mentioning it, which is the failure mode this
whole commit is against, so none was written rather than a weak one.
