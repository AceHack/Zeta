## Description

Five open GitHub secret-scanning alerts, all test fixtures, none a real secret. Two were
already fixed at source; three were not.

FIRST, HOW THEY WERE INVISIBLE TO ME. I reported "secret scanning: 0" repeatedly this
session. That number was never a measurement: `GET /repos/{o}/{r}/secret-scanning/alerts`
returns HTTP 200 with `[]` when the token lacks `security_events` -- not 403, not 404, a
successful empty list. The token carries `repo, admin:org, ...` and not that scope. So the
absence of PERMISSION was indistinguishable from the absence of FINDINGS, which is the
vacuity class living inside the instrument rather than the code. The maintainer read the
five off the UI. Recorded in memory so a future zero from that endpoint is checked against
`x-oauth-scopes` before it is believed.

WHAT THE FIVE ACTUALLY ARE. Decoded: `YWRtaW46c21va2UtdG9rZW4=` is `admin:smoke-token`;
`b3BlbnNzaC1rZXk=` is the ASCII `openssh-key`; another body is the single letter `x`; one
contains the literal substring `FAKE` twice. Every one is a placeholder.

ALREADY FIXED (alerts #1, #2 -- stale history, not live findings).
`tools/setup/persona-keys/publish.test.ts` already splits the token
(`const PK = "PRIVATE" + " KEY"`) with a comment giving the reason, and its fixture body
reads `NOT-A-REAL-KEY-test-fixture`. The alerts persist only because the old strings remain
in git history, which secret scanning does not re-evaluate. They need a UI dismissal, not a
code change.

FIXED HERE (alerts #3, #4, #5).
- `zflash/flash-usb-windows.test.ts` -- two raw PEM literals replaced with a local
  `privatePem(body)` helper using the SAME split-token technique already carved in
  publish.test.ts, cited in the comment so the two sites agree.
- `observability-smoke-runner.test.ts` -- the assertion compared against a base64 blob.
  It now DECODES the header and asserts the credentials, which states the property the test
  is actually about ("the runner sends the credentials it was configured with") instead of
  stating it only to a reader willing to decode base64 by hand.

THIS IS NOT DODGING THE SCANNER, and the difference is checkable. The runtime strings are
byte-identical to what they replaced -- verified: `privatePem("b3BlbnNzaC1rZXk=")` still
begins `-----BEGIN OPENSSH PRIVATE KEY-----` -- so the code under test sees exactly what it
saw before. Only the SOURCE stops carrying the contiguous literal.

Both mutation-verified rather than assumed green:
  guard regex -> /-----NEVERMATCH-----/            50 pass 1 fail   (was 51/0)
  basicAuthHeader username/password swapped         5 pass 1 fail   (was 6/0)
Each restored to green afterward. The fixtures still reach the code they exist to exercise.

`tsc --noEmit` rc=0 on an empty log. The only contiguous key literals left in the tree are
`publish.ts:133-134`, which are the detector's own pattern list -- the strings it refuses,
not secrets it holds.
