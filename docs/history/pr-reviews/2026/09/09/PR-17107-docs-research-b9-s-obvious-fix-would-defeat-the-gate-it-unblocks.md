## Description

docs(research): B9's obvious fix would defeat the gate it unblocks

B9 says "no biometric gate exists on Linux, so every key-custody ceremony
refuses ... needs a Linux consent adapter". The finding is accurate and the abort
is structural, not a bug: biometric.ts closes its platform union at
"macos-touchid" | "windows-hello" | "unsupported", and unsupported means
fail-closed. The gate is doing what a fail-closed gate does.

The register's wording invites the reading "make Linux return ok: true". Two
candidate mechanisms present themselves and BOTH FAIL, for reasons already
written down in this repo.

TPM attestation attests a MACHINE, not a HUMAN. ceremony-gate.ts draws the line:
CEREMONY is the class where "cryptography cannot decide these: there is no prior
fact to chain to, so the only remaining source of authority is a human." A
TPM-satisfied ceremony gate has been satisfied by the very machine asking, and
that same file names the move -- "unattended operation that quietly swallowed
that gate would be a privilege escalation dressed as a convenience".

pam_fprintd IS a human factor, and the parsing already exists (auth-chain.ts was
generalised precisely so the same attribution question could be asked of it). But
it needs a human AT THE BOX, which is what Aaron's hardware constraint rules out.

HIS CONSTRAINT ALREADY CONTAINS THE ANSWER, in its exception clause: "not need
human intervention except though our declared UI and interfaces from humans
REMOTELY." So the Linux adapter is not a local authentication factor at all. It
is a TRANSPORT FOR A REMOTE HUMAN'S APPROVAL -- the only option that keeps both
properties at once (a human authorises the gated class; no human at the box).

The TPM still has a job and it is a different one: attesting WHICH MACHINE is
asking, so the remote approver is not authorising a bare prompt. Machine
attestation and human authorisation answer two questions; the error is
substituting the first for the second.

ONE THING THAT CHANGES THE WORK, from ceremony-gate.ts's own vacuity disclosure:
the classifier is NOT AN ENFORCER. "Nothing in this repo prevents a caller from
ignoring the label and proceeding. The one place the gate is structurally
enforced is yubiHsmSignerRequiringCeremony, which cannot produce a signature at
all -- and it cannot because the credential to open a session is absent, not
because this classifier stopped it." So an adapter returning ok: true on Linux
would not be ADDING a gate anywhere; it would be REMOVING the one refusal that
currently holds.

Recommendation: do not add a Linux arm that returns ok: true from a
machine-local factor. It would turn eleven honest refusals into eleven silent
approvals, and the register would read as fixed while the property it protected
was gone. Also flags that a remote-approval result is not "biometric" in any
existing sense, so reusing macos-touchid would be exactly the false attribution
auth-chain.ts was written to prevent -- the union needs a fourth arm.

Register: mechanism findings verified in code and cited by file; the
recommendation is a design judgement and Aaron's to overrule, which is what
ceremony-gate.ts says about its own embedded policy. Scope for what would need
building is stated as scope, not as a plan I have authority to adopt. Whether the
existing tpm2-seal modules are sufficient is UNVERIFIED here.
