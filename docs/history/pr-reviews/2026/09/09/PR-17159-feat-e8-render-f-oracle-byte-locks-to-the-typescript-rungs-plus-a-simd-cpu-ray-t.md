## Rung 7 — the .NET oracle agrees byte for byte, and the geometry (not the CPU) is what bounds the frame rate

Aaron set the architecture:

> *"for our graphics engine maybe we should start in f# first since it looks like the math for the simd stuff, your css/canvas/webgpu is also a good split, ts is fine too as far as the web stuff but we don't have to vectorize there yet with like simd. ... it's also fine for us to have multi oracle with rust too but i'd love to have a graphics engine built entirely built in dotnet if it's useful."*

So F# owns the math and the SIMD/CPU rendering; the TypeScript rungs 1–6 in `src/Core.TypeScript/research/clifford-e8-*.ts` are **untouched**.

### 1. A second oracle, not a port

Both oracles emit **one canonical text document** and the falsifier is byte equality — no parser on either side, because a lenient comparison is a check that can fail to fail. The F# construction diverges deliberately in three places:

- triangles enumerated **edge-first** (adjacency-row intersection) rather than by clique recursion — and the test asserts both routes agree element for element;
- `affineRank` is **fraction-free integer elimination**, where TypeScript runs float Gaussian elimination against a `1e-9` pivot. A rank is a theorem here, not a measurement;
- `reorderSign` counts **inversions per set bit**, where TypeScript accumulates shifted popcounts.

`tests/cross-verification/clifford-e8-rendering/cross-verify.ts` runs both and asserts three things: TypeScript matches the committed document, F# matches it, and the two match each other. The F# side `#load`s the shipped modules rather than restating them, so the harness compares two implementations instead of comparing one to a copy of itself.

### 3. The ray tracer is the repair of a limit rung 6 measured

27 faces per edge ⇒ the shell has no inside ⇒ a painter's sort is *wrong*, and nearest-hit is the correct occlusion method. Intensity is already exact in 8D integers and takes five values, so a hit reads one byte instead of evaluating lighting.

Binned-SAH BVH, ordered front-to-back traversal, two-sided Möller–Trumbore, scalar and `Vector<float32>` kernels, and a degree-of-parallelism knob (DoP = 1 is a deterministic single loop; DoP = N is the same code path).

### 4. Measurements — Apple M2 Ultra, arm64, 24 cores, .NET 10.0.11, macOS 26.6

`Vector<float32>.Count = 4` (NEON), hardware-accelerated. 60,480 triangles, 11,975 nodes, 142 ms scene build.

| kernel | DoP | resolution | ms/frame | Mrays/s |
|---|---|---|---|---|
| scalar | 1 | 256×256 | 2274 | 0.029 |
| **SIMD** | 1 | 256×256 | **664** | 0.099 |
| SIMD | 24 | 256×256 | 68 | 0.967 |
| **SIMD** | **24** | **512×512** | **229** | **1.15** |
| scalar | 24 | 512×512 | 728 | 0.360 |

**SIMD ×3.4 on four lanes** (×3.2 at DoP 24) · **DoP ×9.8** · DoP 1 and DoP 24 byte-identical · **≈4.4 fps at 512×512**. AVX-512 would give 16 lanes from the same code path — untested here, not claimed. Harness: `bench/Benchmarks/E8RaytraceBench.fs`.

**The honest finding: the bottleneck is the object, not the CPU.** Total leaf surface area ÷ root surface area ≈ **1,140** — 60,480 triangles over 240 vertices, mean triangle edge 1.63 against a scene diagonal 7.87, so every bounding box overlaps every other. Object-median → binned SAH did not move that ratio (1,004 → 1,142), and ordered traversal helped the scalar path only (2,243 → 1,787 ms) because the SIMD path is already triangle-test-bound. A GPU hits the same wall with more lanes to hide it.

**M5** is the survivor the TypeScript oracle already documented as legitimate. **M6 is an equivalent mutant with evidence**: the measured rank spectrum of the 19,680 candidates is exactly `{0: 240, 7: 19440}`, so `= 7` and `≥ 6` select the same set — and the test now pins the *whole spectrum*, so if a candidate family ever yields a rank-6 face the equivalence claim fails loudly instead of quietly becoming false. **M6b** is what proves the filter is not vacuous.

**M11 is the finding.** Mutating the traversal to push only the near child — never opening the far subtree — survived the entire suite, because **every ray-tracer falsifier was RELATIVE**: scalar vs vector, DoP 1 vs DoP N, both sharing `trace`, so a traversal defect changes both sides identically. Repair: `renderBruteForce`, the exhaustive no-BVH scan a BVH is obliged to reproduce. M11 re-run: killed.

**And that reference immediately exposed a second defect.** BVH vs exhaustive disagreed on **6 of 1,024 pixels** — two nearest hits at a *bit-identical* `float32` t on faces of different brightness (4_21 puts many faces on one plane), so the winner depended on visit order. That reintroduced at the occlusion layer exactly the order dependence rung 6 eliminated in shading. Nearest hit now **breaks exact ties on the lowest original face index**, making the answer a pure function of `(scene, ray)`; the two renderers then agree exactly and M12 is killed.

Two more caught in passing and recorded where they happened: a BVH child index computed as `left + 1` (a depth-first build does not place siblings adjacently — the guarding assertion fired on the first real scene), and two of my own test assertions that passed for the wrong reason (`compareCosines` compared against an accidentally-maximal `samples.[0]`; a 96×96 frame asserted to contain all five levels, which is a fact about sampling rather than the kernel).

### 6. Aaron's two design questions, measured

Both answered with numbers the shipped module produces (§7 of the research note), each pinned by a falsifier so the prose cannot go stale.

**"Will that work for a mirror?"** — the question splits, and the halves disagree.

- **A mirror in the scene reflecting our object: yes, unchanged.** Secondary rays are ordinary rays; the BVH and the five-level lookup serve them as-is.
- **Our object BEING a mirror: three obstacles, and the middle one is milder than expected.**
  1. **768 of 60,480 projected faces (1.27%) have no determinable front side** — their plane contains the origin. A genuine gap, not a tolerance artefact: the smallest non-zero origin-to-plane distance over the other 59,712 is **0.002329**, three orders of magnitude above the `1e-9` threshold. Rung 6 already closed the obvious repair (the projection of `a+b+c` is exactly 3× the projected centroid, so "import the 8D orientation" is the same failing test). Underneath: 27 faces per edge means no global inside at all.
  2. **A view-dependent term does not become per-hit work if the view is a root.** Measured over seven root views, the specular numerator takes at most **five** distinct values across all 60,480 faces. So a reflective 4_21 is one five-entry table *per view* — 240 tables, `240 × 60,480 ≈ 14 MB` — precomputable and still exact. What it costs is that the table stops being a property of the object and becomes a property of (object, view).
  3. **Exactness ends at the camera.** The specular denominator is `48 · √(8|V|²)`, rational **iff `8|V|²` is a perfect square** — true for a root (`64`), false for a free camera. That is rung 6's `√6` boundary one layer out, and the existing guard already refuses the mismatch rather than approximating it.

  Honest disposition: a reflective 4_21 would be buildable in exactly one register — **root-quantised views, two-sided, and the 768 sideless faces declared rather than shaded**. Anything else is a claim the geometry does not support.

  **Held on Aaron's instruction (2026-09-09): reflections wait for the projection measurement.** `081M23M0MVD087G0R003NR0ET1` is filed **BLOCKED**, not ready — a sibling agent is measuring whether the interpenetration and the overdraw pathology are intrinsic to 4_21 or artifacts of `embed3d`. The analysis above informs that decision; nothing is being built toward it.

  **One half of that question is already settled here, by where each quantity is computed:**

  | property | computed in | projection-dependent? |
  |---|---|---|
  | **27 incident 2-faces per edge** — `3 · f₂ / f₁` | `E8Exact`, pure integer 8D | **NO — a theorem about 4_21** |
  | f-vector, face normals, `\|n\|² = 48`, five levels | `E8Exact` / `E8Shading`, integer 8D | **NO** |
  | **768 sideless faces** | `E8Embedding`, after projection | **YES** |
  | **leaf/root area ratio ≈ 1,140** | `E8Raytracer`, projected triangles | **YES** |

  No float appears anywhere in the incidence's call graph, so no embedding can give the shell an inside — it can only change how the sidelessness manifests in 3D. The 768 and the overdraw ratio genuinely belong to `embed3d`, and those are the ones worth re-measuring.

**"Is five levels enough compared to real game engines, or is this a toy?"** — **as a renderer it is a toy**, in this repo's exact vocabulary, and the note says so without hedging: engines shade continuously in HDR float and tone-map to 256+ levels per channel, with many lights, shadows, occlusion, textures and a microfacet BRDF; this has one light, Lambert only, no shadows, no textures.

The structural answer is the useful one: **five is not a ceiling of the method.** It is the consequence of one light that *is a root* meeting normals that are *root sums*. Measured, with the field each change lands in:

| change | levels | denominator | field | exact? |
|---|---|---|---|---|
| **baseline** — one root light | **5** | `√384 = 8√6` | `Q(√6)` | yes |
| light off the lattice, integral, `\|L\|² = 204` | **49** | `√9792 = 24√17` | `Q(√17)` | **yes** |
| coordinate axis, `\|L\|² = 1` | 7 | `√48 = 4√3` | `Q(√3)` | yes |
| **two** root lights, summed | 9 | `√384` (shared) | `Q(√6)` | **yes** |
| per-**vertex** normals, at the vertices | 3 | `12096` | **`Q`** | yes |
| per-vertex normals, interpolated across a face | continuous | — | — | **no** |
| distance falloff `1/r²` | continuous | — | — | **no** |
| specular, **root** view | 3–5 per view | `384` | `Q` | yes |
| specular, **free** camera | continuous | `48√(8m)` | irrational unless `8m` square | **no** |

Three rows are worth reading twice:

- **A light off the root lattice buys 49 levels and costs no exactness at all** — it only moves `Q(√6)` to `Q(√17)`. Quantisation is the price of *choosing a root as the light*, not the price of being exact.
- **Two root lights stay in `Q(√6)`** — both terms share the denominator `√384`, so multi-light does not compound the field (9 distinct sums measured).
- **Per-vertex normals go the wrong way**, by an exact identity: every vertex has **756** incident faces and their normals sum to **exactly `1512 × the vertex itself`**, verified on all 240. Gouraud therefore degenerates to the sphere normal, the denominator becomes the *rational* `8 · 1512 = 12096`, and the level count **drops to three**.

**The claim, stated so it cannot be over-read:** the exact-integer core is a differentiator for **correctness and cross-oracle byte-lock**, not for visual quality. Five levels is a measurement of 4_21, not a rendering budget.

The throughput number is likewise a fact about 4_21 rather than about the kernel — filed as `081M23M0R3J087G0R000BBNXHV` to re-measure on a BVH-tractable scene.

**On paying for 8D and projecting to 3D** (§7.3). Aaron has questioned the representation layer itself. The critique is aimed at the geometry pipeline rather than at this core, but the rung supplies one data point and it points his way: **every locked quantity in §2 is computed in 8-dimensional integer arithmetic and never passes through `embed3d`** — the projection is used for exactly one thing, placing pixels, and never touches a brightness. So the extra dimensions are where the work happens and the 3D step is the thin part; and the measurements say the thin part is where all the cost (§4.1) and all the pathology (§6) live. What is **not** established is the stronger form — that we could simulate in 8D and never project. A viewer needs pixels; whether that reduction could move to the end of the ray is unmeasured and unclaimed.

### 7. Verdict on a fully-.NET engine

**Worth pursuing**, with a caveat about the object rather than the platform. The exact layer is ~900 dependency-free lines and F# expressed it without ceremony; `System.Numerics.Vector<T>` gives one code path across NEON/AVX2/AVX-512 at ×3.4 measured on four lanes; the DoP knob is honest and byte-identical at 1 and N; and the byte-lock held on the first run, so the .NET side can be held to the same treaty with no special pleading. Against: **this object is the wrong benchmark for a renderer**, and nothing here touches materials, shadow rays, denoising or an asset pipeline. Recommendation: grow the exact/math/SIMD layer in .NET, keep the web surface in TypeScript, treat Rust as *additional byte-lock independence* rather than a competing engine.
