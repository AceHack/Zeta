## Description

Rung 6 shipped a lit surface and stopped at a Wavefront OBJ. Aaron asked to *see* it, and asked four questions underneath. **The deliverable is the page**; everything else is what the page turned out to be evidence for.

## The thing you can look at

`demo/clifford-e8/index.html` — open it (GitHub Pages, or any static server; it is a classic script, so a plain `file://` open works too).

| | |
|---|---|
| backends | **WebGPU** -> WebGL2 -> Canvas 2D, auto-selected, **all three verified rendering** |
| modes | solid (z-buffer) · additive (order-independent) · wireframe (6,720 edges) |
| controls | drag to rotate, wheel to zoom, spin, exposure, **light-root gauge (0-239)**, CPU ray-trace button |
| page | 31,686 bytes · bundle 27,621 bytes |
| **geometry shipped** | **0 bytes** |
| built in the browser | 240 roots · 6,720 edges · 60,480 triangles · 181,440 vertices · 5 levels |

**Payload choice.** The page ships the *derivation*, not its output. The position buffer alone is 2,177,280 bytes as `float32` (184,320 as 8-bit indices over 240 points); the bundle that computes it is 27,621 bytes — smaller than any encoding of its own output, and the only form that stays true when a rung changes.

**The bundle is our modules, not a port.** `build-clifford-e8-page.ts` runs `Bun.build` over an entry that imports rungs 1-7 directly. There is no hand-written JavaScript geometry in `demo/clifford-e8/`. `clifford-e8-page.test.ts` *executes the committed bundle* and asserts its positions, levels, histogram and a ray-traced frame equal the TypeScript modules'.

## The number that reframes the rest

> **The derived surface has an overdraw ratio of 738.** Total triangle area **9,269** against a bounding-sphere area of **12.57**. Mean triangle bounding box: **29.3% of the whole scene diagonal**.

Everything follows from it: nearest-hit occlusion hides ~99.9% of what it draws; a ray genuinely meets thousands of triangles, so a BVH buys only **7.6x**; an unscaled additive pass saturates to white. Rung 6 declined occlusion and said why — this supplies the number behind the refusal.

## The four questions, answered with measurements

**1. CSS.** The blocker is not element count, it is the model: CSS 3D composites by **sorting elements**, and a per-primitive depth sort is exactly what is undefined here (27 faces per edge, constant interpenetration, depth cycles). **CSS 3D cannot render the 2-skeleton correctly at any element count.** Element count is a second wall, measured in Chrome: 240 elements 1.1 ms, 6,720 24.9 ms, 60,480 **351.5 ms** to build. What *is* viable: the **2D Coxeter projection** (240 points + 6,720 edges), where the occlusion question does not arise — that is the right CSS target, and rung 1 already emits it as SVG.

**2. Shaders.** The shading model *in the shader* is one array index — `o.shade = u.palette[u32(lvl)].x` in WGSL, `vShade = uPalette[int(aLevel)]` in GLSL. No normal uploaded, no dot product, no exponent (a falsifier greps for their absence). The intensity was computed in **8-dimensional integer arithmetic** before any projection; the GPU consumes 5 discrete levels. The single irrational is crossed **5 times for 60,480 faces**. Consequences: flat shading forces unindexed geometry (181,440 vertices over 240 points), and culling is off everywhere because there is no inside.

**3. Ray tracing, and is it fast on a CPU?** Nearest-hit is the **principled repair** of rung 6's refusal: the decision is per-sample, so interpenetration and depth cycles cannot arise. Measured, Apple M2 Ultra, **one thread**, TypeScript, BVH of 32,767 nodes:

| resolution | time | fps | µs/ray |
|---|---|---|---|
| 64² | 545 ms | 1.83 | 133.1 |
| 128² | 1,992 ms | 0.50 | 121.6 |
| 256² | 8,654 ms | 0.12 | 132.1 |
| 512² | 31,028 ms | 0.03 | 118.4 |

**2,780 triangle tests per ray.** So: **no, not at interactive rates.** Labelled *estimates* for the headroom: ~100 ms at 128² with 24 threads, ~22 ms with a native SIMD inner loop; 512² stays out of reach. And the honest closer — the GPU rasteriser already computes the same correct per-sample occlusion at full resolution, so ray tracing's value here is that it **can be checked** against an exhaustive scan.

**4. SIMD.** Ray/box first (3,134 node tests per ray -> a 4-wide MBVH), then SoA ray/triangle packing; ray packets last, because 738x overdraw destroys packet coherence. Layout before instructions, and half of it is done (the BVH is already flat typed arrays). **Plain TypeScript cannot reach it** — measured at ~48 ns per triangle test. The reachable path is **WebAssembly SIMD (`v128`)**, which this repo already builds in `src/wasm-dla/` and which would serve Bun *and* the browser page from one implementation; the ceiling is the **Rust oracle**. Register: `toy` — nothing here is SIMD-implemented or benchmarked.

## Two findings that were not in the plan

**The projection FOLDS.** `embed3d` is linear from 8 dimensions to 3, and edge-adjacent faces land on overlapping regions of the same 3D plane. About **1% of seeded rays meet two distinct triangles at bit-identical depth**, and **some tied faces carry different shading levels** — so the pixel's colour is genuinely ambiguous, not merely its provenance. The tracer now **declares its tie-break** (lowest index) instead of letting traversal order decide. Before that, the BVH and the exhaustive scan disagreed on 2 of 220 rays and *neither was wrong*.

**A silently-black WebGPU pass.** The additive pipeline rendered nothing because the bind-group layout declared `visibility: GPUShaderStage.VERTEX` while the fragment shader read the exposure from the same uniform. No error, just an absent picture. Found by looking at it; fixed; pinned by a falsifier.

## Mutation testing

**10 real mutants, 10 killed.** Killers named in the doc. **M6 is the one that matters**: rung 6 recorded that forcing `lambertCosine`'s numerator to zero *survived its entire suite* because `shadeFaces` carried an inlined copy. It is now killed **across a module boundary** — exactly the check a renderer with its own private copy of the shading model would have defeated.

Controls: a reworded comment **survived**; BVH children visited in the opposite order **survived** — and it survives *only because the tie-break is declared*, so it is a control that measures the fix. A third control (slab test accepts every node — semantically neutral) was **killed by a 5-second test timeout, not by a wrong answer**, and is reported as a failure of my control rather than of the suite.
