## Description

## Aaron's question, answered by measurement

> *"are we using features from the rolling prerelease? if not maybe we could pin the version before, if we are then we are going to need a way to reference the rolling tag for a while until they stop rolling. i really prefer not to have committed jars."* — and *"also for alloy make sure we are on the latest version there too."*

Both halves have measured answers, and they point opposite ways: **Alloy is de-vendored** (and was already the latest), **tla2tools stays committed** because de-vendoring it is not a de-vendoring — it is a verifier version change with a price only the maintainer can pay.

## Alloy — de-vendored, already latest, zero verifier change

| measured 2026-09-09 | value |
|---|---|
| latest Alloy release | **v6.2.0** (2025-01-09). `releases/latest` returns it; the only newer tag is `v6.3.0-begin`, with no release attached |
| committed `src/Core.Alloy/alloy.jar` | sha256 `6b8c1cb5bc93bedfc7c61435c4e1ab6e688a242dc702a394628d9a9801edb78d` |
| upstream `org.alloytools.alloy.dist.jar` @ v6.2.0 | sha256 `6b8c1cb5bc93bedfc7c61435c4e1ab6e688a242dc702a394628d9a9801edb78d` — **byte-identical** |
| asset mutability | every asset on the tag has `created_at == updated_at == 2025-01-09T08:18`, untouched since — no rolling hazard |

So "make sure we're on the latest" is settled by a digest rather than by release notes, and **no expectation could move, because no byte moved.** All five `.als` specs still run clean against the fetched jar.

The row goes into `tools/setup/manifests/from-url`, whose realizer already does exactly what is wanted — and both halves were exercised for real here, not assumed:

- a live fetch landed the pinned bytes at `src/Core.Alloy/alloy.jar`;
- appending one byte to the local copy made the next run refuse with `sha256 mismatch for ... expected 6b8c1cb5..., got 60967270...`. **Fail closed, no warn-and-continue, no bypass flag.**

## TLA+ — deliberately still committed, and the reason is a measurement

**(1) Do we use something only the rolling build has? Yes — one thing, and it is load-bearing.** All 52 gate-tier models in `registry/tlc-models.json` were run under three jars at the pinned invocation (`workers=1`):

| jar | banner | verdict |
|---|---|---|
| committed (control) | `TLC2 Version 2026.05.18.174321 (rev: 8ba1027)` | **52/52 agree with the registry** |
| v1.7.4 — last immutable release | `TLC2 Version 2.19 of 08 August 2024 (rev: 5a47802)` | **51/52** |
| v1.8.0 as re-uploaded today | `TLC2 Version 2026.09.09.124804 (rev: 65fbace)` | **52/52** |

The single 1.7.4 failure is `QuorumCollateralDeterrenceR2`. The registry pins `expectDetail: "Temporal property Deterrence was violated"`; 1.7.4 prints only the generic `Temporal properties were violated.` It still finds the violation and still exits 13 — what it loses is **which** temporal property broke, and `QuorumCollateral` has more than one. Under 1.7.4 a witness that started violating a *different* temporal property would pass. That is precisely the discrimination `judgeTlcRun` exists to keep.

(State counts are version-stable — `BftConsensus` gives the same exhaustive 4665495 distinct states under all three.)

**(2) Can we pin the rolling tag by digest? Mechanically yes — but the bytes we run are gone.** The `v1.8.0` asset was re-uploaded **today at 12:52 UTC**; that is the third build observed on one unchanged URL (2026-05-18 → 2026-08-11 → 2026-09-09). `71546dff…` is not obtainable from the tag, and tla2tools is not on Maven Central (`search.maven.org?q=a:tla2tools` → `numFound 0`).

So a from-url row for TLA is a **version change**, and it costs one of two things:

- **v1.7.4** — immutable, no maintenance tax, loses the diagnostic above.
- **v1.8.0 rolling** — keeps everything (52/52 measured), and the digest pin fails `install.sh` **closed** on the next upstream rebuild. Roughly monthly on the observed cadence, and each one needs 53 models re-measured *plus* a re-pin of the NCI witness receipt (`nci-witness-receipt.ts` `PIN`, the independent Python oracle, and the registry digest both carry) — an artefact whose entire purpose is to make a verifier change loud.

Both are Aaron's call rather than a hygiene decision, so the measurement is written into the manifest, `docs/INSTALLED.md` and the work item, and the decision is left open. **Adding the row later is one line plus one `.gitignore` line.**

## A defect found on the way, and closed

`Alloy.Runner.Tests.fs` had `if File.Exists alloyJarPath then … else ()`. A missing jar made `toolchainReady ()` false, every `assertSpecValid` return unit, and the **whole Alloy suite report green having checked nothing.** Inert while the jar was in git; armed the instant it became a fetch — so the de-vendoring could not land without fixing it.

Replaced by `the Alloy gate leg actually carries the gate on CI`, mirroring the TLA+ sibling: off the gate leg a skip is honest de-duplication, on it a missing toolchain is a failure. **Verified by mutation** — forcing the gate-leg branch with the jar removed fails that one test while the six spec tests still pass, which is exactly the vacuity it now catches.

## `clone-at-tag-stays-sufficient` — how this design stands

Stated plainly, since the rule requires it. `git clone` at a tag no longer yields a runnable Alloy lane without a fetch. What it does yield:

- **The lane degrades loudly, not silently.** On the Linux-x64 gate leg a missing jar is now a test failure naming the toolchain. Off it, the skip is the same de-duplication the TLA+ lane has always had.
- **No package manager is required.** The fetch is `curl` + sha256 in `tools/setup/install.sh`; `ace` is not on the path to a buildable tree, so `lint-clone-at-tag-is-sufficient.ts` is untouched.
- **`dotnet build` and every non-Alloy check are unaffected** — the jar is a verifier, not a build input.

The honest cost: the Alloy lane now needs network once. The honest gain: 20 MB of unreviewable binary leaves the history, and the verifier's identity becomes a line of text a reviewer can read in a diff — which is what `no-binary-in-proof-lineage` asks for in the first place. A verification lane that silently passes with its verifier missing would have been far worse than a committed jar, and that is the case this PR closes rather than opens.

## Falsifiers touched, and mutation-tested

`lint-verifier-jar-provenance.ts` held one regime ("committed ⇒ derive identity") and now derives the regime per jar, refusing a jar that is in **both** (a fetch over a committed copy) or **neither** (a path nothing fills). Nine mutants of its guards, **all killed**:

`isTracked` throws rather than returning `false` when `git` itself fails — a failed probe is `unknown`, never a negative result, and returning `false` there would have produced a confident "neither tracked nor pinned" from a check that did not run.
