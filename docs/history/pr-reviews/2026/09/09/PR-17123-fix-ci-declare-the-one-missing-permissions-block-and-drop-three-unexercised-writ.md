## Description

fix(ci): declare the one missing permissions block and drop three unexercised write grants

Scorecard reports 26 open TokenPermissionsID alerts. Twenty-five of them are
NOT a missing permissions block -- they are workflows that genuinely push
commits or open PRs and are already scoped to a single job. This change fixes
only the four that are real, and states why the rest are not.

Measured, not assumed. Every write-granted workflow was checked for an actual
write, following the call into the script where the workflow itself only
invokes bun:

- 18 of them push, open a PR, rerun a run or file an issue. Legitimate.
- agent-proposal-gated-commit and passkey-proposal-gated-commit look
  write-free in the YAML; both call runners that push
  (planning/agent-proposal-runner.ts:130,
  planning/proposal-gated-commit-runner.ts:310). Legitimate. A grep of the
  workflow alone would have mis-scored these two as over-grants, which is why
  the probe followed the call.
- mux-swarm-tick does not. Fixed below.

The four fixes:

1. udp-lossy-tests.yml declared no permissions at all -- the only workflow of
   92 in that state. It runs `bun install` on pull_request, which executes
   PR-controlled lifecycle scripts, so what the token carries matters. Blast
   radius today is nil: the repo default_workflow_permissions is currently
   `read`, so the job already gets a read-only token. The defect is that this
   is an implicit grant riding on a mutable repo setting rather than a
   declared one. Now declared `contents: read`.
   Closes TokenPermissionsID 671 and CodeQL actions/missing-workflow-permissions.

2. manifesto-citation-snapshot-cadence.yml and
3. context-cost-trend-cadence.yml each carried a top-level write block byte-
   identical to the one their single job already declares. The top-level copy
   granted nothing the job did not have and would have silently handed the
   same privilege to any job added later. Top level is now `contents: read`,
   matching the pattern the other cadence workflows already use.
   Closes TokenPermissionsID 735 and 734.

4. mux-swarm-tick.yml held `contents: write` + `pull-requests: write` for a
   job whose only payload step runs swarm/swarm-controller.ts -- which shells
   out nowhere and performs no git or forge write. The scope was never
   exercised. It was not inert, though: the job fetches and runs a
   third-party installer at runtime (ollama.com install.sh) while the
   checkout leaves a write-scoped GITHUB_TOKEN in .git/config. Narrowed to
   `contents: read` and the checkout set to persist-credentials: false.
   Behaviour risk is nil by the workflow's own record -- its header notes no
   run has ever succeeded.
   Closes TokenPermissionsID 687.

Deferred, not dismissed: the remaining 22 TokenPermissionsID alerts are on
write grants this audit found to be exercised and already job-scoped.
Scorecard offers no in-repo allowlist for a justified write, so they stay
open rather than being dismissed on a claim nothing rechecks. Narrowing them
further is not available -- Scorecard scores a job-level write the same as a
top-level one, so moving the grant down only relabels the alert.

Verification: python3 yaml.safe_load parses all four; the effective
permissions of every job are unchanged except mux-swarm-tick, which loses a
scope it never used. audit-workflow-write-token-consistency,
lint-workflow-job-timeouts and audit-action-sha-roster all pass.
