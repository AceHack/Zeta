## Description

fix(081M22T9CFA087G0R0026YN1NW): a QEMU failure must carry what the guest actually said

The six workflow_dispatch-only ISO scenarios were dispatched for the first time
(run 34324877507). Three failed. Two of them -- scenario 3 (reformat with
retention) and scenario 4 (path-fork migrate vs fresh) -- failed IDENTICALLY, in
the shared baseline step rather than in their own logic:

  QEMU retention command failed at initial-install-from-iso-with-disk with
  exit 1: timeout (1800000ms) waiting for serial markers:
  ZETA CLUSTER NODE INSTALL COMPLETE

And that is the entire record. The serial log is written to a FILE, and no
failure path in `runManagedSerialPhase` put any of it in the result, so thirty
minutes of guest behaviour reached CI as four words. That cannot distinguish:

  - a guest that never booted        -> serial log EMPTY; suspect firmware or
                                        boot order, not the installer
  - a guest that booted and hung     -> serial log full of NixOS output; the
                                        installer is the suspect

Those are opposite diagnoses with opposite fixes. Diagnosing it required
reading the harness source and forming a hypothesis about the firmware, which
is exactly the work a failure message exists to make unnecessary.

Every failure path now carries a bounded serial tail: the timeout, and the
"QEMU exited before serial markers" path. An EMPTY tail is reported AS empty
and says so in words -- "the guest wrote nothing to ttyS0" is a sharper fact
than "we have no information", and it is the more likely case here.

WHAT THIS DOES NOT DO. It does not fix scenarios 3 and 4. I have a hypothesis
-- `buildQemuSystemBootArgs` boots `-machine q35` with SeaBIOS and no pflash,
while the harness that DOES pass on every PR (`qemu-full-install-test.ts`)
UEFI-boots via OVMF pflash -- and I am deliberately not acting on it, because
the next run will now say whether the log is empty or full, and that settles it
in one observation instead of a guess. The scenarios stay dispatch-only and
stay failing; this makes the next dispatch informative.

Falsifiers: five, covering empty, whitespace-only, tail-not-head, no-padding,
and the DEFAULT window. Five mutants, all killed -- including the fourth, which
survived the first pass: widening the default window from 40 to unbounded was
invisible because every test passed an explicit window while no call site does.
An unbounded serial dump is a different defect from an absent one, so the
default is now pinned.
