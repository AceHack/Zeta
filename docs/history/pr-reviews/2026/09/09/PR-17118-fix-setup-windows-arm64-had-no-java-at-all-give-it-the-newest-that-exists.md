## Description

fix(setup): Windows ARM64 had NO Java at all; give it the newest that exists

Aaron, on the earlier finding: "on windows can we use openjdk or whatever that
other version was i see plenty of java 26 versions for windows." He is right, and
the distinction is the whole point: Java 26 exists for windows/X64 and does not
exist for windows/AARCH64. Measured against two vendor APIs, controlled against
x64 so a zero means absence rather than a broken query:

  windows/x64       Adoptium:  21 yes   25 yes   26 yes
  windows/aarch64   Adoptium:  21 yes   25 NO    26 NO
  windows/aarch64   Azul Zulu: 21 yes   25 yes   26 NO

So no vendor ships Java 26 for Windows-on-ARM, and the newest that does exist is
Zulu 25.

WHAT WAS ACTUALLY BROKEN. install.ps1 listed `java` in the Windows ARM64
`$unsupported` map with the reason "mise has no Java 26 metadata for Windows
ARM64". That reason is true and remains true -- but the EFFECT was that this
platform installed NO JAVA AT ALL, rather than an older one. An accurate note
about 26 quietly became a total absence.

Java now leaves that map and is installed separately as `java@zulu-25`. It stays
excluded from the .mise.toml GRAPH, because the pinned 26 genuinely has no build
here.

THE PIN IS DELIBERATELY NOT CHANGED. Every other platform keeps 26; this is a
platform-coverage fallback, not a downgrade. Changing .mise.toml would have
traded a real regression on three working platforms for a fix on one.

VENDOR-QUALIFIED ON PURPOSE: a bare "25" resolves to Oracle OpenJDK, which
publishes no Windows ARM64 build and would fail exactly as 26 does.

BEST-EFFORT BY DESIGN: the prior behaviour was no Java, so a failed install here
can only restore the status quo. A hard failure would make this change strictly
WORSE than the omission it replaces, so it is wrapped and the catch says plainly
that the platform continues without Java.

Verified: PowerShell parses (pwsh 7.6 AST parser, 0 errors); the existing smoke
test is updated and passes 12/12; tsc 0 errors.

MUTATION TESTING CAUGHT MY OWN GUARD BEING VACUOUS, for the fourth time this
session in the same family. The first draft asserted "try {" appeared ANYWHERE
after the spec index -- and passed against a mutant that replaced the guard with
`if ($true)` / `else`, because install.ps1 has other try/catch blocks further
down. Matching a token that also exists elsewhere is not a guard. Now scoped to a
700-character window from the spec, and required to contain the catch's own
"continues with no Java" text so the failure cannot be swallowed silently. Both
mutants now die: dropping the try/catch, and unqualifying the version.
