## Description

## Summary
ADR for the per-maintainer CURRENT-<name>.md pattern, per Aaron's 2026-04-23 framing. Distilled currently-in-force rules per maintainer (human OR external AI), live in per-user memory, pointer-linked to full memory files for depth.

## Problem
Raw memory folder accumulates append-only entries. Conflicting rules pile up (Aaron says X, realises wrong, says Y — both files exist). Reading N memory files to infer current state gets expensive.

## Decision
One CURRENT-<firstname>.md file per maintainer in per-user memory. Distilled topic-sections, pointers to full memories, supersede markers for retired rules. Newer memory triggers same-tick CURRENT update. CURRENT wins on conflict with older raw memory.

## What landed (per-user, outside this PR)
- `CURRENT-aaron.md` — 12 topic-sections
- `CURRENT-amara.md` — 8 topic-sections (first external-AI-maintainer)
- Memory: `feedback_current_memory_per_maintainer_distillation_pattern_prefer_progress_2026_04_23.md`

## What this PR lands (in-repo)
`docs/DECISIONS/2026-04-23-per-maintainer-current-memory-pattern.md` — the ADR. Makes the pattern legible for any factory-adopting project.

## Why ADR in-repo but CURRENT files not
CURRENT files contain maintainer-specific (potentially company-specific) context — stay in per-user memory per the open-source-repo-generic rule. The ADR describes the generic pattern; the instances are private.
