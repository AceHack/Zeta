## What lands

Two load-bearing paths when a vendor harness limitation surfaces:

1. **Submit feedback upstream** to the vendor's open-source repo (bug, PR, design discussion). Treat vendor as peer dependency, not immutable constraint.
2. **Make our substrate resilient** against vendor limitations. Even when upstream fix lands eventually, local resilience lets the factory work reliably *now*. Resilience-against-vendor-limitations is itself substrate.

Most real cases want **both paths** (upstream for long-term fix, local for now).

## Why this matters under the scope reveal

Vendor-resilience is scope-aligned. The intellectual-backup-of-earth mission writes *through* harnesses — when a harness leaks (e.g., Claude Code console-printing conversation content per Gemini's 2026-04-30 flag), the backup leaks. That's not "out of scope," it's a direct integrity threat.

The "out-of-scope" reflex comes from a smaller mental model where we're a *consumer* of vendor harnesses. Aaron's correction inverts: we're a *peer dependency* — both absorber AND contributor. Otto-323/Otto-346 discipline at the harness layer.

## Operational rules

- Classify each vendor limitation into the two paths.
- Treat vendor harnesses as peer dependencies (read CHANGELOGs, participate in issue trackers).
- Don't conflate "vendor limitation" with "fundamental constraint."
- Receipt-track upstream contributions (issue numbers, PR refs).
- Resilience rules need existence-of-vendor-fix triggers — workarounds revisit when upstream fix ships.

## Live example included

Claude Code console-print leak. Path 1 = upstream feature request (`anthropics/claude-code`). Path 2 = prompt-protector content-classification rules (already operationalized as local resilience).
