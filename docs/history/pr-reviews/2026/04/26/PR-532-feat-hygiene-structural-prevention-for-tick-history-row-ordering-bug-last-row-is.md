## Description

## Summary

Aaron 2026-04-26 — *\"anything we can do to prevent it in the first place?\"* — after I caught the recurring tick-history row-ordering bug yet again this tick.

**Bug shape**: Edit tool's `old_string=existing-line` pattern tends to insert NEW row BEFORE the matched line, producing reverse-chronological order in \`docs/hygiene-history/loop-tick-history.md\`. I've caught this at least three times across recent ticks; relying on agent vigilance hasn't worked.

**Structural fix**: three additive layers.

### 1. CI gate — \`tools/hygiene/check-tick-history-order.sh\`

Validates that the **LAST row in the file is the LATEST timestamp**. Catches the specific bug shape (new row inserted before previous last row) without requiring history-rewrite (Otto-229 forbids editing prior rows).

Two-tier:
- **Default**: quiet on historical strict-order violations; fails ONLY on the last-row check
- **\`--strict\`**: reports historical violations as advisory (for human spelunking)

Per Aaron's specific guidance — *\"we might should allow this one override if it exists a lot\"* — historical-violation noise is opt-in.

### 2. Append helper — \`tools/hygiene/append-tick-history-row.sh\`

Wraps \`cat >> file\` (the canonical chronological-tail-append pattern) so the bug shape can't occur via this entrypoint. Validates new row's timestamp >= latest existing.

### 3. CI workflow — \`gate.yml\` job \`lint-tick-history-order\`

Wires the check into CI so violations fail fast at PR-open time.

## Why this is structural, not just another rule

Per Otto-339 anywhere-means-anywhere applied to discipline-enforcement: enforce at the **layer that catches all paths** (CI gate at commit time), not at the input-tool layer (which would require every agent's vigilance and miss future tools / future agents).

Adding a rule in CLAUDE.md or a memory file would be Tier-1 (language layer) — Aaron's question was about **structural** prevention, which means moving the discipline to a mechanism layer.

## What this DOES NOT do

- Does NOT auto-reorder rows. The fix is the committer's responsibility (revert + re-append correctly). Auto-reordering would silently rewrite history; this check is intentionally advisory-with-teeth.
- Does NOT validate row content beyond the timestamp prefix. Markdownlint and other lints handle table structure.
- Does NOT prevent the bug at the Edit tool layer (impossible — that's a tool default). It catches the bug at commit/push time.
