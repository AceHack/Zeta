## Description

## What

Extends WorkspacePort into a full storage abstraction that doesn't assume any specific backend.

### Storage backends

| Backend | Description | Requires |
|---------|-------------|----------|
| `os-fs` | Traditional OS filesystem | OS with fs |
| `git` | Content-addressed (going away per roadmap #1) | git |
| `zeta-fs` | Zeta FUSE — APFS-like history + binary, single-file, embeddable | Nothing (IS the kernel) |
| `simulated` | In-memory DST | Nothing |

### New capabilities

- **Binary content**: `readBinary`/`writeBinary` for compiled artifacts, images
- **FileEntry**: `content: string | Uint8Array` + `binary: boolean` flag
- **Cross-platform permissions**: `FilePermissions { executable }` maps to chmod/git-mode/no-op
- **Platform**: adds `'zeta'` for when we ARE the micro/unikernel
- **readFileEntry**: returns content + permissions + binary flag in one call

### Design

The port assumes nothing about the underlying storage. No git required. No filesystem required. Everything can live in one file on the zeta-fs backend. The interface is the contract; backends are swappable.

her consent). The -x flag IS the NCI at the file-permission level.

Constants:

  GATED_PERMISSIONS      { executable: false } — consent-gated (-x)
  TRADITIONAL_FS_DEFAULT { executable: false } — legacy mapping from POSIX

This inverts the POSIX convention where inert is default. In a database
where content IS code (every file is potentially an executable program,
a prompt source, or a live memory), alive-by-default is correct.
