## Description

## The flake

`lint` jobs intermittently go red at the toolchain-install step:

```
mise ERROR Failed to install pipx:ruff@0.15.17: failed to ln -sf ./3.14.6 .../mise/installs/python/3.14: File exists (os error 17)
```

Observed 2026-06-20 on `lint (§33 migration xrefs)` (commit `c0c7ad4d7`). The §33 content check **never executed** — the install step aborts first under `set -e`, so the failure is an environment race, not anything in the triggering commit.

## Root cause

Hosted GitHub runner images ship a pre-warmed mise cache where the python **minor** alias path (`installs/python/3.14`) is a **real directory**, not a symlink. After `mise install` lays down our pinned patch (`python = "3.14.6"`) it runs `ln -sf ./3.14.6 .../python/3.14` to maintain the minor alias — and `ln -sf` cannot overwrite a directory → `File exists`. This is an **idempotency violation** (discipline #6 / manifesto §12): apply-once vs apply-N-times diverge because the alias slot is occupied.

## Fix

In CI only, before `mise install`, remove a stale **non-symlink** python minor-alias dir (matching `X.Y`) so mise can recreate it as the symlink it expects.

- **Idempotent** — a correct symlink or absent path is left untouched; the real patch install (`3.14.6`, two dots) is never removed.
- **Scoped to `GITHUB_ACTIONS`** — dev laptops, where a real `installs/python/3.14` may be intentional and the collision is unobserved, are untouched. (Revert/widen note in-code if it ever recurs on laptops.)
- **Unix common path only** — `install.ps1` unaffected (Windows mise doesn't use POSIX `ln -sf` for aliases).

## Verification

- `shellcheck` clean, `bash -n` clean.
- Guard logic exercised against a temp fixture: non-symlink `X.Y` dir removed; symlinks and the `X.Y.Z` patch dir preserved.

Note: this is Dejan's install-script domain; flagged + fixed under standing authorization after the flake recurred. The transient instance was cleared by a job re-run; this removes the recurrence.
