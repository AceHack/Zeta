## Description

## The circle, and where it was cut

Our CI proof asserted **19 of 45** ArgoCD Applications. Eleven of the exclusions came from ONE content-based rule in `argocd-health-test.ts` — `isExcludedFromIncludedProof` auto-excluded any Application whose `Application.yaml` or child YAML mentioned `storageClass: longhorn`. That rule was **circular**: the apps were excluded because Longhorn was excluded, and Longhorn was excluded because a kind node has no second disk.

**A StorageClass is a NAME bound to a provisioner, and workloads only ever name it.** So dev now applies a StorageClass named `longhorn` over `rancher.io/local-path` — `full-ai-cluster/dev-cluster/manifests/longhorn.yaml` — and the same unmodified manifests, same 100Gi request, same class name, bind on a kind node.

**Zero application manifests touched. Production untouched** — structurally, not by convention: that file lives under `dev-cluster/`, which ArgoCD never reads, and on bare metal the Longhorn chart creates the real class over `driver.longhorn.io`.

Not a new shape here either. `zeta-local-path` has been exactly this alias since it was added. This adds the second name and routes both through one shared apply path — which also fixes `bringUpK3dDevCluster` and `apply-root-app.ts`, neither of which applied `zeta-local-path` at all.

## The exclusion is CONDITIONAL, not deleted

**An unbindable PVC does not fail.** ArgoCD reports a pending PVC as Progressing, never Degraded, so the run burns its whole `--timeout-sec` and then names the *symptom* rather than the cause — and if the job's 60-minute cap trips first, there is no verdict at all. So the old rule still applies in full whenever the substrate is absent, in four layers:

1. **Repo-side, fails closed.** `devLonghornStorageClassAliasDeclared()` returns `false` on absent / unparseable / multi-document / not-a-StorageClass / wrong-name / **wrong-provisioner**. `false` restores the old blanket exclusion for every longhorn-backed app.
2. **The provisioner is compared, not just the name** — on *both* sides. `kind: StorageClass` + `name: longhorn` + `provisioner: driver.longhorn.io` is exactly what a kind node cannot run; an existence-only check would have passed it while nothing could provision.
3. **Access-mode carve-out, gating on its own.** RWX claims stay excluded whichever class they name — every dev class is `rancher.io/local-path`, which is RWO-only.
4. **Live substrate check — new `DevStorageClassMissing` failure.** Before an included-scope run waits on anything, the harness verifies the class is in the cluster *and* provisionable. Three seconds and the right noun instead of forty minutes and the wrong one.

## Self-review found three fail-open paths — fixed, each with a falsifier

The first commit's guard had real defects, found reviewing it and fixed in the second:

1. **RWX was checked only inside the longhorn branch**, so an RWX claim against `zeta-local-path`, against kind's default, or against no class at all was never access-mode-checked and could hang. Latent (no live instance), now hoisted.
2. **The provisioner was unchecked on both sides** (finding 2 above).
3. **`apply-root-app.ts` applied the root catalog without the aliases** — a third door that the bring-up falsifiers did not watch.

**Two claims corrected rather than left standing**, because a wrong rationale here becomes a cited fact later:

- *"a timeout prints no verdict at all"* was **false** of this harness — `waitForApplications` returns the stuck verdicts and `main()` prints them. Reworded in all four places.
- the RWX guard was described as *structural*. It reads only the **checked-in tree**, and all ten unlocked Applications are `spec.source.chart` against an external `repoURL`, so their access modes live in the upstream chart. It is a **floor**, not a proof — stated as such, with the real fix named.

Also documented rather than glossed: the dev alias is `WaitForFirstConsumer` where prod Longhorn is `Immediate`, so an unschedulable pod or a consumer-less PVC binds in prod and pends in dev. That is exactly what `hindsight` hit. `Immediate` is not the fix — it would have local-path pick a node ahead of the scheduler.
