## The live run refuted my own fix; this is the fix-forward

`main` went red on the k8s lane after #13410 merged (auto-merge fired on
`gate (required)`, the only required check, before the live proof finished). This
restores it and records what the run taught.

**What the live run 32532470499 actually said:** `cockroachdb` and
`kube-prometheus-stack` both reached **Synced+Healthy** — those two fixes are
live-proven and stay asserted. `weaviate` alone failed, `OutOfSync/Progressing`,
with the ~3-minute resync loop unchanged.

The live run refuted my own fix, and this is the fix-forward. Run 32532470499
passed `cockroachdb` and `kube-prometheus-stack` — both reached Synced+Healthy,
so those two stay asserted — and failed on `weaviate` alone,
`OutOfSync/Progressing`, with the ~3-minute resync loop unchanged.

THE CAUSE I DID NOT LOOK FOR. weaviate renders TWO `type: LoadBalancer` Services
(`weaviate`, `weaviate-grpc`). gitops-engine `getCorev1ServiceHealth` reports a
LoadBalancer Service whose `status.loadBalancer.ingress` is empty as PROGRESSING,
unconditionally. A kind node runs no LoadBalancer implementation, so those
Services never get an address and the Application could NEVER have been Healthy
in that lane, whatever its sync status did. `weaviate-0` was 1/1 Running for 39m
while that held, which is exactly how the blocker stayed hidden behind the one
that was found.

THE ERROR WAS THE INFERENCE, NOT THE MEASUREMENT. The `randAlphaNum` render
nondeterminism is real and stays proven by byte diff. What I did was treat a
confirmed cause of OutOfSync as THE cause of the failure and never ask what made
it Progressing — one confirmed cause read as the cause. The `ignoreDifferences`
rule is KEPT, because the nondeterminism it removes is real and because on metal,
where cilium-lb-ipam assigns LB addresses, it may be the whole story. Its status
is now stated as UNMETERED — implemented, plausible, unfalsified — since the loop
survived it live and this lane cannot meter it until the health half lifts. The
Application's own comment now leads with that rather than claiming a fix.

AND THE DIAGNOSTICS THAT WOULD HAVE NAMED IT. The lane could report
`weaviate is OutOfSync/Progressing` and not say WHICH of its six resources was
which, so the cause was reconstructed by rendering the chart locally and reading
gitops-engine — and the first reconstruction was wrong. On every failure the lane
now prints each non-Synced/non-Healthy Application's per-resource
`status.resources` rows plus `status.conditions`; against a fixture that emits
`Service/weaviate: sync=Synced health=Progressing Waiting for load balancer to be
assigned`, which is the line whose absence cost a wrong fix. Green runs print
nothing and it can never fail the job.

Verified: 491 cluster tests pass, tsc, lint:typescript, all six offline audits,
ratchet 320/19 exactly at ceiling, actionlint clean, and the diagnostics jq run
against a fixture covering the failing, healthy and no-resources cases. Three
mutations, each asserted applied by byte cmp before its result was read: weaviate
drifting back onto the asserted roster (red), its reason replaced by a vague one
(red), and — recorded because it is the honest result — narrowing one phrase in
the reason stayed GREEN, since "LoadBalancer" still appeared elsewhere in it.
