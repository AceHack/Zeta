## What this is

The two first-metal bringup runbooks predate everything that landed on 2026-08-20/21. I walked every documented step against `origin/main`, and rehearsed the non-destructive half on the operator's Mac against CI run **32461224707** (`main`, head `94bdcb7da1`) and its real 1.57 GiB x86_64 ISO. **Nothing was written to a block device**; a USB stick is currently attached to that Mac and the flasher was never pointed at it.

## The defect class the task named, found twice

**1. The documented rename is refused by the documented gate.** CP-1's own manual block says: download the artifact, `mv` it to a `zeta-installer-*` name, `mv` the sidecar alongside. The 2026-08-21 text above it then claims a single-entry sidecar is "bound to its file by its own path" so the rename is tolerated, and cites falsifiers at `verify.test.ts` §8 / §8b.

`checkIsoAgainstManifest` does `entries.find(e => e.filename === isoBasename)` and has no other branch. `grep -c "§8" verify.test.ts` is **0**. Rehearsed through the real entry point:

```text
$ bun src/Core.TypeScript/zflash/flash-usb.ts --short <renamed>.iso
ISO: …/zeta-installer-25.11-ci32461224707-2026-08-21-x86_64.iso (1.57 GiB)
flash-usb: ISO INTEGRITY NOT ESTABLISHED (iso-not-in-manifest)
  SHA256SUMS does not mention zeta-installer-…-x86_64.iso -- it lists:
  nixos-minimal-25.11.20260522.b77b3de-x86_64-linux.iso -- refusing
  No device has been touched.                                          # exit 2
```

**2. "`zflash` copies the sidecar across for you" is false, and the bare form both runbooks recommend cannot pass zflash's own gate.** `autoDownloadFreshIsoIfNeeded`'s single `copyFileSync` call site (`cli.ts:479`) copies the `.iso`; `grep -cE 'sha256|manifest' cli.ts` is **0**. And on a machine with no `~/Downloads/zeta-installer-*.iso` at all, `autoDiscoverIso` bails *before* the auto-pull is reachable — it cannot bootstrap itself.

Related: `iso-not-in-manifest` was documented as "you staged the ISO by hand". It is the *default* outcome — and `~/Downloads/SHA256SUMS` on this machine is still the **Bitcoin Knots** manifest, so the refusal prints 28 bitcoin filenames. Rehearsed.

## The three 2am-killers, each verified independently

- **Enter does not cancel the cancel window, and mashing it burns the countdown.** `read -n 1` takes Return as its delimiter and leaves the variable empty, so `[ -n "$ZETA_CANCEL_KEY" ]` never fires — and each Enter satisfies `read` early, so the loop skips its second. Press `x`.
- **A successful cancel exits 0**, which `zeta-first-boot.sh` reports as `Install complete. Rebooting in 10s`.
- **Nothing writes an `ok` record to the attempt ledger** — that `printf` is the only ledger write in the script — and `started` counts as a failure, so the fourth install from one stick opens the breaker.

## Also corrected

- Two documented output lines exist nowhere in the code (one only in a comment header).
- `Which disk is the BOOT disk?` does not prompt — `BOOT_DISK=auto`.
- **A7 / A8 / A9 do not fire at all.** `ZETA_AUTO_CONFIRM=WIPE` disables every prompt, so no console password, no credential blob, no `gh auth login`. CP-3..CP-6 of `zflash-end-to-end.md` are therefore not exercised by a default bringup, and are now banner-flagged as unproven rather than presented as a procedure.
- The discovery halt banner tells the operator to run `zflash --role …` / `--join-server-url` / `--join-token`. zflash refuses all three.
- The inline onboarding flow fires on every run because the derived slug is `aaron-stainback` and the repo has `maintainers/aaron/` — which also silently drops the operator's published SSH keys from the ESP. `--ssh-key` is now in the documented command.

## What could not be rehearsed off-hardware, and why

Stated in the runbooks rather than guessed: **there is no dry-run** (`--test` only swaps the ESP pubkey payload; the `dd` still happens), so nothing past the destroy challenge was executed. Also unverified: `read -n 1` under systemd on tty1, whether a serial-only operator can answer the cancel window at all (output mirrors to `ttyS0`, stdin is `tty1`), whether the boot ESP sits at partition 1 or 2, all real `blkid`/`lsblk` shapes, every mDNS behaviour between two machines (the module says so itself: *"DESIGNED AND UNRUN until two machines boot on one segment"*), and the full keyless cosign chain (`cosign` is not installed; only the digest binding was checked).

## Code defects filed, not fixed here

Deliberately left as documentation rather than a code change to a destructive tool I cannot rehearse end-to-end: the auto-pull should fetch `<artifact>.sha256` and rewrite its filename field; the refusal messages should name reachable remedies; something should write an `ok` ledger record; the cancel prompt should not say "any key".
