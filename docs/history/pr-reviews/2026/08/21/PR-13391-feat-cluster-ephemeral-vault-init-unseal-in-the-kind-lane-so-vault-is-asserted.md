## Description

## What

`vault` was deferred from the included Synced+Healthy proof because it comes up **SEALED** and readiness needs `vault operator init` + `unseal` — commands that MINT root and unseal key material, a gated class under `vault/TOPOLOGY.md` §5.

The maintainer authorised the **ephemeral** case on 2026-08-20: *"if we init key materials and throw it away not a bit deal."* The authorisation is not "agents may init Vault"; it is **"material that cannot outlive the job is not custody"**. So this PR is an argument that the material cannot outlive the job — made by checks, not by prose.

`vault` now reaches Synced+Healthy in the kind lane and leaves both deferral registries.

§5 also says *"Do not automate step 5 [on Vault CE]. Automation would have to hold unseal shares somewhere a process can read them."* That sentence is about the **metal** cluster and still stands there. Here there is no "somewhere": the shares live for the seconds between init and unseal, inside one process about to exit, on a cluster about to be deleted. The new module says out loud that if it ever grows a way to persist a share, that sentence applies again in full and the module must be **deleted, not amended**.

## Same shape as §5, deliberately

## What I did with the generated key material, and how I proved it does not persist

* **Never written.** Init's stdout is never logged, never returned, and never placed in a failure detail — *including* on the failure path, where stdout would still be material.
* **Never in argv.** The share travels on **stdin**, because argv is visible in `ps` inside the pod and in any apiserver audit record of the exec.
* **The falsifier — `scanForKeyMaterial` runs WHILE STILL HOLDING the shares.** It searches every surface a later reader could reach: this job's own stdout transcript, the report object about to be printed, `vault-0`'s container logs, `RUNNER_TEMP` (where `tee` writes `included-proof.log`), and every dirty path in the working tree. That is the *only* moment such a search is possible, which is why it happens there rather than being asserted afterwards.
* It fails if it finds them, **and it fails if it scanned zero bytes.** A scan that looked at nothing and found nothing must not read as a scan that passed.

Fail-closed gate, four separately-named refusals. The sharpest refuses `--existing` — that attaches to a cluster this process did not create and will not destroy, which is the metal case wearing the harness's clothes. The CLI refuses the same combination a second time at parse, before the gate ever runs.

## Not weakened to get a pass

`vault` is asserted under the **FULL auto-sync contract** and joins the guard test pinning `deepseek-coder`/`qwen-coder`/`orleans`. Asserting it under the manual-sync contract instead — exists + compared, never synced — would reproduce the exact cdi/kubevirt vacuity #13084 had to fix, and would let the lane go green with Vault still sealed. `live kind included` is **not** `continue-on-error` and this PR does not re-add the flag.

The old deferral reason is kept in place as a `WAS:` / `LIFTED BY:` record rather than deleted, so both the cause and its lift stay legible.

## `spire` is not lifted here

Its recorded reason — *"Vault upstream CA + kind PVC wiring"* — is **stale on both halves**, and Vault initialisation fixes neither. The `upstreamAuthority.vault` block is entirely commented out, confirmed by rendering chart `0.24.2`: zero occurrences of `upstream` in 1386 lines, the server self-signs (`ca_subject: zeta-spire-ca`). A commented-out block is not a pending dependency, so `spire` was never gated behind `vault` at all. Its PVC is RWO/5Gi on `zeta-local-path`, which the lane serves.

Two **real** blockers were measured instead, both unrelated to Vault, and reported separately rather than guessed at:

1. **No `spire-crds` source in the ArgoCD/kind lane.** Chart 0.24.2 ships no `crds/` and no `spire-crds` dependency, yet renders 3 `ClusterSPIFFEID` resources. The repo knows this only on the k3s path (`k8s/bootstrap/spire-install.yaml` installs `spire-crds` as a k3s-only `helm.cattle.io/v1 HelmChart`), and the kind bring-up never applies that directory.
2. **The chart's `pre-upgrade` hook Job deadlocks the first ArgoCD sync.** gitops-engine maps `pre-upgrade` → PreSync unconditionally, so on the very first sync a Job runs `kubectl patch` against a ValidatingWebhookConfiguration that does not exist yet → PreSync fails → sync aborts → the webhook is never created. Self-perpetuating. The chart documents the escape hatch itself (`global.installAndUpgradeHooks.enabled: false`, *"should be disabled when using helm template"*, which is what ArgoCD does).

Honest limit: those two are derived from the rendered chart plus gitops-engine's hook-mapping source, **not from an observed run**. They are stated as derivations, and `spire`'s registry entry is left in place rather than lifted on an unverified fix.
