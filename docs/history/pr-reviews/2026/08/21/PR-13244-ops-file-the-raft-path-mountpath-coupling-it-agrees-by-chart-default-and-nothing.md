## Description

Found while measuring the OpenBao migration (#13241). **Not a live mismatch** — on `origin/main` the HCL says `path = "/vault/data"` and the chart's default puts the volume there too, so Vault is correct today.

The defect is that they agree **by inheritance rather than by declaration**:

```
:137   storage "raft" { path = "/vault/data" }     # explicit
:140   dataStorage:
         enabled: true
         storageClass: zeta-local-path
         size: 20Gi                                 # <- no mountPath
```

Nothing in the tree compares the two. If they ever diverge, Vault starts, passes its probes, and reports **Ready** — while writing raft state somewhere that is not the mounted volume, losing the store on every restart. A crash would be honest; this is a healthy-looking pod silently discarding the thing it exists to keep.

## Two ways it diverges without anyone touching the HCL

1. **A chart-default change** — the coupling is inherited, so a bump can move one side while the other stays.
2. **The OpenBao migration**, which is live work: openbao-helm defaults to `/openbao/data`. Repointing the Application without editing the HCL produces exactly this state — and the coherence audit, run against an OpenBao fixture, **did not flag it**.

## Deliberately filed rather than fixed

The obvious rule — compare the HCL path to the chart's data `mountPath` — needs to know the chart's **default** when `mountPath` is absent, which is the very assumption being questioned. Hardcoding `/vault/data` as the vault-helm default would swap an unstated assumption for an unverified one.

Two candidate shapes are recorded in the item, neither built, each with the precondition it needs first: require `mountPath` to be stated explicitly whenever a raft `path` is set (cheap, but needs confirming `mountPath` is a real vault-helm value), or compare against rendered chart output (needs `helm` in the checking lane).
