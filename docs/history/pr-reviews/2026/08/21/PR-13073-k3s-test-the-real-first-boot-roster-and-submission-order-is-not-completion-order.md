## Description

The roster had **no test** — all five nixosTests `mkForce` it away, three to an empty set. This adds
two, plus a corrected comment.

## It corrects my own correction

I said the roster was ten, not eleven. **Both counts were wrong, differently.** `k3s-server.nix`
declares **ten**; `local-storage.nix` **merges an eleventh** via its own `services.k3s.manifests`
block — `local-path-provisioner`, which no prior analysis folded in. **The effective roster is 11**,
and the new test asserts the merge so it cannot silently regress.

## The load-bearing finding — it kills the fix I was leaning toward

> **Submission order is not completion order.**

Renaming with numeric prefixes is **free statically** (`validate-bootstrap.ts` keys on the resolved
source path, so a rename passes 52/52) — **but it would not fix anything.** The deploy controller
submits all eleven files **within seconds**; helm-controller Jobs take **minutes**. A renamed
`zz-root-application` is still submitted long before the ArgoCD chart creates the `Application` CRD.

**Ordering the filenames orders the *submission*. The dependency is on *completion*.**

The mechanism was confirmed against the pinned nixpkgs rather than assumed. And because `target` is
`mkDefault`, an entry *could* override its filename — **so the test refuses that case rather than
guessing.**

## The eval test is the half that runs everywhere

**14 properties over 11 manifests**, no VM, no KVM, part of `nix flake check --no-build`. It pins the
exact submission order, asserts the `local-storage` merge, and asserts **`argocd-install` is second** —
so the comment **cannot drift back to "ArgoCD comes LAST" without going red.**

### A mutation survived and was fixed

Perturbing the storage class to `zeta-local-path-MUTANT` **left the suite green**, because that leg was
a **substring** match and therefore **vacuous**. Changed to an exact-line match; it now goes red. Two
other mutations bite as expected.

## The VM test is designed-but-unrun, and honestly scoped

It cannot run here — aarch64 darwin, and it needs x86_64-linux KVM, sandbox off, ~10 GB RAM, 45–70 min.
**Wired as manual/nightly, not per-PR**, because an hour of runner time per PR **does not earn its slot
when the eval check covers the drift half for free.**

Coverage is stated per manifest rather than implied: **11 of 11 applied**, **4 asserted to a running
workload**, **6 asserted only as submitted/accepted** because their pods have prerequisites a
single-node VM does not model — **and a flaky gate is worse than an absent one.**

## Does `root-application` apply or stick?

**Unanswerable offline, and the agent refused to guess** — no k3s source is mirrored locally to read the
deploy controller's retry behaviour.

Instead it made the bad outcome **a finding rather than a timeout** — three named verdicts,
discriminated by the CRD:

- **Self-heals** → pass.
- **CRD never appeared** → its own error saying **this run says nothing about the retry question**, so it
  can never be misread as evidence.
- **CRD exists, object does not** → the real one: the deploy controller does not retry, the app-of-apps
  root never lands, and a fresh cluster halts at the bootstrap charts **with every pod healthy and
  nothing reconciling.**
