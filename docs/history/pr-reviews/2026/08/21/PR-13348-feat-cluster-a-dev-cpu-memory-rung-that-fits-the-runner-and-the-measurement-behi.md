## Description

## The ask

Aaron 2026-08-20:

> "sounds like we can set some resource limits for our dev runners and different defaults for physical hardware, we should try to make things small enough to fit for disk and ram on the runners."

## 1. The measurement, first — because it decides whether the ask is possible

Every one of the 45 Applications was `helm pull`ed at its **pinned `targetRevision`** and rendered
with **that Application's own `valuesObject`**; `resources.requests` summed over every rendered
container times its workload's replica count. Not estimated, not read out of a values file in
isolation — two of the numbers are only visible after rendering (mimir's zone-aware replication
turns one `ingester.resources` key into three StatefulSets; minio's post-install Job draws from
`makeBucketJob`/`makeUserJob`, not from the `resources` block we set).

| cohort | apps | CPU requests | memory requests |
|---|---|---|---|
| asserted `Synced+Healthy` by `--scope included` | 19 | **1221m** | **3.91 GiB** |
| applied by the dev/CI app-of-apps root | 33 | **4131m** | **11.03 GiB** |
| every Application in the tree | 45 | **9756m** | **22.85 GiB** |

**Can all 45 fit 4 vCPU / 16 GB? No — and CPU runs out first**, 9756m against 4000m. That is worth
saying because the question was asked about RAM.

**And the lane is green for a reason that is not "it fits."** The 19 it *asserts* fit with room. The
33 it *applies* do not (4131m against 4000m, before kind's own control plane). The only reason that
has never bitten is that **14 of those 33 hang `Missing` forever** on a `longhorn` StorageClass the
dev catalog glob-excludes, so they never schedule a pod. A reprieve, not a fit.

**The sum is a floor, not the requirement.** 28 of the 45 render pods that request *nothing*
(`resources: {}` chart defaults). Those are BestEffort — the scheduler admits any number of them and
no arithmetic on requests will ever see one. The rung below reserves 4.3 GiB of unreserved headroom
for exactly that, and says so.

## 2. What landed

Same file, same tool as the storage ladder — `full-ai-cluster/k8s/storage-profiles.json` and
`src/Core.TypeScript/cluster/storage-profiles.ts` — because it is the same problem with two more
axes on it.

```
bun src/Core.TypeScript/cluster/storage-profiles.ts --resource-list
bun src/Core.TypeScript/cluster/storage-profiles.ts --resource-profile dev --budget
bun src/Core.TypeScript/cluster/storage-profiles.ts --resource-profile dev --apply
bun src/Core.TypeScript/cluster/storage-profiles.ts --measure-runner
```

**Two rungs, and only one of them cuts:**

- **`metal`** — byte-for-byte what the manifests render today. `verifyResourceProfileApplied` is
  clean against it on `main`, so **nothing here shrinks the hardware deployment.** That is the split
  Aaron asked for, and it is the same construction `large` already uses one ladder up.
- **`dev`** — **1806m / 5.94 GiB** across the applied 33, inside a **2500m / 9216Mi** budget.

| rung | dev lane (33) | all (45) |
|---|---|---|
| `dev` | **1806m / 5.94 GiB** — fits | 7431m / 17.75 GiB — does not |
| `metal` | 4131m / 11.03 GiB — does not | 9756m / 22.85 GiB — does not |

`dev` was **verified end to end, not asserted**: applying it and re-rendering every governed chart
gives exactly the catalogue's numbers component by component (mimir 635m/2272Mi, hindsight
400m/896Mi, seaweedfs 200m/512Mi, gatekeeper 100m/512Mi, minio 50m/384Mi, redis 150m/192Mi, nfd
100m/192Mi, arc-controller 50m/64Mi). The manifests were then restored **byte-identically**; `main`
stays on `metal`.

All 45 at `dev` is still over. gitlab and temporal are 5625m / 11.6 GiB between them and **neither is
applied to a dev cluster** — the `dev` rung does not price apps the dev lane never runs.

### The envelope, and what it reserves

| | |
|---|---|
| capacity | 4000m / 15360Mi / 14 GiB free disk |
| reserved | 1500m / 6144Mi / 4 GiB |
| **budget for application requests** | **2500m / 9216Mi** |

1. **~950m / ~290Mi — kind's control plane and kube-system**, which the scheduler subtracts before
   any Application is placed (kubeadm static-pod defaults, coredns, kindnet). argo-cd 7.7.10 adds
   nothing — rendered, every component's `resources` is unset.
2. **~550m / ~1536Mi ESTIMATED — outside the kind node's cgroup**: host OS, runner agent,
   dockerd/containerd, the bun harness. kind sets no memory limit on its node container, so the
   kubelet reports the *host's* capacity as the node's; this slice is real and invisible to the
   scheduler. Labelled ESTIMATED because it is.
3. **~4300Mi unreserved headroom** for the 28 BestEffort Applications.

**The capacity half has its own falsifier.** 4 vCPU / 16 GB is GitHub's published spec, not our
measurement, so `--measure-runner` reads `/proc` on the runner and exits 1 when the real machine is
smaller. It **refuses** rather than passes where `/proc` is absent.

### Every cut is priced

A request cut below the working set does not make an app smaller — without a limit it moves the
failure from a **Pending pod** (loud, scheduler-attributed) to the **kernel OOM killer** (quiet,
arbitrary). So `loadResourceCatalogue` refuses a row that cuts without stating what the cut costs,
and a test requires every row reserving >=256Mi on metal to name the failure mode. Sharpest:

- **redis master/replica 128Mi → 64Mi** — a hard ceiling on the dataset, not a throttle. Least margin.
- **hindsight postgresql 256Mi → 128Mi** — an OOMKilled database is a crash, not a slowdown.
- **gatekeeper controller-manager 512Mi → 256Mi** — it is *in the admission path*.
- **mimir ruler 128Mi → 96Mi** — a dead alerting path looks exactly like a quiet system.

All dev-only; `metal` keeps the chart default in each case.

## 3. The disk answer, stated honestly

**It is container images, not PVCs, and nothing in this repo measured it before.** Registry manifests
summed, then the compressed:uncompressed ratio **measured** by streaming and gunzipping four real
images from this tree (argocd x2.69, loki x3.21, kube-state-metrics x3.39, cockroach x2.49 —
aggregate **x2.67**; containerd stores layers uncompressed).

| cohort | distinct images | compressed | on disk at x2.67 | vs ~14 GB free |
|---|---|---|---|---|
| asserted 19 | 39 | 1.61 GB | ~4.3 GB | fits |
| applied 33 | 73 | 11.77 GB | **~31 GB** | **2.2x over** |
| all 45 | 120 | 28.77 GB | **~77 GB** | **5.5x over** |

`vllm/vllm-openai:latest` is **9.1 GB compressed** (glob-excluded) and
`ghcr.io/vectorize-io/hindsight-api:0.1.1` is **8.8 GB compressed** and **applied** — the only reason
it does not land on a 14 GB disk is the same longhorn reprieve. **No rung here changes that**; a
CPU/memory ladder cannot shrink an image. It is named, not solved, because solving it means editing
`argocd-health-test.ts`'s exclusion logic, which other agents are in today.

**And the PVC trap.** The storage ladder's 1599 GiB does not apply on a runner: the dev lane's
StorageClass is `local-path`, a hostPath directory with **no quota**, so a PVC request reserves
nothing and consumes nothing until something writes. Said once plainly:

| number | what it is |
|---|---|
| CPU/memory requests | **scheduling reservations.** Bound admission. Not measurements of use. |
| Longhorn PVC GiB | **scheduling reservations**, on metal. On kind: not bytes at all. |
| image footprint | **actual bytes on disk**, the moment a pod is scheduled. |

Honest limit: **11 of 120 images could not be sized** (4 private ghcr 401s, 5 bitnami tags withdrawn
from Docker Hub, 1 rate-limited, 1 404), so all three totals are **lower bounds**.

## 4. Two charts could not be measured, and that is a finding

`forgejo@9.0.6` (its pinned repoURL 404s; 9.0.6 is in neither Forgejo package registry nor OCI) and
`ziti-controller@1.4.5` (already recorded in the companion doc: upstream never published it). Both
are **applied** by the dev root — so **ArgoCD cannot render them from those pins either**. Carried as
`acknowledgedUnmeasuredRequests` keyed `forgejo@9.0.6` / `oz@1.4.5`; the pin is in the key so a
chart bump invalidates the acknowledgement instead of inheriting it, the same construction
`acknowledgedCapacityShortfall` uses. Also noted: `sealed-secrets`'s pinned repoURL now 404s too
(the chart still resolves from its release tarball).

## 6. What this does NOT do

- **Does not shrink metal.** `metal` is the status quo; the ledger is untouched.
- **Does not apply `dev` anywhere.** `main` carries `metal`. The kind lane syncs ArgoCD against a git
  ref, so it renders what is committed — applying `dev` in CI needs a commit or an ArgoCD parameter
  override, and that wiring does not exist. The budget check proves the **ladder** fits the runner; it
  does not prove the **cluster** does, and those are different claims.
- **Does not fix the image footprint**, which is the harder constraint by 2.2x on the applied set.
- **Does not set limits, only requests.** A request without a limit bounds admission and nothing else.
- **Does not touch `argocd-health-test.ts`.**
