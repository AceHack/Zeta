## The suspicion held, and the numbers moved

Verified on `main` @ `94945a6`. The auditor printed:

```
$ bun src/Core.TypeScript/cluster/single-node-readiness.ts
single-node readiness: 129 manifests, nodeCount=1

Derived per-node storage requirement (sum of declared PVC capacity x replicas):
  longhorn             1409 GiB  (budget 2048 GiB)
  zeta-local-path       103 GiB  (unbudgeted)
no blockers.
$ echo $?
0
```

Two corrections to the record before anything else. The design doc's §5.1
figures (1499 GiB longhorn / 73 GiB local-path) are one day stale — vault
dropping to `replicas=1` in #13062 moved them to **1409 / 103**. The defect
itself is exactly as described.

**What the gate compared against:** `ledger.nodeDiskGib * ledger.nodeCount`
= `2048 * 1` — and nothing else. The ledger's own comment on that number reads
*"It is NOT a measurement of the box Aaron has today"*, under a file-level
*"STATUS: awaiting maintainer sign-off on nodeDiskGib"*. So the check was green
against an unsigned aspiration: it could not fail for the reason it exists.

**The arithmetic** (every number re-checkable by running the auditor):

| | |
|---|---|
| declared `longhorn` PVCs, Σ capacity × replicas | **1409 GiB** |
| measured `node-ad1efd` `/dev/nvme0n1 931.5G` | 931.5 GiB |
| measured `node-ad1efd` `/dev/sda 115.5G` | 115.5 GiB |
| **every block device on that node** | **1047.0 GiB** |
| shortfall | **362 GiB — 1.35×** |
| against the NVMe alone | 1.51× |

## What was missing was a comparator, not a number

There is real provenance already in the repo and the gate was not using it.
Four `ClusterNode` registrations sit under
`maintainers/*/cluster-nodes/*/node.yaml`, written by actual metal boots:
`zeta-install.sh:1939` composes `spec.hardware.storage` from
`lsblk -ndo NAME,SIZE,TYPE -e7` **on the node**, and a self-registration PR
commits it. Those are measured bytes off real hardware.

New check **`capacity-provenance`**:

- sums every whole block device on the **smallest** measured node and compares
  the declared total against it;
- **REFUSES** (`exit 1`, message `capacity UNVERIFIED`) when no registration
  carries a measurable `spec.hardware.storage` — it does **not** fall back to
  `nodeDiskGib`. A gate that cannot know must not claim to know;
- treats an unmeasured registration as `null`, never `0`. Two of the four
  nodes (maximdolphin's `node-f82aa6`, `node-5b2dfa`) record no storage at all
  — the post-boot self-register path never captured it. They are printed as
  unmeasured rather than counted as zero disks.

**The inference is one-way on purpose.** The bound counts `/dev/sda`, which
§5.7 of the design doc suspects is the USB stick, and reserves nothing for the
ESP, root filesystem, swap, or Longhorn's own `storageReserved`. It is
deliberately over-generous, so `declared > bound` is *proven* oversubscription
and no reading of the hardware rescues it — while `declared <= bound` proves
nothing. It convicts, never acquits.

`nodeDiskGib` is kept and still checked as the procurement target; it is now
labelled `ASPIRATIONAL` in the output, which is what it always was.

## No declared capacity number was changed

The un-acknowledged run is the honest one, and it is red:

```
[blocker] capacity-provenance: StorageClass "longhorn" declares 1409 GiB, which
exceeds EVERY block device on the smallest measured node (node-ad1efd: 1047 GiB
across 2 device(s) x 1 node(s)) by 362 GiB — 1.35x. ...
    measured evidence: maintainers/Addisons820/cluster-nodes/node-ad1efd/node.yaml
      /dev/nvme0n1 931.5G
      /dev/sda 115.5G
    unmeasured node (not counted): .../node-5b2dfa/node.yaml
    unmeasured node (not counted): .../node-f82aa6/node.yaml
    acknowledge with: longhorn=1409GiB>>1047GiB@node-ad1efd
$ echo $?
1
```

That shortfall is then recorded as **pinned debt** in the ledger, following the
file's existing `acknowledgedRootAppDuplicates` idiom, with two properties that
keep it from becoming a fresh vacuity:

1. **The arithmetic is in the key.** `longhorn=1409GiB>>1047GiB@node-ad1efd`.
   A bigger PVC re-reds it; a smaller node registering re-reds it; buying the
   2 TB drive and re-registering re-reds it — which is exactly when someone
   should be deleting the entry. Both stale-side variants are pinned by tests.
2. **It suppresses the exit code, never the print.** The green path now says:

```
Measured node capacity (smallest registered node, every block device counted):
  node-ad1efd          1047 GiB  (maintainers/Addisons820/cluster-nodes/node-ad1efd/node.yaml)

ACKNOWLEDGED capacity shortfalls (debt, not clearance — exit code suppressed, arithmetic is not):
  longhorn=1409GiB>>1047GiB@node-ad1efd
```

The **UNVERIFIED** case is deliberately *not* acknowledgeable, and a test pins
that: a shortfall you can see is debt; an absent comparator is an absent check,
and an exemption for it would be the vacuity this file exists to catch.

The decision itself — buy 2 TB, trim the catalogue to ~900 GiB, or split by node
role — is §5.1 and stays Aaron's. Deleting the ledger entry is the fix, and
doing so makes the gate exit 1 immediately (mutation M9 below).

## Also: the gate could be bypassed by a path filter

`maintainers/*/cluster-nodes/**` is added to both `pull_request` and `push`
path filters in `k8s-argocd-health-test.yml`. Without it, a node registering
with a smaller disk would move the comparator on `main` **without the gate that
would have caught it ever running** — a check that did not run looking like one
that passed.
