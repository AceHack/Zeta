## Description

## What this is

`§5.2` of `docs/design/2026-08-21-the-zeta-bootstrap-usb-full-design-document.md` — *"the credential
binding: what is the stable key?"* — has blocked **R8 for 74 days**. This PR does not answer it. It makes
it **cheap to answer**: a brief Aaron can read in a few minutes and resolve with one word.

**No binding is implemented. The seam stays a seam.**

## Lead finding: the model and the shipped path disagree

`credential-binding-model.ts:157-159` asserts that binding to `usbISerial` **refuses** on a stick swap —
*"iSerial is physical-stick-bound"* — and `credential-binding-model.test.ts:68` pins it:

```ts
expect(expectedBindingScenarioOutcome("usbISerial", "stick_swap").decrypts).toBe(false);
```

The shipped restore path **never probes the device.** It reads a recorded copy of the serial from
`/etc/zeta/usb-iserial` on the installed root, and admits it in its own log line:

- `full-ai-cluster/nixos/modules/zeta-creds-restore.nix:230` — `BIND_VALUE="$(tr -d '\r\n' < ${cfg.usbISerialPath})"`
- `full-ai-cluster/nixos/modules/zeta-creds-restore.nix:236` — `"binding-factor usbISerial (recorded; not a live probe)"`
- `src/Core.TypeScript/installer/installer-binding-cli.ts:228-229` — *"Re-probe is install-time; restore uses the recorded serial … (stick need not still be plugged in)."*

**Consequence:** on the shipped path `usbISerial` binds to neither the stick nor the node — it is a
plaintext string stored beside the blob on the same disk, adding no key entropy against anyone holding
that disk. The one property that would make iSerial the better option — *only that stick opens it* — is
exactly the property not built. The design doc's §5.2 table inherits the model's claim, so it is wrong
about the shipped code too.

The test is not false; it tests the model, and the model is internally consistent. It is a **falsifier
aimed at the wrong layer**.

## Two more defects, same neighbourhood

**The `iSerial ⊕ UEFI keyfile` option — annotated in §5.2 as *"what your 2026-06-09 phrasing literally
pointed at"* — is refused by construction at three layers**, and asking for both silently yields the
**ephemeral FAT UUID**, the one factor the doc's own root-cause analysis calls broken:
`installer-binding-cli.ts:82-84` · `zeta-creds-picker.ts:112` · `zeta-install.sh:2504-2508`
(*"both set; staying --usb-uuid"*). The model cannot express a combination either —
`CredentialBindingFactorKind` is a single-member union. R8's verbatim ask is an **AND**; every layer
implements **XOR** with an inverted fallback.

**`applyBindingScenario`'s `stick_swap` comment contradicts its own code** —
`credential-binding-model.ts:101-103` says *"no uefi keyfile unless explicitly carried"*, `:107` carries it
unconditionally. One-line fix, noted so it is not lost.

## What the brief contains

1. Both options as `CredentialBindingFactorKind` values — no invented vocabulary.
2. Every scenario cell **derived from `expectedBindingScenarioOutcome` with a line cite**, and a *separate*
   table for **TPM cleared** and **node re-pave**, which are **not in `CredentialBindingScenario`** and are
   fenced off as reasoning beyond the model.
3. **Recovery for each** — the section that decides it. Every credential in `DEFAULT_MANIFEST` is
   re-obtainable by re-authenticating or explicitly declared regenerable
   (`zeta-creds-manifest.ts:48-115`), so **the blob is a cache, not a vault**: a wrong binding costs one
   login, never a loss. That converts the criterion from *"which is safest"* to *"unopenable how often,
   across how many nodes."*
4. **Cost from today's code.** The surprise: a five-state TPM probe (`tpm2-linux-probe.ts:338`, built so a
   check that could not run never reads as "no TPM") and a working injected seal backend
   (`frost-share-adapter.ts:1311-1360`) already exist. And *"flip the default to `--usb-iserial`"* looks
   like one line at `zeta-install.sh:2604` — that is the trap, because of the lead finding.
5. A **recommendation, marked as one**, with what would change my mind.
6. **One question.**

## The recommendation and the question

**Recommend `tpmSeal`** — no PCR policy in phase one (it turns every firmware update into a
credential-loss event and buys nothing against the disk-holder threat), and **never fall back** on a failed
unseal, matching the abort-not-fallback discipline already at `zeta-creds-restore.nix:227`/`:239`.
Reasoning: A's failure event is *"this node is gone"*; B's is *"a USB stick is gone"* — far likelier, and
its blast radius grows with the fleet. Neither the secp256k1 requirement nor the FIPS contradiction in
§5.6 touches this path: sealing uses a keyedhash object, not a curve.

> **Should the credentials belong to the node, or to the stick?**
>
> **`node`** → bind `tpmSeal`; a re-paved machine remembers itself; a lost stick costs nothing.
> **`stick`** → bind `usbISerial`; the stick carries credentials between machines; a lost stick costs
> every node it touched.

One word unblocks R8.
