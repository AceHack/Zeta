## Description

**ArgoCD could not fetch this chart at all.** `bitnami-labs.github.io/sealed-secrets` returns HTTP 404 — the chart moved to the `bitnami` org. Verified both ends: the old `index.yaml` 404s, the new one serves the chart and still carries the pinned 2.16.2.

So this was never a version problem, which is why the URL fix and the bump are separable — and **the URL fix alone is not optional.**

Taken to **2.19.3** (2026-08-20, appVersion 0.39.1) from 2.16.2 (Nov 2024, appVersion 0.27.2), per *"we might as well be on latest now"*. Same chart major; the app moves 0.27 → 0.39.

## Stated, not verified — and written into the manifest, not just here

sealed-secrets keeps its controller keypair in a Secret that survives upgrades, so existing SealedSecrets *should* still decrypt. **Nothing here proves that.** No cluster ran this upgrade, and the only real check is live: after rollout, an existing SealedSecret must still reconcile into its Secret. If it does not, the sealing key was lost — the one failure that matters for this chart. That check is named in the file so whoever rolls it doesn't have to reconstruct the risk.

## Sequencing with #13333 — deliberate, not an oversight

PR #13333 adds `audit-chart-target-revisions.ts` with an acknowledgement register that is **drift-checked both ways**: fixing a pin makes its acknowledgement go stale, and stale acknowledgements are reported as findings. That is the design working, but it means these two PRs are coupled:

- If **#13333 merges first**, this PR must also drop the `sealed-secrets` entry from `ACKNOWLEDGED_UNPUBLISHED`.
- If **this merges first**, #13333's entry is born stale and must be dropped there.

This branch is based on a commit that predates #13333, so the register does not exist here to edit. Whichever lands second needs the one-line removal — flagged so it is a known follow-up rather than a surprise red.
