## Description

## What this is

A boot-time **refusal** for the Longhorn node prerequisites, so a node whose storage substrate is not actually there says so on the console during bring-up instead of handing the operator a Pending pod hours later.

Aaron is booting the first metal node. Everything the cluster requires of a node's storage is currently a *declaration* — `services.openiscsi.enable`, `boot.kernelModules`, tmpfiles symlinks, disko mountpoints — and **nothing on a running node ever looked at whether the declaration came true.**

## The two gaps, measured on `origin/main`

```
$ git grep -n "systemctl is-active" -- full-ai-cluster/
(nothing)
$ git grep -nE "findmnt|mountpoint|ConditionPathIsMountPoint|RequiresMountsFor" -- full-ai-cluster/nixos
(no check — only disko `mountpoint =` declarations and one doc comment)
```

**Gap A — `iscsid` is never verified ACTIVE.** The single lane covering it asserted `systemctl cat iscsid.service`, which proves a unit *file* exists and passes on a dead daemon, and printed `systemctl is-enabled ... || true`, which is diagnostic output and cannot fail. Same shape as the `command -v iscsiadm` assertion that stayed green while longhorn-manager crash-looped **16495 times over 62 days** on node-5b2dfa with 10 PVCs Pending. Longhorn attaches every RWO volume over iSCSI, so `iscsid` down means the `longhorn` StorageClass is never created — and `k8s/applications/` pins ~1.4 TiB of PVCs to that class, including `vault`, `cockroachdb`, `mimir`, `nats`, `weaviate`, and the whole `kube-prometheus-stack`.

**Gap B — a declared Longhorn data disk that is not mounted is invisible.** `disko-shapes/longhorn-node.nix:71` and `boot-disk-partitions.nix` mount every Longhorn partition with `mountOptions = [ "noatime" "nofail" ]`, so a missing or failed device boots silently — by design, so a dead data disk does not brick a node. Then `longhorn-prereqs.nix:77` and `longhorn-disks.nix` create the same paths with tmpfiles `d`. The path exists, has the right mode, and is a plain directory on the **root filesystem**. Longhorn registers it as a disk, sizes it from root's free space, and places replicas there. That is strictly worse than a Pending pod, because a Pending pod is visible.

Five checks, each naming its remedy: declared Longhorn filesystems really mounted · `/var/lib/longhorn` exists · `iscsid` active · `iscsi_tcp` loaded · the five `/usr/local/bin` FHS shims `longhorn-manager` nsenters to are executable.

What the operator sees:

```
[FAILED] Failed to start Longhorn node preflight (storage devices + attach prerequisites).
zeta-longhorn-preflight: REFUSED -- /var/lib/longhorn-disk2 is declared as a filesystem in
  this host NixOS config but is NOT mounted. Longhorn would place replicas on the ROOT
  filesystem there and report the wrong capacity.
zeta-longhorn-preflight:   remedy: the mount carries the 'nofail' option, so a missing or
  failed device boots silently. Run: lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINT ; ...
ZETA_LONGHORN_PREFLIGHT_FAILED failures=1 mounts_checked=2
```

on the physical console (the way `k3s-join-observer.nix` puts its markers on serial), and in `systemctl --failed` and the journal thereafter.

## Severity: it does NOT block k3s, deliberately

`RequiredBy = [ "k3s.service" ]` is the fail-closed shape and is one line away in the module. It is not what ships, and the reason is written into the file rather than left to be rediscovered: **this check has never run on physical hardware.** An unrun gate whose false positive costs the operator the entire cluster during the one bring-up where they are least able to debug it is the same 2am failure, inverted. `before = [ "k3s.service" ]` *is* set, so the verdict is on the console before kubelet advertises this node as a place to put storage. The evidence that licenses the upgrade is one clean metal boot printing `ZETA_LONGHORN_PREFLIGHT_OK`.

**DESIGNED BUT UNRUN:** no VM test and no hardware boot. The QEMU lane is `x86_64-linux` and cannot run on this machine. Two things settle it: `k3s-control-plane-platform-fixes` in CI decides whether the preflight goes green on a real boot (a red result there is a true finding about `iscsid`/`iscsi_tcp` in the VM, not noise), and on metal the console marker `ZETA_LONGHORN_PREFLIGHT_OK` decides it. The mount check itself is exercised non-vacuously only where a host declares Longhorn filesystems — `hosts/control-plane` declares none today, which the eval test pins as a stated property rather than leaving as an unnoticed pass.

## Scope

Touches none of PR #12175's files (`longhorn-disks.nix`, `common.nix`, `longhorn/Application.yaml`, `longhorn-volume-binds.nix`). The preflight derives from `fileSystems`, not from `zeta.longhorn.dataDisks`, so it composes with #12175 either way and gains teeth from it: once `longhorn-volume-binds.nix` declares two real virtual disks, the mount check has a non-vacuous CI instance.

Capacity is out of scope and owned elsewhere (`k8s/single-node-budget.json` + `single-node-readiness.ts`). This asks whether the device is *there*, not whether it is *big enough*.
