## Description

Confirmed on `origin/main`, not inferred.

`arc-runner-set/Application.yaml` sources a **remote** Helm chart:

```
:33   repoURL: ghcr.io/actions/actions-runner-controller-charts
:34   chart: gha-runner-scale-set
:51   minRunners: 1
:72   claimName: arc-model-cache
```

so it cannot apply its own sibling `arc-runner-set/model-cache-pvc.yaml:8`. Nothing else applies it either — the root app-of-apps includes only `{*/Application.yaml,Application.yaml}`, which does not match a bare `model-cache-pvc.yaml`.

Meanwhile `minRunners: 1` keeps a warm runner whose pod spec mounts `arc-model-cache`. **A pod mounting a PVC that does not exist does not start.** This is the current state whenever the runner set syncs — live, not latent. The file's own header comment asserts it *is* applied, which is the same comment-asserts-a-guarantee shape this repo keeps turning up.

## Second-order, and why it is worth filing rather than mentioning

The 100Gi RWX request is counted in the **declared** capacity total while occupying nothing. A future capacity change could "reclaim" it and believe it found headroom that was never used.

## Filed rather than fixed

The three available repairs differ in what they *mean*, not just how they are written:

1. give the PVC its own `Application.yaml` — the root glob does match that;
2. drop the mount and the PVC together;
3. move the volume into the Helm release via chart values.

That is a product call about whether the runner should have a model cache at all, and (1) vs (3) changes who owns the volume's lifecycle.
