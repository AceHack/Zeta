## Description

Answers two questions from the maintainer: **"cdi, kubevirt can we test these?"** and **"are there other charts we need to include?"**

## Part 1 — Yes. Both. Confirmed against upstream, not assumed.

### What was measured first

`cdi` and `kubevirt` are in the `--scope included` roster, report `syncStatus: OutOfSync` / `healthStatus: Missing`, and still count as `ok: true`. That is **not** a bug in `manual-sync-policy.ts` — it is that module working. Both declare `zeta.io/sync-policy: manual` with a mandatory reason, and `Missing` is the honest steady state for an app nothing syncs. The weaker contract it buys is real: the Application must exist, ArgoCD must have **completed a comparison** (`OutOfSync`, never `Unknown`), and health must not be Degraded — so a typo in `directory.include` or a malformed vendored byte still convicts.

But that module states its own limit out loud, and this PR exists because of that sentence:

> "this can no longer catch anything that only appears once the manifests are APPLIED — an API-server rejection, a denying admission webhook, an image that will not pull, a CR the operator never reconciles"

**Nothing in the repo has ever executed those two manifests.** They are the only two Applications in the catalogue in that position.

### (a) Why they are manual-sync — the reason is valid, and it is production-scoped

From the annotations themselves: both adopt operators **installed by hand on `node-5b2dfa`**, which carries **three running production Windows guests**; an ArgoCD auto-sync or selfHeal there could roll `virt-operator` into `virt-handler` underneath live VMs.

That reason is true and is **kept**. What it is not is a claim about the *bytes*. An ephemeral kind cluster on a CI runner has no guests to disturb and is deleted at the end of the job — so the constraint does not apply there, and the bytes can be proved where it does not apply. Both `zeta.io/sync-policy-reason` annotations now say this explicitly, so nobody re-derives "manual-sync" as "untestable".

### (b) KubeVirt on a GitHub-hosted runner — yes, via software emulation

- GitHub, [about GitHub-hosted runners](https://docs.github.com/en/actions/using-github-hosted-runners/using-github-hosted-runners/about-github-hosted-runners): *"While nested virtualization is technically possible while using runners, it is not officially supported. Any use of nested VMs is experimental and done at your own risk."* So `/dev/kvm` is **not** something to depend on — confirmed, not assumed.
- KubeVirt, [`docs/software-emulation.md`](https://github.com/kubevirt/kubevirt/blob/main/docs/software-emulation.md): *"If `useEmulation` is enabled, `qemu` will be used for software emulation, in case that hardware emulation via `/dev/kvm` is unavailable."* And with it disabled and the device absent, *"the VirtualMachine will fail to start and an error will be reported."* Also: *"Hardware emulation is always attempted first, regardless of the value of the `useEmulation`"* — so the flag is a fallback, never a downgrade, and the proof still holds on a runner that does happen to have `/dev/kvm`.
- Our `kubevirt-cr.yaml` ships `developerConfiguration: {}` — `useEmulation` unset. Correct for metal, **wrong for CI**, exactly as suspected.
- The recipe here is **upstream's own, not ours**: the KubeVirt org's [`kubevirt.core`](https://github.com/kubevirt/kubevirt.core) runs `.github/workflows/integration.yml` on `runs-on: ubuntu-latest` with `helm/kind-action@v1.14.0`, and its `hack/e2e-setup.sh` does:

```bash
if ! is_nested_virt_enabled; then
  kubectl patch kubevirt kubevirt --namespace kubevirt --type=merge \
    --patch '{"spec":{"configuration":{"developerConfiguration":{"useEmulation":true}}}}'
fi
kubectl wait --for=condition=Available kubevirt kubevirt --namespace=kubevirt --timeout=5m
```

A KubeVirt-org repository, running KubeVirt on kind, on a GitHub-hosted runner, waiting for it to go Available.

### (c) CDI independently of KubeVirt — yes

CDI is a separate operator (Deployment + CRDs that populate PVCs); nothing in its reconcile path touches `/dev/kvm`. It is proved on its own and **reported on its own** — a KubeVirt failure cannot erase the CDI verdict, which is half the question.

### Shipped

- **`src/Core.TypeScript/cluster/kubevirt-cdi-emulation-test.ts`** — applies each Application's own `spec.source.directory.include` files (**derived from the manifest, never hand-copied**; a glob it cannot expand is **REFUSED**, not silently narrowed), operator before CR, then the CI-only `useEmulation` merge patch **on top of the verbatim CR** — never instead of it, because applying our real bytes is most of the point. Asserts `CDI` reaches phase `Deployed` and `KubeVirt` reaches `condition=Available`.
- **`live-kind-virt` job** in `k8s-argocd-health-test.yml`. **Not `continue-on-error`** — an advisory job here would re-create in a new place the exact misreport this removes. It is **not** in the `gate (required)` floor, so it reports without blocking; promoting it is a maintainer policy call, not a cleanup. It also *records* `/dev/kvm` presence and `kvm_*/parameters/nested` rather than asserting them, so a log reader knows which path was taken.
- **`ClusterControlPlane`** gains `mergePatch` and `waitForResource`. The wait returns a boolean instead of exiting — the two phases must stay independently reportable.
- Both `zeta.io/sync-policy-reason` annotations amended to scope the constraint to the production cluster and name the lane that proves the bytes; `manual-sync-policy.ts`'s admitted gap now points at where it is covered.

### What this does NOT prove

No `VirtualMachineInstance` is booted. It proves the operators install from our bytes and reconcile their CRs to a ready state. Booting a guest under TCG emulation is a much slower, separately-earned claim, and pretending otherwise would be the vacuity class.
