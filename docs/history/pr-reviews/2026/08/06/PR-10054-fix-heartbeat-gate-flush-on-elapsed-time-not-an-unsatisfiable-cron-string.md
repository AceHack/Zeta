## Description

## The break

`flush-to-main` was gated on:

```yaml
endsWith(github.event.schedule, '0 * * * *')
```

This workflow declares exactly one schedule — `*/15 * * * *` — so that predicate can never be true. The flush has therefore never run on schedule, only by manual dispatch. The last one landed **2026-08-01T12:07**.

Between then and 2026-08-05 all three agents (`alexa`, `otto`, `soraya`) kept ticking normally on their `heartbeat/<agent>` branches — their tips were minutes old when this was diagnosed — but their events never reached `main`, and so never reached Pages. `data/tick-latest.json` read `ticks_24h: 0, agents_active: 0` for four days. The dashboard was honestly reporting an empty ledger, not a dead society.

Because each tick resets its branch from `main`, four days of unflushed ticks were discarded rather than accumulating.

## The fix

The hourly cadence is now measured against the last flush that actually **landed** on `main`, rather than against the cron string that was supposed to produce it. The job-level `if:` admits any scheduled run; the `check` step holds unless ≥50 minutes have passed since the last `flush(heartbeat): <agent>` commit, with `workflow_dispatch` bypassing the gate.

This is self-correcting under GitHub's scheduled-run delay. On this repo `tick-metrics` runs land 70–105 minutes apart against a 15-minute cron, so a fixed minute-window check (`is it :00?`) would silently drop whole hours; "has an hour passed?" cannot drift — a late run still flushes, it just flushes late.

## Alternative considered

Adding a second `0 * * * *` cron would also have satisfied the original predicate, and is rejected on cost: GitHub raises one run per matching cron expression, so the top of every hour would fire **two** runs, each re-pulling ~5 GB of Ollama models per agent.

## Verification

- Workflow parses under `uniqueKeys` — this caught a duplicate `env:` key introduced mid-edit, since the `check` step already had one.
- The `--grep` gate logic replayed against real repository history resolves all three agents to FLUSH at 103 h since last flush.

## Note for review

Each tick resets its branch from `main`, so a flush captures only the most recent tick's events. Expect roughly one tick per agent per hour in the ledger, not all 96 daily ticks. Changing that is a separate question from this fix.

Scope is one file. No behaviour changes for the `heartbeat` job itself.
