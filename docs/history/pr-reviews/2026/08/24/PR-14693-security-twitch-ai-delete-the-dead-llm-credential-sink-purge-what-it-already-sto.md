## Description

## The finding, and why it is worse than its severity

CodeQL `js/clear-text-storage-of-sensitive-data` fired on
`localStorage.setItem("zeta_llm_api_key", ...)` at `src/apps/twitch-ai/src/main.ts:120`.
The alert is right. What makes it worth more than a storage-location swap is what
I found when I traced where the key actually goes:

**Nothing consumes it.**

| evidence | file |
|---|---|
| INIT logs a warning and drops `apiKey` and `baseUrl` | `src/apps/twitch-ai/src/swarm.worker.ts:81` |
| all three backends built with `apiKey: "dummy"` | `src/Core.TypeScript/swarm/swarm-controller.ts` (3 sites) |
| CHIP-8 path bypasses the LLM entirely; arena runs offline | `swarm-controller.ts:203` |
| `zeta_llm_base_url` likewise has no consumer | only `main.ts` reads its own write |

So the modal collected a real OpenAI key, persisted it in clear text on a static
host, posted it to a worker that discarded it, and reloaded the page. **100% of the
exposure of a stored secret, 0% of the function.** A prior agent reached the same
conclusion in the 2026-08-23 deploy-truth handoff: *"Do not build on that capability.
It is not there. Consider removing or disabling the modal so the UI stops promising it."*

The surrounding handling was careful — the key was never echoed back into the DOM,
clearing was an explicit button, the label named `localStorage` out loud. None of that
helped, because the defect was the **location** and the **existence of the collection**,
not the handling. I left the careful parts alone.

## The options I actually weighed

| option | threat model | verdict |
|---|---|---|
| `localStorage` (status quo) | clear text; readable synchronously by any script on the origin; survives tab close, restart, and the user forgetting they typed it; no expiry, no `HttpOnly` equivalent. One XSS / bad dep / extension with host permissions takes the whole store. | **rejected** |
| `sessionStorage` | same read surface, shorter window. Narrows the blast radius; does not change its shape. | rejected — still clear text for a key that does nothing |
| in-memory only | dies on reload. `main.ts` **reloads on save**, so this needs the reload replaced by a re-INIT message. Real work for a key nothing reads. | rejected as premature |
| same-origin proxy holding the key server-side | the only option that genuinely honours *"credentials saved in our own harness so we can completely control the flow of authentication."* But this app deploys as a **static** page — there is no server. Building one to hold a credential nothing authenticates with is a large lift for negative value. | rejected **for now**; this is the right answer the day a real remote LLM is wired |
| existing in-repo harness | `src/Core.TypeScript/secrets/credential.ts` is the point-of-use pattern, but it is Keychain/`op://`-backed and **node-side**; it has no browser story. `tools/setup/persona-keys/` is likewise not reachable from a page. | not applicable today; named as the direction |
| **don't collect it at all** | no key, no storage, no exposure, no capability lost — because there was no capability. | **chosen** |

## What I did

1. **Removed** the API key field and all four `zeta_llm_api_key` accesses.
2. **Purged** the key already saved in returning visitors' browsers — on every load,
   permanently. This is the part a pure removal misses: deleting the collection code
   would have turned the alert green while leaving every existing viewer's secret
   exactly where it was, orphaned and still readable. The panel tells them it happened
   and that the key should be rotated.
3. **Disclosure is now a readout, not a promise.** The panel enumerates the origin's
   live `zeta*` storage — **names and byte lengths, never values**. A hardcoded "what we
   store" list is a claim that goes stale the moment another module writes a key; a
   readout cannot. That is `prove presence, never value` as a UI pattern, kept even
   though nothing here is a credential any more, because this is what the next browser
   surface will copy.
4. **Base URL stays** (not a credential) and now says plainly that the engine ignores it.
5. `apiKey` is pinned `null` at the only call site. The protocol field stays because
   `swarm.worker.ts` still reads it to emit its warning — see the note on that file below.

## The guard, and its sabotage control

An eslint `no-restricted-syntax` rule refuses writing a credential-named key to
`localStorage`/`sessionStorage` repo-wide. It runs inside the **existing**
`lint (twitch-ai app)` and `lint (TS)` jobs — no new job, no `gate (required)` treaty
amendment.

A rule that never fires is a vacuous check, so it was falsified before shipping:

```
MUST FIRE     zeta_llm_api_key   -> fired (line 4, the exact removed defect)
MUST FIRE     authToken          -> fired
MUST FIRE     apiKey             -> fired
MUST NOT FIRE zeta_llm_base_url  -> silent
MUST NOT FIRE sortKey            -> silent
MUST NOT FIRE zeta_known_sig...  -> silent
```

Its limits are written into the config rather than implied: string-literal key names
only (a key passed as a variable is invisible to it), bare `key` deliberately excluded
as noise, and it says nothing about the **value** — storing a secret under the name
`preferences` passes and is still wrong. It is a tripwire on the cheapest shape, not a
proof.

## Two corrections to the framing I was handed

- **`main.ts` is not the only browser file touching web storage.** `git grep` over
  `origin/main` finds **22 files / 71 call sites** (`demo/identity-dla-site/*`,
  `docs/design/root-site-iris/*`, `genesis/*`, two `ThemeContext.tsx`,
  `swarm-controller.ts`). The precedent argument survives intact — this is the one
  storing a *credential* — but the uniqueness claim does not, and it matters because
  the guard therefore had to be scoped repo-wide rather than to one file.
- `demo/.../PasskeyProposalPanel.tsx:94` stores a WebAuthn **credential ID**. That is a
  public identifier, not a secret, and storing it is correct. Flagging it here so nobody
  "fixes" it later on pattern-match.

## Not in this PR — three alerts that deserve dismissal-with-reason

I reviewed these independently and **agree they are false positives**; I did not touch
`swarm.worker.ts`.

- **`js/remote-property-injection` ×2** — `setManualKey` loops `k = 0..15` and writes
  `manualKeys[k]`, the *loop variable*. The message value participates only in the
  comparison `k === requested`, never as a property name. No write target is
  attacker-controlled. CodeQL sees `message.payload.key` reach a property write and
  cannot follow the loop-variable indirection.
- **`js/missing-origin-check`** — doubly wrong: a dedicated worker only receives from its
  constructing page, *and* the code already checks `e.origin !== ""` plus a
  `KNOWN_MESSAGE_TYPES` shape gate before any handler runs.
