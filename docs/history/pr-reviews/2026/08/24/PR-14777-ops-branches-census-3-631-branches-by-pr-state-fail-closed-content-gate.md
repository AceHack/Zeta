## Summary

Stage 1 of the branch cleanup Aaron asked for: **census only, no bulk deletion.**
3,631 remote branches classified by **PR state from the GitHub API**, with a
content check behind it, and a committed restore manifest.

`git branch --merged` is the wrong instrument here and that is the whole reason
this has stalled before. Every PR lands via **squash merge**, so a branch tip is
never an ancestor of `main`: the probe reports **6 merged / 3,620 unmerged**. That
3,620 is an artifact of the merge strategy, not a backlog of unmerged work. A
cleanup driven off it deletes nothing; the same cleanup with the test inverted
deletes live work.

## A P0 in the gate this inherits

`triage-orphan-branches.ts` computes its safety check with
`git diff main...branch` under an `allowFail` helper that returns `""` on error.
That diff needs a merge base; **on a shallow clone there is none**, the command
exits non-zero, the absent-file list comes back empty, and the branch is
classified **SAFE TO DELETE on the basis of a diff that never ran.**

Reproduced here: the first census run reported `CONTENT_HELD = 0` across all
3,629 branches. That zero was not a finding — it was the signature of a dead gate.

Fixed three ways: the gate **fails closed** (`UNCHECKABLE`, never reaped), `census`
**refuses to run on a shallow clone**, and the report prints a **vacuity control**
so a silent zero can never again imply safety. After unshallowing, 4 branches moved
out of "safe to delete" — including unlanded `otto-windows` telemetry and a
shadow→lior handoff doc.

## Two generators, and neither is forgetfulness

`deleteBranchOnMerge` is **already `true`**.

1. **`heartbeat/*` (1,538).** The "Heartbeat Branch Protection" ruleset carries a
   `deletion` rule with **zero bypass actors**, so auto-delete-on-merge fires and is
   refused. 1,485 merged flush PRs; all 1,538 branches still present. The namespace
   mixes ~21 durable lanes (protection correct) with ~1,517 ephemeral
   `*-flush-*` lanes (protection is the leak).
2. **`automation/pr-archive-*` (1,880).** The workflow header records four prior
   drains and states of its PAT fix *"this closes the generator."* **Falsified:**
   1,880 exist today, 1,264 with no PR at all. Opening a PR is not merging one.

## `NO_PR` is drain-don't-discard

Sampled 40 of the 1,236 `automation/pr-archive-*` refs in that bucket: **40/40 carry
`docs/history/pr-reviews/` files absent from `main`.** Real archive substrate that
never landed. Not scheduled for deletion; needs `consume-pr-archives.ts` first.

## Reversibility

`docs/branch-reaper/planned-deletions.jsonl` carries `(branch, sha, pr, restore-command)`
for all 220 candidates and **lands on `main` before any deletion runs**.

Restore proven end-to-end on `dejan/pnpm-off-root-devdeps-to-pages-consumer`:
delete → confirm gone → restore → **identical SHA**.

The proof caught a defect worth keeping: zsh applies its `:r` modifier to an
unbraced `"$SHA:refs/heads/$BRANCH"`, producing `<sha>efs/heads/<branch>`. The
first restore failed and left the branch deleted. The literal manifest form is
safe; prefer `branch-reaper.ts restore <branch>`, which uses no shell.

## Recommendation (Aaron's call — both are settings changes)

1. **Narrow the heartbeat ruleset**: add `refs/heads/heartbeat/*-flush-*` to its
   `exclude`, keeping `deletion` protection on the ~21 durable lanes. Largest
   single win — **1,517 refs** — and it stops the namespace growing.
2. **Not a scheduled sweep as the primary fix.** That treats the symptom on a timer
   and would be the fifth drain. Use the census as a **watchdog** instead: report
   bucket counts, fail loudly when they grow.

## Not done

No bulk deletion. The 1,264 `NO_PR` need draining first. The 102 `CLOSED_PR` await
a human decision. The heartbeat ruleset is **unmodified**.
