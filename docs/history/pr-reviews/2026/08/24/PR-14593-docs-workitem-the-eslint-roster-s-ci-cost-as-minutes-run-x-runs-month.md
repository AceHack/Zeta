## Description

Follow-up to #14555 (merged). That PR shipped the eslint roster describing its cost as
*"no new job, ~20 s"*. **That is a per-run number, and a per-run number is not a cost estimate** —
the discipline is minutes/run × expected runs/month, and I only supplied the first term. Recording
the second.

| term | value | source |
|---|---|---|
| added wall-clock per run | **20 s** | `lint (TS)` step `ESLint over the measured-clean path roster`, run 32676220081: `00:18:19Z → 00:18:39Z` |
| runs/day | **594** and **529** | two 24 h windows ending `2026-08-24T00:40Z` and `2026-08-23T00:40Z`, via `search/issues?q=repo:…+is:pr+created:…` |
| is `lint (TS)` path-gated? | **no** — no `if:`, no `needs:` | it runs on every gate run, plus every push that re-triggers one |
| **added runner time** | **≈ 3.1 h/day, ≈ 95 h/month** | 20 s × 560 × 30 |

**95 runner-hours a month is not a rounding error and should not be presented as one.** What makes it
acceptable is that this repo is **public**, so GitHub-hosted standard runners bill at zero. The real
cost is 20 s of added latency on a job whose `tsc` step already takes ~27 s, plus the concurrency
pressure that adds to the runner pool at 560 runs/day.

**The number a future widener should watch is the slope, not the level.** The 20 s is almost entirely
typed-linting *program load*, not the 102 files — the repo-wide run over 2,500 files took 3–4 minutes
on a laptop. So widening the roster is close to free until it is not, and the inflection sits well
below *"the whole repo"*. Re-measure the step before taking the roster past a few hundred files.

Docs only — one workitem file, no workflow or script change. Markdownlint verified with the
copy-outside-the-glob method (`workitems/081*.md` is inside the ignore list, so an in-place run is
vacuous): sabotage control `rc=1`, real content `rc=0`.
