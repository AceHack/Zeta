## Description

fix(ci): stop being indirect — actionlint red on main, and a silent unknown-agent hole

`lint (actionlint)` is red on `main`, so on every PR that runs it. All 6 findings
are SC2034 at two sites in `agent-heartbeat.yml`: the per-agent model roster read
via indirect expansion (`HEARTBEAT_MODEL="${!HEARTBEAT_MODEL_VAR}"`). Shellcheck
cannot follow an indirect reference, so "appears unused" is a FALSE POSITIVE --
the variables are read.

I FIRST FIXED THIS WRONG, and the control caught it. Annotating the sites with
`# shellcheck disable=SC2034` turned the job green -- and a planted, genuinely
unused variable then went UNDETECTED. That is widening a check to make it pass:
the suppression covered the whole region, not the false positive. Reverted.

The honest fix is to stop being indirect. Both sites now select by `case`, so
shellcheck sees the assignment used directly and nothing is silenced.

AND IT CLOSES A REAL HOLE. Indirect expansion yields "" for an agent with no
roster entry, so an unknown agent produced an EMPTY model name and surfaced later
as `ollama pull ""` -- a confusing failure far from its cause. The `case` now has
a `*)` branch that errors and exits. Unknown-include over unknown-exclude: an
unknown that halts is recoverable, one that ships is not.

Worth recording while here: the roster is genuinely HETEROGENEOUS --
alexa=qwen2.5:0.5b, otto=llama3.2:1b, soraya=gemma2:2b, three model FAMILIES.
The structural decorrelation that the fleet-efficiency argument depends on is
already running, not merely proposed.

VERIFIED, exit codes captured directly, never through a pipe:
  actionlint  rc=0  (was rc=1 with 6 SC2034 findings)

SABOTAGE CONTROL, and it is the load-bearing one here: planting a genuinely
unused variable drives actionlint red (rc=1) AND NAMES IT (1 match). Under my
first attempt the same plant was invisible. Removing it restores rc=0.
