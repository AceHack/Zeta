## Description

## A quote inside a regex literal silenced the elevator guard

Follow-up to #14727. Found by running the lint that PR shipped against a comment I was
writing to document the lint's own scope — it flagged the comment, which meant the lexer
was wrong.

`src/Core.TypeScript/zflash/setup.ts:154` is an ordinary line:

```ts
const escaped = path.replace(/(["\\$`])/g, "\\$1");
```

`blankComments` had no regex state, so it read the `"` inside that character class as a
string opener and never recovered. From there to the end of the file, comment text was
scanned as code.

## The direction that makes this a defect, measured

The false positive is only how it surfaced. This is the one that matters:

```ts
const re = /[/*]/;
const r = spawnSync("sudo", ["-p", "", "true"]);
```

The old lexer reads the `/*` inside that character class as a block-comment opener and
blanks the spawn line entirely:

```text
OLD lexer sees the elevator? false
OLD blanked line 2: "                                                "
old_rc=0 (0 = OLD lexer MISSED a real elevator: false negative CONFIRMED)

FIXED lexer findings: 1
fixed_rc=0 (0 = fixed lexer catches it)
```

So the lint reported OK on a file containing the exact defect it exists to find. One
innocuous-looking regex anywhere earlier in the file silences the guard, and it leaves a
diff no reviewer has reason to question. That is a bypass, not a nuisance.

I checked the weaker claim first and it did **not** hold: a quote-bearing regex alone
(`/(["\\$`])/`) leaves the elevator matchable, because desyncing into a string state only
ever *un*-blanks text. The bypass needs the `/*` shape specifically. Recording that because
the stronger version was the one I expected, and it was wrong.

## What changed

- `blankComments` lexes regex literals: character-class aware (a `/` inside `[...]` does not
  close), escape-aware, and it recovers at a newline rather than swallowing the file on an
  unterminated regex.
- `regexAllowedAfter` disambiguates regex from division on the standard rule — a regex may
  not follow a value, so an identifier char, digit, `)` or `]` means division.
- Seven falsifiers, covering both directions, division-vs-regex, unterminated recovery, and
  the length-preservation invariant that keeps reported line numbers honest.

## Also: a dangling suppression cross-reference

`setup.ts:182` said *"same rationale as the sudo spawn above"* — a rationale #14727 deleted
for being false. A pointer to a deleted argument is worse than no argument, because it reads
as though someone checked.

It now stands on its own reasoning, and the distinction is not one of degree: that spawn was
a **privilege elevator**, so shadowing it is an escalation across the user/root boundary.
This `tee` is **unprivileged** and writes the invoking user's own rc file — shadowing it buys
an attacker something they could already do as that user. That is why it is deliberately out
of `lint-no-path-resolved-privilege-elevator`'s scope, which guards elevators and not every
PATH-resolved command. The honest limit is stated too: that holds only while the call stays
unprivileged, and the comment directly above it already contemplates a system-wide variant
that would need `sudo`.
