## The two findings

**P1 -- the biometric approval gate is forgeable by a `PATH` entry.** `macTouchIdAuth` establishes
operator approval as `spawnSync("sudo", ...).status === 0`, with `sudo` resolved by name.
`realBiometric()` is, per `publish.ts:254`, *"the one gate every op shares"* -- CA creation, Shamir
custody, onboarding, rotation, revocation, publish. Reproduced end-to-end on the operator's host with
a shim that executes nothing and obtains no privilege:

```text
PATH="$R/shim:$PATH" bun probe2.ts     # calls the REAL macTouchIdAuth
macTouchIdAuth => {"ok":true,"platform":"macos-touchid","factor":"unattributed",
                   "reason":"...Approval established..."}
--- shim log (proves no real sudo ran) ---
SHIM-REACHED argv: -k
SHIM-REACHED argv: -p  true
```

No Touch ID prompt, no human. The repo's own setup creates the precondition -- `export
PATH="$HOME/.local/bin:$PATH"` prepends a **user-writable** directory ahead of `/usr/bin` -- so the
shim needs no root and leaves **no git diff**, which puts it outside review, AgencySignature and
byte-lock, all of which watch the repo.

The existing suppression at `zflash/setup.ts:105` argues this is safe. Both halves are measurably
false: `brew info sudo` -> *"No available formula"*, and `/usr/bin/sudo` is `restricted` under SIP,
so the portability premise fails; and "would already compromise the machine" conflates *user* with
*root* compromise, which is the boundary `sudo` exists to cross. That line `sudo tee`s
**`/etc/pam.d/sudo`** -- the file `analyzeSudoAuthChain` later reads to judge the gate.

**P2 -- `from-deb` predictable temp path + root install, unverified.** `curl -o` (no `O_EXCL`, no
`O_NOFOLLOW`) to `/tmp/zeta-deb-${name}-${Date.now()}.deb`, then `sudo dpkg -i`. No digest, though
`verifySha256File` exists next door and `from-autotools-tarball.ts` uses it. Symlink half reproduced.
**Latent** -- the manifest has zero entries -- so P2, not P1.

## Dismissed, with the reasoning

- **`/tmp` and the agent fleet.** "Single-user machine" is the right conclusion for the wrong reason.
  There is no second OS *user*, but there are many concurrent *agents* on one uid with zero OS
  isolation. What follows is **not** that every `/tmp` site is a finding -- it is that predictability
  grants a co-uid agent nothing it lacks, since it can already read, write and ptrace everything the
  user owns. It bites only where the file crosses into a privilege the attacker does not hold.
  Exactly one site does. `/tmp/zeta-bus` is fine on its merits (`0o700`, `lstat`ed, traversal-guarded,
  `randomUUID` names); residual worth knowing is that `ensureDir` accepts a pre-existing directory
  without an owner/mode check -- a cluster concern, not a laptop one.
- **`shred` for key erasure.** Looks alarming; is correct. Guarded by `status === 0 && !existsSync`
  with an overwrite-then-unlink fallback and a final existence check.

## CI recommendation: enable neither; ship a targeted lint

The decisive evidence is **recall, not noise**. A full inventory of live `sudo` invocations finds ~15
sites; the rule flags **10**. It misses `setup.ts:106` (suppressed, and the most sensitive one) and
cannot see `sudo` reached via a variable, an array, or a `run()` wrapper.

> Turning this rule on in CI would not have caught the P1 filed here. It costs 443 triage decisions
