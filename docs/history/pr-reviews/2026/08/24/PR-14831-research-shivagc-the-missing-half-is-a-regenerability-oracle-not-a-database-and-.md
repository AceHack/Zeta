## What Aaron asked

> *"for shivagc yes it's a toy we need to connect it to our zetadb/fs and our futamara f# type providers and rosylin stuff to see what the next steps are, this is the first path forward"*

The goal was **to see the next steps**, so this is an exploratory wiring study, not a production GC. Measured against `origin/main` @ `8a8d011de`.

## Three findings, in order of how much they change the plan

**1. There is no F# type provider in this repo.** Not erased, not generative, and no third-party provider is consumed either — 1,329 `.fs` files grepped for the SDK attributes yield exactly one hit, a comment in `ImdbDataset.fs:20` saying the wrapper is *not built*; zero package references anywhere. `src/Core.CSharp.TypeProvider/` is a Roslyn `IIncrementalGenerator` emitting C# `record` declarations — it produces **types**; a GC's regenerability predicate needs **values**.

The stronger hypothesis (reified providers over ZetaIds *witness* regenerability) also does not close, and the measurement is specific: `GeneratorRegistry.idOf` is `hash128 (sprintf "%s@%d" name version)` — it hashes the generator's **name**, not content, and not the product's inputs. The 128-bit `ZetaId` is ULID-shaped by default (48-bit timestamp + 32 random) with content-addressing as **one opt-in category out of sixteen**. Stated in the required register: *consistent with*, not *is*.

**2. ShivaGc's missing half is not storage — it is an ORACLE.** zetadb (TypeScript, `zeta-db-node.ts`) and zetafs (F#, `ZetaFs.fs`) are two unrelated systems sharing a prefix — no shared substrate, record shape, or hash. Neither can answer *"could this be rebuilt?"*: none of the three object shapes in the repo carries a generator, recipe, derivation, or provenance field. Two further obstacles — zetadb has no edge field, so `refs` (what `mark` traverses) does not survive the crossing; and neither store reclaims anything (`ZetaFsDeltaLog.fs:214`: *"The delta blobs are still on the disk and nothing collects them"*).

So the first path forward is a refusal of its own framing — which the brief named as a successful outcome. The correction is that it is not the interface that is wrong, it is the premise that the missing half is a store.

**3. The predicate `reachable OR NOT regenerable` fits the existing interface without breaking purity — iff the oracle is injected.** That is forced by compile order, not chosen for elegance: `Core.fsproj` compiles `ShivaGc.fs` at position **92**, while `ContentStore.fs` is 184, `DvKey.fs` 195, `GeneratorIrRegistry.fs` 366. A built-in regenerability check is not merely undesirable here — it is **unexpressible**.

Today's `partition` turns out to be the degenerate case `regenerable = fun _ -> false`: maximally conservative, always safe, and the reason it frees nothing.

| class | condition | disposition |
|---|---|---|
| resident | reachable | working set |
| **droppable** | unreachable ∧ regenerable | free — rebuild on demand |
| paused | unreachable ∧ ¬regenerable | **must** persist (manifesto §5) |

## The PoC — pure, 10 lines, and it destroys nothing

`ShivaGc.partition3` takes `regenerable: string -> bool` as an argument. The module stays a pure `DynamicValue -> DynamicValue` function, so it remains DST-replayable (§7) and the oracle is a **declared, metered channel** rather than an ambient dependency on a store, a clock, or the host GC (§13). `droppable` is a *permission* granted by the oracle, never an act of dropping.

Deliberately **not** wired: `SpecializationCache` — its `WeakReference` puts the host GC on the replayed path and its public `Hits`/`Misses` are a declared §13 violation. Purity is ShivaGc's main present asset and a naive wiring to a live database would destroy it.

## The vacuity trap this was built to avoid

`tests/Tests.FSharp/ShivaGc.Tests.fs:116` already asserts *"partition then resume reconstructs the heap byte-identically"*. That is a correct test of `resume`, but `partition` returns the paused objects **whole**, so the byte-identity is trivially guaranteed — **the value was never dropped.** It measures retention and reads as evidence of regeneration. The naive version of the falsifier would have added a second one just like it.

The new test never reads the dropped value on the regeneration path: the replacement bytes are produced by re-running `MixIr.runMixCall` over the reified recipe, compared under canonical CBOR.

## Ranked next steps (§8 of the doc)

1. **Make the `id` a real content address, or stop calling it one.** A shipped test already proves the premise false *and shows the collector producing a dangling ref*. Everything below assumes the id determines the value.
2. **Give the oracle a real backing** — a `Map<id, MixCall>` recipe side-table, then generalise to any pure `DynamicValue -> DynamicValue` generator.
3. **Write the ZetaDB frame round-trip test** — the object-granularity form ships here; the frame-level one is the prerequisite for the object-generator compression.
4. **Version the generator by content hash** — this is where the Merkle DAG earns a role in totality.
5. **Then** consider persistence: once regenerability is decidable, `paused` is the only class that must be written down.

Not to build: a `gen` field on `object'` (puts the generator inside the collected set), and chained regeneration (depth is 1 everywhere; there is **no cycle guard on regeneration** — `mark`'s `seen` set guards traversal, not recomputation).
