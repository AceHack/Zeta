## Description

## Three lanes froze; none of them said so

- The Red State lane failed **ten consecutive runs** (2026-08-25T06:37Z → 2026-08-27T02:02Z) and `demo/red/red-state.json` sat at **2026-08-23T18:35Z** — 3.7 days.
- A sibling lane went two days.
- A retired launchd lane went **ten weeks**.

Every one was found because a human happened to read a name off a list.

The surface to catch them was **already built and unused**: `collect-red-state.ts`
writes `generatedAtIso`, `demo/red/index.html` renders it in the footer, and nothing
asserted it was recent. A timestamp that is displayed but never checked is decoration
— it makes a page look accountable and holds nobody to anything.

## The threshold, and why *that* number

`staleAfterSeconds = stalenessFactor × cadenceSeconds`, with **both inputs taken from
something that already exists** rather than chosen here:

| input | source |
|---|---|
| `cadenceSeconds` | the lane's **own declared cron**. red-state's producer declares `23 */6 * * *` → 6 h. |
| `stalenessFactor` | **imported** from `DEFAULT_FOLD_CONFIG`, not redeclared. It is the drift dashboard's already-argued answer to this exact question, and it is **3**. |

**6 h × 3 = an 18 h window.**

Why 3: GitHub drops scheduled runs under load — `drift-dashboard-cadence.yml`'s own
header says so and staggers its cron because of it — so one missed tick is weather and
three is not. 18 h is comfortably shorter than every freeze that motivated this (2 d,
3.7 d, 10 wk) and comfortably longer than any hiccup observed.

Importing the factor rather than copying it means the repo keeps **one** staleness
constant. A threshold nobody chose is the defect that produced the 5000 ms Bun timeout
and the `>= 1.5x` SIMD gate; a threshold *duplicated* is the same defect on a delay.

## Stale ≠ absent, and neither is fresh

Same discipline as *exit code 2 is a check that never ran*. `missing-file`,
`unparseable`, `no-field`, `unparseable-timestamp` each name what actually happened, so
an empty result can never be mistaken for a healthy one.

`from-the-future` is in the enum because the alternative is worse: a timestamp ahead of
`now` has the **smallest age of all** and would otherwise rank as the freshest thing on
the board — which is exactly what clock skew and a fabricated value produce.

## Not the drift dashboard again

That watches whether each **workflow produced a verdict**. This watches whether the
**artifact it exists to publish actually landed.** They come apart, and not
hypothetically: a lane can go green, collect perfectly, and publish nothing when its
flush PR does not merge. The dashboard calls that lane healthy while the file is four
days old.

## Not a gate

The job goes red so a freeze is visible in a *conclusion* rather than in a file nobody
opens, and it is **absent from the required-check floor**, so it blocks no merge.
Promotion to the floor is Aaron's call and must not be a side effect of shipping the
check.

**And the watcher is watched.** The drift dashboard enumerates every ACTIVE workflow
and derives each one's cadence from its own cron, so this lane joins that roster
automatically. A watcher that could go dark unnoticed would just move the problem up
one level.

## On generalising

**Two subjects, not one** — `red-state` and `drift-dashboard`. One would be a
single-lane guard; two is the smallest roster that proves the checker is not welded to
red-state, and a third is a five-line edit.

A *general* version would need cadence derived from each workflow's cron automatically
(`expectationForWorkflow` already does this and could be lifted) and a path expression
for nested timestamps. Neither is worth paying for at two subjects and both become
obvious at five. That is recorded in the file rather than built.

## It can fail — exit codes read directly, never through a pipe

```
live tree, real clock                       rc=0   both fresh (34m, 66m)
same tree, clock advanced 2 days            rc=1   both stale (47.3h, 47.8h)
generatedAtIso set to the incident's value  rc=1   red-state stale 3.4d, sibling still green
generatedAtIso deleted                      rc=1   no-field — NOT fresh
restored                                    rc=0
```

12 unit falsifiers cover every state, including the boundary either side by one second.
The pair that matters is first in the file: **same subject, same clock, one timestamp on
each side of the line.**

### One defect avoided rather than shipped

The audit step sets `-o pipefail` explicitly. Actions runs `run:` under `bash -e {0}`
with pipefail **off**, so `bun … | tee f` reports *tee's* status — always 0 — and the
step would have gone green on every stale artifact it found. Measured locally: `rc=0`
without, `rc=1` with. (`proof-closure-drift.yml` has the same shape today; not touched
here, flagged for its owner.)
