## Description

Follow-up to #15673, which merged with `build-iso` red. Two commits: the reason it was red, and a fix of mine that missed its merge window.

## 1. Both etcd peers advertised the same address

#15673's loopback-alias fix worked — the joiner resolved `control-plane` to the founder and reached the real etcd join. Step 13 then failed 420 s later on **the same defect one layer down**:

```
Adding member joiner-639dff20=https://10.0.2.15:2380
       to etcd cluster [founder-e8c381a4=https://10.0.2.15:2380]
...
etcd cluster join failed: dial tcp 127.0.0.1:2379: connection refused
```

Both peers advertise `10.0.2.15`. That is QEMU's SLIRP address, which **every** nixosTest guest holds on eth0 — the single-node checks in the same run show the identical value — and eth0 carries the default route, so k3s picks it as the node IP. The joiner dialled the founder's advertised peer, arrived at **itself**, found no etcd serving there, and crash-looped to the timeout.

Same shape as the alias it follows: *an address that means "me" on every node, used as the cluster-wide identity of one node.*

**Fixed in the harness, because that is where this defect is.** Each node pins `--node-ip` to its own vlan address, where the guests are genuinely distinct and mutually reachable. Verified by evaluation — this Mac has no `/dev/kvm`, so the boot is CI's to report, exactly as #15673 said of its own VM assertions:

| node | flag |
|---|---|
| founder | `--node-ip=192.168.1.1` |
| joiner | `--node-ip=192.168.1.2` |

`--cluster-cidr` and the rest of `k3s-server.nix`'s list survive, so the flag list **merged** rather than replaced. All 20 `checks.x86_64-linux` evaluate; `nix flake check --no-build` green (27 checks).

### What this does NOT fix

Said out loud rather than left implied. Real hardware has no shared `10.0.2.15` — but it does have more than one NIC, and `k3s-server.nix` pins no `--node-ip` at all, so a multi-homed control plane can still advertise etcd on an interface its peers do not share. That is a **product** question about which interface the cluster segment owns, it belongs with `injected-cluster-address.nix`, and a harness fix must not be read as having settled it.

`k3s-agent-join.nix` is unaffected and always passed: an agent joins the API server by name and never joins etcd at all — which is exactly why the sibling test could not have caught this.

## 2. The pod-IP guard that missed #15673's merge window

Self-caught while re-reading my own commit. `podIpInPool`'s docstring promises `false` for a non-address, and the shape-only regex still threw on `999.1.1.1` / `10.143.0.256` — `CIDR out of range`, a different throw through the very hole the guard exists to close. Guard is now shape **and** range.

Mutation run, not asserted:

| mutation | result |
|---|---|
| shape-only guard | **1 fail** |
| as committed | 10 pass |

The new case pins the other direction too (`10.143.0.255` is still `true`), so it is not a guard that passes by rejecting everything.

For the record, the parent fix is confirmed working: `live kind Cilium CNI (ubuntu-24.04)` came back **success** on #15673's merged head, clearing a lane that had been red on `main` since #15668.
