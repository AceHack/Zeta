## Description

## The defect

**PR #15691 was green on `agencysignature (PR body)` while asserting an identity that provably did not sign it.**

| sha | `Credential-Identity` | `Credential-Mode` | git author + committer |
|---|---|---|---|
| **`d98366df924d`** | `alexa` | `dedicated-agent` | `AceHack <aaron_bond@yahoo.com>` |
| **`759731489461`** | `AceHack` | `shared` | `AceHack <aaron_bond@yahoo.com>` |

Same PR, same branch, same author, **differing only in the two fields under test.** The first is the defect; the second is that PR author's own independent correction. Put beside each other they are the whole argument: the values the correction landed are exactly the values this check demands.

`alexa` is a legal free-text string and `dedicated-agent` is a legal enum member, so the shape check could not see it. **The validator checked ten keys, contiguity, and enum membership — and never asked whether the claim was TRUE of the commit carrying it.** That is the vacuity class in a governance check: it looks like verification and verifies the wrong proposition.

Second instance in one night. The first, **#15676**, is an `INVALID-VALUES` defect; the fix proposed there does **not** catch this one, because both values here are valid. **Complementary, not duplicate.**

## What is added

`src/Core.TypeScript/hygiene/credential-identity-claim.ts` compares the claim to the commit's own author/committer, plus a `credentialIdentities` section on the existing roster.

Refutation needs only **one** side rostered, which is what keeps it fail-closed in the right direction:

- commit identity **unrostered** → `UNVERIFIABLE`. A fresh agent credential with its own git identity is never accused, and **adding an agent needs no roster edit**. This is deliberately not an allowlist of agents — that fails open, exactly as the roster's own §humans note explains.
- commit identity **rostered**, claim resolves elsewhere or nowhere → **`REFUTED`**, naming both values.

That is why #15691 is caught **without anyone rostering `alexa`**: `aaron_bond@yahoo.com` is the shared `acehack` credential, and `alexa` is not it.

## What is deliberately NOT faked

**`Credential-Mode` is a fact about a CREDENTIAL, not about a commit, and is not derivable from one.** It is left UNCHECKED, and the tool prints that on **every** run, pass or fail:

> `Credential-Mode is NOT derivable from a commit and is NOT verified here … treat their absence from this report as silence, not as a pass.`

One narrow half **is** decidable and is taken: `dedicated-agent` on a credential the roster **declares** shared is refuted. `shared` stays unprovable; its **negation** on a declared-shared credential is provable. Refutable is not provable.

The standard being enforced is the repo's own: `merge-heartbeats-to-main.ts` already infers the mode from `gh api user` and **degrades to `unknown` rather than asserting a convenient value**.

## Proven in both directions, on real commits

Not fixtures — the actual git objects, pinned by sha so the fix to #15691 cannot erase the red case:

```
d98366df924d  →  ::error::REFUTED-IDENTITY … claims 'alexa', but this commit was
                 made by the rostered credential 'acehack'   exit 1
759731489461  →  VERIFIED … 'AceHack' resolves to 'acehack', which made this
                 commit. Credential-Mode 'shared' NOT checked.  exit 0
```

Both directions are also pinned as tests (`THE LIVE PAIR`), including one asserting the pair differs **only** in those two fields — so the red case cannot later pass for an unrelated reason.

**This commit's own block passes, for the right reason:** `VERIFIED f7226dc1ade2 — 'AceHack' resolves to 'acehack', which made this commit.`

## A false-positive class found, and fixed

The first roster draft listed `society[bot]` as its own credential and **immediately refuted two honest commits** (`cbc6f1a1c11d`, `93310a63126d`). `society-heartbeat.yml` sets that name with `git config` — a **display** identity — while pushing with `ZETA_TELEMETRY_FLUSH_TOKEN` or `GITHUB_TOKEN`, so its `Credential-Identity: github-actions[bot]` was **TRUE** and the roster was wrong. Display identities of one credential *family* now share one row, pinned by a regression test.

**Measured after the fix: 0 refutations across 63 branch commits of all 15 open PRs, and across 64 branch commits of the 40 most recently merged PRs.**

That failure also sets the honest scope: a git author field is settable, so **this is not an anti-forgery mechanism** and the header says so. An actor who controls the commit controls both halves. What it catches is *a block nobody made consistent with the record it rides on* — which is the defect that actually happened twice tonight.

`audit-coauthor-identity-collides.ts` also caught my own first draft (an unmeasured `web-flow` constant, AH005 `collides-plain-noreply`). Dropped.

## Where it runs — and the door it does NOT close

**Pre-merge only,** as a third step in the existing `validate-pr-body` job, on the PR's own commits.

**Main-tip is structurally vacuous today and is deliberately not wired.** All **600 of the last 600** commits on `main` carry committer `noreply@github.com` — squash-merge rewrites authorship to the merging account. 319 of those blocks claim `github-actions[bot]` while authored `aaron_bond@yahoo.com`: true of the branch commits, uncomparable on the squash object. A main-tip run would report UNVERIFIABLE 600/600 — **green forever, verifying nothing**, which is the precise defect this workflow exists to enforce against. `--source main-tip` exists in the tool (direct pushes *are* checkable) and is left unwired on purpose.

**`PUT /pulls/{n}/merge` with a hand-written `commit_message` still replaces the validated preimage after every pre-merge check has run** — the door #15676 documents. **This check does not close it and structurally cannot:** that object carries GitHub's own attribution, so there is no author left to compare a claim against. What the pre-merge job buys is that every claim a *branch commit* makes is bound; a claim appearing only in a hand-written merge message is a claim no commit ever made. Same residual hole #15676 named, not made worse.
