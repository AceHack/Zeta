## Description

Two defects, one mechanism: `codeql.yml`'s `path-gate` job — which never runs an analyser — synthesised a SARIF with `"results": []` and uploaded it under the five **real** analysis categories on every event. GitHub records a zero-result SARIF as a **successful analysis that found nothing**, and then closes every open alert in that category.

## Defect 1 — the durable security record on `main`

```
analysis 1679102987 — 2026-08-27T02:56:34Z
  analysis_key  .github/workflows/codeql.yml:path-gate
  category      /language:javascript-typescript
  results_count 0     error ""     tool.version 0.0.0
```

`error: ""` is GitHub recording that as clean. **102 alerts across 14 rules** went `fixed` at that exact instant, none dismissed. The commit credited (`acaecd12 → c99878b4`) changed **two lines of `demo/red/red-state.json`**.

Still live, closed with dataflows intact: `js/http-to-file-access` **#267** at `src/Core.TypeScript/peer-call/summon.ts:369`, **#772** at `src/Core.TypeScript/observe/tick-reasoning.ts:59`.

Trigger is cancellation — `Path gate` finishes in ~1 min and uploads; the `Analyze (X)` legs are then cancelled by the next push. **80.7% of codeql push-runs on `main` are cancelled** (n=300).

## Defect 2 — the merge gate on a PR ref

My first commit gated the baseline off `push`/`schedule` and deliberately left `pull_request`/`merge_group` alone, reasoning that those analyses are discarded with the ref. **The first half is true; the conclusion was wrong**, and it was falsified live the same day on PR #15636 (`refs/pull/15636/merge`):

```
04:05:02  path-gate  js-ts  r=0  tool 0.0.0  -> alert #803 fixed, thread AUTO-RESOLVED
04:09:57  analyze    js-ts  r=1  tool 2.26.3 -> alert #803 reopened, thread unresolved
```

Verified rather than relayed:

| claim | evidence |
|---|---|
| both uploads on the PR ref, 4m55s apart | analyses record for `refs/pull/15636/merge` |
| alert reopened at 04:09:57 | alert #803 `updated_at = 2026-08-27T04:09:57Z` |
| the thread resolution is **automatic** | thread author `github-advanced-security`; sibling thread `resolvedBy = github-advanced-security[bot]` — no human in the loop |
| `required_conversation_resolution` enabled | `branches/main/protection` **and** pinned in `hygiene/github-settings.expected.json` — an audited, deliberate control |
| auto-merge is standard | #15636 had it armed at read time |

So a PR-ref alert is **not scratch**. Closing it removes a merge blocker, and with auto-merge armed a PR can merge on an erased finding. The `main` case leaves a wrong record until the next analysis; **this one can let a change through irreversibly**. The ephemeral ref is the *more* dangerous surface.

PR runs cancel at **9.7%** vs 80.7% on push (n=300 each), so the window usually closes itself. *Usually* is not a security control.

## The fix

**The synthesised baseline is removed outright** — emit step and all five uploads, every event.

The balance that justified keeping it no longer holds, and this is measured, not assumed: the **only** required status check is `gate (required)` (ruleset "CI Gate"), and **no active ruleset carries a `code_scanning` rule at all** — the `code_quality severity:all` rule the workflow comments cite is not configured. Neither the aggregate `CodeQL` check nor any `Analyze (X)` leg is required. A docs-only change now records no analysis for that commit, GitHub carries the previous alert state forward, and nothing is blocked.

**`path-gate` also loses `security-events: write`.** It decides whether code changed and never analyses anything, so it has no honest reason to hold the one token that can close an alert. That makes the defect *structurally* unrepeatable here rather than merely linted — a future upload step in that job 403s instead of quietly succeeding.

### Why not `executionSuccessful: false`

It is the format's own way to say "did not run", GitHub honours it (a cancelled analyze leg's upload is recorded `error: "unsuccessful execution, exit code: 0"` and changes no alert), and **it remains the linter's first remedy** for any workflow that genuinely needs a placeholder. Not adopted *here* because (a) the claim could not be isolated from this repo's own record — every unsuccessful upload in the retained window is preceded by a clean one on the same ref — and (b) github/codeql-action#1316 documents uploads **failing** with an "unsuccessful execution" error, trading a silent wrong answer for a hard failure on every PR. Removing the upload needs no such assumption.

## The falsifier

`hygiene:no-clean-sarif-for-skipped-analysis`, in the gate floor job:

> **A job that never runs an analyser may not upload a result that looks like a completed analysis.**

Two remedies only: `executionSuccessful: false`, or an emitting job that runs the analyser. **Both event-shaped escapes are gone** — the condition gate and the trigger-scope gate — with two tests as the ratchet: an event-gated fixture and a `pull_request`-only fixture must *both* still report a finding.

The second remedy still clears `analyze`'s no-source baseline, an honest verdict by the job that owns that category. Its residual — the lint does not check that the `has_source` detector is correct — is named in the source rather than papered over.

**Seven mutants killed:** `declaresUnsuccessful` ignored (1 fail) · `jobRunsAnalyser` always-true (5) · unsuccessful-marker matching `true` too (1) · normalize-after-match (5) · `EMPTY_RESULTS` never-matches (10) · trigger-scope escape (1) · condition-gate escape (1).

## A defect in my own first commit

The audit source carried **four NUL bytes** in a template literal, so `file` reported it as `data` and `grep` refused it as binary — a source file invisible to every text tool in the repo, including the greps other audits use to find it. Fixed, pinned by a test that reads the bytes.

Worth recording: my first attempt to scan for this was itself vacuous. `grep -U $'\x00'` in zsh becomes an **empty pattern that matches every file**, and reported all four files dirty *after* they were clean. The test uses `Buffer.indexOf(0)`, not a shell grep.

## What I could not demonstrate

- **That a docs-only PR is still mergeable with the baseline gone.** Needs a docs-only PR after merge. Short of it: `path-gate` now has exactly two steps and zero `upload-sarif` steps (parsed from YAML), `analyze` still gates on `code_changed`, required set is `gate (required)` alone.
- **Reproducing either closure.** Not attempted — reproducing means closing real alerts.
- **Blast radius before `2026-08-26T09:56Z`.** The analyses endpoint caps at 1500 records and reopening erases the prior `fixed_at`.

## Not done — and not mine

**Nothing here weakens `required_conversation_resolution`.** That is the control this race defeated, not the problem.

**No alerts reopened by hand.** Unnecessary: the next successful analysis re-uploads and GitHub reopens them, which is the oscillation the record already shows (these alert numbers date to May/June and carry old `created_at` through repeated close/reopen).

Two residual asks, **named rather than acted on — both are repo-settings decisions and Aaron's**:

1. **Should auto-merge be refused while an advanced-security review thread exists on a PR?** The workflow fix closes the window this repo has; it does not make "alert closes → thread resolves → last blocker disappears" impossible in general, because that chain is GitHub's, not ours.
2. **Should the `code_scanning` ruleset rule be restored?** Its absence is what makes removing the baseline free. If it comes back, the shape to reach for is `executionSuccessful: false` — validated first — never a clean empty SARIF.
