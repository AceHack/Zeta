## Description

## The reversal

PR #15641 measured two live k3s control planes with different cluster CAs and classified the estate `blocked / control-plane-split`. Aaron 2026-08-26 reframes it:

> *"they should just be different clusters with the ability to join after the fact if they want into one cluster, and also a cluster creator should be able to remove it."*

**Two clusters is the correct default.** A node is complete on its own at boot (§1 scale-free). `clusterInit = lib.mkDefault true` is right and is **not changed here**. The defects are the missing join path and the absent leave path.

## The constraint — established, not assumed

k3s documentation, verbatim:

> "If an etcd datastore is found on disk either because that node has either initialized or joined a cluster already, the datastore arguments (`--cluster-init`, `--server`, `--datastore-endpoint`, etc) are **ignored**."

The flags are not rejected, they are **ignored**. So a declarative *"join by default on network boot"* is a **silent no-op on exactly the nodes it targets**, wearing the appearance of a configured join — the vacuity class in Nix.

**This corrects the assumption behind Guard 1.** k3s does **not** wipe; it fails closed already. The confiscation risk would be **introduced by us**: making join-by-default work on a node holding a cluster requires writing an explicit datastore `rm` into the boot path — a wipe with *no initiator at all*. That is a thing we would have to choose to write, and this design does not write it.

## Exit is cheap, entry is costly — and that runs the right way

| direction | primitive | state | cost |
|---|---|---|---|
| **leave** | `--cluster-reset` — *"Forget all peers and become sole member of a new cluster"* | datastore + CA preserved | cheap |
| **join** | remove datastore, then `--server` | cluster, CA, identity destroyed | irreversible |

Hirschman's exit discriminator is satisfied by k3s itself. No mechanism has to be invented to make exit real.

## Both paths, and the ordered rule that selects between them

Aaron: *same creator + same network => join; different owners + different networks => federate.* Implemented literally over `(owner, network)` that is unsafe, because `network` is attacker-supplied. So:

```
1. owner PROVEN?     no  -> refuse          (guard 2; unknown blocks, never permits)
2. owner the SAME?   no  -> federate        (there IS a second party to negotiate with)
3. anything to lose? yes -> offer + consent (guard 1; spend/stake yes, confiscate never)
4. same network?     no  -> offer + consent / yes -> join automatically
```

Locality is consulted **only at step 4**, after trust is settled. **The network is a discovery hint, never a trust signal** — anyone on the LAN can claim to be on the LAN. That distinction is already carved in-repo about git remotes (*"the repo says which cluster, the key says whether you're in it"*); this applies it one level down. `ssh-ca.nix` is the trust anchor and is **inert today** — activating it is a prerequisite, not a parallel task.

Guard 1's discriminator is **measured**, not a policy flag; an *empty but founded* cluster still has something to lose (its CA and identity), and each holdings field alone flips the answer.

## Three removal operations, not conflated

*"remove it"* is ambiguous between a member and the cluster, so all three ship: **member secedes**, **creator evicts member**, **creator dissolves cluster** — each with who initiates, what the departing node retains, and what each act destroys.

**The confiscation line:** the creator's authority ends at cluster **membership**. The eviction plan contains no datastore wipe, asserted by a test whose negative control is that the *join* path really does emit those strings.
