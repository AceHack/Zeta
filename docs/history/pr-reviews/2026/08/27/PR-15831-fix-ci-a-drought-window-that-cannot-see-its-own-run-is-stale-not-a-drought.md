## Description

## The loudest detector in the repo has been loud about a fact that is not true

`drift (loud)` is the **only** failing job on main's gate runs — 44 of the last 60 `push`
runs on `main` — and the drought it reports did not happen.

**Measured 2026-08-27.** Gate run 33080913662, step *Report main's gate-verdict drought,
loudly*, at 14:26:30Z:

| measurement | value |
| --- | --- |
| register | `drought` |
| last COMPLETED verdict | run 30762762709 `success` a48ffa5c (2026-08-02T19:23:30Z) |
| time since that verdict | **35703 min** (threshold 45) |
| commits on main since | **6029** (threshold 10) |
| of which cancelled | 19 (31.7%) |

`main` had been verdicted **19 minutes earlier**, by run 33078983023. Running the same
reporter unchanged against the live API a few minutes later returned `ok` — newest verdict
33080913662 at 14:26:34Z, **0** cancelled, 60 of 60 carrying a verdict.

### The code is right. The input is not a stable channel.

`GET /actions/workflows/gate.yml/runs?branch=main&event=push&per_page=60` served, from one
credential inside a few minutes, **both**:

- a page whose newest run was `2026-08-27T14:12Z` (observed 9×), and
- a page whose newest run was `2026-08-02T19:22Z`, spanning 08-01 → 08-02 (observed 2×:
  once inside CI, once from a local PAT)

HTTP 200 both times. No error, no marker, no way for the caller to tell them apart. A
~25-day-stale secondary index, served intermittently.

### Why this needed a fix rather than a note

A loud detector that is loud about the wrong thing is worse than a quiet one — it teaches
every reader to skip it, which is exactly the cry-wolf failure `drift-loud.ts` was designed
against. And it is this file's own subject turned inward: **a check that did not look must
never read as a check that ran.**

### The guard is self-reference

The reporter holds one fact a stale listing cannot fake: **it is itself one of the runs the
listing is required to contain.** Executing inside a `push` run of `gate.yml` on `main`, its
own `GITHUB_RUN_ID` must appear in the window. Absent ⇒ the window is stale, and the honest
register is `unmeasured`, never `drought`. Checked on the raw observations *ahead of*
`foldDrought`, so a stale page never reaches the register.

Scope is narrow on purpose: `drift-sweep` calls the same reporter with `--report-only` from
a `schedule` run of a different workflow, where the caller is legitimately absent from a
`push`-filtered listing. Firing there would be a check that always fires. All three of
event / ref / workflow must place the caller inside the window, and each is separately
falsified. No Actions context (local run, fixture replay) skips the guard entirely.

### Nothing about the policy changes

Still outside `gate (required)`. Merges are unaffected either way. What changes is that its
red now means what it says.

### Falsifiers

That last one **survived at first**. Every unit test proved the guard *decides* correctly;
none proved `main()` *asks* it — the same vacuity one level up. It is killed by a subprocess
test that drives the real entry point with a fixture window and a forged Actions
environment, so the stale page has to travel the whole path and come out `unmeasured`.

### What this does NOT do

It does not explain *why* the Actions API serves a stale index, and it does not make the
underlying flap go away. It makes the flap **visible and unmistakable** instead of
laundering it into a false claim about `main`. If the stale window is more than occasional,
the next question is whether the drought detector should retry-and-compare rather than trust
one listing — that is a policy call, and this PR deliberately does not make it.
