## Description

Two `js/file-system-race` alerts our own linter cannot see, and the reconciliation
that explains why.

THE TWO LEDGERS ARE NEAR-DISJOINT. Measured:

    lint-check-then-use-file-races baseline   294 entries across 180 files
      by kind: check-then-use 255, readdir-then-stat 39
    CodeQL js/file-system-race                 22 files
    files BOTH see                             10
    files only CodeQL sees                     12
    files only our linter lists               170

Neither detector is a superset of the other, so neither can be retired in favour
of the other — and, more usefully, our baseline shrinking says NOTHING about
CodeQL's count. They are measuring overlapping but different things.

WHAT OUR LINTER MISSES is one shape: `statSync` paired with a read of the SAME
path. It models `check-then-use` (existsSync -> read) and `readdir-then-stat`,
and `stat-then-read` / `read-then-stat` are siblings it has no pattern for.

THE TWO FIXED HERE ARE NOT COSMETIC:

  observe/workspace-port.ts:271   `statSync(full)` then `readFileSync(full)`
    resolves the path TWICE, so the mode and the bytes can describe two different
    files. Replace the file in between and the entry reports one file's
    executable bit alongside another file's content, with nothing saying so.

  bus/claim.ts:62                 `readFileSync(lp)` then `statSync(lp)` in STALE
    LOCK RECOVERY. The holder PID comes from one moment and the mtime from
    another, so a lock released and re-acquired between the calls yields the OLD
    pid against the NEW mtime — and the recovery path can then unlink a lock that
    is very much alive. That is a correctness bug in mutual exclusion, not a
    scanner nit, and CodeQL found it while our linter could not.

Both become `openSync` + `fstatSync(fd)` + `readFileSync(fd)`: one handle, one
inode, both answers, no window.

NOT DONE HERE, and deliberately: teaching `lint-check-then-use-file-races` the
`stat-then-use` shape is the durable fix — a detector improvement rather than N
patches — but it would surface a large new finding set needing baseline
expansion, which is a decision about how much debt to formalise at once rather
than something to slip into a fix commit.

1440 pass across observe, 106 across bus, tsc clean, oxlint clean, and our own
linter still reports no findings over 2348 files.

    **Correct, and not closable here — filed as debt rather than dismissed.**

    This alert survived two real fixes, and it should have:

    1. `openSync` + `fstatSync(fd)` + `readFileSync(fd)` made the **judgement** consistent. Before, the
       holder PID and the mtime were two separate path resolutions and could describe two different
       locks.
    2. A `dev`+`ino` comparison immediately before the unlink makes **replacement detectable** — if the
       holder released and someone else acquired, the inode differs and the unlink is skipped.

    **What remains is real:** the window between that comparison and `unlinkSync` itself. A path-based
    unlink cannot be made race-free with the filesystem APIs Node exposes — there is no `funlinkat`, and
    `renameSync` has the identical defect because its source is also resolved by path. If it fires, two
    processes believe they hold the same item lock.

    So this is **not** a false positive and it is **not** being suppressed. It is recorded as work:

    &gt; **`081M129GPP9087G0R000G7837F`** — *bus/claim.ts stale-lock reclaim needs a protocol that does not
    &gt; unlink by path*

    with the consequence, the likelihood, and three candidate protocols written down: advisory
    `flock`/`fcntl` (airtight, needs a dependency — a supply-chain decision), directory locking via
    atomic `mkdir` (no new dependency, benign failure mode), or reclaim performed only by the next
    acquirer (no bystander ever deletes another process's lock).

    None is chosen here on purpose. Choosing a locking protocol for a live mutual-exclusion primitive
    under scanner pressure is how a low-likelihood race becomes an outage. The code is better than it
    was, the residue is named with its blast radius, and the decision is available to be made
    deliberately by whoever owns that item.

    Resolving this thread because the finding has an owner and a record, not because it stopped being
    true.

fix(bus): verify inode identity before reclaiming a stale lock

CodeQL flagged the fd fix's remaining half, and it was right — this is the
serious one.

`openSync(lp,"r")` + `fstatSync(fd)` made the READ consistent: the holder PID and
the mtime now come from one inode. But `unlinkSync(lp)` resolves the path AGAIN.
If the holder releases and a different process acquires between the judgement and
the unlink, the path names a NEW, LIVE lock — and the reclaim deletes it. Two
processes then believe they hold the same lock. That is mutual exclusion broken
for a process that did nothing wrong, and it is worse than the read
inconsistency the previous commit fixed.

Now the inode judged stale (held open by `rfd`) is compared against the inode
currently at the path, by dev+ino, immediately before the unlink. A replacement
becomes detectable instead of silent.

HONEST LIMIT, stated in the code rather than implied by the fix: narrowing a
window is not closing it. A path-based unlink cannot be made race-free with the
filesystem APIs Node exposes — there is no `funlinkat`. A window remains between
the identity check and the unlink. Closing it properly requires a DIFFERENT
PROTOCOL — advisory `flock`/`fcntl`, or reclaim performed atomically by the next
acquirer rather than by a bystander — which is a change to how mutual exclusion
works in this file and is not a decision a scanner finding should make. Flagged
rather than quietly declared solved.

So this commit makes the common failure detectable and leaves the rare one
documented, which is the honest split. If the lock protocol is revisited, this
comment is where the requirement is written down.
