## Description

`shard store + derived index` went red on main:

    docs/github/prs/manifest.jsonl has been behind the shards for longer than the
    180-minute repair bound (MEASURED from the oldest unreconciled shard's
    fetched_at, not assumed from the schedule), so the serialised repair writer
    (agent-heartbeat.yml, soraya archive duty) has stopped landing.

The detector is right and its remediation is the one printed:
`bun src/Core.TypeScript/forge-host/github/derive-pr-manifest.ts --write`. The
cause is upstream — the heartbeat lanes wedged for much of today, and the
serialised writer is one of the duties that rides them — so this repairs the
artifact, not the lane.

WHAT CHANGED, measured rather than described:

  * 10 PRs added, all of them today's merges: 15636, 15808, 15816, 15830, 15831,
    15832, 15835, 15836, 15837, 15840.
  * 67 rows rewritten in place, every one of them moving `fetched_at` BACKWARDS
    and re-pointing `commit_sha` at the shard that actually backs the row.
  * 0 rows with a semantic field change — `state`, `merged_at`, `title`,
    `archive_path` and `head_ref` are byte-identical across all 67.

The backwards movement is the correct direction and worth stating so it is not
read as data loss. The manifest is DERIVED — `manifest = f(shards)` — so a row
whose `fetched_at` ran ahead of every shard had drifted ahead of its own source.
Re-deriving puts the provenance back on the shard that carries the content, and
the content itself does not move.

A note on how this was verified, because the first reading was wrong. A second
`--write` printed `already current (13301 entries)` while `git status` showed the
file modified, which looked like the tool contradicting itself. It was not: the
message came from a run that found the file already rewritten by an earlier one.
A single controlled run from a clean tree prints `rewritten from 13301 shards`
and produces exactly this diff. The suspected defect was mine, not the tool's.
