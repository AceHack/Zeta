## Description

## Summary

Closes `081KZZZH24H087G0R002TXQA15`. For any honest sender,
`blockSeq = floor(seq/8)` and `blockPos = seq%8`. Both were still
carried on the unauthenticated header and trusted independently:
`seq` drove NACK/desync, `blockSeq` keyed `recvBlocks`, `blockPos`
selected the slot. A peer could hold `seq` monotone and write any
slot of any block. CRC-32C does not close this — the packet is
well-formed and lying about where it belongs.

Fix: derive both at the two use sites (`blockAddressOf`). The fields
stay on the wire for honest senders; they are no longer an address.

- **ULT-36**: seq 0..7 with lying `blockSeq`/`blockPos` still deliver block 0
- **ULT-17** still generates independent fields (NACK-amplification property); deriving does not change that path
- **ULT-24** still pins `addToBlock`'s out-of-range refusal on the helper itself
