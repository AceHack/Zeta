## Correction to the framing this lane opened with

The brief read `.claude/rules/culture-invariant-by-default.md` as "canonical collation chosen and **never enforced**." That is **half wrong, and the half matters**: the canonical collation *is* implemented in all four oracles and has been since 2026-06 (`Collation.binary` / `UnicodeCodePointComparer` / `stringCompare` / Rust's native `Ord`), with a SQL-Server-styled catalog already in place from Aaron's own 2026-06-07 decision doc. So this is neither a greenfield decision nor a repo-wide migration. The real gaps are narrower, and both are now measured.

## The SQL Server half — the trap was real, and worse than suspected

I verified rather than inherited the brief's claims. `BIN` vs `BIN2` is **confirmed verbatim**. The astral question resolved against the naive answer:

| SQL Server collation | storage | order | equals ours? |
|---|---|---|---|
| `Latin1_General_BIN` | `nvarchar` UTF-16 | first char by code point, then **raw bytes** | no |
| `Latin1_General_100_BIN2` | `nvarchar` UTF-16 | UTF-16 **code unit** | **no** — diverges above the BMP |
| **`Latin1_General_100_BIN2_UTF8`** | `varchar` UTF-8 | code point ≡ UTF-8 byte | **yes — this is ours** |

The decisive bit is an **entailment check, not a citation**: Microsoft labels `BIN2` "pure code-point comparison", and Microsoft separately describes its mechanism as "comparison per WCHAR based, which is 2 bytes". Per-`WCHAR` over UTF-16 *is* code-unit order, and Unicode §2.5.2 states UTF-16 binary order is not code-point order for supplementary characters. **The label and the algorithm cannot both be true** — Microsoft's own mechanism refutes Microsoft's own label. Solomon Rutzky states the same finding independently.

So the conflict the brief anticipated **does not materialise, but only because we pick the right SQL Server name**. Nothing needs to escalate on this point.

Aaron's performance criterion and the rule's correctness criterion also **converge rather than trade off**: UTF-8 byte order is `memcmp`, and it equals code-point order by Unicode §2.5.3 (quoted). Honest caveat in the doc: on .NET/TS we do not get `memcmp` for free (UTF-16 in memory), so UTF-8 byte order is the *specification* of the order, not required to be the *implementation*.

## Correction to the work-item's proposed fix — it would have made things worse

The work-item proposes comparing UTF-8 bytes via F# `compare`, evidenced by `compare [|1uy;2uy|] [|1uy|] = 1`. **That example passes under both length-first and lexicographic ordering, so it supports nothing — and the claim is false.** F# array comparison is **length-first**:

```text
compare [|65uy;65uy|] [|122uy|]  =  1     F# array: "AA" > "z"  (LENGTH first)
utf8 byte order / Rust / memcmp:    -1     "AA" < "z"
compare [65uy;65uy]   [122uy]    = -57    F# LIST comparison IS lexicographic
```

Adopting it would have **closed an unreachable astral divergence by opening a reachable ASCII one.** Found only because the differential harness caught a bug in its own reference implementation first (1.36M mismatches on the first run).

## The more serious gap: the catalog disagrees with itself on ASCII

Not the astral edge case. Two letters. Selecting the shared catalog name `"invariant"`:

```text
"a" vs "B"   .NET (F#/C#)   StringComparer.InvariantCulture  -> -1   (a < B)
"a" vs "B"   TypeScript      catalog["invariant"]             -> +1   (B < a)
```

Same name, opposite answers. Also affects `latin1_general_cs_as`, `latin1_general_ci_as`, `utf8_unicode_ci`, `utf8mb4_unicode_ci`. **This is strictly more reachable than the divergence that opened the work-item.**

It is not sloppiness: **TypeScript cannot faithfully implement `InvariantCulture`** — its only linguistic ordering is `Intl.Collator`, which is ICU-version-dependent. That yields the load-bearing conclusion, which is stronger than "prefer binary":

> **Culture-aware collations must not be members of the shared cross-oracle catalog.** Not discouraged — *excluded*. A shared catalog is a treaty: every name must denote the same relation in every oracle, and a culture-aware name cannot. It does not offer a capability; it offers a name that silently means different things per language.

That is Aaron's "culture-specific orderings should be opt-in" made precise: **opt-in means at the edge, in one process, for display — not "available as a shared name."**

## What landed

1. **Decision doc** — `docs/research/2026-08-15-canonical-collation-is-utf8-byte-order-sql-servers-bin2-utf8-not-nvarchar-bin2.md`: canonical collation named exactly, SQL Server mapping with the naming-grammar recommendation (keep `_BIN2`/`_UTF8`; drop `_SC` as a flag that is never off; do not cargo-cult designator/version), the opt-in-at-the-edge definition, and the honest cost inventory.
2. **`Latin1_General_100_BIN2_UTF8` alias** in the F#, C#, and TS catalogs — the exact name; the pre-existing `_BIN` / `_BIN2` rows now **annotate** the divergence instead of silently implying equivalence.
3. **Differential conformance tests** (F# + TS) over an alphabet straddling every UTF-8 length boundary and the surrogate boundary, against **two independently derived references**: 5,664,400 pairs, **zero mismatches**.
4. **Two named gaps as skipped tests carrying their reason** — `decide` non-conformance, and the catalog divergence. **Both verified to fail when the skip is removed** (I un-skipped, rebuilt, confirmed 2 failures, restored). A test wrapped so it cannot fail is the vacuity class; these are not that.

No golden vectors touched. No call site rewritten. `Consensus.decide` is deliberately **not** fixed here — it is generic over `'T: comparison` and "code-point order" is undefined for arbitrary `'T`, which is a design call, not a drive-by edit.
