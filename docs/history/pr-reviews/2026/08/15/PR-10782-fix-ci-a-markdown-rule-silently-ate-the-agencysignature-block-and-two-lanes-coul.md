## Description

## Summary

Two separate defects in the pre-merge AgencySignature gate. Both are proven with tests that fail without the fix.

## Defect 1 — a bare `---` silently killed trailer parsing

`git interpret-trailers` reads stdin as a commit message **with a patch possibly appended**, so a line that is `---` (or begins `--- `) is the diff boundary and everything after it is discarded. One ordinary markdown horizontal rule made a well-formed trailer block invisible, and the error text then blamed blank-line discipline — pointing a hundred lines from the cause.

**Measured on the open PR set (41 PRs, 2026-08-15): nine bodies carry a bare `---`, including all five dependabot PRs.**

### Correction to the brief: `--no-divider`, not trailing-paragraph extraction

The brief proposed extracting the trailing paragraph as the principled fix and asked me to evaluate it. I found a better one, and the reason is a measurement I made before choosing:

```text
$ git commit -F msg-with-bare-dashes-above-the-block
$ git log -1 --pretty='%(trailers)'
Agency-Signature-Version: 1
Agent: shadow
Co-authored-by: Aaron <a@b.c>          <- the block is INTACT post-merge
```

**git does not apply the divider rule to a stored commit message** — only to `interpret-trailers`' stdin. So the strict behaviour was the pre-merge gate predicting a post-merge failure *that does not occur*: it rejected bodies whose trailers the post-merge auditor reads without complaint. That reframes the fix. It is not a loosening, it is **restoring parity between the two paired instruments** — which is the only property a pre-merge gate has to offer.

`--no-divider` is git's own documented flag for exactly this (git >= 2.24). Weighed against the alternatives: trailing-paragraph extraction is surgery that reimplements a rule git already has a switch for; pre-neutralising `---` lines mangles the input to defeat a parser artifact; a native trailer parser duplicates semantics the post-merge auditor gets from git itself, and divergence there is the whole bug.

### The message now names the real cause

Live example, PR #10675:

```text
Cause:  'Agency-Signature-Version:' IS present, at line 128 of the
        body — so this is a PLACEMENT problem, not a missing block. git
        reads trailers only from the FINAL paragraph, and the final
        paragraph of this body is:
          | 🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

Also: a non-zero exit from `git` is now a TOOLING error (exit 2) instead of reading as "this body has no trailers". The old code took `result.stdout` unconditionally and could not tell a broken tool from a broken PR.

## Defect 2 — actors that structurally cannot comply

Two classes, opposite remedies.

**Our own automation — fix the workflow.** Survey (`grep -rl 'pr create|create-pull-request|pulls.create' .github/workflows/`) found exactly two PR-opening lanes we own: `pr-archive-on-merge.yml` (fixed in the open #10764 — **not touched here**) and `agent-heartbeat.yml`, whose PR call is `merge-heartbeats-to-main.ts`. **That second hole was live and unreported:** PRs #10709/#10710/#10711 are its output and all three are unsigned, passing only by grandfathering. It now emits its own block, with the credential read from `gh api user` rather than asserted — the workflow's token is `ZETA_TELEMETRY_FLUSH_TOKEN || ZETA_PR_ARCHIVE_TOKEN || GITHUB_TOKEN`, so hardcoding one would be a false claim in two of three cases.

**Third-party bots — record, never forge.** Of the three options in the brief I took **repo-side attribution (2)**, and the argument against the others is in the code:

* **Named exemption (1)** is honest but an exemption list is a place things hide — a row costs one line, says nothing, and nothing downstream can distinguish an exempt PR from an unattributed one.
* **A workflow that edits the third party's body (3)** is option 1's dishonesty with extra steps: the block lands in the squash commit indistinguishable from a self-attestation. It is the forgery, merely committed by a robot.
* **Repo-side attribution (2)** costs the person adding a row a full profile *and* its evidence, keeps the record diffable in git and attributable to whoever merged it, and prints what we know instead of only that we declined to look. The profile is never emitted as a trailer, so a self-attestation and a repo assertion are never confused.

This uses the **existing** roster at `src/Core.TypeScript/hygiene/agency-signature-identity-roster.json` (new `externalActors` section; the post-merge auditor's `humans`/`machineLanes` are untouched and disjoint), not a second registry.

### The roster is actually enforced

Given the KSK gate that was found accepting off-roster signers, the matching is exact equality on the trimmed lowercased actor — no prefix, no glob, no `endsWith("[bot]")` — and empty/absent does not match. Negative tests cover a prefix, a suffix, a different bot, a glob, a human, an empty roster, and an absent `--author-identity`.

**Keyed on `pull_request.user.login`, not `github.actor`.** The workflow also fires on `edited`/`synchronize`, so keying on the triggering actor would let a rostered actor exempt *somebody else's* PR by touching it — and dependabot touches other PRs routinely.

## Sovereign mode

The decision is `repoAssertedAttribution(authorIdentity, roster)` — pure, no forge, no network. The two inputs are plain strings (body on stdin, author via `--author-identity`), so GitHub plumbing stays at the yaml edge and a ZetaDB-native proposal lane calls the same binary with the same two strings. **No portability layer was built**; the seam already existed and the author identity only had to stop being implicit.

## Things I found and did NOT change

* **The post-merge auditor has no dependabot row and I did not add one.** Measured: zero dependabot commits in the last 800 on `main`, so what identity such a commit carries after squash-merge is unmeasured. A roster row written from a guess is the exact failure that file's own note warns about; a loud false regression on the first one is the correct outcome.
* **The post-merge auditor does NOT share defect 1.** It uses `%(trailers)` and falls back to a regex over the raw message; both survive a `---`. No change needed, stated because "same root cause" was the obvious assumption and it is wrong.
* `pr-archive-on-merge.yml` — #10764 is open and owns it.
* v1/v2 dual-accept is unaffected: the repo-asserted profile carries no version key because it is not a versioned self-attestation.

## Cost paid honestly

The first draft of the tests spawned a subprocess per case and **introduced a flake** — an unrelated real-git test's 5s `beforeEach` hook timed out in 2 of 6 full-directory runs, against 0 of 6 on `origin/main`. Rewritten to call `main()` in-process (one CLI smoke test still covers the process boundary): 0 of 8 runs flake, and the suite is 4x faster.
