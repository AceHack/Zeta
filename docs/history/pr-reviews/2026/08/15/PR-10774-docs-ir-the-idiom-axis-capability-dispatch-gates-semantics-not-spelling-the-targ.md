## Description

Aaron's 2026-08-15 intent has two halves — the language should **feel** like a C#/F# blend, and generated code must **take advantage of each target's native features**. Testing the second against the v2 design (`2026-06-14-zeta-language-ir-compiler-v2-…`) turned up a gap more useful than the design would have been. Docs only: **one file**, no code, no vectors, no IR touched.

## The reading under test

> "If capabilities are dispatch axes, the target language is another dispatch axis."

**Right about the mechanism, incomplete about the domain.** Multiple dispatch is n-ary and CLOS/Julia resolve by *specificity*, which is exactly the preference order idiom needs — that part transfers and it is not a small thing. But every capability §4 names (algebra, scheduling, collation, precision, representation) is a property of the **source type**, and the dispatch is a **soundness gate**: emit `tree_fold` for a non-commutative type and the Merkle roots diverge. Idiom is a **preference order over semantically-equal emissions**, where the wrong pick still byte-locks.

Two facts, verified at `58c62e25a`:

* `rg -ci 'targetCapabilit|backendCapabilit'` over `tests/cross-verification/_harness/` and `src/Core/` → **0**
* no emission site anywhere offers more than one candidate — `patterns.find(p => p.opType === op.op)` takes the first and only match. **A dispatcher with one applicable method is a function pointer.**

## The larger obstruction is the IR's *level*, not the capability model

Idiom is destroyed by **premature lowering**: you cannot recover `.iter().map().sum()` from a lowered index loop, because the fact that it *was* a fold is gone. `ZetaIrV1`–`V4` are a straight-line list of six scalar bit-ops (`mul`, `xorshr`, `rotl`, `xrotxor`, `xshrxor`, `add`) — no fold, no sequence, no lambda, no type, no capability field. **There is nothing an iterator chain could be emitted *from*.**

So the honest statement is not "the capability model cannot express idiom" but: *the capability model could carry idiom, but there is no IR content for it to carry idiom about.*

The fix is the discipline the v2 doc already anchors (§7, nanopass — Sarkar/Waddell/Dybvig 2004) without applying here:

> **Idiom selection is lowering-arrest.** Stop lowering at the highest IR level for which the target declares a matching capability; continue only for targets that lack it.

Rust stops at `Fold`→`Iterator`, C# at `Fold`→LINQ, **Go keeps lowering to a loop because the explicit loop *is* idiomatic Go.** One IR, one traversal, five different-shaped idiomatic outputs, no per-target emitters. That Go row is why a *structural* predicate ("no manual loop where an iterator would do") is wrong as a rule — idiom is target-relative, so only a target-local authority can judge it.

## The measurement problem — same root cause

Because idiom has no correctness direction, the byte-lock is **structurally incapable** of catching an idiom regression. Not a gap in the golden vectors — a property of what they measure. Any attempt to make them sensitive to idiom is an attempt to make them sensitive to what they are defined to quotient out. (No overlap with the behavioural-adequacy agent; orthogonal by construction.)

**Proposed bar:** the target community's own linter/formatter, **pinned**, over a **committed** generated corpus, with the hand-written peer as a **differential control** — `lints(generated) ⊆ lints(hand-written)`, plus `formatter --check` exit 0. Differential rather than absolute because absolute would fail on things the hand-written peer also does.

### Demonstrated (clippy 0.1.87 / rustc 1.87.0, gofmt, ruff)

| lane | tool | generated | control | verdict |
|---|---|---|---|---|
| Rust straight-line | clippy default | 0 | 0 | tie — **cannot fail here** |
| Rust straight-line | clippy `pedantic`+`nursery` | 10 | 10, identical classes | inclusion **holds** |
| Rust straight-line | `rustfmt --check` | exit 0 | exit 0 | tie |
| **Rust Rx lens** | clippy default | **`unused_imports`: `use futures::stream::{self, …}`** | no peer | **generated-only defect** |
| **Python** | `ruff check` | **`EXE001` shebang w/o exec bit** | — | **generated-only defect** |
| Go | `gofmt -l` / `go vet` | empty / clean | — | pass |
| F# / C# | — | — | — | **no bar exists today** |

Both defects compile, run, and byte-lock identically; the Rust one would be **rejected outright** by any crate with `#![deny(warnings)]`. Neither is visible to any behavioural test in the tree.

### Honest limits, named rather than hidden

* **Default clippy reports zero** on the generated Rust. I did not infer that the linter was inert — canary: `z = z ^ y` warns (`assign_op_pattern`), `z = z ^ (z >> 30)` does not, because clippy declines when the assignee reappears in the RHS operand. So default level is a **check that cannot fail** on this corpus and must not be the gate.
* **The corpus is degenerate, not the bar.** Straight-line scalar `u64` arithmetic has no collection, no ownership, no trait, no iterator choice. *A green bar over a corpus with no idiom surface is the vacuity class.* Fixed by growing the IR's level, not by better linting.
* **Performance is sound but incomplete** — most idiom choices are perf-neutral (`z ^= x` ≡ `z = z ^ x` in machine code), so it convicts and never acquits. Secondary signal only.
* **Structural predicates** (already in the tree: `expect(rs).toContain(".map(|z|")`) are regression *pins*, never the measure — written by the emitter's author, so they can only pin an idiom somebody already thought of, never discover one nobody did. Neither defect above is findable that way.

### The cheapest real rung

**F# and C# have no mechanical idiom bar today** — the artifacts are loose `.fsx`/`.csx` scripts and the repo's analyzer floor (`CA1304/1305/1307/1310/2007` at **error** level) is project-scoped. `dotnet fsi` exits 0 on a compile error, so a load-smoke check would be *worse* than nothing. **Emitting into a real `.fsproj`/`.csproj` converts the existing floor into a hard generated-code gate at zero new tooling cost** — and those five rules are the exact class that produced `081KT07NV0008QG0R001YDB73K`.

Notably, **the un-reified residue and the idiom axis are the same thing.**
3. **The brief's "orthogonal to adequacy" is right and understated** — the byte-lock cannot *in principle* be extended to cover idiom.

## Survey, so the next rung is not re-derived

`ZetaIrV1`→`V4` is a **working** freeze-and-evolve chain (each version adds ops *proved* outside the prior grammar, under a bumped tag, in a new module, predecessors byte-identical) — rarer than the design. The 1st Futamura projection is built (`codegen-specialize.ts`). **No generated source is committed anywhere** (`rg -l 'GENERATED by codegen' --glob '*.rs'` → 0; every `_gen/gen.rs` is a hand-written oracle) — that is the blocking prerequisite for any linter gate, and it is small.

And the one that should be read directionally rather than as alarm: **50 hand-written `emit*` functions** across the codegen harness, ≈ 7 lenses × 7 targets, growing multiplicatively. That is the **Itron negative anchor** — *"no good composability, so it was plumbing everywhere"* — reproduced at 1/20000 scale **inside the artifact built to refute it**. Every one of those functions was the right call at the time; the derivative is what's wrong, and the fix is the project's own principle.
