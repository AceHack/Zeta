## Description

## The rung

*"generate the code for every language from our IR and compare it to hand written code."*

`cross-verify-ir.ts` already generates N lanes from one IR, runs them, and byte-compares. That
proves the **generators agree with each other** — which a wrong IR satisfies exactly as well as a
right one, because every lane is downstream of it. N implementations generated from one spec
agreeing is **one observation counted N times**.

The **hand-written ports** are the independent oracle. Each primitive dir carries five
hand-authored language ports (`_gen/gen.{fsx,csx,go,py,rs}`) that re-derive the algorithm from its
published reference with no IR in the loop. Nothing compared against them. This PR does, and the
comparison found two defects.

***

## What it found — executed, not inferred

### 1. Width was ignored in four of seven emitters

`emitTypeScript` / `emitFSharp` / `emitCSharp` / `emitRust` hardcoded 64-bit words
(`(1n<<64n)-1n`, `uint64`, `ulong`, `u64`) regardless of `ir.width`. `emitPython` / `emitGo` /
`emitQSharp` honoured it. So **one IR produced four lanes computing at width 64 and three at width
32**:

| lane | `hash.fmix32` at `x-1` | |
|---|---|---|
| generated TypeScript | `7340060871154608311` | wrong (64-bit) |
| generated Python | `1364076727` | correct |
| hand-written F#/C#/Rust/Python/Go | `1364076727` | the independent oracle |
| committed golden vector | `1364076727` | |

The Go lane did not even compile — the canonical input list was a fixed u64 set:
`./gen.go:33:16: cannot use 18446744073709551615 (untyped int constant) as uint32 value in struct literal (overflows)`.

### 2. The "total interpreter" was not total

Every emitter was shaped `if (op.op === "mul") {...} return <xorshr>`, so **any op outside v1's
two-op grammar silently became `xorshr undefined`** rather than being refused. Feeding
`rng.lcg64_mmix` (`mul` + `add`) to the pre-fix generator:

```
F#      z <- z ^^^ (z >>> undefined)
Rust    z = z ^ (z >> undefined);
Python  z = (z ^ (z >> undefined)) & MASK
Go      z = z ^ (z >> undefined)
C#      z = z ^ (z >> undefined);
```

Six of the nine committed IRs use `rotl` / `add` / `xrotxor` / `xshrxor`.

**Which side was wrong: the generator.** The IRs are right — they carry `width`, and the
hand-written ports plus the committed goldens confirm their op lists. Both defects were invisible
for one reason: the only IR this generator was ever tested against is splitmix64 — width 64,
`mul|xorshr` only. **One of nine IRs was being generated correctly.**

***

## The fix

One shared v1..v4 op grammar rendered through an explicit **total switch that throws at generation
time** on an unknown op, and a per-language word type derived from `ir.width`. Widths 32 and 64 are
supported; any other is **refused**, not approximated. Canonical inputs are width-derived, and their
ids coincide with the committed vector ids at each width so the diff is key-for-key.

All nine IRs now emit code that compiles and agrees across ts / python / go / rust; F# and C# lanes
spot-checked by execution (`fmix32` width-32 → `1364076727`; `nasam` xrotxor/xshrxor →
`11248308645848015117`).

## The oracle — `_harness/ir-vs-handwritten.ts`

Which bar applied is reported **per primitive and per lane**:

- **bar 1 — behavioural equivalence, fresh execution.** Emits from the IR via the repo's real
  generator, **runs it**, byte-compares against the committed hand-written ports. Fresh execution
  matters: the `<lang>-output.json` files are artifacts, so a stale one would otherwise pass a
  comparison that never re-ran anything.
- **bar 2 — differential / property.** A seeded corpus of 2000 inputs (width edges, every power of
  two, pseudo-random, deterministic seed — no ambient entropy) run through the **same committed
  `_gen/gen.py` with only its `INPUTS` literal rewritten**, so the mixer executed is the
  hand-written one verbatim, not my transcription of it.
- **guard.** The unmodified `gen.py` must first reproduce its own committed artifact byte-for-byte,
  or the whole comparison is a hard failure — never a pass on bytes nobody re-derived.

Bar 3 (structural/AST) was not attempted: the languages emit different word types by design, so an
AST diff would compare shapes that are *supposed* to differ. Behavioural equality is the property
under test.

| primitive | width | hand-written ports | committed vectors | differential inputs | verdict |
|---|---|---|---|---|---|
| `splitmix64` | 64 | fsharp, csharp, rust, python, go | 10 | 2000 | agree |
| `fmix32` | 32 | fsharp, csharp, rust, python, go | 10 | 2000 | agree |
| `fmix64` | 64 | fsharp, csharp, rust, python, go | 10 | 2000 | agree |

| `xoshiro256ss` | 64 | fsharp, csharp, rust, python, go | 10 | 2000 | agree |
| `lcg32_glibc` | 32 | **none** | — | — | **no independent oracle** |
| `lcg32_numerical_recipes` | 32 | **none** | — | — | **no independent oracle** |
| `lcg64_mmix` | 64 | **none** | — | — | **no independent oracle** |
| `murmur3_32_tail` | 32 | **none** | — | — | **no independent oracle** |

**5 of 9 IRs have an independent oracle.** The other four have exactly one lane, generated from the
IR, and their `vectors.yaml` expected values were produced by that lane — `nway-diff.ts` accepts them
at `minOracles = 1`, i.e. the IR checked against itself. That set is **declared** and asserted equal
to the directory scan **in both directions**, so a new bare IR fails, and a bare IR that grows a port
also fails (stale declaration). Assertions are per primitive and fail **by name**; there is no
`>= N agreed` numerator to hide a zero in.

### What this does and does not establish

It establishes that for those five primitives the IR is behaviourally adequate well past the ten
committed vectors — 2000 inputs including every power of two and both width edges. It does **not**
establish anything about the four bare ones, and it does not touch the IR's *anchors*.

## Two unchecked-anchor observations (recorded, not resolved)

Both are in the bare set, which is why nothing could notice them. Both IRs compute exactly what
their op lists say — neither is an arithmetic bug. What is unverified is whether the cited human
anchor **entails** those ops.

- **`rng.lcg32_glibc`** is `(x * 1103515245 + 12345) mod 2^32`. glibc's TYPE_0 `rand()` reduces
  **mod 2^31** — `((state * 1103515245) + 12345) & 0x7fffffff` (`stdlib/random_r.c`). Under that
  reading **4 of the 10 committed vectors differ** (`x-2`, `x-3`, `x-6`, `x-7` — exactly the ones
  whose product exceeds 2^31). The mod-2^32 form matches the ANSI C example `rand()` instead.
- **`hash.murmur3_32_tail`** is `rotl(h,13); h = h*5 + 0xe6546b64`, which in MurmurHash3_x86_32 is
  the **body-block** mix-combine. The *tail* in that algorithm is the leftover-bytes path and
  contains none of these three ops.

Not resolved here: renaming a committed generator changes its derived ZetaId and its golden bytes,
which is an owner's call and not a side effect of a harness PR.

## Also corrected: a vacuous test in `codegen-from-ir.test.ts`

The test named *"generated TS oracle execution produces golden-matching output"* **did not execute
the generated oracle**. It re-implemented the fold inline and checked *that* against the goldens —
so it passed for any emitted text whatsoever, including text that does not parse. It now writes the
emitted program, **runs it**, and asserts on the file the program wrote. A width-32 row and a
`rotl`+`add` row were added, so neither defect can return untested.
