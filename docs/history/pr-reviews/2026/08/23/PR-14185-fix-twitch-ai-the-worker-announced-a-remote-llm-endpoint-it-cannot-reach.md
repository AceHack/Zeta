## Description

## Summary

`lint (TS)` went red on every PR at `src/apps/twitch-ai/src/swarm.worker.ts(40,24)`
after #14159's restore-after-revert. #14169 fixed the type error the cheap way —
`SwarmController.init` takes `dropRate = 0`, so it deleted the
`{apiKey, baseUrl, model}` argument. That was the correct typing fix and it is
**not the whole truth**: deleting the argument left the surrounding branch intact,
so the worker still logged

```
[SwarmWorker] Using remote LLM endpoint: <baseUrl>
```

for an endpoint it has no way to reach — and `local mock LLM fallback` for a
backend that is neither chosen-local nor a mock.

This PR makes the code stop claiming a capability it does not have.

## What was measured, not inferred

`SwarmController.init()` builds all four backends itself:

```ts
const config = getPersona(hat.personaName);
openAiCompatBackend(
  { baseUrl: config.harness.host ?? "http://localhost:11434",
    apiKey: "dummy",
    model: config.preferredModel },
  transport,
);
```

Host and model come from `service/persona-registry`; the key is the literal
`"dummy"`. There is **no seam** through which a payload `apiKey` / `baseUrl` /
`model` could reach a backend. The comment #14169 left in place says exactly
this — and the log line four lines above it contradicted it.

## Which fix this is, stated plainly

**Option 1, completed.** **The capability remains absent.** This PR does not wire
the LLM settings through. Doing that means giving `init()` a per-node
host/model/key override, i.e. changing the contract `persona-registry` owns — a
design decision for whoever owns `twitch-ai`, not for a gate-unblock.

What changes is honesty. The page still posts those settings, so the truthful
report is a `console.warn` that they are **ignored**; dropping them silently
would be the same vacuity in quieter clothes.

## Register

A log line announcing a capability that does not exist is the vacuity class in
user-facing form — the same defect as a green square for a check that did not run.

## Not in this PR

The `test (TS hermetic)` red (10 failing tests under `db/mutation-findings/`) is
**a separate cause with separate owners already on it** — #14165 (Riven) and
#14173 (vera). Root cause for the record: #10559 relocated
`.claude/hooks/harness.test.ts` to `src/Core.TypeScript/claude-hooks/` because
bun does not discover tests under dot-prefixed directories, but the sampling frame
in `effective-agent-count.ts` admits a source only if a `.test.ts` sits in **the
same directory**. When the mutation lane drew `.claude/hooks/harness.ts` at tick
14532 for alexa/otto/soraya, those three draws fell outside the frame and
`assertFrameContainsDraws` threw — by design; it asserts rather than filters, so a
wrong universe cannot produce a confident number. That check is doing its job.
I am not duplicating either PR.

`test (TS hermetic)` is **not** on `gate (required)`'s `needs:` list, so it never
blocked the queue; `lint (TS)` (via `lint-typescript`) is, and did.
