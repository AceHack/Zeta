## Description

fix(deps): regenerate bun.lock for the twitch-ai workspace — main has been red for every PR since #14292

WHAT IS BROKEN, AND IT IS MAIN, NOT ANY ONE PR
----------------------------------------------
#14292 added a `workspaces` entry to `package.json`:

    "workspaces": ["src/apps/twitch-ai"]

and did not regenerate `bun.lock`. Every job in this repository that installs TS
dependencies runs `bun install --frozen-lockfile`, and that now refuses:

    error: lockfile had changes, but lockfile is frozen

REPRODUCED ON A CLEAN CHECKOUT OF origin/main at a3b7f458 — no PR, no merge
commit, no branch involved. `bun install --frozen-lockfile` exits 1. So this is
not base staleness and merging main into a branch does not clear it; the
committed lockfile does not describe the committed package.json, and only
regenerating it can.

The blast radius is every PR: `lint (markdownlint)`, `lint (yaml/k8s)`,
`lint (tick-history order)`, `lint (TS)`, `test (TS hermetic)`,
`lint (bash retirement inventory + hygiene unit tests)` and `cross-verify` all
fail on their first install step. Seen identically on #14296 and #14298 —
two unrelated diffs, one symptom, which is what makes it structural.

THE FIX IS `bun install`, AND NOTHING ELSE
-------------------------------------------
The diff is exactly the mechanical consequence of the package.json edit:

  + the `src/apps/twitch-ai` workspace entry and its three devDependencies
  + the `twitch-ai@workspace:src/apps/twitch-ai` resolution
  ~ root `@types/node` 25.6.0 -> 26.2.0 (twitch-ai asks for ^26.2.0), with
    `undici-types` ~7.19 -> ~8.3 following it
  + `bun-types/@types/node` pinned at 25.6.0 in the nested position, so
    bun-types keeps the version it declares

No dependency was added, removed or chosen here. Verified after regenerating:
`tsc --noEmit -p tsconfig.json` is CLEAN repo-wide across the @types/node bump,
and `bun install --frozen-lockfile` exits 0.

WHAT WAS NOT DONE, on purpose
------------------------------
`--frozen-lockfile` was not relaxed anywhere. It is refusing to install something
the committed lockfile does not describe — the check working, loudly and exactly
as designed. Loosening it to get a green tick would convert a real refusal into a
vacuous pass, which is the failure class this repository is built to refuse.

Noted, not fixed here: `src/Core.TypeScript/cluster/single-node-readiness.test.ts`
"the repo audits clean against its own ledger" takes 6.9s against bun's 5s
per-test budget on this machine. Measured on plain origin/main with only this
lockfile change applied, so it is pre-existing and unrelated — but it is a flake
waiting for a slower runner and it deserves its own timeout argument.
