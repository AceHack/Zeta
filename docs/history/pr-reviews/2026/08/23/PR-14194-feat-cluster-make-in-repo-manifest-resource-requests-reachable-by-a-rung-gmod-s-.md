## Description

Aaron: *"how do we make these resource settings reachable so we can set them?"*

`gmod`'s `statefulset.yaml` hardcodes `requests: { cpu: "1", memory: "2Gi" }` — **1000m, a sixth of the tree's 6166m CPU** — and `--resource-profile dev --apply` could not touch it. This makes it reachable, and closes the class.

## The defect was one line, in the wrong module

The standing account was that a git-path Application has no `valuesObject`, so no rung can reach it. The catalogue said so in gmod's own evidence string.

**That was true of the renderer and false of the applier.** `applyResourceProfile` and `verifyResourceProfileApplied` have always addressed `path` + `docIndex` + `requestsField` as a dotted path into an *arbitrary* manifest — they never cared that the file was an `Application.yaml`. Only `overlayRung`, the render-side reader, required the `spec.source.helm.valuesObject.` prefix and filed everything else as `unoverlayable`.

## The enumeration you asked for

**12 git-path Applications. 5 carried nonzero hardcoded requests: 1270m CPU / 3322Mi, none rung-reachable.**

| Application | manifest | CPU | memory |
| --- | --- | ---: | ---: |
| `game-hosting/gmod` | `statefulset.yaml` | **1000m** | 2048Mi |
| `cdi` | `cdi-operator.yaml` doc 7 | 100m | 150Mi |
| `platform` | `controller.yaml` + `portal.yaml` | 100m | 160Mi |
| `agent-memory` | `statefulset.yaml` | 50m | 64Mi |
| `kubevirt` | `kubevirt-operator.yaml` doc 9 | 20m (10m × 2) | 900Mi |

Plus a **latent** set nobody had counted — four coordinates on `replicas: 0` workloads carrying **5100m / 17536Mi**, of which `vllm` alone is 4000m / 16Gi. They schedule nothing today. That is a reprieve, not a fit.

## The option taken, and why not the other three

All three offered options add a **second way to configure resources**. What shipped reaches option 1's goal through the mechanism that already exists: **a `resourceClaim` whose coordinate is a path into the Application's own manifest.** Same catalogue, same `--apply` verb, same two-rung ladder, same validators — only the coordinate's *address space* differs, and it differs because ArgoCD forces it to.

- **Kustomize patches** would need a `kustomization.yaml` per directory, which flips ArgoCD's source type from `directory` to `kustomize` and makes the existing `directory.include` globs inert. That is a change to *what metal applies*, to buy a dev-rung number — and it needs a second rendering engine in the checker.
- **A Helm wrapper** is the most uniform on paper and the most churn in practice; templating names risks renaming live resources on metal. Worth revisiting per-app if one grows.
- **A generator** was rejected for the reason the brief gives. Note the shipped option is *not* that: no build step, no generator owns the file, the manifest stays hand-written — exactly as `valuesObject` is today — and the existing checker reconciles catalogue against render at both rungs, so a hand-edit that disagrees goes red.

## Three governed, and 120m deliberately refused

`cdi` and `kubevirt` are reachable by the new mechanism and **were governed for one draft, then backed out.** Both manifests are vendored byte-for-byte from upstream, and `single-node-budget.json` says of kubevirt's, in writing, that editing it *"would make the checked-in copy diverge from the cluster it documents, which is a worse lie than this one."*

**Reaching a file is not a licence to edit it.** A CPU budget is not grounds to overturn an invariant another artifact states. Those 120m are acknowledged with that reason, and a test pins the refusal so a later "finish the job" edit has to argue with it.

## `metal` is untouched — checked three ways

Every new row's `metal` value **reproduces the literal already in the manifest** rather than re-deciding it:

- `--resource-profile metal --verify` → `manifests match resource profile "metal"`
- catalogue arithmetic: metal dev-lane **5231m / 13475Mi**, all-47 **9256m / 21810Mi** — identical to before
- full re-render at both rungs: metal **13291m / 30647Mi**, unchanged to the millicore, while dev moved 10201m → 9226m

Memory is unchanged at **both** rungs for every row: CPU is compressible and memory is not, so the cut only touches the axis where being wrong throttles a pod instead of evicting it.

One manifest byte changed: gmod's `memory: 2Gi` → `2048Mi`. Same quantity (both parse to 2147483648 bytes), written so metal is byte-verifiable by the existing string-equality check rather than loosening that check into quantity-equivalence.

## The falsifier — run, not reasoned about

A worktree at `origin/main` (`ba965f8636`) rendering gmod at both rungs:

```
gmod rendered CPU at "dev"   = 1000m
gmod rendered CPU at "metal" = 1000m
overlayRung has manifestOverlays? false
```

After: **100m at `dev`, 1000m at `metal`, from the same file.** Pinned three ways — live tree, hermetic (a synthetic git-path app in a temp dir), and as a *refusal*: a coordinate that misses fails the render with `manifest-overlay-missed` rather than rendering the committed value and looking like a rung that was applied.

The old snapshot had already been reporting this in its own vocabulary: `[inert-rung] game-hosting/gmod @ dev->metal: its governed rows cut 900m ... and the render does not move by a single millicore`.

## The class-closer

`unreachableGitPathRequests` refuses a **new** raw manifest carrying a hardcoded request no `resourceClaim` names — per *container*, not per Application. It reads the **tree**, not the snapshot, so a manifest that grows a request fails on the PR that adds it instead of waiting for the next `--measure`.

The six remaining are acknowledged with reasons and lift conditions, in two classes: four `replicas: 0` (**cannot** be governed — `pods` is validated `>= 1`, so a row would overstate every rung by a whole pod) and two vendored (**will not** be governed). **The replica count is in the finding key**, so scaling `vllm` to 1 makes the acknowledgement STALE and the new count OPEN — both exit 1, and 4000m cannot arrive quietly.

**The lane count does not drop, and why matters: CPU stopped being the binding axis; disk still is** (8.50Gi/lane at `freeDiskGib: 14`). What moved is that lane-2 sat at **99.1% of its 2125m budget — a 19m knife edge** — and now has 719m of slack.

`--resource-profile dev --budget`: the dev lane goes **2906m → 2006m and FITS** 2500m with 494m spare. `acknowledgedLaneBudgetShortfall` is now **empty** — retired by the arithmetic moving, not by deletion. That entry priced two ways out, both about gmod, and named a third as the maintainer's call: *"whether the committed tree should carry `dev` at all or grow a per-substrate override point."* This is that third one.
