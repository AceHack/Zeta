## Description

## The observation

`Zeta.Tests.Storage.SpanSerializerTests."single-entry Z-set round-trips with positive weight"` threw
`System.ArgumentOutOfRangeException : Arg_ArgumentOutOfRangeException` at `src/Core/Serializer.fs:70`
on **windows-2025** — gate run [32646515868](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/32646515868),
job 97211695103, head `4ac632b8`. Non-blocking (Windows legs are `continue-on-error`), which is why it can persist.

**I did not reproduce it, and this PR does not claim to fix it.** What it fixes is that the failure was
**diagnosis-free**, and the reason it was: both hot-tier readers trust an int32 they read *off the buffer*.

## What changed

| | before | after |
|---|---|---|
| `SpanSerializer.Read` | slices on the wire count directly | count checked against the bytes that follow, in `int64` so a hostile count cannot overflow the multiply negative; refused with `invalidOp` naming **both** numbers |
| `TlvSerializer.Read` | `Array.zeroCreate count` runs **before** any bound on `count` is known — 8 bytes of header could ask for a 2^31-entry array | bounded by the minimum entry width (4 B keyLen + 8 B weight = 12 B); refused before anything is allocated |

`FsPicklerSerializer.Read`, 100 lines down the same file, has always bounds-checked its length prefix.
The two hot tiers were the odd ones out.

## Evidence (fails before / passes after — not a streak of green)

Measured by reverting `Serializer.fs`, rebuilding, and re-running:

| new test | pre-guard result |
|---|---|

Also added: `SpanSerializer.Tests.roundTrip` now checks the wire invariant *between* write and read, so the
next occurrence reports `srcCount / header / written / need / hex` instead of an opaque throw; and a
concurrency falsifier (4 threads × 20k round-trips, invariant checked on every one) that replaces the
*argument* that this path is thread-clean with a *check* of it.

Full F# suite locally: **5491 passed, 0 failed** (`dotnet test tests/Tests.FSharp -c Release`).

## What was ruled OUT (each by a measurement)

1. **The buffer-pool hypothesis.** Audited all 16 `Pool.Freeze` sites in `src/Core`: none freezes a *rented*
   array. `ZSet.ofSeq` rents → fills → `Pool.FreezeSlice` (exact alloc + copy) → returns; ownership holds
   everywhere. `Shard.fs:178` looks like a violation and is not — it freezes an `AllocateExact` buffer.
   Independently: a pool race corrupts entry **content**, never the count header, so it cannot produce this
   exception shape.
2. **Concurrency in the serializer path.** A direct stress harness (`ofSeq` → `Write` → wire-invariant check →
   `Read`, plus `ArrayPool` churn) ran **~250 M round-trips** across 8–16 threads on macOS arm64 in four
   configurations — default, `gcServer=1`, `TieredCompilation=0`, `JitStress=2` — with zero breaks. A
   windows-2025 x64 run of the same harness (60 s × 8 threads) was also clean.
3. **Single-threaded arithmetic.** `Write` derives the header count and the payload length from the *same*
   span local, so they cannot disagree; the test's writer is a fresh `ArrayBufferWriter<byte>` — GC-allocated,
   unpooled, unshared.

Still open, recorded in `081M0QPAJG3087G0R002BGJG8H`: for the exception to fire the header must disagree with
the bytes behind it, and nothing single-threaded can do that. Live candidates are below the F# — memory written
by a neighbour, or windows-x64 codegen (`TieredPGO` + `ServerGarbageCollection` are on repo-wide, and in the
full suite this method is hot enough to be tier-1 rejitted, which it never is in isolation — the one
non-scheduling difference between "full suite" and "runs alone").
