## Description

## The question, and why the answer is neither

> Is the 60-minute cap being hit because the model grew, or because the runner slowed?

**Neither. The proof step never ran** — not once in the last 40 runs. The whole cap is
consumed by the *toolchain install*, and `tlapm` is never reached.

The totals (33 cancelled + 7 failed / 40) do not show this. The **step boundaries** do:

| step | run 32605525115, 2026-08-22 | |
|---|---|---|
| Cache opam switch | 23:54:15 → 23:54:15 | 0s — `Cache not found for input keys` |
| Install toolchain | 23:54:15 → **00:54:17** | **cancelled at the 60m cap** |
| Verify TLAPS toolchain | — | skipped |
| **Prove all TLAPS obligations** | — | **skipped** |

### Evidence that the model did not grow

- `NciSafetyProofs.tla` / `NciNonUrgencyProofs.tla` are **untouched since 2026-06-13**
  (#8053, a directory relocation). 76 + 58 lines.
- On the last green run (28550177205, 2026-07-01) the entire `--all` proof took
  **one second**: `22:09:01 → 22:09:02`. The prover is not the cost and never was.

### Evidence that the runner did not slow

- Same green run: cache **HIT** (16s restore) → install 3m09s → total 16m.
- Every run after it: cache **MISS**, cold source-build of `tlapm`.
  The cold build was already 11m36s on 2026-07-02 and reached the same Isabelle
  stage at ~10 minutes on 2026-08-22. The machine is fine; the build does not finish.

## What actually broke, in order

**1. The cache key changed on 2026-07-02.** #9188 *created*
`src/Core.TypeScript/ace/setup-realizers/from-opam-git.ts` — a path inside this
workflow's `hashFiles(...)` cache key. The key changed the instant the file existed,
and every run since is cold.

**2. The cold build hangs at one identifiable place.** `dune build -p tlapm` runs the
upstream `deps/isabelle` rule (fetches + builds a ~1GB Isabelle). A child in that tree
leaves `O_NONBLOCK` set on the **shared** stdout descriptor; dune then writes the
action's multi-MB captured output to it and hits `EAGAIN`:

- **2026-07-02** (run 28619870340) — surfaced as an OCaml `Sys_blocked_io` raised out
  of dune's `print_user_message`: *"Internal error! … unable to serialize exception"*,
  attributed to `deps/isabelle/dune` lines 4–14.
- **2026-08-22** (run 32605525115) — same rule, same point, **no output for 49m50s**,
  then the cap. `dune` was still an orphan process at teardown.

**3. The deadlock is self-sustaining.** The job is killed at the cap ⇒ `Post Cache`
never runs ⇒ the cache is never re-saved ⇒ the next run is cold again. That is the
seven weeks.

## What changed

- **The heavy opam/dune steps no longer inherit the runner's stdout pipe.** Their
  output goes to a descriptor opened on a **regular file** and is replayed afterwards.
  A write to a regular file cannot return `EAGAIN`, so a child's `O_NONBLOCK` is inert.
  `stdin` is `/dev/null`, so a build that prompts fails instead of blocking.
- **A wall-clock budget** (`ZETA_OPAM_GIT_BUDGET_MS`, default 40m, shared across the
  mechanism). A stall now produces a **red with the captured log**. *`cancelled` is not
  a verdict* — this is what lets the lane report one.
- **`--check-toolchain` is no longer vacuous.** `checkToolchain` returned an
  `opam exec --switch=tlaps-build -- tlapm` command line whenever *opam* was on PATH,
  never asking whether tlapm was behind it. On 2026-07-02 the toolchain build failed,
  `linux.sh` swallowed it (`|| echo "from-opam-git failed … continuing"`), the verify
  step printed **`OK: TLAPS toolchain ready`**, and every spec then failed with
  **exit 127**. Every candidate is now probed with `--version` before it is returned.
