## Description

## Why

`ZetaDbImagePort` named its revision discipline with a string, but adapters still duplicated the behavior and a declaration could lie. The browser checkpoint store and database image wrapper also had no typed way to prove they executed the same rule inside the IndexedDB transaction.

## What

- add a source-owned `RevisionPolicyPort` with typed write, idempotent, and refusal decisions
- supply compare-and-swap and monotone last-writer-wins implementations
- require browser checkpoint and ZetaDB image ports to expose the executable policy
- apply the browser policy inside the IndexedDB read-write transaction and inherit it through the ZetaDB adapter
- migrate in-memory, scheduled-file, and test adapters to the shared policy
- replace tag-branching conformance with generated policy-vs-save comparison
- close workitem `081M0Q8TQYE087G0R001WBX1ZC`

## Proof

- 495 browser, ZetaDB, Dark Hall, and policy tests pass
- 51 focused policy/kernel tests pass after the final injection case
- whole-tree TypeScript compilation passes
- canonical TypeScript, Prettier, and style gate passes
- markdownlint and diff hygiene pass

## Limits

The native browser checkpoint adapter intentionally remains monotone by default. Policy decides admissibility; each persistence adapter is still responsible for atomic application. The repository-wide auto-vivify check is independently red on current `main` because it parses QEC bracket notation and three shortened KubeVirt paths as database links; that repair is being handled separately.
