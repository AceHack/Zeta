## Description

The finding turned out to be bigger than the fix, so it leads.

## The coverage claim I made was about a different thing

I had written that **48 install steps incidentally re-prove `install.sh` works on a fresh runner**. Measured on `main`:

| | count |
|---|---|
| `Install toolchain` steps | 48 |
| **preceded, in the same job, by an `actions/cache` restore** (mise runtimes / apt archives / .NET SDK) | **33** |
| no cache restore in the job | 15 |

On a cache hit a warm install step **never exercises the download path** — that is the cache's purpose. And the other 15 are only cold relative to *our* caches; they still run on a hosted image already shipping node, Python, Go, Java and .NET against an apt mirror in the same datacentre.

**None of the 48 is a bare-machine proof.** That belongs to nine workflows — and **none of them had a `schedule:`**. So the only checks that prove the installer works from bare metal fired *solely when somebody edited the installer*, and the failure class they exist to catch never edits anything.

## Two causes, two arrival processes, two triggers

DV2.0 change-rate partitioning applied to CI triggers:

- **path filter** ← *our changes*. Event-driven, fires on the edit, fastest feedback, tied to the cause.
- **`schedule:`** ← *upstream drift* — a mirror moving, a channel updating, a runner image changing. Time-driven, **arrives with no commit**, and a path filter can never fire because there is nothing to filter on.

**The rule for who gets one:** *schedule a check iff its outcome can change with no commit.* Seven qualify, and each states in-file what it reaches outside for. `installer-unit-tests` and `installer-repair-mode-existing-install` deliberately do **not** — their inputs are all committed, so a cron would re-run the same computation over the same bytes. A scheduled tautology dilutes the roster with a check that cannot discover anything.

**Daily**, from the arrival process: mirrors and images move on a days scale. `factory-hygiene-audit-cadence.yml` is the daily precedent. `mirror-to-fork.yml`'s 6-hourly number is *not* copied — it bounds backup staleness, a different quantity; only its principle transfers. Cost: ≈48 runner-minutes/day, and this is a public repo, so standard runners are free.

## Loud without new wiring — verified, not cited

Adding `schedule:` auto-enrols these in the drift-dashboard roster:

- `expectationFromWorkflow` turns a `cron:` into `{ kind: "periodic" }`, and its own comment settles the both-triggers case: *"a workflow that is BOTH scheduled and PR-triggered is `periodic`, because the clock is the stronger claim."*
- `fold.ts` reddens on **failure**, on **silence** (`> 3× period`, :335), and on **never-ran** (:301). *"Unknown never aggregates into green."*

Confirmed live against this tree — the seven now resolve `periodic 86400`; the two excluded stay `on-change`.

**Deliberately not** filing into `docs/drift-events/`: `drift-ledger.ts` allocates ticks as `max+1` and a second concurrent writer reintroduces the documented `000070` double-mint race.

## The failure path is proven, both links

**silence → red:** `fold.test.ts:523` and `:594` already cover it — 84 pass / 0 fail here. `:594` (*"only a finding once the trigger COULD have fired"*) is why seven new schedules do **not** produce a day-zero false red.

**shield → red:** 5 of 7 have an **observed** failure in their last 100 runs. The two that do not — `wsl-install-sh-test` (0/100) and `gitbash-install-routing-test` (0/100) — are **named as unobserved rather than assumed good**. `gitbash`'s failure branch was read and is reachable, and it is *route-only by its own name*, so it should not be counted as a bare-machine install proof at all.

## Closed in passing

`docker-ubuntu-install-sh-test` carried an unconditional `cancel-in-progress: true`, unlike its six siblings. Harmless while every trigger was a PR; **wrong once a schedule exists** — on `main` a scheduled run and a later push share the group, so the clock-driven verdict could be cancelled by an unrelated merge, and a cancelled run reads as neither pass nor fail. Observed cancellation rates on these lanes are **12–39%**, so this was worth fixing rather than noting.

## Scope

No job migrated to a container. Nothing demoted. Nothing added to `gate (required)`'s `needs`. No existing per-PR install step deleted or weakened — the schedule *adds* the time-driven arm. Lands **ahead** of any containerization, deliberately, so the coverage never has a gap.

## What I could not verify

That `wsl` and `gitbash` can fail (0 observed each) · that a scheduled run executes the real job — no job- or step-level `if:` keyed to `github.event_name` exists in any of the seven, but **no scheduled run has happened yet**, so the first one is the proof · whether daily is the right cadence (reasoned from the arrival process; there is no recorded incident history to fit it to) · the warm/cold split is a **static parse** counting cache *steps*, not runtime *hits* — the error direction is conservative for my argument, and stated in the doc rather than hidden.
