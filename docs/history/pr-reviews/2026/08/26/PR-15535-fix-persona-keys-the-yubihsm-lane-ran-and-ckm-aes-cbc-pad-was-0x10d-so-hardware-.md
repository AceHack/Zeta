## H3, measured — and it found a bug the missing key was hiding

Aaron authorized the YubiHSM default credential for **read-only** testing on 2026-08-26:
*"you should be able to proceed testing with the default password `password` just don't change
the password for now."* No device state was changed, verified after the run: the device still
holds exactly its one factory auth key and nothing else.

### The lane ran

```text
2 pass · 1 fail · 10 skip · 13 tests · exit code 1
```

| | |
|---|---|
| Discovery, no login | `YubiHSM#39160506`, slot 0 |
| Login `0001password` | **`CKR_OK`** — the `<4-hex-authkey-id><password>` form is confirmed |
| `zeta-frost-wrap` | **ABSENT** — the device is factory-empty (0 PKCS#11 objects) |
| HW-1 token present · HW-5 lane name valid | pass |
| HW-2 share round-trips through the token | **fail** — `no PKCS#11 key labelled zeta-frost-wrap` |

So the lane failed on the **prerequisite**, not the credential. The anti-vacuity machinery
itself is now measured rather than claimed: it did not fall back to the software fake, and it
failed loudly rather than reporting green on a token that could not serve it.

**Provisioning the key is device state and was out of scope** — it needs a human with that
authorization. Tracked as new item **H3′**.

### What running it found

**1. `CKM_AES_CBC_PAD` was `0x0000010d`. It is `0x00001085`.**

`0x0000010d` is not any defined PKCS#11 mechanism — `0x106..0x10f` is the unassigned gap
between RC2 and RC4. `C_EncryptInit` with an undefined mechanism returns
`CKR_MECHANISM_INVALID`, so **the `hardware-pkcs11` tier could not have sealed a share on any
conforming token**, from the day the file was written. Provisioning the key alone would not
have turned the tier green.

Checked against four independent sources, one of them the device: Yubico's `pkcs11t.h:1019`,
NSS's `pkcs11t.h:1219`, the YubiHSM's own `C_GetMechanismList` (`0x1085` present, `0x10d`
absent), and this repo's OpenBao note recording `CKM_AES_GCM (0x1087)` in the same `0x108x`
block.

**Why nothing caught it** — the software mock's `C_EncryptInit` is `() => 0n`. It never reads
the mechanism, so it accepts every value. A fake that cannot reject a wrong mechanism cannot
falsify a wrong mechanism constant; the suite was green while this value was arbitrary.

**2. `C_Initialize`'s return value was discarded at all three call sites.** Against an
unconfigured module the first visible error was `C_GetSlotList (count) failed: 400` — `0x190`,
`CKR_CRYPTOKI_NOT_INITIALIZED` — naming an innocent downstream call and reading as an absent
token when the token was present and healthy. This is what cost the diagnosis time.

### Falsifiers, mutation-checked

`FSA-32`..`FSA-36`. A falsifier that passes for the wrong reason is the defect it exists to
catch, so both fixes were run against a restored mutant:

| mutant | result |
|---|---|
| `CKM_AES_CBC_PAD` back to `0x0000010d` | **FSA-32, FSA-33 fail** (52 pass / 2 fail) |
| `C_Initialize` rv swallowed again | **FSA-34, FSA-35 fail** (52 pass / 2 fail) |
| neither | 54 pass / 0 fail |

`FSA-32` asserts on the **wire bytes**, not on the imported constant — importing it would
compare the value to itself, which cannot fail.

### The lockout caution, retired with evidence

The readiness doc declined H3 on the risk of an auth-key lockout counter. The PIN is no longer
unknown, so the premise is gone. Separately, `get-object-info` on the auth key exposes **no
attempts-remaining field** — the field PIV *does* expose — and `yubihsm.h` has no blocked/locked
error code. **Stated at its true strength:** that is *consistent with* no lockout, not proof;
proving it would mean deliberately failing authentication, which was not done. The original
caution looks generalised from PIV/smartcard semantics, and declining to touch the only HSM on
an unverified risk was the right call on the information then available.

### Not measured — stated plainly

- **No share has been sealed by this device.** HW-2 never reached `C_Encrypt`. `hardware-pkcs11`
  remains **unexercised end-to-end**.
- The mechanism fix is **header-verified and unit-falsified, not hardware-exercised**. No
  `C_EncryptInit` has been issued against a real key on this device.
- Whether the YubiHSM's CBC accepts the adapter's IV/padding handling in practice — unknown.
- The multi-token lane needs ≥ 2 devices and cannot run here at all.
