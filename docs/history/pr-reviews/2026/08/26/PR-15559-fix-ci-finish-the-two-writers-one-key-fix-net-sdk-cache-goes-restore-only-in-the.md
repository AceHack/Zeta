Correcting a commit message needs a history rewrite and force-push is a gated class, so the branch is rebuilt. **Content is byte-identical** to #15549; only the trailer is corrected.

---

The mise cache in low-memory.yml is already restore-only, with a measured
comment explaining why: "gate.yml:build-and-test writes the IDENTICAL key ...
on the same push: [main] trigger, from a 4-vCPU host ... Two writers, one key:
the slow one was paying for a cache the fast one already maintains."

That fix landed on mise and was never extended to the .NET SDK cache four lines
above it, which has the BYTE-IDENTICAL key expression in both lanes:

  gate.yml        dotnet-${{ runner.os }}-${{ runner.arch }}-${{ hashFiles(...) }}
  low-memory.yml  dotnet-${{ runner.os }}-${{ runner.arch }}-${{ hashFiles(...) }}

Measured consequence (PR #15538): on 2026-08-26 `dotnet-Linux-X64-<hash>` held
172,367 bytes on refs/heads/main while the SAME KEY on a PR ref held
429,822,343 bytes -- 2,500x divergence under one key. A 172 KB ~/.dotnet still
returns cache-hit: true, which suppresses the save on every later job that
matches it, so the bad entry is self-preserving until LRU removes it.

Which lane wrote the 172 KB copy is NOT established and this change does not
guess. What is established is that two lanes on two different runner images
(ubuntu-24.04 vs ubuntu-slim) write one key, and the key currently holds two
irreconcilable contents. Restore-only removes the slim lane as a writer, which
is the same remedy, for the same reason, as the mise step below it. gate.yml
remains the sole writer -- the full-tier superset, per the existing comment's
own argument.

Also drops a dead key input: hashFiles('global.json', 'tools/setup/common/
dotnet.sh') referenced a file deleted in Round 34 (#27), so the key hashed only
global.json while claiming to hash a script that has not existed for months.
Checked before removing that this was not masking a stale-SDK restore: all 3
dotnet pin bumps in the last 90 days moved global.json in the same commit
(audit-dotnet-pin-parity.ts enforces it), so the key did change on every real
SDK change. The path was misleading, not load-bearing.

Costs a one-time cold rebuild of the dotnet entries only. NOT changed: elan and
nuget in the slim lane, which do NOT collide (they omit runner.arch, so their
keys differ from gate.yml's). They are arch-less, which is a latent hazard if a
slim ARM runner ever appears -- named, deliberately not fixed here, because it
buys nothing measurable today and would cost a cold rebuild.

actionlint clean on both changed files, exit code read directly.

## The defect is worse than #15549 could see, now instrumented

#15549 rested on two cache-API samples. Reading the per-job logs of 6 consecutive `gate.yml` runs (212 jobs, 0 skipped) shows the poisoned entry is **restored on 6 of 6 runs**, every time on `build-and-test (ubuntu-24.04)`:

```
Cache Size: ~0 MB (172876 B)     dotnet-Linux-X64-4cf67312…
                429,688,927 B    dotnet-Linux-ARM64-4cf67312…   <- same hash, other arch
              1,948,464,753 B    dotnet-macOS-ARM64-4cf67312…   <- same hash, other arch
```

Every one of those jobs also logs `Cache hit occurred on the primary key … not saving cache`, so `actions/cache` will never overwrite it. **`~/.dotnet` is re-installed by `tools/setup/install.sh` on every ubuntu-24.04 gate run while the cache reports a hit** — a green `cache-hit: true` in front of a cache that contains nothing.

Job ids, so this is checkable: 98118433280, 98117482432, 98117749244, 98118926537, 98119331769, 98120214904.

Which lane wrote the 172 KB copy is **still not established** — that needs the run that originally saved it, outside the sampled window. This change removes the slim lane as a writer regardless, on the structural argument, not on an attribution.
