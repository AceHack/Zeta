## What this does and does not clear — corrected

Every **future** flush PR is clean from the moment it is opened. #15605 and
#15551 are **not**, and my first reading of that was wrong, so it is stated
here plainly rather than quietly amended.

`openMergePR` is idempotent by **reusing an existing open PR** head→base, and
the reuse branch never touches `title` or `body` — there is no `PATCH
repos/…/pulls/N` anywhere in the file (verified: zero occurrences). So a lane
with an open flush PR keeps that PR, and keeps the body it was opened with,
tick after tick. Both bodies still read `Task: 081KSKBP80008QG0R001KK9WV6`
today (checked via REST).

**Consequence:** those two do not self-heal on the next tick. They need one of
— editing each body's `Task:` line to `081M0ZWYF7R087G0R002RXA889`, or closing
them so the following tick opens fresh ones from the fixed generator. Either is
safe only *after* this lands, because until then the work-item file is not on
`main` and the id would not resolve in their CI either.

Worth noting as a second-order finding, not fixed here: a generator whose body
is written once and never refreshed means *any* future body defect is equally
sticky on an open flush PR. That is a real design gap in the reuse path, and it
is a different change from this one.
