## Description

## What this is

The hardware lane could not tell **"one approved command remains"** from **"your hardware is broken."** Both exited 1. This gives the question a ladder with its own exit code for the middle rung, writes the one remaining device-state change as reviewable gated code, and advances H3′ with a measurement taken on the real chip that creates no object on it.

**The device was not modified.** `yubihsm-shell -a list-objects` reports the same single object (`0x0001`, the default auth key) before and after. Its password is unchanged, as asked.

## Measured on the real YubiHSM 2 (fw 2.4.1, serial 39160506)

| command | result |
|---|---|
| `frost-hsm-provision.ts status` | `reachable-unprovisioned`, **rc 3**, token `YubiHSM#39160506`, mechanism ok |
| same, `YUBIHSM_PKCS11_CONF` unset | `unreachable` / **`module-init-failed`**, rc 1 |
| same, module path absent | `unreachable` / **`module-absent`**, rc 1 |
| `plan` | dry run, password redacted, biometric door never opened, rc 3 |

Three rungs, three readouts, two exit codes — the split is measured, not asserted.

## H3′ — advanced without creating an object

```text
C_GetMechanismInfo(slot 0, 0x1085) -> rv 0,   min 16, max 32, flags 0x301  (CKF_HW|CKF_ENCRYPT|CKF_DECRYPT)
C_GetMechanismInfo(slot 0, 0x10d)  -> rv 112  = 0x70 = CKR_MECHANISM_INVALID
```

The corrected constant names a mechanism **this device's module implements**, with encrypt+decrypt and a 32-byte ceiling — exactly the shape an AES-256 wrap key needs. The pre-fix value is refused **by the device**, by name, with the rv the fix predicted. That is a hardware falsification, not a citation.

**It does not close H3′.** No `C_EncryptInit` has run against a real key handle, so the seal/unseal round trip stays `unexercised`. The doc says so in its register table and does not round up.

## Provisioning as code, not instructions

The predecessor doc carried the step as a shell snippet marked *"flags not executed, treat the spelling as unverified."* A command nobody can run is a command nobody can check — and the two things most likely to be wrong fail **silently and late**:

- without `decrypt-cbc`: provisions fine, can never unseal a share
- with `exportable-under-wrap`: provisions fine, voids `keyResidency: "hardware-resident"`

`planWrapKeyProvisioning` refuses both **at plan time, before a human is asked to approve anything**. `apply` runs behind `ceremony-gate.ts`'s existing `provision-or-reconfigure-hardware-token` — **no member was added to that closed set**; the classification already existed. Fail-closed at four points: already-provisioned (no prompt, §12), unreachable device (refuse without prompting), dry run (door never opened), declined/absent approval.

## Two silent-failure defects fixed on the way

Now a real skip with its reason in the title, and `MULTIBOOT_MTOOLS_SMOKE_REQUIRED=1` makes absence a hard failure in the one job that installs the toolchain. Falsified three ways on this host:
