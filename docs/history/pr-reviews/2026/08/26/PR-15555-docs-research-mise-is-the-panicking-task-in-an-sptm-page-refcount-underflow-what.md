## Description

## What this is

Aaron's machine hard-panicked twice. The second panic names **`mise`** as the faulting task inside
Apple's **SPTM** (Secure Page Table Monitor), on a per-page mapping refcount decremented below zero:

```
panic(cpu 16 caller 0xfffffe003905c010): cpt_mapcnt_dec: refcnt underflow: rc ... old_value 0 value 65535
Panicked task ...: 2296 pages, 1 threads: pid 37148: mise
Kernel Extensions in backtrace: com.apple.sptm(25.5)
Darwin Kernel Version 25.5.0 / RELEASE_ARM64_T6020   (M2 Pro, macOS 26.5)
```

**The defect is Apple's** — a userspace process must never be able to panic the kernel. This documents
the *workload that reaches it*. **No toolchain change is made or proposed as done here**; a toolchain
change made autonomously off a crash log is the wrong call, and that decision stays with Aaron.

## The measured answer

The repo's shell integration **execs an 80.7 MB-of-`__TEXT` binary on every shell prompt**, in every one
of **69 live worktrees**, across **24 concurrent agent processes**.

| measurement | value |
|---|---|
| `mise` binary on disk | 101,589,968 B |
| `__TEXT` segment | 80,691,200 B = **4,925 pages** @ 16 KB (macOS ARM64) |
| `_mise_hook_precmd` | execs `mise hook-env` **per prompt**; `_mise_hook_chpwd` per `cd` |
| cost per exec | 62 ms (10 runs, 0.62 s) |
| live worktrees / with a `.mise` config | 69 / **69** (both files are tracked) |
| trusted / untrusted | 61 / 8 |
| trust records; created 2026-08-25 | 338; **74** (baseline 5–15/day) |
| concurrent agent processes | 24 |

There is **one** `mise` binary on disk, so every invocation maps and unmaps **the same 4,925 physical
pages** — the hottest map/unmap target on the machine, driven concurrently from many cores. That is the
traffic the panicking counter counts.

The hook calls `/opt/homebrew/bin/mise` by **absolute path**, so no `PATH` shim can intercept it.

## Two first guesses the panic's own numbers exclude

- **"mise used too much memory."** The task was **2296 pages = 37.6 MB, single-threaded**. Small and
  ordinary. Whatever accumulated did not accumulate inside this process.
- **"it ran out of counter."** An **underflow** is a lost race or double-decrement, not an exhaustion.
  Volume does not produce it — volume produces the *opportunity* to lose the race. That is what explains
  the timing (~24 h, and faster previously) in a way volume alone cannot.

## Literature — including the null result

**`cpt_mapcnt_dec` returns nothing, anywhere. No kernel panic has ever been publicly attributed to
`mise`.** Reported plainly rather than padded into a theory.

The **mirror-image** `cpt_mapcnt_inc: refcnt overflow` is documented twice independently:
[boldright/Knit #17](https://github.com/boldright/Knit/pull/17) / [#76](https://github.com/boldright/Knit/pull/76)
/ [#81](https://github.com/boldright/Knit/pull/81) on Darwin **25.4.0**, and
[antirez on X](https://x.com/antirez/status/2049900673001566320) — both mmap-heavy on memory-rich Apple
Silicon. Two discrepancies are recorded rather than smoothed over: those are the **opposite arithmetic
direction**, and their 2048-range field **disagrees with our 16-bit wrap**, which may mean a different
bug entirely.

**SPTM background is now sourced from the binary, not paraphrased.** The Proteas write-up was fetched
and read directly; strings recovered from the SPTM binary name four per-page refcounts and their
panicking violations — `VIOLATION_OVERFLOW_{RO,WX,NESTED,USER}_REFCNT`, plus `refcounts_update_page_op`.
That makes "SPTM keeps per-page refcounts and panics on refcount violations" a **sourced fact**. It also
**refutes two things**, which the doc now records: **none of the four is named `mapcnt`**, and **every
violation string is `OVERFLOW` — there is no `UNDERFLOW` string at all**, while our panic is an
underflow. Corroborates the **mechanism class**, not our counter.

The symbol is **absent from XNU 12377.121.6's public source** (the exact build), so the counter's
semantics are unverifiable outside Apple — which is also why the Knit authors' "VM compressor"
attribution is not repeated here as fact.

Also ruled out: [jdx/mise#8734](https://github.com/jdx/mise/discussions/8734) is a *different* Tahoe bug
(hang/100 % CPU, fixed in 2026.3.14). `jdx/mise` has Issues disabled; Discussions were searched.

## Mitigations — one is listed to be dismissed

Ordered by evidential support. **None is applied.** #1 report to Apple (`metered` as the correct venue).
#2 turn off the per-prompt hook (`consistent with`). **#3 trusting the 8 untrusted worktrees is listed
specifically to be dismissed** — an untrusted config makes mise print an error and exit; it **does not
skip the exec**, so it fixes noise and nothing else. #4–#6 `speculative`.

Explicitly **not** recommended: changing how the repo declares or consumes toolchains. The finding is
about **invocation frequency in shell integration** — a host/profile setting, not a repo contract.

## Corrections made during the investigation

A first pass reported *0 of 69* worktrees trusted. That was a **bad measurement** — `mise trust --show`
abbreviates `$HOME` to `~`, so a grep for absolute paths matched nothing. Corrected to 61/8 in the doc.

## No malice, no incompetence

Apple's monitor halting on a violated page-table invariant is that design working as intended. `mise`
execing fast and exiting is what a shell-hook tool is supposed to do. Running many agents in many
worktrees is the point of this repo. The panic is where three reasonable things meet — an ordinary
refcount defect at a very hard concurrent boundary.
