## Description

fix(ci): name the real cost of the heartbeat merge credential — no gate verdict, not just no archive run

The task was to make heartbeat flush merges dispatch a gate run. They cannot be made to
from inside the repo, and this states exactly why, with the measurement, rather than
inventing a substitute.

WHAT THE MERGE ACTUALLY IS. A flush PR is merged by GitHub auto-merge, which merges as the
identity that ARMED it. Arming happens in `agent-heartbeat.yml`'s merge-duty step, which
already prefers `ZETA_PR_ARCHIVE_TOKEN` and degrades to `GITHUB_TOKEN` on a refusal. So
there is no code path where "the merge uses GITHUB_TOKEN" is a choice this repo makes — it
is a fallback the repo takes when the PAT is refused.

THE BLOCKER, MEASURED. Job 98152703368 (`alexa heartbeat tick`, run 32960872768), step
`Auto-merge clean PRs`:

    10:59:01Z ##[warning]ZETA_PR_ARCHIVE_TOKEN (the PR-create role credential) was
              refused the GraphQL mutation, so arming falls back to GITHUB_TOKEN ...
    10:59:07Z [merge] armed 3 of 3 (attempted 3, 4 unarmed in queue,
              credential: degraded-to-workflow-token)

`degraded-to-workflow-token` is set ONLY in the refusal branch — the absent-secret branch
sets `workflow-token-only` — so this distinguishes the two faults rather than guessing
between them. The secret IS set; the PAT WAS refused `enablePullRequestAutoMerge`, which is
GraphQL-only with no REST equivalent to fall back to. Fixing it is a scope grant on a
fine-grained PAT: a credential change, and a gated class.

THE DISCRIMINATOR, ON A FULL POPULATION. 89 `main` commits, 06:00Z..11:10Z today, each
queried per-SHA for `gate` runs with `event=push`, then mapped to its merged PR:

  | merged by                            | gate push run | commits |
  |--------------------------------------|---------------|---------|
  | AceHack (PAT)                        | yes, 63/63    | 63      |
  | github-actions[bot] (GITHUB_TOKEN)   | no,  26/26    | 26      |

Total separation. All 26 of the no-run class are `heartbeat/*`; ten OTHER `heartbeat/*`
commits in the same window DID get a run, because those were armed by AceHack. The lane is
not the cause. The credential is. (Reproduces §2 of the 2026-08-26 verdict-loss doc, which
sampled 20 + 18 and measured 40.0% over 245 commits.)

WHAT THIS PR CHANGES — the size of the claim, nothing else.

`agent-heartbeat.yml` has warned about this since it was written, and the warning names the
wrong consequence. It says only that `pr-archive-on-merge.yml` will not fire. That is true
and it is the SMALLER half: the same suppressed event costs the post-merge `gate` verdict,
and because `CI Gate` has `strict_required_status_checks_policy: false`, that run is the
only cover for "two PRs green alone, red together". Archive coverage has a backfill sweep;
a verdict has none.

So all three warnings now name both consequences and carry the measurement. A warning that
under-states its own blast radius gets triaged at the wrong priority, which is how a defect
that costs ~29% of main's post-merge verdicts has been firing every 15 minutes as an
archive-coverage note.

Plus one P1 work-item, 081M0YWHE7G087G0R001PSGEH5, carrying the evidence, the operator
action, and a falsifier for the fix. Distinct from 081M05G8D36087G0R0034D3QPA, which is the
same class of denial on a DIFFERENT token (`ZETA_TELEMETRY_FLUSH_TOKEN`, the BRANCH-PUSH
role) — two tokens, two roles, two grants.

    OPERATOR ACTION: grant 'Pull requests: Read and write' to ZETA_PR_ARCHIVE_TOKEN
    on Lucent-Financial-Group/Zeta.

CONSIDERED AND REFUSED.
  - Substituting ZETA_TELEMETRY_FLUSH_TOKEN for arming — the `||` role-collapse this repo
    already removed once, and whether that token carries the mutation is untested and
    untestable without the secret. A guess wearing a fix's clothes.
  - A `schedule:` sweep dispatching `gate` at unchecked commits — manufactures a verdict
    without the merge having been gated. The vacuity class with extra machinery.
  - Refusing to degrade at all — stalls the merge queue, which the tick-must-never-stop
    rule forbids. That tradeoff is deliberate and documented; reversing it unilaterally
    would be a worse failure than the one it treats.

Registers: the 89/89 separation, the `degraded-to-workflow-token` log line, and the
`auto_squash_enabled -> merged` actor chain are `metered`. That granting the scope will
close the gap is `consistent with` the 63/63 PAT-merged row, not established — the
falsifier in the work-item is how it gets established.

No workflow logic, ruleset, or repository setting is changed. Three `echo` strings and one
comment block; nothing about what blocks a merge moves.
