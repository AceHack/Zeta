## Description

## What this is

A decision doc for the gate's concurrency/trigger topology, answering Aaron's
*"can we redisign this to do parallel runs so none ever get cancled?"*

**It changes no workflow, no ruleset, and no repository setting.** The merge queue
is not enabled, `gate.yml`'s concurrency block is untouched, and
`required_status_checks` is unchanged. Those are gated-class calls and §9 of the doc
lists them for a human read.

## Headline: the canary's number is right, its cause is wrong, and it is not the biggest class

Measured over 600 `gate` runs, 245 `main` commits, 221 merged PRs, 25 h 25 min.

| event | total | success | failure | cancelled | cancel rate |
|---|---|---|---|---|---|
| `pull_request` | 453 | 101 | 219 | 123 | 27.2% |
| `push` (main) | 147 | 14 | 48 | **83** | **56.5%** |
| `merge_group` | 0 | — | — | — | — |

**Queue displacement hypothesis: confirmed, 83 of 83.** Every cancelled push run had
**zero jobs** — the jobs endpoint returns `total_count: 0` for all 83. Nothing was ever
`in_progress`, so nothing was interrupted. Cancellation lands 1–4 s after the *next*
push run is created, which is the documented pending-run displacement under
`cancel-in-progress: false`.

So `src/Core.TypeScript/ci/verdict-drought.ts` and `.github/workflows/drift-sweep.yml`
both misattribute this to `cancel-in-progress` cancelling an in-flight run. The condition
they detect is real; the named cause is falsified, and the remedy differs — there is no
setting to change.

**PR-side hypothesis: confirmed, and it is the opposite population.** 118 of 123 cancelled
PR runs *did* have started jobs — genuine `synchronize` interruption, working as designed.

**The expectation that fleet churn inflates the headline does not hold.** The headline is a
push-lane number and PR cancellations do not enter it. Even within the PR lane,
`heartbeat/*` cancels at **22/151 = 14.6%**, *below* the 27.2% PR average. Excluding fleet
churn does not lower 56.7%, because it was never in it.

## The larger mechanism, previously unattributed

**98 of 245 `main` commits (40.0%) never triggered a `gate` run at all** — queried per SHA,
zero `gate` runs exist. 78 of the 84 mappable ones are `heartbeat/*`. The discriminator is
the merge actor, and the separation is total in the samples: `github-actions[bot]`
(GITHUB_TOKEN) → no run, 20/20; `AceHack` (PAT) → run, 18/18.

**No concurrency design reaches this class.** Both candidates change what happens *to a run*;
here there is no run. It is the second half of the already-fixed PR-side bug in
`agent-heartbeat.yml` / `081M010H4KE` — the branch push got a PAT, the merge did not.

Verdict ledger for `main`: 25.3% concluded · 33.9% displaced · **40.0% never dispatched**.

Mitigating context, stated so the alarm is the right size: every one of those commits *was*
gated pre-merge by `gate (required)`. What is lost is the post-merge verdict — which matters
because `strict_required_status_checks_policy: false`, making that run the only coverage of
the two-PRs-green-alone-red-together class.

## An existing recovery lane that cannot fire

`rerun-cancelled-gate` gave 66 second attempts on the PR lane and **1** on the push lane.
`isSuperseded` matches `head_branch` and ignores `head_sha`, so on `main` every displaced
run is written off as `superseded — "concurrency working as designed"` — true for a PR
branch, false for `main`, where the next run has a different SHA and carries no verdict for
the displaced commit. A one-predicate fix reactivates an already-reviewed lane.

## Both designs costed

**A (per-SHA on push)** — fixes the 83, not the 98. +83 executed runs/day × 94 runner-min.
Runner concurrency is not binding (enterprise plan; measured peak 18 pushes/h, 21 commits/h
— not the 50/h assumed). **Cache is:** the push run is the write-heavy shape (18
cache-participating jobs, **5 actual uploads**) vs the PR run (15 participating, **0**
uploads). A adds ~+415 uploads/day on that lane — ~+130% — in an amplifying loop (more
uploads → more eviction → more misses → more uploads). **Should not land before the cache
work.**

**B (merge queue)** — `merge_group:` confirmed already present on `gate.yml` and `codeql.yml`.
Structurally right, and it would also fix the 98 by moving the verdict pre-merge. **Possibly
disqualifying, and untestable without enabling it:** if `merge_group` events enqueued by
`github-actions[bot]` are suppressed/parked the way `pull_request` events from that actor
were *measured* to be, every heartbeat entry times out and the telemetry lanes wedge
permanently. Throughput is thin at peak (ρ ≈ 0.78, no priority lane, bisect halves it);
`heartbeat/*` is 40% of merges and would see ~25 min per entry against a ~20 min flush
interval.

## Decomposition, priced (per the standing direction)

The gate is **already** decomposed at the job level — 37 jobs, ~26 named `lint (...)` legs.
What is monolithic is the `needs:` rollup and the ruleset. So there are two changes at very
different prices:

- **Promote existing job names into `required_status_checks`** — **zero runner-minutes, zero
  cache bytes.** The jobs already publish named check-runs.
- **Split a job into N** — priced by setup class:

| class | overhead | cache bytes |
|---|---|---|
| 0 — Bun only | **10–14 s** | **none** |
| 1 — install.sh toolchain | 46–149 s | one restore + conditional save |
| 2 — build-and-test | 129–356 s | four caches per leg |

`cross-verify` is **class 0**, so splitting its 31 audits into 31 named checks is
`31 × 12 s ≈ +6.6%` runner time, **zero new cache writes**, no wall-clock change. **The split
the direction most demands is the cheapest one available, and it is affordable today.**

It may be better than free: **42% of the gate's runner-seconds is setup overhead**, and three
class-1 lint jobs pay a 21–44 s toolchain install to run an audit that takes **0 s**.
Demoting those pays for the whole `cross-verify` split.

Rule that falls out: **a job may be split for free along a setup boundary it does not cross.**

Queue composition (direct answer): length of the required list is fine; **shape** is the
footgun. The pre-merge matrix is Linux + `macos-26` only, so promoting a Windows leg to
required would **deadlock the queue permanently**, silently. A lint asserting every required
context comes from a `merge_group`-triggered workflow under the pre-merge matrix should land
*before* any queue.

## Recommendation

Ordering beats the A/B choice, because 40% of the exposure is invisible to both:

1. Make heartbeat **merges** dispatch a run (PAT, or `workflow_dispatch` at the merged SHA).
2. Fix `isSuperseded` to compare `head_sha`.
3. Land the `merge_group` coverage lint.
4. Then **B**, gated on the GITHUB_TOKEN enqueue question.
5. **A** as fallback only, after the cache work.

Steps 1–3 are reversible, change nothing about what blocks a merge, and recover 181 of the
183 lost verdicts.

**The case against my own recommendation** is in §7.1 and is strong: A is one line and cannot
wedge anything; B is a repo setting with an unverified wedge mode. What actually decides it is
a fact I do not have — whether the semantic-conflict class has ever bitten `main` here.

## What I could not verify (§8)

class-1 lints need their toolchain · whether the API will re-run a zero-job run · 14 of 98 no-run
commits unmapped · whether the semantic-conflict class has ever actually bitten.
