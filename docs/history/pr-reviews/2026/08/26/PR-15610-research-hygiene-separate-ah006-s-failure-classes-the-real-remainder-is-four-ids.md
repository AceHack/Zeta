## Description

## What this is

A **classifier** — not a gate, not wired into CI, exits 0 unconditionally — plus the measurement behind it. AH006 (`audit-task-zetaid-resolves.ts`) reports *"no work-item file carries this id"* for four separable defects with four different remedies, and a remedy cannot be chosen from an undifferentiated count.

**Nothing is widened, no files are moved, no gate is touched.** Any code here is a classifier, not a fix.

## Three of the counts I would have reported were artifacts

**1. The input surface.** The audit is fed **PR bodies only** (`gate.yml:2793`), and `extractTaskIds` falls back to scanning all text when no `Task:` line yields an id — which `Task: none` triggers. **Cited** ids are promoted to **declared** ones. Found independently and fixed in flight by **#15607**; not touched here. On the 15 open PRs it accounts for **2 of the 4 live failures**. On commit messages — a surface the audit does *not* read — it would be **48 of 51**, recorded as latent blast radius because it prices the bug rather than naming it.

**2. The denominator.** "647 vs 1138 rows ⇒ 64% cannot resolve" is arithmetically true and operationally irrelevant: **exactly one** of those 1118 backlog rows is declared by a live PR.

**3. Layout conformance.** **Zero structural deviations in 1790 ids** — nobody failed to follow the layout. But the second half of the hypothesis is exactly right, in a place neither of us was pointing.

## The load-bearing finding

A WorkItem ZetaId has **32 free bits of 128**, all in characters 19..25; **characters 0..18 are a pure function of the mint timestamp.** The `docs/backlog/` corpus was backfilled **day-granular** by `legacy-b-id-zetaid.ts`, so:

| | `workitems/` | `docs/backlog/` |
|---|---|---|
| share first 19 chars with a sibling | **0.3%** | **99.6%** |
| largest 19-char cohort | 2 | **98** |
| midnight-exact timestamps | 1 of 672 | 1105 of 1118 |

## Why the resolver must not be widened

`context-cost-trend-cadence.yml` names `081KT7YW00008QG0R002T1XNWT`. That id **resolves** — to a *closed YAML row*, not the P0 context-window row the workflow says it serves (`081KT7YW00008QG0R003JV9D4J`). Same 19-char prefix.

```
081KT7YW00008QG0R00 2T1XNWT   ← stamped   (canonical-YAML, closed)
081KT7YW00008QG0R00 3JV9D4J   ← intended  (context-window minimization, P0)
└──── 19 identical ────┘
```

**Widening to `docs/backlog/` turns this GREEN while it stays wrong.** Misattribution is a property a *resolving* id can have, so the classifier reports the cohort orthogonally to the class.

## The null result

**Structure cannot separate an unminted id from a genuine one** — stated as a live test, not a sentence. The labeled positive `081M0X0JQGY087G0R000EBCPQ3` is byte-perfect: seven constant fields exact, zero gap, millisecond wall-clock **of the day it was written**, and reserved bit 64 **clear** — the minority post-2026-08-11 epoch, so a copy of any visible template would have carried it *set*. Nearest known id is Hamming distance **9 of 26**, falsifying the transcription-error hypothesis.

*Consistent with* (not metered) `pack()` having produced it — a mint that ran whose file was never written. Attributed to **budget exhaustion, not deceit**, per the rule that uses this exact defect as its canonical example.

So the protocol rests on the one surviving asymmetry: **a minted id has a FILE**, which is a fact about the tree rather than a property of the string.

## Falsifiers

Owned errors in §7: that one; an `npx tsc` exit code read **through a pipe** returning 0 when the real exit was 1 and TypeScript is not installed (**no local typecheck ran** — CI is the check); and a reflexive `git stash -u` in a worktree that hit the shared stash index the rules warn is racy (verified by content and popped, nothing lost).

`markdownlint` ignores `docs/research/2026-*-*.md`, so an rc=0 there is **vacuous** and is not claimed.

## This PR is itself an instance of #15607's bug

**The strongest evidence in the set, and a named dependency rather than a broken PR.** This body cites all six ids above in prose and carries `Task: none`. Piping it into the audit exactly as `gate.yml:2793` does:

```
task-zetaid-resolves: UNRESOLVABLE — 6 of 6 Task id(s) against 672 work-item(s).
```

Exit **1** — read directly, because reading it through `grep` reports 0, which is the same defect in a third costume. **All six are citations. Zero are declarations.**

So `cross-verify` is red here, *for the reason this PR documents*. **It goes green when #15607 lands.** Making it green any other way would mean deleting the ids — i.e. deleting the audit to turn a linter green, which is the move `lint-b-refs-resolve.ts`'s own header already refuses for the legacy scheme. A document *reporting* a defect must be distinguishable from a document *containing* one; for ZetaIds it currently is not.

If archive, it is correct and the three mislocated ids are what is out of place. My read: **let #15607 land first and re-measure** — two of four live failures disappear on their own.
