## Description

## The defect was the invocation, not the ceremony

Aaron, 2026-08-26: *"i can touch to test if you bring up touch and test how to make it human AI safe without random bash command — our zflash is close to this."*

`frost-hsm-provision.ts` shipped correct in #15564. The line an agent had to hand an operator was not:

```
export ZETA_YUBIHSM_PASSWORD=<secret>
export ZETA_FROST_PKCS11_PIN=0001<secret>
bun tools/setup/persona-keys/frost-hsm-provision.ts apply --apply
```

Two defects live in those three lines. The credential is on a command line — shell history, `ps e` for every child, any scrollback or screen share. And the **human is the secret transport**, which is precisely the job `docs/protocols/ai-human-secure-handoff.md` §3.1 says the agent must not hand back to them.

Now:

```
bun tools/setup/persona-keys/frost-hsm-provision.ts status
```

No arguments, no exports, nothing sensitive typed.

## What zflash contributed, and what it did not

`zeta flash usb` takes zero arguments because it **discovers** the newest ISO and the newest removable device, **displays** them, and gates on Touch ID. Three of those four properties transfer and are implemented here — the PKCS#11 module and the connector config are discovered, the plan is displayed with the credential redacted, and the gate is the same `pam_tid` door.

The fourth, zflash's typed `yes a3f9` nonce, is **deliberately not copied**: it guards an irreversible disk destruction against misidentification, while this ceremony's device is fixed by the plan and its act adds one object. A second consent surface beside the brief would fork the thing the human reads, which is the drift `ceremony-brief.ts` exists to prevent.

**Stated plainly because it is tempting to claim more:** `zflash-creds.md` is the credential half of that lane and it is `status: placeholder`. Its `--bake-cred name=keychain:account` source-URI syntax is designed and unimplemented — `--bake-cred` appears in no `.ts` in this repo. So zflash had *not* already solved credential resolution and there was nothing to adopt there. What it solved is the invocation shape.

## One stored secret, not two

The PKCS#11 PIN is `<4-hex-authkey><password>` — the module's own header says so and its `login-refused` remedy prints it. So the store holds the **password** and the PIN is **derived**. Half as much for an operator to keep, and no way for the two to drift apart.

## A vacuity found by running it

The shipped `status`, run against the live device with no credential, printed `reachable-unprovisioned` — the rung whose own docstring says it is reached *"ONLY by getting all the way through login"*. It was not. `C_Login` was skipped for an empty PIN, and an unauthenticated `C_FindObjects` returns nothing whether or not the key exists, so **"no such key" and "no session that may see any key" were one answer**. That is the exact conflation the module exists to remove, one rung further down. Now `login-refused`, with a falsifier that fails when the fix is reverted.

## A measured fact about the config handoff

A `dlopen`ed PKCS#11 module reads `YUBIHSM_PKCS11_CONF` with `getenv(3)`, and an in-process `process.env` assignment does not reach it. Same file, same bytes, same device:

| how the conf was supplied | result |
|---|---|
| set in the parent environment | `reachable-unprovisioned`, token `YubiHSM#39160506` |
| assigned in-process before load | `C_Initialize returned 7` (`CKR_ARGUMENTS_BAD`) |

So a freshly-written config is handed to a new process. Bounded to one level by construction: the child sees the variable set, takes the `from-env` branch, writes nothing and hands off to nobody. `needsConfigHandoff` is that decision, pulled out of the process wiring so the termination argument is testable.

## Exercised on this host — measured, not asserted

Device: YubiHSM 2, firmware 2.4.1, serial 39160506.

| step | outcome |
|---|---|
| `status`, empty store | refusal naming the three `secret-clip.sh` steps |
| operator followed them | value went dialog → Keychain **inside the subprocess**; never in the transcript |
| `status` | **rc 3**, `YubiHSM#39160506`, `MECHANISM ok` — the login genuinely succeeded |
| `plan` | `-p <redacted>`, shape legible, biometric door never opened |
| `rehearse --apply` | brief shown, Touch ID opened, **APPROVED**, no-op act ran, device read before and after: **unchanged** |
| `rehearse --without-credential --apply` | the named escape fired, gate opened, act ran, unchanged |
| `sudo -n true` | **rc 1, "a password is required"** |

That last row is the control. Without it, "APPROVED" would be consistent with a passwordless or cached `sudo` and would prove nothing about a human being present.

## Unexercised — named, not implied

- **`apply --apply` has NOT been run.** The device still holds exactly one factory auth key. No object was created, modified or deleted; the password was not changed (Aaron's standing instruction).
- **The approval is not attributable to a biometric.** `biometric.ts` reports `factor: unattributed` on this host because `pam_smartcard`, `pam_opendirectory` and an unreadable `sudo_local` include could each have satisfied the chain. The approval is real; the claim that it was a fingerprint is not observable at that seam. That is the module's existing honest register, unchanged.
- **macOS only.** `secret-clip.sh` declares its Linux and Windows backends PLANNED and exits 3 — and the remedy says so, so a reader on the wrong OS learns it from the refusal rather than from an exit code.

## The escape hatch

`--without-credential` is a `namedEscape` lifting **exactly** `secret-absent`, on **`rehearse` only**, and only because a rehearsal's act writes nothing. It carries a reason and an authorizer and is reported when it fires. `apply` has no escape and cannot acquire one without a change that shows in a diff.

## Falsifiers — each shown failing under mutation before being kept

| id | what it refuses |
|---|---|
| `HSMS-9` / `HSMP-41` | the retired env vars appearing in either module's executable text |
| `HSMS-11` | a remedy naming a verb `secret-clip.sh` does not parse (verbs read from the script itself) |
| `HSMS-12` | a remedy that exports the value instead of re-running the ceremony |
| `HSMP-50` / `HSMP-51` | an empty PIN wearing a key verdict |
| `HSMP-53` | the config handoff recursing (the termination argument) |

**The first drafts of `HSMS-9` / `HSMP-41` proved the property by SETTING the variables, and `lint-no-ambient-credential-hoist.ts` refused them.** It was right: a test that demonstrates a safety property by performing the unsafe act is not a proof, it is the act. Rewritten as comment-stripped source scans — the pattern that check names, and the same one `measure-lane-footprints.test.ts` uses.

## Adoption, recorded against the protocol's own metric

§9 of `ai-human-secure-handoff.md` says the falsifier for its productivity claim is whether the next gated operation re-derives the protocol. It did not — and it **split**, which is the useful part:

- `rehearse` uses **`runGatedCeremony`**, the composed entry point: no ladder, no idempotency question, so the protocol's body is the whole act.
- `apply` uses the **parts**, because it needs two refusals the entry point cannot express — *already provisioned ⇒ no-op and do not prompt*, and *device unreachable ⇒ refuse without prompting*. Both are §7 Step 4's "what you still have to think about yourself".

So the adoption metric must count *"re-derived the protocol"*, never *"did not import one symbol"*. Recorded in the doc.
