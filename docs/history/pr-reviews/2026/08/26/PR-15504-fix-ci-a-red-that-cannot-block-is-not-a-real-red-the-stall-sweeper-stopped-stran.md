## Description

## The defect, observed live

`toolchain-install-stall`'s `mixed-failure` guard refuses to re-run a run holding both an apt-budget install stall and another red, because re-running a real failure is how a real failure becomes a flake. That was right about failures that **block** and wrong about failures that **cannot**.

Gate run [`32886176743`](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/32886176743) (PR #15410) carried a genuine install stall in `build-and-test (ubuntu-24.04)`, the derived `gate (required)` roll-up, and a red `drift (loud)`:

```
action: skip   reason: mixed-failure
detail: "1 install stall(s) but also 1 unexplained failure(s): drift (loud) ..."
```

`drift (loud)` is deliberately outside the `gate (required)` `needs:` floor — gate.yml says so in its own comment, *"It blocks nothing"* — so **no human action could ever have resolved that verdict**. The PR sat ~11 hours, and because drift goes red often the class was not rare.

## What changed

`unexplained` is demoted to a new `non-blocking` verdict for a job that is **provably** outside the required floor. "Provably" is the whole point: the blocking set is derived from gate.yml's own `gate-required.needs:` list, closed transitively and mapped through each job's declared `name:` (`src/Core.TypeScript/ci/gate-blocking-floor.ts`) — never a hand-written roster of harmless names, which drifts silently in the permissive direction. Add a job to the floor and it reads as blocking with no edit here.

**Why it is safe, as a property rather than a preference:** a job outside the floor has no pass to launder. It blocked nothing red and blocks nothing green. The rerun re-runs it, it fails again if it is genuinely broken, its red X stays, and the decision line **names** what it carried past.

**Why it is narrow:**

- demotion applies to `unexplained` only — a stall is still a stall, a roll-up still `derived`
- only when the floor's workflow name matches the run's
- only for job names gate.yml actually declares (unknown ⇒ refuse)
- with no floor supplied the module is byte-for-byte its old self
- `continue-on-error` is **not** read, so a Windows leg inside the floor still counts as blocking — the conservative direction
- the floor is read from the sweep's own **default-branch** checkout, never from a run's head SHA, so a pull request cannot declare its own failing job harmless
