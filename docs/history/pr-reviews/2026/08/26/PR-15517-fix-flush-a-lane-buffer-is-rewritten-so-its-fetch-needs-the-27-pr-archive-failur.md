## Description

# Summary

`pr-archive-on-merge` was failing **8 of every 30 runs (~27%)**, each failure a silently undelivered archive record. Every one printed the same unreadable pair — `flush-via-staging: fetch heartbeat/pr-archive-buffer failed:` with **no reason after the colon**, then exit 3 — so across all 8 occurrences nobody could act on it.

Three defects, all in the same failure path. The first two are in `prepare`, which **all twelve telemetry lanes** call, so this was never a pr-archive bug — pr-archive is just the lane that merges often enough to lose the race visibly.

**1 — the missing `+`.** `prepare` fetched the lane buffer as `` `${candidate}:refs/remotes/origin/${candidate}` ``. A lane buffer is a *disposable aggregate*: every flush does `checkout -B staging-<lane> origin/main` and republishes, so the ref is **rewritten**, not advanced. Callers check out with `fetch-depth: 0`, so the remote-tracking ref already exists. Without `+`, git refuses the non-fast-forward update. That makes failure conditional on another PR's archive flushing between this job's checkout and its fetch — exactly the interleaved, ~27% shape observed. Forcing is *correct*, not a workaround: a remote-tracking ref exists to mirror the remote, rewrites included. `CLAUDE.md` already documents the heartbeat fetch in this form (`+refs/heads/heartbeat/*:...`); this call was the one that did not follow it.

**2 — `--quiet` hid the reason.** It suppresses git's ref-update report, the only place `! [rejected] (non-fast-forward)` appears. Removed; the error now also reports exit status and says so explicitly when git produced no output.

**3 — the 5-attempt retry never retried.** The step runs under `set -euo pipefail`. `flush` was guarded with `set +e`/`rc=$?`/`set -e`; `prepare` was not, so a non-zero `prepare` aborted on attempt 1 and the backoff, the `::error` annotation and its operator guidance were all unreachable.
