## Description

Aaron asked why kind is too heavyweight for the PR lane. Checking the claim rather than repeating it, **the premise is wrong** — and I had propagated it.

## What the registry says

> *"creates a real kind cluster named zeta-ci and installs ArgoCD plus the Gateway API CRDs, with no CI guard. That is minutes of runner time, a docker-in-runner dependency, and shared mutable state on any machine that runs it, a developer laptop included."*

## What the file actually is

**76 lines. Two `describe` blocks. Every port faked.** `ProcessRunner.run` returns `{status: 0}` without running anything; `LocalClusterDriver.create` pushes the string `"create"` to a log array; the control plane pushes strings. **No `execSync`, no `spawnSync`, no `Bun.spawn`, no `child_process` anywhere in it.**

**Measured:** the whole `dev-cluster/` directory runs **7 tests in 27 ms**. No docker. No cluster. No shared state.

## Why it looked heavy

The test's own **console narration**. `bringUpKindCiCluster` logs `Creating kind cluster zeta-ci …`, `Installing ArgoCD …`, `Installing Gateway API CRDs …` — and the injected fakes return success. So the CI output reads exactly like heavy real work while **nothing happens**.

That's this session's recurring defect class **inverted**: not a check that didn't run looking like it passed, but **a check that ran cheaply looking like it did heavy work** — and getting quarantined for it.

Removed from both `bunfig.toml` `pathIgnorePatterns` and `registry/unexecuted-test-files.json`. `cluster/` now runs **75 tests in 5.27 s** in the normal suite.

## Second finding, filed not fixed: `081KZYXRYR8087G0R003E6JZA4`

The checker shipped in #10473 walks the **working tree**, including gitignored `dist/` (`.gitignore:7`, 0 files tracked). On a machine that has built, it exits **1** with four `dist/…` complaints — **CHECKED on unmodified main**.

So it's **green in CI and red for everyone who might fix what it finds**, which is the worst polarity for an adoption-dependent tool.

The fix is to walk the **tracked** set — which is the reasoning already written into `build-graph.ts` (#10395): *"derived from the tracked set, so `derive` is identical on every checkout — a working-tree walk would have picked up caches and made it machine-dependent."* Same defect, same fix, one subsystem over. Filed rather than bundled.

## On the original question

kind-in-Docker isn't inherently unaffordable for a PR lane — but that's moot here, because **this test never needed a cluster at all.** The real k8s surface has its own weekly lane (`k8s-argocd-health-test.yml`, `cron: 43 16 * * 0`).
