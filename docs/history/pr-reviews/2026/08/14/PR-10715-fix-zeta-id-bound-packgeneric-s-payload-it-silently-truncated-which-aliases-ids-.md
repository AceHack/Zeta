## Description

## What this changes

`packGeneric` silently truncated an oversized payload. It now throws.

**This is a behaviour change, not an addition** — from silent corruption to a loud error. That is the change we want, but it needs the caller audit first, so that is where this starts.

> **Base is `main`.** #10690 merged at 20:32:10Z while this was being written (squash `ca8f45e492`) and its branch was auto-deleted, so this was re-cut from `origin/main` rather than rebased off a stale base. Standalone — no dependency.

## Caller audit — every `packGeneric` caller in the repo

| Oracle | Surface | Callers |
|---|---|---|
| **TS** | `packGeneric` | **`inventory/new-item.ts:25` — the only production caller, and it bypasses the validating wrapper. This is the hole.** |
| TS | `packPayload` | validates the 119-bit cap **before** delegating here — unaffected |
| C# | `PackGeneric` (public) | only in-repo caller is the private, validating `PackGenericPayload` |
| F# | `packGeneric` (public) | only in-repo callers are inside `packPayload`, which validates |
| Rust · Python · Go · MUMPS | — | **no generic-pack surface at all** |

### Does any caller currently exceed the cap? **No.**

So the bound is **inert for every id that can be minted today**. But the headroom is **zero**, not comfortable — which is the finding worth more than the bound:

```
new-item.ts builds  (BigInt(Date.now()) << 78n) | random78

  today                       ms=1786739730571   payload = 119 bits   AT the cap
  both on-disk inventory ids                     payload = 119 bits   AT the cap
  last ms before the cliff    ms=2199023255551   payload = 119 bits   AT the cap
  2039-09-07T15:47:35.552Z    ms=2199023255552   payload = 120 bits   was truncated
```

The design consumed the entire payload. One more bit of clock overflows it.

## The failure, stated concretely because a reader in 2038 needs a falsifier

> **At `2039-09-07T15:47:35.552Z`, `Date.now()` reaches 2^41, the top ms bit is masked off, and `packGeneric(ms = 2^41)` returns an id BYTE-IDENTICAL to `packGeneric(ms = 0)`** — a wrap to 1970 and a real collision with any zero-ms id, silently, forever.

Verified, and now a test. Not "a potential overflow."

## Scope

Three things, nothing else:

1. **The bound** in `packGeneric` (plus negative payloads — BigInt masking makes `-1n` indistinguishable from all-ones, the same aliasing class).
2. **A test that the 2039 boundary is rejected** rather than silently aliased, and that the last ms *before* it still mints — the bound fires at the boundary, not before.
3. **The existing documenting test updated**: `"packGeneric does NOT bound the payload — the truncation is real"` → `"packGeneric now BOUNDS the payload — the 2039-09-07 truncation is fixed"`. It asserted the defect; it now asserts the remedy.

`inventory/new-item.ts` is **unchanged**. Its mint is correct (established in #10690's retraction) and needed no offset change; what it needed was for the primitive underneath it to refuse instead of truncate.

## Inertness, proved against real data

Not an invented vector: both ids already committed under `inventory/items/` have their payload recovered and are **re-minted through the bounded path, byte-identical**. Each is exactly 119 bits.

## Parity gap — named, deliberately not bundled

**C# `PackGeneric` and F# `packGeneric` are public and still truncate silently.** Neither has a direct production caller today — every in-repo path goes through the validating wrapper — so the exposure is a *future* caller making exactly the mistake `new-item.ts` made. Fixing four more oracles is the bundle I was asked not to build, so it is recorded here rather than done.
