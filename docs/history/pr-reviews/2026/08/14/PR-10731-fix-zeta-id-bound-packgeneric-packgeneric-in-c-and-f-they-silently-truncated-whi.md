## Description

## What this changes

`PackGeneric` (C#) and `packGeneric` (F#) silently truncated an oversized payload. They now throw.

**This is a behaviour change, not an addition** — from silent corruption to a loud error. It is the parity half of #10715, which bounded the TypeScript peer and **deliberately did not bundle these**, recording the gap instead:

> C# `PackGeneric` and F# `packGeneric` are **public** and **still truncate silently**. Neither has a direct production caller today, so the exposure is a future caller making exactly the mistake `new-item.ts` made.

> **Note on base:** #10715 is still **open**, so the TypeScript bound is not on `main` yet. This branch is cut from `origin/main` and is **standalone** — it touches no TS file and has no dependency on #10715 landing. The two can merge in either order.

## The failure, stated concretely because a reader in 2038 needs a falsifier

The 128-bit Generic layout gives the payload **119 bits** (65 low + 54 high). Both codecs masked rather than validated.

> **At `2039-09-07T15:47:35.552Z`, a caller building `(ms << 78) | random78` reaches `ms = 2^41`, the top ms bit is masked off, and the id is BYTE-IDENTICAL to the same call with `ms = 0`** — a wrap to 1970 and a real collision with any zero-ms id, silently, forever.

Reproduced against the pre-fix code in **both** oracles, not argued:

```
F#  cliff=080000000000A0000000000000  ms0=080000000000A0000000000000  IDENTICAL=true
C#  cliff=080000000000A0000000000000  ms0=080000000000A0000000000000  IDENTICAL=true
```

Not "a potential overflow." A dated collision, and now a test.

The design consumed the entire payload. One more bit of clock overflows it, in any language that grows a caller writing that expression.

## Three corrections to the brief I was given

1. **The negative-payload aliasing class does not exist here** — I was asked to close it "if the language admits it," and it does not. On the TS side `payload` is a signed `bigint`, so masking made `-1n` indistinguishable from all-ones. In C#/F# the parameter is `System.UInt128`, **unsigned** — a negative cannot be admitted at all. What a caller *can* still do is reinterpret `-1`, and `unchecked((UInt128)(-1))` is exactly `UInt128.MaxValue`, the same all-ones pattern. **That** reachable analogue is what the test pins, in each oracle. Saying "fixed the negative case" would have been a claim the types cannot support.

2. **The four-oracle report was re-verified, not inherited.** Rust, Python, Go and MUMPS expose only the structured `pack` — zero hits for `generic` or `119` anywhere in their ZetaId sources. #10715 was right; nothing belongs in this PR from them.

3. **#10715 is still open**, so `main`'s TypeScript `packGeneric` is *also* still unbounded as of this writing. The brief described the TS bound as landed. It isn't yet — which only strengthens the case, since all four remaining generic-pack surfaces currently truncate.

## Cross-verify tells you nothing here — in either direction

Independently confirmed rather than taken on trust: **all 16 byte-lock vectors are category 0 or 3**, both `< 9`, so every one routes to the observation `pack` and none reaches `packGeneric`. A green cross-verify is **not** evidence this bound works, and a red one would **not** be evidence it broke something. The evidence above is targeted, which is why.

## Scope held

`inventory/new-item.ts` and every other minting site are **unchanged**. Nothing was "aligned." What the mint needed was for the primitive underneath it to refuse instead of truncate.
