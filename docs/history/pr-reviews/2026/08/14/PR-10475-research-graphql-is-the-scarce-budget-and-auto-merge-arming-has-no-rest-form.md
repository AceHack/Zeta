## Description

Aaron: *"we also want to avoid using graphql everywhere possible that's what rate limits us … another reason for moving away from the PRs asap"*

Correct, and measurable rather than a matter of taste.

## The measurement

```
core    (REST):    24 used / 5000
graphql        : 1111 used / 5000   ← 22% of the hourly budget
```

**~46× faster consumption on GraphQL.** The budgets are separate — REST counts *requests*, GraphQL counts *points* scaled by query complexity — so a workload can look idle on REST while approaching GraphQL exhaustion.

| call | GraphQL points | returns |
|---|---|---|
| `gh pr view N --json state,mergeStateStatus` | **2** | state, merge state |
| `gh api repos/O/R/pulls/N` | **0** | the same three facts |

**Self-implication, since it's the largest identified contributor:** the autonomous tick loop polls 4–6 PRs per tick with `gh pr view` *and* `gh pr checks` — both GraphQL — on a ~2-minute cadence, plausibly most of that 1111. **The monitoring was more expensive than the work it monitored**, and it was invisible because REST looked idle.

## The structural point

**`enablePullRequestAutoMerge` exists only as a GraphQL mutation — there is no REST endpoint.** So arming auto-merge *cannot* be made cheap; the only way to avoid the cost is not to do it.

Which converges with today's heartbeat failures. `society-heartbeat` fails every run on exactly that call — and the same operation is (a) what the scoped PAT can't perform, (b) GraphQL-only and un-cheapenable, and (c) **not load-bearing**, since the flush already succeeded before arming is attempted. **Three independent reasons to remove one call.**

## Why it's another argument for moving off PRs

**A PR is a GraphQL-shaped object** — create, check state, check checks, arm merge — and its most useful operation has no cheap form. A flush to an **ungated branch** needs no PR and therefore no GraphQL: a git push plus at most a REST merge. `heartbeat/*` is already ungated and already used this way, so the cheap path exists today; the expensive one is habit plus the gate on `main`.

## Limits, stated

- The 1111 is a **snapshot, not an attribution** — other sessions share the budget; the tick loop is the largest *identified* contributor, not a proven majority.
- **REST is separately budgeted, not free.** At 24/5000 there's headroom, but a design assuming REST is unlimited fails later the same way.
- `mergeable_state` can return `unknown` while GitHub computes it — a REST poller must retry, not treat it as a state.
