## Description

## Summary

Retires the PR-archive pairwise-conflict class in production, wires the drift gate that
was never wired, and drains the archive queue. `081KZYP7MNV087G0R002X0E3V9`.

The sharding migration (#10427) made the per-PR shard the ledger and demoted
`manifest.jsonl` to a derived index -- but the on-merge archive COMMIT still staged the
manifest, so every archive PR still mutated one shared file. Measured at the start of
this round: 26 open archive PRs, 13 CONFLICTING. By the end: 30.

## Proof, with a control

Two archive commits branched from one `origin/main`, real repo, real shard bytes from
`serializeShard`:

| shape | `git merge-tree --write-tree` |
|---|---|
| control -- each appends its manifest line (what ships today) | **exit 1, CONFLICT (content) in `docs/github/prs/manifest.jsonl`** |
| fixed -- each writes only its own shard (this PR) | **exit 0, clean** |

The control is the load-bearing half: it shows the conflict is the manifest write, not
the archive path. The shard path is an invertible function of `pr_number`, so two
archive commits cannot address the same file.

The new staging step was also run verbatim against a dirty tree: it stages the shard and
the markdown, and `git restore` leaves the manifest neither staged nor dirty.

## What maintains the derived index, and how stale it gets

`agent-heartbeat.yml` soraya archive duty -- already the only serialised writer of
`docs/github/prs/`: one duty holder, workflow concurrency group with
`cancel-in-progress: false`, branch hard-reset from `origin/main` every tick. It now runs
`derive-pr-manifest.ts --write`: a full regeneration from the shard store, not the per-PR
upsert the archival tool does, because the shards needing indexing were written by other
runs entirely.

**Staleness bound: about one hour** (flush gate `MIN_INTERVAL_SECONDS=3000`), plus
GitHub scheduled-run delay. Stated in the workflow, in the commit, and here, because a
knowingly-stale index is fine and a silently-stale one is not. A reader needing the
current set reads `docs/github/prs/shards/` or runs the deriver.

## The drift gate now runs

`derive-pr-manifest.ts` was referenced by no workflow, and `src/Core.TypeScript/forge-host/`
is in no `bun test` path, so its 109 tests never ran either. Main sat in derive-drift for
an hour after #10427 and nothing reported it.

New `pr-manifest-integrity.yml` runs both, 4x/day plus on PRs touching the tooling, and
splits the verdict by what is legitimate:

- **shard-store integrity failure** (unreadable / misfiled / duplicate-keyed) -- always fails. Never by design.
- **index drift** -- fails on the schedule (6h is far past the 1h repair bound, so drift there means the cadence stopped); reports only on a `pull_request`, where the drift belongs to main and not to the contributor.

`gate.yml` is untouched on purpose -- the 612-test-files problem is #10429 and the two
changes must not collide.

## The 30 open archive PRs: superseded, not merged

Every one carries a manifest line and **no shard** -- verified on #10456, opened after
#10427 merged, containing only `manifest.jsonl` plus the markdown. Merging them would
write 30 index entries for records that do not exist. That is exactly how main got into
drift: #10442 landed that way, and its missing shard is back-filled here by the
re-runnable migrator (`added=1 replaced=0 noop=6340`, round trip byte-identical).

So they are superseded: every subject PR is re-archived here through the fixed shape
(shard + markdown), the index regenerated from the shards, and shard coverage verified
for all 30 subjects **before** any PR was closed. 6411 entries, deriver green.
