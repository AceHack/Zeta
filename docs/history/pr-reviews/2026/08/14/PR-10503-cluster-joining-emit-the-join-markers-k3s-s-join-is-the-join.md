## What landed

**`full-ai-cluster/nixos/modules/k3s-join-observer.nix`** — the witness. It implements no join: it watches the k3s agent-to-server handshake `services.k3s.{serverAddr,tokenFile}` already performs and writes the two contract markers to the console and `/dev/ttyS0`. Imported from `k3s-agent.nix` only — the `--cluster-init` founding server joins nothing, and a witness there would announce a join that never happened.

The two markers are two **independent** facts, because an assertion that cannot fail on its own is not an assertion:

| marker | fact | fails independently when |
|---|---|---|
| `cluster join successful` | the server issued this node a kubelet client cert AND the API accepts it | wrong token, missing `--tls-san`, closed 6443 |
| `joining-node added to the cluster state` | the API server's node registry contains this node (`metadata.uid`) | cert is valid but the kubelet never registers |

`Ready=True` is deliberately **not** claimed — it needs the Cilium image and therefore the internet, and conflating *joined* with *healthy* would silently widen the claim. Membership here, health in the online lane.

**`full-ai-cluster/nixos/tests/k3s-agent-join.nix`** — the falsifier. Two nodes on one shared virtual segment, built from the **shipped** `k3s-server.nix` / `k3s-agent.nix`, k3s's own `node-token` handed over, and both markers awaited on the **serial console** — the same channel the zflash harness reads. Wired into `build-ai-cluster-iso.yml` ahead of the ISO build.

## Can a Compose test fail in a way that is our fault?

**Yes in principle — #10493's stated reason was wrong once the premise changed. But a container cannot consume our configuration, and that is the answer.**

Our config is NixOS module attributes (`extraFlags`, `allowedTCPPorts`, `checkReversePath = false`, `networking.hosts`). A Compose `command:` would have to **transcribe** them, and a transcription drifts from its source with nothing failing — so the test verifies the transcription, not the shipped artefact.

| | Compose (#10493's proposal) | nixosTest (landed) |
|---|---|---|
| consumes the shipped config | no — a transcription | **yes, imports the module** |
| exercises `--tls-san=control-plane` | only if transcribed | **yes** |
| exercises firewall / rpfilter config | **not expressible in a container** | yes |
| observes the serial contract markers | no | **yes** |

So the container layer is **not vacuous — it is dominated here**, and adding it would buy a drift surface for no coverage. Revisit only if we ever need a join tested where a NixOS VM cannot run.

## The tripwire fired, and was inverted rather than deleted

#10493's promotion tripwire was built to fail the day a join landed. **It fired within a day, as designed.** It now asserts presence, because Nix cannot import `serial-markers.ts` — the marker literals live in two files with no compiler between them, and this scan is the only thing that notices drift.

Its limits were **measured by mutation, not assumed**:

| mutation | probe test |
|---|---|
| drop one space from a marker | **FAILS** |
| delete `k3s-join-observer.nix` | **FAILS** |
| keep the literal, delete the emit line | **PASSES** — the honest gap |

That third row is the limit of a text scan, is documented in the test, and is exactly why the nixosTest waits on the real console. Neither check subsumes the other.

Also: `DEFAULT_MULTI_VM.joinProtocol` was `credential-provisioning` pointing at a cred-picker endpoint that does not exist and will not be built. Changed to `explicit-join-token` at `/var/lib/rancher/k3s/server/node-token` — the join that actually happens.

## k8s lane cadence: weekly → **daily** (`53 16 * * *`, was `43 16 * * 0`)

Chosen against measured cost and measured drift (full reasoning inline in the workflow):

- **Billable cost is ZERO — checked, not assumed.** The repo is PUBLIC, and `GET /actions/runs/31754638408/timing` reports `billable.UBUNTU.total_ms = 0` across all 4 jobs of a 12.6-minute run. The real costs are concurrency slots and the attention a failure consumes.
- **Everything is pinned in-repo** (kind 0.31.0, kubectl 1.36.1, helm 4.2.0, argo-cd 7.7.10, Gateway API v1.2.1 vendored). What is **not** pinned is the substrate underneath: the `ubuntu-24.04` runner image, live registry/helm-repo availability, and main-branch changes outside the `paths` filter — `tools/setup/**` is notably absent from it.
- Those drift on the order of **a day**. Weekly gave a mean time-to-detect of ~3.5 days against a ~1-day drift period — the wrong way round. Daily brings it to ~12h.
- **Why not more often:** sub-daily would re-measure unchanged substrate and multiply failure noise without shortening detection below the drift period.

Minute `53` is off `:00`/`:30` and unused elsewhere in `.github/workflows`; 16:53 UTC is mid-morning US Pacific so a failure lands when someone can read it.
