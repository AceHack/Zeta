## Description

Closes `081KZZ3Q990087G0R003QXYVN6`.

`workitems/done/index.jsonl` was a single shared append-only file every completion wrote to, so concurrent completions conflicted pairwise — three hand-union-resolved rebases on 2026-08-13 (#10516, #10541, one earlier).

## Which of the three options, and why

**Option 3 — remove it.** The sharding half of the usual remedy was *already in place*: `done/YYYY/MM/<zetaid>-*.md` is one file per record whose path is a function of the ZetaId, so two writers cannot select the same path and a duplicate is unrepresentable. The only defect was the stored derived aggregate sitting on top of it.

**CHECKED evidence for dropping rather than deriving:**

| finding | measurement |
|---|---|
| readers | **zero.** `rg "done/index.jsonl"` finds one code site and it is the `appendFileSync` *write*. DORA folds read `workitems/events/`; the CLI's own `resolvePath` walks the tree. |
| staleness | **36 index lines vs 76 done items** — 40 completions never indexed, two months of unnoticed drift |
| information content | **none of its own** — all four fields (`id`, `path`, `completed`, `title`) are projections of the done file; a test pins that |

**And `derive-pr-manifest.ts` does not generalise with a small parameterisation.** `pr-manifest-shards.ts` is PR-shaped throughout: `ManifestEntry.pr_number`, `shardZetaId`/`prNumberOfShardId` as an invertible function of the *PR number*, hex-32 JSON shard files bucketed by `pr_number/1000`, a PR-field validator, hardcoded root constants. Serving a markdown-with-frontmatter, month-bucketed store means generifying six seams. That — or a hand-rolled second copy — is the wrong trade for a file with no readers, exactly as the work-item said up front.

Need the list? Walk `workitems/done/**/*.md`. That walk is the index and it cannot drift.

## The concurrency proof has a control

`src/Core.TypeScript/backlog/complete-workitem-concurrency.test.ts` runs the *same* two-concurrent-completions fixture over real `git` twice, differing only in whether the retired append happens:

- **TREATMENT** (what the code does now) — both merges succeed, two disjoint records land, no aggregate exists.
- **CONTROL** (the removed line, reconstructed inline in the test) — the second merge fails with `CONFLICT` naming `workitems/done/index.jsonl`.

A demonstration without a control proves nothing, so the control is the load-bearing half.

## Migration is lossless, and measured with a real JSON parser

Not a shell pipeline — the PR-manifest migration's "3 malformed lines" premise turned out to be an `echo` artifact in the *measuring* step. Round-trip over all 36 lines: **0 unparseable, 0 duplicate ids, 0 orphans**.

Four items carried a `completed` timestamp that lived **only** in the index; those are backfilled into the records' own frontmatter here, so nothing is dropped. One index line also held a stale pre-ZetaId-renumber title — the file is the newer truth.

**Surfaced rather than swallowed:** 32 done items have no `completed:` frontmatter, and 28 of those had no index entry either — their completion instant is in neither surface. `workitems/events/` and git history hold the truth; not invented here.

## §12 idempotency

Re-completing a done item is refused on its terminal state, and a record is *addressed* by its ZetaId rather than accumulated — where the retired append would have produced a second line for the same id. Both are tested.
