## Description

Closes the hole this whole thread was for.

`checkKskAuthorization` counted distinct rostered signers and **verified nothing** — the source note said verification was *"deferred to a follow-up slice"*. So the gate answered *"were enough distinct names supplied?"* rather than *"did enough authorized parties consent?"*, and **any caller able to fabricate bytes passed** — on the emergency bypass of the consent gate for a kinetic safeguard.

It now delegates every decision to `MultiSignatureVerification` (derived three times independently under a clean-room wall, synthesised against the amended spec). The KSK-shaped types stay — roster, threshold, scope — because that's the vocabulary callers speak. **The judgement is no longer made here.**

**No parallel path.** There were no production callers, only tests, so the sound path became *the* path rather than an opt-in beside an unsound default.

## Why the old tests passed

The previous suite used a single zero byte as a stand-in "signature" and was green. **That it was green is the whole point:**

> A gate that verifies nothing cannot be distinguished from a gate that verifies everything, by any test that only supplies well-formed-looking input.

The lead test is now the exact input that previously returned `Authorized` — two genuinely rostered signers, 64 zero bytes each — which returns `InvalidSignatures`. Its discriminator is the identical shape with **real** signatures, which authorizes.

Also covered: one flipped bit rejected as *invalid* rather than a short count · a genuine signature over a **different payload** refused for this one · off-roster signers not counting even with valid signatures · two travelers legitimately disagreeing on one request · a never-authorizing policy surfacing as a config error.
