## Description

Fixes `081KZMGZTB508QG0R003F8AXYQ`. `checkKskAuthorization` used `config.Signers` only for its `.Length` — so **three fabricated identities under a size-3 roster returned `Authorized`.**

Adds `UnknownSigners` as its own explaining result, and orders the checks so duplicates are caught before anything counts them: **submitting one signer N times must never look like N signers.**

## Your design point made it the right shape, not just a patch

**Each traveler has its own trusted roster.** There is deliberately no global one — that is **R11** (per-principal trust, no mandatory central authority) applied to authorization. The consequence is documented because it *looks* like a bug and is not:

> **Two travelers may reach different verdicts on the identical request, and both are correct.**

A single mandatory roster would be a hub — the same capture this substrate refuses everywhere else. There is a test asserting exactly that disagreement.

## Algorithm agility

Recorded per your point: the scheme belongs behind a **port** — hexagonal, pluggable, rollable keys in case an assumption goes bad. A PQ choice today bets on a hardness assumption holding for decades, and that bet should be revisable without a migration event.

**The mechanism already exists:** `KeyCustody`'s three-slot ladder makes **algorithm migration just a key rotation whose `next` slot carries a different scheme** — and its bounded `previous` acceptance window is precisely the hybrid transition a PQ migration needs, with no coordinator to sequence the cutover.

## Still deferred, now stated precisely

Signature verification. The gate asks *"did enough distinct, rostered parties submit?"* — **not** whether the bytes are valid signatures over this scope. Until that lands it is not sound against a caller who can fabricate signature bytes.
