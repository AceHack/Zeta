## Description

## The missing corner, closed at one site

R-1a (#11660) measured that the four-corner shape is **real code in four languages with a byte-locked
treaty and laws tests, and that nothing at a tick boundary runs on it**. What a tick runs is
`RunK : InterruptKind -> ISR<'S,'S>` — In, Out, and an error-position Out-Feedback that short-circuits
rather than carries. The absent corner is **`T Feedback In`**, and `ReceiptScheduler`'s
`onReceipt : (Receipt -> unit) option` is the hole standing in for it.

Order kept: **research → architecture plan → code.**
Plan: `docs/research/2026-08-17-t-feedback-in-the-co-owned-fourth-corner-at-the-tick-boundary.md`.

## What `T Feedback In` means at a tick

`FourCorner.fs:27-29` says the corner is **co-owned — BOTH sides contribute**, *"each side's
contribution is the other side's backpressure."* So it is **not** "the consumer's response"; that
would be a second input. It is:

> a value **both sides write to and both read**, carried across ticks **by the driver** instead of by
> a closure.

The survey found six shipped flows of exactly that shape with nowhere to put them:

| what flows backward | where it goes today |
|---|---|
| the `ComputeReceipt` | `onReceipt : Receipt -> unit` — a hole |
| a distress signal | `TelemetrySource.signalIfOverloaded` **returns** an `InterruptKind` it cannot deliver; a caller must smuggle it into the `Source` |
| a budget revision | arrives disguised as an `OperatorMessageArrived "metric:…"` payload |
| a retraction | `WSet.negate` — implemented in `FourCornerTrace`, not reachable from a tick |
| a memo from a prior run | `Chip8CrossRunStore.Reader` — **the positive control**: a real backward flow that is *not* a hole, because it is an injected parameter |
| a late/corrected input | the GGPO rollback `IntrCtx.fs:54-63` already reasons about |

That fixes the design's one real constraint: **if both sides write, neither may overwrite** — so the
corner needs an associative merge with an identity.

## The type (all additive — `Handler`, `HandlerK`, `drive`, `driveK` untouched)

```fsharp
type CoOwnedCorner<'F> = { Empty: 'F; Merge: 'F -> 'F -> 'F }        // Merge MUST be associative
type HandlerF<'S,'F>   = { Name; Matches; RunF: InterruptKind -> 'F -> ISR<'S, 'S * 'F> }
val  driveF            : CoOwnedCorner<'F> -> HandlerF<'S,'F> list -> Source -> ISoftScheduler<'S * 'F>
```

`driveF` returns the **existing** port at `'S * 'F` rather than a new one, and that is load-bearing
rather than tidy: the corner lands inside the value `TickBoundaryProbe` compares, so information
travelling on it is *observable to the instrument* — which is precisely what an unread `-> unit` sink
is not (TICK-4, blind spot #1).

**A record and not an `interface`, and the reason is recorded.** `interfaces-free-classes-earned`
puts the interface first and this started there. F# rejects a generic abstract member instantiated at
`unit` (`FS0017`), which kills `unitCorner` and with it the whole opt-in migration path. The record is
the same weight-free shape — no instance state, exactly what `Handler`/`HandlerK` already are in the
same file. No class is earned and none is introduced.

## Is it one object with `WSet.FourCornerTrace`? — yes, and here is where it stops

- **Compiler-checked:** `SoftScheduler.toFourCorner` returns the very
  `FourCorner.FourCornerOwnership` record `FourCornerTrace.toFourCorner` returns. Same type
  constructor, two instantiations; nothing new defined (**FIN-5b**).
- **Behaviourally checked:** `CoOwnedCorner` at `Empty = []`, `Merge = WSet.plus >> consolidate` **is**
  the trace's emission monoid (`WSet.fs:293`), so a handler contributes `[7, −1]` and annihilates an
  earlier `[7, +1]` — the corner consolidates to **empty**, not to a zero row (**FIN-4**).
- **Where it stops, stated rather than rounded up:** the tick boundary is **not yet** a
  `FourCornerTrace`. The trace's invariant `Emitted = consolidate (gen after history)` needs `'S` to
  be an `('I, 'H)` pair, and a room's state is advanced forward, not reinterpreted. That is a state
  split, not a rename.

## Migration — the eleven other `RunK` rooms do not move

## `clis/` — do the two converge? Plainly: no

Nothing under `clis/` is touched. On whether the verb family's **free structure** and the tick
boundary's four corners are the same object:

- A **traced** monoidal category is a monoidal category **with added structure**, not a quotient of
  one. So the verb family's free monoidal category would be the object the four corners add a trace
  **to** — `free → traced` is a real arrow between them and **not an identity**.
- Claiming otherwise on the strength of "both are monoidal" is a **count, not an invariant**
  (`numerology-vs-number-theory`).
- And the practical blocker outranks the theory: `clis/Verbs.fs` is in no project and does not
  compile, so **no compiler can check any claim about it today.** Recorded as a coincidence with its
  register attached, not as a belief.

## One correction to the framing I was handed

The brief describes the missing corner as *"the consumer's response to the previous result."*
`FourCorner.fs` says something stronger and the whole algebra turns on it: the corner is **co-owned**.
A corner only the consumer writes is a second input, not the fourth corner — and it would not need a
monoid, which is the part that makes the design non-trivial.
