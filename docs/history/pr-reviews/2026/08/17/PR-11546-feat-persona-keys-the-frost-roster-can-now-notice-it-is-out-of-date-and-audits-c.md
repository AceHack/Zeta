## What it could not do: notice that it was stale

`checkRoster` and `verifyRosterAgainstArtifacts` compare a declaration against artifacts.
Both can agree **perfectly** while the shares have been re-issued underneath them -- every
artifact the roster names is present, correctly bound, right tier, right ca. `verify`
printed `OK` for a custody set whose secret had moved.

That is the same shape as the `foldChain` defect in **#11510**: "current" was reachable by
not having heard anything. FTR-34 asserts both halves in one test -- the artifact checks are
clean *and* the chain check refuses.

### `checkRosterAgainstEpochChain(roster, fold)`

The roster's pinned group key against the **threshold-signed** epoch chain
(`key-epoch-ledger.ts`). Refusals: `roster-key-not-current`, `roster-chain-forked`,
`roster-key-unreadable` -- an unreadable pin is **refused, not skipped**, because a
comparison that cannot run must not report agreement (#11485's shape: an entry that cannot
be checked does not pass as checked).

`ChainFold` is imported **type-only**, erased at runtime, so this module still holds no key
material and verifies no signature itself. The caller folds from a pin it actually trusts;
a fold from an attacker-chosen pin proves nothing, and the header says so.

### `retiredIndices` is explicitly NOT an identity blocklist

The trap #11510 named. A participant index is a **slot, not a party**: retire slot 3 at
epoch 1, re-issue it at epoch 2, and the chain's grow-only union still contains 3 while
slot 3 holds a live share. A blocklist over a set that never forgets would refuse a correct
roster permanently, with no later evidence able to clear it. So a declared index in the
union is reported at `info`, never as an error. **FTR-37 is that exact two-rotation
scenario**, built from two real signed transitions, and flipping the severity to `error`
kills it.

The 8 new tests use real `frostKeygen` + `runDeltaRotationInProcess` + `signTransition` --
the refusal in FTR-34 is produced by a signature a party below the old threshold could not
have made, not by a hand-written fold. FTR-40 anchors that: flip one signature byte and
`admit` drops the element, so the chain stays at the pin.

## En route: the revocation ledger was invisible to every audit

`rg 'foldChain' key-epoch-ledger.ts` printed **`binary file matches`** and **exit 0**. Two
raw NUL bytes in a template literal made the highest-audit-value file in the key stack read
as binary -- ten real matches invisible, and a clean exit to anything consuming the output.
A check that did not run, looking exactly like one that passed.

`frost-token-roster.ts` **already documented this hazard**, in a comment sitting beside its
own escaped separator. It was a convention, and a convention nobody checks is the vacuity
class: **ten tracked files** carried raw NULs, including `treaty-rule-alternatives.ts`,
which is itself an audit tool. Note the diff: files whose NUL sits in the first 8 KB show as
`Bin` (git called them binary); those past 8 KB show as ordinary text -- which is exactly
why review never saw it.

All ten are now escaped (byte-identical at runtime, file stays searchable), and
`audit-no-raw-nul-in-source.ts` enforces it as a `gate.yml` step beside
`audit-proof-lineage-binaries.ts`. The rule is total and needs no allowlist, because a raw
NUL in source is never load-bearing.

**I introduced the same defect four more times while writing the audit that forbids it**
(twice in the audit source, once in the workflow comment, once in a draft of this PR body --
the tooling refused that one). That is the argument for the gate, not against it.

## Enforced vs bookkeeping -- said plainly

**ENFORCED by cryptography.** Which token may open a share: `sealedByToken` is in the AAD
*and* the in-plaintext bind string, so a different token fails the unseal. Which group key
is current: transitions are threshold-signed by the old quorum and `foldChain` follows only
signatures it verified from a held pin.

**BOOKKEEPING.** The roster **file**. It is unsigned JSON a human writes. This apparatus can
now prove a roster is **stale**; nothing here proves a roster is **authorised**. `location`
is decoration.

## Custody decision surfaced, not taken

**Who may change a roster, and what signs the change.** A threshold-signed roster is the
natural next object -- it would make the roster an artifact *of* the custody set rather than
a note *about* it. That is a decision about authority, not an engineering choice, so it is
left open rather than decided in code.

## UNVERIFIED

No FROST hardware, no YubiKey, no TKey, no reader on this machine. The multi-token hardware
lane (`pkcs11-multi`, HW-6 to HW-12) still cannot run. Everything above is the CI-safe lane.

**A named limit, not implied away:** a `zeroDelta` proactive refresh preserves the group key
and revokes nothing, so a pre-refresh artifact is field-identical to its replacement in ca,
x, threshold, groupPublicKeyHex and sealedByToken. **No discriminator exists in any
artifact**, so this check cannot see that staleness and the module header says so. Closing
it needs a refresh-generation field in the sealed-share AAD -- a schema change and a
separate item. Destroying superseded artifacts remains the operative control, and that
control is a ceremony, not a check.
