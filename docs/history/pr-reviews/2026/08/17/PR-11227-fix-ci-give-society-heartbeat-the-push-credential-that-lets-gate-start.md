different job (`gh` PR creation) and was never the missing half.

# Notes

**The control was read out, not deleted.** #11034 treated `tick-metrics` and left this lane
byte-identical on purpose. Same day, one repository, ~10 minutes apart:

```
heartbeat/tick-metrics  00:14Z + 00:32Z  (TREATED)             gate actor=AceHack,             EXECUTES
heartbeat/society       00:21Z           (UNTREATED CONTROL)   gate actor=github-actions[bot], PARKED
```

One variable, two lanes, one hour. That is the attribution the control existed to buy, and
it is spent here.

**Refined mechanism, from what `red-state` showed.** A run's actor is the identity that
produced the event. `pull_request` **opened** comes from `gh pr create` (the PAT → AceHack);
**synchronize** comes from the `git push`. So a lane whose flush PRs land always opens a
fresh, executing PR — and a lane whose PR is stuck open sends every later flush as a
`GITHUB_TOKEN`-actored synchronize, which parks. That is self-sustaining: parked gate →
unmergeable PR → never re-created → next flush is another synchronize. Society sat in that
loop for three days.

**`red-state` stays UNTREATED, and the test now says why.** It is not a control showing the
defect — the defect there is **latent**. 92 `pull_request` runs, only 12 parked and all 12
dated 2026-08-14; its flush PRs merge (#11067, #11010, #10872, #10870, #10858 all landed
2026-08-16), so it never reaches a synchronize push. It returns the moment one of its PRs
stalls. Treat it on a stall or with its own before/after reading — not blind.

**No gate-dispatch belt.** A `workflow_dispatch` gate run's checks never enter the PR's
`statusCheckRollup`, so they cannot satisfy the required check; that belt was measured inert
and removed, and nothing here re-adds it.

**The real-tick falsifier is not yet observed.** The lane runs from `main`, so the first run
under this change happens after merge. This PR claims the defect and the mechanism, not the
cure. What to check ~30 minutes after merge, and what would falsify it:

```
gh api "repos/Lucent-Financial-Group/Zeta/actions/runs?branch=heartbeat/society&event=pull_request&per_page=100" \
  --jq '.workflow_runs[] | select(.name=="gate") | "\(.created_at) \(.status)/\(.conclusion) actor=\(.actor.login)"'
```

Expected after: `actor=AceHack` and a `gate` run that **executes** (any conclusion), plus a
`gate` row appearing in #10708's rollup. Still `action_required` with
`actor=github-actions[bot]` ⇒ this reading is wrong and should be said so out loud. A
`::error title=society PAT cannot push::` annotation instead ⇒ the PAT lacks
`Contents: read and write`, the lane degrades rather than dies, and the fix is a scope grant.
