## Description

## The defect (measured, not reported)

Three PRs whose diffs had nothing to do with a theorem prover — **#11470, #11472, #11475** — failed `lint (tick-shard relative-paths)` on 2026-08-17. Confirmed from the job log, not the brief:

```
lint (tick-shard relative-paths)  Install toolchain ...  curl: (22) The requested URL returned error: 429
   ... 13 identical lines, 13s apart ...
error: curl fetch failed (22): https://github.com/eprover/eprover/archive/refs/tags/E-3.2.0.tar.gz
    at curlFetchToFile (.../curl-fetch.ts:36:15)
```

**Retry was never the missing piece.** `curl-fetch.ts` already passed `--retry 12 --retry-delay 10 --retry-max-time 300 --retry-all-errors`, and the log shows it retried until the 300s cap expired. A GitHub rate-limit window outlasts any in-process budget worth spending. The durable fix is to stop fetching.

## What actually changed

### 1. Cache — the fix
`~/.cache/zeta/from-autotools-tarball/*.tgz` was **absent** from the `install-v2-*` / `full-verify-v2-*` path lists, which made that step's own comment ("comprehensive cache of everything install.sh writes") false for the one component fetched straight from github.com rather than a CDN. Every ubuntu job re-downloaded E-3.2.0 cold.

Added to **all 20 blocks, byte-identically** — `installer-unit-tests.yml` warns that actions/cache identity is `(key, version)` and the version hashes the path list, so one divergent block silently forks a second ~1.5 GB entry. Only `*.tgz` is cached; the sibling `<key>-build/` extraction dirs are rebuilt every run.

The key already hashes `tools/setup/**`, which contains the manifest holding both the URL and the sha256 pin — so a version bump lands on a different key and cannot be served a stale tarball.

### 2. Integrity — what the cache would otherwise have opened
`existsSync(tarball)` was the entire test for reuse: the pin was verified once at download and the file trusted forever after. That is fine for one laptop's `~/.cache`. It stops being fine the moment CI restores the directory from a shared cache, where a truncated upload or a substituted entry walks into `./configure && make install` for **the prover that discharges our FOL obligations** — and the build succeeds.

The pin is now checked on **every** path into the build. A bad *cached* copy is discarded and refetched (derived state may legitimately be corrupt); a mismatch on *freshly fetched* bytes still throws, because that is upstream disagreeing with the pin.

### 3. Classification — 429 vs 404
`--retry-all-errors` retried a permanent 404 twelve times, and the thrown message carried curl's exit code but not the status, so a throttle and a dead URL read identically in CI. Now `-w %{http_code}` captures the status and `classifyCurlFailure` is a pure total function over `(exitCode, httpStatus)`.

**Status outranks exit code, and that ordering is load-bearing.** Measured locally: a real 404 arrived as `curl: (56)` — and 56 is in the connection-level retry set. Classifying by exit code first would have called a dead URL retryable.

**Nothing is swallowed.** An exhausted budget still throws. A prover that silently did not install would make the lint pass without running, which is this repo's cardinal defect.

## UNVERIFIED — named plainly

- **The actions/cache restore path itself.** Whether an entry is actually saved and restored under the new path list is observable only in CI. Locally unexercised.
- **The one-time cold miss.** Adding a path changes the cache *version*, so existing `install-v2-*` entries stop matching and the first run after merge re-downloads E-3.2.0 on every ubuntu job. If that lands inside a live rate-limit window it will fail once more before the cache warms.
- **Build-time is untouched.** Only the tarball is cached, not the built binary, so E is still compiled from source each run. Caching `~/.local/bin/eprover` would be a larger win and a larger risk (E installs several binaries); deliberately out of scope.

## Corrections to the brief

- The brief ordered "cache **or** retry with backoff". Retry **already existed** and had already lost — visible in the log as 13 exhausted attempts. Retry classification is worth having, but it is the *smaller* half; the cache is the fix. Ranking them the other way would have shipped a no-op.
- The brief said "if no checksum exists today, adding one is in scope". A sha256 pin **did** exist and was enforced on download. The real gap was narrower and sharper: it was **not** enforced on *reuse*.
