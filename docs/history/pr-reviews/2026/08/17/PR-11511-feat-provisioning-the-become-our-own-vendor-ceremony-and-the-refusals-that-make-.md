## What is NOT done (said before what is)

No TKey, no TP-1 programmer, no fabricated board, no reader, no fab. **Nothing is provisioned, attested, sealed, signed, burned, or verified.** No cryptography, no USB, no NVCM write, no network call, no key of any kind. Every physical step is UNEXERCISED and carries a reason in `PROVISIONING_IMPLEMENTATION_STATUS`, which a test forces to enumerate the whole ceremony so a step cannot be added without an honesty entry.

## What IS implemented

**`self-vendored-provisioning.ts`** — the ceremony order and, more to the point, its **refusals**:

| refusal | what it declines |
|---|---|
| `step-out-of-order` | burning a UDS before one is generated; skipping to signing |
| `no-named-approver` | an irreversible or root-exercising step with nobody accountable |
| `vendor-root-custody-undecided` | signing while it is undecided who holds the root |
| `uds-commitment-missing` | a missing **or blank** commitment |
| `nvcm-already-burned` | a second, *different* burn — one-time programmable |
| `field-name-looks-like-key-material` | a record carrying a field named `uds`, `udsHex`, `cdi`, `privateKey`, … |

Plus `deferenceReading`, which reports the oracle-vs-hub shape as a **neutral fact** with no verdict attached.

**`vendor-trust-root.ts`** — `"self-vendored"` added as a **separate** authority. #11485 landed the roster yesterday, and a root **we** hold came back from it as `"unlisted"`, rendering as *"caller-declared, not on the checked roster"*. That is true and misleading: it reads as **third-party provenance we did not check**, when in fact **no third party exists at all**. Opposite epistemic situations sharing one label — which lets a self-signature read as an external credential. The JSON boundary now routes by the authority it *read*, so the conflation cannot re-enter where the type system is absent.

Naming a root is still **not** chaining. Nothing here chains, and #11485's central finding is preserved verbatim in behaviour.

## The thing this repo's rules push against — named, not avoided

A self-vendored root that is the only party able to answer *"is this device ours?"* **is a single mandatory trust authority.** Under the exit test (Hirschman 1970, via `itron-hub-patent-boundary-p2p-is-the-upgrade.md`) that is a **hub**, not an oracle — and it stays a hub because the root is *ours*. `deferenceReading("authenticity", [oneRoot])` returns `single-mandatory-authority` / `exitAvailable: false` and says so.

The honest other half, which is why the design is still worth having: **integrity needs no authority at all.** The device identity is a function of the code running on it, so a stranger recomputes it and never defers to anyone. Exit is total there. Self-fabrication costs **third-party** attestation, not attestation.

## Three maintainer decisions — surfaced, not made

1. **Who holds the vendor root.** `VendorRootCustody` defaults to `"undecided"` and **fails closed** at the signing gate. The other members are vocabulary, not a recommendation.
2. **Single root or plural.** Reported by `deferenceReading`, never chosen. Accepting one root, or requiring k independently-held roots, is not decided here.
3. **The approval mechanism.** The model requires a *named approver* for irreversible acts — inherited standing discipline. It deliberately does **not** name biometric or anything else; the work-item's non-goal records that preference, and hardcoding it would be extending authority rather than inheriting it.
