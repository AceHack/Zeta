## AC#3 was vacuous — and the vacuity is mechanically provable

The criterion is *"a custody fork leaves the prior custodian able to read pre-fork content and unable to read post-fork content."* B satisfied it with a field typed as the literal `true`, asserted by `expect(fork.priorCustodianRetainsPreFork).toBe(true)`.

I tried to construct the input that would make that assertion fail:

```
vacuity-check.ts(6,3): error TS2322: Type 'false' is not assignable to type 'true'.
```

The counterexample cannot be written. The assertion passed for every input that type-checked — a check that cannot fail is not a check.

Nothing exported answered the question either. Probing the module's runtime surface on main:

```
exported runtime functions: authorize, emptyCustodyState, foldEvents, isGrantLive,
  rotateKey, selfIssueCredential, validateTransfer, verifyAgainstSlots
exports that could answer 'can prior custodian read X?': (none)
```

**Fix.** The literal-true field is gone. The fork now names `priorCustodian: Ownership`, and `evaluateForkRead` decides the criterion against content lineage — the fork's `ancestorRef` is the boundary, and reachability over parent edges decides which side a ref is on.

The input it must reject, and does:

```
lineage:  g0 ── g1 ── g2(ancestorRef) ── b1 ── b2
evaluateForkRead(fork, dag, "alice", "g1")  ->  allowed  (pre-fork, R3)
evaluateForkRead(fork, dag, "alice", "b1")  ->  DENIED   (post-fork, R4)
```

Same reader, same fork, two refs, opposite outcomes — which is what spec amendment A4 asks for ("name the function whose output demonstrates it, and the two inputs that make that output differ"). Unknown refs deny; unknown is not permissive.

## The retraction was decorative — confirmed by execution, not by reading

`rotateKey` emitted `key-retracted`; `foldEvents` handled it in `default: break`. Folding a stream with and without its retraction events, comparing derived state only (the raw event log trivially differs — that is the input echoed back, not the fold honouring anything):

```
BYTE-IDENTICAL : true   <= retraction is DECORATIVE
```

And the consequence that makes it more than bookkeeping. A grant retracted at phase 4, whose `expiresAtPhase` is 5000, asked at phase 100:

```
authorize@phase100 after g1 was RETRACTED at phase 4 ->
  {"allowed":true,"reason":"grant 'g1' is live (expires phase 5000)"}
```

The fold kept granting a capability nobody asserted any more. That is the ignored-retraction class exactly: the state says something that has been withdrawn.

**Fix.** `foldEvents` consumes `key-retracted` and `grant-expired`, moving the subject out of the asserted set into a retained `retiredKeys` / `retiredGrants` — retraction, not erasure (§5 memory preservation; the event stays in the log). Membership sets rather than integer Z-set weights, deliberately: a redelivered retraction lands on the same state, where integer weights would reach −1 and diverge (#6 idempotency).

One distinction the code now states outright: retraction ends a key's **forward use**; whether **already-signed material** still verifies is the bounded `previous`-slot window (R5). Two questions, two answers, previously muddled.

## Custody claims, stated exactly

**Nothing in this module is cryptographic.** No signature is produced, none is verified, no content is encrypted, no key material is handled, no key is revoked. A module header now says so before a caller can mistake it.

Specifically: `evaluateForkRead` returns a **decision**; it does not make post-fork content unreadable, and cannot stop a party holding the bytes from reading them. AC#3's "unable to read" is demonstrated as a decision the module returns, **not** as an enforced impossibility. `keysInvalidatedPostFork` is a declared list — "invalidated" means *named in this record*, not cryptographically revoked.

Related correction: `verifyAgainstSlots` documented itself as "verify a signature against a principal's key slots". It compares a key **identifier** against three slots and has never verified anything signed. The behaviour is unchanged; the docstring is now true.

## Still open, and not touched

- **Grant span unbounded** (A2) — `expiresAtPhase: Number.MAX_SAFE_INTEGER` still constructible in B; no `MaxSpan`.
- **Deny cites wrong grant** (R12) — `authorize` cites `matching[0]`, not the longest-lived grant.
- **AC#4** — `validateTransfer` still cannot return `false` for any `CustodyTransfer` that type-checks. This is the same vacuity class AC#3 was, on the witness-stake axis, and it needs the same treatment.

## One question left for you rather than answered

Should a custody transfer be **required** to invalidate at least one key across the fork boundary? R4 says no key is valid across the fork in both directions, and today `keysInvalidatedPostFork: []` sails through `validateTransfer`. But a degenerate fork of an empty custody legitimately has zero keys, so requiring ≥1 is a policy choice with a real false positive. That is a custody-policy call, so I left it unmade rather than guessing.
