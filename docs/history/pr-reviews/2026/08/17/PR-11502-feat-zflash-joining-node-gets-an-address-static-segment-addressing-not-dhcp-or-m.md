## Description

## What

Closes the **MECHANISM** half of the `joining-node-address-assignment` blocker filed by PR #11477. Role provisioning told a flashed node *what it is* and gave it a `--server` URL. It did not give either node an **address**, and it gave the joiner no way to turn that URL's host into one.

## The blocker, verified on `main` before building anything

| claim | how checked |
|---|---|
| the segment is a bare wire | `multi-vm.ts` uses `l2-socket-listen` / `l2-socket-connect` — a QEMU socket netdev, no DHCP, no DNS, no router |
| nothing serves a lease | every `useDHCP` / NetworkManager setting in the tree is **client** side; `dnsmasq`/`dhcpd`/`kea` return **zero hits** across `full-ai-cluster/` |
| the name cannot resolve | only name service is Avahi/nss-mdns (`nssmdns4`, `common.nix`), which answers `.local` only — so `k3s-agent.nix`'s bare `https://control-plane:6443` default resolves to nothing |

Not solved by #11477 or anything since.

## The option chosen, and why the other two lose

**Static addressing derived from the role**, carried on the medium PR #11477 just built.

- **The repo had already reached this answer.** `k3s-server.nix`: *"The robust path is to inject a `control-plane <cp-ip>` /etc/hosts entry on each worker at install time … Tracked separately."* `nixos/tests/k3s-agent-join.nix` supplies exactly that mapping by hand and says *"On hardware the mapping comes from an installer-injected /etc/hosts entry (still open)"*. This PR is that entry arriving.
- **mDNS was wrong twice over.** The same `k3s-server.nix` comment records mDNS was **tried** and *"never resolved"*, and NetBIOS/nss-wins *"did not work in testing"*. Worse: `k3s-server.nix` ships exactly **one** name SAN, `--tls-san=control-plane`. So `control-plane.local` — what `SCENARIO5_JOIN_SERVER_URL` dialled — fails **certificate verification** even if it resolves. `k3s-agent-join.nix` records that removing that SAN makes the join fail on cert verification, so the check is real, not theoretical. **Corrected to the bare label.**
- **DHCP on the control plane** appoints the founder as the segment's address authority (§1 — the defect is *appointment*), adds a lease-timing race that cannot replay (§7 DST), and is not checkable without booting something.

## Shape

Pure core + thin IO, same discipline as `firstboot-role.ts`:

```
cluster-address.ts   role -> address, a total function (founder .1, joiner .2+ in 10.88.0.0/24)
  -> firstboot-role.ts emits ZETA_CLUSTER_{NODE_CIDR,SEGMENT_MAC,CONTROL_PLANE_IP}
  -> /zeta-firstboot.conf on the ESP
  -> zeta-install.sh re-validates, stages three scalars under /etc/zeta/
  -> injected-cluster-address.nix applies them + the control-plane /etc/hosts entry
```

The **MAC** is carried, not just the IP: a scenario-5 guest has **two** NICs (SLIRP NAT + segment) and kernel names follow PCI enumeration, so `ens3` is not a stable handle. Addressing the wrong NIC is a naming bug that presents as a network fault.

Name and address stay two values on purpose — the joiner dials the **name** (what the certificate covers), and the address is only what makes it resolve.

## Honest registers

- **`INJECTION-POINTS.md` §5b** records that these values sit **plaintext on a FAT ESP**. They are *not* secret (an IP and a MAC leak nothing) but they are **tamperable**: rewriting the control-plane IP misdirects a joiner. It does **not** buy a silent takeover — the certificate check still holds and a rogue node cannot present a cert for `control-plane` — and it **does** buy denial of service. Recorded as not making the point-6 token exposure any better, not as safe.
- **`JoinBlocker` keeps `joining-node-address-assignment` listed.** Same standing PR #11477 took for role provisioning.
