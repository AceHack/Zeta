## Description

## Reproduced first

Measured at seed 4, 800 walkers, before touching anything:

| module | cluster size |
|---|---|
| `src/wasm-dla/bytelock/dla-canonical-wat.wasm` | 345 |
| `src/wasm-dla/bytelock/dla-canonical-asc.wasm` | 345 |
| `src/wasm-dla/bytelock/dla-canonical-zig.wasm` | 345 |
| **`src/wasm-dla/zig/dla.wasm`** — what the site's Zig panel loaded | **1** |

## Cause

`src/wasm-dla/zig/dla.zig` took its walk direction from `prng % 4` of an LCG whose **low
two bits have period 4**: mod 4 the multiplier `1664525 ≡ 1` and the increment
`1013904223 ≡ 3`, so the state advances by a constant 3 and the direction sequence is

```
3 2 1 0 3 2 1 0 3 2 1 0 …
```

Each cycle of four applies `+x`, `−x`, `+y`, `−y` exactly once, so a walker returns to its
spawn point every four steps — and `MAX_STEPS = 10000` is divisible by 4. No walker ever
reached the cluster. This is not seed-4 specific: it is **cluster 1 at every seed**. Same
defect class as the Go path.

## Why the PRNG was not the fix

Swapping only the PRNG for xorshift32 in that source gives **516** at seed 4 — not 345 —
because the module was a **second, divergent Zig DLA** with its own spawn rule, step budget
and kill radius, not the substrate in `src/wasm-dla/CANONICAL_SPEC.md`. A plausible wrong
number is the same failure in better clothes, and **nothing would have caught it**: that
module was in no byte-lock roster and pinned by no golden vector.

So the divergent implementation is removed and the site's Zig panel now stages
`dla-canonical-zig.wasm` — the substrate `run-bytelock-ci.mjs` loads and
`testdata/golden-seed-*.json` pins. There is now exactly one Zig DLA in the tree.

## Why it survived

`identity-dla-pages-wasm-assets.test.ts` checked WebAssembly magic bytes and export names.
A structural contract cannot see a wrong answer — the degenerate module had every declared
export and returned `1`. The panel rendered that `1` beside WAT's and AssemblyScript's `345`
under a header claiming *"same algorithm, same D_f, zero variance"*.

New `identity-dla-pages-wasm-behavior.test.ts` **runs** each canonical-ABI staged module and
compares it against the `cluster_size` read out of the committed hex-in-JSON golden vector —
so the site's expectation and the byte-lock's cannot drift apart without a visible diff.

## Rule check before committing a `.wasm`

`.claude/rules/no-binary-in-proof-lineage.md`, five conditions, for the binary the site now
stages (`dla-canonical-zig.wasm`) — it was already exempt and stays so:

1. **Subject, not evidence** — `run-bytelock-ci.mjs` loads and executes it.
2. **Expectation is text and is read** — `testdata/golden-seed-*.json`, hex-in-JSON, opened
   by the runner and now by the new test too.
3. **Reproducible from committed source** — *checked, not asserted*: rebuilding from
   `dla-canonical.zig` with pinned Zig 0.13.0 is byte-identical,
   `sha256 c28210dc4e1b33f63058d7a580410503e62be786477401e5d63c42fb97b8dbfe`, before and
   after the mutation cycle.
4. **Named in an enumerable roster** — `WASM_SUBSTRATES` in the runner.
5. **Stripped** — no `.debug_*` sections; `audit-proof-lineage-binaries.ts` passes.


Rebased onto #11489, which fixed the Go panel by **exactly this move** — staging the canonical
`bytelock/dla-canonical.go` substrate rather than patching the divergent `src/wasm-dla/go/main.go`
(that file still carries the LCG; nothing loads it). Four panels now run the canonical spec —
WAT, Zig, AssemblyScript, Go — and three do not.

These are recorded in `PAGES_WASM_ASSETS` with their measured values rather than left
looking like agreement, and the `OracleWASM` header now states what was measured instead of
claiming zero variance across seven panels when three of them still disagree. Bringing C/LLVM/Rust
onto the canonical spec is separate, confirmable work and is not started here.

## Verified vs unverified

- **Verified**: the cause (arithmetic, plus a direct reproduction of `cluster = 1` from the
  committed module at 800 walkers); the fix (staged Zig now matches the byte-locked cluster
  size at seeds 1 and 42); the falsifier (both mutation runs go red with the literal `1`);
  the rebuild reproducibility (byte-identical sha256).
- **Unverified**: browser-side behaviour of the panel — the module and imports are exercised
  in Node with the same import shim `run-wasm.mjs` uses, not in a browser. Also unexplained
  and left alone: the canonical Zig substrate takes ~3 s where WAT takes ~3 ms for the same
  800 walkers and the same import counts. It agrees on every byte-lock seed, so this is a
  performance observation, not a correctness one.
