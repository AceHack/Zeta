## Description

docs(agent-proposal): record that the patch-digest check cannot fire as deployed

Found while diagnosing the first live Pages delivery (proposal 60b7c599). The digest
rejection in `planAgentProposal` is correct code with a real falsifier test, and in
production it is structurally incapable of failing.

Measured: `agent-proposal-runner.ts` is the only production caller, and it builds both
sides of the comparison from the same local variable -- `sha256(payload.trim())` into the
intent, `payload` as the payload. The comparison is `sha256(x.trim()) !== sha256(x.trim())`.
The workflow declares three inputs and no digest, so no independently-declared digest can
arrive.

Stated narrowly, because the honest scope is narrower than "integrity": whoever can
dispatch the workflow already chooses the patch bytes, so this is no defence against the
dispatcher. Its value is the link between the bytes the operator APPROVED on the Pages
device and the bytes applied here -- the "approved, not run" property the gated-review
design exists to provide. Today, if the device approves P and the path presents P',
nothing notices.

Comment only; no behaviour change. Closing it is a producer-side change (the device would
emit its signed digest as a fourth input) and adding a required input would break the
existing three-input producer on the next dispatch, so that call is left to Aaron.
