## Description

## The gap

`OracleWASM.tsx` shipped seven compiler panels; the seventh had a hardcoded body:

```ts
const runGo = useCallback(async (s: number) => {
  void s;
  updateResult(6, { status: "error", error: "pending: Pages build does not yet produce the Go module" });
  return null;
}, [updateResult]);
```

The sentence was **true** — `pages-deploy.yml` had no Go step — and it could never
have said anything else. A status that cannot change when the thing it describes
changes is the same defect in either direction; a hardcoded `"ready"` would have
been the mirror image.

## What was actually missing (the brief's premise, corrected)

The gap was reported as "`src/wasm-dla/go/main.go` exists; the compile step is
missing." The file exists — but compiling *it* would have shipped a broken oracle.

**MEASURED 2026-08-17** (Go 1.26.4, seed 4, 800 walkers, run locally):

| source | cluster size |
|---|---|
| `src/wasm-dla/go/main.go` | **1** — does not diffuse |
| `src/wasm-dla/bytelock/dla-canonical.go` | **345** |
| committed `dla-canonical-wat.wasm` | **345** |
| committed `dla-canonical-asc.wasm` | **345** |

`main.go` takes its step direction from `s % 4` of the LCG
`s = s*1664525 + 1013904223`. An LCG modulo a power of two has period 4 in its low
two bits (multiplier ≡ 1, increment ≡ 3 mod 4), so the direction sequence cycles
through four distinct moves and every walker returns to its start. So this PR
compiles the **canonical** substrate instead — the same source `bytelock.yml`
byte-locks, through the same `build-substrates.mjs --only=Go` recipe, which already
checks the exit status *and* the emitted WebAssembly header. One build path, so
the published module and the byte-locked module cannot drift.

## The status is derived, and the derivation is falsified

Three surfaces, all reading rather than declaring:

- `probeGoOracle` fetches the module **and** its runtime bridge and reports what it
  found — absent, half-published, not-a-module, or available.
- `stagePagesWasmAssets` publishes the Go pair only if both halves exist, and
  returns what it did **not** publish instead of staying silent.
- `verifyPagesArtifact` sets `goOracle: "published" | "absent"` by looking at the
  artifact it just wrote.

**Mutation, measured on the real tree** (`stagePagesWasmAssets` + `verifyPagesArtifact`):

```
MODULE PRESENT : staged=8 evidence.wasmAssets=8 goOracle=published absent=[]
MODULE ABSENT  : staged=6 evidence.wasmAssets=6 goOracle=absent
                 absent=["wasm/dla-go.wasm: src/wasm-dla/bytelock/dla-canonical-go.wasm is missing (the Pages Go build did not run)"]
```

**Mutation, whole Pages build, no Go on `PATH`:**

```
[pages] Go WASM oracle SKIPPED: no Go toolchain on PATH — Oracle 10's Go panel will report the module absent
[pages] WASM asset NOT published — wasm/dla-go.wasm: … (the Pages Go build did not run)
[pages] Race Mode artifact ready: … (6 WASM assets verified; Go oracle absent)
```

**And with the CI switch set, the same absence is fatal:**

```
$ ZETA_PAGES_REQUIRE_GO=1 bun ./src/Core.TypeScript/discovery/identity-dla-pages-build.ts   # no go on PATH
error: teaching error: the Go toolchain is required for this Pages build (ZETA_PAGES_REQUIRE_GO) but `go env GOROOT` did not answer
```

`ZETA_PAGES_REQUIRE_GO` is set **only** in `pages-deploy.yml`, where an explicit
`actions/setup-go` step guarantees the toolchain. A laptop without Go still builds
the site and the page then honestly reports the module absent; the deploy cannot
quietly publish a six-oracle artifact.

The positive staging test does **not** depend on the 1.9 MB module existing — it
uses a 57-byte hex-in-source stand-in carrying the Go runtime ABI
(`run`/`resume`/`mem`), because a positive case gated on `skipIf(!built)` is a
check that never runs looking like one that passed.

## Toolchain

`actions/setup-go` pinned to the SHA `bytelock.yml` already uses —
`b7ad1dad31e06c5925ef5d2fc7ad053ef454303e # v7.0.0` — with `go-version: "1.26.4"`
from `.mise.toml`. Deliberately **not** the v6.0.0 / Go 1.22.2 pins that an earlier
abandoned attempt at this carried; those would have been a supply-chain downgrade
against main's current pins.

The JS bridge is copied out of that toolchain's own `$GOROOT/lib/wasm/wasm_exec.js`
rather than from the committed `src/wasm-dla/bytelock/wasm_exec.js`, which
**MEASURED** as a Go 1.22-era file that differs from Go 1.26.4's (older
`fs.constants`, no `path` shim, no `testExport` hooks). `bytelock.yml`'s comment
calls that pairing a "PARITY REQUIREMENT"; taking the bridge from `$GOROOT` makes
it true by construction instead of true by comment.

## UNVERIFIED — stated plainly

- **The GitHub Actions path has not executed.** No runner has run this workflow, so
  `actions/setup-go@v7.0.0` + `build-substrates.mjs --only=Go` on `ubuntu-latest`
  is untested here. The YAML looking right is not evidence.
- **The module has not run in a real browser.** It ran under bun through the same
  probe/install/read functions the component calls, which is the closest available
  proxy, but neither `fetch` from a Pages origin nor `WebAssembly.instantiate` in a
  browser engine has been exercised.
- `installGoRuntimeBridge` uses `new Function`, which needs `script-src
  'unsafe-eval'`. The site ships no CSP (checked: no meta tag, and GitHub Pages sets
  no policy header), so it works today; the code comment records what to change if
  a policy is ever added.
