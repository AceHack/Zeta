## The gap

**The premise needed correcting first.** There is no UKI. `lanzaboote` is imported by no
host (`081M00KTH58087G0R00120WT6F` is unshipped), so the chain does not *end* at the UKI —
it never starts. Nothing is signed and nothing is measured today. Stating the gap in the
present tense would have been the overclaim this track exists to prevent.

**Confirmed as documented:** `# CONFIG_MODULE_SIG is not set`,
`# CONFIG_SECURITY_LOCKDOWN_LSM is not set`. Secure-boot doc §6.1 is correct as written.

**Wider than documented — the finding worth the item:** `CONFIG_KEXEC=y`,
`CONFIG_KEXEC_FILE=y`, `CONFIG_KEXEC_SIG` **not set**. §6.1 says "root can `insmod`
anything". Root can also **replace the running kernel** with an arbitrary unsigned image
via `kexec` — no signature check, no reboot, no ESP write, no firmware interaction. The
legacy `kexec_load` syscall is unrestricted regardless, because that restriction is a
*lockdown* behaviour and lockdown is not compiled. A signed UKI stays true and stops
mattering one `kexec` later.

Also measured: no IMA, no EVM, no `INTEGRITY_SIGNATURE`; `DM_VERITY=m` present and unused;
no `luks|verity|tpm2|cryptenroll` anywhere in `full-ai-cluster/nixos/`; the hosts evaluate
to `lsm=landlock,yama,bpf` (no `lockdown`, which could not be there since it is not
compiled) and `boot.initrd.systemd = disabled` on all three.

## The three open questions

1. **`INTEGRITY_PLATFORM_KEYRING` / `LOAD_UEFI_KEYS` — answered, no.** Both are **absent**
   from the generated config, not `n`: `INTEGRITY_SIGNATURE` and `SYSTEM_BLACKLIST_KEYRING`
   are off, so the symbols were never offered. `LOAD_UEFI_KEYS` is `def_bool y` and would
   switch on for free — it never gets the chance. `x86_64_defconfig` at v6.12 carries no
   INTEGRITY/IMA/MODULE_SIG/LOCKDOWN row at all, and nixpkgs sets none either. So the route
   is four symbols deep before it is even reachable, not one flag.

2. **The custom-kernel price, with an edge that was not on the list.**
   `CONFIG_SYSTEM_TRUSTED_KEYRING=y` with `CONFIG_SYSTEM_TRUSTED_KEYS=""` — the keyring
   exists and is empty. nixpkgs states its own reason inline (`r13y, generates a random key
   during build and bakes it in`), so `MODULE_SIG=y` without a supplied key means every
   build signs with a key nobody holds. Supplying one makes it a **build input**, and build
   inputs land in `/nix/store`, whose mode measured here is `drwxrwxr-t` — world-readable.
   Labelled in the item as derived from two measured facts, **not** an executed build.

3. **`RANDOM_TRUST_CPU` — the probe the item proposed cannot answer it.** The symbol does
   not exist in this kernel. Occurrences of `RANDOM_TRUST` in upstream
   `drivers/char/Kconfig` — v6.0: 2, v6.1: 2, **v6.2: 0**, v6.6: 0, v6.12: 0. Removed in
   6.2, exactly the boundary nixpkgs' `whenOlder "6.2"` encodes. The behaviour stayed:
   `random.c` v6.12 has `static bool trust_cpu __initdata = true;` with
   `early_param("random.trust_cpu", …)` as the only override, and no host sets it. So
   **RDRAND is credited for the initial seed, unconditionally** — and
   `zcat /proc/config.gz | grep RANDOM_TRUST` prints nothing and exits non-zero, an empty
   result that reads as "off" while the true state is "on". A check that did not run,
   looking like one that passed. Anchor doc §4.4's open cell closes as *trusted*, not
   *unknown*.

## Limits — what is not claimed

**No boot was measured and none can be from here.** The measuring host is macOS 26.5.2
arm64 with no TPM; `bun tools/setup/persona-keys/frost-hardware-probe.ts` reports
`TPM 2.0: Not found` / `Honourable tiers: (none)`, and `ls /dev/tpm*` matches nothing.
Every §2 row is what the kernel *will be built with*, never what a node *did*. The `.config`
was substituted from the cache, not rebuilt locally. Kconfig text was read at tag `v6.12`
while the pinned kernel is 6.12.90; that diff was not taken. Whether the boards have a TPM
at all, and what firmware would extend into PCRs 0–7, remain untouched
(`081M00KTH58087G0R00120WT6F` open question 4).

**No decision and no config change.** The item's predicted outcome — accept the lower rung
and say so — survives and is now priced, but accepting a ceiling permanently is a
WONT-DO-shaped call and belongs to Aaron. `random.trust_cpu=0` is a one-line knob and is
deliberately **not** set: refusing RDRAND at seed time changes early-boot entropy
availability on headless nodes, which cannot be validated from this machine. The row stays
`backlog` because the *decision* is still open; the *measurement* is what shipped.
