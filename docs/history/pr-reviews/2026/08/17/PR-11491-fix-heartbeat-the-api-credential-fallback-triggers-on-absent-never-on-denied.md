## Description

fix(heartbeat): the API credential fallback triggers on absent, never on denied

All three lanes -- otto, alexa and soraya -- failed at 13:46Z and again at 14:10Z on
2026-08-17 with:

    [flush] otto: 4 heartbeat commits to flush
    merge-heartbeats-to-main: compare failed: gh: Not Found (HTTP 404)
    [flush] otto: could not open/arm the flush PR (rc=3)

Not the 429 wave that hit Pages in the same minute: that cleared by 13:50 and the Pages
re-run went green, while 14:10 failed identically.

ROOT CAUSE. The step selects its API credential with
`${{ secrets.ZETA_TELEMETRY_FLUSH_TOKEN || ... || secrets.GITHUB_TOKEN }}`, and its own
comment states the premise: "If the secret is ABSENT this degrades to GITHUB_TOKEN."
Absent is not the condition that occurs. `||` selects on empty, never on denied, and the
production fault is denial -- the PAT is set and unauthorized. GitHub answers 404 rather
than 403 for a resource a token cannot see, so a denied PAT is indistinguishable from a
missing repository.

Measured rather than inferred from the error string: the identical
`gh api repos/{repo}/compare/main...heartbeat/otto-flush-<sha>` call returns
`status=diverged` under an authorized credential. Endpoint, URL form and the
slash-bearing branch name are all fine; only the credential differs.

WHY THE PREFLIGHT DIDN'T CATCH IT. It already solves this, and solves it well -- probe,
swap the extraheader, then RE-PROBE, with a comment naming the vacuity class it avoids.
It repairs `git push` only. `gh api` kept the denied PAT. That is exactly what the log
shows: the snapshot branch pushes successfully, and the very next compare 404s.

This extends the same probe/swap/re-probe discipline to the API credential in both steps
that use it. The second, `Fail if a heartbeat PR is old and gate never started`, matters
differently: its whole job is to READ a check rollup, so a denied credential does not
merely degrade it -- it makes the instrument report on nothing while still going red,
which is how a credential fault gets misread as a gate fault. That check has been failing
intermittently for hours and this is very likely why.

NOT A FIX FOR THE ROOT PROBLEM, and deliberately so. The durable fix is granting
ZETA_TELEMETRY_FLUSH_TOKEN 'Contents: read and write' (081M010H4KE), which is Aaron's to
do. This converts a hard failure -- no flush at all, red every tick -- into the degraded
mode the workflow already documents and accepts: telemetry lands, `gate (required)` does
not start on the flush PR. It warns loudly on every fallback rather than going quiet.

No events were at risk either way; the workflow parks the exact source SHA on an immutable
snapshot before opening its PR, and re-merging an already-landed set is a G-Set union
no-op.
