## Description

**Confirmed root cause of bug B — it was the installer, not the bake.**

iter-4.2 mounts the boot USB ESP at `$PROBE_MOUNT`, finds the pubkey (`break 2` keeps it mounted), then **unmounted it** at the end of that section — *before* iter-5.2 (hostname → `$PROBE_MOUNT/zeta-hostname.txt`) and iter-5-wifi (→ `$PROBE_MOUNT/zeta-wifi-credentials.json`) run. Those probes then checked an **empty** `$PROBE_MOUNT` and silently no-op'd, even though all three files **are** on the ESP. The pubkey was found only because it's read while still mounted.

**How we know it's not the bake:** run 31287137988 — the bake **succeeded** (the #10180 ESP-write verification did *not* fire, proving all files are on the baked ESP), yet the installer logged "no zeta-wifi-credentials.json … skipping". That disproved the earlier bake-side hypothesis and pinned it to the mount lifecycle. (#10180's verification stays as a legitimate guardrail — and it's what proved the bake correct.)

**Fix:** defer the `$PROBE_MOUNT` umount from the iter-4.2 section to *after* the iter-5-wifi probe, so the ESP stays mounted through pubkey → hostname → wifi, then unmounts once. The ESP is read-only, on the boot USB (never the install target), and no other step mounts/needs `$PROBE_MOUNT` — so holding the ro mount across the intervening target-disk steps is safe.

Also fixes **hostname injection** (iter-5.2), broken the same way. `bash -n` clean. Validated by the next `build-ai-cluster-iso` dispatch (the wifi-ESP scenario should now emit the `[iter-5-wifi] found/wrote` markers).
