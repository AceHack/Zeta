## Description

## What this answers

Aaron 2026-08-14 is standing the full stack up on one box for an investor PoC.
The question was: **what does it take, and what is missing?** This PR answers it
from a live single-node bring-up, not from a plan, and lands the check that keeps
the answer true.

## Three-way gap list

### PRESENT and works on one node

- **ArgoCD + root App-of-Apps + 43 child Applications** reconcile on a single
  kind node under podman on Apple Silicon. `argocd-health-test.ts --run --scope
  smoke` returned `ok: true` in ~7 minutes.
- **Longhorn came up Synced/Healthy on ONE node in ~110s.** Its
  `defaultReplicaCount: 1` is honest. It is currently excluded from CI for a
  reason that did not survive contact with the substrate — see "left
  deliberately".
- **k3s multi-node join.** Not invented here and not missing:
  `k3s-agent.nix` carries `serverAddr` + `tokenFile`, `--tls-san=control-plane`
  makes the cert valid, `k3s-join-observer.nix` witnesses it, and
  `nixos/tests/k3s-agent-join.nix` proves it in a VM. What is still missing is
  name resolution on real hardware, and that is already documented in
  `k3s-server.nix`.

### BROKEN — exists, does not work

1. **CockroachDB never starts on one node.** All three Raft members schedule
   onto the same node; three 100 GiB Longhorn PVCs bind; then:

   ```text
   cockroachdb-0/1/2  Init:0/1  node=zeta-dejan-poc-control-plane
   Longhorn volume datadir-cockroachdb-0:
     state=detached  robustness=faulted
     Scheduled=False  reason=ReplicaSchedulingFailure
     message="insufficient storage;precheck new replica failed"
   -> AttachVolume.Attach failed: "volume ... is not ready for workloads"
   ```

   1030 GiB of `longhorn`-class PVCs bound against a 100 GB node disk.

2. **`argocd/zeta-root` is declared twice.** `infra/k8s/applications/` and
   `full-ai-cluster/k8s/bootstrap/` both declare that identity with
   `prune: true` + `selfHeal: true` and different `spec.source.path`. Kubernetes
   has one object at that name; whichever applies last prunes the other tree's
   entire child graph.

3. **14 Applications are applied to every CI cluster and asserted by nothing.**
   Two unlinked exclusion lists: `excludeGlob` in `ports.ts` withholds 12 dirs
   from ArgoCD, the harness withholds 26 from the assertions. The 14-app shadow
   is the stateful core — cockroachdb, vault, nats, redis, spire, hindsight, oz,
   weaviate, mimir, tempo, kube-prometheus-stack. **17 of 43 apps are proven; 26
   are not.** Filed as `081M00QCNYM087G0R000ZS3CE2`.

4. **`live-kind-included` is `continue-on-error: true`** — the only proof that
   Applications reach Synced+Healthy cannot fail a PR. Filed as
   `081M00QCNZG087G0R0008TD6D1` with the evidence that it has earned promotion.

### ABSENT

- **No storage budget anywhere.** No manifest, doc or check states how much disk
  a node needs. This PR derives it: **longhorn 1499 GiB + zeta-local-path 73
  GiB, ~1.6 TiB per node** before headroom.
- **`infra/k8s/` never reaches a live cluster**, and neither does
  `full-ai-cluster/k8s/bootstrap/**` — the k3s first-boot manifests are only
  exercised by the NixOS VM tests, not by the ArgoCD lane.
- **No single-node story is written down.** Which components genuinely need more
  than one node was, until now, nowhere stated.

## Which components genuinely need more than one node

| Component | On one node | Why |
| --- | --- | --- |
| **CockroachDB** | **needs 3 nodes** | 3 Raft members. Chart default `podAntiAffinity type: soft`, so they co-schedule silently. Nominal RF=3, real failure domain = one disk. Majority loss is unrecoverable. |
| **Vault** | **needs 3 nodes** | `server.ha.replicas: 3` + `raft.enabled: true`. Identical shape. |
| **NATS JetStream** | **needs 3 nodes** | `cluster.replicas: 3`. Identical shape. |
| **Mimir** | **needs 3 nodes** | ingester and store-gateway zone-a/b/c are a zone-aware quorum on one node. |
| Longhorn | **honest on 1** | `defaultReplicaCount: 1` matches node count. Proven live. |
| Redis | degraded on 1 | `replicaCount: 2`, async replication. No quorum to lose, but no redundancy either. |
| ArgoCD, cert-manager, trust-manager, external-secrets, sealed-secrets, OPA, alloy, loki, minio, seaweedfs, headlamp, NFD, dapr, argo-rollouts, argo-workflows, arc-controller, hat-system | **fine on 1** | Proven Synced+Healthy in the existing `included` lane. |

The four "needs 3" rows are the honest answer: **you can demo them on one box,
but you cannot call them highly available**, and `kubectl get pods` will not tell
you the difference. That is the failure mode this PR makes impossible to ship
silently.

## The two-trees question — argued, not mechanically resolved

**Do not point the live test at both trees. Consolidate.**

Against dual-testing:

- Both trees declare `Application/argocd/zeta-root`. They cannot share a
  cluster, so it needs two clusters — doubling the most expensive job in the
  workflow (`live-kind` runs 5-6 min x 2 arch; `live-kind-included` 10-13 min).
- It would certify a tree that **cannot run on the target hardware**:
  `infra/`'s Longhorn asks for 2 replicas on one node (permanently Degraded) and
  sets `persistence.defaultClass: true`, colliding with the `zeta-local-path`
  default class the live NixOS module declares — two defaults is an invalid
  config. `infra/`'s CockroachDB sets `podAntiAffinity type: hard`, so 2 of 3
  pods are Pending forever. Making CI green for that means teaching CI to accept
  a configuration that cannot come up.

For `full-ai-cluster/` as the survivor: it is what `zeta-install.sh` installs;
last commit 2026-08-14 (#10503) vs 2026-08-08; 43 apps vs 7; 24 NixOS modules vs
4; 4 VM tests vs 0; and it carries four first-boot fixes each earned on a named
node on a dated day (`tokenFile` crash-loop, duplicate default StorageClass,
Cilium rpfilter DNS blackhole, Longhorn `preUpgradeChecker` deadlock) that
`infra/` does not have.

The deletion itself is filed as `081M00QCHWA087G0R000GKKRXD` rather than done
here: ~20 files across two trees, PR #10652 deliberately left both alone, and
`docs/ZETA-CORE-TECHNOLOGY-FOR-MAX.md` — a partner-facing doc — cites
`infra/k8s/` paths as "Deployed" that do not exist in `infra/` at all. Round-29:
that lands with sign-off.

## CI cost

Two steps on the **existing** `dry-run` job, which already installs the
toolchain and bun deps. Marginal cost **~2s** on a job that runs 3-4 min against
a 12-min cap. No new job, no new cache warm, no second `install.sh`.

Paths filter gains `full-ai-cluster/k8s/bootstrap/**`, the ledger, and the two
new files. **`infra/k8s/**` was deliberately not added** — triggering the
~100-minute live matrix to certify a 7-file tree nothing installs is not worth
it when the recommendation is to delete it. The daily cron covers it at ~12h
MTTD.

Not `continue-on-error`. Green on main today; red on drift.

## What I left deliberately

- **Did not flip `live-kind-included` off `continue-on-error`.** Earned it
  (4/4 green, 10-13 min against a 60-min cap, run ids in the work-item), but
  promoting an advisory job to a gating one changes what blocks a merge for
  everyone. One-line diff is written down and waiting.
- **Did not delete either tree.** See above.
- **Did not touch `infra/k8s/tests/` or `helm-validate.yml`** — PR #10647 owns
  those.
- **Did not re-enable Longhorn in the CI lane** even though it came up healthy
  on one node in 110s, because re-enabling it makes the 14-app shadow set start
  provisioning 1499 GiB against a runner disk. That change belongs after
  `081M00QCNYM087G0R000ZS3CE2`, not before it.
- **Did not fix `discoverExpectedApplications()`**, which still reads Application
  names with a line regex rather than a YAML parse — same class of defect PR
  #10647 removed next door. Noted in the work-item; touching it now would
  collide.
- **Two `kubectl ... | tail -200 || true` lines** in the `Print cluster
  diagnostics` steps have an unreachable `||`. Benign — diagnostic-only,
  `if: always()`, and `tail` succeeding is the intended never-fail outcome — so
  left alone rather than churned.
- **Latent podman-lane leak**: `kind-down.ts` reads `ZETA_CONTAINER_RUNTIME` but
  the health test's `--runtime podman` flag does not propagate to it, so a
  flag-only podman run leaks its cluster. Not live (CI is docker-only); worth a
  future row.

## The blunt version

The full stack does not come up on one box today. In order:

1. Longhorn's `longhorn` StorageClass must exist before 14 apps stop hanging —
   it works, it is just switched off in the dev lane.
2. The node needs **~1.6 TiB**, not the 100 GB a CI runner has.
3. CockroachDB, Vault, NATS and Mimir will each run three co-scheduled replicas
   and look healthy while being single-failure-domain. Decide per component:
   drop to 1 and say so, or set hard anti-affinity and let the shortfall show.
4. The two trees must become one before any of this is testable end-to-end.

That is a plan with four items, not a demo date.
