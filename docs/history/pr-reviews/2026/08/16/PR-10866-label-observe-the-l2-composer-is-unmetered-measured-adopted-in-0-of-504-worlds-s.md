## Description

Follow-up to #10859, which recorded the L2 composer as the one live TypeScript decision surface with a declared pluggable scorer and a production caller, and left it as a different work item. This is that work item, and the answer is **label, not meter** — with a measurement that turned out sharper than expected.

**No weights were tuned. No BNN was wired.**

## What the five weights actually decide: nothing, on the live path

The brief asked to establish first whether a change in the weights changes what the loop does. Measured over a 504-world enumeration, on the tick's exact config (`choose(world, { composer })` — a composer, **no deliberator**, default thresholds):

| measurement | result |
|---|---|
| worlds where `score()` is actually invoked | **156 / 504** — instrumented with a spy, not inferred |
| menu length when scored | **14–16 options** |
| worlds where the composer's result is **adopted** | **0** |
| highest composer confidence anywhere in the escalated space | **0.4272** (threshold **0.7**) |
| worlds where **all five weights = 0** changes the action taken | **0 / 504** |

The mechanism is in `chooser.ts`: the composer's pick survives only if `confidence >= composerThreshold` (0.7). Below it, with no deliberator wired, `choose` falls through to `return oracleResult` — the oracle's pick, which is `menu[0]` by construction. So on every escalated tick the scores are computed and thrown away.

That is the analogue of #10845's `costRatio = 1.000` asked for in the bar: **a perfect scorer here would change nothing**, because nothing downstream reads it.

## Which is why no falsifier was added: there is presently nothing to falsify

A test asserting "the scorer ranks a ready `do_item` above `explore`" would check a value the live system does not use. `composer.test.ts` already does exactly that — five green tests over **hand-built menus** — and its greenness is fully compatible with the weights having zero effect on any decision. I left those tests in place and added a header saying precisely that, so their scope is not misread as coverage.

Per `toy-is-free-metered-must-be-earned.md` the state is **`unmetered`**, not `toy`: it is implemented and called on the live tick, just never falsified. The register is now stated in the identifiers, so it travels to every call site:

* `heuristicComposer` → `unmeteredHeuristicComposer`
* `defaultComposer` → `unmeteredDefaultComposer`
* `DEFAULT_WEIGHTS` → `UNMETERED_DEFAULT_WEIGHTS`

A reader of `choose(world, { composer: unmeteredDefaultComposer })` can now see what is behind the port without opening it.

## Not dead by construction — dead at these values

The cascade is not broken, and saying "the weights don't matter" without this half would be wrong. With `readiness = 1` and the other four at 0, the tier fires in **28 of the same 504 worlds and overrides the oracle in all 28**. The shipped vector is a dead point inside a live space.

Two mechanisms hold it there, both recorded in the module header because they are counter-intuitive for anyone who later tries to tune it:

1. `buildMenu` always emits the four free modes plus grammar / cartography / time options, so the runner-up score is never small — a 70 % gap is hard to open.
2. `scoreAction` clamps to `[0, 1]`, so **large weights saturate**. Measured with `readiness = 1, modeCoherence = 1`: several options hit 1.0, the gap collapses, top confidence over the whole space falls to **0.0000**, adopted in 0 worlds. Raising weights can make the tier *less* likely to fire.

## The tripwire, and proof that it discriminates

`observe/composer-register.test.ts` pins both halves — **the port is live** and **its output is discarded** — plus a **positive control** proving the harness can observe adoption when adoption happens. Without the first and third, "adopted in 0 worlds" would be indistinguishable from a check that cannot see adoption at all, which is the vacuity class this whole thread keeps finding.

The file says out loud that a red is not necessarily a regression: if the composer starts deciding, that may well be an improvement, and it is exactly the moment the model owes a falsifier.

Four mutations, raw exit codes, never piped:

| mutation | raw exit | which lane failed |
|---|---|---|
| baseline | **0** | 4 pass |
| shipped weights → `readiness` 1, rest 0 | **1** | `…ADOPTED IN NO WORLD` (received **28**) + `…ZERO changes nothing` (received 28) |
| `composerThreshold` 0.7 → 0.4 | **1** | same two lanes (received **20**) |
| `composerThreshold` 0.7 → 0.99 | **1** | **POSITIVE CONTROL** (`> 0`, received 0) — the control is itself falsifiable |
| `oracleThreshold` 0.9 → 0.0 (composer never reached) | **1** | `the port is LIVE` + positive control — the degenerate "fix" is blocked |
| all mutations restored | **0** | 4 pass |

Note the first row is the honest form of "perturb a weight": perturbing **one** weight does *not* fail, and that is the finding rather than a weakness — it takes a whole vector change to make the tier fire at all.

## The trap from #10859, not walked into

No BNN was wired. Its three reasons stand unchanged and were not re-derived: chooser-not-scheduler, the menu is supplied by `buildMenu` so a scorer never touches the possibility space, and `error-bnn-bridge.ts`'s posterior is over error dimensions rather than actions. `confidence` was not renamed and not repurposed — it is a score gap, `(max − secondMax) / max`, and this PR only ever calls it that.

## Corrections to the brief, flagged explicitly

1. **"If the menu is usually length ≤ 1, the weights are decorative" — the premise is false, but the conclusion is true by a different mechanism.** Menus are **never** short: `buildMenu` unconditionally appends four free modes, `edit_grammar`, four cartography moves, two scope moves and two time moves, so the measured range is **14–16**. The weights are decorative because of the **0.7 confidence gate plus fallback-to-oracle**, not because there is nothing to choose among. `oracleChoose`'s `menu.length === 1` branch is dead code for the same reason.
