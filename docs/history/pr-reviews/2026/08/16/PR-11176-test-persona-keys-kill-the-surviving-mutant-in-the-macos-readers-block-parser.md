## Description

# Summary

The named defect in `081M00HVPGS087G0R0001T4BF8` — a PKCS#11 driver on disk reported as
attached hardware — **was already fixed** on `main` by #10644, and is not re-fixed here.
Verifying it produced one thing worth shipping: **a surviving mutant on the guard that
fix rests on.**

`macReadersBlockIsNonEmpty` is, by its own docstring, "the whole of macOS reader
detection", and the test file states the invariant explicitly: *"a parser that keyed on
the word 'Reader' would report a reader on every Mac ever made."* That invariant was
**asserted and not checked**. Replacing

```ts
const start = lines.findIndex((l) => l.trim() === "Readers:");
```

with `l.includes("Reader")` passes all 23 tests on `main`. Both fixtures open their
`Readers:` block on the same line where the substring "Reader" first occurs, so neither
can distinguish a header-exact parser from one that matches the **driver list** below it.
Given profiler output with no `Readers:` section, the mutant reads
`#01: …ifd-ccid.bundle` — a bundled driver — as an attached reader, clearing
`noHardwareDetected` and offering `hardware-pkcs11`. That is the work-item's own defect
class, one layer down, in the parser the fix depends on.

This PR adds the fixture that kills it. **No production code changes** — the parser is
correct; only its guard was unfalsifiable.

# Notes

**Sibling with the same shape, filed not fixed:**
`workitems/081M06DSQ0Q087G0R000H91391-…`. `biometric.ts` → `macTouchIdAuth()` greps
`/etc/pam.d/sudo` for a `pam_tid.so` line, runs `sudo -p "" true`, and on exit 0 returns
`{ ok: true, platform: "macos-touchid" }`. Neither observation sees *which* PAM module
satisfied sudo. The stock stack on this host has `pam_smartcard.so` and
`pam_opendirectory.so` as later `auth` entries, and `sufficient` falls through on
failure — so a smart card or a typed password returns a result that names Touch ID. The
FROST hardware lane is exactly the flow where a PIV token is inserted. A stated
mitigation in the code ("stdin is `ignore` so no password can be typed") does not hold:
`sudo` reads from the terminal device, which is what `-S` exists to change. Not fixed
here because the fix changes what the gate promises. **Not exercised** — no `sudo` was
run on the operator's machine; the fall-through is read from code, PAM config, and
`man sudo`, and should be reproduced before a fix is designed.

**What could not be exercised:** no YubiKey, smart-card reader, TPM 2.0 host, or PKCS#11
token was available. Everything hardware-facing was tested through the injected
`HardwareProbeEffects` host. The one real-machine reading taken was
`system_profiler SPSmartCardsDataType` on this Apple Silicon Mac, which emits a present-
but-empty `Readers:` block — matching the existing fixture. Whether any macOS build,
locale, or SmartCardServices state omits that block **is unverified**; the new test pins
the invariant the code already claims rather than a machine I observed.
