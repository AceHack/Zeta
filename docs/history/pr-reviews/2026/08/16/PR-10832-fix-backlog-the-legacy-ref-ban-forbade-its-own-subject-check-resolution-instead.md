## Description

## The defect: a gate that forbade its own subject

`lint-no-b-refs.ts` failed if any hyphenated legacy `B-NNNN` appeared on an authored surface. An agent that needed to discuss a legacy row therefore wrote it **hyphenless** (`B0747`), justifying the workaround by arguing that exempting one reference "would make the lint unfalsifiable."

The instinct was right and pointed the wrong way. The lint was **already** unfalsifiable, for a stronger reason:

> The ban forbids *writing* a legacy ref, so a **stale** legacy ref can never exist in tree, so the lint can never detect one. It achieves compliance by eliminating its own subject.

Same class this repo has hit repeatedly in the last week: a `grep -q` satisfied by a SIGSEGV, `markdownlint-cli2` exiting 0 having linted zero files, a property-test generator fixed at arity 2 passing a decoder that rejected every non-2-ary call (#10828).

Aaron 2026-08-15: *"if the gate is too restrictive I'd rather change it and do better drift checks."*

***

## The replacement

`src/Core.TypeScript/backlog/lint-b-refs-resolve.ts` permits the reference and checks that it **resolves**:

| rung | meaning | example |
|---|---|---|
| `live` | alias maps carry the id, and the ZetaId they name has a row under `docs/backlog/P0..P3`, `workitems`, `workitems/done` | `B-0732` to `081KSE6WT0008QG0R002YBWBB1` |
| `archive` | no live row, but the id names a surviving artifact under `docs/recovered-orphan-branches-2026-05` | `B-0747` |
| — | neither, so **FAIL**, naming file, ref, and the mapped ZetaId if one exists | |

Strictly stronger than the ban: it catches a fabricated id, a typo'd id, and a real id whose target was deleted — **none of which the ban could see** — while letting lineage prose name what it is discussing.

**Alias-map presence is deliberately not resolution.** `b-to-zetaid-map.json` was rebuilt by mining git history for tokens, so it carries ids in the B-2xxx/B-8xxx/B-9xxx bands that were never rows. Requiring the target on disk is what makes this a drift check rather than a second spelling of the map. Measured: of **1251** mapped ids, **1160 resolve `live`, 14 `archive`, 77 to nothing**.

## This does not re-open `B-NNNN` minting

- **`lint-no-new-bnnnn.ts` untouched** — any `B-<digits>*` filename under `docs/backlog/` or `workitems/` still fails. A test now **executes that tool** against a planted B-named row and asserts exit 1, so the claim is checked rather than assumed.
- **Legacy id in a row's frontmatter fails** — naming `B-0747` in prose is lineage; putting one in `id:` / `depends_on:` / `superseded_by:` is minting with it. The gate loosens **references**, never **keys**.

The B-0732/B-0733 trap (legacy-looking numbers that are live ZetaId rows) is the resolver's first rung and both ids are pinned by name in the fixture.

## CodeQL follow-up: TOCTOU, and the symlink cycle underneath it

Three `js/file-system-race` alerts in `rebuild-legacy-b-id-aliases.ts` (164 / 252 / 257): `statSync(p)` to decide entry kind, then `readFileSync`/`writeFileSync` outside any `try`. **Genuine, and my own two new files carried the same shape** — CodeQL's diff scope had not reached them yet. Fixed at every site with #10757's pattern: **let the syscall be the check.** `existsSync` before a read is always a race; `readFileSync` in a `try` is not. No suppression, no inline ignore.

The stronger half is `readdirSync(dir, { withFileTypes: true })` — entry kind comes from the directory read itself, so there is no per-entry `stat` to race against and one fewer syscall per entry across ~30k entries.

**That surfaced a real latent bug, and is why this beats wrapping the `stat` in a `try`.** `statSync` follows symlinks; `Dirent` does not. Tracked links here:

| link | target | consequence of following |
|---|---|---|
| `universal/*.md` | `db/shapes/*.md` | file read twice — and the **rewriting** remedy applies the substitution **twice** |
| `db/hy` | `../hygiene` | a whole subtree walked twice |
| `tests/.../tree1/subdir1/link_to_parent` | `..` | **a cycle** — measured: the old walk recursed **64 levels to a 793-char path** before PATH_MAX stopped it |

Every target is inside the tree and visited directly, so **skipping symlinks loses no coverage** — checked, not assumed. Two tests pin it and **both go red under a mutant that restores the `statSync` walk**.

**Owned error, in this PR's own harness.** My first version of the second test asserted *"a symlink cycle does not hang the walk"* with a wall-clock bound. That check **could not fail** — a cycle under the old walk also finished in milliseconds. I wrote the exact defect this PR is about into the PR's own tests. Replaced with an out-of-tree-target test that discriminates.

**Second owned error, a near-miss.** Probing the remedy's flags I ran it with `--help`, which that script does not have; anything that is not `--dry-run` is a **write** run, so it began a full rewrite. Killed before any file changed (`git status` confirms only the intended files). The correct move was to read the argv parsing. A rewriting tool that treats an unknown flag as "go" deserves a row.

**Runtime:** a strict improvement, but **not** a fix for `081M010NSB8087G0R002PJVJG7` — that item attributes the >10-minute cost to git-history mining, which is untouched. The item stays open.
