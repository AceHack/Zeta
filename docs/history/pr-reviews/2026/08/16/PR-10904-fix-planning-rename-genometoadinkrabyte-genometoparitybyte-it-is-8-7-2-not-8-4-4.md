## Description

## The defect

`src/Core.TypeScript/planning/society-evolution.ts` — `genomeToAdinkraByte`'s docstring claimed the **[8,4,4] extended Hamming code** structure. The implementation is the **single-parity-check code [8,7,2]**: 7 channel MSBs into bits 0..6, their XOR into bit 7.

| property | claimed ([8,4,4]) | actual ([8,7,2]) |
|---|---|---|
| data bits | 4 | 7 |
| min distance | 4 | **2** |
| capability | 1-bit **correction** | **detection only** |
| self-dual | yes | **no** (dim 7; dual is the repetition code [8,1,8]) |
| doubly-even | yes | **no** (weight-2 codewords exist) |

This is a Beacon-register overclaim, not a typo. The adinkra lineage in this repo rests on **Gates' doubly-even self-dual codes**, and [8,4,4] *is* the doubly-even self-dual code at length 8. Both codes share length 8 — that shared count identifies nothing (`numerology-vs-number-theory`); the invariant that separates them is doubly-even self-duality.

## Rename, not upgrade — and the no-consumer check

Re-verified independently by repo-wide search: `genomeToAdinkraByte` has **no non-test consumer**. Every reference was its own tests (SE-11 determinism, SE-12 byte-lock) plus one line in `docs/ZETA-ARCHITECTURE-UNIFIED.md`. Nothing decodes the byte, corrects with it, or checks self-duality.

So upgrading to real [8,4,4] would cost capacity (7 data bits → 4) for zero operational gain, and would create a **second referent** for "adinkra code" alongside the genuine machinery that already exists in the algebra/formal layer. One name, two meanings is the defect class that already bit `Cond`, "time-crystal", and the adinkra `N`/`k` conflation.

## Changes

- **Rename** `genomeToAdinkraByte` → **`genomeToParityByte`**, taken from the behaviour: it computes a parity-checked genome byte. All call sites and test names updated.
- **Docstring rewritten** to state the actual code ([8,7,2], distance 2, detection only, no correction, not self-dual, not doubly-even), to say plainly that it is **not** [8,4,4] and therefore **not an adinkra code**, and to route the reader to where the genuine doubly-even self-dual machinery lives — `research/adinkra-ecc/adinkra-ecc-prototype.ts` (constructs *and verifies* doubly-even + self-dual), `Core.Lean4/Lean4/CayleyDicksonDoublyEven.lean`, `Core/CliffordE8BladeMask.fs`, `Core/OrbitEquivariance.fs`, `algebra/e8-blade-mask-sandwich.ts`.
- **Flip condition recorded** in the docstring: if the generator-as-ECC thesis (`only-the-irreducible-is-primitive-generate-the-rest` — "the highest-value generator IS an error-correcting code") acquires a consumer needing **correction** or **self-duality**, [8,4,4] becomes a *correctness requirement* rather than an upgrade — and the move then is to reuse the algebra-layer machinery, not re-implement in `planning/`.
- **Same conflation corrected in two neighbouring docs surfaces** it had already spread to: the `society-evolution.ts` module header and `docs/ZETA-ARCHITECTURE-UNIFIED.md`, both of which described [8,4,4] as carrying "7 channels + 1 parity bit". It carries 4 data bits.
- **New test SE-12d** pins the separating invariant: a weight-2 codeword exists ⇒ not doubly-even ⇒ not [8,4,4]. This makes the docstring's negative claim falsifiable instead of asserted, and fails if someone restores the [8,4,4] claim without changing the encoding.
