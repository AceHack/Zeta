## Description

## What

KubeVirt **v1.8.4** and CDI **v1.65.0** were installed by hand on `node-5b2dfa` (2026-07-12) and existed **nowhere in git**. A repo-wide search for `kind: VirtualMachine`, `win-unattend`, `windows-golden`, `virtio-win`, `autounattend` returns zero hits.

So a fresh USB install produced a cluster with **no virtualisation layer at all** — while three production Windows guests ran on that undeclared layer:

- `fd-windows`
- `fd-win-flowdent-0ed52dee`
- `fd-win-flowdent-b625336c`

If that box died it did not come back from the installer. It came back from someone redoing the install by hand.

## Approach

Operator manifests are vendored **verbatim** from the upstream releases rather than tracked via a chart — neither project publishes an official Helm chart, and pinning the exact bytes is what makes this genuinely 1:1 with what runs. Both confirmed against the live deployments (`quay.io/kubevirt/virt-operator:v1.8.4`, `quay.io/kubevirt/cdi-operator:v1.65.0`). Same precedent as the already-vendored `k8s/bootstrap/gateway-api-crds.yaml`.

The two CRs are **not hand-written** — their specs were exported from the live cluster, so the empty objects (`certificateRotateStrategy: {}`, etc.) are real and load-bearing rather than tidy-able.

## Verification

`kubectl diff` of both CRs against the running cluster shows **only** the added ArgoCD sync-wave annotation — **zero spec changes**. Adopting this is a genuine no-op.

`yamllint -d relaxed`: clean (warnings only, exit 0).

## Sync is deliberately MANUAL

No `automated:` block on either Application. This adopts operators sitting underneath three running production VMs, where an automated first reconcile could roll `virt-operator` -> `virt-handler` and disturb live guests.

```bash
argocd app diff kubevirt
argocd app sync kubevirt
```

Enable `automated: { prune: false, selfHeal: true }` only once a hand-run sync has been observed to be a no-op.
