## Description

## What

Links the two exclusion lists that govern the kind/k3d ArgoCD health lane, so the
"applied to every CI cluster and asserted by nothing" shadow cannot grow silently.
Closes `081M00QCNYM087G0R000ZS3CE2`.

Also records a **verification pass** on the sibling work-item
`081M00QCHWA087G0R000GKKRXD` (consolidate the two cluster trees) — measured, not
acted on. See "What is deliberately NOT here".

## Verified before proposing

The bug report reproduced **exactly**: 12 glob-excluded, **14 applied-but-not-asserted,
the same 14 names**. The asserted count moved 17 → 19 only because `cdi` + `kubevirt`
landed since (#11089); the shadow itself did not move. Eleven of the 14 share one root
cause — they want `storageClass: longhorn`, and `longhorn` is glob-excluded, so the
StorageClass cannot exist in that lane and the Application hangs `Missing` forever.

## What landed

- `rootDevCatalogExcludedDirs()` derives the applied set **from**
  `DEFAULT_ROOT_DEV_CATALOG.excludeGlob` rather than restating it — one source of truth
  for what reaches the cluster.
- `APPLIED_BUT_UNASSERTED_REASONS` — all 14, each with a stated reason.
- `auditAppliedButUnasserted()` reports drift in **both** directions: a newly applied
  Application nobody asserted, and a stale entry for a directory no longer in the shadow.
  Pure and offline — zero CI seconds.
- `parseApplicationName` now uses a real YAML parser instead of a line regex.

## Honest limits

- **This does not make the 14 pass.** They are still applied and still unproven. It turns
  an *implicit* shadow into an *explicit, reasoned, drift-guarded* one. Proving them needs
  the Longhorn-or-substitute StorageClass question answered — hardware-PoC work.
- **The YAML swap fixed a defect CLASS, not a live bug.** Across all 46 `Application.yaml`
  files the old regex and a real parse **agree** (0 disagreements). The regex is still
  wrong in principle — first `name:` at any indentation inside `metadata:` wins, so a
  `labels:` block with its own `name` would silently beat the real one, and a quoted or
  flow-mapped name is missed. No current manifest has that shape. Calling it a caught bug
  would be rounding up.

## Found while measuring, pinned not fixed

`discoverExpectedApplications()` enumerates `<dir>/Application.yaml` at depth 1 only, and
the tree declares one Application below that — `game-hosting/gmod/Application.yaml`, whose
own header says the App-of-Apps root picks it up. It is in neither exclusion list, so it is
invisible to the harness **and** unrecorded as deferred. Deepening discovery would change
what the live `--scope included` lane asserts and cannot be verified without a real
cluster, so instead a test **pins the gap at its measured size** and goes red if a second
nested Application appears. Left open deliberately.

## What is deliberately NOT here

`081M00QCHWA087G0R000GKKRXD` proposes deleting `infra/k8s/` + `infra/nixos/`. **Nothing was
deleted.** Its core holds (the `argocd/zeta-root` collision is real — both manifests read
and confirmed), but one row of its evidence table is **false**, and it is the row the
deletion plan rests on:

> "referenced outside its own tree: only `infra/README.md` + docs"

`infra/` has **two live CODE consumers** that row misses:

1. **`flake.nix` (repo root)** — `nixosConfigurations.{control-plane,worker-gpu-01,worker-gpu-02}`
   import `./infra/nixos/hosts/*/configuration.nix`, and `nixosModules.{common,k3s-server,k3s-agent,gpu}`
   **are** `./infra/nixos/modules/*.nix`. Deleting `infra/nixos/` breaks `nix flake check`
   and every documented `nixos-rebuild switch --flake .#control-plane`.
2. **`src/Core.TypeScript/ace/deps.ts:429`** — `generateArgoCD()` emits Applications whose
   `spec.source.path` is `` `infra/k8s/applications/${chart}` ``. It ships in the `ace` CLI
   and the test does not assert the path, so after deletion it fails **silently**, in
   generated output, at deploy time.

So consolidation is a **migration, not a sweep**. The tree is now *proven referenced by
code*, deletion is gated on the maintainer sign-off the item already names, and the
ambiguity is recorded in the work-item rather than resolved unilaterally.

**Could not enumerate:** whether any machine outside this repo already tracks
`.#control-plane` from the root flake. Off-repo state, not knowable from here.

**Also confirmed, not touched:** `single-node-readiness.ts` exits 1 on `main` today — a
`false-redundancy` blocker for `full-ai-cluster/kubevirt` (`replicas: 2`, no anti-affinity)
from #11089. Already being fixed on `fix/ledger-ack-kubevirt-false-redundancy`; noted so the
next reader knows the auditor's red is that, not this.
