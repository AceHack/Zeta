## Finding: the aarch64 lane is INTERMITTENT

Three instrumented CI runs, and they disagree — which *is* the result:

| run | ladder | outcome |
|---|---|---|
| [job 95208551157](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/31964938508) | firmware t=1s, bootloader t=16s, efi-stub t=17s, **then nothing for 4184s** | never booted |
| [job 95218377728](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/31969001908) | firmware t=1s, bootloader t=16s, efi-stub t=17s, **login t=192s** | **BOOTED** |
| local (M2 Ultra, pure TCG) | firmware t=1s, bootloader t=16s, efi-stub t=17s, login t=52s | BOOTED |

Same image, same workflow, same runner type. Identical to the EFI stub on all three — then the *same* segment takes 175s on one CI run and >4184s on the other. A **>24x swing**.

So it is **not uniformly slow** (my #11007 story) and **not deterministically hung** (this PR's original story). I had one bad run and inferred a mechanism from it — precisely the error `numerology-vs-number-theory` names: one observation licenses an investigation, never a conclusion.

**This vindicates the comment already in the file** (2026-06-12): two 900s timeouts parked in the EFI stub, then the identical commit passed on rerun once the runner pool freed. That author had it right; credited in the source now.

## What this PR ships

A fourth outcome, **STALLED (exit 4)** — serial produced nothing for `DEFAULT_STALL_SECONDS` past the kernel handoff.

It earns its place as a **cost bound**, not a diagnosis: it cuts the wasted arm-runner time on a bad run from 70 minutes to ~20, without claiming to know why.

- `DEFAULT_STALL_SECONDS = 1200`. A healthy CI boot is **192s end-to-end**, so 1200s of pure silence is >6x a whole good boot. (It was 600s when I believed the hang story; that left too little room for a contended-but-progressing run to be cut off and mislabelled.)
- The reason string reports the **fact** — silence of N seconds at stage X — and says explicitly that it **cannot tell hung from starved**. The earlier text asserted *"this is a HANG, not a slow boot"*, a verdict the evidence does not support. Detection is dual-use; the mechanism reports, it does not judge.
- The **stage floor is load-bearing**: silence *below* the bootloader is already BOOT-FAILED and must not be relabelled a kernel stall, so STALLED only applies at or above `efi-stub`.

## Recommendation — and it flipped

**STALLED should STAY advisory.** My earlier draft argued it was probably a real break and leaned toward blocking. The good run refutes that: on this evidence a stall is at least as likely to be a starved runner as a broken image, and blocking would red the ISO lane for runner contention.

`BOOT-FAILED` (exit 1) remains the bucket that carries positive evidence, and that one blocks.

## Still not known

**Why** a run stalls. Local QEMU is 11.0.1 + edk2-stable202408; CI is 8.2.2 + edk2 2024.02. I could not test QEMU 8.2.2 locally, so no cause is asserted. Given the intermittency, runner contention is the leading candidate and the file's original author already said so.
