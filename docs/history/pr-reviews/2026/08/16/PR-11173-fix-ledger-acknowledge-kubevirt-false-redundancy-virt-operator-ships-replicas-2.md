## Description

## What broke

The single-node readiness auditor went red on main after #11089 vendored the KubeVirt operator manifest:

> `full-ai-cluster/kubevirt` declares replicas > 1 with `none` anti-affinity. On 1 node(s) every replica co-schedules: the redundancy is nominal, the failure domain is one node.

**The finding is correct.** The tool did its job on my change. `kubevirt-operator.yaml:8493` sets `replicas: 2` on the `virt-operator` Deployment — upstream KubeVirt's control-plane HA default — and on one node both pods land together.

It is also *accurate about prod*: node-5b2dfa really does run two virt-operator pods today (`virt-operator-576b8d796c-5xrk2`, `-6cs88`). The manifest isn't wrong about the cluster; the cluster is a single node.

## Why acknowledged rather than edited to 1

That manifest is vendored **byte-for-byte** from the upstream release precisely so it stays 1:1 with what runs. Editing it would make the checked-in copy diverge from the cluster it documents — a worse lie than the one the ledger exists to state out loud.

The entry resolves itself at `nodeCount >= 2` with no code change, which is what the ledger's own comment says should happen.

## Verification — stated honestly

This **could not be fully confirmed locally.**

`single-node-readiness.ts` derives app identity from raw paths without normalising separators. On Windows every app reads as `full-ai-cluster\k8s\applications\<x>\Application.yaml`, so **no** ledger key matches and the local run reports 5 failures — including `cockroachdb`, `vault`, `nats`, `redis`, `platform`, all long-acknowledged and green on Linux.

That is a **Windows portability bug in the auditor**, not a finding, and it is deliberately left alone here rather than folded into an unrelated fix.

What *is* confirmed:

- CI reported the app name as exactly `full-ai-cluster/kubevirt` — that is the key added
- the JSON parses and the key is present

CI is the check on this one, not my local run.
