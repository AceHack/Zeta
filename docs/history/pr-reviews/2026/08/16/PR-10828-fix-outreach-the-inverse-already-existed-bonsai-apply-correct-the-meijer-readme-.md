## Description

## The finding inverts the brief

This PR was commissioned to "write the inverse of `reify`, which does not exist." **It exists.**
It is called `Bonsai.apply`, and it sits 46 lines below `reify` in the same module. A search for
`unreify` / `toExpr` / `ofDynamicValue` / `fromDynamicValue` misses it purely because of the name.

The round-trip law is already pinned, twice, and the stronger of the two is a machine-checked proof:

| Artifact | What it pins |
|---|---|
| `tests/Tests.FSharp/Bonsai.Property.Tests.fs` | FsCheck property: `apply (reify e) = Ok e` |
| `src/Core.Lean4/Lean4/Bonsai.lean` | `theorem apply_reify_eq_self` — strong induction on term size, all six constructors, no `sorry`, imported by `Lean4.lean` |

So **no inverse was written here.** Writing one would have duplicated a proof strictly stronger
than the property test that was requested. Reporting that is worth more than the code.

## What is actually in this PR

### 1. A real gap in the shipped property test, found and closed

The generator fixed `Lambda` params and `Call` args at exactly **arity 2** — no 0-, 1-, or 3-ary
node was ever generated. Closed by generating arity `0..3`.

Proven non-vacuous by a mutation only the new generator can catch. Mutant: `apply` rejects every
call whose arity is not 2.

* old fixed-arity generator vs that mutant: **exit 0 — passes a genuinely broken decoder**
* new generator vs the same mutant: **exit 1**, counterexample `Call ("_Z", [Param "000Z0"])`

### 2. The outreach README's register corrected

Aaron authorized this ("yes please make any fixes"). The document is addressed to Erik Meijer,
whose published work *is* this duality, so a design stated as an implementation is the worst
available outcome. Measured against `main`:

| README claim (present tense) | Measured |
|---|---|
| behaviour AST embedded as a **peer node type** | **design** — `DynamicValue` has no `Quote`/`Expr` constructor; the embedding is an encoding into `Object` nodes |
| `quote : μF → νF`, `run : νF → μF` | **design** — neither function exists |
| `run(quote(d)) == d` | **design** — and see below |
| four **independent executors** | **wrong word** — the four oracles are serializers/parsers; they execute nothing |
| round-trip proofs | **understated** — the Lean proof is stronger than the page claimed |

Three further corrections found while measuring, all cutting against us:

* **`reify`/`apply` are F# + Lean only.** TS/C#/Rust ship `serialize`/`parse`, not `reify`. The
  four-oracle byte-lock covers the *wire format*, not the reification. The page implied otherwise.
* **The `run(quote(d)) == d` check in `Dv.kt` is vacuous.** `quote` wraps `d` in `Node.Quote(d)`;
  `eval` of `Node.Quote` returns the stored value verbatim. It is `unwrap(wrap(d))` — true by
  construction, cannot fail, evidences nothing. The *non-trivial* law is the encoding round-trip,
  which is the one that is actually proven.
* **The μF/νF framing is not licensed by the types.** Both `Expr` and `DynamicValue` are finite,
  strict, inductive trees — least fixed points. Neither is a genuine ν. Worth saying to the person
  who drew that distinction. **Extended in the second commit** — see below.

`run` is not wholly absent, and the page now says so: `BonsaiSoft.evalSoft` is a partial evaluator
(F#-only, covers `Const`/`Param`/`Binary`/`Cond`, declines `Lambda`/`Call`, returns a distribution).

**Recommendation on four-oracle, priced honestly:** do not extend `reify` to four oracles now. The
Lean proof already gives a stronger guarantee than cross-oracle agreement would for this law, and
the wire format — the thing that actually crosses a boundary — is already byte-locked. A four-oracle
reification is real work with a weaker payoff than it appears.

## Follow-up landed: the forward direction on μ vs ν (second commit)

Aaron 2026-08-15: *"yes these are in finite domain, I think his are in infinite domain. We can get

The finding as first landed read as a pure negative. The addition supplies the **mechanism**, which
is the load-bearing part: a ν is reached by a **generator** — an anamorphism with no terminating
condition, codata — **not** by a larger inductive type. Growing `Expr` never approaches it.

**Cited, not restated.** The instance was already in the repo, in two places, so the paragraph points
at them rather than re-deriving:

* `src/Core/CayleyDickson.fs` — the doubling primitive's docstring already carries the degradation
  ladder (ℝ→ℂ lose order, ℂ→ℍ lose commutativity, ℍ→𝕆 lose associativity, 𝕆→𝕊 lose alternativity
  and division)
* `docs/FROZEN-CORE-AND-CONJECTURE-REGISTER.md` — the row already attributes the **exact ladder to
  Hurwitz** and names "Hurwitz 1898" in its anchors, with the floor decision at 𝕆

**Correction to the coordinator's brief, in our favour:** the repo record is stronger than the brief
assumed. Hurwitz was not something to add — it was already recorded and correctly attributed.

**Hurwitz verified before repeating** (checked, not cited): the normed division algebras over ℝ are
exactly ℝ, ℂ, ℍ, 𝕆 — dimensions 1, 2, 4, 8, complete list. Correct as stated in the brief.

**Both bounds written in**, since either omission would be the overclaim this rewrite exists to fix:

1. **The tower is not itself a ν.** Every rung one can materialize is finite; `Doubled<'A>` iterated
   yields finite types at every step. What has no terminating condition is the *lift*
   `IStarRing<'A> → IStarRing<Doubled<'A>>`. The coinductive object is the unfold, not any level.
   This is a sharpening of the brief, which described the doubling as "structurally a genuine ν."
2. **The useful prefix has a hard cliff at 8** — by Hurwitz — which is also where the repo's
   octonion/E8 frontier already sits.

## The second question (asked mid-task): exact fixpoint, or advanced by one tick?

Answered as analysis in the doc; **no ticked fixpoint implemented**, as instructed.

**The question does not arise at the layer `reify`/`apply` operate on**, and for a structural
reason rather than a shrug. `apply ∘ reify` is a total `Expr → Expr` with no injected channel and
no state. For a tick to be *observable* it needs somewhere to be written, and `Expr` carries no
temporal coordinate — no height, generation, or clock reading. A `∂_τ` there is either `id` (no
observable) or it leaves the type. The two candidate laws are therefore not merely hard to separate;
they are **indistinguishable in principle** at that layer.

The sharper form: this is one fact stated twice. What makes the encoding law byte-lockable and
DST-replayable is that it has **no ambient channel** (§13 noninterference) — and that is exactly
what leaves no room for a tick. In `AdinkraClock.fs` the tick *is* observable precisely because the
clock is not in the state; it is an injected `VirtualTimeScheduler`.

So the coordinator's suspicion is confirmed, and the more valuable finding lands with it: **the
encoding law and the reflection fixpoint are different laws about different things**, and the README
conflated them. That conflation is now the README's most prominent correction.

Where the question *would* become askable: at the value/execution level. Even there, `quote` of pure
data reduces in zero steps, so the tick is **0 on data** and the two laws agree on exactly the domain
the README states. They could differ only on the behaviour half. The separating experiment, stated
but not built: give `run` a second output channel (step count or injected scheduler) and check whether
`run(quote(p))` for reducible `p` reports a nonzero tick.

**Register, marked** (`numerology-vs-number-theory.md`): the match between evaluation's decreasing
step measure and the adinkra down-edge is a **resonance, not a shared mechanism**. The adinkra `∂_τ`
comes from a Z2-graded SUSY algebra; a reduction order has no parity and no anticommutator. Generator,
not result. The cited sources were verified rather than taken on trust — `AdinkraClock.fs` and the
2026-07-11 research doc do use that vocabulary as quoted.
