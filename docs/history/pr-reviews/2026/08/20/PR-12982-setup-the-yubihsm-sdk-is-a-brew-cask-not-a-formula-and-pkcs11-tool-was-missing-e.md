## Description

Aaron 2026-08-20: *"we need to make sure new contributors to Zeta just get this for free on Mac,
Windows, Linux."* The YubiKey half was already landed by an earlier round. The two genuine gaps
were the **YubiHSM SDK** and **`pkcs11-tool`** — the SDK ships `yubihsm_pkcs11` and **nothing in
the declared toolchain could load a PKCS#11 module.**

## The hard part evaporated, and the reason is an owned error

The design doc's §6 concluded Homebrew cannot install the SDK, on the strength of
`api/formula/yubihsm-shell.json` → **404**. That checked the **formula** namespace. It is a **cask**:

```
api/cask/yubihsm2-sdk.json  → 200
token yubihsm2-sdk | tap homebrew/cask | version 2026-04
arm64 sha256 2f8e80e9…  |  artifacts: pkg + uninstall pkgutil com.yubico.yubihsm2-sdk
```

The same Yubico `.pkg` Aaron hand-installed, **with a digest Homebrew maintains** — strictly better
than a `from-url` row whose `sha256=` we would have had to supply ourselves.

> This is the identical error class the `manifests/apt` block warns about **in writing** (verify
> the weak proposition, assert the strong one) — committed one manifest over, by the person who
> wrote the warning. Recorded as a correction rather than silently patched.

**Verified independently before landing:** the cask API returns 200 with that digest and a `pkg`
artifact; the formula URL still 404s, so the correction is exact.

The cask is deliberately **not** tier-gated: a `tier=` token would make `macos-install-sh-test` skip
it, and **a row CI never exercises is an unrun check wearing a green face.**

## Apt verification refused the easy source

Rather than `packages.ubuntu.com` — *the exact check that produced the earlier "E: Unable to locate
package yubihsm-shell" failure* — the archive's own binary indices were parsed, reading the
component: `opensc` present in noble/universe (64,754 pkgs parsed) and jammy/universe, **absent
from noble/main**; the yubihsm packages absent from all three. The real shell parsers were run
rather than trusted by reading.

## TODOs, each with its reason

- **Windows YubiHSM SDK — no row.** winget-pkgs has no HSM entry under Yubico; scoop and chocolatey
  404. Yubico ships a zip plus a **detached `.sig`**, and `from-url` downloads but cannot unpack.
  **A sha256 computed from our own download would be trust-on-first-download wearing a pin's
  clothes**, and the `.sig` is the real answer that nothing here verifies.
- **Debian SDK — no row.** Tarball-of-debs; `from-deb` verifies nothing, and `linux.sh` skips apt on
  NixOS anyway.
- **micro/uni kernel — no such target exists.** The term appears only in `memory/` and open P2
  umbrellas; no seL4/Unikraft/Mirage, no image build. The dominating prior question is whether it
  has a **USB host stack** — a YubiHSM 2 is a bulk USB device, invisible to the smartcard stack.
  **No fake target invented.**

## Three findings filed rather than fixed

- **`install.ps1` picks the first available *source*, not the first that *succeeds*** — no
  fallthrough, and scoop is bootstrapped unconditionally, so a winget-only package hard-fails the
  whole Windows install unless marked `optional`.
- **`manifests/apt` has no `tier=` gate** while brew and brew-cask do — five hardware rows now ride
  24 gate jobs with zero CI benefit. **The razor belongs on the gate, not the row.**
- **`manifest-symmetry` parses `apt` + `brew` only, never `brew-cask`** — so a cask can drift from
  Windows unflagged, which is exactly what `yubihsm2-sdk` (mac) vs nothing (Windows) now is.

**Register:** registry facts measured; **installs unverified until CI runs them.** No
brew/apt/scoop/winget executed, device untouched.
