## Description

> *"yes this sound good to do, yubihsm is hooked up here and i will buy many over time if its a secure device"*

**Hardware was exercised.** Device: YubiHSM 2, serial 39160506, **fw 2.4.1**, part `78CLUFX5000P`. Unauthenticated `get-device-info` only — **no session opened, no key material created, read, or handled.**

## Why this run existed

`frost-partial-signer.ts` registers its own claim honestly, and in doing so **names its own falsifier**:

> *"NO HARDWARE WAS EXERCISED FOR ANY CLAIM IN THIS FILE… **CHECKED** against the spec, **PROPOSED** as applying to any particular token, since token mechanism lists vary and vendors add extensions."*

A device is now attached and authorized. So the falsifier was run.

## Result 1 — the FROST claim holds, now measured rather than inferred

- **No modular scalar arithmetic returning a number.** `ecdh` is the only op touching the scalar arithmetically, and it yields a *point multiplication* and a key — not an element of `Z_L`.
- **Signing is all-or-nothing.** `ecdsa-sha{1,256,384,512}` and `ed25519` generate their own nonce and compute the challenge over *their own* `R` — neither can bind to the group's `R`, which is exactly what a FROST partial is.
- **The stated escape hatch doesn't apply.** Yubico's extensions are `*-yubico-otp`, `*-yubico-authentication`, `template-ssh` — OTP, session auth, SSH cert templating. **None threshold-related.**

> The `hardware-boundary` FROST adapter the hexagonal-PKI ADR says is missing **cannot be built on this device.** Scope stated: one device, one firmware — it does not speak for TPM 2.0, other vendors, or future firmware.

## Result 2 — `eck256` is present, and that changes what's possible

**`eck256` is secp256k1.** With `ecdsa-sha256`, this device can **hold a secp256k1 key and sign without it ever leaving hardware** — the curve an **x402** authorization needs.

> *"we connect this yubikey to x402 but a decentralized form not remote custody centralised form"* — **the decentralized form is available on this hardware.** That was not previously established.

Three client-side adaptations, none blocking: **keccak256 off-device** (ECDSA signs a digest, so the on-device hash label isn't load-bearing), **recovery id `v`** recovered by trying both candidates, **low-`s`** normalization for EIP-2. `ed25519` is present too.

## Result 3 — per-agent key partitioning is a device feature, not something we build

> *"maybe we can have AI's per docker continer restricted to only ceratin keys… key/process combination"*

Verified from `yubihsm-shell --help` and `libyubihsm` capability strings:

| mechanism | what it does |
|---|---|
| **`--domains`** | partitions the object space; an auth key sees only its domain |
| **`--capabilities`** | fine-grained per-object verb bitmask (`sign-*`, `export-wrapped`, `exportable-under-wrap`, `get-log-entries`, …) |
| **`--delegated`** | **an auth key cannot grant what it does not hold** — privilege is monotone-decreasing, so there is no escalation primitive to close |

One auth key per container, own domain, `sign-ecdsa` **only**, never `exportable-under-wrap`. One compromise loses *one domain*, and cannot exfiltrate the key.

**The honest limit — the half you already anticipated.** This binds capability to a **credential**, not a **process**. A container is **not** a hardware trust boundary. Closing the process half needs measured launch / code signing, and properly, per-VM attestation (SEV-SNP/TDX) — already on file as the *"Xbox-style"* fix in `081KRW63S0008QG0R0022SFKPM`.

**And an ordering worth stating because it's the opposite of the intuitive one:** a TPM binds to *the node*, and a node runs many agents. **The HSM isn't just "stronger than TPM" — it's the piece that supplies multi-tenancy, which the TPM structurally cannot.**

## Guard

**Custody vs settlement.** A facilitator that only *verifies* a locally-produced signature is an **oracle** you can route around. One that *holds the key* is a **hub** — and the discriminator is **exit**.
