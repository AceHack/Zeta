## Description

Hardware on the bench today: **YubiHSM 2** (serial 39160506, fw 2.4.1) and **two YubiKey 5s** (fw 5.7.4, serials 37516430 / 37600955). Per the standing rule already quoted in `manifests/brew` — *"download whatever tools we need and link them in our declarative installers for all our OS shields"* — the tooling belongs in the manifests, not in whatever each host happened to install by hand.

## One change, not two

**`ace` needs no separate registration.** It already realizes these manifests through `src/Core.TypeScript/ace/setup-realizers/` and `tools/setup/ace-mechanism-pointers.json`. The manifests *are* the single source of truth and `ace` is the realizer over them — so declaring here is declaring for `ace`.

## The asymmetry is the point

| | packages |
|---|---|
| **apt** | `yubikey-manager` `yubico-piv-tool` `yubihsm-shell` `pcscd` `libpcsclite1` |
| **brew** | `ykman` `yubico-piv-tool` |

Linux needs strictly more, and the extra entries are the ones that silently bite.

macOS ships a CCID smartcard stack in the OS — verified on the bench host, where the YubiKey appears under `SPSmartCardsDataType` against an Apple `ifd-ccid` driver with nothing installed by us. **Linux does not.** Without a running `pcscd` the CCID interface is invisible and `ykman` reports *no device* while the key is plugged in and enumerated on USB: tool present, device unreachable, install "succeeded". That's the half-working shape, so `pcscd` + `libpcsclite1` are declared rather than assumed from the runner image.

**udev matters for the same reason.** The `yubikey-manager` and `yubihsm-shell` debs ship rules under `/lib/udev/rules.d/` granting non-root access to Yubico's vendor id (`0x1050`). Installing *via apt* is what puts them there; a pip or tarball install of ykman does not — which is the usual reason a working macOS setup fails to reproduce on Linux.

## What is deliberately *not* declared

`yubihsm-shell` has **no brew formula** — `brew info` resolves to nothing. Yubico ships the macOS YubiHSM SDK as a `.pkg`, which is why the working copy on the bench sits at `/usr/local/bin` and not `/opt/homebrew/bin`: it didn't come from brew.

Wiring that through `from-installer` needs a pinned URL + checksum, and an unpinned installer download is precisely the unverified-binary case the proof-lineage rule refuses. **Left out rather than half-declared.**

## Verification — and one correction mid-check

Every apt name was looked up against `packages.ubuntu.com/noble` (the runner distro) before being declared; brew names against `brew info --json` (ykman 5.9.2, yubico-piv-tool 2.7.3 confirmed).

The first apt lookup returned `000` for four of the five. **That's a failed request, not an absent package** — re-running with a longer timeout returned `200` for all four. It's recorded in the manifest comment, because reading a timeout as *"not packaged"* is exactly how a check that did not run gets treated as one that did.

Windows dispositions are **honest exceptions, not guessed scoop ids**. Yubico ships Windows tooling as signed MSIs and no scoop/winget id was verifiable from this host; `pcscd`/`libpcsclite1` are Linux-only by construction (Windows has `SCardSvr`/`WinSCard` as OS components). Putting an unverified package id into every Windows host's install path would be a claim dressed as a declaration.
