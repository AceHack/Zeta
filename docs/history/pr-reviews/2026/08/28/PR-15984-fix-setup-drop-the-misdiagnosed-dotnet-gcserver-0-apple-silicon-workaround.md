## Description

## The flag does not work, and it was never a .NET bug

`shellenv.sh` exported `DOTNET_gcServer=0` on every Apple Silicon machine as a ".NET 10 Server GC workaround (Otto-248)".

**With the flag active**, the SIGSEGVs continue in the *identical* three GC frames — `plan_phase`, `find_first_object`, `revisit_written_page`. It moved every crash from `SVR::gc_heap::*` to `WKS::gc_heap::*` and stopped nothing.

**And the fault is not .NET-specific.** Eight days of crash reports:

| | |
|---|---|
| memory faults | 97 (68 inside a heap-walker or allocator) |
| affected runtimes | node/V8 (32), dotnet (22), lean, git, rustc, python3, WebKit — **and Apple's own daemons**, which run none of our code |
| kernel panics | 10, eight of them page-mapping accounting failures (`pmap_recycle_page: page is referenced`) |
| last clean shutdown | 2026-08-13 |

One reproduction killed **two independent `fsc` processes in the same second, in two different GC phases**. No compiler bug explains that; a machine-level event does.

## Why removing it is the correct direction

The cost was real — Server GC disabled on a 24-core M2 Ultra for no measured benefit. And a workaround that does not work is *worse* than none, because it makes the fault look handled. That is the vacuity class applied to an environment variable: it has the shape of a mitigation and none of the effect.

## What replaces it

Nothing. A comment stating the measurement and saying not to re-add a GC flag for this. The open question is hardware vs kernel page lifecycle, which cannot be settled from userland — **Apple Diagnostics is the blocking step**, and on Apple Silicon that is: hold the **power button** for startup options, then **⌘D**. (Holding `D` is the Intel procedure and does nothing on an M-series machine.)

## Verification

The script *writes* `~/.config/zeta/shellenv.sh` rather than printing exports, so the check is on the generated file, with a control: **0 gcServer lines, 7 real exports** — a non-zero export count is what makes the zero meaningful rather than vacuous.
