## Description

## A trap with a success message

A tracked-but-ignored file keeps working — git honours the index. But `git add` on a **new sibling** silently does nothing and **still exits 0**. Nobody finds out until content that existed in one place quietly fails to commit.

**Measured 2026-08-28: 17 tracked files were in that state.**

| where | n | what |
|---|---|---|
| `.kiro/` | 5 | tracked specs + service definition |
| `src/wasm-dla/bytelock/` | 7 | the six substrate modules the byte-lock executes, plus `wasm_exec.js` — **the repo's own documented exception** in `no-binary-in-proof-lineage.md` |
| `.claude/bin`, `.gemini/bin`, `src/**/src/bin` | 4 | `bin/` matches at **any depth**; only `.codex/bin/` was exempted. Rust's `src/bin/` is a language convention |
| `db/drop/` | 2 | its `.gitignore` and README |
| `roms/.gitignore` | 1 | excluded by its own `*` |
| `tools/**/.gitkeep` | 2 | legitimate — see below |

## It cost something the same day

Rescuing files from orphaned worktrees, `git add` staged **439 of 447** and reported success. The eight it dropped were `.gemini/bin/lior-loop-tick.ts` copies — files that, being untracked by design in their source trees, existed in **no other copy**.

When a rescue is filtered by the same rules that made the content untracked, the filter removes exactly what most needed rescuing.

## The non-obvious part

**Git cannot re-include a file whose parent directory is excluded.** So `!.kiro/specs/**` under a bare `.kiro/` is *inert* — it looks like a fix and changes nothing. The directories are now excluded as `.kiro/*` and `db/drop/*` so the negations actually apply. Verified by count, not by reading the rule.

## `.gitkeep` stays tracked-and-ignored

That is what the file is **for** — it makes git create an otherwise-ignored output directory. The test carves it out **by exact basename, never by directory prefix**: a prefix allowlist grows silently and re-admits the class it exists to exclude.

## Falsifier

`no-tracked-file-is-ignored.test.ts` checks the **property**, not the 17 known paths, so the next rule that swallows a tracked path fails here rather than in someone's lost work.

- carries a control (`> 1000` tracked files) so it cannot pass vacuously outside a checkout
- `--no-index` is load-bearing: without it `check-ignore` stays **silent on tracked paths**, which is the entire population under test
- verified by injecting a real regression — passes → remove the `.gemini` exemption → **fails** → restore → passes
