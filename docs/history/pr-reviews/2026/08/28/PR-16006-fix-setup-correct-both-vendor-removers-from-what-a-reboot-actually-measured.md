## Description

A reboot on 2026-08-28 **falsified a claim in one script** and revealed a surface the other did not cover.

## 1. The vendor system-extension script's central claim was wrong

It stated app-removal-then-reboot as *"the supported path"* full stop. Two vendors, same machine, hours apart:

| vendor | after app removal + reboot |
|---|---|
| Microsoft Defender | `[terminated waiting to uninstall on reboot]` → **gone**. Zero extensions, zero processes. |
| Insta360 Link Controller | app removed (not even in the Trash) → **still `[activated enabled]`**, payload still in `/Library/SystemExtensions/` |

So it is *a* path, it worked once, and it did not work the next time. The likely reason: deactivation is **requested by the app** via `OSSystemExtensionManager`, and an already-deleted app cannot issue that request — success depends on what the vendor did before its app went away.

Also measured: `systemextensionsctl uninstall` refuses under SIP —

> *"At this time, this tool cannot be used if System Integrity Protection is enabled."*

…and **exits 0 while refusing**, so an exit-code check reads that as success. The output is the only signal. Worth knowing generally.

The header now states the three options that actually remain — reinstall the app so it can deactivate its own extension; disable SIP in recovery; or leave it, since with the app gone the extension is registered but **inert** — and says plainly that none is a command this script can run.

## 2. Paragon: widened to preference panes, third surface named as out of reach

The 2 plists weren't the whole story — `/Library/PreferencePanes/Paragon*.prefPane` survived the vendor uninstaller too. The original scope note invited exactly this (*"widening this is a reviewed diff, not a surprise"*).

**What it still cannot cover, and why it says so:** after the reboot the `FSMenuAppLoginItemHelper` jobs came back, and `launchctl print` shows them as **"submitted by smd"** — SMAppService / Background Task Management registrations, not plists. `sfltool dumpbtm` confirms they point at `/Applications/NTFS for Mac.app`, which no longer exists. Stale BTM entries go through System Settings > Login Items & Extensions or age out; the only CLI lever is `sfltool resetbtm`, which wipes **every** application's background items — far too broad for one vendor. Deliberately not attempted, and named rather than left as a silent gap.

## Falsifiers

4 new tests for the prefPane selector (9 in that file, 16 across both). **Mutation-verified**: a match-everything prefPane matcher turns 3 red, including the control pinning other vendors' panes — this runs as root with `rmSync(recursive)` in a directory every vendor shares, so over-selection deletes someone else's software.

One test pins that the two selectors don't cross: they use different rules (bundle-id prefix vs product-name prefix), and crossing them would either miss the panes or double-count them.
