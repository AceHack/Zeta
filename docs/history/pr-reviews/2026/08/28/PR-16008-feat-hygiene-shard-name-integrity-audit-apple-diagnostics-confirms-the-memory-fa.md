## Description

Apple Diagnostics returned **RED on memory** for the maintainer's Mac Studio today. That closes an eight-day investigation which deliberately stopped one step short — *"between failing memory hardware and a kernel page-lifecycle defect, I cannot discriminate from userland."* The diagnostic discriminates: **hardware**.

## Why `git fsck` cannot find this class

**Git hashes what it is given.** A flip occurring *before* hashing produces an object that is internally consistent — correctly hashed, and wrong. Every integrity guarantee git offers is downstream of the moment the corruption already happened. `fsck` proves bytes have not changed *since*; it says nothing about whether they were right when written.

## What does work: derivable redundancy

Two independent encodings of one fact that must agree. Shard paths have exactly that:

```
docs/github/prs/shards/015/08000000000000007803000000003a98.json
                       ^^^                              ^^^^
                       015 == floor(0x3a98 / 1000) == floor(15000 / 1000)
```

The directory is a *function of* the filename, so a flip in either breaks the relation. The audit catches **both** shapes:

| flip | example | hex-validity alone? |
|---|---|---|
| produces a non-hex char | the observed `0` (0x30) → `<` (0x3c) from PR #15007 | caught |
| **stays valid hex, moves the bucket** | `3a98` → `3298` (15000 → 12952, bucket 015 → 012) | **missed** |

**Measured: 13,448 shards, 0 violations.** main is clean.

## The runner refuses an empty scan

Fewer than 100 paths → exit 2. "0 violations" over an empty population is the difference between *nothing is broken* and *nothing was examined* — and this entire investigation is about checks that cannot fail.

## Where it must run

**CI, on Linux — not the machine under suspicion.** Verifying integrity with the hardware suspected of corrupting it is self-blinding by construction: the same error as probing whether a job finished over the API you are saturating. A clean *local* run of this audit is worth very little.

## Falsifiers

11 tests, built from the real specimen and from flips it did *not* happen to produce — a detector tuned to one observed corruption catches one corruption. Mutation-verified:

- removing the directory check → **3 red** (including the valid-hex flip)
- accepting uppercase hex → **1 red** (a case change is itself a single-bit flip, 0x61 vs 0x41)

## The uncomfortable part, recorded in the research doc

**Any result computed on that machine may be wrong in a way that leaves no trace** — not slow, not crashed, but *wrong and plausible*. Until the hardware is repaired, CI is the oracle and a local green is a hypothesis. Exit 139 is an **absent** check, not a failing one; it bit twice in a single session today.

Also noted: the April `DOTNET_gcServer=0` workaround is now fully explained as a misdiagnosis of this same fault — it moved crashes `SVR::`→`WKS::` and stopped none, at the cost of Server GC on 24 cores. Removed in #15984.
