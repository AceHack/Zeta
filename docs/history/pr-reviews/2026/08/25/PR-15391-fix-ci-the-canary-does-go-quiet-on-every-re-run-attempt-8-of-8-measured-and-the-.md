## Description

Follow-up to #15378. In that PR I reported gap 4 — "the canary detector went quiet" — as **wrong**, because the run I sampled showed it live. **I was sampling the wrong runs.** The canary is live on a first attempt and goes quiet on every re-run, and the mechanism had never been named.

## What #15378's own CI showed

`drift (loud)` on that branch printed:

```
DETECTOR WENT QUIET: no step-level absorption was observed in run 32870525290
(job `drift-canary` concluded `success` carrying 0 failure annotation(s)).
```

The canary **had** run. Its step **had** failed. Its job carried the step. The annotation — the only API-visible evidence of a step-level `continue-on-error` swallow — was absent.

## Measured, and the split is total

| | canary check-runs | failure annotations |
|---|---|---|
| `run_attempt == 1` | 7 | **exactly 1**, every one |
| `run_attempt > 1` | 8 | **zero**, every one |

Attempt >1 runs sampled: `32870525290` a2, `32869359742` a2, `32868648119` a2, `32868481016` a2, `32868231883` a2, `32867917835` a2, `32867661654` **a3**, `32865656489` a2.

> **GitHub does not reproduce a step-level failure annotation on a re-run attempt.**

The canary job on attempt 2 is otherwise byte-for-byte the same shape as on attempt 1 — same steps, same `success` conclusion, same swallowed failure. Only the annotation is gone.

## Why this is routine, not an edge case

`rerun-cancelled-gate.yml` automatically re-runs **every** `cancelled` gate run, and gate cancellation currently measures **63.3%** (`verdict-drought`, same job, same timestamp). So `drift (loud)` was emitting `DETECTOR WENT QUIET` on a large share of runs while step-level detection was working perfectly.

**The false alarm was eating the true one.** A detector that cries wolf on every re-run is a detector nobody reads — which is precisely how a real quiet gets missed. That is what "the canary went quiet" actually was.

## The fix is a third verdict, not a green

`LivenessStatus` becomes `live | quiet | unverifiable`. `unverifiable` is returned only on evidence that supports exactly that reading, and **every clause is load-bearing** — each has a falsifier that goes red if the clause is widened:

| clause | if it fails |
|---|---|
| the canary job is **present** | `quiet`, red — on any attempt |
| it still carries its **deliberate step** | `quiet`, red |
| annotations were **fetched** and came back `[]` | `undefined` ⇒ `quiet`, red — absent is not empty |
| `run_attempt > 1` | attempt 1 ⇒ `quiet`, red |
| a **missing** attempt reads as `1` | the strict reading, never the lenient one |

It is **still not `live`** — nothing was verified, and this file does not report green on unverified. It is a `::warning` naming a measured platform limit instead of an `::error` naming a breakage that is not there, and it does not set the exit code.

## And the exit line was doing the same thing one layer up

```
EXIT 0 -- no sustained drift, detector live, publication landing.
```

…was printed on an `unverifiable` verdict — a summary sentence asserting a check that did not run, which is this file's own defect reproduced in its last sentence. Now status-aware, with its own falsifier:

```
EXIT 0 -- no sustained drift, publication landing, detector liveness UNVERIFIABLE
on this attempt (see the warning above) -- not verified, not broken.
```

## Honest limit

This restores the *signal-to-noise* of the liveness check; it does not recover verification on a re-run. On `run_attempt > 1` there is no channel that carries a step-level swallow, so liveness genuinely cannot be established there — and the output says so on every affected run rather than implying otherwise. Recovering it would mean reading job **logs**, which is a heavier call per green job and a separate, priced decision.
