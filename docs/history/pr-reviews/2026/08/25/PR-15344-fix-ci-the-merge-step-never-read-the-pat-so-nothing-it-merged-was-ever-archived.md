## The merge step never read the PAT — so nothing it merged was ever archived

### Diagnosis: CONFIRMED, verbatim, on `origin/main` at `67cf9c45e`

`.github/workflows/agent-heartbeat.yml:645` — "Auto-merge clean PRs (agent-to-agent value transfer)" — carried `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`. Every other credentialed step in the file used `ZETA_TELEMETRY_FLUSH_TOKEN || ZETA_PR_ARCHIVE_TOKEN || GITHUB_TOKEN` (lines 76, 1490, 1795). The consequence chain is a **silence**, not a failure: armed with `GITHUB_TOKEN` → merge lands as `github-actions[bot]` → GitHub suppresses workflow triggers for `GITHUB_TOKEN`-driven events → no `pull_request: closed` → `pr-archive-on-merge.yml` never runs → **no run is created, so no run is red**.

**This is why granting the PAT more permissions never helped: the step did not read the PAT.**

### ⚠️ The one-line fix, applied literally, would have been WORSE than the bug

Swapping the token blind would have **armed nothing and stalled the merge queue outright**. `gh pr merge --auto` is the GraphQL mutation `enablePullRequestAutoMerge`, and the scoped flush PAT is measured being refused it *on every call*:

```
GraphQL: Resource not accessible by personal access token (enablePullRequestAutoMerge)
```

Recorded in `src/Core.TypeScript/agent-heartbeats/merge-heartbeats-to-main.ts` (§`ARMING_DISABLED`, "on every society-heartbeat run") and `docs/research/2026-08-13-graphql-is-the-scarce-budget-and-automerge-is-graphql-only.md`.

**So the fix prefers the PAT and degrades to `GITHUB_TOKEN` once per run on a refusal, naming the exact missing scope.** Today that is byte-for-byte the current behaviour plus a warning that says what is missing. The day the PAT carries the scope, archive coverage repairs itself with no further edit.

**Neither is required to merge this PR**, and granting **B** will not fix archiving. Nothing here changes a secret, a PAT, or a repo setting.

### The falsifier

`src/Core.TypeScript/hygiene/audit-workflow-write-token-consistency.ts`, wired into the `cross-verify` floor job. Fails when a step performs a forge **write** AND resolves its own `GH_TOKEN` to a bare `secrets.GITHUB_TOKEN` AND sits in a workflow that already references a PAT.

The third condition is what keeps this a **consistency check rather than a policy** — a repo-wide "always use a PAT" rule would be wrong for `accelerator-move-next.yml`. The defect was never `GITHUB_TOKEN`; it was one step out of nine disagreeing with its neighbours.

Write-op coverage is **not just the `gh` CLI**: most PRs here are opened by `flush-via-staging.ts flush` over the API with the step's own `GH_TOKEN`, so matching only `gh pr create` would have left the largest PR-producing population unchecked — the vacuity class. **2 forge-write steps before adding the in-repo writers, 13 after.**

### A behavioural note worth reviewing

`set +e` was added around the new output captures. No `shell:` is declared in this workflow, so `run:` blocks execute under the default `bash -e`, and `OUT=$(cmd)` is **not** errexit-exempt the way the `if gh pr merge ...; then` form it replaces was.
