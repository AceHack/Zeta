## Description

Four asks from the maintainer — vectorised, row store, column store, Arrow-compatible — with the honesty fix that had to come first. PR #15213 is the design doc behind this.

## 1. `SimdMerge.fs` was renamed, not repaired — and here is the measured reason

The file claimed AVX2/NEON/AVX-512 loads, "branchless compare + conditional select", and masked stores. It contained **no vector instruction at all**: `Vector<int64>.Count` was a loop chunk size and `Vector.IsHardwareAccelerated` guarded a second *scalar* loop. It also cited, as its correctness evidence, `FuzzTests."fuzz: SIMD merge matches scalar"` — **a test that does not exist**.

It is now `src/Core/ScalarMerge.fs`; members are `MergeTwoPointer` and `MergeBlockwise` (neither name retains a changed meaning). The header was not simply stripped — a misleading *name* outlives a misleading comment.

**Why it was not made true instead.** A sorted merge is data-dependent: the comparison result decides which side advances, so there is no fixed-stride lane mapping. Vectorised merges (bitonic networks, Inoue & Taura's AA-Sort merge) need a full sorting network or a shuffle-based permute, and both want the keys in a *contiguous* lane — which `ZEntry<int64>` (AoS, `[Key][Weight]` interleaved) cannot supply without a strided gather. **That is the same AoS blocker `ZSet.weightedCount` already documents**, which is exactly why the real vectorisation lives on the columnar side below. An honest rename plus this reason is the deliverable; a fake speedup was the alternative.

Four doc surfaces asserted the false claim as shipped and are corrected: `TECH-RADAR` (was **Adopt**), `ROADMAP` (was ✅), `README`, `SPEC-AUDIT`.

## 2. `ColumnZSet` — struct-of-arrays, a SIBLING of `ZSet`

`src/Core/ColumnZSet.fs`. Two parallel `int64` columns; same keys, weights, sort order and no-zero-weight invariant as `ZSet`. **Nothing is migrated onto it and `ZSet` is untouched** — sibling-vs-replacement is the maintainer's call, not mine, and this PR does not make it.

Three kernels, each with a scalar twin that must agree on every input. `Checked` arithmetic survives vectorisation: signed overflow is detected branchlessly per lane via `((a^s) & (b^s)) < 0`, OR-accumulated and inspected once — the vector paths do **not** buy speed by trading away the noisy-crash guarantee.

## 3. Measured, on an Apple M2 Ultra (arm64/NEON, `Vector<int64>.Count = 2`)

**Provenance, precisely.** The table below was produced by a standalone best-of-21 harness running the *same kernel bodies* that are committed here, with each path sink-consumed and the scalar/vector order swapped to rule out a tier-up or PGO artifact. That control mattered: an earlier sweep of mine showed 0.98x for the same function, and it was wrong — the results were discarded so the JIT deleted the scalar loop's work. `bench/Benchmarks/ColumnZSetBench.fs` is committed as the reproducible BenchmarkDotNet form and is the surface to re-run; its numbers are not yet pasted here. The claim that is *enforced on every test run*, rather than quoted, is the 1.5x gate in §3's falsifier below.

The result is **not** uniformly "SIMD is faster", and the part that loses is stated first:

| operation | scalar | vector | verdict |
|---|---|---|---|
| `SumWeights`, n = 8 192 (in cache) | 9 760 ns | 3 124 ns | **3.1x faster** |
| `SumWeights`, n = 1 000 000 (8 MB, out of cache) | 257 µs | 386 µs | **0.67x — SLOWER** |
| `CountWhereKeyInRange`, n = 256 | 181 ns | 85 ns | **2.1x faster** |
| `CountWhereKeyInRange`, n = 1 000 000 | 3 175 µs | 295 µs | **10.8x faster** |
| `SumWeightsWhereKeyInRange`, n = 1 000 000 | 3 329 µs | 574 µs | **5.8x faster** |

Two regimes, and the difference is **not** lane width:

- **Unpredicated `SumWeights` is bandwidth-bound** out of cache. Wider instructions buy nothing when the loop waits on memory, and the overflow bookkeeping makes it a net loss. So `SumWeights` **dispatches to scalar** — and the design doc's guess that SoA would unlock a fast `weightedCount` via `MemoryMarshal.Cast` + `TensorPrimitives.Sum` is **refuted at the size that matters** (`TensorPrimitives.Sum` measured 0.84x vs the scalar twin at n = 1 000 000). The vector version is kept, tested and benchmarked because *the measurement is the deliverable*.
- **Predicated scans are branch-bound.** Scalar has a data-dependent branch per element, ~11 cycles when unpredictable. The vector form is branchless, so it wins ~9–10x — far more than 2 lanes. These **are** vectorised by default: the win is branch elimination, so it does not need a wide ISA.

**AoS-vs-SoA scalar changed almost nothing** (3 175 µs vs 3 329 µs). Layout alone bought ~0; vectorising it bought 10x. That is Abadi et al. 2013's central claim reproduced in miniature — column storage without column *execution* buys little — and it is why the column store and the vectorisation are one piece of work, not two.

Keys are drawn at random on purpose: sequential keys let the predictor learn the predicate and would understate the win ~5x.

### The speed claim has a falsifier, and I verified it fails

`ColumnZSet vectorized predicate scan is measurably faster than the scalar scan` gates at **1.5x** (~7x below the measurement, so it is not a CI flake risk). **Mutation-checked**: replacing `CountWhereKeyInRangeVectorized`'s body with the scalar loop drops it to **0.94x** and the test fails — while **all 14 correctness tests still pass**. That is the point: a correct scalar rewrite satisfies every equality test by construction, so the timing gate is the only thing that can catch a bypassed vector path.

Stated honestly in the test: there is no supported way to assert on JIT output, so a timing gate is a *weak* instrument. It is labelled as one rather than dressed up.

## 4. Arrow

`src/Core/ColumnZSetArrow.fs`. `ColumnZSet` and an Arrow `RecordBatch` of two `Int64Array` columns are the **same physical layout**, so this is a buffer handoff: write is `MemoryMarshal.AsBytes` per column into an `ArrowBuffer`, read is a span copy out of `Int64Array.Values`. **No builder in either direction.**

That is the argument for the columnar sibling that has nothing to do with SIMD: Arrow *is* a struct-of-arrays format, so `ArrowInt64Serializer` (row store) can only ever *re-encode* into it, walking AoS entries one at a time through `Int64Array.Builder().Append(...)`. A column store can hand it the buffer.

**On vacuity, plainly:** this is a **round-trip check, not a cross-implementation one** — both directions call the same `Apache.Arrow` 23.0.0 .NET library, and agreement between two call sites into one library is agreement between perfectly correlated implementations. Said outright in the header, along with what closing the gap needs (a pyarrow/arrow-rs-produced vector in hex-in-JSON) and that it is **not** done here.

The strongest check available without a second library *is* included: the **buffer** path and the **builder** path are two independent Zeta implementations and each must read what the other wrote — genuine cross-implementation at the Zeta level, explicitly not at the library level.

`golden-vectors-arrow.json` called itself a "cross-language ... interop treaty" while conceding both sides are .NET. Its `description` now says plainly that it is a same-library round-trip check. **Only that field changed** — all 47 `arrowHex` vectors are byte-identical, and no test reads the description (`DynamicValueArrowTests` reads `arrowHex` only); still green 11/11.
