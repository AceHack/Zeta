## Description

GitHub does NOT apply `.gitattributes` merge drivers when it creates a pull
request's merge commit. Several files this lane touches carry `merge=union`
precisely because both `main` and the lane APPEND to them —
`data/ci-runs.jsonl`, `db/mutation-findings/*.jsonl`,
`docs/github/prs/manifest.jsonl`, `data/rs-blocks.jsonl`. Locally git unions
them and merges clean; on GitHub the same pair is a conflict.

So whether a flush lands has been down to TIMING. If `main` happened not to
touch a co-modified append since the lane branched, it merged. If it had, the
PR was born CONFLICTING and the lane wedged.

MEASURED TODAY, which is what separates this from a theory: soraya's #15361
merged, and alexa's #15366 — same files, twenty minutes later — reported
`mergeable: CONFLICTING`. `gh pr merge` answered "the merge commit cannot
be cleanly created" while `git merge-tree` on the exact same base and head
returned rc=0 with zero conflict lines. Resolving that merge by hand (where
the union driver applies) and pushing the result flipped the PR to
`MERGEABLE` immediately. Line counts confirm the union did the right thing:
base 390, main 411, lane 408, merged 429 = 411 + the lane's 18 unique appends.

WHY THIS IS THE FIX AND ANOTHER UNION LINE IS NOT. `.gitattributes` records
this being rediscovered at least SEVEN times, each entry added after a lane
wedged — its own comments are dated 2026-08-17 ("wedged soraya's tick at
02:43Z"), 2026-08-17 again ("wedged otto's and soraya's ticks at 16:43Z ...
Fifth"), and 2026-08-22 ("SEVENTH"). Every one added the driver to one more
file. The driver was never the missing part; it works. What was missing is
that the merge has to happen WHERE THE DRIVER IS HONOURED, which is here.

After this, GitHub only ever fast-forwards, and the squash onto `main` stays
a single commit exactly as `required_linear_history` demands.

Two properties deliberately preserved:

* The immutable park is untouched. `$SOURCE_SHA` is pushed and VERIFIED
  before this runs, so the "no events lost" guarantee does not depend on the
  pre-merge succeeding.
* A REAL conflict still surfaces. If the merge fails even with this repo's
  drivers applied, it is genuine content conflict rather than the GitHub
  driver gap — the step warns, prints the conflict, aborts the merge, and
  leaves the snapshot parked for the PR to report. It does not force anything.
