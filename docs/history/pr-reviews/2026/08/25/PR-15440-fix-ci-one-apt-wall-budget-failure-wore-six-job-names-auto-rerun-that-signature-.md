Sixty of the window's failed runs were sampled and every failed job attributed to its failing

| red job name | workflow |
| --- | --- |
| `build-and-test (ubuntu-24.04)` | gate.yml |

| `live kind included Synced+Healthy proof (ubuntu-24.04)` | k8s-argocd-health-test.yml |

One infrastructure failure wearing six names. It reads as six unrelated flakes because the
job name is what a reviewer sees and the job name has nothing to do with the fault. Each
instance costs a human or an agent a manual `gh run rerun --failed`. **That is the toil this
removes.**

## It is NOT a stall — the correction decides which fix works

`linux.sh` prints *"stalled archive mirror, not a package error"*. Read against job
**97946436709** that word is wrong:

```
attempt 1  247s slice   103 packages fetched, killed inside emscripten (93.2 MB)
attempt 2   89s slice   emscripten COMPLETED in 86s (93.2 MB => ~1.08 MB/s), 8 more, killed
attempt 3   45s slice   27 more incl. pandoc (26.9 MB), killed inside podman
rc=124     "apt-get install did not succeed within the 420s apt budget"
```

Every attempt made continuous forward progress and apt's archive cache carried downloads
across them. The mirror was **slow, not wedged** — ~1.1 MB/s against the ~14 MB/s
(553 MB / 38.2s) healthy figure the 420s budget was sized from. **561 MB at 1.1 MB/s is
~510s of download alone, against a 420s budget.** The job ran out of wall clock while
succeeding slowly: a check that never ran, presenting as one that ran and failed.

## Decision 1 — where the retry lives: a scheduled sweep

Three candidates.

**(a) In-workflow / in the failing job.** Cheapest — the job is already running. **Refused on
supply-chain grounds:** that job executes pull request code, and giving it `actions: write`
hands a fork PR the ability to drive the Actions API.

**(a′) More in-step retry inside `linux.sh`.** **Refused as arithmetically impossible.** Three
attempts already share ONE 420s deadline, so a fourth does not add time — it subdivides the
same wall, and attempt 3 was already down to a 45s slice.

**(b) A `workflow_run` watcher**, the shape already in the tree. Zero latency. **Refused on
cost:** it fires once per failed run, and `gate` alone failed **117 times in the measured
5h15m** (~535/day). At ~40s per evaluation that is **~356 runner-min/day**, and it scales
*with* the failure rate — most expensive exactly when CI is worst.

**(c) A scheduled sweep — chosen.** Flat cost whether nothing failed or fifty things did:
96 ticks/day at ~45s (measured 7.2s for a 25-minute window carrying 4 failed runs) is
**~72 min/day**, ~5x cheaper than (b). One tick covers *every* workflow that calls
`install.sh`, so there is no per-workflow roster to drift, and it is idempotent by
construction — re-running the sweep re-evaluates the same runs and the `run_attempt` ceiling
makes the second pass a no-op.

**The price is latency, stated as a cost and not hidden.** This repo has measured GitHub
dropping ~16% of `*/15` slots with gaps of 12-43 min (p50 16, p90 27 — `heartbeat-liveness.yml`
header). Worst case is ~8 min (to fail) + ~43 min (to the next delivered tick) ≈ **51 min**.
Against a human noticing hours later that trade is not close; the cadence is a one-line change
if measured latency proves too slow.

## Decision 2 — the bounds, and what happens when they are exhausted

- **One automatic rerun per run id**, enforced by GitHub's own `run_attempt` counter, so the
  ceiling needs no state of ours and survives losing every record we keep.
- **Six reruns per sweep.** A degraded mirror hits dozens of runs at once and re-running all
  of them feeds the same wall a second helping of the same runners. Past the cap the sweep
  **stops** and logs `toolchain-install-stall-cap-hit` — that is the signal this is an outage,
  and an outage wants a human, not a retry.
- 120-minute staleness limit; supersession check.
- **Exhausted ⇒ the run stays RED**, loudly, with the mirror named in its own log. Nothing
  here ever manufactures a green.

## CodeQL found a real one, three times — and the resolution is to delete the sink

`js/http-to-file-access` (medium, *"Write to file system depends on Untrusted data"*) on the
`appendFileSync` that built the job summary. **It was right.** A job summary is a file write
onto a page rendered as Markdown, and a run's `name` (a workflow file's `name:` key, which a
contributor controls on a `pull_request` run) and `head_branch` are attacker-influenceable
strings that could close a table cell, inject a link, or forge a row.

Three drafts, same alert each time: the raw one, a character-allow-list one, and one that wrote
only a revalidated integer run id. **Reshaping a sanitiser until an analyser stops objecting is
appeasing a tool, not removing a risk** — and dismissing the alert would need a human clicking
in the code-scanning UI, which is the exact intervention this whole change exists to delete.

So the sink is gone. The summary was **additive**; the visibility contract this module owes was
always the structured stdout, where `JSON.stringify` is the containment and nothing touches
disk. Everything the table carried is in those lines, in the same job log, one scroll away, and
both counting queries in the workflow header read the API and the log rather than a file.

`safeRunId`, `summaryRow`, the `html_url` field and the `node:fs` import are **deleted in the
same commit**. A falsifier pins the absence — the source may not name `appendFileSync`,

so the assertion cannot pass vacuously on a moved path. The workflow header and the research
doc are corrected in the same commit; both had advertised a summary that no longer exists.
