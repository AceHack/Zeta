## 1. ENOSPC — the harness never deleted its 20G qcow2

`qemu-full-install-test.ts` creates a `DISK_SIZE_GB = 20` qcow2 under `mkdtempSync` and **nothing ever removes it**. The dispatch lane invokes the script four times in sequence, so free disk fell monotonically; the worker process died the instant step 28 started.

The blast radius is bigger than the steps that caused it. Steps 33-38 already carry `if: ${{ !cancelled() }}` precisely so a *failing* scenario still ships an ISO — but a *dead worker* ships nothing. **Run 32816110015 produced no x86_64 ISO artifact at all**, which is exactly the thing the maintainer needs to burn a USB stick.

Fix: `reclaimLargeTempArtifacts()` registered on `process.on("exit")`. Deliberately **not** a `finally` block — `reportResult()` calls `process.exit()`, which does not unwind `finally`, and the failing path is precisely the path that leaks. Log files are **not** reclaimed: `reportResult` prints the serial log as "preserved at", and that promise has to stay true.

## 2. The restore path is not proven — and could not be diagnosed

`zeta-creds-restore.service` carries `unitConfig.ConditionPathExists` over **four** paths (blob, USB UUID, restore CLI in the cloned repo, the zeta user's mise `bun` shim). **systemd skips on an unmet condition — it does not fail.** So run 32816110015's phase-2 serial is a clean boot to a login prompt with **zero** `zeta-creds-restore` lines, and the only thing the contract could report was `fw_cfg staging marker missing` — which reads as a fw_cfg bug and is not one. A skipped check and a broken check produced the same message.

`restoreServiceNeverRan()` separates them and names all four preconditions in the failure text. It cannot say *which* path was missing — only the guest knows — but "the unit never ran, here are the four paths to check" is a lead; "a marker is missing" is not.

**#15222's fix is present and working as far as the serial can show it:** phase-1 emits `zeta-creds-persist: wrote 132 bytes to /tmp/zeta-creds.enc` and the `uefiKeyfile -> /tmp/zeta-creds.factor` sidecar, and the `WARN: picker blob written but factor sidecar missing` branch did not fire. What remains unproven is whether `sudo install` lands them on the ESP and whether `/home/zeta/.local/share/mise/shims/bun` exists on the installed system — `mise` is installed as a Nix store path in that log, which makes the shim the leading suspect.

## 3. A marker that could not fail

`INSTALLED_OS_RETENTION_SERIAL_MARKERS` (scenario 3's retention proof) held both `"zeta-creds-restore: reading preserved ESP blob"` and the strict prefix `"zeta-creds-restore:"`. The set is consumed with all-must-appear semantics, so the prefix matched whenever the real marker did — a marker count with zero discrimination. Deleted, and a substring falsifier now refuses a replacement across all three all-required marker sets.
