## The defect

`.github/workflows/` carried **25 multi-secret `||` chains across 12 files** at the branch point,
plus **one more that landed on `main` during the work** — **26 total**:

| shape | sites |
|---|---|
| `${{ secrets.ZETA_TELEMETRY_FLUSH_TOKEN \|\| secrets.ZETA_PR_ARCHIVE_TOKEN \|\| secrets.GITHUB_TOKEN }}` | 15 |
| `${{ secrets.ZETA_TELEMETRY_FLUSH_TOKEN \|\| secrets.GITHUB_TOKEN }}` | 10 |
| `${{ secrets.RULESET_READER_TOKEN \|\| secrets.GITHUB_TOKEN }}` (`github-settings-drift.yml`) | 1, arrived mid-PR |

`docs/security/2026-08-17-society-heartbeat-token-boundary-and-gate-start-failure.md` is the
authoritative role table and it names **three distinct roles with a secret each** — dispatch,
branch-push, PR-create. `||` selects on the left operand being falsy, and for a secret that means
**empty**, so an absent scoped credential is silently replaced by one carrying **different
authority**. The step runs; the lane fails somewhere downstream under an error naming the wrong
subject.

The `secrets.GITHUB_TOKEN` rung is the worst. GitHub's recursion guard means actions taken with it
do not trigger other workflows, so a degraded lane **also stops producing the events downstream
jobs wait on** — while still reporting success.

## What kept a deliberate probe+warn, and why

Three sites in `agent-heartbeat.yml` implement an **explicit, logged** degradation — probe the scope
the work actually uses, then `::warning` with the missing scope named. That distinguishes **denied**
from **absent** and says so out loud, which is the opposite of the defect. Preserved:

- **`686` merge duty** — degrades on `enablePullRequestAutoMerge` refusal; arming is an
  optimisation and a credential fault must not stall the merge queue.
- **`1567` flush** — `commits?per_page=1` Contents-scope probe, 401/403/404 only, 5xx left alone.
- **`1867` arming** — same shape for a single flush PR.

Two consequential edits inside them:

1. The `[ "$GH_TOKEN" = "$FALLBACK_GH_TOKEN" ]` absence test **only ever worked because a chain had
   already collapsed the absent case onto `GITHUB_TOKEN` out of sight in the expression**. With one
   role and one secret, absent is the empty string — so it is now an explicit `-z` test that names
   which secret is missing.
2. `1567` gains an absence check *ahead of* the probe: with an empty `GH_TOKEN`, `gh` fails before
   the network with no HTTP status, and the probe would classify a **missing secret** as
   "inconclusive" — a true sentence about the wrong subject.

**One `FALLBACK_GH_TOKEN` removed**, on the read-only step. With `GH_TOKEN` already the Actions
token, "fall back to the Actions token" is a swap of a value for itself under a warning that reads
as if it could repair something. That is the vacuity class, so the probe now *reports* denial.

## Known operational risk — stated, not hidden

`ZETA_PR_ARCHIVE_TOKEN`'s live grant is **unproven**, because the chain always resolved to
`ZETA_TELEMETRY_FLUSH_TOKEN` first and no lane ever reached it. That unprovenness is a **consequence
of the defect** — the fallback masked whether the scoped credential works at all. Both secrets exist
(`gh secret list`).

The measured 403 above shows `ZETA_TELEMETRY_FLUSH_TOKEN` **lacks** `Pull requests: write` today, so
PR-create is failing *already*, under a credential whose name says branch-push. After this PR it
fails under the credential whose name says PR-create, with a message naming the grant to make. The
telemetry parks safely on the staging branch either way (`flush-via-staging.ts` loses nothing by
design).

Needed grant, stated in every failure message: `Pull requests: read and write` +
`Contents: read and write` + `Metadata: read` on `Lucent-Financial-Group/Zeta`. The alternative —
keeping the chain so the risk stays invisible — is what this PR exists to remove.
