## Description

## Two front ends, one plan

Per the maintainer's brief — *"we do want to try to use computational expressions if possible and also linq for running our sql queries both"* — and his resolution of the design tension: *"in our perfect world you can write almost the exact same SQL for both … in our system they are kind of just the same thing since we have the materialized table views."*

**Status: `toy`** per `.claude/rules/toy-is-free-metered-must-be-earned.md`, with a mutation-verified falsifier. Every public name is `Toy*` or documented EXPERIMENTAL.

Design doc: `docs/research/2026-08-25-query-surfaces-computational-expression-and-linq-over-one-plan.md`

---

### The circuit CE he remembered — it exists, and there was a second one

`Dsl.circuit { }` (`src/Core/Dsl.fs`) is a **reader monad over `Circuit`**, DBSP-shaped (`map/filter/join/integrate/differentiate/delay`), with **no `[<CustomOperation>]` at all**. His memory was right.

The finding that shaped this work: **`src/Core/ZetaSqlBuilder.fs` already has a SQL-shaped `zeta { }` CE with `where`/`select`/`join` — and it never builds a `Circuit`.** It evaluates eagerly over a materialized `ZSet` via `Seq.filter`/`Map.ofSeq`. So the repo had two query surfaces sharing nothing — not a plan, not an operator. This PR adds **the shared plan that was missing underneath both**, not a second surface to a working one.

### The tension, resolved as one surface

`Q^Δ = D ∘ Q ∘ I` (Budiu et al.) says incrementalization is **a lowering pass over a plan**, not a different language. So the plan is identical in both modes and the mode changes lowering at **exactly one place** — the bilinear `Join` (`Circuit.Join` vs `Circuit.IncrementalJoin`). `Where`/`Select` are linear, so `Q^Δ = Q`.

### The falsifier (the real deliverable)

19 tests, all reading **one shared golden file** (`tests/_golden/query-surface-plans.json`) — neither surface holds a private copy of the expected plan.

1. **Plan equivalence** — CE, `IQueryable`, and `IQbservable` canonicalize to the same text; pull/push also compared by structural equality.
2. **Mode equivalence** — `batch(R) == Σ_t streaming(ΔR_t)`, deltas interleaved, **including a retraction**.
3. **Negative control** — stream⋈table is **not** retroactive and **diverges** from batch when the table arrives late.

Plus non-vacuity controls: a drifted predicate must *not* match; both sides of the law must be non-empty; an unsupported operator is **refused**, not dropped.

**Mutation check** — swapping the streaming `IncrementalJoin` for the batch `Join` (one line, still compiles clean) → **`Failed: 3, Passed: 6`**. The plan-equivalence tests correctly survive; they test a different claim. The falsifier is real.

### Both corners of Meijer's duality square

|  | pull | push |
|---|---|---|
| in-memory | `IEnumerable<T>` | `IObservable<T>` |
| expression tree | `IQueryable<T>` | **`IQbservable<T>`** |

**One translator reads both** — it matches on method **name and arity, never declaring type**, so `Queryable.Where` and `QbservableOperators.Where` collapse onto one code path. That is the duality made mechanical rather than asserted.

## Verified, not assumed

The stream/table duality claim **checks out**: `IntegrateZSet`/`DifferentiateZSet` (`src/Core/Primitive.fs`) are mutually inverse and both `IsLinear`, and are already used this way in production (`GeneratorIrRegistry.fs` — *"the materialised relation … This is DBSP's `∫`"*). One correction: the duality is named **twice**, in two unconnected models — `TableStream.fs` is a list-fold over `DynamicValue`, not the circuit.

**Bonsai was not reinvented.** It exists across five oracles. Recommendation in §6.2: **replace `ToyScalar` with `Bonsai.Expr`** — Bonsai is scalar-only, so the relational layer is the genuinely new part.

Also found: `src/Core/Rx.fs`'s header advertises *"a minimal `IQbservable<'T>` skeleton"* that **does not exist** in that file. This PR supplies one.

## Deliberately left out

No SQL parser. No planner/optimizer. No aggregation, `ORDER BY`, outer joins, sub-queries, or `NULL` semantics. No CQL windows (`AsTable` is the only stream→relation direction). No lambda-based CE (`Quote()` route documented, not taken). Bonsai integration recommended but not done.
