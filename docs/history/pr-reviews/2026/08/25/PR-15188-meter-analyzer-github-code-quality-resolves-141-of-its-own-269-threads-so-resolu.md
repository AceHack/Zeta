## Description

The maintainer's disposition on the `github-code-quality` analyzer (2026-08-24):
*"if it's helping maybe we should keep track of the metrics and then decided what to
do."* Measure first, adjudicate second. This ships the instrument, and takes no
position on keeping or disabling the analyzer.

WHY THIS IS URGENT RIGHT NOW
`required_conversation_resolution: true` is set on `main`, so an unresolved review
thread blocks a merge indefinitely, and this analyzer posts its findings as review
threads. That makes its precision a merge-throughput property, not a style opinion.

THE CENSUS IS COMPLETE, NOT A SAMPLE
269 analyzer review threads over 111 PRs, 2026-04-29T00:21:09Z -> 2026-08-24T19:26:19Z.
Enumerated by paginating `GET /repos/.../pulls/comments` to EXHAUSTION — the endpoint
ran out at page 270 of 100 (26,975 review comments repo-wide), and pages 233-270
contained zero analyzer comments. Each hosting PR was then re-queried through GraphQL
`reviewThreads`; that independent pass returned 269 threads, matching the REST count
exactly. Known gaps are recorded in the ledger rather than papered over: comments on
deleted PRs, check-run annotations (out of scope — this covers review threads only),
and outright-deleted comments are all uncountable from the API.

THE TRAP THIS EXISTS TO AVOID
The free metric is thread resolution, and it is worthless. 141 of the 269 threads were
resolved by `github-code-quality[bot]` ITSELF — and that set is exactly the 141 marked
`isOutdated`. The analyzer closes its own thread when the flagged code moves. A
resolution-derived metric would have reported 86% resolved and called it success.
So the enforced invariant is: resolution is RECORDED but is never an input to the
split. A disposition is written by a named adjudicator with an evidence pointer, or
the entry stays `unadjudicated`.

THE MEASURED SPLIT, AND WHAT IT CANNOT SUPPORT
2 true-positive / 15 false-positive of 17 adjudicated. That number is NOT the
analyzer's false-positive rate and the tool refuses to present it as one: every
adjudication came from a single sampling frame (`blocked-a-merge` — only threads that
were blocking merges got looked at), so it estimates that frame, not the population.
The report prints the caveat automatically while the draw stays single-frame, and a
test pins that behaviour against the SHIPPED numbers.

A DISCREPANCY LEFT OPEN RATHER THAN CLOSED
The session was described as 18 findings (16 false / 2 real). Its own itemisation names
4 + 10 + 1 false and 2 real = 17, and the API finds exactly 17 analyzer threads across
those five files. 17 is seeded. The 18th is not reproducible and was not invented to
make the arithmetic close; the ledger's `note` records the disagreement.

IT IS A METER, NOT A GATE
Exit 0 on any report, 2 only on a config error. There is no argv and no ledger content
that makes it exit 1 — a test asserts that a 100%-false-positive ledger still exits 0.
The policy has not been decided, so nothing here enforces one.

MUTATION-CHECKED
30 targeted mutations, 30 killed, 0 survivors. Two SURVIVED the first pass and were
genuinely vacuous, and both are fixed with the reason written at the test:
  - the sort test used two entries, where insertion order reversed is also sorted, so
    it could not tell sorting from reversing (now three);
  - the no-evidence refusal test left the evidence pointer null too, so a loose
    `includes("no evidence")` matched the OTHER rule's "…no evidence pointer…" message
    and passed with the refusal deleted (now one fixture trips exactly one rule).
