## Description

## The gap

`full-ai-cluster/INJECTION-POINTS.md` opens with a rail it calls **constitutional**:

> public identifier → USB ESP at flash time is allowed
> secret material → cluster console at install time ONLY, never on the ESP

Until this PR that rail existed **only as that paragraph**. `FileBackedEspWrite` in `zflash/lib.ts`
carried a closed union of six ESP destinations and no notion of what class any of them held, so
nothing in the build could tell `/zeta-hostname.txt` (a hostname) from `/zeta-join-token` (cluster
membership, in the clear, on FAT). The rail was enforced by whoever happened to read the markdown.

## What landed

`src/Core.TypeScript/zflash/injection-rail.ts` makes the content class a **type**, exhaustive over
that same union via `satisfies Record<EspDestination, InjectionContentClass>` — the #11485 shape
(illegal state unrepresentable) applied to the #11477 gap. A seventh ESP destination without a
declared class is now a TypeScript error, not a review miss. `runFileBackedZflash` calls
`railFindingsForEspWrites` and discloses every secret-class write at flash time, because a policy
nothing calls is the vacuity class.

Three classes, not the catalog's two: the table cannot express why `/zeta-creds.enc` is permitted
while being called secret material. It is permitted because it is an **encrypted envelope** whose
key is not on the medium. **The class is DECLARED, never measured** — nothing here opens the file.

| ESP destination | Class | Verdict |
|---|---|---|
| `/zeta-authorized-keys.pub`, `/zeta-hostname.txt`, `/zeta-firstboot.conf` | public identifier | permitted by class |
| `/zeta-creds.enc` | encrypted envelope | permitted (declared, not measured) |
| `/zeta-join-token` | **secret material** | refused by class; ships under the §6 recorded exception |
| `/zeta-wifi-credentials.json` | **secret material** | **REFUSED — no exception on file** |

## Found while doing it — a divergence, not an exception

Recorded rather than quietly fixed, on #11477's precedent.

`INJECTION-POINTS.md` §4 classifies WiFi credentials as *"**Secret material** (NEVER on USB ESP)"*
and says they are typed at the console into `nmtui`. **The shipping code does otherwise.**
`planFileBackedZflashImage` writes `/zeta-wifi-credentials.json` — the SSID and the PSK as plain
JSON — onto the ESP whenever `--wifi-ssid`/`--wifi-password`/`--wifi-credentials` is passed;
`composeWifiCredentialsFileContent` validates and serialises and performs **no encryption**. Three
existing tests in `file-backed.test.ts` assert that plaintext write as expected behaviour, so the
path is live, not vestigial.

That is categorically different from §6: **§6 was decided and written down; this was not noticed.**
It is left **UNRESOLVED** on purpose — removing a shipped operator flag is a maintainer call, and
the correct destination (§7's encrypted blob, or console-only per §4) is the same open question §6
already carries. Recorded at §4a and as `RAIL_DIVERGENCES`, and disclosed at every flash that
carries it.

## The workload-identity half — answered from prior art, not built

A SPIFFE workload identity is three artifacts, and only the third is what people mean by "the key":

| Artifact | Class | ESP verdict |
|---|---|---|
| SPIFFE ID (the URI) | public identifier | permitted |
| trust bundle (trust-domain CA **public** keys) | public identifier | permitted |
| SVID **private key** | secret material | **refused** |

The refusal has two independent reasons, either sufficient: the rail, and SPIFFE's own design — the
workload generates its own private key and only a CSR leaves it. **So "keys injected at the door"
resolves to: the key is not injected.** What can travel with the medium is the public half and the
node coordinate — and the node coordinate is already there. The hostname zflash writes to
`/zeta-hostname.txt` is exactly the `@<node>` of the identity treaty's Article 3 form
(`spiffe://zeta/persona/<persona>/cell/<surface>[/<instance>][@<node>]`).

`deriveNodeWorkloadSpiffeId` composes them and validates by round-tripping through `parseSpiffe`.
The round trip is load-bearing, not decorative: `VALID_HOSTNAME_REGEX` accepts uppercase and the
actor-ref segment charset (`/^[a-z0-9][a-z0-9._-]*$/`) does not, so **`--host Node-A` flashes
cleanly today and yields a SPIFFE ID this repo's own parser rejects.** `toSpiffe` concatenates and
checks nothing, so trusting it alone would emit those URIs happily.

## Precision about what is claimed

**Nothing here is sealed, bound, attested, or verified.** No cryptography runs in this module and
no key material passes through it. It classifies destinations and artifact kinds and returns
verdicts. That is also why it does not trip this work-item's review gate (*"Nazar + Mateo review the
surface BEFORE implementation; no key handling lands without it"*) — policy that touches no bytes is
not key handling, and **the gate remains unmet; the work item stays open.**

## Custody decisions this deliberately does NOT make

Carried as `WORKLOAD_IDENTITY_CUSTODY_DECISIONS`, every entry `decided: false`, asserted by test —
so answering one is a visible diff rather than a drift:

1. Where an SVID private key is **sealed at rest** — TPM 2.0, Secure Enclave, software keystore, or
   nothing. (The 2026-08-14 hardware probe found no TPM and no usable seal tier on the Mac Studio;
   the x86 nodes are unprobed.)
2. Whether the node identity is **TPM-bound** — sealing and binding are separate choices.
3. **Who authorizes issuance** at first boot. SPIRE node attestation answers *which node is this*
   from a vendor-rooted claim; nothing here answers *and may it have an identity in this trust domain*.
4. Which **governance class** the key takes (self-sovereign / shared-capability /
   delegated-operational — taxonomy fixed by the 2026-08-14 L0→L6 ladder, per-key assignment
   explicitly left to ratification).

Also named but **not shipped**: the **trust bundle has no ESP destination**. It is a public
identifier so the rail permits it, and without a trust anchor on the medium a booting node has
nothing to verify an issuer against — first contact is TOFU. Adding a destination is key handling,
so it sits behind the gate.
