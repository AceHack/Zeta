## Description

Follow-up to #15369. That PR's auto-merge fired on its first commit while its
own CI was still reporting on it — and what CI reported was **two more defects,
both inside the fix**. This carries them.

## 1. Absent read as EMPTY, inside the remedy for absent reading as empty

`GET /repos/{o}/{r}/rulesets/{id}` **omits** the `bypass_actors` key for a reader
without admin rights. It does not 403, and it does not return `[]`.

Verified unauthenticated against this repo's ruleset 16134995 on 2026-08-25 — the
response carries `[_links, conditions, created_at, enforcement, id, name, node_id,
rules, source, source_type, target, updated_at]` and no `bypass_actors`, while the
same call with an admin credential returns one admin PR-bypass actor.

`normalizeBypassActors` coerced the missing key to `[]`. So under `GITHUB_TOKEN`
the drift check reported the live admin bypass as **REMOVED** — and the cheapest
way to turn that green would have been to record `[]`, erasing the P0 finding
#15369 exists to surface. Absence reading as the safe value: the exact class
#15369 is about, reproduced inside its own remedy, and catchable only by pointing
the detector at live.

`null` now means unreadable and lifts to the `insufficient-token-scope` sentinel;
`[]` keeps its real meaning of "read successfully, nobody bypasses". Both sentinel
walks descend into **arrays** — the one field a non-admin credential silently
cannot read lives inside an array element, so a walk over objects alone reports
zero unreadable fields on exactly the run where the most important one was missed.

**Control** — replaying a real unauthenticated read of all five rulesets:

Live compare under an admin credential: still **exit 0**.

## 2. `rc=$?` was dead code — in the new step and in the sibling job

GitHub's default shell is `bash -e {0}` (it is in every job log's `shell:` line),
and `set -uo pipefail` does **not** clear a `-e` that arrived on the command line.
A bare call followed by `rc=$?` therefore aborts the step the instant the command
is non-zero, and every line after it is unreachable — including the `case` whose
whole purpose is to tell DID-NOT-RUN from FAILED. The reporting existed for the
non-zero case and was the only case it could never see.

Observed: job `97868684543` exited 1 with no annotation emitted.

The same shape was **already in the sibling `ruleset-plan` job**, whose reconciler
has five meaningful exit codes — 1 DRIFT / 2 DID-NOT-RUN / 3 REFUSED / 4 APPLIED-
BUT-VERIFICATION-FAILED — every one silently collapsed into a bare red step since
it was written. Fixed there too.

**Control**, reproduced verbatim:

```
$ bash -e -c 'set -uo pipefail; false; rc=$?; echo "UNREACHABLE: rc=$rc"'
  (no output)                                          exit=1
$ bash -e -c 'set -uo pipefail; rc=0; false || rc=$?; echo "REACHED: rc=$rc"'
  REACHED: rc=1                                        exit=0
```

Both now use `rc=0; cmd || rc=$?`.

## 3. The drift step propagates its exit code

#15369's first draft ended the step with `exit 0`. That was wrong in the direction
this whole line of work is about. `continue-on-error` at the job level already
makes the job advisory, so `exit 0` bought nothing — and it cost the `drift (loud)`
reporter its signal, because that job escalates *absorbed* continue-on-error
failures and a step that always exits 0 has nothing to absorb. The annotations
**add** the 1/2/3 distinction the step status cannot carry; they do not replace it.

## Smaller, same class

- `endpointForPath` strips array indices, so `rulesets[1].bypass_actors` resolves
  to its endpoint instead of `(endpoint unmapped)` — not a corner case, it is where
  the most safety-relevant field lives.
- `countLeaves` scores a populated array by its elements. Scoring it `1` hid the
  case where the `rulesets` array is stripped of everything that mattered and still
  counts as compared. An **empty** array stays `1`, because `"topics": []` is a real
  compared value and scoring it `0` would risk calling a legitimate run
  INDETERMINATE.
