## Description

## The problem

GitHub Actions was a **one-inhabitant port for compute**. Ledger row 4 marks "Tick sources — GitHub Actions" dogfooded while rows 5–7 are `partial`/`not started`, so the fleet's liveness — the externalized idle counter — ran on exactly one substrate.

Worse, **there was no port to implement**: a tick existed only as four inlined YAML steps. Same shape as `work-provider.ts`, which declares a 5-provider DU with total dispatch and zero adapters.

## The load-bearing finding: the watchdog measured the wrong thing

`heartbeat-liveness.ts` asked *"how old is the newest SUCCESSFUL Actions run?"* — the provider's **job status**, not whether a tick happened. So "alive" was **defined** as "GitHub ran a job", and a second source could not have turned it green even in principle.

It was wrong in **both** directions, measured not argued:

**FALSE ALARM — live at 2026-08-25T17:11Z:**
```
[heartbeat-liveness] NO SUCCESSFUL agent-heartbeat IN 102 MINUTES     rc=1
```
…while `heartbeat/alexa` carried `heartbeat(alexa): accumulated tick 2026-08-25T16:49:05Z` — **22 minutes old**. The run went red at a *later* step. Only **36 of 65** runs in 24h concluded `success`, so productive-then-red is the normal case.

**FALSE GREEN — structural:** the tick body runs under `|| echo`, and the commit step succeeds on an empty stage. A run concludes `success` having committed nothing. Reproduced on the new adapter's first run (`navigate_cartography` → `not-yet-executable` → nothing staged). *A check that passes when the thing it checks did not happen is the vacuity class.*

## Not claimed

**Compute is decoupled; transport is not.** The lane still pushes to github.com. `--remote` is a parameter so that stays config, not code.

## Browser/PWA (row 5): blocked on DELIVERY, not auth

- Producing and signing unattended: solvable. **Delivering** is not — the `issues/new` carrier works because the human click carries GitHub's session; **the click IS the credential**.
- The repo already answers this: `browser-delegated-device-proposal-gh-cli.ts` shells to local `gh` *"without moving the token into the browser"*. **So the PWA's delivery leg is this adapter.**
- `ZETA_OPERATOR_HARNESS_ORIGIN` (manus.space) returns **HTTP 500 on all three endpoints, GET and POST**, serving HTML. It **cannot** be repointed at Pages — POST endpoints needing a GitHub App key; Pages 404s. The already-written amortised-click design (`authorizeOperatorDevice` → bounded `DeviceCapability` → `submitAutomaticProposal`) is **inert**.
- Not an option: OAuth device flow — no CORS on `login/device/code`.

X named precisely in §5c of the design doc.
