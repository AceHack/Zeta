## Description

The escape I landed this morning (#15348) frees a lane blocked behind a
CONFLICTED flush PR by closing it so the lane re-cuts. Its premise: "the next
flush re-cuts from the current lane head over current main, which also
resolves the conflict."

Measured hours later, that premise is sometimes false. #15362 was retired as
DIRTY, alexa re-cut as #15366, and **#15366 came back DIRTY too**. So the
escape would retire and re-cut on every tick, indefinitely — I had replaced a
permanent wedge with a permanent churn. The churn is QUIETER than the wedge,
which makes it worse: nothing goes red, and the lane looks alive while making
no progress.

Stranger, and the reason this backs off instead of trying harder:
`git merge-tree --write-tree` reports that head merges into that exact base
CLEANLY (rc=0; same base 7e1e1487f, same head 5a67ec385 GitHub records), while
GitHub reports CONFLICTING on three consecutive reads 18s apart. I could not
reconcile them. An automation that does not understand why something fails
must not keep acting on it — so it now acts ONCE and then hands over.

ONE RETRY, THEN LOUD. A second DIRTY on the same snapshot ref within 2h emits
a `::error` naming the lane instead of retiring again.

THREE DEFECTS IN THE GUARD ITSELF, each caught by testing it against live data
before shipping rather than after:

1. `--state closed` INCLUDES MERGED. Counting all closures made a HEALTHY
   lane that merged two flushes look like two retirements, which would have
   refused to retire a genuinely-stuck blocker — reinstating the wedge. Both
   lanes returned 2 under that version; the correct filter now gives alexa 1
   and soraya 0.
2. A HUMAN closure counted too. I closed #15319 by hand this afternoon, so a
   manual intervention would have silently disabled the automatic one. The
   guard now matches the lane's OWN comment marker, which counts exactly the
   event whose repetition means "re-cutting is not working".
3. THE GUARD WAS VACUOUS. Interpolating the marker through `gh --jq` needs
   escaping across two quoting layers; it got it wrong, the expression
   errored, `2>/dev/null` swallowed it, the result was EMPTY, and
   `${PRIOR_RETIRED:-0}` turned empty into 0 — permitting every retirement.
   A guard that always says yes. Now `jq --arg` passes the marker as data so
   there is nothing to escape.

And the trap I cited all day and then walked into: this block runs under
`set -e` WITHOUT `pipefail`, so `$?` after `gh ... | jq ...` is JQ's
status — `gh` could fail outright and the guard would read success. Fetch
and parse are now separate statements with separately-checked outcomes, and
both fail CLOSED (refuse to retire) rather than open.

Verified live before commit: alexa = 1 lane-marked retirement in 2h (so the
next tick escalates rather than looping), soraya = 0 (so a healthy lane keeps
its escape). shellcheck clean, 0 warnings.
