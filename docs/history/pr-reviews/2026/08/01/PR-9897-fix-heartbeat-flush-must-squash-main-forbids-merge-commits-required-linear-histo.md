## Description

The flush I shipped in #9890 **cannot work**. `main` carries the ruleset **Branch Safety** (id 16189060, ACTIVE) targeting `~DEFAULT_BRANCH` with `required_linear_history`, so the `--no-ff` merge commit is rejected outright:

```
! [remote rejected] HEAD -> main (push declined due to repository rule violations)
```

It would have failed on its very first hourly run.

## Why it passed review — the process failed, not the logic

I verified #9890 in a scratch git repo with four cases (quiet main, moved main, idempotent re-flush, rejected-push replay). **All four passed. The scratch repo had no rulesets.** I tested an environment that differed from production in the single way that decided the outcome, and reported it as verified.

I also told Aaron *"this is NOT branch protection — main requires nothing"*, based on the classic branch-protection API:

```
required_status_checks: false / required_pull_request_reviews: false / restrictions: false
```

That was **true and incomplete**. Rulesets are a *separate mechanism* and do not appear in that API. Both must be checked:

```bash
gh api repos/<owner>/<repo>/rules/branches/main
```

## The fix

Squash instead of merge. The payload is append-only ZetaId event files (G-Set), so per-tick commit boundaries carry no information the events do not. One linear commit per flush satisfies the rule and reads better in `git log`.

Idempotency is now explicit: if the squash stages nothing, the flush is a **no-op** rather than an empty commit or an error.
