## 1. Nine stale `.js` deleted — verified stale, verified unreferenced

Of **63** `.js` files shadowing a `.ts`, **9** had a `.ts` newer than the `.js`. Worst case `zflash/lib.js`:

| | last touched | exports |
|---|---|---|
| `lib.ts` | 2026-07-08 (*wifi credential ESP injection*) | **34** |
| `lib.js` | 2026-06-21 | **15** |

`composeWifiCredentialsFileContent` missing entirely. Confirmed empirically that `import "./lib.js"` **resolves to the stale file** — 15 exports, TS-only function `undefined`. Every zflash `.ts` imports `"./lib.ts"` explicitly so the live path was fine, but the trap was one import away with no warning.

*Corrected mid-investigation:* an initial "13 references" was a **basename collision** with `cluster/dev-cluster/lib.js`. Re-measured against the real path: **0 external references.**

**Test count 479 → 472 is a fix, not a loss.** Three deleted files were `.test.js`; all three have `.test.ts` equivalents that exist and pass (43 tests). The suite had been running **stale duplicate tests** — part of that 479 was exercising June code.

## 2. `zflash-qemu-test.yml` → `zflash-harness-lint.yml`

**It never invoked qemu.** No `qemu-system`, no `qemu-img`, no qemu install anywhere; the single job is `zflash-qemu-harness-dry-run` running `bun test`. Three green runs meant *"harness invariants hold"*, not *"a boot was validated"* — and it's the workflow you'd check when asking whether flashing is tested.

**The real boot coverage exists and is green:** `build-ai-cluster-iso.yml` installs `qemu-system-x86` + `ovmf`, boots the image, captures serial logs. 3 successes today. So coverage was better than the naming suggested, in both directions.
