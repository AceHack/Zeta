## Description

Design only, decides nothing. Built **over the four repo-split workitems that already exist** rather than inventing a new plan.

## The headline, stated first because it changes sequencing

**The cache quota is the wrong reason to split.** Self-hosted runners solve it *completely and without a split* — persistent volumes, no ceiling, models on a PVC pulled once instead of ~16GB/tick, **and** they fix the 11%-of-declared cadence that no workflow tuning can touch. If runners land, the cache motivation evaporates.

It also contradicts your own position from earlier today: *"I like trunk based to the extreme and monorepo — **if** you take the time to build the tools and the caching."* Splitting to dodge a quota is precisely not taking that time.

**But the destination is independently right**, and was designed months ago on axes unrelated to CI. So: split for the reasons that were already true, on the schedule those reasons justify.

Plus two recorded drivers a fresh design would miss: **fork-ability** (segregate owner-only substrate — a hard constraint, since a repo with untouchable files isn't forkable) and the **ruleset-divergence smell test** (different rulesets ⇒ different repos — observable, not aesthetic).

## Dependency direction, carved now

```
products / personas ──▶ ace ──▶ zetadb ──▶ (nothing)
```

**`zetadb` must never depend on `ace`** — otherwise installing anything requires something already installed.

## The cost row worth watching

Today's four main-reds were caught because **one** actionlint and **one** mutation runner cover everything. After a split, every repo needs its own guardrails, and **a repo that misses one is invisible.** The guardrail set has to be in `ace`'s day-one scaffolding, never hand-copied.

## Where the existing work disagrees with itself

Axis 3 says Mirror/Beacon is a **repo** split. DV2.0 change-rate analysis suggests it may be a **branch** discipline. That needs resolving before cutting.
