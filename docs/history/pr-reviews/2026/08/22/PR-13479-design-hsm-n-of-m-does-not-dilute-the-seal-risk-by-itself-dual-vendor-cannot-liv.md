## Description

Three inputs from Aaron, three findings — two of which correct the comfortable reading.

## 1. n-of-m does not dilute the risk by itself, and the wrong version does not degrade — it fails to start

> *"in the start with one machine this is scary, when we have n-of-m no so scary anymore"*

Right about the outcome, wrong about the mechanism. **Measured** in OpenBao `v2.6.2`: there is **one** seal-wrapped root key at `StoredBarrierKeysPath = "core/hsm/barrier-unseal-keys"`, read through `core.physical` (raft-replicated, identical bytes on every member) and decrypted by **this node's** seal.

So three nodes with three independently-provisioned TPM keys is not a resilient cluster — it is one where **two members never unseal**. The topology Aaron describes is reachable only via **one key imported into every TPM**, which makes **C1 (custody) a precondition of C5 (topology)**, not an independent preference.

**The counter-case, since it was asked for.** Losing one board *does* still lose a multi-node cluster under **correlated erasure**: `zeta-install.sh` re-paves every fixed disk by default and the `tpm2-pkcs11` token store is per-node state on that disk, so a fleet re-pave clears N TPMs together. **Node count diversifies independent failures and does nothing against a common-mode one** — the same lesson §4 reaches from the vendor side.

## 2. The TPM premise: Aaron knows, and the installer did not

> *"i know all my linux machines have TPMs they were windows 11 certified hardware"*

Sound — Microsoft's requirements page says it verbatim: *"**TPM**: Trusted Platform Module (TPM) version 2.0."* It resolves what a **human** needs to know and not what an **unattended node** can see, and the node is the thing that has to decide. `node.yaml` recorded cpu/cores/memory/gpu/kernel/network and **nothing about a TPM**.

Closed in code, in the five-state vocabulary that already exists rather than a boolean, with a parity test that extracts the bash out of the real script and runs it against **every committed capture** beside `classifyTpm2Linux`.

**A mutant survived that suite** — an unrecognised `tpm_version_major` defaulting to `2.0` passed every fixture, because no capture held a value that was neither `"1"` nor `"2"`. A hand-constructed capture now covers it and **kills the mutant on both implementations** (verified by mutating each).

**The four existing `node.yaml` files are deliberately NOT backfilled.** They are *probe* records; writing `present` from a certification argument would manufacture the exact fake measurement this thread exists to prevent. The field appears when each node next re-registers — level-triggered, ≤6h, nobody visits a box.

## 3. Dual-vendor cannot live at the seal

> *"save a design where we have two hsm's from different vedors per node"*

**Measured:** OpenBao permits at most two `seal` blocks and requires **exactly one to be disabled** (*"seals: two seals provided but neither is disabled"*). That is the **migration** shape, not seal-HA — and upstream carries the literal comment `TODO(SEALHA)`. So **1-of-2 unseal is not configurable**, and the doc says where dual-vendor *can* live instead: the escrow, function separation, ceremony-device separation.

The tradeoff is stated rather than picked: **1-of-2 raises availability and LOWERS security to the weaker vendor** — the direction people reach for when they say two HSMs feel safer.

Anchored on the **refutation**, not the proposal: N-version programming (Avizienis & Chen 1977) with **Knight & Leveson 1986**, and the in-domain instance is measured — **YSA-2024-03 hit YubiKey 5 AND YubiHSM 2 simultaneously because the flaw was in Infineon's cryptographic library**, below the boundary anyone versioned. Confirmed independently: **Nitrokey HSM 2 is CardContact's SmartCard-HSM** driven by the same OpenSC `sc-hsm` driver — monoculture twice over, silicon *and* host module.

## 4. "Most HSMs just have exportable or not" — the binary is false

The third state is the SmartCard-HSM's **DKEK**: a 256-bit AES key **generated by the device's own RNG**, exported only as PBE-encrypted shares, with only a **key check value** disclosed.

**On Aaron's own criterion the two vendors are not equivalent.** Yubico's documented backup flow generates the wrap key with `get-pseudo-random` into a file *its own docs call cleartext and sensitive*, then imports it into both devices. **The $79.26 device wins on the exact axis he named** — structurally, not by care: two devices must share one symmetric key, and only one vendor ships a share protocol for that.

**The central claim is stated so it can be attacked, then attacked.** No key material is ever plaintext outside a secure element — and **two non-key secrets do cross the host**: the **DKEK share password** and the **User PIN**. Eleven surfaces enumerated, including argv, `env:VAR`, printed `(t,n)` share strings, swap, core dumps, history, and **a KVM ceremony putting the password on a network** (this fleet has Comet KVMs, so that is the likely mistake, not a theoretical one).

**So "no side-channel key leaks" is true of the HOST and unproven of the DEVICE.** Kocher 1996 and Kocher/Jaffe/Jun 1999 are cited to say exactly which class is *not* addressed; the CC level stays logged as unchecked.

**The reframe, offered for rejection rather than assumed: a weekly RESTORE DRILL, not a weekly backup.** Re-copying an unchanged key weekly adds copies, not assurance; what decays is confidence the restore works, and the drill **never touches the production token**. And `sc-hsm-tool --initialize` — *"removing all existing keys, certificates and files"* — makes this a **one-way door**: a DKEK cannot be added to a token that already holds the key. **Second one-way door in this thread**, both open today.
