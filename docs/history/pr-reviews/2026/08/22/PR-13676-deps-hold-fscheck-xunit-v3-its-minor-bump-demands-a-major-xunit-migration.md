## Description

deps: hold FsCheck.Xunit.v3 — its minor bump demands a major xunit migration

PR #13653 is red on every platform with NU1608 under Warning-As-Error. The cause
is not FsCheck: it is that FsCheck.Xunit.v3's own version number understates what
it requires.

Measured from the published nuspecs rather than inferred:

  FsCheck.Xunit.v3 3.3.4 (held)  ->  xunit.v3.extensibility.core  3.0.1
  FsCheck.Xunit.v3 3.4.0         ->  xunit.v3.extensibility.core  [4.0.0, 5.0.0)

We pin xunit.v3 at 3.2.2. So a MINOR bump of FsCheck.Xunit.v3 demands a MAJOR
migration of xunit v3 to v4. Dependabot grades the update minor because its own
version is minor; the transitive requirement is not, and there is no signal in
the version number that would tell it otherwise.

This is the second instance of one class in one morning. The first was
Microsoft.CodeAnalysis at 5.9.0 against an SDK Roslyn of 5.6.0 (#13590, ignore
landed in #13634). Both are packages COUPLED to something the tree pins
elsewhere, where the coupling is invisible to semver. Both took eight or nine
unrelated and perfectly good bumps down with them, because the group lands as one
PR -- and both would recur weekly.

Adopting xunit v4 is a test-framework migration across every test project, with
its own API surface to work through. It is not a dependency chore and it is not
mine to start on a Friday morning.

LIFTS WHEN: xunit.v3 is deliberately moved to the 4.x line. That bump and this
one belong in the same change so the constraint can never be half satisfied --
which is precisely what a bot on a weekly schedule cannot know.
