## Description

Full-cluster helm validation across all 54 Applications at both resource rungs,
offline and deterministic, plus the 2x2 closed. The headline is a measurement,
not a mechanism: **applying `dev` to the committed tree is necessary and NOT
sufficient — the dev lane is 2906m against a 2500m budget.**

## 1. The 2x2 was two meaningful cells and two that were not

MEASURED 2026-08-22, exit codes read directly, never through a pipe:

  --resource-profile metal --check   0     the tree carries `metal`
  --resource-profile dev   --check   1     54 drifts, because it does not
  --resource-profile metal --budget  1     metal vs a 4-vCPU CI runner
  --resource-profile dev   --budget  0     <- what CI ran

Two separate defects hide in that table, and neither is fixed by a softer check.

THE `--check` PAIR IS MUTUALLY EXCLUSIVE BY CONSTRUCTION. One committed tree,
one value per coordinate, so at most one rung is applied. Both cells green is
not a goal, it is impossible. `dev --check` exiting 1 with 54 drifts was never
a defect — what was missing is a declaration of which rung is supposed to be
there. `activeResourceProfile` is that declaration, and it makes the interesting
failure invert: a NON-active rung that reports "applied" means two rungs agree
at every coordinate, i.e. the ladder cuts nothing and is one rung with two names.

`metal --budget` WAS A CATEGORY ERROR — a 16-core deployment compared against a
runner it never touches, so its exit 1 carried no information. Meanwhile nothing
compared metal against the machines it does run on, while `capacity-provenance`
compared the STORAGE ladder against those same registrations. A rung is budgeted
against a SUBSTRATE now, and each substrate names the falsifier that reads a real
machine: `dev-lane` by `--measure-runner` (/proc on the runner), `metal` by
`--measure-nodes` against the four checked-in ClusterNode registrations.

Units read off the capture, not assumed: `cores` is `nproc` (logical CPUs, which
is what a millicore is 1/1000 of) and `memory` is `free -h --si`, so `66G` is
62942Mi and not 67584Mi. Reading it as binary would have granted 4642Mi per node
that no node has.

## 2. Every chart, both rungs — and what it found

`rendered-resource-requests.ts` renders all 54 Applications at each rung by
overlaying that rung's numbers into each Application's own valuesObject and
templating the chart at its pinned targetRevision. 54 discovered, 54 rendered,
0 unrenderable. A re-measurement is byte-identical (`cmp` exit 0).

Both rungs is not decorative: it makes inertness OBSERVABLE. A row whose two
rungs differ MUST move the render; one that does not is a key the chart never
reads. That is the CPU/memory form of the defect `inert-valuesobject-keys` found
four times in a day, and it is why the check needs both renders rather than one.

THREE FINDINGS, each confirmed by hand before it was written down:

  gmod       `game-hosting/gmod` renders 1000m / 2048Mi and had NO row. The
             catalogue asserted in writing that it "contributes 0m / 0Mi today
             (in-repo manifests, no requests)". Its statefulset.yaml line 70
             reads `requests: { cpu: "1", memory: "2Gi" }`. The false sentence
             stood immediately beside the honest limit that made it
             unfalsifiable: `applicationDirs()` enumerated depth 1, and ArgoCD's
             include glob is not path-segment bounded — which THIS REPO had
             already established against a live cluster in
             `app-of-apps-discovery.ts`.
  cilium     declared 0m with the evidence "chart default resources are unset".
             True of the regular containers, and the row was still wrong:
             DaemonSet/cilium has an init container requesting 100m / 10Mi, and
             the scheduler reserves max(sum(regular), max(init)).
  gitlab     hand-summed 2475m, renders 2525m. The memory column was already
             exact to the mebibyte, which identifies the cause:
             `gitlab-gitlab-shell` requests 0m across its regular containers and
             50m in each of two init containers — and every init container in
             that chart requests 0 memory.

The two independent oracles now agree to the millicore: the catalogue's own
arithmetic and a full render both report 2906m / 8255Mi for the dev lane at `dev`.

## 3. The result, and it is a result rather than a fix

  dev lane at `metal` (what ships)  5231m / 13475Mi   over by 2731m
  dev lane at `dev`                 2906m /  8255Mi   over by  406m
  budget                            2500m /  9216Mi   memory fits, CPU does not
  metal, whole tree, on metal       9256m / 21810Mi   fits 57000m comfortably

So the decision that was being deferred is bigger than it looked: applying `dev`
to the committed tree takes the lane from 5231m to 2906m and STILL leaves it
406m over, because gmod is a git-path source with no valuesObject and no rung can
reach it. The 406m has two shapes, both cheap, and BOTH ARE PRICED AND NEITHER IS
CHOSEN — that call is the maintainer's:

  * shrink gmod's literal request in its statefulset.yaml (500m -> lane 2406m), or
  * add `game-hosting/**` to the dev root's excludeGlob (lane 1906m, 594m spare).

gmod does not schedule TODAY only because its sync fails on gatekeeper's webhook.
That is a reprieve of exactly the shape `storage-profiles.json` predicted in
writing about the longhorn StorageClass — the one `hindsight-postgresql-0`
eventually cashed as `Insufficient cpu`.

Nothing here was made green by narrowing. The `dev` shortfall is carried as DEBT,
pinned to its arithmetic (`dev@dev-lane cpu 2906>2500`) so one millicore of
movement retires it, with a reason and a `LIFTS WHEN` whose condition IS the gate
rather than a paraphrase of it. The seven `infra/k8s/applications` Applications
that no rung can name (4035m, a second App-of-Apps root) are baselined the same
way, per app per rung, with the schema change that would close them named.
