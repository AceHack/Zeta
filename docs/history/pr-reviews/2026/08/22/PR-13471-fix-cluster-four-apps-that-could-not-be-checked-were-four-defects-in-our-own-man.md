## Description

## The claim

PR #13429 recorded **five UNRENDERABLE Applications** — 106 GiB of declared
storage the render checker could not look at. Four are handled here (temporal is
another agent's). **Not one was a limitation of `helm template`.** Every one was
a defect in our own manifest that would have failed inside ArgoCD in the same
place, on the same line.

| app | what was actually wrong | fix |
|---|---|---|
| `headscale@0.4.0` | declared volume mounted where nothing writes; DB + both private keys on ephemeral disk | `persistence.data` → `persistence.config` + `accessMode` |
| `oz@1.4.5` | pin never published — and it was **masking** a missing required value and an inert values block | pin → `3.1.1`, add `clientApi.advertisedHost`, fix `adminSecret` |
| `gitlab@8.7.0` | one value its own sibling in `infra/` already carries | `global.ingress.configureCertmanager: false` |
| `arc-runner-set@0.12.1` | looked structural (`lookup`); the chart ships an escape hatch it recommends itself | `controllerServiceAccount.{name,namespace}` |

Result: **`53 discovered, 53 rendered, 0 UNRENDERABLE`** and **0 GiB unchecked**.
temporal — the fifth, and not this branch's — landed separately in #13469 while this
was open, so the acknowledgement list is empty for the first time. An empty list here
means 53 of 53 were rendered and compared, not that nothing was checked; the test
asserts it against the render for exactly that reason.

## headscale — worse than reported

`persistence.data` reached the bjw-s common library, which does
`required "accessMode is required for PVC headscale-data"`. Adding `accessMode`
makes it render — **and renders a 3 GiB longhorn volume at `/data` that nothing
writes to.** The chart hard-codes `HEADSCALE_DB_PATH=/etc/headscale/db.sqlite`,
`HEADSCALE_PRIVATE_KEY_PATH` and `HEADSCALE_NOISE_PRIVATE_KEY_PATH` into
`/etc/headscale` — the `config` persistence item, disabled by default, i.e. the
container's ephemeral layer. Every restart mints new keys and drops every
enrolled node off the tailnet.

So the key is **renamed**, not patched: the fix that renders and the fix that
persists are the same fix. It also repairs the init container, whose config.yaml
mount is guarded by `persistence.config.enabled` and was rendering
`volumeMounts: null` — writing `/etc/headscale/config.yaml` into its own layer
where the main container never saw it.

## oz — the pin, and the two defects behind it

`ziti-controller` 1.4.5 has never existed (96 versions published; the 1.x line
ends at 1.3.4). **The breaking-change surface, measured rather than assumed** —
1.3.4 / 2.1.2 / 3.1.1 / 3.2.1 pulled and templated against this Application's own
`valuesObject`:

| chart | appVersion | renders with our values | PVC |
|---|---|---|---|
| 1.3.4 | 1.5.4 | yes | `ziti-controller` 3Gi longhorn |
| 2.1.2 | 1.7.2 | yes | identical |
| **3.1.1** | **1.7.2** | **yes** | identical |
| 3.2.1 | **2.0.1** | no — `cluster.mode` required | identical once set |

Every key this manifest sets survives all three majors, so the earlier
acknowledgement's reason — *"not drop-in for the pinned values in this manifest"*
— was a plausible claim **nobody had checked**, and it is false. **3.1.1** is the
newest chart still on appVersion 1.7.2: the furthest forward the pin moves
*without* changing which OpenZiti server runs. 3.2.1 is a server major plus a new
required key — two operator decisions, not a storage change's to make.

**What the bad pin was hiding.** It failed at `helm pull`, so nothing ever
reached `helm template`:

1. **`clientApi.advertisedHost` was never set**, and every published version
   refuses without it. Correcting the pin *alone* would have moved the failure
   from `pull` to `template` and lifted nothing.
2. **`adminSecret: {name, key}` is inert** — not a key ziti-controller has ever
   had. The chart reads `useCustomAdminSecret` + `customAdminSecretName`, and the
   secret's keys are fixed as `admin-user`/`admin-password`, not `password`. The
   controller would have run on a chart-generated random credential while the
   manifest claimed otherwise. Same class as hindsight and nats. The in-file
   `kubectl create secret` command is corrected with it, because a fix that
   leaves the instructions wrong is half a fix.

## arc-runner-set — the class question, answered by measurement

The brief anticipated a **structurally-unrenderable** class. `lookup` genuinely
cannot run offline — but the chart ships `controllerServiceAccount.{name,
namespace}` to skip it, **its own error message recommends them**, and the values
are *derived*: rendering the sibling controller chart at the same pin with
arc-controller's own releaseName and namespace emits
`arc-controller-gha-rs-controller` in `arc-systems`, labelled as the exact string
the lookup would return. **Both** keys are needed — `name` alone fails on the
namespace lookup, so the previous acknowledgement's stated exit would not have
lifted anything.

So **no app is in that class, and none is recorded as being in it.** Creating the
category with no member would be a category that cannot fail — the thing this
checker exists to refuse. The distinction lives in the reason codes instead,
where it is now *checked*: `helm-pull-failed` (the pin names nothing upstream
serves) vs `helm-template-failed` (the chart is there, our values are wrong).

The static coupling this introduces is pinned by four tests in
`arc-runner-manifests.test.ts`, so renaming the arc-controller release fails
loudly instead of leaving a RoleBinding pointing at a ServiceAccount that does
not exist.

  and rendered by nothing.

The disk did not grow. The count did.

## The checker's own vacuity, found while using it

* **`observed` on an `unrenderable` acknowledgement was required by the loader,
  written on every entry, and read by NOTHING.** An app could stop failing at
  `helm pull` and start failing at `helm template` for an unrelated reason, and
  the acknowledgement written about the first would silently cover the second. It
  now pins the failure **class** (not the detail — that carries upstream line
  numbers and would re-red on a helm upgrade).
* **A stale unrenderable acknowledgement cost nothing.** Four would have been
  left behind by this very change if nothing required otherwise.
* **`pinnedChartVersion` scanned the six lines nearest `chart:`.** Documenting why
  oz's pin moved broke it — and it returns `""` on failure, which is not an error
  but a *wrong answer* that propagates into the `<dir>@<pin>` acknowledgement key.
  Now parsed from the document.

Both acknowledgement registers this touched are **empty**, and neither was
re-keyed: `acknowledgedUnmeasuredRequests` and `ACKNOWLEDGED_UNPUBLISHED`.
Re-keying preserves a "we cannot measure this" claim that has stopped being true.

## Not established, said out loud

* That ziti 1.7.2 behaves identically under chart 3.1.1 as under 1.3.4. **Only
  the manifest surface and the rendered objects were compared.** A render cannot
  tell you that.
* `clientApi.advertisedHost` and headscale's `server_url` are **placeholders** an
  operator must set before anything enrols. A wrong advertisedHost is not a
  render error; it is a fabric nobody outside the cluster can reach.
* `arc-runner-set` is renderable *offline* now. Whether the runners actually
  register still needs real hardware and a GitHub login — that is the check this
  cannot perform, and it is not claimed.
* `full-ai-cluster/temporal@0.59.0` was never touched here — another agent owned
  it and landed #13469 mid-flight. Its entry is gone from the list for that
  reason, not this one.
