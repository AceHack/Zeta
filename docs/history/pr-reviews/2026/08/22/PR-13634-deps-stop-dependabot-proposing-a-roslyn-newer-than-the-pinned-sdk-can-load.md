## Description

deps: stop Dependabot proposing a Roslyn newer than the pinned SDK can load

Microsoft.CodeAnalysis.* is not an ordinary dependency -- it is coupled to the
SDK pinned in global.json. A source generator built against a Roslyn newer than
the SDK's cannot be LOADED (CS9057), so an over-bump does not degrade at
runtime, it fails the build outright.

Measured on PR #13590, which is red on every platform:

  [codeanalysis-sdk-match] CS9057 hazard: the SDK's Roslyn is 5.6.0, but:
    Microsoft.CodeAnalysis.CSharp is pinned to 5.9.0 -- a generator built
    against it CANNOT be loaded.
    Microsoft.CodeAnalysis.Analyzers is pinned to 5.9.0 -- ditto.

The guard did its job. The cost is that the nuget group lands as ONE PR, so two
hazardous packages took nine unrelated and perfectly good bumps down with them,
and would do so again every week -- a standing red PR that trains people to
ignore the queue.

This ignores only the hazardous half: semver-major and semver-minor for
Microsoft.CodeAnalysis.*. Patches inside the SDK's own Roslyn line stay
allowed, because those are safe and there is no reason to hand-carry them.

LIFTS WHEN: global.json's SDK moves to a Roslyn line >= the pin wanted. That
bump belongs in the same commit as the SDK change so the two can never
disagree -- which is exactly what this stops a bot from doing on its own
schedule.

Not done deliberately: raising the SDK to accept 5.9.0. That is a toolchain
decision with a blast radius across every project and four-language byte-lock,
not a dependency chore, and it is not mine to take at 08:00 on a Friday.
