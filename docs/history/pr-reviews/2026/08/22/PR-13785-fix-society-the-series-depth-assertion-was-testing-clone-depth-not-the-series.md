## Description

`rho-series.test.ts` asserted `corpusCommits(ROOT).length > 100` to establish that there is
a real history behind the trend. It went red the first time CI ran it, and the assertion
was wrong rather than the tree: `actions/checkout` defaults to `fetch-depth: 1` and the
`test (TS hermetic)` job sets no override, so `git log -- db/mutation-findings/` returns
one commit or none. Reproduced in a real `git clone --depth 1`, where `corpusCommits`
returns 1.

That is a property of the CHECKOUT, and a test that fails on it is measuring clone depth.
It is also the sharper half of "verify the tree, not just the command" — the check did not
run on the history it claimed to be checking, and a check that did not run reads exactly
like one that passed.

The depth claim moves to the CHECKED-IN series, which is in the tree at any depth, and
gets strictly stronger for it: `db/effective-agent-count/rho-series-cumulative.tsv` must
carry >100 rows and be non-decreasing in `authoredAt`. That now also guards the artifact
against being silently truncated by a regeneration run on a shallow clone, which is exactly
how a series would lose its early history — the failure mode this whole investigation
depends on not having happened.

The live log keeps only the property that survives any depth: whatever it returns is in
order, which still kills a missing `--reverse`. Its limit is stated in the test rather than
hidden: on a depth-1 checkout that loop runs zero times, so it is NOT the non-vacuity guard
— the artifact assertions are, and they hold everywhere.

Verified in a real depth-1 clone of this branch: rho-series.test.ts 18 pass / 0 fail, and
the whole society suite 103 pass / 1 fail — the one being the pre-existing
`effective-agent-count.test.ts:392` band, which is deliberately left red.

Second follow-up to #13753 (see also #13777). Both reds on `main` from that PR are mine.
