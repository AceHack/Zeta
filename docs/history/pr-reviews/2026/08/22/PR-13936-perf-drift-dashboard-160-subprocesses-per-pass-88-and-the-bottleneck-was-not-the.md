## Description

## The first user could not use it

The first person to reach for this dashboard instead of their hand-rolled scan got a **400s timeout on the default** and **540s on `--dop 8`**, and went back to their scan. That is the identical dynamic that killed `src/Core.TypeScript/search/grep.ts` — correct, built for exactly the incident it was meant to prevent, and no output in 300s:

> **A guard slower than the unsafe path selects for the unsafe path.**

Being correct does not exempt a tool from being reached for. Correctness is untouched here; nothing was traded away.

## Measured with a counting shim on PATH, not inferred — and the diagnosis was wrong

The report was *"5% CPU over nine minutes means it is network-bound — far more requests per check than one."* That inference is wrong in a way that matters: **cutting API calls would have bought nothing.**

| | before | after |
|---|---|---|
| `gh` subprocesses | 87 | **87** — 1.06 per check, already near-optimal |
| `git` subprocesses | **73** | **1** |
| total subprocesses | **160** | **88** |
| wall, this host | ~48s at DoP=8 | **6.9s at DoP=16** |
| `--offline` | 0.04s | 0.04s |

The cost was **73 serialised `git log --diff-filter=A --follow` spawns, one per workflow**, inside `listGitHubCheckDefinitions` — **a phase with no DoP knob at all.** One costs ~0.22s here; the bulk call that replaced all 73 costs ~0.22s *for every path at once*. On a loaded host with on-access AV scanning each spawn, 73 serial subprocesses is exactly where nine minutes goes. So the AV was not a red herring — it just was not acting on the network.

The `?event=schedule` probe was suspected and is **vindicated**: 29 probes + 57 branch queries = 86 for 80 checks, because the probe *replaces* the branch call for the 23 periodic checks whose cron fires. Six extra calls total, not a multiple.

## Changes

1. **One `git log` for every path** (`definitionSinceForPaths`), replacing 73. *Honest limit, stated at the function:* the bulk form cannot use `--follow`, so a **renamed** workflow reports the rename date. That biases `definitionSince` younger, hence toward `not-yet-due` — the direction that **declines to alarm**, which is the right way round given `not-yet-due` exists precisely because false alarms get guards muted.
2. **Default DoP 1 → 16.** Measured live: 19.4s serial-equivalent · 9.3s @8 · **4.6s @16** · 3.9s @24 — and **cumulative `gh` time is flat** across all of them (60.6 / 60.7 / 60.8s), so parallelism buys real overlap and provokes no rate-limit penalty. 16 is the knee. The async rule wants the knob to **degrade** to 1, not **default** to 1. `--dop 1` remains the deterministic single loop, and **DoP=1 vs DoP=16 was re-checked** against the live repo (82 rows, byte-identical) rather than carried over from the earlier claim.
3. **`--timing`, permanent.** This tool's thesis is that an unmeasured thing gets guessed at, and its first perf report guessed. It should hand you the number: `timing: 6.9s wall · 87 gh calls (65.9s cumulative, DoP=16) · 1.06 calls/check`.

**Roster caching was suggested and is declined, with a reason:** re-deriving the roster every pass is where **frozen-roster (mode 2) protection** comes from, and it now costs 1 API call + 1 subprocess. Caching would trade a real guarantee for ~0.4s.

## The perf work found a correctness bug

Timing `--offline` on a fresh checkout produced:

```
OK — RED 0 · UNKNOWN 0 · coverage 0/0 · green 0
```

**An empty roster rendered green.** "0 of 0 observed" is the exact vacuity this surface refuses everywhere else, and the stated reason `GitLabAdapter` returns `not-supported` rather than an empty roster. A dashboard that knows of no checks has not passed — it has never enumerated anything.

`ok` now requires `coverage.known > 0`, and the headline reads *"the roster is EMPTY: no check has ever been enumerated, so this dashboard is uninitialised, not clean"*. Offline against a **populated** roster is unchanged and correct: `NOT OK · UNKNOWN 65 · coverage 0/65 (SHORTFALL 65) · green 0`, `rc=1`, 0.04s.

## Falsifiers

A performance regression of this class deserves a test, not a promise. `definitionSinceForPaths` takes an **injected runner** and five tests hold it to **one subprocess regardless of check count** (and zero for zero paths). `parseFirstAddDates` is pinned separately — including that a re-added path keeps its **oldest** date, because getting that backwards would make an established check look brand new, and a brand-new periodic check is `not-yet-due`, so **the alarm would silently switch off**.

**133 tests. 33 hand-written byte-verified mutants — 33 killed, 0 survived.**

## An error I own, and it happened twice

A mutation run hit a 1200s timeout and was killed **mid-mutant**, leaving two mutants applied in the working tree — one of which disabled the `schedule → periodic` mapping. I caught the first, then **read `git diff --stat` instead of the diff content** and declared the tree clean while a second mutant (`case "unknown": return false`, collapsing `registered-but-absent`) was still sitting in `fold.ts`. Only the test suite caught it.

That is *verify the tree, not just the command* — failed twice in one session, in the exact place the standing discipline warns about. Both fixed:

- the harness now restores every in-flight mutant on `SIGTERM`/`SIGINT`/`exit`, so a timeout can no longer strand one;
- the second branch is now its own mutant (33 not 32), so the hole that hid it is itself covered;
- and I verified the final tree by **grepping the diff content** for mutant signatures, not by reading a stat line.
