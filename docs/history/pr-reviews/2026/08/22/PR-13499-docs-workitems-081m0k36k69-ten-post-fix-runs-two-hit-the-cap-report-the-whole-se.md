## What the ten establish — and it is still the claim this work-item was opened for

**The apt-budget failure class is gone.** apt ranges **36.8–119.6s** against the 420s budget (**3.5x–11.4x** headroom, up from **2.8x**); **41** packages installed where it was 234; **~41 MB** fetched where it was **626 MB**; and `apt-get install did not succeed within the 420s apt budget` appears in **none** of the ten. The 119.6s outlier is worth keeping in view: under contention even the reduced set costs 2.5x its median — which is exactly why the margin had to be *multiplicative* and not a few seconds.

## What they also establish

**The lane still exceeds its cap under load, and apt is no longer why.** Both cap hits died inside `dotnet build`. The **pre-fix** cancellations died inside `Post Cache mise runtimes` — *later* in the sequence, because everything ahead of the build used to take longer. `dotnet build` measured **151s to >330s** across the ten, and **453s** on the 91.0% run whose install step was the *shortest* of the set (207s). That is the lane's payload on a contended 1-vCPU runner; no install-side lever reaches it.

**Two of ten is not a rate.** Neither is the 26% (14/54) it replaced. What is comparable is the mechanism and the failure signature, and both moved.

## Next levers, in size order

1. `dotnet build` itself — biggest and hardest, because it is the work.
2. The 76s `eprover` autotools **source build** — removed from slim in #13501.
3. `Cache mise runtimes` — a **122s restore** on the first cap-hit (and the paired save cost 52–62s at the end of several runs).
4. The **29s** of best-effort agent-CLI installs (`claude-code`, `codex`), which a `dotnet build` lane never uses.

Option 1 from the original filing (cache apt) is now worth **far less** than when it was written: apt fetches 41 MB, and its residual cost is dpkg unpack on one vCPU, which a package cache does not remove.
