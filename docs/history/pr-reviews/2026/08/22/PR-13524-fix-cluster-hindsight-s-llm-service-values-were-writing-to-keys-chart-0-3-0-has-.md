## Description

PR #13457 fixed `hindsight`'s storage and named its own limit: `api.llm.*` and the top-level `service` were **"narrowed, not cleared"**. Both are cleared here, and the ledger figure it deliberately left standing is now machine-checked.

Everything below was verified with `helm pull` at the pinned `0.3.0` followed by `helm template` from this Application's own `valuesObject` — via `rendered-storage-claims.ts`'s own `renderApplication`, not by reading the chart.

## 1. What chart 0.3.0 actually reads

| the manifest said | what the chart reads | rendered before | rendered after |
| --- | --- | --- | --- |
| `api.llm.provider: groq` | `api.env.HINDSIGHT_API_LLM_PROVIDER` | *(absent)* | `HINDSIGHT_API_LLM_PROVIDER=groq` |
| `api.llm.existingSecret.{name,key}` | top-level `existingSecret: <name>`, consumed as `envFrom` | *(absent)* | still absent — **on purpose**, see below |
| top-level `service.{type,port}` | `api.service.{type,port,targetPort}` | Service on **8888** | Service on **80** |

`templates/api-deployment.yaml` builds the api container's env from exactly three sources: the computed `HINDSIGHT_API_DATABASE_URL`, a `range` over `.Values.api.env`, and a `range` over `.Values.api.secrets`. There is no `api.llm` key anywhere in the chart, so the provider this file has claimed since PR #4913 never reached a container. The control plane's `HINDSIGHT_CP_DATAPLANE_API_URL` is built from `api.service.port`, so it follows to `http://hindsight-api:80` with no second edit.

**The API key is deliberately still unwired, and that is the honest state rather than the finished one.** The chart's real key is a *top-level* `existingSecret: <name>` string consumed as `envFrom: [secretRef]` — so the Secret's **key names become env var names**, and the key would have to be literally `HINDSIGHT_API_LLM_API_KEY`, not `api-key`. Wiring it today would be worse than leaving it: `grep -rn "kind: ExternalSecret" full-ai-cluster infra` returns **zero manifests** — nothing in either tree creates `hindsight-llm-api-key`, only the external-secrets controller and its store exist — and `envFrom` against a missing Secret holds the pod in `CreateContainerConfigError`. That would trade a silently-absent key for a container that cannot start. The exact one-line change and the required key name are recorded in the manifest, and `full-ai-cluster/README.md`'s claim of "a Vault-backed ExternalSecret" is corrected — it was never true.

**The service NAME was wrong too.** The chart renders `hindsight-api`, `hindsight-control-plane` and `hindsight-postgresql`; there has never been a Service called plain `hindsight`. Four documents said `http://hindsight.hindsight.svc.cluster.local`; all four are corrected. No deployed manifest sets `HINDSIGHT_URL` today, so this was a trap rather than a live break.

## 2. What this does NOT fix — measured, not assumed

The live `BackOff` / `FailedScheduling` is **not** downstream of these values.

- `hindsight-postgresql-0` fails on `Insufficient cpu`. The rendered requests are **500m + 250m + 250m before and after** — this change touches no resource block.
- `hindsight-api` and `hindsight-control-plane` are waiting on that database.

So the three inert values were three false declarations, and removing them removes the declarations, not the blocker. The capacity blocker is the one PR #13410 recorded as needing a per-substrate resource override or a maintainer decision on the metal-side cost; it is untouched here.

## 3. The `103` beside the `193`

The readiness extractor was wrong in two directions. One is fixed; the other cannot be, and saying which is the point.

- **FIXED — a template is not a claim.** It counted `blueprints-flowdent.yaml`'s 8Gi `mssql` **Blueprint**. A PVC exists only once a `Deployable` names it, and none does — the only Deployables live under `examples/`, which the platform Application's `directory.include` glob does not apply. The extractor now skips a template kind **unless some Deployable names it**, so writing one brings the capacity back with no edit to any list. **103 → 95 GiB.**
- **STRUCTURAL — the other 98 GiB has no key to read.** `gitlab` (76), `loki` backend + write (20), `mimir-alertmanager` (1) and `dapr` scheduler (1) take their PVC from **chart defaults**. Our Applications say nothing about storage for them. No amount of teaching a YAML extractor recovers a claim that is not in the YAML; only the render sees them.

A blank `storageClassName` now resolves to the cluster default instead of being **dropped**, and the reading of that default moved to `cluster-default-storage-class.ts`, shared with the render audit — so the two oracles cannot drift apart on the one term that must mean the same thing in both. **Measured honestly: no manifest in the tree writes a blank class today**, so that half closes a hole rather than fixing an observed miss. A test pins exactly that claim and goes red if it stops being true.

### Two oracles stay — and the report now says which to trust

Not because the disagreement is comfortable, but because they answer different questions: the derived figure is *what we declared* (which is what the storage-profile ladder governs), the rendered one is *what the cluster will ask for* (which is what the disk has to hold). The auditor now prints the render **per tree** beside the derived total, the same way the `967/911` longhorn pair already worked:

```
  zeta-local-path        95 GiB derived  (unbudgeted)
                        193 GiB RENDERED (full-ai-cluster tree, snapshot 2026-08-22) — trust this ...
                         76 GiB RENDERED (infra tree, snapshot 2026-08-22) — trust this ...
```

**Per tree, because the trees are mutually exclusive.** The ledger's own `acknowledgedRootAppDuplicates` records that both declare `argocd/zeta-root`, so one prunes the other and a single node runs **one** of them; the 269 GiB sum is a number no cluster is ever asked for. The ledger's `"193 = 117 full-ai-cluster + 76 infra"` was that sum mis-split — 193 is the full-ai-cluster tree **alone**, of which gitlab is 76, which is what made the two look interchangeable. (`rendered-storage-claims.baseline.json` already had this right; only the budget prose did not.)

## 4. The prose is checked now

Named as unfixed in the handoff: *"editing `193` back to `103` there is refused by nothing."* It is refused now.

`findLedgerFigureDrift` parses every aligned `<storageClass>  <N> GiB` row out of `single-node-budget.json`'s `$comment_*` blocks and refuses any number equal to **no** reading the auditor computes — the YAML-derived total, any rung of the ladder (declared or at bring-up), or the render, per tree and across trees. The recognised set is a union on purpose: the prose's job is to explain how those readings differ, and what it may not do is quote a number that is none of them. A rung name (`measured   967 GiB declared`) and an acknowledgement key (`longhorn=1599GiB>>1047GiB@node-ad1efd`) are both proven not to be figures.
