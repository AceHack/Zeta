## Description

## What this fixes

PR #13429 built `rendered-storage-claims.ts` and it immediately found two Applications whose `valuesObject` is **inert** — the declared values are read from keys the chart does not use. Both are fixed here, the render was re-measured, and the three baseline acknowledgements are **retired** rather than carried.

| app | declared | rendered BEFORE | rendered AFTER | the one-line cause |
|---|---|---|---|---|
| `hindsight/postgres` | `10Gi` on `longhorn` | **`8Gi`, no `storageClassName`** | `10Gi` on `longhorn` | wrote `postgresql.`**`primary`**`.persistence.*` (bitnami subchart layout); chart 0.3.0 ships its OWN StatefulSet reading `postgresql.persistence.*` |
| `nats/jetstream` | `10Gi` × **3 pods** | `10Gi` × **1 pod** | `10Gi` × **3 pods** | declared a **top-level** `cluster: {replicas: 3}`; nats 1.2.7 reads `config.cluster` and has no top-level `cluster` key |

## Why this is worth doing before hardware

**`zeta-local-path` is the cluster DEFAULT StorageClass** (`is-default-class: "true"` in `full-ai-cluster/nixos/modules/local-storage.nix`), it is `rancher.io/local-path`, and it has **`reclaimPolicy: Delete`**. Longhorn ships `defaultClass: false`, so nothing reaches the replicated class by accident.

So hindsight's blank class was never "a different disk". **The semantic-memory Postgres has been landing on node-local storage that deletes on reclaim**, for as long as the catalogue said `longhorn`. That is the durability of the store manifesto §5 calls a memory-preservation surface, and it was wrong by two GiB and one reclaim policy — the reclaim policy being the larger half.

**And nats had no quorum to preserve.** The row's `consequence` text asserted that the `measured` rung keeps the JetStream quorum and only `minimal` loses it. It did not: there was one pod at *every* rung, the generated `nats.conf` carried **no `cluster` section at all**, and a stream created with `replicas > 1` **refuses to create**. Anything depending on JetStream replication was silently unreplicated. The text is corrected as well as the values — a corrected mechanism with a stale claim beside it is the failure mode this repo exists to refuse.

## The 103 GiB figure is not silently absorbing these deltas

`single-node-budget.json`'s `zeta-local-path 103 GiB` was known wrong **in both directions**, and it is a number the readiness auditor *prints*, not just a comment — so replacing it outright would have swapped one drift for another. It now prints **both oracles**, the way the longhorn `967/911` pair already does:

- **103 GiB** — the readiness extractor's reading of our own YAML. It **over**-counts `blueprints-flowdent.yaml`'s 8Gi `Blueprint` (a template; a PVC exists only once a Deployable references it, and none does) and **under**-counts every claim that renders with no `storageClassName` and therefore *binds* this class as the default (loki backend + write 10 each, mimir-alertmanager 1, dapr 1 = 22 GiB today, 30 before hindsight moved off). Two errors of opposite sign is why the total looked plausible.
- **193 GiB** — the render (117 full-ai-cluster + 76 infra).

The extractor itself is **not** changed here. Teaching it to resolve a blank class to the cluster default changes how it reads every claim; it is left as a **named** gap rather than a silent one.
