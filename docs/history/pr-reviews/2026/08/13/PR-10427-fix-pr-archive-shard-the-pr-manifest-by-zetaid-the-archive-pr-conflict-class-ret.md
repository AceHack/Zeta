## Description

Implements `081KZYMY46P087G0R003S64V2B` (filed as #10414). Aaron greenlit the migration.

## The defect

`archive-pr-reviews.ts` wrote `docs/github/prs/manifest.jsonl` by **read-modify-write of one shared file**, so every archive PR touched the same trailing region and **N in-flight archive PRs conflicted pairwise**. Observed live 2026-08-13: eight simultaneously open and mutually conflicting, three ticks of hand-draining, and the queue re-grew on every merge. §2 lock-free · §8 DV2.0 · §12 idempotency.

## The fix — option A **and** B, as the work-item proposed

**A — shard by ZetaId.** One file per archived PR at `docs/github/prs/shards/<NNN>/<zetaid>.json`, the shape already proven by `data/tick-shards/` and `workitems/events/`. The ZetaId is a pure, total, **invertible** function of `pr_number` (key in the 32-bit `randomness` field, `Category.Observation`, `timestamp = 0` unspecified — the header explains why `merged_at` would have been wrong). Consequences:

- a duplicate entry for one PR is not merely avoided, it is **unrepresentable** — there is no second path it could occupy;
- distinct PRs get distinct paths **by construction**, not w.h.p. — no digest, no birthday bound;
- no clock and no entropy in the mint — §7 DST and §13 noninterference for free.

**B — derive the manifest.** `manifest.jsonl` stays at its current path with its current schema and becomes a **derived index** (`derive-pr-manifest.ts`, same `derive` + drift-gate shape as `ace/build-graph.ts` #10395). **Writer-side change only: no reader is modified.** A manifest merge conflict is now always resolved by regenerating, never by hand.

## The conflict class, demonstrated rather than asserted

The suite builds two real `git` branches that each archive a different PR and merges both — clean — **and** runs the CONTROL: the same scenario against the single-file manifest, which reproduces `CONFLICT`. Without the control the first result would prove nothing.

## Correction to the work-item's migration note (CHECKED)

#10414 reported **3 malformed lines** (PRs 6247, 6521, 7865). **They are not malformed.** All 6339 lines parse — here and in all 40 prior revisions of the file. Those three are exactly the entries whose `title` contains a backslash or a control character (the only such entries in the manifest), which is what a line- or regex-oriented reader misreads as corruption. They round-trip byte-for-byte and now have a named regression test. The `docs/github/prs/unparseable.jsonl` quarantine ships anyway — the next genuinely unreadable line has to land somewhere a human finds it, with its reason and original line number, instead of vanishing in a cleanup.

## A bug found by running it

Re-archiving #10413 against the live API reported `manifest=noop, shard=replaced`: `updateManifest` excludes `fetched_at`/`commit_sha` from its equality check and the new shard writer did not. Two writers, two idempotency rules — every re-run would have churned a shard **and** drifted the derived index off the manifest it must reproduce. Fixed, and locked by a test that names the incident.

## Split out (constraint 4)

`.github/workflows/pr-archive-on-merge.yml` still stages `manifest.jsonl` into the archive commit; removing that is what retires the conflict **in production**. A PR touching `.github/workflows/**` never gets `gate` scheduled and is unmergeable, so it ships as **`081KZYP7MNV087G0R002X0E3V9`** with the exact diff. `agent-heartbeat.yml` needs **no** change — it already stages the whole `docs/github/prs/` directory, so shards ride along today.

Until that lands the writer keeps updating the manifest, so this PR is a strict improvement with no behaviour regression: same files, same schema, plus the shard store and its generator.
