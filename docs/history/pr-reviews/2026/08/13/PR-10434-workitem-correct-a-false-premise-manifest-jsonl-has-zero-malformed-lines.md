## Description

Corrects work-item `081KZYMY46P087G0R003S64V2B` (filed in #10414), which asserted **3 pre-existing malformed lines** in `manifest.jsonl` and made surfacing them an acceptance criterion.

**CHECKED: all 6340 lines parse** — in this revision and every prior one, verified independently during the migration in #10427. The three named PRs (6247, 6521, 7865) are exactly the entries whose `title` contains a backslash escape or a control character (`\\uXXXX`, a literal `\\n`). They round-trip byte-for-byte.

## Root cause, and it's the second instance today

The detection ran each line through `echo "$l" | jq` in **zsh**, where `echo` **interprets backslash escapes by default**. The `\\u` and `\\n` inside the JSON string values were expanded *before* `jq` parsed them — corrupting well-formed lines **at the measuring instrument**, not in the data.

Earlier the same day the same bug produced a phantom 7-line discrepancy in a manifest line count and sent an autonomous tick chasing corruption that did not exist.

**Lesson recorded so it's reusable:** never parse or count structured text through `echo` in a shell pipeline — read the file directly (`python3`, `jq -c . < file`, `bun`) so no shell builtin sits between the bytes and the parser. *A measuring instrument that mutates its input produces findings about the instrument.*

## What stands

The **defect this item files is unaffected** — the read-modify-write conflict storm is real, was measured live (8 mutually-conflicting archive PRs), and is fixed in #10427. Only the migration-hazard subsection was wrong.

The quarantine sidecar shipped anyway and is still worth having: it's now empty, and the next genuinely unreadable line lands there with its reason and line number instead of vanishing. A regression test pins the three escape-carrying titles so a future pass can't "clean them up" by repeating this mistake.
