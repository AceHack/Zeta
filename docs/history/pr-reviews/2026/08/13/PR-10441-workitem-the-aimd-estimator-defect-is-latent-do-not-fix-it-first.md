## Description

Adds an ordering warning to `081KZYN37T4087G0R00181THA4`, because someone picking it up today would cause a large throughput regression.

**`gapMs` is computed and never read.** `flushBlock` broadcasts all 8 packets of a block in a tight loop and never consults it; repo-wide it is read only by `updateAimd` itself and two test assertions. **The shipped transport has no rate control at all** — the AIMD controller is an open-loop estimator whose output is discarded, so this window defect is **latent**: a wrong number nothing acts on.

## Why fixing it first is harmful

Wiring the pacing — or repairing the estimator so its output becomes trustworthy enough to wire — **activates** the erasure-vs-congestion conflation *before* the signals are separated. Measured with congestion **structurally zero** (asserted, not assumed):

| corruption | shipped (open-loop) | AIMD paced |
|---|---|---|
| 2% | 0.981 | **0.139** |
| 10% | 0.905 | **0.010** |

**7.1× worse than a corruption-blind sender at 2%, 90× at 10%**, with no congestion anywhere. One spurious backoff costs **≈67 minutes** of recovery on a clean link.

## Correct order

1. `081KZYQ8KNB087G0R000G8QPRE` (P1) — **separate the loss signals** (RFC 4653 names the class)
2. This item — the estimator window
3. `081KZYQ8Q9V087G0R0013XR3ZX` — wire `gapMs`, and the 1000 pkt/s `MIN_GAP_MS` ceiling

**The control that keeps this honest:** under loss that genuinely *is* congestion, two paced flows reach **Jain 0.973 at 79% utilisation**. The controller is not broken *as a congestion controller* — it fails specifically when loss is not congestion. Which is why the fix is signal separation, not threshold tuning: no threshold distinguishes 5% corruption from 5% congestion when the estimator doesn't carry the distinction.
