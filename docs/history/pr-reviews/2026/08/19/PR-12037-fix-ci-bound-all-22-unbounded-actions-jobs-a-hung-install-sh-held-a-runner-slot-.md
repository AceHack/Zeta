## The defect

Main did not advance for ~2h on 2026-08-18. Two jobs held runner slots past 67 minutes; `lint-autofix` run `32162265039` was still `in_progress` at 90 minutes. Slots never freed, new work queued, concurrency cancelled the constituent lint jobs, and `gate (required)` correctly read *cancelled* as failure — so PRs went red with no real defect, re-runs added load, and the result was congestion collapse.

## 2. Why 20m for five of them

`gate.yml` caches install.sh outputs 23 times. **None of the five uncached install.sh jobs cache anything** — they pay full install cost every run, so gate 12–15m rungs would be too tight and would turn a slow job into a red one. 20m clears one honest apt stall-and-recover (600s) plus the work, while still cutting the 30m inner apt budget.

## 3. Root cause — a timeout is the seatbelt, this is the crash

Every pathological run spends its entire life in **one step, `./tools/setup/install.sh`**, with the actual lint work taking `0.0m`. Job logs name the stall precisely: `azure.archive.ubuntu.com` stalling mid-download on large packages (pandoc 26.9 MB, golang-1.22-src 19.7 MB, golang-1.22-go 25.9 MB), with `apt-get install exceeded 600s (attempt N/3)` firing three times.

**The retry budget is multiplicative.** `linux.sh` retries apt 3× at 600s (~30m); callers wrap install.sh in a **5-attempt** loop. One unbounded job therefore has a ceiling measured in hours. `linux.sh` says so itself in a comment — *the job `timeout-minutes` is what finally fires* — and 21 workflows shipped without one.

This is **not** a `lint-autofix` bug: the same step is the 140.5m outlier in `backlog-index-integrity`. It is a shared-dependency pathology that only `lint-autofix` made visible, because `lint-autofix` is the one unbounded workflow that also carries the 5× wrapper.

**Follow-ups I did not do here** (behaviour changes, out of scope for a timeouts-only PR): add `actions/cache` for install.sh outputs to the five uncached workflows, and collapse the nested retry loops so the budget is additive rather than multiplicative.

## 4. `lint-autofix-apply` blast radius — a timeout cannot leave a partial write

- `contents: write`, but it **only pushes when `head_branch == main`**; on any other branch it writes a job summary and pushes nothing.
- Everything before the push — `git apply --index`, `git config`, `git commit` — is **local to the ephemeral runner**. A timeout there leaves zero trace.
- The only remote mutation is a single `git push` of a single commit. Git ref updates are **atomic per ref**: a SIGTERM either lands the complete ref update or none of it. There is no half-written ref, no multi-ref or tag+branch pair to desync.
- Worst case at timeout is therefore **a complete commit whose reporting was lost** — not corruption. It is self-correcting: the heal is idempotent, so the next run produces an empty patch and no-ops.
- The push is non-force, so a stale runner finishing late is **rejected**, never a clobber.

Set to **15m** against an observed max of 6.6m (n=33). A false cut here is benign — the heal is advisory and re-runs on the next markdown PR.

## 5. Repo-level default vs 21 per-file edits

**A repo-level default does not exist.** GitHub has no repo- or org-level default job timeout, and workflow `defaults:` covers only `run` shell/working-directory. Per-job declaration is the only mechanism, so this is settled mechanically, not by preference.

What *is* available is making the class **stay** closed: `src/Core.TypeScript/hygiene/lint-workflow-job-timeouts.ts`, wired as one step into the existing `gate` → `lint-structural-hygiene` job, which already has Bun provisioned. **No new job, no new runner slot, no new matrix axis** — marginal cost is a couple of seconds on a job that already runs.

Falsified in both directions, because a check that cannot fail is not a check:

- removing one `timeout-minutes` makes it exit 1 naming the file, line and job (verified by hand and pinned in the test);
- a **step-level** `timeout-minutes` does **not** satisfy the job-level requirement — otherwise an unbounded job would pass because one of its steps is bounded;
- reusable-workflow calls are exempt **by shape** (GitHub rejects `timeout-minutes` there), not by a drifting allowlist;
- it carries a **scan floor** so it cannot pass by inspecting nothing.
