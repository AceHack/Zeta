## Description

Aaron asked, of `.github/workflows/agent-reviewer.yml`: *"is there an alternative to this, is something else doing this job? if not, let's fix it."* Answered first, then acted on.

## The answer: three separable jobs, two already covered

| job | who does it today | state |
|---|---|---|
| **emit** peer attestations | `observe/emit-attestation.ts`, invoked every tick by `agent-heartbeat.yml` | live — **380 records on `main`** |
| **verify** an attestation record | `observe/attestation-record.ts` + `observe/verify-attestation-events.ts` (#12256) | complete, tested, host-independent — **called by no workflow** |
| **gate** on the result | nothing | `summarizeAttestations` is referenced only by its own test |
| filename shape in `docs/observe-events/` | `hygiene/audit-observe-event-filenames.ts`, inside `gate (required)` | live |

So the emit half never needed this workflow, and the filename check it performed was a redundant second opinion — the exact defect `hygiene/agencysignature-block.ts` exists to end. **The genuine gap is that nothing ever ran the verifier.** This PR wires it.

## The auto-approver was refused, not armed

The bar: *strictly harder to get a false approval than the dormant state.* Four findings, measured against production:

1. **It would have fired on nothing.** Its allowlist admitted `docs/observe-events/*.json` + two `data/tick-*.json`. Every live batch also carries `db/mutation-findings/<agent>.jsonl` (PRs #12344/#12345/#12346; #12344 also carried 84 files under `docs/history/pr-reviews/` and `docs/github/prs/shards/`). So `sovereign=false` on every real batch and validate/approve/receipt all skip. Re-pointing the trigger alone buys ~288 runs a day that inspect a real input and can never reach a verdict.
2. **The approval unlocks nothing.** `gh api repos/{owner}/{repo}/rules/branches/main` returns exactly `deletion`, `non_fast_forward`, and `required_status_checks` for `gate (required)` (ruleset 16134995, active). There is **no `pull_request` rule** — `main` requires no approving review.
3. **The receipt push would have deadlocked the flush lane.** It pushed with the checkout's `GITHUB_TOKEN`; GitHub starts no workflow run for such a push, so no `synchronize` fires, so `gate.yml` never runs on the new head — and `gate (required)` is required *at the head SHA*. Auto-merge could never complete, and `required-check-started.ts` exits 1 twenty minutes later. Not a hypothesis: the same failure is already recorded in `agent-heartbeat.yml`, where a stale flush PR *"took THIS VERY JOB red every ~25 minutes"*.
4. **The receipt was a record the verifier refuses** — no `attestedDigest`, and an id from `sha256 | head -c 32` rather than `deriveAttestationId`. One REFUSED record per flush, into a corpus already at 0 bound / 3 unbound / 377 refused.

A dormant approver is one branch rename away from live; an absent one is not. So the capability is **removed**: no `--approve`, no `git push`, `contents: read` + `pull-requests: read`.

## What an attacker who can push a `heartbeat/*-flush-*` branch gets

**Cannot obtain**, after this change and equally before it: an approving review (none is issued, and none is required by any rule); a commit authored by this workflow; any write to any ref; any secret beyond the default `GITHUB_TOKEN`, which is now read-only in this job; a bypass of `gate (required)`, which is unaffected.

**Can obtain**, unchanged by this PR: a red or green X on a *non-required* context, by choosing what the branch contains. Since the job cannot approve and cannot write, that is the whole surface. They could already do this by opening any PR.

**Newly denied**: pushing events authored `by: <someone-else>` under their own branch, or an attestation record with a bad digest or a non-derived id, now produces a visible FAIL where nothing looked before.

## Still open, deliberately

The **independence gap**. There is one identity and no second key behind this workflow, so nothing it prints is a peer attestation — and it does not use the word about its own output, pinned by a test that reads the workflow with comments stripped (which caught the header's own prose on its first run). Closing it needs a signature over the bytes by a key the producer does not hold. **No private key is created, required, or handled here**; `verify-attestation-events.ts message` already emits exactly those bytes for whoever holds one.

Promoting this context to a **required** check is a one-line ruleset change and a maintainer's call, not this PR's to assume.
