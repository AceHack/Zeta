## The decision this implements

Aaron, 2026-08-19, verbatim — it settles a question `081M0BVAV2H087G0R000VXRYRQ` was filed to ask:

> "windows and mac are drift checks, it's fine to check per pr if we want but we don't want to block on them. Also we are moving more and more away from PRs and more into sovereign mode without PRs."

The register change is the whole point. `continue-on-error` on the Windows legs was documented as a **tolerance** — something being put up with, to be worked off against a promotion criterion. It is a **classification**: these legs are drift checks. Drift checks are observed and are not gates.

**Nothing about what blocks changes here.** The flag's value is byte-identical (`startsWith(matrix.os, 'windows-')`), no check is weakened, and no currently-blocking leg is touched.

## The per-PR question — priced, and declined

Aaron allowed it but did not ask for it, so it is decided here rather than skipped:

| | measured 2026-08-19 |
|---|---|
| PR-event `gate` runs | 100 completed in 6h45m → **~355/day** |
| Windows legs | 11m03s + 10m00s = **~21 runner-min per PR run** |
| **Cost** | **~124 runner-hours/day** |

Against near-zero marginal detection: the same legs already run on push-to-main, so for a check whose job is to notice drift rather than attribute it, the latency is at most one merge. It also buys a hazard — a red leg on the PR page that cannot block and that the author usually cannot fix is exactly how a floor stops being read. Reopen if PR volume collapses or the legs get materially faster; the permission does not expire.

## The gap that was actually open — COVERAGE

Non-blocking is only honest if someone notices, so the routing was audited rather than assumed. Two surfaces existed, and **both stop short**:

- `gate-scope-summary.ts` names a non-blocking failed leg in the `gate (required)` summary — per-run, on a push run nobody opens.
- `drift-sweep.yml`'s **BD001** does route it (the Actions API reports `conclusion: failure` for a `continue-on-error` job — the committed fixture proves it), but keys findings to `Zeta.sln`, so **which platform** is lost; it cannot tell a red blocking Linux build from a drift leg doing its job; and it reads **one** run, measuring a level and never a rate.

Then the number that reframes all of it: **of the 300 most recent completed `gate` push runs on main, 265 were `cancelled`** before their legs executed. Main pushes arrive faster than a gate run completes and GitHub keeps at most one *pending* run per concurrency group. So the Windows drift check executes on roughly **one merge in eight**, a detector reading only the latest completed run will usually read a cancelled one and find nothing, and every "N consecutive clean runs" claim about these legs — including the withdrawn criterion — was counting pushes, not executions.

`src/Core.TypeScript/ci/platform-drift-report.ts` closes it: per-leg failure **rates**, clean streaks, and **coverage**, published to `data/platform-drift.json` and rendered on the fleet monitor (`data/monitor.html`). Seeded from 500 real runs, 82 of which executed (16.4% coverage):

| leg | status (observed) | executed | failures | rate | clean streak |
|---|---|---|---|---|---|
| `build-and-test (windows-11-arm)` | drift check, non-blocking | 82 | 12 | 14.6% | 57 |
| `build-and-test (windows-2025)` | drift check, non-blocking | 82 | 6 | 7.3% | 58 |
| `build-and-test (macos-26)` | **BLOCKS** | 82 | 1 | 1.2% | 19 |
| `build-and-test (ubuntu-24.04)` | **BLOCKS** | 82 | 2 | 2.4% | 27 |
| `build-and-test (ubuntu-24.04-arm)` | unobserved | 82 | 0 | 0.0% | 82 |

Design notes that are load-bearing rather than decorative:

- **Classification is observed, never configured.** A leg is called non-blocking only when it has been *seen* to fail beside a green `gate (required)` — so nothing in the fold knows the word "windows", and a future `continue-on-error` leg surfaces itself.
- **`unobserved` is not `healthy`.** A leg with no failures in the window had the question put to it zero times, and the report refuses to round that up. `ubuntu-24.04-arm` is the live instance.
- **Idempotent and incremental** — records keyed by run id and upserted; a tick costs one list call plus jobs for runs it has not seen. `asOf` is the newest *run's* timestamp, not `Date.now()`, so a tick that learns nothing rewrites byte-identical content and produces no commit churn (and no local wall-clock enters a shared artifact).
- **Never fatal.** The step is `continue-on-error`, because a reporter that can fail the build would quietly re-introduce the blocking it exists to describe.

## Deliberately NOT done

- **macOS not flipped** — floor amendment, own work item, own consent path.
- **BD001 not split.** It fires identically for a red Linux build and a Windows drift leg, at 1-tick budget → auto-filed P1, and the monitor renders it as "main build RED". Separating them needs a `registry/drift-slo.yaml` entry, which is a registry consent act — recorded as a follow-up, not slipped in here.
- **The 88% push-run cancellation rate not addressed** — a CI-topology question that degrades every push-cadence check, not just these legs.
