## The decision

Eleven committed records in `docs/observe-events/` hold a filesystem path where a persona name
belongs — `/tmp/attest-0rHTQr`, `/tmp/attest-4EC3oi`, `/tmp/attest-hqFnhO`, `mkdtempSync` fixture
directories from this module's own end-to-end tests, written by a real run and merged 2026-08-17.
Work-item `081M0BTG2M7087G0R0011X5ESW` proposed a disposition and explicitly **did not decide it**.

| option | what it costs |
|---|---|
| leave-and-annotate as-is | the correction lives only in a **test**. A consumer that reads the folder and does not run this verifier still sees eleven ordinary-looking attestations — three phantom personas, ~4.58 strength, `hasTrioAttestation: true`. The data says nothing about itself. |
| **a recorded retraction that supersedes without removing** | a new event kind, and a consumer that ignores retractions is no better off than under option 1. But the correction is **in the corpus**, discoverable by anyone reading the data, and **the eleven files are not touched at all**. |
| quarantine into a fixture path | **breaks the falsifier** — the pinning test asserts those filenames exist *in the corpus directory* — and moving a committed event is itself an edit to the history of where it lived. |

**Taken: the recorded retraction.** It is the repo's own Z-set discipline — emit a `-1`, never
delete the `+1` — and §5 Memory Preservation applied to embarrassing history, which is the only
kind that tests it.

The eleven files are **byte-identical to what merged** (`git status` shows them untouched). Both
pinning tests still assert every one of them REFUSED. Losing the falsifier to tidy the corpus would
have been the worst outcome, and it did not happen.

## One record naming eleven, not eleven records

The work-item weighed *"writing nine or eleven `-1` facts into the shared log"*. One is taken, and
not for tidiness: the eleven share **one cause** and therefore **one basis**, and eleven copies of a
basis string is eleven places for it to drift. A retraction is keyed by what it retracts, so
re-issuing is an upsert rather than a double-count. `retracts` is a list precisely so a second cause
gets a second record rather than an amendment to this one.

## The retraction claims no authority, and that is the design

The finding this work-item opened with is that `by` is a **self-claim** — the corpus holds zero
bound records, so no name in it is authenticated. A retraction asserted by an unauthenticated `by`
would inherit exactly that weakness, and pretending otherwise would be the same defect wearing a
correction's clothes.

So it does not ask to be believed. It carries a `basis` naming the **check** that re-derives it:
anyone can run `verifyAttestationRecord` over the eleven ids and observe an identity-band refusal
for each. It is a **signpost to a mechanical fact**, not a testimony. A test asserts the record is
unsigned and that its basis names the check, so a later signature is a deliberate change rather than
a drift.

## Coverage is checked in both directions

`retractionCoverage` fails on:

- **under-retraction** — an identity-band refusal that no retraction names (the corpus grew a
  polluted record and nothing recorded the correction);
- **over-retraction** — a retraction naming a record that is absent, or present and *not* refused
  (a correction aimed at a fact that was never wrong).

Over-retraction is exactly as wrong as under-retraction, for the same reason a ledger that
over-charges is still one nobody can reconcile.

The band is `malformed-attestor | malformed-attested | malformed-participants |
envelope-attestor-mismatch` — deliberately **not** `missing-digest`, which most of the corpus
carries. A retraction owed to those would be retracting the corpus for being old, and a test pins
that boundary.

`parseRetraction` also refuses the vacuous forms: an empty `retracts`, a blank `basis`, and there is
no `disposition` value meaning *removed*.

## Also fixed: a pre-existing red on `main`, in the same file

`NO record in the corpus is bound today` asserted `refused === records.length`, on the stated ground
that every record *"predates `attestedDigest` or is a leaked fixture, so nothing is merely `unbound`
yet either"*. **The corpus outgrew that sentence.** Three records emitted after the digest feature
landed carry a valid `attestedDigest` and no signature — which is exactly `unbound`, and exactly the
state the feature was built to produce.

This was **red on `origin/main` before this branch existed**; reproduced by removing the new file and
re-running. A snapshot of a count is not a property, and that one was measuring "nobody has used the
feature yet". Restated as the property it was reaching for: every record that is not refused is
unbound **because** it carries a digest and no signature. That says *why*, does not drift as the
corpus grows, and still goes red the moment anything binds.

## And one performance fix the tests found by timing out

The corpus is ~2,600 files and each loader read all of them. Adding a second view pushed the suite
past bun's 5 s per-test timeout. `loadEventJson` + `selectAttestationRecords` / `selectRetractions`
split the *read* from the *selection*, so a caller needing both views pays one disk pass:
**12.6 s → 1.3 s** across the three attestation suites. Selection semantics are unchanged — still by
parsed `kind`, never by filename.
