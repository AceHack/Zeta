## Description

## What broke

#12047 made ISO selection architecture-aware because a wrong-arch flash's only symptom is
**"no bootable device"** on the target board — indistinguishable from Secure Boot or a boot-order
problem — after a full flash-and-walk-to-the-box cycle has been spent.

Both fallback branches it added shipped with **every interpolation missing**:

```text
zflash: WARNING no ISO here names arch ; falling back to , whose arch cannot be read.
zflash: WARNING could not read an architecture from  — assuming it is .
```

Not stripped by a later refactor. `git log -S'assuming it is ${'` finds no reachable commit in
which the interpolated form ever existed — the messages were born empty.

A third defect in the same block: the refusal path built its message with `\\n` inside a template
literal, so it rendered as one line carrying literal backslash-n with the candidate list inlined
into the prose. That is the branch the module's own comment calls *"the one worth stopping for"*.

## Why it matters — this is the live branch on the operator's Mac

Found by dogfooding against real machine state, not fixtures. `~/Downloads` holds exactly two
`zeta-installer-*.iso` files (2026-06-09, 2026-06-21) and **neither carries an arch token**; the ISO
the first-metal preflight staged is gone. So `selectDownloadedIsoForArch` falls through to its
arch-less branch **today** and prints the empty warning.

The one signal that a bringup cycle is about to be spent on the wrong image named neither which
file was picked nor which architecture was wanted.

## Why 90 green tests did not catch it

Every existing assertion pins a substring of the **constant tail**:

```ts
expect(r.warning).toContain("no bootable device");
expect(r.warning).toContain("cannot be read");
expect(r.error).toContain("refusing to guess");
```

The constant part cannot fail. Vacuity class — a check that cannot fail is not a check. 90 pass,
0 fail, message empty.

## Falsifier

Reverting `lib.ts` to `origin/main` turns **exactly the 4 new tests red** and leaves **all 90
pre-existing tests green** — which measures the coverage gap, not merely the bug. 468 tests pass
across the 21 zflash files with the fix in.

One of the four is a **class-level guard**: it enumerates every branch capable of emitting a message
and fails any that names none of its candidates, so a new branch added later with a bare-constant
message fails in CI rather than on a target board.

## Class swept, not just the instance

- `\\n`-in-a-template-literal has two other hits repo-wide, both correct (a `printf '%s\n'` shell
  argument, a `RegExp` source).
- No other dropped-interpolation site in the zflash / installer / persona-keys surfaces.
- `eslint --fix` was checked and does **not** strip these expressions, so the fix survives lint.

## Docs corrected rather than added to

`docs/runbooks/2026-08-16-first-metal-bringup-preflight.md` staged an ISO at a `~/Downloads` path
that is **gone** (re-measured by `ls`, along with its sigstore bundle), so step A2's hand-path failed
at `flash-usb.ts`'s ISO gate with `ISO file does not exist`. A2 now uses the bare `zflash` form the
tool was built to make safe, and the §4 #5 cosign block takes the ISO as a variable rather than a
name that evaporated.
