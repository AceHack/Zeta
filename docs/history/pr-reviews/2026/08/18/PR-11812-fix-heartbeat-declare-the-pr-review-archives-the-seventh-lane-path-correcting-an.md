## Description

This path was measured hours ago and deliberately LEFT UNDECLARED, on the stated ground that
`merge=theirs` "would silently drop a recorded review thread." That reason was WRONG, and the
correction is the whole justification for this change rather than a footnote to it.

THE INVERSION. `prepare-heartbeat-branch.ts` does `checkout -B <lane> origin/main` (line 95)
and then `merge --squash <previous lane>` (line 102). OURS is therefore main and THEIRS is the
LANE. `merge=theirs` keeps the LANE's copy — and the lane is the side that HAS the threads.
Main's copy is the impoverished one, written when the review threads were not fetched. The
concern was real in form and backwards in direction.

MEASURED across the whole path, not sampled — origin/main vs origin/heartbeat/soraya:

    git diff --name-status origin/main FETCH_HEAD -- docs/history/pr-reviews/
      1206  D   present on main, ABSENT on the lane — not conflicts; a merge never touches them
         2  M   the ONLY files present on BOTH sides with differing content

Those two are exactly the pair the failing tick names (run 32104099738):

      PR-9181   lane 6247 bytes / 1 `PRRT_` thread    main 2847 bytes / 0 threads
      PR-9182   lane 8153 bytes / 2 `PRRT_` threads   main 3474 bytes / 0 threads

In 2 of 2 live cases the lane's copy strictly dominates — it holds main's record plus the
threads. The converse case this was parked over, main richer and `theirs` discarding it, has
ZERO instances in the live data.

WHY THIS STOPPED BEING JUST A WEDGED LANE. `pr-manifest-integrity.yml` names soraya's archive
duty as the repair writer for the derived PR index. While soraya cannot land, the index drifts
past its ~1h repair bound and main goes RED (run 32107528665 at 06:34Z). Re-deriving the index
(#11809) clears that for about an hour; only unwedging the writer stops it recurring.

THE TEST asserts on the thread id, not on file size, so it pins the DIRECTION rather than
merely "a side won" — reverse the driver and `PRRT_kwDOSF9kNM6N_x6l` disappears and it fails.
Mutation-checked: deleting the `.gitattributes` line fails it with the production error,
"carry unflushed heartbeat state failed: ... Automatic merge failed". 13 pass with the line.

STATED LIMITS, both, because this rests on a smaller sample than the six lines above it:
  1. N = 2. Consistent, and it is the entire both-present population today, but it is two
     files — not a proof about the generator that wrote them.
  2. `theirs` is correct only while main's copy is the stale one. If the archival producer is
     fixed so main holds the richer record and a lane can write a thread-less copy over it,
     this line inverts from lossless to lossy. The durable fix is producer-side, and this line
     should then be REMOVED rather than kept as belt-and-braces.
