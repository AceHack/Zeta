## Description

## What

The probe whose entire job is to answer *"is there a device here"* **could not see a YubiHSM 2 at all** — and hardware lands today (HSM in Aaron's hand, YubiKey in transit).

Two defects, same class, opposite directions.

### 1. A YubiHSM 2 was unseeable

Every detection route in `frost-hardware-probe.ts` is structurally blind to it:

| route | looks for | why the HSM misses it |
|---|---|---|
| `probeSmartCardReader` (Linux) | USB interface class `0x0B` (CCID) | the HSM is a **bulk** USB interface, not CCID |
| `probeSmartCardReader` (macOS) | `Readers:` block of `SPSmartCardsDataType` | not a smart-card reader |
| `probeYubikey` | `ykman list --serials` | `ykman` enumerates YubiKeys; the HSM CLI is `yubihsm-shell` |
| `probePkcs11` | `ykcs11` / OpenSC paths | the HSM module is `yubihsm_pkcs11` |

An attached HSM read as `Device present: NO`, and the refusal said **"no smart-card reader or token attached"** — false about the hardware in the machine. This is `081M00HVPGS` inverted: there a driver was read as a device; here a device is invisible and reported as absent.

### 2. Any module was paired with any device

`availableHardwareSealTiers` computed `some module && some device`, never matched. `ykcs11` on disk + an attached YubiHSM reported `hardware-pkcs11` **honourable** — and `ykcs11` cannot address an HSM, so the seal dies inside an FFI call having promised at preflight that it would not. A preflight that green-lights an impossible configuration is worse than none: it turns a fast refusal into a deep failure, mid-ceremony, holding key material.

Fixed by `probeYubiHsm2` / `probeYubiHsm2Pkcs11` and `pkcs11MatchedPair`.

## A latent trap removed

The real-host test asserted `pkcs11ModuleFound` whenever `hardware-pkcs11` was honourable. That holds only while the token module is the only module the file knows about — it was scheduled to go red the first time `yubihsm_pkcs11` + an HSM were the honourable pair, i.e. **on ceremony day, in a test named "the real host"**.

## Update: the fix was wrong on the first real device, and has been corrected

Aaron attached the HSM and installed the SDK. **The probe above still reported `Not detected`.** Measured on his Mac:

```console
$ system_profiler SPUSBDataType | wc -l
0                                     # EXIT STATUS 0 — succeeded and said nothing
$ ioreg -p IOUSB -w0 | grep -oE '\+-o [^<]+'
  +-o YubiHSM@00142200                # behind two hub levels on a Thunderbolt dock
```

An empty string does not throw, so the `catch` was dead code and an empty haystack matched no marker. **"No device", "the enumerator returned nothing", and "the enumerator failed" were one value** — the third instance of the class this file exists to refuse, committed *inside* the fix for the first two. The marker was never wrong; there was no text to match against, and loosening it would have made the probe worse while making it pass.

**Fixed** with `YubiHsm2State` = `attached` / `absent` / `indeterminate` + `yubiHsm2CheckRan`, mirroring the `Tpm2State` vocabulary already in the same file rather than inventing a second one. `ioreg -p IOUSB` is now the primary enumerator (`system_profiler` is a formatter above IOKit, and the formatter is the layer that failed). `indeterminate` is **fail-closed** — it never clears `noHardwareDetected` and never offers a tier; it only changes what the operator is *told*.

**Verified on the live device:**

```text
  YubiHSM 2:          ATTACHED
                      (the check ran) a YubiHSM was named in the ioreg USB enumeration
  PKCS#11 pair:       /usr/local/lib/pkcs11/yubihsm_pkcs11.dylib drives YubiHSM 2
  Device present:     YES
  Honourable tiers:   hardware-pkcs11
```

First honourable hardware seal tier this repo has reported on real hardware. Still L1 — invariant 2 has not moved and no share has been sealed.

53 tests (was 40), **608 pass** across the persona-keys lane, **8/8 mutants killed**. Mutation found two further holes of the same shape after the first pass (an unavailable enumerator and an unlistable Linux USB tree, both roundable to `absent`); tests for both are in the suite now.

## Update: the checked answer on erase — a clean negative

Aaron asked whether erase can be protected even when `yubihsm-setup` is present, since an attacker can bring or reimplement a client binary. **He is right**, and the earlier recommendation was **hygiene presented as a control**. The note now states the distinction and files it correctly.

Checked against Yubico documentation:

- **Capabilities are enforced per session and cannot be escalated** — an auth key without `reset-device` cannot issue a reset. A genuine control **against a remote adversary**.
- **A physical reset bypasses authentication entirely** — press the metal rim while inserting, hold 10 seconds, all keys wiped. It exists *precisely* as the lost-auth-key recovery path, needs no credential or tool, and has no documented way to be disabled. Independently described by iqlusion's `tmkms`.

**So the capability model is a control against the remote adversary and provides zero protection against anyone with ten seconds of physical access.**

The reframe: this is **"destruction, not leakage" appearing as a vendor feature**, not a gap. The design already accepted destruction and refuses extraction. The goal is therefore not to prevent erasure but to make it **cheap** — threshold (a wipe costs one share) plus reshare-without-reconstitution. Sizing consequence recorded: **`n − k` is not spare capacity, it is the number of wipes the roster survives.**

Where capabilities *are* worth spending: they cannot stop erase and **can** stop export. The note lists what the operational auth key must not carry — `export-wrapped` first — with admin capabilities on a separate ceremony-only key.

Still detection and documentation only: no PIN, no auth-key change, no session, no key material.
