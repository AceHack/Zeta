## The genuinely open question

Every existing artifact describes a **repo-to-repo dependency pin**. Nothing describes an **actor-to-repo working set** -- which repos an agent holds, how it verifies them, what it does when one is stale. Those are different objects and conflating them is the failure the doc exists to prevent: the pin belongs in the repo (or builds are unreproducible), the working set belongs on the host (or one repo's checked-in list becomes authoritative over the others, which is an appointed hub).

Specified: host-local `peers.json`, canonical JSON via ace's existing serializer, content-addressed with ace's existing `blake3` identity, and a **five-state total resolution** -- `resolved` / `stale` / `diverged` / `missing` / `unverified`. `unverified` is deliberately not folded into `stale`: drift and substitution are different facts.

## The measurements disagree, and that is the design content

| Criterion | Selects | Evidence |
|---|---|---|
| DV2.0 change rate | telemetry/archive lane | 19,100 files, 57% of all 30-day file-touches |
| Actions cache | language | .NET 7.4 GiB, polyglot installer 7.5 GiB, cap 10 GiB, **currently 103%** |
| ruleset divergence (our own smell test) | telemetry lane | `heartbeat/*` already ruleset-disjoint |
| projects | civsim etc. | already executed; moves **neither** number |

They disagree because a repository is one mechanism serving three separable jobs: what is *stored* separately, what is *built* separately, what is *governed* separately.

## Honest limits, recorded not glossed

- The cache duplication is **per-ref, not per-content** (identical keys under different `refs/pull/*`). A split alone takes the worst repo from 103% to ~74%: necessary, not sufficient. The co-fix is a `gate.yml` cache-step change, independent of topology.
- If `install.sh` stays monolithic, a language split delivers **zero** cache relief.
- civsim -- the one executed split -- has **no ruleset, no CI, and a 10,075-commit-stale pin that nothing reads**. The gate was stranded once already.
