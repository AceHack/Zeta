## Description

081M08MVPR9087G0R000NCF8PV. pr-archive-on-merge.yml fetches review threads the instant a PR
closes; the automated reviewer posts its threads after that. The archiver wins the race, freezes
a wrong snapshot, and nothing ever revisits — so `| Total threads | 0 |` reads identically whether
it means "there were none" or "we looked too early". That is the vacuity class applied to the
review record itself: a check that did not run looking like one that passed.

RE-MEASURED FIRST (new instrument, audit-review-archive-capture-window.ts, which compares each
thread against the shard's `fetched_at` — when the archiver LOOKED — rather than `merged_at`,
when the event fired):

  n=150 uniformly sampled docs, seed 4
    doc-level under-report   30/150  = 20.0%   (filed 21% reproduces: 24/100 on its own arm)
    thread-level capture    191/257  = 74.3%
    fetchable capture       191/191  = 100.0%
    LOSS (thread existed at fetch time, not recorded)  0 of 150

The filed 21% holds. Its downstream READING does not: "captures 21 of every 100 reviews" is a
count of wrong documents, not of lost reviews. The archive keeps 74.3% of threads and 100% of
what was fetchable.

MECHANISM CONFIRMED, against the right clock. Zero loss against what was fetchable is what
excludes the alternatives, each of which would show up as loss: pagination (paginates with
`--paginate` + endCursor), an API cap (counts run 1-15), a permissions gap (same credential
reads them now), a parse bug (1,978 docs carry non-zero counts). The single LOSS in the
zero-arm is PR 2135, a 1.8-second margin — read-replica visibility lag, recorded as LOSS
anyway because the classifier takes the side that accuses the archiver.

The tail is also shorter than filed: 65 post-merge threads across the 2,000 most recent merges,
all from copilot-pull-request-reviewer, p50 +177 s, max +283 s. The filed +78 min came from a
period with a second reviewer.

FIX — a sweep, not a sleep. Only 55 of 1,997 recent merges (2.8%) ever acquire a thread, so
waiting out the tail on every merge would spend ~165 runner-hours/month to help 2.8% of runs,
and a fixed wait is correct only until the reviewer population changes — at which point it is
wrong silently. reconcile-review-archive.ts re-archives when the live count exceeds the recorded
count, which is correct for any tail and idempotent once they agree.

  --write  bounded sweep in agent-heartbeat.yml soraya archive duty (48h, --limit 5, oldest-first)
  --check  guard in pr-manifest-integrity.yml (scheduled; reports rather than fails on a PR)

Two properties keep it from becoming theatre. It can only ADD: a re-archive is a whole-file
rewrite, so the new count is re-read and the previous bytes restored if it went down (§5 — this
tool cannot lose a thread it already had). And `--check` refuses a verdict without a POSITIVE
CONTROL — a doc with a recorded, nonzero count that still matches GitHub — because 97% of merges
here never acquire a thread, so "everything agrees" is also what a totally broken archiver
produces. No control means exit 2 INCONCLUSIVE, never 0.

THE DEMONSTRATION FOUND A DEFECT IN THE FIX. Doctoring PR #10367 from 12 threads to 0 and running
`--check` produced a PASS. The draft enumerated candidates with `gh pr list --state merged` and
filtered by merge time — but that listing is ordered by CREATION, and #10367 was created four days
before it merged, so it fell off the end. The coverage test then compared the oldest listed
mergedAt against the window and reported "fully covered". A scan returning success while dropping
rows is the same family as the bug being fixed. Now enumerated from the archive docs joined to
their PR shards: complete by construction, no cap, no ordering assumption, zero API calls. On the
same 72h window the listing scan saw 0 thread-bearing docs; the archive scan sees 57.

Falsifier: 46 tests, 29/29 mutants killed. `--check` exits 1 on the doctored archive naming
PR #10367, exits 0 on the real one with an in-window control.
