## Description

## What

A comparison of **TPM 2.0 vs YubiHSM 2 as root of trust**, written as an explicit delta against
[#12178](https://github.com/Lucent-Financial-Group/Zeta/pull/12178) rather than as a second survey.
Prompted by Max joining the k8s and hardware-USB work on a machine that *probably* has a TPM and no HSM.

`docs/research/2026-08-18-tpm-2-0-versus-yubihsm-2-as-root-of-trust-the-isolation-architectures-are-inverted.md`

**Analysis and documentation only** — no TPM session opened, no key created or used, no ownership taken,
no device probed. **Max's machine was not accessed and no access was sought.** The TPM presence there is
*"probably"*, unverified, and is treated throughout as a relayed capability fact, never extended.

Used the repo's existing five-way `Tpm2State` probe as the starting point, as instructed. **No new probe
was written and `tools/setup/` was not modified.**

## The answer — a clean negative

> The two devices have **opposite** isolation architectures. The YubiHSM 2 has a *shared,
> unauthenticated path* to a device that enforces *per-caller partitioning*. The TPM 2.0 has a
> *kernel-enforced per-caller path* to a device that enforces **no per-caller partitioning at all**.

**The TPM has no tenants.** No domains, no caller identity, no notion of who is asking — its access
control is per-*object*, so isolation between tick sources rests on secrets each container holds. That is
credential isolation, the L1 rung, and the device does not help. It is an excellent root of trust *for a
machine*; it is not a multi-tenant key store and was never specified as one.

## The two sub-findings worth reading separately

**The session-starvation finding does not transfer — and saying so precisely is the point.** The
in-kernel resource manager genuinely *virtualises*: TPM spaces give "an isolated execution context for
transient objects and HMAC and policy sessions" per file descriptor. #12178's `YH_MAX_SESSIONS = 16`
result is retired in that form; a leaking tick source now leaks into its own space. **Real advantage.**

**It is replaced by a worse one.** The global dictionary-attack lockout needs **no credential** — only
the ability to *fail*, 32 times — **cannot be cleared by the victim** (a success does not reset it, by
correct design; only the owner/lockout auth can, which is the same standing device-wide weight #12178
flagged, on different silicon), and has an **accidental trigger unrelated to authorization**: a systemd
user reported sealed storage failing to open after three power cycles. The TCG's own guidance concedes
*"lockout of all TPM use could make the system unstable."* `noDA` closes the accidental path, not the
adversarial one.

## Also in it

- **PCRs cannot distinguish one container from another.** Non-resettable PCRs measure the *host*,
  identically for every tenant; resettable ones are resettable by anyone. So the **L3 rung of the
  code-bound-key-access ladder is unreachable per-container on a shared TPM** — not expensive, as that
  note assumed, but structurally absent, because the measurement has no per-container component.
- **The physical tier inverts the usual intuition.** A soldered chip feels safer than a USB stick you can
  pull out; on the evidence it is the opposite. The HSM's cheap physical attack **erases**; the TPM's
  cheap physical attacks **extract** — dTPM bus sniffing (~$300) and faulTPM on AMD Zen 2/3 (~$200,
  arXiv:2304.14717), the latter recovering anything sealed *even with PCR policy and anti-hammering in
  place*. Destruction is already priced at n−k wipes; extraction is not priced at all.
- **Software TPMs solve tenancy and root nothing new.** A vTPM per microVM makes the global-state list
  per-tenant, at the cost of a VM per tick source. The limit is exact: it is a root of trust for the guest
  against *other guests*, never against the *host*, because its state is a file the host owns and its EK
  is not manufacturer-certified. **Adds a tenancy boundary; adds no trust root.**
- **Docker limitations between AIs.** On the Mac Studio a container can reach *neither* device — no USB
  passthrough for the HSM, and no TPM on Apple Silicon to pass through. On Max's box
  `--device=/dev/tpmrm0` works natively, but the grant is **binary**: it grants the whole TPM, and there
  is no merged TPM namespace to make it otherwise. The fleet cannot have one root of trust.
- **Vacuity analysis carried across unchanged**, plus a trap the TPM adds: **during DA lockout every
  attempt returns an error**, so a cross-access test run inside a lockout window reports total isolation
  while proving nothing. Five of six discriminating checks need no hardware — a higher proportion than
  the HSM's four of six, because more of the TPM's isolation story lives in configuration.

## Verdict

For Max's machine as a node: probe it with the existing five-way probe and record the result; a TPM is
worth having for what a TPM is for. For *agents on one machine cannot reach each other's keys*: a shared
TPM is **worse** than the shared HSM. Three routes forward, none of them "put the keys on the TPM and
share it" — vTPM per microVM, one device per trust domain (#12178's T5, unchanged), or a TPM as the
*machine's* root of trust with something else as the *agent's* key store.
