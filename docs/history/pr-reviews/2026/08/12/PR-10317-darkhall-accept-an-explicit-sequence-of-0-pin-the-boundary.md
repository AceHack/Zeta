## Description

Live heartbeat finding (otto, tick 11223): `gte-to-gt` on `darkhall-browser-page.ts` read INDISTINGUISHABLE UNDER SUITE. A genuine test gap, same shape as the ferry-throttler one in #10310.

## The guard

```ts
Number.isSafeInteger(sequence) && sequence >= 0
```

The suite exercised `sequence=12` (accepted) and `sequence=-1` (refused) — both stay on the same side under `> 0` — and omitting the parameter never reaches the check at all, since a null value returns 0 early.

So **0, the legitimate starting sequence for a fresh page**, was the only value separating `>=` from `>`, and nothing exercised it. Relax the guard and a fresh page gets refused with "must be a non-negative safe integer".

Test added at the boundary, asserting the presence broadcast actually carries `sequence: 0` rather than merely that startup succeeded.

## Worth recording

The first draft of this test **failed on unmutated code**, and the reason was not the guard — it was `page-database-start-failed: This runtime does not expose IndexedDB`, because the happy path needs both `databaseIntentOutbox` and `databaseExecutor` injected.

Had I read that red as "sequence=0 is rejected, I found a bug", the report would have been confidently wrong in the more embarrassing direction. Printing the actual result instead of inferring it from the failed assertion is what separated a harness mistake from a defect.
