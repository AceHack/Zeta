## Description

> Aaron: *"we should show the drift between configured and observed."*

The step already compared one gap against the declared 900s — enough to catch a stalled tick, not enough to see the actual condition: the society has been running at roughly a **quarter** of its declared cadence for hours, and a single-gap reading can't tell that from one late tick.

Now it reports the **median over the last 10 gaps**, how many exceeded 2x, and warns on *sustained* drift specifically. One late tick is weather; a median sitting far from the declared cadence is climate — measured over a window so a lone outlier can neither raise the alarm nor silence it.

## Measured on real committed event data before shipping

Inline workflow Python is exactly the thing that ships broken — this file's own comments record #9890 and #9898 doing so:

```
[cadence] otto: gap=4489s (74.8min) declared=900s actual=20.0% of target
[cadence] otto: DRIFT over last 10 ticks — median=62.6min vs declared 15min = 4.2x slower; 9/10 over 2x
```

So the number is stated rather than asserted: **4.2x, sustained, 9 of the last 10 ticks.** The workflow is `active`, so this is GitHub throttling scheduled runs, not a stopped tick.

## Why it matters beyond tidiness

Every rate this apparatus computes is *per tick* — the false-alarm denominator, the findings ledger, the DORA folds. While the declaration says 15min and reality is ~63min, **all of them silently mean something other than they say.** The drift line makes that visible at the point of measurement instead of leaving it to be rediscovered.

## Deliberately not done here

Adding a second scheduled workflow to fish for more triggers. Three agents already tick in one matrix and the flush/push path is shared; a second overlapping schedule risks concurrent ticks racing that path, and GitHub throttles per-repo anyway — so it may buy nothing while introducing a real race. Worth trying only with the concurrency group examined first. Flagged rather than taken.
