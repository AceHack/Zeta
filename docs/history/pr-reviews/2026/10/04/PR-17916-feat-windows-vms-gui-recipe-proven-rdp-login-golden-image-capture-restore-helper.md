## Description

## What

The owner asked to drive `win11-desktop`'s GUI end to end (Open Dental, the Flowdent API) and to capture its disk afterwards for reuse.

* **GUI**: `docs/ops/WINDOWS-11-VMS.md` "Using the desktop (RDP/VNC from a Mac or Windows)". Every command runs as `ssh zeta@ssh.flowdent.net '...'`: the password to the Mac clipboard (`pbcopy`, never shown), the tunnel (ClusterIP looked up on the node, local port 13389), Windows App / mstsc settings, and a VNC console bridge through `ncat` in the launcher's `compute` container (the node has no `virtctl`).
* **`windows-11-rdp-check.ts`**: a real RDP login from a throwaway pod (FreeRDP `/auth-only`), password on stdin only, output scrubbed.
* **Golden image**: `windows-vm-golden-image.ts` (one file, Node built-ins only; the node has Node 24 and no bun) with `guard | capture | restore | selftest`, and `docs/ops/WINDOWS-VM-GOLDEN-IMAGE.md`.
* `40-network-policy.yaml` selects guests by `zeta.io/windows-role` so a restored desktop is fenced from its first minute (**git only, not applied live**).

## Proven live (2026-10-04, against the real cluster; `win11-ci` and `win11-desktop` untouched)

* NLA login as `zetaadmin` **accepted**; TLS-only refused `HYBRID_REQUIRED_BY_SERVER`; legacy RDP layer reset; `UserAuthentication=1`.
* The exact tunnel one-liner answered with an RDP connection confirm (NLA) through `ssh.flowdent.net` and `192.168.1.79`; the VNC bridge delivers `RFB 003.008` (security type None).
* Guest ports: listens on 22, 135, 445, 3389, 5040, 5357, 7680 + RPC range; reachable from a pod: **22, 3389, 5040, 7680** (so not "only 22 and 3389"; 5040/7680 are Windows in-box, behind the network policy).
* `selftest --with-vm` **passed** (2Gi stand-in, then deleted; PV list, Longhorn volumes and quota identical to before): default CDI clone path is 2x quota, `usePopulator:"false"` is 1x and is the helper's default; full sha256 identical and sparseness preserved; restore is a clone of the golden and the pattern reads back through a pod; KubeVirt adopts a pre-made `persistent-state-for=<vm>` claim; TPM+NVRAM carry only to the same name + `firmware.uuid`; `capture` against a RUNNING stand-in with `runStrategy: Always` stops it, snapshots, clones, verifies and restarts it.
* `guard --vm win11-desktop --with-state` (read-only, on the node under Node 24): a capture fits (307.4 of 400 GiB; the 106 GiB claim really occupies 19.4 GiB); the populator path does not (413.4 > 400); a restore next to the golden or a third running guest does not fit (storage / memory quota).
* Restore manifests pass `kubectl apply --dry-run=server` (this caught a missing `kind`, now tested).
* Longhorn snapshot deletion still hangs (reproduced; the finalizer removal is documented).

## Not proven (stated in the runbooks)

A human watching a real client (resolution, clipboard, audio); booting a clone of the real, in-use Windows disk; a renamed restore carrying the TPM; `sysprep /generalize` and its first-run screens (the repo's `Unattend.xml` has no `oobeSystem` pass); the Mac client menu names (no Mac here); VNC in a real viewer. **`C:` is BitLocker-encrypted with protection Off**: read step 2 of the golden-image page before capturing. No off-node target exists; the page recommends Azure Blob with a scoped token and does **not** use or write to it.
