## Description

## What and why

Measured 2026-10-05 on `node-5b2dfa`: the 119 GiB root held the k3s container store (`/var/lib/rancher/k3s/agent/containerd`) at **48 GiB**
(132 images, 534k entries) at 22 GiB free, swinging 16-36 GiB while CI ran. The kubelet evicts every pod, production included, near
17.7 GiB free. The two Longhorn data disks beside it (797 + 916 GiB) were ~88% free.

Work item `081M44HD9T2087G0R000G9NR1N`. Runbook: `docs/ops/CONTAINERD-ON-BIG-DISK.md`.

### 1. Installer (the main change)

* `zeta-install.sh` Step 6.64d writes `/etc/zeta/containerd-data-disk` = the **largest mounted `/var/lib/longhorn-disk*` of >= 200 GiB**
  (same rule as `local-storage-placement.sh`). Below that nothing is written and the store stays on root (a QEMU lane's 1 GiB tail).
* `nixos/modules/containerd-on-data-disk.nix` (imported by `common.nix`): a `systemd.mounts` bind of `<disk>/containerd` onto the store
  path; `k3s.service` `Requires=` it, has `RequiresMountsFor=` it, and its **first `ExecStartPre` asserts it**. Absent file = module inert.
* **Failure mode, chosen on purpose: fail closed.** A missing disk / directory / wrong source keeps k3s down, with the remedy in the message,
  because the alternative is silent: k3s recreates an empty store on root and re-pulls every image onto the disk this protects.
  A populated root store with an empty disk directory is also refused (a mount would hide 48 GiB).
* The ordering is on this module's own units because `k3s-wait-for-address.nix` does `systemd.services.k3s.after = lib.mkForce [...]`,
  which would silently discard an `after` added here. Only an evaluation of the resolved host shows that, hence the eval test.
* Longhorn: no setting changes (measured: the store consumes `storageAvailable`, 872 -> 821 GB against a 246 GB floor; the installer's
  capacity check already discounts 25%). `/var/lib/kubelet` (2.6 GiB) deliberately not moved. Both documented in the runbook.

### 2. Live-node cut-over kit (prepared and tested, **not executed**)

`full-ai-cluster/scripts/move-containerd-to-data-disk.sh`: `preflight`, `precopy` (online, `--bwlimit`, aborts on DiskPressure), `build`
(builds the generation, **proves** it declares the mount, prints the unit delta), `cutover` (cordon, graceful app-pod delete + Longhorn
detach, stop k3s, kill k3s's own containerd, final rsync + verify, bind, switch, start, image-count guard), `verify`, `reclaim` (device-guarded),
`rollback`, `launch` (detached transient unit). `--dry-run` everywhere.

**Findings that changed the plan (all read from the live node):** `/etc/nixos/configuration.nix` is NOT what the node runs (a rebuild
there would have switched it to stock NixOS with no k3s) -- the persistent change goes through `/etc/zeta/full-ai-cluster#control-plane`;
`/etc/zeta` is a dirty clone 63 files behind `main`, so only this change is applied; `KillMode=process` means stopping k3s leaves every
container running and k3s's containerd is the k3s binary re-exec'd (Docker's two `containerd`s must not be touched); `kubectl drain` can
never finish on one node (PDBs allowed=0); ionice is a no-op on NVMe `none`; there are 2 running Windows VMs (330 s grace) and a bare CI pod.

## Tests

* `lint-containerd-store.test.ts` -- executes the guard and the installer's disk choice (39 tests; mutation-checked).
* `lint-containerd-move.test.ts` -- the kit against a stubbed world: refusals, the pre-copy loop, the order of the window, every rollback
  path, the dry-run promise, Docker's containerd never signalled, the reclaim device guard (62 tests; mutation-checked).
* `containerd-on-data-disk-eval-test.nix` + flake check `containerd-on-data-disk-eval` (added to the CI eval-only list).
* Run for real on the node's own nixpkgs (read-only/unactivated): the eval test held 26/26; the node's real config + this change built
  in 8.4 s and differs from the running system in only the new units; the script's `preflight` and `cutover --dry-run` ran as root on
  the node (41.5 GiB to copy, 140 pods / 39 volumes / 2 VMs identified).
* One existing test adjusted: `storage-profile-shell-parity.test.ts` extracts Step 6.64c up to the next step, which is now 6.64d.

## NOT proven

The cut-over has **never been executed** on a node; `k3s-killall.sh` on this NixOS, the unmount of ~830 mounts, `switch-to-configuration`
with the new unit, k3s on a bind-mounted store, the systemd ordering on a real boot, sustained disk write speed and pod start times
(hence the 12-20 min estimate) are unmeasured. Hence: no auto-merge; the runbook has go/no-go conditions and a reboot test before `reclaim`.
