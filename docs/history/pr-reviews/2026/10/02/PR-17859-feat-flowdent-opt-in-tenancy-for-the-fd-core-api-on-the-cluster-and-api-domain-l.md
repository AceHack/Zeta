## Description

## What

Cluster side of running the flowdent `fd-core` API (ASP.NET, today on Azure Container Apps) on this cluster, deployed by the application repo's own GitLab pipeline. Two independent pieces, **nothing that already runs changes**:

1. **`k8s/public-tls/`** — `api.<domain>` and `api-staging.<domain>` become Gateway listeners 5 and 6 of `zeta-public-gateway`, each with its own certificate Secret, exactly as `git.<domain>` is listener 4 (template patch + base listeners). No route is owned here (the HTTPRoutes ship with the app) and **no DNS record is created; `api.flowdent.net` still resolves to Azure**.
2. **`k8s/flowdent/`** — OPT-IN tenancy, outside `k8s/applications/` so the app-of-apps root never sees it and no catalog ledger moves. An operator applies one Application once. It owns: namespaces `flowdent-staging`/`flowdent-prod` (+ ResourceQuota ceilings), two CNPG `Database` CRs on `postgres-shared` with one owner role each, a create-only Job that mints the passwords in tmpfs and writes the role Secret and the app Secret `flowdent-db` (Npgsql connection string) in one act, and a least-privilege namespaced `flowdent-deployer` ServiceAccount + token Secret per environment for GitLab CI.

Runbook with the exact human steps: `docs/ops/FLOWDENT-ON-CLUSTER.md`.

## Why it is shaped this way

- CNPG requires a managed role, its Cluster and its `passwordSecret` in one namespace (documented in `POSTGRES-SHARED-AS-THE-DATABASE-FOR-OTHER-APPS.md`), so the credential is born in `postgres-shared`; the Job writes the app-namespace copy in the same act so the two cannot diverge at birth.
- Listeners were put in the install-time template (the `git.<domain>` precedent) rather than an overlay: a Gateway's listeners are one object owned by one Application. Cost stated in the runbook: two idle listeners + pending certificates on public-domain installs until DNS exists.
- Not under `applications/`: adds no pod/PVC to any ledger (databases live on the existing 20 Gi volume).

## Proof, and its limits

- `cluster/flowdent-platform.test.ts` (32 tests): opt-in boundary, RBAC isolation (no ClusterRole, no wildcard, deployers identical modulo namespace, secrets `create`-only unrestricted), role/Database/Secret wiring, no password literal, create-only, listeners 5/6 with own certs and earlier listeners unmoved, `postgres-shared/cluster.yaml` has no `managed` block (the Job's merge patch would replace it).
- The Job's `draw-entropy` script was run in the pinned busybox image under `--read-only`, uid 1001: 64-hex passwords, distinct per environment, 0600 files, correct Npgsql string.
- kubeconform (v0.7.0, the gate's flags, k8s 1.35.6) on `k8s/flowdent`: 20 valid, 0 invalid, 4 skipped (CRDs).
- **NOT proven here**: nothing was applied to a live cluster (no cluster-admin from this session). A CNPG role actually being created, certificates issuing, and the deployer token working are all human-step verifications listed in the runbook.
- `local-checks.ts`: the changed-file checks that apply pass; failures are environment ones on this Windows box (no go/z3/uv/dotnet-format) and `lint-graphql-transport-in-scripts` findings in files this PR does not touch.
