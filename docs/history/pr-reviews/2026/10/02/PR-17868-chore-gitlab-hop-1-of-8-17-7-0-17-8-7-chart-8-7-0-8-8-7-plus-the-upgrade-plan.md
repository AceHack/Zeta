## GitLab upgrade, hop 1 of 8: 17.7.0 -> 17.8.7 (chart 8.7.0 -> 8.8.7)

First required stop on the path to 19.4.1 (`config/upgrade_path.yml` in gitlab-org/gitlab). Full plan, rationale,
per-hop procedure and rollback: `docs/ops/GITLAB-UPGRADE.md` (added here).

- `targetRevision: 8.7.0 -> 8.8.7`. 17.8.7 rather than 17.8.0: 17.8.0-17.8.6 can empty `ci_runner_taggings`
  when upgrading from 17.5+ (gitlab issue 524402, fixed in 17.8.7) and this instance's one runner carries tags.
- Rendered with the Application's own values at both pins: the same 21 images with the version tag moved
  (webservice/sidekiq/toolbox/workhorse/gitaly/shell/kubectl v17.8.7, registry v4.14.0 -> v4.15.2,
  exporter 15.0.0 -> 15.2.0, runner alpine-v17.6.0 -> alpine-v17.8.3); the bundled postgres/redis images are unchanged.
- Two cluster tests assumed the pin they were written against and would have gone red for a reason that is not
  the code under test: `gitlab-upgrade-path-guard.test.ts` read the FROM-pin of its fixtures from the Application
  (now frozen at 8.7.0); `gitlab-exposure.test.ts` (e) pinned chart 8.7.0's duplicate gitaly `TZ` env, which 8.8.7
  no longer renders (measured).
- Backups were taken and verified before this PR (off-repo, `~/.zeta/backups/2026-10-02-gitlab-upgrade/`).

Merging this IS the upgrade: ArgoCD syncs it, the migrations Job runs, GitLab is unavailable for the minutes the
rollout takes (webservice/sidekiq/registry are single-replica, maxSurge 0). The guard
(`gitlab-upgrade-path-guard.ts`) prints PASSED for this bump locally.

Not proven by CI: that the live cluster comes up healthy. That is measured on the node after the sync and recorded
in `docs/ops/GITLAB-UPGRADE.md`.
