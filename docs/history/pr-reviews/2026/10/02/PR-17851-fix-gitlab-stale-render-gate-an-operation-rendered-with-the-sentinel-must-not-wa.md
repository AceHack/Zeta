## Description

## Why (follow-up to #17846, which merged before this commit reached it)

#17846 fixed the permanent OutOfSync (stable migrations Job name + Force/Replace + PostSync GC; lane checks a6/a7 blocking). Its own lane run (36951220893) then measured a second defect that the fixed name unmasked: with no early failure to trigger an ArgoCD retry, an operation **rendered with the `192.0.2.250` sentinel before the install-time pin landed** reached wave 20, created the Gateway with the sentinel, and waited on `Gateway/gitlab-lan` for 27 minutes with the pin long landed -- Application Progressing for ever, GitLab unreachable on the LAN. Four earlier lane passes on the same timings escaped only because an unrelated failure (HPAs with no metrics yet) made ArgoCD retry the operation, and a retry re-renders from current values. So #17835's "exposure last" was luck, not a fix, and merged `main` is exposed to it on a fresh install.

## Fix

`Job gitlab-pin-fresh` -- Sync hook, wave 15 (after the runner, before exposure): compares the address THIS operation rendered with the Application's current `global.zeta.lanAddress` and exits 1 when they differ, so ArgoCD retries on purpose, from current values. Equal passes (including both-sentinel: an install with no LB range, where exposure honestly stays pending); an unreadable read does not gate (unknown is not stale). RBAC: `get` on `applications/gitlab` only.

## Tests

`gitlab-exposure.test.ts` (i): the gate sits between the runner (10) and every exposure object (20), has exactly that Role, and the Application's retry is unbounded; and the rendered script is **executed** under bash against a stub `kubectl`: stale -> exit 1, current -> 0, both-sentinel -> 0, unreadable -> 0 "NOT gating". The lane (`gitlab-live-proof`) runs on this PR; its blocking a6/a7 and a-f must pass.
