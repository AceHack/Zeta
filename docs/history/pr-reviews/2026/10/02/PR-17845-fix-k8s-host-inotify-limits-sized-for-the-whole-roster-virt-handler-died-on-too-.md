## Description

## Measured failure (owner's real node)

node-5b2dfa, NixOS from the 2026-10-01 ISO, ~9 min after first boot, 150+ pods: kubevirt `virt-handler` in CrashLoopBackOff with a fatal `Failed to create an inotify watcher ... reason: too many open files` (pkg/certificates/bootstrap/cert-manager.go:105). That is the host-wide per-user `fs.inotify.max_user_instances` pool (kernel default 128) exhausted by the roster's watchers.

## Change

- `full-ai-cluster/k8s/node-tunables.json` (the single declaration read by the NixOS module and the CI runner step): `fs.inotify.max_user_instances` 512 -> 8192; `fs.inotify.max_user_watches` 524288 -> 1048576 (kernel dynamic-clamp top; ~1 KiB kernel memory per watch actually created, documented). Documented the checked-and-unchanged set: `fs.file-max`, `fs.nr_open`, k3s `LimitNOFILE=1048576`, systemd `DefaultLimitNOFILE`, `vm.max_map_count` (524288 already). All kubevirt components share the same host pool; no separate virt-launcher knob.
- `first-boot-replica.yml` (both jobs) now applies node-tunables before booting the roster (they previously did not, so could not reproduce this class).
- `first-boot-replica.ts`: crash-loop and stage-6 failure diagnostics grep for the host-limit signature and print a pointer at the declaration.

## Falsifiers
Red against HEAD's json/workflow, green with this (4 tests verified red): inotify floors and a per-job "applies node-tunables before booting" parity test in `node-tunables.test.ts`; `hostLimitExhaustionNote` tests; floors added to `k8s-node-tunables-eval-test.nix` (not evaluated locally -- no nix here).

## Unproven
Whether the failing ISO already carried 512 or predated the module (live sysctl not captured); that 8192 suffices (judgement, no per-pod census). Needs a reflash.
