## Description

## Why
The owner's logged-in GitLab dashboard (`GET /`) returned 500. Cause (measured): GitLab reads a user avatar (`/gitlab-uploads/user/avatar/<n>/duo-bot.png`) from this SeaweedFS and gets S3 `InternalError`. The master log says `automatic volume grow failed: Not enough data nodes found!` for collection `gitlab-uploads`. With `-volume.max=0` (auto) and `volumeSizeLimitMB: 1000` the single volume server computed **Max 40 slots and all 40 were used** (SeaweedFS pre-grows 7 volumes per collection; six collections exist), so the seventh collection, `gitlab-uploads`, could never get a volume. It first became necessary when a GitLab upgrade created the Duo bot users and their avatars.

## What
In all-in-one mode `-volume.max` is read from `volume.dataDirs[0].maxVolumes` even though the volume Deployment is disabled. Set it to **100**. Slots are reserved capacity, not disk (real total ~2.5 GB on ~35 GB free). `helm template` before/after at 4.45.0: the only rendered change is `-volume.max=0 -> 100` (the SFTP secret differs every render; the Application already ignores it).

## Important
The GitLab upgrade agent found the same cause independently and applied **100 live** at 23:08Z (SeaweedFS restarted once for it) via an `ignoreDifferences` pointer on live `zeta-root`. This PR makes git say the same, so **merging it does not restart SeaweedFS again**. After it merges, that live `ignoreDifferences` pointer for `seaweedfs` can be removed.

## Proven
Live: `s3cmd` put/get/delete on `gitlab-uploads` works, 0 HTTP 5xx in the GitLab webservice log for 15 minutes, `weed shell volume.list` shows 40/100 used (agent's measurement). Not proven: a CI check for this value.
