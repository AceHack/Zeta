## Description

## What

The console password when none is typed at the installer is now an explicit install-time policy, `ZETA_CONSOLE_PASSWORD_POLICY=default|mint`. **The repo default is `default`: the PUBLIC `zeta-change-me`. That is the repo owner's decision**, made after the one-time password minted by #17796 scrolled off the console of a real node and left the owner unable to `sudo` on their own machine. `mint` (#17796's behaviour) stays, as the explicit opt-in.

- `zflash --console-password default|mint` on the macOS/Linux device path, the file-backed/Linux bake path and the Windows flasher, through the shared planner -> ESP `/zeta-firstboot.conf` -> exported by `zeta-first-boot.sh` -> resolved in `zeta-install.sh` **before the wipe** (an unknown value refuses, nothing wiped). `--dry-run` (Windows) names the policy even when the flag is omitted.
- A password TYPED at the installer prompt always wins.
- Policy `default`: sha512crypt of the public password (stdin, never argv), marker `/etc/zeta/initial-password-default`; **no lock, no mint**; loud banner on stdout + `/dev/console` + `/dev/tty1`, repeated in the install-complete summary; applied ONCE via the existing state file so a later `passwd zeta` is never reverted; a `zeta-default-password-reminder` service + timer and a login-shell snippet remind until the shadow hash changes.
- SSH `PasswordAuthentication = false` is unchanged (asserted).
- The ISO's own conf never carries the policy.

## Risk (also in the decision record, INJECTION-POINTS section 3, INSTALL-TIME-CONFIG row 19)

Under `default`, anyone with console access is root via `sudo`. Physical-access threat model; do not use on exposed hardware. `zflash --console-password mint` restores the safe behaviour.

## Proven vs not

Proven (tests that fail without this change): policy parser/renderer; the flag on all three flasher paths and the shared planner (conf line, junk refused, `--no-inject` contradiction); the shell resolver vs the TS oracle; every branch of the REAL Step 6.55 executed under bash (typed wins x3 policies / default / mint / mint-locked / mkpasswd failure / invalid policy refuses loudly), exact file sets, password on stdin not argv.

Not proven: no nix on the authoring machine. The Nix activation branch, the reminder service/timer and `interactiveShellInit` are checked by reading their text only; nothing was evaluated or booted. First real exercise is a NixOS build plus an install.

Local `local-checks` failures on this machine are environmental (no go/python3/dotnet, `/bin/bash` missing, network) or pre-existing on main (the graphql-transport lint sites are other files); the one that was mine (R5 absence assertions) is fixed.
