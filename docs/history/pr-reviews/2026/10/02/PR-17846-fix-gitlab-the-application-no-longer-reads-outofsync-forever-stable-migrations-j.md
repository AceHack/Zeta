## Description

## Problem (measured on the owner's real node, 20:53 after first boot)

`gitlab OutOfSync/Healthy`, with two Completed migrations pods: `gitlab-migrations-39fcdbd` (11m) and `gitlab-migrations-52e7f78` (4m). The chart suffixes its Job names with a hash of the chart version and **every** value (`gitlab.jobNameSuffix`); the install-time address pin re-renders the Application, so the Job is renamed; `prune: false` keeps the old one as a live-only "requires pruning" resource for ever. The live-proof lane measured the same (informational check a6).

## Fix (least risky of the three options)

1. `global.job.nameSuffixOverride: zeta` -- the chart's own documented Argo CD answer: the name stops depending on the values (also stabilises the `gitlab-shared-secrets` hook Jobs).
2. `argocd.argoproj.io/sync-options: Force=true,Replace=true` on the migrations Job (`gitlab.migrations.annotations`). A Job's pod template is immutable, so a fixed name would otherwise turn the next values/image change into `field is immutable`; Force+Replace recreates it, which is the chart's intent for the hash ("run again whenever GitLab changes").
3. PostSync Job `gitlab-migrations-gc` removes leftovers (by label `app=migrations`, never the current name; Role = jobs get/list/delete only; non-blocking) -- what the owner's node needs, since the already-orphaned Jobs have no desired twin.

Rejected: `prune: true` on a data application (gitaly/postgres); per-resource exclusion (cluster-wide ArgoCD config); making migrations a hook on its own (does not clean the Jobs that already exist).

## Tests

- `gitlab-exposure.test.ts` (h) x2 -- red against the unfixed Application (verified), green with it: the migrations Job name is identical across the address pin and an unrelated values change; carries Force+Replace; the GC keeps exactly the name the chart renders and has no more RBAC than that.
- `gitlab-live-proof.ts`: a6 is now BLOCKING (the Application reaches Synced+Healthy after the pin's re-render, no leftover Job); new blocking a7 plants a stale tracked Job in the shape the owner's node had, then patches the Application so the migrations Job's pod template changes -- asserting the sync still succeeds (no immutable-field error), the Job is actually replaced, the stale Job is GC'd, only `gitlab-migrations-zeta` remains, and the Application stays Synced+Healthy for 120 s. The runner/token/exposure checks (#17763/#17835) are untouched and run in the same lane on this PR.

The cluster tracks main, so this reaches the live node without a reflash; the GC cleans its two stale Jobs on the next sync.
