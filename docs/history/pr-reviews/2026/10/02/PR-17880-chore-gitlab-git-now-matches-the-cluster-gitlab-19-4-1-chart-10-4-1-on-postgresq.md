## GitLab 17.7.0 -> 19.4.1 is DONE on the cluster; this makes git equal what is live

The upgrade ran hop by hop on the live `gitlab` Application (fast path chosen by the owner; ~50 min of CI per hop was the
bottleneck). GitLab is on **19.4.1 (chart 10.4.1)**, PostgreSQL 17.11 (CloudNativePG) and Valkey 7.2.14, all 337 batched background
migrations finished, 9 projects with every default-branch SHA equal-or-descendant of the baseline, clone + registry pull + registry
push + runner pipeline verified. `docs/ops/GITLAB-UPGRADE.md` has the path, the measured per-hop log, the backups, the rollback and
the findings.

What this changes in git: `targetRevision` 8.11.8 -> 10.4.1; `global.psql` / `global.redis` pointed at the dedicated datastores and
the bundled `postgresql`/`redis` blocks (four `bitnamilegacy` images) removed; chart-10 values (`installCertmanager`,
`global.gatewayApi` off, toolbox backups -> `gitlab-backup-s3cmd`, derived from `zeta-blob-store` by a Sync-hook Job); the ledgers
and tests that follow the pin (`reason-truth`, `inert-valuesobject-keys`, `essential-priority`, secret-production acknowledgements,
the upgrade-check docs URL); the doc. The live Application spec was compared to this file: identical except the three install-time
pinned leaves and `helm.parameters`, which `zeta-root` already ignores.

**Merge this before anything removes the live `zeta-root` ignoreDifferences for `gitlab`**: with them removed and git still at 8.11.8,
root selfHeal would try to downgrade the Application against a 19.4 database.

Not here: the SeaweedFS `-volume.max` fix (its volume slots were exhausted, which made `GET /` 500 for a signed-in user once 19.x
created its Duo bot; fixed live, repo change tracked separately).
