## Description

## What

The GitOps-first path for Windows CI on the cluster. Opt-in; nothing is applied by a fresh install; Windows is never shipped or downloaded (the operator supplies the image and licence).

- `k8s/examples/gitlab-windows-runner-token.yaml` — Job that mints a runner record tagged `windows,zeta-windows`, `run_untagged: false`, via the same in-cluster Rails call as the Linux runner (no admin PAT), into pre-created Secret `gitlab-windows-runner-token`. Patches one named Secret, cannot create Secrets, fails loud, rejects Ruby injection; the same Job with different env mints any extra runner.
- `k8s/examples/kubevirt-windows-gitlab-runner.yaml` — Halted VM, sentinel image URL, virtio-win CD, labelled Secret/ConfigMap/sysprep CD-ROMs, cloudbase-init config drive; `bootstrap.ps1` downloads gitlab-runner.exe (version + sha256 pinned, verified before it runs) and registers by auth token. Lives in the `gitlab` namespace beside the token Secret. Placed outside `k8s/applications/` for the reason `kubevirt-windows-vm.yaml` is.
- `kubevirt-vm-live-test.ts` — the live lane's server-side dry-run now judges both new files.
- `gitlab-windows-runner.test.ts` — disjoint tags / one untagged taker (read from both sources), token Job script executed against a stub kubectl, guest spec consistency, runbook drift.
- `docs/ops/WINDOWS-GITLAB-RUNNER.md` — runbook, how to add any extra runner without a reflash, honest proven/unproven section.

## Free by default: Microsoft evaluation media

Windows Server 2022/2025 Evaluation (~180 days, no key) is the documented default image; Windows 11 Enterprise Evaluation (~90 days) the alternative. A human downloads the ISO from the Microsoft Evaluation Center (terms and registration are theirs; the repo links only the landing page) and supplies it by an HTTP URL they host or `virtctl image-upload --no-create`. The VM installs itself via Autounattend.xml (no product key; the Administrator password is rendered from the environment into a Secret by `windows-runner-unattend-secret.ts`, never committed). An in-guest watchdog reports the evaluation clock and never rearms; a reboot/rearm/expiry shutdown keeps the same runner. The runbook has a plain Limits section (expiry, hourly shutdown, finite rearm, evaluation-only terms, OEM licence not movable into a VM).

## Proven vs unproven

Proven: the offline tests (mutation-checked); the server-side dry-run in the `live-kind-virt` job (spec validity only).
Unproven: no Windows image exists in CI, so the unattended install, driver load, guest boot, bootstrap.ps1 end to end, the watchdog and registration have never run. The runbook says how the operator verifies (Admin > CI/CD > Runners shows `zeta-windows` online; a `tags: [windows]` job runs).
