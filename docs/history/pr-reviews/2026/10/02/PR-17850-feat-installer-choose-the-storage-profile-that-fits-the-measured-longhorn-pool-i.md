## Description

## The defect

node-5b2dfa (one 1 TB boot NVMe + one 1 TB NVMe carrying old Longhorn data) was refused by the installer's Longhorn capacity check: 810 GiB tail x 75% = **607 GiB** schedulable against the committed roster's **943**, "short by 336 GiB", every remedy a manual flag or a destructive wipe. The check compared the pool against ONE number as if the storage-profile ladder did not exist.

## What changes

The installer now picks, **before the wipe**, the LARGEST rung of the existing ladder (`k8s/storage-profiles.json`: minimal / standard / measured / large) whose declared demand fits, prints the whole ladder and what the choice changes, and **refuses only when even `minimal` (204 GiB) does not fit** (same three remedies). **607 GiB selects `standard` (571 GiB): `ollama/models` and `vllm/hf-cache` 200Gi -> 48Gi; nothing that provisions at bring-up changes.**

- Not a fourth ladder: the installer's table, its TS twin, the generated kit and the root's ignore set are all DERIVED from the catalogue (`cluster/storage-profile-install.ts --write`); a test fails on any drift. What a rung demands is what it *actually requests* (a claim a directory-source Application cannot resize keeps its committed size and is charged at it).
- Override: `zflash --storage-profile <auto|name>` (device, Windows with `--dry-run` output, file-backed) -> `ZETA_STORAGE_PROFILE` on the ESP, or the env var in a shell. A name is forced and refused before the wipe if the pool cannot hold it; a non-rung is refused, never read as `auto`.
- Reaches the cluster the lb-pool way: `/etc/zeta/storage-profile` (written only for a rung that differs from the committed one) -> `injected-storage-profile.nix` -> `zeta-storage-profile` Application -> one generated Job per Application merge-patches that rung's size leaves; the root ignores exactly those leaves. `vllm` becomes a kustomize source so its PVC is reachable.
- **Never shrinks**: a recognised prior install's profile + high-water mark is the floor (`ZETA_STORAGE_PROFILE_FLOOR=none` is the named escape), an explicit request below it is refused, the Nix module takes the higher of the file and `/var/lib/zeta/storage-profile-high-water`. Joiners write nothing.
- single-node-readiness: a pool that cannot hold the *committed* profile is no longer a `longhorn-geometry` blocker (the installer picks a smaller rung); only a pool where NO rung fits is. The two `694<<943` acknowledgements are retired, with the reason kept as text.

## Proven vs unproven

Proven (tests that fail without the change): the owner's numbers through the **real** `assert_longhorn_pool_holds_the_roster` under bash (`blockdev` stubbed): 607 -> `standard`, not refused; 1 GiB pool refuses; boundaries per rung; never-shrink (selection, shell parity over a case matrix, real function); the writer; zflash flags on all three paths; every claim's patch applied to the committed Application yields the catalogue value and the committed rung's patch is a no-op; no inert key; placeholder lint renders the template at every rung.

**Not verified** (no nix / QEMU locally): the Job-vs-first-sync race (a Job patches an Application after `zeta-root` creates it; only `minimal` could be hurt, since `standard` equals the committed size for every bring-up claim); ArgoCD's kustomize applying the inline patches incl. the per-Job rename; a real install on a 607 GiB pool. **Growing later is not fully automatic**: adding a Longhorn disk is Longhorn's own operation, and a StatefulSet's volumeClaimTemplates are immutable, so those claims need the PVC-expansion steps - documented in `docs/ops/INSTALL-TIME-CONFIG.md` row 29, not automated.

The existing QEMU lanes use a 1400 GiB disk, so they select `measured` (nothing written) and exercise the new pool-check code but not the shrunk path.
