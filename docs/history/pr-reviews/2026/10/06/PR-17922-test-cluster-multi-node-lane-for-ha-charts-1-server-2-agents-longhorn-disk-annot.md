## Description

## What

Adds the multi-node lane for HA charts: `full-ai-cluster/nixos/tests/k3s-multinode-ha-agents.nix`, run by a new `cluster-multinode` job in `build-ai-cluster-iso.yml`. The setup is one k3s server and two k3s agents. Agents run no apiserver or etcd, so the cluster has only one leader election and nothing competes with it.

The 3-server `k3s-ha-longhorn-cluster.nix` / `cluster-ha` lane is left as it is. It is still the only place the control-plane HA claim gets tested, and it still needs a runner with 8 or more vCPUs.

**The lane checks, in order:**

1. Two agents join through the shipped `k3s-agent.nix`, using the product token flow.
2. All three nodes are Ready on the product Cilium.
3. Longhorn registers a disk on all three nodes, including both agents.
4. postgres-shared at the **metal rung** comes up: 3 CNPG instances on 3 distinct nodes, 2 replicas streaming, and a PDB.
5. The primary is moved to agent1, and a row is written and seen replicated.
6. A 32 MiB write goes to a 3-replica Longhorn volume, with the replicas on 3 distinct nodes.
7. agent1 is hard-killed with `crash()`.
8. CNPG fails over. The row written before the crash reads back, and a new write commits.
9. The 32 MiB reads back on agent2 with the volume `degraded`.

**Derived, not transcribed.** Longhorn, the CNPG operator and the postgres-shared Cluster are generated with yq at build time from `k8s/applications/{longhorn,cloudnativepg}/Application.yaml` and `postgres-shared/cluster.yaml`. The 3-server sibling hand-copies Longhorn's values, and that copy has already drifted (it is missing `guaranteedInstanceManagerCPU`). The Cluster derivation drops two things, both named in the file: the Barman plugin, and 20Gi becomes 1Gi. A build-time guard fails if the 3-instance HA shape stops shipping.

**Which charts count as HA, and coverage.** The set of HA charts is the union of two sources: `extractReplicaClaims` at nodeCount 1, and `acknowledgedFalseRedundancy`. `multinode-ha-coverage.json` sorts them as follows:
- **Covered:** postgres-shared and longhorn.
- **Not covered, with reasons:** cockroachdb, nats, redis, kubevirt, platform.
- **Stale ledger entry:** `vault`, which has no Application directory.

`multinode-ha-lane-coverage.test.ts` fails if an HA chart appears in none of these lists. I mutation-checked it.

## Product fix found by the lane

`longhorn-disks.nix` hardcoded `KUBECONFIG=/etc/rancher/k3s/k3s.yaml`, and only a k3s **server** writes that file. On an agent, the annotator failed with `connection to the server localhost:8080 was refused`, so **Longhorn registered no disk on any worker**. In practice replicated storage stayed on a single node no matter how many workers joined. On agents the annotator now uses the kubelet's own kubeconfig.

## Not proven / needs a human

- **Product decision: `zeta-block-replicated` is `numberOfReplicas: "1"` with `dataLocality: disabled`.** Two of the three runs that reached Postgres put an instance's only replica on a *different* node, so losing one node can also take out a surviving instance's disk. The green run happened to place all three locally. The class comment says "raise it as nodes join", but nothing in the tree does that. The options are to raise the replica count, set `dataLocality: best-effort`/`strict-local`, or accept the risk. This changes production storage, so I left it for you.
- Control-plane HA is still unproven on hosted runners. It needs an 8+ vCPU runner, which is a budget decision. I did not provision one.
- cockroachdb, nats, redis, kubevirt and platform are not exercised; the reasons are in the coverage file.
- Tier: the lane runs on dispatch and on the daily schedule, not on push or PRs. One green run is not much evidence, and the placement hazard above can turn the lane red by itself.
