## Description

## What

`forgejo`'s server container requested nothing once its init containers exited. Rendered at chart 17.1.5 the `forgejo` container carries `resources: {}` while its three init containers each request 100m/128Mi, so the running pod held no request at all (cpu weight at the kubelet floor of 2, first in line for eviction -- the failure measured for the ArgoCD control plane in #17666). The app-level figure the budget prints (100m/128Mi) was `max(init)`, never the running pod, which is why total-based checks could not see it.

## Fix

A `resources` block on the Application's valuesObject: requests 100m/128Mi, memory limit 2Gi, no CPU limit. The request is deliberately **equal to the init-container figure**, so `max(init, sum(regular))` does not move: no catalogue row, rendered snapshot or pinned lane-debt literal changes (the dev lane's registered `dev memory 9868>9216` is untouched).

## Test (fails without the fix)

`src/Core.TypeScript/cluster/workload-steady-state-requests.test.ts` reads PER CONTAINER where the existing total-based checks cannot: every regular container of the AI/workload/platform family's git-path workloads, and `resources.requests` on its helm Applications, plus proof the pinned chart accepts the `resources` key (not inert). Remaining gaps (opt-in gmod SFTP sidecar, oz's controller) are a ratchet table the test asserts EQUALS what it finds, so new gaps fail and fixed ones force their entry out. Verified red on the parent commit (forgejo in the gap set), green here.

## Verified / unverified

- Verified: rendered forgejo Deployment now has `requests 100m/128Mi, limits memory 2Gi` on the `forgejo` container (repo renderer); `bun test src/Core.TypeScript/cluster` shows no new failures vs. the same tree without the change (Windows-only path failures pre-exist).
- Unverified (runtime): that 128Mi is a good steady-state figure under real load. It is a floor chosen to match the budgeted number.
