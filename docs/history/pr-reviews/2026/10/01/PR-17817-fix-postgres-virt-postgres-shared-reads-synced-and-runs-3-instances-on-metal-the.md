## Description

## Why

The owner's USB ISO (WP11 run 36832486494) read `postgres-shared` OutOfSync/Unknown for 3000s, `kubevirt` Progressing and `cdi` Degraded, on a 4 vCPU/12 GiB guest whose k3s restarted 14 times. Every static check was green because `postgres-shared`, `cnpg-barman-cloud` and `temporal/postgres` were deferred from every CI lane and nothing had ever executed them.

## What the live lanes found

- **postgres-shared (run 36855350178, red):** the database was healthy in 30s with a completed base backup, and ArgoCD still read the Application OutOfSync/Healthy forever (`autoHealAttemptsCount` 9). CNPG's webhook defaults `plugins[].enabled`; ArgoCD diffs a CRD's list atomically, so desired never equalled live and selfHeal re-applied the Cluster in a loop. Fixed by writing the defaulted field out. Green: run 36865035319.
- **Windows VM template:** the new server-side dry-run against KubeVirt v1.8.4 admission rejected it (`hyperv.stimer: field not declared in schema`; the field is `synictimer`). A unit test pinned the wrong name. Fixed; green: run 36865186970.

## Changes

- `plugins[].enabled: true` written out (postgres-shared, temporal/postgres); unbounded capped-backoff `retry` on the three CRD-consuming CNPG Applications (ArgoCD's default is 5 attempts and never again for that revision; `platform` already carries the same block)
- **Replica count rides the rung ladder** (no host loop, no ignoreDifferences): metal = `instances: 3` + `enablePDB` + `switchover`; the CI/dev rung serves 1 through `rung-overrides.yaml` `postgres-shared/single-instance-dev`. CPU request 250m -> 200m per instance because three at 250m put the metal roster 10m over the smallest node's allocatable. Ledger `pods` 3, metal roster 14347m/33379Mi, acknowledged as nominal redundancy on one node (soft anti-affinity + node-local PVCs: safe and pod-resilient, not node-resilient). `postgres-shared-cluster.test.ts` fails if instances/PDB/update method/ledger/dev override disagree
- `zeta-virt-first-sync`: the one-time operation carries a bounded retry. A manual-sync app has no `syncPolicy.automated`, so an operation with no retry is tried exactly once; on the ISO guest `cdi`'s only attempt hit "connection refused" and stayed Failed. The unit's exit-1-then-restart on `waiting` is intended and pinned
- Live lanes: `k8s-cnpg-live.yml` (dispatch-only; Application Synced+Healthy, 3/3 healthy, row read-back, ContinuousArchiving, completed Backup, bytes in the bucket under a scoped credential, a streaming replica, primary-pod loss with failover) and a VM step in `live-kind-virt` (CDI import, Windows template server-side dry-run, cirros VM Running under emulation)
- `docs/ops/POSTGRES-SHARED-AS-THE-DATABASE-FOR-OTHER-APPS.md`: findings on GitLab / Temporal / Hindsight using the shared Cluster (nothing built)
