## Description

Follow-up to #17812, from what its first live run (36875247887) showed.

The capture found the root cause (k3s restarted 19+ times on `leaderelection lost`; requests are 279% CPU / 242% memory of allocatable) but lost much of its own per-app and per-pod evidence:

- it spent 400 of a 1000-line budget on `get pods -o wide` first, then dropped every end-of-run app section as `(budget)`;
- k3s's first exit landed *during* the mid capture, so later sections read `connection refused`;
- `kubectl top pods | head` died of SIGPIPE (exit 141) and a healthy top read as unavailable.

Changes: order is priority (nodes, capacity, Pending census, Warning events, per-app, per-pod, bulk list last); short bounded API re-wait before the app and pod groups; budget 1600; mid capture at t>=600 s; `top` reports kubectl's own status. Tests added for the ordering, the tight-budget behaviour and the SIGPIPE case.
