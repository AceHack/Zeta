## Description

## What

A `wait-for-s3-buckets` init container on the six mimir components whose start-up runs the object-storage sanity check: ingester, store_gateway, compactor, querier, ruler, alertmanager. It does a SigV4-signed ListObjectsV2 against the endpoint, access key and minted secret mimir itself uses, for every bucket the Application names (`mimir-tsdb`, `mimir-ruler`). 200 = ready, 404 = bucket missing, 000 = gateway down. Status every 5s; exit 1 after 1200s (a visible `Init:Error`).

## Why (measured)

Constrained first-boot replica, run 36831938019 (main@15bbbc3433): mimir's sanity check logged `Unable to successfully connect to configured object storage (will retry) ... The specified bucket does not exist` until its 20 retries (1-5s backoff, ~85s; v3.2.0 `sanity_check.go`) ran out, then `module failed module=sanity-check`, `error running application`, exit 1. CrashLoopBackOff, restartCount 1-4 on querier, ruler and store-gateway. The same logs show the S3 Service refusing connections on :8333 first. (Loki logged `NoSuchBucket` / S3 500s in the same run and tolerated them without exiting.)

## Why the fix is in the consumer

seaweedfs is wave -5, mimir wave 0, and the dependency graph says mimir dependsOn seaweedfs. But the root's Application health check is deliberately non-gating: only `zeta.io/gates-later-waves: "true"` Applications propagate health (`argocd/Application.yaml`). So wave 0 does not wait for wave -5. A gating seaweedfs would not close it anyway: the buckets come from the chart's `post-install` hook Job, which only starts after the all-in-one Deployment is Healthy. Making seaweedfs gate would put every later wave behind one Application to fix one consumer type.

## Tests

`src/Core.TypeScript/cluster/mimir-wait-for-s3-buckets.test.ts`, 28 cases, 13 red without the init containers:
- structure derived from the Application's own `structuredConfig` (every bucket, access key, endpoint, secret) with the image tied to the seaweedfs chart's own version;
- negative controls: no wait, one bucket only, wrong endpoint, unsigned probe, no give-up, foreign image, wrong secret, a seaweedfs chart bump;
- behaviour: the script run under `sh` against a stub `curl` for ready, ready-after-waiting (000 then 404 then 200) and gave-up (exit 1, names the bucket and last status);
- scope: distributor, query-frontend, query-scheduler, overrides-exporter and gateway carry no wait.

Also run for real, read-only and non-root, against seaweedfs 4.45 in docker: 200 when the bucket exists, a wait with `http 404` when it does not, exit 1 on timeout.
