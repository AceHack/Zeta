## Description

## Why
WP11 run 36832486494 ran the committed `metal` tree on a 4 vCPU / 12 GiB guest. For the WP11 envelope (full tree minus gitlab/temporal/gmod) the rendered snapshot gives requests of 9122m CPU / 21822 Mi / 123 pods at metal (2702m / 14158 Mi at dev) against 3250m / 9228 Mi allocatable. The guest uses the metal rung. Every workload ran at priority 0, so nothing defined which Pending pod may displace which running one; a real node under pressure had no rule for shedding optional apps before the GitOps controller.

## What
Essential workloads name `system-cluster-critical`, a built-in class: it exists on every substrate, so no pod can be rejected for a missing PriorityClass (a custom class applied by ArgoCD could be, for bootstrap charts that start before ArgoCD). It outranks priority 0, and the kubelet does not evict critical pods.

argocd, cert-manager, trust-manager, external-secrets (3 Deployments), sealed-secrets, CNPG operator + barman plugin, postgres-shared and temporal-postgres (`spec.priorityClassName`), GitLab state (gitaly, postgresql, redis; web tier stays optional). Already classed by their charts: cilium, longhorn, gatekeeper, coredns, metrics-server. First-boot HelmCharts sharing a release carry the same value.

## Tests
`essential-priority.test.ts`: (A) values coordinates in Application and HelmChart, (B) helm-gated render proves every long-running pod carries the class (so a misspelt/ignored key fails), (C) the Postgres Clusters. 22 of 24 fail on the previous tree. `src/Core.TypeScript/cluster` fails the same 78 tests with and without this change (Windows path handling), so none are new.

Does NOT by itself make the 4 vCPU guest converge: requested CPU there is 2.8x allocatable. It decides who wins under that pressure. Details in work item 081M3VKWF4N087G0R00258SBT4 (PR #17811).
