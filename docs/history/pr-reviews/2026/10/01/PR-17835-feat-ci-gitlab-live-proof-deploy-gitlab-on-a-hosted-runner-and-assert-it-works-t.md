## Description

## What

A live proof that GitLab and its CI runner come up on a cluster -- the first lane that has ever deployed GitLab. `gitlab-live-proof.yml` brings up kind + the shipped Cilium + ArgoCD + SeaweedFS + the installer's own `cilium-lb-ipam-pool` Application + the committed `gitlab` Application on ONE hosted `ubuntu-24.04` runner and asserts, as separately named checks that each end `passed` / `failed` / `did-not-run` (never a pass for a check whose prerequisite failed):

- (a) webservice / sidekiq / gitaly / registry / shell Ready
- (b) root admin login (OAuth password grant, `GET /user` is_admin)
- (c) Job `gitlab-runner-token` Complete **and** Secret `gitlab-gitlab-runner-secret` holds a `glrt-` token (the Job exits 0 on its own failure by design, so Complete alone proves nothing)
- (d) runner pod Running, zero restarts after a soak, `GET /runners/all` shows it `online` with `run_untagged`
- (e) an untagged `.gitlab-ci.yml` pipeline succeeds in a Kubernetes executor pod
- (f) Job `gitlab-lan-address` pinned the three address leaves; Gateway Programmed at the pinned address; external URL, `/v2/` and the advertised clone URL (`git ls-remote`) answer from the runner host, outside the pod network

It runs on dispatch, weekly, and on a PR that touches what it deploys. It reuses `bootstrapKindClusterInProcess` / `buildLaneTreeForProfile` / `renderLbPoolApplicationText`; nothing parallel.

## Measured

GitHub Actions, public repo, standard runner. **Run 36886512326: every blocking check passed on the production pin path** (peak 7.0 GiB memory used with 9.0 GiB available, 13 GiB disk, load 5.1 on 4 vCPU, proof step 1223 s). Earlier runs 36855715576, 36860368378, 36862429321, 36865265497, 36871713092, 36878157147, 36881451548 are the defects below; each is in `workitems/081M3VKM164087G0R001RJFB2Z-*`.

## Defects found

Manifests (each with a falsifier in `gitlab-exposure.test.ts` that I ran red against the unfixed Application):

1. **The exposure Gateway sat in sync-wave 0 and the runner could never be created.** The install-time Job can only patch the Application after it exists, ArgoCD starts its first sync the moment it does, so the first sync renders the Gateway with the `192.0.2.250` sentinel, Cilium cannot assign it, and ArgoCD held every later wave: the operation sat on `waiting for healthy state of Gateway/gitlab-lan` for 30+ minutes; `Job gitlab-runner-token` and the runner Deployment were never created. Same hold on an install with no LB range. Gateway + both HTTPRoutes -> wave 20. (f)
2. **The default rolling-update surge stalled the second sync.** The pin re-renders the Application, so a fresh install rolls every Deployment once; sidekiq's surge pod (900m) sat `Pending: Insufficient cpu` for 14 minutes on a node at 3160m/4000m requested, the Application went Degraded, the exposure wave was never reached. `maxSurge 0 / maxUnavailable 1` on every Deployment. (g)

Lane (not the manifests): kind has no `metrics.k8s.io` (k3s ships it), so the chart's HPAs read Degraded in wave 0 -- the lane installs metrics-server; `kubectl proxy` strips `Authorization`; the lane's own `.gitlab-ci.yml` had a one-key YAML mapping in `script` (`ciScriptProblems`); the served lane tree is pruned to `applications/` so lb-ipam must come from the repo.

## Not proven

`prune: false` leaves the first migrations Job behind after the pin (the chart renames it), so a healthy install reads `OutOfSync` -- reported by informational check a6. Not exercised: public-domain TLS, `docker push`, GitLab upgrade, real metal (NixOS k3s, Longhorn, a physical L2 LAN -- (f) proves Cilium's L2 announcement over the docker bridge). Larger hosted runners could not be queried (org admin scope); the standard runner suffices.
