## Description

## The defect

A freshly flashed node never gets a virtualisation layer. `kubevirt` and `cdi` are declared **manual-sync** because they adopt operators hand-installed on node-5b2dfa under production Windows guests. That is a property of *that* cluster, but the declaration sits in the one tree every cluster syncs, and nothing on a fresh boot ever runs `argocd app sync` -- so both Applications sit `Missing` forever and the Windows-VM capability does not exist on a new install.

## The fix keeps the declaration (third path, not `automated:`)

Flipping to `automated:` would delete the protection from the cluster that needs it, and `manual-sync-policy.test.ts` pins the manual list on purpose. Instead `zeta-virt-first-sync.service` (server role) starts **one** ordinary `operation.sync` per Application, **once**, and **only where that operator's CRD does not already exist**. A cluster that already runs either operator is never touched.

- Phase 1: the one-time sync (write-once sentinel, per-app skip on CRD present or a sync already run).
- Phase 2: sets KubeVirt `useEmulation` **only** if this unit synced KubeVirt **and** the host has no `/dev/kvm` (otherwise VM pods sit Pending on `devices.kubevirt.io/kvm` with no error naming why). Never on an adopted cluster, never on hardware.
- `waiting` (API/Application/CR not answerable) is kept apart from `skipped` and `synced`: an error read as "CRD absent" would sync, read as "present" would give up forever.

## Also

- `kubevirt-cr` / `cdi-cr`: memory **limits** on the six operator-deployed components (limits only, requests untouched, no CPU limit). They had a request and no limit, and no rendered manifest names them, so no render check could see it. Only handle is `customizeComponents.patches`; container name = workload name was checked against the KubeVirt v1.8.4 / CDI v1.65.0 sources (a strategic merge naming a nonexistent container adds an imageless one). virt-operator / cdi-operator are vendored verbatim and out of reach -- stated in the CR headers. Values are unmetered reservations and say so.
- `cdi-cr`: `scratchSpaceStorageClass` named instead of inherited.
- `k8s/examples/kubevirt-windows-vm.yaml`: Windows guest template (EFI, Hyper-V enlightenments, virtio-win CD-ROM pinned to the vendored KubeVirt release, CDI ISO import, replicated root disk, RDP Service, `Halted` until the ISO has imported). Kept **outside** `k8s/applications/`: inside it, its 64Gi DataVolume was counted as Longhorn-pool demand and failed three ledger tests (measured).

## Evidence (all local, Windows)

- `zeta-virt-first-sync.test.ts`: 26 tests EXECUTE the script over a fake kubectl, including two mutants (CRD skip deleted; `kubevirt=sync` guard deleted) that the scenarios must detect.
- `kubevirt-cdi-component-limits.test.ts` (16) and `kubevirt-windows-vm-example.test.ts` (14). The limits tests fail on the old tree (`customizeComponents: {}`).
- Full `src/Core.TypeScript/cluster` + `full-ai-cluster/k8s/tests` run: no new failures versus the same run on the base (91 pre-existing Windows path/kubectl failures, listed before the change; one 5.04s timeout flake in the bash-inventory test that passes alone).

## Not verified / honest limits

- **No NixOS eval and no cluster run** (no nix locally). CI is the first execution of the module.
- **A real diff on a cluster that already runs KubeVirt**: the CR header's "no-op adoption" held for the captured spec; the limits add to it. Manual sync, so a human reads `argocd app diff kubevirt` first; running guests live in virt-launcher pods and are not restarted by a control-plane rollout.
- Nothing boots a guest. Windows needs `/dev/kvm` and a licensed ISO.
- `virt-operator` (probe kill budget 25s) and `cdi-operator` remain in the liveness-kill-budget allowlist unvetted; their probes live in vendored bytes.
- The `.sh` is added to the bash-retirement allowlist (host-service wrappers).
