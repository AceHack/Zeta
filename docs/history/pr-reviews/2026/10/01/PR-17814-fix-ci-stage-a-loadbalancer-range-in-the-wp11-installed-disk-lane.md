## Description

## What

The WP11 installed-disk QEMU lane (SLIRP guest 10.0.2.15/24, gateway 10.0.2.2) gave the cluster **no Cilium LoadBalancer pool**. Every `type: LoadBalancer` Service stayed `<pending>` and every Gateway reported `Programmed!=True`, which ArgoCD reports as `Progressing` forever (Argo CD `Gateway/health.lua`, gitops-engine `health_service.go`). So the `platform` Application (Gateway `zeta-gateway`) could never be Healthy in this lane (run 36832486494).

A real install supplies a range (INSTALL-TIME-CONFIG row 3, `zeta_lb_pool_resolve`, ESP `ZETA_LB_POOL=`, `injected-lb-pool.nix`). The lane now does the same.

## Changes

- **Stage a pool.** The WP11 bake passes `lbPool: { kind: "range", start: "10.0.2.240", stop: "10.0.2.250" }`. This is the installer's own `.240-.250` window of the SLIRP /24: clear of guest (.15), gateway (.2), DNS (.3) and the derived pod/service CIDRs, and explicit rather than `auto` (which refuses the install when the LAN cannot be read). Exported as `WP11_LB_POOL_*` / `SLIRP_LAN` with the SLIRP rationale in the comment.
- `prepareBootImage` did not forward `lbPool` to the file-backed bake (only `runFileBackedZflashCli` accepted it); it does now, and reports `espFirstbootConfStaged` via `stagesEspFirstbootConf`.
- **WP27 contract live.** `stagedEspFirstbootConf` is derived from that result instead of a literal `false`, so `assertEspFirstbootConfWasRead` convicts a lane whose staged conf the guest silently did not read. Stale "dormant" comments updated.
- **Second observable (arrival in the cluster, not just the conf read).** `zeta-first-boot-k3s-verify.nix` prints `[wp11-k3s-verify] lb-pool: state=...` and the verdict JSON gains an additive `lbPool` key: does Application `cilium-lb-ipam-pool` exist, and does CiliumLoadBalancerIPPool `zeta-lb-pool` list exactly the installed range. `unknown` when the API could not be asked (or `kubectl` is missing); `fail` only when the API answered and the object is absent / lists a different block, or when the installed disk has no `/etc/zeta/lb-pool` although the lane staged one. A note beside verdict 7, not a new numbered verdict: numbering and existing keys are unchanged. The host gates on `fail` only (`evaluateLbPoolNote`).

## Tests (each fails without the change; mutations checked)

- `wp11-lb-pool.test.ts`: the range passes the installer's own `zeta_lb_pool_validate` and `zeta_lb_pool_resolve` for the SLIRP LAN with the cluster's real derived CIDRs (and the same harness refuses ranges containing the node or gateway, or outside the LAN); the ESP conf line carries `ZETA_LB_POOL`; `stagesEspFirstbootConf` is derived and cross-checked against `planFileBackedZflashImage`; the three-way note judgement and its gating of the verdict.
- `wp11-lbpool-shell-parity.test.ts`: extracts the in-guest classifier verbatim from the `.nix` and runs it under bash (present / absent / unknown, including `command not found` != object not found).

Not verifiable without a live run: that the SLIRP guest accepts the range end to end (see below), and the in-guest `kubectl` jsonpath output on a real cluster.

Risk: phase 1 fails outright if the installer refuses the range. Evidence it will not: the real shell validator returns `valid`; the only other refusal path is the ICMP busy-probe, and SLIRP answers ARP/ICMP only for its special addresses (.2/.3/.4), so `.240-.250` should read free. That last point is inferred, not measured.
