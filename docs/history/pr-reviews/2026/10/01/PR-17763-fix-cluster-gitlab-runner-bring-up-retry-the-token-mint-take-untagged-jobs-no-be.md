## Description

Follow-up to #17737 / #17711 (workitem 081M3TRSR03087G0R0035B51JA). A paper audit plus `helm template` of gitlab 8.7.0 found four defects that only appear once the first pipeline or the first busy minute arrives.

## Defects and fixes

- **Token mint had one attempt.** The `gitlab-runner-token` Job made a single `gitlab-rails runner` call; one cold-start blip left `runner-token` empty and the runner crash-looping on the removed registration-token flow. It now retries on a wall-clock budget inside `activeDeadlineSeconds` (still exits 0 on give-up, so a failed Sync hook cannot block later syncs) and falls back to `reset_token!` if an existing runner yields no token.
- **Runner skipped untagged jobs.** Created `run_untagged: false`, so a `.gitlab-ci.yml` without `tags:` sat Pending behind a healthy runner. Now `true`.
- **BestEffort pods.** redis (Sidekiq queues, sessions, cache) and its exporter, the postgres exporter, the runner manager and CI job pods requested nothing. Requests added (reservations, not limits). Runner `concurrent` 10 -> 4 for a single node.
- **HPAs sized for a cluster.** The chart's HPAs (webservice/registry/shell min 2, all max 10) are live under k3s's metrics-server: a 5.2 GiB webservice floor, and sidekiq scaling toward ten 2 GiB pods on the first-boot CPU spike. Bounded to floor 1 / ceiling <= 2.
