## Description

Adjudication of the `platform` defect candidate (census Part D/E), and the fix it supports.

**The error** (`platform`, run 36887261429): `PrometheusRule`/`ServiceMonitor` `SyncFailed: failed to discover server resources for group version monitoring.coreos.com/v1: forbidden: User "system:serviceaccount:argocd:argocd-application-controller" cannot get path "/apis/monitoring.coreos.com/v1"`.

- **(a) missing nonResourceURL RBAC: excluded.** In the same capture the same ServiceAccount was denied on a *resource* verb its ClusterRole grants through `*`: `cockroachdb` `cannot get resource "clusterroles" ... at the cluster scope`. And `system:discovery` grants `/apis/*` to every authenticated user.
- **(b) CRD group not registered: not what that error says.** An unregistered group answers 404 to a permitted caller, which is the path `SkipDryRunOnMissingResource` covers. (b) is real as an ordering fact (kube-prometheus-stack was capacity-blocked) and explains why platform stayed non-Healthy, but not this message.
- **(c) transient apiserver: fits everything.** One cluster-admin-equivalent SA denied at cluster scope for a resource and a path, in runs where k3s had just exited on a lost lease: a restarted apiserver whose RBAC authorizer had not synced. The same outage gave `connection refused` on cdi, kubevirt, kube-prometheus-stack.

**Fix.** A manifest cannot prevent a transient denial; it decides whether the Application survives it. ArgoCD's automated sync defaults to 5 attempts (~2.5 min) and never re-attempts a revision whose sync already failed (`platform/Application.yaml` records the measured case). Only 5 of 50 Applications, and not the root, had the unbounded retry. This adds `retry: {limit: -1, backoff: {duration: 30s, factor: 2, maxDuration: 5m}}` to 43 more Applications and `zeta-root`, and raises gitlab (5) and hat-system (10) to -1.

**Test.** `application-retry-unbounded.test.ts`: every automated Application and the root has `limit: -1` and a capped backoff, plus a non-vacuity guard; 86 cases fail without the change (verified by running the suite on the pre-change tree).

**Not claimed.** The outage itself is not fixed here (#17833 and the capacity work address it). No live lane was run: the evidence is the two WP11 captures, and the new `retry` field is not exercised by anything but a boot. The wave inversion `platform` -> `kube-prometheus-stack` stays registered; this is the robustness fix, not repair (2). Locally, `validate-applications.test.ts` fails on Windows path handling (`Application.yaml/Application.yaml` ENOTDIR) with or without this change; CI is the check for it.
