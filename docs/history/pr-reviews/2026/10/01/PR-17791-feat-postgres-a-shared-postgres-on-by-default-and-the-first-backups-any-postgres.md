## Description

## What a fresh install now runs

- **`postgres-shared`** (new Application, wave 5, namespace `postgres-shared`): a CloudNativePG `Cluster`, instantiated from the #17767 template, **on by default**. Consumers dial `postgres-shared-rw.postgres-shared.svc:5432` with the operator-minted Secret `postgres-shared-app` (database `app`, role `app`). `-ro` has no endpoints at one instance; `-r` works. Documented in the Application header.
- **`cnpg-barman-cloud`** (new Application, wave -65): the CloudNativePG Barman Cloud plugin (chart 0.8.1 / v0.15.1) in the operator namespace.
- **Backups for both Postgres Clusters** (`postgres-shared` and `temporal-postgres`): continuous WAL archiving plus a daily base backup (`ScheduledBackup`, `immediate: true`), 14-day recovery window, to bucket `zeta-backups` in the in-cluster SeaweedFS. No external service is named anywhere.

## Decisions worth a reviewer's eye

1. **Plugin, not `spec.backup.barmanObjectStore`.** The 0.29.0 CRD still accepts the in-core field, but CNPG's v1.30.0 docs mark it deprecated since 1.26, and the `minimal` PostgreSQL image every Cluster here runs carries no Barman binaries (only the deprecated `system` image does). The in-core path would pass admission and then fail at runtime with an archiver that never succeeds and WAL piling up on the data volume.
2. **`instances: 1`, not 3.** This is a single-node install, and the tree's own convention (longhorn: "keep this == node count") is a committed value, not a derived one. Three instances on one node triple the memory and PVCs and protect against nothing. Scaling to 3 is a one-commit edit; `postgres-shared-cluster.test.ts` fails if `instances`, `enablePDB`, `primaryUpdateMethod` and the ledger `pods` disagree. **No automatic node-count-driven scaling exists**, and I did not invent one.
3. **`enablePDB: false` and `primaryUpdateMethod: restart`** at one instance: a lone primary's PDB (`minAvailable: 1`) makes `kubectl drain` hang on the only node, and a switchover has no replica.
4. **Least-privilege backup credential.** The seaweedfs gateway gets a second identity `pgBackup`, scoped to `zeta-backups` (no `Admin`), drawn independently in the existing first-boot seed Job and written as `postgres-backup-s3` into `postgres-shared` and `temporal`.
5. **ArgoCD health:** ArgoCD v3 ships a built-in health check for `postgresql.cnpg.io/Cluster` (present at v3.2.0), and this tree's argocd-cm overrides only the Application kind, so nothing needed adding. A test pins that no conflicting override appears.
6. **PodMonitor** is on, as a manual object (`enablePodMonitor` is deprecated in the CRD), because kube-prometheus-stack (wave 0) provides the CRD before it and the edge is declared in the sync-wave graph. It carries the `release` label the stack's default selector requires.
7. Both new Applications are **dev-lane excluded** with reasons and lift conditions (ghcr pulls, an unproven operator-plugin mTLS handshake, and a first-boot credential dev bring-up does not mint).

## Not verified

Nothing here ran against a live operator. Open first-boot questions: does the operator discover the plugin Service; do the scoped `Read/Write/List:zeta-backups` SeaweedFS actions satisfy barman; does path-style addressing hold against the gateway; does WAL actually reach the bucket. Watch the Cluster's `ContinuousArchiving` condition: a failing archiver leaves the phase Healthy. The backups share a node and a disk with the databases, so they protect against logical error and a lost pod, not a lost machine. SeaweedFS's 20Gi volume is shared with loki and mimir; the retention window is the lever if it fills. The plugin's injected sidecar image (`plugin-barman-cloud-sidecar`) and the PostgreSQL `imageName` are operator-injected and not seen by the image audits.
