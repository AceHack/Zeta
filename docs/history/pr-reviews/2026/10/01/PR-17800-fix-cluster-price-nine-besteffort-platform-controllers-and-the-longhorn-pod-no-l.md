## Description

missing-resource-requests.ts listed 18 ACTIONABLE Applications, platform
controllers among them. Their pods requested nothing: QoS class BestEffort,
cgroup cpu.weight 1, first reclaimed by the kubelet. The constrained first-boot
replica on main (2026-09-30, run 36685251210, 4 vCPU) had 19 of 38 Applications
FAIL where the unconstrained lane the day before had them Healthy; the ArgoCD
control plane got this treatment in WP32 (#17666) and the rest of the platform
tier did not.

PRICED, as requests with no limits (the WP32 precedent): cert-manager (3
workloads), trust-manager, sealed-secrets, external-secrets (3), argo-rollouts
(2), argo-workflows (2), headlamp, dapr (5 workloads; the scheduler is THREE pods
even with global.ha.enabled=false), spire (5 containers). Each is a
`resourceClaims` row whose evidence says the numbers are ESTIMATES sized to leave
BestEffort, not usage readings. The nine left `ungovernedRequests`.

COST, STATED. Dev lane CPU 2145m -> 2425m (inside the 2500m budget only because
the dev floor for these rows is 10m, not the catalogue's usual 25m, which would not
fit); dev memory 11980Mi -> 13380Mi, so the already-acknowledged shortfall is
re-keyed `dev memory 13380>9216`. Metal, all 50 Applications: 13645m/30347Mi ->
13995m/32323Mi (+350m: 10m for idle controllers, 25-50m for the hot ones) against
the smallest node's 16000m/62942Mi.

THE FINDING THAT SHAPED THE METAL NUMBERS. Longhorn creates one instance-manager
pod per node at RUNTIME, requesting `guaranteedInstanceManagerCPU` percent of the
node's allocatable CPU (chart 1.12.1: default {"v1":"12","v2":"12"}). No manifest
renders it, so no ledger row ever counted it. On the smallest node, 15250m
allocatable after the 750m kube+system reservation, 12% is 1830m: the metal roster
on main BEFORE this change (13645m) plus that pod is already 15475m -- over
allocatable, so the last pods to schedule go Pending forever. Longhorn's
reservation is set to 5% (763m) through the chart's own key: 13995m + 763m =
14758m of 15250m, 492m spare. STILL TIGHT -- any further metal pricing must redo
this sum, and the new test fails the PR that does not.

FALSIFIERS. platform-controllers-requests.test.ts (a) fails on any non-hook
workload of the nine that requests nothing -- 13 workloads against the pre-change
snapshot, none after -- and (b) asserts roster + Longhorn instance manager <=
allocatable, which the 12% default breaks. Numbers quoted in prose across the
ledger, the reason-truth citations and the ladder tests were re-derived, not
guessed; the whole cluster/, k8s/tests, hygiene and full-ai-cluster/tools suites
ran on Linux (7241 tests, one environmental failure unrelated to this change).

NOT DONE, named: longhorn-manager, cilium-agent/envoy/operator/hubble and the
openbao unseal sidecar still carry no request of their own. gitlab's snapshot row
is left at main's value (it now renders 14 workloads / 2445m against a declared
2375m) for its owner to re-measure; this snapshot keeps main's gitlab entry.
