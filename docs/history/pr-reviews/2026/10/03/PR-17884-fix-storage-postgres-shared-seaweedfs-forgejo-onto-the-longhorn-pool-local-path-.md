## Description

## What

The one real node (`node-5b2dfa`) gave root 120.5 GB, put 39 GB of container images on it, and also pointed the default StorageClass (`rancher.io/local-path`, no quota) at a directory on that root. Every default-class PVC -- the production PostgreSQL clusters, the blob store behind the registry and the database backups, GitLab's repositories -- was an unbounded directory on the filesystem the kubelet evicts pods from, while the two Longhorn data disks (1.7 TB) were ~98% free.

Measured (docs/ops/STORAGE-RELOCATION.md): all 22 local-path PVCs together hold **8.6 GiB** of the root's 75.6 GiB used; containerd is **37.5 GiB**. Moving state frees ~6 GB; the image store is an OS change and is the owner's decision (documented, not done).

## This PR is the git half of a live, ordered migration

- `postgres-shared`, `seaweedfs`, `forgejo`: `storageClass: zeta-block-replicated` (Longhorn, 1 replica). The live data is moved afterwards, one workload at a time, with verified copies, `Retain` on every old PV, and rollbacks stated per step. **Merging this moves nothing by itself**: CNPG applies the class only to PVCs it creates afterwards, and the two chart-owned claims are quiesced with `argocd.argoproj.io/skip-reconcile` until the swap is done.
- **Capacity ladder told the truth**: three new `storage-profiles.json` claim rows; demand 943 -> **1043**; ladder `minimal 279 / standard 671 / measured 1043 / large 1701` (generated by `storage-profile-install.ts --write`); QEMU lane disk 1400 -> 1540 GiB so the lane's pool still clears the roster (sparse qcow2, free). A CNPG `Cluster` was priced at **one pod** because `spec.instances` was not read (understated the disk by 40 GiB) -- fixed, with a test. Two dev-lane overrides the ladder now makes redundant are removed.
- **Fresh installs no longer put local-path on root**: `local-storage-placement.sh` + unit `zeta-local-storage-placement` bind-mounts the largest `/var/lib/longhorn-disk*` (>= 200 GiB) onto `/var/lib/zeta-local-storage` before k3s. Fail-open, never shadows a populated directory, never moves or deletes anything; the one exit 1 (placed before, data disk gone now) holds k3s down rather than hand local-path empty directories over data. Executed by a hermetic test.

## OWNER DECISION NEEDED: the price

A **single-1-TB-disk** install has 607 GiB schedulable. `standard` now declares 671, so the installer selects **`minimal`** for it (it selected `standard` before) -- and `minimal` is the rung that drops cockroachdb and nats to one member. Two-disk shapes and anything larger are unaffected (this node has two). Remedies the installer already prints: add a second internal disk, or raise `LONGHORN1_TAIL`. This is the honest cost of counting 100 GiB of databases and blob store against the pool that now holds them, which is the explicit request; the alternative was leaving them as an unmetered directory on root. Say so if you would rather size something down.

## Proof, and what is unproven

- Proven offline: the capacity/ladder/shell-parity/install-kit/readiness suites (530+ tests), the placement script over fixtures (23 tests: happy path, tie-break, threshold, unmounted disk, failing mount, populated target not shadowed, the single refusal, typo'd config), and the CNPG pod-count reading.
- Server-side dry run on the live cluster: CNPG's webhook accepts the `storageClass` change.
- **Not proven**: `nix` is not available on the machine this was written on -- the NixOS unit is read by a test but not evaluated or booted; `mount --bind` of a longhorn-disk subdirectory under the real local-path helper pods is not exercised on hardware. Windows-only failures in the wider suites (`/bin/bash`, `\` path separators) are pre-existing and are compared against a clean `origin/main` run.
