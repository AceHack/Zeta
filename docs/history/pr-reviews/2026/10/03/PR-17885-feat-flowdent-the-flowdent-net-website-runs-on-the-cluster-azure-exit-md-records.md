## Description

## What

Moves the public website `flowdent.net` / `www.flowdent.net` off Azure Container Apps onto the cluster, and records what is left on Azure, the registry copy, and the safe deletion order.

- `full-ai-cluster/k8s/flowdent-web/` (opt-in Application, outside `applications/` like `k8s/flowdent/`): namespace `flowdent-web` (Pod Security `restricted` enforced, quota, no PVC), PDB, Service, HTTPRoutes + a `:80` redirect.
- **The Deployment is deliberately not in this tree.** It names a private image on `registry.flowdent.net`; the first version of this PR failed `image-source-provenance` for exactly that (Zeta must not depend on a Flowdent-private artifact; Aaron's one-way rule, the #14250 incident). It lives in `flowdent/fd-webclient` MR !2 (`k8s/flowdent-web/deployment.yaml`, `kubectl diff` against the live object is empty), the same split as fd-core. A test now pins "no workload and no `registry.flowdent.net` image in this directory".
- `public-tls`: Gateway listeners 7 (apex) and 8 (`www`), each with its own certificate Secret, patched in by `argocd-application.yaml.in` like the api listeners.
- `docs/ops/AZURE-EXIT.md`: re-measured proof, the registry table, the final dependency table, the deletion order (commands, not run), the Azure OpenAI note.
- Tests: `cluster/flowdent-web.test.ts` (new); `flowdent-platform.test.ts` E updated for 9 listeners.

## Measured (2026-10-03)

- Cluster vs Azure vs public (via Cloudflare): status + body md5 identical on 11 paths, response headers equal apart from the proxy that added them; origin certs Let's Encrypt for `flowdent.net` and `www` (Ready, valid to 2026-12-31); `x-envoy-upstream-service-time` arrives through Cloudflare, so the public path ends on the cluster.
- The apex `525` was Azure's: custom domain `flowdent.net` `bindingType: Disabled`, its managed certificate `Failed`; `curl --resolve flowdent.net:443:48.223.241.141` resets the handshake, `www` there returns 200.
- Cloudflare records (both proxied, ttl auto): `A flowdent.net` and `A www.flowdent.net` -> `66.10.240.234`; rollback values and record ids in the doc.
- ACR `flowdentacr` -> `registry.flowdent.net`: web images (serving `672c0d13`, Failed `06a4d160`), the services images, the `flowdent-api` tag and the six named one-off tags, every digest compared and equal. All 226 sha tags resolve to commits that exist in GitLab.
- Whole-cluster scan (130 pod images, all ConfigMaps/workloads, every Secret key): Azure endpoints only in the two kept-storage connection strings and the deleted AI endpoint.

## Not done / honest limits

- External probes through Cloudflare show an intermittent 520/525 (apex 70/80 and 78/80, www 79/80 and 78/80 in two runs); the node itself answers 60/60 per name from the LAN; the DNS-only api name was worse (50/80) in the same minutes. The cause is upstream of the node; a Cloudflare Tunnel would remove it and needs a credential this change does not hold.
- The Deployment is applied by hand (no Argo Application exists on the cluster for it); a node rebuilt from git gets namespace and routes but not the pods until the fd-webclient manifest is applied.
- The served site 404s every URL its own sitemap lists, on Azure and on the cluster alike.
- `flowdent-containerapp-rg` contains the kept storage account `fddiagbundlesprod`: delete resources individually, never the group.
