## Description

Follow-up to #17890 (merged): the first real run against the Windows 11 Enterprise Evaluation ISO (build 26300, one image, index 1), and the desktop made reachable the way the user asked.

## What changed

- **Answer file fix (a real defect found by running it):** Setup rejected the unattend at the specialize pass ("The computer restarted unexpectedly or encountered an unexpected error"). `setuperr.log` (read through Shift+F10 on the install screen) named `RunSynchronousCommand[Order=2]` as invalid: a `<Path>` is limited to 259 characters and ours was ~500 (copied from the Windows Server answer file, which has the same defect and is **untouched here**). Now two short commands; a test pins every `<Path>` at 259 or fewer.
- **`win11-desktop`**: OpenSSH server, **key-only** (official `PowerShell/Win32-OpenSSH` MSI pinned by sha256, hash = the digest GitHub records for the release asset), keys from ConfigMap `win11-desktop-ssh-keys` into `administrators_authorized_keys` with `icacls`; Service `win11-desktop-ssh` (ClusterIP :22); the firewall opens 22 and never 5000.
- **`40-network-policy.yaml`**: a `CiliumNetworkPolicy` admitting ingress to the guests only from the node host and their own namespace.
- ISO claim 10Gi (the ISO is 8.2 GB); runbook: connect commands, SSH/API recipe, the measured timeline, the firmware-menu recovery for the boot-from-CD prompt.

## Verified live (no secrets in this text)

- `win11-desktop` installed unattended end to end: `Windows 11 Enterprise Evaluation`, build 26300, `WIN11-DESK`; bootstrap log ends "desktop bootstrap finished"; `sshd` and `QEMU-GA` running; listening on 22 and 3389 only.
- `ssh -J zeta@192.168.1.79 zetaadmin@<ClusterIP>` authenticates by key; password-only is refused. With `-L 5000:127.0.0.1:5000 -L 13389:127.0.0.1:3389`: a throwaway listener on the guest's `127.0.0.1:5000` answered `curl http://localhost:5000/`, and an RDP X.224 handshake through `localhost:13389` returned a connection confirm. From the node, `<guest IP>:5000` times out.
- With the policy applied: the node still reaches both ClusterIPs, the guest still reaches GitLab and the runner bucket, a pod in `default` is refused (its control probe to GitLab succeeds).
