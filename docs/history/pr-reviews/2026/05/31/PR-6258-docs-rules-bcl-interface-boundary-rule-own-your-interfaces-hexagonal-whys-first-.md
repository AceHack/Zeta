## Description

## What

Lands the **BCL-interface-boundary rule** you proposed across the Rust observe-reader arc (`(shadow*)` "land the BCL-interface-boundary rule") — an auto-loading `.claude/rules/` file codifying the dependency-interface invariant.

## The rule (hard/soft)

- **HARD:** depend on a 3rd-party *interface* only if it's **BCL / BCL-like** (the platform's own foundational library — `System.*` / ASP.NET Core / Rust `std` / JDK / Web+Node stdlib). Any swappable 3rd-party gets **wrapped behind our port** and adapted in — depend on its *implementation*, never its *interface* (hexagonal / ports-and-adapters).
- **SOFT:** direct dependence on a 3rd-party interface only if it's **BOTH provenance-vetted AND a widely-used de-facto standard** (e.g. serde); else **use our own**.
- The port is the **I/O-monad shape** (a Kleisli `Result<OurType, OurError>`) — composes the framework's `Result<T, TFeedback>` / monad-propagation / asymmetric-authorship substrate.

## Authored whys-first

Per your meta-principle — *"a rule without a why is dogma"* — **every clause states its real, questionable, agreeable why**, so a reader can dispute the *logic* (not just the conclusion) and the rule gets revised if a why is wrong:

- *why* BCL-tier is OK to depend on (it IS the platform — vendor-maintained, long-term-compat, doesn't churn; a different risk profile than a swappable lib);
- *why* wrap 3rd-party (churn / abandonment / supply-chain / lock-in; wrapping = swappable + testable + isolated);
- *why* SOFT needs **both** provenance AND adoption (provenance = supply-chain integrity; adoption = many-eyes/Schelling-point; provenance-without-adoption = unstressed, adoption-without-provenance = untrusted chain).

## Empirical anchor

The Rust observe oracle (PRs #6255 + #6257): `Json`/`JsonParser` are our ports; `ZetaJsonParser` (zero-dep) is the default; `SerdeJsonParser` (feature `serde`) is the adapter — serde (provenance-vetted + ecosystem-ubiquitous → SOFT-qualifying) conforms to *our* interface; nothing outside `from_serde` names a serde type. We went *beyond* SOFT to HARD (own parser default + serde wrapped/optional).
