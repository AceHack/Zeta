## Shape: a port, not a resolver

- **`ServiceControlPort`** — `bootstrap` / `bootout` / `describe` / `listLabels`, plus a `guarantee`. No argv, no exit codes, no raw stdout: those are adapter internals. `launchctl print` parsing moved *into* the adapter, which is what leaving it at the call site would have made impossible.
- **`createLaunchctlControl`** — today's adapter. Admits the binary, checks the version, spawns the absolute path.
- **`inMemoryServiceControl`** — a second adapter, no subprocess, no filesystem, no launchd.

### Is a second adapter genuinely constructible, or does the shape encode "spawn a subprocess"?

Genuinely constructible — and exercised, not asserted. The test `CONTRACT PARITY: one caller works unchanged against both adapters` runs one caller function against both and gets the same answer. It never learns which adapter it holds.

**Where the port is honestly limited:** its vocabulary (`domain`, `definitionPath`) is launchd-shaped. This is *not* a cross-OS service port and claiming so would be the overclaim — the repo already has that port, `IServiceManager`, with launchd/systemd/task-scheduler adapters. Two layers, two jobs:

```
IServiceManager      "manage a persona service"   cross-OS
ServiceControlPort   "control a launchd domain"   launchd, swappable mechanism
```

A future native implementation replaces the adapter; no caller changes. Per `.claude/rules/interfaces-free-classes-earned-under-rules.md`: the port is the interface (free, weight-free), each adapter the earned class.

## What the version guarantee verifies — and what it cannot detect

Measured: `Darwin Bootstrapper Version 7.0.0: ...`. The adapter parses the major and refuses below `MIN_BOOTSTRAPPER_MAJOR = 2` (the generation with `bootstrap`/`bootout`), and refuses an **unparseable** version rather than proceeding.

- **Verifies:** the program at the admitted path answers `version` with a string of the expected shape and generation. A compatibility check.
- **Cannot detect: binary substitution.** A substituted binary can print any string it likes. This is not an authenticity check.

## The "fingerprint" — I am not calling it one

`toolIdentity` records `(realpath, dev, ino, size, mode, uid, sha256)`. Measured cost (macOS 26.5.2, Bun 1.3.14, median of 5, warm):

| target | size | sha256 |
|---|---|---|
| `/bin/launchctl` | 0.4 MB | **0.36 ms** |
| `bun` | 63.1 MB | **31.75 ms** |
| `statSync` | — | 0.0036 ms |

So hashing is affordable here once per process and is *not* affordable per-invocation for a 63 MB runtime — which is measurement, not preference, and is why this module is not proposed for the `bun`/`git` sites.

Stated plainly:

- **A hash detects substitution only against a recorded baseline.** With no `pin`, identity is an **observation** and refuses nothing. Called with `pin`, it becomes a real substitution detector for any byte/inode/size/realpath change.
- **It proves nothing about provenance.** No signature verification, no notarisation, no trust root. A root-authored replacement with a matching pin is undetectable, and a first-run pin records whatever is already there.
- **SIP is asserted, not verified.** `SF_RESTRICTED` on `/bin/launchctl` is the property that actually makes the absolute path meaningful (measured: `ls -lO` → `restricted,compressed`; `csrutil status` → enabled). **Bun's `statSync` exposes no `st_flags`**, so the code cannot read that flag and does not claim to. The allowlist encodes a measured OS property; it does not re-verify it at run time.

## PATH-hijack test — the point of the work

Runs against the real host, with a control that could have come out the other way.

1. **CONTROL** — plant `launchctl` (`#!/bin/sh\nexit 0`) earlier on PATH. A PATH-resolved `spawnSync("launchctl", ["version"])` **executes the forgery**: exit 0, no `Bootstrapper` banner, and `which` confirms the forgery is what a lookup finds. The vulnerability is real, not hypothetical.
2. **The resolver is unaffected** by the hijacked PATH — still `/bin/launchctl`, uid 0.
3. **The forgery is refused even if allowlisted** — user-owned, so the structural check catches it independently of the allowlist.

## A bug this PR introduced, then caught

My first `parsePrintOutput` used `/state\s*=\s*(\S+)/`, which reports `"spawn"` for `state = spawn scheduled` and `"not"` for `not running`. My own fixtures used single-word states, so **my tests agreed with my implementation** — the vacuity class. Found by noticing `parseLaunchctlPrint` had become dead production code and reading its real captured fixtures.

Fixed by adopting the proven `/^\s*state = (.+)$/m`, adding the real fixtures as regression tests (M17), and making `parseLaunchctlPrint` **delegate** so the tree has exactly one launchctl-print parser that cannot drift.

# Update — the two reds, investigated

## 1. `installer unit tests (bun)` — hypothesis REFUTED, pre-existing flake

The proposed chain was: `sudo`/`sfdisk`/`losetup` now route through `system-tool.ts`, the Linux roster is empty, so the port refuses every privileged tool on Linux. **That is not what is happening.** Three independent checks:

- **`installer/` imports neither new module.** `rg` over the whole directory for `system-tool|service-control-port|resolveSystemTool|createLaunchctlControl` returns nothing.
- **`resolveSystemTool` has exactly two callers** — its own test and `service-control-port.ts`. Nothing in the installer path can reach it.
- **The test uses its own local helper:** `function run(cmd, args) { spawnSync(cmd, [...args], …) }` — a raw spawn, deliberately outside the elevator discipline (`lint-no-path-resolved-privilege-elevator.ts` explicitly EXCLUDES `*.test.ts`, and says so).

**The decisive control.** Main run [`32759542708`](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/32759542708) (2026-08-24, commit `02169a883`, before this branch existed) fails **byte-identically**: `error: sfdisk failed: ` with **empty stderr**, same stack at `repair-mode-existing-install.test.ts:133:77`. The workflow's recent main history is 2 failures in 12 runs (~17%).

**Also worth correcting: neither local run was a valid control.** `environmentReason()` returns `platform is darwin, loop devices need linux` and skips the whole suite on macOS. Both "1 pass, 0 fail" results were the skip guard, not the Linux path — a check that did not run reading as one that passed. The only real execution of this code is the ubuntu runner.

So the empty Linux roster is **not** implicated and remains what it was: unexercised, and correct-by-design (launchd is Apple-only; an empty roster there yields a refusal naming the platform). The disclosure stands unchanged rather than being upgraded to a regression.
