## Description

Two defects that fed each other: `required-check-started` reported healthy PRs as stuck, and nothing ever retired a superseded flush PR — so the false alarms had a growing population of abandoned PRs to fire on.

## 1. Absent from the rollup is not never-going-to-run

The guard asked *does the rollup contain `gate (required)`?* A gate run that has **started** does not publish that name into the rollup for ~28 minutes, so healthy-but-queued PRs were reported with the words "never started". Measured the same morning:

| PR | gate runs for head SHA | outcome |
|---|---|---|
| #11387 | present at **28.0 min** | merged |
| #11401 | present at **28.4 min** | merged |
| #11389 | present; transient failure, passed on rerun | merged |
| #11369 | **zero, ever** | genuinely stuck |
| #11426 | **zero, ever** | genuinely stuck |

Raising `--min-age-min` past 28 would have silenced the three false positives **and delayed the two real ones** — trading a loud wrong answer for a quiet late one. The discriminator is not time but **existence**: a run that exists will report; one that does not never will. So `stalled` (no run) fails and `queued` (run exists) is reported and tolerated.

This is strictly **sharper** than the threshold, not weaker — every genuine hang still fails on the first check past `--min-age-min`, with no extra waiting.

A failed measurement is not a measured failure: if the run-count query errors, or a PR has no head SHA, the tool exits `2` (unmeasured) rather than converting host trouble into a verdict. The caller already treats `2` as "gate state unavailable".

## 2. A replaced flush PR should retire

Every tick snapshots the lane onto an immutable `heartbeat/<agent>-flush-<sha>` ref and opens a PR; nothing closed the previous one. On 2026-08-17 **eight** heartbeat PRs were open at once, three for the same lane, with #11362 and #11394 hours stale. An abandoned flush PR whose gate never starts then fails `required-check-started`, taking the flush job red every ~25 min until someone closes it by hand — which is exactly how #11369 and #11426 were spent.

**Why closing loses nothing, and why the tool earns that claim.** The snapshots are *not* ancestors of each other (#11373 did not contain #11369's commits). What makes retirement safe is the **lane**, not the snapshot chain: each tick rebuilds `heartbeat/<agent>` carrying any prior unflushed delta over current main, so an unlanded payload is re-accumulated into its replacement. Verified on both hand-closed PRs — main was a strict superset of the abandoned findings log (60 vs 59 lines, and 49 vs 48, **zero** lines missing in each), with content-addressed event files present under identical ZetaId names.

That argument holds only while a replacement is actually open, so `supersededFlushPrs` returns **empty** when the keeper is absent from the open set. Closing a predecessor whose replacement never opened would strand the delta behind a closed PR with no live path to main — the one outcome worse than accumulation.

## Falsifiers, not assertions

- Deleting the keeper-present guard fails `retires NOTHING when the keeper is not open` (10 pass / 1 fail; restored → 11 pass).
- The mutable lane `heartbeat/<agent>` is unparseable as a snapshot by construction, so it can never be retired — pinned by test.
- No ref is ever deleted: the immutable snapshot stays as the recovery copy, since closing is reversible and deleting is not.

Wiring is non-fatal: retirement runs only after `rc=0`, when this tick's telemetry is already safe on an open PR, so failing the flush over unfinished housekeeping would trade a real success for a cosmetic failure.
