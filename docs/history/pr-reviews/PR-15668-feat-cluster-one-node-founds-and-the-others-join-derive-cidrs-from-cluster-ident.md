## The finding that has to come first

Two k3s control planes answer on the LAN right now (`192.168.4.152` / `.153`, CA
founding epochs twelve days apart, both 401). They are **abandoned hardware from
over a month ago**, scheduled for reformat. `cluster-bringup`'s `shape` reports
them as "2 sovereign clusters", which is correct about the wire and wrong about
the world.

> **A reachability probe cannot distinguish a current estate from abandoned
> hardware that is still powered on.** Both answer 401 identically. There is no
> packet that carries "nobody intends this any more."

Any conclusion from probing a LAN needs an out-of-band *"is this intended?"*
input that no probe supplies. This burned three agents today; it is §0 of the doc.

## Two defects behind one hardcoded line

`k3s-server.nix` hardcoded `10.42.0.0/16` / `10.43.0.0/16`, restated twice more
in the Cilium manifests. That produces **two different problems**, fixed
separately:

### (1) Multi-node within ONE cluster — this is what "multi node cluster" needs

The CIDR is **not** the blocker; members share the cluster CIDRs by design. The
blocker is the **server half of the join**:

| flashed as | on `main` |
|---|---|
| worker (`role = agent`) | joins. **Already works.** |
| control plane (`role = server`) | `injected-join-server.nix` guards itself to agents, so `clusterInit = mkDefault true` stands. **Founds its own cluster, silently.** |

Two CAs twelve days apart is that row's signature.

**`injected-server-join.nix`** supplies the missing branch:

| state | result |
|---|---|
| endpoint **and** token | `clusterInit := false`, `serverAddr`, `tokenFile` |
| neither | nothing set — byte-identical to today's founding |
| exactly one | **assertion failure at Nix eval**, naming which half is missing |
| `role == "agent"` | contributes nothing |

`clusterInit = mkDefault true` is **unchanged**. Sovereign by default; joining by
declaration, never by a guessed default.

**Name resolution was already solved** and was verified by reading the tree
rather than assumed: `cluster-address.ts` → `zeta-firstboot.conf` →
`zeta-install.sh` → `injected-cluster-address.nix` writes the
`control-plane -> <founder ip>` `/etc/hosts` entry on joiners. What this adds is
the missing token leg — `zeta-install.sh` now also stages
`/mnt/etc/zeta/k3s-join-token` (**not** k3s' own `server/token`, which k3s
manages and writes itself).

### (2) Distinct clusters that may later federate — #15661's F0

Pod/service CIDRs are now a pure function of `clusterName` in
`full-ai-cluster/cluster-identity.json`. **No allocator, no registry** (§1).
`"zeta"` → id 31, `10.143.0.0/17`, `10.99.192.0/19`.

**Collision-resistant, never collision-free, and the ceiling is not ours:**
Cilium's ClusterMesh cluster-id is **8 bits**, so the pigeonhole applies to any
allocator-free scheme. Bound stated rather than implied — ~3.9% at four
federated clusters, ~50% at nineteen — with detection (`clusterNetworksCollide`
reports the *fact*, not a verdict) plus renaming as the mitigation.

**The reserved-range walk caught a real bug in the first draft.** The service
space was `10.64.0.0/10`, which looks fine and puts **slot 96 on `10.88.0.0/18`
— containing the `10.88.0.0/24` cluster segment every joiner is addressed on**.
One name in 255 would have made the segment unroutable. Enumerating the reserved
ranges as *data* and walking all 255 slots found it on the first run.

**Deriving the k3s flag alone would have been worse than the bug.** Kubelet and
CNI disagreeing about where pods live produces addresses that route nowhere — it
reads as a network fault. And the ArgoCD Cilium twin has `selfHeal`, so a stale
value there is re-applied over the bootstrap manifest **forever** (the same
two-owners shape `k3s-server.nix` already records for Vault). Both manifests were
regenerated; agreement is asserted at Nix eval **and** by a lint.

## The dirty-disk case

k3s docs, verbatim: *"If an etcd datastore is found on disk … the datastore
arguments (`--cluster-init`, `--server`, …) are **ignored**."* Every option above
is a datastore argument, so a declarative join on a dirty disk is a **silent
no-op** with `systemctl status k3s` green throughout.

`k3s-datastore-preflight` refuses to let k3s start in that state — `before` +
**`requiredBy`** (fail closed; `wantedBy` would be the vacuity class in unit-file
form). **It deletes nothing.** A boot-path wipe would be confiscation we
introduced (§5). The refusal names both facts, both ways forward, and which one
is irreversible. A founding node that already founded is **not** refused —
refusing there would brick every reboot of a healthy cluster.

## Added 2026-08-26 — the five reds that were gating the join-path VM tests

Every `build-iso` failure was at `Check flake evaluates`, which sits **before** the seven VM steps and skips all of them. Nothing about the cluster-join path had ever been observed, because evaluation never got far enough to boot a VM.

| red | cause | fix |
|---|---|---|
| `build-iso` | `k3s-server.nix` **set** `zeta.k3sDatastorePreflight.enable` and **read** `config.zeta.cluster.{podCidr,serviceCidr}` while importing neither definer — so it evaluated only through `common.nix` and threw in every VM test, all of which import the role module directly | import the definers in the module that owns the value; same for `k3s-agent.nix` |
| `lint (TS)` | `cluster-cidr.ts` indexed `match[1..5]` / `octets[0..3]` under `noUncheckedIndexedAccess`, which the `match === null` guard does not narrow | destructure + fold, rather than assert away with `!` |
| `cross-verify (stage0-independence)` | `k3s-datastore-preflight.sh` is a real new stage-0 door — systemd ExecStarts it, so no shell script can be its parent | recorded in `exceptions` with that reason, the remedy the tool itself names |
| `live kind Cilium CNI` | the manifests moved to the derived `10.143.0.0/17` but `cilium-kind-up.ts` still hardcoded `10.42.` | read the pool from the values actually installed; test membership by address arithmetic |
| `installer unit tests` / `repair mode` | not ours — the bun 5s `beforeAll` hook timeout fixed by #15689, which this branch predated | carried in by the merge from `main` |

**The flake fix was verified against a control, eval cache cleared before both runs.** With the two `imports` blocks reverted, `nix eval .#checks.x86_64-linux.k3s-control-plane-cluster-init.drvPath` exits **1** with CI's exact message; with them, exit **0**. `nix flake check --no-build --all-systems` is exit 0. Those two `.nix` files are byte-identical to the same fix on #15673, so that branch's merge is a no-op on them.

On the Cilium asserter: the obvious repair — `startsWith("10.143.")` — is **also** wrong, because `10.143.128.0` is outside `10.143.0.0/17` while matching the text prefix. That boundary case is now a test.

**Deliberately not fixed:** the two suspected defects in the join path (`control-plane` → `127.0.0.1` unconditionally; etcd 2379/2380 closed between servers). They are what the VM tests exist to answer, and patching them pre-emptively would destroy the evidence. Static reading does narrow the first: a joining server dials `injectedUrl`, not the name, so it is not a k3s-join defect — it is an open question for Cilium, which is pointed at `k8sServiceHost: control-plane`.
