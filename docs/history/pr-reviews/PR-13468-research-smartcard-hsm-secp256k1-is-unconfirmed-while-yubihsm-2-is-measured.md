## Description

Aaron, considering a dual-vendor HSM pair per node: *"can you research and make sure it supports crypto wallet keys."*

## Split answer

| device | secp256k1 | basis |
|---|---|---|
| **YubiHSM 2** | **YES — measured** | `eck256` in the fw 2.4.1 mechanism list, enumerated on Aaron's own device |
| **SmartCard-HSM 180K** | **UNCONFIRMED, evidence leans no** | vendor page says only "RSA and ECC keys"; OpenSC's docs name NIST + Brainpool curves and never name secp256k1 |

**The "Bitcoin Wallet" bullet does not settle it, and the spec line is the tell.** *"521 bit ECC"* describes the **NIST prime family**; secp256k1 is a 256-bit **Koblitz** curve not implied by any upper bound on ECC length. A device can support P-521 and have no secp256k1 at all. `secp256r1` and `secp256k1` differ by one character and are different curves.

Register kept honest: **absence of confirmation, not confirmation of absence.**

## Why the pair is right regardless — complementary recoverability

**DKEK n-of-m *is* confirmed** in documentation (worked 3-of-5 example), and that is the property that matters:

| | TPM 2.0 / YubiHSM 2 | SmartCard-HSM |
|---|---|---|
| key export | non-exportable by design | **DKEK-wrapped backup/restore** |
| device loss | key gone with the device | **restore onto a replacement token** |

A TPM-only design has no device-layer recovery — `credential-binding-model.ts` already tests `tpmSeal × machine_swap → decrypts: false`. Pairing it with a DKEK-capable token makes Aaron's *"n-of-m no so scary anymore"* implementable **at the device layer**, before the cluster is large enough to provide it across nodes.

## The threshold choice, stated rather than picked

| | availability | security |
|---|---|---|
| **1-of-2** | up | **DOWN** — attacker need only break the weaker vendor |
| **2-of-2** | **DOWN** — either failure bricks the node | up |

Neither buys both; the composition that does is dual-vendor per node × n-of-m across nodes. Anchored to N-version programming (**Avizienis 1977**) **with its refutation** (**Knight & Leveson 1986** — independently developed versions fail on correlated inputs far more than independence predicts).

## The falsifier is scheduled, not just named

Aaron ordered **two** — which promotes two claims, since a threshold scheme cannot be exercised against a single token: mechanism list (1 device) **and DKEK restore across devices** (2 devices). Exact unauthenticated enumeration commands are in the doc, following the YubiHSM precedent of opening no authenticated session, plus what each outcome means — including that an ambiguous `ECC-SECP256` label is **not an answer** and must be resolved by OID (`1.3.132.0.10`).
