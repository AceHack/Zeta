## Description

# Summary

Follow-up to #14869, which shipped the ARC pixel agent with a gap disclosed in its body: `src/Arc.Python` was invisible to CI three ways. Closing that turned up **a real bug that had nothing to do with typing**.

**The environment advertised no legal actions at all.** `GameAction` is a plain `Enum`, **not** an `IntEnum`, so `GameAction.ACTION1 == 1` is `False`. `ARCBaseGame` dispatches `available_actions` through `match action: case 1 | 2 | 3 | 4 | 5:` — literal patterns compared by `==` — so passing enum *members* fell through every case.

```
>>> ZetaChase(seed=4)._get_valid_actions()
[]
```

It survived because our own agents never ask — they carry their own action vectors. It would have surfaced the moment a generic ARC agent, or the toolkit's own `listen_and_serve`, asked the environment what it may do and was told *nothing*. `available_actions` now derives from `_MOVES`, so the advertised set cannot drift from the accepted set.

**Correcting myself:** in #14869 I wrote that "GameAction is an IntEnum so it works at runtime." It is not an IntEnum, and it did not work. I asserted that from mypy's output instead of checking the type.

The other three mypy findings were annotations that described neither the value nor its use: `_MOVES` is keyed by `GameAction` (`self.action.id` **is** one), not `int`; `perform_action` is declared `FrameData | FrameDataRaw` because of a `raw` switch we never pass, so `advance` now **asserts** the branch rather than casting, failing loudly here if the engine ever changes; and `arc_agi` ships no `py.typed` marker, ignored explicitly rather than papered over with invented stubs.

## The lane now has CI — in two pieces, deliberately

**Static checks join the existing PR-time job.** `lint-python.ts` hardcoded `src/Core.Python`, so the lane's clean ruff/mypy state was checked by nothing. It now iterates both projects, which needs **no workflow change** — `lint (Python)` already runs that script. `Arc.Python` gains the same dev group (ruff/mypy/pytest).

That wiring had a bug I only found by *running* it: the mypy step hardcoded `src/`, which exits 2 against a project laid out as `zeta_arc/`. Type-check paths are per-project now, with the reason recorded at the field.

**Tests get their own non-blocking workflow.** `arc-lane.yml`, and the shape is a design constraint rather than a preference. §3.2 constraint 2 of the lane's design doc says it outright: *"No gate job depends on it … never a required check."* The reason is constraint 1 — `arc-agi`/`arcengine` live in their own uv project precisely so a resolution failure there cannot break `uv sync --project src/Core.Python`. A required job would hand this lane the power to block every PR in the repo, which is the exact coupling the split exists to prevent.

`arc-lane.yml` appears in **no** `needs:` list — verified by grep, not by intent.

> **One departure from §3.2, stated in the file rather than slipped in.** The doc names the triggers as *"workflow_dispatch (+ optional cron)"*. This also runs on `pull_request`, path-filtered to the lane. The doc's stated *reason* is that the gate must not be touched, and a workflow outside every `needs:` list does not touch it — while post-merge-only feedback finds a broken lane after it lands. **If you want the literal reading, delete the `pull_request:` block; nothing else changes.**

**What is hard here is liveness, not the result.** The hazard is this job going green while running *nothing* — the false-green shape that put the byte-lock's "verified 0 of 10" on record. So the run parses its own junit output and exits 2 below a floor of collected tests. That floor is itself fail-closed, measured not assumed: delete the env entry and `set -u` exits the step non-zero rather than quietly disabling the check.

A second step plays a full scored episode, because every unit test can pass while the loop is broken. It asserts the agent still **clears** every level rather than merely running.
