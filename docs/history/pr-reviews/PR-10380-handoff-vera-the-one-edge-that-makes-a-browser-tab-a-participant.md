## Description

A brief for Vera, who owns `browser-node/` outright (114 of 114 signed commits).

## The gap

The node has **no network egress at all.** `fetch`/`WebSocket`/`XHR`/`EventSource` across both trees returns three service-worker smoke-test stubs and one capability probe. `BrowserDatabaseIntentOutboxPort` has `enqueue/begin/settle/acknowledgeArchive/refuse` and **no `flush`, no `push`, no remote sink**. Receipt handoff is BroadcastChannel-only — a "peer" is another tab on the same machine.

Everything else is genuinely built and wired. Also worth knowing: **`hall/room/index.html` is not the node** — it is a static zero-JS still; the live node is the sibling `node.html`.

## Why it is the highest-leverage edge

1. **It is what makes the liveness claim true.** IndexedDB is origin-scoped and evictable, so today the answer to *"what survives the last tab closing?"* is "one machine's browser profile", not "git".
2. **It is a witness-vs-quorum problem.** Grep for `quorum|witness|majority|f+1|2f+1` across both trees returns **nothing** — not a criticism, but because peers cannot see each other across machines, so no quorum is constructible even in principle.
3. **It solves `gitpull.html`'s write-back for free** — same missing edge: a way to hand a signed batch to something that can write git.

## The ask

`flush()` on the outbox port; a `fetch` sink POSTing signed content-hashed batches to `repository_dispatch`; an Action folding them into git. `BROWSER_DATABASE_RECEIPT_HANDOFF_BATCH_SCHEMA` already carries `contentHash` and dedupe acks, so the drain is **idempotent by construction** — Vera already built the property that makes an unreliable sender acceptable.

## Done condition

A tab that has been closed, on a machine now off, has its work land in git — and a second tab elsewhere can tell that it did.
