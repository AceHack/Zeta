## Description

## What

`spire` — the SPIFFE identity substrate the federated-identity and per-node-CA
work stands on — reaches `Synced`/`Healthy` in the dev lane and leaves the
exclusion list.

## The control run, before the fix

Applying `main`'s spire Application alone to a fresh kind cluster reproduced the
reported failure exactly: `OutOfSync`/`Missing`, `one or more synchronization
tasks are not valid`, 27 resources `Missing` including the three
`ClusterSPIFFEID`s, zero pods.

## Three blockers, only one of which was known

**1. No CRD source in the kind lane.** The chart renders three `ClusterSPIFFEID`
resources and ships no CRDs for them; the only `spire-crds` install in the tree
is a k3s-only `helm.cattle.io/v1 HelmChart` that kind never processes.

Options were weighed rather than the first one taken:

| option | verdict |
|---|---|
| the chart's own CRD subchart | **unavailable** — spire 0.24.2's dependency list is spire-lib, spire-server, spire-agent, spiffe-csi-driver, spiffe-oidc-discovery-provider, tornjak-frontend. No CRD chart. |
| an explicit apply step in kind bring-up | **rejected** — it would make the ordering a property of a script the metal lane does not run, i.e. two lanes with different sources for the same CRDs |
| **a separate Application at an earlier wave** | **taken** — same chart, same version the k3s bootstrap pins, ordering declared in the dependency graph |

`spire-crds` 0.5.0 is not an arbitrary pin: it is what `k8s/bootstrap/spire-install.yaml`
already installs, and it is the floor the chart's own README states under
*Upgrade notes / 0.24.X* — "You must upgrade spire-crds to 0.5.0+".

**2. The `pre-upgrade` hook — recorded as DERIVED on `main`, now OBSERVED.**
It was unverified because blocker 1 aborted the sync first. With blocker 1 fixed
it fired exactly as derived:

```
Error from server (NotFound): validatingwebhookconfigurations.admissionregistration.k8s.io
  "spire-spire-controller-manager-webhook" not found
```

five failed `spire-server-pre-upgrade` pods, Application pinned at `waiting for
completion of hook batch/Job/spire-server-pre-upgrade`, zero workload pods. The
hypothesis is confirmed, not deleted. Closed with the chart's own documented
setting for template-rendering consumers — which ArgoCD is, on **both** lanes:
`global.installAndUpgradeHooks.enabled: false`. What that costs (the webhook
stays `failurePolicy: Ignore`) is written in the manifest rather than glossed.

**3. `ServerSideApply` — found only because the first two were fixed.**
It makes the spire-server StatefulSet permanently `OutOfSync` on a
`volumeClaimTemplates` artifact nobody wrote. The 2x2, measured on one cluster,
both directions, reversible:

| | `ignoreDifferences` off | on |
|---|---|---|
| **SSA on** | OutOfSync | OutOfSync |
| **SSA off** | **Synced** | Synced |

**The attempt that failed is kept in the record because it is the more useful
half.** An `ignoreDifferences` rule naming the three jq paths was tried *first*.
It cleared two and could not touch `creationTimestamp: null` — ArgoCD introduces
that downstream of the normalizer, and an ignore rule cannot remove a field that
does not exist yet when the rule runs. It is **not shipped**: unnecessary with
SSA off, insufficient with it on, so in neither cell does it constrain anything.

This is the weaviate lesson applied in advance — *one confirmed cause is not THE
cause* — and it is why the verification below is a clean-slate run rather than a
patch on the cluster that found the problem.

## Mutation testing

Eight mutations, each verified by byte `cmp` to have **actually applied** before
its result was read (a harness that patches nothing manufactures fake survivors).

**Six refused:** drop the `spire-crds` node (refused by `ace`'s own resolver —
`chart 'spire' depends on unknown chart 'spire-crds'`) · move its wave to `-45`,
after spire (refused as a NEW order disagreement) · empty its manifest ·
re-defer `spire` · drop its resource-catalogue row · delete the
`spire -> spire-crds` edge.

That last one **survived the first pass** and the survival is the finding: the
node is enforced and the wave order is enforced, but nothing can derive that an
edge someone *deleted* ought to have existed. A named pin in
`derive-sync-waves.test.ts` closes it for this edge; the general case is stated
as still open rather than papered over.

**Two still survive, and are reported rather than hidden:** re-enabling the hooks
and re-adding `ServerSideApply` have no offline falsifier — nothing offline can
render a chart, run a PreSync hook, or compute an ArgoCD diff. **The live lane is
what refuses them**, which is precisely why taking `spire` off the deferral list
is the load-bearing half of this change and not the bookkeeping half.
