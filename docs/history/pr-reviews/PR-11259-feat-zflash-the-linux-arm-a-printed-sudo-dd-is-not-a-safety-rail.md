## Description

Closes half of `081M037KPG1087G0R0005ANAFV` (recovered lost row B0738); the row stays `in-progress` for the half that is not built.

## The gap, in code

`src/Core.TypeScript/zflash/flash-usb.ts:188` refused on anything that is not darwin and printed a command for the operator to type by hand:

```text
lsblk; sudo dd if=<iso> of=/dev/<device> bs=4M status=progress conv=fsync
```

That line has none of the checks the macOS path has above it — no bus check, no boot-disk check, no size bound, no runtime consent. The Windows sibling was built (`flash-usb-windows.ts`); the Linux half was dropped on an orphan branch, and Linux is the cluster-node OS.

## What landed

**`src/Core.TypeScript/zflash/flash-usb-linux.ts`** — the same contract as the other two arms: whole disk only, `tran=usb` (not merely "removable" — an internal SATA disk in a hot-swap bay reports `rm`/`hotplug` true), not read-only, size in [4 GiB, 256 GiB], hosting none of `/ /boot /boot/efi /efi /nix/store`, not the disk backing `/`, exactly one surviving candidate, and a fresh runtime nonce typed back verbatim.

**`src/Core.TypeScript/pam/auth-chain.ts`** — the PAM `auth`-chain resolver, generalized out of `analyzeSudoAuthChain` (`tools/setup/persona-keys/biometric.ts`). **Sharing it is a correctness point, not a DRY one:** that parser knows only OpenPAM's `auth include <service>`. Debian and Ubuntu splice sudo's chain in with Linux-PAM's `@include common-auth`, which it skips silently — run unchanged on Ubuntu it resolves to an *empty* chain, reports zero competing satisfiers, and concludes the fingerprint was the only possible factor. That is the exact false `biometric` claim #11234 removed, reintroduced by a copy. There is a test for it.

`analyzeSudoAuthChain` becomes a thin wrapper pinned to `syntax: "openpam"` — behaviour-preserving, its 27 tests pass untouched.

## The gate degrades; it does not open

`planEscalation` picks `sudo` or `pkexec`, preferring whichever actually offers the fingerprint, tie-breaking to `sudo`, and **refusing** when neither can authenticate (no TTY and no pkexec is a refusal, never an unprivileged write, never a NOPASSWD rule).

What it will not do is claim a fingerprint happened. `sudo` and `pkexec` report their own exit status and never name the module that satisfied PAM, and `pam_unix.so` shares the chain with `pam_fprintd.so` on every mainstream stack — so the readout is `unattributed`, naming the competing modules. `factor: "biometric"` is reachable only where the resolved chain holds nothing else, and a test pins that it is not vacuously false.

## Two encodings that would have destroyed a boot disk

- `"mountpoints": [null]` is util-linux's **unmounted** form. Read as one mount point, every unmounted partition looks mounted.
- The older scalar `"mountpoint": "/"` must still be read, or a mounted root on a pre-2.37 host looks unmounted and the system-mountpoint rail never fires.
- The root guard matches on the device tree, not string prefixes (`/dev/sda` is not the parent of `/dev/sdaa`), and an unresolvable root spec (LVM/dm, MD, LUKS, ZFS, empty `findmnt`) makes every disk suspect rather than none.

## What is NOT done — and why the row is in-progress

- **Not run against hardware.** No ISO has been written to a physical stick by this arm. Everything above `main()` is pure and tested; the imperative shell below it is not.
- `zflash` (`cli.ts`) still refuses on Linux — its ESP pubkey-injection step is diskutil-shaped.
- `tools/setup/linux.sh` has no `zflash` touchpoint yet.
- A QEMU harness scenario driving this end to end against a file-backed device (`test-harness/prepare-boot-image.ts` already builds images without physical USB).

Both entry points now point Linux operators at the arm that carries the rails instead of at a bare `dd`.
