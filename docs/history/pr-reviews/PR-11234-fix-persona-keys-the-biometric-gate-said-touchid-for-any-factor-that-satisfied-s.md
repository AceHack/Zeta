## Description

# Summary

`macTouchIdAuth()` in `tools/setup/persona-keys/biometric.ts` reported a factor it could not
observe. It grepped `/etc/pam.d/sudo` for `pam_tid.so` (configuration **presence**), ran
`sudo -p "" true`, and on exit 0 returned `{ ok: true, platform: "macos-touchid" }`. Neither
observation sees **which** PAM module satisfied the transaction, and `man pam.conf(5)` on this
host says it cannot:

> **sufficient** — If this module succeeds, the chain is broken and the result is success.
> **If it fails, the rest of the chain still runs**, but the final result will be failure
> unless a later module succeeds.

The stock chain continues `auth sufficient pam_smartcard.so` / `auth required
pam_opendirectory.so`, so declining Touch ID falls through to a smart-card PIN
(`man pam_smartcard(8)`: an appropriate card in an attached reader, unlocked with its PIN) or
the account password — and all three exited 0 under the name `macos-touchid`. The sharpest
instance is that the FROST hardware lane is **exactly** the flow where a PIV token is plugged
in: the token being provisioned could satisfy the gate meant to prove a finger was on a sensor.

The code's stated mitigation was also wrong. The comment claimed stdin being `ignore` meant
"no password can be typed", but `man sudo` documents `-S, --stdin` as reading the password
from standard input **instead of** using the terminal device — the default path is the tty and
closing stdin does not close it. It fails closed only where there is no tty at all (CI), which
is why the gate was honest in the environment nobody watches and soft in the interactive one.

## The shape chosen, and the trade

**Report honestly**, not "verify genuinely" — on evidence:

- **Verify genuinely is not reachable from here.** `LocalAuthentication` / `LAContext` is the
  only mechanism that observes the biometric rather than a proxy for it, and it needs a native
  Security.framework bridge this TS CLI does not have. The cheaper `sudo -S` variant genuinely
  shuts the *password* path, but whether `pam_smartcard`'s PIN prompt also routes through
  sudo's conversation function is an **inference** — and inference-standing-in-for-observation
  is the defect itself. Both are filed as `081M06KM523087G0R002ANKAZJ` with what is unknown
  about each stated, including that confirming `-S` requires a human with a PIV token inserted.
- **Telling the truth is cheap here.** No caller branches on `platform === "macos-touchid"`;
  the only consumers were three readout lines and test fixtures (full list below). `ok`
  semantics are unchanged, so no gate that previously opened now closes.

What changed:

- `ApprovalFactor` splits what was **established** from `platform`, which only ever documented
  what was **attempted** (its own docstring said so; every readout printed it as the former).
  `establishedFactor()` / `claimsBiometric()` are the `supportsClaim` analogue from
  `src/Core/DerivationProtocol.fs`: an `ok:true` result declaring no factor reads as
  `unattributed` and is **never** rounded up to `biometric`.
- `analyzeSudoAuthChain()` parses the chain (resolving `include`, per pam.conf(5)) instead of
  grepping one line. Deliberately conservative: every non-`pam_tid` `auth` entry counts as a
  competing satisfier, and an unreadable `include` is an **unknown** chain, never an empty one.
  macOS ships no man page for `pam_deny` on this host, so treating it as harmless would be the
  same class of inference that caused the bug.
- `SudoGateEffects` makes the gate testable at all — it previously had **zero** coverage
  because it touched `fs` and `sudo` directly. A test now describes a host's PAM files and sudo
  exit status; no `sudo` runs and no fingerprint is required (§13 noninterference, the same
  shape as `frost-hardware-probe.ts`).
- The three readouts print the established factor, which on a stock Mac reads `unattributed`.
- `docs/DECISIONS/2026-05-29-biometric-sudo-elevation-via-touch-id-pam.md` carries a correction:
  its "Biometric proof of physical presence is required" pro is where the over-claim originated.

## What stays unverified

Per the work-item, **no `sudo` was invoked on the operator's machine.** The finding is a reading
of the code, `/etc/pam.d/sudo`, `man pam.conf(5)`, `man pam_smartcard(8)` and `man sudo`. The
fall-through itself remains unreproduced by execution and cannot be reproduced without
authenticating as the operator and declining a Touch ID prompt on their laptop.

**reports** (a new `factor` field and the readout wording); the approve/deny decision is
unchanged on every input.

**No caller anywhere branches on `platform === "macos-touchid"` to make a security decision**,
which is why the honest register costs nothing downstream today. `claimsBiometric()` exists so
that a future caller whose argument genuinely needs the biometric has something correct to gate
on instead of `ok`.

`async () => ({ ok: true, method: "passphrase", prompt: "auto", platform: "macos-touchid" })`
— an auto-approving door that labels itself Touch ID while naming its own method as
`passphrase`. Different literal, same family; left for a separate look rather than folded into
a security-semantics PR.
