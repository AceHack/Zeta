## Description

Scenario 5 (`cluster-joining`) has never run. This clears the *argument* half of its hardest blocker and — deliberately — does **not** claim the scenario now works.

## A fourth blocker the brief missed, and it is the worst one

`full-ai-cluster/usb-nixos-installer/zeta-first-boot.sh:47` is `HOST="${HOST:-control-plane}"`, read from the ISO's own `/etc/zeta-firstboot.conf` — and `grep -rn firstboot src/Core.TypeScript/zflash/` returns only test-harness comments. **zflash writes no firstboot config to the ESP.**

So a zflash-prepared image installs a **second control-plane**, which runs no k3s agent and therefore no join observer. `scenarios.ts:219-227` and `run.ts:840` already named this. By severity it is blocker #1, not #4: without it, a "cluster join" has nothing to join as.

## What now exists

`buildQemuSystemBootArgs` accepts an optional `networkDevices` spec (`QemuNetworkDevice`; backends `user-nat` / `l2-socket-listen` / `l2-socket-connect` / `l2-multicast`). `planMultiVMRuntime` puts the two VMs on one **rootless QEMU socket L2 segment** — listen on `cluster-existing`, connect on `joining-node` — each keeping its NAT NIC on `net0` with the segment on `net1`.

**Socket over bridge, deliberately:** `zflash-test-br0` needs root on the host, so the previously-declared `shared-bridge` topology was undeliverable on any hosted runner. `DEFAULT_MULTI_VM` moves to `shared-socket-segment`.

## The find worth keeping

**QEMU defaults *every* NIC to MAC `52:54:00:12:34:56`.** Harmless on disjoint SLIRP networks — which is exactly why scenarios 1–4 never hit it — and a **silent duplicate-MAC collision** on a shared segment: both VMs boot clean, frames flow, traffic misroutes. That would have surfaced as a flaky k3s join and been chased for hours. Any `l2-*` backend without an explicit unique unicast MAC is now refused up front, and the guard is mutation-checked (flip `isL2 = false` → a test fails; restore → green).

## Scenarios 1–4 are untouched

Only `multi-vm.ts` passes `networkDevices` (grep-verified); everything else falls through to a default that emits the previous command line **byte-for-byte**, pinned by a test. Those two scenarios are hard-gated on push-to-main and must not regress to enable one that does not work.

## Scenario 5 still reports `skipped` and still exits 1

**Not gated, on purpose.** Gating it would manufacture the false green this harness has already been burned by twice.

## The honest gap, stated in the code as well as here

`shared-l2-segment` stays on the blocker list. The *argument* half cleared; the *proof* half did not — **no frame has ever crossed that segment**, because nothing runs the VMs concurrently. A planned topology that has never carried traffic is a claim, not a capability.

`scenarios.ts`, `run.ts`, `join-implementation-probe.ts` and the 2026-08-13 research doc are updated to say so, because their prose asserted *"emits only per-VM SLIRP NAT"* — which this change made false. `docs/history/pr-reviews/` left alone; those are archives.

Remaining, in dependency order: **(1)** role provisioning (zflash must write a firstboot config to the ESP, or the ISO must accept `--role`); **(2)** concurrent lifecycle (`Qcow2RetentionExecutor` needs background-spawn + wait, honoring the listener-before-connector ordering the socket backend imposes); **(3)** `create-joining-disk`, declared in `MultiVMExecutionStep` and still emitted by nothing.

Repointed both filters and the header. Same class as everything else here: **a check that cannot fire looks exactly like a check that passed.**

## What a green matrix must never be read as covering

**Needs hardware, cannot be faked:** Touch ID / PAM (no QEMU biometric); USB-UUID-bound key derivation — a qcow2/raw image has no real USB serial, so the binding is stubbed and a passing QEMU run **proves nothing about it**; physical re-seat and power-loss-mid-write; real TPM sealing.
