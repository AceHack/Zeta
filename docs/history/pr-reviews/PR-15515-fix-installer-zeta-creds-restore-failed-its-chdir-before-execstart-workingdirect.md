## What

Layer-2 of `081M0WTB5MN`. Fixes the *real* reason phase-2 restore is silent: the unit fails **before `ExecStart`**.

- `full-ai-cluster/nixos/modules/zeta-creds-restore.nix`: `WorkingDirectory = cfg.repoRoot` → `WorkingDirectory = "/"`. The `ExecStart` uses only absolute paths, so cwd is irrelevant; `/` never fails the chdir. Plus an unconditional first line `zeta-creds-restore: ExecStart entered`.
- `src/Core.TypeScript/ci/qemu-full-install-test.ts`: add the `execStartEntered` marker.
- `qemu-full-install-test.test.ts`: drift guards (`WorkingDirectory = "/"`, entered marker).
- Workitem `081M0WTB5MN` updated with the corrected root cause.

## Why

Layer-1 (#15374) moved the precondition checks into `ExecStart`, but the `workflow_dispatch` verification run [32873212247](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/32873212247) — built from that fix — still showed **zero `zeta-creds-restore` lines in phase-2**, not even the new `MISSING precondition` logging. So the unit wasn't skipping on a precondition; it was **failing before `ExecStart` ran at all**.

The service is enabled by default (`common.nix`: `zeta.credsRestore.enable = lib.mkDefault true`), so the only remaining pre-`ExecStart` filesystem dependency is `WorkingDirectory = cfg.repoRoot` (the cloned repo). When that directory is absent as the unit fires (`After = local-fs.target`, early), systemd fails the unit at chdir before `ExecStart`, and every log line — including the precondition gate — is unreachable. The earlier "blob delivery" hypothesis was one layer too shallow; the verification run corrected it.
