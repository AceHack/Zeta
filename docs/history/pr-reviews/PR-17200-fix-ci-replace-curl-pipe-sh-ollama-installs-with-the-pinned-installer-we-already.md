## Description

Scorecard PinnedDependenciesID alerts 690 (mux-swarm-tick.yml:49) and 714
(arc-swarm-fanout.yml:78). Both ran:

  curl -fsSL https://ollama.com/install.sh | sh

mux-swarm-tick is hourly and has 655 runs, so that is 655 fetches of a remote
script handed to a shell as root.

WHAT THE ALERT DID NOT NAME: the fix was already built and these two lanes
never adopted it. agent-heartbeat.yml stopped piping that installer on
2026-08-16 and moved to .github/ollama-pin.json + install-pinned-artifact.ts --
version-addressed URL, SHA-256 cross-checked against two independent sources,
refusal unit-tested in pinned-artifact.test.ts, and proved on a real runner by
verify-ollama-pin.yml on any PR touching the pin. The mechanism, refresher,
verifier and doc all shipped; these two workflows kept the old line. This is
adoption, not new engineering -- inventing a second install path here is the
duplication that registry exists to prevent.

A STEP THAT ERRORED EVERY RUN AND REPORTED SUCCESS. Measured in run
34420600400, which concluded success:

  00:18:02.34  >>> Creating ollama systemd service...
  00:18:05.06  >>> The Ollama API is now available at 127.0.0.1:11434.
  00:18:05.10  Error: listen tcp 127.0.0.1:11434: bind: address already in use

install.sh registers and starts a systemd unit, so the step own "ollama serve &"
could never bind. Backgrounded, so set -e never saw it. Removing the installer
removes the unit, which makes the serve line load-bearing again instead of dead
-- fixed as a consequence of the pinning, not as a separate patch. The fixed
"sleep 5" is replaced by a readiness poll, matching the heartbeat lane.

ALSO: arc-swarm-fanout.yml had no persist-credentials: false on the checkout
that preceded the runtime-fetched installer, while its sibling set exactly that
and named the installer as the reason. One of two identical lanes had the
mitigation. It now has it too.

AN OPEN QUESTION, RECORDED NOT FIXED. In the same run the payload step -- four
hats, each meant to take a completion from the model just pulled -- ran in
9.7 ms (00:18:16.1739702 -> 00:18:16.1836430). Four CPU completions against a
freshly loaded qwen2.5:0.5b cannot take 9.7 ms. That is CONSISTENT WITH
observeWithLlm taking its silent fallback (observe/observe.ts:
"if (result.fallback) return observe(world)"), which returns the deterministic
oracle and prints nothing. Consistent with is not measured: what IS established
is that the workflow cannot tell you either way, and that missing signal is the
defect worth naming. It is a swarm-lane change, so it stays in the work item.

VERIFICATION AND ITS LIMIT: actionlint rc=0 on both files; the install path is
the one agent-heartbeat.yml has run since 2026-08-16. LIMIT -- both swarm lanes
are ubuntu-22.04 while verify-ollama-pin runs ubuntu-24.04. The artifact is laid
into /usr/local and starts nothing, so the image should not matter, but "should
not" is not a measurement; the hourly schedule exercises it within the hour, and
both steps are continue-on-error so a bad pin degrades the tick loudly instead
of stopping it. arc-swarm-fanout has never been dispatched (total_count 0), so
the change is unexercised there by construction.

.github/ollama-pin.json is at v0.32.13 while upstream latest is v0.33.3. NOT
bumped here: a pin bump has its own proof workflow and belongs in its own PR.

**Proved on a real ubuntu-22.04 runner after this PR was opened.** The limit stated
above ("should not matter, but should-not is not a measurement") is now closed for
the install step: `mux-swarm-tick.yml` was dispatched on this branch,
[run 34425003074](https://github.com/Lucent-Financial-Group/Zeta/actions/runs/34425003074),
and concluded `success` with every step green.

```
[pin] ollama 0.32.13 - ollama-linux-amd64.tar.zst
[pin] expected sha256:0fd1dece38a1c6242e8013ce20b597345c5de072ae6b320160edb0e729ef1de1
```

Three things measured on that run:

- The digest was verified before anything from the artifact executed.
- `grep -c "already in use"` over the whole job log is **0**. The bind error that
  fired on every previous run is gone, because the pinned artifact registers no
  systemd unit for the `ollama serve &` to collide with.
- It is also FASTER: 23s install + 13s serve/pull = 36s, against 64s for the
  `curl | sh` step it replaces.
