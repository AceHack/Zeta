## Description

## What

Commits a `flake.lock` for the **root** `flake.nix`, generated with `nix flake lock`. No input upgraded, added, or restructured — the lock records what the flake resolves to today.

Also corrects one now-false clause in `src/Core.TypeScript/hygiene/cluster-tree-consumers.json`, which recorded "There is also no root flake.lock, so this flake's inputs are unpinned."

## The divergence (metered)

`git ls-tree -r origin/main` at `b42fec3757` returns exactly three flake files:

```
flake.nix
full-ai-cluster/flake.lock
full-ai-cluster/flake.nix
```

The cluster flake has been locked all along; the root flake was not. `flake.lock` is **not** in `.gitignore` — the Nix section there covers `result*`, `.direnv/`, `.nix-eval-cache/` and nothing else. So this was a divergence inside the repo, not a policy of not locking. The locked cluster flake is the precedent this restores.

The root `flake.nix` header has meanwhile claimed, since it was written, that *"The flake.lock pins the entire universe."* That sentence was false at every commit until this one.

## Is the root flake live or dead? — **live, but only on human paths**

This is the question that decides what the PR is for, so it was answered before the lock was generated rather than assumed.

**Metered — it evaluates.** `nix flake check --no-build` at the repo root exits **0** against the new lock, evaluating all three `nixosConfigurations` (`control-plane`, `worker-gpu-01`, `worker-gpu-02`), `darwinConfigurations.zeta-mac`, the devShell, the formatter, and all four `nixosModules`. It is not a dead file.

**Metered — CI never evaluates it.** No `nix build` / `nix develop` / `nix flake` invocation anywhere in the tree targets the root flake. The only `nix flake check` in CI is in `build-ai-cluster-iso.yml` and runs with `working-directory: full-ai-cluster`. `bytelock.yml` contains no `nix` at all. There is no `.envrc` and no `.devcontainer/` in the tracked tree.

**Its real consumers are documented manual paths:**

- `nix develop` — `scripts/hooks/README.md` names the root devShell's `shellHook` as **one of the three install paths that must stay equivalent** for the git hooks; `src/wasm-dla/README.md` names the same devShell as the desired-state declaration of the byte-lock toolchain.
- `nixos-rebuild switch --flake .#<host>` for the three hosts.
- `darwin-rebuild switch --flake .#zeta-mac` — the `linux-builder` VM on the maintainer's Mac.

**The repo already knew.** The `cluster-tree-consumers.json` roster entry for `flake.nix` records, verified 2026-08-17: *"`nix flake check --no-build` at the repo root evaluates all three hosts today… NOT verified by CI… There is also no root flake.lock, so this flake's inputs are unpinned."* This PR closes the last clause of a gap the repo had already written down.

So: **not cheap insurance on a dead file, and not a CI supply-chain hole either.** It is an unpinned dependency on the paths a human uses to build a cluster host or enter the toolchain shell — where an unreproducible result is hardest to notice, because nobody diffs it.

## Does anything break?

**No — and the honest reason is that almost nothing consumes it.** Reporting "no regressions" as evidence of safety would overclaim here, so:

- `nix flake check --no-build` → `0` (the one real falsifier; it exercises every output).
- `nix flake lock` re-run → no-op, so the lock is at a fixed point.
- `audit-cluster-tree-consumers.ts` → `0`, "roster matches the tree".
- `lint-clone-at-tag-is-sufficient.ts` → `0` (a lock file is not a resolver; `ace` is still not required).
- Every other consumer of the root flake is a **static text scanner** that reads `flake.nix` and never evaluates it — `mise-pin-parity.ts` (`git ls-files -- *flake.nix`), `lint-clone-at-tag-is-sufficient.ts`, `audit-cluster-tree-consumers.ts`. None of them reads `flake.lock`.
- `build-ai-cluster-iso.yml`'s `paths:` filter is scoped to `full-ai-cluster/flake.lock`, so the root lock does not trigger it. `lockfile-healer.yml` is `bun.lock`-only.
- Note in passing, not fixed here: `audit-dep-currency.ts` hardcodes `full-ai-cluster/flake.nix` as its only Nix input source, so the root flake's four inputs are invisible to the dependency-currency audit as well. Same divergence, different surface.

House style followed — `full-ai-cluster/flake.lock` is lockfile `version: 7`, 2-space JSON, trailing newline, `nix flake lock` output. This file is byte-identical in shape.

## Why a lock rather than a date — the anchor

Microsoft's **MRAN / CRAN Time Machine** had the better ergonomics: one scalar, a date, reconstructed a whole consistent package universe including transitive dependencies. `checkpoint("2018-01-01")` beat any per-project lockfile for legibility.

It died because it was an **appointed hub**. Every one of those calls was a pointer into one vendor's dated archive, and when Microsoft retired the snapshots, every one of them stopped resolving. Exit test (Hirschman 1970): could a consumer resolve without it? No — so it was a hub, not an oracle, and its removal halted the algorithm with no successor.

A `flake.lock` is that same good idea with the fatal flaw removed. It keeps the one-coordinate-yields-the-universe property, but the coordinate is a **content hash** (`narHash`, present on all six nodes here) rather than a vendor's dated URL. Any mirror, any binary cache, any substitutor can serve it, and the bytes are verifiable **without trusting who handed them over**. Concentration was never the defect; enforcement was.

This is also the repo's own rule for verification artifacts, satisfied by construction: the lock is text, diffable, and mergeable — `no-binary-in-proof-lineage`.

**Register:** the divergence, the six pins, the `nix flake check` exit, and the consumer inventory are `metered` (each is a command re-runnable from this tree). The MRAN framing is `consistent with` the exit/appointed-hub discriminator already in `itron-hub-patent-boundary-p2p-is-the-upgrade.md`; it is an argument for the shape, not a measurement.

## Explicitly out of scope

No migration to Nix, no Nix added to CI, no change to `tools/setup/`, no change to `.github/workflows/gate.yml`, and **no input upgraded** — `nixos-24.11` is EOL and `nixos-hardware` is seven days old, but bumping either is a separate, testable decision (there is already a P1 row, `081KSGS9H0008QG0R001EKTS5A`, for the nixpkgs channel). A lock that changed what the flake resolves to would not be a lock; it would be an upgrade wearing one.
