## Description

## The finding

Three telemetry flush lanes — `tick-metrics`, `society-heartbeat`, `lockfile-healer` —
granted `GITHUB_TOKEN` **`pull-requests: write`**. `GITHUB_TOKEN` could not use it.

**Every token binding in each file was enumerated**, not grepped for a pattern:

- `GITHUB_TOKEN` appears **only** as `FALLBACK_TOKEN` — the degraded git-push credential
  the preflight step installs when the PAT is denied. That is a `contents` concern, never
  a PR one.
- The single `GH_TOKEN` binding in each file is `ZETA_PR_ARCHIVE_TOKEN`, on the flush step.
- `flush-via-staging.ts` **errors** (returns 3, printing the remediation) rather than
  falling back to the workflow credential.

`flush-via-staging.ts:47` records why *no* lane can use this grant:

> THE PR CANNOT BE OPENED BY `GITHUB_TOKEN`. The enterprise forbids the Actions identity
> from creating pull requests.

So the grant was **unreachable for its stated purpose** while still conferring **close,
merge, comment and label on every pull request in the repository**.

## Why this is separate from #17152

It was deliberately held back there. The evidence at that point was a grep over the
workflow, and **a grep cannot prove the absence of a fallback.** This lands only after
enumerating every binding and reading the flush script's failure path — which is what
turns "looks removable" into "provably unused".

The same argument already justified the identical removal on `agent-proposal-gated-commit`
in #17152, where the call path was traced to source (`createGatedReviewPullRequest` sets
`GH_TOKEN` explicitly and throws on an empty token).

## Not `agent-heartbeat`

It genuinely falls back to `GITHUB_TOKEN` for `gh pr merge --auto` when
`ZETA_PR_ARCHIVE_TOKEN` is absent or is refused `enablePullRequestAutoMerge`. It keeps
the grant on both jobs.

## Verification

- `actionlint` rc=0 on all three.
- `yaml.safe_load`: each job now holds `contents: write` alone; top level stays
  `contents: read`.

## Honest limit

**This closes no Scorecard alert.** Each job still holds `contents: write`, which
`TokenPermissions` flags on its own. The gain is capability removed, not a number moved —
and that is the whole reason it is worth doing.
