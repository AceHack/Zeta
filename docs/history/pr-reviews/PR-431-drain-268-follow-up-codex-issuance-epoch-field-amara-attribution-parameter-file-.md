  <pre>
  The rationale for `issuance_epoch` being bound into `h_r` claims this prevents circumventing the deprecation gate by rewriting the epoch. Binding does prevent *post-signature mutation*, but it does not prevent an attacker (or compromised signer) from backdating the `issuance_epoch` at receipt creation time, which would still bypass a cutoff-based policy. Consider clarifying the threat model and/or specifying a non-malleable time source/anchor for `issuance_epoch` (e.g., ledger inclusion time, trusted timestamping, or an authenticated monotonic counter) so the gate is meaningful.

  </pre>

different binding]'.

P1 (line 166) — parameter_file_sha name vs BLAKE3 algorithm:
Field name implies SHA-family but the canonical encoding
specifies BLAKE3-256. Added clarification: the '_sha' suffix
is legacy Otto-91 naming (where '_sha' meant 'hash digest'
in that context); the actual algorithm bound by hash_version
= 0x01 is BLAKE3-256. Future schemes may pick different
digest algorithms via the hash_version registry; the field
name stays for Otto-91-prose compatibility.
