## Description

## What this is

The measurement the **existing** repo-split plan lacks. It proposes no cut and changes no workflow and no cache key.

Aaron, 2026-08-26: *"we have a plan to split out to different repos based on our tool chain splits so we can have different caches for different tooling, this is our multi repo plan, we have a lot on this already and a plan that's gone through a few rounds."* This PR supplies numbers for that plan. Every candidate name it uses is round 3's.

Round 3 §5.3 stated its own limit — **"I did not instrument a cache miss"** — and listed **"Check the Actions cache ceiling"** as its first action item. Both are now measured.

## The four results

1. **The cache is a sawtooth, caught live — twice.** Peak **30.86 GiB**; sweep 1 deleted **41 entries / 23.06 GiB in one 61-second window**, landing at 9.68 GiB; sweep 2 five minutes later deleted 24 entries / 10.32 GiB, landing at 9.07 GiB.
2. **The ceiling has NOT been raised — measured, not assumed.** Both sweeps converged on ~9–9.7 GiB ≈ 10 GB. A raised ceiling would sweep to the raised value. `actions/cache/usage-policy` is still 404 at this credential, so this comes from the eviction's own behaviour rather than a settings page.
3. **80% of the evicted bytes had never been read.** 28 of the 41 evicted entries (18.39 GiB) had `last_accessed_at == created_at` at deletion — terminal, so no later hit can correct them. A **1,158 MB Python toolchain cache lived 126 seconds and was never restored once.**
4. **The partition arithmetic does not close, and that is the finding.** Under round 3 §7's own candidates, **`Zeta-core` alone measured 11.17 GiB charged at peak** — over the ceiling by itself, before any share of the two union blobs.

## Method note that matters for every future reading

**The `usage` endpoint lags by gigabytes.** Same repo, 58 seconds apart: `cache/usage` read 15.18 GB while the itemised `actions/caches` endpoint read 22.08 GB. It then sat frozen for three minutes while the itemised list moved every sample. Round 3's 11.57 GB, a prior agent's 16.75 GB and today's readings were **all correct at the instant taken** — they are samples of a sawtooth, not disagreements. All figures in the doc come from the itemised endpoint, diffed by cache `id`, which is what makes eviction observable at all.

## Why the arithmetic does not close (all measured)

- **59% of the logical working set sits in blobs no candidate owns.** `install-v2` / `install-*-full` / `full-verify-v2` cache **one tar containing every toolchain at once** (mise + dotnet + elan + rustup + cargo), referenced by **23 job definitions**. Round 3's union thesis in its most physical form.
- **The split partitions the toolchain axis and leaves OS×arch untouched.** `dotnet-macOS-ARM64` is **1,858 MB — 20% of the whole ceiling for one leg of one toolchain**, and 4.5× the Linux-X64 entry for the same SDK.
- **`Zeta-core`'s logical footprint (4.81 GiB) fits; its 2.6× ref multiplier is what carries it over** — and round 3 §6 measured that its dotnet component absorbs 96% of build-touching commits, so that multiplier travels with it.

## Union thesis corroborated on a second axis — invalidation, not size

`hashFiles('.mise.toml', 'tools/setup/**', 'global.json')` puts `tools/setup/persona-keys/**` (FROST/Shamir/TPM/biometric TypeScript and its tests) inside the union blob's cache key. Measured over 30 days: **38 of 92 commits — 41% — invalidated a 1.2–1.5 GB blob on every OS/arch leg while touching zero toolchain-installation files.** Five mutually-unhittable `install-Linux-X64-{base,full}` key hashes appeared in one 35-minute window.

That is DV2.0 violated at the cache layer: a fast-changing satellite packed into the same key as a slow-changing hub.

## Findings for Aaron — reported, not adjudicated

1. `Zeta-core` does not land under 10 GB. Whether that calls for a further cut on an axis the plan already has, or means the per-leg install subset is the real fix, is not decided here.
2. **The per-leg install subset looks like a PREREQUISITE for the split's cache goal, not a follow-up.** Checked, not inferred: `mise.sh` runs `mise install --yes` from the repo root, which provisions **everything `.mise.toml` declares**, and the only subsetting anywhere in the tree is the slim/full tier merge. **The union blob's size is a function of `.mise.toml`, not of which repo you are in** — a `zeta-formal` repo running today's install script would still provision dotnet, rust and go, carrying a ~1.2 GB blob for a component whose own toolchain cost is 0.02 GiB. A repo boundary relocates these blobs; it does not shrink them. Named and handed back — not specified, not implemented.
3. **The cache axis is silent on `zeta-formal`**, round 3's strongest closure cut: its `elan` entries total 0.02 GiB. The cut's case stands on closure and clone bytes; cache pressure should not be cited for it.
4. **A poisoned 172 KB `dotnet-Linux-X64` entry is live on `main`** under a key that should hold ~410 MB. Any job matching it gets `cache-hit: true` on a near-empty archive. Reported, not fixed.

## Two hypotheses tested and FALSIFIED (§4.4)

Recorded because acting on either would have changed correct code.

- **"The never-read caches are a save/restore key mismatch."** Structurally impossible — a mismatch needs *split* `actions/cache/restore` + `/save` steps, and the repo has exactly **one** split usage (a deliberate restore-only step). Everywhere else the combined action reuses the restore key by construction. Replaced by three measured mechanisms: key churn outrunning reuse (dominant), eviction before reuse, and `codeql-trap-*-<40-hex>` keys that embed the **commit SHA** (7 keys, 162 MB, none reusable by construction — `codeql-action`'s design, not ours).
- **"The `install-v2` thrash loop is a save firing when a hit should have prevented it."** The sample data settles it: for every `(key, ref)` with two cache ids, **the ids never coexist**. The first was deleted by the 08:23:48 sweep; the save then fired because there was genuinely nothing to hit. Correct behaviour, a symptom of pressure — not a defect, and it needs no code change.

## Honest limits

- The ceiling inference comes from where two sweeps stopped, not from the settings page (404).
- **No CI job failure is attributed to a cache miss here.** The correlation with round 3's "82% died provisioning the toolchain" is plausible and **not** established — joining them needs per-job `cache-hit` outputs this note did not collect.
- Cache write volume (~69 GiB/hour) is a **lower bound**; 60-second sampling cannot see entries born and evicted between samples.
- Ref-scope duplication ⇒ base-branch miss follows from `actions/cache` skipping save on an exact hit; not instrumented at job level.
