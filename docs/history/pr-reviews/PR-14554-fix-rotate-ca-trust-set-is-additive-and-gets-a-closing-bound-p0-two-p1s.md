## Description

## The defect, verified before it was fixed

`tools/setup/persona-keys/rotate.ts` `rotateCaKey` wrote the trust set as literally
`[currentActive, new]` and never unioned with the self-CA lines already in
`trusted-user-ca-keys.pub`. Rotation #1 gave `[CA1, CA2]`; rotation #2 gave `[CA2, CA3]`,
**evicting CA1 while device certificates it signed were still inside their `-V` window**.
Reachable from the shipped CLI with no typo: run it twice. Found by Mateo (PR #14510, tests
and `docs/BUGS.md` only, deliberately no source change).

Reproduced independently against `origin/main` before touching anything — throwaway `HOME`
and `repoRoot`, real `ssh-keygen`, fake biometric door, fingerprints only:

```
CA1 (signed the existing cert) = SHA256:4x87A86g9kKRQ1HakMEQK4FPrDF4nxO6mIRwGXq6n0I
cert signer/validity           = {"signer":"SHA256:4x87A86g...","valid":"from 2026-08-23T19:48:00 to 2027-08-22T19:49:18"}
after rotation #1: trustSet=[CA1, CA2]   CA1 still trusted? true    cert still verifiable? true
after rotation #2: trustSet=[CA2, CA3]   CA1 still trusted? false   cert still verifiable? false
```

Same script after the fix: `after rotation #2: trustSet=[CA1, CA2, CA3] ... true / true`.

## The design: two halves, because either alone is a defect

Mateo's cost was the load-bearing part of the brief. *Union the sets* is not the fix on its
own — retaining every prior CA forever makes each retired CA a **permanent trust root**, which
is worse than the defect being repaired. So:

**OPENING — rotation is additive, always.** `rotateCaKey` unions the incoming pair with every
self line already present, and preserves peer lines **and lines carrying no recognised marker**.
That last one was a second silent eviction hiding in `parseTrustSetPeers`: a hand-added root
without a `# <name> cluster CA` comment was dropped on every rotation, so *"we preserve peers"*
was true while *"we preserve trust roots"* was not. A rotation can no longer remove a trust root
— not as a side effect, not under any flag.

**CLOSING — a CA leaves only through `--finalize`, on evidence.** A separate act that rotates
nothing and drops a retired CA only when a **certificate census** proves no *unexpired*
certificate names it as signer. Its own biometric prompt names every CA it would drop.

### Why narrowing is NOT automatic, and never happens during a rotation

The census reads certificates committed under `<repo>/machines` **in the caller's clone**. A
stale clone and an estate with nothing left to protect are indistinguishable from inside the
process, and guessing wrong re-creates the P0 in slow motion. So the eviction direction is a
separate, operator-approved act — the standing position that the agent executes and the human
authorizes via biometric, applied to the one step here that is consumer-visible and hard to
reverse. The P0 fix itself has **no dependency on the census being complete**; only the
narrowing does.

### The eligibility rules, all fail-closed

A self-CA line may be dropped only when **every** one holds. Each failure keeps the CA and
carries its reason into the readout:

| # | Rule | Why the refusal direction |
|---|---|---|
| 1 | not the ACTIVE signer | never drop the key signing going forward |
| 2 | a census could be built at all | no doors wired ⇒ absent evidence, not evidence of absence |
| 3 | the census is COMPLETE | one unparseable cert could be the one that names it |
| 4 | the census found ≥ 1 certificate | zero looks exactly like a mistyped `--repo-root` |
| 5 | no UNEXPIRED cert names it | the actual closing condition |

Peer CAs and unrecognised lines are never candidates: this cluster did not issue them and cannot
reason about what they protect. The set is swept **per CA**, not all-or-nothing.

**Rotation is never blocked** by a large trust set — refusing to rotate during a suspected
compromise would be worse than the surface. Instead every rotation *reports* which windows have
closed and prints the exact `--finalize` command. Stated tradeoff, not an oversight.

### The census is checked, not asserted

`ssh-cert-census.ts` parses the OpenSSH certificate wire format directly (RFC 4251 §5 encodings,
`PROTOCOL.certkeys` field order) instead of shelling out to `ssh-keygen -L` and parsing English —
so it is pure, injectable and DST-replayable. A hand-rolled wire parser is worth exactly its
differential, so `ssh-cert-census.test.ts` compares it **field for field against real
`ssh-keygen -s` output**, across ed25519 / rsa / ecdsa certificate layouts (the subject-field-count
table is the part that yields plausible garbage rather than an error when wrong). Unknown key
types are refused, never guessed at. `now` is injected, never ambient (§13); this is the local
"is it stale **to me**" use that `local-time-never-enters-the-shared-fold` permits.

## The two P1s, same pass

* **`formatRotate` printed the guarantee unconditionally** and byte-identically on the run that
  falsified it. It is now **computed** from a measured `TrustSetDelta`: `∅-blast-radius VERIFIED`
  with this run's counts, `NOT ESTABLISHED` naming every CA that left, or — on a run that never
  touched the trust set — **no line at all**. The old line printed even for `--ports machine-key`.
* **The retired-key slot was one fixed path** and `movePrivate` renamed onto it, so rotation #2
  destroyed rotation #1's retired private key. Retirement now takes the first **free** generation
  and **refuses** when the archive is full rather than choosing which key to destroy — that is
  `export-or-destroy-key`, a ceremony (`ceremony-gate.ts`), not a rename.

## Safety

No live key, certificate or credential was touched, read, printed or logged. Every test runs in
`mktemp` HOME + repoRoot against a **fake** biometric door (`realBiometric` is not imported by
either new test file); keys are compared by **SHA256 fingerprint only**. Work was done in a
throwaway clone, never the shared checkout. No `--admin`, no widened check.

## Deliberately left alone

* **RR-7 / the open port dispatch (P1).** Its pin is still GREEN because the defect is still
  there. It is a different defect class — dispatch closure, a type-level change to `planPort` and
  `rotatePort` — with no interaction with the trust-set arithmetic, and it is not reachable from
  either shipped CLI. Folding it in would have made both harder to review. Its `docs/BUGS.md` row
  now records that decision so the row does not read as an oversight.
* **Destroying retired private key material.** Generation-suffixing preserves it; nothing here
  deletes a key. That is `export-or-destroy-key`, a ceremony requiring the human maintainer.
* **`prettier --check`** on `tools/setup/persona-keys/**` — already failing on `origin/main` for
  ~79 untouched files in that tree. Reformatting them here would bury the fix. The repo's own
  `lint:typescript` (tsc + Prettier + style) passes.
* **Automatic narrowing during rotation**, and **blocking a rotation** on a large trust set. Both
  argued above; both are choices, not omissions.
* **Any live rotation, revocation or ceremony.** Advisory lane. The mechanism is fixed; firing it
  on the estate is the maintainer's, and `rotate-cli.ts` still defaults to a dry run.

## Not proven here

No real sshd handshake (certificate acceptance is asserted by the rule sshd applies — signing-CA
fingerprint present in `TrustedUserCAKeys`), no real biometric, no real HSM, no live estate. The
`--finalize` census sees only certificates committed in the caller's clone; that limit is why it
refuses on an empty or incomplete census and why it is human-approved.
