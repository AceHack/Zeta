## Description

## What

`ace` read every package document and registry index through some spelling of

```ts
isHttp ? await (await fetch(u)).text() : readFileSync(u, "utf8")
```

**six** times, plus a seventh in `registry-remote.ts`. No byte cap, no deadline, no scheme check, and — the one that bit in practice — **no status check**: a 404 body was parsed as a package manifest and surfaced as a JSON syntax error, which is the wrong diagnosis printed with total confidence.

CodeQL reports the **sinks** those bytes reach: four lockfile writes in `ace.ts` (**#208 #209 #210 #211**), the store extraction in `store.ts` (**#199**), and the registry cache write plus its conditional-request headers in `registry-remote.ts` (**#196 #202**).

Those flows are what a package manager **is**. They are not removable and this change does not pretend to remove them. What it removes is the unboundedness of the doors they come through — and **the cap belongs at the door, because there are five sinks and one door**.

| door | replaces |
|---|---|
| `ace.ts` → `readPackageDocument(source)` | six call sites |
| `registry-remote.ts` → the conditional index fetch | the cache's own door |

`readPackageDocument` also unifies the URL and the path branch: a local source goes through `readFileBounded` under the same cap, so *where did this manifest come from* stops changing what protects you from it.

## registry-remote is the interprocedural one, and worth reading closely

The conditional-request headers are read out of the on-disk cache and sent over the network (**#202**); what comes back is written to the cache (**#196**). Those two **are** the cache — neither is removable without deleting it — and they sit several frames apart, which is exactly why no regex found them.

What the fetch gains:

* **a cap** — a registry index larger than memory is now a refusal, not an OOM;
* **a deadline**, and this matters more than it looks: there is a **cache on disk**, so an unresponsive registry should fall back to it in seconds rather than hang `ace install` forever with the answer already local;
* `failOnHttpError: false`, because 304 and non-200 are **answers** here rather than failures — each falls back to the cache. A truncated body is the one thing that is neither, so it is refused rather than parsed. Half a registry index that happens to parse is a package resolver's worst input.

## safe-io gains one field

`FetchOutcome.headers` — lower-cased names, copied out rather than handed over live (the `Response` is gone by the time the call returns). A conditional-request cache cannot be built without `etag` / `last-modified`, and a caller forced back to bare `fetch` to read one header loses the cap, the deadline and the scheme check along with it.

## And one vacuity admitted rather than shipped

The first draft asserted that `collectHeaders` lower-cases the names. It does call `toLowerCase()`, but **the Fetch spec already guarantees lower-cased names** from `Headers.forEach`, so removing the call changes nothing observable — **measured: that mutant survived the whole suite.** The assertion was a check that could not fail.

It is gone. The call stays as an explicit statement of the field's contract, and both the docstring and the test now say plainly that no test pins it. The falsifier that *does* work — `headers: {}` — kills the remaining test.

## Also

Lockfile and cache writes move to `writeFileOwned` with an explicit `0o644` — the mode `writeFileSync` produced under the umask, kept exactly — so a write failure is a `Result` rather than an exception out of the middle of an install.

`store.ts`'s slice-3 note is updated to point at the new door. **Its alert stands, correctly:** the http→file write *is* the package manager's function.
