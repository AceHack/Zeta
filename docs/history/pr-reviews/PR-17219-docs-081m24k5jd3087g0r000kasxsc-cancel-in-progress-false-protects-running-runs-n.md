## Description

Recorded so the falsifier for the cancellation fix is not misread in either direction.

`cancel-in-progress: false` protects a workflow that is RUNNING. It does not protect one that
is PENDING: when a newer run claims the concurrency group, GitHub keeps the newest pending run
and cancels older pending ones. A burst of pushes can therefore still drop analyses that never
started.

Observed within a minute of the fix landing, 2026-09-10:

  run 34429876121, head a9151aba -- the fix's OWN merge commit, carrying the fix in its own
  workflow file -- cancelled at 02:33:29, one second after the next push queued at 02:33:28.
  `total_count: 0` jobs. It never started, which is what identifies this as the pending case
  rather than the setting failing to apply.

So the expected outcome of the fix is a LARGE REDUCTION, not zero. The sibling workflow is the
calibration: `scorecard.yml` has run `cancel-in-progress: false` all along and still cancels
~3% of runs on `main` (n=99), against `codeql.yml`'s 62% before the change.

Why this is worth a commit rather than a note in a report: the finding filed as PR #17211
hands the next person a re-runnable ratio, and a residual few percent is what SUCCESS looks
like. Read as failure it would justify reverting to the configuration that produced 62% --
concluding a working check is broken, which is the same class of error as believing a broken
one works, pointed the other way. The number needed its interpretation committed next to it.

The workflow file had already recorded 80.7% cancellation on `main` (n=300, 2026-08-25..26)
in a comment two weeks before this fix, alongside the 102-alerts-falsely-closed incident it
caused. Measuring it was not the missing step.
