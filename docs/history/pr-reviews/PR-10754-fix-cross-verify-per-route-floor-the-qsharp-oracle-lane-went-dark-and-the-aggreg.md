## Description

## The lead, and the answer

An agent flagged that a cross-verification oracle lane **shelled out to a missing `.venv/bin/python3` three times and still reported 0 fail**, and asked someone to confirm it wasn't a vacuous pass.

**It was one.** Reproduced on a fresh worktree, raw exit code of the bare command:

```
$ bun test tests/cross-verification/_harness/cross-verify-ir.test.ts
/bin/sh: .../src/Core.Python/.venv/bin/python3: No such file or directory
/bin/sh: .../src/Core.Python/.venv/bin/python3: No such file or directory
/bin/sh: .../src/Core.Python/.venv/bin/python3: No such file or directory
 5 pass / 0 fail / 12 expect() calls
RAW EXIT: 0
```

Two corrections to the brief, both narrowing rather than widening it — flagged as required.

1. **It is the Q# lane, not the Python lane.** The Python lane calls bare `python3` and runs fine. The Q# lane runs a `qdk` script through the venv interpreter. "Three times" is exactly right: `crossVerify` is called by three tests, one Q# invocation each.
2. **CI is not currently vacuous for this case.** See the scope section below. The observation was accurate; its blast radius is smaller than the headline suggests, and saying so is part of the answer.

## 1. Does the lane execute?

Yes — when its interpreter exists. Measured participation:

| condition | lanes that executed | dark | raw exit |
|---|---|---|---|
| fresh worktree, no venv | **6** — typescript, python, go, csharp, rust, fsharp | `qsharp` | **0** |
| after `uv sync --project src/Core.Python` | **7** | none | 0 |

The venv is gitignored and self-ignoring (`src/Core.Python/.venv/.gitignore`), so a fresh clone never has it. CI creates it in a `QDK venv setup (uv sync)` step. The lane is fine; **its absence was what went unreported.**

## 2. Did anything notice?

No — and two independent mechanisms produced the silence.

**The floor was aggregate.** `expect(result.languages.length).toBeGreaterThanOrEqual(6)`, in three places, over **seven** lanes. Six live lanes satisfy the floor on the seventh's behalf. N drops to 6 and the claim does not. This is precisely the shape #10744 established an aggregate floor cannot detect: redundancy in the numerator hides a zero.

**The Q# test was conditionally vacuous.** `if (hasQdk) { expect(...) }` — when the import check failed, the body never ran, **zero `expect()` calls executed, and the test passed.** The expect count is the receipt: **12** without the venv, **13** with it. The one missing assertion is the whole finding.

Compounding both: the toolchain-presence test checks `bun, python3, go, rustc, dotnet` via `which`. The Q# lane's interpreter is a **gitignored venv, not a PATH tool** — so the presence gate checked every prerequisite except the one that was absent. The only signal was `/bin/sh: ...: No such file or directory` on stderr, which no assertion reads.

## 3. How many oracles, and does anything assert it?

**7 available, 6 running in the reported condition.** Before this PR **nothing asserted 7** — the only arity assertions in the file were the three `>= 6`, while the file header called itself a *"7-language byte-lock oracle (CI-enforced)"* that *"FAILS if expected toolchains are missing (not just warns)."* The docstring claimed the stronger property; the floor implemented the weaker one.

## Scope — the honest bound

CI's `full-verify` job runs `smoke-7-toolchains.sh` **before** the cross-verify step, and that script hard-fails on a missing venv or unimportable `qdk`. **So the missing-venv vacuous pass is not currently live in that CI job.** The protection is a neighbouring step in the same job, not the oracle's own floor — it survives only as long as nobody reorders the steps, splits the job, or invokes cross-verify from another workflow. It is live today for local `bun test`, which is where it was observed.

And the neighbour is weaker than it looks. `smoke-7` checks `import qdk`. Verified with a stub `qdk.py` exporting no `Context`, on `PYTHONPATH`:

```
$ PYTHONPATH=/tmp/qdkstub CI=true ./tools/setup/common/smoke-7-toolchains.sh
  qdk importable
✓ All toolchains functional
RAW EXIT: 0
```

Toolchain *presence* is not lane *execution*. A `qdk` that imports but whose API has moved leaves the lane dark and smoke green. (Credit where due: the pre-existing conditional test *did* catch this particular variant — exit 1 — because `hasQdk` was true. It was vacuous specifically in the branch where the venv is absent, which is the reported one.)

## 4. The fix — per-route, never aggregate

- **`ORACLE_LANES` is exported** from `cross-verify-ir.ts`. The byte-lock's arity now has exactly one named home, and it is asserted.
- **`crossVerify` reports `laneCases` and `darkLanes`.** A lane is credited for inputs it actually produced a value for — not for failing to throw.
- **Every lane must contribute >= 1 executed case**, asserted per lane, with the lane name and its cause in the failure message. **No aggregate floor added.**
- The vacuous conditional is replaced by an **unconditional** prerequisite test naming the venv path and the `uv sync` remedy.
- The CLI exits non-zero on a dark lane instead of printing a warning next to a success line.

## Boundary

Did not touch `src/wasm-dla/` or `bytelock.yml` — a sibling agent is auditing the wasm byte-lock substrates. **Same defect class, different mechanism**, so no cross-boundary edit was warranted: theirs is artifacts that were never built or cannot load; this is an interpreter that cannot be found, hidden behind an aggregate floor. The shared lesson is the one worth carrying: *a lane that does not run reduces N without reducing the claim.*
