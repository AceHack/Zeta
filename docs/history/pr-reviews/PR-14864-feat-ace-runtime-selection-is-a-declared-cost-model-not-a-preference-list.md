## Description

## What this is

ace's runtime selection becomes the **output of a declared cost model** computed against the host,
rather than a hardcoded preference list. Aaron's framing: *"imagine every install has a cost that can
be quantified... our ultimate ace dependency order on what is enabled."*

No installer one-liner and no publish workflow land here. **The publish leg needs four decisions from
you (§7 of the doc) and I stopped rather than guessing. No registry entry was created and nothing
publicly visible was configured.**

## The design in three lines

| module | answers | kind |
|---|---|---|
| `runtime-probe.ts` | which toolchains exist here | observation |
| `runtime-candidates.ts` | what each rung costs and unlocks | declaration |
| `runtime-cost.ts` | given those, what to do | pure function |

**Cost is a FACT; enablement is a QUALIA; they are never fused.** Per your correction — *"dotnet has a
huge enablement on every os is a qualia over time not a fact"* — costs are measured with a method,
host and date; enablement scores are attributed, dated and marked `unmetered-by-nature` (not "not
measured yet", but *not the kind of thing that gets measured*). `rank()` takes an explicit enablement
weight so the ordering is **conditional and says so**, and `sensitivity()` reports how far the
judgment must move before the winner changes. A peer can dispute the judgment without disputing the
bytes.

**Trust rank dominates cost** — source you recompile is source you can verify; a prebuilt binary is
bytes you must trust. **"Toolchain missing" is a return value**, not a log line. A third probe state
(`indeterminate` = THE CHECK DID NOT RUN) stays distinct from `absent`, reusing the repo's existing
`RootEvidenceState` vocabulary rather than coining one.

## Lead finding: the computed ladder DISAGREES with the stated ladder

Judgments were declared first and **the model was not tuned to reproduce the expected order**
(`numerology-vs-number-theory.md`). On every host profile the answer is `source-on-bun` or
`TOOLCHAIN MISSING`. Rungs 3 and 4 never appear — not because they rank badly, but because they are
unbuildable today:

| rung | state | measured evidence |
|---|---|---|
| `source-on-bun` | works | `ace.ts list` rc=0; keygen/trust/registry exercised |
| `source-on-node` | **blocked** | rc=1 `ERR_MODULE_NOT_FOUND`; 16 extensionless specifiers in a 24-file closure. Rewriting exactly those 16 made node run it — rc=0, output identical to bun. Also needs npm `@noble/hashes` (proven by an isolated run with no `node_modules` ancestor). **A 16-specifier repo change away from real, not a rewrite.** |
| `portable-wasm` | **blocked** | TypeScript does not compile to wasm. Needs an AssemblyScript rewrite or a JS engine in wasm. `wasm-dla/bytelock/` proves we can *produce* wasm but every module there is a hand-written numeric kernel, not a TS port — not precedent. |
| `native-dotnet-aot` | **blocked** | ace is TypeScript; there is no .NET ace. Plus §F# below. |
| `native-bun-compile` | works | 63,627,746 B (**61 MiB**), runs |

**F# NativeAOT is a false green.** `dotnet publish -p:PublishAot=true` on a hello-world F# app returns
**rc=0**, emits **zero** IL2*/IL3* trim warnings, and produces a 1,134,392-byte binary that **crashes
on execution: rc=134, `FileNotFoundException: FSharp.Core`.** The mitigation attempt
(`TrimMode=partial` + `TrimmerRootAssembly`) **failed to build (rc=1)**, so it is unproven, not
disproven.

**Second finding: the enablement dial currently changes nothing.** `sensitivity()` reports one band on
every profile — trust rank dominates and only one rung is viable. The apparatus is built correctly and
is **not yet earning its keep**. Worth knowing before anyone calls the cost model validated.

## Register

`metered` — every byte figure (method + host + date recorded beside it). `unmetered` — node and wasm
rung costs, each stating *why* there is no number. `unmetered-by-nature` — every enablement score,
permanently. **The chooser itself is `unmetered` as an installer**: it has never run on a clean host.
A real clean-host test needs a container/VM with no bun, node or .NET, booted from a pinned image,
running the one-liner and asserting all three outcomes. That does not exist; this is not validated.
