## Description

## What was wrong

`src/Renderers/website` was named in `.github/dependabot.yml` and in **no workflow**.
Verified before changing anything — `grep -rl "Renderers" .github/workflows/` → **rc=1, zero files**.
Root `tsconfig.json` also excludes `src/Renderers/website/**`, and the `lint:eslint` roster omits it,
so the blocking `lint (TS)` job never saw it either. Dependabot proposed version bumps against a tree
that nothing built, typechecked, or tested.

It also **could not be installed from a clean clone**. Reproduced independently in a fresh copy with
no `node_modules`:

```
 ENOENT  ENOENT: no such file or directory, open '.../patches/wouter@3.7.1.patch'
AS_IS_INSTALL_RC=254
```

## Why the patch was removed rather than committed

Decided on evidence. Borrowing the sibling's copy of the same patch and installing **still fails**:

```
 ERR_PNPM_PATCH_NOT_APPLIED  The following patches were not applied: wouter@3.7.1
 Either remove them from "patchedDependencies" or update them to match packages in your dependencies.
EXP_A_WITH_PATCH_RC=1
```

pnpm names two options and only one works here:

- The key is pinned to an **exact** version that no longer resolves — the manifest asks `wouter@^3.3.5`,
  which resolves to **3.10.0**.
- The patch is a Manus scaffold shim collecting routes into `window.__WOUTER_ROUTES__`. **Nothing in this
  repository reads that symbol** — its only occurrences are inside the patch text itself.
- The sibling `demo/identity-dla-site` (same scaffold, same `"name": "identity-dla"`, same wouter range)
  **already removed the entry** in `0e96bdd31f`.

`overrides` is left untouched — it does not block install, and removing it would change resolution for
no reason. Verified in a clean tree built from `git archive` with no `node_modules`:
`pnpm install --frozen-lockfile` → **rc=0**.

## The new job

`lint (Renderers/website)` copies the sibling `lint-identity-dla` shape rather than inventing one: same
pinned runner, same SHA-pinned actions, install → check → build, **no caching** (queue is saturated,
cache over budget; ~20s of real work). pnpm is resolved from the site's own `packageManager` pin so YAML
and manifest cannot drift.

It runs `vite build`, **not** `pnpm build`: that script chains `esbuild server/index.ts`, and this project
has **never** had a `server/` directory — only `client/` was ever committed — so `pnpm build` cannot
succeed here.

It is also claimed in `build-graph.json` by a new `ts:src/Renderers/website` target. Adding the job without
that made `lint (build-graph completeness)` fail, correctly:
`[C/unclaimed-job] gate/lint-website — no target claims this job`. It is **not** added to
`INFRASTRUCTURE_JOBS`, which is for jobs owning no sources.

Like `lint-identity-dla`, this job is **deliberately not** in `gate (required)`'s `needs` — a **drift check,
not a floor**. Adding it there is a treaty amendment and stays with the consent path.

## Proof the job can go red — both halves observed on CI

| step | evidence | result |
|---|---|---|
| **install** | run `32948772847` — `ERR_PNPM_OUTDATED_LOCKFILE`, **unprompted** | 🔴 |
| **typecheck** | job `98117804407` — install green first (`Done in 6.1s`), then 3× `TS2304`, exit 2 | 🔴 |
| **whole job** | `61c480cdb2` | 🟢 |

The install red was not staged: three Dependabot bumps landed on `main` mid-branch —
`react-day-picker ^9.11.1→^10.0.1` (**semver major**), `esbuild ^0.25.0→^0.28.2`,
`vite-plugin-manus-runtime ^0.0.58→^0.0.59`. `pull_request` builds the *merge* commit, so main's newer
manifest met the older lockfile and `--frozen-lockfile` failed closed. **That is the Dependabot guard
firing on a real bump within hours of existing.**

The typecheck red is the one that matters: install passed *before* it, so the failure is the step under
test rather than an earlier guard firing — and `vite build` passes a type error, so `check` is
independently load-bearing. The break was reverted; `toggle-group.tsx` is byte-identical to `61c480cdb2`.

Locally, a third mutation (unresolvable CSS `@import`) fails **build** while install and check pass — so
each of the three steps catches something the other two cannot.

## The 4 pre-existing type errors — fixed, not scoped around

Typecheck is green **without widening anything**:

- **3× TS2304 `Cannot find name 'VariantProps'`** — a dropped
  `import { type VariantProps } from "class-variance-authority";`. The sibling's copy of this file has the
  line. Type-only, no behaviour change.
- **1× TS2307 `Cannot find module '@shared/const'`** — dangling by construction: tsconfig maps `@shared/*`
  → `./shared/*` and this project has **never** had a `shared/` directory (`git log --all` over that path
  is empty). Nothing imports the two constants, so they are defined locally as the sibling did. Both are
  inert placeholders with zero consumers, commented as such.

The `react-day-picker` v10 major is genuinely covered, not merely resolved:
`client/src/components/ui/calendar.tsx` is inside the tsconfig `include` and imports
`DayButton, DayPicker, getDefaultClassNames`, with `react-day-picker@10.0.1` in the lockfile.

## Known blocker — NOT introduced here

`lint (TS)` (a **required** check) fails on `src/Core.TypeScript/observe/f2-role-correlation.ts` with
TS6133 for unused `writeFileSync`, `join`, `falseNegativeRate`. That file is **absent from this branch's
diff against main** and carries the same unused imports on `origin/main`. Pre-existing breakage on main;
this PR neither causes nor fixes it, and it blocks this PR as it blocks everything else.

## Not verified / left alone

- **Pre-existing:** `demo/identity-dla-site/patches/wouter@3.7.1.patch` is still committed and orphaned
  there; this PR does not touch the sibling.
- **Pre-existing:** the website's `pnpm` devDependency (`^10.15.1`) disagrees with its `packageManager`
  pin (`10.4.1`). Changing it would alter resolution, so it is left alone.
- The `data-panel-group-direction` half of the `react-resizable-panels` v4 break is **not** catchable by
  this job — a dead Tailwind selector is not a type error. Named rather than papered over; that is why
  `resizable.tsx` carries its own explanatory comment.
