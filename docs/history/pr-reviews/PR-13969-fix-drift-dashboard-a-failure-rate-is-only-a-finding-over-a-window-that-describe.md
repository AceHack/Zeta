## Description

## You were right, and the fix is `not-yet-due` on the other axis

The `MOSTLY FAILING` rule counted the last N concluded runs **with no bound on the span they cover**. For a high-frequency lane 20 runs is an hour and the rate means what it says; for a rarely-run one 20 runs can be a quarter, and one old incident then dominates the verdict **permanently** — passing runs arrive too slowly to dilute the window before someone stops trusting the dashboard.

| check | reported | actually |
|---|---|---|
| `vocab-hygiene` | RED, "12 of 20 concluded runs failed" | **every failure from June**; fixed, passing every run since 2026-06-10 |
| `agent-proposal-gated-commit` | RED, "2 of 3 failed", "red for 5d" | its **entire history** is failure, failure, success inside about an hour on 08-17 — a fix landing |

That one refuses to call a trigger dead before it has had an opportunity to fire; this one refuses to call a lane broken off evidence that has stopped describing it. Same generator, same cure.

## The bound — all four things you suggested

1. **Time-bounded window.** The rate is over concluded runs inside `rateWindowSeconds` (7d), not "the last N whenever they happened".
2. **Insufficient data is not a verdict.** Below `minConcludedForRate` (5) concluded runs inside the window there is a small sample, not a rate — **no rate claim, and never a clean bill of health**. The row keeps its own latest verdict, so a check whose newest run failed stays red.
3. **Recency can clear it.** `recoveryPassStreak` (5) consecutive passes since the last failure clears a rate finding. A lane that broke, was fixed, and has passed that many times running has earned its way out.
4. **The window is printed in the row**, the way coverage is:
   > `MOSTLY FAILING over 7d (15 of 20 concluded runs failed, 2026-08-18T00:36:18Z .. 2026-08-22T18:3…, 0 consecutive pass(es) since the last failure)`

The producer now reports **timestamped outcomes** (`concluded: {at, passed}[]`) rather than bare counts, and the fold owns all the windowing. That split is the real fix: the producer says what it saw, the policy decides what counts as recent. A bare `concludedRed: 12` cannot be windowed by anyone.

## An error inside the fix, caught by its own tests

My first `recovered` definition was *"every failure predates the newest pass"* — which is true of **any** lane whose most recent run passed, and since the rate rules only run when the newest verdict is green, that definition **nullified the entire rule**. Four of its own tests went red immediately. Recovery is now a **streak**, which is what you actually described and what I should have written first.

## Two bad measurements of my own, for the record

While diagnosing this I twice nearly reported a false finding — the same trap you describe:

- I ran `grep -c $'\000'` in zsh to count NUL bytes; zsh collapsed it to an empty pattern, so it matched **every line** and I read `318` as "318 NUL bytes". It was the line count.
- I then flagged `pr-archive.ts` as corrupt on `main`. It contains `U+FFFF`, a noncharacter — well-formed UTF-8 that only my deliberately-strict validator rejects, and which `tsc` accepts. **Not a defect.**

What *was* real: `generate-metrics.ts` in **my clone** had a `0xFF` byte where the `x` in `prefix` should be — silent local corruption, `origin/main` unaffected, `git fsck` clean, restored. Worth flagging only because it means a measurement taken from a working tree can be wrong in ways the object store never shows.
