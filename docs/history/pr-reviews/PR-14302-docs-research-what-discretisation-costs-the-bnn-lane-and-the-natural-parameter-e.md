## 1. Yes, discretisation costs three things — and truncation is the one that bites

| case | exact | grid ±5, N=201 |
|---|---|---|
| 5 in-range observations | μ=0.833333, var=0.166667 | identical to 6.66e-16 |
| **one observation at 40** | **μ=7.333333, var=0.166667** | **μ=4.953864, var=0.004226, 51.4% of mass on the two edge points** |

The mean is off by 2.38 and the posterior is **~40× more confident** than the correct one. That
combination — wrong mean, inflated confidence — is exactly what `src/Bayesian/HeavyTailFold.fs` was
written to prevent, and truncation manufactures it with no member to blame. `HeavyTailFold`'s
redescending influence `ψ(z) = z(ν+1)/(ν+z²)` is a statement about large `|z|`; on a finite grid `|z|` is
capped, so the mechanism that should discount the outlier never sees one.

Conjugacy costs `O(1)` → `O(N)` (2 float adds → measured 238× at N=20 001), and the grid is a modelling
decision you must make before you have seen the data. Making it adaptive turns it into a particle filter,
whose resampling is not associative and not replayable without carrying the RNG stream.

## 2. The monoid framing survives — and it is stronger than "same law"

```
A homomorphism h(a*b)=h(a)+h(b): HOLDS over 20000 pairs
A identity      h(One)=empty:    HOLDS
```

`Gaussian` **is** a `WeightedSet<NatCoord, float>` with a two-element key set — put the
*sufficient-statistic coordinates* in `'K`, not the sample space. NG4 is the same with `|'K| = 4`. The
homomorphism extends to the group, so the EP cavity `Gaussian.( / )` is `WeightedSet.subtract`, improper
messages included. `h(One) = empty` holds *because* `WeightedSet` prunes `Zero`.

The exhibited shared object is **the free `'W`-module on a finite basis**. "Commutative monoid"
identifies nothing — the repo's own precedent is *"sharing the length 8 identifies nothing"* — so the
claim rests on the exhibited map, not the shared law.

**Why the naive unification failed:** `SoftValue` carries *probability* coordinates, where fusion is
⊗-then-renormalise, not ⊕. Measured negative control, and the bridge:

```
B combine (Bayes, prob coords) : x=0.30303  y=0.63636  z=0.06061
B WeightedSet.add (prob coords): x=0.7      y=1.0      z=0.3     ← sums to 2.0; not a belief
C log-domain add then renormalise vs combine: max abs diff = 1.110e-16
```

A discrete distribution is itself an exponential family whose natural parameters are the log-probabilities
— which is what `wset.ts`'s `LogProbRing` already is.

**Four honest limits are stated in the doc**, including: this is a **monoid** homomorphism, **not** a
semiring one (`WeightedSet`'s ⊗ has no Bayesian meaning under `h`), which narrows the in-flight PR #14243
claim that a transfer is a semiring homomorphism.

## 3. "Dual BNN" is not in the tree

`git grep -i 'dual[ -]?bnn'` at `6a23b9fc45` returns nothing. Widening to `two BNNs|BNN pair|second BNN`
returns **one line** — a reviewer's proposal being evaluated in
`docs/design/2026-08-13-…-linguistic-seed-bridge.md:376` — plus its PR-review archive. No type, no
interface, no test. Nor were that document's five proposed interfaces (`ILexicalChannel`, `IChannelSplit`,
`IProductionPrior`, `IBeliefProjection`, `ICalibratedBelief`) ever built, and `MinimalBnn`/`MultilayerBnn`
have **zero consumers in `src/`**.

**syntax↔`'K` / semantics↔`'W` is refuted as a partition.** State-splitting (parent annotation / latent
annotations) absorbs a context-sensitive distinction into the *key*, so neither side is confined to its
coordinate. Half of it *is* exhibited — `Sppf.expectedCounts : … -> Map<int, float>` is a
`WeightedSet<prodIndex, float>` in all but the type name. What survives is weaker and more useful:
**enriching `'K` keeps the fold `'W`-linear (DBSP-incremental, inside `WSet.apply`'s discipline);
conditioning `'W` on context does not.** That is the real fork behind the intuition, and it is decidable.

## 4. The parsers are not semiring-generic

`src/Core/Sppf.fs` is hardcoded `float` — literal `1.0` as ⊗-identity, `*` as ⊗, `List.sumBy` as ⊕, no
`ISemiring<'W>` parameter anywhere. It is also **single-oracle** (F# only, no golden vectors), so the
parse layer sits outside the four-oracle byte-lock. The Aji–McEliece 2000 citation is quoted verbatim in
`WSet.fs` and `wset.ts`; **the parser has never read it.** Proposed, not built, and not coincidental.

`LinguisticSeed.fs` (new since the 2026-08-13 doc) is the CE Aaron remembers — but it is a **Mercer-kernel**
CE, not parser combinators, and it is a case where `float` is the *model*: PSD-closure is a property of ℝ,
so a sweep that "made the soft regime semiring-generic" would silently delete its proof. Recorded because
that sweep is the obvious next thought.

## 5. Two consequences nobody had written down

**PR #14266 put the BNN lane's exact-weight question on its critical path.** No `WireWeight<float>`
exists, so a BNN posterior encoded as `WeightedSet<NatCoord, float>` is local-only *by construction*. That
is correct (float addition is not associative), and it means exactness is not an adjacent concern.

**And the exact path diverges three ways across the oracles.** Same input, verbatim replicas of each
oracle's own source:

| oracle | `add(1/4e9, 1/3e9)` | `mul` |
|---|---|---|
| TypeScript (`number`) | `{n:7, d:12000000000}` | `{n:1, d:12000000000000000000}` — **exact** |
| F# (`int64`, unchecked) | `{Num=-13671875; Den=12591297018963968}` | `{Num=-1; Den=6446744073709551616}` — **a negative probability** |
| Rust release | identical to F# | identical to F# |
| Rust debug — **the `cargo test` default** | *panic* | *panic* |
| C# (`long`) | inferred same as F#; not separately executed | — |

`golden-vectors.json` carries no integer of six digits or more; its header says the seeds stay in the safe
range. **A lock whose vectors never reach the divergent path is not a lock** — same lesson as the
tie-break divergence in #14266. `WireWeight.fs` already records the overflow honestly; the *divergence* is
new.

On the fix: `bigint` is right, and `src/Core/WSet.fs` already uses it for sequence numbers, so `int64` was
a choice. The hard half is cross-oracle — **Rust has no std bigint and none is in the tree** (dependency
decision, settle first); .NET `BigInteger` and JS `bigint` division/mod signs **verified to agree**
(`-7/2 = -3`, `-7 % 2 = -1`, `7 / -2 = -3`, `7 % -2 = 1`); `num-bigint` unverified. Note TS is currently
the *correct* one, so widening only the int64 side does not close the gap.
