## Description

## What

`src/Core/SoftValueNumeric.fs` said `SoftValue` was *"effectively a `WeightedSet<DynamicValue, float>` over the probability semiring"*. It was an association list; `SoftValue.fs` did not mention `WeightedSet` at all. It is one now, and the float/exact boundary is a signature rather than a sentence.

## Why it was not one — the obstruction is type-level, and it is the finding

`WeightedSet<'K,'W>` requires `'K : comparison`. `DynamicValue` is declared `[<RequireQualifiedAccess; CustomEquality; NoComparison>]` (`src/Core/DynamicValue.fs:82`).

**So `WeightedSet<DynamicValue, _>` does not typecheck.** The comment described a type nobody could have written. And the `NoComparison` is *right* — `Float nan`, `Float -0.0` and a default `ImmutableArray<byte>` each break the order F# would derive, so no derived order could have agreed with the hand-written `Equals`.

`src/Core/CandidateKey.fs` supplies the missing order from **outside** the type, leaving `DynamicValue` untouched (out of scope, as asked). Its one obligation is agreement with the equality that already exists:

> `DynamicValueOrder.compareValues a b = 0` ⟺ `a.Equals b`

which is why NaN is folded to one class and `-0.0` is identified with `+0.0` — `Double.Equals` says both of those pairs are equal.

## The weight type

| candidate | verdict |
|---|---|
| **`ProbabilitySemiring.RationalRing` (exact ℚ)** | **chosen for the wire.** Already an `IRing<Rational>`, exactly associative, encodes as two integers ⇒ byte-locks. |
| **middle-out float** | **not chosen — because the 2026-08-02 handoff's Task B is already implemented, and it already landed on rationals.** |
| **raw IEEE `float`** | **kept, deliberately, as the LOCAL posterior weight** — the "specialised code where needed" half of the standing signal. |

### Was the 2026-08-02 handoff already implemented? Yes — in TypeScript, and it chose ℚ

`src/Core.TypeScript/algebra/exact-weight.ts` exists and is a bigint rational. Its header carries the decision explicitly:

> *"WHY RATIONAL (not interval/ball): in the sum-product domain the operations are purely {+, ×, negate} — all closed over Q. An interval/ball representation adds complexity for tracking uncertainty that doesn't exist when the arithmetic is exact."*

So the spec's title (*"middle-out float wset weight"*) resolved, in the shipped implementation, to exact ℚ — the implementer took the handoff's own instruction to *"do it in the SUM-PRODUCT domain"* to its conclusion. Choosing `RationalRing` on the F# side is **finishing that work in the second language**, not starting beside it. It also gives the two languages the same shape: num/den, lowest terms, positive denominator.

The tri-boolean float is still the right carrier for a self-describing *number*. It is not the right carrier for a probability *weight*, because the property that makes the fold safe is exactness, and ℚ has it with no error term to track.

**Honest limit, measured not assumed:** F#'s `Rational` is `int64/int64` and `ProbabilitySemiring.rat` reduces but never checks overflow, so long exact chains wrap silently. That is why `toExact` takes a **bounded** denominator instead of carrying a float's exact binary expansion — `0.3` is `5404319552844595 / 18014398509481984`, and two of those multiplied overflow `int64` on the first step. The unbounded fix is a bigint rational, which is exactly what the TS sibling already has and F# does not.

## How the boundary is enforced — precisely, including where it stops

`WeightedSetWire.toDynamicValue` demands a `WireWeight<'W>` capability.

- **Structural half.** `WireWeight<'W>`'s only constructor is `internal`. **No caller outside `Zeta.Core` can construct one at any `'W`** — a downstream holder of a `WeightedSet<'K, float>` simply cannot produce the argument. That is a type error, not a review note.
- **Test half, said plainly.** Inside `Zeta.Core` the inhabitants are the two exported values, and three reflection falsifiers pin them: no public constructor; the exported set is exactly `{integer, rational}` with no float; and **no generic factory exists that could be instantiated at float** (that last one is the escape hatch the first two would miss).
- **What would make it fully structural:** an `.fsi` signature file for `Zeta.Core`, which the project does not use today. Named as the follow-on rather than glossed over.

`SoftValue.toExact` / `SoftValue.toWire` are the one named crossing: local float belief → exact ℚ at a stated denominator → canonical CBOR.

## Falsifiers — `tests/Tests.FSharp/SoftValueWeightedSet.Tests.fs`, 14 facts

1. **Parity.** `compare = 0` exactly when `DynamicValue.Equals`, over a corpus containing two distinct NaNs, both signed zeros, a default `ImmutableArray`, and nested `Array`/`Object`; plus antisymmetry and transitivity; plus `SoftValue` still merges `-0.0` with `0.0` and NaN with NaN, exactly as the old `Dictionary`-keyed `build` did.
2. **Boundary.** The three reflection checks; the crossing round-trips; an out-of-range denominator is refused; the wire form is byte-identical under every permutation of the evidence.
3. **Associativity — both arms.** Exact ℚ folds identically under 200 seeded permutations (S=4), **and the same permutations are shown to change the float fold.** The reason for the boundary is asserted in the suite, not just in prose: if float addition ever starts associating, the test goes red and this design loses its justification.

**The two survivors are reported, not healed away.** F#'s `Operators.compare` on `float` already identifies `-0.0` with `+0.0` and already treats NaN as equal to itself, so that body is redundant *in F#*. It is kept because **F# is the lucky one**: `Double.CompareTo` — what a C# oracle reaches for — orders `-0.0 < 0.0` and sorts NaN below every number, **disagreeing with `Double.Equals` on exactly those inputs**, and Rust's `f64` has no `Ord` at all. The body is the cross-oracle specification of the order, written where a peer implementation will look for it. The comment now says this, with the measurement attached.

## Behaviour changes — three, none buried

1. **`candidates` is in ordinal candidate order, not first-seen order.** A `WeightedSet` is a `Map`, so the order is a property of the value rather than of how it was assembled.
2. **`resolve`/`best` break ties by ascending candidate. This is a fix.** `src/Core.CSharp/SoftValue.cs` breaks ties with `ThenBy(key, StringComparer.Ordinal)` and the TS oracle sorts keys before scanning, while F#'s `List.maxBy` took the first maximum *in arrival order*. **The three oracles and F# disagreed on ties**, and the shared golden seed does not exercise one, so nothing caught it. Now pinned by a test.
3. **The representation is private, so `{ Candidates = … }` no longer compiles.** Two suites used that route *on purpose* — `ComputeReceipt.Tests.fs` CR-6/CR-7 need an empty `SoftValue` that `ofWeighted` refuses to build, "because the guard exists for values that arrive by any route". Sealing it without a replacement would have **deleted a falsifier**, so `SoftValue.unnormalized` is exported and named for what it is.

`tests/Tests.FSharp/Algebra/CellScheduler.Tests.fs` and `tests/Tests.FSharp/ComputeReceipt.Tests.fs` are the **only** test files changed, one line each. The entire pre-existing SoftValue suite — `SoftValue`, `SoftValueMonad`, `SoftValueInfo`, `SoftValueNumeric`, `SoftValue.CrossVerify`, `SoftValueWidening` — passes **unmodified**.
