## Description

#15372 pre-merges `origin/main` into the snapshot so GitHub never has to apply
a `.gitattributes` merge driver. It works — the log shows
`pre-merged origin/main into heartbeat/alexa-flush (8ee0f51 -> c6ebf34);
GitHub now only fast-forwards`. But it moved the ref without updating
`$SOURCE_SHA`, and `merge-heartbeats-to-main.ts` is handed
`--source-sha "$SOURCE_SHA"` and refuses when the ref does not point at it:

    merge-heartbeats-to-main: snapshot ref collision:
      heartbeat/alexa-flush does not point to 8ee0f511bce13e0f...

So the verification failed BY CONSTRUCTION, and only on ticks where the
pre-merge actually did something. Measured at 16:23: alexa rc=3, soraya
SUCCESS — because soraya's lane already contained main, its pre-merge was a
no-op, and $SOURCE_SHA stayed correct. **The fix bit exactly when it was
working**, which is why it survived its own merge run.

One line: after a pre-merge that pushed, `SOURCE_SHA="$MERGED_SHA"`. The
snapshot ref IS the merged commit now, so that is what downstream should verify
against.

Safe at that point, and it matters that it is: the immutable park is UPSTREAM
of the pre-merge — $SOURCE_SHA was pushed and verified against the ref before
the merge ran — so the "no events lost" guarantee never depended on this
variable afterwards. Nothing was at risk during the window; alexa's three
commits stayed on the lane.

A note on my own verification, since it nearly sent me down a wrong path: my
first check reported the reassignment landing AFTER the consumer. It was
matching the COMMENT I had just written above the fix, which quotes
`--source-sha "$SOURCE_SHA"` verbatim. Real order in the run block is
line 371 (reassign) then 432 (consume), same shell, same step. A string search
that cannot distinguish code from prose is not a verification.

shellcheck clean.
