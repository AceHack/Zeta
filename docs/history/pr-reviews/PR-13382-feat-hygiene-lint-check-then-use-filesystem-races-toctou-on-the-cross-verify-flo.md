## Description

## The defect

Three TOCTOU instances landed on **2026-08-20, in one day, from three independent agents**, all in code that had already been written and reviewed:

| # | file | shape | fix applied |
|---|---|---|---|
| 1 | `cluster/restricted-namespace-workloads.test.ts` | `readdirSync` + `statSync().isDirectory()` + `readFileSync` | `withFileTypes: true` |
| 2 | `cluster/storage-profiles.ts` | `existsSync(abs)` -> `readFileSync(abs)` | read-then-interpret-ENOENT |
| 3 | `hygiene/audit-chart-target-revisions.ts` | three sites in one file | all converted |

Each was found by CodeQL (`js/file-system-race`, HIGH), one at a time, **after** merge. Nothing in this tree looked for the shape.

`if (!existsSync(p)) return;` reads as defensive and is the opposite: between the check and the read the path can be created, deleted, or replaced — by a concurrent agent in this fleet, by a `git checkout`, by a background clone. It converts one atomic syscall into two that can disagree.

## What landed

`src/Core.TypeScript/hygiene/lint-check-then-use-file-races.ts`, wired into **gate.yml's `cross-verify` floor** — pre-merge, offline, no CodeQL database.

**Rule 1 — `check-then-use`.** An existence gate followed by a filesystem operation on the *same path text* in the block enclosing the gate. Gates: `existsSync`, and `statSync`/`lstatSync` used for their *kind* — both inline (`statSync(p).isDirectory()`) and bound (`const st = statSync(p); if (st.isFile())`). Uses: `readFileSync`, `readdirSync`, `readlinkSync`, `copyFileSync`, `realpathSync`, `openSync`, `createReadStream`, `renameSync`, `unlinkSync`, `rmSync`, `appendFileSync`, `truncateSync`, `chmodSync`, `utimesSync`.

**Rule 2 — `readdir-then-stat`.** `readdirSync(D)` without `{ withFileTypes: true }` whose block then re-stats an entry. Instance 1's shape, which rule 1 structurally *cannot* see: `readdirSync(d)` and `statSync(join(d, name))` never name the path identically.

**Every refusal names the fix for the shape it found** — `withFileTypes: true` for the listing case, `try { read } catch (ENOENT)` for the read case. A lint that says what to do instead gets obeyed; one that only says no gets suppressed.

A `statSync(p).size` is a measurement, not a gate, and is deliberately not flagged — `withFileTypes` cannot supply it.

The key is the **call-pair signature, not the line**, so an unrelated edit above a row does not thaw it, and renaming the path expression at a grandfathered site *does*.

## Proof it can fail

The tree being dirty is itself the strongest evidence, but the fixture proof is explicit and does not depend on the tree:

- 36 tests. The load-bearing ones are **positive**: each of the three instances rebuilt as a fixture, and the lint refusing it. `analyzeSource(INSTANCE_2)` -> exactly one `check-then-use`; the corrected forms -> `[]`.
- **End-to-end, the real CLI over real directories**: a temp dir holding the defect exits **1**, a temp dir holding only the corrected form exits **0**. Same binary, same flags, opposite verdicts, decided only by what is in the tree.
- **A new defect injected into a real, previously-clean tree file** (`audit-flash-entrypoint-parity.ts`) reddened the exact CI command while the 295 stayed grandfathered; restoring the file returned exit 0.
- **Dropping one baseline row** reddened the gate. The baseline is not a blanket.

## The honest limit, stated in the file

Static detection of this class is heuristic, inherently and permanently. Claiming otherwise would be the same defect class in a new place.

**It does not see:** a check and a use in **different functions**; a check stored in a variable and consumed later (`const ok = existsSync(p); ... if (ok) readFileSync(p)`); a path **named differently** at the two sites (`existsSync(abs)` vs `readFileSync(resolve(abs))`) — renaming between the sites *hides* the defect from this lint; anything outside TypeScript or in a `.d.ts`; and **the entire async family** (`fs.promises.stat` then `fs.promises.readFile`) — the three observed instances are all sync, the async shape is real and NOT covered.

CodeQL stays wired. This is a floor beneath it, never a replacement.

## A check that did not run must never look like one that passed

Three ways this audit can fail to run, and all three are **findings**, not skips:

- `unparsed` — a file the lexer cannot read.
- `unreadable` — a file that exists and will not open.
- `scan-floor` — fewer files inspected than `--min-files` (CI passes `1500`). A mistyped root or a walker that returns early looks exactly like a clean tree from the exit code.

The lexer earned its own regression suite: five constructs in `src/Core.TypeScript` made it choke on the first run — `return /re/.test(s)` (regex vs division after a keyword), `h[i]! / h[j]!` (TS non-null assertion before a division), a template substitution containing a nested template, and cascades from both. All 1872 files now lex cleanly, and each construct has a test.

## The lint obeys its own rule

`loadTypeScriptFiles` uses `readdirSync(dir, { withFileTypes: true })` and read-then-interpret-ENOENT. It is its own first fixture, and it reports zero findings against itself.

## Suppression

`// toctou-ok: <reason>` on the check's line, reason **mandatory** — a blank one is itself a finding (`empty-suppression`). No suppressions exist in the tree; the mechanism is covered by fixtures. A lint with no hatch does not get obeyed, it gets deleted.

## Anchor (Beacon)

TOCTTOU is named in the RISOS study (Abbott et al. 1976). Bishop & Dilger, *Checking for Race Conditions in File Accesses* (Computing Systems 9(2), 1996) is the direct anchor: their central claim is this lint's premise — the flaw is a syntactic pattern in the source, statically detectable, and their detector was likewise pattern-based and likewise incomplete. The remedy they name is the one every refusal here names: perform the operation and handle its failure, rather than asking a question whose answer is stale the instant it returns. CWE-367.
