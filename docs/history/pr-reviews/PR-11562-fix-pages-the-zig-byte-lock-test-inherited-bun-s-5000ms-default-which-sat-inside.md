fix(pages): the Zig byte-lock test inherited bun's 5000ms default, which sat inside its range

#11530 landed `identity-dla-pages-wasm-behavior.test.ts` with no explicit per-test timeout, so
it inherited bun's 5,000 ms default. That is now failing `test (TS hermetic)` on unrelated PRs
(#11546, #11550, #11555) — a boundary flake blocking the queue. From #11546, on a green tree:

  (pass) Zig at seed 1  ... [3482.08ms]
  (fail) Zig at seed 42 ... [5138.05ms]   ^ this test timed out after 5000ms

Nothing reported a trajectory mismatch. The byte-lock is not failing; a wall-clock limit that
was never chosen for this workload is, and it decides by runner load.

MEASURED FIRST, rather than assumed (bun 1.3.14/JSC + node/V8, 800 walkers). All six substrates
compute the identical trajectory from the identical PRNG, so all execute the SAME walker-step
count (123,690 at seed 1; 151,722 at seed 42) — only per-step cost differs:

  WAT 22.7 ns/step · LLVM/C 11.5 · Emscripten 11.7 · Rust 15.5 · ASC 25.2 · Zig 20,279

  run(): WAT 2.8 ms, LLVM 1.4, emcc 1.4, Rust 1.9, ASC 3.1, Zig 2508 ms (seed 1) / 3148 (42).
  Cluster size 332/339 for all six — Zig is CORRECT, and agrees on every byte-lock seed.

Ruled out by measurement, not by argument:
  - NOT startup: compile 0.25 ms, instantiate 0.08 ms. The cost is inside run().
  - NOT extra work: Zig's `run` body is 700 B of ordinary opcodes vs WAT's 411 B; no
    call_indirect, no software float, no exotic instructions.
  - NOT engine-specific: reproduced on both JSC and V8.
  - NOT a per-walker constant: cost is exactly linear in steps (a degenerate build ran 40M
    steps in 843 s = 21 µs/step, the same rate).
  - NOT mainly the optimization mode: `-O ReleaseFast` gives 643 ms — 4x better, still ~200x
    off WAT — while inflating the artifact 1,314 B -> 512,211 B, which would wreck the
    Conjecture Z-7 size table and likely trip the DWARF ceiling in the proof-lineage audit.

So the slowness is real, per-step, and its root cause inside Zig 0.13 codegen is NOT
identified. Filed with the full measurement rather than guessed at:
workitems/081M089HKQ7087G0R003H2G8JF-*.md.

THE FIX, and why the other option was rejected. Accommodating a cost is the wrong move when
the cost is accidental — but the only accidental-looking lever, ReleaseFast, is a 390x size
regression to a byte-locked artifact for a 4x gain that still does not reach the other five.
That is its own reviewed decision, not a side effect of unblocking a queue. What IS clearly
wrong is the limit: 5,000 ms was never chosen for a WASM substrate that legitimately takes
seconds; it was inherited.

  - Scoped to this test only, via the third argument to `test()`. The global default is
    untouched, so no other test in the suite is loosened.
  - Attributed inline: the per-step table, the wall-clock range, the CI observations, the
    #11534 hidden-oracle rule this obeys, and the work-item that owns the underlying defect.
    `audit-hidden-oracles.ts` counts are unchanged (125 gating constants, 111 unattributed,
    14 attributed) — this adds no 113th bare number.
  - Set FAR from the boundary (60,000 ms ≈ 9x the worst run yet observed) so the clock cannot
    decide the verdict; and deliberately not tight enough to double as a performance
    assertion, because a degenerate substrate is also a slow one and should report "returned
    1", not "too slow".

Also halves the work: one module run per (asset, seed) with both assertions taken off the
single result, degeneracy checked first so the defect this file exists for names itself.
10 tests -> 7; file wall-clock ~9.2 s -> ~6.7 s.
