## Description

Closes `081KZZ3JHP1087G0R00027ARRR`. Sweep half of the finding filed in #10520.

## Does a working timeout mechanism exist? Yes -- two, and neither is the bunfig key

**CHECKED**, reproduced from scratch rather than inherited. Isolated directory, one bunfig containing only `[test] timeout = 20000`, one test sleeping 7s:

```
x A1 bunfig-only: sleeps 7s [5000.74ms]
  ^ this test timed out after 5000ms.
```

| mechanism | result |
|---|---|
| `bunfig.toml` `[test] timeout = 20000` | **ignored** -- fails at 5000.74ms |
| `bun test --timeout 20000` | **works** -- 2 pass |
| `test(name, fn, 20_000)` | **works** -- passes beside the failing bunfig arm |

**The why, which the original finding did not have.** The key is not deprecated and not broken: bun 1.3.14 does not implement `[test] timeout`, and it does not validate unknown bunfig keys either. A deliberately bogus key (`thisKeyIsNotRealAtAll = "garbage"`) added next to it also drew **no warning and no error**. The line was indistinguishable from a typo. `bun test --help` confirms the supported path: *"Set the per-test timeout in milliseconds, default is 5000."*

## How many tests sit within 2x of the cap, and which

Whole suite with the cap raised to 120s so durations are **true** rather than clamped at 5000: **9785 tests, 907 files, 268.53s**. Nine tests at or within 2x of the real cap. Seven already carried an explicit per-test timeout -- an earlier grep missed them only because `180_000` uses underscore separators. **Exactly two were unprotected:**

Both unprotected ones were slow the *same* way -- redundant repeated work:

- **`no-agent-gate-bypass.test.ts`** read ~1700 tracked files **once per pattern**: four full passes over the tree to ask four questions of the same bytes. 4.0s in-suite, and standalone at the default cap it **failed outright at 8109ms**. Reads hoisted to collection, each assertion now pure regex over memory. Drops out of the band entirely (<500ms). Made fast, not given a timeout.
- **`build-graph.test.ts` DRIFT GATE** called `deriveGraph(REPO_ROOT)` twice, once per `expect`, re-deriving an identical repo-wide graph. Derived once: **2624ms -> 1264ms**.

Two further `build-graph` tests are slow **by nature** and got explicit timeouts instead of rewrites, because the repeated work *is* the assertion: proving determinism requires deriving twice, and the tamper gate needs both a tampered derivation that fails and a control that passes, or it is vacuous.

**After this change every test in the >=2500 ms band carries an explicit per-test timeout.** Verified at the **default** cap -- the real CI condition: **9777 pass, 7 skip, 3 fail, 265.72s, zero timeouts.** The 3 failures are pre-existing `cross-verify-ir` assertion errors from language runtimes absent in this worktree, identical in the pre-change baseline. Not a regression.

## Stopping the file from lying

The key is **deleted, not commented out**, and replaced with the measured cap, both working mechanisms, and the work-item. `hygiene/bunfig-declares-no-test-timeout.test.ts` fails if it returns -- and it was **falsified before shipping** (key re-added, watched go red, reverted). The guard deliberately does *not* assert that a 5s timeout fires; that would cost 5 seconds of CI on every run to re-learn something now written down.

## Run-vs-block reasoning

**`test (TS suite)` stays out of `gate-required`'s `needs`.** Stated deliberately, not left to default.

A flaky test in a **non-blocking** lane degrades signal; the same test in a **blocking** lane stops the fleet. Load-dependent flake is exactly the shape that converts a noisy runner into a fleet-wide stall -- the priority inversion the 2026-08-01 drift-and-heal ADR narrowed the floor to avoid. Promoting a lane that contains known load-sensitive tests would re-introduce it.

Non-blocking is **not** ignorable, though. A permanently-red non-blocking lane trains readers to discount it, which is precisely how the #10508 timeouts hid the `light-time` solver finding. So: lower urgency, same remedy -- **fix the flakes, do not raise the cap.** Because the lane does not block, that remediation is affordable incrementally, which is what made per-test fixes the cheaper option here.

## Why no global `--timeout` in gate.yml -- parity above all

A flag in the workflow applies **in CI only**. A contributor running `bun test` on a laptop or in the devcontainer still gets 5000. That is **three-way parity drift (GOVERNANCE 24) deliberately introduced**, and it is the same defect as the line being deleted here: a number true in one place and false in another. A per-test timeout lives in the test file, so all three legs agree. That is the deciding argument.

Secondarily: a global raise silently re-admits every test in the 5-20s band without anyone deciding it earned that, and a hung test would burn 20s instead of 5 against a 20-minute job cap.

## Cost

The new guard is one file read, **450ms** measured. The two fixes remove three redundant repo-wide manifest walks and ~5000 redundant file reads per run. **Net CI-minute negative** -- this gives back more than it costs.

## Honest limit

The durations above are **lower bounds**. The same test measured 4.0s in-suite and 8.1s standalone-under-load, so band membership shifts with machine load, and a GitHub runner is noisier than this machine. An idle measurement understates it -- which is exactly how the two instances in #10520 were missed sideways.
