## Description

# Summary

The §6 capability audit (`docs/security/webauthn-delegation-section-6-capability-audit.md`) found
the device-delegation capability mostly sound and left **three concrete gaps**. All three were
**re-verified as still open against `main`** before being touched; this PR closes all three. None
required minting a capability or invoking a passkey.

**1. §6.5 — the audit chain broke at `→ descriptor`.** The receipt pinned *which credential* and
*which device*, but not *the capability the use was granted under*. It now records
`delegationDigest` — SHA-256 over the canonical delegation intent, covering `action`, `baseRef`,
`branchPrefix`, `maxPatchBytes`, `pathPolicy` and `validity` in 32 hex-encoded bytes. The value
recorded is the one `validateProposalShape` has **already verified**, so the receipt pins a checked
value, not an attacker-supplied one. Schema `zeta.proposal-receipt.v3` → **v4**.

The audit's own warning — *"without such a script the field is decoration"* — is answered by
`receiptBindsDelegation()`, which recomputes the digest and compares in constant time, failing
closed on a missing or malformed value.

**2. §6.3 caveat 1 — `revokedDevices` had never run through the loader.** DDP-9 already exercised
device revocation, but against an **in-memory registry object**. The registry on `main` has no
`revokedDevices` key at all, so the JSON path — parse, `validRevocations`, the loader's propagation
of the field — had never executed. DDP-14 writes a fixture registry to a real file and loads it
through the production `loadProposalAuthorRegistry`; DDP-15 is the control that keeps it honest
(same file *without* the key must verify `ok: true`, else the refusal could be a load failure
wearing a revocation's clothes); DDP-16 pins that a malformed entry fails the **load**.

**3. §6.3 caveat 2 — the operator trap.** Bumping registry `sequence` does **not** revoke a device
delegation (`>` on the delegation path vs `!==` on the v2 proposal path). This is intended and
correct — a delegation is valid `until-authority-revoked`, and `!==` would silently kill every
enrolled device on an unrelated registry edit. But an operator reaching for a sequence bump as an
emergency revoke would believe they had revoked and be wrong. DDP-11/12/13 pin the asymmetry, and a
docstring at `validateDelegation` names the levers that actually work (`revoked` / `revokedDevices`).

# Notes

**Owned error.** PGCR-6 was **vacuous as first written**. It compared two separate `fixture()`
calls with different `maxPatchBytes` and asserted the digests differed — they did, but because each
call generates fresh keypairs, not because of the capability. M7 (dropping `capability` from the
canonical bytes entirely) left the whole suite green. Corrected to vary **exactly one field off a
single fixture**; M7 now kills it. The trap is documented in the fixture module so the next author
does not repeat it. Recorded in the audit doc rather than quietly fixed — without the mutation
requirement, a decorative test would have shipped attached to a real fix.

**Still unexercised, stated plainly.** There are still **zero receipts** on `main` —
`docs/observe-events/proposal-receipts/` does not exist. The receipt *shape* and the descriptor
binding are now VERIFIED at unit level with failing mutants, but the receipt *being written during
a real staged proposal* remains **DOCUMENTED-UNVERIFIED**. `applyPlan()` — which writes the file,
commits and pushes — is still untested because it shells out to `git` and reads
`GITHUB_EVENT_PATH`; extracting `proposalReceipt()` shrank that untested surface but did not
eliminate it. **Nothing here should be read as end-to-end coverage.** T-6 stays open.

**Not attempted:** T-1 (`maxPatchBytes` refusal has no test — still open, needs no biometric, cheap
follow-up), and T-2/T-3/T-4/T-5, which need a live capability or local machine state. No capability
was minted and no passkey invoked — that gate is Aaron's.
