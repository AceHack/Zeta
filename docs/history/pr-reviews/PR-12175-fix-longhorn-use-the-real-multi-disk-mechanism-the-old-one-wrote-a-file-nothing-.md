## Description

## The bug

`longhorn-disks.nix` wrote `/etc/longhorn/node-disks.yaml` as `kind: NodeDiskCatalog`, with a header saying a cluster-side DaemonSet+Job would consume it *"once the first physical node is up"*. That companion was never built.

Measured:

```
$ grep -rl "node-disks" --include=*.yaml --include=*.nix --include=*.ts .
full-ai-cluster/nixos/modules/longhorn-disks.nix     <- only the WRITER

$ kubectl get crd | grep -i nodediskcatalog
(nothing -- NodeDiskCatalog is not a real CRD)
```

So every extra data disk was declared into a file nothing read, in a format nothing understood. Longhorn silently used `defaultDataPath` alone: on a 2-NVMe box the second drive sits idle — against a ledger (`k8s/single-node-budget.json`) recording ~1.6 TiB of `longhorn`-class PVCs implied by the manifests.

## The real mechanism

Longhorn 1.7.2, *"Default Disk and Node Configuration"*. **Three parts, all required, none sufficient alone:**

| # | part | delivered by |
|---|---|---|
| 1 | label `node.longhorn.io/create-default-disk=config` | k3s `--node-label` |
| 2 | annotation `node.longhorn.io/default-disks-config=<JSON>` | systemd oneshot |
| 3 | setting `createDefaultDiskLabeledNodes=true` | chart values |

kubelet can set labels but not arbitrary annotations, hence the oneshot. It matters that it runs at **boot**: the annotation is honoured only while the node has no disks, so applying it later is a silent no-op. JSON is built with `builtins.toJSON`, so a path containing a quote cannot break out of the value.

## Proven, not assumed

The test now boots a VM with two **real** 4 GiB virtual drives and asserts Longhorn registers both:

```yaml
disks:
    allowScheduling: true
    path: /var/lib/longhorn-disk1
    allowScheduling: true
    path: /var/lib/longhorn-disk2
```

It asserts `longhorn-disk2` **specifically**, not "has disks" — one disk is what the broken version produced, so the looser check would have passed against the bug. It also asserts both are real mountpoints: a bind-mount would satisfy the CR check while giving zero extra capacity.

## The test earned its keep

Three runs failed first, and each failure was mine:

1. The test carries its own inline `valuesContent` mirroring the prod Application. I added `createDefaultDiskLabeledNodes` to prod and **not** to the test copy — exactly the divergence that file's own comment warns about.
2. I shipped a second run on that same theory **without evidence**. It failed identically, which is what forced the diagnostics.
3. Plain `fileSystems` is silently **dropped** in a qemu-vm test — no mount unit was generated at all, not even a failing one — so neither path existed and Longhorn registered `disks: {}`. The applicable option is `virtualisation.fileSystems`.

Every one would have shipped invisibly on component evidence: the annotation JSON, the label, and the chart setting each verified correct **in isolation** while the feature did nothing, because nothing checked they reached the same cluster with the paths actually mounted.

`disks: {}` was the tell — zero disks rather than one meant the label *was* working, which pointed at the paths rather than the plumbing.

## Diagnostics

Added **before** the assertion (annotator unit + journal, node labels/annotations, resolved Longhorn setting, Node CR, mounts). A timed-out `wait_until_succeeds` prints nothing about why, and the post-mortem block at the end is unreachable once it fails. Dropped that timeout 900s → 300s; the passing run satisfies it in **0.12s**.

Full chain still green: PVC `Bound` on a fresh volume, real CSI attach, data read back through the mount.
