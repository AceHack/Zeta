## Description

## Why

The browser now has a credential-free passkey proposal path and an immutable accepted-record reader, but callers still had to coordinate them manually. That left room for an automatic lifecycle path to invoke user authorization accidentally or to treat issue presentation as durable receipt storage.

## What

- expose the existing pure archive-generation preparation step without contacting or compacting a downstream store;
- brand repository acceptance as a distinct source-owned port;
- add a browser receipt sync runtime with separate `submitFromUserActivation()` and `pollAcceptance()` methods;
- construct acceptance handoff internally so polling has no proposal signer or carrier edge;
- compact the archive only after an exact accepted-record acknowledgement;
- preserve pending, presented, submitted, accepted, backpressure, and heat as distinct readout states;
- reject proposal receipts whose content hash or target path does not match the prepared generation.

## Reconciliation

This composes Otto's accepted-record and gated heartbeat pipeline with the credential-free WebAuthn adapters from #10528. It remains separate from #10512's hosted operator-service capability exchange; the two trust models are not silently merged.

## Boundaries

- Passkey signing and issue presentation are reachable only from `submitFromUserActivation()`.
- `pollAcceptance()` reaches the branded accepted-record port and archive compactor, never the proposal port.
- A `presented` or `submitted` proposal does not release local receipts; only exact immutable acceptance does.
- This slice does not yet wire controls or polling cadence into the Dark Hall page.
