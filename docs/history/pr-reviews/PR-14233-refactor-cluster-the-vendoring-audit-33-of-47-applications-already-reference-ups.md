## Description

refactor(cluster): the vendoring audit — 33 of 47 Applications already reference upstream; the 2 that cannot, now hash-checked against it

Aaron: "why are we vendoring anything rather than just referencing and having
our own values files? ... it's much better to just reference and override with
our own values and don't vendor the charts."

THE AUDIT'S ANSWER IS THAT THE TREE ALREADY DOES THIS, and the finding is worth
stating before the change: of 47 Applications, 33 reference an upstream Helm
chart at a pinned targetRevision and override it with an inline valuesObject —
already exactly the shape the principle asks for. 12 are our own first-party
manifests (`agent-memory`, `orleans`, `platform`, `hat-system`, `gmod`, …),
which are authored, not vendored. That leaves TWO vendored files in the whole
tree, and neither is a chart:

  full-ai-cluster/k8s/applications/cdi/cdi-operator.yaml            356707 bytes
  full-ai-cluster/k8s/applications/kubevirt/kubevirt-operator.yaml  490554 bytes

There is nothing to reference for either. Measured 2026-08-23 against the
release asset lists: kubevirt v1.8.4 ships virtctl binaries and raw YAML;
containerized-data-importer v1.65.0 ships two YAML files. No Helm chart, no
kustomize base, from either project. Nor does the CR help — the KubeVirt CRD's
`spec.customizeComponents.patches` reaches the components virt-operator
DEPLOYS, never virt-operator's own Deployment.

WHAT THIS COMMIT DOES. Both file headers claim the copies are byte-for-byte
upstream, and `single-node-budget.json` REFUSES an edit on the strength of that
claim ("would make the checked-in copy diverge from the cluster it documents,
which is a worse lie than this one"). A load-bearing refusal was resting on a
sentence in a YAML comment that nothing re-measured. It is now a check.

`vendored-upstream-parity.ts` sha256s each copy against the digest of its
pinned upstream release asset, offline, on every CI run of the cluster plan
job, and requires every file the Application's own `directory.include` glob
applies to be classified as upstream's bytes or ours. `--fetch` additionally
re-checks what the pinned URL serves TODAY, because a GitHub release asset can
be deleted and re-uploaded in place — the same failure mode
`lint-verifier-jar-provenance.ts` records for tlaplus. The digest is the pin,
not the URL.

MEASURED, both halves green: the two copies hash to e96d59ab…a222015 and
d1d8264e…3857eda, which is what upstream serves. So "vendored VERBATIM" stops
being asserted and starts being checked — which is what makes the copies a
CACHE of a pinned immutable URL rather than a fork. Cache-vs-fork is not a
matter of intent; it is a matter of whether anything would notice.

KUSTOMIZE WAS EVALUATED AND IS REFUSED, with the reasons measured rather than
argued. The render itself is clean — a `kubectl kustomize` overlay carrying
only the cpu delta produces, by semantic per-object diff against today's
directory render: cdi 9 objects in / 9 out / ONE field changed; kubevirt 11 in
/ 11 out / ONE field changed; and the local-base and remote-pinned-URL renders
are byte-identical. Four things break anyway:

  1. `kubevirt-cdi-emulation-test.ts` derives its apply list from
     `spec.source.directory.include` and throws PlanRefusal without it — by
     design, so it cannot drift from what ArgoCD applies. It is the only lane
     proving these two install at all, and both Applications' sync-policy
     reasons cite it.
  2. `directory` and `kustomize` are mutually exclusive in ArgoCD at the API
     level. `ApplicationSource.ExplicitType()` (argo-cd v2.13.2 — the
     appVersion of the argo-cd 7.7.10 chart this cluster pins) appends a type
     per NON-NIL sub-block and errors on more than one; and it is consulted
     BEFORE filesystem discovery in `GetAppSourceType`. So the include set
     cannot be preserved: keeping `directory` makes a kustomization.yaml
     inert, and setting both is `multiple application sources defined`.
  3. The repo's own renderer would then report the wrong bytes. Measured on a
     scratch tree: with `directory` removed, `includeGlob` collapses to "",
     `includeMatcher("")` matches every .yaml, and `renderGitPath` returns 11
     documents instead of 9 — including `kind: Kustomization` as if it were an
     API object — and reports the UNPATCHED 100m. The checker and the cluster
     would disagree about the exact number the exercise exists to move.
  4. A remote base needs egress from the ArgoCD repo-server and from any
     renderer, against `clone-at-tag-stays-sufficient` and the offline-by-
     default doctrine — and buys nothing, since the two renders are identical.

NO RESOURCE NUMBER MOVES HERE, and that is deliberate. `lane-partition.ts
--rung dev` is BYTE-IDENTICAL before and after (5191m / 15406Mi / 75.8Gi over
127 images); `--resource-profile metal --check` exits 0 ("manifests match
resource profile metal"); `--resource-profile dev --budget` exits 0. Metal is
untouched. The 120m stays acknowledged; what changed is that the reason it is
acknowledged is now falsifiable, which is the precondition for spending it —
sized in 081M0QHPF6Z087G0R0026RMZ6B rather than spent here, because
storage-profiles.json is in flight under #14163.

ADJACENT FINDING, filed not fixed (081M0QHPF7W087G0R0017B2GDK): the
`replicas: 0` latent set has a FIFTH coordinate nobody counted.
`unreachableGitPathRequests` walks Applications, and
`infra/k8s/bootstrap/initial-orleans.yaml` is not one — it is applied directly
by K3S (`infra/nixos/modules/k3s-server.nix:78`) and carries 500m/512Mi on a
`replicas: 0` StatefulSet with none of the `@x0` baseline protection the other
four have. The sibling's 5100m/17536Mi reproduces exactly; this is beside it.

Falsifiers: `vendored-upstream-parity.test.ts`, 26 tests, every finding class
reached by mutating a scratch tree rather than by constructing a Finding — one
byte changed in the copy, a `cpu: 25m` added to it, the copy deleted, the
roster URL moved to a branch, a third file added to the glob, a rostered file
dropped from the glob, upstream serving different bytes, and a fetch that
FAILS (a finding, never a pass). A file the glob EXCLUDES stays green, because
the glob decides what is applied, not the directory listing.

Honest limit, stated in the module: this proves committed-bytes ==
upstream-bytes. It does NOT prove committed-bytes == what runs on node-5b2dfa.
That second gap is named in `manual-sync-policy.ts` and nothing offline can
close it.
