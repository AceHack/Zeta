The work-item says hardware inventory lives on **three surfaces that do not know about each other**. Measured before building: it is **six**, they are **not copies of one list**, and the named third one is **not an inventory at all**.

| surface | provenance class | measured today |

| `machines/*.pub` | **hostkey** — SSH host-cert identity | **1** |

Two corrections that change the answer:

1. **The count.** The item said "~40 assets" (15 mini-PCs + 24 GPUs). The snapshot carries **206 units**; those two sections are 41 of them. A bulk import would have been 5× the expected size.
2. **The third surface is not an inventory.** `docs/HARDWARE-CAPABILITY-MATRIX.md` is keyed by **target class** (`linux-x64`, `qemu-aarch64`, `nvidia-gpu`), never by asset — a class-keyed evidence table and an asset-keyed register share no key to reconcile on. It is deliberately **not** reconciled, and its only asset content (prose asides: "hardware IN HAND … RTX 4090 + RTX 3090") is labelled as the drift risk it is.

The two surfaces the item did not name — **probe** and **hostkey** — are where the live divergences actually are.

**Two bugs the mutants found**, both kept as pinned regressions:

- `/^key:\s*(.*)$/m` **spans the newline** — an empty field absorbs the next line's value. Produced a phantom `HWR-1` on the very first run (`assigned_machine:` empty → parsed as `sample: true`).
- an unanchored quantity regex reads `Minisforum MS-A1 Pro (with 4× 20TB IronWolf HDDs)` as **20 units**. That single line is the difference between **206 and 225**.

A third came from mutating rather than reasoning: appending at EOF lands inside the excluded `## Provenance` section — the file's last — so the counts have a blind spot. Closed by byte-pinning the snapshot body as **hex-in-text** (`body-sha256=`) alongside the human-readable counts, with `bun run inventory:repin` as the supported path for an editorial edit.

# Notes

**What was deliberately NOT unified.**

- **The 2026-05-27 snapshot is not bulk-imported into the register.** Aaron 2026-08-14: Addison is re-doing the audit. Importing a superseded snapshot would hand her **206 rows** to re-verify against her own fresh numbers, and every correction would become a diff against data that was never right. Her re-audit is the source of truth; the register is the target. Held open as `HWR-5` with the magnitude printed on every run so it cannot quietly stop being reported.
- **The duplicate MAC is not deleted.** A `node.yaml` is a machine's own self-report; deleting one to make a check green is the wrong direction of repair, and choosing between the two readings from the repo alone would be inference. Held open as `HWR-2` with both readings recorded.
- **The capability matrix is not reconciled** — no shared key.
- **The Amazon order history stays off-repo.** Better provenance data than a hand-typed list (work-item point 4), and it is personal-account data behind a human-driven extractor. Named in the surface map, excluded from the check.
- **`hardware-to-buy.md` is declared `class=wishlist`** so it can never be counted as an asset.

**Doctrine.** Drift detection over prevention — the check is not in the `gate-required` roll-up, so a red is signal, not a block. It reconciles; it does not merge, and it rewrites nobody's data.

**Scope of the anti-re-fork guard, honestly.** `HWR-3` owns a declared glob set (`docs/inventory/`, `docs/HARDWARE-CAPABILITY-MATRIX.md`). A seventh list created *outside* those paths is still invisible to it. That is a bounded guard, not a total one.

**Open for whoever picks this up next:** Max resolving the duplicate MAC, and the register-coverage gap closing when Addison's numbers land — both already carry `081M00R59KS087G0R001W3837V` in the ledger.
