## The headline, verbatim from the vendor

> "FIPS approved mode means the following algorithms are no longer available: rsa-pkcs1-decrypt,
> rsa-pkcs1-sha1, rsa-pss-sha1, ecdsa-sha1, **eck256**."
> — [Set FIPS Mode, docs.yubico.com](https://docs.yubico.com/hardware/yubihsm-2/hsm-2-user-guide/hsm2-option-fips-guide.html)

`eck256` **is** secp256k1. So **on a YubiHSM 2 FIPS you may have the validation or the curve, never
both at once** — and `hardware-to-buy.md`'s standing advice (*"for real custody use the FIPS SKU"*)
would buy a device that **cannot sign an x402 payment while operating under the validation it was
bought for.**

That is not a defect in the earlier survey; it answered its question correctly with the criteria it
had. **secp256k1 does not appear anywhere in that document.** It is a criterion collision.

**I re-checked this against the live page before landing. Confirmed verbatim.**

## The SKU inverts

The non-FIPS YubiHSM 2 was scored as the *development* unit with FIPS as the custody answer. Under
the new criterion that **flips**. Recommended action for the Mac: **spend nothing** — the attached
unit is measured to have `eck256` + `ecdsa-sha256`, has no button so it is unattended-capable, and
per-agent partitioning is already a device feature.

## Unattended signing is the crux

**Class 1 — credential-gated, unattended-capable** (YubiHSM 2, Nitrokey HSM 2, NetHSM). Protects
against key **exfiltration**, never against the **holder of the credential** — which moves the whole
security argument onto credential scoping.

**Class 2 — presence-gated, non-starter as an agent's wallet signer.** Notably **Ledger**, which is
building explicitly for AI agents on an *"agents propose, you approve"* model, with async approval
listed **coming soon** — i.e. not available.

> Class 2 is not lesser — it is the correct implementation of a **different** requirement this repo
> already holds (*"nothing operator-run, only operator-approved via biometric"*). **The Secure
> Enclave and our owned wallets are the right devices for the human-consent gate and the wrong
> devices for the agent's payment key.**

**Dead lead recorded so nobody re-walks it:** GridPlus Lattice1's spending-limit auto-signing is
described by multiple secondary sources and **contradicted by primary docs** — *"all signing requests
must be authorized by the user."* Cited-secondary, contradicted-by-primary ⇒ **NO**.

## The genuinely novel result — the TKey is neither class

Touch is a property of the app you **compile**. And because `CDI = BLAKE2s(UDS ‖ USS ‖ BLAKE2s(app))`,
**the no-touch build is a different identity** — a verifier distinguishes a touch-required signer
from a no-touch one **by its public key alone**, with no attestation, no CA, no policy database.
Every other device has physical presence as a fixed hardware fact; the TKey is the only one where it
is a **declared, cryptographically-bound choice.** Unused anywhere in the repo.

## New operational finding — it blocks an existing claim

The device reported **2/62** audit slots used. Yubico documents both options: `force-audit` off means
*"new operations will overwrite old ones, losing the trail"*; on means the HSM *"will refuse further
operations until the logs are exported."*

**At x402 frequency, 62 entries is seconds of history.** So an x402 signer needs a **log drainer** on
a schedule — otherwise the choice is between **losing the tamper-evident trail** and **the device
DoSing itself mid-payment.** Nobody has designed it, and it is **not optional if the audit log is
counted as a security property.**

## Fleet parity — where money actually gets spent

**Recommended:** one USB HSM per node — **3× Nitrokey HSM 2 @ €109 ≈ €327.** Cheap, custody stays
local everywhere, adds the vendor-diversity axis.

**Recommended against:** sharing the Mac's YubiHSM over the network — it recreates **exactly the
shape cloud KMS is excluded for**: one box holding every agent's key, every node routing through it,
an **appointed hub with no second one to use**. Plus CVE-2021-28484 in the connector as advisory
history.

## The gap that could not be closed

**NetHSM is technically the best fit** — open system software, secp256k1 **+ BIP-340**, and
**namespaces where "R-Administrators can not see keys in a Namespace"**, a *stronger* per-agent
partition than YubiHSM domains because **root is excluded by construction rather than by delegation
discipline.** It costs **€11,898.81** — making the repo's recorded `~$1,200` wrong by **~10×** and
materially changing the four-guard budget plan.

⇒ **The open/auditable secp256k1 axis is unfilled under ~€12k**, and dropping FIPS makes that axis
*more* important, not less. Of the two candidate fills, the NetHSM software container keeps the
auditable stack and **gives up the hardware boundary entirely — a downgrade wearing the open badge**,
and must be labelled that way if anyone proposes it.

## Honest limits, carried at the claim

Nothing here reaches *"as mathematically safe as coinbase"*, and **dropping FIPS did not change
that.** Single-device custody protects against exfiltration, **not against the holder of the
device.** **FROST remains unavailable in hardware on everything recommended** — the YubiHSM cannot
produce a partial (measured), and **NetHSM cannot either**: `/keys/{KeyID}/sign` takes only
`{mode, message}`, with **no parameter supplying an external nonce or group commitment**. Cloud KMS is
excluded as remote custody, and the doc **states the real cost of that exclusion** rather than hiding
it.
