## Description

DEBT DISCOVERY, which is the point. Aaron 2026-08-27: "debt discovery is just as
important as feature design — if you don't know your debt then you will rush into
unstable features."

THE GAP, measured against CodeQL over the same tree: `js/file-system-race` flagged
22 files, this baseline listed 180, and only TEN were in common. Twelve files
CodeQL saw that this linter structurally could not, and they were all one shape —
a `statSync` beside a read of the same path. Rule 1 misses it because a bare
`statSync` is not an existence GATE (there is no `if`); rule 2 misses it because
there is no `readdirSync`. Neither detector was a superset of the other, and this
was the half that was ours to fix.

THREE NARROWINGS, each one removing findings that would have made the lint
ignorable rather than useful:

  25 findings   first pass — paired any statSync with any same-named use in the
                file. `full` is declared independently in several functions of
                `observe/workspace-port.ts`, so it happily paired a stat in one
                with a chmod in another: two different variables sharing a name.
                Not races. That is precisely the unreliable-lint failure this
                rule's own comment warns about.
   5 findings   after bounding the pairing to the enclosing block.
   2 findings   after excluding a stat read purely for `.size`.

THAT LAST NARROWING WAS NOT MINE TO MAKE ALONE. A pre-existing test — `a stat read
for SIZE is a measurement, not a gate` — already recorded the judgement, and my
first pass broke it. The prior decision is right: `statSync(p).size` beside
`readFileSync(p)` is common and almost always benign, because `readFileSync`
returns the whole file regardless of the size read earlier. Flagging it would make
this lint noisy, and a noisy lint gets suppressed rather than obeyed. Rewriting
the test to match the new rule was the wrong move; narrowing the rule to honour it
was the right one.

What survives is the pairing that bites: a stat whose result STEERS BEHAVIOUR
beside a read, and a stat beside a DESTRUCTIVE use. Both were live instances —
`workspace-port.ts` reported one file's executable bit alongside another file's
content, and `claim.ts` judged a lock stale and then unlinked whatever the path
named next.

VALIDATION WORTH NOTING: run on top of the fs-race fixes, the new rule
independently rediscovered exactly the instances CodeQL had found and I had fixed
by hand, and `workspace-port.ts` dropped out because the fd fix cleared it. The
rule models the right shape.

Baseline 294 -> 295: two `stat-then-use` entries added, both stat->unlink and both
already understood — `claim.ts` is the documented residue with work item
081M129GPP9087G0R000G7837F, and `qemu-full-install-test.ts` carries a comment that
already names this linter and explains why its stat-then-unlink is deliberate.

One entry REMOVED, and it is not mine: `ace/setup-realizers/from-git-hooks.ts` was
fixed on main without pruning the baseline, so the baseline carried a stale row.
Verified absent with AND without this change before writing it out.

fix(bus): verify inode identity before reclaiming a stale lock

CodeQL flagged the fd fix's remaining half, and it was right — this is the
serious one.

`openSync(lp,"r")` + `fstatSync(fd)` made the READ consistent: the holder PID and
the mtime now come from one inode. But `unlinkSync(lp)` resolves the path AGAIN.
If the holder releases and a different process acquires between the judgement and
the unlink, the path names a NEW, LIVE lock — and the reclaim deletes it. Two
processes then believe they hold the same lock. That is mutual exclusion broken
for a process that did nothing wrong, and it is worse than the read
inconsistency the previous commit fixed.

Now the inode judged stale (held open by `rfd`) is compared against the inode
currently at the path, by dev+ino, immediately before the unlink. A replacement
becomes detectable instead of silent.

HONEST LIMIT, stated in the code rather than implied by the fix: narrowing a
window is not closing it. A path-based unlink cannot be made race-free with the
filesystem APIs Node exposes — there is no `funlinkat`. A window remains between
the identity check and the unlink. Closing it properly requires a DIFFERENT
PROTOCOL — advisory `flock`/`fcntl`, or reclaim performed atomically by the next
acquirer rather than by a bystander — which is a change to how mutual exclusion
works in this file and is not a decision a scanner finding should make. Flagged
rather than quietly declared solved.

So this commit makes the common failure detectable and leaves the rare one
documented, which is the honest split. If the lock protocol is revisited, this
comment is where the requirement is written down.

106 pass across bus, tsc clean, oxlint clean.
