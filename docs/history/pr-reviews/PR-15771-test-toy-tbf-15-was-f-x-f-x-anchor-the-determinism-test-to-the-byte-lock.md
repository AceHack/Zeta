## Description

`audit-check-arity` R2 is red on `main` from #15762. Fixing it, not adjudicating it away.

## The defect

`TBF-15`'s determinism assertion compared **two calls to the same pure function**:

```fsharp
let a = Gen.generate 42UL 2 32 |> List.map Gen.toHex
let b = Gen.generate 42UL 2 32 |> List.map Gen.toHex
Assert.Equal<string list>(a, b)
```

True by construction under every implementation, including a broken one. The irony is on the nose: my brief warned that *"a generator ignoring its seed would pass a same-seed-twice check trivially"*, and what I wrote was a step **weaker** than that — a static reading cannot even distinguish the two sides.

**No census row.** `registry/check-arity-census.json` is for assertions legitimately narrower than they look. This was a real finding, and the ledger's ten-edits / ten-raises / zero-lowerings shape is exactly how a judgement registry turns into a suppression list.

## The fix — three anchors

- **(a) The byte-lock.** Assert against the **checked-in hex-in-JSON vector** (seed 42, k = 2). An assertion that *can* fail, and fails as a readable diff (`no-binary-in-proof-lineage`).
- **(b) Two different code paths.** Batch API vs hand-threading the source through `generateOne`, with an unrelated generation run in between as a decoy for hidden global state — plus the metering (`BitsDrawn`, `Draws`) asserted across the seam.
- **(c) Seed sensitivity.** A different seed must produce different output.

## Mutation bar — both mutants stated and measured

**Mutant 1 — `generate` ignores its seed** (`sourceOfSeed 0UL`)

| | result |
|---|---|
| old `TBF-15` | **FAILED** — its seed-sensitivity half already caught this |
| new `TBF-15` | **FAILED** at the byte-lock: expected `55904f01d1d1ede16f602d2178719bb0`, actual `f6f0cc001f916240bc91b2b14241d391` |

**Mutant 2 — one extra bit off the stream** (`draw 5` for the blade)

| | result |
|---|---|
| old `TBF-15` | **PASSED — survived entirely.** This is the gap. |
| new `TBF-15` | **FAILED** at the byte-lock: expected `55904f01d1d1ede16f602d2178719bb0`, actual `1559114f001d1d0ede16f6012d20787119bb1` |

So the self-comparison was not merely redundant — **it left a real corruption of the generator's output stream uncaught**, and the byte-lock is what closes it.

## Metered entropy — confirmed, not implied

Asked, so stated plainly rather than left to inference. It **did** land in #15762:

- `Source.BitsDrawn` counts bits **at the membrane**; `draw` is the only door (#13 noninterference).
- `Sample.MeteredBits` carries `4 + 3k` per sample — exact, since 8 is a power of two, so no rejection-sampling waste.
- `Sample.RealizedDamage` carries the Hamming weight **actually realized**.

Both axes are reported. The code's correction bound is a Hamming weight, so the headline degradation curve is stratified by `RealizedDamage` — the axis the bound lives on. The metered bits are what expose the gap between the two: **at k = 2, one sample in eight is completely undamaged**, so a curve indexed by requested flips mixes uncorrupted samples into its corrupted bucket. That gap is the reason the metering is load-bearing rather than ceremonial.
