## Description

Stacked on #10644 — base is `nazar/hardware-lane-honest-ladder`, retarget to `main` once that merges.

#10644 fixed the half cryptography cannot catch: the sealed artifact recorded no token identity, and the default `keyLabel` is `zeta-frost-wrap` on every token, so provisioning one wrapping key across a pack gave a roster where **any one token opened every share**. This is the addressing half, and it is worth having only *on top of* that binding.

> Slot binding is addressing, and addressing is not a security property. Making it "a real, tested path" without identity binding would have produced a roster that looks distributed and isn't, which is worse because it reads as done.

That correction is why this landed second, and nothing here should be read as claiming addressing protects anything.

## Automatic or explicit enumeration?

Neither, as posed — **enumeration is automatic, assignment is explicit.**

- **Assignment** (which device holds which share) is a human declaration. Derived from enumeration order it would be a restatement of today's USB topology, and a roster that agrees with the machine by construction cannot check the machine. There is deliberately no `--write-roster`.
- **Enumeration** (where a named device is *right now*) must be automatic, because the answer changes and nobody should have to know it.

So `C_GetSlotList` is finally called — declared in the FFI table since the file was written, invoked by nothing — as a **search for a device the caller already named**. `by: "slot-index"` survives as discovery-grade for single-token hosts, with an optional `expectTokenIdentity` that upgrades it to a checked address.

**No default.** `opts.slotId ?? 0` is gone: it made N adapters built for N tokens all address one device — the original finding arriving through a defaulting expression instead of through provisioning.

## What the artifact records

**Token identity only.** A slot index is positional and goes stale on the first replug; a stale positional field in a security artifact is one someone will eventually trust. Same reasoning removes the directory as an authority: verification reads the device out of `sealedByToken`, never out of the path (FTR-23).

## Absent token

Throws, naming what *is* attached. A fallback to slot 0 would undo #10644 from the outside — the seal would write a share to the wrong device under a confident label and prompt for the wrong token's PIN. FSA-36 asserts not just the throw but that **no session was opened with any slot at all**.

## Duplication is one participant

`participant := one x, one position, MANY devices`. Devices live *inside* a participant, so "this token counts twice" has no spelling; the two remaining ways to get it wrong are both error findings (`device-holds-two-positions`, `duplicate-participant-index`). `seizureWitness` exhaustively searches for fewer-than-threshold devices meeting the threshold and names them — one-way in the useful direction, and it throws rather than returning a clean-looking null when over budget. Availability is reported too (`positionsSurvivingLoss`, `participant-without-backup`).

`verifyRosterAgainstArtifacts` checks **both** directions; observed→declared is what catches the extra copy sealed onto a spare six months later, which is individually flawless and correctly bound.
