## Description

`gate (required)` went red on PR #15636 because
`ColumnLinearOpsTests.ColumnLinear vectorized filter is measurably faster on
unpredictable data` measured 0.93x against a 1.5x gate: 1 failure in 5921 tests,
on a TypeScript-only change. The test is careful and says so in its own comments
("if this flakes on a loaded runner it will flake in Debug first") — but it
flaked in RELEASE, at 0.93x, which is below even the 1.02x a deliberately
bypassed vector path measures. That is either a very loaded runner, a different
CPU model in the pool, or a real regression, and ONE observation cannot tell
those apart.

That indistinguishability is the actual problem. Deleting the assertion throws
away a real detector; leaving it un-instrumented means every red is argued from
memory. This does not decide whether to keep the gate — it makes the question
answerable.

The split that matters, and the reason this is not a failure counter:

  - a FLAKE is an isolated miss surrounded by passes — the machine, not the code
  - a REGRESSION is a SUSTAINED miss — consecutive observations below the gate

A counter conflates them, and a conflated number is exactly what lets a real
regression hide inside a reputation for flakiness. `longestMissStreak` is
reported separately from `missRate`, and neither is derived from the other. The
falsifier for it fixes the miss COUNT and the rate and varies only the
arrangement: 2 misses in 6 reads `flaky` scattered and `regression` consecutive.

The denominator is part of the measurement. A run in which the assertion PASSED
is an observation; a ledger of failures alone reports a rate over an unknown
denominator, the same defect as counting failures on a `main` where most runs
never finished. Zero observations register as `unknown`, never `clean` — and the
report prints "this is not a clean bill of health" instead of an empty table,
because an empty ledger and a healthy one otherwise render identically.

Two details that are load-bearing and easy to get wrong:

  - `missMagnitude` is direction-AGNOSTIC. This repo holds lower-bound assertions
    (speedup >= gate) and upper-bound ones (allocations <= gate); ranking by
    `measured` would call the worst allocation regression the mildest.
  - `pass` is RECORDED, never re-derived from `measured` vs `gate`, for the same
    reason. Re-deriving would invent misses in every upper-bound test.

The key is (test, config): `ColumnLinearOps` gates at 1.15x in Debug and 1.5x in
Release, and folding them together averages two different questions.
