## Description

## The defect

Measured on the fleet Mac (macOS 26.5.2, arm64), read-only:

```
grep -c pam_tid /etc/pam.d/sudo   -> 1
ls /etc/pam.d/sudo_local          -> No such file or directory
ls /etc/pam.d/sudo_local.template -> exists (179 B, mode 0444)
```

Touch ID for sudo works there, and it works from the **wrong file**. macOS
replaces `/etc/pam.d/sudo` on OS updates. Apple ships
`/etc/pam.d/sudo_local.template` precisely so the customisation survives — its
own first line reads *"local config file which survives system update"* — and
the stock `/etc/pam.d/sudo` already carries `auth include sudo_local`.

So the biometric gate that `zflash` and the persona-keys ceremonies depend on
drops to password-only at some future update, silently. Same class as
everything else here: a protection that stops applying without saying so.

**The repo taught the fragile method.** The ADR's implementation step
prescribed `sudo sed -i '' '2i\ auth sufficient pam_tid.so' /etc/pam.d/sudo`.
That instruction is the origin of the state on the machine. Corrected in this
PR rather than left to regenerate the defect on the next Mac.

## Where the config goes, and why

`/etc/pam.d/sudo_local`. Never `/etc/pam.d/sudo` — not once, not to clean up
the redundant line already there. The verifier *reports* that stray line and
deliberately leaves it: it is harmless (`sufficient`, and the durable copy
covers it) and it disappears at the next update on its own.

Written file, minimal by design:

```
auth       optional       /opt/homebrew/lib/pam/pam_reattach.so   # only if installed
auth       sufficient     pam_tid.so
```

`pam_reattach` is **detected, not assumed**, and emitted **before** `pam_tid` —
it re-attaches the process to the GUI session so the prompt can appear inside
`tmux`/`screen`, which is where agent work runs. It is not installed on the
fleet Mac today, so Touch ID sudo silently does nothing in tmux there; the
verifier now says so. Its Mach-O header is parsed, because *present* is not
*loadable* — an x86_64 module on an Apple Silicon Mac is both.

## Lockout impossibility

Not a ceremony, and not a guarantee I have to argue for step by step — it is a
property of the content:

1. **Every control emitted is `optional` or `sufficient`.** Per `pam.conf(5)`,
   a failed `sufficient` module falls through and the chain continues;
   `optional` is ignored either way. Neither can DENY. `pam_opendirectory.so`
   — your password — stays reachable no matter what is in this file. A unit
   test asserts no rendering ever emits a denying control, and a control case
   asserts `required`/`requisite` *would* be caught.
2. **A missing `sudo_local` is tolerated by the include.** Evidence rather than
   assertion: Apple ships `auth include sudo_local` in the stock file while
   shipping *no* `sudo_local`, only the template — and stock macOS sudo
   authenticates fine.

So both "file is wrong" and "file is gone" degrade to password-only. `rm
/etc/pam.d/sudo_local` is a complete undo.

`--apply` also uses the root it was **already given**: it writes atomically
(temp + `rename` — which is simply how you write a file, and incidentally works
where `cp` fails on the 0444 template), validates, and if the result is unsound
removes the file *while still elevated*. Nothing is asked of the operator, no
second terminal, no Recovery. Recovery remains a one-line footnote in the file
header for the case that never happens.

**That validation is structural only, and says so.** `pam_start(3)` looked like
a non-prompting way to test the stack. It is vacuous — measured here on macOS
26.5.2:

```
pam_start("sudo", ...)                          -> 0
pam_start("zzz_nonexistent_service_zzz", ...)   -> 0
```

OpenPAM parses policy lazily at dispatch, so a check that returns success for a
service that does not exist is a check that cannot fail. It is not used. An
honest "wrote it, validated the file and its modules, could not test
authentication without prompting" beats a step that quietly proves nothing.

## The four proofs

**1. Idempotency** — apply twice against a fixture tree:

```
rc_run1=0
already correct -- /etc/pam.d/sudo_local matches the desired content byte for byte.
rc_run2=0
cmp r1 r2 -> rc=0          # byte-identical
mtime_before=1787576366
mtime_after =1787576366    # second run did not touch the file at all
```

**2. Already-correct path** — the line above is the whole report; it byte-compares
first and returns before writing.

**3. Verifier catches the revert** — fixture only, never the live system:

| state | rc |
|---|---|
| baseline durable | `0` GREEN |
| OS update **deletes** `sudo_local` | `1` RED |
| OS update **clobbers** it back to Apple's template | `1` RED — *"the shape a silent OS-update revert leaves behind"* |
| repaired via `--apply` | `0` GREEN, byte-identical to original |

Plus the rollback path, proving the validation can actually fail: with the
include stripped, `--apply` writes, detects the file would be inert, reverts,
exits 1, and leaves no file behind.

**4. The verifier raises no prompt** — this is the claim I was most careful with,
because *"it did not prompt on my run"* is weak: a cached sudo timestamp
produces exactly that observation on a machine where the check **does** prompt.
So the claim is structural. `assess()` is handed `read` and `readBytes` and
nothing else — a prompt needs an exec port or a `LocalAuthentication` binding,
and the module imports neither. Tests assert its only import is the shared PAM
parser and that no exec token appears anywhere in it. The timestamp question is
then moot: nothing is spawned that could consult or refresh one.

Corroborated dynamically with a PATH canary — shims named `sudo`, `security`,
`osascript`, `bioutil`, `sfltool`, `su`, `login`, `dscl` that log any
invocation:

```
verifier under poisoned PATH -> canary absent (nothing invoked)
control: sudo -n true        -> "INVOKED: sudo -n true"   # canary works
```

The control matters. Without it the empty canary would prove nothing.

`sfltool dumpbtm`, `bioutil -r` and `sudo -n true` are all **refused** as
checks. A command is judged by what it REQUIRES, not by what it reads.

## Wiring — and why not a fourth orphan hygiene check

A CI job for the live check would be a **skip on ubuntu**: there is no
`/etc/pam.d/sudo_local` and no Touch ID on a GitHub runner. That is the vacuity
class, and adding it beside the already-orphaned
`hygiene:no-culture-sensitive-collation` and `hygiene:mise-pin-parity` would
have made it worse. So the split follows where the corpus actually lives:

- **Pure logic → gated in CI.** `assess()` is a total function over injected
  doors, so the OS-update-revert case is pinned as a *fixture* and runs on
  ubuntu. Wired into `installer-unit-tests.yml` (paths + one step). I chose that
  workflow deliberately to stay off `gate.yml`, which #14727 is editing.
- **Live check → `tools/setup/doctor.sh`**, every doctor pass, matching the
  existing fd-limits block exactly: read-only, reports, prints the sudo remedy,
  never applies it. Verified working — it currently reports the fleet Mac as
  FRAGILE.
- `bun run setup:touchid-sudo-verify` / `setup:touchid-sudo` for direct use.

`hygiene:linter-coverage` passes (13 tools, 23 scripts, ledger agrees).

## The constraint that makes this mean anything

**Touch-ID-enforced sudo is worth nothing if the caller invokes `sudo` by
name.** A `PATH` entry intercepts it before PAM is ever consulted — live P1 in
`docs/BUGS.md` §"The biometric approval gate is forgeable by a `PATH` entry",
which **#14727** fixes (*resolve every privilege elevator by absolute path*).
This PR and that one are two halves of one property: PAM enforcement is only
real if the binary is the real one. The single elevation here uses absolute
`/usr/bin/sudo`. **`tools/setup/persona-keys/biometric.ts` is untouched** — Nazar
is changing it.

## Honest limits

- **macOS only, permanently.** PAM policy files are an OS-specific mechanism.
  Written in `.ts` per the one-interface goal, not because it runs elsewhere.
- **`sufficient` means ACCEPTED, not REQUIRED.** The chain continues to
  `pam_opendirectory`, so a password still authenticates and sudo never reports
  which module satisfied it — the 2026-08-17 ADR correction already says this.
  This verifies the Touch ID factor is **available and durable**. It does not
  prove any sudo was satisfied biometrically. `required pam_tid.so` would be
  the enforcing form and is not shipped: it locks out lid-closed and SSH.
- **The template-clobber case is inferred, not observed.** I have not watched an
  OS update run. What is measured is that Apple's own template says the file
  survives updates while `/etc/pam.d/sudo` does not — and separately that
  `/etc/pam.d/sudo` on this machine has mtime May 25 while every other file in
  `/etc/pam.d` is dated Jun 24, so the Jun 24 update did not overwrite it. The
  direct edit is unmanaged and out-of-band either way; the verifier is what
  makes the question answerable instead of assumed.
