## Description

Aaron 2026-09-10, having said it several times before: "lets not fail on that, and just let it
keep rolling and accept the security risk i've said several times."

Upstream's `v1.8.0` is a PRERELEASE TAG THAT GETS RE-CUT -- stable URL, changing bytes.
bb82311b -> 8836549e -> ede5b88 -> 8ab94b6 inside a day, and the last one reddened `main`
with 52 identical TLC failures while five open PRs inherited it. Failing on that is failing
on someone else's release cadence.

WHAT CHANGED: exactly one of five verdicts. The banner check now writes a loud diagnostic to
stderr instead of throwing.

WHAT DID NOT: the other four -- completion marker, expected-violation substring, exit code,
and the pinned exhaustive distinct-state count -- remain hard failures. So the rule this
encodes is

    we accept a different BUILD; we do not accept a different RESULT.

THE OBJECTION, AND WHY IT DOES NOT SURVIVE. `repin-rolling.ts`'s own header warns that a
digest bump without re-measuring is "a verifier swap: every claim the old verifier
established is now resting on a verifier nobody ran." That is the right worry about a silent
re-pin, and it is answered by a check that was already here: `DistinctStates` is asserted
against the registry on every gated run, and its own failure text says an exhaustive count is
worker-independent, so a difference "is a real change in the state space". A rolled TLC that
reaches the same distinct-state count on every pinned model has demonstrably explored the
same space and reached the same conclusion. THE RE-MEASUREMENT HAPPENS ON EVERY RUN. That is
what makes this an accepted risk rather than an unexamined one.

The warning is loud and goes to stderr, and names the re-pin command. An accepted risk nobody
can see is not accepted, it is unnoticed.

STILL A HARD FAILURE, unchanged: a JVM that never started. That is reported as "TLC DID NOT
RUN" and explicitly NOT as drift, because an absent banner from a process that never printed
anything says nothing about the jar.

FALSIFIERS. The rewritten test is the thing that stops the acceptance becoming a hole: it
asserts that banner drift ALONE does not throw, AND that the same rolled banner with a
nonzero exit still throws -- about the run, not about the version. Mutation-tested: removing
the exit-code verdict kills 2 tests; reverting the banner to a hard failure kills 1.

THE FIXTURE WAS UNDER-SPECIFIED AND ONLY THIS CHANGE REVEALED IT. The old test's stdout
carried "Model checking completed." while `cleanMarker` is the longer "Model checking
completed. No error has been found". It passed anyway, because it threw on the BANNER before
reaching the clean-run check -- so the truncated fixture never mattered. Relaxing one verdict
made the other four load-bearing in that test for the first time, and it went red until the
fixture was made honest. A test that passes because an EARLIER guard fires is the vacuity
class, and this one had been sitting there.

17 verdict tests pass. Build 0 warnings / 0 errors.
