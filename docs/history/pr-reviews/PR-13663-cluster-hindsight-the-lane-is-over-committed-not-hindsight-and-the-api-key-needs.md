## Description

`hindsight-postgresql-0` takes `Insufficient cpu`. The obvious fix — lower a request until it fits — is refused here, with the arithmetic that refuses it. **Nothing is lowered in this PR.**

## 1. Capacity — hindsight is the symptom, not the cause

MEASURED 2026-08-22 first-hand (`helm template` of the cached hindsight-0.3.0 chart against this Application's own `valuesObject`; every exit code read directly, never through a pipe):

`api 500m` / `control-plane 250m` / `postgresql 250m` — **every one a chart default** (`metalSource: chart-default` on all three ladder rows). Neither rung is a measurement of hindsight's working set; both are reservations, and the ladder already says so in its `consequence` fields.

The whole picture, which is what makes the app-local fix wrong:

| cohort | CPU | vs 2500m budget |
|---|---|---|
| dev lane (37 apps) at the rung the tree ships | **4231m** | over by 1731m |
| …hindsight's share of it | 1000m | |
| lane with hindsight removed **entirely** | 3231m | **still over by 731m** |
| lane with hindsight alone cut to `dev` | 3631m | still over by 1131m |
| **whole lane at `dev`** | **1906m** | **fits, 594m spare** |

`mimir` at 1610m is the larger single reservation. So the only cut that closes this is lane-wide — shrinking hindsight converts a Pending pod into a *different* Pending pod.

**The lane has been over-committed since the dev `longhorn` alias landed**, and `storage-profiles.json` predicted it in writing: *"the only reason that has not bitten is that 14 of them hang `Missing` on a longhorn StorageClass the dev catalog excludes… That is a reprieve, not a fit, and it evaporates the moment the StorageClass exists."* It has evaporated. `hindsight-postgresql-0` is the first pod handed the bill.

**The two substrates are ~4x apart**, which is why a fix for one is wrong for the other: the runner is 4000m (checked, not trusted — `--measure-runner` convicts a smaller machine), while the checked-in `ClusterNode` registrations measure **16 cores** (Addisons820 ×2) and **22 cores** (maximdolphin ×2). The whole 46-app catalogue at `metal` is 8106m — over one runner, under one 16-core box twice over.

**Gap named, not fixed:** `capacity-provenance` compares the *storage* ladder against `spec.hardware.storage`. There is **no CPU equivalent**, so `metal` is the one rung in this ladder with no measured machine behind it.

**And the green budget gate is about a rung the tree does not carry.** Measured today: `--resource-profile metal --check` **exits 0** (`manifests match resource profile "metal"`), `dev --check` **exits 1** with 54 drifts. `metal --budget` **exits 1**; `dev --budget` **exits 0** — and `dev --budget` is what the `plan + unit tests` job runs. Nobody misreported this (the workflow comment already said metal exits 1), but **no check compares the rung CI budgets against the rung the tree ships**, so a green budget step is not evidence the lane can schedule what it applies.

**The maintainer's call, stated with its numbers:** `bootstrap/root-application.yaml` points the metal cluster at the same `main` / `full-ai-cluster/k8s/applications` path the CI lane uses. One committed tree, two substrates, no override point. Applying `dev` to the tree makes the lane fit and costs the 16-core box under-sized requests (evictable under pressure rather than refused a node). That trade is not a CI convenience.

## 2. The Secret — five missing layers, not one

Re-read the chart, and the earlier account was incomplete. There are **two** ways in:

- top-level `existingSecret: <name>` → `envFrom` on **api AND control-plane**, so a missing Secret is **two** pods in `CreateContainerConfigError`; and it **suppresses the chart's own Secret entirely** (`{{- if not .Values.existingSecret }}`), making it the only secret source for the release.
- `api.secrets: {KEY: value}` → needs the plaintext key **in Git**. Named so it is not rediscovered as an option.

What must exist before that one line:

1. **the key** — maintainer-held, cannot be in this repo
2. **a Vault holding it** — never initialised on metal (`vault/TOPOLOGY.md` §2); in CI, #13391's ephemeral init is scoped to **unsealing only** (`init` → `unseal` ×3 → `token revoke -self`, and it greps clean for `auth enable` / `policy write` / `kv put`). **It is not a secrets path** — it ends with an unsealed, empty Vault and no token.
3. **a kubernetes auth mount + policy + `external-secrets` role** — nothing creates one
4. **a `ClusterSecretStore`** — no manifest declares one; only a commented-out sketch
5. **the `ExternalSecret`** — would be the tree's first

**The decision left for Aaron:** one mechanism gated on Vault everywhere, or ESO on metal plus a minted dev Secret (the `applyDevBootstrapSecrets` Grafana precedent). It decides whether the dev lane may diverge from metal on secret provenance. `LIFTS WHEN:` is recorded in the manifest. Landing an ExternalSecret today would fail closed on every lane.
