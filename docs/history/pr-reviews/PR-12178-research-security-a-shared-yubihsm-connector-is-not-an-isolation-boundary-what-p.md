## Description

## What

A research doc on the isolation model and attack surface for **per-tick-source YubiHSM 2 access under
containers**, and — first — on what **"prove-ish" can honestly mean** for a boundary of this shape.

`docs/research/2026-08-18-hsm-container-isolation-a-shared-connector-is-not-a-boundary-and-what-prove-ish-can-honestly-mean.md`

**Design and analysis only.** No session was opened, no auth key created, no key material read, and the
physical device was neither probed nor written to. Every device constant is cited to the shipped SDK
header (`/usr/local/include/yubihsm.h`, libyubihsm 2.7.3), the installed connector's own usage output
(v3.0.7), or Yubico's published documentation and security advisories.

## The answer

> **Container A cannot USE container B's keys. Container A CAN deny container B its keys, and can
> attack container B's client process.**

Confidentiality between tick sources is real and device-enforced. Availability and client-process
integrity are not isolated at all, and cannot be made so by any arrangement of containers, because the
single path to the device is an unauthenticated shared multiplexer that Yubico itself declines to call
trusted — *"The Connector is not a trusted component."*

So "prove-ish" can honestly mean a **machine-checked proof about the declared policy, plus a device
read-back, plus a paired negative test**, together with a named list of what none of that covers. It is
a coverage statement, not a confidence number.

## What is in it

- **Topology table**, five options, with the real isolation boundary named for each. Two of the five do
  not exist on this machine: macOS has no complete USB/IP server, so per-container USB passthrough is
  unavailable, which in turn forces the connector onto a non-localhost interface — precisely the
  non-default configuration Yubico's own advisories assume you are not in.
- **Attack classes ranked by required access** — in-container, host, physical. The in-container tier is
  the whole story and it has six entries; the physical tier is already priced at n−k wipes.
- **The CVE pattern is the finding.** Nearly every SDK-side advisory in this product's history is a
  client-side parser bug on the *response* path — CVE-2020-24387 (session IDs 16–255 into a 16-element
  array, over a cleartext unauthenticated handshake), CVE-2020-24388 (integer underflow firing *before*
  the MAC check), YSA-2021-01, YSA-2023-01 in the PKCS#11 module. SCP03 protects the key material; it
  does not protect the client library, and a shared connector sits exactly where those bugs are
  triggered from. All patched on the installed stack — the specific CVEs are **Dismiss**, the position
  is architectural.
- **Two constants do most of the damage.** 16 sessions device-wide with a 30s inactivity timeout, so
  any tick source can starve every peer — including by accident, from an ordinary session leak. And a
  **62-entry audit ring**: either it wraps, in which case the evidence is destructible by an adversary
  *and* by ordinary traffic, or `force-audit` is set and a full log halts the device for everyone.
  Audit completeness and availability are strictly traded, 62 entries at a time.
- **Discriminating checks vs. vacuous ones.** Five that will be written and cannot discriminate,
  including the insidious "assert an error was returned" — which passes when the object does not exist,
  when the connector is down, when the session failed to open, and when the label was mistyped, and is
  made worse by the device returning `OBJECT_NOT_FOUND` rather than `INSUFFICIENT_PERMISSIONS` for
  cross-domain access. **A negative test with no positive control in the same run is the vacuity
  class.** Four of the six checks that *do* discriminate need no hardware at all.
- **Disclosure measurement through the existing `measure` verb** — three witness forms, three
  class-specific refusals (notably: a disclosure witnessed only by the on-device log is refused, because
  a witness the attacker can delete is not a witness), and a score that is two ordinals crossed rather
  than an invented number the repo has no metering discipline to support. No new currency; payment is
  the existing socially-conferred earning path.

## One recommendation that removes a risk rather than measuring it

Provisioning requires an auth key holding `put-authentication-key` and the `delete-*` capabilities — a
standing device-wide authority across every tick source, which is a weight (§3) and a central point of
control (§1). **Provision once, then delete it.** Re-provisioning then becomes a reset, a reset is a
wipe, and the wipe budget is already priced at n−k.

## Also recorded

**EUCLEAK (CVE-2024-45678) qualifies the accepted physical model.** Below firmware 2.4.0, physical
access *plus a signing credential* can **extract** ECDSA keys, not merely erase — and YubiHSM 2 firmware
is not field-upgradable, so the version is a permanent property that should be read once and recorded.

It also answers the open question left by
`2026-08-14-code-bound-key-access-preliminary-integration-…` §8 Q1, on both halves: containers
materially strengthen L1 by removing all four vectors that note graded it thin on, *and* L1 shipped bare
is the false sense of isolation it feared — because the tidy diagram displays confidentiality and
conceals availability, the client path, and the evidence.
