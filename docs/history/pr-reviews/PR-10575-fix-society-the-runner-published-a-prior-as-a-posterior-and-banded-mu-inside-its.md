### The principled statement, which is why the guard is a no-op for a correct sender

Under EP the message a peer owes is its SITE contribution (`posterior / cavity`), not
its posterior (Minka 2001 ch. 4). Sending the posterior counts the shared prior once
per peer — the prior-double-counting the cavity exists to prevent. `StudentTState`
already carries that site message as `factorMu` / `factorSigma2`, and for a
never-observed dimension it is exactly uniform (`factorSigma2 = +Infinity`, precision
0). A hint built from the right object would have contributed nothing here anyway.
The guard makes the wrong object behave like the right one in the one case where the
difference is total; exchanging site messages is the full repair and changes the wire
type — 081M005CFFE087G0R0026WF2DS.


### Both ends refuse, and the hardcoded `obsCount: 0` was a second, quieter defect

Producer: `evidenceBackedPriorHints` withholds any dimension with `obsCount === 0` —
today all nine, so the list is `[]`, which is the truthful output. Receiver:
`mergePriorHint` returns the local belief unchanged for a hint with no observations.
And `obsCount` is now READ FROM THE STATE. The old literal `0` would have gone on
reporting `0` after the BNN learned something, disarming any receiver-side guard
exactly when it began to matter.

Widening would have been a second unmeasured vote. The band is declared only when the
plus/minus-1-sigma interval does not straddle an edge:
`band(mu-sigma) === band(mu) === band(mu+sigma)`, else `indeterminate`. That is
`tailSensitivity`s gate in a different unit — a SYSTEMATIC against a STATISTICAL, both

as `pointBand`, under a name that does not promise a decision.

## 3. Three defects found while verifying, all measured, all fixed here

- **`mu * 1e6` is not a ppm.** `mu` is a posterior mean on the `SEVERITY_Z` alphabet
  (info 0.5, warn 1, error 2, fatal 4) — not a probability, not bounded by 1. A steady
  stream of ordinary `error`s published **1,940,259 ppm** against a `MAX_TEMPERATURE_PPM`
  of 1,000,000. Now divided by `MAX_SEVERITY_Z`, a number that comes FROM the alphabet
  rather than from taste, so both sides of the ratio are severity z-scores.
- **The `mu > 0.1` cut was inert.** `unaccountedHeatPpm` returns 0 before `failedItems`
  is read, and when it is read it only sets a denominator already clamped to `max(1,..)`.
  Swept over `mu` in [0,4] at 1e-3, forcing `failedItems` to 1 or 0 changed the band at
  NO value of mu.

- **`warm` and `hot` were structurally unreachable.** The reachable set was
  `{cold: mu <= 0.5, critical: mu > 0.5}` against a comment advertising
  "cold -> warm -> hot -> critical". A warn-only stream and a fatal-only stream both
  read `critical`, so the readout could not tell a nuisance from an emergency. This is
  the #10553 shape exactly: an unreachable verdict that looks like a property of the
  model and is a property of the bug.

And **`trend` was a level reported as a derivative** — `mu > 0.6 ? warming : ...` off a
single snapshot. One sample has no derivative. `declareTrend` now needs two beliefs and
declares a direction only past `sigma_delta = hypot(sigma_now, sigma_prev)`; `stable`
additionally needs the error bar narrower than the narrowest band, because `stable` is a
stronger claim than "no direction declared". The runner passes no previous belief (the
BNN does not survive the process boundary), so it honestly reads `indeterminate`.
