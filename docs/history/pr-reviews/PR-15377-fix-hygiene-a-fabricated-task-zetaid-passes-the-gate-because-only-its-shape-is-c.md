## Description

`agencysignature-block.ts` validates the `Task:` trailer twice —
`PLACEHOLDER_TASK_RE` (is it an unfilled template?) and `TASK_RE` (is it
SHAPED like a ZetaId?). Neither asks whether the id EXISTS. So a well-formed
invented key passes silently, and it is HARDER to catch than a placeholder
precisely because it looks exactly right.

I did this today. I wrote `Task: 081M0X0JQGY087G0R000EBCPQ3` into a commit
trailer instead of minting one. It matches no work-item, it passed local
validation, and it would have merged. It was caught because I happened to
re-read my own trailer a minute later — which is luck, not a control.

The legacy id scheme already had this guard: `b-ref-resolve.ts` requires a
`B-NNNN` named in prose to resolve to a real row or archive artifact. The
ZetaId scheme that REPLACED it (`.claude/rules/workitems-mint-with-zetaid.md`)
never got the equivalent — so the newer, mandatory, machine-generated key was
the LESS checked of the two.

WHAT RESOLUTION MEANS. An id resolves when a work-item carries it as its
filename prefix in either state: `workitems/<id>-*.md` or
`workitems/done/YYYY/MM/<id>-*.md`. State is a FOLDER here, so checking only
the open set would fail every commit whose item has since been completed —
that is a test case, not a footnote.

CONTROLS, all run:

  fabricated id                -> rc=1, names it unresolvable
  real OPEN item               -> rc=0
  real DONE item               -> rc=0
  empty work-item index        -> rc=2 (configuration error, NOT a pass)

That last one matters most. An audit that indexes zero work-items would find
every id unresolvable OR, wired the other way, pass everything — either way it
would be reporting on a scan that did not run. It exits 2 instead.

A correction to my own first control, recorded because the mistake is
instructive: I tested a "real" id that had been minted on an unmerged branch
and read its failure as a bug in the tool. It was a true negative — the id
genuinely was not in that tree. The audit indexes the WORKING TREE, which in
CI includes the work-item the PR itself mints, so the normal
mint-and-use-in-one-PR flow passes. Verified by running this audit against the
id in THIS commit's own trailer before writing it: rc=0.

`events/` is deliberately excluded from the index — it is keyed by a different
id space and walking it would admit ids that name no work-item, quietly making
the check pass. Pinned by a test.
