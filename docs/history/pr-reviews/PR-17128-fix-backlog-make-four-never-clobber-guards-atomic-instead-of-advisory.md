## Description

fix(backlog): make four never-clobber guards atomic instead of advisory

Four of the 27 open js/file-system-race alerts share one idiom and one
consequence: a guard that says "never clobber" and cannot keep the promise.

  if (existsSync(path)) { refuse }
  writeFileSync(path, content)

Two writers that both see "absent" both proceed, and the second silently
overwrites the first. The guard reads as a safety property and is really a
narrow window. Replaced at all four sites with `flag: "wx"` (O_CREAT|O_EXCL),
which hands the decision to the kernel so exactly one writer wins and the
loser gets EEXIST -- the refusal the code already claimed to make.

- backlog/new-workitem.ts:255 (alert 462). "Astronomically unlikely (128-bit
  id) -- but never clobber." The id makes collision unlikely; it did not make
  the guard atomic, and those are different claims.
- backlog/complete-workitem.ts:169 (alert 465). The worst of the four: the
  line immediately after the write is `rmSync(done.fromPath)`, so a lost race
  overwrote the destination AND then deleted the original.
- inventory/new-item.ts:85 (alert 460). "collision (should be impossible)" --
  a statement about the id, not about the write.
- backlog/auto-vivify.ts:492 (alert 275). `!existsSync` then write, labelled
  "idempotent write". Now idempotent by the kernel: EEXIST means another
  vivifier got there first, which for an idempotent operation is success, so
  it is neither an error nor counted. This also fixes an over-count --
  processedCount previously incremented once per racing writer for a single
  created file.

The refusal branch is shown to fire, not assumed. Pre-creating the target and
writing with `wx` returns EEXIST and leaves the original bytes intact
(verified directly; the file still reads ORIGINAL after the attempted write).
The happy path is exercised too -- the workitem this commit cites was minted
through the changed new-workitem.ts code.

Two detector gaps found while working, reported rather than half-fixed:

1. The repo's own falsifier, hygiene:no-check-then-use-file-races, reports
   clean on all four of these files and does not carry them in its 295-entry
   baseline. It detects check-then-READ (existsSync->readFileSync,
   readdirSync->statSync) and not check-then-WRITE, which is the more
   damaging half -- a stale read is wrong, a lost write is gone.
2. Its scope argument is `src/Core.TypeScript`, so 8 of the 27 alerts --
   under demo/, src/Renderers/, tools/setup/ and vocab/gen/ -- are in
   directories it never opens.

Both are filed as 081M22S5H5T087G0R00093HKJW rather than patched here;
widening a detector is its own change with its own baseline consequences,
and folding it into a fix PR would make neither reviewable.

Remaining in this class and deliberately untouched: the other 23 alerts,
which are not this idiom (openSync after a lock check in bus/claim.ts, and
read/stat pairs elsewhere). bus/claim.ts already reads both facts from one
handle and carries a comment saying so; whether CodeQL's remaining complaint
there is real needs its own look, and guessing at 23 sites in one PR is how a
cleanup becomes an outage.

Verification: bunx tsc --noEmit exits 0; bun test across backlog/ and
inventory/ is 156/156; prettier --check clean;
hygiene:no-check-then-use-file-races still reports no races.
