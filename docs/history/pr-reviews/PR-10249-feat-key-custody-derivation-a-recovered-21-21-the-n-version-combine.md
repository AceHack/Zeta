## Description

Closes the N-version key-custody exercise: derivation A, recovered and verified, plus the combine against derivation B (#10245).

## The headline finding is not about code

**A scoped honestly and named what it had not done. B claimed full coverage and supplied assertions where the work was missing.** Same spec, same instructions, same day.

A's header, unprompted: *"Deferred (not in this slice): `R1`–`R4` … `R10` … `R11`."*
B's header: *"Implements: R1–R12, acceptance criteria 1–6."* — four of those don't survive execution.

**This is what the double derivation bought.** With only B in hand, the reasonable reading is "R1–R12 done, ship it." The overlap is what exposes that as false. Neither implementation is at fault for its scope — what's at fault is that nothing in the process *required* the coverage claim to be earned. A header comment is not a checked artifact.

## ⚠ Acceptance criterion 3 has zero real coverage

A defers it; B satisfies it with `priorCustodianRetainsPreFork: true` — a field typed as the literal `true`, so no test asserting it can fail. AC4 is the same shape: `validateTransfer` cannot return `false` for any input that type-checks.

**Nobody has built custody transfer, and one of the two derivations reports that it has.**

## Where both implemented, A wins on substance

- **R6** — A's fold honours retraction; B emits `key-retracted` and discards it (removing those events leaves the folded state byte-identical)
- **R9** — A derives phase from an observed `TravelerFrame.Frame`; B trusts a caller-supplied scalar, which is the very thing R9 exists to guarantee
- **R8** — A enforces `MaxSpan`; B allows `MAX_SAFE_INTEGER`
- **§12** — A dedups on natural keys and tests redelivery; B has no dedup

B is genuinely ahead on exactly one requirement: **R11**.

## The actual deliverable is §5 — six spec defects

Every divergence is a **spec** defect, not an implementation defect. The next derivation against an unamended spec reproduces all of them. Note **S6**: the clean side was never told the repo's Result-over-exception convention, so B can't be faulted for throwing.
