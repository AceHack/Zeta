## Description

Work-item `081KYYJEJ4X08QG0R003P8GXSY`, slice 1: a **build receipt** that rides in the commit
message, is bound to the tree it claims, and can be verified by a peer with only a clone.

A CI gate is prevention by a host. A receipt is attestation: a writer states, signed, *"I ran
these checks over this tree and this is what happened"*, and anyone checks that claim without
asking a forge. This PR is that claim made **checkable** — nothing here blocks anything.

## The format

```
Build-Receipt-Version: 1
Build-Receipt-Tree: 4b825dc642cb6eb9a060e54bf8d69288fbee4904
Build-Receipt-Checks: dotnet-build=pass;ts-lint=pass;bun-test=fail
Build-Receipt-Signer: SHA256:7DS+F+oWIaIY6g2LsoCBfDou38nWnfhbz5eUUI6yt+8
Build-Receipt-Signature: U1NIU0lHAAAAAQ…
```

**Bound to the TREE, not the commit** — and that is forced, not chosen: the message is an input
to its own commit hash, so a receipt inside the message cannot name its commit, while
`git write-tree` fixes the tree *before* the commit object exists. The consequence is written
down rather than glossed: a receipt attests to a **snapshot**, never to a history, so the same
receipt is valid for any commit with that tree (a cherry-pick, a content-preserving rebase) and
must never be read as approving a merge.

## Exactly what a valid receipt proves

**Proves** (ed25519 over SSHSIG): the holder of that key signed *these results over this tree*.
A `fail` cannot be edited to `pass` and the receipt cannot be moved to another tree, because
both are inside the signed bytes.

**Does not prove**: that the checks were ever run. Nothing observes the signer's machine. The
value is that a false claim becomes **attributable and retractable**, not that it becomes
impossible. It also carries no timestamp and says nothing about the commit's history.

## Forge-independent, and checkable as such

The only external programs are `git`, and `ssh-keygen` for *signing*. No network call, no forge
API, no PR concept anywhere in the code — `rg 'fetch\(|https://|gh api'` over the new files
returns nothing.

## No new dependency, no new key registry

Signers come from the already-committed `maintainers/<who>/ssh-pubkeys.txt` — the same keys the
SSH CA and commit signing use. `maintainers/zeta/ssh-ca.pub` is excluded by default: a CA key
signs certificates, not build claims.

`src/Core.TypeScript/crypto/sshsig.ts` implements OpenSSH `PROTOCOL.sshsig` verification in pure
TypeScript over `node:crypto` ed25519. That combination is the point: **signing** can use
`ssh-keygen -Y sign` with a key that never leaves an agent (1Password, hardware key), while
**verification** needs no `ssh-keygen` binary, no `allowed_signers` file, and no filesystem —
so a browser tab or a peer with a clone can check a claim.

## Five refusals that do real work

Each has a test that fails without it:

| refusal | what it catches |
|---|---|
| `tree-mismatch` | the receipt does not apply to this commit's content |
| `bad-signature` | a result was edited, or the receipt was moved to another tree |
| `untrusted-signer` | a valid signature by a key no committed roster vouches for |
| `signer-mismatch` | a genuine signature reattributed to another roster identity |
| `unknown-check` | a check id outside the committed vocabulary |

The vector for the last one is a **real `ssh-keygen` signature over `everything-is-fine=pass`**:
every cryptographic check passes, and only the closed vocabulary stops it. Widening the allowed
set makes the very same bytes verify — which is how the test proves the *vocabulary* is what
refused, not the cryptography. An open vocabulary would make a receipt signed, true, and
constraining nothing.

## No timestamp — deliberate

The obvious sixth field is a signing time, so a later receipt could supersede an earlier one.
That is precisely what `.claude/rules/local-time-never-enters-the-shared-fold.md` forbids: two
peers with different clocks would fold different evidence and diverge. So conflicting receipts
are **surfaced** (`detectReceiptConflicts` — the −1) and left for peers to settle by re-running.

## Not wired into CI

`--require-receipt` is opt-in. A receipt that blocks a merge has become the gate this work-item
exists to remove.

## Anchors (checked, not cited)

OpenSSH `PROTOCOL.sshsig` — the golden vectors are real `ssh-keygen -Y sign` output, so the
reimplementation is judged by bytes it did not produce; RFC 4251 §5 / RFC 8709 (SSH wire format,
ed25519); Bernstein–Duif–Lange–Schwabe–Yang 2012 (Ed25519); Merkle 1987 (a git tree oid is a
Merkle root); in-toto (Torres-Arias et al., USENIX Security 2019) and SLSA provenance — this is
the host-free rung of that idea. The committed `maintainers/aaron` fingerprint is cross-checked
against `keyring-public.json` in a test, so the roster reader is verified against real repo data.
