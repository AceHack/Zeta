## Description

## The request, inverted twice

Asked: "update to the latest Java runtime for our tooling," after an isolated BFT
rerun was reported as working on "the installed newer Java 21 runtime."

**First inversion (VERIFIED).** `.mise.toml:170` pins `java = "26"`. Java 21 is
**older** than 26. 21 and 25 are LTS; 26 is a non-LTS interim release. There is
no upgrade available in the direction requested.

**Second inversion (VERIFIED).** The crash the request was meant to fix is not a
Java-version defect.

## Did it reproduce? No — and the retained evidence explains why

The reported failure was already on disk with a full `hs_err` log at
`TestResults/tlc-diagnostics/BftConsensus-d3605d4a.../`. Three facts from it kill
the JVM-version hypothesis:

1. **The C1 workaround was already active.** The crash command line contains
   `-XX:TieredStopAtLevel=1` — the darwin-arm64 policy from
   `081M1XR248G087G0R000H0WJT1`. This is not the failure that policy addressed.
2. **The frame is GC, not JIT.** `DefNewGeneration::copy_to_survivor_space` on
   the VMThread under `VM_SerialCollectForAllocation`. VMThread GC code is not
   JIT-compiled — which is precisely why a compiler-policy flag has no purchase
   on it.
3. **The fault is corruption.** `si_code: 1 (BUS_ADRALN)`, `si_addr:
   0x0000000300000009` — misaligned and *below* the heap base `0x3c0000000`.
   Registers x3–x6 hold ASCII bytes of the metadir path (`"50/state"`,
   `"s/26-09-"`, `"08-15-28"`, `"-22.544/"`) being walked as an object pointer
   during evacuation.

## Does an LTS fix it? No evidence that it would

Local A/B, identical argument vector, only the JVM binary varying, unchanged
`BftConsensus` model:

| arm | JVM | result | elapsed | distinct states |
| --- | --- | --- | --- | --- |
| A | 26.0.0 (`26+35-2893`) | exit 0 | 293s | 4,665,495 |
| B | 21.0.2 (`21.0.2+13-58`) | exit 0 | 285s | 4,665,495 |

Both match the registry's pinned `distinctStates: 4665495` exactly. Neither
crashed.

**Stated limit:** the crash is intermittent, and this A/B runs on the corrupted
host above — which contaminates it *as a test of JVM versions*. It can disprove
immunity (a crash on 21 would settle it) but cannot establish it. A clean A/B
needs a healthy host. So this is reported as "no support for the JVM-version
hypothesis," not as "21 is fine."

## Windows ARM64 — a real, version-caused gap (VERIFIED)

`install.ps1:435` excludes java on Windows ARM64: "mise has no Java 26 metadata
for Windows ARM64." Measured vendor availability for `windows/aarch64`:

| version | Adoptium | Azul Zulu |
| --- | --- | --- |
| 21 (LTS) | yes (21.0.12.1) | yes (21.0.12.1) |
| 25 (LTS) | **no** | yes (25.0.4.1) |
| 26 (non-LTS) | **no** | **no** |

Controlled: Adoptium serves `windows/x64` for 21, 25 *and* 26, so the aarch64
404s are platform-specific, not version-missing. **No vendor ships Java 26 for
Windows ARM64.** An LTS move would close this hole — but only with a
*vendor-qualified* pin that actually ships the platform (bare `21`/`25` resolve
to Oracle OpenJDK, which publishes no Windows ARM64 build).

Note this gap is currently harmless in CI: Windows ARM64 never runs TLC, and the
Windows/macOS gate legs are `continue-on-error`.

## Parity drift found while measuring (VERIFIED)

`java = "26"` resolves to **26.0.2.1** (2026-08-18) today. This laptop runs
**26.0.0** (`26+35-2893`, 2026-03-17) from the same pin. There is no mise tool
lockfile. **CI and dev laptop are five months of JVM patches apart from an
identical pin string** — GOVERNANCE §24 drift that is invisible by construction.

## Recommendation

**Do not change the Java pin to chase this crash.** It would not fix a host
fault, and a bare `java = "21"` resolves to Oracle OpenJDK **21.0.2 dated
2024-01-16** — roughly 2.7 years of missing security updates, because Oracle's
OpenJDK archive stops publishing a line once superseded. That trades a real
security regression for an aesthetic one, and touches CI on every platform.

Open, in priority order:

1. **Triage the host** (Apple Diagnostics / memory test). Until then every local
   crash on this machine is suspect evidence — including ones already attributed
   to other causes.
2. **Decide pin resolution**: exact version or a tool lockfile, so laptop and CI
   cannot diverge silently.
3. **Windows ARM64**: argue the LTS question there on *platform coverage*, not on
   this crash, and price it separately.
