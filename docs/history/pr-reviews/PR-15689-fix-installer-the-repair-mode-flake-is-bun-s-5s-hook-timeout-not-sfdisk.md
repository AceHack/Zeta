## Description

`installer unit tests (bun)` has been intermittently red at
`repair-mode-existing-install.test.ts:133` with `error: sfdisk failed:` and nothing
after the colon. The empty reason turned out to be the whole story.

## The measured rate, with its denominator

The lane is path-filtered, so most runs never execute this file. Counting only runs
where it **did** execute, between `2026-08-24T10:58Z` and `2026-08-26T22:01Z`:

**15 / 90 = 16.7%**

Not introduced by #15554 (merged 19:28Z). First occurrence is `2026-08-24T16:36Z`,
two days earlier. The rate did rise around it — 9/73 before, 6/17 after — but that
window is also the day's busiest CI period, and the timing distribution below shows
why load alone moves the rate.

## The mechanism

Timestamping the log group in each job gives the `beforeAll` duration. The two
populations **do not overlap**:

| | n | min | median | max |
|---|---|---|---|---|
| runs that PASSED | 75 | 0.76s | 2.61s | **4.94s** |
| runs that FAILED | 15 | **5.08s** | 6.90s | 7.69s |

The cut is exactly **5.00s — bun's default hook timeout**. Every run under it passed;
every run over it failed. Bun says so in each failing log, two lines above the error
nobody read:

```
killed 1 dangling process
(fail) (unnamed) [7355.54ms]
  ^ a beforeEach/afterEach hook timed out for this test.
```

The kill lands inside a blocking `spawnSync`, which returns `status === null` with an
empty stderr because the child never got to speak. `run()` collapsed that to `-1` and
printed the blank stderr — so **a timeout reported itself as an sfdisk failure with no
cause**. Reproduced locally to the character: a `beforeAll` that spawnSyncs `sleep 6`
prints the identical four lines.

This is a real timeout, not a retry papering over a race. The hook does a GPT write,
two `mkfs.ext4`, four mounts, several `tee`s and a `sync` on a shared runner. 2–5s is
its honest cost — and the slowest *passing* run cleared the default by **60 ms**.

Ruled out along the way: shared filesystem state (`mkdtempSync` per run, and this is
the only file in the tree touching loop devices), ordering dependence (the failure is
in `beforeAll`, before any sibling leg runs), and check-then-use races (no check-then-use
on the failing path).

## The fix

1. **An explicit 120s bound on `beforeAll`/`afterAll`.** Far above the 7.69s worst case
   on purpose: a hang detector, not a performance budget. Merely doubling the worst case
   would buy the same flake back at a lower rate. The job's `timeout-minutes: 12` is
   still the real ceiling. The nine test legs keep the default — slowest ever observed is
   948ms, so they have 5× headroom and raising them would only hide a genuine hang.
2. **`run()` stops destroying the evidence.** A status-less child now names its signal or
   its spawn error instead of returning an empty string.

## Before / after, same iteration count both arms

Replaying the 90 measured CI durations through a scale model of the hook (durations and
hook timeout scaled identically by 1/50, same bun-hook + `spawnSync` code path):

```
before (default timeout)   pass=70  fail=20   n=90
after  (the fix)           pass=90  fail=0    n=90
```

The model runs slightly hotter than production's 15/90 because fixed process startup is
amplified by the scaling; the direction and the mechanism are the point. The real file
also ran **50× locally: 50 pass, 0 fail**. Full installer suite: 666 pass, 0 fail.

## Falsifiers

Three new tests, deliberately **outside** the `CAN_RUN` gate so they run on macOS too.
Mutation-checked by restoring the old `run()` body: the killed-child and
unspawnable-command tests both go red, and the third — an ordinary non-zero exit must
keep its own stderr unannotated — stays green. So the fix is pinned against
over-reaching as well as under-reporting.

## Not in this PR — two findings handed back

- **Windows `build-and-test` on `main`** is not a script or parity bug: both Windows legs
  died at `scoop install gnupg` on an unreachable external host
  (`www.gnupg.org:443`, `[::ffff:5.9.17.227]`). The preceding `main` commit `f44997541`
  passed all five legs. Upstream availability transient.
- **The on-failure diagnostic is broken**, and this is real: `gate.yml` runs
  `bun src/Core.TypeScript/ci/print-blame-sequences.ts` when a job fails — but when the
  step that failed *is the one that installs bun*, the reporter dies with
  `The term 'bun' is not recognized`. That is why those annotations say only
  `Process completed with exit code 1`. A failure-path reporter that cannot run on the
  failure path is a check that did not run. Not fixed here because it lives in
  `gate.yml`, which this task is bounded away from touching.
