## Description

# Summary

The aarch64 boot discriminator built today (#11007, #11052) **did not transfer to x86_64**, and the lane stayed green throughout. Three of the five boot-stage rungs match strings that an x86_64 boot cannot emit, so on that lane the ladder was reading a constant.

Measured on a **real, successful** x86_64 CI serial log — run 31975465756's uploaded `qemu-full-install-serial.log`, 170KB:

| marker | rung | occurrences |
|---|---|---|
| `UEFI firmware` | firmware | **0** |
| `` Booting `NixOS `` | bootloader | **0** |
| `EFI stub: Exiting boot services` | kernel | **0** |
| `Welcome to NixOS` | userspace | 1 |
| `zeta-installer login:` | login | 1 |
| `ISOLINUX ` | *(the real bootloader banner)* | 1 |
| `Linux version ` | *(the real kernel handoff)* | 1 |

x86_64 boots **SeaBIOS → ISOLINUX → a BIOS kernel handoff**; the ladder was written for **EDK2 → GRUB → EFI stub**. So it could only ever report `none` or `login` — and **nineteen consecutive successful runs confirm it** (31964938508 … 31977504172): every one printed exactly one stage line, `stage → login`.

And the crux itself reproduces on x86_64. A non-bootable image on the harness's own xhci/usb-storage chain:

```
serial log = 0 bytes, QEMU still alive at 25s
```

Indistinguishable from a healthy boot that has not reached userspace — so only the clock could settle it, at the full 300s, with an empty serial tail.

# Notes

**What was reused vs built.** Reused: the whole harness — ladder, `classifyBoot`, exit codes 0/1/3/4, stall detection, the workflow's outcome branching. x86_64 needed no separate machinery, only per-road markers on the same rungs (the two vocabularies are disjoint, so the API stays arch-blind) and a channel for the firmware to speak on.

**The firmware channel is `isa-debugcon` on port 0x402, to a separate file.** `-fw_cfg name=etc/sercon-port` also works (verified), but it shares the guest's UART. This lane is a blocking gate that has passed 19 consecutive runs, so the instrument must be additive only — a test pins that the guest-visible device model is byte-identical with and without it.

**`efi-stub` renamed to `kernel`.** The rung means "the kernel took over from the bootloader". On a BIOS boot that is not an EFI stub, and the old name would have been printed as a false statement in every x86_64 CI log line.

**The self-test asserts settle TIME, not only exit codes — and that is a mutation result, not a precaution.** Deleting the `No bootable device` marker left the BOOT-FAILED case **still exiting 1**, because it fell through to the budget-exhaustion branch. Only the elapsed time moved: 10s → 120s. An exit-code-only check would have passed while the evidence-based verdict was gone and the harness had quietly reverted to deciding by clock.

**Why a CI step and not only unit tests.** This defect was invisible to unit tests by construction: every assertion was over strings we wrote ourselves, and the defect was that those were not the strings the guest emits. The self-test boots two 1MB synthetic images (~30s) *before* scenario 1, so a blind instrument fails there rather than mis-reporting the real ISO. It also guards a new runner-dependency: whether a distribution's SeaBIOS was built with debug output is a property of the runner, not of this repo, so if Ubuntu ships a quiet one the step fails loudly instead of silently degrading.

**The x86_64 lane is NOT intermittent** — the opposite of aarch64. Those 19 runs booted in **21–24s** against a 300s budget (≤3s spread, ~14%), versus aarch64's 175s vs >4184s swing on identical images. So no timeout tuning and no loosening of the blocking policy: there is no evidence that would justify it.

**Also fixed:** the STALLED message hardcoded *"~192s on a good CI run and ~52s on a local TCG host"* — aarch64 numbers, printed by an arch-blind classifier on a lane where a healthy boot is 21–24s. Removed rather than duplicated per-arch.

## Honest limits

- The four live outcomes were demonstrated with **synthetic marker images**, not the real NixOS ISO. Real: SeaBIOS, the UART, the usb-storage chain, the harness. Synthetic: the guest. The real ISO can only produce BOOTED, which is exactly why the other three had no live evidence before this.
- Demonstrated under **TCG on macOS/arm64**, not on a KVM ubuntu-24.04 runner. The CI numbers in this PR come from job logs; the local numbers come from local runs. **Unexercised until this PR runs:** the self-test on a GitHub runner, and whether Ubuntu's SeaBIOS emits on debugcon there. If it does not, the step fails and says so — that is the design.
- The settle bound is set at 75s against a 180s budget to allow for iPXE running on a runner with real NAT (measured 23s locally in that shape, 10s with no network). If it proves tight in CI it is a bound to re-measure, not to raise by feel.
- The deadline branch still calls "budget exhausted below the bootloader" a BOOT-FAILED. That inherited policy is untouched here; on a TCG x86_64 host it is the one place a slow-but-healthy boot could still be mislabelled. Left alone deliberately — changing a blocking policy needs its own measurement.
