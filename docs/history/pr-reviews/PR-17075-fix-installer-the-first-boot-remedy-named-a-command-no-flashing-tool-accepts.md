## Description

fix(installer): the first-boot remedy named a command no flashing tool accepts

B5. When discovery refuses -- "Something already answers on this segment ...
proceeding would create a second cluster that is undone by hand" -- first boot
printed exactly one instruction:

    zflash --role first-control-plane
    zflash --role joiner --join-server-url <url> --join-token <file>

NO DEVICE-FLASHING ENTRYPOINT ACCEPTS `--role`. Both `cli.ts` and `flash-usb.ts`
run a strict argv allowlist and exit 2 on an unknown flag; measured, `--role`
appears zero times in either. It is accepted only by `file-backed.ts`, whose
usage is `--iso <installer.iso> --output <raw.img> --esp-offset-bytes <bytes>`
-- it builds an IMAGE, not a flashed stick, and needs an ESP offset the operator
does not have.

So the single instruction given at the moment the operator is blocked named a
command that cannot be run on the medium in their hand.

THERE IS A REAL PATH AND IT WAS ALREADY THERE. The 10-second keystroke prompt at
the top of this script sets ZETA_ROLE_SOURCE=keystroke:c|w, and
`esp:*|keystroke:*) ZETA_ROLE_DECLARED=yes` accepts a keypress exactly as it
accepts an ESP-written role. The remedy now names that, plus the fact that a
keypress is DECLARED while the ISO default is not -- which is the distinction the
refusal is about.

It also states plainly that joining a node to an existing cluster from a device
flash is NOT WIRED, rather than implying a flag would do it.

FALSIFIER: `first-boot-remedy-flags.test.ts` parses the PRINTED lines of
zeta-first-boot.sh (comments excluded, so the corrected text can still discuss
the flag) and asserts every `zflash --flag` it names is in the CLI's allowlist.
That pins the general rule -- an operator remedy must be runnable -- not just
this instance. A second test pins that `keystroke:*` really does satisfy
ZETA_ROLE_DECLARED, because the new advice is only correct while it does.

Mutation-checked: restoring the old `zflash --role` line fails the guard
(1 pass / 1 fail); restored, 2 pass. Full zflash suite 788 pass / 0 fail.
`bash -n` clean. tsc 0 errors.

The guard caught its own author on the first run: my first draft of the
corrective NOTE contained the literal string `zflash --role` inside an echo, to
say the flag does not exist, and the test could not tell that apart from an
instruction. Reworded to warn without looking like a command.

To make the allowlist checkable, `ALLOWED_FLAGS` moves from inside `main()` to
`allowed-flags.ts` and is exported as `ZFLASH_ALLOWED_FLAGS`. The extraction is
required rather than tidiness: `cli.ts` calls `main()` at module scope, so a test
importing it to read one constant would run the CLI. Same reason the freshness
list moved out in #17031.

NOT ADDRESSED: wiring role/join-token onto the device-flashing path. That is a
design decision about whether a flashed stick should carry cluster-join material
at all, and the register already notes those are structurally not flashable. This
commit stops the installer from claiming otherwise.
