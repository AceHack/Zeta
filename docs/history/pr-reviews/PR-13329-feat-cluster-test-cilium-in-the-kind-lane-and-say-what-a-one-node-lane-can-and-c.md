## Description

## The question

Aaron, 2026-08-20: *"Also can we test cilium? This is the plan on real metal."*

**Yes — and doing it turned up two things about the metal configuration itself.**

## 1. The mechanism, cited

- kind ships `networking.disableDefaultCNI` and `networking.kubeProxyMode`
  ([kind config docs](https://kind.sigs.k8s.io/docs/user/configuration/)); Cilium documents the kind
  install path ([Cilium on kind](https://docs.cilium.io/en/stable/installation/kind/)).
  Note the asymmetry that is easy to get wrong: kind's field is `kubeProxyMode: "none"`. There is no
  `kubeProxyReplacement` field on the kind side — that is the *helm* value on the Cilium side.
- WireGuard on a GitHub-hosted runner is not a guess: cilium/cilium's own
  `.github/workflows/conformance-clustermesh.yaml` runs kind on `ubuntu-24.04` with
  `--helm-set=encryption.enabled=true --helm-set=encryption.type=wireguard` (matrix rows 140 / 215 / 260).

## 2. Our specific values — the honest judgement

Every shipped value runs in kind. There is **one** delta, enumerated in code and printed on every run:
`k8sServiceHost`. `control-plane` resolves on metal because `k3s-server.nix` writes it into the node's
`/etc/hosts` and SANs the API cert for it; a kind node has no such entry and reaches the API server by
its Docker-DNS name. Same endpoint, different resolver.

**Encryption is NOT disabled for the dev lane, and a dev overlay that disabled it would be worse than
the exclusion it replaced.** The reason is the first finding:

### WireGuard encrypts nothing on the cluster we plan to run

Two independent Cilium behaviours, from the pinned release's own docs:

- *"Packets are not encrypted when they are destined to the same node from which they were sent."*
- *"Cilium automatically disables node-to-node encryption from and to Kubernetes control-plane nodes"*
  — `node-encryption-opt-out-labels` defaults to `node-role.kubernetes.io/control-plane`.

`full-ai-cluster/k8s/single-node-budget.json` declares `nodeCount: 1`, and that node is the control
plane. So `encryption: {enabled: true, type: wireguard, nodeEncryption: true}` is **inert on metal
today** — the device is created, keys are exchanged, and zero bytes are encrypted. A
control-plane + one-worker cluster is still zero on the node plane; **two workers (three nodes) is the
first shape that node-encrypts anything.** Cilium's own connectivity test agrees — `node_to_node_encryption.go`
is built `.WithMultiNodeOnly()`.

Consequence for this PR: the kind profile is **one control-plane node on purpose**. Not a resource
compromise — it reproduces metal exactly, including the uncomfortable part. Adding workers would make
CI encrypt traffic metal does not. `cilium-kind-lane.ts` **REFUSES** if the two shapes' encryption
verdicts ever diverge.

(Also worth knowing before metal: `encryption.nodeEncryption` is marked deprecated in the chart —
*"will be removed in v1.22"*. We pin 1.16.5.)

### `gatewayAPI.enabled: true` — a feature that never starts, reported as on

Both Cilium surfaces set it. `full-ai-cluster/k8s/bootstrap/gateway-api-crds.yaml` is Gateway API
**v1.2.1 STANDARD** — five CRDs, no `TLSRoute`. Cilium 1.16.5 lists `tlsroutes` in
`operator/pkg/gateway-api/cell.go` `requiredGVK`, and on the CRD check failing
`initGatewayAPIController` **logs and `return nil`**: the operator stays Ready, ArgoCD reports the
Application Healthy, and the Gateway API controller never runs. That is "a check that did not run
looks like a check that passed", applied to a *feature*.

Recorded with a `LIFTS WHEN:` condition rather than fixed here — vendoring the experimental channel
changes what first boot applies on metal, which is a cluster-config call, not this lane's.

## 3. What shipped

- `full-ai-cluster/dev-cluster/profiles/ci.cilium.kind-config.yaml` — no default CNI, no kube-proxy,
  podSubnet `10.42.0.0/16`, one control-plane node.
- `src/Core.TypeScript/cluster/cilium-kind-lane.ts` — offline and pure. Reads the surface roster **out of
  `cilium-wireguard-sources.nix`** rather than restating it (that file's own header asks for exactly this
  and could not have it across languages before), audits surface drift, audits Gateway API CRD coverage,
  and computes encryption reachability. Runs in the existing cheap `dry-run` job.
- `src/Core.TypeScript/cluster/dev-cluster/cilium-kind-up.ts` + a new **`live kind Cilium CNI`** job.
  Six assertions, each able to fail: kindnet absent, kube-proxy absent, all nodes Ready under Cilium,
  CoreDNS pod IPs from the cluster pool (this is what separates *"Cilium is installed"* from
  *"Cilium is the CNI"* — kind's own default is 10.244/16), `cilium_wg0` present in the agent, and the
  Gateway API verdict matched against the registry in both directions. It deliberately does **not**
  install ArgoCD: this lane answers one question in a log short enough to read.
- A gating WireGuard preflight on the runner — the same three probes
  `cilium-wireguard-node-preflight.nix` runs on metal.
- The two value surfaces are described throughout the repo as carrying the same values and **do not**.
  Five real deltas are now recorded with reasons; a sixth goes red.
- `DEV_EXCLUDED_DIRS` was a bare seven-name `Set`. It is now **built from** a reasons map in which every
  entry must name a `LIFTS WHEN:` condition, so an unreasoned exclusion is unwritable.

`cilium` and `cilium-lb-ipam` stay excluded from the *default* kind lane, deliberately: that lane brings
up kindnet before ArgoCD exists, so applying the Application there would install a second CNI over a
working one. The exclusion is now reasoned and names the lane that does exercise it.

## What the first CI run taught (recorded, not quietly fixed)

The first run of the new lane went **red** on the WireGuard preflight with:

```
Error: Attribute failed policy validation
```

which reads exactly like *"this runner cannot do WireGuard"* — and is nothing of the kind.
`modprobe wireguard` had already succeeded. The failing call was
`ip link add dev zeta-wg-preflight type wireguard`, and **that name is 17 characters**; `IFNAMSIZ`
is 16 including the NUL, so the kernel's netlink policy for `IFLA_IFNAME` rejected it.

The name I needed was one file away with the comment `Under IFNAMSIZ (16)` beside it —
`probeIface = "zeta-wgprobe0"` in `nixos/modules/cilium-wireguard-preflight-checks.nix`. **I restated
it instead of reading it**, in a PR whose entire argument is that a value copied into a second place
drifts. So the fix is the derivation, not a shorter string: `wireguardProbeInterface()` parses that
nix module and **refuses** rather than falling back to a hard-coded name, the workflow captures it
from `--print-wg-probe-iface`, and putting the 17-character name back now fails **offline**, in the
1-second plan step, instead of costing a runner.

Worth stating plainly because it is the same class of failure the lane exists to catch: an error
message that names the wrong cause is indistinguishable from the real thing until someone reads the
line above it.
