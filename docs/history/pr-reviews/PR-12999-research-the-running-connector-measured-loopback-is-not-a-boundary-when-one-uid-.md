## Description

Adversarial read of the **live** `yubihsm-connector` found running on the maintainer's Mac with the
HSM attached. Advisory, not binding. **The device was not touched.**

## The headline inverts the prior doc's assumption

The connector **is** bound to `127.0.0.1` only — the narrow bind the 2026-08-18 note recommended and
assumed macOS made impossible. **It is still not a boundary**, for a reason unrelated to the bind
address: it was started **by hand** as `acehack`, is **not** under launchd or `brew services`, and
**nothing respawns it.**

> Any process running as that uid can `kill 14449` and bind 12345 itself. **There is no race to win,
> because the legitimate listener does not come back.**

The 2026-08-18 doc treated occupying the endpoint as requiring *"a bind race, a container-bridge
spoof, or compromise of the connector process."* **Measured, it requires `kill`.** The attacker then
*is* the connector — the responder on the parse path of every client, which is the position that doc
already priced High-as-a-class citing three response-parser CVEs, **at least one executing before the
MAC is checked.**

**Re-verified before landing:** `launchctl` and `brew services` both show no yubihsm job; `lsof`
confirms the loopback-only bind.

**Cheapest fix is not a firewall — it is supervision.** launchd `KeepAlive` converts a silent
takeover into a visible service flap. It doesn't stop an attacker who also unloads the job; **it
removes the free, quiet version.**

## Every reachable row reduces to one predicate: can you execute code as `acehack`?

One user account — **empty by provisioning accident, not by control** — and 8+ same-uid processes
including five `bun`, one `node`, and two third-party AI computer-use apps. A LAN host reaches it in
**two hops** via qbittorrent or Plex, both same-uid, **with no escalation.**

**And a loopback-only service is one control-port command from the internet.** Tor runs as the same
uid with a cookie-authenticated control port; `ADD_ONION` maps an ephemeral onion to
`127.0.0.1:12345` — no port opened, no firewall rule changed, no inbound connectivity required.

> Worth naming precisely: the Itron rule records **outbound-initiated connection** as the portable,
> genuinely good half of that patent. **That property is symmetric.** It is exactly as good for the
> attacker, and here it is pre-installed and running.

Honest strength: this does **not** let a remote attacker sign. It gives them **the pre-auth surface
and the DoS surface, from anywhere.**

## The asymmetry that matters for x402

A port-holder cannot read commands, forge them, or mint a session. What they get anyway: session-slot
exhaustion, total denial of the root of trust, the response-parser position, traffic analysis.

> **None of these steal a key, and all of them stop a payment.** For an agent that must sign
> unattended, **availability *is* the security property** — and availability is what the port-holder
> owns completely.

## Serial pinning — a correctness control mis-shelved as a security one

The case *against* is stronger than it looks: the check is **on the wrong side of the trust boundary**
(performed by the untrusted component over a value the device supplies); a serial is **a claim, not a
proof**; and it gives **zero** defence against the attack that matters — **the rim-press factory reset
leaves the serial unchanged**, because it's a hardware property. *Pull → reset → reinsert* produces a
device a pinned connector **accepts without hesitation**, now holding the factory-default auth key
with all capabilities and all domains.

**Verdict: pin it as correctness, and stop calling it a perimeter control.** What actually detects
substitution belongs where pinning is tempting to put it: treat `Authenticate Session` failure as a
**device-may-have-been-replaced** alarm (that check is on the *right* side of the boundary), watch
`Log used` going backwards as a **pre-auth wipe signature**, and use **attestation**, where the serial
is a proof rather than a claim.

## The distinction that collapses — the most decision-relevant fact here

Sessions expire after **30 seconds** of inactivity. An agent signing every few minutes has no live
session between payments.

> **Unattended signing therefore necessarily means a credential resident on the host. There is no
> configuration in which the host holds only a session handle.**

"Live session, credential zeroed" is **illusory, not a distinct configuration.** Keychain-ACL'd
storage equals a plaintext file once the attacker executes *inside* the ACL'd binary — which is what
"compromised agent" means: **ACLs bind to a code-signed binary, not to the intent of the code inside
it.**

So the question is not *how to stop host compromise from producing signatures* — it cannot be stopped
— but **how small, how attributable, and how expensive-to-repeat each stolen signature is.** That
points at domain scope, capability scope, and **rate limits that live off the host.** The device
offers none, the connector offers none, **the repo has none.** That is a **design gap, not a
configuration knob.**

## 62 entries is not an audit log — it is a 62-deep undo of the evidence

Default behaviour is documented: **it wraps silently, it does not refuse.** An adversary hides one
signature with **62 boring operations** — no vulnerability, no extra credential — and **the hash chain
stays perfectly valid across the wrap.** Integrity preserved while the evidence is destroyed is the
worst combination for a reviewer, **because the chain verifies and invites confidence.**

It's destroyed **without an adversary** too: an agent signing once per second clears the window in
about a minute — **for an x402 payment agent, ordinary operation is the eviction mechanism.** And the
log carries a monotonic **tick**, not wall-clock, so correlating tick→time is a host-side step **and
the host is the thing assumed compromised** — an undeclared crossing under
`local-time-never-enters-the-shared-fold`, letting a compromised host **silently supply the timeline
of its own audit.**

`force-audit 0x02` is **irreversible until factory reset** — a gated class needing fresh human
authorization. That belongs in the runbook where the command appears, not a footnote.

## The mitigation split is the point

**Theatre or mis-shelved:** binding to loopback is genuinely useful against a LAN host and useless
against every *reachable* actor — listing it as **the** perimeter control is the vacuity failure, *the
check cannot fail against the attacker who exists*. Firewalling 12345 stops nobody the bind didn't
already stop (**the macOS firewall does not filter loopback**). Host-side session limits duplicate a
tighter hardware timeout. And *"key material never leaves the device"* is true but **implies bounded
loss in a mitigation column and delivers none** — it is an exclusion, never a control.

## Two measured corrections that make the prior doc *less* alarming

Its §4 warned the connector *"cannot listen only on localhost and still serve containers"* — it **is**
loopback-bound and the Docker VM is down. Its §5-T2-A listed dyld injection unqualified — **hardened
runtime with no entitlements means dyld ignores insertion.** Likewise the pre-auth firmware disclosure
currently tells an attacker *"this one is patched"* (EUCLEAK is pre-2.4.0; this is 2.4.1).

> **Recorded because that is how the alarming parts stay credible.**

## The window

**No Zeta code path uses the connector yet** — `rg` for `YUBIHSM_CONNECTOR`, `connector/api`,
`127.0.0.1:12345` returns nothing. Blast radius today is ad-hoc human use, **so every control above
can land before anything depends on the current shape. That window closes the first time an agent
signs.**
