## Description

fix(dogfooding): the first-session tick budget was a hidden oracle -- three bare numbers, no attribution

The dogfooding loop carried three tick bounds with three different values and no
record of who chose any of them:

    observe/first-session-run.ts:260   const maxTicks = 24    no comment
    observe/first-session.ts:324       maxTicks = 12          no comment
    arc-solver/arc-harness.ts:68       let maxTicks = 20      "Safety valve to
                                                              prevent infinite
                                                              loops during testing"

All three verified on origin/main before touching anything. The one comment
explains why a BOUND exists, not why 20 -- and that gap is the whole defect,
since nobody disputes a bound is needed. Meanwhile the F# core has had the right
shape all along: SimLoop.run takes a Budget and reads `max 1 budget.MaxTicks`;
DarkHallScheduler reads the same field. The loop never picks the number, it
receives one.

WHAT CHANGED

observe/tick-budget.ts (new): `TickBudget` = { name, maxTicks, chosenBy,
rationale } plus `clampTicks` (mirrors the F# `max 1`, so no caller can switch
the rail off) and `budgetIsAttributed`. The type refuses to carry a number
without someone on the record for it.

THE NUMBERS ARE NOW DERIVED, NOT PICKED

I measured the first-session state machine instead of asserting a bound.
Exhaustive walk of every state reachable from `defaultNodeSession()` under the
menu the operator is actually offered:

    reachable states                            115
    longest simple advancing path                 6
    witness   setup gh -> offer cloud -> setup claude -> setup codex
              -> setup gemini -> complete
    transitions that leave the state unchanged    0

So:

  - FIRST_SESSION_LLM_TICK_BUDGET = 6, EXACTLY the diameter with no headroom --
    and that is a measurement, not taste: with zero non-advancing transitions
    the pure loop cannot spend a tick without progressing, so a 7th tick could
    only ever run on an already-complete session. 12 was not wrong, it was
    unexplained: twice what is needed, with nothing saying why.

  - FIRST_SESSION_RUN_TICK_BUDGET = 6 + 3x4 = 18. The conductor needs a retry
    term that the pure loop does not, because `applyAction` returns the session
    UNCHANGED when `executeSetupCredential` reports `failed` ("pick another
    option") -- so this loop, unlike the pure one, can burn a tick without
    advancing. Three retries at each of the four credential-setup steps on the
    longest path. The 6 is measured; the 3 is a CHOICE and is labelled as one.

    This is why the two budgets stay DIFFERENT rather than being unified: the
    difference is now a stated reason instead of the gap between an unexplained
    24 and an unexplained 12.

  - ARC_SWARM_TICK_BUDGET = 20, VALUE DELIBERATELY UNCHANGED, reason supplied.
    This bound cannot be derived the way the other one was: `swarm.tick` can emit
    `decompose`, which ADDS backlog items, so the backlog is not monotonically
    draining and there is no finite path length to measure. What actually bounds
    it is cost -- 20 ticks x 4 role model-calls = up to 80 completions per
    puzzle. Moving the number to make something pass would be inventing evidence,
    so it did not move.

DOGFOODING ADVANCED: the marker write is now exercised for real

`writeMarker` had ZERO coverage. All five pre-existing `runFirstSession` tests
pass `--dry-run`, which is precisely the flag that skips it -- so the single
durable side effect of the first session, the file that decides whether a fresh
node re-runs first-login on every subsequent shell, was never once executed by a
test. Two tests now do it for real: one writes the marker to a tmpdir and parses
the timestamp back off disk, one proves a second non-demo run short-circuits on
the marker the first run wrote. No live model and no live `gh` -- the backends
are deterministic prompt-parsing mocks and the shell runner is faked.

FOUND AND PINNED, NOT FIXED: the short-circuit returns `defaultNodeSession()`
rather than probing, so it reports `gh: "missing"` even when gh is authenticated.
`main` reads only `.complete`, so it is latent rather than live -- a fabricated
value on a real path. The test asserts the current behaviour on purpose, so a
future fix shows up as a deliberate test change instead of a silent one.

ALSO FOUND, NOT CHANGED: two more unattributed bounds of the same class in the
same loop, outside the three named -- `observe.ts:769 maxSteps = 20` (default
param) and `observe.ts:918 runLoop(start, topPick, 30)` (bare literal at the demo
call site). Left alone deliberately: observe.ts is 923 lines under cross-language
golden-vector parity and this PR should stay reviewable. Reported, not smuggled.
