## Description

## What

Aaron's observation (2026-08-27): the loop should be driven from outside, not by each agent
remembering to keep itself alive — **with an exit** so an agent can deregister from a specific loop.

Externalising the *drive* was already done: 43 scheduled workflows. The missing half was the **exit**.

### `src/Core.TypeScript/agent-loops/loop-registry.ts`

> A recorded opt-out makes **chosen** silence distinguishable from **broken** silence.

An agent that stops and an agent whose loop is wedged are the same observation from outside —
absence. That ambiguity is the standing-by failure: a check that did not run wearing the face of one
that passed.

Three ways a loop ends; only one needs an intelligence to notice:

| | | |
|---|---|---|
| `deregister` | the agent chooses out | recorded, attributed, reversible |
| `exhaustion` | the tick budget lapses | **automatic** — forgetting to renew *stops* it |
| `renew` | a positive act extends it | |

Exhaustion is what *bounded* buys: the loop **fails closed**. The cost is stated rather than hidden —
continuity now needs periodic renewal, so an exhausted enrolment keeps its reason and the quiet
stays legible.

**Nobody can deregister anybody else.** `actor != subject` is refused, with no maintainer exception
— an override would be the invariant with a door in it, and the door is what gets used. Same shape
as the privacy budget: spend / stake / **never confiscate**. Mutation-checked: neutering that guard
kills 2 tests.

The driver asks `shouldTick`, not the agent. If honouring an opt-out depended on the agent
remembering it had opted out, the responsibility would still sit with the intelligence.

### The hook: rewritten, not deleted

Two defects. It cited `.claude/rules/tick-must-never-stop.md` — **a path that has not existed since
that rule was archived to `rules.bak/`**; enforcement outliving its reason is how an instruction
becomes folklore. And it made continuity depend on every agent arming its own cron.

It now states where ticks come from and how to leave one. The in-session cron is **kept and named as
a bridge** for interactive sessions — a mechanism, not an imperative — since no external driver
covers them yet.

### Ferried: the data-flywheel video

Transcript quarantined under `docs/ip-questionable/` per that folder's segregation rule; analysis
separate and independent of it.

Aaron's structural claim, developed: **a DU is the case set; a flywheel is a *learned discriminator*
over it.** The closed case set is the load-bearing half — the same property as the closed command
set, where the far side may *name* a command but never *define* one.

And his correction, which fixes a hole I'd left: we have exactly one extra case, `NeedsNewCode`,
handled by another agent writing code that society evaluates. That is an escape which is a **case,
not a hole** — extension happens at authoring time, never at inference time, so the discriminator
still cannot mint a case. Same shape as hygiene-by-capability, where the escape hatch is *write the
missing CLI* and each use leaves the system **more complete**.

Corpus claim recorded **with its limits**: we have a log store, not a dataset; the volume is
uncounted; and the adversarial corpus is bounded by the trainset floor, so it is less independent
than its transcript count suggests.

## Second commit — `corpus/labelled-observation.ts`

Aaron's follow-on: *"we can now make this generic and reusable and have well defined types that work
in any domain, where today each one of our corpuses are a little bit adhoc, our agency signature
stuff is half of the labling too ... i'm sure they will [be] even more we didn't think of."*

The hard ask is the third: labels **nobody has thought of** must work without a schema change,
because the ones we'd design for today are exactly the ones we already know about. That pulls
against *well-defined* — a closed enum needs a migration per question, a free-form blob is not a
type. Resolved by DV2.0 on change rate:

| | |
|---|---|
| **hub** | the observation — stable, content-addressed, domain-agnostic |
| **satellite** | the labels — open set, many asserters, added constantly |

Label **space** open; label **shape** closed. A new label kind needs no migration; it still cannot
be anonymous, undated, or unnamespaced.

### The property that makes it ours

Standard labelled datasets carry one label per row, because the consumer wants a supervised target —
that format *cannot represent a disagreement*, so pipelines discard it before storage. Here
conflicting labels **coexist**, and no API can pick a winner. Raw vault as a type: *a single version
of the facts, never a single version of the truth.*

`resolvedLabel()` is **deliberately absent, and its absence is tested** against the module's real
export list — a resolver would be one keystroke away and would make collapse the default path.

- **Extensibility:** the test uses `bathymetry/sediment-grain-class` — a namespace appearing nowhere
  in the source — plus a non-code corpus row. A roster, enum, or switch fails both.
- **AgencySignature mapping:** all ten keys map with nothing dropped, and an unrecognised *eleventh*
  key survives — the open-label property exercised on the surface most likely to grow.
