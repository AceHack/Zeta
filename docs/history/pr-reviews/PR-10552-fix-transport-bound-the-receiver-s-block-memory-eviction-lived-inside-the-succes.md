## Description

Closes `081KZYQJPNG087G0R002B9E9S1` (P1).

`LossyUdpChannel.recvBlocks` grew one `ReceiverBlock` per peer-chosen u32 `blockSeq`, forever. Eviction existed — it was lexically inside `if (recovered)`, the one branch a leaking stream never reaches, because a block that never becomes recoverable never triggers its own cleanup.

**It is not attack-only.** A block becomes recoverable at 4 of 8 symbols, so a block that never recovers is one that lost 5+ — ordinary heavy loss, which is what this transport is *for*. An attacker only makes it fast: `blockSeq` is a header field separate from `seq`, so a peer holds `seq` monotone (provoking no NACK at all) while spending 4.29e9 distinct keys.

## Measured — 200,000 packets, 256-byte payloads, 82.8 MB in, `Bun.gc(true)` both sides

| | before | after |
|---|---|---|
| blocks retained | 200,000 | **8** |
| RSS growth, total | 259,833,856 | 93,863,936 |
| **RSS growth, 2nd half** | **119,848,960** | **901,120** |

**Read the second-half slope, not the total.** A Bun heap that expanded to hold transient JSON/Buffer garbage does not return those pages, so ~100 MB of high-water mark survives a full GC either way — the total flatters the fix. That residue is *flat* in packet count (72.9 MB at 25k, 104.1 MB at 400k: 16x the traffic, same residue) while the defect was strictly linear. The slope falls **133x**. Reproduce: `bun src/Core.TypeScript/discovery/udp-lossy-transport.retention-measure.ts 200000`.

## The bound is derived, not invented

`RECV_BLOCK_WINDOW` — the same constant `MAX_NACK_GAP` is already derived from. Retaining past it buys nothing: the [8,4,4] decoder acts *within* a block, never across blocks.

## The order was the real decision, and it was measured

Every candidate caps the map at 8. They differ entirely in *what they evict*. Delivered payloads of 1600, 400 blocks, seeded reorder jitter, 0% channel loss:

| depth | 0 | 8 | 16 | 32 | 64 | 128 | 256 | parkable? |
|---|---|---|---|---|---|---|---|---|
| unbounded (the defect) | 1600 | 1600 | 1600 | 1600 | 1600 | 1408 | 724 | n/a |
| lowest key | 1600 | 1600 | 1600 | 1600 | 1600 | 1284 | 488 | **YES — 8 packets, forever** |
| **LRU (shipped)** | 1600 | 1600 | 1600 | 1600 | 1632\* | 540 | 96 | no |
| FIFO | 1600 | 1600 | 1600 | 1600 | 1712\* | 284 | 48 | no |
| fewest-symbols | 1600 | 1272 | 444 | 104 | 48 | 32 | 32 | no |

Lowest-key eviction is the obvious fix, tracks the unbounded map almost exactly, and is **disqualified on the last column**: 8 packets claiming the top of the u32 range occupy all 8 slots permanently, because every honest block sorts below them and is evicted the instant it is created. Measured at 20/20 honest payloads → **0/20**, and it never recovers. Trading an unauthenticated memory drain for an unauthenticated permanent shutdown is not a fix.

`*` totals above 1600 are duplicate deliveries — a separate, pre-existing defect (below).

## What it costs — priced, not waved past

Inside the declared envelope this is free: through a reorder depth of 32 packets LRU is identical to the unbounded map at every loss rate measured. Past it there is real loss (540 vs 1408 at depth 128), and on a uniform round-robin across 9 blocks delivery is **zero** — LRU's classical cyclic-access pathology (Belady 1966). Pinned *exactly* in ULT-36 so nobody reads "bounded at 8" as "degrades gently at 9". Filed as `081KZZZH7H4087G0R001HV0W40` with the real repair named (per-peer block state, which the shared `expectedSeq` already needs).

**Checked and NOT used as justification:** "a block outside the window is unrecoverable anyway because `MAX_NACK_GAP` refuses to NACK for it." NACKs here update the loss estimate and never trigger retransmission, so no NACK bound can be what makes an old block unrecoverable. The argument does not hold.

## Tests ULT-32..37, and the mutants that shaped them

| mutant | killed by |
|---|---|
| eviction removed (the original defect) | ULT-32, 33, 36, 37 |
| LRU → lowest-key (the parkable policy) | ULT-34, 36, 37 |
| move-to-tail removed (LRU → FIFO) | ULT-37 |
| `>` → `>=` (off-by-one on the cap) | all six |

**Mutant 3 survived the first suite** — the line making the policy LRU rather than FIFO was unobservable, so ULT-37 was written to observe it: fill the window, touch the oldest block, force one eviction, complete whichever survived. Every mutant was re-run after rebasing onto #10541.

`retainedBlockCount` is added as an observation point (no setter, unread by the module). It exists because unbounded growth changes no delivered output — which is exactly why no test in this suite could see the defect.

## Also filed — both pre-existing, both measured here rather than asserted

- **`081KZZZGYBR087G0R00302Z2J6`** — evicting a *recovered* block drops its delivered-once guard with the object, so a straggler re-delivers the same payloads (§12). Present on the unfixed code at reorder depth 128; reachable at depth 64 after this change (21 blocks of 400).
- **`081KZZZH24H087G0R002TXQA15`** — `blockSeq`/`blockPos` are fully derivable from `seq` (`seq = blockSeq * 8 + pos` in the encoder) yet trusted independently. Bounding the buffer makes that harmless for *memory*; it does not stop one packet addressing any block at any position, and the CRC-32C trailer from #10541 does not close it either — such a packet is not corrupt, it is correctly formed and lying about where it belongs.
