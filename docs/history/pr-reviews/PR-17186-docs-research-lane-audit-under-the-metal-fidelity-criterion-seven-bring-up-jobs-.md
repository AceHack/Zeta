## Description

**No lane is retired by this PR.** It is a measurement and a recommendation with five numbered open questions. Lane changes need maintainer sign-off.

## The criterion

> "we don't necessarily need to test all the different environment types unless they are testing something for us one of the other specific environments cannot, like the goal is not to test with kind and k3s and all the modded versions, the goal is to test as much of a real metal run before we get to metal."

That replaces **environment coverage** with **metal fidelity**.

## What metal actually is — measured

| axis | metal | source |
|---|---|---|
| distribution | **k3s** | `kubernetes-version.json` — the version is *derived* from `pkgs.k3s` via this repo's flake lock |
| CNI | **Cilium** | `cluster-identity.json` derives both the k3s `--cluster-cidr` **and** Cilium's ClusterMesh `cluster.id` from one `clusterName` |
| virtualisation | **kubevirt + CDI** | `cdi`/`kubevirt` are `manualSync` because node-5b2dfa runs three production Windows guests |

**This inverts the current emphasis.** `live-k3d` runs k3s in Docker with Cilium — metal's distribution *and* metal's CNI. Every `kind` lane runs a distribution metal does not use, and three of four run a CNI metal does not use. **The deepest proof in the workflow — the 37/37 `included` run — is on the least metal-like substrate in it.**

## The seven jobs

| lane | substrate | CNI | what ONLY it tests | verdict |
|---|---|---|---|---|
| `dry-run` | none | — | manifests/rosters/unit tests before any bring-up | **KEEP** |
| `live-k3d` | **k3s** | **Cilium** | metal's own pair | **KEEP + promote** |
| `live-kind-virt` | kind | kindnetd | kubevirt + CDI emulation | **KEEP** |
| `live-kind-included` | kind | kindnetd | the deep 37/37 proof | **KEEP coverage, MOVE to k3d** |
| `live-kind-cilium` | kind | Cilium | Cilium on kind — k3d already runs Cilium on metal's distro | **MERGE into `live-k3d`** |
| `live-kind` amd64 | kind | kindnetd | kindnetd, which metal never runs | **RETIRE** |
| `live-kind` arm64 | kind | kindnetd | arm64 image availability | **HOLD** — open question 1 |
| `live-kind-cilium-included` | kind | Cilium | dispatch-only, currently skipped | **RETIRE or restate** |

## The single highest-value change

**Move the `included` proof from kind to k3d.** It is the deepest evidence the repo has that the cluster comes up, and it currently establishes that on a substrate metal does not use. Running the same roster on k3s + Cilium makes the strongest proof also the most metal-faithful, and makes three kind lanes redundant at a stroke.

It is also the change with the most unmeasured cost, which is why it is a recommendation and not a diff.

## Open questions (maintainer's, with expected answer shapes)

1. **Does metal have arm64 nodes?** Decides the one lane this audit cannot adjudicate from the tree. *Shape: yes/no + node inventory.*
2. **Will k3d host the `included` roster inside the budget?** kind finished in **513 s against a 2400 s cap**; k3d's per-node overhead against that headroom is unmeasured. *Shape: a measured run, not an estimate.*
3. **Does anything in the roster depend on kindnetd or kind's node image?** The lane already substitutes a StorageClass and an LB-IPAM pool. *Shape: a list of substitutions and what each becomes on k3d.*
4. **Is `live-kind-cilium-included` answering a question anyone still has?** *Shape: the question, or retire.*
5. **What replaces kindnetd coverage?** Honest answer may be "nothing, because metal never runs it" — but said out loud. *Shape: explicit accept/decline.*

## Effect on the split

Seven jobs → **four**, if the recommendation is taken. **That is a better outcome than the split**: it removes lanes rather than adding them, and every lane removed is one that can no longer produce a cascade for the split to isolate. The six-job figure for the split is about **chart-sets** and is orthogonal to this.

Priority stands: vacuity column + post-deploy assertions (#17181, #17185) first, then this, then the split.
