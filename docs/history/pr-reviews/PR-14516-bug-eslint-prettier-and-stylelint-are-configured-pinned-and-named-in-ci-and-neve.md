## Description

bug: eslint, prettier and stylelint are configured, pinned and named in CI — and never invoked

Filed as 081M0RBXF6J087G0R0023EX9X2 (P2). Found on an autonomous tick while
diagnosing lint (TS) on PR #14501.

src/Core.TypeScript/lint/lint-typescript.ts describes itself as "Post-install
orchestration of TypeScript tools (tsc, eslint, prettier, stylelint)". Its STEPS
array, line 112, contains EXACTLY ONE entry — tsc. Three of the four documented
tools never run.

Measured on origin/main. eslint has a full strict type-checked eslint.config.ts
over **/*.ts, is pinned at 10.2.1, and is named in a gate.yml step ("Install npm
devDependencies (typescript@6.0.3 + eslint stack)") one line above a step labelled
"Run TypeScript Lint Script" whose comment reads "Type check and lint checks".
A git grep for an actual INVOCATION — bunx/npx/bun run/.bin path/workflow run: —
across json, yml, ts, js, toml, sh and md returns only the two package.json
dependency declarations. No git hook, no husky, no lefthook. format:check
(prettier) and lint:css (stylelint) are likewise defined in package.json and never
called by CI.

This is the vacuity class rather than a missing feature: everything that LOOKS
like the check is present — config, pin, a CI step named for it — and the code
DOCUMENTS a behaviour it does not have.

The falsifier is measured, not hypothetical. PR #14501 added the first two .ts
files to docs/research/scripts/ (23 prior files, all .py and .fsx). Against the
repo's own committed ruleset they produce 72 errors (41
restrict-template-expressions, 25 no-non-null-assertion, 2 others). lint (TS) on
that PR is SUCCESS. Seventy-two errors under the repo's own config passed CI
green — that pair is the discrimination proof.

DELIBERATELY NOT FIXED IN THIS PR. The repo-wide count is unknown, and wiring the
tools on without knowing it could redden main across hundreds of files;
reddening main to fix a lint gap is worse than the gap. The acceptance criteria
therefore require measuring first, then DECIDING the profile boundary — **/*.ts
sweeps in docs/research/scripts/, demo/ and genesis/, and whether research
measurement scripts belong under the same strict ruleset as src/ is a judgment
call with a concrete case already on the table. Landing incrementally, and fixing
the documentation either way: an accurate "tsc only" beats an aspirational
four-tool sentence.

Explicitly ruled out in the workitem: deleting the config or dropping the
dependency to make the divergence disappear (it encodes real standards and 72 real
findings), and wiring it in behind blanket disables — widening a check to make it
pass is forbidden, and doing it to a check whose defect IS that it never ran would
be self-refuting.

Note for whoever picks this up: this is the SECOND instance of "the linter is
present and does not examine the file" found today — docs/research/2026-*.md is
carved out of the markdownlint profile, so markdownlint-cli2 on a research doc
also exits 0 without linting. Two independent instances in one day suggests the
class deserves a sweep, not two point fixes.

markdownlint verified the honest way (workitems/081*.md is inside the ignore
glob): linted a copy OUTSIDE the glob, rc=0, with a sabotage control on the same
copy returning rc=1.
