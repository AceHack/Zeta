## The premise was wrong, and the correction is the finding

The brief said both kube contexts refuse connection and nothing has been applied to any cluster — so establish whether the gap is *"installed but never bootstrapped"* or *"never installed"*.

**It is neither. The k8s layer has been up since 2026-06-09 — and it is two clusters.**

| measured 2026-08-26 | |
|---|---|
| Live k3s control planes on the LAN | **two**: `192.168.4.152`, `192.168.4.153`, both returning a proper `401` on `/version` |
| `.152` says it is | `node-ad1efd`, CA public key `d10d7070…`, founded 2026-06-09 |
| `.153` says it is | **`node-542b91`**, CA public key `682c3123…`, founded 2026-06-21 |
| The two refusing contexts | local `kind` clusters at `127.0.0.1`; the podman machine is stopped |
| kubeconfig for the real estate | **none exists** — which is why every `kubectl` probe read as "the cluster is down" |

**The two CAs have different public keys.** That is a proof, not an inference: two k3s servers in one cluster share a CA; two that each ran `--cluster-init` never do. So the estate is two independent clusters, both believing they are `control-plane`, both owning `10.43.0.1`.

Every negative above was taken against a control (mDNS browse returned 90 services while `_zeta-k3s._tcp` returned none; `.local` resolution works for this Mac but for no cluster node; `nc` reports closed on a known-closed port).

### Root cause — a default that was right once

`k3s-server.nix` sets `clusterInit = lib.mkDefault true`, and both machines were flashed from the `control-plane` flake host. **Every machine flashed that way founds a cluster.** The join path is independently broken too: `k3s-agent.nix` points at `https://control-plane:6443`, and `control-plane` does not resolve on this LAN.

### Why this blocks Vault

`vault operator init` mints the root token and unseal shares **once**, against whichever cluster the operator's kubeconfig names. With two clusters and no kubeconfig, the subject of the most irreversible command in this repository is **unidentified**.

## What ships: the falsifier that was missing

## Three things that are decisions, not work

1. **Vault init is currently UNNAMEABLE.** `ceremony-gate.ts`'s closed set of 25 operations has no member covering it, and the `switch` has no `default` arm, so `assertGatedCeremony` throws. Two members are **proposed with draft `reason` strings, not added** — extending a closed set is a maintainer decision.
2. **The anticipated circular dependency does not hold.** Auto-unseal via YubiHSM is *measured-unavailable*: `seal "pkcs11"` is Vault Enterprise-only and there is no `tpm` seal type at all. So Vault init is **not** blocked behind a Touch ID ceremony under any option available today. It applies only if OpenBao is adopted — and then it is a chain with a known first link, not a cycle.
3. **A trap in reusing `ca-shamir-custody.ts` for unseal shares:** it writes **all n shares to one directory on one machine** as plain unencrypted JSON, records no custodian, and warns about distribution only in prose. Defensible for a CA cold backup; for unseal shares it defeats the threshold until a human distributes them, *while looking like k-of-n*.
