## Description

Three related changes to the USB installer, all asked for directly by Aaron — plus one bug the third one found on its first real run.

## 1. A force-reformat override

> Aaron: *"we could allow for an override to completely reformat and ignore the installed version as an override."*

**Three independent factors, and none of them is inferrable.**

| factor | what it is | why it cannot be reached by accident |
|---|---|---|
| flag | `ZETA_FORCE_REFORMAT` must equal the exact literal `REFORMAT` | `1`, `true`, `yes`, `reformat`, `REFORMAT ` all do nothing |
| declaration | `ZETA_FORCE_REFORMAT_NODE_ID` must **name the node recovered off this disk this run** (or `unreadable`, only if nothing was readable) | a stale env names a *different* machine. It also makes the override **self-disarming**: after the reformat the node has a new identity, so the same env on the next boot no longer matches |
| confirmation | `REFORMAT` typed at a prompt of its own, before the existing `WIPE` one | skipped only on the **declared** zero-typing path (`ZETA_AUTO_CONFIRM=WIPE`), never on a `[ -t 0 ]` test — the headless first-boot path *does* have a tty, so a tty test would have silently demanded typing where nobody is watching |

**It routes THROUGH the R9 breaker, with a stricter bound.** The same `zeta_pf_breaker` is called a second time with `ZETA_MAX_REFORMAT_ATTEMPTS` (default **1**) instead of `ZETA_MAX_DESTRUCTIVE_ATTEMPTS` (default 3), so the override is refused strictly **earlier** than an ordinary attempt, never later. `blind` — the ledger surface is unwritable, so the attempt cannot be counted — **refuses outright**, where the ordinary path merely widens the cancel window: a destructive attempt that cannot be counted *is* the reboot loop R9 exists to bound. There is no branch anywhere that reaches the wipe with the breaker unread, and a test asserts that the override flag never appears in a condition guarding a destructive call.

**Consent is untouched.** Identity recovery still happens read-only under `-o ro,noload` *before* any of this is evaluated — the override cannot even arm without it, because factor 2 needs the recovered id. It never shortens the cancel window and never flips a `default=abort` back to `proceed` (asserted by reading the block's own text). The attempt is written to the ledger with `stage=reformat`, so a later reader can tell a **deliberate** wipe from a repair that **failed into** one.

## 2. A ZetaId, minted at install time and recovered on repair

> Aaron: *"yes we should move this to a zetaid."*

The `MEASURED GAP` comment at Step 2.7 is now closed and rewritten to say what actually happens.

- **Where it is minted** — Step 6.65 writes `/etc/zeta/node-zetaid`: a `Category.InventoryAsset` ZetaId, `packGeneric(1, 10, (ms << 78) | random78)`, **byte-identical in scheme to `inventory/new-item.ts`**. That is the category the asset register already uses (`reconcile-surfaces.ts` calls `inventory/items/` "identity of record; ZetaId-keyed"), so this reuses the existing convention rather than inventing a parallel one. **No node/traveler category exists** — a dedicated slot is a four-oracle byte-lock change (C#/F# already lag `InventoryAsset = 10`), sized and filed as `081M0QB3HP2087G0R0029W97ZZ` rather than silently skipped.
- **Where it is recovered** — Step 2.7, beside the other keys, under the same `-o ro,noload` mount. **Recovered, never re-minted**: a repaired node that came back with a new key would have forgotten itself (manifesto §5).
- **A force-reformat mints a fresh one**, explicitly — `unset ZETA_REPAIR_NODE_ID` + clear the recovered ZetaId — because that is a new node by declaration, and carrying the old identity across a deliberate wipe is the opposite error. The three provenances are printed by name: `recovered` · `minted-on-repair-legacy` · `minted`.
- **`cluster-node-id` keeps working**, unchanged and still written. Two keys, two jobs: the hostname is what the network calls the machine (`injected-hostname.nix` `readFile`s it at flake-eval time), the ZetaId is what the substrate calls it. Nodes installed before today have no `node-zetaid` — that is **not** a failure (refusing them would make adding a key a fleet-wide outage); a present-but-malformed one **is**, and lands in the existing abort-default path.
- The installer has no bun, so the mint is a bash-3.2 **fifth oracle**, byte-locked against the TypeScript one over fixed vectors — including the boundaries where **both must refuse** (an ms needing >41 bits would silently wrap to 1970 in shell and throws in TS).

## 3. A test that mounts a real existing install

> Aaron: *"yes it would be good to have this path tested too."*

`src/Core.TypeScript/installer/repair-mode-existing-install.test.ts` — **it mounts a real one; it does not simulate one.**

It builds a **real GPT disk on a loop device**: `sfdisk` partition table, two **real ext4 filesystems** with real labels (`boot`, `nixos`), a real `/etc/zeta/` tree written through a real `mount`, and a **decoy identity on the wrong partition** so selection-by-ordinal cannot pass. Then it extracts `zeta_pf_gather` / `zeta_pf_classify` / `zeta_pf_recover_identity` out of the real `zeta-install.sh` and runs them against that device — real `lsblk`, real `blkid`, real `mount`.

Eleven legs, covering what was asked for:

- **probe → classify → `mode=repair`**, end to end, against the real disk
- repair **recognises the node and recovers its ZetaId**; verdict `trusted`
- the recovery **writes zero bytes** (sha256 of the partition, before and after)
- a **malformed** ZetaId on disk makes the identity untrusted; an **absent** one still repairs (legacy nodes)
- **force-reformat overrides it and mints a fresh one**, different from the recovered id
- a **stale** override naming a different node is refused against this disk
- the **breaker still bounds the override**: with one prior unfinished attempt the ordinary bound (3) is `closed` while the reformat bound (1) is `open`, and that state is what refuses

**What it does not claim:** it does not run `nixos-install`. A full QEMU round trip is tens of minutes per leg and needs an ISO build. What repair mode actually reads is the partition label and `/etc/zeta` — **both real here**. The install that produced them is simulated; the install the code reads is not.

**It cannot pass by skipping.** It skips off Linux (the maintainer's machine is macOS) and prints why — but the new lane sets `ZETA_REPAIR_LOOPBACK_REQUIRED=1`, which turns the skip into a **failure**, and the workflow asserts the tools and `/dev/loop-control` before the test runs. Verified end to end on real Linux with real loop devices: **11/11 pass in required mode.**

## 4. The bug it found

`081M0QC7TCG087G0R00252NYHW` — measured into `db/uncertainty/`.

`lsblk -p -n -o NAME,TYPE <disk>` renders NAME as a **tree** and glues UTF-8 box-drawing glyphs onto the device path with **no separating whitespace**:

```
$ lsblk -p -n -o NAME,TYPE /dev/vda | cat -A
/dev/vda    disk$
M-bM-^TM-^\M-bM-^TM-^@/dev/vda1 part$
```

So `awk '$2=="part" {print $1}'` yielded `├─/dev/vda1`. Two call sites used that form — `zeta_pf_gather` (the R6 pre-format probe) and `zeta_pf_recover_identity` (R4 recognise-self). Every `blkid` on the mangled name returned **empty**, so the probe emitted `part=<glyph+path>|||` and never a `volumelabel=` or `esp=` record, the classifier returned **`indeterminate`** for a disk carrying a complete prior Zeta install, and **`mode` never became `repair` on any real hardware**. A re-paved node therefore drew a new random hostname while keeping its NIC — HWR-2, two roster registrations on one MAC, which is the exact failure the R4 block was written to prevent. The R8 creds carry-forward seam never fired either, same root cause.

Fixed with `-l` at both sites. **Reverting it turns 6 of the 11 loopback tests red**, including `the FULL chain runs: probe -> classify -> mode=repair`.

Nothing that existed before could have found it. `disk-preflight-shell-parity.test.ts` hands **fact records** straight to `zeta_pf_classify` — so it proved the classifier right about facts the **prober could never gather**. Both halves were tested; the seam between them was not.

One more, found the same way: the mint originally used `xxd -p` (as the hostname generator does). Ubuntu 24.04 split `xxd` out of `vim-common`, so on a runner without it the mint would have silently produced an **empty** id. Now `od -An -tx1` — coreutils, everywhere.
