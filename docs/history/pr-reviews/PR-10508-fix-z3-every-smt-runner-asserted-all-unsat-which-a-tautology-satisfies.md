## The defect

An `unsat` expectation is satisfied by a **tautology**. If a lemma's premises secretly contain its conclusion, negating that conclusion is trivially unsatisfiable, the runner goes green, and it has reported a *proof* where there is only a *restatement*. **Every pre-existing `.smt2` runner in this repo was in that state**, so none could catch a vacuous lemma — the one failure this lane exists to prevent. Not hypothetical: `landauer-floor-lemma.smt2` was exactly this, fixed in #10494, whose runner is the pattern followed here.

Nine lemma files. Four had a runner, five had none. All nine now have one, all nine assert a verdict **sequence** containing at least one deliberate `sat` from a non-vacuity probe, and all nine execute in CI — #10473's bare `bun test` at `gate.yml:1631` discovers `tools/Z3Verify/*.test.ts` with no workflow edit.

## `light-time` specifically

It is **CLEAN**: `unsat unsat unsat unsat unsat unsat unsat unsat sat sat sat` under z3 4.16.0 — precisely what its own header predicted (eight proved lemmas, a sharpness witness, two hypothesis-necessity witnesses). It was **already non-vacuous by construction**, written that way by the same author whose other files were not. The practice existed; what did not exist was anything that RAN it.

The property was never at risk either way: `src/Core.Lean4/Lean4/LightTimeAsymmetry.lean` proves it independently and **is** gated.

Consistency is therefore established **by witness** in a decidable fragment, which also commits `LEMMA 1` (described in prose as "checked separately", never runnable) as a real query.

2. **`whitewash` W2's `sat` does not depend on its `mu < 0` hypothesis** — flipping it to `mu > 0` still returns `sat`, because the SAT goals get finite monotonicity *instances* rather than the quantified axiom, so the sign is hand-asserted rather than derived. The witness is sound (W1 carries the theorem) but the block would witness for the wrong population too. **Not repaired here**: fixing the encoding is the author's call, and weakening or reshaping a claim to suit its runner is the same defect with a fresh coat. ## The runners are proven falsifiers

A probe never seen to fail is a probe you are guessing about. Every runner carries mutation legs that were **run and observed red**:

- **chsh** — restore the ablated `eps >= 0` → probe flips, sequence goes all-unsat. And collapsing `unionPredicate` into `convicts` (the literal planted tautology) also goes red, because the probe **shares** the definition rather than copying it.
- **consolidate** — false bound → theorem flips `sat`; true bound in the probe → all-unsat.
- **splitmix64** — un-corrupt the mutant multiplier → probe flips `unsat`.
- **predictive** — restore the ablated window ordering → red; reverse the theorem's inequality → theorem flips `sat`.
- **externality** — repair the degeneracy L4 exhibits → red; break harm-antitonicity → L6 flips `sat`.
- **whitewash** — ablate Phi monotonicity → W1 flips `sat`; ablate `v > 0` → W3 flips `sat`.
- **privacy-budget** — starve the witness family → V1 flips `unsat`; remove Shannon saturation → V2 flips `sat`.
- **light-time** — restore R2's ablated hypothesis → red; halve the envelope past its own sharpness point → M1 flips `sat`.

**An honest limit, because it bounds what this buys.** A tautology planted inside a block that is *already* expected `unsat` is invisible to any verdict-sequence runner. What the probe protects is that a **named hypothesis is doing work** — which is exactly the landauer failure — and it catches a conclusion-level collapse only when the probe shares text with the theorem. Where a lemma has no load-bearing hypothesis at all (`consolidate`: `n >= 0` is decorative, now a checked block saying so), the available probe is weaker, and the runner says so instead of dressing it up.

## One self-inflicted error, kept in the log

The first push failed CI at exactly `5007ms` on five tests. I had read `bunfig.toml`'s `[test] timeout = 20000` and sized a 10s solver limit under it. **bun 1.3.14 does not honour that key** — the real cap is its 5s default, and a solver limit *above* the test cap is the worst possible ordering: the test dies before the solver answers, so a broken proof and a slow solver report identically. Fixed by stating the ordering in one place (`solver 20s < process 25s < bun test 60s`) and passing the bun timeout as an explicit third `test()` argument. It is also what surfaced the finding above, since the timeout had been hiding it.
