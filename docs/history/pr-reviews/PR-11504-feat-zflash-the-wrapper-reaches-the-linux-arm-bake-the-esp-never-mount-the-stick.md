## Description

## The gap

`flash-usb-linux.ts` landed in #11259 carrying every wrong-disk rail — and then no operator
could reach it. `cli.ts` gated the whole wrapper on `platform() !== "darwin"` and printed a
pointer telling Linux operators to run the arm by hand. This closes that.

## Why the ESP step is not a verb-for-verb port

The macOS injection flow is flash → rescan → find FAT partition → `diskutil mount` (or
`sudo mount_msdos`) → `sudo tee` → unmount → `diskutil eject`.

The literal Linux translation — `lsblk` → `mount -t vfat` → write → `umount` — would have
introduced a **second wrong-target surface**: choosing and mounting a partition on a device
whose partition table the kernel has just re-read, one step *after* `selectUsbCandidate`
finished establishing which disk may be touched. That is the one question this arm exists to
answer once.

Instead the ESP writes are **baked into a keyed COPY of the ISO before the flash**, using the
mount-free `qemu-img` + `mtools` pipeline `lib.ts` already drives for the file-backed (QEMU)
path. `mcopy -i <image>@@<espOffset>` writes straight into the FAT ESP at a byte offset — no
loop mount, no partition selection, no root. The device write is then delegated to
`flash-usb-linux.ts` **unchanged**.

This PR adds **no device-selection logic** and relaxes none of it. `selectUsbCandidate` and
`hostsRootFilesystem` are untouched.

Worth noting: this is the **third platform to arrive at bake-before-write**. The Windows arm
(`flash-and-inject.ts`, 2026-06-14) was forced there because Windows invalidates the device
handle after the raw write. Linux chooses it because it deletes a destructive-target decision.

## Guards that refuse rather than guess

- **`flashUsbLinuxArgv` structurally cannot emit `--no-eject`.** The macOS wrapper builds
  `[flashUsb, "--short", "--no-eject", iso]`, and `--no-eject` is **not** in the Linux arm's
  allowlist — reusing that argv would abort every Linux flash at the child's own flag check,
  *after* the operator had been told a flash was starting. Pinned against the arm's exports.
- **`planLinuxBakedImagePath`** refuses a device path, a non-`.iso` name, and a path colliding
  with the source ISO (baking in place would mutate the operator's pristine cached download
  and silently invalidate the freshness checks).
- **`requireLinuxBakeTools`** refuses the flash when `qemu-img`/`mcopy`/`mdir` are missing
  rather than flashing an un-keyed stick — that stick boots a node the operator cannot log
  into, discovered only at the hardware. `mdir` is required because 081KZHJPJCF showed `mcopy`
  can exit 0 without the file landing; an unverified bake is not a bake.
- **`--bake-cred` is refused BY NAME** on Linux (its credential pipeline is macOS-shaped),
  never silently dropped.
- `--no-inject` suppresses the hostname write on Linux exactly as on macOS, so the platforms
  cannot disagree about what the flag means.

## Verified by execution

Against a synthetic isohybrid ISO (MBR `0xEF` @ LBA 276 + a real `mformat` FAT), the actual
bake pipeline ran:

```
detected ESP offset = 141312 (expected 141312) -> OK
bake result ok = true
ZETA-A~1 PUB        88 2026-08-17  10:34  zeta-authorized-keys.pub
ZETA-H~1 TXT         8 2026-08-17  10:34  zeta-hostname.txt
source untouched: true
```

That ran on **macOS**, on the same cross-platform code path Linux uses.

## UNVERIFIED — stated plainly

**No Linux host was involved in this PR.** `lsblk` is not even installed on the machine that
wrote it. `lsblk` enumeration, the `pam_fprintd` gate, the escalation, and the `dd` write to a
real block device remain **executed-nowhere**. This wiring is typechecked and unit-tested; it
has **never selected a real disk**. Do not read "401 pass" as "flashes a USB stick".
