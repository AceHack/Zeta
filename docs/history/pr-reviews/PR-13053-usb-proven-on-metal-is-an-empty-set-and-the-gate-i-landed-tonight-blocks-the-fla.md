## Description

Full gap analysis of what was asked of the USB stick versus what exists — **plus the one fix that
unblocks everything downstream.** No device written to; read-only `diskutil` only.

> **Nothing has ever been flashed to a physical stick and booted.** The repo's own ladder agrees: tiers
> **S0–S4 green, S6 (physical boot) never run.** Two P2 bugs have sat in backlog **12 days** carrying
> the identical close condition, verbatim: *"one clean boot on Aaron's hardware."*

## The gate I landed hours ago hard-stopped the flash path — and not the way the docs predicted

Replayed against the real `~/Downloads`:

```
manifest found: /Users/acehack/Downloads/SHA256SUMS
gate ok       : false
refusal reason: iso-not-in-manifest
```

**That manifest belongs to Bitcoin Knots** — 28 entries, Sep 2025, zero mention of zeta. The gate finds
it, parses it happily, and **prints 28 bitcoin filenames at an operator trying to flash a NixOS
installer.**

> **Looking up a bare well-known filename in a shared download directory is a namespace collision, not
> a manifest.**

## The keystone, fixed here

The x86_64 job computed a SHA-256 and wrote it **only to `$GITHUB_OUTPUT` and the step summary** — it
existed for humans reading a run page and **for nothing else.** It now writes a **per-ISO sidecar**
beside the image and uploads it as its own artifact.

**Per-ISO rather than a bare `SHA256SUMS`, deliberately** — and the reason is measured, not
theoretical: the collision above already happened on this machine. **A per-ISO sidecar cannot be
hijacked that way.** `actionlint` passes.

This unblocks a path that is currently hard-stopped, turns the integrity gate from refusing-everything
into a working check, and is a prerequisite for everything downstream — **you cannot read-back-verify a
write you were never allowed to start.**

## Two guards from #13030 cannot fire in production

**R1 is dead code on the live path.** It detects *"labelled `ZETA_INSTALL` but the head digest
disagrees"*, needs two digest fields, and **the only production call site omits both** — the sole
supplier is the test file.

> **A stick with bad bytes classifies as `provisioned`** — precisely the dangerous misread R1 exists to
> prevent. **Green in tests, unreachable in life.**

**The first identity check compares observed to itself** when no `--expect-*` is passed — which
`cli.ts` never passes. It prints `UNPINNED TARGET` as a **warning, never a refusal.** The *second*
check, re-read immediately before the write, is the one doing real work.

And **only `unrecognized` blocks** — `half-provisioned` is printed, then proceeds to the destroy
prompt. **Detection landed without policy.**

## The 2026-06-09 ask is still unbuilt, 73 days on

> *"check if the partition exists every time before formatting … **do this now**"* — refined the same
> day to a **cancel window** rather than a prompt.

**Neither exists.** `wipefs -af` runs over every internal disk with only capacity and set-membership as
pre-checks. And `zeta-first-boot.sh` exports `ZETA_AUTO_CONFIRM=WIPE`, so **on the default zero-typing
path every internal disk is wiped 30–130 s after power-on, and the OS installs from an unpinned,
unverified `git clone` of `main`.**

> **The structural miss: tonight's classifier landed on the USB-stick side. The ask was about the
> target-disk side. Detection is on the wrong side of the wire.**

## The classifier itself works — on real evidence

`/dev/disk6` (PNY, 124.0 GB, FDisk scheme, one `0xEF` partition of 3,145,728 bytes, no filesystem)
classifies **`half-provisioned`, rule R4** — *less is allocated than the smallest ISO we would write.*
**Measured, not cited.**

## Other measured findings

**No platform parity** — all four new gates are macOS-only, and **`MIN_ISO_BYTES` is now defined three
times** despite `verify.ts`'s own comment claiming it is centralised *"so they cannot drift apart."*
**The Windows read-back verifies a small SSH-pubkey text file on the ESP, not the ISO.** **`cosign
verify-blob` appears nowhere in executable code** — signing exists, verification does not. **aarch64
downgrades TIMEOUT and STALLED to advisory**, and its own comment is honest: *"catches images that fail
to boot, not images that hang."* **The new tests run but do not gate.** **Every operator document is
stale** — the preflight's failure-signature list does not include the refusal you will actually hit.
And **both local ISOs are pre-fix** (Jun 9, Jun 21), predating the 2026-08-09 fixes that made
first-boot install work — **flashing either reproduces a bug that is already fixed.**

## Remaining order, each small

Prefer the per-ISO sidecar in the lookup and require a basename match · **pass the head digests at the
classifier call site so R1 can fire** · have `cli.ts` pass `--expect-*` from the device it just showed
you · refresh the runbook and blueprints · **emit the same manifest from aarch64**, which still emits
nothing.

**Then the one act no agent can do: flash and boot.** That closes two P2 bugs, moves S6 from never-run
to attempted, and **converts the entire "built, unproven" column into evidence.**

**Register:** the refusal replay, the classifier verdict and the dead-R1 analysis are **measured**. The
CI digest emission is **designed-but-unrun** — the first ISO build after this lands is what proves it.
