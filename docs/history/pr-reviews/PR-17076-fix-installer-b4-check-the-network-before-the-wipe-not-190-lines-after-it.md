## Description

fix(installer): B4 — check the network BEFORE the wipe, not 190 lines after it

Measured on main: the wipe is at :1583 (`wipefs -af`, `sgdisk --zap-all`), and
`git clone "$REPO_URL" /mnt/etc/zeta` is at :1776. No connectivity check existed
anywhere before it.

So on a machine with no working network the installer destroyed every disk in
scope and then, ~190 lines later, discovered it could not fetch the thing it was
installing. Previous OS gone, nothing bootable, drop to a shell. That is the
same shape as the UEFI preflight immediately above this one, which exists
because the identical mistake surfaced at `bootctl install` after the wipe.

The probe is `git ls-remote "$REPO_URL" HEAD`, not a ping: it exercises DNS, the
route, TCP, TLS and the repository actually being readable -- the full set of
things `git clone` needs -- and transfers no objects. A ping passes on a network
that blocks 443 or has no DNS.

`GIT_TERMINAL_PROMPT=0` so a credential prompt cannot hang a non-interactive
install waiting for a username, and `timeout 60` bounds a black-hole route that
accepts SYN and never replies. Both otherwise hang forever rather than bailing,
which on the zero-typing path is a machine that never finishes and never says
why. The bail says plainly that nothing has been wiped.

NOT COVERED, stated in the code rather than implied: the closure download from
the substituter is a SECOND network dependency, later still, and this does not
probe it. A network that reaches GitHub but not the binary cache still fails
after the wipe. Narrowing that is separate work.

FALSIFIER: `preflights-precede-the-wipe.test.ts` pins the ORDERING rather than
the existence of these checks, because a preflight that drifts below the wipe is
worse than none -- it reads as protection while providing none. It asserts the
UEFI check and the reachability probe both precede the first `wipefs`, that the
clone they protect is still after it (so the reasoning cannot go stale
silently), that the probe carries both the timeout and the prompt guard, and
that the wipe is present at all so the suite cannot pass vacuously.

MUTATION TESTING FOUND A HOLE IN MY OWN GUARD, and the fix is in this commit.
The first draft matched `git ls-remote` on any non-comment line, which matched
the phrase inside the BAIL MESSAGE -- so deleting the actual probe still "found"
one and the ordering assertion passed. Removing the command killed only one of
the two tests that should have died. `firstCodeLine` now also skips lines whose
first token is `bail`/`echo`/`printf`: they MENTION a command rather than run
it. Re-mutated after the fix: 3 pass / 2 fail, both the right ones. Restored:
5 pass. This is the same mentions-vs-executes distinction the first-boot remedy
guard needed in #17075.
