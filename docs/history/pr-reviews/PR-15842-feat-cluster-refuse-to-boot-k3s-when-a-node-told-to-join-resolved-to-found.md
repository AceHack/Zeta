## Description

`injected-server-join.nix` names this in its own header and calls it the worst
reversion in the family:

    PURE EVAL IS A SILENT NO-OP ... `builtins.pathExists` on an absolute path
    returns FALSE under pure eval (measured 2026-08-21, Nix 2.34.6), so a
    `nixos-rebuild` without `--impure` reverts a joining server to a FOUNDING
    one ... it re-founds a sovereign cluster on a node that was a member.

Two guards exist and neither closes it:

  * `lint-nixos-rebuild-needs-impure.ts` keeps DOCUMENTED rebuild strings
    carrying `--impure`. It is a lint over prose — it cannot see a human typing
    the command, a tool composing it, or any path not in the corpus.
  * `k3s-datastore-preflight.sh` refuses a join-provisioned node that already
    holds a datastore, and states its own boundary: "On a genuinely from-scratch
    flash that is fine — there is no datastore, so nothing is ignored."

THE FROM-SCRATCH FLASH IS THE UNCOVERED CASE, and it is the one an operator
performs deliberately: format the second machine from USB, join it to the first.
No prior datastore, so the sibling passes. If evaluation did not see `/etc/zeta`
the node comes up a healthy sovereign cluster of ONE — unit active, node Ready,
`kubectl get nodes` green on both machines showing one node each. Nothing errors.
It is found by noticing the second machine never appeared in the first's list.

THE MECHANISM is a comparison of two facts recorded at two different times:

    INTENT   read at BOOT,  from the disk  -- /etc/zeta/cluster-join-server-url
    OUTCOME  baked at BUILD, from the eval -- config.services.k3s.{clusterInit,serverAddr}

The outcome is interpolated from the RESOLVED config, so it records what
evaluation decided rather than re-deriving it. When evaluation cannot see the
intent there is nothing left at eval time to compare against — which is exactly
why the reversion is invisible today. Reading the intent a second time, at boot,
from the disk it is actually on, makes the disagreement observable, and it
convicts regardless of WHY eval missed the file.

WHY NOT AN ASSERTION: an assertion evaluates in the same pure context that lost
the input. Under pure eval it would see "no join intended, founding" and be
satisfied. A check that cannot fail in the condition it exists to catch is the
vacuity class, and an assertion here would be precisely that.

It deletes nothing, rewrites nothing, starts nothing — the remediation is printed
and is the operator's (manifesto §5), same discipline as the sibling. The token
file's PRESENCE is reported because a missing token and a missing URL are
different repairs; its CONTENT is never read, because a secret echoed to serial
by the unit meant to make things safer is a worse bug than the one it catches.

Two defects caught during construction, both by the tooling rather than by
review, and both recorded because they are the same class this file is about:

  * The `clusterInit` branch was DEAD. Every conviction that reached it had an
    empty `serverAddr`, so the earlier branch fired first and deleting the
    clusterInit check broke no test. Fixed by adding the state that reaches it —
    address landed, override did not — which is a real half-applied config.
  * `JOIN_TOKEN_FILE` was declared and never used (shellcheck SC2034) while the
    option's description promised it was "reported in the refusal for
    diagnosis". An option documented as doing something it does not do is this
    file's own subject in miniature. The description is now true.
