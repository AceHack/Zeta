## Description

Wires the bootstrap-or-join decider from #13110 into the installer ISO, and
answers the question that blocked it: **what does discovery cost the USB image?**

#13110 landed the decider in no host closure with nothing calling it, because
the installer ISO shipped neither an mDNS responder nor a JS runtime, and the
size of adding them was written down as UNMEASURED. That was the right call to
make at the time and the right thing to refuse to guess at.

## 1. The measurement

nixpkgs `b77b3de8` (this repo's pin), **x86_64-linux**, cross-evaluated from an
aarch64-darwin workstation. Closures read from `cache.nixos.org` narinfo without
building anything. **Marginal** = store paths NOT already in the installer's
`environment.systemPackages` closure (105 attrs resolved, 483-path baseline).

| package | closure paths | NEW paths | marginal, uncompressed NAR | marginal, on-ISO |
|---|---|---|---|---|
| **avahi 0.8** | 36 | **0** | **0 MiB** | **0 MiB** |
| **bun 1.3.3** | 5 | 1 | 99.4 MiB | **30.5 MiB** |
| nodejs 22.22.2 | 27 | 8 | 101.0 MiB | ~20.3 MiB (xz proxy) |
| python3 3.13.12 | 22 | **0** | **0 MiB** | **0 MiB** |

Two of those numbers are worth stating out loud.

**avahi is already on the ISO.** Not "an equivalent"; the identical store path
`9bhrl41prsjx30r4n061ajqbb6gdmn80-avahi-0.8`, pulled into the closure by
`mesa-demos`. `avahi-browse` and `avahi-daemon` have been physically on the
stick this whole time — absent from `PATH`, with no daemon running. The prior
note read the cost off `systemPackages`, which was right about PATH and wrong
about the store; *not in systemPackages* and *not in the image* are different
claims and only the first was true. Same for `python3`, present via
git / zfs / xfsprogs / neovim / mise / nvd / tldr / iotop.

**The 30.5 MiB for bun is measured, not extrapolated.** The store path was
downloaded and run through `mksquashfs` with the ISO's own settings —
`-b 1048576 -comp zstd -Xcompression-level 19`, the `iso-image.nix`
`squashfsCompression` default — giving **31,944,704 bytes**. A compression
ratio guessed off the xz narinfo would have been an assertion; this is a file
whose size was read with `stat`.

## 2. Recommendation: (a), add avahi + bun. Wired here.

**+30.5 MiB, all of it bun**, against an image where this same file already
spends a documented **~80 MB** on `enableRedistributableFirmware` to quiet
cosmetic dmesg lines. Discovery is under half of an already-accepted line item,
and it buys the end of a real failure: every stick cut from one ISO ships
`HOST=control-plane`, so today the second node founds a **second cluster** on a
segment that already has one.

The other two options were rejected on the same numbers, not on taste:

- **(b) avahi-browse + reimplement in an already-present language** costs
  **+0 MiB** — genuinely zero, since python3 is also already in the closure.
  Rejected because it buys 30.5 MiB with a **second implementation of a
  split-brain-preventing decision**: 583 lines of decider carrying 755 lines of
  tests, ported into a language with no golden-vector cross-check against the
  first. Two implementations that drift apart is the failure this module exists
  to prevent, arriving by another door. 30.5 MiB is cheap next to that.
- **(c) hand-rolled UDP 5353 probe** saves **nothing at all**, because the thing
  it avoids — avahi — is already free here. It only adds hand-written packet
  parsing where a mature responder already sits.

## 3. What was wired

**`nixos/installer/configuration.nix`** — `avahi` and the `zeta-cluster-discover`
package in `systemPackages`, plus `services.avahi.enable`. `avahi-browse` is a
D-Bus **client** of `avahi-daemon`; without the daemon it exits non-zero with
`Failed to create client object` and every probe fails, so enabling the daemon is
what makes the check able to run at all. **Publishing is explicitly off** — the
inverse of `nixos/modules/common.nix`, because an installer is not a cluster node
and a live ISO answering on the Zeta service type is a phantom member that
vanishes at reboot. `openFirewall` punches UDP 5353, without which our own
firewall would manufacture the silence.

**`zeta-first-boot.sh`** — the decision was gated on *provenance*, which is what
makes the bug fixable at all. `HOST` is **always** set by the time the script
gets there, because the ISO's own `/etc/zeta-firstboot.conf` ships
`HOST=control-plane`; so "is a role set?" is not a usable question and reading
that yes as an operator decision is precisely how the second cluster gets
founded. `ZETA_ROLE_SOURCE` already carried the answer:

| source | meaning | discovery |
|---|---|---|
| `esp:<part>` | a `zflash --role` flash wrote it | **DECLARED** — skipped |
| `keystroke:c\|w` | a human pressed a key | **DECLARED** — skipped |
| `iso:/etc/…` | build-time fallback, nobody chose it | **DEFAULTED** — consulted |

An explicit declaration always wins, so the zflash flow is untouched.

Discovery runs **after the network wait and before `zeta-install`**, not at the
role prompt — the role prompt fires before `[1/3]`, where the NIC routinely has
no carrier and every probe would fail for a reason having nothing to do with
whether a cluster exists. Nothing has touched a disk yet at that point, so
refusing still costs nothing. The `[3/3] Running zeta-install` serial marker that
`zflash/test-harness/serial-markers.ts` pins is deliberately left unrenumbered.

## 4. The two refusals are NOT collapsed

A discovery result that silently reads as "no cluster" when the probe never ran
is the failure this design refuses, so the call site splits the decider's
refusal reasons rather than treating `exit 3` as one thing:

- **a cluster was HEARD and we may not join it** (`join-token-unavailable`,
  `multiple-clusters-answered`, `malformed-advertisement`, `trust-domain-*`,
  `cluster-id-does-not-match-token`) → **HALT**, with the reason, detail and
  operator action on screen. Continuing would found the second cluster.
- **the probe DID NOT RUN** (`probe-failed`, `dwell-too-short`, a missing
  binary, `ZETA_DISCOVERY=off`, an undefined exit code) → say so **loudly**,
  name the non-result, and fall back to the declared ISO default. That fallback
  is byte-for-byte today's behaviour; what changes is that the non-result is
  *named* instead of reading as silence. `ZETA_DISCOVERY_REQUIRED=1` turns it
  into a halt.

A short dwell is **not** auto-acknowledged. Lowering `ZETA_DISCOVERY_DWELL_MS`
alone makes the decider refuse; `ZETA_DISCOVERY_ACK_SHORT_DWELL=1` is a separate
step, because auto-passing the acknowledgement whenever the dwell is lowered
would delete the guard while appearing to respect it.

## 5. No token ever goes near mDNS

`--token-present` is a **boolean** computed with `test -s` — a stat. The script
never opens the file, so no secret can reach a flag, a log line or a crash
trace. Discovery finds an **address**; the k3s token still comes from the ESP or
an operator, exactly as today.

## 6. Falsifiers

`installer-wiring.test.ts` (23 tests) checks the seam that no decider unit test
can reach: a caller that folds a failed probe back into "no cluster" undoes the
module from outside with every existing test still green. The `RefusalReason`
roster is **parsed out of `decide.ts`**, not copied, so a new reason added there
is covered the moment it exists.

Nine mutants were run; all nine go red, each on the assertion that names it:

| mutant | caught by |
|---|---|
| collapse `join-token-unavailable` into the did-not-run arm | could-not-run arm carries EXACTLY the two reasons |
| catch-all falls back instead of halting | cluster-was-heard refusal HALTS |
| run discovery even when the role was DECLARED | discovery is skipped when declared |
| ISO advertises itself | publishing is explicitly off |
| `services.avahi.enable = false` | an mDNS responder is enabled |
| drop `avahi` from systemPackages | avahi-browse is on PATH, not merely in the store |
| `openFirewall = false` | the firewall is opened for mDNS |
| read the token file instead of stat-ing it | the token file is size-tested, never read |
| move discovery after `zeta-install` | the decision happens before anything is destroyed |

Two of those tests were **vacuous when first written** and only the mutation run
exposed it: one extracted a shell case-arm by regex, found nothing, and then
asserted over an empty string; the other's `enable = true;` match was satisfied
by `networking.networkmanager.enable = true;` twenty lines away, so it stayed
green with avahi switched off. Both now parse their block and throw when it is
missing. The episode is recorded in the file rather than quietly fixed.

## 6b. The verification failed this PR's own discipline once

`lint (TS)` went red on `installer-wiring.test.ts(61,23) TS2532`, after this PR
had already claimed "`bunx tsc --noEmit` clean". That claim was **false**, and
the way it was false is exactly the failure class the code under review exists
to prevent, so it is recorded rather than quietly fixed:

1. `bunx tsc` in a fresh clone with no `node_modules` resolved a bare
   `typescript`, could not find the `bun` type library named in `tsconfig.json`,
   and exited 1 with `TS2688` **before type-checking a single file**. Zero files
   checked produces the same empty output as zero errors.
2. The exit code was read with `${PIPESTATUS[0]}` under zsh, where the array is
   `$pipestatus`. It expanded to empty, so the nonzero exit was never seen.

A check that did not run looked exactly like a check that passed — the sentence
this PR's call-site design is built around, failed in the PR's own verification.
It now runs as `bun install` then `./node_modules/.bin/tsc --noEmit -p
tsconfig.json` with the status captured directly, and was confirmed to actually
be checking the file by reintroducing the error (three diagnostics naming it)
and restoring it. Same lesson as the two vacuous tests in §6, arriving twice in
one change: **an assertion is only as good as the evidence that it ran.**

## 7. MEASURED vs DESIGNED-BUT-UNRUN

**Measured:** every size number above; `tsc --noEmit -p tsconfig.json` clean
(exit 0, zero output); `bash -n`
clean; `shellcheck -S warning` clean apart from one pre-existing `SC1090`;
102 tests green under `full-ai-cluster/nixos/cluster-discovery/`;
`audit-installer-substrate` PASS.

The installer config was also **evaluated through the real NixOS module system**
for `x86_64-linux` (cross-evaluated from darwin via `nixos/lib/eval-config.nix`
on the pinned nixpkgs), which is a stronger check than parsing the file — a bad
option name or an unresolvable import path fails there. Every property this PR
claims is read out of the evaluated config rather than asserted about its text:

```json
{"avahiEnabled":true,"avahiPublish":false,"avahiFirewall":true,
 "mdnsPort":true,"daemonUnit":true,"discoverOnPath":true,"avahiOnPath":true}
```

`mdnsPort` is `5353 ∈ config.networking.firewall.allowedUDPPorts` and
`daemonUnit` is the existence of the `avahi-daemon` systemd unit, so the
responder and the firewall hole are confirmed in the built config, not inferred
from the module's documented defaults. `discoverOnPath` confirms the
`../../../nixos/packages/zeta-cluster-discover.nix` import resolves.

**DESIGNED BUT UNRUN — no metal was booted.** No two nodes have ever run this
probe near each other. The 30 s dwell is still derived from RFC 6762 timers and
a cost asymmetry, not from an observed time-to-first-answer, and it stays
`UNMETERED` under `toy-is-free-metered-must-be-earned`: what this PR measured is
the **ISO cost**, not the protocol behaviour. The bootstrap path, the halt path
and the loud-fallback path have each been exercised only as text-level
assertions and unit tests. The first real signal will be a two-node QEMU or
hardware boot on one segment, and until that runs, the wiring is a design
carrying falsifiers — not a validated one.
