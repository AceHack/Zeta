## Description


`installer-unit-tests` on main, twice (runs 32531281015 and 32590647061, a day and
several commits apart, always the same line):

  (fail) the completed install records its success (R9 write side) >
         THE REGRESSION: four installs from one stick, all successful,
         breaker stays CLOSED [5005.65ms]
    ^ this test timed out after 5000ms

No assertion failed. bun names a timed-out test, so a resource budget renders as
a claim that the circuit breaker regressed. It did not.

FIRST, A CORRECTION TO THE OBVIOUS READING

  5005.65 against 5000 is not "0.1% over". bun KILLS the test at 5000 ms; the
  5.65 ms is teardown. The true duration is unbounded above and unmeasured --
  both failing runs report the identical 5005.6x, which is the signature of a
  cap, not of a distribution that happens to straddle one. Sizing a budget
  against 5005 would have been sizing it against a number the runner invented.

WHERE THE TIME GOES -- from CI's own log, same run, same file

  test (appends)                                     CI time
  THE REGRESSION                      (6 appends)    >5000.00 ms  KILLED
  a successful install writes an `ok` (2 appends)     1912.43 ms
  the bound still bites               (3 appends)       75.62 ms
  a success in the middle             (4 appends)      144.51 ms
  records stay contiguous            (10 appends)      138.83 ms
  ten successful installs            (20 appends)      210.26 ms
  BLIND stays blind                   (0 appends)       40.18 ms

  Read the append column and the time column together: they do not correlate.
  TWENTY appends cost 210 ms while SIX cost more than 5000. What the times DO
  track is declaration order -- the first test pays seconds, the second pays
  most of what is left, and from the third on the file is uniformly fast.

  That is the profile of a fixed backlog being drained, not of work the test
  performs. The backlog is the host's, and the drain is one line:

    $ZETA_SUDO sync 2>/dev/null || true      # in zeta_ledger_append

  `sync` with no argument flushes EVERY filesystem on the machine. This job runs
  it directly after ./tools/setup/install.sh restores a ~1.5 GB toolchain cache
  and `bun install` writes node_modules, so the first call in the process has to
  push all of that to a contended cloud disk. The R9 falsifier is simply the
  first test in the first file that calls it. Nothing about the breaker, the
  ledger, or four installs from one stick is involved.

  MEASURED locally, 6 rounds, to price the call itself: 40 `sync` calls cost
  3.78-4.19 s (~95 ms each) against 0.146-0.245 s for 40 trivial process spawns
  (~4 ms) -- 24x, and stable across back-to-back rounds. The other four
  processes per append (cat, grep, date, tee) are ~10 ms combined and scale
  with the work, which is why 20 appends are cheap once the queue is empty.

THE FIX: NAME THE BARRIER AND MAKE IT INJECTABLE

  `zeta_ledger_append` already has one seam for exactly this reason -- $ZETA_SUDO
  exists so the write path is reachable without root. The durability barrier now
  has the second:

    ZETA_LEDGER_SYNC="${ZETA_LEDGER_SYNC-sync}"
    ...
    $ZETA_SUDO $ZETA_LEDGER_SYNC 2>/dev/null || true

  The installer's behaviour is byte-for-byte unchanged: unset defaults to `sync`,
  and it must, because the whole reason the record is written is that the node
  may lose power in the next second on a FAT ESP. The falsifier supplies a shell
  FUNCTION that records the call instead.

  This is the noninterference discipline applied to time (local-time-never-enters
  -the-shared-fold, §13): the one operation whose duration was set by ambient
  global state now enters through a declared channel. No budget was raised, no
  test was skipped, retried, or split, and the test asserts everything it did.

IT ASSERTS MORE THAN IT DID -- the barrier was previously observed by NOTHING

  Three new falsifiers, and the speed-up is not allowed to be silent:

    - the durability barrier fires once per record written (6 records, 6 calls)
    - a ledger that records nothing runs no barrier either (BLIND returns first)
    - the durability barrier DEFAULTS to a real sync in the installer

  MUTATION RESULTS, all three killed, `cmp`-verified restored after each:

    M1  default `sync` -> `true`         -> 18 pass / 1 fail   KILLED
    M2  flush line deleted from helper   -> 17 pass / 2 fail   KILLED
    M3  test's seam name misspelled      -> 18 pass / 1 fail   KILLED

  M3 is the one that matters most: it is the mutant where the fix quietly stops
  applying and the real `sync` comes back. A speed-up that cannot detect its own
  absence is how the 5000 ms gets re-approached without anyone noticing.

NOT THE SAME CAUSE AS #13855, CHECKED RATHER THAN ASSUMED

  A sibling investigation traced four hygiene timeouts to Microsoft Defender's
  per-(process, file) open authorisation on the fleet's macOS host. That was
  raised against this one and does not fit it:

    - this failure is on GitHub-hosted ubuntu-24.04, where no such scanner runs;
    - `sync` is a syscall, not an open, so ES first-open authorisation cannot
      gate it -- and it measured stable, not first-slow-then-fast, over 5
      back-to-back rounds on the very host that does run Defender;
    - the sibling's class MOVED between runs under load; this one is pinned to
      the same test on two commits a day apart;
    - the "first pass slow, later passes fast" signature the sibling proposed as
      the discriminator is visible here WITHIN ONE PROCESS in CI's log, and it
      resolves to the flush queue rather than to a scanner.

  Same family -- host-global state charged to a per-test budget -- different
  mechanism, and opposite repairs. `mdatp health` on this host does report
  real_time_protection_enabled: true; it is not what CI was measuring.

RESULT

  THE REGRESSION, 10 single-file runs on the fleet host (load average 37):

    before   min 0.630  p50 0.678  max 1.680 s
    after    min 0.228  p50 0.326  max 0.645 s

  2.1x at the median, and the term that was unbounded is gone rather than
  smaller. CI's own number for this test at the parent commit was >5000 ms; the
  same runner measured the file's other tests at 40-210 ms once the queue was
  drained, which is the neighbourhood this test now joins.

  installer suite: 513 pass / 0 fail (was 510; +3 falsifiers), exit 0.
  The 7 other test files that read zeta-install.sh: 128 pass / 0 fail, exit 0.
  `typecheck` exit 0. `shellcheck -S error` exit 0. `prettier --check` exit 0.

STILL OPEN, recorded not taken: `ten successful installs in a row` is the file's
slowest remaining test at 210 ms on CI and ~1.0-1.2 s on the Defender host. It is
80 process spawns and its cost is now proportional to its work, which is the
legible kind -- but it is the next member of this class if the class is ever
closed with a rule rather than member by member.
