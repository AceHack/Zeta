## Description

The maintainer, 2026-09-10: "codeql is something we should also install with
our install.sh and our github package manager."

The measurement behind it: a PR spent SIX round-trips failing on CodeQL alerts,
each round a guess at what the analyser would accept, because CI was the only
feedback loop. The same alerts reproduce locally in about fifteen seconds. A
CodeQL CLI was already sitting at ~/.zeta/codeql-cli on the maintainer's
machine -- downloaded ad hoc by an agent, pinned by nothing, present on one
host. That is the state this repo's dependency discipline exists to prevent.

from-zip: a new mechanism, because from-url cannot unpack

from-url puts ONE FILE at ONE PATH, a limit tools/setup/manifests/windows had
already recorded as a blocker for the YubiHSM2 SDK ("a Windows-side
unzip-to-PATH mechanism (new mechanism -- needs sign-off)"). from-zip is that
mechanism: a pinned per-platform release ZIP, extracted into a declared
directory, with an optional PATH shim.

  * the digest is verified BEFORE a byte is extracted -- a ZIP is an
    instruction set for writing files, so verifying after unpacking would
    verify bytes already acted upon;
  * opt-in= is REQUIRED per row and its absence THROWS. A release bundle is
    heavy by construction, so "installs everywhere" must not be the failure
    mode. tier= answers the separate question of whether the host can run the
    tool; both gates must pass and neither substitutes for the other;
  * a <dest>/.zeta-from-zip.json receipt decides a re-run. A moved pin
    therefore reaches the machine, and a hand-placed tree with no receipt is
    re-installed rather than adopted -- present is not correct;
  * the swap is one rename from a SIBLING staging dir, so an interrupt cannot
    leave a half-extracted toolchain behind a receipt that says it is complete,
    and rename never crosses a filesystem (tmpfs /tmp would have made this work
    on a laptop and fail on a runner).

Four CodeQL v2.27.0 rows -- osx64, linux64, linux-arm64, win64 -- each digest
cross-checked against three independent publications of the release: the GitHub
release API assets[].digest, upstream's own <asset>.checksum.txt, and (win64)
the scoop Main bucket's codeql.json hash. All agree. v2.27.0 is the bundle
github/codeql-action v4.37.9 resolves, which is what makes a local run
comparable to the CI alert rather than merely similar.

OPT-IN, with the numbers: 1.09 GB on macOS (universal asset), 411 MB linux64,
393 MB linux-arm64, 416 MB win64. Nothing downloads unless
ZETA_INSTALL_CODEQL=1. tier=standard rather than full because the tier gate
asks whether the host can RUN an analysis (~8 GB), and install.ps1 narrows
Windows to standard -- a Windows developer who explicitly asks should get it.

The wrapper is the point

  bun src/Core.TypeScript/formal-verification/run-codeql.ts <paths...>

builds a database SCOPED to those paths and runs the same suite CI runs
(security-extended), printing "rule  file:line  message". The hidden flag is
--codescanning-config, which is both what makes the database scoped (6s rather
than minutes) and the exact mechanism github/codeql-action uses, so the local
run differs from CI in its inputs and not in its method. Exit 0 no findings /
1 findings / 2 COULD NOT RUN -- a tool that returned 0 for "never looked" would
read as a clean bill of health.

Compiled languages are refused BY NAME rather than silently analysed into an
empty database, because an empty database reports no alerts and that is not the
same as there being none.

The falsifier runs both ways

Against the fixtures committed in #17253, same rule, same shared creds.ts, only
the guard differing:

  unguarded.ts + partly-guarded.ts -> 3x js/file-access-to-http, exit 1
  guarded.ts                       -> nothing, exit 0

Measured end-to-end on macOS today: install from the manifest (digest verified,
tree swapped, shim linked, re-run a 47ms no-op), then both legs above. Two real
SARIF documents are committed as text golden vectors -- one substitution, the
CLI's absolute path -- so the parse half runs where no CLI exists. CI does not
install the CLI, so on a runner the live half is skipped with a printed reason:
a probe that could not run is unknown, never a pass.

Not touched, deliberately: CodeQL is not made a required check, no ruleset or
branch protection is edited, no paths-ignore is added and no alert dismissed.
There is no model-pack path either -- #17253 measured that data extensions do
not reach built-in queries by any route, so this tool reproduces rather than
customises.

Three-way parity (GOVERNANCE section 24): install.sh -> macos.sh/linux.sh both
call the realizer graph with --all/--post-mise, so dev laptops, CI runners and
devcontainer images take one code path, and on all three it is a manifest read
until someone opts in. install.ps1 now drives from-zip alongside from-url;
that leg is wired and UNVERIFIED on a Windows host, stated in the file.
