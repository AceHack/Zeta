## `131:7 no-unnecessary-condition` — the guard is **not** dead. No behaviour changes.

The rule says *"value is always falsy"* on `!window.PublicKeyCredential`, which reads like the unsupported-browser branch of `enrollProposalPasskey` is dead code on a WebAuthn path. **It is not.**

`lib.dom.d.ts` declares the global non-optional:

```ts
declare var PublicKeyCredential: { ... };      // lib.dom.d.ts:17448
```

so TypeScript proves the property always truthy. That proof is about the **ambient DOM declarations** — which describe a fully modern browser — and is not a runtime guarantee. A browser without WebAuthn has no such property; the access yields `undefined` and the guard fires as intended.

Checked rather than assumed, because a wrong answer here means a dead security guard:

| check | result |
|---|---|
| does `tsc` erase the branch? | **no** — emitted verbatim (TS does no type-directed DCE) |
| does `esbuild --minify` drop it? | **no** — preserved |
| runtime, no WebAuthn | both old and new form → `GUARD FIRED` |
| runtime, with WebAuthn | both old and new form → `supported` |
| present in the shipped bundle? | yes — `typeof window.PublicKeyCredential=="function"` |

So this is a **true positive about the types and a false positive about the behaviour**. What is fixed is the maintenance hazard: *a guard the linter calls unnecessary is a guard the next refactor deletes.* The check moves into `browserSupportsWebAuthn()` using `typeof`, which is opaque to the narrowing and so is honest to the type-checker and the runtime at once. The reasoning is recorded at the function so it is not re-litigated. **No `eslint-disable`.**

## `47:73 sonarjs/slow-regex` — real about the regex, unreachable at this call site

`/=+$/` is genuinely super-linear, **measured** rather than asserted — on a run of `=` that never reaches end-of-input it backtracks quadratically:

| n | 10,000 | 20,000 | 40,000 | 80,000 |
|---|---|---|---|---|
| time | 47ms | 186ms | 747ms | 2941ms |

Four times the work per doubling. Sonar is right about the construct.

It is still **not exploitable here** — and the reason is *not* "the input is trusted". Some of it isn't: `rawId`, `clientDataJSON`, `authenticatorData`, `signature` and `userHandle` all originate from the authenticator. The reason is that the regex is applied to **`btoa()` output**, and base64 bounds the `=` run at 2 with no interior `=` (RFC 4648 §4). An attacker controls the bytes going *into* the encoder, never the encoder's output alphabet. Confirmed over lengths 0..599: max trailing run **2**, interior occurrences **0**.

Fixed by **removing the construct** rather than arguing for it: `replaceAll("=", "")` is linear, cannot backtrack, and is byte-identical on base64 output — verified over 2000 adversarially-patterned payloads, **zero mismatches**.

## Update: `lint (TS)` was ALSO already red on `main` — same file, mirror-image bug

Running the real CI orchestrator (`bun src/Core.TypeScript/lint/lint-typescript.ts`) locally surfaced 4 more errors in this same file, under the **root** toolchain:

```
demo/identity-dla-site/src/lib/passkeyProposal.ts(139,7): error TS2322:
  Type 'Uint8Array<ArrayBufferLike>' is not assignable to type 'BufferSource'.
... 4 errors in the same file
```

**Confirmed pre-existing**, not introduced here, by checking out the `origin/main` version of the file and re-running the root `tsc` — same 4 errors.

The two toolchains had **contradictory** requirements, so no written annotation satisfied both:

| toolchain | `Uint8Array` | `Uint8Array<ArrayBuffer>` |
|---|---|---|
| root, TS 6.0.3 | widens to `Uint8Array<ArrayBufferLike>`, **not** assignable to `BufferSource` → **TS2322** | fine |
| site, TS 5.6.3 | fine | not generic until 5.7 → **TS2315** |

That is why `main` was **green on Pages and red on lint for the same file at the same commit**. #10501 had no correct annotation available to it — fixing the subpackage error necessarily introduced the root one. It reads as two unrelated problems and is one.

**Inference satisfies both at once**, so the three helpers drop their return-type annotations: `new Uint8Array(new ArrayBuffer(n))` infers the precise `Uint8Array<ArrayBuffer>` under 6.0.3 and plain `Uint8Array` under 5.6.3, from a single spelling. The omission is load-bearing, so it is commented at the site.

Verified against **both**, which is the point:

```
bun x tsc --noEmit -p tsconfig.json                   -> clean (TS 6.0.3)
cd demo/identity-dla-site && bun x pnpm@10.4.1 check   -> clean (TS 5.6.3)
bun src/Core.TypeScript/lint/lint-typescript.ts       -> passes (was FAILING on main)
```

This unblocks CI but does **not** close `081KZZ0K0XM087G0R003RNC0C7` — it is a workaround that happens to exist for this construct, not a general one. The next cross-version disagreement may have no such escape hatch, and that is the real argument for aligning.
