## Description

fix(cluster): the two-control-plane join test read an argv k3s had erased

`build-iso` has been red on every run for ~4 hours, on push and on PR. Two
steps failed; the second is downstream of the first and needs no fix of its
own. `Build installer ISO` was SKIPPED once step 13 failed, and `Locate ISO +
capture metadata` carries `if: !cancelled()`, so it ran anyway and reported
"No installer ISO found under result/iso/". That message is true and its cause
is one step earlier: there is no ISO because nothing built one.

The real failure is the provenance assertion at the end of the two-control-
plane join test, and THE JOIN ITSELF WAS FINE. In the same run (33040848262
step 13) `kubectl get nodes` on the founder returned exactly [founder,
joiner], the two `server-ca.crt` digests compared EQUAL — the invariant the
step is named for, one cluster CA and not two — the joiner carried the
control-plane label, and the joiner's own journal recorded

    Adding member joiner-2dc3b09f=https://192.168.1.2:2380
           to etcd cluster [founder-851fe68a=https://192.168.1.1:2380]

Every one of those passed. What failed was

    assert "--server" in joiner_cmdline

reading `/proc/<MainPID>/cmdline`, and its message — "injected-server-join.nix
did not take effect" — was false. The module took effect; the ORACLE could not
see it.

K3S ERASES ITS OWN ARGV, and has since v1.19.1+k3s1 (2020).
`pkg/cli/server/server.go` opens `run()` with

    // hide process arguments from ps output, since they may contain
    // database credentials or other secrets.
    proctitle.SetProcTitle(os.Args[0] + " server")

which reaches `github.com/erikdubbelboer/gspt`, a cgo port of BSD
setproctitle: it `memset`s the whole argv region to zero and writes the short
title back in place. Blanket, not per-secret — `--node-ip` and
`--cluster-cidr` are destroyed alongside `--token-file`. (k3s-io/k3s PR #2072,
commit 1eec7348, for issue #2014 "Database password written to process list".)

Measured, not inferred: the joiner's cmdline is a 445-byte region whose first
74 bytes are `/nix/store/...-k3s-1.34.5+k3s1/bin/k3s server` and whose
remaining 371 bytes are NUL. The region keeps the length systemd exec'd it
with, so the flags were overwritten AFTER exec rather than never passed — a
short ExecStart would have produced a 74-byte region, not a 445-byte one.
`tr '\0' ' '` turned those 371 NULs into 371 spaces and the assertion read a
command line with no flags on it at all. This oracle could never have worked
on any k3s this repo would ship; the test has never been green, and #15673 /
#15746 / #15792 each cleared a real blocker in front of it.

WHAT CHANGES IS THE ORACLE, AND NOTHING IS WEAKENED. All ten flag assertions
are kept verbatim on both nodes. They now read systemd's record of the argv it
exec'd (`systemctl show -p MainPID -p ExecStart k3s.service`), which is not
scrubbed and is still a statement about the running system rather than about a
file on disk. Both properties are read in ONE call so they cannot straddle a
restart, and the record's `pid=` is bound to the live `MainPID` before a single
flag is read out of it — unbound, it would be the argv of whatever ran last,
which is the "looks checked, checks nothing" shape these assertions exist to
refuse. A missing `argv[]` field or an argv that does not invoke k3s fails
closed rather than asserting over a string that may not contain the flags.

The honest limit, stated in the file: what `/proc` could have caught and this
cannot is a process that re-execs itself with different arguments. k3s does
not.

Because that limit is real, the provenance `/proc` used to carry is replaced
with something stronger and genuinely runtime — the joining node's own
journal. A control plane that JOINS logs `to etcd cluster [<existing
members>]`, and the bracketed list is the membership it found already there; a
control plane that FOUNDS logs `Starting etcd for new cluster` and never emits
the first line. Both halves are asserted, positive and negative, on the two
machines, plus that the cluster the joiner joined contains the founder's peer
URL. Neither half alone tells founding from joining, which is the split-brain
this step exists to detect.

Verified locally: the file parses (`nix-instantiate --parse`), the rendered
testScript compiles as Python, and the new helper was exercised against
realistic `systemctl show` output — the happy path recovers all six flags, and
a stale `pid=`, `MainPID=0`, a missing `argv[]`, and a non-k3s argv are each
rejected. NOT verified locally: the VM test itself. This host is
aarch64-darwin with no x86_64-linux builder, so `checks.x86_64-linux.k3s-
server-join` cannot run here; CI is the first execution.

Also repairs four garbled comment references in the same file — "leftover
UNIQUE leftover #15746 leftover unique @ c1f0aff9" was an earlier automated
edit's wreckage over "#15746 @ c1f0aff9", and it obscured the measured run-id
trail this lane's next reader needs.

Not fixed, and not what failed here: `k3s-server.nix` still pins no
`--node-ip`, so a multi-homed real host can advertise etcd on an interface its
peers do not share. #15746 named that gap and left it open; it stays open, and
it stays a product question for `injected-cluster-address.nix`.

## Commit 2 — the misleading downstream error

fix(ci): stop reporting a missing ISO for a build that never ran

`Locate ISO + capture metadata` carried `if: ${{ !cancelled() }}`, so it ran
even when `Build installer ISO` had been SKIPPED — and then failed with

    No installer ISO found under result/iso/ (looked for zeta-installer-*.iso
    OR nixos-minimal-*.iso per nixpkgs 25.11 default; ...)

which is an error about a missing artefact for a build that never happened.
On 2026-08-27 that turned ONE broken step — the two-control-plane join test,
which runs ahead of the build and stopped it — into two red steps, the second
of which named a file instead of naming its cause. Time went into asking
whether the ISO lane had a defect of its own. It did not.

A step that reports a missing output when its producer was skipped is
describing the symptom of an earlier failure as a defect of its own, which is
the reporting form of the same problem the surrounding lane is built to
refuse: a signal that looks like a finding and carries none.

Gating on the producer's outcome keeps the original intent intact. The comment
being replaced explains why `!cancelled()` was there — the flaky QEMU
full-install gate sits BELOW the build, and a successfully built ISO must
still upload when that gate trips. `steps.iso_build.outcome == 'success'` is
true in exactly that case, so the flaky-gate path is unchanged; what changes
is that a skipped or failed BUILD no longer produces a second, misleading
error.

This is also the convention the file already uses: every consumer downstream
(`Install cosign`, `Sign ISO with cosign`, the three uploads) is already
written `!cancelled() && steps.<producer>.outcome == 'success'`. `Locate ISO`
was the one link in the chain not gated on its own producer. Verified against
the parsed workflow: when `Locate ISO` skips, `steps.iso.outcome` is
`'skipped'` and all five consumers skip too — the same as today when it fails,
so no step can now run with empty `steps.iso.outputs.*`.

Verified locally: the workflow YAML parses and both steps carry the intended
`id` / `if`. Not verified locally: an actual Actions run — expression
evaluation is GitHub's, and CI is the first execution.

## Commit 3 — self-caught vacuity in commit 1

test(cluster): prove the k3s journal readable before reading an absence from it

Self-caught in the commit that introduced it. The etcd-provenance block added
two assertions in the same breath:

    assert "to etcd cluster [" in joiner_etcd_log      # the joiner JOINED
    assert "to etcd cluster [" not in founder_etcd_log # the founder did NOT

The second one is an ABSENCE, and an absence is only evidence if the place you
looked was readable. "the founder never logged joining" and "nothing could
read the founder's journal" produce the identical empty result, and only one
of them says anything. A wrong unit name, a non-persistent journal, or a
`journalctl` that failed for any reason would have made that assertion pass
while checking nothing — a check that cannot fail, in the highest-stakes gate
in the suite, added by the commit that was fixing exactly that class of defect
one screen higher up.

So the unit's journal is now MEASURED non-trivial on both machines before a
single absence is read as meaning anything: `journalctl -u k3s.service | wc
-l` must exceed 100 lines, which k3s clears by thousands during bring-up and
an unreadable journal cannot clear at all.

Two smaller things fall out of the same rewrite. The greps now run IN THE
GUEST rather than hauling a multi-MB journal across the test driver, and the
`|| true` that keeps a non-matching grep an empty result instead of a failed
command is now safe precisely because the line count is what stops "empty"
from meaning two different things. The founder's positive and negative
patterns are also read separately, so a failure message names which one.

The patterns themselves are validated against the real thing, not guessed —
on run 33040848262 step 13, `to etcd cluster [` appears on the joiner once and
the founder zero times, and `Starting etcd for new cluster` appears on the
founder once and the joiner zero times. They discriminate the two roles
cleanly on measured output.

Verified locally: the file parses, the rendered testScript compiles, and the
helper was exercised over stubbed machines — a healthy journal returns the
matching lines or an empty string as appropriate, and a 0-line or 5-line
journal is REFUSED rather than answered. Not verified locally: the VM test
(aarch64-darwin host, no x86_64-linux builder).
