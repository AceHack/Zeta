### The Roslyn question, answered by measurement rather than by rule of thumb

Aaron flagged that an SDK bump and a Roslyn bump *"sometimes go together"*. Here they do not, and the reason is the feature band:

```
sdk/10.0.302/Roslyn/bincore/csc.dll -version  →  5.6.0-2.26329.109
sdk/10.0.303/Roslyn/bincore/csc.dll -version  →  5.6.0-2.26377.103
```

Both **5.6.0**. The ceiling did not move, so `Microsoft.CodeAnalysis.*` stays at 5.6.0 and its `ignore:` entry is untouched. A **patch**-band roll keeps the Roslyn minor; the change that moves it is a **feature**-band roll (10.0.3xx → 10.0.4xx, currently 10.0.400), and that is the one that must carry CodeAnalysis and `FSharp.Core` in the same commit. The new parity check says so at the place the version is read.

### mise vs `global.json` — the decision, and a correction to the framing

The brief said `rollForward: latestPatch` is a safety property mise silently overrides. The sharper reading is that **the property was never there to override**: `rollForward` is a *resolution* policy over SDKs already on the machine. It has never downloaded one. No `global.json` setting has ever acquired a newer SDK, with or without mise.

**Decision: `.mise.toml`'s `dotnet` pin is the single declared source** — because mise is the only one of the two that *acquires* an SDK, and it is what `tools/setup/install.sh` runs everywhere.

`global.json` is **not** demoted to a pointer. Under `clone-at-tag-stays-sufficient.md` the tree must stay buildable from a clone at a tag with no package manager present, and `global.json` is the .NET-native contract that path reads — so it keeps a real, exact version, as a **restatement held equal by a check**. `rollForward: latestPatch` also stays for that path, and a `//` note now says what it is (tolerance over an installed set, not an update mechanism) where a reader looks.

`audit-dotnet-pin-parity.ts` on the `cross-verify` floor makes the disagreement impossible rather than discouraged. Offline, text-only, 12 falsifiers including the state `main` was actually in.

### Owned error, and a trap the next Mac will hit

`mise install dotnet@10.0.303` replaces the shared host at `~/.local/share/mise/dotnet-root/dotnet` **in place**; the kernel keeps the previous binary's code-signature cache entry for that vnode, and every later `dotnet` call is **SIGKILLed — exit 137, no stdout, no stderr, for every installed SDK**. mise's own post-install probe fails the same way (`"exited with non-zero status: no exit status"`), which is the tell. Not a bad download: `codesign -v` passes and the same bytes at a new path run. I broke the shared dotnet-root on this machine doing it, and repaired it by giving the file a new vnode. Recorded in `.mise.toml` beside the pin.

## 2. Dependabot: two ecosystems → eight

Added **`bun`**, **`npm`**, **`cargo`**, **`gomod`**, **`uv`**, **`dotnet-sdk`**.

The audit ran the control without meaning to: §2.5 checked every NuGet pin — all at latest. §2.4 checked npm, which no bot watched — `typescript` a whole **major** behind, `z3-solver` a major, two crypto packages two minors. Where the bot was aimed nothing drifted. The mechanism was under-aimed, not broken.

Checked rather than assumed:

- **bun vs npm** — every CI lane runs `bun install --frozen-lockfile`, so `bun.lock` is authoritative. `bun` is pointed only at the four directories that *have* one; lockless `package.json` dirs go to `npm`. An entry aimed at a file its ecosystem does not read is a declaration that silently does nothing.
- **`uv`, not `pip`** — `src/Core.Python/` has a committed `uv.lock`; `pip` would edit `pyproject.toml` and leave the lock behind, and `uv sync --frozen` would refuse the tree.
- **`dotnet-sdk`** — this corrects the brief, which said `global.json` is not a package manifest and no bot can watch it. It is a documented ecosystem and `global.json` is exactly what it reads. Acting on the unchecked version of that claim is what let a 10-CVE roll sit for twelve days.

**Both existing `ignore:` entries survive byte for byte.** One is added — `typescript` majors — in the same shape and for the same reason, with `LIFTS WHEN:` pointing at a real work-item id.

### The two guards I was asked for and did not write

The ask was `ignore:` entries for rust ⇄ the cache globs and zig ⇄ the byte-lock. **Neither could fire.** An `ignore:` suppresses an update Dependabot would otherwise *propose*; both pins live in `.mise.toml`, a manifest of no supported ecosystem. The entry would suppress nothing while sitting exactly where a reader takes it for protection — a guard that cannot fail. Writing it would have satisfied the request and left the coupling unguarded.

## 3. The guard that *can* go red

`audit-mise-toolchain-couplings.ts`, on the `cross-verify` floor, offline.

**rust — the count in the tree was wrong.** `.mise.toml` said a bump must move the cache globs in two workflows. Measured: **17 operative restatements**, and the one that matters most is not a glob —

> **`.mise.full.toml` carries its own `rust = { version = "1.87.0", … }` pin.**

So a bump doing exactly what the documented constraint asked would still have left full-tier hosts on a different compiler from slim ones, with nothing able to say so. Sites are **discovered**, not listed, so a new workflow with a stale glob is caught the day it lands. `docs/`/`memory/`/`workitems/` are out of scope on purpose — that boundary is itself a falsifier in the tests. Check what *executes*, never what *narrates*.

**zig — the failure that stays green.** The committed `.wasm` does not move when the pin does. The byte-lock keeps passing, because artifact and vectors are both unchanged, while the module silently stops being reproducible from the pinned toolchain (condition 3 of the no-binary-in-proof-lineage exception). The `(version, sha256)` pairing is now recorded and checked **both** ways.

**Mutation-tested** — all three real failure modes induced, all three went red; tree restored and sha re-verified:
