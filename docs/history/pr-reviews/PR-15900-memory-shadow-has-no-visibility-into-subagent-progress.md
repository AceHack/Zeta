## Description

Aaron's observation, mid-tick, after I dispatched two background agents:

> "it seems shadow does not have context to the multi agent workflow context, i can see on the
> screen these are not finished yet"

Correct, and worth recording. Dispatching a background agent returns an id and nothing else until a
completion notification — no progress signal, no partial output, no way to tell *running* from
*stalled* from *dead*. Aaron, watching the same work, can see all of it.

**The orchestrator is blind to work it delegated, and the human is the only one who can see it.**

Three consequences:

1. **The only honest answer is "still running."** This is the vacuity class pointed *inward*, and
   its worst form — a fabricated result is more damaging than a check that silently didn't run,
   because it's confidently wrong rather than merely absent. The tooling's own instruction never to
   predict a pending agent's results is a prohibition standing in for a missing channel.
2. **Scheduling happens blind.** The substitute is elapsed wall-clock and a guess — the same
   unreliable-narrative-counter failure the heartbeat rule names for a different surface.
3. **The asymmetry runs the wrong way.** This substrate's ethos is that agents externalise state so
   it survives them. Here the *human* holds the observability and the *agent* is asked to report on
   it.

Not a defect anyone introduced, and not the subagent's fault — background execution without a
progress channel is how the harness works. Report the fact, not a motive. Nor is it an argument for
fewer agents: decorrelated parallel reads are worth the cost, and the fix is a channel.

Candidate fixes named, **none built or chosen** — this is an observation, not a design.
