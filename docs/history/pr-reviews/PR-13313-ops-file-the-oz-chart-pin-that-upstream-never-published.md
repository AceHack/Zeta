## Description

`applications/oz/Application.yaml:21` pins `ziti-controller` at `targetRevision: 1.4.5`. Checked against the upstream index at that exact `repoURL`: **it does not exist.** The published 1.x line ends at **1.3.4** (2025-05-01). `1.4.2` exists upstream only as an *appVersion* — the likely origin of the mistake, an app version copied into a chart-version field.

ArgoCD cannot resolve a chart version that was never published, so this Application **cannot sync at all**. Not drift, not a deprecation — the coordinate has never been valid.

## Why it went unnoticed is the more useful half

`oz` is not in the included dev/CI proof, so **nothing ever attempted to resolve its chart** — one of 26 Applications out of 45 that no lane exercises. An Application can carry a coordinate that has never once been resolved, and no check says so.

The general form is worth more than this row: **nothing in the tree verifies that a pinned `chart` + `targetRevision` is actually published.** Every Application sourcing a remote Helm chart carries that risk, and a typo in a version field is indistinguishable from a correct pin until something tries to sync it. A resolvability check over every remote-chart Application would catch the class rather than this instance.

## Filed rather than fixed

Choosing the replacement is a product call: 1.3.4 is the newest 1.x, but published 2.x and 3.x lines exist, and moving major versions is a decision about OpenZiti compatibility rather than about this field.

## Provenance

Found by the day-zero chart research (#13309) while pulling all twelve pinned charts at their exact revisions — eleven resolved; this was the twelfth. Verified independently against the upstream index before filing.
