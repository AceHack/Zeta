## Description

`tools/setup/common/mise.sh` runs `mise trust --all --yes` for the clone it installs
into, once. A worktree allocated later is a NEW PATH, and mise keys trust by path,
so every lane this fleet allocates inherits nothing. Measured on this machine
2026-08-25: 34 of 56 live worktrees untrusted. No worktree-creating code path in
the repo granted trust — `grep -c "mise trust"` across them returns 0.

WHY IT WENT UNNOTICED FOR SO LONG, WHICH IS THE INTERESTING PART:

1. mise reports an untrusted config as `error parsing config file: .mise.full.toml`.
   That reads as a malformed pin file — a defect in the config — rather than a
   missing grant. Agents (this one included) treated it as noise to suppress.

2. The suppression did not work and nobody checked. Every command in this session
   carried `export MISE_DISABLE=1`. There is no such mise setting; the error
   printed on all of them. A workaround that visibly fails to work, run hundreds
   of times, because its output was never read.

3. The tools still resolve. PATH already held the mise install, so `bun` came from
   the pinned 1.3.14 regardless — the lane LOOKED like it was inside the closure.
   On a host whose PATH differs it would silently disagree with CI, which is the
   exact divergence the closure exists to prevent.

4. CI cannot see it. mise assumes trust when it detects CI (`mise trust --help`),
   so the failure mode does not exist on a runner and no gate could ever have
   caught it. It is local-only by construction.

The trigger is worth recording because it is not obvious: configs holding only
`min_version`, plain-version `[tools]`, and `[tasks]` are auto-trusted — nothing in
them executes at load. Tool OPTIONS are not. This repo's `.mise.toml` carries
`node.compile`, `python.compile`, `python.uv_venv_auto`, so it demands a grant.

Fix: `lane-allocator.ts` grants trust after `git worktree add`, non-fatally — a
lane that cannot be trusted is still a usable lane, and failing allocation over it
would turn a degraded closure into no lane at all. The 34 live worktrees were
repaired by hand and re-measured at 56/56.

The falsifier asserts the allocator's OWN "mise: trusted <path>" line rather than
mise's, because mise prints nothing when the config was already auto-trusted —
i.e. on every runner. Two earlier designs are documented in the test as rejected:
a before/after trust-state check passes for free in CI, and MISE_PARANOID=1 makes
it unpassable anywhere (paranoid ignores the trust store, so no grant satisfies
it). Both were built and measured before being discarded.
