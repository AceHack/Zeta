## Description

fix(ci): drop the unreachable push path that made lint-autofix-apply a dangerous workflow

Scorecard DangerousWorkflowID (critical, alert 560) named the untrusted
checkout in lint-autofix-apply.yml: a workflow_run-triggered job that
checked out github.event.workflow_run.head_sha while holding
contents: write.

The privilege it held was for a branch that could never execute. The job
pushed only when head_branch == 'main', but the producer (lint-autofix.yml)
triggers on pull_request ONLY, the apply job additionally gates on
workflow_run.event == 'pull_request', and a pull_request head_branch is the
PR source branch -- which cannot be main in the same repository, and a
fork's main is excluded by the same-repo gate. Every run took the report
path while the job still requested write scope and checked out PR-controlled
content with a persisted credential (persist-credentials defaults to true;
the producer sets it false, this job never did).

So the fix is a removal, not a mitigation. Gone: the checkout, the
AUTOFIX_TOKEN/github.token credential on disk, fetch-depth 0, the git-apply,
the push, and contents: write. The job now downloads the patch artifact and
renders it in the job summary -- which is what it already did on every real
run.

Two smaller defects fixed on the way, both from rendering PR-controlled
content:

- the diff was emitted inside a ```diff fence, so a patch containing a fence
  marker could break out and inject markdown into the job summary. It is now
  HTML-escaped into a <pre> block (ampersand substituted first so the later
  entities are not double-escaped).
- the ::notice line interpolated HEAD_BRANCH, a PR-controlled value, into a
  workflow command. The notice text is now static and the branch name is
  printed to the log instead.

Closes Scorecard alert 560 (DangerousWorkflowID, critical) and alert 138
(TokenPermissionsID, jobLevel contents: write on this workflow).

Verification: python3 yaml.safe_load parses; lint-workflow-job-timeouts,
audit-workflow-write-token-consistency, audit-workflow-step-output-has-writer,
audit-workflow-credential-role-separation and audit-action-sha-roster all
pass. The job now declares no `uses:` at all, so there is no action to pin.

Not fixed here, and deliberately: trunk healing is a stated intent this
change does not restore. Reviving it needs a push: trigger on the producer
and a design that never checks out PR-controlled content in a privileged
job. That is a new design, not a resurrection of this branch.
