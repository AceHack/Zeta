## Description

## What the installer selects today

`full-ai-cluster/usb-nixos-installer/zeta-install.sh` is already greedy, and I did not change it. Measured by reading it back rather than trusting the header prose:

```
mapfile -t ALL_DISKS < <(lsblk -d -p -n -o NAME,TYPE,RM,RO,TRAN |
    awk '$2=="disk" && $3==0 && $4==0 && $5!="usb" {print $1}')
...
for d in "${SORTED[@]}"; do
  [[ "$d" != "$BOOT_DISK" ]] && DATA_DISKS+=("$d")
done
```

Every fixed, writable, non-USB `type=disk` device — NVMe, SATA SSD, HDD, SAS, hardware-RAID volume, eMMC alike — is enumerated, sorted NVMe→SSD→HDD, the fastest becomes BOOT, and **everything else becomes a whole-disk `longhorn{2..N}`**. The boot disk additionally carries a `longhorn1` tail. Nothing is skipped by a rule; a disk the installer sees is a disk it formats. That covers both box shapes in the ask — a NAS full of spinning disks and a PC with one NVMe get the same treatment.

## Whether formatted / declared / registered can diverge

There are four sets, and a node only stores data if all four agree:

| | set | source |
|---|---|---|
| 1 | **FORMATTED** | `zeta-install.sh` → `/var/lib/longhorn-disk{1..N}` |
| 2 | **DECLARED** | the host's `fileSystems` |
| 3 | **REQUIRED** | `zeta-longhorn-preflight`'s `requiredMounts` |
| 4 | **REGISTERED** | `zeta.longhorn.dataDisks` → the Longhorn Node CR |

**1 == 2** is enforced from both ends already: #13263 made the `hardware-configuration.nix` capture fail closed *and* verify the file it installed declares every mountpoint the install mounted, and #13252's preflight check 1b refuses at boot when a `longhorn`-labelled device is not mounted under the Longhorn root. **2 == 3** holds by construction — `requiredMounts` is derived from `fileSystems`.

**3 == 4 was enforced by nothing, and was false on the host the USB installs.**

```
$ nix eval .#nixosConfigurations.worker-template.config.zeta.longhorn.dataDisks
["/var/lib/longhorn-disk1","/var/lib/longhorn-disk2"]

$ nix eval .#nixosConfigurations.control-plane.config.zeta.longhorn.dataDisks
error: flake ... does not provide attribute
       'nixosConfigurations.control-plane.config.zeta.longhorn.dataDisks'
```

The option is **not even declared** on `control-plane`. `longhorn-disks.nix` is imported by exactly one thing in the tree — `hosts/worker-template/default.nix` — and `zeta.longhorn.dataDisks` is set by exactly one thing — `disko-shapes/longhorn-node.nix`, reachable only from that host. `control-plane` and `worker-gpu` are menu options **1 and 2 of `zeta-install.sh` itself** and are hardware-configuration hosts.

So the value that reached Longhorn was the option's fixed default, `[ "/var/lib/longhorn" ]` — a directory on the **root filesystem**, created by `longhorn-prereqs.nix` tmpfiles precisely so `longhorn-manager` can start on a node with no data partition. A 4-disk box formatted four partitions, declared four, required four to be mounted, and told Longhorn about one path on the boot disk. Every dedicated partition contributed **zero** schedulable capacity — while the install-time capture check and the boot-time preflight both went green, because both of them measure `fileSystems`, and `fileSystems` was correct.

A check that did not run, looking exactly like a check that passed. Preflight check 1b already names the outcome verbatim — *"Longhorn will place replicas on the ROOT filesystem instead"* — but it can only fire on the **undeclared** case; on a normal successful install nothing looked at set 4 at all.

## Disposition on #12175

**It solves the mechanism, and this builds on it and assumes it lands.** #12175 replaces the `kind: NodeDiskCatalog` file nothing read with Longhorn's real three-part mechanism (`create-default-disk` label + `default-disks-config` annotation + `createDefaultDiskLabeledNodes`), and proves it with a two-real-drive VM test. I did not touch any part of it, did not push to its branch, and built no second mechanism.

The two halves are orthogonal and the ask needs both:

> **#12175 makes `dataDisks` REACH Longhorn. This makes `dataDisks` CONTAIN every disk the node has.**

With only #12175, a control-plane box annotates itself with the one-element default and Longhorn faithfully registers a single root-filesystem path. With only this, the correct multi-disk list is written to a file nothing reads. Neither half is visible in the other's tests. #12175 also owns the `common.nix` import edge that makes this derivation reachable on `control-plane` at all — the eval test **measures** that edge count rather than asserting it, so it is green on either side of that merge and prints which state it is in.

Trial-merged: `longhorn-disks.nix` **auto-merges** with #12175. That merge does conflict on `common.nix`, and it reproduces merging `pr/12175` into `origin/main` with none of my commits present — pre-existing rebase debt on #12175, not introduced here.

## What changed

Three files, one behavioural line.

- **`nixos/modules/longhorn-disks.nix`** — `dataDisks`'s default is no longer a literal. It is now `longhorn-preflight-checks.nix`'s own `requiredMounts`, so the set the node **refuses to boot quietly without** and the set Longhorn is **told about** are one expression and cannot drift. Falls back to `[ "/var/lib/longhorn" ]` when the host declares no Longhorn filesystem — `[ ]` would trip the module's own `lib.mkIf (cfg.dataDisks != [ ])` and take the node label with it.
- **`nixos/tests/longhorn-disk-registration-eval-test.nix`** — new, 23 properties.
- **`flake.nix`** — wires it as `checks.<system>.longhorn-disk-registration`, forced by `nix flake check --no-build` on every PR touching `full-ai-cluster/nixos/**`.

No PVC size, no `storage-profiles.json`, no chart values, no installer line. Nothing was written to a block device at any point.

- 23/23 properties green.
- 10 mutations, each byte-verified applied, each killed something.
- `nix flake check --no-build --show-trace` → **exit 0**, with `✅ checks.aarch64-darwin.longhorn-disk-registration` in the output. Exit code read directly, not through a pipe.
- Under `lib.evalModules`: a 4-disk `fileSystems` resolves to all four paths, emits four tmpfiles rules and `--node-label=zeta.io/longhorn-disks=4`; a no-Longhorn host resolves to the one-element fallback with the module still enabled; `mkDefault` and an explicit setting both still win.
- **No regression on the one host that already worked**: `worker-template`'s resolved `dataDisks` is `["/var/lib/longhorn-disk1","/var/lib/longhorn-disk2"]` both before and after, evaluated against a `cmp`-confirmed pristine copy of the module and again after restoring the edit.
- `bash -n zeta-install.sh` clean; `nix-instantiate --parse` clean on every `.nix` touched.

**DESIGNED BUT UNRUN:** no metal boot, no Longhorn API, no disk formatted. This proves the node *computes* the right set. Two things would settle the rest, and neither can run here:

1. That the set reaches the Node CR — #12175's VM test covers the mechanism; the field reading after one install on a multi-disk box is `kubectl -n longhorn-system get nodes.longhorn.io <host> -o jsonpath='{.spec.disks}'`, which must list **one entry per formatted partition**.
2. That the installer's enumeration really sees every disk on a real NAS. `lsblk` output on the actual hardware is the only thing that can say so; the console marker on that boot is `ZETA_LONGHORN_PREFLIGHT_OK`.
