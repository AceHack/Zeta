## Description

## What

`gate (required)` now publishes **which green it is**, and **names legs that failed
without blocking**. Nothing new blocks; nothing stops blocking.

Two findings from today's audit third pass -- "what does the implementation emit that
the model does not mention?" -- both in `.github/workflows/gate.yml`.

## Finding 1 -- SUCCESS was two-valued and the value was not in the signal

Treating `skipped` as success is correct: the path filter legitimately skips
`full-verify` and the .NET build/test steps on a docs-only PR. But that made a green
`gate (required)` either the full seven-language byte-lock or a materially smaller
run, with **wall-clock duration the only thing telling them apart** to anything reading
check status -- including armed auto-merge. That is the vacuity class at the rollup
level: a check that did not run looks exactly like a check that passed.

The rollup now emits to its **step summary** and to a **notice/warning annotation**:

- which floor jobs ran, and which were **skipped** (named);
- which **steps** were skipped inside the jobs that did run;
- which legs **failed non-blockingly**;
- the same, machine-readable, as job `outputs` (`scope`, `floor-executed`,
  `floor-skipped`, `nonblocking-failures`).

**The floor is not copied anywhere.** Scope is derived from `${{ toJSON(needs) }}` --
literally the `needs:` block, keyed by job id, with each result -- so adding or removing
a floor job updates the summary with no edit to the script. `gate.yml` is parsed only to
map a job id to the display name the Actions API reports (`lint` -> `lint (semgrep)`,
`build-and-test` -> `build-and-test (<os>)`); a parse miss degrades to an explicit
`UNRESOLVED` row, never to a silently wrong summary.

`path-filter` itself is untouched -- it derives from `git diff base..head` rather than a
PR self-declaration, and `test-typescript-hermetic` still deliberately carries no
`needs: [path-filter]`. That is the good pattern; the rollup was the part that did not
tell the truth about its inputs.

## Finding 2 -- Windows legs report green while failing

`build-and-test` carries `continue-on-error: ${{ startsWith(matrix.os, 'windows-') }}`
and **is** in the required floor, so a Windows build/test failure reaches
`gate (required)` as SUCCESS.

This is **not flipped here** -- it is a policy call, not a cleanup. What changed:

1. Such legs are now **named** in the summary (`FAILED (non-blocking)`) and raise a
   warning annotation.
2. The residue is **stated plainly** in the workflow comment at the flag: the floor's
   name overstates its coverage on one of three platforms.
3. The recommendation is filed **with evidence**, not decided:
   `workitems/081M0BVAV2H087G0R000VXRYRQ-decide-whether-the-windows-build-and-test-legs-should-block.md`.

**Measured** (Actions API, all completed `gate` runs on `push` + `workflow_dispatch`,
conclusion not `cancelled`, 2026-04-25..2026-08-19, **152 runs**):

| leg | failures | rate |
|---|---|---|
| `build-and-test (windows-2025)` | 12 | 7.9% |
| `build-and-test (windows-11-arm)` | 9 | 5.9% |
| runs with at least one Windows failure | 14 | 9.2% |

In **11 of 11** instances since `gate-required` existed, the required check reported
green beside the red leg. Failing steps in the four most recent: `Test` (x3) and the
Windows `install.ps1` step (x1) -- a mix of real test failures and installer maturity.

**Recommendation: do not flip it yet.** At 9.2% run-level, blocking would red the floor
on roughly one merge in eleven for causes mostly outside the author's reach -- and a
floor that is red for reasons you cannot fix is how a floor stops being read (the exact
mechanism recorded in the `test-typescript-hermetic` header). Proposed criterion, now
cheap to check from the annotations this PR adds: **30 consecutive completed push runs
with zero Windows-leg failure** -> propose the flip.

**And a structural note that changes the question:** Windows legs do not run on
`pull_request` at all (`matrix-setup` gives Linux + macOS pre-merge). Flipping
`continue-on-error` alone would red main *after* the fact rather than block any merge.
The real decision is two decisions, and the first costs money: measured on run
32203290237, `windows-2025` 11m03s and `windows-11-arm` 10m00s -- adding them to the PR
matrix is ~21 runner-minutes per PR run.

## Cost

`gate (required)` was 3 s. It is now ~20 s: sparse checkout (~11 s measured on this
workflow's other jobs), `setup-bun` (~3 s measured), one Actions-API call (~2 s). The
job timeout goes 1 -> 5 min as a **runaway cap, not a budget** -- nothing in the job
retries, polls, or waits on anything that can hang open.

That is the honest price of the fix, and it earns its slot: the required check is what
auto-merge reads, and a required check that cannot say what it covered is the vacuity
class sitting on the merge path.

`permissions:` is job-scoped least privilege: `contents: read` for the sparse checkout,
`actions: read` for exactly one call against **this** run. The `needs` context collapses
a whole matrix to a single value -- which is precisely what kept the Windows legs
invisible -- so per-leg truth has no other source.

## Verified, not asserted

Three **real** Actions-API job listings are committed as fixtures (trimmed to the fields
the module reads) and the renderer is run against them:

| fixture | run | rendered |
|---|---|---|
| code PR | 32202982324 | `Scope: FULL`, 5/5 floor jobs ran |
| docs-only PR | 32204203148 | `Scope: REDUCED`, 4/5, `full-verify` named as not run |
| push w/ Windows failure | 31978270082 | `build-and-test (windows-2025)` -> **FAILED (non-blocking)** |

The first two report an **identical** green today. They now render differently -- and the
difference includes the step-level half a job-level rollup cannot see: `build-and-test`
skipped **4** steps on the code PR and **7** on the docs-only PR while reporting
`success` in both.

Actual rendered output for the docs-only fixture:

```
**Scope: REDUCED** -- at least one floor job did NOT run. ...

| `full-verify` | skipped | full-verify (7-lang oracle + cost + proofs) | skipped | 0 | 0 |
...
**Floor jobs that did NOT run:** `full-verify`
::notice title=gate scope::gate scope=reduced: 4/5 floor jobs ran. Skipped: full-verify.
```

and for the Windows-failure fixture:

```
| `build-and-test` | success | build-and-test (windows-2025) | **FAILED (non-blocking)** | 12 | 9 |
::warning title=non-blocking failure::build-and-test (windows-2025) FAILED. It is inside
the required floor but carries continue-on-error, so `gate (required)` still reports success.
```

Local gates: **7/7 tests**, `tsc --noEmit` clean, `eslint` clean, `actionlint` clean on
the edited `gate.yml`, prettier clean. `bun run preflight --quick` has one failure --
`auto-vivify` on two dangling paths in a YubiHSM work-item from #12067, pre-existing on
`main` and unrelated to this change.

**What I could NOT verify before landing:** the live step summary. It is only produced by
a real run of the modified workflow, and this PR touches `.github/workflows/**`, so its
own gate run is the **FULL** case. The REDUCED case is demonstrated against the captured
docs-only fixture, not against a live docs-only run. First docs-only PR after this lands
is the real confirmation.
