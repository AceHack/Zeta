## Description

`run.ts --all` exited **0 while silently omitting scenario 5 of 5**. This makes the exit code stop lying.

## The bug

`run.ts:797-803` returned `status: "skipped"` for `cluster-joining`; `:862` and `:884` counted only `"failed"` and `"scaffolded"` as non-zero. A full-matrix run therefore reported green having never run a fifth of the matrix.

Same defect class the harness authors already caught one level up and confessed in-file (`zflash-harness-lint.yml:11-22`): *"Three consecutive green runs therefore meant 'the harness invariants hold', NOT 'a boot was validated'… A green check that implies more than it tested is worse than no check."*

## The fix

New exported `isPassing(result)` / `exitCodeForResults(results)` — **only `"passed"` is green**. Both `--scenario` and `--all` route through it.

The omission is now **loud, not merely non-zero**: stderr names every non-passing scenario, the JSON summary gains a `nonPassing` count, and the `cluster-joining` message leads with `NOT RUN (counts as non-passing)` plus the real blocker.

**A second bug fell out.** `--all` gating keyed off *failed* rather than *non-passing*, so a gate-skip never entered `failedIds` — meaning if scenario 1 failed, scenario 2 was skipped but **3 and 4 still ran**: real QEMU work downstream of a scenario that never ran. Now `--all` on a missing ISO correctly gives `1=failed, 2..5=skipped`, exit 1.

## Which CI jobs go red: **none — and that is the more alarming finding**

Every consumer of the exit code was checked. **`--all` is invoked by nothing in CI**; it exists only in the file header and `test-harness/README.md`. `--scenario cluster-joining` is likewise invoked by nothing.

- `zflash-harness-lint.yml` — stays green. `--dry-run` still exits 0, and its fail-closed assertions on scenarios 3/4 are unchanged (`failed`, not `skipped`).
- `build-ai-cluster-iso.yml` (`:285/:317/:369/:390`) — stays green. Runs scenarios 1–4 individually, all `composes-with-existing`, never `skipped`.

So the false green was **latent to CI and live to operators**: anyone running the documented full-matrix command got a 0. This fixes the lie told to humans, not a CI signal.

**Dry-run vs execution is encoded structurally rather than as a flag:** `--list`/`--dry-run` never call `runScenario`, produce no `ScenarioResult`, and claim only "this plan is well-formed" — exactly what they check, so they legitimately exit 0. Only execution modes are held to "did it run and pass." Stated in the docblock so nobody later "fixes" dry-run into redness.

## Scenario 5 was NOT wired, deliberately

It is not a missing dispatch hop. Three blockers, each verified in source:

1. **No network between the VMs.** `multi-vm.ts` plans `networkTopology: { shared-bridge, zflash-test-br0 }`, but both VMs take args from `buildQemuSystemBootArgs` (`qemu-state.ts:278`), which hardcodes `-netdev user,id=net0` — per-VM SLIRP NAT. Two SLIRP VMs cannot see each other. **The topology field is decorative.**
2. **The VMs never run concurrently.** `executeMultiVMRuntimePlan` loops `plan.vms` serially; the cluster node is torn down before the joining node boots.
3. **The joining disk is never created.** `MultiVMExecutionStep` declares `"create-joining-disk"` but no code path emits it — no `qemu-img create` for `joiningDiskPath`, and no scenario-5 baseline bootstrap analogous to `planPathForkBaselineBootstrap`.

Wiring an env-gated dispatch on top of that would produce a "cluster join" with no path to the cluster — and if the serial markers ever matched, a **`passed` for a join that never happened**. That is the same false green this PR exists to remove. All three blockers are recorded in the `cluster-joining` branch comment so the next person meets the real obstacle instead of the word "pending".
