### Three corrections to the brief

1. **Path.** The bootstrap is `tools/setup/host-loop-bootstrap.sh`, not
   `tools/kiro/…`. The line number (142) was right; `tools/kiro/` does not exist
   on `main` at all.
2. **A sixth unit.** `com.lucent.zeta.kiro.plist` also names the dead wrapper. It
   is **not loaded** (`launchctl print` → rc 113), so it is dormant rather than
   failing and never appears in `launchctl list`. It should be deleted.
3. **The replacement was replaced.** #8088 ported the wrapper to
   `src/Core.TypeScript/kiro/kiro-loop-wrapper.ts`; **#8121 deleted that too**.
   The correct target is neither wrapper — it is
   `src/Core.TypeScript/service/loop-tick.ts`.

## Two more reasons those cells could not have worked

- **Label mismatch.** The bootstrap installed `com.lucent.zeta.<persona>`;
  `persona-registry.ts` expects `com.lucent.zeta.<persona>-loop`. So
  `IServiceManager.status("otto")` answered **`not-installed`** for a plist that
  was installed and failing every minute.
- **`alexa` and `vera` were not in the loop registry** at all, though the
  manifest provisions cells for them. A path-correct unit would still have exited
  1 on "Unknown persona". Both added; harness derived from
  `registry/personas.yaml` (id=3 Kiro, id=5 Codex) and the manifest's own
  `harness=` column, which agree — not invented.

## The failure underneath the failure

Nothing reported persona-loop liveness, and the thing that looked like it did
could not fail:

```text
healthy kiro-loop   ->  state = not running       ->  installed-stopped
dead otto (exit 78) ->  state = spawn scheduled   ->  installed-stopped
```

`ServiceState` has no value for "installed, scheduled, and failing every
invocation", and `adapters/launchd.ts` keys on `includes("state = running")` — but
a `StartInterval` loop is *supposed* to be "not running" between ticks. The one
state that could have carried the signal is the one that is normal. The
discriminating fact, `last exit code = 78`, was in the same output nothing parsed.

The bootstrap's own health check was worse, in three independent ways: it globbed
`zeta-*/runner.log` and guarded with `[[ -f ]]`, so a cell that never started was
**silently skipped**; it only ever `echo`'d, never affecting exit status; and it
grepped for `"heartbeat complete"`, which `loop-tick.ts` does not emit — it logs
`"tick complete"` (**0 vs 33** matches in the live kiro log). A healthy cell could
only ever reach the ⚠ branch.

`loop-liveness.ts` reads launchd's exit code **and** the heartbeat artifact
`loop-tick.ts` already writes (`<stateDir>/heartbeats/<persona>-tick.json`). That
is deliberate: `CLAUDE.md` already says liveness must be **externalized** because
the narrative self-counter is unreliable. This extends that discipline one layer
down to the scheduler, reusing the artifact the work had to produce rather than
inventing a parallel signal.

#    ~/.zeta/clones/<agent>, installs the units, waits 65s, and now EXITS

bun run check:loop-liveness            # expect exit 0, all five OK
