## Description

## What

`js/http-to-file-access` and `js/file-access-to-http` are **interprocedural** — the fetch and the write are frames apart, so there is no regex that finds them and no single line to patch. Each site needs a decision about **where the cap belongs**, and that decision is now written in the code beside the call.

For all six sites here the answer is the same, and it is not "at the write": there are several sinks and **one door**, so the bound goes at the door.

## What was actually missing

Every one of these called bare `fetch` and then `res.json()` / `res.text()` / `arrayBuffer()` — **no byte cap, no deadline, no scheme check**. Two run unattended in CI, and one of those (`retraction-actuator`) fires precisely when `main` is already red: a hung API call there holds an incident response open.

`fetchBounded` supplies all three — bytes counted as they arrive with the transfer abandoned the moment the cap is crossed, a deadline, and a refusal of any scheme but `http:`/`https:`, so none of these can be pointed at `file:` and turned into a local read with none of `readFileBounded`'s guarantees.

**A truncated body is a refusal, never a partial parse.** Each site checks `truncated` and throws. Half a JSON listing that happens to parse is the worst possible input to a fold that decides whether main is healthy, or whether a commit gets reverted.

## The step summary was also unbounded — a live defect, not a scanner finding

GitHub **drops** a `$GITHUB_STEP_SUMMARY` larger than 1 MiB rather than truncating it. So an oversized report did not overflow loudly; it silently produced no summary at all. Both CI folds now bound it with `truncateUtf8Bytes` at 900 KiB and **say so in the output** when they cut. The bound is in **bytes** — `String.slice` counts UTF-16 code units and would not have been one.

## The datfile download needed a different shape, and the obvious migration is wrong

`fetchBounded` decodes its body as UTF-8, and a datfile is **bytes**: any sequence that is not valid UTF-8 comes back as U+FFFD, and the sha256 would then be computed over something the server never sent — **a checksum gate that cannot fail**. And `fetchToFile` straight to the destination would put **unverified** bytes at the path the next tool reads.

So:
1. the transfer goes to a `mkdtempSync` staging directory (0700, unpredictable name) under `exclusive: true` (`O_CREAT|O_EXCL`, so nothing pre-planted is followed),
2. the checksum is taken from **what landed on disk** — strictly stronger than a check over an in-memory buffer,
3. only a verified file is `renameSync`d into place, and every failure path removes the staging directory.

**Unverified bytes never reach `outDir`.**

## What this does not claim

`fetchToFile` is an http-to-file sink and says so in its own docstring. The flows above are what these tools are **for** — a CI reporter renders remote data; a datfile fetcher downloads a pinned datfile; the vocab dogfood posts a carved sentence to a local LLM. Bounding them is the honest outcome, not their deletion.

**Some of these alerts will persist, and they should.** The flow is real; it now happens once, in a named function, under a stated cap, at a line a reviewer can find. **No alert is dismissed.**

## Follow-up commit: the sparse checkout

**Caught by CI, which is where it could only be caught.** `drift-loud.ts` and `verdict-drought.ts` run in the `drift (loud)` job, which uses a **sparse checkout listing individual files**. `src/Core.TypeScript/io/safe-io.ts` was not on that list, so both reporters died with `Cannot find module '../io/safe-io.ts'`.

A sparse checkout does not fail at *checkout* time when a file is missing — it fails at *run* time, in the one job whose entire purpose is reporting on other jobs. The lane that exists to make silence loud went silent for a reason that had nothing to do with drift.

Fixed by adding the path, and **verified by reconstructing the sparse checkout locally** — a directory holding exactly the six listed paths and nothing else — and running both reporters in it. Before: `Cannot find module`. After: both run and render.

Every other checkout that runs either reporter (`drift-sweep.yml`'s sweep job) is a full checkout and was unaffected; that was checked across every workflow in the repo, not assumed.

The comment above the step said the reporter "imports nothing but node built-ins", which is what made the sparse list look like an optimisation rather than a contract. It now says the list is load-bearing, that a missing entry surfaces at run time rather than checkout time, and that an in-repo import must be added there.
