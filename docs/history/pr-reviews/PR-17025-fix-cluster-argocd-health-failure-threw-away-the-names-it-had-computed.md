## Description

## The symptom

`live kind included Synced+Healthy proof` has failed on **all 12 of its most
recent runs, `main` included**, and every one reports the same sentence:

> one or more included dev ArgoCD Applications are not Synced/Healthy

It never says **which**. The names were computed, then dropped one step before
they were printed.

## The defect

The health-wait call site builds the failure with the names in hand:

```ts
detail: lastVerdicts.filter((verdict) => !verdict.ok)   // an ARRAY
```

That failure goes through `attachClusterDiagnostics` → `mergeArgoCdTimeoutDiagnostics`:

```ts
const existing = asRecord(failure.detail) ?? {};
return { ...failure, detail: { ...existing, diagnostics: dumps } };
```

and `asRecord` is `typeof value === "object" && value !== null && !Array.isArray(value)`.
**For an array it returns `null`**, `existing` becomes `{}`, and the verdict list
spreads into nothing. What survives is `detail.diagnostics` alone — ~10 KB of pod
dumps, warning events and CoreDNS config, with the one field that named the defect
deleted.

## Why it stood

The function has two call sites with two `detail` shapes. The **record**-shaped one
(`{stdout, stderr, childCount}`) merges correctly and is the only one with a test.
The **array**-shaped one had no test at all.

## The fix

One branch: when `detail` is an array, carry it as `unhealthy` alongside
`diagnostics`. Both call sites keep everything they had.

## Falsifier

`array-shaped detail keeps the failing Application names alongside the dumps`.

**Mutation-checked** — replacing the new branch with `{}` fails that test and only
that test (**97 pass / 1 fail**), so it is not vacuous. Whole file: **98 pass / 0 fail**.

## Scope — stated plainly

This is a **diagnosability fix and it does not turn the lane green.** The underlying
cluster failure is untouched. I am deliberately not guessing the cause from a dump
whose useful field was missing; the next red run produces the Application name, and
that name is what gets fixed.
