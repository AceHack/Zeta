## Description

## What

`tools/setup/install.sh` fetches **561 MB of `.deb` on every ubuntu job**. On 2026-08-25 the archive mirror delivered **~1.1 MB/s** against the ~14 MB/s the installer's **420s** apt budget was sized from — **~510s of download inside a 420s wall** — and **17 jobs died at exit 124 in the install step**, under six different red job names across four workflows.

This caches apt's archive directory, which the predecessor investigation named as *"the root fix, and the only one with negative CI cost"* and did not implement.

Predecessor: `docs/research/2026-08-25-one-apt-wall-budget-failure-wearing-six-job-names-and-why-more-retry-cannot-fix-it.md`
Design doc: `docs/research/2026-08-26-caching-var-cache-apt-archives-is-the-root-fix-for-the-apt-wall-budget-class.md`

## Why not the other two levers

| lever | why it is closed |
| --- | --- |
| more in-step retry | three attempts already share **one** 420s deadline. A fourth subdivides the same wall; measured, attempt 3 was already down to 45s. |
| a bigger budget | tightest **fitting** margin is **18 seconds** (`k8s-lane-partition.yml:plan`, 420+10+152=582 vs 600). Covering the cold path needs ~+180s → `timeout-minutes` edits across ~49 jobs, and `low-memory` is already 1001s vs 840s on a runner class capped at 900s. **No budget value fits that lane.** Not taken; arithmetic in §6. |
| **fetch the bytes once** | open. This is that. |

## Shape

- **`ZETA_APT_ARCHIVES_DIR`** in `linux.sh` relocates `Dir::Cache::archives`, prunes superseded `.deb`s with `autoclean`, and hands the tree back to the unprivileged user (apt creates `partial/` at 0700 root, which the cache save cannot tar). Unset — laptop, devcontainer — nothing changes.
- **`.github/actions/apt-archive-cache`** derives the key, restores, and exports `ZETA_APT_ARCHIVES_DIR` into `$GITHUB_ENV` — so **all 48 install steps are byte-identical**; adoption is one additive step per job.
- **`src/Core.TypeScript/ci/apt-archive-cache.ts`** refuses a Linux `install.sh` job with no restore step, one whose cache tier disagrees with its install tier, or one that restores *after* the fetch it serves.

## Cache key

```
apt-archives-v1-<suite>-<arch>-<effective-tier>-<sha256(manifests/apt ‖ host-tier.sh)>-<iso-week>
```

- **`suite`/`arch`** — `.deb`s are per-suite and per-arch; a noble archive must never reach a jammy job.
- **`effective-tier`** — the tier decides the package set (slim 149 pkg / 139.7 MiB vs standard 388 / 713.0 MiB), and it **normalises down** to the highest rank actually present in the manifest. There is no `tier=full` entry, so `full` and `standard` are one entry rather than two copies of the same 561 MB. Derived from the manifest at run time, so adding a `tier=full` entry separates them again on its own.
- **`iso-week`** — the rotation. A cache entry is immutable once written, so a deterministic key would freeze the archive at whatever versions existed the first time and decay silently. Weekly + a 3-rung `restore-keys` ladder gives the rolling shape; the widest rung means a one-line `manifests/apt` edit cannot cold-start 48 jobs at once.

## Correctness — measured against `ubuntu:24.04`, not assumed

- **A warm directory eliminates the fetch**: `Need to get 0 B/714 kB of archives.`
- **A stale version cannot be substituted.** A planted `jq_0.0.1-1_arm64.deb` and a wrong-arch file were left **untouched** while the resolved version installed from cache. apt asks for exactly one `name_version_arch` filename, and `apt-get update` still runs every time, so resolution is always from a fresh index. **This is the load-bearing property and it holds.**
- **And the half that came out other than expected:** apt does **not** re-hash a cached file — it accepts it on **filename and size**. A truncated `.deb` is re-downloaded; a **same-size** corruption reaches dpkg, whose decompressor checksum refuses it (`zstd error: Restored data doesn't match checksum`, rc=100). So the property is *"a poisoned cache cannot install **silently**"*, not *"apt validates the cache"*. The code comments in the first draft asserted the stronger claim and **the experiment corrected them**.
- **The containment is GitHub's branch scoping**, not apt: a cache entry is scoped to the branch that wrote it, so a pull request cannot write bytes that `main` or another PR will read. What a PR can poison is its own later runs, on a runner already executing that PR's code.

## The banner was wrong, and is fixed here

`linux.sh` said *"stalled archive mirror, not a package error"*. Measured, **bytes were flowing the whole time** — the word sent every reader at the wrong fix. It now measures the archive directory across each attempt and reports the observed rate, and says WEDGED only when the delta really is zero. Same correction to the `apt-get update` banner and to the final `✗`, which used to recommend raising the one knob that does not fit in CI.

The rerun sweeper is unaffected, deliberately: `APT_BUDGET_EXHAUSTED` matches the final `✗ apt-get install did not succeed within the …` sentence, which is byte-identical across this change.

## Falsifiers

`apt-archive-cache.test.ts` — 17 tests. Both adoption failures are invisible by construction (an absent step is green until the mirror is slow; a miskeyed tier gets a cache **hit** on a payload missing two thirds of what it needs), so the mutants are pinned: absent step, miskeyed tier, restore-after-install, commented-out step, and *"a matrix `runs-on` stays in scope"* — without which `gate.yml`'s `build-and-test`, the biggest apt consumer in the tree, would silently leave the audit's scope. Both audit and tests run in `ci-cache-paths-lint.yml`, whose subject already is actions/cache discipline.

**Two confounds, named.** (1) Runner variance exceeds some of these deltas — `main`'s own six samples for `manifests (offline)` span 110–244s; §7a of the doc is the measurement that does not depend on it. (2) This branch's *first* wave was doubly cold, because the existing `install-v2` key hashes `tools/setup/**` which this PR edits — that one-off disappears once this lands.

**And the number that matters is not in the table.** On a healthy mirror this saves tens of seconds. On a degraded one it is the difference between a job that runs and a job that exits 124 with its work never started — and `main`'s history for `helm-validate:manifests (offline)` contains exactly that inside the same six-run window sampled above: a **420s failure**, run 32850274047.

**Cache footprint, measured:** slim **37 MB** / standard **534 MB** = 571 MB per epoch, ~1.1 GB across two live epochs. Reported against its neighbours: the repo's total cache occupancy measures **14.47 GB across 30 entries** — already past the documented 10 GB, with four ~1.3 GB `install-*` entries above ours. Eviction pressure is real and pre-existing; auditing it is a stated follow-up, not something this PR claims to fix.

## Three defects this change's own falsifiers caught, worth listing

1. **apt does not re-hash a cached `.deb`.** The first draft's code comments said it verified size *and* SHA-256. The container experiment refuted it; the comments now state the weaker, true property and name dpkg's decompressor checksum as what actually refuses a tampered file.
2. **`"${arr[@]}"` on an empty array is an unbound variable under `set -u` in bash 3.2** — macOS `/bin/bash`, which is where `apt-phase-wall-budget.test.ts` executes `linux.sh`. That test caught it, four lines below the assertions that pin the banner text.
3. **`existsSync` gating `readFileSync` in the new test** is check-then-use (CWE-367); `lint-check-then-use-file-races.ts` refused it in the `cross-verify` floor. The read is now the existence assertion.
