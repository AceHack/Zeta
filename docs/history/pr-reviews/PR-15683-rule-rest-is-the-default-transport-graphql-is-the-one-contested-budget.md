## The transport half

`gh pr view|list|checks` and `gh run view` are **GraphQL**; `gh api repos/{owner}/{repo}/…` is **REST**; separate 5000/hour budgets and only GraphQL is contended here.

- **2026-08-14:** GraphQL **1147/5000** vs REST **33/5000**.
- **2026-08-25/26:** polling hit **0/5000 within a minute** of an hourly reset, twice.
- **The drain is observation, not action.** 7 lane runs and 11 PRs in the same hour ⇒ auto-merge arming cost at most **11 mutations of 5000, ~0.2%**. Any fix aimed at the write path is aimed at 0.2% of the problem.
- `enablePullRequestAutoMerge` is **GraphQL-only** and stays explicitly permitted. A rule that said "never GraphQL" would be false on first contact and then discarded wholesale.
- Trap, misdiagnosed three times that night: **`rate_limit` at 5000/5000 while calls are refused means a SECONDARY (burst) limit**, which those counters never reflect.

## The sharper half — and it is in the rule

From the runaway loop author's own post-mortem: the loop **did** have a `state=MERGED` stop condition, read via `gh pr view` — *the same transport it was saturating* — with `api-unavailable) : ;` as the failure branch.

1. **Probe the goal over a different transport than the one you are consuming.** A loop that saturates the channel it needs to see it is finished cannot terminate.
2. **A failed probe is `unknown`, never a negative result.** `catch → not-done` is an infinite loop; `catch → done` is a false success. `api-unavailable) : ;` is the vacuity class in shell.
3. **A retry loop stops when the GOAL is met, however it was met** — not when its own attempt succeeds. Those differ exactly when auto-merge, another agent, or repo automation completes the work, which here is routine.
