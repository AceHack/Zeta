## Description

Acts on the code-bound key access note (#10657). Builds the **manifest** half of Singularity's
answer without the **verified-kernel** half — the cheap, diffable, deniable half, and the one
that is close to what `ace` already produces (§7).

## What the manifest expresses

A self-declared `capabilities` list on an ace package: `<scheme>:<resource>`, closed scheme set
(`key file net exec env`), no wildcards, sorted and deduplicated so meaning and signed bytes stay
in bijection.

## What it deliberately does not express

- **Authorization.** A declaration is an upper bound a publisher placed on its own code — the
  wallet-owner-imposes-a-spend-ceiling shape from §6. It is `source`; only a key's **holder** may
  attach a grant. There is deliberately no grant type in this module, because a grant a third
  party could write is a forced-upgrade path wearing a maintenance hat.
- **Enforcement.** Nothing consults this at key-access time. That is an OS ACL, a keychain
  binding, or a TPM seal, each with prerequisites nobody has answered.
- **Runtime identity.** Everything is verified over bytes at rest.
- **A kind of entity.** There is no `holder:` / `kind:` / `species:` / `role:` scheme, so a
  capability *cannot* say "agents only" however it is spelled. This is the structural form of the
  `holderKind` removal in `frost-custody-contract.ts`. A denylist of species words in the resource
  segment was considered and **rejected**: `key:agent-otto` is a legitimate key name, so such a
  guard would fire on innocent names and miss a renamed one — it would guard spelling, not shape.

## No crypto was added, and that is the finding

`signing.ts` `canonicalManifestBytes` covers the whole manifest **minus its own `signature`**, so
`capabilities` is bound by the existing Ed25519 signature the moment the field exists. Confirmed
empirically *before* the module was written: bolt-on, edit, and strip all yield `bad-signature`.
This is the §5 seam paying off — the integration is a declaration plus a checker, not a signature
scheme, and no bridge to X.509/Authenticode was built (§5, policy bridge not crypto bridge).

## Install-time vs runtime — open question 4, resolved in the negative

**Ace's install-time verification cannot support a runtime capability claim, and the gap is not
closeable inside ace.** Exported as `INSTALL_TIME_VS_RUNTIME` so it is greppable rather than
folklore. Three independent reasons:

1. **Time-of-check vs time-of-use.** The store is ordinary files under the same user as every
   agent on the box. Verification at install does not survive to first use; re-verification at
   `ace verify` does not survive to the next microsecond.
2. **No process binding.** Ace has no notion of a running process, and a PID is not an identity
   anyway (`docs/writer-actor-routing-model.md`).
3. **The unmeasured interpreter.** Signing a TypeScript package says nothing about the runtime
   that executes it.

Ace can supply the **policy** an external enforcer names. It cannot be that enforcer. Closing this
needs macOS keychain ACL, Linux IMA/EVM, or a TPM PCR seal — deliberately not attempted here.

## The update case, designed in rather than bolted on

Code identity is `ace:<signer key_id>/<name>` — **invariant under version bump and content
change**. Binding to `content_hash` would orphan every declaration on every code change, forcing a
re-grant ceremony, and whoever performs that ceremony holds power over someone else's key.

So an agent editing and re-signing its **own** code keeps its identity and its capabilities with
no third party in the loop. A stranger re-signing the same package name gets a **different**
identity and inherits nothing — `describeUpdate` reports those capabilities as `orphaned` rather
than carrying them across, because a mechanism that carried them would *be* the forced-upgrade
path. Tested with the stranger's key **also trusted**: trust does not merge identities, which is
what keeps "trusted" from meaning "may impersonate". That is §6a's design test — *can any party
other than the key's holder cause that key to move?* — answered no, by construction.

## The declaration is read by something

`ace verify` **was a check that could not fail**: it confirmed a package was PRESENT and
re-verified nothing — not the signature, not the trust store, not the manifest bytes — so a
manifest edited on disk after install passed, in the file whose name promises it can fail. It now
re-verifies the signature, reports code identity + capabilities, and gained `--capability`
(repeatable) and `--require-signature`. `ace install` gained a capability-declaration gate before
extraction, so what installs and what verifies are the same set.

## Mutation results — 41 tests, each a mutant that must die

Every named mutant dies with its **specific** reason asserted, not a generic `ok === false`:

| mutant | outcome |
|---|---|
| unlisted capability claimed | `capabilityPermitted` false; `verify --capability` exit 1 |
| signature does not match manifest | `bad-signature`; `install` exit 1, nothing extracted |
| manifest changed after signing | `bad-signature` (add / edit / strip / version rollback) |
| capabilities bolted onto an unsigned-for manifest | `bad-signature` |
| signature lifted from a different manifest | `bad-signature` |
| signed by an untrusted key | `untrusted-key` |
| unsigned code declaring capabilities | `no-signature`, null identity, cannot satisfy `--capability` |
| signed but malformed declaration | `invalid-capabilities` — refuses, never degrades to empty |
| third party re-signs same name | different identity, capabilities `orphaned` |
| entity-kind scheme (`holder:agent`, …) | `unknown capability scheme` |
| wildcard (`key:*`, `key:frost/*`) | rejected by grammar; `install` exit 1 |
| unsorted / duplicate / over-cap list | rejected |
| prefix widening (`key:frost` ⇒ `key:frost/otto`) | not permitted |

**A refusal is structurally distinct from "authorized for nothing"** — if they were the same
value, a caller checking `capabilities.length === 0` would treat a forgery as well-behaved.

## Retracted

- **A capability-specific signature/binding scheme** — dropped once the probe showed the existing
  manifest signature already binds the field. It would have been redundant crypto.
- **A species-word denylist on resource names** — see above; a guard on spelling is a guard that
  cannot do its job.
- **Wildcards and capability hierarchy** — a grammar admitting `key:*` is a grammar that cannot
  deny. Explicit enumeration only.
- **The grant side** — out of scope by construction, not by time. Only a key's holder may write one.
