PR #10795 established a memory-integrity fault beneath every runtime on `AceHacks-Mac-Studio` and drew the consequence: *"treat locally-produced byte-locks from 08-08 onward as suspect."*

## The eight, and why they are not byte-locks

Byte-locks are the **best-covered** class in the repo — redundant by construction, which is the point of an N-oracle treaty. The exposed class is the one with **no** redundancy: generated source, emitted by one generator, consumed by one compiler, verified by nobody.

Six of the eight are the generated ZetaId bit-layout files. The sharpest two are `zeta_id.gen.go` and `bit_layout.gen.rs`, and the reason is measurable:

```
gate.yml:1744   cargo test --manifest-path src/Core.Rust.Observe/Cargo.toml   # 1 of 36 crates
gate.yml:1747   go test ./algebra/                                            # not the module root
```

Those codecs execute in **no CI job**. So a wrong constant in either produced no compile error, no test failure, and no oracle disagreement — because the oracle it would have disagreed with is a JSON file committed beside it. `cross-verify-all.ts` says the quiet part in its own header: *"It does NOT regenerate the F#/C#/Rust outputs … it asserts the committed outputs."*

The gap itself was **already written down**, in `tests/cross-verification/zeta-id/README.md`. What this adds is why it was sharper than it read.

## Three corrections to the brief that sent me

1. **The four IR primitives are not in the window.** `lcg32_glibc`, `lcg32_numerical_recipes`, `lcg64_mmix`, `murmur3_32_tail` were last touched **2026-06-21** — 48 days before it opens. They are a real *structural* exposure and not a *corruption-window* one; those are different sets. Sibling agent's files untouched.
2. **`db/shapes/golden/` is not in the window.** All 42 rendered goldens last written **2026-07-02**.
3. **The `.wasm` exposure is empty, by measurement.** 16 of 17 committed binaries predate the window; the 17th (`dla-canonical-zig.wasm`) agreed **9 of 9 substrates, byte-identical trajectories**, in CI run `31886039431`, with all 7 fault-injection negative controls passing.

And a **premise** corrected: *"a corrupted artifact fails loudly"* does not hold for `bytelock.yml`, which **exits 0 on divergence** by design. Detection without a gate is not the same as failing loudly, and the two-way REGENERATED/REFERENCE-ONLY split hides that fourth disposition.

## The window's sharpest commit, checked both ways

`cabe946d8` (2026-08-11, pushed **directly to main**) rewrote the layout YAML, all six generated sources, all seven oracle outputs and `vectors.yaml` in one commit, on the machine, in the window.

* **Reassuring, checked:** `push: main` triggers the gate; run `31488980802` ran 30 jobs green including `cross-verify`, `full-verify` and `build-and-test` on **five** OS legs.
* **Not reassuring:** on 2026-08-11 `compare.ts` **did not open `vectors.yaml`** — it compared the six outputs against each other. Pinning landed three days later in #10614. The gate that ran was weaker than the gate that exists now, in exactly the dimension that mattered.

Retroactively closed by measurement, not argument: `bun compare.ts` on current `main` reports **7 of 7 oracles, 16 of 16 vectors, pinned to `vectors.yaml`**.

## The remediation

`tests/cross-verification/zeta-id/gen-layout-drift.ts` compares every offset/width constant in all six generated lanes against `docs/zeta-id-v1-layout.yaml`, wired into `gate.yml`'s **blocking** `cross-verify` job — not `test (TS suite)`, which `gate.yml:1612` says by design "RUNS, DOES NOT BLOCK".

**Constants, not a byte diff of the regenerated file.** Regenerating in CI needs prettier + gofmt + cargo fmt + ruff on the runner, and then a formatter bump fails the check for a reason that is not drift. Measured: without `src/Core.Python/.venv/bin/ruff` the Python lane differs by exactly one quote character and nothing else.

**Anti-vacuity floor**, because this is the PR where that matters: a regex that matches nothing returns an empty set, and an empty set agrees with every file — the same shape as the `grep -q` that passed while the prover segfaulted. Each lane must yield **exactly 2 × 9** constants; short or empty is a hard failure whose message says the check *did not run*.

**Watched failing.** 13 mutants: wrong Go constant, wrong Rust constant, an unregenerated layout edit (all six lanes red at once), an emptied lane, a lane short by exactly one, a deleted lane, a zero-field layout, a deleted layout. Each asserts its own mutation landed before asserting the finding, because a `.replace()` that silently no-ops is how a mutation test becomes vacuous. End-to-end via the CLI on the real tree: wrong Go constant → **exit 1** naming `'personaoffset' = 52, docs/zeta-id-v1-layout.yaml says 51`; restored → **exit 0**.

* **No F# touched, so `dotnet build -c Release` was not run.** Stated rather than skipped silently.

## Limits, said plainly

* The re-derivations in §5b ran **on the suspect machine**. Bounding it: all 147 observed manifestations are *detected* integrity failures (145 process deaths, 2 code-signature kills) — the fault's observed signature is loud, with no recorded silent wrong answer in that population. That is evidence about the failure mode, not proof. **The local result is the finding; the CI step is the falsifier.**
* **Residual, named rather than closed** (§5c): `go-output.json` / `rust-output.json` are still never re-derived (staleness, not corruption, remains possible); `complexity-registry.gen.ts` is imported by nothing; `package-lock.json` is reproduced by no CI job but self-verifies via 376/376 SRI hashes; the 9 `registry/*` files are hand-authored declarations, so "regenerate and compare" does not apply.
* **Side observation, measured and not acted on:** `reindex-memory-md.ts --check` exits **2** on `origin/main` @ `e4481f19a` ("Index STALE"), and its workflow is path-triggered on `memory/**` only. Not this audit's subject; recorded because I ran the command and saw it.
* **One retry, recorded:** a per-file scan over 3,706 files hit my own 2-minute tool timeout (SIGTERM 143 — my cap, not the machine) and was replaced with a single `xargs -0 grep -l` pass. No `dotnet` or `bun` signal death occurred during this audit.
