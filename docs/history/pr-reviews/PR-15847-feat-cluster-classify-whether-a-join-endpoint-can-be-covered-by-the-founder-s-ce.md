## Description

§4.3 of the hardware-remainder doc calls this "a real question and a cheap one".
It is cheaper than expected, and the answer is worse than "IP might not work".

`zeta-install.sh:1983` validates the staged join endpoint with a SHAPE check and
nothing else:

    ^https://[A-Za-z0-9._:-]+$

That language is strictly broader than the set of endpoints the founder's
certificate covers, and the gap is silent. The founder covers exactly two
sources: `--tls-san=control-plane` (ONE literal name, set in `k3s-server.nix`),
and k3s' own defaults (127.0.0.1 / localhost / the node IP). So:

    https://control-plane:6443     covered-by-explicit-san   the designed path
    https://192.168.4.152:6443     covered-if-node-ip        probably; see below
    https://zeta-cp-1.local:6443   NOT COVERED               passes the regex

The third is not a corner case. It is the first thing an operator types who has
a hostname for the box, it is accepted, written to
`/etc/zeta/cluster-join-server-url`, evaluated into `serverAddr`, and fails at
the TLS handshake AFTER the disk has been partitioned.

And it fails confusingly, which is why the advice says so explicitly: **TLS
verifies the name presented, not the address reached.** A name that resolves
correctly to the founder still fails. `ping` works. `curl` does not.

WHAT THE CLASSIFIER REFUSES TO CLAIM. There is no `verified` verdict and no bare
`covered`, and a test asserts the vocabulary contains neither. It reads no
certificate and contacts nothing; it decides only what the STRING decides. An IP
literal is `covered-if-node-ip`, never `covered`, because k3s SANs the node IP it
SELECTED (`--node-ip`, else the default-route address) and on a multi-NIC box the
other interface's address is real, reachable, and not in the cert.

`localhost` / `127.0.0.1` gets its own verdict rather than being folded into
"fine": TLS would SUCCEED there, and the node would join ITSELF — a failure that
looks least like one.

A FINDING THE CLASSIFIER SURFACED ON ITS OWN. The installer's pattern has no `[`
and no `]`. The bracketed form is the only one that can carry an IPv6 host and a
port unambiguously (RFC 3986 §3.2.2), and the unbracketed form cannot carry a
port at all. So **an IPv6 join endpoint with a port is inexpressible through
`zeta-install.sh`**. Found by writing the test wrong — the first version asserted
brackets would classify as an IP literal, they came back `malformed`, and the
classifier was right. Recorded rather than patched away: "the installer cannot
express this" is a fact about the installer.

The installer's regex is read OUT OF the shell script by the test rather than
copied into a comment, so tightening it fails the drift guard and widening it
leaves the gap test standing. Neither can move silently.

19 pass, 0 fail. Mutants killed: SAN-as-substring 1, unknown-names-blessed 3,
IP-promoted-to-covered 2, loopback-branch-removed 1, shape-check-removed 3,
unbracketed-IPv6-mangled 2, empty-host-accepted 1, port-range-unchecked 1.

NOT WIRED into the installer. This is the decision layer; calling it from
`zeta-install.sh` means a bash/TS boundary on a script that is about to partition
a disk, and that is a separate decision with its own trade. What it does today is
make the gap statable and testable, and give an operator the three real fixes:
use `control-plane`, use the founder's IP, or add `--tls-san=<name>` on the
FOUNDER before flashing.
