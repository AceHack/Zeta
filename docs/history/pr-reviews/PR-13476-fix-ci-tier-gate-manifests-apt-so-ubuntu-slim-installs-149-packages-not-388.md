## Description

Closes the low-memory lane's budget defect (work-item `081M0K36K69087G0R003BYSCF8`) by not installing 573 MiB of packages the lane cannot use.

| whole job, same run | **637s of the 840s cap = 76%** |
| failing run 32537060851 | apt attempt 1 killed at its **237s** slice mid-`dpkg`; attempts 2 + 3 `rc=100` |

The work-item's "~420 seconds" is the **budget**, not a measurement — quoting a budget as a measurement is how an over-budget lane reads as merely slow. `linux.sh` sizes that 420s against a recorded **38.2s** apt phase on `ubuntu-24.04` ("~11x headroom"). On 1 vCPU the same phase is 148s, so the real headroom on this runner is **2.8x**. That is the defect, stated exactly.

## Cause

`manifests/apt` was installed in full on every host. Measured on `ubuntu:24.04` amd64, universe enabled, `--no-install-recommends`:

| set | packages | download |
|---|---|---|
| every row | 388 | **713.0 MiB** |
| slim rows only | 149 | **139.7 MiB** |

Concentrated in `agda` +242 MiB, `emscripten` +150, `r-base` +57, `llvm` +53, `pandoc` +26, `podman` +21. This lane runs `dotnet build` on one csproj.

## Fix — option 2, and it does not cost the parity the work-item worried about

`macos.sh` has gated `manifests/brew` on `tier=` since `081KTWQZY7F`. `linux.sh` never gated apt, and `manifests/apt` carried the debt in its own prose: *"The right fix is a tier= gate for apt, which does not exist yet -- filed as DEBT"*. That debt is paid here.

The work-item's objection to option 2 was that shrinking the lane's install *"mirrors gate.yml's sequence by design, so diverging costs the parity the lane exists to test."* It does not diverge: same `install.sh`, same code path, same mechanism the macOS leg already uses. The 13 rows tagged `tier=standard` mirror brew's `tier=standard` set exactly, plus the apt-only helper packages of those same tools. `low-memory.yml` already declared `ZETA_HOST_TIER: slim` — nothing was honouring it for apt.

**What it stops detecting**, recorded in `low-memory.yml` rather than left to be found later: the lane no longer proves the standard-tier packages install on a 1-vCPU / 5 GB host. Those packages are still installed and exercised on all 24 `ubuntu-24.04` gate jobs, so package coverage is unchanged; only that pairing is uncovered, and nothing claims it — brew has declared those tools out of scope for a slim host since `081KTWQZY7F`.

Options **1** (cache apt) and **3** (raise the cap) were not taken. (1) is still available and now cheaper to size; (3) hides the next regression, per the work-item.

## Second defect, found in the same log

The `DPKG RECOVERY` block added 2026-08-18 exists so a mid-`dpkg` kill does not cost all three attempts. **It could not work.** `timeout` signals `sudo apt-get`, not the `dpkg` apt-get forked, so the orphan keeps `/var/lib/dpkg/lock`:

```
23:37:09.80  attempt 1 hits its 237s slice, timeout fires
23:37:09.84  dpkg --configure -a -> "lock was locked by another process with pid 1072"
23:37:24.94  attempt 2 -> "Could not get lock ... held by 1072"  rc=100
23:37:24.98  dpkg --configure -a -> same lock error
23:37:55.01  attempt 3 -> "dpkg was interrupted, you must manually run ..."  rc=100
```

By `23:37:55` pid 1072 had exited and the lock was free — nothing tried again. The recovery now polls, inside the same 30s cap and the same shared deadline, so it can only spend time the budget already allowed the single call to spend. Only a *lock* error is retried; any other dpkg failure still breaks out immediately.
