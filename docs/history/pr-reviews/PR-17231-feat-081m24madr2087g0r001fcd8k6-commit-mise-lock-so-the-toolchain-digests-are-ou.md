## Description

## What

`mise.lock` and `mise.full.lock` are committed. Fourteen tool rows carry a `sha256:` per
platform in diffable, mergeable text, across eight platforms including `windows-arm64`, plus
36 lock-time attestation records.

**`locked = true` is deliberately NOT set, and that is a measured result rather than a
shortcut — see §1 and §3d.** The digests are enforced regardless: measured on both mise
versions the fleet runs, a checksum that does not match the bytes refuses with
`Checksum mismatch` and installs nothing.

## Why

There was no `mise.lock` in the tree and `locked = false`. So the `[2/3] checksum` step every
`mise install` prints was verified against a checksum **fetched from upstream at install time**.
Across the ~24 tool pins in `.mise.toml` + `.mise.full.toml`, **not one digest was one we owned.**

On 2026-09-10 GitHub's attestation service returned 503 (`trust-metadata-api service
unavailable`) and both ARM lanes on `main` died on `kubeconform@0.7.0` — `build-and-test
(windows-11-arm)` and `live kind ArgoCD health (ubuntu-24.04-arm)`. It survived five retries over
three minutes. **The `[2/3] checksum` step had already passed.** Integrity was established; the
install died on an *availability* check layered over it, because neither of the two trust sources
lived in this repository.

## The four things the work item required be MEASURED, and what came back

Every measurement below was run on the mise version `tools/setup/linux.sh` pins (**2026.6.12**),
not on the newer mise this laptop happens to carry.

### 1. Does `locked = true` fail closed on a platform not in the lockfile?

**Yes — and nothing is installed.** But locked mode is not what ships; §3d has the reason.
Host platform row deleted from the lockfile, `locked = true` active:

```
mise ERROR Failed to install aqua:koalaman/shellcheck@0.11.0:
  No lockfile URL found for shellcheck@0.11.0 on platform macos-arm64 (--locked mode)
rc=1        installs/ dir: does not exist
```

Three adjacent behaviours were measured because "fails closed" alone would have been a partial
answer:

| probe | result |
|---|---|
| tool declared in config, absent from the lockfile | `rc=1`, "`actionlint@1.7.12` is not in the lockfile" |
| digest present but wrong | `rc=1`, `Checksum mismatch`, expected + actual both printed |
| digest wrong, `locked = false` | **`rc=1` anyway** — a digest we own is enforced even unlocked |
| platform row **missing**, `locked = false` | **`rc=0`, installed, and mise WROTE the fetched digest back into `mise.lock`** |

That last row is the cost of shipping without locked mode, and it is the honest limit of this
PR: **a digest we HAVE is enforced; a digest we LACK is not demanded.** Coverage loss is
caught by the audit and by `verify-mise-lock.yml`, not by the install failing closed. The
workflow asserts that self-heal behaviour in both directions, so if mise ever changes it, the
claim stops being true loudly rather than quietly.

**The unfavourable half, and it is the important one.** `locked = true` does **not** fail closed
for backends that emit no artifact URL. Measured: with `locked = true` active, `rust`, `dotnet`,
`npm:markdownlint-cli2` and `pipx:yamllint` all **installed happily, unlocked, rc=0**. So the
setting's name promises more than it delivers, and the promise is scoped in `.mise.toml`, in the
audit's roster, and here.

### 3. Three-way parity (GOVERNANCE §24)

The lockfiles sit at the repo root and are read by mise itself, so `install.sh`, `install.ps1`
and the container images all honour them by construction — there is no third place to keep in
sync. What was actually measured, and what was not:

| surface | status |
|---|---|
| dev laptop (macOS, mise 2026.8.14) | **verified locally** — resolves the 2026.6.12 lockfile with zero warnings, installs `shellcheck` from the committed digest, and refuses a tampered one |
| CI runner (ubuntu-24.04, pinned mise 2026.6.12) | **verified in `verify-mise-lock.yml`** on this PR |
| devcontainer / container images | **verified in CI, and they are what found both real defects** — §3c and §3d were caught by `docker-ubuntu`, `docker-ubuntu-jammy`, `docker-nixos`, `docker-windows` and `ci-runtime`, each failing CLOSED with a precise diagnosis. Not verified by hand locally; the lanes on this PR are the measurement. |

**One cross-version fact worth naming:** the lockfile *format* is compatible both ways (a file
written by 2026.6.12 installs cleanly under 2026.8.14 and vice versa, neither rewriting it), but
`mise lock` **output** differs between those releases — header URL, `specifiers`, and which
x86-64 `-baseline` variants get emitted. macOS runs Homebrew's mise and has drifted to 2026.8.14
while Linux and Windows pin 2026.6.12, so the committed file and the drift check both use the
**pinned** version, and the refresh instructions say so.

### 3b. The attestation is now VERIFIED AT LOCK TIME and committed as text

Not planned — found by the first CI run, when the runner's re-lock produced
`provenance = "github-attestations"` rows for `python` that the local file lacked and the
byte-for-byte drift check called it drift. Measuring what that field does inverted the naive
reading:

```
with    provenance in the lockfile  ->  [2/3] checksum ... installed
without provenance in the lockfile  ->  [2/3] verify GitHub artifact attestations
                                        [2/3] checksum ... installed
```

**A `provenance` row is an attestation mise verified at LOCK time and recorded, and with it
present mise SKIPS the live attestation call at install time.** That is precisely the
*relocation* the work item said would become legitimate once a digest of ours existed — and it
arrives without disabling anything, because the check is still performed, once, by us, with its
result committed as diffable text.

So it is maximised rather than avoided. The lockfile is generated with a token, at the SAME attestation
settings the installers use (see 3c for why that constraint is not optional):
**36 attestation records** across `actionlint`, `golangci-lint` and `uv` that their
installs no longer have to fetch. Tools without a row still make the live call, exactly as
before — nothing is turned off.

**And the drift gate must not depend on that service.** A provenance row's presence depends on
GitHub's attestation API being reachable at lock time, so a byte-for-byte gate would let an
attestation outage redden the very check that exists so an attestation outage would stop
mattering. `--relock-diff` therefore fails on url / checksum / version / platform differences
and *reports* a provenance row that appears or disappears. A failed probe is `unknown`, never a
negative result.

### 3c. The container lanes caught the mistake that made — and they failed CLOSED

Precondition 3 did its job on the first push. Every containerised `install.sh` path went red
on **one** cause, and the diagnosis was better than most:

```
core:python@3.14.6: Lockfile requires github-attestations provenance for core:python@3.14.6
but the corresponding verification setting is disabled. This may indicate a downgrade attack.
Enable the setting or update the lockfile.
```

`tools/setup/common/mise.sh` exports `MISE_PYTHON_GITHUB_ATTESTATIONS=0` at install time; the
lockfile had been generated with `1`. **mise refuses to honour an attestation record it has
been told not to check** — correctly, because accepting one would let a lockfile assert a
verification that never ran. Two halves of one fact, in two files, with nothing holding them
together.

**Fixed by matching, not by weakening.** The lockfile is regenerated with `…=0`, so python
carries no provenance row and its install behaves exactly as it did before this PR. The 36
rows for `actionlint`, `golangci-lint` and `uv` stay — those are governed by the still-enabled
global `github_attestations = true` and installed cleanly on every runner. Turning python's
setting on and re-locking *with* provenance is a real improvement and a follow-up that must
move both halves in one commit; this PR does not make it.

**And it is now a check.** `checkProvenanceMatchesInstallSettings()` derives the coupling from
`mise.sh`'s own export line rather than restating it. It passes once `mise.sh` stops disabling
the setting, so it guards against doing half the follow-up without blocking the follow-up.

Proved both ways locally on the real python install path, not only in fixtures:

| state | result |
|---|---|
| provenance row present, setting `0` | `rc=1`, the CI error verbatim, nothing installed |
| the shipped lockfile, setting `0` | `rc=0`, `[1/3] checksum … installed`, no attestation call |

### 3d. THE FINDING THAT CHANGED THE DESIGN — no lockfile satisfies both mise versions

Once §3c was fixed and installs got further, `docker-nixos-install-sh-test`,
`docker-windows-install-ps1-test` and `macos-install-sh-test` produced a second, different
failure:

```
node@24: node@24 is not in the lockfile
npm:markdownlint-cli2@0.23.2: npm:markdownlint-cli2@0.23.2 is not in the lockfile
```

Reproduced locally on **both** mise versions the fleet actually runs, against this repo's own
files:

| lockfile written by | mise 2026.6.12 resolves | mise 2026.8.14 resolves |
|---|---|---|
| **2026.6.12** | all 25 tools | **FAILS** `node@24`, `npm:markdownlint-cli2` |
| **2026.8.14** | **FAILS** `node@24`, `npm:…` | all 25 tools |

2026.8.14 writes and matches a `specifiers = ["24"]` field; 2026.6.12 does not write it and
matches by version prefix. Neither can read the other's answer for a **fuzzy** pin (`node`,
`bun`, `java`) or an `npm:` entry, and `mise install` then refuses and installs nothing.

**Exact pins are unaffected — which is why the two-tool cross-version smoke test I ran before
shipping passed and hid this.** That test was too small, and it was recorded as evidence of
compatibility when it was evidence about exact pins only. Recording that here because the
under-powered check is the more useful finding of the two.

**And the fleet runs both versions, on the record:**

| installer | mise |
|---|---|
| `tools/setup/linux.sh` | `MISE_PIN_VERSION="2026.6.12"` — exact |
| `tools/setup/install.ps1` | `$MisePinVersion = '2026.6.12'` — exact |
| `tools/setup/macos.sh` | `MISE_MIN_VERSION="2026.6.12"` — a **floor**: *"macOS installs mise via Homebrew, whose formula advances in place; accept newer versions"* |

That divergence is pre-existing and deliberate. `locked = true` would convert it from a
documented difference into a **fleet-wide install failure on whichever platform did not
generate the file**.

**So locked mode is off, and with it off both versions are clean** — measured: zero unresolved
tools on either, installs take the committed digest, a tampered digest still refuses.

**The exemption cannot become permanent.** `checkLockedModeSafety()` is bidirectional: it
refuses `locked = true` while the three installers disagree, and **REQUIRES** `locked = true`
the moment they agree, naming the re-lock. Converging the mise versions is the work that
unlocks locked mode, and the check will ask for it.

### 4. The refresh path, and the check that notices drift

Following the `verify-rustup-pin.yml` / `refresh-rustup-pin.ts --check` shape rather than
inventing one.

**Refresh:**

```
export MISE_GITHUB_TOKEN=$(gh auth token)   # anonymous release metadata is 60/hr; a run this size exhausts it
export MISE_PYTHON_GITHUB_ATTESTATIONS=0    # MUST equal what mise.sh exports at install time (see 3c)
MISE_LOCKED=0 mise lock
MISE_LOCKED=0 mise lock --platform windows-arm64
MISE_LOCKED=0 mise lock      # again: the first pass discovers the x86-64 baseline variants
```

Two properties of that recipe are measured, not assumed:

- **`MISE_LOCKED=0` is load-bearing.** With `locked = true` active, `mise lock` cannot resolve a
  version that is not already in the lockfile and **prunes the old entry instead** — observed
  emptying a lockfile to zero tools while exiting 0.
- **`mise lock` is not idempotent on the first run.** The second pass adds `-baseline` platform
  rows the first pass did not know to ask for. The committed files are at the **fixed point**:
  a further re-lock is byte-for-byte a no-op, which is what makes the drift check well-defined.

**Two checks, split by whether they need the network:**

- `src/Core.TypeScript/hygiene/audit-mise-lock-coverage.ts` — offline, on the `cross-verify`
  floor, so it cannot redden a PR because a release host is down. Refuses: a config pin that
  moved without a re-lock, a lost platform, a missing `locked = true`, and an exemption roster
  entry that has gone stale *in either direction* (a roster tool nothing declares, and a roster
  tool that has since become lockable). The exemption set can shrink; it cannot grow without a
  diff here.
- `.github/workflows/verify-mise-lock.yml` — networked, on touch **and weekly**. A committed
  digest goes stale silently: it is only wrong once upstream changes what it serves, and no PR
  diff can notice that, so something has to ask when nobody edited anything.

- **One falsifier caught its own author.** The self-heal step asserted the writeback with

  successful self-heal restores exactly that file, so the assertion reported "no writeback"
  precisely when the writeback worked: a check that reddens when the thing it tests succeeds.
  Reproduced three ways locally (targeted install, full install, both tools named) to confirm
  the behaviour was right and the measurement wrong. It now diffs against a snapshot of the
  stripped file, and keeps the HEAD comparison as a *second* assertion — the refilled row must
  come back byte-identical to the committed digest, which would catch an upstream serving
  different bytes under the same URL. Generalises: **a `git diff` against HEAD cannot observe
  any event whose effect is to restore HEAD.**
- **`verify-mise-lock.yml` runs three live refusals on a real runner:** a re-lock on the pinned
  mise must reproduce the committed file byte for byte; a tampered digest must be rejected *with
  `Checksum mismatch` specifically*, not merely fail; a removed platform row must install
  nothing; and a final step asserts the installs did not rewrite the lockfile.
- Locally, on this laptop, against the **real** committed lockfile: tamper → `rc=1` with
  `Checksum mismatch`; drop the host platform row → `rc=1` with `No lockfile URL found` and no
  `installs/` directory; restore → installs from the committed digest and the tree stays clean.

## What this PR deliberately does NOT do

**It does not disable `github_attestations`.** No setting is changed. What §3b does instead is
*perform* the attestation at lock time for the tools that support it and commit the result, so
those installs stop making the call — the relocation, arrived at by recording more rather than
checking less. The tools with no provenance row still make the live call exactly as they did
yesterday. Turning the setting off remains a separate change with its own argument, and this PR
does not make it.

**It does not extend any retry budget.** More retry was not the answer and none was added.

**It does not narrow `install.ps1:415`'s Windows `full` default.** That is a behavioural change
to tier selection and already has its own row.
