## Description

## What this is

The task was "make the self-hosted runner scale set actually register a runner."
It cannot be done from here, and the reason it cannot is more useful than the fix
would have been. What ships instead is the **observer that was missing** — plus
two corrections, one of which invalidates the check the task asked for.

## Ground truth (measured 2026-08-26)

**The cluster is unreachable.** Both kube contexts refuse connection
(`kind-zeta-ci-podman`, `kind-zeta-local-included`, `rc=1` each), and there is no
container runtime running. So no pod state, no ArgoCD Application health, no
events. Per the brief, that is a stop on the deployment fix — and everything
below is deliberately cluster-free.

**The runner has never registered, but not for the cited reason.** Three
independent blockers, and the PVC is the least binding of them:

1. **No reconciled cluster.** `applications/vault/TOPOLOGY.md` is categorical:
   *"Nothing has been applied to any cluster."* NixOS did provision four
   physical nodes in June 2026 (real MACs, kernel versions, disk geometry in
   `maintainers/*/cluster-nodes/`); the k8s layer above them never came up.
2. **No credential.** `githubConfigSecret: arc-github-app` is materialised by
   external-secrets from a Vault that has never been initialised. Naming it and
   stopping, per the brief — it is not one this repo can mint.
3. **The PVC nothing applies** — confirmed, below.

CI cannot cover it either: `argocd-health-test.ts` excludes `arc-runner-set`
from the kind lane for two independently sufficient reasons (no GitHub App
credential to bind; `ReadWriteMany` unservable by `rancher.io/local-path`).

## Correction 1 — the runners API cannot see this runner set

This is the finding that outlives the bug.

`gh api orgs/Lucent-Financial-Group/actions/runners` returns `total_count: 0`,
and **that zero is not evidence of anything.** ARC v2 (`gha-runner-scale-set` /
`AutoscalingRunnerSet`) runners are **invisible to that endpoint** — it returns
traditional self-hosted runners only. A perfectly healthy scale set reads
`total_count: 0` there too.

- `GET /orgs/Lucent-Financial-Group/actions/runner-scale-sets` → **404** (measured).
- `actions/actions-runner-controller#2990` is the standing request for such an
  endpoint; scale sets appear in the settings UI with no REST equivalent.
- The offered control does not rescue it: `runner-groups` returning
  `total_count: 2` proves the **token** works, not that the **endpoint** can see
  scale sets. Both groups report `runners: 0` for the same reason.

**Consequence: the check the brief asked for cannot be built on that endpoint.**
It would be red against a working runner and could never go green — a result
carrying no information about its subject, which is the vacuity class inverted.
So it is not added. A real registration monitor has to read the listener
in-cluster, which needs the cluster that does not yet exist.

(The conclusion "no runner has ever registered" survives — established by the
three blockers, not by that API call.)

## Correction 2 — the PVC is latent, not live

The work-item says the missing PVC *"is not a future risk; it is the current
state whenever the runner set is synced."* The conditional is right, the framing
is wrong: **the runner set has never been synced anywhere**, so the missing PVC
has never blocked a pod. It is a real blocker for the day a cluster exists — not
the current cause.

## Proven it can fail

`0 drift` with it. 27 tests, including synthetic red cases for the arc shape
(supporting manifest beside a remote-chart Application) and the ddns shape
(directory with no Application).

**Mutation-checked, and one mutant survived** — worth reading:

| mutant | result |
|---|---|
| `sourceReconciles` ≡ true | killed (5 fail) |
| include glob ignored | killed (5 fail) |
| chart sources admitted | **SURVIVED — 25/25 green** |

The chart mutant is exactly the "a test passes because an EARLIER guard fired"
failure: a remote-chart source carries no `path`, so the empty-path skip fired
before the chart skip and the assertion passed for the wrong reason — while
deleting the line that makes the arc bug detectable. Killed by asserting the
unit directly against the live `arc-runner-set` manifest. It now fails (1 fail).

The empty-include inversion is also pinned: an **absent** `directory.include` is
no filter (applies everything), while an empty include glob on a root matches
nothing. Same empty string, opposite meaning; collapsing them would report every
supporting manifest in the tree as an orphan.
