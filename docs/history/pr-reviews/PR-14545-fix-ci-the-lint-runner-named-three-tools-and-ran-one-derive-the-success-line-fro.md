## Description

## The false statement

`src/Core.TypeScript/lint/lint-typescript.ts` printed this on **every green run**:

```text
✓ TypeScript, Prettier, and style checks passed successfully!
```

while `STEPS` held exactly one entry — `tsc`. Prettier and stylelint are not invoked in that job, or
anywhere reachable from it. Two of the three checks it announced as passed had never executed. The
header said the same thing, describing the file as orchestrating "tsc, eslint, prettier, stylelint".

**This is worse than the missing invocation underneath it.** A gap is visible to anyone reading the
workflow. A runner that *states two checks passed* defeats the reader at exactly the surface — the CI
log — they went to in order to confirm what ran. It has already propagated: the string appears in
~30 archived PR-review documents, quoted as evidence of a clean run.

This PR does the one piece of workitem 081M0RBXF6J087G0R0023EX9X2 that is decoupled from every open
decision in it, and **nothing else**.

## Fixed so it cannot drift back

A corrected string is one edit away from regressing, so the line is **derived from `STEPS`** rather
than rewritten:

- `successMessage(STEPS)` — the message is a function of what ran. Today: `✓ 1 check passed: tsc`.
  A step added to `STEPS` appears for free; a step removed cannot leave its name behind.
- `Step.tool` is the only channel a tool name may reach the message through, and a test asserts each
  step's `cmd` actually contains its declared `tool` — so a step cannot declare `eslint` and shell out
  to something else, putting a true-looking name in a false message.
- **Empty `STEPS` now fails.** Commenting the last step out would previously have exited 0 having
  checked nothing — the same defect one step further along.
- The header states what runs, and names eslint / prettier / stylelint explicitly as **not invoked**,
  with a pointer to the workitem, so the next reader does not have to rediscover it.
- `gate.yml`: the step named *"Run TypeScript Lint Script"*, commented *"Type check and lint checks"*,
  is now *"Run TypeScript type check (tsc --noEmit, via the orchestrator)"*. A step name is read as a
  claim about what ran. **The job's `name: lint (TS)` is a required status check and is untouched.**

## Deliberately NOT in this PR

- **eslint / prettier / stylelint are not wired in.** Measured: `bunx eslint src/Core.TypeScript`
  alone is 14,218 errors — one directory. Turning it on would redden `main` across five figures.
- **No config deleted, no dependency dropped.** `eslint.config.ts` encodes real standards and real
  findings.
- **No ignore entry, disable or override added.** Widening a check to make it pass would be
  self-refuting on a check whose defect is that it never ran.
- **The profile-boundary question is left alone.** Two positions are recorded in the workitem
  (shadow vs Lumen); it is the maintainer's call.
- **`package.json` untouched.** `lint:typescript` names no *tool* — it is the entry point's name in
  the `lint (F#) / (C#) / (TS)` family, so it asserts nothing false. Renaming it would be churn across
  ~20 referencing docs for no gain in honesty.

The workitem is updated with which half closed and which four items remain open. One narrow-path slice
already exists independently: `lint (twitch-ai app)` does run `bunx eslint src/apps/twitch-ai/src` — so
eslint is invoked *somewhere* in CI, just not by the job whose step name claimed it.
