## 1. The git operation and its stderr

From the job log, not from reading the source:

```
flush-via-staging: push to heartbeat/red-state failed: To https://github.com/Lucent-Financial-Group/Zeta
 ! [rejected]            HEAD -> heartbeat/red-state (stale info)
error: failed to push some refs to 'https://github.com/Lucent-Financial-Group/Zeta'
```

`git push --force-with-lease` with no `=<expect>` compares against `refs/remotes/origin/<ref>`. When that ref is **absent**, git does not treat it as "no expectation" — it rejects with `(stale info)`, the same words it uses for a real lease violation. The lease was never violated; it was **unreadable**.

The tracking ref is absent by construction: this workflow pins `actions/checkout` with **no `fetch-depth`**, so the runner clones at depth 1. `prepare` fetches only the **first** candidate that exists and then `break`s — and the buffer always exists, so the **active** ref is never fetched. The log shows exactly that asymmetry: in the same run, seconds apart, the buffer push (fetched) succeeded and the active push (not fetched) was rejected.

> This also falsifies the prep-phase hypothesis in the brief. The failure is in the **flush** phase, at the `activeRef` push. `prepare` completed fine. The token-role story in the step comments was indeed the wrong place to look — but so was the git prep.

A comment in `prepare` asserting `fetch-depth: 0` "in the calling workflows" is false for this one. Corrected rather than left to mislead again.

## 2. What changed on 2026-08-25 — a ref-state transition, not a commit

Nothing in `flush-via-staging.ts` or `proof-closure-drift.yml` changed between the last success and the first failure. **PR #12321 merged at 2026-08-25T03:26:23Z**, squarely between them.

While a flush PR is open, `chooseFlushRoute` returns `buffer` and `flush` returns **before reaching the active push at all**. The bug was unreachable for as long as the lane stayed backpressured. #12321 merged, the next run took the publish path, and every run since has failed identically.

The commit at **15:09:57Z** (`#15351`, the credential-chain fix) looks like a suspect and arrives **nine hours after the streak began**. It cannot be the cause.

## The fix

Name the expectation instead of relying on a ref nobody fetched — **without weakening it**:

- `<ref>:<sha>` is still a compare-and-swap. A concurrent writer that moves the ref is **still refused**.
- `<ref>:` (empty expect) asserts "must not already exist" — correct for a lane ref never published.
- Tips are observed at **routing time**, not push time, so the CAS spans the whole decision rather than the microseconds around the push. Reading them at the push site would have made the new guard *weaker* than the bare form it replaces.
- An unreadable remote **fails closed**: a lease that cannot be computed must not silently become a push with no lease.
- Degrading to a plain `--force` would also have made the symptom vanish, and would have discarded the protection that stops this lane clobbering a PR head mid-gate. Deliberately not done.

**Exit-code vocabulary unchanged** — `0` / `2` / `3` mean exactly what they meant.

## Legibility

All ten failures annotated only `Process completed with exit code 3`. `3` is a **class** ("a git operation failed") and names no instance; the stderr naming the command was in the log the whole time.

- the script now emits `::error title=...` carrying the **exact git command**
- the workflow grows a toolchain-free `if: failure()` step in the shape `build-and-test` took in **#15692** — `echo` only, no `shell:` key, no installed program, so it still reports when the failure **is** the toolchain

## The wider question — they are NOT coupled

Independently measured, and the answer is no. This lane's cause is a ref-state transition at 2026-08-25T03:26:23Z specific to `heartbeat/red-state`. The `observe` lane has been red since at least 2026-08-23, **before** this streak began — a cause that starts later cannot explain a failure that started earlier. The two frozen heartbeat PRs are merge conflicts, a different mechanism again. No shared root cause; reporting that rather than manufacturing one.

## The finding that outranks the fix

**A scheduled lane that fails silently for two days is a monitoring gap, not just a bug.** Nothing surfaced this until a human read a check name.

And the specific shape here is circular: `collect-red-state.ts` **already** reports failing runs on `main`, so this lane's own failures were inside its remit — but its liveness depends on the flush lane that broke. It froze at its last good value and kept rendering `findings: 0`.

The cheap existing surface is already 90% built: `generatedAtIso` is written by the collector and rendered by `demo/red/index.html`, and **nothing asserts it is recent**. One freshness assertion would have made a two-day freeze visible immediately. A frozen dashboard is otherwise indistinguishable from a healthy one — the same class as a check that never ran looking like one that passed.

Deliberately **not** bundled here; it is a separate change and should be routed as one.
