## Description

The mutation runner (#9900) was built, merged, and **invoked nowhere**. A tool only I run by hand is the tier-4 pattern it was written to replace.

## Now the society's standing job

One mutant per agent per tick. Selection is deterministic from `(agent, tick)`, so three agents cover three different files having exchanged **no messages**. Verified on a real 175-commit window:

| agent | mutation | target |
|---|---|---|
| alexa | `eq-to-neq` | `installer/credential-binding-*` |
| otto | `gte-to-gt` | `tools/setup/persona-keys/machine.ts` |
| soraya | `and-to-or` | `browser-node/browser-node.ts` |

**Drift report, never a gate** — exit 3 is swallowed so a finding can't fail the tick. This bounds *detection latency*; it doesn't block.

## And the bug it shipped with — the exact defect it exists to find

The default was `--since=24h`. **That is not valid git approxidate.** Git doesn't error; it silently matches zero commits:

```
--since="24h"           ->    0 commits
--since="24 hours ago"  ->  175 commits
```

Same repo, same instant. The runner would have reported *"nothing to do"* **every tick forever**, looking perfectly healthy. A mutation runner with a silent no-op inside it.

Fixed twice, because the date alone leaves the trap:

1. default is now `"24 hours ago"`
2. **zero files in the window is a `::warning::` and a non-zero exit** — never a cheerful no-op. Zero commits is almost always a bad date spec, not a quiet repo. Zero *pairs* among real commits stays informational; that one is legitimately quiet.

The second fix is the general lesson restated: **distinguish "nothing happened" from "I cannot see."** Alexa's monitor gets this right (live / offline / ledger-empty are three states); the healer reporting `all clean` while crashing did not.
