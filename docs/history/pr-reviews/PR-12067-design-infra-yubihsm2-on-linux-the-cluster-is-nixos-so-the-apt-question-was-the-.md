## Description

## What

Aaron installed the YubiHSM2 SDK on macOS and flagged the gap: *"we are going to need to have this available on our Linux distributions."* Verified — `yubihsm` appears nowhere in `tools/setup/linux.sh` or `.github/workflows/build-ai-cluster-iso.yml`. A freshly-flashed cluster node has no route to an attached YubiHSM.

**Design only.** No workflow, installer, or NixOS module changed. **Q8 is answered** (measured, below); Q1–Q7 remain open, plus a new Q9 the measurement raised.

## The finding that reframed the task

**Our cluster nodes are NixOS, not Debian/Ubuntu** — so the apt-vs-`.deb`-vs-source question had no correct answer among its options. Checked against the exact revision the ISO builds from (`flake.lock` → nixpkgs `b77b3de8`):

| package | in pinned nixpkgs | version |
|---|---|---|
| `yubihsm-connector` | yes | 3.0.7 |
| `yubihsm-shell` | yes | 2.7.3 |
| `yubihsm-setup` | yes | — |

No third-party apt source, no vendored `.deb`. The supply-chain posture is already the strongest option available: flake-locked, hash-pinned, source-built from a revision we trust for the whole node OS. **The trade, stated rather than assumed:** we take Yubico's *source* plus a nixpkgs recipe instead of Yubico's *compiled artifact*.

What nixpkgs does **not** ship is the operational glue. `yubihsm-connector` is a bare `buildGoModule`; Yubico keeps the udev rule and systemd unit in a `deb/` directory the Nix build never installs. **There is no `services.yubihsm-connector` NixOS module** — confirmed against a full tree listing.

## Node vs laptop vs runner

| piece | node | laptop | CI runner |
|---|---|---|---|
| `yubihsm-connector` (daemon) | **required** | if device attached | **no** |
| `yubihsm_pkcs11.so` | **required** | if device attached | **no** |
| `yubihsm-shell` (CLI) | diagnostic only | yes | **no** |
| `yubihsm-setup` (**reset tool**) | **no** | Aaron's laptop only | **no** |

`yubihsm-setup` is excluded from nodes deliberately: a node *uses* a key, it never *re-keys* the device. Shipping the reset tool to every machine holding key material widens a node compromise from "can sign while I hold the box" to "can wipe the box."

## udev: required, and the constant is verified

`SUBSYSTEM=="usb", ATTRS{idVendor}=="1050", ATTRS{idProduct}=="0030", OWNER="yubihsm-connector"` — read from Yubico's own shipped `deb/70-yubihsm-connector.rules` at tag `3.0.7`, not inferred. Upstream's unit runs as a dedicated non-root user with `ProtectSystem=full`, and the rule is what hands that user the device. So the rule is not just a permissions fix: **it is the mechanism that keeps the daemon unprivileged.**

## What it costs the install path

**Nothing recurring, because the CI runner gets none of it.**

- `install-v2` caches only `$HOME` paths — nothing apt writes to `/usr` is cached by anything. A `manifests/apt` entry is therefore re-installed on **24 gate jobs, every run, forever**.
- And `linux.sh` skips apt on NixOS (line 49), so that entry would reach **zero cluster nodes**. Maximum recurring cost on machines that will never see an HSM; zero effect on the machines that will. It is exactly where the naive fix would have gone.
- The `install-v2` key hashes `tools/setup/**`, so **any** file there rotates the key for 19 consumers at once — against a cache already at 200% of its 10 GiB limit.

I did not touch `tools/setup/linux.sh`. Its 610 MB unconditional `PKGS` and unbounded `apt-get update` are real, but enlarging that surface to carry an HSM driver would have made tonight's worst pathology worse.

**This PR's own cost:** the workitem file flips `code=true`, so it pays one full matrix. Stated rather than hidden.

## Q8: answered, measured

Run on Aaron's Mac with the device attached, using #12042's `probeYubiHsm2Pkcs11`:

```
yubihsm_pkcs11 module found: true   /usr/local/lib/pkcs11/yubihsm_pkcs11.dylib
```

The macOS `.pkg` writes the **third entry** on the probe's darwin list, and that entry is correct. The darwin *module* leg is now verified against a real install rather than assumed.

## The answer came with a bigger finding (§11)

`probeYubiHsm2` — **device** detection — returned `false` **with the device physically attached**. `system_profiler SPUSBDataType` emitted zero lines, and the darwin branch is `try { ...includes(MARKER) } catch { return false }`, so *no device*, *enumerator returned nothing*, and *enumerator failed* are one value.

**I checked the Linux branch rather than assuming sysfs was safer. It is the same shape:** a `readDir("/sys/bus/usb/devices")` throw — no sysfs, permission denied, a container without the tree — returns `false` identically to "no device". sysfs lowers the probability and does nothing to the structure.

The remedy already exists *in that same file, with a name*: `probeTpm2` was refactored for exactly this defect and answers a five-way `Tpm2State` (`present`/`absent`/`unreadable`/`unavailable`/`indeterminate`). `probeYubiHsm2` is still a boolean.

**Why this is mine and not only the probe's:** my node design had assumed "device present" was a solved input. On headless metal nobody can see whether the HSM is seated, so a provisioning fault must not be able to impersonate an absent device.

**The mechanism is already inside the software we are installing.** The connector's `/connector/status` (`api.go` @ 3.0.7) emits `status=OK|NO_DEVICE`, and `usbCheck` calls `usbopen` and reads the device serial — so it **actually opens the device** and is permission-sensitive. Crossed with the unprivileged sysfs read:

| sysfs | `/connector/status` | node state |
|---|---|---|
| found | `OK` | healthy |
| found | `NO_DEVICE` | **udev rule missing or not applied** |
| found | unreachable | **connector unit down** |
| absent | `NO_DEVICE` | genuinely no HSM seated |
| unreadable | any | **inconclusive — the check could not run** |

Rows 2 and 3 are the ones a boolean cannot express, and they are exactly "correctly cabled, provisioning silently failed" — which would otherwise surface mid-ceremony instead of at provisioning time. Every row needs **no session, no PIN, no credential**.

New **Q9** asks whether that ships as a boot-time readiness unit. My recommendation is yes: no CI minutes, and it converts the likeliest provisioning failure here from silent into named.

The probe fix itself is the probe author's, on #12042. Read, not edited.

## A defect in #12042's Linux paths (§5, unchanged)

On NixOS the module resolves to `/run/current-system/sw/lib/pkcs11/yubihsm_pkcs11.so` (`/lib` is in the default `environment.pathsToLink`, verified). That matches **none** of the three Linux paths — so a **correctly provisioned** node would report the module absent. **Not a request to loosen the probe:** no wildcard, no `find`, no fallback. The fix is a fourth *exact* path, because NixOS is genuinely a fourth packaging convention.

## Also worth its own row

`from-deb` runs `dpkg -i` on a bare URL with **no checksum and no signature**, while its sibling `from-url` refuses any row without `sha256=`. It also cannot install a library-only package at all — its idempotence check is binary-only.
