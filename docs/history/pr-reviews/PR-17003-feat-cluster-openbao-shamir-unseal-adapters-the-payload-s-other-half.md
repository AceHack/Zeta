## Description

`vault-unsealer.ts` says of itself that it is *"the payload that commit will call"* — a pure decision loop, no CLI, and an `UnsealHttp` type that deliberately has **no init method** (*"a client that can init is a client this module must not be handed; the type is the gate"*). It has had **zero consumers** since it landed. This is the adapters and entrypoint, and nothing else — it adds no decision of its own.

## What it cannot do, by construction

The HTTP client exposes exactly `health` and `putUnseal` — asserted at runtime as well as in the type — so no call site can reach `/v1/sys/init` even by mistake. On a fresh cluster the loop classifies `not-initialized` and returns `refuse-init` forever. That's correct: an uninitialised store needs a ceremony, and a sidecar that could perform one would be a sidecar that could mint and hold root material next to the thing it guards.

## Unreachable is not sealed

A connection refusal returns status 0 → `miss`. Reading it as `sealed` would make the loop fetch shares and spend unseal attempts against a listener that isn't there — share material on the wire for no reason.

**Mutation-checked:** making the catch return `{status: 503, sealed: true}` turns the suite red (8 pass / 1 fail); restored, 9 pass / 0 fail.

## Where shares come from

`MENO.md:39-41` — *"Shamir shares / HSM authkey references. USB / Keychain / k8s Secret are caches"*, and *"Shamir N-of-M on kind/CI until an emulator job inits without it. Threshold 1 is coercion (S=4)."*

So a mounted Secret is a sanctioned **cache** for the kind path, not the custody model. The fetcher re-reads the mount on **every** sealed tick because the port's contract is *"never cached across ticks"* — a rotated Secret takes effect next tick rather than living in this process until restart. Threshold below 2 is refused at the entrypoint as well as in the payload, since a sidecar is exactly where someone would try to lower it.

**`ephemeral-vault-init.ts` is untouched.** It holds shares in memory on purpose, and its header says a module that grows a way to persist material *"must be deleted, not amended."*

## What is deliberately NOT here

MENO item 7 asks for the `extraContainers` valuesObject in the **same commit**. It isn't, because I could not name an image that can actually run this: `zeta-ci-runtime` carries bun but is a *toolchain* image and does not carry the repo, so the script has no path inside it.

Writing a container spec against an image I can't prove pulls and runs would be shipping the shape of a sidecar without the sidecar — the exact failure this repo keeps naming. **The remaining gap is packaging, not logic**, and it's one decision wide: mount the script, add it to an image, or point at a different one.

Also not here: the `TOPOLOGY.md` §5 recast, which MENO ties to the extraContainer rather than to the adapters.
