## Description


`rerun-cancelled-gate` went red on `main` at 2026-08-26T08:06. Nothing was broken.
`api()` in rerun-cancelled-gate-run-cli.ts threw on any non-2xx, so the two
refusals GitHub issues in normal operation -- "This workflow run cannot be
retried" (CodeQL default-setup runs carry `event: dynamic`; the Actions API
declines `rerun-failed-jobs` on them) and "This workflow is already running" (a
run with jobs still in flight) -- presented as crashes. A tool whose entire job
is re-running cancelled gate runs meets both constantly.

The log made it undiagnosable: the throw was a bare `Error` naming the status but
not the API's own sentence, and the workflow surfaced only its STACK TRACE. An
untriageable red is one that gets re-run until it goes away, which is how a real
breakage gets absorbed as flake.

WHAT THIS DOES NOT DO IS BLANKET-CATCH. Both refusals arrive as HTTP 403 -- and so
do permission errors, the primary rate limit, and the secondary rate limit. Keying
on the status would make the tool structurally unable to report its own breakage: a
check that cannot fail, which is the defect class this repository is built to
refuse. `classifyRerunRefusal` (pure, in the policy module) matches a CLOSED
allowlist of the forge's two sentences and requires the 4xx band; everything else,
including any other 403 and every 5xx, throws. The safe direction is deliberate --
a false loud failure costs one look, a false silent skip costs the guarantee.
Same line `.github/workflows/heartbeat-liveness.yml` already draws around
`gh label create`: only "already exists" is benign.

The refusal boundary is exactly one call. `fetchRun` and `fetchSiblings` stay
outside it, so a refusal-shaped message on a READ still fails.

Observability: `GitHubApiError` carries `status` and `apiMessage` as fields, the
message names both, and the top-level handler emits a `::error` annotation instead
of a naked trace.

FOUND WHILE WRITING THE TESTS, same class pointed at success: `rerun-failed-jobs`
answers 201 with NO BODY, and `api()` special-cased only 204 -- so the one call
this tool exists to make threw `SyntaxError: Unexpected end of JSON input` on its
happy path. Fixed and pinned.

FALSIFIERS -- 37 tests, 6 mutants, each killed:

  M1  classify on `status === 403` alone      -> 9 tests, incl. "a 403 rate limit is GENUINE"
  M2  drop the 4xx band                       -> 3 tests, incl. "5xx is an outage, never a refusal"
  M3  `if (refusal === null) return 0`        -> 6 tests, the whole "genuine errors STILL FAIL" block
  M4  drop the API message from the error     -> 6 tests, incl. the observability pins
  M5  revert to 204-only body handling        -> "an accepted rerun posts once (201, EMPTY body)"
  M6  drop the already-running phrase         -> 4 tests

One test is labelled `[over-reach guard]` in the source ("dry-run never posts"):
it passes under both the fixed and the pre-fix CLI and is NOT counted as proof.
