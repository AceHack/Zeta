## What this is

A **seeded, DST-replayable** chaos harness for `udp-lossy-transport.ts` (`UCH-1..UCH-16`), plus the
research doc and three filed defects. **No production file is modified.**

ULT-1..ULT-16 are unit tests of the algebra and the state machine — none of them runs a loss
process. This adds one that does, deterministically: every fault is a pure function of
`(seed, stream, index)` over the repo's byte-locked SplitMix64 mixer, **counter-based**
(Salmon et al. SC'11), so a fault at packet 91,847 replays in O(1) without generating its prefix.
No `Math.random`, no `Date.now`. Faults draw on **disjoint streams**, so changing the reorder rate
provably cannot perturb the loss trace (`UCH-2`) — which is what makes a sweep a controlled
experiment rather than a walk.

## Loss model: Gilbert–Elliott, because uniform loss produces a false green

At **one fixed 5% mean loss rate**, changing only the correlation (`UCH-11`):

| | delivery |
|---|---|
| uniform (mean burst 1) | **100.00%** |
| bursty (mean burst 8) | **94.80%** |

Bernoulli ships only as the degenerate `L=1` case of the same model — kept so the harness can
*demonstrate* the false green rather than assert it. The model is **metered, not a toy**: measured
loss matches the analytic `p/(p+r)` within 0.5pp and mean burst matches `1/r` within 10% over
200k packets (`UCH-3`, `UCH-4`).

## The cliff, as numbers (`UCH-12`)

> The transport holds 99% delivery to **~2% loss uniform** and **~0.5–1% once loss is correlated**
> (mean burst 2–8). The same wire format decoded to the code's actual capability holds 99% to
> **~20% uniform** and **1–3% correlated**.

## The main finding — the cliff is in the DECODER, not in the code

A linear code with minimum distance `d` corrects **any `d−1` erasures**. [8,4,4] has `d = 4`, so it
corrects **any 3** per block of 8. `recoverAdinkraErasure` returns `null` at 2. `UCH-7` enumerates
all 56 three-erasure patterns: GF(2) ML decoder **56/56** byte-exact, shipped decoder **0/56**.

| loss | burst | shipped | full-capability |
|---|---|---|---|
| 5% | 1 | 96.05% | **100.00%** |
| 10% | 1 | 84.95% | **99.96%** |
| 20% | 1 | 52.03% | **99.35%** |
| 30% | 1 | 19.72% | **95.68%** |

**"The XOR fallback should be worse — if it isn't, something is wrong."** It isn't. On goodput
(delivered data packets per wire packet), XOR-7/8 at 12.5% overhead **dominates** the shipped
[8,4,4] path at 50% overhead everywhere in the useful range — 0.869 vs 0.497 at 2% loss, 0.705 vs
0.429 at 10% (`UCH-13`). The module header recommends the opposite. [8,4,4] earns its overhead only
above ~30–40% loss *and* only with a full-capability decoder. Fix is decode-side, no wire change.

## AIMD does not converge — it saturates

`onNack` evaluates immediately and `updateAimd` **resets the window every time**, so the estimate is
never "NACKs per 64 packets" as `LOSS_WINDOW` and the comment both state — it is *1 NACK per
packets-since-the-last-NACK*. A NACK within **19 sends** reads as >5% loss and doubles the gap
(`UCH-14` pins 19 and 20 as the real boundary). Driven by a 20k-packet trace (`UCH-15`), the gap
pins at the **500ms / 2-packet-per-second floor from 1% true loss** — five times below its own 5%
backoff threshold. `AimdState.windowStart` is written twice and read nowhere in the repo.

## The composition neither side shows alone

Reordering does not hurt delivery — but `handleIncoming` NACKs every sequence gap, and a reordered
packet *is* a gap that closes a moment later. On a **lossless** channel, 5% reordering yields **183
NACK broadcasts per 4000 packets with 2000/2000 payloads delivered** (`UCH-16`). Feed that ~4.6%
spurious NACK rate to the controller above and **reordering alone collapses throughput ~500× with
zero packet loss.** That seam is the argument for a chaos harness over more unit tests.

## Where my going-in reading was wrong

Two of five suspected gaps were **not defects**, and are pinned as such rather than left as prose:

- **Reordering** — lossless to depth 32 (`UCH-10`); block assembly is position-indexed and
  `recvBlocks` is keyed by `blockSeq`, so out-of-order arrival cannot mis-assemble a block.
- **Duplication** — idempotent at a 100% duplication rate (`UCH-9`); §12 holds on this path.
- Also: the existing test file *does* contain the word `seed`, as a payload-shaping parameter in
  `makeData`. The concept of a replayable fault seed is what is absent, not the token.

## Why FoundationDB's DST does not reach here

FDB injects machine/disk/**partition** faults over a reliable **ordered** substrate, and **TCP hides
erasure** — "2 of these 8 datagrams vanished and the other 6 arrived" never reaches the application
in that stack. This is per-packet erasure on an unreliable datagram channel with an ECC that has a
correlated-failure cliff: **different fault class, same method**. The single-threaded seeded
deterministic run is FDB's and is copied gratefully (Zhou et al. SIGMOD 2021; Wilson Strange Loop
2014 — CITED, not page-checked). The pioneering is the **composition** — a 1960s burst-loss channel
model inside an FDB-style simulator over an ECC-carrying datagram transport — not the invention of
either half. **Honest limit:** this models the channel only, not machine failure or partition, so it
complements FDB-style DST at a lower layer rather than replacing it.

## Filed as PROPOSED, not implemented

- `081KZYN3B79087G0R0014ZKE3C` — use the code's full 3-erasure capability (decode-side only)
- `081KZYN37T4087G0R00181THA4` — accumulate the AIMD window instead of resetting it per NACK
- `081KZYN3D53087G0R0036XZSYM` — reorder-tolerance hold-down before emitting a NACK

**Not done, named rather than implied:** `recvBlocks` eviction sits lexically inside
`if (recovered)`, so a run of unrecoverable blocks accumulates without bound — **CHECKED by reading,
NOT measured** (the map is private and I found no external observable), so it is recorded as a
code-reading finding and not filed as a defect on that basis. A golden-vector byte-lock of a
canonical trace is the obvious next step and is **PROPOSED**, not built.
