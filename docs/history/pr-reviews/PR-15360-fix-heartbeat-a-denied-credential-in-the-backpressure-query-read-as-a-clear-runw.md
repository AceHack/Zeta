## Description

The backpressure guard was `gh pr list ... 2>/dev/null || true`, which makes
a FAILED query indistinguishable from a successful one that found nothing.
Both yield an empty `OPEN_FLUSH_PR`, and empty means "no PR is open,
proceed".

So a 403 here does not blind the check — it INVERTS it. The lane concludes
the runway is clear and force-pushes `$SNAPSHOT_REF` over the head of a PR
still under test. The guard against clobbering in-flight work becomes the
thing that causes it, by failing quietly.

NOT HYPOTHETICAL. At 15:07 today this exact job ran with a token that cannot
perform PR operations — `gh pr create` returned HTTP 403. The same
credential was equally denied for this list. The only reason no ref was
clobbered is that the failure happened to land on the create rather than on
the list; nothing in the design prevented the other ordering.

I found it while reporting on that 403, and I nearly reported the opposite:
that PR *reads* were working and only *writes* were denied. That inference
was unsupportable for exactly this reason — the read path cannot report its
own failure. A guard that cannot say "I could not tell" will say "all clear".

The fix captures stderr, reads the status DIRECTLY (never through a pipe —
`$?` after a pipeline is the last command's status, an error this repo has
made before), and treats a failed query as fatal with the gh output echoed.
Refusing to flush costs one tick, and the lane re-accumulates so the next
flush carries it. Guessing costs another agent's in-flight work.

Deliberately NOT changed: the `gh pr view --json mergeStateStatus` call
below it also swallows, but its fallback is `UNKNOWN`, which is not
`DIRTY`, so a failure there declines to close a PR. That defaults toward
inaction and is already safe.
