## Description

## What

Vectorises the two **linear** relational operators — `Where` and `Select` — over the columnar (`ColumnZSet`) representation, as zero-allocation span→span kernels with scalar twins. Adds **ZLinq** (Cysharp, MIT) to the prior-art register, which the maintainer named.

Origin — Aaron, 2026-08-25:

> "for the where and select not being parallel, i was assuming it could be done in simd batches. i think this library does similar and we can add it to our prior art references too — https://github.com/Cysharp/ZLinq"

New file `src/Core/ColumnLinearOps.fs` (`ColumnLinearKernel` + `ColumnLinear`), 18 tests, a BenchmarkDotNet harness, and the prior-art entries.

## The headline is that two written predictions were REFUTED, and both are kept

Predictions were written into the source **before** measuring. Both were wrong, in opposite directions, and the corrections are the actual result of this PR rather than a footnote to it.

### 1. `Where` — the axis is branch PREDICTABILITY, not selectivity

Predicted: wins at low selectivity (empty 64-bit mask words skipped wholesale) and at high selectivity (full words bulk-copied), weakest in the middle.

Measured (M2 Ultra, arm64/NEON, `Vector<int64>.Count = 2`, best-of-9, scalar ÷ vector):

| n | key order | selectivity | ratio |
|---|---|---|---|
| 1 048 576 | shuffled | **50%** | **3.45x** |
| 1 048 576 | shuffled | 1% | 0.87x |
| 1 048 576 | shuffled | 99% | 0.69x |
| 1 048 576 | sorted | 50% | 0.95x |
| 1 048 576 | sorted | 1% | 0.82x |
| 1 048 576 | sorted | 99% | 1.12x |
| 65 536 | shuffled | 50% | 3.12x |
| 65 536 | sorted | 50% | 0.78x |
| 4 096 | shuffled | 50% | 1.16x |

The prediction had selectivity and predictability backwards. A 1%-selective predicate is *almost always false* and a 99%-selective one *almost always true* — **both extremes are trivially predicted**, so the scalar twin costs almost nothing there. Predictability is maximal at the extremes and minimal in the middle, the exact inverse of the assumption. Sortedness kills the win from the other direction: a sorted column has two branch transitions in the entire scan.

So the claim is narrow, and it is stated narrowly:

> The vectorised filter wins **only where the scalar branch is unpredictable** — **3.45x** at 50% selectivity on shuffled keys at n = 1 048 576 — and **loses 1.05x–1.45x everywhere else**.

`FilterKeyInRange` dispatches to the vector path anyway. That is a **worst-case-bounding** decision, stated as such: ≤1.45x given up on predictable columns to buy 3.45x on unpredictable ones. A caller that knows its column is sorted should call the scalar twin — or binary-search the boundaries and not scan at all, which is the honest caveat carried over from #15246.

**ZLinq does not vectorise `Where` at all.** Given these numbers, that is a defensible call by a mature benchmark-driven library, not an oversight — and worth recording as a negative result rather than quietly out-performing it.

### 2. `Select` — the multiply prediction priced one instruction instead of the loop

Predicted `≤ 1.0x` for `map (*m)`: AArch64 NEON has no 64-bit integer vector multiply, and on x86 `vpmullq` is AVX-512DQ only, so RyuJIT scalarises `Vector<int64> * Vector<int64>` on both ISAs we target.

Measured on NEON:

| n | `map (+delta)` | `map (*m)` |
|---|---|---|
| 4 096 | 1.12x | 1.12x |
| 65 536 | 1.46x | 1.27x |
| 1 048 576 | **1.60x** | **1.28x** |

The multiply is one of *three* per-element operations; the other two are the overflow guard's range compares, and those vectorise fully. Scalarising one third of a loop leaves two thirds vectorised. The gap between 1.60x and 1.28x is what the scalarised multiply actually costs — a **reduction** in the win, not its elimination.

`MapScale` was written dispatching to scalar on the strength of the prediction. **The dispatch was changed to vectorised on the measurement.**

### 3. Identity projection — no win, and now with a real control

`CopyColumn` is `Span.CopyTo` and is deliberately not hand-vectorised. The first version of the benchmark compared `CopyTo` against itself, which would have reported 1.00x and proved nothing — the vacuity class. Replaced with a genuine control:

| n | hand-rolled `Vector<int64>` loop | `Span.CopyTo` |
|---|---|---|
| 4 096 | **0.84x** — slower than scalar | 41.7x |
| 65 536 | **0.91x** — slower than scalar | 4.6x |
| 1 048 576 | **1.00x** — no better | 2.8x |

Hand-vectorising an identity projection is a **regression** at every size measured, while looking like optimisation work. "No win here, and here is why" is the deliverable.

## Zero allocation — measured, and tested at the COMPOSITION

Every kernel takes a caller-supplied `Span<int64>` destination and returns the count written (the BCL `Utf8Formatter`/`Base64` idiom). No intermediate selection vector, no bitmap buffer, no `stackalloc`: the selection mask is a single `uint64` local covering 64 elements, which is why the block size is 64. The lane-bit seed is hoisted to a static — an `Array.init` inside the kernel would have allocated per call, and mutation M7 confirms the test catches exactly that.

A too-small destination is **refused**, not truncated. Silent truncation would be a short count with no indication rows were dropped.

Measured with `GC.GetAllocatedBytesForCurrentThread()`, **Debug and Release both**:

| surface | Debug | Release |
|---|---|---|
| `FilterKeyInRange{Scalar,Vectorized}` | 0 B | 0 B |
| `MapAdd{Scalar,Vectorized}` / `MapScale{Scalar,Vectorized}` / `CopyColumn` | 0 B | 0 B |
| **`Where` → `Select` pipeline over `ArrayPool`, 8 192 rows** | **0 B** | **0 B** |
| `ColumnLinear.filterKeysInRange` (allocating wrapper, 1 000 rows) | < 33 000 B | < 33 000 B |

The pipeline row is the one that matters: two individually-clean stages that allocate *between* them is the failure this API shape exists to prevent, and it is invisible to per-operator tests. It is asserted non-vacuously — the test also checks that the pipeline produced rows and produced the *right* rows, so "zero bytes" cannot be bought with a no-op.

The exact `= 0L` guard holds in both configurations, so no `#if DEBUG` split was needed. The one non-zero budget is on the allocating module wrapper, and it is a bound rather than an exact golden **because the second exact-size allocation depends on the data's selectivity** — a property of the input, not of the build configuration. That reason is written in the test.

## DoP = 1 → ∞, without spawning anything

The kernels are pure span→span functions: no ambient state, no `Task.Run`, no thread. DoP=1 is the ordinary call; DoP=N is a ferry sharding the span, and the DoP knob stays on the ferry throttle where `.claude/rules/async-all-the-way-truthful-signatures.md` puts it.

What licenses that sharding is **proved rather than asserted**, and it is the same algebra the query surface already relies on:

> `QuerySurface.fs` tags `Where`/`Select` LINEAR — `Q(a ⊎ b) = Q(a) ⊎ Q(b)`. A SIMD lane, a 64-element block, and a `MaxDegreeOfParallelism`-th shard are all *parts* of such a decomposition.

Two tests run filter and map over **arbitrary partitions** (1/2/3/4/7/8 shards × cut-point skews of 0/1/5/64, so cuts land block-aligned, lane-aligned and aligned to nothing) and assert the concatenation equals the whole-span result. Discharged algebraically on purpose: a test that started tasks would be nondeterministic under DST replay and would prove less.

**This is also the one place the maintainer's observation and the DBSP property genuinely meet, and the PR is careful not to conflate them.** `Q^Δ = Q` is an *incrementalization* property and says nothing about SIMD. Aaron's point is orthogonal and correct: linear operators are the ones that vectorise cleanly. The reason they rhyme is the distributivity above — the same fact that makes the incremental form trivial makes the batched form safe to split.

## The #15246 failure class cannot occur here — and that is checked, not asserted

#15246's P0 was a vector kernel checking overflow **per lane** while its scalar twin used four unrolled accumulators: different partitions of one sum, disagreeing in **both** directions, with the answer depending on host ISA (2-lane NEON vs 4-lane AVX2).

That defect is specific to **reductions** — an accumulator is shared state whose partitioning is visible in the result. `Where` and `Select` have no accumulator; every element's outcome depends on that element alone, so lane width cannot reach the answer. Overflow checking is **per element** and partition-free by construction.

"Cannot happen" is still a claim, so it has falsifiers:

- Differential tests at `n ∈ {0,1,2,3,7,8,9,63,64,65,127,128,129,191,1000,4097}` — crossing **both** the lane boundary and the 64-element block boundary. (#15246's differential test capped `n` at 40, one chunk, and missed a real defect for exactly this reason.)
- A dedicated test slicing the same data at **every offset in `[0, 64+width)`**, so every alignment of data relative to lane and block boundaries is covered, compared against a lane-width-independent oracle.
- Overflow boundary tests including the two multipliers whose *bound computation itself* faults naively: `m = 0` (divide by zero) and `m = -1` (`Int64.MinValue / -1L` raises).

Overflow is made vectorisable by turning it into a **range test**: precompute scalar bounds `[lo, hi]` such that the result fits iff `lo ≤ x ≤ hi`, then the per-element check is two compares. There is no portable vector division; there is a portable vector compare.

**ISA coverage is an honest partial.** Everything above was executed on **arm64/NEON, 2 lanes**. The alignment-sweep test is written to be lane-width-independent and will exercise 4 lanes on an AVX2 runner, but I did not have an x86 host — so the AVX2 half is claimed as *"the test is constructed to catch it"*, not *"it was observed to pass there"*. CI running on x86 is what closes that, and it should be watched on this PR rather than assumed.

## ZLinq — what it actually contributed

**Licence checked first** (`.claude/rules/cleanroom-two-team-separation.md`): **MIT**, so reading the source would have been permitted. It was **not read** — findings come from the published README and generated documentation, cited as prior art. Requirements taken, no expression. The one primitive that coincides (the two's-complement add-overflow test `(a^s) & (b^s) < 0`) is a textbook identity predating both projects.

1. **Vectorisation is gated on layout, not on the operator.** ZLinq applies SIMD only when `TryGetSpan` succeeds. That is Abadi et al. 2013's claim arrived at from the LINQ side, and it is the independent confirmation that `ColumnZSet` had to exist before these operators could be vectorised at all.
2. **Checked and unchecked are two contracts; name both.** ZLinq ships `Sum` *and* `SumUnchecked`, documenting ~2x (721 ns vs 1 351 ns on 16 K `int[]`). #15246 paid that cost in a different currency. ZLinq's split is evidence it was a genuine trade, and that a future `SumWeightsUnchecked` would be legitimate **provided it is named**.
3. **An arbitrary `Select` lambda cannot be auto-vectorised.** ZLinq's vectorised `Select` requires `AsVectorizable()` with **two** caller-supplied functions (one over `Vector<T>`, one over `T`). This PR reaches the same conclusion differently — *named* projections whose vector form is written once — but the design point is ZLinq's: a library claiming to vectorise `Select(f)` for arbitrary `f` on a managed runtime is claiming something it cannot do.
4. **`Where` is absent from its SIMD set** — the negative result discussed above.

Not taken (.NET-idiom-specific): the `IValueEnumerator` struct-enumerator tower, `allows ref struct` plumbing, and `System.Linq` drop-in compatibility. Those solve "make LINQ allocation-free without changing user code", which is not this repo's problem.

Added to `references/reference-sources.json` (8-line append) and `docs/PRIOR-ART-LIST.md` (new section), together with the human anchor underneath it — **Boncz, Zukowski & Nes, MonetDB/X100 (CIDR 2005)** — since anchoring wants the paper, not only the repo.

## Honest limits

- **NEXMark Q1/Q2 were not wired through these kernels.** Q1 (`Map` over `ZSet<Bid>`) and Q2 (`Filter` over `ZSet<Bid>`) are **row-store circuits over a struct record**; these are `int64`-column kernels. Measuring one through the other requires a columnar `Bid` representation and a columnar circuit operator, which this PR does not build. Stating that is better than reporting a number from a harness that does not actually exercise the code. Additionally **NEXMark Q2's predicate is an IN-list** (`auction in (1007,1020,2001,2019,2087)`), and the kernel here is range-only — a real gap, named rather than glossed.
- `Vector.ExtractMostSignificantBits` would collapse the mask fold to one instruction but **is not reachable from F#** (`FS0503`). The fold uses `Vector.Sum` over a lane-bit seed instead — only primitives already proven in `ColumnZSet.fs` and `Simd.fs`. This costs real performance and is part of why the `Where` win is narrow.
- Portable .NET has **no compaction instruction** (`vpcompressq` is AVX-512, `compact` is SVE, neither reachable through `System.Numerics.Vector<T>`), so the compaction step is scalar stores driven by `TrailingZeroCount`. That is a ceiling on this design, not a defect in it.
- The timing gate is a **weak instrument** and is labelled as such: it shows the vector path is still taken, not that any particular instruction was emitted. There is no supported way to assert on JIT output from a unit test.
- `ZSet` is untouched. No existing public signature changed, so no consumer migration was needed and none is claimed.

### The Debug run caught a real defect in my own test

The first Debug run **failed**: the timing gate measured **1.37x** against its 1.5x threshold, while Release measures **3.45x**. The JIT optimises both paths in Release and neither in Debug, which **compresses the ratio** — the same Debug/Release divergence the allocation goldens have, applied to timing instead.

The fix is the repo's existing idiom (`BenPort.Tests.fs`): an **exact threshold per configuration** via `#if DEBUG` — 1.15 in Debug, 1.5 in Release — rather than one loose threshold covering both. A single value would have to sit under 1.37 and would then be slack in Release, which is the configuration that ships.

The thinner Debug margin (1.15 against 1.37) is written into the test, along with the instruction for what to do if it ever flakes: **skip it in Debug, do not lower it further.** A gate below ~1.05 could not distinguish a vector path from a scalar one and would be a check that cannot fail.

The allocation tests passed in **both** configurations unchanged, so no `#if DEBUG` split was needed there.
