## Three findings that would have cost him keyboard time

- **`zflash` refuses to flash today.** The iter-4.3 guard diffs seven install-substrate files against `origin/main`, and `zeta-install.sh` currently differs in the shared checkout. Step A0 is the pull.
- **The old runbook's CP-1 does not resolve.** There is no artifact named `zeta-installer-iso` — nixpkgs 25.11 names the derivation from its own default, so it is `nixos-minimal-<version>-x86_64-linux.iso`, which `zflash`'s `ISO_GLOB_PREFIX` then will not see. Corrected in place, together with a `--usb` flag that does not exist.
- **`zflash`'s CI auto-pull is architecture-blind.** `gh run download` with no artifact filter, then `findIsoUnder` returns the first `.iso` it walks; a run has carried two ISOs since the aarch64 job landed. Hence the explicit path in step A2.

## One correction to a sibling's read

The aarch64 boot smoke-test **does** report green while failing — `continue-on-error: true`, exactly 1800 s, log ending at `EFI stub: Exiting boot services`. That part stands and is reported here as a **skip**, not a pass.

But the image is not broken. The same artifact from that same run was downloaded and booted locally under HVF, and it reaches `zeta-installer login:`. So the CI defect is a **TCG budget**, not a boot defect. The reproduction command is in the doc.

aarch64 **metal** remains unproven, and it is not this bringup's target: `full-ai-cluster/flake.nix` says our cluster nodes are x86_64, and x86_64 is the arch whose k3s control-plane / agent-join / cluster-online tests are green.

Riven's #10959 touches `src/Core.TypeScript/installer/multiboot/*`, not `ci/qemu-boot-test.ts` — a different, still-open lane. Nothing in that branch was touched.
