The brief asked me to check whether they are still meant to be runnable before repairing. They are
not, and this is the finding the rest follows from.

Live rulesets on `Lucent-Financial-Group/Zeta` today, read read-only:

```text
15256879  Default                                        active   rules: []

16189060  Branch Safety                                  active   rules: [deletion, non_fast_forward]
```

"Review Policy" — the ruleset `b0266` exists to create — **does not exist**, and is absent from the

### What each one actually does if run today

Recorded through a `gh` shim on `PATH` that logs every invocation and answers `[]`. **Nothing was
ever pointed at GitHub**; the migrations spawn `gh` by name, so a failed shim is `ENOENT`, not a
credentialed call.

```text
b0266-review-policy-ruleset      GET  /rulesets
                                 POST /rulesets                 <- recreates a retired ruleset
                                 PUT  /rulesets/15256879        <- puts 3 rules back on an
                                                                   intentionally-empty Default
b0267-branch-safety-ruleset      GET  /rulesets
                                 POST /rulesets
                                 PUT  /rulesets/15256879
b0267-safety-ruleset             GET  /rulesets
                                 GET  /rulesets/15256879
```

`b0267-safety-ruleset` is the sharp one, and the shim **cannot** show it: its canned `[]` is not a
ruleset object, so the run dies on `defaultRuleset.rules.filter`. The conclusion comes from reading
the live state instead. `Default` has zero rules, so `remainingRules` is empty, `defaultIsEmpty` is
true, and step 2 takes the branch that issues
`DELETE /repos/Lucent-Financial-Group/Zeta/rulesets/15256879` — and *then* dies in step 3. That is
the ordering defect in its live form, on `origin/main`, today. `Default` is empty so no protection
is lost, but it is in the baseline and a deleted ruleset id does not come back.

`b0267-branch-safety-ruleset` is the **weakest** of the three and the file says so rather than
being flattened into one story: step 2 is already a no-op, and its only live effect would be
re-adding `required_linear_history` to `Branch Safety`. That is a policy question, not a migration.

### The fix

A refusal above the first `ghApi` call, so a live invocation makes **no request at all — not even
the read**. `--dry-run` still works, because it is read-only and it is the executable record of
what the migration did. `--rerun-spent-migration` re-arms deliberately.

```text
$ bun src/Core.TypeScript/migrations/b0267-safety-ruleset.ts
REFUSED — this migration is SPENT (081KR2E4K0008QG0R002NYV33T closed 2026-05-10).
Against live Lucent-Financial-Group/Zeta today its step 2 takes the DELETE branch and would remove the
"Default" ruleset (15256879) outright — an action re-running nothing
can undo. Nothing was read, modified or deleted.
EXIT=3          gh calls recorded: 0      (the canary file was never created)
```

Paths are fixed as well, behind the guard, so the file is not a trap for whoever re-arms it.

### Ordering — argued, and NOT changed

**Snapshot-after is deliberate and stays.** `expected.json` is not a rollback record; it is the
**declared baseline** that `check-github-settings-drift.ts` diffs live settings against. A snapshot
taken before step 1 records the state that is already checked in — it writes the file back to
itself and proves nothing. Capturing the post-state is the entire job of that step.

What closes the crash window is the guard, not a reordering: no mutation, no window. And for
`b0267-safety` specifically, **no ordering could have helped** — a snapshot is a record, never a
rollback, and nothing recovers a deleted ruleset id.

A **pre-mutation snapshot** would be a genuinely useful *second* artifact. That is a different
artifact with a different purpose, and adding one is a change to make deliberately rather than by
relabelling this step. Named, not smuggled.

# Defect 2 — the fork, and why the security finding is the strongest argument

**It is not reachable.** `zeta-flash.ts`, `flash-and-inject.ts`, `flash-usb-windows.test.ts` and
`audit-installer-substrate.ts` all name the `zflash/` copy. Even
`full-ai-cluster/tools/README-flash-usb-windows.md`, which sits in the same directory, documents
`bun src/Core.TypeScript/zflash/flash-usb-windows.ts` in every one of its examples. Nothing invokes
the fork, including its own README.

**The 3 hunks are pure drift, and git says why.** The fork's last commit is #6895; the canonical
copy was *created* by #8076 ("consolidate CLIs under src with hexagonal ports"), which is also the
commit that introduced the `mkdtemp` fix. #8076 never touched the `full-ai-cluster/` file — it
copied rather than moved, and left the original behind. Two of the three hunks are the file's own
path in its header and usage string. **One is substantive, and it is the security fix.**

**It does still carry the defect — measured, not inferred.** `full-ai-cluster/**` is not in
`.github/codeql/codeql-config.yml`'s `paths-ignore`, so CodeQL scans it, and it has:

```text
alert 173   js/insecure-temporary-file   severity: HIGH   state: open   since 2026-06-07
            full-ai-cluster/tools/flash-usb-windows.ts:557
            "Insecure creation of file in the os temp dir."
```

Line 557 is `const tmp = join(tmpdir(), ...)`. This is worse than an untidy filename: the file is a
**diskpart script handed straight to `diskpart /s`** while the tool runs **elevated**, so a
predictable name in a world-writable directory is a substitutable input to a privileged
disk-partitioning command.
