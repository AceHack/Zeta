## Description

fix(ci): the canary caught a real blind spot on run one — a swallowed step reads `success` in the REST API

`drift (loud)` went red with DETECTOR WENT QUIET on gate run 32651748761 while
`drift-canary` was running two feet away and had done exactly what it was built to do.
The canary was not broken. The detector was, and the falsifier found it in minutes.

WHAT IS ACTUALLY TRUE, measured against the live API:

  GET /actions/runs/32651748761/jobs
    -> drift-canary: conclusion "success"
       steps: [Set up job: success,
               "drift canary -- deliberate non-blocking failure": SUCCESS,
               Explain the green: success, Complete job: success]

The step that exited 1 under `continue-on-error` is reported as having SUCCEEDED.
`outcome` — the pre-continue-on-error value — exists only inside the workflow as
`steps.<id>.outcome` and is not on the REST payload at all. So a step-level swallow is
not merely unsurfaced: in the data every earlier surface reads, it is UNREPRESENTABLE.
gate.yml's standing note that "the API reports a continue-on-error leg's conclusion as
`failure`" is true of JOBS and false of STEPS, and that asymmetry is what hid the class.

THE CHANNEL THAT DOES CARRY IT:

  GET /check-runs/97224512630/annotations
    -> [{ annotation_level: "failure", message: "Process completed with exit code 1." }]

on a check run whose own conclusion is `success`. So the detectable signature of a
step-level swallow is a GREEN check run carrying a FAILURE-level annotation, and that is
what `censusOfRun` reads now. Annotations are fetched for green jobs of the CURRENT run
only — one call each, ~33 on a gate run — which is also why liveness now asserts against
this run rather than the window: it is the stronger claim (detection worked on the very
payload being reported) and the only affordable one.

`undefined` and `[]` are kept as different claims throughout: "did not look" must not
read as "looked, found none", or every unfetched run would count as a clean execution
and inflate the clean streaks that demote bands to HEALED.

THE CANARY IS NOW EXCLUDED FROM THE ALARM, NEVER FROM THE CENSUS. It fails on every run
by design, so leaving it in the bands would have climbed it to SUSTAINED and emitted an
::error:: forever — a permanent false alarm, self-inflicted by the instrument, and the
exact cry-wolf failure this surface exists to avoid. It still has to be found, and
`assertDetectorLive` still goes red when it is not.

The secondary step-conclusion branch is kept live with its own falsifier rather than
deleted, so if GitHub ever does start reporting a swallowed step as `failure` the
reporter names the STEP instead of only the job — and the test pinning today's blind
spot goes red, forcing the claim above to be corrected rather than quietly kept.

Verified against run 32651748761, the one that exposed the bug: detector live via the
annotation channel, canary unannotated, exit 1 preserved for the genuine
PUBLICATION NOT LANDING defect (081M0QPZD9C087G0R002W8QC2A). 41 falsifiers; repo
typecheck, actionlint and build-graph completeness clean.
