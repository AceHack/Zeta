## Description

Found while auditing all 70 workflows for red. **This one never showed as red, which is the point.**

## The state

**28 of the last 30 runs cancelled. Zero successes, ever.** One run observed sitting in its final step for **2h37m** and still going. It has never completed a single tick since it was added in `fe38a2a8e`.

## Why it hid

**Cancelled is not failure.** Every hourly tick queues behind the hung one (concurrency group `mux-swarm-tick`, `cancel-in-progress: false`) and is then cancelled when the *next* hour's run arrives. So the workflow burns a runner continuously while reporting nothing red — the same shape as every other defect this session: **a thing that never ran looking like a thing that did not fail.**

## Where it hangs

Step-level status on stuck run `31694827817`:

```
completed    Set up job / Check out repo / Install Bun / Install Ollama
IN PROGRESS  Run Mux-Duplex Swarm Tick (4 Roles)    <- started 11:28Z, 2h37m
```

So `bun src/Core.TypeScript/swarm/swarm-controller.ts` does not exit.

## Likely cause — reported, not fixed here

It needs a decision inside the swarm subsystem:

```ts
if (import.meta.main) {
  main().catch(e => { console.error(e); process.exit(1); });
}
```

`main()` runs exactly one tick and returns 0, so it isn't an infinite loop. But there's **no `process.exit(0)` on the success path**, so any still-open handle keeps the process alive after `main` resolves — and the step forces four roles through Ollama (`ZETA_SWARM_USE_LOCAL_LLM=1`, `qwen2.5:0.5b`) with no request timeout, plus `ollama serve &` backgrounded in the previous step holding the step's output pipe. Either an unresolved LLM call or an open handle produces exactly this.

## What this commit does

**It does not fix the hang. It bounds it.** 15 minutes — generous for an Ollama install, a model pull, and four small-model calls. A timed-out job reports **failure**, so the next occurrence is visible instead of silent, and the hourly queue stops being blocked by a run that will never finish.

Parsed YAML verified to carry `timeout-minutes=15` on the job rather than trusting the text edit.
