## Description

feat(cluster): control plane AND gpu on one machine — roles compose, agents refuse cluster work

Aaron 2026-09-07: "control-plane and worker-gpu are distinctions, almost
placeholders, and we want to be able to support more than one on a machine at
the same time — control plane and gpu, not just one or the other."

MEASURED FIRST, by evaluating a probe rather than reading modules: k3s-server +
gpu + gpu-device-plugin already composed cleanly and yielded role = "server".
Nothing technical prevented the combination. The obstacle was that every host
hand-assembled its own module list, so "control plane and gpu" existed only if
someone wrote a third bundle by hand.

`nixos/lib/mk-host.nix` makes the assembly a function of a ROLE and
CAPABILITIES, and the split in it is not cosmetic:

  role                EXCLUSIVE, server | agent. Both k3s role modules assign
                      `services.k3s.role` outright, so importing two is a
                      conflict — correct, since a k3s node is one or the other.
  nodeCapabilities    COMPOSABLE under either role: drivers, container runtime,
                      disks, credentials.
  clusterCapabilities COMPOSABLE, valid ONLY on a server, and REFUSED elsewhere.

That third category is the point. Cluster capabilities install through
`services.k3s.manifests`, which the deploy controller applies ON A SERVER — on
an agent the files are written and nothing reads them, silently. That is exactly
how the NVIDIA device plugin came to be declared only on worker-gpu and never
installed (081M1XXA0FC087G0R002F92ZQC).

`audit-k3s-manifests-reach-a-server.ts` DETECTS that class. This makes it
UNREPRESENTABLE: the assertion fires at evaluation, naming the reason, before
anything is built. A detector can be silenced; a shape you cannot express cannot.

`checks.mk-host-refuses-cluster-capability-on-an-agent` proves the assertions
FIRE rather than trusting they would — `builtins.tryEval` makes an assert
testable, and all four directions are asserted: the refusal fires on an agent, a
server accepts cluster capabilities, control-plane + gpu composes, and a
misspelled capability is refused rather than silently dropped. It runs in the
existing `nix flake check --no-build --all-systems` lane.

The new `control-plane-gpu` host is a TEMPLATE — it borrows control-plane's
hardware-configuration.nix because no such machine exists yet, the same shape as
worker-template. Verified by evaluation: role = "server", hostName
control-plane-gpu, `hardware.nvidia.open` present, and 13 manifests INCLUDING
nvidia-device-plugin — it can apply what it declares, which the previous
arrangement could not.

EXISTING HOSTS ARE UNTOUCHED, checked rather than assumed: control-plane still
13 manifests, worker-gpu still exactly [local-path-provisioner]. This adds a
configuration; it does not refactor the three that work.

One real bug found and fixed while writing it: `"${modules}/x.nix"` stringifies
a path into the store instead of concatenating. The nix idiom is
`modules + "/x.nix"`, which yields a path. The first evaluation failed with an
absolute-path error that named the symptom and not the cause.

Verified: `nix flake check --no-build --all-systems` exits 0 with
control-plane-gpu among the green outputs. (One run exited 139 — a transient
crash, not a failure; a clean re-run passed, and the difference is stated rather
than quietly retried.)
