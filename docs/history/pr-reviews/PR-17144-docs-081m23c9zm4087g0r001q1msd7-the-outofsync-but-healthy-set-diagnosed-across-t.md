## Description

Aaron: *"yes lets diagnose all those issues"* — including the apps that are `OutOfSync` but `Healthy`, which look like drift rather than breakage. This is the answer, measured across **two** independent bring-ups.

## Why one dump could not answer it

The `Name the drifting resources` step runs `if: always()`, **after** the verdict. ArgoCD re-syncs on a ~5-minute cycle, so one dump reads a moment rather than a state — the **green** run lists **more** `OutOfSync` Applications (20) than the red one.

So both were tallied: `34338106811` (green, dump 2 s after a 513 s verdict — barely settled) against `34323056405` (red, dump 18 s after a 2400 s timeout — 39 minutes to settle). A class in both is persistent; a class only in the fast run is reconcile in flight.

| kind | green | red | reading |
|---|---|---|---|
| CustomResourceDefinition | **54** | **2** | **TRANSIENT** — not drift at all |
| StatefulSet | **7** | **7** | **PERSISTENT**, and the same seven apps |
| Gatekeeper Constraints | 7 | 7 | a **real defect** (#17136) |
| manual-sync resources | 20 | 20 | expected by declaration |

## The persistent set is exactly seven, identical both times

`agent-memory`, `cockroachdb`, `headscale`, `hindsight`, `nats`, `opensearch`, `weaviate` — one StatefulSet each.

This **vindicates** the comment that justifies the `OutOfSync + Healthy` allowance in `isApplicationSynced`. *"Helm apps with benign StatefulSet drift"* had never been measured and was doing load-bearing work as prose; measured, it names exactly the class that persists, and the 54 CRDs that looked like a larger class are not drift.

## What is deliberately left unmeasured

**Which field** of each StatefulSet differs. The dump names the resource, never the diff. The usual suspect is defaulted `spec.volumeClaimTemplates` values the rendered manifest does not carry — recorded as a **hypothesis with a named instrument** (`argocd app diff --server-side-generate`, which needs the CLI, a port-forward and a login inside the job — a real addition and a CI decision), not as a finding.

## The lesson

Because the persistent class is genuinely benign, the allowance that admits it was widened until it also admitted a **failed sync**. `hat-system` presented identically — `OutOfSync + Healthy`, persistent in both runs — and was broken. What separates them is a third field, the **condition**, which was parsed and never read. That is #17138.

## And two that were never drift

`cdi` and `kubevirt` show every resource `OutOfSync/Missing` in both runs, and that is **correct**: both declare `manualSync: true`, are asserted under `manualSyncAssertion` plus a dedicated `live kind kubevirt+cdi emulation proof` job, and that job passed in every run examined. The roster is **not** over-claiming them — the earlier reading that it was came from the raw `kubectl get applications` dump rather than from the proof own verdict.
