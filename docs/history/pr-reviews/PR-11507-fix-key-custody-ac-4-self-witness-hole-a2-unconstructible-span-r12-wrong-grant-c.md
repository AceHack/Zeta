## AC#4 — the filed diagnosis was partly wrong, and the truth was worse

The work item and the combine doc both record that `validateTransfer` **"cannot return `allowed: false` for any `CustodyTransfer` that type-checks"**. I tried to construct the falsifying input for each of its three guards, the same way AC#3's vacuity was proven:

```
ac4-vacuity-probe.ts(13,3): error TS2322: Type 'undefined' is not assignable to type 'WitnessStake'.
ac4-vacuity-probe.ts(21,3): error TS2322: Type 'false' is not assignable to type 'true'.
```

Two errors, not three. So:

| guard | reachable by a type-checking input? |
|---|---|
| `!transfer.witness` | **no** — `undefined` not assignable |
| `!transfer.witness.voluntary` | **no** — `false` not assignable to literal `true` |
| `!transfer.witness.resource` | **yes** — `resource: ""` compiled, and denied correctly |

**One third of the criterion was live.** The recorded claim was too strong, and I have corrected it in the combine doc rather than deleting it.

The serious defect was one neither guard covered — nothing checked that the witness was a party **other than the two transacting**:

```
empty staked resource                          -> {"allowed":false,...}
PRIOR custodian witnesses her own transfer     -> {"allowed":true,"reason":"transfer witnessed by 'alice'..."}
NEW custodian witnesses the transfer to himself-> {"allowed":true,"reason":"transfer witnessed by 'bob'..."}
```

A custodian can witness her own transfer away, and the beneficiary can witness the transfer to himself. That is exactly the **one-sided transfer R10 exists to prevent**, and it is a worse hole than the vacuity that was filed.

**Fix.** `voluntary` becomes `boolean`, so a compelled stake is *representable* and therefore *refusable* — a stake must never be coerced. Distinctness from both the prior and the new custodian is enforced, and whitespace-only resources and unnamed witnesses are refused.

## A2 — the span ceiling is now unevadable, not merely stated

A2 asks that indefinite authority be **"unconstructible through the public surface"**. A structurally-typed interface is not that: `const g: Grant = { ..., expiresAtPhase: Number.MAX_SAFE_INTEGER }` was a public construction path no constructor could police. So a constant alone would not have satisfied A2 — the type had to change.

`Grant` is branded now, and the bypass no longer compiles:

```
a2-unconstructible-probe.ts(6,14): error TS2741: Property '[grantBrand]' is missing in type
  '{ id: string; principalId: string; capability: string; issuedAtPhase: number; expiresAtPhase: number; }'
  but required in type 'Grant'.
```

`tryIssueGrant` is therefore the only way to obtain a `Grant`. It returns `Result<Grant, GrantError>` rather than throwing (amendment A6, Result-over-exception), refuses spans over `MAX_GRANT_SPAN_PHASES = 65536`, and refuses `Infinity` and non-positive spans — `Infinity` would otherwise sail past a naive span comparison, which is the same evasion in a different costume.

**The event stream is not a bypass either.** `foldEvents` routes `grant-issued` through the same constructor, so a peer emitting a grant to `MAX_SAFE_INTEGER` cannot smuggle indefinite authority in by having it folded. It is **refused out loud** into a new `refusals` list rather than dropped silently — a silently-dropped event is indistinguishable from one never received, which is the failure class this module has already been caught in twice.

**On the number:** 65536 is **taken from derivation A**, as recorded in the work item, rather than independently chosen — so the two derivations agree on a dial instead of inventing two. It is a policy dial and remains yours to retune. What this module owes R8 is that a ceiling exists and cannot be evaded, not that 65536 is the right ceiling.

## R12 — the denial cited the wrong grant

`authorize` cited `matching[0]` — arbitrary stream order. With grants expiring at 5 and 100, a denial at phase 200 reported *"expired at phase 5"*. The outcome was right and the explanation was wrong, which is worse than a bare deny: it sends the reader to the wrong grant.

It now cites the **longest-lived** matching grant (the one whose absence of authority is decisive), returns that grant on the decision, and no longer describes a **not-yet-issued** grant as "expired" — those are different failures and were reported identically.

## Custody claims, stated exactly

**Nothing here is cryptographic.** No attestation is signed. No stake is escrowed, held, or slashed. No key is revoked.

`validateTransfer` checks that a transfer **record** names a distinct, willing witness and a non-empty resource. It cannot tell you the named witness actually consented, or that the staked resource is real. And **which resources count as socially-conferred and non-purchasable is a policy roster that is deliberately not invented here** — refusing an empty string is not the same as verifying unpurchasability, and this PR does not claim it is.

`tryIssueGrant`'s bound is enforced at the type and value level within this module. It is not a distributed guarantee: nothing stops a remote peer from believing in a longer grant, only from having one admitted by *this* fold.
