## Description

fix(tests): four Windows failures, one diagnosis — bounds with no tolerance

Measured over the last 14 commits on main: windows-11-arm and windows-2025 each
failed 2 of 13 completed runs (15%, down from 88%/94% before the custody-path
fix). Four distinct tests, and they share a shape: a measurement bound set tight
enough that platform variance crosses it, asserted as though the bound itself
were the property under test.

TlcRunnerTests, "owned process capture retains probe streams". `captureProcess`
ran `bun -e "console.log(...)"` under `Some 3000`. On a loaded Windows runner a
bun cold start can exceed 3 s; `captureProcessWithDeadline` then calls
`proc.Kill true`, which on Windows surfaces as ExitCode -1, and the next line
reported that as a capture failure (Expected 0, Actual -1). The assertion is
about capture and exit status, not about how fast bun starts. Raised to 30000,
matching the java-version budget in the same file.

TlcRunnerTests, "probe cancellation drains inherited pipes". A 10 s spin waiting
for a fixture that spawns bun which spawns bun again -- two cold starts -- and
the test burned exactly its 10 s before "fixture readiness not observed". This
is SETUP PATIENCE, not the cancel-and-drain behaviour under test. Raised to
30000; readiness that never arrives still fails, so it tolerates the delay and
not the absence. The three bounds that DO measure the behaviour (:914 launcher
exit, :922 cancelled drain, :957 capture join) are untouched at 10000.

FactoredPredictiveTests, "allocation growth sampler rejects retained context
copies" -- the sharpest of the four. The assertion was
`excess >= copiedPayload`, demanding the measured excess REACH the payload size,
while a perfect measurement produces exactly the payload size. Zero headroom, and
`Array.min` makes one low sample decisive. Measured on windows-11-arm @03741bf5:

  short = [43008; 43008; 43008; 43008; 43008]
  long  = [174080; 174080; 174080; 174080; 170240]   <- one sample 3840 low

giving excess 127232 against a threshold of 131072. The discriminator had
detected 97% of the payload and was reported as having MISSED it. Now a
documented 90% floor: the null hypothesis it must reject is NO retained copy,
whose excess is ~0, so the threshold still sits an order of magnitude above the
thing being excluded while tolerating ~3x the noise observed. `Array.min` is
kept -- it is the right statistic for a steady-state allocation floor, since
noise adds allocations rather than removing them.

Budgets that ARE the property under test are deliberately unchanged: the
`Atomics.wait` call asserting TimedOut, and the empty-argv call asserting
IOException on the CreateNew collision.

THE FOURTH ONE GETS DIAGNOSABILITY, NOT PATIENCE, and that is the deliberate
part. `Fuzz: Arrow garbage + truncated-header inputs are rejected fast` failed
with "Arrow hostile input hung or threw". Those two want OPPOSITE responses: a
slow decode wants more budget, a throw is a totality violation and more budget
would HIDE it. Raising that timeout without knowing which would risk masking the
exact bug the test exists to catch, so the 2000 ms budget is left where it is.

The conflation was structural rather than a wording slip:
`completesWithin ms (fun () -> isTotal ...)` returns `false` for a decoder that
threw AND for one that hung, so every assertion built on that pair could only
ever say "hung or threw". Replaced with `decodeOutcome` returning
`Total | Threw of string | HungPast of int`, and `assertDecodeTotal` which names
the mode and, for a throw, includes the exception type and message. Applied to
all five composed call sites. `completesWithin` had no other caller and is
removed; `isTotal` stays for the budget-free property tests.
