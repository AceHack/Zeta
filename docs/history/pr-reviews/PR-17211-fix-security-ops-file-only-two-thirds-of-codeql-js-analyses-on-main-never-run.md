## Description

A finding, not a fix. Filed so it survives the session that measured it; the
remedy is deliberately NOT applied here and the reason is stated below.

MEASURED over the full history of the code-scanning analyses API for
ref=refs/heads/main, category /language:javascript-typescript:

  20,390 analyses total
  13,335 with rules_count == 0   (65.4%)

rules_count 0 means no queries were evaluated, and those uploads carry GitHub
own verdict: error "unsuccessful execution, exit code: 0". The analyses that DO
run are unmistakable by contrast -- rules 103 / results 61, every time. No
middle band, so this is not a threshold judgement.

CAUSE: .github/workflows/codeql.yml:166-171 sets
group: codeql-${{ github.workflow }}-${{ github.ref }} with
cancel-in-progress: true. That is right FOR PULL REQUESTS, which is what its
comment describes. On main every push shares refs/heads/main, so each push
cancels the previous commit baseline, and pushes land faster than an analysis
completes. Confirmed on a second, independent surface: of the last 99 completed
codeql.yml runs on main, 61 cancelled (62%), 38 success.

CAUGHT IN THE ACT, ON SECURITY WORK. Not inferred from a ratio -- it happened
to the tranche that found it, three times in one hour:

  34427573531  4dc0a3714  in_progress  <- PR #17175, a js/xss-through-dom FIX
  34427150554  a7d8a9086  cancelled    <- carried four merged security fixes
  34427065475  12170c610  cancelled    <- PR #17203 (shell injection)
  34426765814  54ec04844  cancelled    <- PR #17201 (TOCTOU)

Read the top two together: one security fix merging cancelled the analysis that
would have verified four other security fixes. The lane is self-defeating under
exactly the load it exists to handle -- the busier the security work, the less
of it gets analysed.

Consequence for this tranche, stated so nobody misreads it later: alerts 557,
558, 576, 577 and 288 are still open with fixed_at null after their fixes
merged. That is NOT evidence the fixes failed. Nothing has looked at them. The
last successful javascript analysis is dac0086974 at 01:32:53Z, BELOW all four
merges.

WHY IT IS THE WORST CLASS. For ~2/3 of pushes, main alert state is a stale
reading presenting as a current one. A fix closure is merely delayed; a NEWLY
INTRODUCED defect is invisible for the same interval, and that direction is the
dangerous one. results: 0 is a check that did not run wearing the appearance of
one that passed -- the class lint-no-clean-sarif-for-skipped-analysis.ts was
written for on 2026-08-27, after a synthetic clean SARIF falsely closed 102
alerts across 14 rules.

THE PROTECTION IS NOT OURS. These uploads do not close alerts today only
because GitHub marks them unsuccessful and declines to act on them. Nothing in
this repo produces that. Depending on an upstream implementation detail for a
security invariant is a standing exposure even while it holds.

REMEDY, NOT APPLIED. One line at codeql.yml:171 -- make cancel-in-progress
conditional on the event being a pull_request. It preserves the PR force-push
behaviour the comment asks for and stops main pushes cancelling each other;
cost is concurrent runs on main, i.e. minutes.

Left unapplied for two reasons, the second load-bearing: (1) CI workflow wiring
is the devops lane, this lane audits what is wired; (2) a concurrency change
cannot be verified inside the session that makes it -- confirming it requires
watching several main pushes NOT cancel each other, and the evidence channel
for that is the very channel being repaired. Shipping it and declaring it fixed
would be asserting the conclusion on the instrument under repair.

HOW TO CHECK IT WORKED, once applied: re-run the measurement above. The ratio
is the falsifier -- if rules_count == 0 does not fall well below 65% of
javascript analyses on main over the following day, it did not take. A green
workflow run is NOT the check: cancelled runs already report a conclusion.

**Update: the remedy is not a hypothesis. A controlled A/B is already running.**

A sibling workflow already uses the proposed configuration, on the same branch,
under the same push rate, with a same-shaped concurrency group:

```
scorecard.yml:68-70   group: ${{ github.workflow }}-${{ github.ref }}
                      cancel-in-progress: FALSE

codeql.yml:170-171    group: codeql-${{ github.workflow }}-${{ github.ref }}
                      cancel-in-progress: TRUE
```

Last 99 **completed** runs of each on `main`:

| workflow | `cancel-in-progress` | cancelled | success |
|---|---|---|---|
| `scorecard.yml` | `false` | **3 (3%)** | 95 |
| `codeql.yml` | `true` | **61 (62%)** | 38 |

Single differing variable. The remedy stops being "a change I believe will
work" and becomes "make it match its sibling, which has been running that way
all along."

**And the asymmetry runs the wrong way.** Scorecard finds cheap supply-chain
posture and runs 95/99; CodeQL finds dataflow -- injection, TOCTOU, XSS,
prototype pollution -- and runs 38/99. The cancellation is severity-weighted
toward the deeper analysis.

This tranche is the worked example: every `PinnedDependenciesID` closure was
confirmable within minutes (690/714 at 01:41:42Z, 782/783 at 02:07:27Z), while
every `js/*` closure from the same hour is still `unknown`. The dispositions
differ by which scanner had to run, not by anything about the fixes.

Still FILE ONLY -- better evidence for a remedy is not authorization to apply it.
