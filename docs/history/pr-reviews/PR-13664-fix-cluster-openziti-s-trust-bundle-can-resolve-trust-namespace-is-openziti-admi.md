## Description

openziti's trust Bundle can resolve — the trust namespace is `openziti`, and the admin Secret has a real source.

Two blockers deferred `oz` on 2026-08-22, hours after #13471 made the
Application render for the first time. Both are fixed at their source and the
deferral is deleted rather than left to outlive its cause.

BLOCKER 1 — THE TRUST BUNDLE COULD NEVER RESOLVE, AND IT FAILS THE SAME WAY ON
METAL. ziti-controller 3.1.1 renders a trust-manager `Bundle` sourcing
`secret: ziti-controller-edge-signer-secret`, which cert-manager mints into
`openziti`, while trust-manager was pointed at `cert-manager`. Measured against
the PINNED chart rather than assumed: at trust-manager v0.15.0 the Bundle CRD's
only served version (`v1alpha1`) documents both source kinds as read "in the
trust Namespace" and has NO per-source `namespace` field; `deployment.yaml:86`
passes a single `--trust-namespace`; and `role.yaml` creates the Secrets-reading
Role in that namespace ALONE — so it is an RBAC boundary, not a lookup default.
Of the three candidate fixes, the one the pinned version supports is the one
upstream names: ziti-controller's own README:33 says "You must set the Trust
Manager's 'trust namespace' to the namespace of the Ziti controller".

  * `app.trust.namespace: openziti` on BOTH surfaces that install this chart —
    the ArgoCD Application and the k3s first-boot HelmChart. They share a Helm
    release name and namespace; a disagreement would have the two reconcilers
    flipping the flag against each other.
  * Diffing the two renders shows exactly three lines move: the Secrets Role,
    its RoleBinding, and the flag. trust-manager still RUNS in `cert-manager`.
  * The cost is stated where it is paid: the trust namespace is a cluster-wide
    singleton and openziti now spends it. Affordable on a checked fact, not a
    hope — `kind: Bundle` appears nowhere else in the tree and
    `defaultPackage.enabled` is false, so openziti is trust-manager's only
    consumer. A second consumer makes this a real conflict, and the answer then
    is a version whose sources can name their own namespace.
  * ORDERING, which the move creates: that Role lands at sync-wave -45 and a
    Role into a missing namespace is a sync failure. `k8s/bootstrap/openziti-
    namespace.yaml` creates it on metal (it sorts before
    `trust-manager-install.yaml`, now asserted rather than merely true), and
    `applyDevBootstrapSecrets` does it in the dev lane.

BLOCKER 2 — DECIDED: the chart keeps `useCustomAdminSecret: true` and the Secret
gets a real source, which is the mechanism that already exists. `oz` is the
SAME shape as Grafana's `existingSecret` one Application over, so
`DEV_ZITI_ADMIN_SECRET` joins `DEV_BOOTSTRAP_SECRETS` and is minted per cluster,
drawn fresh, never committed. No `ExternalSecret`, no invented Vault path, and
nothing mounts a Secret nothing creates.

Letting the chart generate one instead is not the cheaper option, it is a worse
one, and that is measured: `secrets.yaml` builds the password from `lookup` with
a `randAlphaNum 32` fallback, ArgoCD's repo-server templates with no cluster, so
two `helm template` runs of the same chart at the same values differ in
`admin-password` — under `selfHeal: true` that rotates the controller's
credential every reconcile.

STILL OPEN, NAMED NOT HIDDEN: `ziti-controller-trust-domain` has the identical
`lookup`-with-random-fallback shape, so this Application will sit OutOfSync and
selfHeal will rewrite the fabric's SPIFFE trust domain on every reconcile. It
does NOT block health (kubelet resolved the env at container start), which is
why `oz` is asserted anyway. The one-value fix is `cluster.trustDomain`, and
that value IS the fabric's identity namespace — an operator decision, not one to
guess here. Recorded in the manifest with what would lift it.
