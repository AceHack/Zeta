## Description

## What the evidence actually says

I was asked to establish whether heartbeat runs are *failing* or *missing*. Both are true, and they are unrelated.

**Declared schedule:** `*/15 * * * *` (`.github/workflows/agent-heartbeat.yml:19`). So "every 15 minutes" was right.

**Measured fire times**, scheduled runs only, 2026-08-16T00:19Z .. 2026-08-17T00:49Z — 84 runs where the cron declares 100 slots (**16% dropped**):

| hour (UTC) | runs | hour | runs |
|---|---|---|---|
| 00 | 2 | 12 | 3 |
| 01 | **1** | 13 | 3 |
| 02 | 2 | 14–22 | 4 each |
| 03 | 2 | 23 | 4 |
| 04 | 3 | 00 (8/17) | 2 |
| 05 | 4 | | |
| 06 | 2 | | |
| 07–11 | 4 each | | |

Inter-run gaps: min 12, **p50 16**, p90 27, **max 43** minutes against a declared 15.

**Verdict: GitHub is dropping scheduled slots.** This is documented best-effort scheduler behaviour, it predates the lane-carry bug (hours 01–06 dropped slots while ticks were *succeeding*), and it is not fixable from here.

### Ruled out, with how

- **`concurrency:` cancelling queued runs** — ruled out. `agent-heartbeat.yml:26-28` uses `cancel-in-progress: false`, and across 89 runs **zero** have conclusion `cancelled`. Runs also complete in ~3min, well inside a 15min slot, so they never queue behind each other.
- **Auto-disabled by GitHub** — ruled out. `GET /actions/workflows/agent-heartbeat.yml` reports `"state": "active"`, and runs continued throughout.
- **Workflow conditions skipping the job** — ruled out at the workflow level. Every run reached a real `success`/`failure` conclusion; none are `skipped`.
- **My "15 minutes may be wrong" hypothesis** — checked and rejected. The cron really is `*/15`, so the 28min and 30min gaps are genuinely missed slots, not the schedule.

## So what is the actual defect

Not punctuality — a dropped tick is recoverable, because the lane carries unflushed state forward. The defect is that **a missed tick is silent**, so a recoverable 15-minute gap and an unrecoverable multi-hour outage look identical from outside.

The existing cadence check cannot close this, for two independent reasons:

1. **It is switched off by the thing it watches.** "Measure cadence (declared vs actual — detect silent degradation)" (`agent-heartbeat.yml:535`) sits inside the heartbeat job, downstream of "Accumulate unflushed heartbeat state over current main", with no `if:` — so it inherits the default `success()` gate. Across 23:05Z–00:49Z the accumulate step failed on every tick and **the cadence step was reported `skipped` on every one of them.**
2. **It can only see ticks that happened.** It reads `docs/observe-events/*.json` from inside a run. An outage made of runs *not happening* has no run to execute a check inside.

## What this adds

A watchdog **outside** the lane — its own workflow, its own schedule, asking the Actions API about the heartbeat rather than asking the heartbeat about itself.

- **Level-triggered**, never edge-triggered: "how old is the newest success?", not "did a tick just land?". The same dropped-slot behaviour applies to *this* workflow, and a level check that runs late still answers correctly. An edge check would miss the edge and go quiet — reproducing the bug it exists to catch.
- **Threshold 60min**, sized off the measured 43min worst-case *healthy* gap, not the declared 15. Below the noise floor it would fire on GitHub's normal jitter, and an alarm that cries wolf gets muted — a slower way of having no alarm.
- **Two surfaces**: the run goes red (non-zero exit, not `continue-on-error`), and one deduplicated tracking issue is raised/refreshed, because a red run in a repo with 60+ workflows — one of which is often already red — is easy to miss.

## It can fail, and has

The alarm path is the tested part. `assessHeartbeatLiveness` is pure over run records + injected `now`, so outage shapes that are hard to stage in production are reachable from tests — 14 tests, and the negative branches are the point:

- an **empty** API result alarms rather than reading as health (the case that turns a watchdog into decoration: renamed workflow, token missing `actions: read`, API hiccup)
- runs firing but **all failing** alarms
- an **in-progress** or **cancelled** run is not proof of life
- an **unparseable timestamp** is dropped, never defaulted to `now` (which would make a stale lane look fresh)
- a **future-dated** run is clamped to age 0, so clock skew cannot produce a negative age that silences the alarm forever — this repo has already been bitten by exactly that, per the cadence step's own comments about a MINUS 59.6 hour gap
- an unrecognised payload **throws** rather than becoming `[]`, which would be a real-looking finding nobody observed

**Live proof, not just unit tests.** Run against real production API data at 01:21Z:

```
[heartbeat-liveness] NO SUCCESSFUL agent-heartbeat IN 149 MINUTES — last success 2026-08-16T22:52:01.000Z, threshold 60min
[heartbeat-liveness] runs considered: 50
EXIT=1
```

That is the true state of the lane right now, and it is the outage the current tooling reported as nothing at all.
