## Description

build(nix): root flake off EOL — nixpkgs + nix-darwin 24.11 -> 26.05

Stacked on #15573 (root `flake.lock`). Aaron's standing direction:
"anything that's EOL we need to replace and not depend on, we can either
pickup new deps and replce them later or now." This is now.

WHAT WAS EOL, MEASURED FROM #15573's LOCK

  input        declared        locked rev            resolved     status
  nixpkgs      nixos-24.11     50ab793               2025-06-30   EOL 2025-06-30
  nix-darwin   nix-darwin-24.11 fc84389              2025-03-28   EOL with it

The irony is worth stating rather than leaving for a reader to notice:
those two were the ONLY inputs of the six that resolved to a stable value
across `nix flake update`, and they were stable BECAUSE THE RELEASE IS
DEAD, not because anyone pinned them deliberately. A dead branch stops
moving. That is not the same property as a pinned one, and it should never
have read as one.

WHY THIS RELEASE, CHECKED NOT ASSUMED

Per WebSearch 2026-08-26 (`.claude/rules.bak/dep-pin-search-first-authority.md`):
  https://nixos.org/blog/announcements/2026/nixos-2605/
    NixOS 26.05 "Yarara", released 2026-05-30, current stable, supported
    through 2026-12-31.
  https://endoflife.date/nixos
    25.11 "Xantusia" EOL 2026-06-30; 24.11 EOL 2025-06-30.
Cross-checked against the branch list itself — `git ls-remote --heads
https://github.com/NixOS/nixpkgs 'refs/heads/nixos-2*'` tops out at
`nixos-26.05`, and nix-darwin has a matching `nix-darwin-26.05`. So 26.05
is the only release under support today, which is why this goes there
rather than to the intermediate 25.11.

nix-darwin moves in the SAME commit because the branch match is an
eval-time assertion ("nix-darwin and Nixpkgs branches in use must match"),
not a convention.

WHY THE SEQUENCING WAS RIGHT

Locking first (#15573) was deliberate, and this diff is the payoff. The
lock captured what the flake resolved to TODAY, so the upgrade is a
diffable before/after instead of an invisible change:

  flake.lock | 16 ++++++-------

Sixteen lines. Two inputs. Two `original.ref` values and two `locked.rev`
values, and nothing else moved. Without #15573 landing first there would
have been no `flake.lock` to diff, "upgrade nixpkgs" would have been a
one-line `.nix` edit with no evidence of what actually changed underneath
it, and it would have been unreviewable.

WHAT BROKE — ONE THING, NAMED

`nix.useDaemon = true;` in `infra/nix-darwin/configuration.nix`.
nix-darwin-26.05 asserts on it at eval time:

  The option definition `nix.useDaemon' no longer has any effect; please
  remove it. nix-darwin now only supports managing multi-user daemon
  installations of Nix.

The behaviour it asked for is now the only behaviour, so the option is
gone rather than defaulted, and deleting it IS the whole migration — there
is no replacement setting to carry the intent to. Nothing else in the
multi-release jump needed a change: not the three `nixosConfigurations`,
not the four `nixosModules`, not `darwinConfigurations.zeta-mac`, not the
devShell. NO STAGING WAS NEEDED, so none is proposed.

The `--all-systems` run is the load-bearing one: the plain run omits

`nixosConfigurations` live. Both baselines were taken on #15573's tip
before any edit.

THREE-WAY PARITY (GOVERNANCE.md §24 / `scripts/hooks/README.md`)

`nix develop` is one of three paths that must stay equivalent, and that
equivalence was unverifiable while the flake floated. It is checkable now,
so it was checked rather than asserted:

  nix develop --command bash -c 'echo DEVSHELL_OK; command -v kubectl ...'
  rc=0
  install-git-hooks: linked .../commit-msg -> scripts/hooks/commit-msg
  install-git-hooks: linked .../pre-push   -> scripts/hooks/pre-push
  DEVSHELL_OK
  kubectl-1.36.3 / emscripten-5.0.6 / zig-0.16.0

That is the full 1.5 GiB closure realised (196 substituted paths, 2 built),
not a dry run — so every package attr in the 9-substrate byte-lock
toolchain still exists in 26.05, and the shellHook that carries the parity
still fires. `metered`. What is NOT claimed: the pre-upgrade devShell was
only EVALUATED, never realised, so this is evidence that `nix develop`
works on 26.05, not a before/after comparison.

DELIBERATELY NOT IN THIS CHANGE

  * `nixos-hardware` `@master`, and the `nixos-unstable` CHANNEL URL it
    drags in transitively as the lock's `nixpkgs` node. These are not EOL,
    they are UNPINNED BY DECLARATION — #15573's lock pins them today, and
    the next `nix flake update` jumps them arbitrarily again. Changing a
    declared ref is a decision about what this flake tracks; replacing an
    EOL dependency is not. A comment now says so at the declaration site so
    the next reader does not fold them in by reflex.
  * `stateVersion = "24.11"` stays. It is `lib.mkDefault`-applied to
    `system.stateVersion`, which by design records the release a host was
    FIRST INSTALLED with and must not track the nixpkgs pin. Bumping it
    silently changes stateful service defaults on existing hosts. That is a
    fresh-install-scope decision, exactly as `full-ai-cluster/flake.nix`
    treated its own bump ("Already-installed hosts should NOT bump
    stateVersion").
  * `full-ai-cluster/flake.nix`, which is on `nixos-25.11` /
    `nix-darwin-25.11` — itself EOL since 2026-06-30, i.e. two months past.
    It is the next item under the same direction and it is a bigger surface
    (installer ISO, disko, a `nix flake check` in CI). Not folded in.

The doc refs that named the old branch move with it:
`infra/nix-darwin/README.md` and the `darwin-rebuild` invocation comments.
`markdownlint-cli2 infra/nix-darwin/README.md` rc=0 — and that path is NOT
under the `docs/research/2026-*` carve-out, so the rc=0 is a real pass.
