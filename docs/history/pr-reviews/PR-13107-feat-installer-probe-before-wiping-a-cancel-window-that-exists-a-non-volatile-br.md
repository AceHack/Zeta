## Description

Aaron asked to push the destructive path and repair mode forward. R6/R7/R9/R4 land together because they are one path: **probe before you wipe, give a window to stop it, stop looping if it keeps failing, recognise a node we already installed.**

## The safety bug, found while reading rather than looked for

The only thing excluding the boot stick from the wipe scope was a `TRAN != "usb"` test. **A Zeta installer stick behind an NVMe/USB-C enclosure — or in QEMU, where it presents as `vd*` — was IN SCOPE, and the installer would have destroyed itself mid-install.** `ZETA_INSTALL` was stamped on the volume by `configuration.nix:328` and read by nothing. It is now the refusal, with the reason printed.

## The comment that asserted a guarantee the code did not provide

`zeta-first-boot.sh` described a Ctrl-C window before the wipe. There was no `sleep` between the device list and `wipefs` — **the window was zero-width**, and the 10 s it cited is the *role* prompt, not a wipe prompt. The old sentence is **quoted and marked "used to read"** rather than quietly replaced, with a test pinning that form. Fixing the code and leaving the comment would have been the same defect wearing the other hat.

## R7 — the number is not the interesting part

60 s, but the **default** and the **scope** are what matter: it defaults to proceed, any keypress aborts, and **it runs on the zero-typing path too** — that path is exactly where nobody is watching a prompt, which makes it the one place a wrong-disk wipe is both unrecoverable and unwitnessed.

The probe *shapes* it: all in-scope disks `blank` → **10 s** (nothing to consent to losing); foreign data, a prior install, or a probe that **failed** → the full **60 s**. An unreadable disk is treated as a full one.

## R9 — the loop is a reboot loop, so the counter cannot be volatile

Line-oriented ledger on the boot ESP, parsed by **the same parser** from bash and TypeScript rather than two that drift. Three states, and the middle is the point: **an untrusted ledger is not an empty one** — unparseable or non-contiguous opens the breaker, because treating a corrupt counter as zero *is* the infinite loop. A breaker that cannot count (unwritable ESP) reports `blind` and forces the full window rather than reading as closed.

## R4 also closes HWR-2

With no hostname on the ESP the installer generated `node-$(random)` **per install** — so a re-paved node drew a new hostname while keeping its NIC. One physical NIC, two roster entries. **That is the `node-5b2dfa` / `maximdolphin` duplicate in the design doc's own table.** Repair mode recovers the node id read-only and prefers it over generating a fresh one.

`-o ro,noload` is deliberate: a plain `mount -o ro` on ext4 **replays the journal**, which is a write to a disk we have not yet been given consent to touch.

## Why the logic is in shell

The brief preferred TypeScript the shell calls. The shell physically cannot call it here — **the installer ISO ships no `bun` and no `nodejs`, and the repo is not cloned until after the wipe.** A TS module the shell "calls" on the pre-wipe path would have been an unread golden vector. So: shell owns the decisions, TypeScript owns the executable specification, and `disk-preflight-shell-parity.test.ts` **extracts the marked block from the real `zeta-install.sh`, runs it under bash**, and compares both over shared fixtures. Bash-3.2 subset, so it runs on the maintainer's macOS bash.

## R8 is a marked seam, not a guess

A blob bound by `usbUuid` is *provably* undecryptable after reformat — not judgement, but `expectedBindingScenarioOutcome(factor, "reformat_same_stick")` from the existing `credential-binding-model.ts`, which this code **calls** rather than restates. Carrying it forward yields a dead file that looks like a recovered credential: refused. The others survive, but the default binding is the open §5.2 TPM-vs-iSerial question, so carry-forward stays unwired and named.
