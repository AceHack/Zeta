1. No code copying — verbatim imports = plagiarism / theft
   / dishonest engineering even when Aaron authors both
   projects.
2. No name copying — variables, functions, classes, files,
   types. Names carry source assumptions.
3. No historical-context preservation — their history is
   theirs; Zeta's is Zeta's.
4. Internals are privacy-class — generalized 'about'
   framings ARE allowed ('a database-related sibling
   project'); specific identifying details (companies,
   customers, architectures, specific IP, subdirectory
   structures, named experiments) MUST stay inside the
   sibling repo and never leak. Test: would the named
   detail mean something outside the sibling repo? If yes,
   privacy-class.
5. Top-level path only when contextually necessary —
   '../<repo-name>' plus a generalized purpose-line is
   the maximum granularity. Subdirectory paths never
   appear in Zeta documents.
6. Do learn — read the code, internalize patterns,
   generalize abstractions, write Zeta's version fresh
   with no traceable source artifacts.

Why:

- Plagiarism / theft framing — bad engineering even
  when same-author across projects.
- Verbatim shrinks operating scope — sibling repos are
  narrow-focus; Zeta is broader. Imports drag narrow
  assumptions in.
- Privacy concerns about sibling internals — companies,
  customers, contracts, IP details, experiment names
  may only be safe inside the sibling boundary.
- Generalize-first is the engineering discipline — the
  factory extracts generalizable abstractions; sibling
  repos are cases, Zeta is the general theory.
