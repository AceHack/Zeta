## Description

> *"we support the smartcard hsm too, it's attached to this box, there has been some code on this but not from an agent that's attached to this box where we have one plugged in."*

That's the point of this record. The smartcard/HSM support in this tree was written **blind**. This is the first capture taken by an agent running on the box with the devices in the readers.

**Read-only** — enumeration and identification only. No PIN presented, nothing written, no object created or destroyed. A PIN attempt against an initialised token risks lockout, and a measurement isn't worth a bricked device.

## What is actually attached

| reader | device | token | manufacturer |
|---|---|---|---|
| 0 | Yubico YubiKey FIDO+CCID | `PIV_II` | `piv_II` |
| 1 | Identiv uTrust Token Flex → **SmartCard-HSM v4.1** | **`zeta-test-token`** | `www.CardContact.de` |

Both: `PKCS#15 emulated`, flags `login required, rng, token initialized, PIN initialized`. Serials deliberately **not** recorded — the repo is public and a serial identifies a specific device.

So two manufacturers are confirmed **on hardware**, and the SmartCard-HSM is not merely present but **already provisioned for this project**. Nothing in the tree records that anyone did that.

Also measured: `opensc-tool -l` enumerates both readers while `security list-smartcards` reports *"No smartcards found"* on the same box at the same moment. **Two OS surfaces disagree** — a probe consulting only the second would report absence with total confidence.

## What it refutes

`named-probe-from-frost.ts:37` hardcodes `smartcardHsm: false`. On this box that is **factually wrong**.

The hardcode isn't simply an oversight, which is what makes it worth writing down. The header states the discipline it follows — *"A YubiKey / CCID reader does not set `smartcardHsm`"* — a deliberate refusal to infer an HSM from a reader. **That refusal is correct.** The defect is what it wrote instead: the same header says *"Null is unmeasured, not absent"*, and `false` is not null. It asserts **absent** about a device it never looked for.

## The type makes the mistake unavoidable

`Tpm2CaptureState` has six states, `YubiHsm2CaptureState` four — **both including `not-asked`**. `smartcardHsm` is a bare boolean with no way to say "unmeasured", so a mapper that doesn't measure has two options and both are lies.

**And the field is already read with two meanings in one file:**

- `host-seal-profile.ts:145` — `if (capture.smartcardHsm)` → here `false` means **absent**
- `host-seal-profile.ts:163` — `automaticOracleUnprobed` includes `!smartcardHsm` → here `false` counts toward **unprobed**, i.e. *"we did not look"*

One field, two incompatible readings. Its siblings have `not-asked` precisely so this can't happen to them — and `:172` repeats it inside `automaticCheckDidNotRun`, the function whose whole job is telling a check that didn't run from one that ran and found nothing.

## Why it matters

`unseal-path.ts` routes the seal decision through `smartcardHsmAccessible` — a direct read of this boolean — at four decision points including `pkcs11-smartcard`. A hardcoded, unmeasured, now demonstrably wrong value feeds the choice of unseal path. Under the standing constraint that hardware is controlled by the AI after bootup without human intervention, that path is the mechanism replacing a person at the console.

**No fix applied here, deliberately.** Changing the field to a capture state touches ~50 sites across ten files including the seal-oracle decision — a change to make with the suite green, not as a footnote to a measurement.
