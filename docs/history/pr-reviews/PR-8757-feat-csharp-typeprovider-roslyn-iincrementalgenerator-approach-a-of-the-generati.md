## Description

## What

**Approach A** of the "generative C# type provider, no F#" pair — a literal Roslyn `IIncrementalGenerator` (compile-time C# source generator). Approach **B** (#8755, `Zeta.Core.CSharp.SchemaCodegen`) is a plain library you *call*; **A** runs INSIDE the compiler so a consumer just *uses* the generated type with no codegen step and no committed `.cs`. Aaron wanted both "to learn from both."

## The two new projects

- `src/Core.CSharp.TypeProvider/` — netstandard2.0 Roslyn component (`IsRoslynComponent` + `EnforceExtendedAnalyzerRules`). `SchemaSourceGenerator : IIncrementalGenerator` reads every `*.zetaschema.json` provided as `AdditionalFiles` and emits a `public sealed record` per schema with the **same header + shape as approach B** (`// <auto-generated/> … #nullable enable … namespace X; … public sealed record T(csType name, …);`). A tiny dependency-free JSON reader keeps the generator from loading any design-time assembly beyond Roslyn; malformed input becomes a `ZTP001` diagnostic, never a crash.
- `tests/Tests.CSharp.TypeProvider/` — the consumer/proof. References the generator `OutputItemType="Analyzer" ReferenceOutputAssembly="false"`, includes `ImdbName.zetaschema.json` via `<AdditionalFiles>`, and the xunit.v3 test constructs the generated `Zeta.Generated.ImdbName`. There is no `ImdbName.cs` anywhere — **the project compiling at all is the proof the generator ran at compile time.**

Did NOT touch `tests/Tests.CSharp/` (approach B's test project) to avoid conflict.

## netstandard2.0 / analyzer friction — resolved with per-project config only

The global gate was NOT weakened. Each diagnostic resolved legitimately:
- **RS2008** (analyzer release tracking) → `AnalyzerReleases.{Shipped,Unshipped}.md` manifests wired as `AdditionalFiles` (the canonical fix, declaring `ZTP001`).
- **MA0051** (method too long), **CA1859** (return type) → fixed the generator code.
- **GenerateDocumentationFile** off for the netstandard2.0 analyzer (it can't see net10 framework docs); warnings-as-errors stays ON.

## Package pin

`Microsoft.CodeAnalysis.CSharp` **4.14.0**, added to `Directory.Packages.props`, referenced `PrivateAssets="all"`. Pinned to **match** the Roslyn bundled in the net10 SDK (10.0.203 → Roslyn 4.14, verified in the SDK's `Roslyn/bincore`) — an analyzer must not reference a newer Roslyn than the host compiler can load.

## Gate

- `dotnet build Zeta.sln -c Release` → **0 warnings / 0 errors**.
- Consumer test → **3/3 green** (constructs the generated record, asserts fields + `int?` nullability + record value-equality).

## A vs B

- **A buys:** IDE-integrated / "magical" (the type just exists), no committed generated output, zero consumer-side build step.
- **A costs:** real compiler machinery (netstandard2.0, Roslyn pin, analyzer-rule friction), C#-only, doesn't generalize to the other oracles — whereas B is a plain portable library whose IR (`TypeSchema`) is the same one TS/Rust codegen consume.
