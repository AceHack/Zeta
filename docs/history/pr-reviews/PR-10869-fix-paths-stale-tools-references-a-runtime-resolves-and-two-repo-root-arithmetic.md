## The `check drift` failure — diagnosed, and two corrections to the read

**Trigger identified.** `github-settings-drift.yml` fires on `pull_request` for exactly
four paths. This PR touches **two** of them:

- `src/Core.TypeScript/hygiene/check-github-settings-drift.ts`
- `src/Core.TypeScript/hygiene/snapshot-github-settings.ts`

**Both edits stay, and the reason is #10862 itself.** The changed lines include the
tool's own **printed remediation command**:

```
bun tools/hygiene/snapshot-github-settings.ts --repo <R> > <expected>
```

That is the exact reference #10862 found live-hazardous — its ruleset migrations called
that stale path, mutated live branch protection, and died. A detector that *prints* the
stale command re-seeds the defect for the next operator who copies it. Tier 2 by the
brief's definition, not Tier 3.

**The drift itself is not mine and is not touched.** It is live repository settings
disagreeing with the checked-in baseline. Changing repo settings is a gated class.

### Correction 1 — the job cannot fail, and there is no second configuration

Measured, not inferred (run `31925558749`):

```
{"name":"github-settings-drift","event":"pull_request","conclusion":"success"}
```

`github-settings-drift.yml` is **one workflow with one job** (`check drift`) carrying
`continue-on-error: true` at line 71, and **three** triggers — `schedule`,
`workflow_dispatch`, and `pull_request` on those four paths. The path-triggered run is
the *same non-blocking job*; the workflow run concluded **success**. The red is the
job-level check-run conclusion, which `continue-on-error` does not suppress in the
Checks API.

So there are **not** two configurations of this check, and the PR-triggered one does
**not** block. The "detection without enforcement" observation is still correct — it is
just one job, non-blocking on every trigger, not a divergence between two.

## Two errors of mine, and what they changed

**1. I reverted test files wholesale and left a production string they pin.**
The bulk Tier-2 pass touched 16 `*.test.ts` fixtures; I reverted all of them because
fixtures are deliberate test *data*, not defects. But `seed-test-repo.ts:626` (a repo
**description** string, Tier 3 provenance) had also been rewritten, and its test pins it.

**reverted**, not the test.

**2. That failure led me to a third root-arithmetic bug my own checker could not see.**
`seed-test-repo.ts` uses `new URL("../..", import.meta.url)`; my checker only matched
`resolve(dirname(fileURLToPath(...)))` and `join(import.meta.dir, ...)`. Extending it to
the `new URL` spelling found `REPO_ROOT` → `src` and `MANIFEST_PATH` →
`src/docs/bootstrap-razor/SEED-MANIFEST.md` (absent). Both fixed. So the instrument had a
**third** hole beyond the two the positive control caught — the honest reading is that the
control set proves what it covers and nothing more.

I ran `rebuild-legacy-b-id-aliases.ts`, which is a **rewriter**, not a checker — it
modified 3 files in my clone. Reverted immediately; the tree was verified clean and
