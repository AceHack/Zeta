## Description

## The finding, verified — and one correction to it

PR #10779 closed by naming the root cause of both its defects:

> The IR has no canonical evaluator anywhere.

**Verified, and the situation is worse than the note implied.** There is no *canonical* evaluator, but there is no shortage of evaluators. Op semantics are independently re-implemented in roughly **22 places**:

| where | what it is | notes |
|---|---|---|
| `src/Core/ZetaIrNormalizer.fs` `evalOp64` | F#, u64, op-level | used only by `ZetaIrNormalizer.Tests` |
| `src/Core/ZetaIrNormalizer.fs` `evalOp32` | F#, u32, op-level | a **separate transcription**, incl. its own `rotl32` |
| `src/Core.Lean4/Lean4/NormalizerCorrect.lean` `evalOp` | Lean 4, `UInt64` only | the normalizer soundness proof is stated against *this* |
| `tools/Z3Verify/gen-smt2-from-ir.ts` `renderOp` | SMT-LIB, `side="oracle"` | |
| `tools/Z3Verify/gen-smt2-from-ir.ts` `renderOp` | SMT-LIB, `side="interp"` | deliberately distinct expression (`rotlManual` vs `rotlNative`) |
| `tests/cross-verification/_harness/codegen-from-ir.ts` | seven per-language emitters | TS · F# · C# · Rust · Python · Go · Q# |
| `tests/cross-verification/*/_gen/gen.ts` | **nine** per-primitive TS interpreters | one per committed IR, each ~130–150 lines with its own op switch |

**Correction to the brief:** the brief says to check whether a canonical evaluator exists "anywhere", and the honest answer is *partly*. `ZetaIrNormalizer.evalOp64` / `evalOp32` are a real denotation of the full v4 grammar and predate this PR. They are not canonical for three reasons, and the third is the one that matters:

1. They are **op-level**, not program-level — there is no `run : Ir -> word -> word`.
2. They never read `ir.Width`. The width is chosen by *which function the caller calls*.
3. Therefore a caller holding a width-32 IR who calls `evalOp64` gets a **plausible, silently wrong answer**. That is defect 1's exact shape, reachable from the closest thing the repo had to a referent.

So this PR does not introduce semantics that did not exist; it makes the existing semantics **authoritative, program-level, and width-correct**, and pins the incumbent to it.

***

## The empirical result that decided the design

Before writing anything I folded every committed IR over its committed golden vectors with a single width-parametric single-word interpreter:

```
fmix32   w=32 10/10   fmix64    w=64 10/10   lcg32_glibc              w=32 10/10
lcg32_nr w=32 10/10   lcg64_mmix w=64 10/10  murmur3_32_tail          w=32 10/10
nasam    w=64 10/10   splitmix64 w=64 10/10  xoshiro256ss             w=64 10/10
```

**All 9 committed IRs. All 90 golden vectors. One fold.** That is the finding that answers the brief's "is an evaluator the wrong move / are the duplicated interpreters load-bearing?" question: **they are not.** There is no primitive whose semantics required a private interpreter. The ~22 implementations are duplication with no load-bearing divergence — which is precisely the condition under which a referent is worth having and a rewrite is not.

***

## Answers to the four design questions

**1. Where does it live? F#.** Not because the types happen to be there, but because F# makes the defect *unrepresentable*: the match over `ZetaIrV4.Op` is exhaustive and this repo builds with `TreatWarningsAsErrors`, so a future v5 op that nobody taught the evaluator is **FS0025, a build failure**. In a TypeScript string-union switch the `default:` throw is a line you have to remember to write — and defect 2 is what happens when nobody writes it. The text boundary is already guarded by `ZetaIrV4.validate`, which names an out-of-grammar op rather than accepting it, so `runCanonicalJson*` inherits loud rejection for free.

The cost is real and worth stating: the codegen harness is TypeScript and cannot call this in-process. **That cost is actually a feature here** — see (3).

**2. What is it for? (a) reference semantics, explicitly not (b) a runtime.** `run : Ir -> uint64 -> Result<uint64, string>` and nothing else. No state, no control flow, no host interop. The brief warned about drifting from (a) into (b); the guard is that the module has exactly one shape of entry point and no way to grow one.

**3. Does it subsume the existing oracle? No — and it must not be wired into it.** Three questions, three mechanisms:

- `cross-verify-ir.ts` — *do the N generated lanes agree with each other?* (consistency)
- `ir-vs-handwritten.ts` — *does the IR say what the published algorithm says?* (adequacy, via hand ports)
- `ZetaIrEval` — *what does this IR mean?* (**definitional**)

The evaluator is **not an (N+1)th ballot**. It is deliberately not imported by any emitter, because an emitter that called it would stop being an independent observation and start agreeing by construction — `numerology-vs-number-theory.md`'s "one observation counted N times". The shared referent between the F# authority and the TS emitters is the committed `vectors.yaml` corpus, which both are checked against separately. That keeps the two lanes genuinely independent.

**4. Width.** `run` reads `ir.Width`; there is no `run64`/`run32` pair to pick wrongly. Three properties make width-incorrectness *detectable* rather than merely avoided:

- an input outside `[0, 2^width)` is **rejected**, not masked — truncation is how a width mismatch stays plausible;
- a width outside `{32, 64}` is **rejected**, not approximated;
- a shift of width-or-more is **refused**. It is mathematically zero, but .NET masks the shift count (`x >>> 64` on a `uint64` is `x >>> 0`), so rather than encode a divergence no committed IR exercises, the evaluator declines to define it.

***

## The falsifier (`toy-is-free-metered-must-be-earned.md`: this is **metered**)

`tests/Tests.FSharp/ZetaIrEval.Tests.fs`, 13 tests, four parts.

**Golden conformance.** All 9 committed IRs × all 90 committed `vectors.yaml` goldens, both from the value and from canonical JSON. Those goldens were produced by hand-written language ports, so agreeing with them is agreeing with an **independent** oracle rather than with another copy of this evaluator.

**Discrimination — mutated IRs must diverge:**

| mutation | divergences vs goldens |
|---|---|
| op list reversed | **81** |
| any single op dropped (every position, every IR) | **287** |
| evaluated at the other supported width | **69** |
| any single `mul`/`add` constant bumped by 1 (19 sites) | every site diverges |

**Rejection — must fail loudly, never fall through:** an op outside the grammar is rejected *by name* (`frobnicate` appears in the error); an unsupported width is rejected; an over-wide input is rejected; a shift of width-or-more is rejected at both 32 and 64; text valid under no frozen schema is rejected.

**Agreement with the incumbent.** `ZetaIrNormalizer.evalOp64` / `evalOp32` are pinned to the canonical evaluator on every golden, and `ZetaIrNormalizer.normalize` is shown to preserve the canonical denotation at *program* level. This converts the incumbent denotation — and the Lean/FsCheck soundness proof stated against it — from a second unrelated answer into a checked consequence of the referent.

## Mutating the evaluator itself

Six mutations of `ZetaIrEval.fs`, each built and run, then the source restored:

| mutant | result |
|---|---|
| M1 — ignore `ir.Width`, hardcode 64 (defect 1's exact shape) | **7 of 13 tests fail** |
| M2 — fold the ops in reverse | **6 of 13 fail** |
| M3 — drop the last round | **6 of 13 fail** |
| M4 — truncate the input instead of rejecting it | **1 of 13 fails** |
| M5 — accept a shift of width-or-more | **1 of 13 fails** |
| M6 — rotate in the wrong direction | **4 of 13 fail** |
| **restored** | **13/13 pass**, source byte-identical to pristine (`diff -q` clean) |

M4 and M5 each kill exactly one test, which is the correct and honest signature: they remove a *rejection*, and only the rejection test can see that. A mutation that killed many tests there would mean the rejections were entangled with the arithmetic.

## Scope, and what is deliberately not here

- **Widths 32 and 64 only** — the two the repo uses. Anything else is rejected, not approximated.
- **No emitter is rewired.** Making `codegen-from-ir.ts` call this would be a tautology, not a check.
- **Named residual gap:** the evaluator and the emitters are each checked against the goldens, but nothing checks an emitter against the evaluator for an IR that has *no* committed goldens. That is the next rung and it is stated as a gap, not claimed as covered.
- **`runCanonicalJsonAny` widening order** (v4 → v3 → v2 → v1) is a convenience over the existing frozen validators; it adds no new acceptance, since each validator's schema-tag check is unchanged.
