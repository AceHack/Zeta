## Description

# Summary

The certified markdown healer's MD032 pass ("a list needs blank lines around it") inserted a blank line before a **hard-wrapped numeral** — and the inserted blank is what **made it a list**. markdownlint then parsed an ordered list starting at 2007 and failed `MD029/ol-prefix` (`Expected: 1; Actual: 2007`) **on the healer's own edit**. Self-fulfilling: the fix manufactured the defect it believed it was repairing, in an author's prose, and it was the sole failing check on #14371 — the first `drift-sweep` flush on a publication route repaired today after ten days and 1,597 runs of publishing nothing.

```diff
 chosen as the headline property of an installer in
+
 2007. It rhymes with two other things in this record:
```

Closes 081M0QZF4QY087G0R000WKDYFZ (filed in #14380).

## CommonMark already settles the predicate — so the filed rule is not what shipped

The work-item proposed "do not insert blanks when the previous line **ends mid-sentence**". That is a heuristic, and it was checked before implementing rather than after. CommonMark 0.31.2 answers the question outright, and names this exact failure mode while doing so (§Lists):

> "`Markdown.pl` does not allow this, through fear of triggering a list via a numeral in a hard-wrapped line:
>
> ```markdown
> The number of windows in my house is
> 14.  The number of doors is 6.
> ```
>
> […] In order to solve the problem of unwanted lists in paragraphs with hard-wrapped numerals, **we allow only lists starting with `1` to interrupt paragraphs.**"

plus §List items: *"However, an empty list item cannot interrupt a paragraph"*, and an ordered list marker is *"a sequence of 1–9 arabic digits"*.

Conforming to the spec rather than to a punctuation heuristic is the load-bearing choice: **markdownlint parses with micromark**, so a healer that disagrees with CommonMark heals documents into shapes the linter rejects — which is precisely what happened. `canInterruptParagraph` implements the spec rule; `classifyListItems` decides which list-shaped lines are *real* items, and where its two pieces of state disagree it chooses **not-an-item**, because a missed heal leaves drift for the next tick to report while a wrong heal **mints** drift (the harness's closure law).

**The residual is stated because the spec states its own:** a wrapped line beginning exactly `1. ` *does* start a list under CommonMark, and the healer will still insert a blank there. The spec admits it (*"We may still get an unintended result in cases like … but this rule should prevent most spurious list captures"*). Diverging from the parser to dodge it would be the worse bug.

## Two things the filing did not know, both found by measuring

- **The after-pass was implicated too.** On the design brief the healer inserted blanks on **both sides** of the `2016.` line. Guarding only `insertBlanksBefore` would have moved the split, not removed it.
- **A third, previously unobserved instance:** `docs/PRIOR-ART-LIST.md`. The two reported cases are **a class** — every hard-wrapped line whose first token is digits followed by `. ` is vulnerable: years, dates, version numbers, RFC numbers (`… per RFC` / `2119. Which says …`), page and paragraph refs. It was never a `docs/books/` problem, which is also why excluding book prose would have *read* as a fix and left the class alive.

# Spec alignment

No capability under `openspec/specs/` changes. Behaviour of `fixMarkdownText` changes in exactly one direction: it now withholds blank-line insertions it should never have made. The lint profile, the markdownlint job, and `drift (loud)` are untouched; nothing is `continue-on-error`; no document was edited to route around the defect.

# Notes

**`docs/books/` is deliberately NOT excluded here, and that is a decision with a reason** — filed as **081M0R50J09087G0R000AN2QAT** rather than smuggled in:

1. Excluding books would **not have fixed the bug** — the same defect landed in `docs/design/` and `docs/PRIOR-ART-LIST.md`.
2. There is deliberately **one** exclusion list: `md-heal-scope.ts` reads the *linter's* `ignores`, and its header says why — *"A second hand-maintained exclusion list would drift from the first the moment someone edited one and not the other, which is how this class of defect regenerates."* So excluding books means either also **stopping the check** on book prose (coverage loss) or **introducing that second list**. Both are real decisions, neither belongs inside a bug fix.
3. Changing what `drift-sweep` measures on the same tick that unblocks its first publication in ten days would mix two effects in one signal.

The standing question — is markdown lint a *style* contract or a *structural* one, and should REPORTING on authored prose and WRITING to it move together — is written out in that work-item.

Pre-existing and untouched: `sonarjs/cognitive-complexity` reports 17/15 on `classifyLines` in this file on `main` as well as on this branch (the repo's own `lint-typescript.ts` orchestrator passes either way). Not fixed here — it is not this defect and refactoring the fence/frontmatter classifier alongside a prose-safety fix would be the wrong thing to couple.
