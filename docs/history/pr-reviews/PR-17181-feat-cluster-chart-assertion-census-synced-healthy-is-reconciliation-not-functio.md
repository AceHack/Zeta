## Description

## The question, and how it sharpened

> "how many are fully tested green fully green and have some sort of test to make sure it's not vacuous?"

then

> "why can't we attribute when it fails, can we not look at the logs or have some post deploy tests to tell what's working and what's not?"

**The first half was already solved, and I had overstated it.** The lane runs three diagnostic steps on failure — *Name the drifting resources*, *Logs from crash-looping pods, including the PREVIOUS container*, and *Gatekeeper compiled every ConstraintTemplate*. That is how `headscale` and `orleans` were both diagnosed today. Attribution works for **independent** failures; it works poorly only for **cascades**.

## The finding

**`argocd-health-test.ts` carries 72 references to `Synced`/`Healthy` and ZERO post-deploy functional assertions.**

The lane is not silent about the running system — it has `nc -z` probes against kube-dns and spire-server and a `git ls-remote` against the overlay tree. **Every one of them prints `OPEN`/`FAIL` and then `return 0`.** Diagnostics, which is the right shape for a diagnostic; none of them gates. I verified this rather than taking it on report.

So the whole lane asserts exactly one class of thing:

> **`Synced + Healthy` is ArgoCD's opinion about RECONCILIATION. It is not evidence that anything works.**

And the proof is not theoretical — it landed the same day: **all seven Hat Constraints were unapplied in runs that reported green** (#17174). A gatekeeper holding zero policies is a gatekeeper that reconciled perfectly. A post-deploy check would have caught it on the first run; no amount of lane-splitting would have caught it at all.

## What `Healthy` cannot see, structurally

ArgoCD assesses health **per kind**, and has none for Namespace, ConfigMap, Secret, ServiceAccount, RBAC, CRD or Gatekeeper Constraint. Measured over the committed manifests:

| chart | health-bearing | health-blind | tier |
|---|---:|---:|---|
| `deepseek-coder` | **0** | 2 | asserted `Synced+Healthy` |
| `qwen-coder` | **0** | 1 | asserted `Synced+Healthy` |
| `hat-system` | 2 | **30** | asserted `Synced+Healthy` |
| `platform` | 2 | **31** | never applied |
| `kubevirt` | 1 | 10 | manual-sync |
| `cdi` | 1 | 8 | manual-sync |
| `orleans` | 1 | 8 | asserted `Synced+Healthy` |

`deepseek-coder` and `qwen-coder` are inside the lane's 37/37. They were lifted into the asserted set because they "render exactly one Namespace + one ConfigMap between them" — a correct reason to *apply* them, and, unremarked, the exact reason their `Healthy` verdict carries no information.

**Stated precisely, because the overclaim is tempting.** This does *not* say those two are asserted by nothing. `Synced` is real, and `failedSyncMessage` refuses an app carrying ArgoCD's own `SyncError`. It says the **health half is empty** for them, so the whole assertion rests on the sync half plus a condition check that landed today with one day of evidence. Counting them beside `cockroachdb` in a single "37/37" hides that difference.

## The census

```
49 charts, 35 asserted Synced+Healthy, 2 manual-sync, 3 applied-unasserted,
9 never applied, 3 health-blind, 0 with a POST-DEPLOY FUNCTIONAL assertion
```

Generated, never hand-maintained — a census maintained by hand is a dated finding, and a dated finding ages. `helm-unknown` is the honest verdict for a chart Application whose resources are not in this tree; reporting `yes` for them would be the move the census exists to refuse.

## Charts that belong to no job

Aaron: *"there must be a check that fails when a chart belongs to no job — that check is worth more than the split."* Here it is.

Nine directories are applied by no lane. **Two are covered** (`cilium`, `cilium-lb-ipam` — the CNI leg and k3d bootstrap Cilium directly). **Seven are covered by nothing live**: `longhorn`, `ollama`, `vllm`, `gitlab`, `temporal`, `platform`, `game-hosting/gmod` — and that fact lived only in prose inside `ports.ts`.

`NEVER_APPLIED_COVERAGE` now holds it, checked **both ways**: a new never-applied directory with no entry fails, and an entry for a directory a lane now applies fails as **stale**.

**One limit stated rather than quietly fixed:** the census keys on Application *directories*, so `ddns` — a lone CronJob with no `Application.yaml` — is invisible to it. Widening the key would change what every other row means.

## Proposal: six post-deploy functional assertions

`FUNCTIONAL_ASSERTIONS` is empty, and a test pins it at zero — **written to go red the moment the first one lands.** It is a measurement of a gap, not a rule that the gap stays open.

Ranked by what a silent failure costs:

1. **`open-policy-agent` / `hat-system`** — submit a resource a Hat Constraint must REJECT; require the rejection. *This is the failure that already happened.*
2. **`openbao`** — `bao status`, require `Sealed: false`. A sealed store is `Healthy`.
3. **`spire`** — request an SVID for a known entry and require one back. The lane already probes the port and discards the result.
4. **`cockroachdb` / `redis`** — write a key, read it back. Membership and quorum are invisible to pod readiness.
5. **`orleans`** — require the silo to report cluster membership. 8 of its 9 resources are health-blind.
6. **`seaweedfs` / `weaviate`** — PUT then GET. Storage that accepts writes and loses them is the canonical silent failure.

**Shape:** a labelled `Job` in the lane cluster whose completion the step waits on — not a `kubectl exec` from the runner, because the runner is outside the mesh and a check that has to reach in is a check that tests the reaching.

**Cost:** seconds each, reusing images already pulled. The green run finished in **513 s against a 2400 s cap**, so all six fit without touching the cap.

## What this demotes

The per-chart-set split. Its starvation premise is **refuted** (4.7× headroom). What survives is cascade isolation — real but narrow, since attribution already works for independent failures. Design doc keeps its five open questions; the one piece worth landing regardless is in this PR.
