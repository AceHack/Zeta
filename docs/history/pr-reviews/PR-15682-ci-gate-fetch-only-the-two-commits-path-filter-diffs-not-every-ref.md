## Description

> **Stacks on #15678** (the timeout stopgap). Until that merges this PR's diff shows both commits; after it merges this reduces to its own two changes.

## What the diff needs vs what it was fetching

The comment on the Checkout step said the cap was *sized for* `fetch-depth: 0` — so the 5-minute cap in #15678 and this over-fetch were the same decision, and #15678 only bought time. This is the actual fix.

`fetch-depth: 0` makes `actions/checkout` run:

```
git fetch --no-tags --prune origin \
  +refs/heads/*:refs/remotes/origin/* \
  +refs/tags/*:refs/tags/* \
  +<sha>:refs/remotes/pull/N/merge
```

Every branch and every tag at full depth — **81 heads + 359 tags today**. Measured against the real remote:

| fetch | bytes | 
|---|---|
| `fetch-depth: 0` (current) | **297 MB** |
| two commits at depth 1 (this PR) | **162 MB** |

The stated need in the old comment was *"both PR base and head shas for `git diff`"* — that is two commits, and two commits are 162 MB. The over-fetch also **grows with the ref count**, which is why the cap keeps being outgrown; a two-commit fetch does not.

Corroborating evidence from CI itself: **every other job in this workflow already checks out shallow**, completes in ~9s, and does not hang — across hundreds of samples in the same runs. `path-filter` was the only `fetch-depth: 0` job in the file and the only one whose checkout was being killed at the cap.

## Why two commits is provably enough — the correctness argument

The diff is **two-dot** (`git diff A B`), which is a direct tree-to-tree comparison. It does not walk ancestry and **does not need a merge base**. I verified this rather than asserting it, using two commits with *no common history at all*:

```
$ git merge-base $A $B            ; echo rc=$?     # rc=1  (no merge base exists)
$ git diff --name-only $A...$B                     # fatal: no merge base
$ git diff --name-only $A $B                       # f1.txt f2.txt   rc=0
```

So **PR shape is irrelevant to this diff**: long-lived branches, force-pushes, and merge commits in the range all behave identically, because none of them are traversed. This is also why a bounded `fetch-depth: N` would have been the *wrong shape* of fix — N is a guess about branch length, and this is not a guess.

## The silent-wrong-answer risk is closed by construction

The review concern worth taking seriously is a shallow fetch missing an object and the filter reporting a **wrong changed-file set**, silently skipping jobs that should have run. That cannot happen here, and it is verified:

```
$ git diff --name-only <absent-sha> HEAD
fatal: bad object <absent-sha>            rc=128
```

Under the step's existing `set -euo pipefail`, rc=128 **aborts the step and fails the job**. A missing object produces a loud failure, never a wrong answer. I confirmed the guarded line after the diff is never reached when the object is absent.
