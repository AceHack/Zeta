## Description

## `main` is red, and the coordinator's read was right — with one correction

`main` went red on `live kind included Synced+Healthy proof` at `e162ecd3e4` (#13471).
This is **newly-visible truth, not a regression**: making `headscale` and `oz`
renderable made them **asserted for the first time**, and both are unhealthy. Nothing
could see it while they could not render.

The hypothesis to check was: *if both need an operator-supplied value, asserting them
is the bug.* **Measured, that is right for one and wrong for the other**, and the two
need opposite fixes.

| app | verdict | why |
|---|---|---|
| `headscale` | **our defect — fixed** | its entire `config:` block was inert; the container ran with **no `server_url` from any source** |
| `oz` | **genuinely cannot be healthy unattended — deferred** | two independent blockers, one of which fails identically on metal |

## headscale — not an operator-value problem

Rendering the Application against its own `valuesObject`:

- headscale 0.4.0 declares **exactly six** top-level values — `image`, `env`, `service`,
  `ingress`, `persistence`, `postgresql`. **There is no `config` key.**
- the render contains **zero occurrences of `server_url`**.
- `HEADSCALE_SERVER_URL` is emitted by the chart *only* under
  `ingress.main.enabled` (`templates/common.yaml:30-32`), which this Application does
  not set.

So the container was started with no `server_url` at all while the manifest read as
though it had one. Pod: **CrashLoopBackOff, 12 restarts.** This is the **fourth** time
this tree has been bitten by an inert `valuesObject` key — after hindsight's
`postgresql.primary.*`, nats' top-level `cluster:`, and oz's `adminSecret:`.

**The first three were caught by a storage check, and that is the point.**
`rendered-storage-claims.ts` catches an inert key only when that key happens to govern
storage. headscale's governed *whether the process could start*.

Fixed on the chart's own documented path (`env:` — which its `values.yaml` uses and its
init container's config file explains in prose). **The value is unchanged** from what
the manifest always declared; what changed is that it arrives. The other three keys are
deliberately **not** ported — the chart already hardcodes `LISTEN_ADDR` /
`METRICS_LISTEN_ADDR` from the service ports and `IP_PREFIXES` to the same two ranges,
so re-declaring them would put a second copy of a value we do not own beside the
chart's, free to drift.

## oz — two independent blockers, either alone sufficient

**(1) The trust bundle cannot resolve — the observed failure.**
`MountVolume.SetUp failed for volume "ziti-controller-ctrl-plane-cas": configmap ... not found`.
**Not a cert-manager gap**: in the same run all 8 Certificates report *"up to date and
has not expired"*, all 5 Issuers report *"Signing CA verified"*, and the PVC is Healthy.
The chart renders a trust-manager `Bundle` whose only source is
`secret: ziti-controller-edge-signer-secret`. trust-manager resolves Bundle secret
sources from **its own trust namespace**, pinned here to `cert-manager`
(`trust-manager/Application.yaml` → `app.trust.namespace`), while that secret is issued
into **`openziti`**. The namespaces never meet, so the target ConfigMap is never
written and the Deployment can never mount it. The rendered Bundle also declares no
`target.namespaceSelector`. **This fails identically on metal** — a wiring decision
between two charts, not a CI substrate gap.

**(2) The admin credential is operator-supplied by design.**
`useCustomAdminSecret: true` + `customAdminSecretName: ziti-admin-credentials` makes the
init container read `admin-user`/`admin-password` from a Secret this repo deliberately
does not contain, with **no chart-generated fallback rendered**. **Owned plainly:**
#13471 introduced this by making the manifest's own long-standing stated intent reach
the chart, where it had been an inert `adminSecret:` key ziti-controller has never had
in any published version. The intent is correct and is **kept**; its consequence is that
the app cannot be healthy unattended — a reason to stop *asserting* it, not to undo it.

Recorded as **two** because fixing (1) alone leaves a pod that still cannot start. That
is the weaviate lesson this file already carries: *one confirmed cause is not THE cause.*

## Read this part closely: headscale is deferred too, on purpose

Its repair is verified to **render**. It is **not** verified to make the pod **healthy** —
that needs a live kind cluster and this host has no container runtime. The lane captures
pod events but **not container stderr**, so nothing on file discriminates the missing
`server_url` from a second, unrelated cause. The crash is **consistent with** it, not
proven to be it.

Asserting a repair nobody ran is exactly the *check-that-did-not-run-looking-like-one-
that-passed* this lane exists to refuse, and gambling `main` red on it is worse. The
lane still **prints** status for deferred apps, so the exit condition is observable in
the very next run:

- prints `Healthy` → **delete the entry**, the theory is confirmed;
- prints `Degraded` → the theory is **refuted** and the real cause is still unfound.

That is written into the `LIFTS WHEN:` rather than left as an intention.

## New file, and what it is NOT

`inert-valuesobject-keys.test.ts` says its own limit out loud. The **general** guard
compares every Application's `valuesObject` key set against its pinned chart's
`values.yaml`; it needs the chart, and **it is not built here**. This pins the specific
measured facts offline so a revert cannot be silent while that guard does not exist.
*A narrow falsifier that runs beats a broad one that does not.* The general guard is the
real fix for this defect class and is the obvious next piece of work.

## Not established, said plainly

- Whether the ziti Bundle would resolve if trust-manager's scope were widened — the
  second blocker means that cannot be tested in isolation from this tree today.
- The lane's diagnostic gap is real and unaddressed here: **it does not capture
  `kubectl logs --previous` for CrashLoopBackOff pods**, which is why this PR has to
  reason from a render instead of reading the error. Worth fixing, and out of scope for
  a change whose job is to make `main` green.
