## Description

Drives the bug-B fix. Root cause from the captured serial (run 31283198561): in the real CI isohybrid-ISO bake, the **first** ESP write (pubkey) landed but later **inline-content** writes (hostname, wifi) did **not** — and every `mcopy` still exited 0, so the bake reported success and shipped a silently-incomplete boot image (installer then logged "no zeta-wifi-credentials.json … skipping").

**Why not a direct mcopy fix:** the whole TS plan/execute/executor chain is logically correct and non-silent, and the multi-file mcopy pattern lands **all** files against a synthetic FAT locally (verified with qemu-img + mtools 4.0.49, including a tight near-full root dir). The silent drop is specific to the real isohybrid ESP and **not reproducible locally** — so blind-fixing the mcopy layer would be guessing.

**The fix (#9937 discipline — "do not fail" ≠ "do not notice"):** after bake, read the ESP back via `mdir` and **fail loud**, naming any planned write that's absent and dumping the full ESP listing. This (a) stops shipping silently-incomplete images, and (b) converts the un-reproducible silent drop into a **self-diagnosing CI failure** that emits the exact ESP state to finish the root cause.

Defaults **ON for a real (non-injected) executor** — production `prepareBootImage` + the `zeta flash` CLI — and **OFF when a mock executor is injected** (existing plan/execute unit tests, unchanged); override via `deps.verifyEspWrites`. Added 2 tests (all-present → ok; wifi-absent → loud error naming the file). `tsc` clean; file-backed tests **7/7**.

Next CI dispatch of `build-ai-cluster-iso` will now either bake correctly or fail loud with the ESP listing.
