## Description

RESEARCH AND PLAN ONLY. No boot configuration changed. Nothing lands until the human answers the seven numbered open questions in §9 (round-29 discipline: no CI/boot decision lands without human sign-off).

## The answer

Aaron's constraint decided it: *"we don't want to sacrifice that for secure boot."* Declarative desired-state is the fixed point, so Secure Boot had to fit into it.

**It does.** Lanzaboote is a NixOS module — every signing decision becomes a `boot.lanzaboote.*` option in the flake, and `nixos-rebuild switch` signs each generation's Unified Kernel Image as part of ordinary activation.

**Exactly one step stays imperative:** putting each machine's firmware into UEFI Setup Mode from the BIOS menu. That cannot be engineered away — deleting a Platform Key requires an authenticated variable update signed by the OEM's PK private key, which we do not have. systemd's own manual is the citation: enrollment happens *"if the system is in setup mode"* (`man/loader.conf.xml:293`). Identical under every OS on the list.

Effort: ~1 engineer-day of config, one QEMU/OVMF CI scenario, ~15 minutes of firmware ceremony per node. Lanzaboote gets ~90% of the value for ~2% of the work.

## The finding that usually kills this on GPU nodes, and why it does not here

nixpkgs ships `MODULE_SIG = no` and `SECURITY_LOCKDOWN_LSM = no` (`pkgs/os-specific/linux/kernel/common-config.nix:820-823`). Without the lockdown LSM, Secure Boot never forces kernel module signing. **The proprietary NVIDIA driver loads unchanged. `gpu.nix` needs zero edits. No MOK, no shim, no module-signing key.**

Honest counterpart recorded in the doc: the chain of trust ends at the UKI. It does not seal the running kernel.

## Two things reported, not resolved

Per the instruction not to drop a constraint to make Secure Boot fit:

1. **Microsoft's CA in `db` vs. our-keys-only.** Discrete NVIDIA GPUs carry option ROMs signed under the Microsoft UEFI CA. Dropping MS keys risks the GPU's GOP driver; keeping them imports an external centralized authority and materially weakens what Secure Boot buys. A per-host split (control-plane without MS keys) may resolve it — depends on open question 3.
2. **Headless recovery.** Every upstream recovery path begins with "disable Secure Boot in firmware." `bootCounting.initialTries` self-reverts a bad generation without a site visit, but firmware-level rejection has no software remedy. Whether the nodes have BMC/IPMI is the fact that decides the risk class — open question 2.

## Decentralization and the ace question

- `autoGenerateKeys` makes **each node generate its own PK/KEK/db**. No fleet CA, no escrow, no central signing authority — the decentralized shape falls out of the default config. The centralized alternative is named as a disqualifier.
- **ace is not the same crypto shape.** ace is Ed25519 over canonical JSON (`src/Core.TypeScript/ace/signing.ts`); UEFI `db` is X.509 + PE/COFF Authenticode, and sbctl generates RSA-4096. Ed25519 is not a UEFI signature type. They share a *policy* shape (trust roots + revocation ≡ db/dbx), not a mechanism. The doc says plainly: do not build a bridge.
- Upstream seam for later (GOVERNANCE §23): lanzaboote's `Signer` trait has only `LocalKeyPair` and `EmptyKeyPair`. A PKCS#11/YubiKey impl is the biometric-approval path — an upstream PR, never a fork in-tree.

## Unikernel path, costed honestly

Signing a unikernel is the *easy* part — it is one EFI binary. k3s, containerd, Longhorn/iSCSI and a Linux kernel module for the GPU are the program: multi-quarter, for zero Secure Boot gain over lanzaboote. Rejected for cluster nodes; legitimate narrow lane for single-purpose appliances. "Switch to a secure-boot OS" is worse on both of Aaron's axes — Fedora/RHEL/Ubuntu root their trust in a Microsoft-signed shim.

## Debt surfaced, not fixed here

- **Duplicate NixOS trees** — `infra/nixos/` (24.11) and `full-ai-cluster/nixos/` (25.11) both define `common.nix`/`gpu.nix`/`k3s-*.nix`. `zeta-install.sh:1451` installs the latter. Greenfield rule says the stale one goes, but I will not delete another tree on my own read — open question 1.
- **`configurationLimit` unset on a 1 GiB ESP** — unlimited generations on the ESP is a latent disk-full failure *today*, independent of Secure Boot.

## On checks

The proposed check is a QEMU/OVMF VM test asserting the provisioning sequence. It is **not** landing in this PR. When it does, red is demonstrated before green: corrupt a UKI (upstream's `hash-mismatch-kernel-sb.nix` does exactly this and asserts `hash does not match`), and a mutation flipping `boot.lanzaboote.enable = false` must make the `bootctl status` assertion fail. If the scenario passes with Secure Boot disabled, the check is vacuous and does not land.

## Safety

No key material handled, printed, or logged. Key generation happens on the node, by a systemd unit, from declarative config; the private key never leaves `/var/lib/sbctl`. The enrollment commands in §10 are written for Aaron to run — there is no path where an agent enrolls keys.
