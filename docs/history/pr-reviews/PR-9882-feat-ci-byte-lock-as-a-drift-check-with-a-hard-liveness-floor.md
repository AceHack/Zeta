## Description

**Answer to the design question: drift check — with exactly one thing hard.**

**Why drift, not gate:** (1) your architecture — retraction over prevention, CI gates are corporate; (2) `on: push: main` is **post-merge**, so it can't gate anything anyway; (3) **empirically decisive** — this runner printed *"Byte-lock FAILED — divergences found"* when the only cause was `lua5.4: command not found`; **8 missing-tool errors were reported as byte divergences.** As a required gate, one runner without a toolchain blocks all work *and* trains everyone to ignore the signal; (4) a real divergence is usually something you **want to know** (a Zig upgrade changed float rounding), not something to forbid.

**What IS hard — liveness, not the result.** The hazard isn't divergence, it's going **green while verifying nothing**. `exit 2` = fewer than `BYTELOCK_MIN_SUBSTRATES` executed. **Negative control run, not asserted:** with the floor at 99 it exits 2 — *"LIVENESS FAILURE: only 6 substrate(s) actually executed"*.

**Runner defects fixed:** run errors now classify **tooling vs genuine** (a missing toolchain reports `TOOL`, never `FAIL`); and the summary no longer says *"all substrates produce identical trajectories"* — it states **coverage**: *"6 of 7 executed … 1 NOT exercised and therefore NOT verified."* Saying "all" when one never ran is the same overclaim we spent today removing.

Workflow records tool versions (so future drift is attributable to a toolchain change, not the code) and uploads the JSON report as the drift record. 🤖 Generated with [Claude Code](https://claude.com/claude-code)
