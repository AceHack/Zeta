## Summary

The archive lane accumulated again — fourth time (~4,049 branches drained in #6879, 1,132 in #8043, 16 in #9059, 1,229 in #10346). This round was **measured against a fetched tree** rather than assumed, and **both suspected causes were wrong**. What was actually missing is a detector.

## 1. Arming did not stop — there is no change to revert

Five archive PRs looked "never armed" with a clean boundary at 20:26Z. There is no such change, and nothing was re-armed by hand.

`pr-archive-on-merge.yml` **never arms auto-merge** and says so: *"leaves merge/auto-merge handling to the next maintainer or agent pass."* Arming is the **"Auto-merge clean PRs"** step in `agent-heartbeat.yml` — a rate-limited FIFO: oldest-first, `CAP=3` **successes** per tick, filtered to unarmed automation branches. The "boundary" was simply where that queue's drain frontier sat at the moment of measurement.

Confirmed live rather than argued — the 21:07Z tick, watched to completion:

```
[merge] armed auto-merge on PR #13915
[merge] armed auto-merge on PR #13916
[merge] armed auto-merge on PR #13920
[merge] armed 3 of 3 (attempted 3, 7 unarmed in queue)
```

`#13916` and `#13920` merged at 21:08Z; their records are on `main` at `db4613d43`. The only workflow change today (`a8ad6e0a7`, 19:27Z) is a 17-line addition at line 1090 — arming lives at line 614 and was untouched.

**Neither a regression nor a deliberate pause. Queue latency, reported as a state change.**

## 2. The conflict was a two-writer race, not the pairwise-manifest class

That class was already retired when the derived manifest stopped being staged; per-PR shard paths cannot collide. The single CONFLICTING PR (`#13843`) was the **event lane racing soraya's backfill duty** on the same source PR from different bases:

| time | event |
|---|---|
| 18:04:39 | PR #12059 merges |
| 18:04:42 | event lane starts, from a `main` **without** the record |
| 18:05:19 | fetches, opens #13843 |
| 18:08:40 | backfill lane fetches the **same** PR |
| 18:25:04 | backfill copy lands on `main` via #13850 |

Both writers are **already idempotent** — `writeArchive` short-circuits on identical bytes; `writeShard` and the manifest updater both no-op modulo `fetched_at`/`commit_sha`. Idempotency was never the gap. They raced from different bases, and the loser cannot be rebased into relevance: its markdown was byte-identical to main's and its shard strictly staler.

**Batching or serialising the lane would not have prevented this**, which is why this PR does not rebuild the lane.

## 3. What actually accumulated is the silence

A stranded archive PR is **armed**, so the arming step filters it out (`auto_merge != null`); `--auto` can never merge a CONFLICTING PR; and **no reaper existed**. #13843 sat open ~3 hours and was found by hand. So this adds the missing detector:

- `audit-archive-pr-lane.ts` — for each open `automation/pr-archive-<N>` PR, reports **REDUNDANT** when source PR `<N>`'s record is already on `main`. A 60-minute grace window separates the normal race *in flight* from a *stranded* PR, so it does not flap on healthy operation. Pure core with an **injected clock**, so the verdict is a function of (evidence, phase) and replays under DST.
- **Liveness floor** — refuses to pass on an empty index. *"Checked 0 records"* must never read as success; a clean lane and a broken lookup otherwise produce the same empty finding list.
- Wired into the existing soraya archive duty, **non-fatal**. It reports and never closes — whether a record is truly redundant needs a diff a reviewer can read. Detection is a measurement, not a verdict.

## Falsifiers

A third mutation **survived**, and that correction is in the diff: the `0*` zero-strip in the index regex is redundant (`parseInt` already does it), so the comment now says so instead of calling it load-bearing.
