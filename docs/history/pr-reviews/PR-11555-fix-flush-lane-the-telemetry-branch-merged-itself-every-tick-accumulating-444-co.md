## Description

fix(flush-lane): the telemetry branch merged itself every tick, accumulating 444 commits

PR #11528 (`heartbeat/tick-metrics`) failed `agencysignature (PR body)` on a
cross-commit governance disagreement. The reported values were real; the reason
they were reachable was a producer defect, not a check defect.

MEASURED, not inferred:

    git rev-list --count origin/main..origin/heartbeat/tick-metrics   -> 444
    git rev-list --count --merges  (same range)                       -> 164

164 of those are literally `Merge remote-tracking branch
'origin/heartbeat/tick-metrics' into staging-tick-metrics`. `prepare` reset to
`origin/main` and then unioned in the lane's previous staging tip with a real
`git merge`, which records a merge commit whose second parent is that tip's whole
history — including the tip it had itself pushed the tick before. The branch never
reset. It grew, one self-merge per tick.

WHERE THE DISAGREEING VALUES CAME FROM. `origin/main..HEAD` is 100% clean: all 444
commits carry `Credential-Mode: dedicated-agent` / `Action-Mode:
autonomous-fail-open`. But the CI step validates `GET /pulls/{n}/commits`, and for
#11528 that returned 14 commits ALREADY MERGED INTO `main`, authored by Otto, Vera,
otto-shadow and pr-archive-on-merge. All six commits carrying `shared` /
`human-directed` / `autonomous-fail-closed` were among those 14; zero were in the
delta the PR introduces. The accumulated history is what makes them reachable.

THE CHECK WAS LEFT ALONE, DELIBERATELY. It validates the squash preimage, and that
is not a technicality: `squash_merge_commit_message` is `COMMIT_MESSAGES`, so
GitHub really does concatenate every commit message in that list. Landed commit
71444e1cd0 on `main` is 2470 lines carrying 176 identical AgencySignature blocks.
Narrowing the check to `main...HEAD` would make it validate a text GitHub does not
build — reintroducing exactly the false-premise class the workflow header documents
at length, and buying a green check that certifies the wrong artifact. The
disagreement it reported was true of the thing that would land.

THE FIX IS ONE WORD: `--squash`. Same tree, same `-X ours` strategy, same merge
base, no commit and no second parent — the union lands in the index for the flush's
single commit to capture. Telemetry preservation, which is the property the union
exists for, is bit-for-bit unchanged. Simulated over five cycles with another agent
landing on `main` between ticks: 9 commits / 4 merges before, 1 commit / 0 merges
after, identical payload.

Two smaller things fixed with it:

  - `git merge --abort` cannot clean up a failed `--squash` and must not be tried
    first: `--squash` never writes MERGE_HEAD, so abort exits 128 and leaves the
    conflicted index in place. Verified against a real modify/delete +
    file/directory conflict. `reset --hard` is the working cleanup.
  - A ratchet, `accumulatedHistoryError`, now asserts after `prepare` that the
    branch sits exactly on `origin/main`. It fires BEFORE the generator runs, so
    refusing costs zero telemetry — that is the fail-closed point of the lane. An
    unreadable `rev-list --count` arrives as NaN and is refused, never read as
    "zero commits, all clear".

NO HISTORY IS REWRITTEN BY THIS CHANGE. `flush` already force-pushes
`heartbeat/<lane>` every run by design; this only changes what future runs push.
The telemetry payload survives the union either way. What stops being republished
is the redundant commit history of flushes that already landed on `main` as
squashes.

MUTATION (both guards broken, both caught):
  - revert `--squash` to plain `merge`  -> 34 pass / 1 fail (the real-git cycle
    test; the ratchet fired at cycle 2 with "2 commit(s) (1 merge(s))")
  - `accumulatedHistoryError` -> always null -> 32 pass / 3 fail
  - restored: 35 pass / 0 fail; whole directory 173 pass / 0 fail

STILL OPEN, reported not fixed: `GET /pulls/{n}/commits` is capped at 250 by
GitHub and the branch was 444 ahead, so the check could not see all of its own
subject — a silent under-scan. Left for a separate change because it lives in
`.github/workflows/` and is a distinct defect from this one.
