## Description

## What I verified before writing anything

`grep -rn 'lanzaboote|secureboot|sbctl|SecureBoot' full-ai-cluster/ infra/` returns **nothing**. Secure Boot is not wired, not half-wired, and not described anywhere in either NixOS tree. The 2026-08-14 design doc is research; its §9 gates every boot-path change on seven questions the maintainer has not answered. Work item `081M00KTH58087G0R00120WT6F` says so in its own status line.

So this PR lands the half that needs no answers — the desired-state model — and refuses the half that does, out loud.

## The one-place problem, and where it honestly stops

Two descriptions of enrolment state drift, and then nobody can say which is authoritative. The fix is **one declaration plus derivation**, never two descriptions checked for agreement:

- a host declares exactly one fact — `zeta.secureBoot.phase` ∈ `off` / `provision` / `enforce`
- `derivePlan` derives every other setting from it (`modules/secure-boot-phase-model.nix`)

Firmware is the honest exception, and it is not a second description. No software can put its own firmware into UEFI Setup Mode — deleting the Platform Key needs an authenticated variable update signed by the OEM's key — so firmware state is a **measurement**, not a declaration (doc §3.2). `assess` compares a declared phase against an observed one and returns **`unmeasured`** as an outcome distinct from `agree`: a check that never ran must not read as one that passed. Nothing calls it yet; no code in this repo reads an efivar.

## What is implemented vs what is scaffolding

**Implemented:** the phase enum, the derivation, the read-only derived plan, the fail-closed gate, and 18 properties over all of it, wired into CI.

**Scaffolding:** nothing here is connected to a bootloader. The module sets **no `boot.*` option at any phase** — that is a checked property, not a claim.

**UNVERIFIED / unexercised:** lanzaboote itself (no flake input), signing, key generation, enrolment, the firmware ceremony, `sbctl verify`, `bootctl status`, and every claim about how a real node behaves. **I cannot boot a machine and did not.** No `nixos-rebuild` or `nixos-install` evaluated any of this. Nothing in this PR is signed, enrolled, or verified in the Secure Boot sense of those words. What remains untested is the entire runtime half: whether enrolment succeeds on real firmware, whether the NVIDIA option ROM survives, whether a signed generation boots, and whether recovery works headless.

The boot path after this PR is byte-for-byte what it was before it. At the default phase the module contributes one always-true assertion and zero settings.

## Key custody: refused, not decided

Where the PK/KEK/db private keys live at rest, whether Microsoft's UEFI CA enters `db`, and whether signing/enrolment is operator-approved are maintainer decisions (doc §9 Q3/Q4/Q5). An agent writing a default for any of them would be extending authority rather than inheriting it. So:

- `zeta.secureBoot.phase` other than `off` **fails evaluation**, and the assertion message names Q2–Q6 as the blockers.
- `custodyKeys` is an explicit refusal list, and a property asserts no derived plan may name one **or carry anything but a bool/null** — so a key path, a CA name, or a URL cannot be smuggled into the model later. The option type (`attrsOf (nullOr bool)`) independently rejects it.

**The decision I am asking for** is doc §9, and Q4 is the sharp one: §6.4 shows that with root on plain ext4 and no BIOS password, a db private key sitting on disk defeats Secure Boot against anyone with physical access — regardless of what the config says. That ordering question (FDE/TPM before enforcement?) is the maintainer's, not mine.
