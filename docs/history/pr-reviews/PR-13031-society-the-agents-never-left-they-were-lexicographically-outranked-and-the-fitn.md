## Description

**This corrects the audit landed hours ago in #13022**, which said the population *"aged out of the
200-file window"* over one hour. That framing was wrong, and the real cause is simpler and worse.

## The agents were alive the whole time

Over all 3,518 event files: **alexa 1085, otto 1049, soraya 967**, society 403. They were writing
**minutes before the fix was written.**

`readdirSync().sort()` orders by **filename**, and the directory holds **two naming schemes** — agents
write `080d….json` (32-hex ZetaId), the runner writes `society-<base36>.json`. **`"0" < "s"`, so every
society file sorts after every agent file, forever, regardless of time.** Once the loop wrote 200 of
its own, it owned the name-sorted tail permanently.

**Re-verified independently before landing:**

```
name-sorted last 200 : { society: 200 }
time-sorted last 200 : { alexa: 61, soraya: 60, otto: 57, society: 17, junk: 5 }
```

> **A fix that only widened the window would have worked exactly until the loop wrote another 200
> events.**

And the historical **"4" was 3 real agents plus `society` itself** — the loop was already counting
itself back when the population looked healthy.

## A second, independent bug: the fitness proxy saturated

`log(events+1)/log(200)` — **the 200 being the old window size** — exceeds 1 for every agent above
~200 events, so `mu = min(0.95, fitness)` **pinned every agent identical, genomes identical,
`geneticDiversity === 0`.** Normalising by the window's own busiest agent is scale-free and cannot
saturate. **Live: meanFitness 0.4321 (was pinned at 0.6505648066545648), diversity 5.75 (was 0).**

## Population source — reasoning stated, not assumed

The observe-event log minus the runner's own lane, **not heartbeats**: that lane is a *liveness*
signal with no content to score, lives on refs rather than the working tree (**a clone at a tag
couldn't fold it**), and its failure mode is **worse** — **CI writes heartbeats on an agent's behalf,
so an agent that stopped *thinking* still looks present.**

Its own failure mode is named too: an agent that stops emitting disappears even if its process lives.
Correct here — **the society scores contribution, not uptime** — but a real limit.

`SOCIETY_RUNNER_BY` is **one exported constant the runner emits and the loader excludes**, so they
cannot drift. An id-shape guard was also needed: six events carry a leaked test temp dir as their
`by` — **without it the fix would have reported a population of six.**

## The window, made deliberate

**Per-agent membership**, not a global count — presence is a predicate on that agent alone, and **a
global count is a shared budget one chatty writer consumes**, which is what killed it. **Anchored to
the corpus's own `max(at)`, never `Date.now()`.**

**Trade-off named:** because the anchor is the data's own max, **the population cannot drain to zero
by time passing** — if everyone stops, the last 7 days stay the population forever, **a fossil reading
as alive.** That is why the audit also carries a liveness deadline.

> **`slice(-200)` *was* the optimisation that caused the bug** — so if scanning gets expensive, shard
> the directory, don't re-add a count window.

## The falsifier

**A** scans and fails on `population < 2` or `diversity === 0` — **forward-looking: red *before* a
degenerate event is written.** **B** judges *published* events on their own fields, because **a healthy
input doesn't prove the runner used it.** **C** requires generation to move.

B/C are scoped by a **structural marker, not a date** — a date cutover would go red for every tick
between writing and merging. **Two anti-vacuity floors:** a deadline so *"the fix never reached the
loop"* cannot read as a pass, and a regression guard so the newest event must stay marked. **Right now
B and C are honestly empty and say so on stdout.**

**Live, verified independently:** `OK — population=3 (min 2), diversity=5.7507, 3518 files scanned`,
exit 0.

## `generation` — persisted as a fold

Over the runner's own lane, not a sidecar: idempotent, DST-replayable, no second source of truth.

> **The loop's own events are its LINEAGE, never its POPULATION.**

Verified `1 → 2 → 3 → 4`.
