## Description

fix(heartbeat): merge duty was a LIFO stack with a cap, so the tail never merged

`gh pr list` returns newest-first. The selection was `gh pr list ... | head -3`,
which made merge duty a stack: whenever three fresher mergeable PRs existed at
tick time, every older PR was passed over. Not merged slowly - passed over on
every tick, indefinitely.

Observed 2026-08-14T12:36Z: 19 bot PRs stranded, oldest 13 hours, while PRs
created in the preceding 30 minutes merged normally. It is also what turned main
red. `pr-manifest-integrity` failed with "the repair writer has stopped landing"
- but soraya's archive duty had run on schedule and committed the manifest.jsonl
repair at 12:32:05; its PR was in the starved tail. The writer had not stopped.
The queue had. A drift check that reports a stalled writer when the writer is
healthy is pointing at the wrong component, and it pointed there for hours.

Capacity was never the constraint: 3/tick x 2 ticks/hour = 144/day against ~100
PRs created/day. Ordering was.

Three changes:

1. OLDEST-FIRST. The cap becomes a rate limit instead of a queue bound.

2. Filter to UNARMED (`auto_merge == null`). Arming is durable and idempotent -
   an armed PR merges when its checks go green with no further help - so
   re-arming one is pure waste, and spending slots on it is precisely how a cap
   this small starves the tail. The candidate set now shrinks monotonically as
   it is worked, which is what makes 3/tick sufficient rather than merely
   average-case adequate.

3. The cap counts SUCCESSES, not attempts. Oldest-first alone converts
   tail-starvation into head-of-line blocking: three PRs that can never be armed
   (conflicting, failed required check) would occupy all three slots on every
   tick. A failed arming now costs an API call and moves on, bounded by
   ATTEMPT_LIMIT=20.

Also drops a GraphQL call. `gh pr list --json mergeable` is GraphQL, and the
GraphQL budget is the one that binds us; the REST list endpoint is one request,
zero GraphQL points, and already carries `auto_merge`, which the GraphQL path
did not give us at all.

Verified: bash -n on the extracted step; the `[ x ] && break` guards confirmed
exempt from `set -e` in both branches (they are non-final commands in an AND
list); the live jq selection run against the repo; and the head-of-line property
tested with a stub `gh` where the oldest PR always fails - it consumes an
attempt, not a slot, and the next three arm. Queue drained by hand in the same
pass: 20 of 21 open PRs armed, the passkey-auth PR deliberately left for the
maintainer's biometric gate.
