## Description

The claim the USB design rests on: credentials are USB- and machine-specific, so a key lifted off one device is useless on another.

## What was already there, and why it wasn't this

| existing | what it covers | why it isn't the falsifier |
|---|---|---|
| `credential-binding-model.test.ts` | 23 of 24 factor × scenario cells reach real crypto | tests the **model** — scenarios simulated by mutating a fixture context in-process |
| `zeta-creds-persist-restore.test.ts` | `planRestore` with a wrong UUID | also in-process, library level |

So the shipped path — `bun zeta-creds-persist.ts` writes a blob on machine A, `bun zeta-creds-restore.ts` reads it on machine B — had **never once been executed across an identity boundary**. That's precisely the seam where a refusal goes missing: a wrapper swallowing an exit code, a CLI that warns instead of failing, a plan that reports an error and writes the files anyway. This session found that exact shape twice already (the heartbeat's `|| echo` after a pipe, and the node installer's).

## What lands

17 tests spawning the **real binaries**, asserting on exit codes *and* the filesystem:

- **positive control** — same identity restores, and the secret comes back byte-for-byte (a restore that "succeeds" while writing garbage is worse than one that fails, and exit 0 alone can't tell them apart)
- **the falsifier** — bound on A, presented on B → non-zero, decrypt refusal
- **refusal writes NOTHING** — no partial credential left on the foreign device
- **plaintext never appears in output** on refusal
- **uniform refusal** across six wrong-identity shapes, including case-flipped and trailing-whitespace — a near-miss behaving differently from a wild guess is an oracle, and lenient input normalisation is how binding gets loosened by accident
- **two-factor both ways** — wrong device + *right* passphrase is still refused, so a leaked passphrase is one of two factors rather than total compromise
- **tampered and truncated blobs** refused on the *correct* device
- **the RMA tradeoff made explicit** — replacement device can't use the old blob, can be provisioned fresh, and the two are non-interchangeable in **both** directions

## Proven able to fail

Sabotaging key derivation to ignore binding material entirely (passphrase-only, portable key):

```
SABOTAGED:  7 pass / 10 fail
RESTORED:  17 pass /  0 fail
```

A refusal suite that can't detect a removed binding is decoration.

## What this does NOT close

That the machine-identity **factor** is read correctly from real hardware. `getPartitionUuid` shells out to `diskutil` (macOS-only), and no test presents a key to a genuinely different physical machine. That wants a deliberate hardware cycle, not another in-process fixture — named in the file header so this suite's presence isn't mistaken for closing it.
