## 2. The secret-data question, with its citation

**Nothing to migrate, because Vault has never been initialised** (`TOPOLOGY.md` §2; `spire` and `external-secrets` reference it only inside comments, re-verified by grep). That is load-bearing, not incidental — the documented path does **not** cover this deployment:

- OpenBao's **ratified migration policy** (`website/content/community/policies/migration.mdx` @ `v2.6.2`) defines seal / storage / API compatibility and picks one: *"Aim for API compatibility only, with limited seal compatibility when using remaining seal, storage, and plugins."* API compatibility implies **nothing** about whether your barrier-encrypted bytes are readable.
- The **in-place guide** (`docs/guides/migration.mdx` @ `v2.6.2`) caps at *"Vault version 1.14.1 (OSS)"* and warns *"This guide will not work on Vault versions 1.15.0 and newer."* Our chart pins appVersion **1.18.1**.
- Its procedure is a **rolling raft-join** (*"One by one, upgrade the follower nodes first"* → `step-down` the leader). At `replicas: 1` there are no followers and no step-down target — structurally inapplicable, independent of the version miss.
- And the destination config breaks compatibility by construction: *"Because PKCS#11 auto-unseal was not present in Vault v1.14 OSS, it is not expected that it is seal-compatible; manual migration of data between nodes may be required."*

**So: the migration cost is zero today and rises the moment `vault operator init` is run.** That is the strategic content.

## 3. Two defects found by running the checks — named, measured, NOT fixed here

- **`chart-version-unmeasured` is satisfiable by the wrong chart.** `MEASURED_CHART_VERSION` is compared against `targetRevision` alone, with no tie to `(repoURL, chart)`. openbao-helm forks vault-helm's version line, so **both publish `0.29.1`** (measured from both indexes) — the collision is systematic and permanent. Demonstrated above: exit 0, 0 findings, while the audit asserts chart behaviours it never measured.
- **Nothing compares the raft `path` to the chart's data `mountPath`.** They agree on vault-helm (`/vault/data`) and differ on openbao-helm (`/openbao/data`). A copy-paste migration mounts the PVC at one path and writes raft at the other: the pod **is ready**, serves traffic, and loses its raft store on every restart. Silent — and worse than the failures the audit was built for, which at least stayed NotReady.

Both are audit changes, not migration changes; fixing them inside a research PR would put an unreviewed rule in front of the migration it is supposed to protect. Proposed owner: Dejan. They should land **before** any migration PR.

## 4. Also resolved, from primary sources

- **The build cost is gone.** Upstream publishes `quay.io/openbao/openbao-hsm` (46 tags, `2.6.2`, amd64 + arm64) plus signed release assets; the gate is a Go build tag `//go:build hsm && (linux || darwin)`. The seal costs an **image pin**, not a build pipeline. The v2.7.0 external-plugin move still stands.
- **The prior doc's named unknown is answered — conditional yes.** OpenBao supports `{CKM_AES_GCM, CKM_RSA_PKCS_OAEP}`; `tpm2-pkcs11` v1.10.1 `src/lib/mech.c` has **zero** occurrences of `CKM_AES_GCM` and does have `CKM_RSA_PKCS_OAEP`. Intersection = `CKM_RSA_PKCS_OAEP`, which must be **pinned explicitly** because the default is *"best available"* and prefers AES-GCM.
- Still open, each with an owner: the `openbao-hsm` image ships no PKCS#11 module; the PIN cannot live in the HCL (it renders into a ConfigMap) and must go through `BAO_HSM_PIN`; key material must be created **before** init; three TPMs mean three wrapped root keys, which makes single-vs-three-node a **seal-design** input.
