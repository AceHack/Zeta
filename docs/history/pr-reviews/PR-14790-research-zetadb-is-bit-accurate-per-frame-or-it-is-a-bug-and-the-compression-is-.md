## Description

research: zetadb is bit-accurate per frame or it is a bug — and the compression is object generators, not pixel deltas

Aaron 2026-08-24: "i designed the zetadb to be bit accurate per frame for any
emulator, if it can't be it's a bug, this was the point ... the efficient part is
still to come, it requires merkel root like behavior over video codecs for content
based compression over video. different than like mjpeg cause this is not just the
deltas, it's the objects in the scenes that are captured and their generator
functions so each frame can be recomputed from object composition and physical
rules."

"If it can't be, it's a bug" is an INVARIANT, not an aspiration — it names a defect
class, which makes it falsifiable, which makes it the kind of claim this repo
requires a test for.

MEASURED: zetadb appears in 118 files and "deterministic frame" in 110, but
"bit accurate" in ONE and content-based/semantic compression in ZERO. The design
goal Aaron calls "the point" is essentially unwritten and nothing enforces it.

The invariant is load-bearing rather than a nicety: DST replay needs the frame to
be a function of state not of run; content addressing needs bit-identity or dedup
collapses to nothing; and the compression in §4 is only possible if recomputation
is EXACT — approximate recomputation is a lossy codec, exact recomputation is a
generator, and only the second can be byte-locked. Bit-accuracy is the
precondition for the store being a store rather than a cache.

§3 is the missing falsifier and it is cheap: run N frames, persist through ZetaDB,
reload, cmp byte-for-byte. Strengthenings in cost order — same seed across two
processes, two machines, the four language oracles (where a float or collation
difference would surface, as 081KT07NV0008QG0R001YDB73K did for ZSet.ofSeq), and
across store versions. One test promotes the invariant from unmetered to metered.

§4 states why the compression is categorical rather than incremental: MJPEG stores
frames and MPEG stores motion-compensated deltas, both in PIXEL space; this stores
objects + generator functions + rules in SEMANTIC space and recomputes the pixels.
And it is EXACT, which no lossy codec is, because the emulator is deterministic —
recomputation reproduces the bits. "Merkle-root-like" is the dedup mechanism:
content-address the object composition and identical scenes store once, which is
the frame-level form of the 2026-06-09 chip8-memory dedup result.

§5 records that this is ONE MOVE MADE THREE TIMES — build state stores the
generator, a moving heap object stores a path from a stable root, an emulator frame
stores objects+generators. Store the generator, derive the artifact. And the
CHIP-8/ISR orbit reversal is not adjacent to the compression, it is its INPUT
STAGE: decomposing a heap into non-DMA orbits produces exactly the object inventory
the generators need.

Honest limits in §6: object decomposition may be impossible for chaotic titles;
generators can exceed deltas in size so a raw fallback is required and the winner
must be measured per title; "physical rules" for an undocumented Atari is a
research problem where CHIP-8 is plausible; and nothing here is measured at all.
