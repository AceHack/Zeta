## Description

## Two instruments disagreed about the same repo, and both were right

Adjudicated by measurement rather than by picking a winner. **Neither was lying** — and both mechanisms were defects in how the disagreement was *presented*, not in either verdict.

### `build-ai-cluster-iso` — mode 8, FLAPPING

Its concluded runs on `main` that afternoon:

```
success 21:53:34 · failure 21:18:29 · success 20:37:03 · success 20:03:31 · failure 19:07:46
```

A latest-verdict reader sampling at 21:55 says **green**; one sampling at 21:20 says **red**. Both read the truth. A lane whose next verdict is a coin flip has no colour, so it gets its own — green would launder a 90% claim as a 100% one, and red would make an oscillating lane permanently red until the alarm is muted.

**The first live pass then forced a second split**, and this is the part I would not have got right by reasoning alone. One band lumped `pr-manifest-integrity` (**15 of 20** concluded runs failed) together with `agencysignature-enforcement` (**2 of 20**). Those are not the same claim: when a *majority* of concluded runs fail, the newest passing run is the **outlier**, and the lane is broken rather than flaky. Majority-failing is now **RED** with `MOSTLY FAILING: n of m`.

That split immediately surfaced something worth its own attention: **`gate` — the required check — failed 7 of its last 11 concluded runs.**

### The three cadence lanes — the design was right, the rendering was not

You named both readings. **Reading 2 was the mechanism** (the query filters to `?event=schedule`, so a dispatched run can never appear), and **reading 1 is the design I am keeping** — because the alternative is a snooze button: a hand-run proves the code, not the cadence, and letting a manual dispatch clear a scheduled lane's red is a button anyone could press to silence a gate.

What was wrong was **suppressing the contrary evidence**. The producer now fetches both paths and attaches the newer, different-trigger verdict as `supersededBy`:

```
budget-snapshot-cadence | 6d | periodic | run 31959534906 concluded 'failure' ·
  **awaiting scheduled confirmation** — a later workflow_dispatch run concluded 'green'
  at 2026-08-22T17:32Z, NEWER than the verdict above. The verdict reports the DECLARED
  (scheduled) path, which is the stronger claim: a hand-run proves the code, not the
  cadence. This row clears when the next scheduled run passes.
```

Both instruments' answers are now visible in one row, and the row says what would clear it. You were right that if the design is deliberate it has to **say so in the output**.

## Spawn count is the cost, and it is now 2

Your number was the diagnosis: **142.5s wall, 63.2s cumulative API, 9% CPU.** The missing 79s was not network — it was **88 process creations**, each paying an on-access AV authorisation.

`gh api` calls now go through **`fetch`**, with the token resolved once (env first — CI already supplies it — else one `gh auth token`). Same credential, same endpoint, same auth semantics: `gh auth token` is exactly what `gh api` would have used.

| | original | after 160→88 | now |
|---|---|---|---|
| **subprocesses** | 160 | 88 | **2** |
| API calls | 87 | 87 | 114 (periodic checks fetch both paths) |
| wall, my host | ~48s | 6.9s | **4.2s** |

I measured your suggested `gh api --paginate` bulk sweep first and **rejected it**: 600 runs covered only **31 of 80** workflows — heartbeat saturation again — so it re-introduces the window problem for the remainder and buys nothing the direct queries do not. The spawn was the cost, not the call count, which is why the fix removes processes rather than requests.

The transport recognises **only** the exact `gh api <path>` shape; anything with a flag, method or body keeps the subprocess, and the subprocess path stays as a fallback when no token resolves. A transport swap that quietly changed another call's semantics would be a worse bug than the latency it saved.

**Honest limit, unchanged:** I cannot verify the AV-host number from here. `--timing` now reports `114 api calls (114 via fetch, 0 via subprocess)`, so if it is still slow on your host, that line distinguishes "the transport did not engage" from "something else is costing you".
