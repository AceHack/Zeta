## Description

Three verdict-for-evidence substitutions in one record, in
`src/Core.TypeScript/observe/emit-attestation.ts` and `attestation-event.ts`.

1. **The attestor was a plain string.** `process.env.ZETA_AGENT_ID ?? "alexa"`,
   overridable by `--attestor`, copied straight into `by:`. Nothing bound it to a key,
   so any process able to write into `docs/observe-events/` could mint an attestation
   from any persona.
2. **The claim carried no evidence.** `claim: "heartbeat-genuine"` was documented as
   "I verified these events are genuine". What the producer did was list a directory,
   `JSON.parse`, and check that `by`/`at` were strings. The record carried
   `eventCount` and a window and no digest of the events attested — so a verifier
   holding the same event set could not tell whether the attestation referred to it.
   A count is not an identification.
3. **The derived id was never recomputed.** `deriveAttestationId` was correct; the
   only check anyone ran was `^[0-9a-f]{32}\.json$` — a shape check standing in for a
   value check — so one actor could write N self-attestations under N arbitrary ids
   and defeat the G-set dedup the derivation exists to provide.

## It is not hypothetical

Pointing the new verifier at the committed corpus found **eleven records whose
identity fields hold a filesystem path**: **6** with `attestor` = `/tmp/attest-<random>`,
**6** with `attested` = one, **2** with only a `simultaneousParticipants` entry (the
sets overlap — both the "6" and the "11" are correct, they count different fields).
Those are `mkdtempSync` fixture directories, written by a real run and merged to `main`
on 2026-08-17.

Worse than a fixed fake name: `mkdtempSync` mints a **fresh path per run**, so each run
produces a **new apparent witness**. That is a Sybil count anyone can mint for free,
arrived at by accident — and a deliberate one would be indistinguishable.

**One secondhand claim did not reproduce**, and is reported as such:
`src/Core.TypeScript/observe/self-claims.ts` was said to fold `distinctAttestors` from
the attestor field. It does not. `distinctAttestors` occurs only in
`attestation-event.ts` and its own test, and `self-claims.ts` contains no reference to
attestations at all (`git grep -n distinctAttestors origin/main`, tip `3465e2fc57`).

## Ranking, not inflated

No production code consumes `summarizeAttestations` today; only tests import it. The
**current** blast radius is a polluted event log, not a bypassed gate. It is worth
fixing now precisely because `totalStrength` / `distinctAttestors` /
`hasTrioAttestation` are built to be folded into trust later, and every field of that
summary was forgeable by one actor.

## What is added

**`attestation-record.ts`** (new, pure — no fs, no clock, no process):

- `attestedEventsDigest` — SHA-256 over the sorted, deduplicated, nested
  length-prefixed id set. This is what makes the claim name its own subject.
- `verifyAttestationId` — recomputes the id from the record's own fields.
- `attestationSigningBytes` — the canonical form.
- a persona-**keyed** roster, so `otto`'s key cannot speak as `alexa`.
- a three-state verdict — `bound` / `unbound` / `refused` — with **no `ok` boolean**
  a caller could fall through into folding an unattributed record.
- `strength` is **recomputed, not believed**, and is deliberately **outside** the
  signed bytes: signing a derived field would let a signer inflate the one number a
  trust fold multiplies by. `at` is outside too — local time never enters the shared
  fold.

**`verify-attestation-events.ts`** (new, CLI — the only part that touches a disk):
recursive persona-roster discovery over `maintainers/**/ssh-pubkeys.txt` (the
one-level scan in `verify-build-receipt.ts` sees no personas at all), record selection
by `kind` rather than filename, and a `message` subcommand printing canonical bytes for
`ssh-keygen -Y sign`.

**`emit-attestation.ts`**: computes the digest, self-checks its own derived id, **refuses
to run when `--attestor` is not a persona name** (fail closed), **skips peers whose `by`
is not one**, and says on every write that the record is UNBOUND. That last pair is the
guard that needed no cryptography and did not exist.

**`attestation-event.ts`**: `attestedDigest` required; `summarizeAttestations` takes
records paired with their binding verdict and folds **bound ones only**. The type change
produced a compile error at every call site, which is the point.

## Canonicalisation — the signed bytes are not a JSON serialisation

A signature over "the JSON of this record" is a signature over nothing: key order,
whitespace, escaping, and number formatting are all free variables.

So nothing here hashes or signs JSON. `attestationSigningBytes` builds an explicit,
enumerated, length-prefixed concatenation of named **field values** in a fixed order.
Re-ordering the keys, re-indenting, or round-tripping through another serializer is
**structurally incapable** of changing the signed bytes, because the JSON is never an
input. Tested: a compact record and a shuffled, 4-space-indented one parse to identical
signing bytes; participant **order** does not change them and participant **membership**
does; and the bytes are pinned by a hex golden vector (text, per
`no-binary-in-proof-lineage`). Length-prefixing makes the encoding injective — tested
by showing attestor `"ab"`/attested `"c"` and `"a"`/`"bc"` do not collide.

## No private key is created, handled, or required

Signing is **designed and stopped**. `message` emits the canonical bytes; a key holder
signs them elsewhere, key never leaving their agent:

```
bun src/Core.TypeScript/observe/verify-attestation-events.ts message <event.json> \
  --signer SHA256:<fp> > msg.bin
ssh-keygen -Y sign -n zeta.attestation.v1 -f <key> msg.bin
```

The honest consequence: the **`bound` accept path is exercised with a stub verifier**,
because no signature over these bytes can be produced in this repo. Every signature
**refusal** path runs against a real `ssh-keygen -Y sign` blob — including a genuine
`zeta.build-receipt.v1` signature refused here as `namespace-mismatch`, which proves the
cross-protocol replay guard is live. That split is the first thing
`attestation-record.test.ts` says, rather than being left for a reader to discover.

## Disposition of the 11 polluted records — proposed, not decided

**Leave and annotate.** Not deleted, not rewritten: they are real recorded facts about
what this system did, and Memory Preservation (§5) applies to embarrassing history too —
the same call `audit-observe-event-filenames.ts` `FROZEN_LEGACY_NAMES` made. They are
pinned by name in `verify-attestation-events.test.ts` and asserted **refused**, so they
are the falsifier for the persona gate. Emitting retraction events is deliberately not
done here: it is a decision about the ledger, not a fix to this defect.
