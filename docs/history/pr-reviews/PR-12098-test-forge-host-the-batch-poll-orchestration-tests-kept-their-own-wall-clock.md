The previous commit wrote "the same file at 17-18s under 12x CPU contention"
about the timer channel. That number is real but it is not this channel's: it
was measured at the PRE-#12045 tip with a 6s `gh` shim on PATH, so ~18s of it is

to the timers credits this rewrite with the outage's magnitude, which is exactly
the move `toy-is-free-metered-must-be-earned` forbids — a number attached to a
claim it does not support.

Re-measured with the confound removed (post-#12045 tip, so no `gh` on any path,
old test file vs new, 10 competing busy-loops):

  with timers     1150 / 563 / 538 ms      spread 2.1x
  without         393 / 388 / 423 ms       spread 1.09x

So the honest reading, now recorded in the file itself rather than only in a
commit nobody re-reads: the ambient time channel is real and it is worth
removing — it is the file's entire remaining run-to-run variance — but ~83ms of
timer would never have reached a 5000ms cap by itself. It was a secondary
variance source sitting next to a primary one. Both are now gone; only the first
was the outage.

test(forge-host): the batch-poll orchestration tests kept their own wall clock

`test (TS hermetic)` went red on seven PRs at once, all on the same three
`main() — --with-bus-claims` tests, each timing out at exactly 5000ms. The cause
was NOT those tests: it was `main()` reaching the module-level `readPRState()`,
a BLOCKING `spawnSync("gh", ["pr","list", ...])` with a 30s ceiling. spawnSync
stalls the event loop, so bun's 5000ms budget could not fire until `gh` returned.
Reproduced exactly with a 6s `gh` shim on PATH at the pre-fix tip: 6253ms /
5002ms / 5001ms against CI's 5809ms / 5009ms / 5008ms. #12045 already landed the
injection + the single-PR skip, so main is green; this commit closes what that
fix left standing.

Two things it leaves standing.

1. The three orchestration tests drove their assertions with real `setTimeout`
   delays — a staggered `(6 - pr) * 5`ms and two 10ms holds. That is an
   undeclared ambient time channel: bun's per-test budget is wall-clock, so the
   OS scheduler decides how long the file takes, and the out-of-order premise the
   ordering test depends on was only probably true. Measured per-test: 26.8ms /
   44.3ms / 11.4ms idle, and the same file at 17-18s under 12x CPU contention.
   §4 DST and §13 noninterference, and `local-time-never-enters-the-shared-fold`.

   The substrate they schedule on has no timer at all — zero hits for
   `setTimeout|setInterval|setImmediate|Date.now` across
   `src/Core.TypeScript/ferry-throttler/` — so the test can own the clock. Each
   poll now parks until released by name and `settle()` drains microtasks. Same
   three properties, asserted harder: the ordering test now STATES the reversal
   instead of hoping a 5ms stagger survives; the concurrency test checks the
   ceiling after every single release rather than sampling a peak; the clamp test
   pins the dispatch set, not just its size. 38 -> 69 expect() calls, and the
   three tests drop to 1.39ms / 0.26ms / 0.21ms with no wall-clock term at all.

2. All three `main()` tests poll ONE PR, and single-PR runs skip prior-state
   classification entirely. They are hermetic by that shortcut, so they would
   stay green if the injection itself regressed. The added multi-PR test takes
   the >1 branch, where the reader is actually consulted, and asserts the
   injected one is called. Restoring the ambient `readPRState()` call makes it
   time out at 6025ms on a machine with a slow `gh` — the outage, reproduced by
   the guard that now stands where it happened.

Falsifiers, all confirmed red before this landed: ambient reader restored -> the
new multi-PR test times out; `pollAllBounded` returning completion order instead
of input order -> the ordering test fails in 2.07ms; ceiling raised by one -> the
concurrency test fails in 0.35ms. No assertion was weakened.
