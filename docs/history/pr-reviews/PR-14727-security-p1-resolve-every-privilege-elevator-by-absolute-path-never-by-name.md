## Description

## P1 — the biometric approval gate was forgeable by a `PATH` entry

`realBiometric()` is, in `publish.ts:254`'s own words, *"the one gate every op shares"* —
CA creation, Shamir custody, machine onboarding, rotation, revocation, publish. It
established operator presence as `spawnSync("sudo", ["-p","","true"]).status === 0`, with
`sudo` resolved through `PATH`. Aaron's standing constraint is *"nothing operator-run, only
operator-approved via biometric"* — the biometric **is** the authorization. If approval is
established by whichever binary named `sudo` appears first on `PATH`, the authorization is
forgeable and every gated ceremony inherits that.

The channel needed no root and left **no git diff**, so code review, AgencySignature and
byte-lock — all of which watch the repo — could not see it.

## The mechanism, and why `sudo` stays

`src/Core.TypeScript/privilege/elevator.ts` is now the one place an elevator's program path
is decided. It requires a **regular file, root-owned, setuid, and not group/other-writable,
at an allowlisted absolute path**, and never consults `PATH`. The structural check matters
as much as the absolute path: a path in the source is a claim, the `stat` is the evidence.

On darwin the `sudo` allowlist is the **single** entry `/usr/bin/sudo`, and the narrowness
is the point — measured here:

```text
$ ls -lO /usr/bin/sudo
-r-s--x--x  1 root  wheel  restricted,compressed 1580368 Jun 24 22:29 /usr/bin/sudo
$ csrutil status
System Integrity Protection status: enabled.
$ brew info sudo   ->  Error: No available formula with the name "sudo".
```

`restricted` is `SF_RESTRICTED`: with SIP on, that file cannot be replaced by the operator
or by root. No other macOS location has that property, so accepting one would reintroduce
the hole in a smaller form. Linux keeps a short allowlist with `/run/wrappers/bin` first
(NixOS has no `/usr/bin/sudo`) — portability bought with an allowlist of paths an
unprivileged process cannot write, never with `PATH`.

**`LAContext.evaluatePolicy` was investigated and deliberately not adopted.** It is
reachable — an ad-hoc/linker-signed Swift CLI built with `/usr/bin/swiftc` reports
`canEvaluatePolicy(biometrics) = true`, `biometryType = 1` on this host. It was rejected
for three reasons, written into `realSudoGateEffects` so the next reader does not re-derive
them: (1) it does not fix this bug — it returns through the same in-process seam, whereas
this P1 was about the channel that needed no code in the repo at all; (2) it would put a
Swift toolchain on a ceremony path, or an unsigned executable in the repo whose integrity
has no better guarantee than the SIP-restricted binary it replaces
(cf. `clone-at-tag-stays-sufficient`); (3) what it buys is **attribution**, which is the
separate tracked row `081M06DSQ0Q087G0R000H91391`, already reported honestly as
`factor: "unattributed"`.

Honest register unchanged: this gate proves **an operator factor answered on this host**,
never **a human was present**. That is fix (b) in `docs/BUGS.md` and it stays open for
Aminata + Kenji.

## The false suppression is gone

`zflash/setup.ts` no longer carries `eslint-disable-next-line
sonarjs/no-os-command-from-path`. Both halves of its rationale were measured false — no
Homebrew `sudo` formula exists, and *"would already compromise the machine"* conflates
**user** compromise with **root** compromise, when shadowing `sudo` is the escalation
*across* that boundary. The measurements are written where the suppression stood, so the
argument cannot be re-derived. It bit hardest exactly there: that call `sudo tee`s
`/etc/pam.d/sudo`, the very file `analyzeSudoAuthChain` reads to judge the gate.

## The guard, and why not the eslint rule

`lint-no-path-resolved-privilege-elevator.ts`, wired into the **existing**
`lint (structural hygiene)` gate job. It matches on the **argument**, not the callee — which
is the whole design difference. `sonarjs/no-os-command-from-path` was available while this
P1 was live, matched 10 of the 17 sites, and **would not have caught it**: it cannot see
`run("sudo", ...)`, `["sudo"] as const`, or `needsSudo ? "sudo" : "tar"`. Enabling it
repo-wide would have cost 443 triage decisions for a superset that still misses the
sensitive cases.

Non-argv literals (a PAM service name, a shell parser's vocabulary) carry an explicit
`zeta-elevator-not-argv: <reason>` marker. A marker with **no reason does not waive** — an
unexplained suppression is what hid this bug, and there is a test for that.

## What remains unguarded — stated, not implied

- **`*.test.ts` is excluded.** Live privileged test harnesses still run `sudo` by name on CI
  runners; `installer/repair-mode-existing-install.test.ts` alone is ~25 sites.
- **Shell scripts are not covered at all** — not by this lint and not by eslint. Measured:
  **199 `sudo` occurrences in 5 of 31 non-archive `.sh` files** (37 `.sh` files are tracked
  repo-wide; the archived `docs/` copies are not scanned). The lint prints this count on
  every run so the gap stays visible rather than assumed closed. Independent control:
  `git grep -cE '(^|[[:space:];&|(])sudo[[:space:]]' -- '*.sh'` sums to 197 lines across the
  same 5 files.
- **A program name assembled at run time** is invisible to a source-text check. What catches
  that is the resolver's structural refusal, not the lint.
