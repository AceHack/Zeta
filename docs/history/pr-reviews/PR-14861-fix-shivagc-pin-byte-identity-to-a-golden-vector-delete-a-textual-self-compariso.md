## Description

fix(shivagc): pin byte-identity to a golden vector; delete a textual self-comparison

`audit-check-arity` R2 has been red on `main` since #14831, and therefore red on
every open PR. Not a blocker -- `lint-bash-retirement-inventory` is not in
`gate (required)`'s needs -- but a permanently-red check trains readers to
ignore red, which is the failure this repo cares most about.

WHAT R2 ACTUALLY FLAGGED. Not what I first thought, twice. Found by bisection
(comment each assertion, re-run, see which clears it) rather than by a third
guess: line 196, in the NEGATIVE CONTROL --
`Assert.Equal<byte[]>(original, bytes (run (recipeFor program)))`. `original` is
bound to that exact expression, so after the checker's let-substitution both
sides are byte-identical text.

ADJUDICATION: it was CORRECT, not vacuous. At runtime those are two separate
evaluations, so a non-deterministic `run` would fail it. The checker compares
syntax and cannot see that -- and was right not to try to.

But the claim is better made against a THIRD PARTY, which is the other half of
this commit. §4's falsifier had its own defect: the heap stores `run recipe` as
the object's value, so `droppedBytes` traces to `bytes (run recipe)` -- exactly
what `regeneratedBytes` is. Both sides shared one producer, so the test
established determinism of `run`, not the claim in its name (that regeneration
reproduces what was dropped -- impossible while what was dropped is DEFINED as
the regeneration). That is the same defect the author agent had just caught in
the test it replaced, one level subtler.

§4 now pins both sides against a committed hex literal
(`.claude/rules/no-binary-in-proof-lineage.md`: verification artifacts are TEXT).
Neither side is defined in terms of the other, and determinism is checked against
a third party -- which strictly supersedes line 196, so line 196 is deleted
rather than registered in the census. Registering it would have recorded a
syntactic self-comparison no reader can audit.

VERIFIED, exit codes captured directly:
  audit-check-arity   rc=0  (755 files, 155 census self-comparisons, none new)
  ShivaGcRegen tests  rc=0  (5 passed, 0 failed)

MUTATION CONTROL: perturbing the program by one instruction (`add 0 3` ->
`add 0 9`) turns the golden red (rc=1, 1 failed / 0 passed). So the literal is a
check that can fail, not a value copied from the code it judges.

Two process notes. A first test run returned rc=134 (SIGABRT) -- the transient
F# compiler crash another agent hit today; a rerun on the identical tree was
clean, and it reads exactly like a real failure. And a `git checkout --` fired
to undo the mutation clobbered the uncommitted work; re-applied from the edit
record, and the file is now copied to scratch BEFORE any tree-writing command.
