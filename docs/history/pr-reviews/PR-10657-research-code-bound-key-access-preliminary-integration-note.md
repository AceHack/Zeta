## Description

research: code-bound key access - preliminary integration note

Aaron 2026-08-14: "code signing so that only certain code/processes can access certain
keys would be ideal, so that multiple agents on the same machine would have no access to
each others keys, this is the ultimate agent to agent security."

Preliminary only - establishes the shape, the ladder and the seam that already exists;
proposes no implementation.

The central point: this is the rung ABOVE secure boot, not a parallel track. The secure
boot analysis established its own ceiling honestly - the trust chain ends at the UKI and
does not seal the running kernel. Boot integrity says the machine started as intended; it
says nothing about which of four agent cells is asking for a key ten hours later.
Code-bound key access is exactly the extension of the measurement from boot into runtime.

Where we are is L1, and its boundary is weaker than the diagram suggests. A YubiHSM's
domains and per-agent auth keys give CREDENTIAL isolation, not code isolation. Any agent
that can read another's auth credential - same user, same filesystem, a debugger, a core
dump - has that agent's keys. On a shared box with four cells running as one user that is
thin, and the mitigation looks complete precisely because the diagram does not show the
credentials sitting beside each other in one process's reach.

Two candidate mechanisms with real costs: macOS has native keychain ACLs bound to a code
signature; Linux has no standard simple equivalent (IMA/EVM or an LSM label, both real
work, both change failure modes). TPM-sealing to PCRs extended with the code measurement
is strongest and has no credential to steal - but Apple Silicon has no TPM 2.0 (confirmed
by the probe), so it is x86-only, and every legitimate code update becomes a re-seal
ceremony. That last point decides whether it is livable at 20 sites.

The seam that already exists is ace: keygen/sign/verify/trust already ship, so the
question is narrower than "build code signing" - can an ace package signature serve as the
code identity a key policy names? Carried forward from the secure-boot work: ace is
Ed25519 over canonical JSON, UEFI db is X.509 + Authenticode, so this is a POLICY bridge
and not a crypto bridge.

One constraint recorded so it cannot be lost: the policy must name CODE, not KIND OF
ENTITY. "Only this signed binary may use this key" is symmetric and constrains an agent's
own code exactly as it constrains a human's tool; "only agent code needs this restriction"
would be the capture wearing a security hat. Corollary: an agent should be able to bind
its own keys to its own code as self-protection - the same shape as a wallet owner
imposing a ceiling on its own hot key.

Five open questions for the routed task, including whether shipping L1 alone creates a
false sense of isolation, and what a key bound to code means when agent cells ROTATE
through a node.

Docs only.
