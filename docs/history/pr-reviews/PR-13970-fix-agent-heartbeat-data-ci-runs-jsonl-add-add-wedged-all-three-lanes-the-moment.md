## Description

The heartbeat has been red since 22:05:54Z (runs 32601483043, 32602358227) after a long green
streak. All three lanes died in **"Accumulate unflushed heartbeat state over current main"**:

```
prepare-heartbeat-branch: carry unflushed heartbeat state failed: Auto-merging data/ci-runs.jsonl
CONFLICT (add/add): Merge conflict in data/ci-runs.jsonl
```

## What changed

`data/ci-runs.jsonl` reached `main` for the **first time in the repository's history** at
**21:54:47Z** (`7fe1ef1bb`, PR #13955) — between the last green tick (21:52:16Z) and the first
red (22:05:54Z). #13935 had just fixed a `git add` with no `git commit`, so the drift-rate
recorder's appends finally landed. Until then the file existed only on the `heartbeat/*` lanes,
where there was nothing on main to conflict with.

The preparer does `checkout -B <lane> origin/main` then `merge --squash <previous lane>`. Both
sides had now independently **created** the file, so the merge base has neither — add/add, not
the content conflict the earlier members of this class produced.

## One root cause, two independent failure paths

The second symptom is **not** the credential fault it reads as. `flush alexa heartbeats` failed
with `no gate.yml run exists for heartbeat PR(s): #13963, #13962, #13961`. Measured with
`git merge-tree origin/main <pr-head>`: the **only** conflicting path on those three flush PRs
is the same `data/ci-runs.jsonl`. They are `CONFLICTING`/`DIRTY`; GitHub builds no merge ref for
a conflicting PR, so no `pull_request`-triggered workflow — `gate.yml` included — can ever run
on them, and the check correctly reports that `gate (required)` can never report.

It is a **sibling** of the tick failure, not a consequence: in the first red run (32601483043)
all three tick jobs failed and all three flush jobs still **passed**. It surfaced one run later
only because those PRs had to age past `--min-age-min 20`. They need no manual action —
`retire-superseded-flush-prs.ts` closes each once its lane's next tick opens a replacement.

## Not the diagnosis it looked like

Both strings that read like errors in `gh run view --log-failed` are the workflow's own script
text, echoed by the `##[group]Run` header, and **neither was ever emitted**:

- `fatal: empty ident name` — three occurrences, all inside the step's comment documenting the
  *2026-08-16* outage. The step sets `user.name`/`user.email` before the preparer today; that
  fix is present and working.
- `BOTH credentials were refused` — one occurrence, inside the `echo` in the probe's source. The
  probe passed and emitted no warning or error.

Verified by filtering log lines on the ANSI script-echo prefix: zero occurrences of either
outside it.

## The fix

Declare `data/ci-runs.jsonl merge=union` — the eighth member of the heartbeat lane
merge-semantics class. Measured on the live refs rather than assumed:

- append-only — all six commits touching it across main and the three lanes are `+N -0`
- 9 rows across the four copies, **7 distinct rows, 7 distinct `(lane, runId)`** — distinct-rows
  equals distinct-keys, the precondition under which union cannot duplicate a key
- single-writer **per row**: each lane holds only rows whose `lane` field is its own

Stated limit, in the same terms the `data/rs-blocks.jsonl` entry uses: that key uniqueness is
not enforced by any check, and `drift-rate.ts` reads `runId` without folding on it, so a
duplicated row would double-count in the Wilson interval rather than being caught.

## Falsifier

`prepare-heartbeat-branch.test.ts` §"carries a ci-runs log both sides CREATED, keeping every row
exactly once" builds the live divergence from the real row bytes and asserts all three rows
survive exactly once. It reads the **repository's** `.gitattributes`, not a copy, so it
genuinely binds the declaration: removing that one line fails this test and **only** this test
(checked: 14 pass → 1 fail). `union` and not `theirs` is forced by the assertions, since taking
one side drops the other lane's records.
