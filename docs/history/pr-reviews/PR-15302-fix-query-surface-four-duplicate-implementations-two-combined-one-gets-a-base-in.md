## Description

## 1. `zeta { }` — COMBINED. It was carrying a defect, not just a duplicate.

#15249 found that `src/Core/ZetaSqlBuilder.fs`'s `zeta { }` CE evaluates eagerly over a materialized `ZSet` and never builds a `Circuit`. Re-reading those four operators against `ZSet`'s own contract turned a duplication finding into a **bug** finding.

`ZSet`'s array constructor is documented as: *"Construct from an already-sorted-by-key, nonzero-weighted run. Callers are responsible for the invariant; use `ZSet.ofSeq` for arbitrary input."* `zeta { }`'s `select`, `join` and `for` each built a `ResizeArray` in **input order** and handed it straight to that constructor. Three consequences, all reachable from the public API:

- **A non-injective `select` emitted the same key twice** instead of summing the weights. That is not a Z-set. `ZSet.Item` binary-searches, `(+)` sorted-merges and `Equals` compares position-wise, so the result read as a *different* Z-set depending on which operator touched it next.
- **The run was left unsorted**, so `zset.[k]` returned `0` for keys that were present.
- **Weights cancelling to zero were retained**, breaking the no-zero-weight invariant every other `ZSet` producer maintains.

**The fix is deletion, not repair.** Every operator now delegates to `ZSet.filter` / `ZSet.map` / `ZSet.join` / `ZSet.flatMap` — *the same functions* `FilterZSetOp` / `MapZSetOp` / `JoinZSetOp` call in their `StepAsync` (`Operators.fs`). Those primitives `sortAndConsolidate`, which is exactly the invariant the hand-rolled copies dropped. `zeta { }` stopped being a second implementation of the relational operators and became typed surface syntax over the one implementation.

One constraint tightened and it is named in the docstring: `join`'s key now needs `'Key : not null`, inherited from `ZSet.join`'s `Dictionary` probe side. The old `Map.ofSeq` version accepted a nullable key — an accidental capability the circuit path never had.

**Falsifiers:** `ZetaSqlBuilder.Tests.fs` §THE INVARIANT, **five** tests, plus one in §CROSS-SURFACE. Verified by reverting only the operator bodies to the previous implementation and re-running: **6 failed / 3 passed**. They are falsifiers, not descriptions.

**Two costs this delegation inherits — disclosed, pinned, not fixed.** `ZSet.join` sizes its output buffer at `|left| × |right|` rather than by actual matches, and refuses outright when that product exceeds `Array.MaxLength` (~46 341 rows a side) *however selective the key is* — the deleted `ResizeArray` version completed there. Separately `ZSet.flatMap` folds with `acc <- add acc …`, so `for` went from O(N·M) to O(N²·M). Both are pre-existing properties of the shared primitives that `Circuit.Join` and the whole circuit path have always had; delegating **inherits** them rather than creating them. The refusal is now pinned from both sides (§THE INHERITED LIMIT: throws at 46 341², completes at 46 340²) so the boundary is known rather than latent. The fix is a geometrically-grown buffer in `ZSet.join` — a hot-path change that wants a benchmark, so it is named, not attempted at the end of this pass.

## 2. Eager evaluation — kept as an execution MODE, per the brief

Eager evaluation is worth keeping: it answers a one-shot question over relations already in memory without building and scheduling a circuit. So it is now `ToyExecutionMode.Eager` + `ToyEager.run` over the **shared** `ToyPlan`, not a private evaluator.

`ToyLowering.lower` **refuses** `Eager` rather than silently treating it as `Batch`. A quietly-ignored mode argument is the vacuity class — the caller gets a correct answer and never learns the request was dropped.

`ToyExecution.run` is the entry point that **accepts** a mode and routes it; without it `Eager` would be a DU case nothing accepts, since `lower` only rejects it and `ToyEager.run` takes no mode. Every mode test now drives the dispatcher instead of reimplementing a circuit harness beside it. It refuses `Streaming`, which needs a sequence of deltas — a one-shot feed there is Batch wearing a different label.

The genuine sharing is one level below the mode. The four operator closures (predicate, projector, join key, row merge) were inline in `lower`; they are now `ToyOps`, and **both engines call them**. So `Eager ≡ Batch` is structural rather than a coincidence — and `QuerySurface.Equivalence.Tests.fs` §EAGER MODE holds it to that on every plan in the golden file, including the `AsTable` one where the circuit emits a real `IntegrateZSet` and eager emits nothing (`I` over a single tick is the identity — an argument, and now also a test).

**The claim this section could overstate, stated narrowly.** `zeta { }` does **not** build a `ToyPlan`, does not use `ToyExecutionMode.Eager`, and never calls `ToyEager.run` — a `grep` of `ZetaSqlBuilder.fs` returns only comments. It remains its own eager evaluator over its own typed representation; what it stopped duplicating is the **operator semantics**. `ToyExecutionMode.Eager` is the plan-level home for the same capability on the same primitives — a sibling, not a destination. An earlier draft of this PR and of the file header said the eager evaluation in `zeta { }` "is the third execution mode of the shared plan". That was false and is struck.

**What was NOT merged, and why a merge would have been wrong.** `zeta { }` is generic in the row type and takes F# lambdas; `ToyPlan` is closure-free over an erased `ToyRow`, and #15249 §3.1 explains why that closure-freedom is load-bearing — it is the only reason two front ends can be compared for structural equality. Lowering a typed lambda into a `ToyScalar` needs quotation splitting. So the two IRs stay separate and the sharing sits below them, checked by a test that runs the same query through both surfaces with **independently hand-written** predicates and demands the byte-identical Z-set.

## 3. The two stream/table models — SHARED BASE INTERFACE, deliberately not merged

`Circuit.IntegrateZSet`/`DifferentiateZSet` versus `TableStream.toTable`/`toStream`. Measuring them showed they differ in **two independent ways**:

|  | `IntegrateZSet` / `DifferentiateZSet` | `TableStream` |
|---|---|---|
| combiner | `ZSet.add` — abelian group | `Map.add`/`Map.remove` — last-writer-wins |
| idempotent per delta | no (`a + a = 2a`) | yes |
| **fold commutative** | **yes** | **no** |
| table shape | full running-integral sequence | one collapsed snapshot |

**Commutativity is the one that matters operationally.** `toTable [Upsert("k",v); Retract "k"]` is empty; the same two deltas reordered are not. So `TableStream`'s fold **reads receive order** — correct as a local materialization of a stream a node already holds in order, and unsafe as a shared conclusion over deltas that reached different nodes in different orders (`.claude/rules/local-time-never-enters-the-shared-fold.md`). A forced merge would have had to pick one answer here and would have been wrong for one of the two callers.

`IStreamTableDuality` (`src/Core/StreamTableDuality.fs`) carries the one law both satisfy — `ToTable (ToStream t) = t` — and carries the two properties they disagree about as **declared flags that a test measures**. Flipping a flag without changing behaviour fails the build; verified by flipping `TableStream`'s `FoldIsCommutative` to `true`, which turned **2 tests red**.

One flag is unflattering and is declared honestly: `TableDeterminesStream` is `false` for **both** at the snapshot level. The Z-set pair regains invertibility only in its running-integral form (`ZSetStreamTable.integrate`/`differentiate` — tested mutually inverse, and tested tick-for-tick against `Circuit.IntegrateZSet` so it is the value-level statement of an existing operator rather than a third implementation). `TableStream` has no analogue of that form. Declaring the flag `true` on the strength of `D∘I=id` would have borrowed a property from a different framing than the interface states — the vacuity class.

This also closes #15249's §10 item 6, which left the reconciliation open as *"reconcile — or record deliberately that they stay separate."* The answer is both: they stay separate, under a shared interface, with the difference measured.

## 4. `src/Core/Rx.fs`'s phantom header — struck and redirected

The header advertised *"a minimal `IQbservable<'T>` skeleton for expression-tree-based query composition"*. **No such type was ever defined in that file** — the word appeared only in the comment. A header asserting an absent surface is the vacuity class in documentation form: a reader greps, finds nothing, and cannot tell whether the type was removed or never written.

The header now says `IObservable` only, says plainly that the claim was never true, and points at `src/Core.CSharp/Linq/ZetaQbservable.cs`, where #15249 put the real one.

## An adversarial review ran before merge, and found real defects

The diff was handed to a zero-empathy reviewer. It returned **1 P0, 4 P1, 5 P2**; nothing was disputed, and the corrections are in this branch. The findings are more instructive than the fixes, so they are recorded in §11.5 of the design doc. The three that mattered:

1. **The headline claim was false.** `zeta { }` never used `ToyExecutionMode.Eager`. Narrowed everywhere to what is true.
2. **`Eager` was a case nothing accepted** — `lower` only rejects it, `ToyEager.run` takes no mode. `ToyExecution.run` now exists and every mode test drives it.

Plus: a duality assertion that compared two source literals and measured nothing, a commutativity claim that overreached past `Checked.(+)` overflow, an inverted build/probe description, and a miscounted test total. All corrected.

## CI diagnosis and fix (shadow, 2026-08-26)

`build-and-test` was red on **both** `ubuntu-24.04` and `ubuntu-24.04-arm`, in the
**`Test`** step (step 13) — so not the toolchain-install stall, and the identical
failure on two architectures ruled out a runner problem from the start.

**One test failed**, and it was one this PR added:

```
Zeta.Tests.ZetaSqlBuilderTests.join SUCCEEDS just below the threshold
  System.OutOfMemoryException
    at System.Buffers.SharedArrayPool`1.Rent(Int32 minimumLength)
    at Zeta.Core.Sql.ZetaQueryBuilder.Join(...) in src/Core/ZetaSqlBuilder.fs:209
```

**Root cause — the assertion was unsatisfiable by construction.** The test joined
46 340 × 46 340 to sit one row under `Array.MaxLength`. But §THE INHERITED LIMIT's
*own first finding* is that `ZSet.join` rents the whole product rather than sizing
by matches — so "just under the threshold" **is** a request for
2 147 395 600 × `sizeof<ZEntry<int64>>` = **32 GiB in one contiguous block**. A 16 GB
runner cannot serve it; neither can most machines. Deterministic, not a flake.

**The finding this produced.** The disclosed limit *understates* the real one. The
`invalidOp` at `Array.MaxLength` is the boundary callers are **told** about;
allocation is the boundary they actually **meet**, and it binds ~32 GiB earlier.
Every product large enough to be interesting is unusable well before the guard can
fire. Now recorded as item (3) of the `Join` docstring and in the test section prose.

**The fix — the test was wrong, with a falsifier showing the replacement is stronger.**
Exact-boundary success is untestable by construction while the rent is the product, so
the witness now holds the refused input **fixed** at 46 341 rows and shrinks only the
other side to 2. The product falls to 92 682; the input that supposedly caused the
throw is unchanged. It completes ⇒ the guard reads `|left| × |right|`, not either
side's size.

That discriminates **strictly better** than straddling did, which shrank both sides
together and left "large inputs throw" confounded with "large *products* throw".
Mutation test, guard replaced with a size-based `if int64 sa.Length > 46340L`:

| test | under the size-based mutant |
|---|---|
| `join REFUSES …` | **passes** — vacuous, cannot tell size from product |
| `join SUCCEEDS on the very input that was refused` | **fails** — catches it |

`Failed: 1, Passed: 10` (mutant, rc=1) → `Failed: 0, Passed: 11` (restored, rc=0).
The old witness would have survived a mutation the new one kills.

**Nothing was widened.** The refusal test is untouched, no assertion was relaxed, and
`src/Core/ZSet.fs` is byte-identical — the over-reservation stays a disclosed,
deferred hot-path fix, because giving it a geometrically-grown buffer would change
the very refusal semantics this PR deliberately pins.
