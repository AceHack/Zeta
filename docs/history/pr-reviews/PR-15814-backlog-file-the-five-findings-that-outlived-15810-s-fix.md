## Description

backlog: file the five findings that outlived #15810's fix

#15810 fixed a `build-iso` outage and, in doing so, surfaced five things that
were not the outage. They existed only in a task transcript. Filing them.

The one that matters is 081M10ZG61D087G0R001A70F0P, and the reason it outranks
the bug that was actually fixed is an asymmetry worth stating plainly: the argv
oracle #15810 repaired produced a FALSE RED, and it took four hours of a dark
hardware gate before anyone chased it. The etcd firewall gap produces a FALSE
GREEN — `checks.x86_64-linux.k3s-server-join` passes because the TEST opens
2379/2380 that `k3s-server.nix` deliberately closes — and nobody would notice
until a real second control plane refused to join. A red gate advertises itself.
A green one that proves nothing is silent by construction.

Filed, with the falsifier that would close each rather than only the problem:

  081M10ZG61D087G0R001A70F0P  bug  P1  etcd 2379/2380 open only in the harness
  081M10ZG624087G0R003JW3K8E  bug  P2  no `--node-ip` pin (multi-homed etcd)
  081M10ZG62W087G0R002X76P1D  task P2  no SECOND control-plane host exists
  081M10ZG63M087G0R000SG5KV6  task P2  harness-posture-exceeds-product check
  081M10ZG64B087G0R00173PFC0  bug  P3  second dead argv oracle (doubly dead)

Two judgements recorded in the rows, because both change what an implementer
should do:

The closed etcd ports are DELIBERATE, not an oversight. `k3s-server.nix:324`
reasons it out and prescribes a source-scoped host override; the test at
`k3s-server-join.nix:153` independently refuses to change the product. The bug
is not the closed port — it is that the prescribed override has ZERO instances,
nothing says which one to write, and nothing detects the omission. The fix costs
almost nothing: `k3s-server-join.nix:409,412` already probes founder:2379/2380
before joining, and promoting those two lines into a product preflight on the
`k3s-datastore-preflight.nix` pattern turns `MemberAdd request timed out` into a
sentence naming the ports.

And 081M10ZG62W087G0R002X76P1D is arguably the ROOT of the other two, since both
reduce to "a thing a second control plane would need" and there is exactly one
`hosts/control-plane/` directory to put it in. They stay separate — each has its
own falsifier and either is fixable alone — but that row says to read it first,
because expressing a joining control plane will likely surface the others rather
than depend on them.

081M10ZG63M087G0R000SG5KV6 carries the caveat that makes it a joint decision: the
check goes RED the moment it lands, because the violation is real and unfixed.
Landing it alone leaves a lane whose cheapest remedy is an exception entry for
the one test it was built to detect, which recreates the problem while looking
like a solution. It and 081M10ZG61D087G0R001A70F0P are one change.

Nothing here is fixed. (1) is a firewall default on the hardware path and (4)
turns a lane red; both are the maintainer's call. Rows are cross-linked to each
other and to #15810, #15792, #15746, #15673 so the lineage survives.
