## Description

## The gap

PR #10656 replaces an asymmetric safety property — *"the agent structurally cannot amend its own capability"*, which is permanent human authority and therefore capture under manifesto §3 — with a stronger one:

> **Nobody can spend what they do not own.**

Conservation is better than the thing it replaces because it is a property of the ledger and **survives a fork**, whereas "the agent lacks the creation share" holds only while the key distribution is what we believe it to be.

That module's header says plainly that the ledger is not in it. **Nothing enforced it.** This is the ledger.

> **Correction to the brief that routed this work:** #10656 has **not landed** — it is OPEN and `BLOCKED` as of this writing, and `origin/main` still carries the asymmetric `holderKind` version. This PR is independent of it (it touches nothing under `tools/setup/persona-keys/`) and is correct under either outcome, but the premise "PR #10656 landed" was not true when checked.

## Design, and the part that is actually interesting

**Conservation of total supply is a structural tautology of double-entry.** If the fold credits exactly what it debits, the sum is invariant under *any* order, for *any* event set. A "conservation check" that verifies only that is checking its own arithmetic and cannot fail — the `x >= x` shape.

The real content of the invariant is **non-negativity**, and non-negativity is **not** order-independent. Two 60-unit spends from a wallet holding 100 are individually valid against the balance each was signed against, and as an unordered set they fold to −20. **So a G-Set of signed transfers plus a sum does not suffice, and this module does not claim it does.**

### Ordering is required — but only per sender

A wallet can only be driven negative by its *own* outgoing transfers; incoming credits only help. Only the wallet's own key can author those, so it can sequence them alone. Each transfer carries a `seq` and a sender's transfers form a gap-free chain.

This is exactly **Guerraoui, Kuznetsov, Monti, Pavlović & Seredinschi, "The Consensus Number of a Cryptocurrency" (PODC 2019)**: asset transfer has consensus number 1 for singly-owned accounts — it needs *source-ordered broadcast*, not consensus. We implement the sequencing half.

### No mint, by design

Supply is fixed at genesis. A runtime issuance operation needs a key allowed to create value, which is precisely the privileged wallet the brief disqualifies — **named rather than built**. "Top up the agent's budget" is a transfer from a wallet that already holds the units, which is what Aaron's model already says it is. If the funding wallet is empty the top-up genuinely cannot happen, and a ledger that said otherwise would be lying about a real constraint.

This is also what keeps the audit honest: total supply is a **constant** the auditor checks balances against *without re-running the fold*.

### Symmetric

A wallet id **is** an ed25519 public key. No `holderKind`, no species union, and nowhere to store the question — a species registry would have to be built as a second structure that nothing here reads. A test greps the module's code (comments stripped, so the header may still explain *why* the identifier is absent).

## What conservation refuses, and where

| Point | Stops | Binding? |
|---|---|---|
| `admit` | honest overdraft — refuses to produce the document | **Advisory.** Runs on the sender's own machine. |
| `fold` | everyone | **This is the enforcement point.** |

So an offline signer **can** emit an overspending transfer with a real signature over a well-formed document. It **cannot make it count**: every honest replica folds it to nothing, the recipient's balance never rises, and the units never become spendable onward. *"Cannot overspend at all"* would require the signer to be unable to emit the bytes, which no ledger can promise about a machine it does not control.

Underfunded is **deferred, not rejected** — a later credit may fund it, and a replica that rejected permanently would disagree forever with one that saw the credit first. The fold is a **least fixpoint** (monotone operator ⇒ unique by Knaster–Tarski), which is why sender visit order cannot change the result.

## Convergence without coordination — and the honest limit

**Holds for honest senders.** The event set is a G-Set and `fold` is a pure function of it. Evidence: 200 random arrival orders fold to identical balances; a partition/merge across two replicas receiving disjoint halves in different orders converges; each partial view is itself conservative.

**Does not hold silently for byzantine senders.** A wallet can equivocate — two different transfers at one `seq`. The fold freezes that wallet's chain at the lowest such seq and applies **neither** branch (choosing between them *is* consensus). The freeze point is a `min`-lattice, so replicas converge on it without coordination.

**The residual risk, stated plainly:** between one replica seeing branch A and the other branch B, they disagree, and a recipient acting on an unreconciled balance can be defrauded. Closing that window needs source-ordered reliable broadcast (Collins et al., DSN 2020). **That is not implemented here.** Acceptance is consequently not monotone under equivocation discovery — unavoidable, and convergence survives it because the freeze point is a lattice.

## Falsifiability — measured, not asserted

The auditor **never calls the fold**. An auditor that recomputed and compared would be checking the fold against itself. Instead it takes the state's own claims (`balances`, `applied`) and checks them against two things the fold does not choose: the genesis total, and the signed input set. `applied` is read as a **certificate** — a witnessing order in which the state is reachable with no wallet below zero.

**18 ablations planted; 17 kill at least one test.**

fold: debit the sender         ->  9 fail     audit: double-applied        -> 1 fail
fold: signature verification   ->  2 fail     audit: overdraft             -> 1 fail
fold: ledgerId binding         ->  1 fail     audit: negative balance      -> 1 fail
fold: malformed screen         ->  3 fail     audit: balances-vs-applied   -> 1 fail
fold: equivocation freeze      ->  2 fail     audit: chain order           -> 1 fail
fold: slot (sender,seq) key    -> 15 fail     audit: fabricated            -> 1 fail
fold: freeze excl. pending     ->  2 fail     audit: bad-sig applied       -> 1 fail
fold: content-addr dedup       ->  0 fail  <-- SURVIVES (disclosed below)
                                             audit: unaccounted           -> 1 fail

Each audit ablation kills **exactly** its own mutant and no others — a clean 1:1 map, so no check is redundant and none is coasting on another.

Mutants required by the brief, all dying: credit-without-debit (`supply-inflated`), replayed double-credit (`double-applied`), accepted negative balance (`negative-balance` + `overdraft-applied`), silently dropped event (`event-unaccounted`). Plus fabricated transfer, skipped chain position, forged signature, and a balance edited with no event behind it — the last of which keeps the total at exactly 1000, so **only** the independent replay catches it.

**Non-vacuity is structural.** The report carries a `vacuous` flag; the suite asserts `totalTransferred > 0` and pins that an empty corpus reports `ok: true, vacuous: true` — the demonstration that `ok` alone proves nothing.

## What I retracted

**1. One mutant survives, and it is disclosed rather than papered over.** Deleting the content-address dedup map breaks nothing — and *no test can be written that it would break*, because two byte-identical transfers necessarily share a `(sender, seq)`, so the chain-position map subsumes it on every possible input. An earlier draft of the header credited the content address as *the* idempotency guard. **That was wrong**, ablation showed it, and it is corrected in place: `(sender, seq)` is the duplicate guard; the content address earns its place as **tamper-evidence**, which *is* falsifiable. I wrote a test claiming to pin the id-keyed map, found it could not fail, and deleted it — a test that cannot fail is the exact defect class this PR exists to refuse.

**2. Signature verification was untested and I did not notice until I ablated it.** My forgery test mutated `from`, which breaks the content address, so `malformed` killed it before the signature was ever consulted — removing signature verification entirely left the whole suite green. Fixed with the transfer a thief would actually construct: correct `from`, correct content address, every field canonical, signed by the wrong key.

**3. A `toBe(CORPUS[0]?.id)` assertion** that would have compared `undefined` to `undefined` on an empty corpus. Caught by `noUncheckedIndexedAccess`, fixed to assert definedness first.

**4. `admit` computed the next seq from applied-count**, which would reissue the seq of a merely-*deferred* transfer — self-equivocation, freezing a wallet for doing exactly what the ledger told it to. Now counts withheld transfers too, with a regression test.

**5. The linter demanded `localeCompare` for sorts.** Refused — that is culture-**sensitive** and would make two nodes in different locales fold the same event set differently, violating `.claude/rules/culture-invariant-by-default.md`. Replaced with an explicit ordinal comparator that cites the rule.

## Honest scope — what this does NOT do

- **No reliable broadcast.** The equivocation divergence window is real and open.
- **No mint / no top-up-from-nothing.** Deliberate; see above.
- **Not wired into `x402-envelope.ts` or the custody contract.** This PR adds the invariant and its falsification suite only. Wiring the envelope's cap to a ledger balance is the obvious next step and is not claimed here.
- **CI placement, stated because it matters for an investor-facing claim:** TS tests run in gate.yml's `test (TS suite)` job, which **runs but does not block** (`build-and-test` is .NET-only). Promotion to `registry/uncompensatable-floor.yaml` is a treaty amendment and I did not make one.
