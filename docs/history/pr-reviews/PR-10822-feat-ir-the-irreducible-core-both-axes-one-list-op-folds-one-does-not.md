## Description

# The zeta-ir irreducible core: derivability and portability are two different axes

Aaron asked what the minimal op set is — "i think we have some math proof that says all our ops
can be derived from some base two ops" — and then added the constraint that the set was chosen
to be substrate-agnostic, "we even have it working on q# and other exotic runtimes."

This PR answers the instruction-set question **without changing the grammar** (no v5), fixes a
denotation bug it turned up, and replaces a file of tests that could not fail.

## Three corrections to the record

1. **The proof on file says FOUR, not two.** `2026-06-20-lumen-zeta-ir-minimal-generating-set.md`
   proves 6 -> 4 (`mul`, `add`, `xshrxor`, `xrotxor`). There is no two-op result in the repo.
2. **That note's `mul` irreducibility argument is false as written** — "the only operation that
   propagates carries" is wrong, `add` propagates carries too. `mul` is now marked **open**.
3. **The v4 `add` "necessity proof" is an illustration.** The test carrying the name asserts
   `0 + k = k` and three fixed instances of `f 0 = 0`; it never builds an op sequence, never
   calls an evaluator, and passes with `Add` deleted from the grammar.

Smaller correction to my brief: `src/Core/ZetaIrEval.fs` is **not** on `main` — #10807 is still
open — so everything here is checked against `ZetaIrNormalizer.evalOp64` / `evalOp32`.

## The result: the two list ops are not the same kind of thing

Write `R` for shift-right-1 and `X` for rotl-1. Both list ops are polynomials, and both rings
are local because 32 and 64 are powers of two — but `R` is nilpotent and `X` is a unit, and that
single difference decides the question:

* **`XShrXor [s1..sn]` IS a fused fold.** Its polynomial `1 + R^s1 + ...` is a unit, and the
  units of `F2[R]/(R^W)` are generated by the `(1 + R^m)` — i.e. by single-shift `XorShr` ops.
  Greedy elimination gives the factorisation. Executed at both widths; the rewrite of nasam's
  two `XShrXor [23;51]` ops replays the committed `nasam` vectors exactly.
  **The cost is real and measured:** `[23;51] -> 2` ops, but `[1;2;3;5;7] -> 35` ops at width 64.
* **`XRotXor [a;b]` is NOT.** `Rotl` denotes a monomial and monomials are closed under
  composition, so the entire monoid `Rotl` generates is the W rotations — checked exhaustively,
  not sampled. `1 + X^a + X^b` has three terms. Arity 2 is primitive.
* **What the `0` in a list buys:** `XRotXor [0;r]` = `Rotl r`, `XShrXor [0;s]` = a plain shift,
  `XShrXor [0]` = `XRotXor [0]` = the zero map. Those are the non-units, and they are exactly
  what the arity-1 form cannot reach.

`add` keeps the one real necessity argument (the 0-fixing invariant), now with a quantified
falsifier: 4000 random non-`add` sequences at both widths.

## Portability, and why it is the same invariant

`QuantumArithmeticMix.qs.sketch` lifts `xorshr` to a reversible circuit by arguing
`M = I + S^s` is invertible over GF(2) because `S` is nilpotent. That is the same unit condition
— and it generalises: **the F2-unit criterion predicts bijectivity exactly**, 22/22 exhaustive
at width 16. So one theorem decides both "does this list factor" and "can a reversible/quantum
lane carry this op without ancillas".

State of the Q# lane, read from the code (I could not execute it — `qdk` is not installed):
the 7-lane harness `cross-verify-ir.ts` types ops as `{op, k, s}` with no `r`/`rs`/`ss`, and all
seven emitters `return ""` for `rotl`/`xrotxor`/`xshrxor`/`add`; the emitter that does cover all
six ops (`codegen-from-ir.ts`) has six lanes and no Q# lane. **The Q# lane has never executed an
op outside `{mul, xorshr}`.** The Q# oracle itself is real and live for quantum observables —
this is a coverage statement, not a "Q# doesn't work" statement. Flagged for the
corruption-exposure sibling: an IR with a v2+ op would be emitted with that op silently dropped
and all seven lanes would agree on the wrong answer.

**So the grammar has two admission criteria and writes down one.** `add` was admitted on
*necessity*; `rotl` and the list ops earn their place on *portability* — every substrate has a
rotate, and deriving it pushes a lowering step into every backend. Those are independent, and an
op can be derivable and still earn primitive status.

## Bug found and fixed: `ZetaIrCanonicalizer.fromPolyF2Rot`

It deleted the constant term unconditionally, with an in-code comment arguing the constant term
can never be absent. It can: `(1 + X^63)(1 + X) = X + X^63` at width 64, because `X^64 = 1`.

| input | old output | correct |
|---|---|---|
| `XRotXor [63]; XRotXor [1]` @64 | `XRotXor [1;63]` — off by `x` (`f(1)`: ...810 vs ...811) | `X + X^63` |
| `XRotXor [31]; XRotXor [1]` @32 | `XRotXor [1;31]` — off by `x` | `X + X^31` |
| `XRotXor [0]; XRotXor [1]` | `XRotXor []` = identity, and **rejected by `ZetaIrV4.validate`** | the **zero** map |

Fixed in two places — and I record that my first cut was wrong: emitting two ops for the
cancelled case made `fuseOps` rewrite two `XRotXor` into two `XRotXor` and loop forever. Fusion
now fires only when it strictly shortens. Pinned by an exhaustive sweep of all W^2
single-rotation pairs (1024 at 32, 4096 at 64), which is both the soundness and the termination
check.

**Why a Lean certificate did not catch it:** `CanonicalizerCorrect.lean` re-declares its own
`fuseOps` whose `xrotxor` case is one hardcoded literal
(`xrotxor [1] :: xrotxor [2] => xrotxor [2,1,3]`), while the F# runs general polynomial
multiplication. The certificate and the code share a name, not a definition. Separately,
`NormalizerCorrect.lean` is sound but stated over `UInt64` only — no width-32 statement exists;
that half is now executed rather than proved.

## Tests: replacing three tautologies

The old `ZetaIrMinimalSet.Tests.fs` compared an inline re-implementation to itself
(`x ^^^ (x >>> s) = x ^^^ (x >>> s)`) and never mentioned `ZetaIrV4` or any evaluator. 17 tests
now go through the committed evaluator at **both** widths and replay the committed golden
vectors on seven routes covering all six ops.

## Recommendation: no v5

Priced in the doc: a fifth layout + validator + firewall, `ofV4`, six emitters plus the 7-lane
harness, new frozen goldens, both Lean oracles restated — against a benefit that is *negative*
on the portability axis. The core/derived split is worth knowing, not enforcing. The one change
I would argue for is a validator tightening (bound term lists to `[0, width)`), which is not a
grammar change.
