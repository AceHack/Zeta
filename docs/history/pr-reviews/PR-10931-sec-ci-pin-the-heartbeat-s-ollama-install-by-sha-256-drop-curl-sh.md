## Description

## The defect

`.github/workflows/agent-heartbeat.yml` ran

```
curl -fsSL https://ollama.com/install.sh | sh
```

on **every cron tick** — a remote script fetched over the network and handed straight to a
shell, every 15 minutes, three times over (one per matrix agent), in a job holding
`contents: write` and `pull-requests: write`. Whatever that URL served at that instant
executed with the runner's token in the environment, and nothing in this repo could have
told us it had changed. Influence entering through an undeclared, unmetered channel —
manifesto §13, noninterference / entropy quarantine.

## Approach chosen, and why

Option **(b)**: **pin the release binary by version + SHA-256, skipping the installer
entirely.**

The workflow never needed the installer. It needs `ollama` on PATH; it starts the server
itself with `ollama serve &`. Hashing the *script* (option a) would have been an
indirection with nothing behind it — and one ace would later have to unwind, since a
`contentAddress` denotes an artifact, not the program that fetches one. Dropping the
installer also drops what it does that we never wanted on an ephemeral, GPU-less runner: a
systemd unit, a service user, and an apt-based NVIDIA/ROCm driver install. A container by
digest (option c) would have meant restructuring the job for one step.

`https://ollama.com/download/<asset>` 302-redirects to `github.com/ollama/ollama/releases/…`
(checked, 2026-08-16), so the pinned URL fetches **the same bytes** the installer would
have — now with a version and a digest attached. Same bandwidth, same artifact, checked.

## The tension — stated, not resolved silently

A pin fails closed when upstream rotates. On this lane failing closed means the tick stops,
which `tick-must-never-stop` forbids — a lapse cost 12 hours once.

| option | verdict |
|---|---|
| fail the tick | maximum safety, violates tick-must-never-stop |
| silently fall back to unpinned | **forbidden** — a check with a bypass is not a check |
| **fail loudly, tick proceeds** | **chosen** |

So the install step is `continue-on-error: true` and the verifier emits an `::error::`
annotation: the step goes **red in the run UI**, the job continues, and the tick runs
**without a model**. Every downstream consumer already degrades rather than dies — the
observe tick and the codegen step both end in `|| echo "… (non-fatal)"`, and the healer,
mutation runner, cadence measurement, attestation, archive and push never touch a model. A
model-less tick is a large loss; a stopped society is a total one.

This is also **strictly safer for liveness than what it replaced**: the model pulls used to
sit under `set -e` in the same step as the install, so a failed `ollama pull` killed the
entire job. They are now a separate `continue-on-error` step, and the `sleep 5` before them
became a readiness poll.

## TypeScript, not bash — the collision worth naming

The first cut wrote this as two `.sh` files and `lint (bash retirement inventory)` refused
them. That refusal was correct and the shape of it is the interesting part: **a SHA-256 pin
reaches naturally for shell — `curl`, `sha256sum`, compare, branch — at exactly the moment
this repo is retiring bash.** Registering two new scripts in the retained-shell allowlist
would have made the check green and the repo worse.

The allowlist's premise does not hold here anyway: it exists for scripts that run *before*
bun is available, and this step runs after `bun install --frozen-lockfile`. So the verifier
is TypeScript — `src/Core.TypeScript/ace/pinned-artifact.ts` — which buys three things the
shell version could not:

- **no new shell** — nothing to register;
- **real tests** — the effects (network, filesystem, process, host identity) are injected,
  so `pinned-artifact.test.ts` drives the actual decision logic and proves the refusals;
- **it is the ace-shaped artifact** — reusable by ace's `verify`, rather than trapped in YAML.

## ace shape and the dogfooding hook

`.github/ollama-pin.json` is an ace `PackageEntry` — `name`, `version`, `contentAddress`,
`weight`, `packageManager`, `lastUpdated` — plus an `artifact` block holding the locator ace
has no field for. A content-addressed install *is* a hash-pinned install; this is the same
mechanism at a lower maturity, recorded in the shape ace will consume.

**Nothing in ace reads it yet, and this PR does not pretend otherwise.** Verified by reading
the source, not by trusting the header:

- `ace-cli.ts` `install()` performs no download and no filesystem write — a pure Z-set delta
  over a 4-row hardcoded `STUB_REGISTRY` whose content addresses are literals
  (`sha256:abc123`), and `registryLookup` ignores its `version` argument.
- `ace.ts` is **further along than the stub header implies**: it has a real fetch with
  `package_hash` verification and a lock-pin refusal. But it fetches `.text()` — JSON package
  manifests. No binary-artifact path, so a 1.4GB `.tar.zst` is out of scope for it today.

The gaps are enumerated in `aceGaps` in the pin file. **No ace code was touched.**

The dogfooding payoff is already visible: `artifact.verify` (binary + versionArgs) exists
because running this on a real runner surfaced a hole ace's own `verify` has — comparing a
recorded contentAddress against a registry cannot notice that an older binary is *shadowing*
the installed one. That is a requirement discovered by use.

## Maintenance story

- **Where the digest lives:** `.github/ollama-pin.json` — one source of truth, read by the
  verifier and shaped for ace.
- **How it is refreshed:** `bun src/Core.TypeScript/ace/refresh-ollama-pin.ts [--tag vX.Y.Z]`.
  It refuses to write unless the release's `sha256sum.txt` and GitHub's API asset digest
  agree. Hashing the artifact you just downloaded would be a check that cannot fail.
- **How it is proved:** `verify-ollama-pin.yml`, which runs **automatically on any PR
  touching the pin or the verifier**, plus `workflow_dispatch` once this is on `main`. The
  maintenance path is enforced, not merely documented.
- **What failure looks like when upstream moves:** nothing. The URL is version-addressed, so
  a new upstream release does not touch us — the pin goes stale, it does not break. It fails
  only if the tagged asset is deleted or its bytes change, and then the install step is red,
  the annotation names the mismatch, and the tick continues without a model.
