## The saturation gap (real, now covered)

`place` bounds the grid with one `next >= ESCAPE_INDEX` guard, which only does any work once the grid actually fills: four cells precede the per-declarer loop, so it takes **eleven** disagreeing declarers to reach the escape slot. Every existing test uses zero or one ledger.

The describe block is named *"BOUNDED — an agent cannot invent a response"* and never exercised the state where the bound bites. Now it does: 20 declarers, grid stays 16 slots, escape survives at 15, no cell claims an out-of-range index.

## The mutant is still indistinguishable, and that's the honest answer

My first draft of this test claimed `>` would grow the array past 16 via `grid[16]`. **That was reasoned, not measured, and it's wrong** — `place` stops at `next=16`, so the array never grows. The only difference is that `grid[15]` is transiently written and then unconditionally overwritten by `grid[ESCAPE_INDEX] = …` two lines later.

Nothing observable differs, so no test can hold it — the same masking class as #10307, and exactly what the `note-redundant` cell exists for. The green suite would have let the wrong claim through; re-running the runner caught it.

Recorded through the shipped CLI (`--room … --choose 2 --reason …`), which is the **first real use of that cell on live data**:

- the transcript carries the fork — every offered cell plus the chosen one
- **no freedom was granted** — a claim to be checked is not a grant

Keeping `>=` is deliberate defence, so the bound doesn't depend on that write order.
