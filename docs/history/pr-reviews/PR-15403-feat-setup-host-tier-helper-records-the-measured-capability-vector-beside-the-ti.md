## Description

## What

`tools/setup/common/host-tier.sh` now additionally **records the measured host capability vector beside the tier the enum chose**, as one JSON artifact.

**Install behaviour is unchanged.** The tier enum still decides every package. This measures and records; the enum still decides.

## Why

Aaron 2026-08-25:

> "eventually we want tiers of optional features that can coexist/compose with each other in higher layers"
> "in a perfect world i imagine some matrix for cpus, memory, solid state, and rotational disk and picking the right dependence to install based on those results"

The shipped design is a **tier enum** (`slim | standard | full`). An enum is a **total order**, and that is the defect: it cannot express "rotational disk but 128GB RAM", and two tiers do not compose, so "tiers of optional features that coexist" is unrepresentable in it. A **capability vector** that dependencies state requirements over is the shape that can, with tiers demoted from primitive to a derived named region.

**That redesign is blocked** — not enough installed hardware to fit a model over, and Aaron said so. This PR does only the unblocked half: make the pair *(measured vector, chosen tier)* a record, which is what later makes the tier a **checkable function of reality** rather than a guess.

## Controls

Every claim below is the output of a command, not a description of one.

**Memory and CPU agree with an independent source:**

```
sysctl hw.memsize    = 206158430208     emitted totalBytes = 206158430208   (192.0 GiB)
sysctl hw.logicalcpu = 24               emitted logicalCount = 24
```

**Rotational — the discriminating control.** This is the one that changed the design:

```
$ for d in disk0 disk6; do ... grep -q '<key>SolidState</key>' ...
disk0: KEY PRESENT -> <true/>
disk6: KEY ABSENT (grep rc=1)
```

`disk0` is the internal Apple SSD; `disk6` is a USB flash drive. `diskutil` **omits the `SolidState` key entirely** for the USB device rather than reporting it false. A naive `rotational = !info.SolidState` would therefore have reported a **USB flash drive as ROTATIONAL**. So `rotational` is three-state — `true | false | null` — and `null` means *not determinable*, never a synonym for `true`. Absence of evidence is recorded as absence of evidence.

**Idempotency (this is why there is no timestamp field):**

```
$ cmp -s vec1.json vec2.json  ->  IDENTICAL (cmp rc=0)
```

The artifact is a pure function of (hardware, env), so N emissions are byte-identical. A wall-clock field would make two emissions on one unchanged host differ, destroying the byte-comparability that makes the tier checkable. No serial numbers or UUIDs either — host-identifying and not needed to decide what to install.

**End-to-end, sourcing the helper the way an installer does:**

```
CONTROL A (before): ls: .zeta: No such file or directory
$ bash -c '. tools/setup/common/host-tier.sh && echo "shell says: tier=$ZETA_HOST_TIER source=$ZETA_HOST_TIER_SOURCE"'
→ host capability vector recorded: .zeta/host-capability-vector.json (measurement only; installs unchanged)
shell says:    tier=full source=detected
artifact says: {'tier': 'full', 'rank': 2, 'source': 'detected'}
```

### A control caught a real bug in this PR's own integration

The first run of that end-to-end control disagreed with itself: the shell said `source=detected`, the artifact recorded `"declared"`. Cause: `host-tier.sh` `export`s `ZETA_HOST_TIER` **before** invoking the emitter, so the child process saw a set variable and inferred an operator declaration for a tier the shell had just auto-detected from memory.

That is not cosmetic. The tier's provenance is the *one* fact this artifact exists to carry — "was this tier a function of the hardware, or a human's assertion?" is precisely what a later capability-vector design must answer. Fixed by having the shell pass its own resolved verdict down in `ZETA_HOST_TIER_SOURCE`, which wins over re-inference; a junk value is ignored rather than trusted. Falsified by three tests and by mutants M12/M13.

## What I could NOT verify — stated, not smoothed over

- **The Linux path has never executed on a Linux host.** `/sys/block/<dev>/queue/rotational` is covered by unit tests over fixture strings *only*. The kernel documents the contract (`Documentation/ABI/stable/sysfs-block`: 1 = rotational, 0 = non-rotational), but documentation is not a measurement and the code comment does not claim it is. The runtime path also pushes an explicit `unmeasured` entry saying so, so a Linux artifact carries its own warning.
- **Windows / other platforms have no probe at all.** Block devices come back as an empty list *with the reason recorded in `unmeasured`* — never as a silent zero that reads like "no disks".
- **No host with an actual spinning disk was available**, so `rotational: true` has only been produced from a fixture, never from real hardware. The `SolidState=false` branch is fixture-tested.
- **Not measured, and named in every artifact:** GPU, core frequency, cache sizes, performance/efficiency core split, cgroup/container CPU quota.
- **Nothing consumes the artifact yet.** It is read by a human and by the tests. It is deliberately gitignored (`.zeta/`) because it is host-local by nature and would churn on every clone; `ZETA_CAPABILITY_VECTOR_OUT` redirects it somewhere collectable (CI could upload it as a workflow artifact) without it ever entering the tree. Whether it *should* be collected centrally is left open in the work-item.
- **Cost:** one `bun` invocation per install run, ~0.3s measured on darwin/arm64, spent once — `ZETA_CAPABILITY_VECTOR_EMITTED` is exported so the three sourcing sites (`mise.sh`, `linux.sh`, `macos.sh`) do not each pay it. Opt out with `ZETA_CAPABILITY_VECTOR=0`.
- **Emission is fail-open by design.** Missing `bun` (expected during early bootstrap, before the toolchain exists), missing emitter, or a non-zero emit all print loudly and return 0. A measurement that can break an install would be worse than no measurement.
