## Description

## Diagnosis first — and the brief's hypothesis was wrong

The task named a leading hypothesis: a `concurrency:` group too coarse, with `cancel-in-progress: true`. **The run metadata refutes it for the class that matters.** `gate.yml` already keys concurrency per-PR and only cancels on PR events; it was never coarse.

Of **37 cancelled `gate` runs** in a 2h18m window:

- **27 superseded** — a newer run exists on the same branch. `cancel-in-progress` working as designed, and benign.
- **10 orphans** — cancelled with no replacement. These block merges, and **none is a concurrency cancel.**

### Every orphan is a job timeout

| job | timeout-minutes | budget | observed | delta |
|---|---|---|---|---|
| lint (Rust) | 15 | 900s | 916s | +16s |
| lint (markdownlint) | 12 | 720s | 737s | +17s |
| lint (semgrep drift) | 20 | 1200s | 1215s | +15s |

**10 of 10**, each against its *own* differing budget. Three distinct timeout values each reproduced exactly — an identification, not a coincidence of counts.

**Correction to the brief:** the victims are short **lint** jobs, not `full-verify` / `cross-verify`. In the orphan runs `cross-verify` finished green in 373s.

### Where they hang

12 of 14 hung jobs stalled in `Install toolchain`, inside `apt-get install`. `azure.archive.ubuntu.com` decayed from 8083 kB/s to ~1.5 kB/s and stopped mid-`pandoc` (26.9 MB) without closing the socket.

**Both existing guards were structurally unable to act:**

- apt's `Acquire::http::Timeout` is an **inactivity** timer — a slow trickle keeps resetting it.
- The 5-attempt retry wrapper in `gate.yml` guards **failure**. A hung `apt-get` never returns, so the loop never reaches iteration two. The retry was not broken, it was **unreachable**.

*A retry bounds failure, not duration.*

## The fix

**Root cause — `tools/setup/linux.sh`:** wall-clock `timeout` around `apt-get install` (600s default, `ZETA_APT_TIMEOUT_SECONDS`) with 3 attempts and explicit `Acquire::Retries` / `Acquire::*::Timeout`. Exhaustion still fails loudly, so no package error degrades to a false-green. Landed in `linux.sh`, not the workflow, so dev laptop / CI / devcontainer get the identical bound (GOVERNANCE §24).

**Residual — `.github/workflows/rerun-cancelled-gate.yml`:** 2 of 14 hangs were in other steps, so bounded recovery is still warranted. Four guards: cancelled-only (never `failure`), `run_attempt == 1`, not-superseded, not-stale. Re-runs via `rerun-failed-jobs`, not `rerun` — orphans had 26–28 jobs already green, so a full re-run burns ~28× the minutes.

## Proof both directions

A recovery that cannot fail is the thing we are trying to stop building.

- **Mutation testing:** each guard deleted in turn plus the safety property inverted — **5/5 mutants caught**.
- **Live dry-run against production runs:** fires on real orphans; declines on the two real failures, a superseded cancel, an already-retried cancel, and a success.
- **apt guard vs a stalling stub:** bounded exit 124; a genuine package error still exits 100; a transient stall recovers on attempt 2.
