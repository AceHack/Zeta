## Description

The automated flush lanes open roughly **60 PRs a day** and not one of them could arm its own auto-merge, so each sat waiting on a human to arm it by hand.

The cause was a feature flag, not a credential. `armingEnabled` gates the attempt on `ZETA_FLUSH_ARM_AUTOMERGE === "1"`, and that variable was **unset everywhere in the repo** — the only occurrences were the reader itself, its two tests, and the `ARMING_DISABLED` message.

## What changed

`ZETA_FLUSH_ARM_AUTOMERGE: "1"` on the **flush step's own `env:`** in twelve workflows — never at job or workflow level, so the flag cannot reach an unrelated step:

`budget-snapshot-cadence` · `context-cost-trend-cadence` · `drift-dashboard-cadence` · `drift-sweep` · `lockfile-healer` · `manifesto-citation-snapshot-cadence` · `pr-archive-on-merge` · `proof-closure-drift` · `search-index-cadence` · `society-heartbeat` · `tick-metrics` · `zetadb-scheduled-node`

## Two corrections to the roster

Both came from checking the invocation rather than trusting the grep.

**`agent-heartbeat.yml` is EXCLUDED.** It is the one workflow that invokes `merge-heartbeats-to-main.ts` directly, but it already arms in its own `Arm heartbeat PR auto-merge` step — which carries a PAT → `GITHUB_TOKEN` degradation ladder this module has no equivalent for. Opting in there would spend a second GraphQL call to re-arm what is already armed, and would bypass the fallback.

**`zetadb-scheduled-node.yml` is INCLUDED** and was absent from the original list. It runs `flush-via-staging.ts flush` exactly like the other lanes, but its step comment never names `merge-heartbeats-to-main`, so a grep for the module misses it.

Ten of the remaining eleven reach the module through `flush-via-staging.ts`; `pr-archive-on-merge` calls it through a `$FLUSH` shell variable, which is why the literal-path grep missed that one too.

## The three reasons, one retired and two accepted

The docstring above `armingEnabled` gave three reasons for keeping this off. It now records **when, by whom, and on what evidence** each was resolved, rather than leaving a flag whose rationale had silently rotted.

1. **RETIRED.** *"The scoped flush PAT cannot call the mutation."* Aaron rotated `ZETA_PR_ARCHIVE_TOKEN` at **2026-08-26T19:54Z** with permissions derived from a measured audit of all 15 lanes that use it. **Retired on the rotation, not on an observed green arm** — the docstring states that limit and names the exact GraphQL error (`Resource not accessible by personal access token (enablePullRequestAutoMerge)`) that would mean the scope is still missing.
2. **ACCEPTED COST**, not deleted. `enablePullRequestAutoMerge` is GraphQL-only and GraphQL is the budget that rate-limits this repo (measured 2026-08-14: 1147/5000 points vs REST 33/5000). Accepted on two grounds: the quota resets hourly, and budget spent on a call that *succeeds* buys a merge where budget spent on one that never has bought nothing. If exhaustion starts costing lanes, this is the first knob to turn back — and turning it off is per-step.
3. **ACCEPTED COST**, not deleted. Arming is not the flush's job; the flush has already succeeded by then. Tidiness, weighed against ~60 hand-arms a day, and outweighed.

Authorized by Aaron 2026-08-26: *"yes this should be okay, it resets once an hour anyways."*

## What did NOT change

`armingEnabled` still matches only the exact string `"1"`, the default is still off, and `armOutcome`'s contract — **a failed arm never destroys a successful PR** — is untouched. So if the rotated token still lacks the scope, each lane's PR still opens, the lane still exits 0, and the warning names the PR and the cause.
