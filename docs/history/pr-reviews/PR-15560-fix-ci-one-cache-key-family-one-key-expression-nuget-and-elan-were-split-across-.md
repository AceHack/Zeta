## Description

A save whose restore key never matches is a save that does nothing. Two cache
families were writing into namespaces the lane that maintains them never reads:

  gate.yml / lean-proof.yml   nuget-${{ runner.os }}-${{ runner.arch }}-<hash>
  low-memory.yml / codeql.yml nuget-${{ runner.os }}-<hash>          <- no arch

Same content, same hash inputs, two namespaces, neither able to restore the
other. Same split on elan (gate.yml + lean-proof.yml vs low-memory.yml).

BOTH HALVES MEASURED, not inferred.

  * Itemised actions/caches endpoint, 2026-08-26T09:0xZ: the SAME
    hashFiles('Directory.Packages.props') digest charged TWICE --
    nuget-Linux-c922cac0... (357 MB) and nuget-Linux-ARM64-c922cac0... (358 MB).
    ~3.7% of a ~9.31 GiB ceiling spent storing one dependency set twice.
  * Slim-lane restore logs, 7 consecutive main runs (08:31Z..09:01Z):
    nuget-Linux-<hash> MISSED 5 of 7, elan-Linux-<hash> MISSED 5 of 7 -- while
    gate.yml's copies of the same content sat in the cache the whole time under
    the arch-qualified key. Each miss is a full ~357 MB re-download AND a full
    re-upload, which is pressure on the same ceiling the entries are evicted by.

The convention was already written down TWICE and still drifted:
  * gate.yml: "Cache keys include `runner.arch` ... so Linux x64 (ubuntu-24.04,
    ubuntu-slim) and Linux arm64 (ubuntu-24.04-arm) do not share entries" -- it
    NAMES ubuntu-slim, the lane that was violating it.
  * codeql.yml: "Keys on Directory.Packages.props - same as gate.yml" -- a
    comment asserting a parity the code did not have.
  * lean-proof.yml got it right, which shows the convention was understood and
    simply unenforced.

So this ships a falsifier, not just a fix: audit-cache-key-namespace-parity.ts
groups every cache key by its FAMILY (its literal, non-${{ }} text -- the part
that carves the namespace) and refuses a family carrying two key expressions.
It goes RED on origin/main with exactly these two families and green here.
Wired into ci-cache-paths-lint.yml beside its two siblings, which that job's own
comment already describes as "ways an actions/cache step is present and not
doing what its name says".

NOT "every key must contain runner.arch". That proxy would flag lake-* in
lean-proof.yml, used in exactly ONE workflow, forcing either a pointless cold
rebuild of the Mathlib olean cache or a hand-written allowlist that drifts from
the code. Family parity needs NO allowlist: a single-use family is consistent by
construction. 14 tests; 6 mutants applied and all 6 killed, including one on the
scan floor itself (MIN_KEYS_EXPECTED = 0 passed every other test until a test
was added to pin it).

WHY RESTORE-ONLY AND NOT JUST RE-KEYED. Unifying the namespace alone would
CREATE the two-writers-one-key condition that poisoned the dotnet key (172 KB
under a key that should hold ~410 MB; measured hitting in 6 of 6 gate runs). The
slim lane builds and tests core only, so the ~/.nuget/packages it would write is
a SUBSET of gate.yml's full-tier superset -- the exact "replaces a superset with
a subset" failure low-memory.yml's own mise comment describes. gate.yml stays
the sole writer for that lane.

codeql.yml is treated DIFFERENTLY and deliberately: it runs on ubuntu-24.04 at
tier full -- the same image and tier as gate.yml's ubuntu-24.04 leg -- so it is
a legitimate co-writer and stays read-write. The subset hazard is a property of
the reduced-tier runner, not of having two writers, and over-applying the
restore-only remedy would remove a writer for no measured reason.

COST: none of the usual one-time cold rebuild. gate.yml's and lean-proof.yml's
key expressions are UNCHANGED, so their entries stay valid and the slim/codeql
lanes start reading entries that already exist. What is retired is the
*-Linux-<hash> namespace, whose entries age out under LRU without being
rewritten. This is the rare cache-key change that costs nothing to land.

Verified with exit codes read directly, never through a pipe: actionlint rc=0 on
all three workflows; tsc --noEmit under the repo's strict settings rc=0; prettier
--check rc=0 on every file this touches (codeql.yml's pre-existing prettier
warnings are at lines 117-365 and are untouched by this hunk); bun test rc=0
(14 pass); the audit rc=0 here and rc=1 against an origin/main worktree.
