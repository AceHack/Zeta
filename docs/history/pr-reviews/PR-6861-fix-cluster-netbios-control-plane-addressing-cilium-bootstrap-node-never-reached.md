## Description

## Why

After #6684 fixed the k3s `--cluster-init` token deadlock, the control plane comes up — but a fresh single-node install **still never reaches `Ready`**. Caught live on `node-bc8d77` (2026-06-06): `k3s.service active`, API up, node registered, but `helm-install-cilium` stuck `Pending` ~9 min and the node `NotReady`. Two pre-existing Cilium-bootstrap bugs that the token deadlock had masked (the old node died before it ever got this far):

### Bug 1 — Cilium can't schedule (CNI chicken-and-egg)
`cilium-install.yaml` (a k3s `HelmChart`) lacked **`bootstrap: true`**. The install Job only had the default `NoExecute` tolerations, so it couldn't tolerate the node's `node.kubernetes.io/not-ready:**NoSchedule**` taint → Pending forever. Cilium can't install because the node isn't Ready; the node can't be Ready without the CNI.

### Bug 2 — the control-plane name never resolves
Both Cilium `k8sServiceHost` and worker `serverAddr` used `control-plane.zeta.local`. Confirmed on the box: `getent hosts control-plane.zeta.local → NXDOMAIN`. It can't resolve — mDNS is single-label `.local` (this has an extra `.zeta.` label), and **nothing** (no DNS, no `/etc/hosts`, no `extraHosts`) ever defined it. With `--disable-kube-proxy`, Cilium *must* reach the API directly, so this is fatal even once it schedules.

## Fix — NetBIOS-based addressing (mDNS doesn't work here; `nmbd` already runs)

`common.nix` already runs Samba `nmbd` "because mDNS fails, NetBIOS works" — but it was **publish-only**: `nsswitch.conf` had no `wins`, so nothing could *resolve* NetBIOS names. This wires it up properly:

| File | Change |
|---|---|
| `common.nix` | `services.samba.nsswins = true` → add `wins` to nsswitch so glibc (k3s/Cilium) resolves NetBIOS names |
| `k3s-server.nix` | `netbios aliases = control-plane` (answer to the fixed name regardless of `node-<6hex>` hostname); `/etc/hosts` `control-plane → 127.0.0.1` on the CP; `--tls-san=control-plane` so the API cert is valid for the name |
| `cilium-install.yaml` | `bootstrap: true` + `k8sServiceHost: control-plane` |
| `applications/cilium/Application.yaml` | `k8sServiceHost: control-plane` (so ArgoCD doesn't revert Cilium to the dangling name after adoption) |
| `k3s-agent.nix` + workers | `serverAddr: https://control-plane:6443` |
| docs | updated |

On the control-plane the name resolves to `127.0.0.1` (local API, deterministic); on workers it resolves via NetBIOS broadcast + nss-wins to the CP's LAN IP.

## Test

`nixos/tests/netbios-control-plane-resolution.nix` — a **2-node VM test**: a worker resolves `control-plane` via NetBIOS broadcast to the server's IP (+ pings it). Wired as a flake check + CI step. NetBIOS broadcast works on the test VLAN, so it runs **fully offline** and is the regression gate for the resolution fix.

## Honest scope / what's NOT covered here

- **Full Cilium-to-`Ready`** needs internet to pull the Cilium image, so it can't run in the nix sandbox — confirm on a **live reinstall** (I couldn't, since the node is currently on a different subnet from my Mac).
- NetBIOS name resolution is **broadcast / single-LAN**; cross-subnet needs a WINS server or DNS. Fine for a single-LAN homelab.
