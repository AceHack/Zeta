## Description

## The asymmetry

PR #10734 fixed a **producer** that minted event ids by hex-encoding the event's own JSON and truncating to 32 characters — a "content hash" with no hash in it, so the id was a function of the attestor's first three characters. That stops *us* minting bad ids.

It does nothing about a **reader**. Every reader here asked `/^[0-9a-f]{32}$/` — a check on the *encoding* that cannot see the *value*. Such a reader accepts ids from the old broken producer, from any other broken or malicious producer, and ids whose decoded version and category are structurally impossible.

`packGeneric` was bounded across TypeScript, C# and F# this week precisely so an out-of-range payload **fails rather than silently aliasing**. A reader that never decodes buys none of that. **The mint side became strict and the read side stayed a regex** — that asymmetry is the defect this closes.

## Acceptance points found

Six non-test sites used the bare regex. Three are readers, three are write-side guards; all four `isCanonical*Id` predicates now delegate to one decoding validator.

| site | role | wired |
|---|---|---|
| `observe/load-world.ts` | reader — folds the observe event log | yes |
| `work-items/types.ts` → `read-events.ts` | reader — work-item event G-Set | yes |
| `agent-bus/types.ts` → `subscribe.ts` | reader — the cross-**machine** channel | yes |
| `observe/event-sink-folder.ts` | mint-time path-segment guard | yes |
| `forge-host/github/pr-manifest-shards.ts` `SHARD_ID_RE` | filename-stem shape, no reader call site | no |
| `observe/tick-shards.ts` `SHARD_ID_RE` | filename-stem shape, no reader call site | no |

`load-world.ts` carried its **own copy** of the regex rather than importing one. That duplicate is gone.

## One parser, not two

`zeta-id/canonical-hex.ts` owns no parsing — it calls the codec's `unpackGeneric` and checks two fields. A second, independently-written id parser would drift from the first, which is the shape of the treaty divergences found this week. Same approach as #10734's own audit, which decodes the version field instead of trusting the regex.

It adds one check that audit does not have: **registered category**. The category field is 4 bits (0..15) but only 0..11 and 15 are registered, so 12/13/14 decode cleanly and mean nothing.

## Rejection policy — unchanged per call site, deliberately

Every call site already had a considered outcome for a bad id: the tolerant readers skip, the sink returns `ok:false`. Only the predicate got stricter. Making one forged file abort a whole load would turn a single bad file into a denial-of-service on the observe loop, and the fold is a mode projection over a G-Set where skipping is the documented schema-on-read contract.

### The bar

- **Forged id rejected.** Two forgeries planted, both 32 valid lowercase hex. The sharper one decodes to **version 1 — a valid version** — and is caught only by the category check; a version-only check accepts it. Removing the forgery returns the reader to green with nothing genuine lost.
- **Legacy files still load.** All three present and still readable as attestation facts. They are consumed by `vault-state-bridge-cli` → `computeConnectivity`, a path that never validated ids and is untouched. They were **already** invisible to `load-world` via the `KNOWN_KINDS` gate (`attest_peer` is not a known action kind) — so no allowlist is added to the reader; it would be dead code able to drift from the real list in #10734's filename audit, which is the right home for it. A test pins that reasoning so it cannot rot silently.
- **Fails against pre-fix code.** Reverting the four wired files leaves the new suite at **4 failures**, the reader accepting **all 4** planted events instead of 1.
