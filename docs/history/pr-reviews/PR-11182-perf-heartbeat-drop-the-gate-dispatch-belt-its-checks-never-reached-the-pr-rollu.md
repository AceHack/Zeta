## Description

perf(heartbeat): drop the gate dispatch belt — its checks never reached the PR rollup

Each agent heartbeat lane started `gate.yml` twice per tick: once via the flush
PR's `pull_request` event and once via an explicit dispatch. Measured cadence
over 13 consecutive cycles: exactly 3 dispatch gate runs every 15 minutes,
without exception, alongside 1–3 pull_request runs — 288 full-matrix runs a day
crowding out ordinary PRs.

The belt existed because a `pull_request` gate run on a heartbeat lane used to
be created and immediately parked (`completed`/`action_required`) when the
pushing actor was `github-actions[bot]`. #10986 fixed that at the root. Verified
before deleting anything: after the 17:49Z cutover there are zero
`action_required` gate runs on alexa/otto/soraya, and run 31976373498
(pull_request, heartbeat/otto) executed a full 29-job matrix and produced
`gate (required)` = success.

The measurement then showed something stronger than redundancy: the dispatch was
INERT. A `workflow_dispatch` gate run's checks do not enter the flush PR's
statusCheckRollup, so they can never satisfy the `gate (required)` required
status check. Both halves observed on real PRs:

  - #11165 (head 3da9b0f3): dispatch check-suite 86701078150 carried
    `gate (required) completed/success` on that exact commit, and the PR's
    rollup carried nine contexts, none of them gate. The repo's own falsifier
    agreed — `required-check-started.ts` reports "gate (required) never started
    on heartbeat PR(s): #11165, #11153, #11152, #10708".
  - #11166 / #11167 (merged): the `gate (required)` in the rollup came from the
    `pull_request` run, never from the dispatch run created seconds beside it.

It was also the more expensive of the two — `matrix-setup` gives
`workflow_dispatch` the full OS set (5 build legs, Windows + macOS) and gives
`pull_request` the pre-merge set (3 legs). So the run being deleted is the
heavier one, and nothing reads it.

No check is weakened. The gate still runs on every flush PR, through the one
mechanism the merge actually consumes, and the production falsifier that catches
a missing gate is untouched: "Fail if a heartbeat PR is old and gate never
started" exits 1 when a heartbeat PR older than one tick has no
`gate (required)` in its rollup. If this removal is wrong, that step says so on
the next tick rather than letting a lane merge unchecked.

Reasoning inherited from #10986, which declined to ADD this belt to the lanes it
treated on the grounds that two independent gate-starting mechanisms make the
result unattributable. That argument applies here in reverse.

The unit pin is inverted rather than deleted: it now asserts the belt's ABSENCE
repo-wide, plus the presence of the falsifier that makes the absence safe.
Mutation-checked — re-adding a dispatch step fails the test (27 pass / 1 fail),
removing the mutant passes (28 pass / 0 fail).

Lanes left alone, deliberately:
  - `tick-metrics.yml` — already carries the #10986 PAT, already has no
    dispatch. One mechanism; nothing to remove.
  - `society-heartbeat.yml` — has no dispatch either, but its `pull_request`
    gate runs are still parked in `action_required` under
    `github-actions[bot]` (11 of them after 18:00Z), so `gate (required)` never
    starts on #10708. That is a real defect and it is NOT fixed here: the cure
    is the credential arrangement, which is proven work belonging to someone
    else, and the alternative — adding a dispatch belt — is the exact thing this
    change removes.

Also noted, not acted on: the three flush PRs currently missing a
`pull_request` gate run (#11152, #11153, #11165) are all
`mergeStateStatus: DIRTY`. A conflicting PR has no computable merge ref. That is
upstream of this step and a dispatch never fixed it — it only put a green check
on the commit that no merge would read.
