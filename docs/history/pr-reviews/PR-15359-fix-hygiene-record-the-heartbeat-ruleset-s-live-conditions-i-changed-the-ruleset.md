## Description

`check drift` reported my own undeclared change. Today I added
`exclude: ["refs/heads/heartbeat/*-flush-*"]` to ruleset 16934633 so 1,612
legacy flush snapshot refs could be deleted, and I did not update the
committed expectation. The detector was right; I was the drift.

    -  "exclude": [],
    +  "exclude": ["refs/heads/heartbeat/*-flush-*"]

WHY THE WHOLE `conditions` OBJECT AND NOT JUST MY FIELD. The snapshot also
claimed this ruleset targets `refs/heads/agent-heartbeats`, while live it
targets `refs/heads/heartbeat/*` — a pre-existing, separately-undeclared
change that #15349's audit documented. Correcting only my `exclude` would
have left an internally incoherent record: a ruleset scoped to
`agent-heartbeats` carrying a `heartbeat/*` exclusion, which describes
nothing that exists. So the entry now states live truth on both fields, and
this message is where the second fact is attributed rather than silently
absorbed into mine. Key order matches the file's existing convention
(`exclude` before `include`, as the other three rulesets use) so the record
carries no gratuitous diff.

WHAT I DELIBERATELY DID NOT DO: regenerate the snapshot wholesale with
`snapshot-github-settings.ts`, which is what the failure output suggests. The
same run reports it is `skipping 21 field(s) not readable with current
token` — including `default_branch_protection`, `actions_permissions`,
`codeql_default_setup` and the whole merge-settings group. Regenerating with
that token would have written a file MISSING those 21 fields, converting
"recorded and checked" into "absent and unchecked" across the most
safety-relevant part of the record, while turning the check green. That is
the vacuity class with extra steps. A hand-edit of the one entry I actually
changed keeps every unreadable field recorded as it was.

A CORRECTION TO MY OWN FIRST DRAFT OF THIS MESSAGE, which claimed `check
drift` "has failed on every scheduled run on main since at least 2026-08-23
(8 consecutive)". That was FALSE and the error is worth recording. `check
drift` comes from `github-settings-drift.yml`; I measured
`drift-dashboard-cadence` — a different workflow — because I resolved the
workflow id with `grep -i drift | head -1` and took whatever came first.
`github-settings-drift` actually SUCCEEDED on its 2026-08-24 scheduled run
and on #15351 today at 14:55:39. So this check is not chronically red, and
the remaining differences it reports are real and unowned rather than
pre-absolved background noise.

Two other differences are visible in the same report and are NOT mine, NOT
fixed here, and should not be assumed benign: `has_downloads` disagrees, and
ruleset 16134995 "CI Gate" is recorded `enforcement: disabled` while live it
is `active` with a different required-check set. That second one is a
security-relevant record being wrong in the permissive direction.
