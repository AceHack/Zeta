### A confound I found and removed

My first syntax mutation appended a second top-level `metadata:`. It went red —
on **duplicate keys**, not on the syntax. That is exactly the zflash-allowlist
shape (every case caught incidentally by a different rule), and it would have
let me claim row 1 was closed on the strength of row 2's check. Re-run under a
unique key, the syntax defect fails on its own. Only then is the row closed.

### Mutation testing — is the guard load-bearing?

| Mutation | Suite |
| --- | --- |
| baseline | **12 pass / 0 fail** |
| `process.exit(1)` → `exit(0)` | **3 pass / 9 fail** — independently reproduces the claimed 9-of-12 |
| `uniqueKeys: true` → `false` | **11 pass / 1 fail** — and it is *exactly* the duplicate-key case |
| exact version → original `text.includes("name: " + chart)` | bogus pin prints `PASS: cockroachdb: cockroachdb 999.999.999 is published`, **exit 0** |

That last row is the one that matters: it reproduces the historical defect live,
which is the evidence that the exact-version comparison — not something
incidental — is what carries the check. An exit-code stub alone would not have
shown that; it is blunt enough to catch nearly any change.
