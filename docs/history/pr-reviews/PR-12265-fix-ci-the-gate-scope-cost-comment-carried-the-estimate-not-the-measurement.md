## Description

## What

Follow-up to #12252. That PR landed with a **pre-land estimate** in the
`gate-required` timeout comment; the first live run measured it, and the estimate
was wrong. This corrects the comment to the measurement and cites the run it came
from. Comment-only, no behaviour change.

## The numbers

`run 32207501412` attempt 2, job `95940135217` -- the first execution of the job's new shape:

| step | measured | estimate in #12252 |
|---|---|---|
| Checkout (sparse) | **2 s** | ~11 s |
| Setup Bun | **2 s** | ~3 s |
| Emit scope | **3 s** | ~2 s |
| Check all gate jobs | 0 s | -- |
| **job total** | **12 s** | ~20 s |

The ~11 s figure was priced off the **full** checkouts the other jobs in this
workflow take. `sparse-checkout` + `filter: blob:none` is what closed the gap.
Real cost of making the required check say what it covered: **~9 s per run**, not
~20 s.

## Why bother re-running the gate for a comment

Because the workflow's whole subject is "a check should publish what it actually
did", and it was carrying a cost claim nobody had measured. An estimate presented
in the register of a measurement is the same defect one layer up. The comment now
names the run and job id, so the next reader can check it rather than trust it.

## Also verified on that run (recorded here, not re-litigated)

The live summary rendered as designed on a real run: `Scope: FULL`, 5/5 floor
jobs, the per-leg table with `build-and-test` showing 17 steps ran / 4 skipped on
each of the three legs, and the `::notice::` annotation carrying the one-line
scope. That was the half of #12252 I could not verify before landing.
