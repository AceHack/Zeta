# ShivaGc byte-identity falsifier compares run recipe to itself — tests determinism, not regeneration fidelity

<!-- Work-item body. ZetaId-keyed (conflict-free, time-sortable). "Backlog" is a
     STATE = this folder; completion moves the file to workitems/done/YYYY/MM/.

## The defect

`tests/Tests.FSharp/ShivaGcRegen.Tests.fs` §4, the test named
**"BYTE-IDENTITY: an object DROPPED by partition3 is regenerated byte-identically
from its recipe"**.

The heap is built as:

```fsharp
ShivaGc.object' "derived" (run recipe) []   // the value IS `run recipe`
```

`droppedBytes` then extracts that object's value, so it traces to
`bytes (run recipe)`. And two lines later:

```fsharp
let regeneratedBytes = bytes (run recipe)
Assert.Equal<byte[]>(droppedBytes, regeneratedBytes)
```

**Both sides share one producer.** `audit-check-arity` R2 flags it after
let-substitution, and R2 is correct.

## What it actually tests

That **`run` is deterministic** — the same recipe run twice yields the same
bytes. That is a genuine and non-trivial property (DST depends on it) and the
test can fail, so it is not fully vacuous.

What it does **not** establish is the claim in its own name: that regeneration
reproduces *what was dropped*. It cannot, because what was dropped was *defined
as* the regeneration.

The in-test comment makes the reasoning visible and is where the slip is:

> *"Note what is NOT read here: the dropped object. These bytes are produced, not
> copied."*

True — and the dropped object's bytes were **also** produced by `run recipe`.
Not copying is not the same as not sharing a producer.

## Why this matters more than an ordinary redundancy

This is the **same defect the author agent identified in the test it replaced**.
Its own report says `ShivaGc.Tests.fs:116` "asserts partition-then-resume
reconstructs the heap byte-identically — but `partition` returns paused objects
*whole*, so the value was never dropped. It measures retention and reads as
regeneration evidence."

The replacement repeats the shape one level subtler: the value *is* dropped, but
the expectation is regenerated from the same generator that produced it. Catching
the pattern did not confer immunity to it, which is exactly why the mechanical
check exists.

## Fix direction

Break the shared producer: pin the expected value as a **committed hex-in-JSON
golden vector** and assert *both* `droppedBytes` and `regeneratedBytes` against
that literal. Neither side is then defined in terms of the other, and it becomes
a real byte-lock under `.claude/rules/no-binary-in-proof-lineage.md` rather than
a determinism check.

**Do NOT raise `registry/check-arity-census.json`.** Registering this would
record a near-vacuous assertion as a legitimate check — the vacuity class
acquiring a permanent home, which is the outcome the census ratchet exists to
prevent.
