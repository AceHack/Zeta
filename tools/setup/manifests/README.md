# `tools/setup/manifests/` — where a new dependency goes

**One line, in the manifest named for the mechanism that installs it.** That is
the whole rule, and it has not changed while `ace` has been growing.

```
tools/setup/manifests/brew        # macOS Homebrew formulae   -> macos.sh
tools/setup/manifests/brew-cask   # macOS Homebrew casks      -> macos.sh
tools/setup/manifests/apt         # Debian/Ubuntu packages    -> linux.sh
tools/setup/manifests/windows     # Windows packages          -> install.ps1
tools/setup/manifests/from-*      # 15 mechanism manifests    -> ace-realize
```

## The halfway state, measured (2026-08-24)

`ace` is mid-adoption, so "does ace handle this?" has different answers per
manifest. Measured rather than assumed — the pointer set is
`tools/setup/ace-mechanism-pointers.json`, generated by
`src/Core.TypeScript/ace/setup-mechanism-pointers.ts`:

| manifest family | declared in | realized by | in ace's pointer set |
|---|---|---|---|
| the 15 `from-*` | `manifests/from-*` | `ace-realize --all` (macos.sh step 6) | **yes** (17 entries) |
| `brew`, `brew-cask`, `apt`, `windows` | `manifests/<name>` | shell loop in `macos.sh` / `linux.sh` / `install.ps1` | **no** |

So the four OS-native package managers are the part that has not moved yet.
There is **no `from-brew.ts`**, and that is the gap — not a missing declarative
surface. The declaration side is already single-source for every mechanism.

**This means there is no duplication to keep in sync.** A dependency is written
down exactly once regardless of which half realizes it; what varies is only the
*consumer*. That is worth stating plainly because the obvious guess — "declare it
in two places until ace lands" — would be the wrong shape and would need a parity
audit that this design does not.

## Why that satisfies `clone-at-tag-stays-sufficient`

The manifests are plain text parsed by `awk`. `macos.sh` and `linux.sh` read them
with no package manager present and no `ace` on `PATH`, so a `git clone` at a tag
still builds. `ace` reading the same files is **additive**: it is the good path,
never the only one (`.claude/rules/clone-at-tag-stays-sufficient.md`, enforced by
`src/Core.TypeScript/hygiene/lint-clone-at-tag-is-sufficient.ts`). Any future
`from-brew.ts` must preserve that — which means it replaces the shell loop rather
than sitting beside it, or the tree acquires two realizers for one manifest.

## Format traps, both learned the hard way

- **`tier=` is brew-only.** `manifests/brew` and `brew-cask` are parsed by
  `zeta_tier_of_line` / `zeta_strip_tier`, so a `tier=slim|standard|full` token
  is understood. `manifests/apt` passes the whole line to `apt-get`, so a `tier=`
  suffix there is read as a version pin and fails with
  `E: Unable to locate package tier` — see `docs/history/pr-reviews/PR-10083-*`.
  Untagged means `tier=slim`, i.e. required on every host.
- **Inline `#` comments are stripped, then the line is trimmed.** A row may carry
  a trailing comment. Verify a new row against the real parser before trusting it:

  ```bash
  awk '{ sub(/#.*$/, ""); gsub(/^[[:space:]]+|[[:space:]]+$/, "") } NF > 0 { print }' \
    tools/setup/manifests/brew | tail
  ```

## A declaration that nothing checks is not a declaration

`manifests/brew` declares `pam-reattach`, and `tools/setup/touchid-sudo.ts`
**reads this manifest** to decide whether the module's absence is drift (RED) or
merely an observation. It parses the row the same way `macos.sh` does, and a test
asserts the real manifest still declares it — so deleting the row fails a test
rather than silently downgrading the check. That is the pattern to copy when a
manifest row is load-bearing for a runtime property.

## Prior art we were modelled on

`../scratch/declarative/` is a **platform × manager × tier** directory matrix of
native `Brewfile`/`.apt` files applied with `brew bundle`, with tiers composed by
`instance_eval` rather than duplicated. `../SQLSharp/scripts/setup/{dev,github,repo}`
decomposes by **consumer role** instead and has no manifest layer at all. Zeta's
shape is a third: one file per mechanism, tier as an inline token. The trade is
explicit — Zeta hand-rolls an `awk` parser that `brew bundle` would provide for
free, and in exchange keeps one uniform format across brew, apt, windows and the
15 `from-*` mechanisms that no single native tool spans. Migrating `brew`/
`brew-cask` to native Brewfile syntax would delete that parser and is a real
option; it is not free, because 26 rows carry per-row rationale that a Brewfile
has nowhere to put. See `docs/backlog/P1/081KSGS9H0008QG0R0031PBNGA-*` (the
N-dimensional platform × manager × tier space) and
`docs/backlog/P1/B-0854-*` (the install.sh -> ace migration trajectory, which
names both repos as the models).
